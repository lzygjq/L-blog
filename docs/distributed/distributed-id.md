# 分布式 ID 的生成方案

这个主题看起来简单——"生成不重复的 ID"，但工程上栽跟头的地方几乎都不在"唯一性"上：

> **唯一性是门槛，不是目标。** 真正决定方案好不好用的，是另外四条隐性要求：趋势递增、生成性能、可用性、以及"传出去之后会不会被改坏"。

## 一、先把需求列全：唯一性只是第一条 {#requirements}

| # | 要求 | 不满足的后果 |
|---|---|---|
| 1 | **全局唯一** | 数据串号、主键冲突。**这是底线，不是优势** |
| 2 | **趋势递增** | 主键随机 → InnoDB **页分裂**、索引碎片、插入性能断崖（见第四节） |
| 3 | **生成性能** | ID 生成在写链路最前端，它慢 1ms，全链路慢 1ms |
| 4 | **高可用** | ID 服务是**全局单点**——它挂了，全系统写不进去（比一般的单点更致命） |
| 5 | **信息安全与长度** | 连续 ID 会**泄露业务量**（"我们才 3000 单"）；过长会撑大索引 |

**第 5 条常被当成"过度设计"，其实很实际**：自增 ID 会暴露"你们一天多少单"，且让人可以**遍历接口**（`/order/1001` 猜 `/order/1002`）——这与[越权防护](/security/authorization#broken-access)是同一个问题。ID 不可枚举本身就是一层安全设计。

**第 4 条值得强调**：ID 生成器是**所有写操作的公共依赖**。它的可用性要求高于任何一个业务服务——业务服务挂了只影响一个功能，ID 服务挂了**整个系统的写入全部停止**。所以"本地生成"（雪花、UUID）相比"远程调用"（Redis INCR、DB 自增）有一个结构性优势：**它不引入新的可用性依赖**。

## 二、方案谱系与时序对照 {#spectrum}

| 方案 | 唯一性 | 趋势递增 | 生成性能 | 外部依赖 | 存储长度 |
|---|---|---|---|---|---|
| **UUID v4** | 概率唯一（碰撞概率可忽略） | ❌ 完全随机 | 极高（纯本地） | 无 | 36 字符 / 16 字节 |
| **UUID v7** | 概率唯一 | ✅ 时间戳前缀 | 极高 | 无 | 16 字节 |
| **数据库自增** | ✅ | ✅ | **低**（每次一次 DB 写） | DB | 8 字节 |
| **多实例步长**（`auto_increment_increment`） | ✅ | ✅ | 中 | DB | 8 字节 |
| **号段模式**（一次取一批） | ✅ | ✅（**段间跳变**） | 高（DB 压力降为 1/N） | DB（偶发） | 8 字节 |
| **Redis `INCR`** | ✅ | ✅ | 中高（一次网络往返） | Redis | 8 字节 |
| **雪花算法** | ✅ | ✅（趋势 ≠ 单调） | **极高**（本地、单机 400 万/秒理论值） | 无（需 `workerId` + 时钟） | 8 字节 |

**这张表的读法**：从下往上，是"**性能与依赖的权衡**"。

- **有外部依赖的方案**（DB、Redis）：天生有一个可用性风险点，但**不依赖时钟**，实现简单；
- **本地生成的方案**（UUID、雪花）：无可用性风险、性能最高，但**要么牺牲有序性（UUID v4），要么依赖时钟（雪花）**。

**UUID v7 是这条权衡线上近年的新答案**：它把 48 位毫秒时间戳放在高位（后接随机位），既保留 UUID 的"无中心、无依赖"，又拿到了趋势递增。**"要么无序、要么依赖时钟"不是必然的**——它是可以绕开的，代价是它仍然是 16 字节、且唯一性靠概率而非机制保证。

## 三、雪花算法：位分配与它的算力上限 {#snowflake}

雪花（Snowflake）是目前业务系统最主流的方案，原因很简单：**8 字节、趋势递增、纯本地生成、无外部依赖**。它的结构：

```text
 63        62 ──────────── 22        21 ──── 12        11 ──────── 0
┌───┬──────────────────────┬──────────────┬──────────────────────┐
│ 0 │  41 bit 毫秒时间戳    │ 10 bit 机器ID │   12 bit 序列号       │
└───┴──────────────────────┴──────────────┴──────────────────────┘
  ↑            ↑                    ↑                 ↑
符号位      约 69.7 年          1024 个节点      同一毫秒 4096 个
（保证正数）                                      
```

**每一位的容量都是算出来的**，不是拍脑袋：

| 段 | 位数 | 容量 | 计算依据 |
|---|---|---|---|
| 符号位 | 1 | 固定 0 | Java 的 `long` 有符号，最高位置 1 会变成负数 |
| 时间戳 | 41 | **≈ 69.7 年** | `2^41 ms ÷ (365×24×3600×1000) ≈ 69.7 年`。**起点要自定义**（如项目启动日），从 1970 算会浪费掉几十年 |
| 机器 ID | 10 | **1024 个** | 通常再拆成 5 位机房 + 5 位机器 |
| 序列号 | 12 | **4096 / 毫秒** | 同一毫秒内的自增计数 |

**单机理论吞吐 = 4096 × 1000 = 约 409.6 万 ID/秒**。这个数字远超任何单机的业务写入能力（受 DB、网络限制），所以**在业务场景下雪花算法几乎不存在性能瓶颈**——它的瓶颈永远在"时钟"与"`workerId`"这两个非性能维度上。

**序列号耗尽时怎么办**：同一毫秒内超过 4096 个请求，必须**自旋等待到下一毫秒**（而不是溢出回绕）。这是实现时的必查点，回绕会立刻产生重复 ID。

**一个必须记住的性质：趋势递增 ≠ 单调递增。**

| | 含义 | 雪花的实际情况 |
|---|---|---|
| **全局趋势递增** | 后生成的 ID 整体上比先前的更大 | ✅ 满足（时间戳在高位） |
| **多机严格单调** | 任意两次生成，后者一定更大 | ❌ **不满足**——1024 个节点的 ID 会交错（A 节点 10:00:00.100 生成的 ID，可能小于 B 节点 10:00:00.099 生成的） |
| **单机严格单调** | 同一节点内严格递增 | ✅ 满足 |

**这个区分关系到业务正确性**：凡是"用 ID 大小推断先后顺序"的逻辑（如"用 ID 做分页游标"、"用 ID 判断是否是新数据"），在多节点场景下都不成立。**需要严格顺序就必须另加一个序列表字段**，不能借用 ID。

## 四、为什么"趋势递增"能救命：页分裂 {#page-split}

这是主键选型里最值钱的一条知识，也是"为什么不用 UUID 做 MySQL 主键"的完整答案。

**InnoDB 的聚簇索引按主键顺序物理存储数据行**。当插入一个主键值落在**已有页的中间位置**时，该页要分裂成两页、搬走一半数据、还要更新父节点指针——这就是**页分裂**：

| 主键类型 | 插入模式 | 页分裂 | 后果 |
|---|---|---|---|
| **自增** | 永远插在最右侧 | 无 | 页始终顺序填满，空间利用率接近 100% |
| **雪花** | **趋势递增**，也基本插在最右侧 | 极少 | 与自增接近 |
| **UUID v4** | **完全随机**，每次落在随机页中间 | **严重且持续** | 空间利用率可能降到 **50%**、索引膨胀、写入变慢、磁盘 IO 放大 |

**"趋势递增"够用的原因**：避免页分裂只需要"**新值比绝大多数已有值大**"，不需要"严格单调"。雪花满足这一点（时间戳在高位且单调），所以它能拿到与自增大体相同的插入性能。

**还有一层容易被忽略的代价**：**InnoDB 的每个二级索引叶子节点存的都是主键值**。所以主键长度会被放大到**所有二级索引**上：

```text
一张表有 3 个二级索引：
  主键 8 字节（BIGINT）  → 每个二级索引项都多 8 字节
  主键 36 字节（UUID）   → 每个二级索引项多 36 字节，索引体积膨胀 4~5 倍
→ 索引越大，一次查询要读的页越多，缓冲池命中率越低
```

**这解释了为什么 UUID 的问题"不止是插入慢"**：它的代价会渗透到**所有查询**的性能上。

## 五、时钟回拨：雪花算法的唯一真问题 {#clock-drift}

雪花依赖"当前时间毫秒"，而生产环境的时钟**不保证单调**：

| 回拨原因 | 典型场景 |
|---|---|
| **NTP 校时** | 机器时钟略快，NTP 一次把它"拨回来"几毫秒到几秒 |
| **虚拟机/容器迁移** | 热迁移后时钟与宿主对齐 |
| **人工改时间** | 运维误操作、时区配置错误 |
| **闰秒 / 时钟源抖动** | 少见的边界情况 |

**回拨为什么危险**：若当前时间 `now` 小于上次生成用的 `lastTimestamp`，序列号会**从 0 重新开始**，而这个毫秒的 ID 之前已经生成过了 → **直接产生重复 ID**。

### 五种处理策略对照 {#clock-strategies}

| 策略 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **小幅自旋等待** | 回拨 < 阈值（如 5ms）时自旋等到时间追上 | 该次调用阻塞几毫秒 | **最常见的首选**，多数回拨都是小幅 NTP 调整 |
| **小幅回拨 + 序列号补偿** | 不等待，把回拨量并入序列号位（相当于"这台钟慢了几毫秒"） | 序列号位被占用，上限下降 | 对延迟敏感且回拨可预测 |
| **抛异常 / 拒绝服务** | 检测到回拨立即报错 | 该节点暂时不可用，**需要业务能重试** | 对唯一性零容忍的场景 |
| **切换备用 `workerId`** | 预留若干 `workerId`，回拨时切到一个"上次生成时间更早"的 ID | 需预留机器位，`workerId` 消耗快 | 有充足机器位余量 |
| **直接忽略、按新时间生成** | —— | **会产生重复 ID** | ❌ **绝不可用** |

> **工程上的正解通常是"组合拳"**：小幅回拨自旋等待（覆盖 95% 的 NTP 微调）+ 超过阈值就**告警并拒绝服务**（把问题暴露出来，而不是悄悄生成重复 ID）。同时**部署 NTP 时避免大幅跳变**（用 `ntpd` 的渐进调整而非 `ntpdate` 的跳跃式校时）。
>
> 业界方案可以对照看：**美团 Leaf-snowflake** 在启动时校验 `workerId` 与时间、运行中把时间戳周期上报到 ZooKeeper，回拨时告警；**百度 UidGenerator** 走另一条路，用 RingBuffer 预生成 + **"借用未来时间"**，把时钟问题转化为缓存容量问题。

### `workerId` 分配：容器化时代的真正难点 {#worker-id}

`snowflake` 的 10 位机器 ID 必须**全局唯一**，而在容器/云环境下这个前提很容易被打破：

| 分配方式 | 问题 |
|---|---|
| **手工配置** | 节点一多必然配重（而且往往在扩容时才发现） |
| **取 IP 末位**（如 `IP & 1023`） | **容器重启后 IP 会变**；不同宿主机上的容器可能撞号 |
| **K8s `StatefulSet` 序号** | 可靠（序号稳定且唯一），但要求用 StatefulSet 而非 Deployment |
| **Redis `INCR` / etcd 注册** | 可靠，且能回收失效节点，但**引入了原本想避免的外部依赖** |
| **ZK 持久顺序节点** | 老牌做法（Leaf 用的就是它），效果同上 |

**这里的取舍值得想清楚**：**用外部注册中心分配 `workerId`，等于把"本地生成"降级成了"启动时依赖外部"**——好在它只在**启动时**依赖，运行期不依赖，比"每次生成都调远程"好得多。所以这个代价是**可接受的**，且通常比"手工配"更可靠。

## 六、精度陷阱：Long 型 ID 传到前端会丢精度 {#js-precision}

这是**最容易在生产上炸、又最容易在测试时漏掉**的一条：

```text
JavaScript 的 Number 是双精度浮点，安全整数范围只有 ±(2^53 - 1)
雪花 ID 是 64 位 long，典型值约 19 位十进制数（超过 2^53 ≈ 9.007×10^15）

→ 前端 JSON.parse 后 【末几位变成 0】或产生误差
→ 用这个 ID 再回调查询/删除 → 查不到、删不掉、甚至删错
```

**关键特征：服务端日志里的 ID 完全正确，只有前端拿到的错。** 后端自测、Postman 自测（Postman 也可能受影响）、单元测试全都发现不了。

**解法（按推荐度）**：

| 做法 | 说明 |
|---|---|
| **序列化为字符串** | 全局配置（如 Jackson 对 `Long` 统一序列化为 `String`），或对 ID 字段加注解。**一次配好，全站生效** |
| 前端用 `BigInt` | 可行但要求前端全链路替换（`BigInt` 不能与 `Number` 混算，JSON 也不原生支持） |
| 前端引 `json-bigint` | 只处理解析层，容易漏掉某些请求库 |

> **⚠️ 一个更彻底的做法**：**对外暴露的 ID 与内部主键解耦**——外部用字符串化的 ID 或短码，内部主键仍是 `long`。这样连"ID 可枚举"的安全问题也一并解决。

## 七、常见坑 {#pitfalls}

| 坑 | 正确认识 |
|---|---|
| **时钟回拨不处理** | 会产出**重复 ID**。必须检测 `now < lastTimestamp` 并至少告警 |
| **序列号回绕而非等待** | 同一毫秒超 4096 个时必须**自旋到下一毫秒**，回绕即重复 |
| **`workerId` 在容器里取 IP** | 容器重启 IP 变化、跨宿主机可能撞号 → 生产事故的经典来源 |
| **用 ID 大小判断先后顺序** | 雪花是**趋势递增**不是**严格单调**，跨节点不可比（见第三节） |
| **用 UUID 做 InnoDB 主键** | 页分裂 + 二级索引全面膨胀（见第四节）。若一定要用，选 **UUID v7** 而非 v4 |
| **号段模式的段间隔被当成 bug** | 号段模式本来就是"段内连续、段间跳变"，**不要假设 ID 连续**（如"订单号连号"这种需求它满足不了） |
| **号段模式的 DB 成单点** | 号段耗尽的瞬间若 DB 不可用，**立即无号可发**。要用**双 Buffer 预取**，在上一段用掉一定比例时就异步取下一段 |
| **时间戳起点用 1970** | 白扔掉几十年容量。应从业务启动时间起算 |
| **忘记 ID 不可枚举的安全含义** | 连续自增 ID 会泄露业务量、且可被遍历猜测（见第一节第 5 条） |

## 面试口径 {#interview}

- **选型五要求**：全局唯一（底线）、**趋势递增**（关系型主键必需）、生成性能、**高可用**（ID 服务挂 = 全系统写不了）、信息安全与长度。
- **雪花位分配**：`1 位符号 + 41 位毫秒时间戳（≈69.7 年）+ 10 位机器 ID（1024）+ 12 位序列号（4096/ms）`，单机理论 **约 409.6 万 ID/秒**。时间戳**起点要自定义**。
- **趋势递增 ≠ 单调递增**：雪花满足全局趋势递增与单机单调，但**跨节点不单调**（多节点 ID 交错）。所以**不能用 ID 大小推断先后顺序**。
- **为什么趋势递增就够**：InnoDB 只要求"新值基本落在最右侧"以避免**页分裂**。UUID v4 随机插入 → 页分裂 + 空间利用率降到约 50%；**且主键长度会放大到所有二级索引**（二级索引叶子存主键）。
- **时钟回拨**：NTP 校时/迁移/改时间是主因。核心危险是**序列号重置导致重复 ID**。策略：**小幅自旋等待（首选）+ 超阈值告警拒绝**；不可用"直接忽略"。业界参考 Leaf-snowflake（ZK 上报 + 告警）、UidGenerator（RingBuffer + 借用未来时间）。
- **`workerId` 分配**：10 位必须全局唯一。手工配易重、取 IP 在容器下不可靠；推荐 **K8s StatefulSet 序号**或**Redis/etcd/ZK 注册**——**只在启动时依赖外部**，运行期仍是纯本地生成。
- **精度陷阱**：雪花 ID 超 JS 安全整数 `2^53-1`，前端会丢末几位。**服务端日志正常、只有前端错**，测试极易漏。解法是**全局把 `Long` 序列化为字符串**。
- **号段模式**：一次取一段缓存本地，DB 压力降为 1/N；**段内连续、段间跳变**，必须配**双 Buffer** 防止取号阻塞。
- **延伸**：分片主键为何用雪花见[分库分表](/database/sharding/#主键避重为什么是雪花算法)；数据如何按 ID 分布见[数据分布](/distributed/data-partition)；ID 可枚举的安全含义见[授权与越权](/security/authorization#broken-access)。
