# 分布式锁：三种实现的语义差异与 fencing token

分布式锁是"协调服务"里被用得最多、也最容易被用错的一个原语。用错的根源通常不是实现细节，而是搞错了它的能力边界：

> **锁能保证的是"同一时刻只有一个人认为自己持有锁"，它不能保证"失去锁的人停止动作"。**

前半句是锁服务能提供的；后半句**只能由被保护的资源来保证**。把这两句分开，本文后面的所有结论都能自己推出来。

## 一、先问：这个场景真的需要分布式锁吗 {#do-you-need}

真实项目里"上一把分布式锁"的需求，**七成以上是杀鸡用牛刀**：

| 场景 | 第一反应 | 更合适的做法 |
|---|---|---|
| 防重复提交 | 分布式锁 | **唯一索引**——一次 `INSERT` 就是原子的 |
| 状态机流转（已支付 → 已发货） | 分布式锁 | `UPDATE ... SET status='已发货' WHERE id=? AND status='已支付'`，**看影响行数** |
| 库存扣减 | 分布式锁 | `UPDATE stock SET n = n - 1 WHERE id=? AND n > 0`，或 Redis 原子操作 |
| 并发更新同一行 | 分布式锁 | 乐观锁版本号 / 悲观锁 `FOR UPDATE` |
| 缓存与数据库一致性 | 分布式锁 | 延迟双删 / 订阅 binlog（见 [Redis 缓存模式](/database/redis/cache-patterns)） |

**判据只有一句：竞态的对象是"你自己数据库里的一行"，还是"外部资源"？**

- 是**自己库里的一行** → 数据库的原子语句、唯一索引、行锁就够了，**不要引入外部依赖**（引入意味着多一个故障域，还多一段网络延迟）。
- 是**外部资源**（调第三方 API 时限制并发、操作同一个文件或设备、对一个不支持事务的系统做"读-改-写"）→ 这时才真需要一把外部锁。

## 二、三种实现：互斥分别是怎么保证的 {#three-ways}

| | **Redis** | **ZooKeeper** | **etcd** |
|---|---|---|---|
| 加锁动作 | `SET key uniqId NX PX 30000` | 在锁目录下创建**临时顺序节点** | `lease + txn`（比较 `create_revision == 0` 后写入） |
| 互斥依据 | `NX` 的原子性 | **序号最小者持锁** | txn 的 compare-and-put |
| 释放机制 | 显式 `DEL`，**或 TTL 到期** | **会话结束自动删除**（也可显式删） | 显式删，**或 lease 到期** |
| 等待公平性 | 无队列，靠重试（**可能饿死**） | **天然 FIFO**：只 watch 排在自己前面的那个 | 官方 `concurrency` 包用 revision 排序，接近 FIFO |
| 可重入 | 需自己实现（存持有者 + 计数） | 需自己实现 | 需自己实现 |
| 故障检测 | **TTL 到期**（时间到就删，不区分死没死） | **会话超时**（心跳缺失才判定） | **lease 到期**（需客户端 keepalive 续约） |
| 是否会"双持有" | **会**（见下节三个坑） | 会（会话超时的窗口） | 会（lease 超时的窗口） |

三段最典型的代码形态：

```bash
# Redis：加锁
SET lock:order-42 <uniqId> NX PX 30000

# Redis：释放 —— 必须比对 uniqId 再删，不能直接 DEL
# （否则会删掉别人后来加上的锁）
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
```

```text
ZooKeeper：锁目录下的结构
/locks/order-42/
├── lock-0000000000   ← 序号最小者持锁（临时顺序节点）
├── lock-0000000001   ← 只 watch 0000，0000 消失时才轮到我
└── lock-0000000002   ← 只 watch 0001
```

```java
// etcd：lease + txn，官方 concurrency 包已封装
// 关键点：加锁成功后必须持续给 lease 续约（KeepAlive），否则租约一到期锁就没了
```

## 三、Redis 锁的三个坑 {#redis-pitfalls}

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | **过期时间两难** | 设短了，业务还没跑完锁就过期；设长了，宕机后别人要等很久 | 业务侧续约（看门狗）；但**续约只能说明"客户端自认为还在跑"，不是多数派见证的存活** |
| 2 | **主从切换丢锁** | 主节点写入了锁但还没同步给从节点就挂了 → 新主上没有这把锁 → **两个持有者** | 单实例 Redis 无法根治；这是 RedLock 想解决的问题（见下） |
| 3 | **误删别人的锁** | 直接 `DEL key`，把别人加的锁删了 | 值里放唯一标识，**用 Lua 比对后再删** |

### 3.1 RedLock 的争议，以及它的正确定位 {#redlock}

RedLock 的思路是"**同时向 N 个独立的 Redis 主节点加锁，多数成功才算成功**"，试图用多数派抵消主从切换丢锁的问题。它长期有争议，主要论点可以这样记：

| 批评方向 | 内容 |
|---|---|
| **时钟假设** | RedLock 的活性依赖各节点时钟以相近速率前进；而分布式系统里**时钟漂移是常态**，不能用它做安全性假设 |
| **解决错了问题** | 主从切换只是"双持有"的一条路径；**GC 停顿 / 网络分区导致的过期，RedLock 一样防不住** |
| **工程收益有限** | 引入 N 个独立主节点，运维成本大幅上升，而它防的场景可以用 fencing 更便宜地覆盖 |

**正确的定位**：RedLock 是一个**在特定故障模型下有争议的工程折中**，不是"分布式锁的标准答案"。落地上更稳的两条路是——

1. 用**带续约的 redis 锁 + 资源端 fencing**（绝大多数业务场景够了）；
2. 要求锁的语义更硬 → 直接用 **etcd / ZooKeeper**。

## 四、ZK / etcd 锁：更"正确"，但有它自己的代价 {#zk-lock}

ZK 锁的两条优势是实打实的：

| 优势 | 说明 |
|---|---|
| **公平队列** | 临时顺序节点天然 FIFO，且"只 watch 前一个"**避免了所有等待者同时被唤醒的羊群效应**（见 [Watcher 的羊群效应](/distributed/coordination/zookeeper-model#herd)） |
| **感知更快** | 会话超时默认窗口是 4~40s，比"业务猜一个 TTL"更靠谱；且释放是**服务端判定**，不依赖客户端主动删 |

但**它的代价也恰好在"会话"上**：

```text
ZK 锁最危险的一幕：
  持有者发生长 GC 停顿
   → 心跳发不出去
   → 会话超时（服务端认为它死了）
   → 临时节点被删、锁释放
   → 另一个客户端拿到锁并开始写
   → 原持有者从 GC 中恢复，它并不知情，继续写
   → 同一时刻两个写者
```

**关键认知**：这不是 ZK 的实现缺陷，而是"**用超时来判断存活**"这件事的固有缺口。`etcd` 的 lease 完全一样。**换掉锁服务不能解决它**——只能在资源端解决。

## 五、fencing token：把"锁的正确性"补完 {#fencing}

### 5.1 缺口的本质 {#fencing-why}

把上一节那一幕抽象出来：

> 任何一个用"超时/租约"判断过期的锁，都存在一个窗口：**旧持有者已经失去锁，但它自己还不知道，并且它的写入仍然有效。**

所以真正的命题是：**怎么让已经失去锁的那个人的写"作废"？**

答案是给每次获取锁附上一个**单调递增的令牌（fencing token）**，并在**写入资源时带上它**；资源端**只接受比"已见过的最大值"更大的令牌**。

### 5.2 令牌从哪来 {#fencing-source}

| 系统 | 天然单调量 | 说明 |
|---|---|---|
| **ZooKeeper** | 节点的 `zxid` / `cversion`，或顺序节点的序号 | zxid 全局单调，最直接 |
| **etcd** | KV 的 `mod_revision` / txn 的 `revision` | 每次写全局递增 |
| **Redis** | 单独的 `INCR` 计数器 | 需要额外一次调用，且主从切换下也可能回退——**这是 Redis 做 fencing 的弱点** |
| **数据库** | 自增序列 / 行版本号 | 被保护资源本身就在数据库时最自然 |

### 5.3 一个具体的时序 {#fencing-timeline}

| 时刻 | client-1 | client-2 | 资源端记录的 `maxToken` |
|---|---|---|---|
| T0 | 获取锁 → token = 33；写一次 | | 33 |
| T1 | **GC 停顿 30s**（进程没死） | | — |
| T2 | 会话 / 租约超时 → 锁被释放 | | — |
| T3 | | 获取锁 → token = 34；写入 | **34** |
| T4 | 恢复，仍以为自己持锁，**写入 token = 33** | | `33 < 34` → **拒绝** |

**T4 那一行的拒绝，就是全部收益。** 没有 fencing，T4 会成功执行，数据被改写。

### 5.4 代价与替代方案 {#fencing-cost}

fencing 不是免费的，它要求**被保护的资源支持校验令牌**：

- 数据库表加一列 `fence_token`，写入时带 `WHERE fence_token < ?` 的守卫；
- 对象存储 / 文件系统用"条件写 + 版本号"；
- 对外部 API 则通常做不到——**这时要换思路**。

**做不到 fencing 时的两条退路**：

1. **把操作变成幂等的**——重复执行不产生副作用，那"两个写者"就退化成"多算一次"；
2. **把超时窗口调得远大于最大停顿**——只是降低概率，**不是修复**，且会让故障恢复变慢。

> **工程上的判断顺序应该是**：① 能不能不做分布式锁（第一节）→ ② 能不能让操作幂等（这条最便宜）→ ③ 能不能做 fencing → ④ 才去纠结锁服务的选型。

## 六、选型判据 {#selection}

| 场景 | 建议 | 理由 |
|---|---|---|
| 短临界区、可容忍极小概率重入、已有 Redis | **Redis 锁 + 唯一标识 + 续约** | 最轻，吞吐最高；**必须配幂等或 fencing** |
| 需要公平排队、不饿死 | **ZK / etcd 锁** | 顺序节点天然 FIFO |
| 需要长期持有（选主、单写者任务） | **ZK / etcd 的临时节点 / lease** | 长 TTL 在 Redis 上是反模式 |
| 只有"防重复"这一件事 | **不要用锁** | 唯一索引/幂等表更简单也更可靠 |
| 资源不支持校验令牌，且必须绝对互斥 | **改用"单写者 + 队列"** | 把并发从"抢锁"改成"排队"，从根上避开超时窗口 |

**三句收口**：

1. **能不用就不用**——数据库的原子操作能解决的问题，不要引入第二个故障域。
2. **用就带上 fencing**——否则你拿到的是"大概率互斥"，不是互斥。
3. **锁的正确性最终由被保护的资源决定**，与锁服务是 Redis 还是 ZK 关系不大。

## 七、面试口径 {#interview}

- **分布式锁的能力边界**：锁能保证"同一时刻**只有一个人认为自己持有锁**"，**不能保证"失去锁的人停止动作"**。后半句只能由被保护的资源（fencing / 幂等）保证。
- **什么时候不需要分布式锁**：竞态对象是"自己库里的一行"时——防重复提交用唯一索引、状态流转用带条件的 `UPDATE` 看影响行数、库存扣减用 `n = n - 1 WHERE n > 0`。**引入外部锁等于多一个故障域**。
- **三种实现的互斥依据**：Redis 靠 `SET NX` 的原子性；ZK 靠**临时顺序节点的序号最小者**；etcd 靠 `lease + txn` 的 compare-and-put。
- **Redis 锁的三个坑**：① 过期时间两难（短了业务没完、长了恢复慢）→ 续约；② **主从切换丢锁**（主写了锁还没同步就挂）→ 两个持有者；③ **直接 `DEL` 误删别人的锁** → 值里放唯一标识、Lua 比对后再删。
- **RedLock 怎么定位**：它试图用"N 个独立主节点 + 多数成功"抵消主从切换丢锁，但**活性依赖各节点时钟以相近速率前进**（分布式系统里不可靠），且**解决不了 GC 停顿导致的过期**。结论：它是一个**有争议的工程折中，不是标准答案**。
- **ZK / etcd 锁的优势与代价**：优势是**天然 FIFO 且无羊群效应**（只 watch 前一个）、释放由服务端按会话判定；代价是**长 GC 停顿会让会话超时、锁被释放而自己不知情**——这与 Redis 的 TTL 是**同一个缺口的两种表现**。
- **fencing token 解决什么**：让"已经失去锁的旧持有者"的写入**作废**。做法是获取锁时拿一个**单调递增令牌**，写入时带上，**资源端只接受比已见最大值更大的令牌**。ZK 用 `zxid`、etcd 用 `revision`、Redis 用 `INCR`。
- **fencing 的代价**：要求资源端支持校验（表加一列 + 条件写）。做不到时的退路是**把操作幂等化**，或把超时窗口调到远大于最大停顿——**后者只是降低概率，不是修复**。
- **正确的判断顺序**：① 能不能不做锁 → ② 能不能幂等 → ③ 能不能 fencing → ④ 才选锁服务。**绝大多数人从第 4 步开始，这就是问题所在。**
