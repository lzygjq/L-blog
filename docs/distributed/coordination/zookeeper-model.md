# ZooKeeper 数据模型：znode、会话与 Watcher

ZooKeeper 对外只有三个概念：**一棵树（znode）、一次连接（会话）、一个通知（Watcher）**。三者的关系是——

> **会话决定"谁还在"，znode 决定"谁占了位置"，Watcher 决定"变化多久传到"。**

理解这三句，就理解了 ZK 能做什么、以及它的每一个坑来自哪。

## 一、znode：既是文件，也是目录 {#znode}

znode 是树上的一个节点，它同时承担两个角色：自己可以带一小段数据（像文件），也可以有子节点（像目录）。**没有"纯目录"和"纯文件"的类型区分**——所有 znode 都能两样都做。

```text
/
├── services                          ← 持久节点：命名空间根
│   ├── order-api
│   │   ├── 10.0.1.7:8080             ← 临时节点：在不在由「会话」决定
│   │   └── 10.0.1.8:8080
│   └── pay-api
├── config
│   └── rate-limit                    ← 持久节点，data 里放配置内容
└── locks
    └── daily-reconcile
        ├── lock-0000000000           ← 临时顺序节点：序号最小者持锁
        ├── lock-0000000001
        └── lock-0000000002
```

### 1.1 四种节点类型 {#znode-types}

| 类型 | 生命周期 | 名字 | 用途 |
|---|---|---|---|
| **持久（PERSISTENT）** | 一直存在，除非显式删除 | 指定 | 配置、命名空间骨架 |
| **临时（EPHEMERAL）** | **绑定会话**，会话结束即自动删除 | 指定 | 成员管理、选主、存活标志 |
| **持久顺序（PERSISTENT_SEQUENTIAL）** | 一直存在 | 系统在路径后追加 10 位递增序号 | 需要稳定顺序的队列、任务编号 |
| **临时顺序（EPHEMERAL_SEQUENTIAL）** | 绑定会话 | 同上 | **分布式锁**、公平排队（最常用的一种） |

两个容易忽略的点：

- **临时节点不能有子节点。** 所以想表达"某个服务的实例列表"时，结构必须是「持久节点 `/services/order-api`」+「它的临时子节点是各实例」，而不是把实例做成持久节点。
- **序号是父节点下的计数器**，全局唯一但不连续（有删除就会跳号），所以**不能用序号做计数**，只能用它排序。

### 1.2 约 1MB 的硬上限，以及为什么不该调大 {#znode-limit}

单个 znode 的数据大小上限由 `jute.maxbuffer` 决定，**默认 `0xfffff`（1048575 字节，约 1MB）**。这个值可以调，但官方文档的态度很明确：

> ZooKeeper **就是用来存千字节量级数据的**（`designed to store data on the order of kilobytes`），生产环境不建议把 `jute.maxbuffer` 调到默认值以上。

原因是**大 znode 会连锁伤害整个集群**，而不只是那一个节点变慢：

| 后果 | 机制 |
|---|---|
| 延迟尖刺、吞吐下降 | 每次读都要把 value 完整传输与反序列化，占满处理线程 |
| **Leader 与 Follower 的同步时间不可预测** | 快照/日志里出现大条目后，同步时间可能**不收敛**（超时），进而**影响 quorum 稳定性** |
| 客户端与服务端的配置必须一致 | 两边不一致时报错很隐晦：**客户端大于服务端** → 服务端报 `Len error`；**客户端小于服务端** → 客户端报 `Unreasonable length or Packet len is out of range!` |

> **面试里这一条很值钱**：问"ZK 能存多大的数据"，答"1MB"只是背了个数字；答"**约 1MB，而且这个上限的本质目的是保护 quorum 的稳定性——大 znode 会让 Leader/Follower 同步不收敛，进而动摇 quorum**"，才是理解了它为什么必须小。

### 1.3 stat：每个 znode 都带的版本号 {#stat}

每个 znode 有一份元数据（`stat`），其中三个版本号是**做 CAS 与 fencing 的基础**：

| 字段 | 含义 | 用途 |
|---|---|---|
| `version` | 该节点 **data** 被修改的次数 | `setData` 可带期望版本 → 乐观锁 |
| `cversion` | 该节点 **子节点列表** 变更的次数 | 成员变更的单调依据 |
| `aversion` | 该节点 **ACL** 变更的次数 | 权限审计 |
| `czxid` / `mzxid` | 创建 / 最后修改的 zxid | **单调递增**，可当 fencing token（见[分布式锁](/distributed/coordination/coordination-lock#fencing)） |
| `ephemeralOwner` | 临时节点的所属会话 id；持久节点为 0 | 排查"这个节点是谁建的、怎么还没删" |

## 二、会话：崩溃感知为什么"自动"发生 {#session}

**会话是把"一个进程还活着"这件事变成一个可被协调服务判定的状态。** 它由三部分构成：

| 组成 | 说明 |
|---|---|
| **session id** | 服务端分配的 64 位标识，**同一会话内重连后不变** |
| **超时时间** | 由 `tickTime` 的倍数决定：下限 `2 × tickTime`、上限 `20 × tickTime`；`tickTime` 默认 2000ms → **下限 4s、上限 40s** |
| **心跳** | 客户端按 `tickTime/3` 左右自动发 ping；服务端每收到一次就刷新过期时间 |

会话一旦过期，服务端做的事是**原子的**：把这个 session id 名下的**所有临时节点一并删除**。这就是"成员管理不需要写清理代码"的原因。

### 2.1 三个必须记住的边界 {#session-limits}

**① 感知不是即时的，最长要等一个会话超时。**

进程真的崩了，ZK 也要等超时才认定——所以**故障感知延迟 ≈ 会话超时**。这就是"不能把 ZK 当秒级健康检查用"的原因。

**② 超时判定区分不出"死了"和"卡住了"。**

这是 ZK 最危险的一类事故：

```text
10:00:00  client-1 拿到锁（临时节点 lock-0000000000）
10:00:05  client-1 进入长 GC 停顿 30s        ← 进程没死，只是被暂停了
10:00:12  会话超时 → ZK 删除 client-1 的临时节点 → 锁释放
10:00:13  client-2 拿到锁，开始写
10:00:35  client-1 从 GC 中恢复                  ← 它以为自己还持有锁
10:00:36  client-1 继续写                        ← 同一时刻两个写者
```

**注意结论**：这不是"ZK 有 bug"，而是**任何基于超时的租约都有这个窗口**——Raft 的 term、etcd 的 lease 完全一样（参[误判的代价：脑裂与 fencing](/high-availability/redundancy-failover#split-brain)）。**唯一的正解是在被保护的资源上做 fencing，而不是在锁服务上调参数。**

**③ 分区中的节点读得到、写不了。**

ZK 有一个默认关闭的 **Read Only Mode**（`readonlymode.enabled`）：开启后，与 quorum 失去连接的服务端仍可为**声明支持 ROM 的客户端**提供读，但写不了、也看不到其他客户端的新写入。它的价值是"分区期间读操作不全部失败"，代价是**你读到的是可能过期的数据**——用之前必须先回答"这里的读错了会怎样"。

## 三、Watcher：三个特性决定三种正确用法 {#watcher}

Watcher 是"一次性触发器"。它有三个特性，**每一个都对应一类典型的错误用法**：

| 特性 | 准确含义 | 错误用法 |
|---|---|---|
| **一次性** | 触发后立即失效，**必须重新注册** | 注册一次就不管了，之后的变化全部收不到 |
| **客户端本地触发，通知不含数据** | 服务端只发"你关注的那个节点变了"这一个信号，**不告诉你变成什么** | 把通知当结果直接用；不知道必须"收到通知 → 再去读一次" |
| **不保证看到每一次变化** | 只保证"**若数据在 watch 有效期内变过，你会至少收到一次通知**"；中间态会被合并跳过 | 做变更流水、审计日志、计数器 |

### 3.1 正确姿势：「注册 + 读取」必须在同一次调用里完成 {#watcher-pattern}

ZK 的读取 API 把这两件事合成了一次原子操作：

```java
// getData(path, watch, stat)：一次调用同时完成「注册 watcher + 读取数据」
// 关键：watcher 与数据来自同一个快照点，不会漏掉两者之间的变更
Stat stat = new Stat();
byte[] data = client.getData("/config/rate-limit", true, stat);

// 用 stat.getVersion() 做乐观锁更新（CAS）
client.setData("/config/rate-limit", newData, stat.getVersion());
```

**为什么必须这样写**：如果先 `getData(path, false, ...)` 读一次，再单独注册 watcher，那么**"读"与"注册"之间发生的变更会被永久漏掉**——这是 ZK 使用中最经典的 bug，且在小流量环境里几乎测不出来。

### 3.2 羊群效应：一个节点挂几千个 watch {#herd}

默认做法"所有实例都 watch 同一个父节点"在实例数变多后会出事：

```text
    /services/order-api  ← 2000 个客户端同时 watch 这一个节点
             │
      有一个实例上下线
             │
             ▼
    2000 个通知同时下发 → 2000 个客户端同时 → 同时读 + 同时重新注册
             │
             ▼
    瞬时打到 ZK 的请求量 = 实例数的平方级放大
```

**解法是"只关注前一个"**：不给所有人 watch 同一个节点，而是让每个等待者**watch 排在它前面的那一个**（临时顺序节点的天然结构）。这样一次变化只会唤醒一个等待者，而不是全体。

### 3.3 新版本的两处改进 {#watcher-versions}

| 改进 | 从哪个版本 | 解决了什么 |
|---|---|---|
| **持久 watcher / 持久递归 watcher**（AddWatch API） | 3.6.0 | 不必每次"收到通知再注册一次"，监听可以跨事件存活；递归模式一次注册可覆盖整棵子树。同一路径上还能并存不同模式的 watch |
| **WatchEvent 携带触发它的 `zxid`** | **3.9.0** | 以前"收到通知但不知道对应哪个版本"，只能重新读一次去猜；带上 `zxid` 后**可以和自己已经处理到的位置做对账** |

> 这两条都是"工程体验"层面的补强，**没有改变前面三个特性的语义**——一次性（对普通 watch 而言）与"不保证每次变化"依然成立。别因为 API 变好用了就把它当消息队列。

## 四、四种协调原语的 znode 结构骨架 {#recipes}

把上面的三件套组合起来，就是六种原语里最常用的四种。**结构定下来，行为就定下来了**：

| 原语 | znode 结构 | watch 挂在哪 | 关键点 |
|---|---|---|---|
| **成员管理** | `/group/member-0000000001` 等，**临时顺序** | 父节点的 **children** | 序号只用来排序，会跳号；成员表 = children 列表 |
| **选主** | 同上，**序号最小者为 Leader** | 父节点的 children（或只 watch 前一个） | 主挂 → 临时节点消失 → 次小者自动接任 |
| **分布式锁（公平）** | `/lock/x-0000000000` 起，**临时顺序** | **只 watch 排在自己前一个** | 天然 FIFO 队列，避免羊群效应；释放 = 删自己的节点 |
| **屏障 / 分配** | `/barrier/task-0000000000` 起，**临时顺序** | 父节点 children | 先到者拿小序号 → 顺序分配任务 |

> **一个反直觉但重要的推论**：这四种原语都**不存业务数据**，只存"位置"。所以 ZK 的容量上限（1MB/节点、节点总数）**几乎从不成为瓶颈**——真正的瓶颈永远是**写吞吐**与**watch 数量**。这也解释了为什么它是"协调"服务而不是"存储"服务。

## 五、面试口径 {#interview}

- **znode 是什么**：树上的一个节点，**同时是文件也是目录**——没有类型区分，谁都能带数据、谁都能有子节点。
- **四种节点类型**：持久、临时、持久顺序、临时顺序。**临时节点绑定会话，且不能有子节点**——所以"服务实例列表"的正确结构是「持久父节点 + 临时子节点」。
- **ZK 单节点能存多大**：`jute.maxbuffer` 默认**约 1MB**（`0xfffff`）。官方口径是"它就是用来存千字节量级数据的"，**不建议调大**——大 znode 会让 Leader/Follower 同步时间不收敛，进而**动摇 quorum**。客户端与服务端配置不一致时，报错是 `Len error`（客户端大）或 `Unreasonable length`（客户端小）。
- **会话为什么重要**：把"进程还活着"变成服务端可判定的状态。会话过期时，**该会话名下的所有临时节点被原子地一并删除**——这是"崩溃自动清理"的全部来源，所以**故障感知延迟 ≈ 会话超时**。
- **GC 停顿会发生什么**：进程没死但续约不上 → 会话过期 → 锁被释放 → 第二个持有者进来 → 原持有者恢复后继续写 → **两个写者**。**这是所有基于超时的租约的共有缺口**，只能在资源端用 **fencing token** 兜住，调大会话超时只是减小概率。
- **Watcher 的三个特性**：**一次性**（触发即失效，要重新注册）、**客户端本地触发且通知不含数据**（必须"收到通知再去读"）、**不保证看到每一次变化**（中间态会被合并，不能当变更流水）。
- **为什么必须「注册 + 读取」一次完成**：`getData(path, true, stat)` 把注册与读取放在同一个快照点；分成两步会在"读完之后、注册之前"漏掉变更，且**小流量下几乎测不出来**。
- **羊群效应怎么解**：不让所有人 watch 同一个热点节点，改成**每个等待者只 watch 排在自己前面的那一个**（临时顺序节点的结构天然支持），一次变化只唤醒一个等待者。
- **Read Only Mode 是什么**：与 quorum 失联的服务端仍可提供**读**（需客户端声明支持），但不可写、也看不到新写入。价值是分区期间读不整体失败，代价是**可能读到过期数据**。
- **延伸**：ZAB 协议如何保证顺序见 [ZAB 协议](/distributed/coordination/zab-protocol)；锁的完整语义与 fencing 见[分布式锁](/distributed/coordination/coordination-lock)；集群规模与磁盘要求见[协调服务选型](/distributed/coordination/coordination-selection#zk-ops)。
