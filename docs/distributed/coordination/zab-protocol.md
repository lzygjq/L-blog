# ZAB 协议：ZooKeeper 为什么不直接用 Raft

ZAB（ZooKeeper Atomic Broadcast）和 Raft 同族：都是 **Leader + 多数派 + 逻辑任期**。所以常有人问"既然 Raft 更简单，ZooKeeper 为什么不换"。

一句话回答：

> **ZAB 与 Raft 的差别不在"能不能做到"，而在"把什么当成第一公民"——ZAB 面向"一段历史"，Raft 面向"一条日志"。**

这个差别推下去，就得到 ZAB 最有辨识度的设计：**它把"选主"和"正常广播"做成了两套独立的机制**。

## 一、两个模式：恢复与广播 {#modes}

```text
               ┌──────────────────────────────┐
               │   恢复模式（Recovery）        │  ← 选主 + 对齐历史
               │   只在"换届"时进入            │
               └──────────────┬───────────────┘
                              │ 历史对齐、新 Leader 就位
                              ▼
               ┌──────────────────────────────┐
               │   广播模式（Broadcast）       │  ← 正常写入
               │   类两阶段提交                │
               └──────────────┬───────────────┘
                              │ Leader 失联 / 失多数派
                              └──────────▶ 回到恢复模式
```

| | ZAB | Raft |
|---|---|---|
| 机制数量 | **两套**：恢复阶段（选举 + 同步）与广播阶段 | **一套**：靠 `term` 一个变量贯穿选举与复制 |
| 恢复阶段的产物 | 一个**已完成历史对齐**的 Leader（对齐是选举的组成部分） | 一个新 Leader（对齐靠之后的日志匹配逐步做） |
| 广播阶段的前提 | 必须**先提交一条 NEW_LEADER 提案**，才允许接受新提案 | Leader 当选后即可开始复制（但要先提交当期空条目才能推进 commit） |

> **这个结构差异在实践中意味着什么**：ZAB 的"恢复"更重（要显式对齐完才能干活），但恢复完之后广播阶段非常轻——**没有逐条回溯的日志匹配**，因为一致性在恢复阶段已经保证过了。Raft 反过来：选举很轻，但每条 `AppendEntries` 都带一致性检查。

## 二、zxid：一个 64 位整数同时承担两件事 {#zxid}

ZAB 里最重要的一个量是 `zxid`（ZooKeeper Transaction Id），它是个 **64 位整数，硬拆成两段**：

```text
 ┌──────────────────────────────┬──────────────────────────────┐
 │      高 32 位：epoch          │      低 32 位：计数器          │
 │  「第几任 Leader」            │  「这一任里的第几个提案」      │
 └──────────────────────────────┴──────────────────────────────┘
       每换一次 Leader +1              每发一个提案 +1
```

设计要点：

- **epoch 单调递增**，且**同一 epoch 只会有一个 Leader 发号**——这一条保证了 zxid 全局唯一。
- 新 Leader 上任后，第一条提案的 zxid 是 **(e+1, 0)**：取自己见过的最高 epoch 加一，计数器归零。
- 因为高 32 位在前，**比较 zxid 的大小就是比较 (epoch, counter) 的字典序**——`(2, 99) < (3, 0)`。

> **这就是"为什么不用 Raft 的 term"的答案**：Raft 的 `term` 只标识"第几次选举"，数据新旧要靠 `log index` + `term` 两个量一起判断。ZAB 把两件事**压进同一个单调整数**，于是"谁是更新的数据"退化成**一次整数比较**——这正是恢复阶段能做得那么干脆的原因。

## 三、恢复阶段：三步，以及 TRUNC 的推理链 {#recovery}

```text
崩溃后所有节点进入 LOOKING 状态
   │
   ├─ ① Discovery        互相交换 (acceptedEpoch, lastZxid)
   │                     → 最高的当选（平手比 serverId / myid）
   │
   ├─ ② Synchronization  Leader 与每个 Follower 逐个对齐历史：
   │                       ├─ DIFF   Follower 落后      → 补发缺的提案
   │                       ├─ TRUNC  Follower 多了未提交 → 截断它
   │                       └─ SNAP   落后太多          → 直接发全量快照
   │                     对齐完成后提交一条 NEW_LEADER 提案
   │
   └─ ③ Broadcast        开始接受新提案（进入广播模式）
```

### 3.1 TRUNC 为什么是安全的 {#trunc}

`TRUNC` 是 ZAB 里最精妙的一步：**Leader 会命令一个 Follower 把自己多出来的、Leader 没有的提案直接删掉**。听起来很危险——凭什么认定那些提案不重要？

官方的推理链是这样的（可以当作一道证明题来记）：

1. 那些提案记为 `U`，它们的 zxid **比 Leader 见过的都高**（因为提案按顺序产生）。
2. 如果这个 Follower 在选举时就在场，**它见过更高的 zxid，它就该当选 Leader**。
3. 现在 Leader 不是它 → 说明它是在**选举结束之后**才连上来的，或者它当时没参与那次选举。
4. 已提交的提案**必须被一个多数派看到**；而选出当前 Leader 的那个多数派**没有见过 U**。
5. 两个多数派必然相交（[多数派交集](/distributed/consensus#quorum)）→ 所以 **U 从未被提交**。
6. 结论：**丢掉 U 是安全的**。它就是"发出去但没凑够多数派"的残骸。

> **反过来看**：这个推理成立的前提是"**投票集合与提交集合都是多数派**"。如果集群配置不当（比如允许"少数派也能提交"），第 5 步就不成立，TRUNC 会变成数据丢失。**这是"为什么共识协议必须严格按多数派来"的一个具体体现，而不是一句口号。**

### 3.2 选举判据 {#election}

| 优先级 | 比较项 | 说明 |
|---|---|---|
| 1 | `lastZxid`（越大越优） | **Leader 必须见过集群中最高的 zxid** —— 这是 ZAB 唯一的硬性正确性要求 |
| 2 | `serverId`（越大越优） | 平手时用来打破僵局；所以配置里 `myid` 要各不同 |

注意这里与 Raft 的**表述差异**：Raft 的表述是"只投给日志不旧于自己的候选者"（每条投票各自判断），ZAB 的表述是"**被选出来的人必须拥有最高的 zxid**"（对结果的要求）。**要求结果 vs 限制行为**，这是两种不同的表达，但都指向同一个安全性目标。

## 四、广播模式：写入的两阶段 {#broadcast}

进入广播模式后，每个写请求走一轮类两阶段提交：

```text
客户端写请求
   │
   ▼
 Leader ──PROPOSAL(zxid)──▶ Follower A ──ACK──┐
   │      ──PROPOSAL(zxid)──▶ Follower B ──ACK──┤ 收齐多数派 ACK
   │      ──PROPOSAL(zxid)──▶ Follower C        │
   │◀───────────────────────────────────────────┘
   │
   ├──COMMIT(zxid)──▶ 所有 Follower（各自把提案应用到内存树）
   └──回复客户端成功
```

三个实现细节值得注意：

| 细节 | 说明 |
|---|---|
| **所有通道是 FIFO 的** | 所以"收到顺序 = 发送顺序"，Leader 不需要给提案编号来纠正乱序——**排序由网络层保证，协议层只保证内容** |
| **客户端不参与第二阶段** | 与业务里的 2PC 不同，这里的"参与者"是 ZK 自己的 Follower。所以**写延迟 = 一轮多数派往返**，不会因为客户端慢而卡住 |
| **提交点是"多数派 ACK"** | 只要多数派把提案写进了自己的事务日志，Leader 就可以 COMMIT。**"提交"与"应用到内存树"是两件事**——后者可以异步、可以晚 |

> **注意最后一条**，它是"读到旧值"现象的来源之一（下一节）。**提交不等于所有节点都应用了。**

## 五、ZAB 与 Raft 的逐维度对照 {#vs-raft}

| 维度 | Raft | ZAB |
|---|---|---|
| 面向的对象 | **一条日志**（日志项之间相互独立） | **一段历史**（整体带前缀顺序，允许连续多个提案同时在途） |
| 任期变量 | `term`：仅表示选举代数 | `epoch`：嵌在 `zxid` 高 32 位，**同时承担定序** |
| 选举与复制 | 一套机制贯穿 | **两套独立机制** |
| 日志对齐 | `prevLogIndex / prevLogTerm` 逐条回溯匹配 | 在恢复阶段**一次性判定** DIFF / TRUNC / SNAP |
| 未提交项处理 | 新 Leader 靠"当期空条目"间接覆盖旧任期未提交项 | **显式 TRUNC 截断** |
| 选举资格 | 候选者日志不旧于自己 | **Leader 必须见过最高的 zxid** |
| 默认读一致性 | 实现上通常提供线性读（ReadIndex / leader lease）与本地读两档 | **默认任意节点本地读，不是线性一致**（见下节） |
| 成员变更 | 一次只改一个节点（单步变更） | 支持 reconfig 动态配置 |

### 5.1 最容易被忽略的后果：默认读不是线性一致 {#read-consistency}

**ZK 的读可以在任意服务端本地完成，不经过共识**（见 [ZAB 的读路径](https://zookeeper.apache.org/doc/current/zookeeperInternals.html)）。好处是读的扩展性极好——加 Follower / Observer 就能加读能力；代价是：

| 现象 | 原因 |
|---|---|
| 客户端 A 刚写完，客户端 B 立刻读却读不到 | B 连的 Follower 还没收到那条 COMMIT |
| 同一个客户端先写后读，也可能读不到 | 除非用同一个会话且 API 支持"先 sync 再读" |
| 已提交的数据在新 Leader 上"暂时看不到" | 应用的异步性：提交 ≠ 所有节点都已应用 |

**想要"读到最新"就得显式付出代价**：调用 `sync()` 把当前服务端与 Leader 同步一次，再读。

```java
// 强读的写法：先 sync（把本节点与 Leader 对齐），再读
client.sync("/config/rate-limit", null, null);
byte[] data = client.getData("/config/rate-limit", false, null);
```

> **一句话记住**：**ZK 保证的是"写不丢 + 全序"，不是"读到最新"。** 这两件事在多数场景下够用（配置、成员、选主结果最终都会传播到），但如果你的逻辑里存在"**写完必须立刻读到**"的断言，就必须 `sync()`，或者干脆把该数据放在提供线性读的系统里。

## 六、四种状态与多数派 {#quorum}

| 状态 | 含义 | 参与投票 | 能处理写 |
|---|---|---|---|
| **LOOKING** | 正在选举，还没确定 Leader | — | 否 |
| **LEADING** | 当前 Leader | 是 | 是（转发给它） |
| **FOLLOWING** | 正常 Follower | 是 | 否（转发给 Leader） |
| **OBSERVING** | Observer：只同步数据、不投票 | **否** | 否 |

规模判据与共识协议一致：**quorum = ⌊N/2⌋ + 1，N 取奇数**（3 容 1、5 容 2）。

**Observer 的价值与边界**：

- 加 Observer **能提升读能力**（多一个可读节点），**不提升写可用性**（它不投票，也不增加容错数）。
- 它的真实用途是**跨机房/跨地域的只读副本**，以及**降低投票集合的通信开销**（Observer 不参与选举通信）。

> **最后一条工程结论**：ZK 的写延迟由 quorum 内最慢的那次往返决定，所以**投票节点必须放在低延迟网络内**。跨机房部署 Observer 可以，把投票节点跨机房铺开不行——这一点与 [共识协议的跨城问题](/high-availability/multi-datacenter#physics) 完全同源。

## 七、面试口径 {#interview}

- **ZAB 与 Raft 最大的差别**：**ZAB 面向"一段历史"、Raft 面向"一条日志"**，于是 ZAB 把"选主"与"广播"做成**两套独立机制**：恢复阶段（Discovery/Synchronization/Broadcast）负责对齐历史，对齐完才允许接受新提案；Raft 用 `term` 一个变量贯穿始终。
- **zxid 是什么**：64 位整数，**高 32 位是 epoch（第几任 Leader）、低 32 位是计数器**。所以**比较 zxid 的大小就是比较 (epoch, counter) 的字典序**——"谁的数据更新"退化成一次整数比较。
- **为什么不用 Raft 的 term**：`term` 只表示选举代数，数据新旧需要 `term` + `log index` 两个量；ZAB 把**换届与定序压进同一个单调整数**，这是它恢复阶段能一次判定 DIFF/TRUNC/SNAP 的前提。
- **新 Leader 的第一条 zxid**：取见过的最高 epoch 加一、计数器归零，即 **(e+1, 0)**；并先提交一条 **NEW_LEADER** 提案，提交完成前不接受新提案。
- **TRUNC 为什么安全**：Follower 上多出来的提案 `U` 若已提交，则它必然被某个多数派看到；而**选举当前 Leader 的多数派没见过 U**；两个多数派必然相交，矛盾 → **U 从未提交**，可以安全丢弃。**推理依赖"投票与提交都走多数派"。**
- **选举判据**：**Leader 必须拥有集群中最高的 `lastZxid`**；平手比 `serverId`。注意这与 Raft"只投给日志不旧于自己的候选者"是**对结果的要求 vs 对行为的限制**，两种表达、同一目标。
- **广播阶段为什么是两阶段**：PROPOSAL → 多数派 ACK → COMMIT。**客户端不参与第二阶段**（参与者是 ZK 自己的 Follower），所以写延迟 = 一轮多数派往返；**FIFO 通道让排序由网络层保证**，协议层不必编号纠错。
- **ZK 默认读是线性一致的吗**：**不是**。读可以在任意服务端本地完成、不经过共识，所以"刚写完立刻读"可能读不到。要强读必须显式 `sync()` 对齐后再读。**ZK 保证的是"已提交的写不丢 + 全序"，不是"读到最新"。**
- **四种状态**：LOOKING / LEADING / FOLLOWING / **OBSERVING**。Observer 不投票 —— **加 Observer 提升读能力，但不提升写可用性**；它适合做跨机房只读副本，而**投票节点必须放在低延迟网络内**。
