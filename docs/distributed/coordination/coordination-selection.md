# 协调服务选型与集群治理

选型这一篇要回答两个问题：**用哪个**，以及**买到之后怎么才不出事**。第二个问题其实更重要——协调服务是体系里"**最不能被牺牲的一环**"：

> 它挂了，不一定影响正在跑的读写；但**任何一次扩缩容、故障转移、配置变更都会被冻结**。

这句话决定了它的运维标准要高于普通业务服务。

## 一、四个候选的定位 {#candidates}

| | **ZooKeeper** | **etcd** | **Nacos** | **Consul** |
|---|---|---|---|---|
| **数据模型** | 树（znode） | 扁平 KV（前缀即层级） | 配置 + 注册两类对象 | KV + 服务目录 |
| **共识协议** | **ZAB** | **Raft** | **双协议**：临时实例走自研 Distro（AP）、配置与非临时实例走 Raft（CP） | Raft |
| **变更通知** | Watcher（一次性 / 持久 / 持久递归） | Watch（长期流式，**带 revision，不丢中间态**） | 长轮询 + UDP 推送 | blocking query |
| **健康检查** | 靠会话（临时节点） | 无内置（靠 lease） | **内置**（心跳 / HTTP / TCP） | **内置**（多种探针） |
| **控制台** | 无 | 无 | **有** | 有（部分） |
| **许可** | Apache 2.0 | Apache 2.0 | Apache 2.0 | **BUSL 1.1（2023-08 起）** |
| **典型场景** | 老一代 Dubbo 注册中心、Hadoop 系、Canal HA | **K8s 控制平面**、Patroni | Spring Cloud 体系 | 混合云 / 非 K8s 工作负载 |

### 1.1 两个容易忽略的许可事实 {#license}

| 事实 | 说明 |
|---|---|
| **Consul 自 2023-08-10 起改为 BUSL 1.1** | 同批变更的还有 Terraform / Vault / Nomad / Packer 等。**但 API、SDK 与大部分库仍是 MPL 2.0**，且**2023-08 之前发布的版本仍是 MPL 2.0** |
| **BUSL 的触发边界与 SSPL 类似** | 自用、内部部署、不把该产品本身作为服务卖给第三方 → 不受限。真正需要法务确认的是"**把它做成托管服务对外售卖**" |

> 这条与[存储选型的许可红线段落](/database/mongodb/nosql-selection#license)是同一套判断逻辑：**先看"你会不会把它当服务卖"，再决定要不要紧张**。但要注意 BUSL 比 SSPL 更"商业化"——**它不是 OSI 认可的开源许可证**，部分发行版（如 Fedora）因此拒绝打包。

### 1.2 一句话选型 {#quick-pick}

| 你的场景 | 选它 |
|---|---|
| 已经在 K8s 里，只是要用协调能力 | **etcd**（本来就有，别再装一套 ZK） |
| Spring Cloud 体系，要注册中心 + 配置中心 | **Nacos** |
| 混合云、非 K8s 工作负载、要服务网格 | Consul（注意许可） |
| 要自己定义协调原语（非标准选主、自定义锁语义） | **ZooKeeper 或 etcd**——见[你要的是原语还是成品](/distributed/coordination/what-coordination-solves#boundary) |

## 二、ZooKeeper 的治理要点 {#zk-ops}

### 2.1 集群规模 {#zk-size}

- **节点数取奇数**：`2N+1` 个投票节点可容忍 `N` 台故障（3 容 1、5 容 2）。4 个节点的容错能力与 3 个相同，只是多付一台的成本与更长的选举时间。
- **投票节点必须在低延迟网络内**：写延迟由 quorum 内最慢的那次往返决定，跨机房会让每一次写都背上 RTT。
- **读扩展用 Observer**：它同步数据但不投票——**提升读能力，不提升写可用性**（见 [ZAB 的四种状态](/distributed/coordination/zab-protocol#quorum)）。

### 2.2 磁盘与持久化 {#zk-disk}

| 项 | 要求 | 原因 |
|---|---|---|
| **事务日志与快照分盘** | 强烈建议 | 事务日志是**追加写 + fsync** 的延迟敏感型 IO，与快照的顺序大块写相互干扰 |
| **`forceSync` 不要关** | 保持默认开启 | 关掉它意味着"更新还没落盘就返回成功"，**会丢已确认的写**，只适合压测 |
| **磁盘不要与高 IO 邻居共用** | — | 与共识协议同源：fsync 抖动会拖长写延迟，甚至触发不必要的选举 |

### 2.3 会话超时与版本现状 {#zk-tuning}

- **会话超时下限 `2 × tickTime`、上限 `20 × tickTime`**（`tickTime` 默认 2000ms → 4s~40s）。**调大能减少"GC 停顿被误判为宕机"，但会拉长故障感知**——这是一条无法两全的取舍，正解在资源端做 fencing。
- **不要把大配置放进 znode**：单节点默认上限约 1MB，且官方反对调大（见 [znode 的硬上限](/distributed/coordination/zookeeper-model#znode-limit)）。

| 版本现状 | 值 |
|---|---|
| **当前版本** | **3.9.x**（最新 3.9.5） |
| **稳定版** | 3.8.x（最新 3.8.6）——社区同时维护两个分支 |
| **已 EOL** | 3.7（2024-01-19）、3.6、3.5、3.4 |
| 3.8 起的变化 | 日志框架迁移到 **Logback**、支持 **JDK 17**、配额强制执行 |
| 3.9 起的变化 | Admin Server 支持导出快照、**WatchEvent 携带触发它的 zxid**、FIPS 模式默认开启 |
| 客户端兼容性 | 3.5.x+ 的客户端可连 3.9.x 服务端；3.9.x 客户端可连 3.5~3.8.x 服务端（不使用新 API 时） |

## 三、etcd 的治理要点 {#etcd-ops}

etcd 的运维风险几乎全部集中在**存储配额**与**磁盘延迟**两件事上。

### 3.1 2GiB 配额与 NOSPACE {#etcd-quota}

| 项 | 值 / 说明 |
|---|---|
| **默认配额** | **2 GiB**（`--quota-backend-bytes`，默认 `0` 即取 2GB；负数表示禁用配额） |
| **官方建议上限** | **8 GiB** —— 超过时 etcd 启动会告警，再大性能显著下降 |
| **超限后的行为** | 触发 **NOSPACE 告警**并同步给所有节点、持久化到 db → **集群转为只读**，且**之后每个写命令都会被 Apply 模块拒绝** |

**这里有一个反直觉的坑**：**光调大配额不会恢复写入。**

因为 NOSPACE 告警**已经被持久化**了，Apply 模块每次执行命令都会检查它。所以正确顺序是：

```bash
# 1) 调大配额（重启 etcd 时生效）
#    例如 --quota-backend-bytes=4294967296   # 4 GiB
# 2) 用 defrag 把物理文件真正缩小回配额以下
etcdctl defrag --cluster
# 3) 关键一步：解除告警，否则依然只读
etcdctl alarm disarm
```

### 3.2 compaction 与 defrag 是两件事 {#etcd-compaction}

| | **compaction（压缩）** | **defrag（碎片整理）** |
|---|---|---|
| 层次 | **逻辑**：回收旧版本的 MVCC revision | **物理**：重写 db 文件，回收磁盘空间 |
| 效果 | 把旧版本占的空间**标记为空闲**，后续写入可复用 | **真正缩小文件大小** |
| 代价 | 低 | **会阻塞该节点的读写**（重写期间不可服务） |
| 频率 | 例行（K8s 里 API Server 默认每 5 分钟一次） | 按需；**一次只对一个节点做**，绝对不能全集群同时 |

> **"为什么 compaction 之后 db 文件还是那么大"** 是 etcd 最常见的疑问——因为 compaction 只释放了逻辑版本，**物理空间要靠 defrag 才能还回去**。

### 3.3 为什么 etcd 对磁盘延迟异常敏感 {#etcd-disk}

etcd 的写路径是：**客户端请求 → Raft 提案 → 追加写 WAL → `fsync` → 复制到多数派 → 多数派 fsync 后提交**。

**`fsync` 是同步的、在关键路径上**——在它返回之前 etcd 无法确认这次写。所以：

- 关注的是**延迟**，不是吞吐。慢速网络盘、与别的重 IO 邻居共用盘，都会直接抬高**每一次 K8s API 写**的延迟。
- 极端情况下，一个 fsync 不够快的 Leader 会**来不及发心跳**，进而触发选举。
- **大 key 同样是杀手**：接近 1MB 的 ConfigMap / annotation 会阻塞 Raft 状态机的序列化与传输，表现为整个集群变慢（而根因只是某个命名空间里的一个大对象）。

### 3.4 版本现状 {#etcd-versions}

| 项 | 值 |
|---|---|
| **3.6.0** | **2025-05-15 发布** —— 距 3.5.0（2021-06-15）**近四年的第一个 minor 版本**，主要工作是把 raft 拆到独立仓库、引入 v3store |
| 3.6 起的关键能力 | **首次支持版本降级**（一次只降一个 minor）、`/livez` 与 `/readyz`、`snapshot-count` 默认值**从 100000 降到 10000** |
| 3.6 当前补丁 | 3.6.13（2026-07-01）；3.5 分支仍在维护（3.5.32 同期发布） |
| **3.7.0** | **已 GA（2026-07）**：RangeStream（大结果集分块）、改从 v3store 引导 |
| **已 EOL** | **3.4 于 2026-05-15 终止支持** |

## 四、KRaft：Kafka 为什么把 ZooKeeper 去掉 {#kraft}

这是"**协调服务与它服务的系统**"之间一次完整的解耦，值得完整看一遍因果链。

### 4.1 旧架构的瓶颈 {#kraft-why}

| 问题 | 机制 |
|---|---|
| **元数据成为分区数的天花板** | ZK 只存元数据（topic、分区、ISR、ACL），但**元数据变更的频率随分区数放大**——ISR 抖动在分区多时非常频繁，于是**ZK 的写入能力成了 Kafka 能承载多少分区的上限** |
| **故障面多了一套** | ZK 不在数据面上（消息读写不经过它），却要额外维护一套高可用集群、独立扩容、独立监控 |
| **两套一致性的边界很难讲清** | "业务数据走 ISR 复制、元数据走 ZAB"——这是正确的分工，但把两个协议的一致性模型缝在一起，排查问题时边界不直观 |

### 4.2 KRaft 的做法与时间线 {#kraft-how}

**做法**：把元数据交给**内部的 Raft**（Controller quorum），**消息数据仍然走 ISR 复制**。

```text
旧：  Broker 集群 ──元数据──▶ ZooKeeper 集群（ZAB）
新：  Broker 集群 ──元数据──▶ Controller quorum（Raft，通常 3 节点）
      Broker 集群 ──消息数据─▶ ISR 主从复制（不走 Raft）
```

**注意最后一行**：KRaft 不是"把 Kafka 全放到 Raft 上"，而是**只把该用共识的那部分放上去**——这正是["共识是昂贵的一致性，只用在刀刃上"](/distributed/consensus#practice)的范例。

| 时间线 | 事件 |
|---|---|
| **2.8（2021）** | KIP-500 引入 KRaft，早期访问 |
| **3.3** | KRaft 生产可用 |
| **4.0（2025-03）** | **ZooKeeper 模式被移除，KRaft 成为唯一模式** |

4.0 同时还有两个与之无关但同样需要知道的硬门槛：**Broker / Connect / tools 要求 Java 17，clients / Kafka Streams 要求 Java 11**。

### 4.3 同一思路的其他例子 {#kraft-others}

| 系统 | 动作 |
|---|---|
| **ClickHouse** | 用 **ClickHouse Keeper** 取代 ZooKeeper —— **协议兼容 ZK、客户端无感**（见[副本与分片](/bigdata/clickhouse/cluster-and-replica#keeper)） |
| **Doris** | FE 之间直接用 **Paxos** 选主，**整个架构不依赖 ZK** —— "少一个外部组件就等于少一整个故障面" |
| **RocketMQ** | 5.x 起引入 **Controller 模式**（Raft 选主），把职责与 NameServer 分离 |

> **共同趋势**：**把外部协调依赖内化**。收益是部署与运维的组件数下降、故障面收敛；代价是每个系统都要自己实现一遍共识逻辑（所以才能看到这么多"我们不用 ZooKeeper 了"的公告）。

## 五、五种最常见的误用 {#misuse}

| # | 误用 | 后果 | 正解 |
|---|---|---|---|
| 1 | 把 ZK 当配置中心，存大配置 | 单节点约 1MB 上限 + 动摇 quorum | 配置中心 / 对象存储 |
| 2 | 把 ZK 当服务发现，存海量实例 | znode 与 watch 数量爆炸，写能力被服务列表变更吃满 | Nacos / Consul / K8s Service + CoreDNS |
| 3 | 用 watch 做事件流、变更流水 | 一次性、且**看不到每次变化**（中间态被合并） | 消息队列（Kafka / RocketMQ） |
| 4 | 用临时节点做"长任务"的存活标志 | 长 GC 或网络抖动 → 会话超时 → 任务被误判死亡 | 长任务用心跳表 + 显式状态机 |
| 5 | 把协调服务当业务存储 | 数据丢了整个体系起不来；容量与吞吐都不够 | 数据库 / 对象存储 |

### 5.1 一条贯穿的判据 {#misuse-rule}

**协调服务只存"谁说了算"，不存"发生了什么"。**

- "谁说了算" → 选主结果、锁的归属、成员列表、配置。**特点：小、能重建、丢了会震荡。**
- "发生了什么" → 订单、日志、消息。**特点：大、不能重建、必须持久。** 这类数据放消息队列或数据库。

## 六、面试口径 {#interview}

- **四个候选怎么选**：**已经在 K8s 里 → etcd**（本来就有）；**Spring Cloud 体系 → Nacos**；**混合云/非 K8s + 服务网格 → Consul（注意许可）**；**要自定义协调原语 → ZK 或 etcd**。判据是"你要原语还是成品"，不是性能高低。
- **Consul 的许可变化**：**2023-08-10 起由 MPL 2.0 改为 BUSL 1.1**（同批还有 Terraform / Vault / Nomad）。**API、SDK 与大部分库仍是 MPL 2.0，2023-08 之前的版本也仍是 MPL 2.0**；BUSL **不是 OSI 认可的开源许可**，自用不受限，做成托管服务售卖才需要法务确认。
- **ZK 的集群规模**：取奇数，`2N+1` 容 `N`。**投票节点必须在低延迟网络内**（写延迟由 quorum 最慢往返决定）；**Observer 同步数据但不投票——加它提升读能力、不提升写可用性**。
- **ZK 的磁盘要求**：**事务日志与快照分盘**；`forceSync` 保持开启（关掉会丢已确认的写，只适合压测）；不要与高 IO 邻居共用盘。
- **会话超时的取舍**：下限 `2 × tickTime`、上限 `20 × tickTime`（默认 4s~40s）。**调大减少 GC 误判但拉长故障感知**——无法两全，正解是在资源端做 fencing。
- **etcd 的默认配额是多少**：**2 GiB**，官方建议上限 **8 GiB**；超限触发 **NOSPACE 告警 → 集群转只读**。
- **调大配额为什么还是不能写**：因为 NOSPACE 告警**已被持久化**，Apply 模块每次执行命令都会检查它。必须先 `defrag` 缩小物理文件，再 `alarm disarm` 解除告警。
- **compaction 与 defrag 的区别**：compaction 是**逻辑回收**（释放旧 revision，空间标记为空闲、可复用）；defrag 是**物理重写**（真正缩小文件），**会阻塞该节点、必须一次只做一个**。"压缩完文件还是那么大"就是因为少了 defrag。
- **etcd 为什么怕慢盘**：写路径上的 **`fsync` 是同步的且在关键路径**——它返回前无法确认写入。所以关注**延迟**而非吞吐；慢盘会直接抬高每次 API 写延迟，甚至让 Leader 来不及发心跳而触发选举。**大 key 同样是杀手**（阻塞 Raft 状态机）。
- **KRaft 为什么去掉 ZooKeeper**：旧架构里**元数据变更频率随分区数放大**，ZK 的写能力成了分区数的天花板，且 ZK 不在数据面却要单独维护一套集群。KRaft 用内部 Raft 管元数据，**消息数据仍走 ISR 复制**——共识只用在刀刃上。时间线：2.8 引入 → 3.3 生产可用 → **4.0 起 ZK 模式被移除，KRaft 成为唯一模式**。
- **同类动作**：ClickHouse Keeper（**协议兼容 ZK、客户端无感**）、Doris FE 用 Paxos 不依赖 ZK、RocketMQ 5.x 的 Controller 模式。**共同趋势是把外部协调依赖内化**——收益是组件数与故障面收敛，代价是每个系统都要自己实现一遍共识。
- **协调服务最容易被误用的地方**：当配置中心存大配置、当服务发现存海量实例、用 watch 做事件流、用临时节点标记长任务存活、当业务存储用。**一条判据：它只存"谁说了算"，不存"发生了什么"。**
- **延伸**：协调服务的边界判据见[协调问题的边界](/distributed/coordination/what-coordination-solves)；znode 与会话语义见 [ZooKeeper 数据模型](/distributed/coordination/zookeeper-model)；共识协议通论见[共识协议](/distributed/consensus)；Kafka 侧的元数据实现见 [Kafka 高可用](/middleware/kafka/high-availability)。
