# 协调问题的边界：什么该交给协调服务

先给结论：**协调服务只解决一类问题——让多个进程对"谁说了算"达成一致，并且在有人退出时立刻知道。**

它有两个硬特征，决定了它能做什么、不能做什么：

| 特征 | 含义 | 直接推论 |
|---|---|---|
| **数据极小** | 存的是元信息（几百字节到几 KB），不是业务数据 | 不能当存储用——容量与吞吐差着好几个数量级 |
| **正确性优先** | 读到旧值会出大问题，所以宁可短暂不可用 | 代价是高延迟，以及"多数派不可用即不可写" |

把这两句记牢，后面所有判据都能自己推出来。**本文只回答"边界在哪"，机制细节（znode、ZAB、选主）在后面几篇。**

## 一、六种原语：协调服务被用来干什么 {#what}

所有用法都能归到六种原语上。它们的共同结构与差异如下：

```text
        进程 A            进程 B            进程 C
          │                 │                 │
          └─────────────────┼─────────────────┘
                            │  「现在谁当主？」「配置变了吗？」「还有谁活着？」
                     ┌──────▼───────┐
                     │   协调服务    │  ← 只存元信息（KB 级）
                     │ ZK / etcd    │  ← 用共识协议保证一致
                     └──────┬───────┘
                            │  变更主动推送（watch / lease）
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
       进程 A            进程 B            进程 C
```

| 原语 | 解决什么 | 依赖的底层能力 | 典型场景 |
|---|---|---|---|
| **命名 / 服务发现** | 逻辑名 → 当前可用地址列表 | 临时节点 + 子节点 watch | 老一代注册中心（Dubbo + ZK） |
| **配置管理** | 一份配置改了，所有进程都要知道 | 数据节点 + watcher | 开关、路由表、限流阈值 |
| **成员管理** | 现在有哪些进程活着 | 临时节点 + 会话 | 集群成员表、分片归属 |
| **选主** | 同一时刻只有一个实例做写操作 | 临时顺序节点（或 create 成功者） | 主备切换、单写者定时任务 |
| **分布式锁** | 临界区互斥 | 临时顺序节点 + watch 前一个 | 对账、批处理去重 |
| **屏障 / 队列** | 等所有进程到齐，或按序分配任务 | 顺序节点计数 | 批量任务分发 |

六种原语看着不像，但**三条要求是共通的**：

1. **读多写少**——配置、成员列表、谁是主，都是读远远多于写。
2. **要"被通知"，不要"轮询"**——变更必须在毫秒级传到每个进程，靠 `SELECT` 循环做不到。
3. **持有者崩了要自动清理**——进程没机会执行"退出时清理"那段代码（被 OOM Kill、断电、网络分区），所以状态清理必须由外部完成。

> **第 3 条最容易被低估。** 它是"为什么不能自己在业务库里存一张锁表"的根本原因：业务库里的每一行都需要有人去删，而**最需要被删的那一行，恰恰是那个已经死掉的进程留下的**。

## 二、为什么不能直接用业务库或 Redis 顶 {#why-not-db}

这三种"自建"方案在真实项目里都出现过，它们不是完全不能用，而是**各缺一件关键能力**。

| 需求 | 业务库（MySQL） | Redis | 协调服务 |
|---|---|---|---|
| **互斥** | `SELECT ... FOR UPDATE` 可以互斥，**但锁的生命周期被绑在事务上**——没法"跨两次请求持有" | `SET NX PX` 快且原子，**但没有会话概念**，只能靠 TTL 猜"还活着吗" | 临时节点 / lease，**持有者一断连就自动释放** |
| **变更通知** | 没有。只能轮询，把 QPS 与延迟一起拉高 | keyspace notification **不保证不丢、不保证顺序**，且是全局广播 | 原生 watch，**精确到某个节点、事件驱动** |
| **崩溃感知** | 依赖超时字段 + 定时扫描，感知延迟 = 扫描周期 | TTL 到期，**但区分不出"进程死了"和"进程还活着、只是超过 TTL 了"** | 会话心跳 + 多数派确认的存活判定 |
| **一致读** | 主从延迟下可能读到旧值 | 主从异步复制，**主挂时可能连锁一起丢** | 可以 `sync()` 强制追平 Leader 再读 |

其中最容易混淆的是第二行右边那一列。**Redis 的 TTL 是"绝对过期"，不是"会话"。**

它记录的是"到点就删"，而不是"持有者还在"。平时这两者看不出差别，只在两种情况下分岔：

- **持有者卡住了**（长 GC、网络分区）——它没死，但续约不上，锁被删；等它缓过来，它**仍然以为自己持有锁**。
- **Redis 换主了**——新主上根本没有这把锁，于是第二个持有者可以拿到锁；而第一个持有者也没死。

这两种情况都会导致**同一时刻两个持有者**。**这不是"配置没调好"，是 TTL 语义的固有缺口**，只能靠第 4 篇讲的 fencing token 在资源端兜住。

> **反过来说**：如果你的场景里"两个持有者同时动作"的后果可以被幂等或唯一索引吸收掉，那 Redis 锁完全够用，没必要为它引入一套 ZK。**先看后果，再看工具。**

## 三、边界：协调服务、配置中心、注册中心 {#boundary}

这三类产品常被当成竞品，实际是**两层**：

| 层次 | 代表 | 你拿到的是什么 | 谁决定数据怎么组织 |
|---|---|---|---|
| **原语层** | **ZooKeeper、etcd** | 一棵树 / 一个 KV + watch + 临时节点。**原语，不是产品** | 你。schema、命名规范、监听逻辑都要自己设计 |
| **场景层** | **Nacos、Consul**、Eureka | "注册中心""配置中心"这两个成品能力，带控制台、带健康检查、带推送 | 产品。你只是使用者 |
| **平台层** | **K8s Service + CoreDNS**、Apollo | 服务发现由平台承担，应用无感知 | 平台 |

判断该用哪层，只问一句：**你要的是原语，还是成品？**

- 要实现的是**标准场景**（服务注册 + 配置下发）→ 直接上 Nacos 这类场景层产品，别用 ZK 自己造。
- 要实现的是**非标准协调逻辑**（比如"三个实例里选一个做对账，且每次会话只能选一次"）→ 场景层产品表达不了，才需要原语层。

> **一个历史遗留的常见错配**：老项目用 ZooKeeper 做服务发现（Dubbo 时代很常见），本质是**拿原语层去干场景层的活**——zkCli 里一屏临时节点，没有任何健康检查与灰度能力。**这不是 ZK 的问题，是选层选错了。**

## 四、五条"不该用它"的判据 {#when-not}

下面这五种情况，在项目里几乎每周都能遇到，**没有一种是协调服务的合理用法**：

| # | 症状 | 真正该用的 | 为什么 |
|---|---|---|---|
| 1 | 要存的数据有几十 KB 甚至几 MB | 对象存储 / 配置中心的文件模式 | ZK 单节点默认上限约 1MB，且官方明确反对调大（见[znode 与它的硬上限](/distributed/coordination/zookeeper-model#znode)） |
| 2 | 要按条件查、范围查、聚合查 | 数据库 / 搜索引擎 | ZK 只有树、etcd 只有 KV 前缀，**没有查询语言** |
| 3 | 只是"防重复提交" | 唯一索引 / 幂等表 | 数据库的一次 `INSERT` 就解决了，不需要分布式锁 |
| 4 | 高吞吐计数、秒杀扣减 | Redis 原子操作 / 数据库行级原子更新 | 协调服务的吞吐在**每秒千级写**，比 Redis 低两三个数量级 |
| 5 | 只是"存一份配置读一读" | 配置中心（Nacos / Apollo） | 用 ZK 存配置要自己写监听与格式约定，等于重造一个配置中心 |

> **收口一句**：协调服务的价值在**正确性**，不在吞吐。**把它当数据库用，两边都会做不好**——数据库被元数据的强一致要求拖慢，协调服务被数据量压垮。

## 五、面试口径 {#interview}

- **协调服务解决什么**：让多个进程对"谁说了算"达成一致，并在有人退出时立刻知道。六种原语（命名 / 配置 / 成员 / 选主 / 锁 / 屏障）都建立在三条共通要求上：**读多写少、要通知不要轮询、持有者崩了要自动清理**。
- **为什么不能自己存锁表**：业务库里的锁行需要有人去删，而**最该被删的那一行恰恰是死掉的进程留下的**。"崩了自动清理"必须由外部机制完成，不能靠应用自己。
- **Redis 锁与 ZK 锁的本质差别**：Redis 的 `TTL` 是**绝对过期**（到点就删），ZK 的临时节点是**会话绑定**（持有者断连才删）。平时看不出差别，只在**持有者卡住**或**换主**时暴露——两者都可能导致**同一时刻两个持有者**。
- **怎么兜住"两个持有者"**：靠 **fencing token**（单调递增的隔离令牌，写入时带上、资源端只接受更大的那个）。**锁的正确性最终由被保护的资源决定，不是由锁服务决定。**
- **协调服务 vs 配置中心 / 注册中心**：**原语层 vs 场景层**。ZK / etcd 给你原语，schema 与监听逻辑自己设计；Nacos / Consul 给你成品。判断标准是"**你要的是原语还是成品**"，不是"谁性能好"。
- **为什么不建议用 ZK 做服务发现**：那是**拿原语层干场景层的活**——没有健康检查与灰度能力，且把服务列表压在了一个对写延迟极敏感的集群上。
- **五条不该用的判据**：数据大（>KB 级）、需要查询语言、只是防重复提交、高吞吐计数、只是存配置读一读。前两条是**能力边界**，后三条是**杀鸡用牛刀**。
- **延伸**：znode 与 1MB 硬上限见[ZooKeeper 数据模型](/distributed/coordination/zookeeper-model#znode)；一致性协议本身的原理见[共识协议](/distributed/consensus)；CAP 取舍判据见 [CAP 与 BASE](/java/spring/spring-cloud/cap-base)。
