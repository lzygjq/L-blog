# 共识协议：Paxos、Raft 与选主

先把一个问题摆正：**共识协议要解决的不是"数据一致"，而是"顺序一致"。**

这句话听起来像文字游戏，但它是理解 Paxos 和 Raft 的分水岭。多数人学不进去，是因为一上来就把它当成"多副本同步数据的技术"，于是所有设计都显得绕；一旦换成"让多个节点对一串操作的顺序达成一致"，Raft 的每个约束都会变成必然。

## 一、从「复制状态机」说起 {#rsm}

共识协议的理论基础叫**复制状态机（Replicated State Machine, RSM）**，它只有一个朴素的前提：

> **相同的初始状态 + 相同顺序的确定性操作 = 相同的最终状态**

推下去就是整个分布式一致的骨架：

```text
① 只要各副本从同一个初始状态出发
② 并且按【完全相同的顺序】执行【相同的操作序列】
③ 那么各副本的最终状态必然相同

→ 于是"保证数据一致"被归约成"保证日志（操作序列）一致"
→ 共识协议要做的全部事情：让多个节点对【同一份日志的顺序】达成一致
```

**这个归约解释了两个常见困惑**：

| 困惑 | 用 RSM 解释 |
|---|---|
| 为什么 Raft 反复强调"日志顺序"，很少谈"数据同步"？ | 因为数据是日志的**执行结果**。日志一致 → 数据必然一致，反过来推不成立（时序不同也会得到不同的最终状态） |
| 为什么说"用了随机数、时间戳、`UUID` 的操作不可复制"？ | RSM 要求操作是**确定性**的。非确定性操作会让相同日志在不同副本上得到不同结果——所以这类值必须由 Leader 生成后**写进日志**再复制，这就是"Leader 统一发号"的根因 |

> **判据**：任何"多副本保持一致"的方案，最终都会落到"把操作排序"上。反过来，如果一个方案说不清"顺序由谁定"，它的一致性就是运气。

## 二、多数派：所有保证的来源 {#quorum}

共识协议的安全基石是一条集合论性质：

> **任意两个多数派（Quorum）必然有交集**

它的推论是整个体系的地基：

| 性质 | 推导 |
|---|---|
| **不会选出两个 Leader** | 两个候选者各自需要多数派投票，两个多数派必有交集，而一个节点在一个任期内只投一票 → 不可能双双过半 |
| **已提交的日志不会丢** | 已提交 = 多数派已复制。新 Leader 也必须由多数派选出，两个多数派有交集 → 交集节点上存着那条日志 |
| **脑裂被杜绝** | 少数派凑不够多数票，无法选出 Leader，也无法提交任何写 |

**多数派的计算公式与容错能力**：

```text
多数派 = ⌊N / 2⌋ + 1

N=3 → 需 2 票 → 容错 1 台
N=4 → 需 3 票 → 容错 1 台   ← 与 3 副本相同！
N=5 → 需 3 票 → 容错 2 台
N=6 → 需 4 票 → 容错 2 台   ← 与 5 副本相同！
```

**所以副本数要配奇数**——偶数副本在容错能力上等同于少一台，那一台纯粹是白白多出的成本。这解释了几乎所有共识系统都推荐 3 或 5 副本，以及为什么 Raft 的成员变更要"一次只改一个节点"：从 4 改到 5 的中途会短暂出现既非 3 也非 5 的配置，若一次改两个，可能出现两个不相交的多数派。

> **⚠️ 一个容易踩的坑**：配了 3 副本 ≠ 一定能容 1 台故障。还要看**写入需要几份确认**。例如 Kafka 的 `acks=all` 配合默认 `min.insync.replicas=1`，只要 1 个副本在就允许写——3 副本里挂 2 台，剩下的 1 台照样接受写入，此时若它再挂，数据就真丢了。**"副本数"和"写入确认数"是两个独立的旋钮，容错能力由后者决定。**

另一个由多数派派生的模型是 **NWR**（Dynamo 式）：读需 `R` 份、写需 `W` 份，只要 `W + R > N`，读写集合就必有交集，从而保证"读到的至少包含最新写入"。它是"用多数派做取舍"的另一种参数化形式，与共识协议的区别是**它不保证线性一致**（并发写可能冲突，需要版本向量与冲突解决）。

## 三、Paxos：只保证安全，不保证活着 {#paxos}

### 3.1 三个角色与两个阶段 {#paxos-phases}

Paxos 的角色是**逻辑角色**，一个进程可以同时是三者：

| 角色 | 职责 |
|---|---|
| **Proposer** | 提出提案（编号 `n` + 值 `v`） |
| **Acceptor** | 投票并记住已接受的提案（真正决定结果的角色） |
| **Learner** | 学习被选定的值（只读，不参与决议） |

**Basic Paxos 的两个阶段**：

```text
阶段一（Prepare / Promise）—— 探路 + 锁票
  Proposer → 多数派 Acceptor:  Prepare(n)          我要用编号 n 提案
  Acceptor  → Proposer:        Promise(n)         承诺不再接受编号 < n 的提案
                              [+ 返回自己已接受的最高编号提案 (n', v')]

阶段二（Accept / Accepted）—— 提案 + 定值
  Proposer → 多数派 Acceptor:  Accept(n, v)       请求接受
  Acceptor  → Proposer:        Accepted(n, v)     接受并持久化
  → 多数派接受 ⇒ 值被【选定】，通知 Learner
```

### 3.2 那条最关键的不变式 {#paxos-invariant}

阶段一返回的 `(n', v')` 不是顺手带的，它是 Paxos 安全性的全部：

> **如果任何 Acceptor 已经接受过某个值，新的 Proposer 必须提出"已接受提案中编号最大"的那个值，而不是自己的值。**

由此得到 Paxos 的核心不变式：

> **一旦某个值被多数派接受，之后任何编号更大的提案，提出的一定是同一个值。**

直觉是：Proposer 在动手前先问一圈"你们手上有没有已经定下来的东西"，只要有就必须**继承**它——这就堵住了"新提案覆盖旧决议"的可能。**代价是 Paxos 只保证 Safety（不会选出两个值），不保证 Liveness（一定能选出值）**：两个 Proposer 交替用更大编号打断对方，就会出现**活锁（dueling proposers）**，永远选不出结果。

### 3.3 为什么工程上没人直接用 Basic Paxos {#paxos-multipaxos}

两件事决定了它只能当理论：

1. **它只解决"一个值"的选定**。而工程要的是一串源源不断的日志。朴素做法是"每条日志跑一轮 Paxos"——两轮 RPC × 每条日志，成本无法接受；
2. **活锁需要外部机制补救**。

工程解法是 **Multi-Paxos**：先选出一个稳定的 Leader，之后所有提案都由它发起，**阶段一可以省掉**（Leader 用一次 Phase 1 就把"编号区间"锁下来了），退化成"一次 RPC 完成一次复制"。

**这里有个值得记住的洞察**：Multi-Paxos 引入 Leader 之后，它在结构上已经非常接近 Raft 了——**Raft 某种意义上就是"把 Multi-Paxos 里那些没写清楚的细节全部定义死"的产物**。所以"Raft 是不是 Paxos 的简化版"这个问题，严谨的答法是：**Raft 解决的是同一个问题，但它的设计目标从一开始就是"可理解"与"可直接实现"**。

## 四、Raft：把每个细节都定义死 {#raft}

### 4.1 强 Leader 设计 {#raft-leader}

Raft 与 Paxos 最直观的差别是：**Raft 只有一个 Leader，所有写都必须经过它**。

| | Paxos / Multi-Paxos | Raft |
|---|---|---|
| 写请求入口 | 任何 Proposer 都可以提 | **只有 Leader**，Follower 收到写请求会转发 |
| Leader 的地位 | 优化手段（可省阶段一） | **协议的一等公民**，日志只能从 Leader 单向流向 Follower |
| 日志顺序 | 各日志项独立，可乱序定序 | **强制连续**，不存在空洞（Leader 的日志才是真相） |

**"日志强制连续、只能单向下发"带来一个巨大的工程收益**：**Follower 的日志只可能"落后"，不可能"分叉出不同内容"**。凡是分歧，都可以用"Leader 覆盖 Follower"来收敛——这让实现和调试都简单得多。代价是灵活性下降（不能在多个节点并发提日志）。

### 4.2 三个子问题 {#raft-subproblems}

Raft 把共识拆成三个可独立讲清的问题，这是它"易理解"的直接来源：

**① Leader 选举（Election）**

```text
Follower 在【选举超时】内没收到 Leader 心跳 → 转为 Candidate
  → term + 1，投自己一票，向所有节点发 RequestVote
  → 拿到多数派票 ⇒ 成为 Leader，立刻发心跳压制其他节点
  → 发现别人的 term 更大 ⇒ 退回 Follower
```

三个关键机制：

| 机制 | 解决的问题 |
|---|---|
| **任期号 `term` 单调递增** | 全局逻辑时钟：term 小的消息一律被忽略，旧的 Leader 一旦发现自己 term 落后就会退位 |
| **随机选举超时（如 150–300ms）** | **打散同时竞选**。若所有节点同时超时，票会被瓜分导致无人过半，进入新一轮——随机化让"某个人先超时"几乎必然发生 |
| **投票限制：只投给"日志不旧于自己"的候选者** | 保证新 Leader 一定包含全部已提交日志（见 4.4 的第一条约束） |

**② 日志复制（Log Replication）**

```text
客户端写 → Leader 追加到本地日志
        → 并发发 AppendEntries 给所有 Follower
            携带 prevLogIndex / prevLogTerm 做【一致性检查】
            · 匹配 → 追加，返回成功
            · 不匹配 → 返回失败，Leader 回退一格重试
        → 多数派成功 ⇒ Leader 推进 commitIndex
        → Leader 通知 Follower 提交（下一个心跳携带新 commitIndex）
        → 各节点把已提交条目【应用到状态机】
```

两个容易被忽略的点：

- **`commitIndex`（已提交）≠ `lastApplied`（已应用）**。提交是"日志已获多数派确认"，应用是"操作真的执行到状态机上"。两者之间必然有延迟，**所有"读到最新数据"的保证都以应用完成为准**——这也是为什么主从切换后可能出现"读到的还是旧值"（新 Leader 的应用进度落后于提交进度）。
- **日志改写的代价被"一致性检查"挡住了**：`prevLogIndex/prevLogTerm` 让 Follower 能精确定位分歧起点，Leader 从该点开始覆盖，而不用整份重传。

**③ 成员变更（Membership Change）**

必须**一次只变更一个节点**，且新旧配置通过**联合共识（Joint Consensus）**或单节点变更过渡。原因在第二节已给出：任何时刻都不能出现"两个不相交的多数派"，一次性改多台就可能制造出这种配置。

### 4.3 日志压缩：Snapshot {#raft-snapshot}

日志会无限增长，所以要有**快照**：把状态机在某个 `lastIncludedIndex` 的状态整体落盘，之前的日志即可丢弃。

一个实现上常被忽略的要求：**快照必须与日志一起原子替换**。如果先删日志、写快照一半时进程崩溃，节点重启后既没有旧日志也没有完整快照，只能从 Leader 全量重传——在数据量大时这等同于长时间不可用。工程做法是先写新快照文件、`fsync`、再原子 `rename` 覆盖，最后才截断日志。

### 4.4 两条必须记住的安全约束 {#raft-safety}

Raft 的多数机制都很直观，但**有两条约束反直觉，且实现时最容易漏**：

| # | 约束 | 漏掉的后果 |
|---|---|---|
| 1 | **选举限制**：候选者的日志必须"不旧于"投票者的日志（比较 `(lastLogTerm, lastLogIndex)`）才能拿到票 | 一个日志落后的节点可能当选 Leader，而 Raft 的日志只能**由 Leader 流向 Follower** → 已提交的日志被永久抹掉 |
| 2 | **Leader 只能提交"自己当前任期"的日志**（靠一条当前任期的空条目"钉"住） | 出现经典的"已提交条目被覆盖"反例：Leader 复制了旧任期的条目到多数派后崩溃，新 Leader 不含该条目 → 它被覆盖，而客户端此前已收到成功响应 |

第 2 条是 Raft 论文里最著名的陷阱，也是面试区分度的分水岭：**"为什么新 Leader 上位后要先提交一条空日志？"** ——因为**只有这样，它才能安全地把前任遗留的日志一并纳入提交**。题目看似在问细节，实际在问"你知不知道'多数派复制'和'已提交'之间隔着一条任期边界"。

## 五、脑裂：为什么共识协议能杜绝它 {#split-brain}

**脑裂的定义**：网络分区后，两侧都认为自己是主，同时接受写入 → 数据分叉，且恢复后无法自动收敛。

**共识协议杜绝它的机制**：少数派一侧凑不够多数票，既选不出 Leader 也提交不了写——它只能**拒绝服务**（表现为这类系统在分区时"宁可不可用"）。这正是 CAP 里 CP 取向的具体实现。

但要注意**它成立的前提条件**：

```text
① 判定必须基于【多数派】而非【全员】
   · 若采用"全员确认"，一台宕机就永久阻塞 → 那是牺牲 A 换不来 C，只是坏了
② 投票信息必须【持久化】
   · 投票记录与 term 若只在内存，节点重启后可能在同一任期重复投票 → 两个 Leader
③ 时钟只用于【超时判断】，不能用于定序
   · 用物理时钟排序会因时钟漂移而错乱，所以才有 term 这种逻辑时钟
```

**反面教材正好在站内**：RabbitMQ 的镜像队列（[RabbitMQ 高可用](/middleware/rabbitmq/high-availability)）没有共识协议，选主"不严谨"——它可能选出一个**数据还没同步完**的镜像作为新主，且分区时可能同时出现两个主节点。这就是它被标记 deprecated、由基于 Raft 的仲裁队列取代的根本原因。**判断一个高可用方案靠不靠得住，只需要问一句：它选主时用的是多数派，还是"谁先发现"？**

## 六、落地对照：谁在用哪个协议 {#practice}

| 系统 | 协议 | 用在哪 | 值得注意 |
|---|---|---|---|
| **etcd / Consul** | Raft | 元数据、KV、分布式锁、服务发现 | K8s 的整个控制平面依赖 etcd 的一致性，**etcd 不可用则集群无法变更** |
| **ZooKeeper** | **ZAB** | 元数据、选主、分布式锁 | 与 Raft 同族（Leader + 任期 + 多数派），差别是**选举与广播是两个独立阶段**，且用 `zxid`（epoch + 计数器）标识顺序 |
| **RabbitMQ 仲裁队列** | Raft | 队列数据复制 | 推荐 3 或 5 副本；相比镜像队列拿到"不丢消息 + 严格选主" |
| **Kafka KRaft** | Raft | 元数据管理（取代 ZooKeeper） | 2.8 引入、3.3 起生产可用；**只把元数据交给 Raft，消息数据仍走 ISR 主从复制**——这是"该用共识的地方才用"的范例 |
| **RocketMQ Controller** | Raft | **只负责选主**，数据同步仍用原生 CommitLog | DLedger 之所以被废弃，正是因为"数据也走 Raft 日志"带来额外 IO；Controller 模式把选主与数据同步拆开，各取所长 |
| **Nacos（非临时实例）** | Raft（JRaft） | 配置数据、持久实例 | 临时实例走 Distro（AP），**同一个组件里两种取向并存** |

**这张表最值得带走的一条判据**：**共识协议是昂贵的一致性，只应该用在"读错会出大问题"的数据上**。Kafka 与 RocketMQ 都做了同一个选择——**元数据（谁是主、分区在哪）用 Raft，海量业务数据用更轻的复制**。把全部数据塞进共识协议，是这条路线上最常见的过度设计。

## 七、常见坑 {#pitfalls}

| 坑 | 正确认识 |
|---|---|
| **把 CAP 当共识协议讲** | 两者不是一个层次：CAP 是**取舍判据**（分区时选 C 还是 A），共识协议是**实现手段**（怎么在多副本上定序）。CAP 不告诉你怎么做 |
| **以为 3 副本必然容 1 故障** | 还要看写入确认数。`min.insync.replicas` 配置不当，3 副本也可能丢数据（见第二节） |
| **混淆"已提交"与"已应用"** | 两者之间有窗口。主从切换、Follower 读旧值都源于此 |
| **以为 Raft 不会卡住** | 分区持续存在时，少数派会不断超时、不断加 `term`（**term 膨胀**），恢复后大量高 term 消息会迫使 Leader 退位，造成二次抖动。生产上要关注 `term` 变化速率 |
| **跨机房部署 Raft** | 共识需要多数派 RPC 往返，跨机房延迟会直接放大写延迟，且抖动容易触发"选举风暴"。**多数派应部署在同城低延迟区**，异地只做非投票的副本或异步备 |
| **选主窗口被忽略** | 故障转移时间 = 选举超时 + 新一轮投票 + 日志追赶。**副本数据量越大，追赶越久**，这段时间不可写。这是"高可用"需要压测验证的原因，不能只看架构图 |
| **把"有副本"当作"高可用"** | 高可用是三件事：**数据不丢（共识复制） + 访问不断（负载均衡与 VIP） + 连接自愈（客户端重试）**，缺一不可 |

## 面试口径 {#interview}

- **共识协议解决什么**：基于**复制状态机**——相同初始状态 + 相同顺序的确定性操作 = 相同最终状态。所以它真正保证的是**日志顺序一致**，数据一致是推论。
- **为什么用奇数副本**：多数派是 `⌊N/2⌋+1`，偶数副本的容错能力等同于少一台（4 副本与 3 副本都只能容 1 台故障）。
- **Paxos 两阶段**：Prepare/Promise（锁票 + 继承已接受的最高编号提案）→ Accept/Accepted（多数派接受即选定）。核心不变式是"**已被接受的值，后续提案必须继承**"。**它只保证 Safety，不保证 Liveness**（有活锁）。
- **Paxos 与 Raft 的区别**：Raft 是**强 Leader、日志强制连续、只能单向下发**；Multi-Paxos 的 Leader 是可省的优化、日志项之间独立。设计目标上，Raft 追求**可理解与可直接实现**。
- **Raft 三个子问题**：Leader 选举（term + 随机超时 + 受限投票）、日志复制（`prevLogIndex/prevLogTerm` 一致性检查 + `commitIndex`）、成员变更（一次只改一个节点）。
- **两条安全约束**：① 只投给**日志不旧于自己**的候选者；② Leader **只能提交当前任期的日志**（靠一条当期的空条目）。漏掉任一条都会导致**已提交日志被覆盖**。
- **脑裂为什么不可能**：少数派凑不够多数票。前提是**基于多数派判定 + 投票持久化**；时钟只用于超时，定序靠 `term` 这类逻辑时钟。
- **落地怎么选**：元数据、选主、分布式锁用共识协议（etcd/ZAB/Raft）；海量业务数据用更轻的复制（Kafka ISR、RocketMQ 原生 CommitLog）。**Kafka 与 RocketMQ 都是"元数据 Raft、数据不走 Raft"**——共识是昂贵的一致性，别滥用。
