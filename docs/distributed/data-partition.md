# 一致性哈希与数据分布

这是分布式系统里少见的"**一个算法就能讲清全部收益**"的主题。起因是一个很具体的问题：

> 数据要分散到 N 个节点上，规则是 `hash(key) % N`。现在节点从 N 变成 N+1，会发生什么？

答案是：**几乎所有数据都要搬家**。因为 `% N` 和 `% (N+1)` 之间没有连续性——同一个 key 在两个模数下的结果几乎必然不同。3 个节点扩到 4 个，约 **3/4 的数据需要迁移**；100 台扩到 101 台，约 **100/101 需要迁移**。

这个代价不是"多搬一会儿数据"，而是：迁移期间**缓存大规模失效**（请求穿透到数据库）、**集群带宽打满**、**迁移本身又触发新一轮超时**。一致性哈希就是为了把这件事的代价从"几乎全部"降到"约 1/N"。

## 一、哈希环：把节点和数据放到同一个圆上 {#ring}

做法只有一步，但很关键：**不再用取模定位节点，而是把"节点"和"数据"都哈希到同一个值域，再规定一个寻找规则。**

```text
① 把哈希值域首尾相接成一个环（如 0 ~ 2^32-1）
② 每个【节点】用它的标识哈希出一个位置，落在环上
③ 每个【数据 key】也哈希出一个位置
④ 规则：从 key 的位置【顺时针】找，遇到的第一个节点就是它的归属
```

```
                 0 / 2^32
                     │
        ┌────────────┼────────────┐
        │                         │
   key C ●──▶ node A              │
        │                         │
   node A ●                       │
        │                    node C ●
   key A ●──▶ node B              │
        │                         │
   node B ●                   key B ●──▶ node C（绕回）
        │                         │
        └────────────┬────────────┘
                     │
        key 顺时针找到的第一个节点 = 归属节点
```

### 1.1 为什么迁移量只有 1/N {#why-1n}

**加一个节点时，只有新节点"顺时针前一段"上的数据需要移动**，其余 key 的归属完全不变：

| 操作 | 受影响的 key | 占比 |
|---|---|---|
| 增加 1 个节点（N → N+1） | **只有新节点顺时针前一个节点的一段区间** | 约 `1/(N+1)` |
| 移除 1 个节点 | **只有该节点自身的区间**，交给它的后继 | 约 `1/N` |

**这就是"一致性"这个词的来源**：节点集合变化时，**绝大多数 key 与节点的映射关系保持一致**。对比取模：

| 路由方式 | 3 → 4 节点时需迁移 | 100 → 101 时需迁移 |
|---|---|---|
| **取模 `% N`** | 约 **3/4** | 约 **100/101**（几乎全部） |
| **一致性哈希** | 约 **1/4** | 约 **1/101** |

> **值得追问的一层**：一致性哈希解决的是"**迁移量**"，不是"**不迁移**"。扩容终究要搬数据，它只是把搬的量级从 O(全部) 压到 O(1/N)。**判断一个方案好不好，看的应该是"扩容时动了多少数据"，而不是"有没有动数据"。**

### 1.2 虚拟节点：解决"节点间不均衡"，不解决"热点" {#virtual-nodes}

哈希环有一个直接缺陷：**物理节点少的时候，它们落在环上的位置是随机的**，很可能两个节点挤在一起、另一大段空白——于是某个节点圈走了远超平均的数据。

解法是**虚拟节点（Virtual Node）**：不再为每个物理节点在环上放 1 个点，而是放几百个点，每个点都映射回同一个物理节点。

```text
不均衡：                      虚拟节点后：
  ● A                          ● A-1  ● B-1  ● C-1  ● A-2
     ● B          →               ● B-2  ● C-2  ● A-3
              ● C                    ● B-3  ● C-3  ● B-4
（A 圈走一大段，B、C 挤一起）      （每个物理节点的 vnode 散布开，自然均匀）
```

| 项 | 结论 |
|---|---|
| 每个物理节点配多少个虚拟节点 | 经验值 **100～250** 个；数量越大越均匀，元数据与查找成本也越大 |
| 解决什么 | **节点间数据量不均衡**（有的节点撑死、有的闲着） |
| **不解决什么** | **数据本身的热点**——如果某个 key 被高频访问，它在环上只有 1 个位置，虚拟节点再多也只会把"这个 key"锁在那一个节点上 |

**这个区分非常实用**：遇到"某个节点 CPU 明显高于其他"的症状，要先分清是**分布不均**（虚拟节点太少、节点权重没配）还是**热点 key**（业务上某几个 key 访问量畸高）。前者调虚拟节点数，后者只能靠**业务拆分或本地缓存**——一致性哈希对它无能为力。

## 二、工程变体：从哈希环到哈希槽 {#variants}

哈希环是"**隐式计算**"：节点的归属靠"顺时针找第一个"现场算出来。这在节点少、变化少时很好，但在需要**精确控制迁移**的场景下就会暴露问题——你没法说"把 A 节点的 1/3 数据迁到 B"，因为数据是连续区间，切在哪不由你决定。

于是有了**哈希槽（Hash Slot）**方案，Redis Cluster 是典型：

| | 一致性哈希环 | Redis Cluster 哈希槽 |
|---|---|---|
| 路由方式 | 环 + 顺时针查找（隐式） | `CRC16(key) % 16384` 得槽号，再查"槽 → 节点"映射表（**显式**） |
| 迁移单位 | 环上的一段区间 | **槽**（一个槽就是一个明确可搬运的单位） |
| 迁移可控性 | 差（区间边界由哈希决定） | **强**（运维可指定迁哪几个槽、迁多少） |
| 映射表大小 | 与虚拟节点数成正比 | 固定 16384 项，且可用**位图**表达 |

**为什么是 16384 而不是 65536？** 这个数字有三个约束共同决定：

1. **心跳包体积**：集群节点间通过 Gossip 交换"我负责哪些槽"，用**位图**表示。16384 bit = 2KB，65536 bit = 8KB——后者在每秒多次心跳时是显著的带宽负担；
2. **节点规模**：Redis 集群的设计规模通常在千节点以内，16384 个槽给每个节点平均分配已经足够均匀；
3. **位图压缩**：槽数越多，位图越稀疏，压缩效果越差（槽数少时"连续一段全 1"更常见，压缩率高）。

**四种数据分布方式的定位**：

| 方案 | 路由结构 | 迁移单位 | 适合 | 代表 |
|---|---|---|---|---|
| **取模** | `hash % N` | 无（几乎全部重排） | 节点数固定不变的场景 | 早期缓存客户端 |
| **一致性哈希** | 环 + 虚拟节点 | 环上区间 | 节点动态增减、无范围查询 | Cassandra、Memcached 客户端 |
| **哈希槽** | 固定槽数 + 映射表 | 槽 | 需要精确控制迁移 | Redis Cluster |
| **Range 分区** | 有序区间表 | 区间（可自定义切分点） | **范围查询友好** | HBase、TiKV、MongoDB |

**Range 分区值得单独说一句**，因为它与哈希的思路相反：**按 key 的有序区间切分**（如 `user_id` 0–100 万一块）。好处是范围查询（`WHERE id BETWEEN ...`）只打少数几个分片；代价是**极易热点**——如果 key 单调递增（自增 ID、时间戳），写入会全部落在**最后一个区间**上。

> **一条选型判据**：**哈希类方案牺牲范围查询换均匀，Range 类方案牺牲均匀换范围查询**。所以业务主键常做"哈希分片"、时序数据常做"Range 分片"。想两者兼得，就用**组合键**：以时间做 Range 前缀、以设备 ID 做哈希后缀（如 `date + hash(deviceId)`），让同一时间段内写入均匀散开。

## 三、路由在谁手上：三种位置 {#routing}

数据分片后，"客户端怎么知道该找哪个节点"有三种实现位置，代价完全不同：

| 方式 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **客户端路由** | 客户端持有分片规则/映射表，直接连目标节点 | 无中间跳数，延迟最低 | 规则变更要下发到所有客户端；多语言客户端需各实现一遍 |
| **代理路由** | 客户端连代理（如 `twemproxy`、Codis），代理转发 | 客户端零改造 | **多一跳**，代理成为吞吐瓶颈与单点（需自身集群化） |
| **服务端重定向** | 客户端随便连一个节点，节点发现不归自己就返回重定向 | 客户端逻辑简单、无需维护映射表 | **可能多一次往返**（先被拒再重试） |

**Redis Cluster 用的是第三种，且区分了两种重定向**——这个细节很能说明工程取舍：

| 重定向 | 触发场景 | 客户端行为 |
|---|---|---|
| **MOVED** | key 的所属槽**已经**永久属于另一个节点 | **更新本地槽映射表**，以后直接连新节点 |
| **ASK** | key 的所属槽**正在迁移中**，且该 key 已在目标节点 | **只这一次**转发到目标节点，**不更新**本地映射表 |

**ASK 的存在正是为了"迁移期间还能正确读写"**：槽正在迁移时，映射表还没改，若客户端把 ASK 当 MOVED 处理并更新映射，就会在迁移完成前把请求全部打到新节点，而旧数据可能还留在源节点上 → 读到空值。

## 四、再平衡：真正难的是迁移期间 {#rebalance}

**扩容三阶段**（也适用于减容）：

```text
① 准备：新节点加入，但先不接管任何数据（对读写无影响）
② 迁移：按单位（槽/区间）逐个搬运
         · 搬一个，切换一个的归属（可分批、可暂停、可回滚）
         · 期间对同一数据的读写要【都能正确路由】→ 靠 ASK/双写
③ 收尾：映射表全量生效，清理旧节点上的残留
```

**迁移期间的三条一致性要求**（缺一条就会读到脏数据）：

| 要求 | 说明 |
|---|---|
| **读要能兜底** | 若新位置没有该 key，要回源到旧位置读（Redis 的 `ASKING` 命令即为此设计） |
| **写不能丢** | 迁移中的 key 是"先写新、后删旧"还是"双写"，必须明确；**先删后写会丢数据** |
| **迁移要可中断** | 大批量迁移应分批、可暂停。一次迁太多会打满带宽、拖垮源节点，**故障往往不是发生在迁移本身，而是发生在"迁移把线上拖垮"** |

> **一条容易被忽略的判据**：**迁移速度不由带宽决定，由"源节点的可承受负载"决定**。所以生产上要给迁移**限速**，并且**优先在业务低峰做**——扩容窗口选在白天，是"扩容导致故障"最常见的原因。

## 六、常见坑 {#pitfalls}

| 坑 | 正确认识 |
|---|---|
| **虚拟节点只配几个** | 虚拟节点太少等于没配（每节点 10 个点，环上仍可能严重不均）。经验值 **100～250** |
| **以为一致性哈希能防热点** | 它只均匀**数据量**，不分散**访问量**。热点 key 要靠业务拆分或本地缓存 |
| **节点"权重"当摆设** | 新机器配置更好、期望多分数据时，**两种实现**：多配虚拟节点（哈希环）或直接指定槽数（哈希槽）。不加权重就是强行平均，浪费了硬件差异 |
| **扩容时忽略"迁移本身的压力"** | 迁移＝源节点读 + 网络传 + 目标节点写，**三份开销叠加到线上**。必须限速 + 低峰执行 |
| **把 ASK 当 MOVED 处理** | 会导致迁移期间读到空值。见第三节 |
| **把一致性哈希当成"强一致"** | 它只解决**分布**，不解决**副本一致性**。"一致性哈希"里的"一致性"指的是**映射关系的稳定性**，与 CAP 里的 C 是两回事 |
| **Range 分片配单调递增的 key** | 写入全部压到最后一个分片。要么改哈希，要么用"时间 + 哈希"组合键 |
| **忘记给分片键加唯一约束的兜底** | 分片规则变了（换哈希算法、改槽数）意味着**全量重排**，历史数据必须能靠"双写 + 校验"过渡，不能只改配置 |

## 面试口径 {#interview}

- **取模为什么会崩**：`% N` 与 `% (N+1)` 无连续性，节点数一变几乎全部 key 的归属都变 → 缓存大规模失效、迁移量 O(全部)。一致性哈希把它降到 **O(1/N)**。
- **一致性哈希的原理**：节点与 key 都哈希到同一个**环**上，key 顺时针找到的第一个节点即归属。**增删节点只影响环上一段区间**，故称"一致性"。
- **虚拟节点的作用**：物理节点少时环上分布不均 → 每个物理节点映射成 100～250 个虚拟节点，使分布趋于均匀。**它解决"数据量不均衡"，不解决"访问热点"**。
- **哈希环 vs 哈希槽**：环是**隐式**路由（顺时针找）、迁移边界由哈希决定；槽是**显式**映射（`CRC16 % 16384` + 槽→节点表）、**迁移单位明确可控**，且能用位图在 Gossip 中高效传递。Redis Cluster **16384** 这个数字由心跳位图体积（2KB vs 8KB）、节点规模、位图压缩率共同决定。
- **两种重定向**：**MOVED** = 槽已永久移走，客户端**更新**本地映射；**ASK** = 槽迁移中，**只转发这一次、不更新**映射（否则会读到空值）。
- **扩容三阶段**：准备（加入但不接管）→ 迁移（按单位搬、可分批可暂停）→ 收尾（映射生效）。关键是**迁移必须限速、低峰执行**——迁移本身的开销（源读 + 网络 + 目标写）才是风险源。
- **选型判据**：**哈希类牺牲范围查询换均匀，Range 类牺牲均匀换范围查询**。要兼得就用"时间前缀做 Range + 设备/用户 ID 做哈希"的组合键。
- **别混淆概念**：一致性哈希的"一致性"指**映射关系的稳定性**，与 CAP 的 C（线性一致）无关。
- **延伸**：共识协议与选主见[共识协议](/distributed/consensus)；分片落地与跨库代价见[分库分表](/database/sharding/)；哈希函数与冲突处理见[线性结构](/fundamentals/algorithms/linear#hash-table)。
