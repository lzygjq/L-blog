# IO 模型与多路复用

> 上一篇：[虚拟内存与内存管理](/fundamentals/os/memory)　|　下一篇：[文件系统与文件描述符](/fundamentals/os/filesystem)

这一篇讲的是**内核视角的 IO**：数据怎么从设备进到内存、进程怎么知道"可以读了"、以及"等"这件事有几种不同的处理方式。

> **和 [IO 与 NIO](/java/basics/io-nio) 的分工**：那篇讲的是 **Java 视角**——`InputStream` 的装饰器体系、`Buffer` 的三个指针、`Selector` 的 API 用法、`transferTo` 怎么调。**本篇讲的是这些 API 底下调用了什么、内核里发生了什么。** 两篇的边界是"机制与原理 vs 落地与用法"：机制在本篇，API 在那篇。

**先把结论放前面**：

1. **网络 IO 的本质是「两次等待 + 两次拷贝」**。所有 IO 模型讨论的都是怎么处理那两次等待——**等数据到达内核、等数据拷到用户空间**。
2. **同步与异步的分界线在「数据拷贝阶段是否阻塞调用方」**。按这条线，**前四种模型（阻塞、非阻塞、多路复用、信号驱动）都是同步 IO**；只有异步 IO 连拷贝都不让调用方等。所以 **Java NIO 是"同步非阻塞"，不是异步**。
3. **`epoll` 快在哪**：`select`/`poll` 每次调用都要**把整个 fd 集合拷进内核 + 线性遍历**；`epoll` 把 fd 集合维护在内核（红黑树存 fd、就绪链表存结果），**一次注册长期有效，只返回就绪的**。连接数越多，差距越大——这就是 C10K 的解法。
4. **`epoll` 在 2026 年依然是绝大多数网络服务的正确默认**。`io_uring` 是"统一的异步 IO 接口"，优势在磁盘与网络混合、批量提交、可省系统调用，但**有内核版本与安全面（容器常默认屏蔽）的约束**，而且是"重构成 ring 模型才有收益"，不是把 `epoll` 改个名字。

## 一、问题场景：为什么 IO 是性能问题的常客 {#why-io}

先建立一个量级感——这是理解"为什么要搞这么多模型"的前提：

| 操作 | 典型延迟量级 | 相对 CPU 的倍数（以 1 个 CPU 周期 ≈ 0.3ns 计） |
|---|---|---|
| L1 缓存访问 | ~1ns | 几个周期 |
| 主内存访问 | ~100ns | 数百倍 |
| **同一机房网络往返（RTT）** | ~0.1~0.5ms | **约百万倍** |
| **SSD 随机读** | ~0.1ms | **约百万倍** |
| **机械磁盘随机读** | ~5~10ms | **千万倍量级** |

**结论**：**IO 比计算慢了几个数量级**。所以现代服务性能优化的主战场从来不是"把循环写快一点"，而是**别让 CPU 白白等着 IO**。

而"等"这件事，正是这一篇要拆的东西。**同一个"等"，内核提供了五种不同的处理方式，它们的差别决定了你的服务能扛多少并发。**

## 二、一次 IO 在内核里经历了什么 {#kernel-path}

### 2.1 网络收包：从网卡到 socket 缓冲区 {#recv-path}

```text
   网卡收到数据帧
        │
        ▼ ① 网卡 DMA 把帧写进内核预分配的 **ring buffer**（不经过 CPU）
        │
        ▼ ② 网卡发**硬中断**：告诉 CPU"有包来了"
        │     （中断处理要快，否则丢包；现代用 NAPI：只做最简单的登记）
        │
        ▼ ③ 软中断 / ksoftirqd 线程：**NAPI poll** 批量收包
        │     ─ 关中断 + 轮询（poll）把 ring buffer 里的包批次取走
        │     ─ 这就是"中断 + 轮询"的混合策略：高负载下轮询更划算
        │
        ▼ ④ 协议栈逐层处理：链路层 → IP 层 → TCP 层
        │     ─ 校验、去重、按序号拼装、递交给对应 socket
        │
        ▼ ⑤ 数据放进 socket 的**接收缓冲区**（内核内存）
        │     ─ 更新接收窗口；若是 ACK 之外的唤醒条件，**唤醒等待的进程**
        │
        ▼ ⑥ 进程被唤醒（或 epoll 报告可读）→ 调用 read()
        │
        ▼ ⑦ **拷贝**：内核 socket 缓冲区 → 用户缓冲区
              ← 这一步就是"第二次等待"发生的地方
```

**三个值得记住的点**：

| 点 | 说明 |
|---|---|
| **DMA 让 CPU 不参与搬运** | 网卡直接写内存，所以"收包"本身不烧 CPU——**烧 CPU 的是协议栈处理与后面的拷贝** |
| **软中断（`si`）高说明收包量大** | `top` 里 `si` 高通常意味着网络流量大；`ksoftirqd` 吃满一个核是典型的收包瓶颈 |
| **socket 接收缓冲区是"泄压阀"** | 进程读得慢 → 缓冲区满 → 通告窗口变小 → 发送方被迫降速（这就是**流量控制**，见 [TCP 核心机制](/fundamentals/network/tcp#congestion)） |

**这里能解释一个常见的排查困惑**：`ss -lnt` 看到 `Recv-Q` 非 0（已建立连接下）意味着**应用没及时把数据读走**——不是网络问题，是应用处理慢。

### 2.2 块设备 IO：从 `read` 到磁盘 {#block-path}

```text
   read(fd, buf, n)
        │
        ▼ ① VFS 分流：这个 fd 是什么文件系统上的什么文件
        │
        ▼ ② 查**页缓存**（见 [页缓存](/fundamentals/os/memory#page-cache)）
        │     命中 → 拷贝到用户缓冲区，**结束（不碰磁盘）**
        │
        ▼ ③ 未命中 → 构造 bio（块 IO 请求），交给**块层**
        │
        ▼ ④ IO 调度器排序合并（none / mq-deadline / kyber / bfq）
        │     ─ 同一磁道的请求合并（机械盘重要）
        │     ─ 现代 NVMe 多队列设备上 `none` 往往最优（设备自己会调度）
        │
        ▼ ⑤ 驱动下发命令 → 设备 DMA 把数据写进页缓存
        │
        ▼ ⑥ 完成中断 → 唤醒等待的进程 → 回到步骤 ② 的"命中"分支
```

**两个工程结论**：

1. **`iostat` 的 `%util` 是"设备有请求在处理的百分比"，不是"繁忙度"**。对能并行处理多请求的 NVMe，`%util` 到 100% 不代表到瓶颈（要看 `aqu-sz` 队列深度与 `await`）。
2. **IO 调度器的选择是设备相关的**：机械盘需要合并排序（`mq-deadline`/`bfq`），NVMe 通常直通（`none`）。

## 三、五种 IO 模型 {#five-models}

### 3.1 分界线：拷贝阶段是否阻塞 {#sync-async}

```text
                          ① 等数据到达内核    ② 数据拷到用户空间
   阻塞 IO           │    阻塞             │    阻塞
   非阻塞 IO         │   不阻塞（轮询）      │    阻塞
   IO 多路复用        │   阻塞在 select/epoll│    阻塞
   信号驱动 IO        │   不阻塞（等信号）    │    阻塞
   ─────────────────┼────────────────────┼─────────────────
   异步 IO           │   不阻塞            │   **不阻塞**（内核拷完才通知）
                                            ↑
                              分界线在这一列：前四种都算**同步 IO**
```

**这条分界线是"Java NIO 是不是异步"这个高频争议的标准答案**：`Selector` 告诉你"可以读了"，你还是得自己调 `read` 去把数据从内核缓冲区拷到用户缓冲区——**这一步你在等，所以它是同步 IO**。

### 3.2 五种模型逐个说 {#five-models-detail}

| 模型 | 机制 | 优点 | 致命缺点 |
|---|---|---|---|
| **阻塞 IO** | `read` 一直等，直到有数据并拷完 | 最简单，代码直白 | 一连接一线程，线程数与连接数绑定 |
| **非阻塞 IO** | `read` 立即返回（没数据时返回 `EAGAIN`） | 不让出 CPU 给"等待" | **轮询空转烧 CPU**，单独使用无意义 |
| **IO 多路复用** | 一个线程等**多个 fd**：`select`/`poll`/`epoll` | **少量线程管大量连接** | 仍需自己拷贝；编码复杂（半包、事件注册时机） |
| **信号驱动 IO** | 注册 `SIGIO`，内核有数据时发信号 | 等待期不阻塞 | 信号语义差（不排队、可能丢），**Java 不支持** |
| **异步 IO** | 提交请求，内核完成全部工作后通知 | 真正不阻塞 | Linux 上长期不成熟（`io_uring` 才改善） |

**为什么"非阻塞 IO"不能单独用**：因为它把"等待"变成了"反复问"。一个线程反复问一个 fd 是浪费；**只有当"问一次能覆盖很多 fd"时，轮询才划算** —— 这正是多路复用的立足点：

```text
   非阻塞 IO 单独用：          多路复用：
   while(true) {               while(true) {
     if (read(fd) != EAGAIN)      // 一次系统调用问"这 10000 个 fd 谁就绪了"
       handle();                   epoll_wait(fds, 10000);
   }                            }
   ← N 个 fd 就要 N 次系统调用     ← 1 次系统调用覆盖 N 个 fd
```

### 3.3 阻塞 IO 的瓶颈到底在哪 {#bio-bottleneck}

"一请求一线程"的问题**不在线程创建开销，而在数量级**：

| 成本项 | 量级 | 说明 |
|---|---|---|
| 线程栈内存 | **1MB+ / 线程** | 10K 连接 ≈ 10GB 内存，还没算业务数据 |
| 上下文切换 | 微秒级（含间接成本） | 见 [上下文切换](/fundamentals/os/process-thread#context-switch) |
| 调度开销 | 随线程数上升 | 就绪队列变长，调度器与锁竞争加剧 |
| **真正浪费的** | — | **这些线程绝大部分时间阻塞在 `read` 上什么都不做** |

**改进的三条路**（按工程实际的主流程度排）：

1. **IO 多路复用 + 少量 IO 线程**——**主流**。Netty、Nginx、Redis、大部分网关都在这条路上。
2. **虚拟线程 / 协程**——用"写作像阻塞、调度像异步"绕过复杂度（见 [协程与虚拟线程](/fundamentals/os/process-thread#coroutine)）。**代码简单是它最大的优势**，适合新项目或 IO 密集的简单场景。
3. **异步 IO**——理论上最省线程，Linux 上 `io_uring` 之后才真正可用。

## 四、多路复用：select / poll / epoll {#multiplexing}

### 4.1 三者的核心差别 {#select-poll-epoll}

| | `select` | `poll` | `epoll` |
|---|---|---|---|
| 数据结构 | 位图 `fd_set` | 数组 `pollfd[]` | **内核事件表**：红黑树（存 fd）+ 就绪链表 |
| 最大 fd 数 | **1024**（`FD_SETSIZE`，编译期常量） | 无硬限制 | 无硬限制 |
| 每次调用 | 要把**整个集合拷进内核** | 同 `select` | **一次注册（`epoll_ctl`）长期有效** |
| 就绪查找 | 内核**线性遍历**全部 fd，O(n) | 同 `select`，O(n) | **回调把就绪 fd 挂到就绪链表，只返回就绪的**，O(就绪数) |
| 返回值 | 数量 + 需要自己遍历找哪个就绪 | 同 `select` | **直接给出就绪的 fd 列表** |
| 触发模式 | 只有水平触发 | 只有水平触发 | **水平触发（LT）+ 边缘触发（ET）** |
| 适用 | 连接数很少 | 连接数中等 | **高并发长连接** |

```text
   select/poll 每次调用的三个浪费：
   ① 拷贝：用户态的 fd 集合 → 内核（每次都要）
   ② 遍历：内核把整个集合走一遍，挑出就绪的（O(n)）
   ③ 再遍历：用户态拿到"有 3 个就绪"后，还得自己遍历整个集合找出是哪 3 个

   epoll 的三次改造：
   ① fd 一次注册进内核的红黑树，之后不再重复拷贝
   ② 设备就绪时**回调**把 fd 加入就绪链表（不需要主动遍历）
   ③ epoll_wait 直接把就绪链表的**内容**返回给用户（不需要二次遍历）
```

### 4.2 `epoll` 的三个 API 与两个模式 {#epoll-internals}

```c
int epfd = epoll_create1(0);                        // 创建 epoll 实例（内核里那棵红黑树 + 就绪链表）

struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET;                      // 监听可读，边缘触发
ev.data.fd = fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);            // 注册（只做一次，之后长期有效）

struct epoll_event events[1024];
while (1) {
    int n = epoll_wait(epfd, events, 1024, -1);     // 阻塞直到有 fd 就绪，返回就绪数量
    for (int i = 0; i < n; i++) { /* 直接处理 events[i]，不用自己找 */ }
}
```

### 4.3 水平触发 vs 边缘触发 {#et-lt}

| | 水平触发（LT，默认） | 边缘触发（ET） |
|---|---|---|
| 通知条件 | **只要还有数据可读，就一直通知** | **只在状态发生变化时通知一次** |
| 读的方式 | 可以只读一部分，下次还会通知 | **必须循环读到 `EAGAIN`**，否则剩余数据可能永远不通知 |
| 是否必须非阻塞 | 不必须 | **必须**（否则最后一次 `read` 会永久阻塞） |
| 优点 | 编程简单、不容易丢事件 | 减少通知次数与系统调用（**高并发下更省**） |
| 缺点 | 就绪 fd 多时会多轮唤醒 | **写错就丢事件**，调试困难 |

**ET 模式的标准写法**必须是这样：

```c
// ① fd 必须设为非阻塞
fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK);
// ② ET 模式下必须读到 EAGAIN（表示"真的读干净了"）
while (1) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n == -1) {
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;   // 读干净了，正常退出
        if (errno == EINTR) continue;                          // 被信号打断，重试
        /* 其他错误：关闭连接 */ break;
    } else if (n == 0) { /* 对端关闭 */ break; }
    handle(buf, n);
}
```

### 4.4 `epoll` 的四个坑 {#epoll-pitfalls}

| 坑 | 现象 | 原因与解法 |
|---|---|---|
| **惊群（thundering herd）** | 多进程/多线程同时 `epoll_wait` 同一个 fd，一个事件唤醒全部 | `EPOLLEXCLUSIVE`（4.5+，只唤醒一个）；或改用 **`SO_REUSEPORT`** 由内核把 accept 队列分片 |
| **`EPOLLONESHOT` 用混** | 同一个 fd 的事件被两个线程同时处理 | 用 `EPOLLONESHOT` 让事件只触发一次，处理完重新注册 |
| **忘记处理 `EPOLLERR`/`EPOLLHUP`** | 连接已断但一直触发事件，CPU 空转 | 必须处理这两个事件类型，及时关闭 fd |
| **`accept` 后没设非阻塞** | 一个慢连接卡住整个 IO 线程 | accept 出来的 fd 也要 `O_NONBLOCK` |

> **`accept` 的 `EAGAIN` 场景**：多进程共享监听 fd 时，A 进程的 `epoll_wait` 被唤醒，但连接已被 B 进程 `accept` 走，此时 A 的 `accept` 返回 `EAGAIN`——**这是正常现象，不是错误**，正确处理是忽略它继续等待。

## 五、零拷贝 {#zero-copy}

### 5.1 传统 `read` + `write` 的代价 {#traditional-copy}

**把文件内容通过网络发出去**（这是"零拷贝"最经典的场景）：

```text
   read(file, buf, len)  ─┬─ ① DMA 拷贝：磁盘 → 内核页缓存
                          └─ ② CPU 拷贝：内核页缓存 → **用户缓冲区**
   write(socket, buf, len) ┬ ③ CPU 拷贝：**用户缓冲区** → socket 缓冲区
                           └ ④ DMA 拷贝：socket 缓冲区 → 网卡

   = 4 次拷贝（其中 2 次是 CPU 参与）+ 4 次用户态/内核态切换
```

**问题很明显**：数据只是"路过"用户空间，却被完整地搬进搬出两趟。**"零拷贝"要消除的就是这两次多余的动作**。

> **对"零"的理解**：它不是"真的不搬数据"，而是**消除 CPU 参与的拷贝**，或**让数据不经过用户态**。所以更准确的说法是"零 CPU 拷贝"或"零用户态参与"。

### 5.2 四种实现 {#zero-copy-ways}

| 方式 | 机制 | 拷贝次数 | 典型 API / 场景 |
|---|---|---|---|
| **`mmap` + `write`** | 把内核页缓存**映射**到用户空间（共享同一块物理页） | 3 次（省掉 ②） | `mmap` + `write`；**需要读写文件内容时**（如索引文件） |
| **`sendfile`** | 数据不经过用户空间，内核内部直接搬运 | 3 次（2 DMA + 1 CPU） | `sendfile(2)`；**纯转发**：静态文件、消息投递 |
| **`sendfile` + SG-DMA** | 只把"页描述符 + 偏移"交给网卡，网卡自己去搬 | **2 次 DMA，0 次 CPU 拷贝** | 需要网卡支持 scatter-gather DMA（**现代网卡普遍支持**） |
| **`splice` / `tee`** | 在两个 fd 之间移动数据（借助管道缓冲）零拷贝 | 视路径 | 代理、转发、日志管道 |

```text
   sendfile + SG-DMA 的路径（最优情况）：

   磁盘 ──DMA──▶ 内核页缓存 ──────┐
                                  │ 只传递"描述符 + 长度"（CPU 不搬数据）
                                  ▼
                              网卡 ──DMA──▶ 网络

   = 数据完全没有进过用户空间，CPU 一次都没搬
```

### 5.3 Java 侧对应什么 {#zero-copy-java}

| Java API | 对应机制 | 注意 |
|---|---|---|
| `FileChannel.transferTo` / `transferFrom` | Linux 上是 `sendfile` | **单次调用有传输上限（不同平台 2GB 或更小），大文件必须循环并累加返回值** |
| `FileChannel.map` | `mmap` | 映射的缓冲区不是堆内存，不受 `-Xmx` 直接管理 |
| `ByteBuffer.allocateDirect` | 堆外内存 | 省掉"堆内 → 堆外"的拷贝；**必须复用**（分配回收成本高） |

**中间件里的落地**（面试官真正想听的）：

| 系统 | 用法 |
|---|---|
| **Kafka** | 日志段投递给消费者走 `sendfile`（`transferTo`），**配合顺序写 + 页缓存**——这是它高吞吐的核心机制之一 |
| **RocketMQ** | 用 `mmap`（`FileChannel.map`）映射 CommitLog 做读写 |
| **Nginx** | 静态文件服务 `sendfile on` |
| **Netty** | `FileRegion`（走 `transferTo`）、`CompositeByteBuf`（组合多个缓冲区避免合并拷贝） |

## 六、`io_uring`：异步 IO 的现代答案 {#io-uring}

### 6.1 为什么 Linux 的"原生 AIO"不好用 {#why-not-aio}

Linux 很早就有 `io_submit` / `io_getevents`（俗称原生 AIO），但它在实践中没成为主流，原因很具体：

| 限制 | 说明 |
|---|---|
| **主要只对 `O_DIRECT` 生效** | 对普通缓冲 IO（`buffered`）支持很差，甚至退化成同步——**而大多数应用用的是缓冲 IO** |
| **只覆盖块设备** | 网络 IO 不在它的范围内 |
| **每个请求一次系统调用** | 没有批量提交，省不了多少开销 |

**所以"Linux 的 AIO 不成熟"这个说法是准确的**——不是 API 不存在，而是**它的覆盖面和可用性不足**。这也是 Java AIO（NIO.2）在高并发下没成为主流的底层原因之一（见 [IO 与 NIO](/java/basics/io-nio#aio-netty)）。

### 6.2 `io_uring` 的机制 {#io-uring-internals}

`io_uring`（Linux 5.1 引入）的思路完全变了：**用户态与内核态共享两块环形队列，用内存映射通信，不用每次陷入内核**。

```text
   用户态                                    内核态
   ┌────────────────┐   ┌────────────────┐
   │  SQ 提交队列     │──▶│  内核读取 SQ     │   ← 用户态写入"我要做什么"
   │  (submission)  │   │  （做 IO）       │
   └────────────────┘   └────────┬───────┘
   ┌────────────────┐   ┌────────▼───────┐
   │  CQ 完成队列     │◀──│  内核写入 CQ     │   ← 内核写回"做完了，结果是什么"
   │  (completion)  │   └────────────────┘
   └────────────────┘
   两块环形缓冲区都由 mmap 共享，正常路径下**连系统调用都可以省掉**
   （可配合 SQPOLL 模式让内核线程轮询 SQ）
```

**它相对 `epoll` 的三个真实增益**：

| 增益 | 说明 |
|---|---|
| **统一的异步接口** | 磁盘、网络、`fsync`、`accept`、`splice`、甚至 NVMe 直通，都在同一个 ring 里提交——**这是 `epoll` 做不到的**（`epoll` 只解决"等就绪"） |
| **批量提交** | 一次 `io_uring_enter` 提交多个请求，把系统调用开销**摊薄** |
| **零拷贝与缓冲注册** | 可以注册固定缓冲区，避免每次映射 |

**它必须知道的代价**：

| 代价 | 说明 |
|---|---|
| **不是免费的性能提升** | 把 `epoll` 的代码直译成 `io_uring` 往往**没有明显收益**（社区基准里甚至能看到小幅回退）。**要重构成"ring 原生"写法**（批量、注册缓冲区、零拷贝收发）才能拿到收益 |
| **内核版本要求高** | 5.1 引入，但接口与稳定性在 5.10~6.x 之间才逐步完善；**生产上建议现代 LTS 内核** |
| **安全面大** | 它是一个很复杂、权限面很宽的接口，历史上出过多个本地提权 CVE。**很多发行版和容器运行时默认限制甚至禁用**：可查 `/proc/sys/kernel/io_uring_disabled`（0 全开 / 1 仅禁非特权用户 / 2 全禁），Docker 一类运行时的默认 seccomp 策略也常屏蔽相关系统调用 |
| **可观测性差** | `strace` 只能看到一次 `io_uring_enter`，看不到里面提交了什么——**得靠 eBPF 或专门的跟踪点** |

### 6.3 定位与选型 {#epoll-vs-uring}

| 场景 | 建议 |
|---|---|
| 普通 Web / API 服务、网关、RPC | **继续用 `epoll`**。生态成熟、可观测性好、运维经验足 |
| 你的运行时不支持（大部分语言的标准运行时都还没默认切） | 用 `epoll`，**不要为了用它而自己写 liburing 层** |
| **磁盘与网络混合的异步引擎**（存储引擎、数据库、自研代理） | 值得认真评估 `io_uring`（NVMe 场景收益最明显） |
| 容器环境 | **先确认它没被 seccomp / sysctl 禁用**，这是最容易白忙一场的地方 |

**一句话总结**：`io_uring` 是自 `epoll` 以来最重要的 IO 接口演进，但它**不是 `epoll` 的替代品，而是另一个层次的东西**——`epoll` 解决"多个 fd 谁就绪"，`io_uring` 解决"如何统一地异步提交与收割 IO"。**2026 年的主流网络服务仍然跑在 `epoll` 上**，这不是技术保守，而是"收益与代价的取舍"。

## 七、对比辨析 {#compare}

| 对比 | 关键差异 | 记忆锚点 |
|---|---|---|
| 同步 IO vs 异步 IO | 拷贝阶段是否阻塞调用方 | **NIO 是同步非阻塞** |
| 阻塞 vs 非阻塞 | 没数据时是等还是立即返回 | 非阻塞单独用 = 空转 |
| 非阻塞 vs 多路复用 | 一个一个问 vs 一次问一批 | **多路复用是"高效地问"** |
| `select`/`poll` vs `epoll` | 每次拷+遍历 vs 内核维护 + 回调就绪链表 | O(n) vs O(就绪数) |
| 水平触发 vs 边缘触发 | 一直通知 vs 变化时通知一次 | **ET 必须读到 `EAGAIN`** |
| LT/ET vs `EPOLLONESHOT` | 触发模式 vs 一次性注册 | 后者用于多线程处理同一 fd |
| `read` + `write` vs `sendfile` | 数据经过用户态 vs 不经过 | 4 次拷贝 vs 2 次 DMA |
| `mmap` vs `sendfile` | 映射后可改内容 vs 纯转发 | **要不要读/改数据** |
| `epoll` vs `io_uring` | 等就绪 vs 异步提交收割 | 前者不能表达"磁盘异步" |
| AIO vs `io_uring` | 只覆盖 `O_DIRECT` 块设备 vs 全统一 | 这就是 AIO 没流行起来的原因 |

## 八、使用场景与面试问答 {#interview}

- **五种 IO 模型**：阻塞、非阻塞、IO 多路复用、信号驱动、异步 IO。**分界线在"数据拷贝阶段是否阻塞调用方"**——前四种都是同步 IO，只有异步 IO 连拷贝都不阻塞。所以 **Java NIO 是"同步非阻塞（多路复用）"，不是异步**；Java 的 AIO（NIO.2）才是异步。所有模型讨论的都是**两次等待**：等数据到达内核、等拷到用户空间。
- **阻塞 IO 的瓶颈**：**不是线程创建开销，而是数量级**——每线程栈 1MB 起（Java 默认 1MB），且绝大部分线程时间都阻塞在 `read` 上。改进路径：IO 多路复用（主流）→ 虚拟线程/协程（写法简单）→ 异步 IO。
- **`select` / `poll` / `epoll`**：`select` 有 1024 的 `FD_SETSIZE` 硬限，`poll` 无限制，但**两者每次调用都要把整个 fd 集合拷进内核并线性遍历**，返回值还要用户自己再遍历一次找就绪的。`epoll` 用**红黑树存 fd（一次注册长期有效）+ 回调把就绪 fd 挂到就绪链表**，`epoll_wait` 直接返回就绪列表——**O(n) 变 O(就绪数)，连接数越多优势越大**（C10K 的解法）。
- **水平触发与边缘触发**：LT 是"只要还有数据就一直通知"，编程简单；**ET 只在状态变化时通知一次，必须配合非阻塞 fd 并循环读到 `EAGAIN`**，否则剩余数据可能永远不再通知。ET 通知次数少、更省系统调用，但**写错就会丢事件**。
- **`epoll` 的实战坑**：**惊群**（`EPOLLEXCLUSIVE` 或 `SO_REUSEPORT` 解决）、`EPOLLONESHOT` 保证事件只被一个线程处理、必须处理 `EPOLLERR`/`EPOLLHUP` 否则空转、`accept` 出的 fd 也要设非阻塞。**多进程共享监听 fd 时 `accept` 返回 `EAGAIN` 是正常的**，不是错误。
- **零拷贝的四种实现**：`mmap + write`（省一次 CPU 拷贝，适合要读改内容）、`sendfile`（数据不进用户态，适合纯转发）、`sendfile + SG-DMA`（**0 次 CPU 拷贝**）、`splice`。传统 `read + write` 是 **4 次拷贝（2 次 CPU）+ 4 次上下文切换**。Java 对应 `transferTo`（**单次有传输上限，大文件必须循环**）与 `map`。
- **零拷贝在中间件的落地**：**Kafka 用 `sendfile` 投递日志段**（配合顺序写与页缓存，是它高吞吐的核心机制之一）、RocketMQ 用 `mmap` 读写 CommitLog、Nginx 静态服务 `sendfile on`、Netty 用 `FileRegion` 与 `CompositeByteBuf`。
- **Linux 原生 AIO 为什么不行**：它**主要只对 `O_DIRECT` 的块设备 IO 有效**，对普通缓冲 IO 支持差、不覆盖网络、每个请求一次系统调用。**"不成熟"指的是覆盖面与可用性，不是 API 不存在**——这也是 Java AIO 没成为主流的原因之一。
- **`io_uring` 是什么、能不能替代 `epoll`**：它用**共享的 SQ/CQ 环形队列**（`mmap`）通信，支持**批量提交**与**磁盘+网络统一的异步接口**，还能注册固定缓冲区。**但把 `epoll` 代码直译过去通常没有收益**，需要重构成 ring 原生写法；并且有**内核版本要求、安全面（历史 CVE、容器默认 seccomp 常屏蔽、`io_uring_disabled` 可禁用）、可观测性差（`strace` 看不到 SQE 内容）**三重代价。**结论：2026 年主流网络服务继续用 `epoll` 是正确选择，`io_uring` 更适合存储引擎与自研高性能代理。**
- **`top` 的 `si` 高说明什么**：软中断（网络收包）消耗大，说明网络流量或小包比例高；常配合 `ksoftirqd` 单核跑满出现，此时要考虑多队列网卡/`RSS` 或 `SO_REUSEPORT` 分散处理。
- **`iostat` 的 `%util` 是不是"磁盘繁忙度"**：**不是**。它表示"设备有请求在处理的时间百分比"，对能并行处理请求的 NVMe，`%util = 100%` 不代表到瓶颈。**要看 `aqu-sz`（队列深度）与 `await`（平均等待）**。
