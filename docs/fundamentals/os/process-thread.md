# 进程、线程与调度

> 下一篇：[虚拟内存与内存管理](/fundamentals/os/memory)　|　导览：[操作系统](/fundamentals/os/)

操作系统里唯一「活着」的东西就是进程。内存是它的、CPU 时间分给它的、文件是它打开的——**其他所有概念都是它的资源**。所以这一篇要先把这个主体立起来。

**先把结论放前面**：

1. **进程是资源分配单位，线程是调度单位**。这不是定义背诵，而是理解后续一切的前提：为什么线程崩溃会带走整个进程（共享地址空间）、为什么线程池能省线程创建开销（不用复制页表）。
2. **上下文切换的成本，主要不在"保存寄存器"，而在"切换后缓存变冷"**。直接成本是百纳秒到微秒量级，间接成本（L1/L2/L3、TLB、分支预测器）往往更大——**这解释了为什么线程数调大反而更慢**。
3. **Linux 6.6 起调度器从 CFS 换成了 EEVDF**（6.12 完成转换）。核心变化：从"谁累计运行得最少"改成"**谁最该现在跑**"（虚拟截止时间），并且可以用 `sched_setattr` 显式表达"我要短时间片"——**CFS 时代那套 `sched_latency_ns` 调参经验已经失效**。
4. **"负载高"不等于"CPU 忙"**。`load average` 把 D 状态（不可中断睡眠，典型是等 IO）也计入，所以 load 高而 CPU 空，八成在等磁盘。

## 一、问题场景：为什么要「进程」这个抽象 {#why-process}

最早的批处理系统一次只能装一个程序，CPU 与 IO 无法重叠——程序读磁盘时，CPU 就干等着。要解决它，必须让多个程序「同时」待着，于是有三个问题必须回答：

| 要解决的问题 | 操作系统给出的答案 |
|---|---|
| 多个程序如何共存、互不破坏？ | **虚拟地址空间**：每个进程看到自己的地址空间，物理内存由内核映射 |
| CPU 怎么在它们之间轮转？ | **调度器** + **上下文切换** |
| 一个进程的崩溃如何不牵连其他？ | **隔离**：独立地址空间 + 页表权限位 |

**「进程」这个词的真正含义是「一组被内核跟踪的资源的集合」**，而不是"一个正在运行的程序"。这个去魅点很重要——它解释了：

- **为什么 fork 是廉价的**：Linux 用**写时复制**（见 [虚拟内存](/fundamentals/os/memory#cow)），父子进程最初共享同一份物理页，只有真的要写时才复制。所以 `fork` 不需要"复制一个进程的内存"。
- **为什么线程不是"轻量级进程"那么简单**：线程共享地址空间，所以它**没有自己的页表**，切换时不用换页表——这是"轻"的地方；但共享也意味着**它没有隔离**——这是"危险"的地方。

## 二、进程、线程与协程 {#process-thread-coroutine}

### 2.1 一个共享，一个不共享 {#process-vs-thread}

| 维度 | 进程 | 线程 |
|---|---|---|
| 角色 | **资源分配单位** | **调度单位** |
| 虚拟地址空间 | 独立 | **共享** |
| 页表 | 独立（切换要换 CR3） | 共享 |
| 文件描述符表 | 独立 | 共享（一个线程 `close` 会影响全部） |
| 信号处理方式 | 独立 | 共享（信号可能投递给任一未屏蔽它的线程） |
| 栈 | 独立 | **独立**（各有自己的调用栈） |
| 寄存器 / 程序计数器 | 独立 | 独立 |
| 线程局部存储（TLS）、`errno` | — | 独立 |
| 创建成本 | 高（要建页表、地址空间） | 低（共享已有资源） |
| 隔离性 | **有**（一个进程崩溃不影响别的进程） | **无**（一个线程段错误带走整个进程） |
| 通信方式 | 需要 IPC（管道 / 共享内存 / socket…） | 直接读写共享变量（**要自己加锁**） |

> **一个反直觉的事实**：**Linux 内核并不区分进程和线程。** 两者都是 `task_struct`，都由同一个 `clone()` 系统调用创建，区别只在创建时传了哪些 `CLONE_*` 标志：
>
> ```c
> // 线程：共享地址空间、文件表、信号处理、线程组
> clone(fn, stack, CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, ...);
> // 进程：都不共享（fork 就是 clone 不带这些标志的特例）
> ```
>
> `fork`、`pthread_create`、`vfork` 在 Linux 上**最终都走 `clone`**，只是标志不同。所以"进程 vs 线程"在 Linux 里是**共享程度**的差异，不是两种东西。这也解释了为什么 `/proc/<pid>/task/` 下能看到进程的所有线程——它们就是同一进程下的一组 `task_struct`。

### 2.2 线程的「独立」部分最容易踩坑 {#thread-private}

线程共享的东西大家都记得，但**它独立拥有的那几样，恰恰是线上踩坑点**：

| 线程私有的 | 典型坑 |
|---|---|
| **调用栈** | 默认 8MB（`ulimit -s`）；Java 线程栈默认 1MB（`-Xss`）→ **一万个线程 ≈ 10GB 栈内存**，即使这些线程什么都不干 |
| **`ThreadLocal` 数据** | 线程池里线程复用 → 上一个任务的值会"泄漏"到下一个任务（详见 [ThreadLocal](/java/concurrent/threadlocal#memory-leak)） |
| **`errno` / 信号掩码** | 一个线程改了信号掩码，其他线程不受影响，导致"同一个进程里行为不一致" |
| **调度优先级 / 亲和性** | `taskset` 与 nice 都是**按线程**生效的，不是按进程 |

**栈这一项尤其值得记住**：很多人算"我能不能开更多线程"时只算了 CPU 和内存的堆，忘了 **每个线程都有一份固定大小的栈**。这是 `-Xss` 调小能撑更多线程的原因，也是虚拟线程（栈可以按需增长）能开百万级的原因。

### 2.3 协程与虚拟线程 {#coroutine}

协程（coroutine）的本质是**把调度从内核搬到用户态**：`yield` 时只保存少量寄存器和自己的栈帧，**不陷入内核、不切换地址空间**，所以切换成本比线程低一两个数量级。

| 维度 | 线程 | 协程 |
|---|---|---|
| 调度者 | **内核**（抢占式，时间片到就抢） | **运行时 / JVM**（协作式，只在 `await`/`yield` 处切换） |
| 切换成本 | 微秒量级（含缓存影响） | 纳秒量级 |
| 数量级 | 几千（受栈内存与切换成本约束） | 可以到百万 |
| 并行能力 | 可多核并行 | **单线程内不可并行**（要并行得有多个载体线程） |
| 致命约束 | — | **一个协程里的阻塞调用会卡住整个载体线程**（"不能用阻塞 API"的由来） |

**Java 的虚拟线程（JDK 21 正式）属于"有栈协程 + 运行时调度"**，它的关键设计是：遇到阻塞式 IO 时，JVM 把虚拟线程**从载体线程（carrier thread）上卸载（unmount）**，让载体线程去跑别的虚拟线程；阻塞结束后再挂载回来。所以它**保留了同步写法**，却在 IO 密集场景拿到了接近异步的吞吐——这正是它相比响应式（Reactor）最大的吸引力。

> **一个必须说清的误区**：虚拟线程**解决的是「线程数受限于栈与切换成本」，不解决「CPU 不够」。** 如果任务是 CPU 密集的，虚拟线程不会带来任何吞吐提升（反而多了一层调度开销）。判据是这一条：**你的线程大部分时间在等吗？** 在等 → 虚拟线程收益大；在算 → 别用。

## 三、上下文切换：代价在哪 {#context-switch}

### 3.1 什么时候会切换 {#switch-trigger}

| 触发原因 | 是否自愿 | 说明 |
|---|---|---|
| 时间片用完 | **非自愿** | 被调度器抢占 |
| 被更高优先级任务抢占 | **非自愿** | 实时任务到来时会立刻抢占 |
| 等待 IO / 锁 / `sleep` | **自愿** | 主动让出 CPU，进入睡眠 |
| 等待的 IO 完成、锁释放 | — | 不是"切换"，是**被唤醒**（进入就绪队列） |

这个区分很重要，因为 **`pidstat -w` 把它们分成了两列**：

```bash
pidstat -w 1            # -w: 报告上下文切换
#   UID  PID  cswch/s  nvcswch/s  Command
#   cswch/s   = 自愿切换（voluntary）：主动等资源让出 CPU
#   nvcswch/s = 非自愿切换（involuntary）：被抢占
```

**读法**：

- **自愿切换高** → 任务在频繁等待（IO 慢、锁竞争激烈、`sleep` 太多）。**这是"看起来 CPU 不高但很慢"的典型特征**——切换本身不是病因，病因是它在等的那个资源。
- **非自愿切换高** → CPU 真的不够分（线程数远超核数，或被 cgroup 限流）。这时加线程只会更糟。

### 3.2 成本由两部分组成 {#switch-cost}

```text
                     一次上下文切换
                            │
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
   ① 直接成本                              ② 间接成本（更贵）
   ─ 保存/恢复寄存器                         ─ L1/L2 缓存变冷（新任务的数据不在缓存里）
   ─ 切换内核栈                              ─ TLB 失效（进程切换要换页表；用 ASID/PCID 缓解）
   ─ 更新 PCB、地址空间（线程切换免换页表）     ─ 分支预测器状态被污染
   ─ 调度器选下一个任务的算法开销              ─ 内存访问模式改变，预取器失效
   量级：百纳秒 ~ 微秒                       量级：微秒级，且**难以直接测量**
```

**这就是"为什么线程数不能无限加"的定量答案**：线程越多 → 抢 CPU 越激烈 → 切换越频繁 → **间接成本越高**（每个线程的缓存都被别人冲掉）。当切换开销的增长超过并行收益，吞吐就会掉头向下。

**线程切换与进程切换的差别**：

| | 线程切换（同进程） | 进程切换 |
|---|---|---|
| 页表 | **不用换**（共享地址空间） | 要换（写 CR3，或至少切 PCID/ASID） |
| TLB | 部分保留（同一地址空间的映射仍有效） | **基本全失效** |
| 成本 | 更低 | 更高 |

> 这条差别是"进程比线程重"的机制层原因，也解释了为什么 **DPDK/Seastar 这类框架追求「一核一线程、线程间不共享」**：它们宁可自己管理，也不愿付切换与缓存失效的代价。

### 3.3 怎么观测 {#observe-switch}

```bash
vmstat 1                 # cs 列 = 每秒上下文切换总次数（含中断处理）
pidstat -w 1             # 按进程拆开，分自愿/非自愿
perf sched record ...    # 记录调度事件，可看切换耗时分布
perf sched latency       # 每个任务的等待延迟与切换次数
cat /proc/<pid>/status | grep -i ctxt   # 进程级累计切换次数（voluntary/involuntary）
```

**一个经验判据**：`vmstat` 的 `cs` 稳定在几千/秒是正常的；**上万且伴随 `sy`（内核态 CPU）偏高、`us` 不高**，就值得查是不是切换或系统调用过密。但如果 `cs` 高、吞吐也正常，**不要为了指标好看去降它**——切换是调度在工作，不是故障。

## 四、调度：谁来选下一个 {#scheduler}

### 4.1 五个调度类，优先级从上到下 {#sched-class}

| 调度类 | 策略 | 用途 | 抢占能力 |
|---|---|---|---|
| `stop` | — | 内核内部（如 CPU 热插拔） | 最高 |
| `deadline` | `SCHED_DEADLINE` | 有明确截止时间的周期任务（最严格） | 高 |
| `realtime` | `SCHED_FIFO` / `SCHED_RR` | 实时任务 | 可抢占普通任务 |
| `fair` | `SCHED_NORMAL` / `SCHED_BATCH`（**CFS → EEVDF**） | 绝大多数普通进程 | 被以上抢占 |
| `idle` | `SCHED_IDLE` | 只在 CPU 全闲时跑 | 最低 |

**实时任务是双刃剑**：`SCHED_FIFO` 的线程一旦跑起来，**除非它自己让出，否则普通任务永远拿不到 CPU**。所以历史上的做法是"实时带宽限制"（rt throttling）。**Linux 6.12 引入了 SCHED_DEADLINE server 来替代它**——保证普通任务至少能拿到约 5% 的 CPU 时间，比原来的节流机制更平稳。

### 4.2 nice 值：权重的近似指数关系 {#nice}

普通进程之间用 `nice`（-20 ~ 19，越小越"不客气"）调节权重。关键点：

- **每差一级，权重比约 1.25 倍**；nice 差 10 级，CPU 份额约差 **10 倍**。
- **nice 只能调"份额比例"，不能表达"我要低延迟"**。一个 nice=0 的批处理任务和一个 nice=0 的 Web 服务，在 CFS 眼里完全一样——**这正是 CFS 被换掉的原因**。

### 4.3 从 CFS 到 EEVDF：为什么换、换了什么 {#cfs-eevdf}

**CFS（完全公平调度器，2007 ~ 2023）**的思路很朴素：给每个任务记账 `vruntime`（虚拟运行时间，按权重缩放后的实际运行时间），**永远选 `vruntime` 最小的那个跑**，用红黑树维护。它的调参旋钮是 `sched_latency_ns`（一个调度周期多长）与 `sched_min_granularity_ns`（单次最少跑多久）。

**CFS 的软肋**：它只有一个"公平"目标，**没有表达延迟需求的通道**。一个只想跑 100μs 就结束的短任务，和一个要跑 10ms 的批任务，在 CFS 下只能排队等 `vruntime` 收敛——**短任务被拖长了**。

**EEVDF（Earliest Eligible Virtual Deadline First）**在 Linux 6.6 引入、6.12 完成转换，加了两把尺子：

```text
        lag_i = V - vruntime_i          （我该得的减去我实得的）
        d_i   = vruntime_i + q_i / w_i  （虚拟截止时间，q=请求的时间片，w=权重）

        ① 只有 lag ≥ 0（"合格 eligible"）的任务才有资格被选
        ② 在合格者中，选虚拟截止时间 d 最早的那个

        → 时间片 q 越短，截止时间越早，越容易被优先挑中
          （应用可以用 sched_setattr(2) 传 sched_runtime 指定 q）
```

**这个改动的实际意义**：

| 变化 | 影响 |
|---|---|
| **有了"低延迟"的表达方式** | 延迟敏感任务（音视频、交互式查询、消息中间件）可通过 `sched_setattr` 请求更短时间片，**不需要再靠调 nice 这种间接手段** |
| **参数体系变了** | CFS 时代的 `sched_latency_ns` / `sched_min_granularity_ns` 调参经验**基本作废**（新的基准是 `base_slice`） |
| **抢占更积极** | 内核可以在任务时间片没用完时就把它换下——只要它让出的那个位置该给更急的任务 |

**运维要记住的一句话**：**从 5.x 内核升级到 6.6+ 之后，任何基于 CFS 参数做的性能调优脚本都要重新评估**——旧参数不再生效，照着老文档调只会得出错误结论。

### 4.4 sched_ext：用 BPF 写调度器 {#sched-ext}

Linux 6.12 引入了 **`sched_ext`（可扩展调度类）**：允许用 **BPF 程序**在运行时定义调度策略，**不改内核、不重编译、不用重启**，并且**出错时内核会自动回退到默认调度器**。

它解决的是"调度策略高度场景相关"的问题：AI 训练需要把一组 GPU worker 线程"成组调度"到同一插槽、游戏需要优先渲染线程、数据中心需要给不同 cgroup 分级。这类需求以前只能靠打补丁，现在可以在用户态迭代。

**它不改变的事实**：默认调度器依然是 EEVDF。`sched_ext` 是"允许你替换"，不是"已经替换"。

### 4.5 亲和性与 NUMA {#affinity}

```bash
taskset -c 0,1 ./app          # 把进程绑到 0、1 号核
numactl --cpunodebind=0 --membind=0 ./app   # 绑到 NUMA 节点 0 的 CPU 与内存
numastat -p <pid>             # 看进程的内存分布，numa_hit / numa_miss
```

**为什么绑核有用**：任务被换核执行后，L1/L2 缓存是私有的（跟随物理核），**换核等于缓存全冷**。绑核的代价是**失去负载均衡**——如果绑定的核上有别的重任务，你就得跟着等。所以绑核是"用弹性换确定性"，**只在延迟敏感且负载可预测时值得做**。

**NUMA 的坑**：跨节点访问内存的延迟明显高于本地（典型量级是本地延迟的一点几倍，SNC/多 NUMA 机型上更明显）。**进程如果跨节点取内存，会稳定地慢一截**——这也是 K8s 里 `topologyManager` / `cpuManager` 存在的理由。

### 4.6 load average 的陷阱 {#load-avg}

```bash
uptime
# 10:56:12 up 3 days,  load average: 12.50, 4.20, 1.80
```

**load average 统计的是"处于可运行（R）和不可中断睡眠（D）状态的任务数"的指数移动平均**。三个数字分别是 1、5、15 分钟。

| 现象 | 说明 |
|---|---|
| `load` 高、CPU 使用率低 | 大量任务卡在 **D 状态**——典型是等磁盘 IO、等 NFS、等块设备。**"负载高但 CPU 空闲"必须查 IO** |
| `load` 高于核数 | 有任务在排队，但不代表一定有问题（还要看它们是在等 CPU 还是在等 IO） |
| `load` 高但一切正常 | 可能只是短时间的突发，看 1 分钟值是否快速回落 |

**这是本篇第一个"结论要落到指标"的例子**：说"系统负载高"时必须说清是**哪种**负载，否则下一步动作会完全错——CPU 排队要减线程，IO 排队要查慢 IO。

## 五、进程间通信 {#ipc}

### 5.1 五种方式与它们的取舍 {#ipc-five}

| 方式 | 数据边界 | 拷贝次数 | 亲缘要求 | 适用 |
|---|---|---|---|---|
| **匿名管道 `pipe`** | 无（字节流） | 2 次 | **需要父子/兄弟关系** | shell 的 `\|`、父子进程简单通信 |
| **命名管道 FIFO** | 无（字节流） | 2 次 | 无 | 无亲缘进程之间的简单通信 |
| **消息队列** | **有**（保留消息边界） | 2 次 | 无 | 需要按消息处理的场景（但 **POSIX MQ 性能一般**） |
| **共享内存 `shm`** | 无 | **0 次**（直接映射同一物理页） | 无 | **高频、大数据量**，配合信号量同步 |
| **信号量 `sem`** | — | — | 无 | **只做同步**，不传数据 |
| **信号 `signal`** | — | — | 无 | 异步通知（如 `SIGTERM`），**不携带数据、语义有限** |
| **socket**（`AF_UNIX` / `AF_INET`） | 无 | 2 次（UNIX 域略快） | 无 | **最通用**，还能跨机 |

**一句话选型**：**能用 socket 就用 socket**（通用、可跨机、生态完整）；**要极致的本地吞吐用共享内存 + 信号量**；**只需要"通知"用信号或 `eventfd`**。共享内存快在"零拷贝"，但代价是**同步要自己做**——多进程写同一块内存且没有锁，等于回到并发编程的最难处。

> **一个能加分的细节**：Android 的 Binder 之所以快，就是因为它在"共享内存"和"消息队列"之间取了折中——**只做一次拷贝**：发送方数据拷进内核缓冲区，接收方把这块内核缓冲区**映射**进自己的地址空间。既保留了消息边界，又省掉一半拷贝。这个设计后来在 `io_uring`、`AF_XDP` 里也能看到同一思路。

### 5.2 socket 与 fd 的关系 {#ipc-socket-fd}

无论用哪种 IPC，**在进程看来它都是一个文件描述符（fd）**：管道是 fd、socket 是 fd、`eventfd`/`timerfd`/`signalfd` 都是 fd。

**这条"一切皆 fd"的统一性是 Linux IPC 好用的一半原因**：

- 所以 `epoll` 能同时监听 socket、管道、`eventfd`、`timerfd`（详见 [IO 模型](/fundamentals/os/io-model#multiplexing)）；
- 所以 `lsof` 能一次列出进程打开的所有东西；
- 所以 `ulimit -n` 会同时限制"能开多少文件"和"能开多少连接"（详见 [文件描述符](/fundamentals/os/filesystem#fd)）。

## 六、容器里的 CPU：cgroup 与 limit {#container-cpu}

容器不改变调度机制，**只是用 cgroup 给进程组加了一层配额**。必须理解的两组参数：

| 参数（cgroup v2） | 含义 | 对应 K8s |
|---|---|---|
| `cpu.max` | `quota period`，一个周期内最多用多少时间 | `limits.cpu` |
| `cpu.weight` | 相对权重（只有竞争时才体现） | `requests.cpu` |
| `cpuset.cpus` | **只允许跑在哪些核上** | 静态 CPU 管理策略 |

### 6.1 一个反直觉的必然结果：CPU 限流（throttling） {#throttling}

假设 `limits.cpu = 1`，内核默认周期是 **100ms**、配额是 **100ms**。听起来"正好一核"，但实际行为是：

```text
   一个 100ms 的周期内：
   ├──────────── 前 20ms 用光了全部配额 ────────────┤
   │ 线程跑得飞快                                    │
   └─────────────────────────────────────────────────┘
                                    ↓
   ├──────── 剩下 80ms 全部被"节流"，完全不能跑 ──────┤
   │ 请求已经开始，但只能干等下一个周期                  │
   └─────────────────────────────────────────────────┘

   → 平均 CPU 用量确实是 1 核，但**延迟会被按周期切碎**
```

**观察它的指标**：

```bash
cat /sys/fs/cgroup/<path>/cpu.stat
# nr_periods   nr_throttled   throttled_usec
# 周期总数      被节流的周期数   累计被节流时长
```

**K8s 里排查"CPU 没打满但延迟抖"的正确动作就是看 `nr_throttled` / `throttled_usec`**——它们不为 0 就说明限流在起作用，此时该做的是**提高 limit 或调整 `period`**（很多发行版/运行时支持把 period 从 100ms 调小，让节流更细粒度），而不是去优化代码。

### 6.2 Java 与容器 CPU 的一个历史坑 {#java-container-cpu}

**JDK 8 不认识 cgroup 的 CPU 配额**，`Runtime.getRuntime().availableProcessors()` 会返回**宿主机核数**（比如 64）。用它算出来的线程池核心数（`核数 × 2`）在 `limits.cpu = 2` 的容器里会开到一百多个线程，**结果是互相抢那 2 核的配额、被反复节流**。

| JDK 版本 | 容器感知 |
|---|---|
| 8（早期） | **不感知**，需手动 `-XX:ActiveProcessorCount=2` |
| 8u191+ / 10+ | 支持 `UseContainerSupport`（默认开） |
| 11+ | 完善支持 CPU 配额与内存限制 |

**即使在新版 JDK 上，也建议显式指定 `-XX:ActiveProcessorCount`**——因为"JVM 认为有几核"直接影响 GC 线程数、ForkJoinPool 并行度、`commonPool` 大小，而这些在容器里是**稳定性的关键变量**。

## 七、对比辨析 {#compare}

| 对比 | 关键差异 | 记忆锚点 |
|---|---|---|
| 进程 vs 线程 | 资源分配单位 vs 调度单位；独立地址空间 vs 共享 | **崩溃会不会带走别人** |
| 线程 vs 协程 | 内核抢占调度 vs 用户态协作调度 | **能不能多核并行** |
| 自愿切换 vs 非自愿切换 | 主动等资源 vs 被抢占 | 前者查"在等谁"，后者查"是不是不够分" |
| CFS vs EEVDF | 最小虚拟运行时间 vs 最早虚拟截止时间 | **能不能表达低延迟需求** |
| nice vs 实时优先级 | 调节份额比例 vs 直接抢占 | nice 调不出"低延迟" |
| load average vs CPU 使用率 | 前者含 D 状态（等待），后者只算实际占用 | **负载高 CPU 空 → 查 IO** |
| `limits.cpu` vs `requests.cpu` | 硬配额（超了被节流） vs 相对权重（只在竞争时生效） | 前者导致 throttling，后者不会 |
| 管道 vs 共享内存 | 2 次拷贝但有边界 vs 0 次拷贝但要自己同步 | **快的东西要自己保证正确** |

## 八、使用场景与面试问答 {#interview}

- **进程与线程的本质区别**：**进程是资源分配单位，线程是调度单位**。进程有独立地址空间与 fd 表，线程共享地址空间与 fd 表但有自己的栈、寄存器、TLS、`errno`。**Linux 内核不区分两者**，都是 `task_struct`，由 `clone()` 的 `CLONE_*` 标志决定共享程度——`fork`/`pthread_create` 最终都走 `clone`。
- **线程"轻"在哪里、"重"在哪里**：轻在**共享地址空间**（切换不用换页表、TLB 不用全失效）；重在**没有隔离**（一个线程崩溃带走整个进程、共享 fd 与信号处理）。别忘了每个线程**有独立栈**——默认 8MB、Java 默认 1MB，这是线程数上不去的关键约束之一。
- **上下文切换的成本**：直接成本是保存/恢复寄存器、切换内核栈、调度算法开销（百纳秒到微秒量级）；**真正的代价是间接成本**——L1/L2/L3 缓存变冷、TLB 失效、分支预测器被污染。用 `pidstat -w` 区分**自愿切换**（在等 IO/锁）与**非自愿切换**（被抢占，CPU 不够）；`vmstat` 的 `cs` 是总量。
- **什么时候线程数加不动**：当切换的间接成本增长超过并行收益时。**判断依据是自愿 vs 非自愿**：非自愿高说明 CPU 真的分不过来，加线程只会更糟；自愿高说明瓶颈在它等的资源（IO、锁、下游），加线程也只是把等待搬到更多线程上。
- **CFS 与 EEVDF**：CFS 用 `vruntime` 红黑树，**只表达公平、不能表达延迟需求**；EEVDF（6.6 引入、6.12 完成）引入 **lag（该得 − 实得）** 与**虚拟截止时间**，只选 lag ≥ 0 的合格任务，再在其中挑截止时间最早的；应用可用 `sched_setattr` 传 `sched_runtime` 请求更短时间片。**CFS 时代的 `sched_latency_ns` / `sched_min_granularity_ns` 调参经验已作废。**
- **调度类优先级**：deadline > realtime（FIFO/RR）> fair（EEVDF）> idle。实时任务可无限抢占普通任务，因此 6.12 用 **SCHED_DEADLINE server** 取代旧的 rt throttling，保证普通任务至少约 5% 的 CPU。
- **`sched_ext` 是什么**：6.12 引入的**BPF 可编程调度类**，能在运行时替换调度策略且出错自动回退，不需要重编译内核。它不改变"默认调度器是 EEVDF"这个事实。
- **协程为什么快、什么时候不该用**：快在**用户态切换**（不陷入内核、不换地址空间，纳秒级）；约束是**单线程内不能并行**、且**一个阻塞调用会卡住整个载体线程**。**Java 虚拟线程（JDK 21）是有栈协程**：阻塞时从载体线程卸载，保留同步写法但拿到异步吞吐。**判据：任务大部分时间在等 → 收益大；在算 → 没有收益。**
- **IPC 五种方式**：管道（字节流、有亲缘要求）、FIFO（无亲缘要求）、消息队列（有边界）、共享内存（**零拷贝最快，但要自己做同步**）、信号量（只同步）、信号（通知、不带数据）、socket（最通用）。**选型口诀：能用 socket 就用 socket，要极致吞吐上共享内存。** 它们在内核里统一表现为 **fd**。
- **load average 的陷阱**：它统计**可运行 + 不可中断睡眠（D）**的任务数。**load 高而 CPU 空闲 = 大量进程在等 IO**，此时该查磁盘而不是加 CPU。这也回答了"为什么 load 高不一定慢"。
- **容器 CPU 限流**：`limits.cpu = N` 实现为 `cpu.max = N×100ms / 100ms`。**配额在周期内用完后，剩余时间被完全节流**，表现为"CPU 均值不高但延迟抖动"——**查 `cpu.stat` 的 `nr_throttled` / `throttled_usec`**。另外注意 JDK 8 早期版本不感知 cgroup 配额，`availableProcessors()` 会返回宿主机核数，导致线程池开过大；建议显式 `-XX:ActiveProcessorCount`。
