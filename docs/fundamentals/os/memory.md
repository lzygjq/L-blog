# 虚拟内存与内存管理

> 上一篇：[进程、线程与调度](/fundamentals/os/process-thread)　|　下一篇：[IO 模型与多路复用](/fundamentals/os/io-model)

内存是进程最大的那份资源，也是线上问题里**最容易被误读**的一份——`free` 的输出几乎每个人都会看错，`df` 与 `du` 对不上时更是无从下手。

**先把结论放前面**：

1. **虚拟内存不是"内存不够时用的磁盘"，它是地址抽象**。它同时解决了三个问题：**隔离**（进程不能互相踩）、**超卖**（合计可超过物理内存）、**抽象**（程序不需要知道物理布局）。
2. **`buff/cache` 不是"被占用"，是可回收的页缓存**。判断内存够不够，看 `available`（内核估算的可回收量），不要看 `free`。**"内存要用满才有价值"，一个缓存常年偏低的机器才是浪费。**
3. **`write()` 返回成功 ≠ 数据落盘**。它只是把数据写进**页缓存**并标脏，回写是异步的——**这正是"断电丢数据"和"必须 `fsync`"的机制层原因**。
4. **JVM 堆 ≠ 进程内存**。RSS 还要算元空间、线程栈、直接内存、Code Cache、JVM 自身开销。**`-Xmx` 按 limit 的 70% 左右给**，剩下的留给堆外，否则容器会被 OOMKilled 而不是抛 `OutOfMemoryError`。

## 一、问题场景：为什么要虚拟内存 {#why-virtual}

如果让程序直接用物理地址，会立刻遇到四个躲不开的问题：

| 问题 | 后果 | 虚拟内存的答案 |
|---|---|---|
| 程序之间互相踩内存 | 一个 bug 拖垮整机 | **隔离**：每个进程独立地址空间，越权访问触发缺页异常 |
| 程序需要连续的大块内存 | 内存碎片一多就分配不出来 | **分页 + 映射**：物理页可以离散，虚拟地址保持连续 |
| 程序不知道该装到哪 | 编译期无法确定地址（重定位问题） | **地址抽象**：程序看到的地址固定，实际映射由内核决定 |
| 内存不够时只能失败 | 无法支撑"多个大程序同时待着" | **按需调页 + 交换**：合起来可以超过物理内存 |

**一句话概括**：虚拟内存把"内存"从一个**物理资源**变成了一个**可以由内核随意编排的抽象**。这也是后面一切机制的基础——

- **`fork()` 为什么廉价** → 写时复制（[§4.1](#cow)）
- **`malloc` 大块内存为什么快** → 只分配虚拟地址，不立刻给物理页（[§4.2](#mmap)）
- **为什么内存"用满"反而正常** → 页缓存把空闲内存利用起来了（[§5](#page-cache)）

## 二、地址空间与分页 {#address-space}

### 2.1 虚拟地址到物理地址的三步 {#paging}

```text
   进程看到的虚拟地址
   0x00007f8a3c4d5123
   ┌────────┬────────┬────────┬────────┬──────────┐
   │ PGD 索引│ PUD 索引│ PMD 索引│ PTE 索引│ 页内偏移  │
   └────┬───┴────┬───┴────┬───┴────┬───┴──────────┘
        │        │        │        │
        ▼        ▼        ▼        ▼
      页全局目录 → 页上级目录 → 页中间目录 → 页表项 ──→ 物理页帧号
      （四级页表，x86-64 每级 9 位索引，页大小 4KB）

   ① MMU 拿虚拟地址查页表  →  得到物理页帧号
   ② 拼接页内偏移          →  得到物理地址
   ③ 若 TLB 命中则跳过 ①   →  快路径
```

**几个必须记住的数字与术语**：

| 术语 | 含义 | 要点 |
|---|---|---|
| **页（page）** | 映射的最小单位 | x86-64 常规 **4KB**；大页 **2MB / 1GB** |
| **页表** | 虚拟页 → 物理页帧的映射表 | 存在内存里，每级都是数组 |
| **多级页表** | x86-64 用 4 级（PGD→PUD→PMD→PTE） | **为了省内存**：不用为没用的地址空间预留表项；5 级页表（57 位）在支持 LA57 的硬件上可选 |
| **TLB** | CPU 里的页表缓存 | 容量很小（L1 dTLB 几十项、L2 TLB 上千项量级）→ **这是大页的价值所在** |
| **缺页异常** | MMU 查不到映射时陷入内核 | 由内核补上映射，然后重试指令 |

**为什么大页（Huge Pages）能提速**：一个 4KB 页需要一个 TLB 表项，一个 2MB 大页也只需要一个。**同样大小的内存，用大页所需的 TLB 表项少 512 倍**——TLB 未命中率大幅下降，进而减少页表遍历的内存访问。这是数据库（Oracle、MySQL `innodb_buffer_pool` 相关配置）与 JVM（`-XX:+UseLargePages`）都支持大页的原因。

**透明大页（THP，Transparent Huge Pages）**由内核自动把合适的区域合成大页，不用应用改代码。配置在：

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never
#   always  : 内核尽量用大页（可能带来分配延迟与内存碎片）
#   madvise : 只对显式 madvise(MADV_HUGEPAGE) 的区域用（**生产常见折中**）
#   never   : 关闭
```

> **这是个真实的取舍**：THP 的 `always` 模式在**分配大页时会有停顿**（需要整理内存），对延迟敏感的数据库反而可能造成毛刺，所以很多数据库厂商建议 `madvise` 或 `never`。**不要照抄任何一个配置——要看你的延迟目标。**

### 2.2 内存分配的三种形态 {#alloc-forms}

| API | 用途 | 背后机制 |
|---|---|---|
| `brk` / `sbrk` | 调整堆顶 | 小块内存（`malloc` 的常规路径），连续、简单 |
| `mmap` | 映射一块新的虚拟内存 | **大块内存**（glibc `malloc` 超过阈值就走它），可独立 `munmap` |
| **匿名映射** | 不对应文件的内存 | `mmap` + `MAP_ANONYMOUS`，用于堆、线程栈等 |

**关键性质：分配虚拟地址不等于占用物理内存。** `malloc(1GB)` 成功只代表**虚拟地址空间够用**，物理页要等第一次写（触发缺页）才分配。这条性质解释了两个常见困惑：

- **为什么"申请了 1G 但 RSS 只有几十 M"** —— 还没真正用。
- **为什么 `malloc` 成功之后程序仍然可能被 OOM Kill** —— 真正的分配发生在触碰内存的时候。Linux 默认的 overcommit 策略允许"超卖"，**这笔账是在使用时结算的**。

## 三、缺页与内存回收 {#page-fault-reclaim}

### 3.1 缺页的三种情况 {#fault-types}

| 类型 | 触发条件 | 代价 | 计为 |
|---|---|---|---|
| **软缺页（minor）** | 页已在内存里（在页缓存中 / 已映射但页表项未填） | 低（只补页表项） | `min_flt` |
| **硬缺页（major）** | 页不在内存，需要读磁盘 | **高（磁盘 IO）** | `maj_flt` |
| **写保护缺页** | 写时复制场景，页是只读共享的 | 中（要复制一页） | 计入 minor |

```bash
ps -o min_flt,maj_flt,cmd -p <pid>          # 进程累计缺页次数
perf stat -e page-faults,minor-faults,major-faults -p <pid>   # 实时
/usr/bin/time -v ./app                       # 含 page faults 的完整统计
```

**读法**：**`maj_flt` 持续增长是内存不足或 IO 慢的强信号**——它在说"我在等磁盘换页"。而 `min_flt` 高但增长平稳通常正常（进程启动、按需分配都会产生）。**这是"结论要落到指标"的第二个例子**：说"内存不够"要能给 `maj_flt` 或 `available` 的具体读数，而不是"感觉慢"。

### 3.2 回收：LRU 与水位线 {#reclaim}

内核把物理页分成两类来管理：

```text
                 ┌─────────────── 可回收（reclaimable）───────────────┐
                 │                                                    │
     匿名页（anon）                                    文件页（file）
     ─ 堆、栈、mmap 匿名区                              ─ 页缓存里的文件数据
     ─ 无 swap 时**不可回收**                            ─ 干净页可直接丢弃（有磁盘备份）
     ─ 有 swap 时可换出                                  ─ 脏页需先回写
                 │                                                    │
                 └──────────┬─────────────────────────────────────────┘
                            ▼
                 各维护 active / inactive 两条 LRU 链表（共 4 条）
                 ─ 被二次访问的页从 inactive 提升到 active
                 ─ 回收时优先淘汰 inactive 尾部的页
```

**水位线（watermark）决定了"什么时候开始回收"**：

```text
     min      low                              high
      │        │                                 │
  ────┼────────┼─────────────────────────────────┼──────▶ 空闲内存
      │        │                                 │
 低于 min：  低于 low：                        高于 high：
 **直接回收** 唤醒 kswapd 后台回收             回收停止
 （分配者自己
   同步回收，
   **会卡住**）
```

| 水位 | 触发动作 | 影响 |
|---|---|---|
| `high` | 停止回收 | 稳态 |
| `low` | 唤醒 `kswapd` **异步**回收 | 正常，不阻塞业务 |
| `min` | **直接回收（direct reclaim）** | **分配内存的进程自己去做回收 → 卡顿抖动** |

**这是排查"偶发卡顿"时最值得查的一条**：如果 `pgscan_direct` / `allocstall`（在 `/proc/vmstat`）在增长，说明**已经进入直接回收**，业务线程正在替内核收拾内存——此时该做的是给应用更多内存或降低内存压力，而不是优化代码。

**最后一道防线是 OOM Killer**：所有可回收手段用尽后，内核按 `oom_score`（与内存占用正相关、可用 `oom_score_adj` 调整）选择进程杀掉。

```bash
dmesg | grep -i "killed process"        # 确认是否被 OOM Killer 杀过
cat /proc/<pid>/oom_score               # 当前得分（越高越容易被杀）
```

**RSS 之外还要看 PSS**：多个进程共享同一份内存（比如共享库、`fork` 后的页）时，`RSS` 会**重复计算**，而 `PSS` 按共享者数量**分摊**：

```bash
cat /proc/<pid>/smaps_rollup            # Pss / Private_Clean / Private_Dirty / Swap
```

> **一个常被忽略的事实**：**`fork` 之后子进程即使什么都不做，也会被 OOM Killer 按"它可能占用父进程的全部内存"来评分**（因为写时复制的页在语义上属于它）。这就是"Redis `bgsave` 期间被 OOM Kill"这类事故的机制——`fork` 出的子进程 `oom_score` 会因为共享了父进程的大内存而偏高。

### 3.3 swap 与 OOM {#swap-oom}

**swap 不是"内存不够才用"的兜底**。它的作用有两层：

| 作用 | 说明 |
|---|---|
| **给冷页一个去处** | 长期不访问的匿名页换出去，把内存让给页缓存——**提升磁盘 IO 命中率** |
| **作为过载缓冲** | 内存峰值时避免直接 OOM，争取时间 |

```bash
cat /proc/sys/vm/swappiness            # 默认 60：越小越不愿意换出匿名页
free -h                                # Swap 行
vmstat 1                               # si/so 列：换入/换出速率
```

**两个工程结论**：

1. **`si`/`so` 持续非 0 是危险信号**（不是"有事"而是"已经在拿磁盘当内存用"）。**偶发的 `si`/`so` 尖峰才是正常的**（换出冷页）。
2. **现代还有 zswap / zram**：先用压缩内存做一层"交换缓存"（zram 把换出的页压缩后存内存），避免直接落到磁盘。这在内存紧张的容器里很有效——**用 CPU 换内存，往往比用磁盘换内存划算**。

## 四、写时复制与 mmap {#cow-mmap}

### 4.1 写时复制（COW） {#cow}

`fork()` 的成本为什么能低到"几乎免费"：

```text
   fork 之前：            父进程页表 ──→ ┌────────┐
                                        │ 物理页  │ 可写
                                        └────────┘
   fork 之后：            父进程页表 ──→ ┌────────┐  ← 双方都标为**只读**
                          子进程页表 ──→ └────────┘     引用计数 = 2

   子进程第一次写：        触发写保护缺页 → 内核复制一页给子进程 → 各自可写
                          父进程页表 ──→ ┌────────┐  可写（原页）
                          子进程页表 ──→ ┌────────┐  可写（新复制的页）
```

**它带来的三个后果**：

| 后果 | 说明 |
|---|---|
| `fork` 极快 | 只复制页表（不是复制内存） |
| **但内存可能翻倍** | 一旦子进程开始写，就真的复制。**Redis `bgsave` 的内存开销就来自这里**——写多的实例 fork 期间内存可达 2 倍 |
| **OOM 评分会偏高** | 子进程的 `oom_score` 把共享页也算进去了（见 [§3.2](#reclaim)） |

### 4.2 mmap：把文件映射进地址空间 {#mmap}

`mmap` 让文件内容直接出现在进程地址空间里，**读写内存就是读写文件**。

| 模式 | 语义 | 用途 |
|---|---|---|
| `MAP_SHARED` | 修改**对其他进程可见、且会写回文件** | 共享内存、多进程共享文件 |
| `MAP_PRIVATE` | 修改只对本进程可见（写时复制），不写回 | 加载可执行文件、只读映射 |
| `MAP_ANONYMOUS` | 不对应文件（堆、栈） | `malloc` 大块、线程栈 |

**`mmap` 读文件的性能真相**：

| 说法 | 事实 |
|---|---|
| "`mmap` 比 `read` 快" | **一半对**。它省掉了"页缓存 → 用户缓冲区"这一次拷贝，但代价是**每个页第一次访问都触发一次缺页**（可能演变成 `maj_flt`）。**顺序大文件读写时，`read` 配合预读往往更好**；随机访问时 `mmap` 优势明显 |
| "`mmap` 写完就落盘了" | **错**。`MAP_SHARED` 的脏页同样要回写，要保证持久化仍需 `msync(MS_SYNC)` —— 与 `write` + `fsync` 是同一个道理 |

```bash
# 关键调优接口
madvise(MADV_SEQUENTIAL)  # 告诉内核我会顺序访问 → 加大预读
madvise(MADV_WILLNEED)    # 提前把页读进来（预热）
madvise(MADV_DONTNEED)    # 这些页我不要了（匿名页直接释放；文件页丢弃需已回写）
madvise(MADV_HUGEPAGE)    # 本区域用透明大页
```

## 五、页缓存：读写的真实路径 {#page-cache}

### 5.1 `read` 与 `write` 到底做了什么 {#read-path}

```text
  read(fd, buf, n)：
    ① 在**页缓存**里找这一页
       命中 → 直接把数据从页缓存拷到用户 buf（**1 次 CPU 拷贝**）
       未命中 → 从磁盘读入页缓存（DMA）→ 再拷到用户 buf（**2 次拷贝 + 1 次磁盘 IO**）
    ② 所以：**第二次读同一个文件几乎不碰磁盘**

  write(fd, buf, n)：
    ① 把用户 buf 的数据拷进页缓存对应页（1 次 CPU 拷贝）
    ② 把该页标记为**脏页（dirty）**
    ③ **立即返回**

    → 数据此刻只在内存里。磁盘上的文件还是旧的。
```

**这张图直接解释了三个线上现象**：

| 现象 | 机制 |
|---|---|
| 刚写完的文件立刻读，非常快 | 读的就是页缓存（内存） |
| 断电 / 进程被 KILL 后数据丢失 | 脏页还没回写 |
| 大文件写入时"越写越慢" | 脏页比例超过阈值，写入者被迫**同步回写**（见下） |

### 5.2 脏页回写与 `fsync` {#dirty-writeback}

**内核用两个比例控制回写的积极性**：

```bash
cat /proc/sys/vm/dirty_background_ratio   # 默认 10：脏页占比超它 → 后台开始异步回写
cat /proc/sys/vm/dirty_ratio              # 默认 20：脏页占比超它 → **写入者自己同步回写**
cat /proc/sys/vm/dirty_expire_centisecs   # 默认 3000：脏页最长待 30 秒必须回写
cat /proc/sys/vm/dirty_writeback_centisecs # 回写线程唤醒间隔
```

**这就是"写入突然卡住"的机制**：突发写入把脏页比例顶过 `dirty_ratio`，此后**每个 `write` 都要等一部分回写完成**，写入速率被强行压到磁盘速率。**调大 `dirty_ratio` 能吸收更多突发，代价是断电时丢的数据更多** —— 这是一个纯粹的取舍，没有免费的设置。

**持久化的四个接口，别搞混**：

| 接口 | 保证 | 代价 |
|---|---|---|
| `write` | **什么都不保证**（只到页缓存） | 最低 |
| `fdatasync` | 数据落盘（**不含**不影响读的元数据，如 `mtime`） | 中 |
| `fsync` | **数据 + 元数据**都落盘 | 高（一次设备级 flush） |
| `sync` | 所有文件系统的脏页都回写 | 全局，运维用 |
| `O_SYNC` / `O_DSYNC` | 每次 `write` 都同步落盘（等价于每次写都带 `fsync`） | **极高，慎用** |
| `O_DIRECT` | **绕过页缓存**直接读写设备 | 省掉拷贝与缓存污染，**但要求对齐，且失去预读优势** |

**三条能加分的工程结论**：

1. **数据库之所以用 `O_DIRECT`**（或自己管理缓存 + `fsync`）：它们不想让数据被缓存两遍（自己的 buffer pool + 页缓存），也**不想让内核的脏页策略干扰自己的 WAL 语义**。
2. **`fsync` 是昂贵操作，批量提交才划算**：这解释了为什么 Kafka / RocketMQ / MySQL 都有"批量刷盘"机制，以及为什么"每条消息都 fsync"会成为吞吐杀手。
3. **`fsync` 在文件系统层面可能"连坐"**：一次 `fsync` 可能触发比预期更多的回写（部分文件系统对同一设备的 flush 会互相影响），这是"小文件随机写 + 频繁 fsync"性能极差的原因之一。

## 六、怎么看内存 {#observe-metrics}

### 6.1 `free` 的每一列到底是什么意思 {#free-columns}

```bash
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            31Gi        12Gi       1.2Gi       512Mi        18Gi        18Gi
Swap:          8.0Gi       0.0Gi       8.0Gi
```

| 列 | 含义 | 常见误读 |
|---|---|---|
| `total` | 物理内存总量 | — |
| `used` | **新版 `free` 里等于 `total - available`** （旧版是 `total - free - buff/cache`） | **先确认你的 `free` 是哪个版本**，否则数字对不上 |
| `free` | 完全没用到的内存 | **`free` 小很正常**，不代表内存紧张 |
| `buff/cache` | 内核缓冲 + 页缓存 | ❌ 不是"被占用"；**大部分可回收** |
| **`available`** | **内核估算的"新程序能用多少"**（含可回收的缓存） | ✅ **判断内存够不够，只看这一列** |
| `shared` | `tmpfs` 等共享内存 | tmpfs 占的是内存（`/dev/shm` 也在其中） |

> **一句话**：**"内存要用满才有价值"。** 一个 `free` 一直很大的机器说明页缓存没被利用起来，磁盘 IO 白白多了。**真正要警惕的是 `available` 低 + `maj_flt` 涨 + `si/so` 有值**，这三者同时出现才是内存压力。

### 6.2 进程视角：VIRT / RES / SHR {#process-memory}

```bash
$ ps aux | grep java
USER   PID  %CPU %MEM    VSZ   RSS  COMMAND
echo  1234  120  38.5 10234567 12345678 java -Xmx8g ...
```

| 列 | 含义 | 注意 |
|---|---|---|
| `VSZ` / `VIRT` | **虚拟**地址空间大小 | 可以远大于物理内存（含未触碰的映射、共享库）——**看到它很大不用慌** |
| `RSS` / `RES` | **实际驻留**的物理内存（含共享部分，**会重复计算**） | 容器 memory limit 主要按它算 |
| `SHR` | 共享内存部分 | 共享库、`tmpfs` 映射 |
| `%MEM` | RSS / 物理内存总量 | **在容器里这个分母是宿主机内存，没有参考价值** |

**容器里必须用 cgroup 的视角，而不是 `ps`**：

```bash
cat /sys/fs/cgroup/<path>/memory.current    # 当前用量（**含页缓存**）
cat /sys/fs/cgroup/<path>/memory.stat       # anon / file / kernel / sock 分项
cat /sys/fs/cgroup/<path>/memory.max        # 限额（= K8s memory limit）
cat /sys/fs/cgroup/<path>/memory.events     # oom / oom_kill 计数 ← **确认 OOM 的直接证据**
```

**关键区分**：cgroup 的 `memory.current` **把页缓存也算进去了**。所以一个进程"看起来没超限"却触发 OOM，往往是页缓存 + 匿名内存合计超了。（新内核会优先回收本 cgroup 的文件页，把容量压力更多压在匿名内存上，但**总量仍是同一个池子**。）

## 七、落到 Java：为什么 RSS 总比 `-Xmx` 大 {#java-mapping}

**这是内存问题在 Java 项目里最常见的困惑**：`-Xmx4g` 的进程，RSS 可能是 6G+ 甚至被 OOMKilled。

```text
       容器 memory limit
   ┌──────────────────────────────────────────────────┐
   │  JVM 进程 RSS                                     │
   │  ┌──────────────┐  ┌───────────────────────────┐ │
   │  │  Java 堆      │  │  堆外（**不受 -Xmx 管**）   │ │
   │  │  -Xmx 控制    │  │  ─ 元空间 Metaspace         │ │
   │  │  （最大一块）  │  │  ─ 线程栈 -Xss × 线程数      │ │
   │  │              │  │  ─ 直接内存 DirectByteBuffer │ │
   │  │              │  │  ─ Code Cache（JIT 后代码）  │ │
   │  │              │  │  ─ GC 辅助结构（记集/卡表）   │ │
   │  │              │  │  ─ JVM 自身 + JNI + 网络缓冲  │ │
   │  └──────────────┘  └───────────────────────────┘ │
   │  ─────────────────────────────────────────────── │
   │  + 页缓存（读写的文件，若同 cgroup 也计入）         │
   └──────────────────────────────────────────────────┘
                 ↑
        还有：堆虽然 -Xmx 是上限，但**堆外 + 堆 + GC 峰值**才是真正的峰值
```

| 区域 | 相关参数 | 常被忽略的点 |
|---|---|---|
| 堆 | `-Xmx` / `-Xms` | **`-Xms = -Xmx` 能避免运行期扩容**，但启动就占满 |
| 元空间 | `-XX:MaxMetaspaceSize` | 动态生成类多（反射、CGLIB、脚本引擎）时会持续涨；**默认不限，可涨到耗光内存** |
| 线程栈 | `-Xss` | **默认 1MB × 线程数**：1000 线程 = 1GB |
| 直接内存 | `-XX:MaxDirectMemorySize` | 默认约等于 `-Xmx`；Netty、NIO、Kafka 客户端大量使用；**OOM 时提示 `Direct buffer memory`** |
| Code Cache | `-XX:ReservedCodeCacheSize` | 默认 240MB 量级，JIT 满后会退回解释执行（性能突然下降） |
| GC 结构 | — | G1/ZGC 的记集、卡表也是实打实的内存 |

### 7.1 两个必须分清的错误 {#oom-types}

| | `OutOfMemoryError` | OOMKilled（退出码 137 / `oom_kill` 计数 +1） |
|---|---|---|
| 谁动手 | **JVM 自己** | **内核 OOM Killer** |
| 触发点 | 某个内存池申请不到（堆、元空间、直接内存…） | 进程 RSS 超过 cgroup limit，且无法回收 |
| 现象 | 抛异常，有完整堆栈（可 dump） | 进程**直接被 SIGKILL**，无异常、无 dump |
| 处理方向 | 查内存泄漏 / 调大对应池 | **给容器更多内存 或 降低总 RSS**（调堆比例、降线程数、限直接内存） |

**排查 OOMKilled 的顺序**：

1. `memory.events` 里 `oom_kill` 是否 > 0 → 确认是内核杀的
2. `dmesg` 找 `Killed process` → 确认杀的哪个进程、当时 RSS 多少
3. JVM 启动参数：`-Xmx` 是否合理、`MaxMetaspaceSize` 是否设置、线程数与 `-Xss`
4. 加 `-XX:NativeMemoryTracking=summary` + `jcmd <pid> VM.native_memory summary` **直接看堆外分布**

### 7.2 参数怎么给 {#jvm-sizing}

| 原则 | 说明 |
|---|---|
| **留给堆外的比例** | 常见做法是 `-Xmx` 取 limit 的 **60% ~ 75%**，其余留给元空间、线程栈、直接内存、GC 结构 |
| **让 JVM 按比例算** | `-XX:MaxRAMPercentage=60`（容器感知开启时，自动按 cgroup limit 计算） |
| **线程栈要单独估** | 线程数 × `-Xss` 是硬开销，**线程多的服务要按 512KB~1MB 显式设小** |
| **直接内存显式上限** | `-XX:MaxDirectMemorySize` 别用默认，避免它悄悄吃掉预留量 |

## 八、对比辨析 {#compare}

| 对比 | 关键差异 | 记忆锚点 |
|---|---|---|
| 虚拟内存 vs 物理内存 | 地址抽象 vs 真实页帧 | `VSZ` 可以远大于 `RSS` |
| 页 vs 大页 | 4KB vs 2MB/1GB | **TLB 表项少 512 倍** |
| 软缺页 vs 硬缺页 | 补页表 vs 读磁盘 | `maj_flt` 增长 = 内存/IO 压力 |
| kswapd 回收 vs 直接回收 | 异步后台 vs 分配者同步 | 后者 = 业务线程在替内核干活 |
| `free` vs `available` | 完全空闲 vs 含可回收缓存 | **只看 `available`** |
| RSS vs PSS | 共享内存重复计算 vs 按份分摊 | 多进程共享时 RSS 会虚高 |
| `write` vs `fsync` | 写到页缓存 vs 保证落盘 | **`write` 成功 ≠ 数据安全** |
| `fsync` vs `fdatasync` | 含元数据 vs 只管数据 | 有大批小文件时差别明显 |
| 页缓存 vs `O_DIRECT` | 内核帮你缓存 vs 自己管 | 数据库选后者，是为了不让缓存做两遍 |
| 堆 vs 堆外 | `-Xmx` 管 vs 不管 | **RSS > `-Xmx` 是正常的** |
| OOM 异常 vs OOMKilled | JVM 抛异常 vs 内核杀进程 | 前者有堆栈，后者只有 137 |

## 九、使用场景与面试问答 {#interview}

- **虚拟内存解决了什么**：三件事——**隔离**（进程互不干扰，越权访问触发缺页）、**超卖**（虚拟地址总量可超物理内存，按需分配）、**抽象**（程序不需知道物理布局，也回避了重定位问题）。它不只是"内存不够用的磁盘"。**分配虚拟地址不占物理页**，物理页在首次写触发缺页时才分配——这解释了"申请 1G 但 RSS 很小"以及"`malloc` 成功仍可能被 OOM Kill"。
- **虚拟地址怎么变成物理地址**：MMU 用**多级页表**（x86-64 四级：PGD→PUD→PMD→PTE）逐级查，每级 9 位索引，最后拼 12 位页内偏移；**TLB** 是这整套查询的缓存。多级页表的目的是**省内存**（不用为空洞地址预留表项）。
- **大页为什么快**：同样的内存量，4KB 页要的 TLB 表项是 2MB 大页的 **512 倍**。大页让 TLB 命中率大幅提升、页表遍历减少。**THP 的 `always` 模式可能因内存整理带来分配停顿**，延迟敏感（数据库）场景常选 `madvise`。
- **缺页分几种**：**软缺页**（页已在内存，只需补页表，代价低）、**硬缺页**（要读磁盘，代价高）、**写保护缺页**（COW 场景）。`ps -o maj_flt` / `perf stat -e major-faults` 可观测；**`maj_flt` 持续增长是内存不足或 IO 慢的强信号**。
- **内存回收的两条路径**：LRU 按 **active/inactive 双链表**（匿名页与文件页各一对）维护；水位线低于 `low` 由 **kswapd 异步回收**，低于 `min` 触发**直接回收**——**分配者自己同步做回收，会造成业务卡顿**（看 `/proc/vmstat` 的 `allocstall`）。最终防线是 **OOM Killer**，按 `oom_score` 选进程杀，可用 `oom_score_adj` 调。
- **为什么 fork 之后 Redis 内存可能翻倍**：**写时复制**让 `fork` 只复制页表，父子共享物理页；但子进程一旦写，就真的复制页。另外 **`fork` 出的子进程 `oom_score` 会因共享了父进程的大内存而偏高**——这是"Redis `bgsave` 期间被 OOM Kill"的机制。
- **`write` 之后数据在哪**：**在页缓存**（内存里），`write` 返回只表示"我收下了"。**要持久化必须 `fsync`（数据+元数据）或 `fdatasync`（数据）**。`sync` 是全局回写，`O_DIRECT` 则绕过页缓存直接读写，`O_SYNC` 等于每次写都同步落盘。**"断电丢数据"就是脏页还没回写。**
- **脏页比例的两个阈值**：`dirty_background_ratio`（默认 10%）超了就**异步**开始回写；`dirty_ratio`（默认 20%）超了**写入者被迫同步回写**——这是"突发写入突然变慢"的机制。调大能吸收更多突发，但**断电时丢的数据更多**。
- **`mmap` 比 `read` 快吗**：**未必**。`mmap` 省掉一次"页缓存→用户缓冲区"拷贝，但每次首次访问都要缺页；**顺序大文件用 `read` + 预读往往更好，随机访问才是 `mmap` 的主场**。而且 `MAP_SHARED` 的脏页同样要回写，持久化仍需 `msync`。
- **`buff/cache` 高要不要清**：不要。它是**可回收的页缓存**，"内存要用满才有价值"。**判断内存够不够只看 `available`**；真危险的是 **`available` 低 + `maj_flt` 增长 + `si/so` 非 0** 三者同时出现。注意新版 `free` 的 `used = total - available`，跟旧版口径不同。
- **容器里的内存怎么看**：`ps` 的 `%MEM` 分母是宿主机内存，**没有参考价值**；要看 cgroup：`memory.current`（**含页缓存**）、`memory.stat`、`memory.max`、`memory.events`（确认 `oom_kill`）。**页缓存计入 cgroup 用量**，这是"看起来没超限却 OOM"的常见原因。
- **为什么 Java 进程 RSS 比 `-Xmx` 大**：堆外还有**元空间、线程栈（`-Xss` × 线程数）、直接内存、Code Cache、GC 记集/卡表、JVM 自身**。给参数的原则是 **`-Xmx` 占 limit 的 60%~75%**（或用 `-XX:MaxRAMPercentage`），并显式设 `MaxMetaspaceSize`、`MaxDirectMemorySize`、调小 `-Xss`。**排查堆外最直接的工具是 `-XX:NativeMemoryTracking=summary` + `jcmd VM.native_memory summary`。**
- **`OutOfMemoryError` 与 OOMKilled 的区别**：前者是 **JVM 自己**抛的（某个池申请失败，有堆栈、可 dump）；后者是**内核 OOM Killer 发的 SIGKILL**（退出码 137，无异常、无 dump）。处理方向完全不同：前者查泄漏或调大该池，后者要给容器更多内存或降低总 RSS。
