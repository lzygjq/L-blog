# 文件系统与文件描述符

> 上一篇：[IO 模型与多路复用](/fundamentals/os/io-model)　|　下一篇：[Linux 排查实战](/fundamentals/os/linux-tools)

前一篇讲了"数据怎么进出内核"，这一篇讲**数据最终落在哪、以及进程用什么句柄去够到它**。

**先把结论放前面**：

1. **文件名不在 inode 里**。inode 存元数据与数据块索引，名字存在**目录项（dentry）**里，目录项指向 inode。**所以一个 inode 可以有多个名字**——这就是硬链接，也解释了"删除文件"其实是"删掉一个名字"。
2. **`fd` 只是进程 fd 数组的下标**。它的真身是"进程 fd 表 → 系统打开文件表 → inode"这条三层链。**这解释了 `fork`/`dup` 为什么共享文件偏移量**，也解释了为什么 `ulimit -n` 会同时限制"文件数"和"连接数"。
3. **`unlink` 之后空间不一定会释放**。只要还有进程持有这个 fd，inode 的引用计数就不为 0——**"`df` 满了但 `du` 对不上"的第一嫌疑就是这个**（`lsof | grep deleted`）。
4. **要保证"写文件不写坏"，标准姿势是"写临时文件 → `fsync` → `rename`"**。`rename` 在同一文件系统内是原子操作，这是配置热更新、发版、数据库 WAL 通用的手法。

## 一、问题场景：三个高频困惑 {#why-fs}

| 现象 | 缺的是哪块认知 |
|---|---|
| `df -h` 显示磁盘 100%，`du -sh` 加起来只有 60% | 不知道"被删除但仍被打开"的文件仍占空间 |
| 报 `No space left on device`，但 `df -h` 显示还有空间 | 不知道 **inode 也会耗尽**（`df -i`） |
| 写配置/发版时，进程读到"半个文件" | 不知道 `write` 不保证原子，而 `rename` 保证 |
| `Too many open files` | 不知道 socket 也占 fd，也不知道各类 `ulimit` 的分层 |
| 硬盘上"明明没那么多数据" | 不知道日志式文件系统会保留空间、稀疏文件、以及 ext4 的 5% 保留块 |

## 二、一切皆文件：VFS 的四类对象 {#vfs}

Linux 用一层抽象（**VFS，虚拟文件系统**）把 ext4、XFS、NFS、`tmpfs`、`procfs` 这些完全不同的东西**统一成同一套接口**。理解 VFS 只要理解它的四类对象：

| 对象 | 代表什么 | 生命周期 | 关键点 |
|---|---|---|---|
| **超级块 `super_block`** | 一个已挂载的文件系统 | 挂载期间 | 记录块大小、inode 总数、空闲块数（`df` 读的就是它） |
| **索引节点 `inode`** | **一个文件**（不含名字） | 与引用计数绑定 | 元数据 + 数据块索引；**名字不在里面** |
| **目录项 `dentry`** | **一个名字 → inode** 的映射 | 由 dcache 缓存 | 目录本质是"名字到 inode 的表" |
| **打开文件 `file`** | 一次打开（含**文件偏移量**） | `open` → `close` | 同一文件多次 `open` 会有多个它，**各自有自己的偏移量** |

```text
   进程 A                                    内核                     磁盘
   ┌─────────────┐      ┌──────────────────┐   ┌──────────────┐
   │ fd 表        │      │ 系统打开文件表     │   │              │
   │  0 → stdin   │      │  ┌────────────┐  │   │              │
   │  1 → stdout  │      │  │ file 对象    │──┼──▶│  inode       │
   │  3 ──────────┼─────▶│  │ 偏移量 / 标志 │  │   │  元数据      │
   │  5 ──────────┼──┐   │  └────────────┘  │   │  数据块索引  │
   └─────────────┘  │   └──────────────────┘   └──────────────┘
                    │            ▲                     ▲
   同进程 dup() 出来的 fd ────────┘                     │
   共享同一个 file 对象 → **共享偏移量**                 │
                                                       │
   dentry（dcache）：名字 → inode                        │
   多对一 → 这就是**硬链接** ────────────────────────────┘
```

**这张图的三个直接推论**：

| 推论 | 解释 |
|---|---|
| **`fork` 之后父子共享文件偏移量** | 因为子进程继承的是同一份 `file` 对象（不是复制），**一方 `read` 会推进另一方的位置**。要独立偏移量得各自 `open` |
| **`dup`/`dup2` 出来的 fd 共享偏移量** | 同一个 `file` 对象的两个下标 |
| **硬链接是"多个名字指向同一 inode"** | dentry 多对一 |

## 三、inode 与目录项 {#inode}

### 3.1 inode 里有什么、没有什么 {#inode-structure}

| inode 里**有** | inode 里**没有** |
|---|---|
| 文件类型（普通/目录/字符设备/socket…） | **文件名**（在 dentry 里） |
| 权限（rwx）、属主 uid/gid | **文件内容**（在数据块里，inode 只放索引） |
| 大小、块数 | 父目录信息 |
| **时间戳**：`atime` / `mtime` / `ctime` |  |
| **链接计数**（有多少个名字指向它） |  |
| **数据块索引** |  |

**数据块索引的两种组织方式**：

| 方式 | 说明 | 适用 |
|---|---|---|
| **多级间接块**（直接 12 个 + 一级 + 二级 + 三级间接） | 传统 ext2/ext3 的做法，小块文件快，大文件要多次寻址 | 老文件系统 |
| **区段（extent）** | 用"起始块 + 长度"描述一段连续空间，**减少索引项数量** | **ext4 默认**、XFS 也用它 |

> **一个容易懵的点**：**目录也是一个文件**，它的"内容"就是一张「文件名 → inode 号」的表。所以遍历目录 = 读这个文件的内容；`ls -i` 看到的就是 inode 号。这也解释了为什么"一个目录下的文件数太多会变慢"（查表变慢，而且 ext4 目录默认不做索引）。

### 3.2 硬链接与软链接 {#hard-soft-link}

```bash
ln target hard_link        # 硬链接：创建新的目录项，指向同一 inode
ln -s target soft_link     # 软链接：创建一个**新的文件**，内容是 target 的路径
ls -li                     # -i 显示 inode 号 → 硬链接的两个名字 **inode 号相同**
```

| 维度 | 硬链接 | 软链接（符号链接） |
|---|---|---|
| 本质 | **同一 inode 的另一个名字** | **一个存着路径的独立文件** |
| inode | **相同** | **不同**（自己有自己的 inode） |
| **能否跨文件系统** | ❌ **不能**（inode 号只在单个文件系统内唯一） | ✅ 能 |
| **能否指向目录** | ❌ 不能（会造成目录环） | ✅ 能 |
| 原文件删除后 | **仍然可用**（引用计数 -1，数据还在） | **悬空（dangling）**，报 `No such file` |
| `ls -l` 显示 | 无特殊标记，链接计数增加 | 显示 `名字 -> 目标` |
| 占用空间 | 只多一个目录项 | 多一个 inode + 目标路径的存储 |

**删除的真相**：`unlink`（也就是 `rm`）做的事情是**删掉一个目录项、把 inode 的链接计数减 1**。**只有当链接计数归零、且没有任何进程打开它时**，inode 与数据块才真正被释放。这是 [§6.1](#space) 那个"空间没释放"问题的全部机制。

### 3.3 inode 也会用完 {#inode-exhausted}

**"磁盘还有空间却报 `No space left on device`"** 的经典原因就是 inode 耗尽：

```bash
df -h    # 看空间
df -i    # 看 inode ← 这个报错时要看这一列
# Filesystem      Inodes  IUsed   IFree IUse% Mounted on
# /dev/sda1      6553600 6553600      0  100% /
```

**关键差异**：

| 文件系统 | inode 分配方式 |
|---|---|
| **ext4** | **`mkfs` 时确定数量**（按容量比例预分配），**用完了无法新增**——只能删文件或重建文件系统 |
| **XFS** | **动态分配**，基本不会遇到 inode 耗尽 |

**典型触发场景**：大量小文件（会话文件、缓存碎片、日志按秒切片、`/var/spool` 队列堆积）。**这类问题的正确解法是治理小文件数量，而不是加磁盘。**

## 四、文件描述符 {#fd}

### 4.1 fd 的三层结构与限制的分层 {#fd-table}

**fd 是一个非负整数，它是进程 fd 数组的下标**。每次 `open`/`socket`/`pipe`/`eventfd`，内核都会找一个**当前最小的可用下标**返回，并在数组中填入指向 `file` 对象的指针。

| fd | 用途 |
|---|---|
| `0` / `1` / `2` | stdin / stdout / stderr（进程启动时由 shell 或运行时建立） |
| `3+` | 所有 open 的文件、socket、管道、`epoll` 实例、`timerfd`… |

**"一个 TCP 连接占一个 fd"** —— 这是 `ulimit -n` 直接影响"能扛多少并发连接"的原因。同时：

```text
   fd 相关限制分三层，不要搞混：

   ① 单进程软限制：ulimit -n（默认常见 1024）
         └─ 进程可随时提高到硬限制以内；**运行中改只对之后 fork 的子进程生效**
   ② 单进程硬限制：ulimit -Hn（普通用户不能自行提高）
   ③ 系统级：/proc/sys/fs/file-max（所有进程合计）
         └─ 单进程能拿到的上限还受 /proc/sys/fs/nr_open 约束

   改法（三处都要改，只改一处会白干）：
   ─ /etc/security/limits.conf：* soft nofile 65535 / * hard nofile 65535
   ─ systemd 服务：LimitNOFILE=（**systemd 启动的服务不读 limits.conf**）
   ─ 容器/K8s：**容器里 ulimit 由运行时决定**，要显式配
```

> **一个特别常见的坑**：**`limits.conf` 对 systemd 管理的服务无效**。改了 `/etc/security/limits.conf` 后重启服务发现 `ulimit -n` 还是 1024，原因就在这里——**systemd 服务要改 unit 的 `LimitNOFILE`**（或在 `/etc/systemd/system.conf` 里设 `DefaultLimitNOFILE`）。

### 4.2 `EPOLL` 和 fd 的配额关系 {#epoll-fd-quota}

`epoll_create` 本身也占一个 fd；**被监听的每个 fd 也都占一个 fd 名额**。所以一个"一万连接"的服务需要考虑的不只是 `ulimit -n` 要大于一万，还要注意：

| 项 | 说明 |
|---|---|
| `ulimit -n` ≥ 连接数 + 文件数 + 少量余量 | 通常设成 65535 甚至更高 |
| **`epoll` 实例数** | 每创建一个 `Selector`/`EpollEventLoop` 都占一个 fd（Netty 每个 EventLoop 一个） |
| **`epoll` 可管理的 fd 上限** | 受 `/proc/sys/fs/epoll/max_user_watches` 约束（每个被监听的 fd 在内核里要占约 160 字节） |

### 4.3 怎么看"fd 都去哪了" {#fd-leak}

```bash
ls -l /proc/<pid>/fd | head -30          # 列出所有 fd 及其指向（最直接）
ls /proc/<pid>/fd | wc -l                # 当前 fd 总数
lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn   # 按类型统计
lsof -p <pid> | grep -c "socket"         # 有多少 socket
ls -l /proc/<pid>/fd | grep deleted      # **指向已删除文件的 fd** ← 见 §6.1
cat /proc/sys/fs/file-nr                 # 系统级：已分配 / 未使用 / 上限
```

**fd 泄漏的典型形态**：数量**单调上升不回落**（不是"高"而是"只涨不跌"）。常见原因：

| 原因 | 说明 |
|---|---|
| 连接用完没 `close`（异常路径漏了 `finally`） | 最经典，Java 里靠 try-with-resources 规避 |
| `Socket`/`Stream` 包装后只关外层 | 一般没问题（外层会连带关内层），但**自己写的包装类容易漏** |
| `Selector` 注册了新 fd 但没在关闭时 `cancel` + 关 fd | 两处都要做 |
| `HttpClient`/`RestTemplate` 每次 new 一个新客户端 | **连接池没复用**，对方连接迟迟不释放 |
| 线程池 + 同步 IO 阻塞，任务堆积 | 实际上不是 fd 泄漏，是 fd 被"占用"着不放 |

## 五、一致性：日志与 `fsync` {#journal}

### 5.1 为什么需要日志：崩溃后的中间状态 {#journaling}

**一个动作要改多处元数据**（比如创建文件要：分配 inode、写目录项、更新超级块的空闲计数）。如果改到一半断电，文件系统就处于**不一致状态**——可能出现"inode 已分配但没有名字"或"目录项指向一个空 inode"这类结构损坏。

**日志式文件系统（journaling）**的解法：**先写日志（记录"我要做这些修改"），日志落盘后再改真正的结构**。崩溃恢复时只需重放日志——要么全做，要么全不做。

| 日志模式（ext4） | 记什么 | 崩溃后风险 | 性能 |
|---|---|---|---|
| `data=journal` | **数据 + 元数据**都进日志 | 最安全 | **最慢**（数据写两遍） |
| **`data=ordered`（ext4 默认）** | 只记元数据，但**保证数据先于元数据落盘** | 不会出现"文件变长但内容是旧的" | 折中，推荐 |
| `data=writeback` | 只记元数据，**不管数据顺序** | 崩溃后可能看到新元数据配旧数据（如文件尾部有垃圾） | 最快，风险最高 |

```bash
mount | grep " / "                      # 查看当前挂载参数（含 data=ordered）
cat /proc/mounts | grep data=
```

> **注意**：**日志保证的是"文件系统结构一致"，不是"你的数据不丢"**。`data=ordered` 保证的是"不会出现结构损坏或与旧数据混搭"，但**还没回写的脏页仍然会丢**（见 [页缓存与回写](/fundamentals/os/memory#dirty-writeback)）。**"文件系统没坏"和"文件内容对"是两件事。**

### 5.2 安全写文件的四步法 {#safe-write}

```bash
# ① 写临时文件
echo "new config" > /etc/app/conf.yaml.tmp
# ② 把数据刷到磁盘（关键！）
fsync(conf_tmp_fd)         # 或 sync 命令
# ③ 原子替换
mv /etc/app/conf.yaml.tmp /etc/app/conf.yaml    # rename 在同一文件系统内是**原子**的
# ④ （严格做法）再 fsync 目录
fsync(dir_fd)              # 让"目录项本身"的修改也持久化
```

| 步骤 | 为什么必须 |
|---|---|
| 写临时文件 | 避免在目标文件上出现"写了一半"的中间状态 |
| **`fsync` 临时文件** | 否则 `rename` 之后**目录项已更新、数据还在页缓存**，断电就得到一个空文件——**这是"文件存在但大小为 0"事故的根源** |
| `rename` | POSIX 保证**同一文件系统内 `rename` 是原子的**：读到的要么是旧文件，要么是新文件 |
| `fsync` 目录 | 保证目录项本身落盘（不 fsync 也能工作，但极端崩溃下可能丢掉这次改名） |

**这就是配置热更新、发版、以及数据库写 WAL 都采用这个模式的原因。**

### 5.3 `O_DIRECT` 与写穿透 {#o-direct}

| 标志 | 语义 | 代价 |
|---|---|---|
| （默认） | 走页缓存，`write` 只到内存 | 断电丢未回写数据 |
| `fsync` / `fdatasync` | 显式要求落盘 | 昂贵（一次设备 flush） |
| `O_SYNC` / `O_DSYNC` | **每次 `write` 都同步落盘** | 极慢，慎用 |
| **`O_DIRECT`** | **绕过页缓存**直接读写设备 | **要求地址与长度按块大小对齐**（常见 512B 或 4KB），不对齐会失败或退化成缓冲 IO；**失去预读优势**，小 IO 反而更慢 |

**数据库为什么偏爱 `O_DIRECT`**：数据已经在自己的 buffer pool 里缓存过一遍了，再经页缓存就是**缓存两遍**，既浪费内存又让"脏页什么时候回写"变得不可控。**自己管缓存 + 用 `fsync` 控制持久化时机**，语义更清晰。

## 六、空间为什么没释放 {#space}

### 6.1 deleted 文件仍然占空间 {#space-deleted}

```bash
$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2       100G   98G  2.0G  98% /var

$ du -sh /var
62G     /var          # ← 差了 36G！

$ lsof +L1 | head          # 列出链接计数为 0（已 unlink）但仍被打开的文件
COMMAND   PID  USER  FD   TYPE  ...  SIZE/OFF  NODE NAME
java     1234  app   42w   REG   ...  38654705664  99123 /var/log/app/app.log (deleted)
```

**机制**：`unlink` 只是删了一个名字、把 inode 链接计数减到 0；**但只要有进程还持有打开的 fd，inode 的引用计数就不为 0，数据块不会释放**。日志轮转（logrotate）之后忘记通知应用重新打开文件，就会稳定复现这个场景。

**三种处理方式**：

| 方式 | 说明 |
|---|---|
| **重启/重载应用** | 最直接，但代价大 |
| **让应用重新打开日志文件** | 发信号给支持的应用（如 nginx 的 `USR1`、很多日志框架支持 `SIGHUP`），或 logrotate 的 `copytruncate` |
| **`truncate` 那个 fd** | `: > /proc/<pid>/fd/<fd>`（**在 Linux 上可行**，用 shell 就能清空） |

> **顺带一个 `tmpfs` 的坑**：`/dev/shm`、`/run` 是 **tmpfs，占的是内存**。往里面写大文件会直接吃掉内存并被算进 cgroup；容器里 `/dev/shm` 默认只有 **64MB**，Java/数据库用共享内存时经常在这里踩坑。

### 6.2 另外两个"空间对不上"的原因 {#space-others}

| 原因 | 检查方式 | 说明 |
|---|---|---|
| **inode 耗尽** | `df -i` | 见 [§3.3](#inode-exhausted)：ext4 的 inode 是固定的 |
| **ext4 保留块** | `tune2fs -l /dev/sda1 \| grep -i reserved` | **ext4 默认保留 5% 给 root**，所以普通用户看到的是 95%。可用 `tune2fs -m 1` 调整（数据盘可调小，系统盘别动） |
| **稀疏文件** | `du` 与 `ls -l` 大小不一致 | `ls -l` 显示逻辑大小，`du` 显示实际占用块数 |
| **挂载点遮蔽** | — | 在挂载点下写了文件，之后又挂载了东西，原文件被遮住但仍占空间 |

## 七、对比辨析 {#compare}

| 对比 | 关键差异 | 记忆锚点 |
|---|---|---|
| inode vs dentry | 文件本体（含元数据） vs 名字到 inode 的映射 | **inode 里没有文件名** |
| 硬链接 vs 软链接 | 同一 inode 的别名 vs 独立文件存路径 | 硬链接不能跨文件系统、不能指目录 |
| fd vs `file` 对象 vs inode | 进程数组下标 vs 一次打开（含偏移） vs 文件本身 | `dup`/`fork` 共享 `file` → **共享偏移量** |
| 软限制 vs 硬限制 | 进程可自行提高 vs 不能超过 | `ulimit -n` vs `ulimit -Hn` |
| `limits.conf` vs `LimitNOFILE` | 登录会话 vs systemd 服务 | **systemd 服务不读 limits.conf** |
| 日志模式 `ordered` vs `writeback` | 数据先于元数据落盘 vs 不管顺序 | 前者是 ext4 默认 |
| **日志 vs `fsync`** | 保证**结构一致** vs 保证**数据落盘** | **两件不同的事，别混** |
| `write` vs `rename` | 不保证原子 vs 同文件系统内原子 | **安全写文件 = 临时文件 + fsync + rename** |
| 页缓存 vs `O_DIRECT` | 内核帮缓存 vs 自己管 | 数据库选后者避免缓存两遍 |
| `df` vs `du` | 文件系统视角（含 deleted） vs 目录树视角 | 对不上先查 `lsof +L1` |

## 八、使用场景与面试问答 {#interview}

- **inode 是什么**：**文件的元数据 + 数据块索引**，包含类型、权限、属主、大小、三个时间戳、**链接计数**、数据块索引（ext4 用 extent）。**它不包含文件名**——名字在**目录项（dentry）**里，由 dcache 缓存。目录本质是"名字 → inode 号"的表，所以 **`ls -i` 能看到 inode 号**。
- **硬链接与软链接**：**硬链接是同一 inode 的另一个名字**（inode 号相同、不能跨文件系统、不能指向目录）；**软链接是一个独立文件，内容是目标路径**（可跨文件系统、可指向目录、原文件删了会悬空）。`rm` 的本质是 `unlink`——**删掉一个名字并把链接计数减 1**，只有计数归零且无人打开时才真正释放数据块。
- **为什么 `df` 和 `du` 对不上**：最常见是**已删除但仍被进程打开的文件**（`lsof +L1` 或 `lsof | grep deleted` 可查），机制就是链接计数为 0 但引用计数不为 0。解法是让应用重新打开文件（`SIGHUP`/`copytruncate`）或清空那个 fd。其他原因有 **inode 耗尽（`df -i`）**、**ext4 默认 5% 保留块**、稀疏文件。
- **`No space left on device` 但空间还有**：**先看 `df -i`**。ext4 的 inode 数量在 `mkfs` 时固定，小文件多（会话、缓存、按秒切的日志）会把 inode 用光；XFS 动态分配 inode 基本不会遇到。**这类问题的解法是治理小文件数量，加磁盘没用。**
- **fd 的本质**：它是**进程 fd 数组的下标**，背后是"进程 fd 表 → 系统打开文件表（`file` 对象，含偏移量） → inode"三层。**`fork` 与 `dup` 让多个 fd 指向同一个 `file` 对象，因此共享文件偏移量**；要独立偏移量必须各自 `open`。**一个 TCP 连接就是一个 fd**，所以 `ulimit -n` 直接决定能扛多少连接。
- **`ulimit -n` 的三层与常见坑**：单进程软限制、单进程硬限制、系统级 `file-max`。**最大的坑是"改了 `/etc/security/limits.conf` 却对 systemd 服务无效"**——systemd 服务要在 unit 里设 `LimitNOFILE`（或全局 `DefaultLimitNOFILE`）。容器里 ulimit 由运行时决定，需显式配置。
- **fd 泄漏怎么查**：`ls -l /proc/<pid>/fd | wc -l` 看总数是否**单调上升不回落**；`lsof -p <pid>` 按类型统计；`/proc/sys/fs/file-nr` 看系统级。常见原因：异常路径漏 `close`、`Selector` 关闭时没 `cancel`、每次 new 一个 HTTP 客户端导致连接不复用。
- **文件系统的日志解决了什么**：**只解决"崩溃后的结构一致性"**，不解决"数据不丢"。`data=ordered`（ext4 默认）保证数据先于元数据落盘；`data=writeback` 更快但可能看到"新元数据 + 旧数据"；`data=journal` 最安全最慢。**日志落盘 ≠ 你的业务数据落盘**，那需要 `fsync`。
- **安全写文件的正确姿势**：**写临时文件 → `fsync` 临时文件 → `rename` 覆盖目标（同文件系统内原子）→ （严格做法）`fsync` 目录**。**漏掉临时文件的 `fsync` 会导致"文件存在但大小是 0"** ——因为目录项已更新而数据还在页缓存。这是配置热更新与数据库写 WAL 的通用手法。
- **`O_DIRECT` 是什么、什么时候用**：绕过页缓存直接读写设备。代价是**要求地址与长度按块大小对齐**（常见 512B/4KB）、**失去预读**、小 IO 更慢。数据库用它是因为**数据已在自己的 buffer pool 中缓存过，再经页缓存等于缓存两遍**，且想让持久化时机完全可控。
- **`/dev/shm` 为什么会导致 OOM**：它是 **`tmpfs`，占内存不占磁盘**，而且会被计入 cgroup 内存。**容器里 `/dev/shm` 默认仅 64MB**，Java、数据库、或者用了 POSIX 共享内存的组件容易在这里踩坑。
