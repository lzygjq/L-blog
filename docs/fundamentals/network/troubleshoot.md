# 网络排查实战

> 上一篇：[DNS 与 CDN](/fundamentals/network/dns-cdn)　|　回到：[计算机网络 · 导览](/fundamentals/network/)

前四篇讲的是机制，这一篇讲**怎么用机制去定位问题**。因为网络问题的特点很鲜明：**症状相似、原因完全不同**。

同样是"接口超时"，可能是 DNS 慢、可能是 SYN 被丢、可能是 TLS 握手失败、可能是服务端 GC、也可能是连接池在排队。**如果你只有"超时"这一个信息，就没法定位**——所以这一篇的核心不是工具清单，而是：

**把"一个笼统的症状"变成"一个精确到层的判断"。**

**结论先放**：

1. **排查要自下而上逐层剥**，每层都有一个"确定性验证动作"。跳层排查是靠运气。
2. **`Connection refused` 和 `Connection timed out` 是两个完全不同的故障**——前者有人回 RST（端口没监听/被 reject），后者包被静默丢弃（路由或 drop 规则）。**这一条能省掉一半的排查时间。**
3. **`curl -w` 的分段计时是性价比最高的网络工具**——一条命令把 DNS、建连、TLS、首字节、总耗时全部分开。
4. **别用 `netstat`**，用 `ss`。前者在高连接数下本身就会拖慢机器。

## 一、问题场景：为什么排查容易乱 {#why-troubleshoot}

排查乱的三个典型原因：

| 症状 | 为什么会乱 | 对策 |
|---|---|---|
| "超时了" | 超时可能发生在**五个不同环节**（DNS/建连/TLS/等待/响应），笼统的一个"超时"没有信息量 | 用分段计时把"超时"拆开 |
| "一会儿好一会儿坏" | 偶发问题里，**应用层证据（日志）往往被掩盖**，且时间窗口难对齐 | 先量化（丢包率、错误率、P99），再定位 |
| "重启就好了" | 重启能治百病恰恰说明是**状态问题**（连接泄漏、队列堆积、缓存脏） | 重启前**先留现场**：`ss` 快照、线程栈、堆转储 |

**一条纪律**：**重启之前先取证。** 重启把证据一起清掉了，同一问题会以更高频率回来——而且下次你手上什么都没有。

**自下而上还是自上而下？**

| 情况 | 方向 | 理由 |
|---|---|---|
| 完全不通、看不出是哪一层 | **自下而上** | 排除法最可靠，且下层不通时上层的一切结论都不可信 |
| 明确报错（如 500 / 证书过期） | 直接跳到对应层 | 症状已经给出了层 |
| 性能问题（慢，但不报错） | **先量化分段耗时** | 慢的原因必然落在某一段，分段就是定位 |

## 二、工具链：按层归类 {#toolchain}

把工具按"它验证哪一层"排列，这是本篇最有价值的一张表：

| 层 | 工具 | 验证什么 | 典型命令 |
|---|---|---|---|
| **名字解析** | `dig` | 域名解析结果、走的是哪个解析器、TTL | `dig example.com` / `dig +trace example.com` / `dig @8.8.8.8 example.com` |
| **地址/接口** | `ip addr` | 本机有没有 IP、网卡是否 up | `ip addr show` |
| **路由** | `ip route` | 默认网关是谁、到目标走哪条路由 | `ip route get 1.2.3.4` |
| **网络层可达** | `ping` | 目标 IP 能否被路由到（ICMP） | `ping -c 4 1.2.3.4` |
| **路径** | `traceroute` / `mtr` | 经过哪些跳、哪一跳开始断或延迟陡增 | `mtr -rwzc 20 1.2.3.4`（`mtr` 比 `traceroute` 更适合持续观察） |
| **同链路寻址** | `arp` / `ip neigh` | 网关的 MAC 有没有学到 | `ip neigh show` |
| **端口可达** | `nc` / `telnet` | 目标**端口**能否建连（TCP 握手） | `nc -vz 1.2.3.4 3306` |
| **连接/端口状态** | **`ss`** | 本机所有连接状态、队列水位、谁在用端口 | `ss -lntp` / `ss -s` / `ss -tan state time-wait \| wc -l` |
| **防火墙** | `iptables -L -n` / `nft list ruleset` | 有没有 DROP/REJECT 规则 | `iptables -L -n --line-numbers` |
| **内核参数** | `sysctl -a` | TCP 相关参数现值 | `sysctl net.ipv4.tcp_max_syn_backlog net.core.somaxconn` |
| **抓包（终极手段）** | `tcpdump` | 实际网线上发生了什么 | `tcpdump -i any -nn 'host 1.2.3.4 and port 80' -c 50` |
| **应用侧分层计时** | **`curl -w`** | DNS/建连/TLS/首字节/总耗时 | 见下方 §2.1 |
| **TLS 层** | `openssl s_client` | 证书链、协议版本、握手是否成功 | `openssl s_client -connect example.com:443 -servername example.com` |
| **HTTP 层** | `curl -v` / `curl -I` | 请求头、响应头、状态码、重定向链 | `curl -vI -o /dev/null https://example.com` |

### 2.1 `curl -w`：一条命令做完分层计时

这是本篇**最推荐先学会的一个技巧**——它把"慢"这个笼统症状直接拆到层：

```bash
curl -o /dev/null -s -w '
  DNS 解析      : %{time_namelookup}s
  TCP 建连      : %{time_connect}s          （含 DNS）
  TLS 握手完成  : %{time_appconnect}s       （含前面两项）
  首字节 TTFB   : %{time_starttransfer}s    （含前面三项）
  总耗时        : %{time_total}s
' https://example.com/
```

**怎么读数**（各值是**累计**的，要看差值）：

| 现象 | 推断 |
|---|---|
| `time_namelookup` 就很大 | **DNS 问题**：解析器慢、走了完整的迭代链路、或被劫持后超时重试 |
| `namelookup` 正常但 `connect` 很大 | **建连慢**：路由绕远、SYN 丢包触发重传、目标半连接队列满 |
| `connect` 正常但 `appconnect` 差值大 | **TLS 握手慢**：证书链不全导致客户端去补载中间证书、或加密套件协商反复 |
| `appconnect` 正常但 `starttransfer` 差值大 | **服务端处理慢**：应用本身、下游依赖、GC、连接池排队 |
| `starttransfer` 到 `total` 差值大 | **传输慢**：响应体大、带宽受限、丢包导致吞吐上不去 |

> **这一张表的实用价值**：把"接口慢"这句话从"可能是任何原因"压缩成"某一层的问题"。**排障的第一步永远是把症状量化到层。**

### 2.2 `ss` 的读法

`ss` 是排 TCP 状态问题的核心工具。三个常用姿势：

| 目的 | 命令 |
|---|---|
| 看监听端口与**队列水位** | `ss -lntp`（`Recv-Q` 是堆积待 accept 的连接数，`Send-Q` 是上限） |
| 看整体状态分布 | `ss -s`（直接给出各状态计数） |
| 数某个状态的数量 | `ss -tan state time-wait \| wc -l` |

**`ss -lntp` 的 `Recv-Q` 是最容易被忽略的指标**：

```text
  State   Recv-Q  Send-Q   Local Address:Port
  LISTEN  0       128      0.0.0.0:8080

          ↑ 当前堆积在 accept 队列里、应用还没取走的连接数
                 ↑ 队列上限 = min(listen 的 backlog, net.core.somaxconn)
```

**`Recv-Q` 持续逼近 `Send-Q`** ＝ 应用 `accept()` 得太慢（线程被占满、业务处理阻塞在别处）。这时候客户端会看到**建连超时**，而服务端进程还活着、CPU 也不高——**很容易被误判成"网络问题"**。

## 三、按层定位的排查路径 {#layers-path}

下面这张图是本篇的主干：**拿到一个"不通"，怎么一步步把范围缩小到一层。**

```text
  症状：连不上目标（不通 / 超时）

  ① 域名解析对不对？                                ← 名字解析层
     dig 目标域名 → 有 A 记录吗？IP 是我期望的吗？
        │ 否 → 解析问题：DNS 配置、TTL 缓存、被劫持
        │ 是 ↓
  ② 本机网络与路由正常吗？                            ← 网络层
     ip addr（有 IP 吗）→ ip route（有默认网关吗）→ ping 网关 → ping 目标 IP
        │ 不通 → 网络层问题：网卡 down、路由缺失、网关不通、安全组/ACL
        │ 通 ↓
  ③ 端口通不通？（最关键的分水岭）                     ← 传输层
     nc -vz 目标 端口
        │
        ├─ Connection refused  → 有 RST 回来：端口没监听 / 被 REJECT
        │                         → 查服务是否启动、是否绑对网卡、防火墙 reject 规则
        ├─ Connection timed out → 包被静默丢弃：DROP 规则 / 上游 ACL / 路由黑洞
        │                         → 查 iptables DROP、云安全组、中间设备
        └─ 通 ↓
  ④ 应用层协议对不对？                                ← 应用层
     curl -v（看状态码、响应头、重定向）
        │ 异常 → 应用问题：路由没配、鉴权失败、后端 5xx
        │ 正常 ↓
  ⑤ TLS 有问题吗？                                    ← 应用层（加密）
     openssl s_client -connect 域名:443 -servername 域名
        │ 异常 → 证书过期 / 证书链不全 / 域名不匹配 / SNI 未传
        │ 正常 ↓
  ⑥ 都通，但很慢？                                    ← 回到性能维度
     curl -w 分段计时 → 定位到具体是哪一段慢
```

**两道分水岭必须记住**：

| 分水岭 | 意义 |
|---|---|
| `ping` 通 vs 不通 | 通只能证明**网络层**可达——**后面还有三层可能出问题**。"ping 通了所以网络没问题"是个错误的推论 |
| `refused` vs `timed out` | **有 RST = 有设备回应了**（端口/规则问题，通常是自己这边）；**无回应 = 包被吞了**（ACL/路由问题，可能在中间设备）。**这个区分直接决定你该查服务端还是查网络设备** |

## 四、五个场景推演 {#cases}

### 4.1 场景一：完全连不上

**先做的第一件事**：`nc -vz 目标 端口`，看是 refused 还是 timed out。

| 结果 | 含义 | 排查顺序 |
|---|---|---|
| `Connection refused` | 对端回了 RST，说明**包到了、但没人接收** | ① 服务进程在吗（`ps`）② 监听在哪个地址（`ss -lntp`，注意 `127.0.0.1` vs `0.0.0.0`）③ 防火墙是不是 reject |
| `Connection timed out` | 包被丢弃、没有任何回应 | ① 本机 `iptables` 有没有 DROP ② 云安全组/ACL ③ 路由是否可达（`ip route get`）④ 目标是否有防火墙 DROP |
| 域名解析不出 IP | 卡在第一层 | `dig` 看权威与本地结果是否一致；`dig +trace` 看链路断在哪一级 |

**一个高频坑**：服务**监听到了 `127.0.0.1`** 而不是 `0.0.0.0`。`ss -lntp` 一眼能看出来，但很多人只查"进程在不在"就下结论。

### 4.2 场景二：能连上，但首字节很慢

用 `curl -w` 分段（§2.1），按差值定位。**若 `starttransfer` 段大**，问题在服务端：

| 进一步排查 | 命令 | 看什么 |
|---|---|---|
| 是不是连接池排队？ | 应用侧连接池指标 + `ss -tan state established \| wc -l` | 活跃连接数 vs 池上限 |
| 是不是 GC？ | `jstat -gcutil <pid> 1000` | Full GC 频率与停顿 |
| 是不是下游慢？ | 链路追踪 | 自己耗时 vs 下游耗时占比 |
| 是不是 `accept` 太慢？ | `ss -lntp` 的 `Recv-Q` | 堆积是否逼近上限 |

### 4.3 场景三：偶发超时（最难的一类）

偶发问题的排查关键是**先量化再定位**，否则永远在猜。

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 统计错误率与时间分布（是不是集中在某时段/某实例） | 区分"全局性"还是"单点" |
| 2 | `mtr -rwzc 100 目标` 持续观察 | 看**丢包发生在哪一跳**——只有最后一跳丢才是对端问题 |
| 3 | 抓包留存现场：`tcpdump -i any -nn host <对端IP> -w /tmp/x.pcap` | 事后用 Wireshark 看有没有 SYN 重传、RST、零窗口 |
| 4 | 检查内核与连接状态：`ss -s`、`dmesg \| grep -i 'nf_conntrack\|syncookies'` | 有没有 **conntrack 表满**、SYN 队列溢出 |

**抓包要看的三件事**（比工具本身更重要）：

| 现象 | 含义 |
|---|---|
| **SYN 发出但无 SYN+ACK，间隔 1s/2s/4s 重发** | 对端或中间设备丢 SYN → 建连超时，应用层看到"超时" |
| **出现 RST** | 连接被强制终止：端口没监听、被防火墙 reject、或对端进程崩溃 |
| **窗口 = 0** | 接收方应用读得太慢 → 发送方暂停（**这是"服务端卡住"而非"网络慢"的信号**） |

### 4.4 场景四：TIME_WAIT / CLOSE_WAIT 堆积

这两个状态的**处置方向完全相反**，务必先分清（机制细节见 [TCP 的挥手](/fundamentals/network/tcp#teardown)）：

| | TIME_WAIT 多 | CLOSE_WAIT 多 |
|---|---|---|
| 性质 | **正常**的协议状态 | **异常**——应用没 `close()` |
| 命令 | `ss -tan state time-wait \| wc -l` | `ss -tan state close-wait \| wc -l` |
| 判断成因 | 是短连接太多，还是服务端在主动关闭？ | 一定是代码/连接池问题 |
| 对策 | 改长连接/连接池（治本）；主动发起连接的一方可开 `tcp_tw_reuse` | **查代码**：连接泄漏、异常路径未关、池只借不还。调内核参数**无效** |

**一个必须避开的坑**：`net.ipv4.tcp_tw_recycle` 在新内核里**已经被移除**（Linux 4.12）。老博客推荐的"优化 TIME_WAIT 三件套"里它**在 NAT 环境下会误杀大量正常连接**——看到就跳过。

### 4.5 场景五：DNS 解析慢

| 检查 | 命令 | 判断 |
|---|---|---|
| 解析耗时 | `dig example.com \| grep -E 'Query time\|SERVER'` | `Query time` 是否异常大；`SERVER` 是你实际用的解析器 |
| 是否命中缓存 | 连续两次 `dig`，对比 TTL 是否递减 | 递减幅度不合理说明中间有异常缓存 |
| 是否走了完整链路 | `dig +trace example.com` | 看断在哪一级、是否绕远 |
| 权威结果是否一致 | `dig @<权威NS> example.com` | 与本地结果对比，判断是缓存问题还是配置问题 |

**"解析慢"最容易被误判为"接口慢"**：因为 DNS 耗时被算在应用的"连接耗时"里。**把 `curl -w` 的分段计时用在生产环境的健康检查上，这类问题就藏不住了。**

## 五、对比辨析 {#compare}

| 对照 | A | B | 关键区别 |
|---|---|---|---|
| 连接失败 | `Connection refused` | `Connection timed out` | 前者**有 RST 回应**（端口/规则问题，通常在自己侧）；后者**无任何回应**（DROP/路由问题，可能在中间） |
| 连接查看 | `ss` | `netstat` | 前者读内核 `netlink`，O(1) 级别；后者逐行读 `/proc`，**高连接数下自身就是性能问题** |
| 路径探测 | `traceroute` | `mtr` | 前者一次性打一枪；后者持续统计**每跳丢包率**，偶发问题靠它 |
| 解析查看 | `nslookup` | `dig` | 前者读本地配置、拿到的可能是缓存；后者能指定解析器、能 `+trace`、字段完整 |
| 关闭状态 | TIME_WAIT | CLOSE_WAIT | 前者正常（主动方），后者异常（被动方未 close）；**处置方向相反** |
| 排查方向 | 自下而上 | 自上而下 | 症状不明→自下而上（排除法）；症状已明确层→直接跳到那层 |

## 六、使用场景与面试问答 {#interview}

### 6.1 按场景跳转

| 场景 | 去哪里 |
|---|---|
| 完全不通 | [场景一](#cases) + [分水岭](#layers-path) |
| 慢但不报错 | [`curl -w` 分段计时](#toolchain) |
| 偶发超时 | [场景三](#cases) |
| 连接数异常 | [场景四](#cases) |
| 解析慢 | [场景五](#cases) |
| 要一条命令说清"哪一层慢" | [`curl -w`](#toolchain) |

### 6.2 高频问答

| 问题 | 答案要点 |
|---|---|
| 网络不通，第一步做什么？ | 先分清 `refused` 还是 `timed out`（`nc -vz`），它决定你查自己还是查中间设备 |
| `ping` 通就说明服务正常吗？ | **不能**。ping 只到网络层，后面还有传输层、TLS、应用层；且很多环境会单独禁 ICMP |
| 502 和 504 怎么区分？ | 502＝后端响应无效（多半挂了）；504＝等后端超时（慢）。**一个崩一个慢** |
| 为什么推荐 `ss` 不用 `netstat`？ | `netstat` 遍历 `/proc` 逐行拼，连接数上万时自身就会拖慢机器；`ss` 走内核 netlink |
| `ss -lntp` 的 Recv-Q 高说明什么？ | **应用 `accept()` 太慢**（线程被占满），连接堆积在 accept 队列，客户端表现为建连超时 |
| 服务明明起来了却连不上，常见原因？ | 监听在 `127.0.0.1` 而非 `0.0.0.0`；被防火墙 reject；绑错网卡/端口 |
| TIME_WAIT 多要不要处理？ | 它是**正常**状态。先分清成因（短连接多 / 服务端主动关），治本是长连接与连接池 |
| CLOSE_WAIT 多怎么处理？ | **查代码**——连接泄漏或异常路径没关。调内核参数无效，因为状态没往前走 |
| `tcp_tw_recycle` 能开吗？ | **不能**，新内核已移除；NAT 环境下会按时间戳误杀正常连接 |
| 偶发超时怎么定位？ | ① 先量化错误率与时间分布 ② `mtr` 看哪一跳丢包 ③ `tcpdump` 留现场看 SYN 重传/RST/零窗口 ④ 查 conntrack 与队列溢出 |
| 抓包该看什么？ | SYN 有无重传（建连问题）、有无 RST（被拒/崩溃）、窗口是否为 0（**接收方应用慢**） |
| 怎么一句话证明慢在哪一层？ | 用 `curl -w` 的 `time_namelookup / connect / appconnect / starttransfer / total` 差值判断 |
| 排查完要做什么？ | **留证据**：`ss` 快照、抓包文件、参数现值。重启前先取证，否则同一问题会以更高频回来 |
