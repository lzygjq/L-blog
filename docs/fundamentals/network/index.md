# 计算机网络 · 导览

计算机网络是**面试问得最多、日常最容易被跳过**的一门。原因很实际：平时的开发都包在框架和 SDK 里，`RestTemplate` 一调就通了，没有人会去读 TCP 头部。但一旦出问题——连接池打满、偶发超时、TIME_WAIT 堆积、换机房后延迟翻倍——**能不能定位，取决于脑子里有没有那张分层的图**。

所以这一域的组织原则是：**以分层为纲，不以协议为纲。** 先建立"数据在哪一层、被谁处理、带了什么头部"的空间感，再去填 TCP、HTTP 这些具体协议的细节。反过来先背协议的字段，遇到新问题就套不上。

## 一、问题场景：为什么会"会用不会查" {#why}

| 常见困境 | 根因（缺的是哪一层认知） |
|---|---|
| 接口偶发超时，加了超时时间还是超时 | 不知道超时是分段的（DNS / 建连 / 读 / 写各有各的超时），也不知道重传会让一次调用远超预期 |
| 服务刚上线，连接数飙升、报端口不够用 | 不知道 `TIME_WAIT` 是谁产生的、为什么服务端主动关闭会积压 |
| 本地跑得好，一上生产就慢 | 不知道 MTU 与跨机房 RTT 对吞吐的影响（带宽时延积） |
| 换了 CDN 但没变快 | 不知道 DNS 调度和 Anycast 是两套机制，宿主的本地 DNS 可能把调度带偏 |
| HTTPS 证书过期后全站 502 | 不知道 TLS 握手失败发生在 TCP 建连之后、HTTP 之前，属于"第三层失败" |

**共同的答案是同一张图**：把"一条请求"拆成分层流水线，每层各自会怎么失败。这也是下一节要做的事。

## 二、分层是纲 {#layers}

四层模型（TCP/IP）与七层模型（OSI）的对应关系，以及**每层真正负责的事**：

| TCP/IP 四层 | 对应 OSI | 这一层负责 | 典型协议 | 数据的叫法 | 出错时的现象 |
|---|---|---|---|---|---|
| 应用层 | 应用 / 表示 / 会话 | 业务语义：请求什么、返回什么 | HTTP、DNS、SSH、MQTT | 报文 message | 400 / 404 / 证书错误 |
| 传输层 | 传输 | **端到端**：进程之间可靠或不可靠地传送 | TCP、UDP、QUIC | 段 segment / 数据报 datagram | 连接超时、连接被重置 |
| 网络层 | 网络 | **主机到主机**：寻址与路由，跨网络转发 | IP、ICMP、ARP（常划在此层） | 包 packet | 目标不可达、路由不通 |
| 网络接口层 | 数据链路 / 物理 | **链路内**：同一网段内怎么送到对面的网卡 | 以太网、Wi-Fi | 帧 frame | 网线没插、Wi-Fi 掉线 |

**两条必须建立的直觉**：

1. **每一层只为上一层提供服务，不管上一层在干什么。** TCP 不知道你传的是 HTTP 还是 MQTT 消息；IP 不知道 TCP 是可靠还是不可靠。这是"换 WiFi 不用改 HTTP"的原因，也是"网络排障必须逐层剥"的原因。
2. **越往下越"没有地址概念"**。应用层知道域名，传输层只有端口，网络层只有 IP，链路层只有 MAC。**DNS 做的事就是把域名翻译成 IP，ARP 做的事就是把 IP 翻译成 MAC**——两张翻译表，位置不同。

数据一路往下走时的**封装过程**，是理解后续所有协议（MTU、分片、粘包）的基础：

```text
  应用层   HTTP 报文
           ┌──────────────────┬─────────┐
           │   HTTP 头部 + 体  │         │
           └──────────────────┴─────────┘
                    │ 交给传输层，加上源/目的端口、序号、窗口
                    ▼
  传输层   TCP 段
           ┌──────────┬──────────────────┬─────────┐
           │ TCP 头部  │   HTTP 头部 + 体  │         │
           └──────────┴──────────────────┴─────────┘
                    │ 交给网络层，加上源/目的 IP、TTL
                    ▼
  网络层   IP 包
           ┌─────────┬──────────┬──────────────────┐
           │ IP 头部  │ TCP 头部  │   HTTP 头部 + 体  │
           └─────────┴──────────┴──────────────────┘
                    │ 交给链路层，加上源/目的 MAC
                    ▼
  链路层   以太帧
           ┌──────────┬─────────┬──────────┬──────────────────┬─────┐
           │ 帧头+MAC │ IP 头部  │ TCP 头部  │   HTTP 头部 + 体  │ FCS │
           └──────────┴─────────┴──────────┴──────────────────┴─────┘
```

**接收端逐层剥掉自己那一层的头部，把剩下的交给上一层**——这个过程叫解封装。链路层剥帧头、网络层剥 IP 头、传输层剥 TCP 头，最后应用层拿到的就是完整的 HTTP 报文。

| # | 篇目 | 解决的问题 | 最值得记的结论 |

| 1 | [分层与封装](/fundamentals/network/tcp-ip) | 数据在网络里长什么样、被谁处理 | 分层是为了**隔离变化**；MTU 1500 是所有传输层设计的隐含前提 |

| 3 | [HTTP 演进：1.1 → 2 → 3](/fundamentals/network/http) | 应用层协议为什么一代代重做 | HTTP/2 解决了**应用层**队头阻塞，HTTP/3 才解决**传输层**队头阻塞 |
| 4 | [DNS 与 CDN](/fundamentals/network/dns-cdn) | 域名怎么变成 IP、请求怎么被调度到最近的机房 | DNS 是**分布式缓存系统**，TTL 决定切换代价；CDN 本质是"用缓存换距离" |

### 4.2 概念级速查

| 问题 | 一句话答案 | 详见 |
|---|---|---|
| 域名、IP、MAC 分别在做什么？ | 域名给人看、IP 用于跨网络寻址、MAC 用于同一链路内寻址；DNS 与 ARP 分别是两张翻译表 | [#encapsulation](/fundamentals/network/tcp-ip#encapsulation) |
| MTU 和 MSS 什么关系？ | MTU 是链路层的载荷上限（以太网 1500），MSS = MTU − IP 头 − TCP 头；TCP 按 MSS 分段，为的就是**不让 IP 层分片** | [#mtu-mss](/fundamentals/network/tcp-ip#mtu-mss) |
| IP 分片和 TCP 分段有什么区别？ | 分段是 TCP 主动的、接收端可重组且有重传；分片是 IP 被动的、任一片丢失就要整包重传，代价高得多 | [#mtu-mss](/fundamentals/network/tcp-ip#mtu-mss) |
| 子网掩码在算什么？ | 算"目标和我是不是同一网段"——是则直接 ARP 找 MAC，否则交给网关转发 | [#ip-subnet](/fundamentals/network/tcp-ip#ip-subnet) |
| `ping` 通但 `telnet` 端口不通，说明什么？ | 网络层可达（ICMP 通），问题在传输层之后——服务没监听、被防火墙拦、或绑错网卡 | [#toolchain](/fundamentals/network/troubleshoot#toolchain) |
| `ss` 和 `netstat` 该用哪个？ | 用 `ss`。`netstat` 读 `/proc` 逐行拼，连接数上万时本身就会拖慢机器 | [#compare](/fundamentals/network/troubleshoot#compare) |
