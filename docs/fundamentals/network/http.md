# HTTP 演进：1.1 → 2 → 3

> 上一篇：[TCP 核心机制](/fundamentals/network/tcp)　|　下一篇：[DNS 与 CDN](/fundamentals/network/dns-cdn)

HTTP 三十多年只换了两代，而每一次换代的驱动力都是**同一个矛盾的两种表现**：**队头阻塞（Head-of-Line Blocking，HOL）**。

这篇的核心线索就是这一条：

```text
  HTTP/1.1  请求在应用层排队  →  浏览器只能开 6 个并发连接来绕
                                    ↓  HTTP/2 用「多路复用」解决了它
  HTTP/2    应用层不排队了，但底层是裸 TCP
            →  丢一个包，这条连接上所有流一起等（传输层 HOL）
                                    ↓  HTTP/3 把可靠传输搬到用户态按流实现
  HTTP/3    每条流独立重传，传输层 HOL 也消掉
```

**结论先放**：

1. **HTTP/2 只解决了应用层的队头阻塞**，它跑在 TCP 上，TCP 的丢包重传会阻塞这条连接上的所有请求。
2. **HTTP/3 的本质是把 TCP 的两个机制（有序交付、可靠重传）打散到"流"这一级**，为此必须放弃内核 TCP、在 UDP 上重做（QUIC）。
3. **服务端推送（Server Push）已经出局**——Chrome 106 起默认移除，Firefox 132 也移除，用 `103 Early Hints` 与 `rel=preload` 替代。
4. **HTTPS 的握手成本已经很低**：TLS 1.3 只需一次往返，恢复会话可 0-RTT。

## 一、问题场景：HTTP 到底在解决什么 {#why-http}

TCP 已经保证了字节可靠有序，但"一段字节流"和"一次业务请求"之间还差三层约定：

| 要约定的事 | HTTP 的答案 |
|---|---|
| 边界在哪 | 头部空行 + `Content-Length` / `Transfer-Encoding: chunked` |
| 请求什么 | 方法（GET/POST…）+ 路径 + 头部 |
| 结果如何 | 状态码 + 头部 + 体 |
| 怎么复用连接 | `Connection: keep-alive`（1.1 起默认） |
| 谁在跟谁说话 | Host 头（1.1 起强制）——这让一个 IP 能承载多个域名 |

**一个常被忽略的历史点**：`Host` 头是 HTTP/1.1 才**强制**的。它让"同一个 IP 上的多个站点"成为可能，是虚拟主机、CDN、反向代理这些东西的前提。少了它，Nginx 就没法按域名分流。

## 二、HTTP/1.1 与两层队头阻塞 {#http11}

### 2.1 最核心的缺陷：请求必须排队

HTTP/1.1 虽然支持 `keep-alive`（一条 TCP 连接上连续发多个请求），但在同一条连接上**同一时刻只能有一个请求在"处理中"**——必须等上一个响应回来，才能发下一个。

```text
  单条 HTTP/1.1 连接（串行）
  ──▶ 请求 A ──── 等 A 的响应 ────▶ 请求 B ──── 等 B 的响应 ────▶ 请求 C ──
      └────────── 如果 A 很慢（比如是个慢查询），B 和 C 全在排队 ──────────┘
                  这就是「应用层队头阻塞」
```

**浏览器的绕道方案**：对同一域名开 **6 个左右**并发 TCP 连接，让请求摊到多条连接上。代价是：

| 代价 | 说明 |
|---|---|
| 建连成本 | 每个连接都要 TCP 握手（+ TLS 握手），服务器端连接数被放大 6 倍 |
| 竞争 | 6 条连接之间在拥塞控制上互相抢带宽 |
| 仍然受限 | 6 条连接还是有限，页面有 100 个资源时照样排长队 |

**工程上的临时补丁**（这些手段的存在本身就说明 1.1 不够用）：

| 手段 | 思路 | 代价 |
|---|---|---|
| 域名分片（domain sharding） | 把资源拆到多个子域，突破 6 连接上限 | 更多连接与 DNS 查询；**HTTP/2 下反而是负优化**（应在同一连接复用） |
| 雪碧图 / 资源合并 | 减少请求数量 | 缓存粒度变粗——改一个小图标要重下整张图 |
| 内联（data URI / 内联脚本） | 消灭请求 | 无法单独缓存，且阻塞主文档 |

### 2.2 另一个 1.1 的老问题：头部重复传输

1.1 每个请求都要把 Cookie、User-Agent、Accept 这些头部**明文重复发一遍**，且**不压缩**。一个带 2KB Cookie 的请求，发 50 个资源就是 100KB 纯头部开销。这也是 HTTP/2 引入头部压缩的直接动机。

## 三、HTTP/2 {#http2}

HTTP/2 规范为 **RFC 9113**（取代 RFC 7540），HTTP 语义本身在 **RFC 9110**。**语义没变**（方法、状态码、头部含义一致），改的是"怎么在传输层上编码"。

### 3.1 四项核心改进

| 改进 | 做法 | 解决的问题 |
|---|---|---|
| **二进制分帧** | 把报文切成带类型的二进制帧（HEADERS / DATA / SETTINGS / WINDOW_UPDATE…） | 文本协议解析歧义多、扩展性差 |
| **多路复用** | 一条 TCP 连接上并行交错多个流（stream），每个流有独立 ID | **应用层队头阻塞** |
| **头部压缩（HPACK）** | 静态表 + 动态表 + 哈夫曼编码，重复头部只发索引 | 1.1 的头部重复传输 |
| **流优先级** | 声明哪些流更急 | 关键资源先到 |

```text
  HTTP/2 一条连接上多路复用
  ──▶ [流1 HEADERS][流3 HEADERS][流1 DATA][流5 HEADERS][流3 DATA][流1 DATA]…
                  ↑ 帧交错发送，接收端按流 ID 重组
       一条连接承载所有请求 → 不需要域名分片，也不需要 6 条连接
```

**流优先级的两段历史**（细节但显专业）：RFC 7540 原始的优先级方案**实现复杂、实际效果差，已被 RFC 9113 弃用**；取而代之的是更简单的可扩展优先级，定义在 **RFC 9218**（通过 `Priority` 头声明）。

### 3.2 遗留问题：跑在 TCP 上，传输层 HOL 还在

这是理解"为什么还要 HTTP/3"的关键：

```text
  HTTP/2 的困境
  连接上同时有 流1、流3、流5
      ↓
  TCP 只认「一串有序字节」——它不知道"流"的存在
      ↓
  承载 流3 的一个 TCP 段丢了
      ↓
  TCP 必须等这个段重传成功，才把后续字节交给上层
      ↓
  流1 和 流5 的数据其实早就到了，但被压在 TCP 缓冲区里交不上去
      ↓
  「一个包丢了，整条连接上所有请求一起等」
```

**根因**：TCP 的有序交付是**连接级**的，而 HTTP/2 的多路复用是**流级**的——两者粒度不匹配。**这个错配无法在应用层修复**，只能换传输层。

### 3.3 Server Push 已出局（这条要更新掉老资料）

HTTP/2 的 Server Push 曾被当作亮点，实际结果是**被主流浏览器移除**：

| 事实 | 细节 |
|---|---|
| 使用率极低 | 曾仅 1.25% 的 HTTP/2 站点使用，后来还降到约 0.7% |
| 效果存疑 | 分析结果不一致，**很多情况下反而性能回退**（推了已缓存或不用的资源，浪费带宽） |
| Chrome 移除 | **Chrome 106 起默认停用**，后续从 Blink 中移除 |
| Firefox 移除 | **Firefox 132 起移除** |
| HTTP/3 侧 | 很多 HTTP/3 实现直接没做 Push |

**替代方案**（要用就用这两个）：

| 替代 | 机制 | 为什么更好 |
|---|---|---|
| **`103 Early Hints`** | 服务端在最终响应前先回一个 103，只给"你可能需要这些资源"的**提示** | **浏览器保留决策权**（已缓存就不请求），比"强行推"安全 |
| **`rel=preload`** | 在 HTML 里声明关键资源优先加载 | 简单直观；但要求主文档先到 |

### 3.4 一个安全事件值得记住

**HTTP/2 Rapid Reset（CVE-2023-44487）**：攻击者用一条连接**快速开流再取消**，让服务端为大量"永远不会完成"的请求消耗 CPU。它暴露的是"多路复用"带来的新攻击面——**协议越省往返，越容易被用来放大攻击**。修复靠服务端补丁限制流取消速率。

## 四、HTTP/3 与 QUIC {#http3}

### 4.1 规范族与现状

| 规范 | 内容 | 发布时间 |
|---|---|---|
| **RFC 9000** | QUIC 传输本体（流、连接、帧） | 2021-05 |
| **RFC 9001** | 用 TLS 1.3 保护 QUIC | 2021-05 |
| **RFC 9002** | 丢包检测与拥塞控制 | 2021-05 |
| **RFC 9114** | HTTP/3（HTTP 语义映射到 QUIC） | 2022-06 |
| **RFC 9204** | QPACK（头部压缩） | 2022-06 |

**两个必须澄清的点**：

1. **HTTP/3 ≠ QUIC**。QUIC 是**传输层**协议，HTTP/3 是"跑在 QUIC 上的 HTTP"。QUIC 之上还可以跑别的（如 DNS over QUIC）。
2. **IETF QUIC 不是 Google 的 gQUIC**。gQUIC 自带一套私有加密、还有前向纠错（FEC）；IETF 版**丢掉了自家加密、改为内嵌 TLS 1.3**，**FEC 也在标准化前被移除**（实测它对 YouTube 等场景是负收益）。所以"QUIC 有 FEC"是十年前的旧认识。

### 4.2 QUIC 解决了什么

| 能力 | 怎么实现的 | 价值 |
|---|---|---|
| **彻底消除队头阻塞** | 流与流之间**独立**做有序交付与重传——丢包只卡住属于它的那条流 | 弱网、移动网络下收益最大 |
| **握手更快** | TLS 1.3 内嵌进传输层握手，新连接 **1-RTT**，会话恢复 **0-RTT**（有重放风险，需谨慎用于非幂等请求） | 省往返 ⇒ 首包更快 |
| **连接迁移** | 用不绑定 IP 的 **Connection ID** 标识连接 | 手机从 WiFi 切 4G，连接不断、不用重新握手 |
| **内核之外实现** | 跑在 UDP 上、在**用户态**实现可靠传输 | 协议演进不用等操作系统内核升级——这是它推广快的重要原因 |
| **默认加密** | 连传输层元数据都加密 | 中间盒难以窥探与干扰 |

**代价与限制**（面试里能说清代价才算真懂）：

- **UDP 未必通**：部分企业网络/防火墙封 UDP 443。**所以浏览器不会直接上 HTTP/3**——它先从常规 HTTPS 响应里的 **`Alt-Svc` 头**（或 HTTPS DNS 记录）得知服务端支持，再尝试 QUIC，**失败自动回落 HTTP/2**。这让部署 HTTP/3 风险很低。
- **CPU 开销更高**：用户态协议栈缺少内核优化（如 GSO/GRO 卸载），早期实测 CPU 占用偏高。
- **服务端支持参差**：Nginx 自 **1.25.0** 起才支持（且依赖 quiche 或 ngtcp2），Caddy 从 **2.6** 起默认开启。
- **采用率**：2026 年大约 **30%~35% 的网络流量**已走 HTTP/3，浏览器侧支持率超过 95%。**已经不能算"实验特性"，但也还不是全覆盖。**

### 4.3 QPACK 为什么不能沿用 HPACK

HTTP/2 的 HPACK 依赖"**所有帧按序到达**"来维护动态表（只发索引、双方同步更新表）。但 QUIC 的流**可以乱序到达**——如果动态表更新依赖顺序，一条流就会因为另一条流的数据没到而无法解压，**把头阻塞又请回来了**。

QPACK 的解法：**把"表更新"和"帧引用"解耦**，允许阻塞，但**限制阻塞的流数量**和**提供显式的确认机制**。**这是"换了传输层，上层压缩算法也得跟着重做"的典型案例。**

## 五、HTTPS 与 TLS 1.3 {#https}

### 5.1 为什么需要 HTTPS

| 没有 HTTPS 时的问题 | HTTPS 的三项保证 |
|---|---|
| 内容可被中间设备读取（明文） | **机密性**：对称加密 |
| 内容可被篡改（插入广告、改金额） | **完整性**：AEAD 认证加密 |
| 服务器身份可被冒充（DNS 劫持、假热点） | **身份认证**：数字证书 + CA 体系 |

**证书链的作用**：浏览器信任的是**预置的根 CA 列表**，服务端出示的证书由中间 CA 签发、中间 CA 由根 CA 签发。**信任是沿链条传递的**——所以"证书过期 / 链不全 / 域名不匹配"是三类最常见的握手失败原因。

### 5.2 TLS 1.3 砍掉了什么、为什么快

| TLS 1.2 | TLS 1.3 |
|---|---|
| 握手 2 个往返（2-RTT） | **1 个往返（1-RTT）**；会话恢复可 0-RTT |
| 支持 RSA 密钥交换 | **移除 RSA 密钥交换**，只保留（EC）DHE——**强制前向安全** |
| 支持多种分组密码模式（含 CBC） | 只留 AEAD（如 AES-GCM、ChaCha20-Poly1305） |
| 允许重协商、压缩 | **移除重协商与压缩**（压缩是 CRIME 攻击的根源） |
| 明文传输较多握手字段 | 大部分握手字段加密，中间设备能看到的更少 |

**"前向安全"为什么重要**：在 TLS 1.2 里用 RSA 密钥交换时，服务器的私钥一旦泄露，**攻击者可以解密此前录下的所有历史流量**。TLS 1.3 强制用临时密钥协商，**每次会话的密钥用完即弃**，私钥泄露也解不开旧流量。

### 5.3 后量子密码：2026 年的现实进展

这是一个值得更新的新事实（老资料里通常没有）：

| 项 | 状态 |
|---|---|
| 威胁模型 | "先记录、后解密"——今天录下的加密流量，等量子计算机成熟后再破解 |
| 标准 | **ML-KEM**（原 Kyber）由 NIST 于 2024-08 标准化，用于密钥交换 |
| 部署方式 | **混合模式**：经典 ECDHE 与 ML-KEM 同时跑、共享密钥混合——**任一方安全则连接安全**，不赌单一算法 |
| 落地速度 | Cloudflare 自 2024 年起对所有域名默认启用 hybrid X25519+ML-KEM；截至 **2026 年 4 月约 52% 的 TLS 握手**已使用具备后量子能力的密钥交换 |
| 签名侧 | ML-DSA（原 Dilithium）签名更大、证书生态要改，**推进较慢，预计 2027–2030 逐步铺开** |

**实用结论**：如果你把站点放在主流 CDN 后面，**后量子保护可能已经默认生效了**，不需要你做任何配置。

### 5.4 一个实务细节

**浏览器只在 TLS 之上协商 HTTP/2 与 HTTP/3**（通过 ALPN）。所以"要不要上 HTTPS"在现代浏览器里已经不是选择题——**不上 HTTPS 连 HTTP/2 都用不了**。

## 六、缓存与状态码 {#cache-status}

### 6.1 强缓存 vs 协商缓存

| | 强缓存 | 协商缓存 |
|---|---|---|
| 要不要发请求 | **不发**，直接用本地副本 | **要发**，但服务端可能只回一个 304（不带体） |
| 谁决定 | 浏览器自己看新鲜度 | 服务端比较后决定 |
| 相关头 | `Cache-Control: max-age` / `Expires` | `ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since` |
| 成本 | 最低（零请求） | 一次往返，但省了响应体 |
| 失效方式 | 到期 | 内容变了 |

**优先级与坑**：

- `Cache-Control` **优先于** `Expires`（后者是绝对时间，受客户端时钟影响）。
- **`ETag` 优先于 `Last-Modified`**——后者精度只到秒，且"文件时间变了但内容没变"会造成误判。
- **`no-cache` ≠ `no-store`**：`no-cache` 是"可以缓存，但每次都要**去验证**"（走协商）；`no-store` 才是"完全不缓存"。这两个混用是常见配置错误。

**前端发布的标准做法**：**内容哈希文件名 + 长 `max-age`**——文件内容变了名字就变了，天然绕过缓存问题，不需要用户清缓存。**这比配 `no-cache` 高明得多。**

### 6.2 状态码分类

| 段 | 含义 | 要记住的 |
|---|---|---|
| 1xx | 信息 | **`101 Switching Protocols`**（WebSocket 升级）、**`103 Early Hints`**（Server Push 的替代） |
| 2xx | 成功 | `200`、`204 No Content`、`206 Partial Content`（断点续传/视频拖动） |
| 3xx | 重定向 | `301` 永久（会缓存）、`302` 临时、**`304 Not Modified`**、`307/308` 保留方法与体 |
| 4xx | 客户端错 | `400`、`401`（未认证）、`403`（无权限）、`404`、`429 Too Many Requests`（限流） |
| 5xx | 服务端错 | `500`、`502`（网关收到无效响应，通常是后端挂了）、`503`、**`504`（网关超时）** |

**排障落点**：**502 和 504 的区分很有用**——502 是"后端回了垃圾/没回完整"，504 是"等后端等到超时"。一个是后端崩了，一个是后端慢。**Nginx 日志里的 upstream 状态能进一步区分**（`upstream prematurely closed connection` vs `upstream timed out`）。

## 七、对比辨析 {#compare}

### 7.1 三代 HTTP

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | **QUIC over UDP** |
| 规范 | RFC 9112（1.1） | **RFC 9113** | **RFC 9114** + RFC 9000 |
| 编码 | 文本 | **二进制分帧** | 二进制分帧 |
| 并发 | 一条连接一个请求（靠多连接绕） | **单连接多路复用** | 单连接多路复用（**流级独立**） |
| 头部压缩 | 无 | **HPACK** | **QPACK** |
| 应用层 HOL | **有** | 解决 | 解决 |
| 传输层 HOL | 有 | **仍有**（裸 TCP 的固有缺陷） | **消除**（丢包只阻塞所属流） |
| 握手往返 | TCP 1 + TLS 2 | 同左 | 新连接 **1-RTT**，恢复 **0-RTT** |
| 连接迁移 | 不支持（换网即断） | 不支持 | **支持**（Connection ID） |
| 服务端推送 | 无 | 有但**已出局** | 实现普遍缺失 |
| 部署风险 | —— | 低（回落 1.1） | 低（靠 `Alt-Svc` 发现，失败回落 h2） |

### 7.2 三组易混概念

| 对照 | A | B | 区别 |
|---|---|---|---|
| 队头阻塞 | 应用层 HOL | 传输层 HOL | 前者是"请求排队"（h2 已解）；后者是"丢包阻塞所有流"（只有 h3 能解） |
| 缓存头 | `no-cache` | `no-store` | 前者"缓存但每次验证"，后者"完全不存"。**混用会导致该缓存的没缓存、敏感的却存了** |
| 缓存校验 | `ETag` | `Last-Modified` | 前者是内容指纹、精度高；后者只到秒，且会被"改回原内容"误判 |
| 网关错 | 502 | 504 | 前者后端响应无效（多半挂了），后者等后端超时（慢） |

### 8.2 高频问答

| 问题 | 答案要点 |
|---|---|
| HTTP/1.1 的队头阻塞和 HTTP/2 的是一回事吗？ | **不是**。1.1 是请求在应用层串行排队；h2 已解决它，但裸 TCP 上丢包仍会阻塞该连接所有流 |
| HTTP/2 为什么还留着队头阻塞？ | 因为 TCP 的有序交付是**连接级**，而多路复用是**流级**——粒度错配，**无法在应用层修复** |
| 那 HTTP/2 凭什么比 1.1 快？ | 多路复用消除了请求排队、HPACK 省掉重复头部、单连接免去 6 倍建连成本 |
| HTTP/3 为什么建在 UDP 上？ | 要绕开 TCP 的连接级有序语义与内核实现，把可靠传输下沉到**用户态按流**实现；顺带获得连接迁移与快速迭代能力 |
| QUIC 有前向纠错（FEC）吗？ | **没有**。那是 Google gQUIC 的方案，实测负收益，**标准化前已移除** |
| 浏览器怎么知道该用 HTTP/3？ | 先正常走 HTTPS，从响应头的 **`Alt-Svc`**（或 HTTPS DNS 记录）得知；尝试 QUIC 失败则回落 HTTP/2 |
| Server Push 现在能用吗？ | **基本不能**。Chrome 106 起默认移除、Firefox 132 移除；改用 `103 Early Hints` + `rel=preload` |
| 为什么 HTTP/3 要用 QPACK 而不是 HPACK？ | HPACK 的动态表依赖"帧按序到达"，而 QUIC 的流**可乱序到达**——沿用会把头阻塞请回来。QPACK 把表更新与帧引用解耦并限流 |
| TLS 1.3 比 1.2 快在哪？ | 握手从 2-RTT 降到 **1-RTT**（恢复可 0-RTT）；只保留 AEAD 与（EC）DHE，砍掉 RSA 密钥交换、重协商与压缩 |
| "前向安全"是什么意思？ | 会话密钥用完即弃：即使服务器私钥将来泄露，**也解不开此前录下的流量**。TLS 1.3 通过强制 DHE 实现 |
| 后量子进展到哪了？ | ML-KEM 2024-08 成为 NIST 标准，以**混合模式**部署（X25519+ML-KEM）；2026-04 约 **52%** 的 TLS 握手已具备 PQ 能力；签名侧 ML-DSA 推进较慢 |
| `no-cache` 和 `no-store` 有什么区别？ | `no-cache`＝可以存但每次必须验证；`no-store`＝完全不存。混用会造成缓存失效或敏感数据被缓存 |
| ETag 和 Last-Modified 用哪个？ | 优先 `ETag`：它是内容指纹，而 `Last-Modified` 只到秒、且"时间变了内容没变"会误判 |
| 前端发布怎么让用户不用清缓存？ | **内容哈希文件名 + 长 `max-age`**：内容变→文件名变→天然失效。比配 `no-cache` 更可靠 |
| 域名分片在 HTTP/2 下还要做吗？ | **不要**，反而是负优化。h2 下所有资源应走**同一条连接**以复用多路复用与头部压缩 |
| 502 和 504 的区别？ | 502＝后端返回无效响应（多半挂了）；504＝等后端超时（慢）。**一个是崩，一个是慢** |
