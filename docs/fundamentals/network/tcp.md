# TCP 核心机制

> 上一篇：[分层与封装](/fundamentals/network/tcp-ip)　|　下一篇：[HTTP 演进：1.1 → 2 → 3](/fundamentals/network/http)

TCP 是全站最值得逐字读透的一篇——因为它解释的现象最多：**为什么偶发超时会远超设定值、为什么连接池会莫名耗尽、为什么 RPC 要开 `TCP_NODELAY`、为什么高并发短连接会堆 TIME_WAIT、为什么自研协议一定会遇到粘包**。这些问题的答案都在 TCP 的机制里，而不是在框架文档里。

**先把结论放前面**：

1. **TCP 提供的是一串字节，不是一串消息**。它不保证消息边界——粘包不是 bug，是"你以为它在传消息"的误解。
2. **可靠性是用延迟换来的**。确认、重传、拥塞控制这套机制让"不丢"成立，代价是抖动和额外往返。
3. **实际能发多快 = min(接收窗口, 拥塞窗口)**。一个是"对方收得下吗"，一个是"网络受得了吗"。
4. **TIME_WAIT 是主动关闭方的正常状态**；真正要警惕的是 **CLOSE_WAIT 堆积**——那是代码没关连接的信号。

## 一、问题场景：TCP 到底解决了什么 {#why-tcp}

IP 层只承诺"尽力而为"（best effort）：**可能丢、可能乱序、可能重复、可能延迟**。在这之上要传可靠数据，有两条路：

| 做法 | 说明 | 代价 |
|---|---|---|
| 应用层自己处理 | 每个业务自己实现确认、重传、排序 | 重复造轮子，且每个实现都可能出错 |
| **交给传输层统一做** | TCP 把不可靠的 IP 变成"看起来可靠的字节流" | 为通用性付出性能代价（延迟、头部开销） |

TCP 选择的是后者，所以它必须解决四件事：

| 要解决的问题 | TCP 的手段 |
|---|---|
| 丢包 | 序号 + 确认 + 超时重传 + 快速重传 |
| 乱序 | 序号 + 接收缓冲区重组 |
| 重复 | 序号去重（重复段直接丢） |
| 收不下的情况 | 滑动窗口做**流量控制** |
| 网络承受不住 | 拥塞窗口做**拥塞控制** |

**"连接"到底是什么？** 这是理解 TCP 的一个关键去魅点：TCP 连接**不是一条物理通路，内核里也没有一个叫"连接"的实体**。所谓连接，就是双方内核里各存了一份状态，用**四元组**（源 IP、源端口、目的 IP、目的端口）互相标识。这也解释了：为什么四元组耗尽就没法建新连接、为什么 NAT 设备上的四元组资源是稀缺的。

## 二、三次握手 {#handshake}

### 2.1 过程

```text
     客户端                                              服务端
       │                                                   │
       │  ① SYN  seq=x  （我还想告诉你：MSS、窗口缩放…）      │
       │ ─────────────────────────────────────────────────▶│  状态：SYN_RCVD
       │                                                   │  （进半连接队列）
       │  ② SYN+ACK  seq=y, ack=x+1                        │
       │ ◀─────────────────────────────────────────────────│
       │  状态：ESTABLISHED                                  │
       │                                                   │
       │  ③ ACK  ack=y+1                                   │
       │ ─────────────────────────────────────────────────▶│  状态：ESTABLISHED
       │                                                   │  （移入全连接队列，
       │                                                   │    等 accept() 取走）
```

**双方确认了什么**，这是"为什么是三次"的核心：

| 步骤 | 客户端确认 | 服务端确认 |
|---|---|---|
| ① SYN 发出 | —— | 确认"客户端发送能力正常、自己接收能力正常" |
| ② SYN+ACK 收到 | 确认"自己收发都正常、服务端收发都正常" | —— |
| ③ ACK 收到 | —— | 确认"服务端发送能力正常、客户端接收能力正常" |

**为什么不是两次**：两次时，**服务端无法确认自己的发送能力**——它发出了 SYN+ACK，但不知道对方是否收到。更要命的是**历史失效连接问题**：一个很早以前、因网络拥塞被困在中间设备里的 SYN 迟到了，服务端会当成新请求建立连接并分配资源，而客户端根本不认这个连接（两次就"建立"了），资源被白白占用。**第三个 ACK 就是让服务端确认"这是当下的真实请求"。**

**为什么不是四次**：服务端把"确认对方 SYN"和"自己发 SYN"合并成了一个报文（SYN+ACK），省掉一次往返。

### 2.2 两个队列：握手阶段的真实瓶颈

服务端在握手期间维护**两个队列**，这是理解"连接建立不上"的关键：

| 队列 | 存什么 | 相关内核参数 | 溢出表现 |
|---|---|---|---|
| **半连接队列**（SYN queue） | 收到 SYN、已回 SYN+ACK、**还没等到 ACK** 的连接 | `net.ipv4.tcp_max_syn_backlog` | 新 SYN 被丢弃，客户端超时后重试 |
| **全连接队列**（accept queue） | 三次握手已完成、**等着应用 `accept()` 取走**的连接 | `min(backlog, net.core.somaxconn)` | 队列满后新完成的连接被丢弃或回 RST |

**三个非常实用的落点**：

1. **`listen()` 的 `backlog` 参数不等于你写的值**，实际取 `min(backlog, somaxconn)`。很多语言/框架的默认 backlog 很小（如 128），高并发下会成为瓶颈。
2. **`ss -lnt` 能直接看到队列水位**：`Recv-Q` 是当前堆积在 accept 队列里没被取走的连接数，`Send-Q` 是队列上限。**`Recv-Q` 持续接近 `Send-Q`，说明应用 accept 得太慢**（典型原因是应用线程被别的活占满）。
3. **半连接队列被打满是 SYN Flood 的典型症状**。防御手段是 **SYN Cookies**：服务端不再为半连接分配内存，而是把自己的状态编码进 `seq` 里回给对方，收到 ACK 时再还原——代价是丢失部分选项（如窗口缩放），所以**只在压力下才启用**。

## 三、四次挥手与 TIME_WAIT {#teardown}

### 3.1 过程

```text
     主动关闭方                                          被动关闭方
       │                                                   │
       │  ① FIN  seq=u                                     │
       │ ─────────────────────────────────────────────────▶│  FIN_WAIT_1 → CLOSE_WAIT
       │  ② ACK  ack=u+1                                   │
       │ ◀─────────────────────────────────────────────────│
       │  FIN_WAIT_2                                        │
       │                                                   │  ……应用调用 close()……
       │  ③ FIN  seq=w                                     │
       │ ◀─────────────────────────────────────────────────│  LAST_ACK
       │                                                   │
       │  ④ ACK  ack=w+1                                   │
       │ ─────────────────────────────────────────────────▶│  CLOSED
       │  TIME_WAIT（等 2MSL 后 → CLOSED）                  │
```

**为什么是四次而握手是三次**：TCP 是**全双工**的，两个方向独立关闭。一方发 FIN 只表示"我不再发数据了"，**不代表对方也没有数据要发**。所以"确认对方的 FIN"和"自己发 FIN"不能合并——中间可能隔着一段对方还在发数据的时间。而握手时双方都没有数据要发，可以合并。

### 3.2 TIME_WAIT 为什么必须存在

主动关闭方在收到最后的 ACK 前，要额外等 **2MSL**（报文最大生存时间的两倍，Linux 上通常表现为 60 秒）。两个理由：

1. **保证最后一个 ACK 能到达对方**。如果这个 ACK 丢了，对方会超时重发 FIN；此时若本端已经彻底关闭，收到 FIN 只能回 RST——对方收到 RST 会认为"连接异常"，而不是"正常关闭"。**等 2MSL 期间保持状态，才能重发 ACK。**
2. **让本次连接的残余报文在网络中自然消亡**。否则一个延迟很久的旧报文可能被同一四元组的新连接收到，造成数据错乱。等 2MSL 就能保证旧报文已经过期。

### 3.3 TIME_WAIT 与 CLOSE_WAIT：两个性质完全不同的问题

这一节的落点极其重要——**很多人把这两个搞混，然后去"优化"错的那个**。

| | TIME_WAIT | CLOSE_WAIT |
|---|---|---|
| 谁的状态 | **主动**关闭方 | **被动**关闭方 |
| 触发原因 | 正常的、协议要求的状态 | 收到对方的 FIN，但**应用没有调用 `close()`** |
| 是不是 bug | **不是**。是 TCP 正确性的保证 | **是**。几乎总是应用层的连接泄漏（没关连接、异常路径漏了 finally、连接池只借不还） |
| 处置方向 | 减少主动关闭（用长连接、连接复用），或作为客户端时开启 `tcp_tw_reuse` | 查代码，把连接关掉。加内核参数**没用**，因为状态没往前走 |

**TIME_WAIT 过多的两种不同成因**（诊断时必须先分清）：

| 成因 | 特征 | 对策 |
|---|---|---|
| **短连接过多** | 每次请求都建连，服务器或客户端频繁主动关闭 | 改用长连接 / 连接池（治本）；`tcp_tw_reuse` 只算缓解 |
| **主动关闭方是服务端** | 服务端先关（如客户端读超时、业务上"服务端主动断开"） | 让客户端主动关闭（把关闭责任推给连接发起方） |

> **两个被广泛误用的参数**：
> - `tcp_tw_recycle`：**已于 Linux 4.12 从内核移除**。它会丢弃来自同一源 IP 但时间戳更小的包，**在 NAT 环境下会误杀大量正常连接**（成百上千个用户共享一个出口 IP）。看到老文档推荐它，直接跳过。
> - `tcp_tw_reuse`：**只对主动发起连接的一方安全有效**（依赖 `tcp_timestamps`）。它复用的是"作为客户端时"的本地端口，不影响接收来自旧连接的报文——所以对"服务端 TIME_WAIT 堆积"帮助有限。

## 四、可靠传输 {#reliability}

### 4.1 序号、确认与重传

| 机制 | 做法 | 解决的问题 |
|---|---|---|
| 序号（seq） | 每个字节都有编号（SYN/FIN 各占 1） | 乱序重组、重复识别 |
| 累计确认（ack） | `ack=n` 表示"**n 之前的所有字节我都收到了**" | 一个报文确认一大段，省带宽 |
| 超时重传 | 超时未确认就重发 | 兜底 |
| **快速重传** | 收到 **3 个重复 ACK** 立即重传，不等超时 | 快得多——不用等 RTO 到期 |
| **SACK**（选择确认） | 通过选项告诉对方"我还缺这一段，别的都收到了" | 避免"缺一个包要重传后面全部" |

**累计确认的一个副作用**：如果中间丢了一个包，后面到达的包都无法被"确认"（因为 ack 编号必须连续）。这就是为什么需要快速重传与 SACK——**它们是针对"累计确认"这个设计的补丁**。

### 4.2 RTO 怎么算：Karn 算法为什么必要

重传超时时间不能是固定值——它必须跟着实际 RTT 走。RFC 6298 的做法是维护平滑的 RTT 估计：

```text
  SRTT  = (1 - α) × SRTT  + α × RTT样本          （α = 1/8，平滑）
  RTTVAR = (1 - β) × RTTVAR + β × |SRTT - RTT样本| （β = 1/4，偏差）
  RTO   = SRTT + 4 × RTTVAR                      （有下限，通常 200ms 起）
```

**Karn 算法**解决的坑是：**被重传过的段，它的 RTT 样本不能用来更新 RTO**。因为重传之后收到的 ACK，你无法判断它确认的是原始报文还是重传报文——如果用错了样本，RTO 会被严重低估，导致更激进的重传，形成恶性循环。**重传过的段不做采样**，这是 Karn 的核心。

### 4.3 这个机制带来的第一个"反直觉"

**设定 3 秒超时的调用，实际可能等 20 秒以上才失败。** 原因：超时是分层的，而且底层有重传。

```
  应用层超时 3s  ─┐
  连接超时        │  一次 RPC 实际要经历的等待：
  读超时         │  ① DNS 解析（可能几秒，且自带重试）
  写超时        ─┘  ② TCP 建连（SYN 重传：1s → 2s → 4s…指数退避）
                    ③ TLS 握手（多次往返）
                    ④ 请求传输（丢包则按 RTO 重传，RTO 本身还会翻倍）
                    ⑤ 服务端处理时间
```

**所以"超时要分层设置且逐层收敛"**：DNS < 建连 < 读 < 应用总超时。<br>
**也所以"重试必须配退避"**：在已经拥塞的链路上立即重试，等于往堵塞的路口再加车。

## 五、滑动窗口与流量控制 {#flow-control}

### 5.1 窗口就是"我还能收多少"

每个 ACK 都携带一个**接收窗口（rwnd）**字段，意思是"从确认号开始，我还能收这么多字节"。发送方据此限制"已发送但未确认"的数据量。

**为什么需要它**：接收方的应用可能读得很慢（比如业务在写磁盘），数据堆积在内核接收缓冲区里。缓冲区满了再收只会被丢弃并触发无谓重传。**窗口把"我快撑不住了"提前告诉对方**。

| 情况 | 处理 |
|---|---|
| 窗口变为 0 | 发送方停止发送，启动**坚持计时器（persist timer）**，定期发探测包问"窗口开了吗" |
| 窗口变小（应用读得慢） | 发送方降速。**窗口收缩是被允许的，但不推荐** |
| 窗口变大 | 发送方可以多塞数据 |

**窗口字段只有 16 位**（最大 65535 字节），这个数字在高带宽高时延链路上远远不够——所以要靠**窗口缩放选项**（Window Scale，在握手时协商）把窗口左移放大。这也是"长肥管道"为什么必须开这个选项。

### 5.2 Nagle 算法与延迟确认：一个经典的互相伤害

两个为"省带宽/省 CPU"而生的优化，凑在一起会制造延迟：

| 机制 | 做什么 | 目的 |
|---|---|---|
| **Nagle 算法** | 有未确认的小数据时，**先把小数据攒起来**，等能一次发出去或收到确认后再发 | 减少小包数量 |
| **延迟确认** | 收到数据后**不立刻回 ACK**，等最多约 40ms 看能否捎带数据一起回 | 减少 ACK 数量 |

**两者相遇的经典问题**：客户端用 Nagle 攒着小包等确认，服务端用延迟确认等 40ms 再回——**互相等**，表现为**每次小请求固定多出约 40ms**。这就是"接口单个测试很快、串起来跑就慢"的一种成因。

**解法**：对延迟敏感的场景（RPC、实时通信、数据库协议）**关闭 Nagle**——即设置 `TCP_NODELAY`。**代价**是会产生更多小包，所以它是"延迟换带宽"的取舍，不是无脑开。

> **落点**：这解释了为什么几乎所有 RPC 框架与 Redis / MySQL 客户端都默认 `TCP_NODELAY`。而批量日志上报这类场景反而适合保留 Nagle——**是否关闭取决于"延迟敏感还是吞吐敏感"**。

### 5.3 糊涂窗口综合症（SWS）

另一种浪费：接收方应用每次只读走几个字节，于是反复通告"窗口 = 3 字节"，发送方就反复发 3 字节的小包。**双方都在做无用功**。对策是：接收方窗口小于某个阈值时不通告（等攒大再通告），发送方小于 MSS 时不急着发。**本质是"别用碎片化的小窗口把链路当涓流用"。**

## 六、拥塞控制 {#congestion}

### 6.1 流量控制 vs 拥塞控制

这是最容易混的一对概念，一句话分清：

| | 流量控制 | 拥塞控制 |
|---|---|---|
| 关心谁 | **接收方**来得及收吗 | **网络**受得了吗 |
| 依据 | 对端通告的 `rwnd` | 自己推断的 `cwnd`（丢包/延迟信号） |
| 谁受伤 | 撑爆对端缓冲区，丢包重传 | 压垮中间链路，全网络一起恶化 |

**发送窗口 = min(rwnd, cwnd)**。两个都满足才敢发。

### 6.2 四个阶段

```text
  cwnd
    ▲
    │                        ┌── ③ 快恢复：ssthresh 和 cwnd 都减半，
    │                       │      然后进入线性增长
    │     慢启动             │
    │   （指数增长）   拥塞避免（线性增长）
    │        │              │
    │        │              │
    │        └──── ssthresh ─┘
    │            （慢启动阈值：超过它就放慢）
    │
    └──────────────────────────────────────────────▶ 时间 / RTT
              ② 超时：cwnd = 1，重新慢启动（重  ③' 丢包（3 个重复 ACK）：
                 创；ssthresh 也减半              cwnd 减半，不回到起点
```

| 阶段 | 增长方式 | 什么时候切换 |
|---|---|---|
| **慢启动** | 每收到一个 ACK，cwnd 加 1 个 MSS → **每 RTT 翻倍（指数）** | cwnd 达到 `ssthresh` |
| **拥塞避免** | 每 RTT 加 1 个 MSS（线性） | 检测到丢包 |
| **快速重传** | 3 个重复 ACK 就立即重传，不等超时 | —— |
| **快恢复** | cwnd 与 ssthresh 减半，直接进入拥塞避免（**不是回到慢启动**） | 下一轮 |

**名称里的坑**："慢启动"**一点都不慢**——它是**指数增长**。"慢"指的是"从一个 MSS 这么小的窗口开始"，不是增速慢。这个命名是历史上公认的误导。

**为什么超时比快速重传惩罚更重**：超时意味着"连 ACK 都回不来"，网络状况可能更糟，所以 cwnd 直接归 1 重新来过；而 3 个重复 ACK 说明"数据还在流动，只是丢了个别包"，所以只减半。**惩罚强度与"证据强度"成反比**——这是设计上很讲究的一点。

### 6.3 CUBIC 与 BBR：两种哲学

| | CUBIC（Linux 长期默认） | BBR（Google 提出） |
|---|---|---|
| 核心信号 | **丢包** = 拥塞 | **不把丢包当拥塞**；建"带宽 × 最小 RTT"模型 |
| 增长曲线 | 三次函数，接近上一次拥塞点时才放缓（因此得名） | 按探测到的带宽与往返时延主动定速 |
| 优势场景 | 通用、对传统网络友好 | **有随机丢包的链路**（丢包不等于拥塞，如部分无线/跨洋链路） |
| 争议 | 在有缓冲膨胀的链路上可能把队列顶满 | 与传统 CUBIC 流竞争时可能占优；对缓冲深度敏感 |

**理解这个对照的价值**：它说明"拥塞"是个**推断**，不是可测量的量。CUBIC 的推断是"丢包了所以拥塞"，BBR 的推断是"带宽时延积变了所以拥塞"。**换一种推断就换一套行为**——这是所有拥塞控制算法的本质分歧。

## 七、粘包与拆包 {#sticky-packet}

### 7.1 先纠正一个说法：粘包不是 TCP 的缺陷

TCP 提供的是**字节流（byte stream）**：它保证"字节按顺序、不丢不重地到达"，**但完全不保证"你一次 send 的内容，对方一次 recv 就能拿到"**。

```text
  发送方 3 次 send                    接收方可能出现的情况
  ┌────┐┌────┐┌────┐               ①  一次 recv 拿到全部：「ABC」        ← "粘包"
  │ A  ││ B  ││ C  │               ②  一次 recv 只拿到一半：「A」+「BC」  ← "拆包"
  └────┘└────┘└────┘               ③  拿到「AB」+「C」（任意切分都可能）
```

**为什么会这样**：发送侧 Nagle 会攒批、内核发送缓冲区会合并；接收侧内核缓冲区是"一池子字节"，`recv` 只是从池子里取走当前有多少。**边界信息从来没有被传输过**，所以也就无从恢复。

**对比 UDP**：UDP 是**数据报**协议，一个 `sendto` 对应一个 `recvfrom`，**内核保留边界**。所以 UDP 不会粘包——但换来的是"不保证到达、不保证顺序、包太大直接丢"。

### 7.2 三种解法

| 方案 | 做法 | 优缺点 | 典型用例 |
|---|---|---|---|
| **长度字段**（最常用） | 头部固定几字节声明"后面还有 N 字节" | 一次解析、效率高；需要处理"头都没收全"的情况 | 几乎所有自研 RPC、二进制协议（Dubbo、gRPC 帧） |
| **分隔符** | 用特殊字符（如 `\n`、`\r\n`）标记消息结束 | 可读性好、实现简单；**内容里出现分隔符要转义** | Redis 协议、HTTP 头部、日志流 |
| **定长** | 每条消息固定长度 | 实现最简单；**浪费带宽**，不灵活 | 少数嵌入式/金融场景 |

**工程上必须处理的两个细节**：

1. **"头都没收全"**：定长头本身也可能被拆开。正确做法是**先读满头部字节数，解出长度，再按长度读满消息体**——不能假设一次 `read` 就能拿到完整的头。
2. **长度字段的信任问题**：如果直接按对端声明的长度分配缓冲区，一个恶意的超大长度会让服务端 OOM。**必须设上限并校验**——这是很多自研协议的经典安全漏洞。

## 八、对比辨析 {#compare}

### 8.1 TCP vs UDP

| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（三次握手） | 无连接，直接发 |
| 可靠性 | 确认 + 重传，保证不丢不重不乱 | 不保证 |
| 边界 | **字节流，无边界** | **数据报，保留边界** |
| 顺序 | 保证有序 | 不保证 |
| 速度/开销 | 头 20 字节起，且要握手、要等待 | 头 8 字节，无握手 |
| 流量/拥塞控制 | 都有 | 都没有（应用自己实现，如 QUIC） |
| 一对多 | 只支持一对一 | 支持一对一/一对多/多对多（组播、广播） |
| 适合 | 文件传输、HTTP、数据库、RPC | DNS、音视频、游戏、日志上报、QUIC 底座 |

**怎么选**（一句话判据）：**"丢一个包能不能接受、消息边界要不要保留"**——

- 不能丢（数据要完整）→ TCP
- 能丢（丢一帧画面比卡一下好）→ UDP
- 需要边界且能自己实现可靠性 → 在 UDP 上自建（QUIC 走的就是这条路）

### 8.2 三组易混状态/概念

| 对照 | A | B | 区别 |
|---|---|---|---|
| 关闭状态 | TIME_WAIT | CLOSE_WAIT | 前者是主动关闭方的**正常**状态；后者是被动方的**异常**状态（应用没 close） |
| 控制机制 | 流量控制 | 拥塞控制 | 前者看**接收方**容量（rwnd）；后者看**网络**容量（cwnd） |
| 大块切分 | TCP 分段 | IP 分片 | 前者主动、可单独重传；后者被动、丢一片全重传 |
| 优化手段 | Nagle | 延迟确认 | 都是省小包/省 ACK；**同时开启会互相等待造成延迟** |

### 9.2 高频问答

| 问题 | 答案要点 |
|---|---|
| 为什么是三次握手？两次不行吗？ | 两次时**服务端无法确认自己的发送能力**，且历史延迟的 SYN 会让服务端建立"客户端不认"的连接白占资源 |
| 为什么挥手是四次，不能三次？ | TCP 全双工，一方 FIN 只关闭单向；"确认对方 FIN"和"自己发 FIN"中间可能隔着对方还在发数据 |
| 为什么要有 TIME_WAIT？ | ① 保证最后的 ACK 能重发（否则对方只能收到 RST）；② 让旧报文在网络中消亡，避免污染同一四元组的新连接 |
| TIME_WAIT 过多怎么处理？ | 先分清成因：**短连接过多**→改长连接/连接池（治本）；**服务端主动关闭**→把关闭责任交给客户端。`tcp_tw_reuse` 只在主动发起连接时安全有效 |
| CLOSE_WAIT 多说明什么？ | **代码 bug**——收到 FIN 但没 `close()`。查连接泄漏、异常路径未关、连接池只借不还。调内核参数无效 |
| `tcp_tw_recycle` 能用吗？ | **不能**，Linux 4.12 已移除；它会按时间戳丢弃包，NAT 环境下误杀大量正常连接 |
| TCP 是字节流是什么意思？ | 不保留消息边界——`send` 3 次，对方可能 1 次 `recv` 拿全，也可能拿到一半。所以**粘包必须由应用层解决** |
| 粘包怎么解决？ | 长度字段（最常用）/ 分隔符 / 定长。自研协议务必**先读满头再按长度读体**，并对长度设上限防 OOM |
| 累计确认有什么缺点？ | 中间丢一个包会让后续到达的包无法被确认（ack 必须连续）→ 所以才需要**快速重传与 SACK** |
| Karn 算法解决什么问题？ | 重传过的段不用于 RTT 采样——否则会把 ACK 当成对重传的确认，导致 RTO 被严重低估 |
| 快速重传为什么是 3 个重复 ACK？ | 1~2 个可能是乱序而非丢包；3 个足以排除偶然乱序。**惩罚强度要与证据强度匹配** |
| 慢启动真的慢吗？ | **不慢，是指数增长**。"慢"指起点小（1 个 MSS），命名有历史误导性 |
| 超时和快速重传的惩罚为什么不同？ | 超时说明 ACK 都回不来（网络更糟）→ cwnd 归 1；3 个重复 ACK 说明数据仍在流动 → cwnd 减半 |
| Nagle 和延迟确认为什么互相伤害？ | 发送方攒包等确认、接收方等 40ms 再回 ACK → 互等，小请求固定多约 40ms。RPC 要设 `TCP_NODELAY` |
| `TCP_NODELAY` 是万能优化吗？ | 不是。它是**延迟换带宽**：关闭后小包变多。延迟敏感开、吞吐敏感（批量日志上报）保留 Nagle |
| 发送窗口由什么决定？ | `min(接收窗口 rwnd, 拥塞窗口 cwnd)`——一个管"对方收得下吗"，一个管"网络受得了吗" |
| 为什么窗口字段要"缩放"？ | 原始字段仅 16 位（最大 64KB），高带宽高时延链路上不够用；靠握手时协商的 Window Scale 选项放大 |
| TCP 连接到底是什么？ | 内核中的一对状态 + **四元组**标识，不是一条物理通路。四元组耗尽就无法建新连接 |
