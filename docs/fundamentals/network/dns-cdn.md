# DNS 与 CDN

> 上一篇：[HTTP 演进：1.1 → 2 → 3](/fundamentals/network/http)　|　下一篇：[网络排查实战](/fundamentals/network/troubleshoot)

前面几篇讲的是"数据怎么传"，这一篇讲**"传给谁"**。听起来是小事，实际上它决定了三件很重的工程问题：

1. **切换的成本**——机房迁移、服务扩容、灰度发布，都要靠 DNS 或 CDN 把人导过去。**TTL 设多长，决定了你切换时要"忍多久的不一致"。**
2. **就近接入**——同一域名，深圳用户和北京用户应该拿到不同的 IP。
3. **可用性**——故障时能不能快速把流量摘到健康机房。

**结论先放**：

1. **DNS 的本质是一个分布式缓存系统**，不是一次"查询服务"。理解了缓存，就理解了 TTL、解析延迟、以及"为什么改了记录没生效"。
2. **递归与迭代是两种角色分工**，不是一个东西的两个阶段——客户端让解析器"帮我查到底"（递归），解析器自己"逐级去问"（迭代）。
3. **CDN 的核心是"用缓存换距离"**，调度是它的第二个能力。调度做偏了，缓存再强也没用。
4. **DNS 调度天然不精确**——它看到的是**用户本地 DNS 的出口 IP**，不是用户真实 IP。

## 一、问题场景：为什么不能写死 IP {#why-dns}

用 IP 直连当然也能跑，但会立刻遇到一组问题：

| 用 IP 的困境 | DNS 怎么解决 |
|---|---|
| 换机房、换机器要改所有客户端配置 | 客户端只认域名，服务端改解析即可 |
| 一台机器扛不住，要分发到多台 | 一个域名解析出**多个 A 记录**，客户端轮询/由调度决定 |
| 想按地域分配不同后端 | 按解析来源返回不同结果（智能解析） |
| 想上 HTTPS，但证书绑域名 | 证书校验的是域名，用 IP 直连证书就对不上 |
| 想换 CDN 厂商 | 改 CNAME 即可，不用改任何代码 |

**一句话**：**DNS 是"可变更的间接层"**。它的全部价值在于——把"用户怎么找到你"和"你实际部署在哪"解耦开。

## 二、解析链路 {#resolution}

### 2.1 两种角色：递归 vs 迭代

这一对概念必须分清，否则排障时不知道该问谁。

| | 递归查询 | 迭代查询 |
|---|---|---|
| 谁做 | 客户端 → **本地递归解析器**（如运营商 DNS、`8.8.8.8`） | 递归解析器 → 各级权威服务器 |
| 承诺 | 解析器**负责给你最终答案**（查不到就报错，不会让你自己去问） | 每级只回答"下一步去问谁"（ referrals ） |
| 结果 | 最终 A 记录或 NXDOMAIN | 一串"往那边问"的指引 |

```text
  客户端               本地递归解析器            根        顶级域(.com)     权威(example.com)
    │                        │                  │            │                │
    │ ① 递归：example.com 是? │                  │            │                │
    │ ──────────────────────▶│                  │            │                │
    │                        │ ② 迭代：. 是几号? │            │                │
    │                        │ ────────────────▶│            │                │
    │                        │ ◀──────────────── │ 去问 .com   │                │
    │                        │ ③ 迭代：.com 是几号?             │                │
    │                        │ ──────────────────────────────▶│                │
    │                        │ ◀────────────────────────────── │ 去问 ns1...    │
    │                        │ ④ 迭代：example.com 的 A 是?                     │
    │                        │ ───────────────────────────────────────────────▶│
    │                        │ ◀─────────────────────────────────────────────── │ 1.2.3.4
    │ ◀──────────────────────│ ⑤ 返回答案，并按 TTL 缓存起来
    │ 1.2.3.4                │
```

**三个实用推论**：

1. **"第一次解析慢、之后快"** 是正常的——本地解析器缓存没有，要走完整的迭代链路（可能几百毫秒）。
2. **排障要用 `dig` 看权威结果，而不是 `nslookup` 看本地缓存**。`nslookup` 默认走本地配置的解析器、拿到的可能是缓存；`dig @8.8.8.8` 或 `dig +trace` 才能看到真实链路。
3. **根服务器只有 13 个逻辑地址**（a~m.root-servers.net），但通过 **Anycast** 在全球部署了远超 13 台的物理实例。**"13 台机器扛全球 DNS"是个常见误解。**

### 2.2 传输层细节

| 场景 | 用什么 | 说明 |
|---|---|---|
| 普通查询 | **UDP 53** | 快、无连接；响应超过 512 字节时会置 TC 标志要求改走 TCP |
| 大响应 / 区域传送 | **TCP 53** | 保证完整性 |
| 加密查询 | **DoT（853）/ DoH（443）** | 防窥探与篡改；DoH 混在 HTTPS 流量里更难被拦 |

**为什么 DNS 容易被劫持**：UDP 无连接、明文，且**没有身份校验**——中间设备可以抢先回一个假响应（因为先到的响应被采信）。这不是"配置问题"，是协议设计的历史遗留。**DoH/DoT 是当前的主要缓解手段。**

### 2.3 TTL：切换成本的度量

**TTL 是 DNS 里最重要的一个旋钮**，它直接决定"改一条解析，多久能全网生效"：

| TTL 设置 | 优点 | 代价 |
|---|---|---|
| 很长（如 24h） | 解析快、解析器压力小、抗故障强 | **切换极慢**——想换 IP 要等一天 |
| 很短（如 60s） | 切换快、灰度灵活 | 解析次数暴涨、解析延迟概率变高、故障时无缓存兜底 |

**工程上的标准做法是"两段式"**：

```text
  计划内的切换（如机房迁移）：
    步骤1：提前 TTL 降到 60s，等一个"旧 TTL 周期"过去（让旧的长缓存都过期）
    步骤2：改解析指向新机房
    步骤3：观察稳定后，把 TTL 调回长值

  计划外的故障切换：TTL 长就只能等——这就是"为什么关键域名 TTL 不能太长"
```

> **落点**：如果你的域名 TTL 是 24 小时，那么"紧急切流"这个能力实际上是**不存在的**。这不是运维不行，是提前没设计。

## 三、记录类型 {#record-types}

| 类型 | 作用 | 容易踩的坑 |
|---|---|---|
| **A** | 域名 → IPv4 | 一个域名可以配多条，形成"多 IP 轮询" |
| **AAAA** | 域名 → IPv6 | 客户端会**优先尝试 AAAA**；IPv6 通路有问题时会表现为"偶发连接慢" |
| **CNAME** | 域名 → 另一个域名（别名） | **不能与其它记录共存**（同名的 CNAME 和 MX 会冲突）；**根域名通常不能设 CNAME**（要用 ANAME/ALIAS 之类的厂商扩展） |
| **NS** | 该域名由哪些权威服务器负责 | 改 NS 是"换 DNS 服务商"，生效最慢（受父域 TTL 影响） |
| **MX** | 邮件服务器 | 需配优先级；配错的表现是"收不到邮件"而不是"域名不通" |
| **TXT** | 任意文本 | 常用于**域名所有权验证**（SPF/DKIM、证书签发验证） |
| **SOA** | 区域起始授权信息 | 含**该区域的默认 TTL**，是很多"为什么 TTL 不是我设的值"的答案 |

**CNAME 的两个实用场景**：

1. **接 CDN**：把 `static.example.com` CNAME 到 CDN 厂商给的域名，之后调度与扩容都由 CDN 侧负责——**你不需要再动自己的解析**。这是"换 CDN 只改一条 CNAME"的原因。
2. **多环境隔离**：`test.example.com` CNAME 到测试集群入口，发布时不互相干扰。

**AAAA 的一个真实坑**：终端和网络"有 IPv6 地址但走不通"的情况并不少见（路由器宣告了前缀但上游没通）。因为系统**优先尝试 AAAA**，表现就是**首连慢、之后正常**（失败后回落 IPv4）。**这也是排查"偶发首包慢"时要看的一条。**

## 四、CDN 调度与回源 {#cdn}

### 4.1 基本模型

```text
   用户 ──① 解析域名──▶ DNS / CDN 调度系统
                          │
                          │ ② 按用户位置、运营商、健康度
                          ▼   返回「就近边缘节点」的 IP
   用户 ──③ 请求──▶ 边缘节点 ──④ 命中缓存？──▶ 命中则直接返回
                        │
                        │ 未命中（回源）
                        ▼
                    源站 / 中间层节点
```

**CDN 的本质是"用缓存换距离"**：把内容复制到离用户最近的地方，让用户不用跨越半个国家去取。**它不提升源站的能力，只是把大部分请求挡在离用户更近的地方。**

| 核心指标 | 含义 | 不达标时的现象 |
|---|---|---|
| **缓存命中率** | 边缘直接返回的比例 | 命中率低 → 大量回源 → 源站压力大、用户变慢 |
| **回源率** | 需要回源的比例 | 回源率高时，性能收益几乎消失 |
| **回源带宽** | 边缘到源站的流量 | 直接决定成本 |
| **首字节时间（TTFB）** | 边缘开始返回的延迟 | 高 → 调度偏了（调到了远节点） |

### 4.2 两种调度机制

| | **DNS 调度** | **Anycast（BGP 调度）** |
|---|---|---|
| 做法 | 权威 DNS 按请求来源返回不同 IP | 多个机房**宣告同一个 IP**，由 BGP 选最近路径 |
| 判断依据 | **本地递归解析器的出口 IP** | 真实网络路由 |
| 精度 | **天然不精确**——它看到的是解析器的位置，不是用户的位置 | 精度高，按路由收敛 |
| 切换 | 受 TTL 约束（秒~分钟级） | **路由收敛，通常更快**，但对已建连接无效 |
| 主要问题 | 用户用了公共 DNS（如 8.8.8.8）时，解析器出口 IP 可能离用户很远 → **调度到错误节点** | 故障时路由可能"甩远"；对 UDP 之外的状态无感 |

**DNS 调度的偏差怎么缓解**：**EDNS Client Subnet（ECS）**——解析器在查询里**带上用户的网段前缀**，权威侧据此做更精确的判断。**代价是暴露了用户的部分网络位置**，所以有些公共 DNS 出于隐私考虑默认不传，这直接导致 CDN 调度不准。

> **落点**：用户抱怨"我在深圳，怎么感觉走的北方节点"——先看他的 DNS 出口在哪。**这类问题通常不在 CDN 厂商，而在用户的 DNS 设置。**

### 4.3 回源与缓存治理

| 操作 | 作用 | 注意 |
|---|---|---|
| **预热** | 提前把热点内容推到边缘 | 大促/发布会前必做，避免第一波用户全部回源 |
| **刷新（purge）** | 主动让边缘缓存失效 | 发布后"改了没生效"的常规解法；但刷新有配额与生效延迟 |
| **版本化文件名** | 用内容哈希做文件名 | **比刷新可靠得多**——完全不依赖 CDN 的一致性与配额 |
| **分层回源** | 边缘 → 中间层 → 源站 | 减少源站压力；代价是首访延迟略高 |
| **动态加速** | 对不可缓存请求优化回源链路（协议优化、多路复用、就近接入回源） | 收益来自"回源路径优化"，不是缓存 |

**"要不要 purge"的答案通常是"尽量不用"**：只要文件名带内容哈希，就永远不需要刷新——**能把一致性问题从"运维操作"降级成"前端构建规则"，这是更划算的做法。**

## 五、对比辨析 {#compare}

| 对照 | A | B | 关键区别 |
|---|---|---|---|
| 查询角色 | 递归 | 迭代 | 前者对你的客户端负责并给最终答案；后者只指引"下一位问谁" |
| 调度机制 | DNS 调度 | Anycast | 前者看**解析器出口 IP**（不精确）；后者看**真实路由** |
| 记录 | A | CNAME | 前者直接给 IP；后者给别名，**不能与其它记录共存** |
| 记录 | CNAME | NS | 前者是"这个域名的别名"；后者是"谁负责这个域"，改 NS＝换 DNS 服务商 |
| 缓存失效 | 刷新（purge） | 版本化文件名 | 前者依赖 CDN 一致性与配额；后者是构建规则，**推荐** |
| 加密查询 | DoT | DoH | 前者独立端口 853、易被识别与封禁；后者走 443、混在 HTTPS 里 |

### 6.2 高频问答

| 问题 | 答案要点 |
|---|---|
| DNS 是"查询"还是"缓存"？ | **本质是分布式缓存**。这也解释了 TTL、解析延迟、"改了没生效" |
| 递归和迭代有什么区别？ | 递归是"解析器替你查到底并负责结果"；迭代是"解析器逐级去问，每级只说下一位是谁" |
| 根服务器真的只有 13 台吗？ | 只有 13 个**逻辑地址**，但通过 Anycast 在全球部署了远超 13 个物理实例 |
| DNS 一般用 UDP 还是 TCP？ | 默认 **UDP 53**；响应超 512 字节或区域传送走 **TCP**；加密走 DoT(853)/DoH(443) |
| DNS 为什么容易被劫持？ | UDP 明文且**无身份校验**，先到的响应被采信 → 中间设备可抢答。缓解手段是 DoH/DoT |
| TTL 该怎么设？ | 常规划长（省解析、抗抖动），**计划内切换前临时降到 60s** 并等一个旧周期过去。TTL 长＝紧急切流能力不存在 |
| 为什么 CNAME 不能和别的记录共存？ | 别名语义上"整个域名的信息都在对面"，与自有的 MX/A 记录会冲突；**根域通常也不能直接设 CNAME** |
| 配了 AAAA 反而变慢？ | 系统优先尝试 IPv6；若 IPv6 通路实际不通，会先失败再回落 IPv4 → **首连慢、之后正常** |
| CDN 调度准不准？ | **DNS 调度天然不精确**：它看到的是本地 DNS 出口 IP 而非用户 IP；靠 **EDNS Client Subnet** 缓解，但公共 DNS 可能不传 |
| DNS 调度和 Anycast 怎么选？ | 要精确就近、能容忍路由收敛 → Anycast；要按业务策略灵活分流（灰度、按运营商）→ DNS 调度；**实务上常组合使用** |
| 发布后怎么让静态资源必定更新？ | **文件名带内容哈希**，而不是靠 purge。把一致性问题降级成构建规则 |
| 缓存命中率低怎么查？ | 看是否 URL 带随机参数（`?t=时间戳` 会击穿缓存）、`Cache-Control` 是否被源站设成不缓存、回源路径是否绕过边缘 |
| 换 CDN 厂商要改什么？ | 改一条 **CNAME** 即可，源站与业务代码都不用动——这是"用别名解耦"的价值 |
