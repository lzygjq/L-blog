# 分层与封装

> 上一篇：[计算机网络 · 导览](/fundamentals/network/)　|　下一篇：[TCP 核心机制](/fundamentals/network/tcp)

网络这门课最容易学成一堆散装名词：MAC 地址、IP、端口、TCP、HTTP……每个都认识，但说不清它们**分别在哪一层、谁处理谁**。这篇的目标就是先把那张"空间图"建起来——即数据在网络里长什么样、一路上被谁加头、被谁剥头。

**先把这篇的结论放前面**：

1. 分层是为了**隔离变化**——换 WiFi 不用改 HTTP，换 IPv6 不用改 TCP。
2. 每一层只为上一层提供服务，**不关心上一层在干什么**（TCP 不知道你传的是 HTTP）。
3. 数据在发送方**逐层加头**、在接收方**逐层剥头**（封装与解封装）。
4. **MTU 1500 是所有传输层设计的隐含前提**——TCP 分段、UDP 建议包长、HTTP/2 分帧，全都围着它转。

## 一、问题场景：不分层会怎样 {#why-layers}

分层不是学术洁癖，是为了解决一类具体的问题。假设把网络功能写成一整块：

| 不分层的后果 | 分层怎么解决 |
|---|---|
| 换物理介质（网线 → WiFi）要重写业务代码 | 链路层以下换了，上面的 IP/TCP/HTTP 原样不动 |
| 想在 TCP 上叠加加密（HTTPS），得改所有程序 | 加密作为独立一层（TLS）插进来，应用层几乎无感 |
| 一家厂商的"网络模块"无法和别家的互通 | 每层定义**公开接口**，只要接口一致，实现可以任意替换 |
| 排查问题时无从下手——只知道"不通" | 逐层验证：链路通不通 → IP 通不通 → 端口通不通 → 应用对不对 |

**一句话**：分层把"一个巨大的耦合系统"切成了"若干可独立替换、可独立验证的层"。这是网络能长成今天这个规模的根本原因。

## 二、四层与七层 {#four-vs-seven}

OSI 七层是**教学与描述**用的模型，TCP/IP 四层是**实际运行**的模型。两者的对应关系：

| TCP/IP 四层 | OSI 七层 | 核心职责 | 典型协议 | 标识符 |
|---|---|---|---|---|
| 应用层 | 应用层 | 业务语义 | HTTP、DNS、SSH、MQTT | 域名 / URL |
| 　 | 表示层 | 数据格式、加解密、压缩 | （现实中并入应用层） | —— |
| 　 | 会话层 | 会话建立与保持 | （现实中并入应用层） | —— |
| 传输层 | 传输层 | 端到端（**进程到进程**） | TCP、UDP、QUIC | **端口** |
| 网络层 | 网络层 | 主机到主机（**跨网络寻址转发**） | IP、ICMP、ARP | **IP 地址** |
| 网络接口层 | 数据链路层 | 同一链路内传帧 | 以太网、Wi-Fi、PPP | **MAC 地址** |
| 　 | 物理层 | 电信号 / 光信号 | 双绞线、光纤 | —— |

**为什么 OSI 没赢**（这是面试常问的"软题"，答好能显出判断力）：

1. **实现先于标准**。TCP/IP 随 BSD 免费分发、已被真正跑起来，OSI 是设计委员会先出标准再等实现。
2. **过度设计**。会话层、表示层在现实中很难划清——"加密算表示层还是应用层？"这种问题说明切分本身不自然。
3. **商业推动错位**。OSI 带有电信与政府强制的色彩，产业链没动力替换已经能用的 TCP/IP。

**一条实用判断**：面试里说"OSI 七层"没人会挑错，但你要能指出**真正工作的是 TCP/IP 四层，OSI 只是描述语言**。这个区别在排障时很实际——你手上的工具是按四层切的。

## 三、封装与解封装 {#encapsulation}

发送方在每一层给数据**加自己的头部**，叫封装；接收方反过来逐层**剥掉头部**，叫解封装。

```text
      发送方                                            接收方
  ┌──────────────┐                              ┌──────────────┐
  │   应用层      │  HTTP 报文                    │   应用层      │
  │              │  ┌───────────┬────────┐       │  （拿到完整    │
  └──────┬───────┘  │ HTTP 头部 │  体    │       │   HTTP 报文） │
         │ 加 TCP 头└───────────┴────────┘       └──────▲───────┘
         ▼                                             │ 剥 TCP 头
  ┌──────────────┐                                     │
  │   传输层      │  ┌────────┬───────────┬────────┐    │
  │              │  │TCP 头部│ HTTP 头部 │  体    │    │
  └──────┬───────┘  └────────┴───────────┴────────┘    │
         │ 加 IP 头                                    │
         ▼                                             │
  ┌──────────────┐                                     │
  │   网络层      │  ┌────────┬────────┬───────────┐   │
  │              │  │IP 头部 │TCP 头部│ HTTP 部分 │   │
  └──────┬───────┘  └────────┴────────┴───────────┘   │
         │ 加帧头（源/目的 MAC）                         │
         ▼                                             │
  ┌──────────────┐                                     │
  │  网络接口层   │  ┌───────┬────────┬────────┬─────┐ │
  │              │  │帧头+MAC│IP 头部 │TCP 头部│ ... │ │
  └──────┬───────┘  └───────┴────────┴────────┴─────┘ │
         │                                             │
         └──────────────▶ 物理介质 ───────────────────┘
```

**三个必须记住的点**：

1. **每一层只碰自己那一段头部**。网络层的路由器只读 IP 头（源/目的 IP、TTL），**不会去解析 TCP 头和 HTTP 体**。这就是为什么 HTTPS 能对抗中间人——中间设备能看 IP 和端口，看不到内容。
2. **封装是有开销的**。TCP 头 20 字节 + IP 头 20 字节 = 每包固定 40 字节开销。发 100 字节的 payload，实际要传 140 字节，**有效载荷率只有 71%**。这是"小包频繁发"比"攒批发送"低效的根本原因（后面讲 Nagle 算法会回到这一点）。
3. **地址在不同层是不一样的**。应用层认域名、传输层认端口、网络层认 IP、链路层认 MAC。**"一次请求"在每层看到的目标地址都不同**——这正是排障时"要分层看"的物理依据。

## 四、MTU、MSS 与分片 {#mtu-mss}

这一节是全篇最能"解释现象"的部分。

### 4.1 三个尺寸的关系

| 名词 | 属于哪层 | 含义 | 以太网典型值 |
|---|---|---|---|
| **MTU** | 链路层 | 一次能承载的**载荷上限**（不含帧头） | **1500 字节** |
| **IP 包** | 网络层 | IP 头 + 载荷；载荷就是 TCP 段 | 最大 1500 |
| **MSS** | 传输层 | TCP 段的**数据部分**上限 = MTU − IP 头 − TCP 头 | 1500 − 20 − 20 = **1460** |

**MSS 的取值不是随便定的**：TCP 在握手时会**在 SYN 里带上自己愿意接收的 MSS**，双方取较小值。目的非常明确——**让 TCP 按 MSS 切分数据，从根源上避免 IP 层分片**。

### 4.2 TCP 分段 vs IP 分片

两者都能把大块数据变小，但代价完全不同：

| | TCP 分段（segmentation） | IP 分片（fragmentation） |
|---|---|---|
| 谁发起 | TCP 自己主动按 MSS 切 | 路由器发现包超过下一跳 MTU 时被动切 |
| 在哪一层 | 传输层 | 网络层 |
| 接收端 | 每段独立确认、独立重传 | 必须**全部片到齐**才能重组 |
| 丢包代价 | 只重传丢失的那一段 | **丢任意一片，整个原始包全部重传** |
| 中间设备 | 无感 | 每跳可能再分片，效率与风险都高 |
| 现状 | 正常路径 | **应尽量避免**；IPv6 直接取消了中间路由器分片能力 |

**所以"避免 IP 分片"是网络设计的硬约束**：分片不仅让丢包代价放大，还容易被防火墙/负载均衡丢弃（很多设备不处理分片包）。

### 4.3 PMTUD 与"ICMP 黑洞"

链路 MTU 不一定都是 1500——隧道（VPN、VXLAN、IPsec）会在原有头部之外再包一层，导致**有效 MTU 变小**（比如 VXLAN 之后只剩 1450）。这时如果发送方仍按 1500 发且设置了"不许分片"标志（DF），路由器会丢掉包。

**正确做法**是路径 MTU 发现（PMTUD）：路由器回一个 ICMP "需要分片但设置了 DF" 的差错报文，发送方据此调小。**但现实中最常见的故障是**：运维出于安全把 ICMP 全禁了，于是发送方永远收不到通知，**大包静默丢失、小包正常**——表现就是「能 ping 通、能打开首页，一提交大表单就卡死」。这个现象叫 **PMTUD 黑洞**。

> **落点**：云上做 VXLAN / IPsec 网络时，如果发现"小请求正常、大请求超时"，第一个要查的就是路径 MTU，而不是先怀疑业务代码。

### 4.4 带宽时延积：为什么跨机房单连接跑不满带宽

```
  带宽时延积 BDP = 带宽 × 往返时延 RTT
  例：100 Mbps × 50 ms = 5 Mbit ≈ 625 KB
```

意思是：**为了让链路"一直有数据在飞"，发送方必须有至少 625 KB 的数据在途**。TCP 能有多少数据在途，取决于**发送窗口**。窗口不够，链路就会周期性空转——带宽再大也跑不满。

这也是"长肥管道"（Long Fat Network，高带宽 + 高时延）需要**窗口缩放选项**（TCP Window Scale，因为原始窗口字段只有 16 位，最大 64 KB）的原因。

> **落点**：跨地域数据同步、大文件下载慢，别只看带宽——看 RTT 和窗口。把几百 KB 的窗口放在 2% 丢包的链路上，吞吐会被拥塞控制压得远低于理论值。

## 五、IP 与子网 {#ip-subnet}

### 5.1 IPv4 地址与私有段

IPv4 是 32 位地址，写成点分十进制。其中三段被划为**私有地址**，只能在内部网络使用，出公网要经过 NAT 转换：

| 私有段 | CIDR | 地址数量 | 常见用途 |
|---|---|---|---|
| 10.0.0.0 – 10.255.255.255 | `10.0.0.0/8` | 约 1677 万 | 大型企业内网、云上 VPC |
| 172.16.0.0 – 172.31.255.255 | `172.16.0.0/12` | 约 104 万 | 中型内网、Docker 默认网段 |
| 192.168.0.0 – 192.168.255.255 | `192.168.0.0/16` | 约 6.5 万 | 家庭、小型办公 |

**这段要建立的关键直觉**：私有地址不唯一（你家的 `192.168.1.2` 和别人的一模一样），所以**跨公网通信必须经过 NAT**。NAT 的存在也意味着"从外部主动连内部机器"天然不可行——这是内网穿透、端口映射这些需求的来源。

### 5.2 子网掩码在算什么

子网掩码的唯一作用：**判断目标 IP 和我在不在同一个网段**。判断法是按位与：

```
  我的地址   192.168.1.10    11000000.10101000.00000001.00001010
  掩码       255.255.255.0   11111111.11111111.11111111.00000000
  按位与 →   192.168.1.0     ← 我的网段

  目标地址   192.168.1.20    按位与掩码 → 192.168.1.0   ✅ 同网段
  目标地址   10.0.0.5        按位与掩码 → 10.0.0.0      ❌ 不同网段
```

- **同网段** → 直接在链路层用 **ARP** 问对方 MAC，直接发帧。
- **不同网段** → 发给**默认网关**（网关本身就是"通往其它网段的出口"），由它去转发。

**这解释了 `route` / `ip route` 输出里的默认路由 `0.0.0.0/0`**：它是"其它所有情况都交给网关"的兜底规则。网关配错，症状会是"内网能通、公网不通"——正好对应"同网段/不同网段"这条分界线。

### 5.3 CIDR 与可用地址数

`/24` 表示前 24 位是网络号。**记住"每减 1 位，地址翻倍"**：

| CIDR | 掩码 | 总地址 | 通常可用 |
|---|---|---|---|
| `/24` | 255.255.255.0 | 256 | 254（去掉网络号与广播地址） |
| `/16` | 255.255.0.0 | 65,536 | 65,534 |
| `/30` | 255.255.255.252 | 4 | 2（点对点链路常用） |

**云上划子网的实用口径**：K8s 集群、Pod 网段、Service 网段的规划都依赖这套算法。**子网划小了后期扩容非常痛苦**——因为已分配出去的 IP 收不回来，只能重建节点池。

## 六、ARP 与 ICMP {#arp-icmp}

这两个协议都属于"辅助层"，但它们解释了日常排障里最常见的两种现象。

### 6.1 ARP：IP → MAC

IP 是逻辑地址，真正在以太网里发帧靠的是 MAC 地址。ARP 就是那张翻译表：

```text
  ① 主机要发数据给 192.168.1.20，但不知道它的 MAC
  ② 广播 ARP 请求：「谁是 192.168.1.20？请告诉我你的 MAC」
  ③ 目标主机单播回应：「我是，我的 MAC 是 xx:xx:...」
  ④ 双方都把结果写进 ARP 缓存（有老化时间）
```

**三个现象级落点**：

- **ARP 缓存会老化**，所以"偶尔第一包慢"是正常的。
- **ARP 只在同一广播域内有效**——跨网段必须先经过网关的 ARP，这也是为什么网关挂了表现为"跨网段全不通、同网段正常"。
- **免费 ARP（Gratuitous ARP）** 用于宣告"这个 IP 现在归我了"。主从切换、VIP 漂移时靠它让全网刷新缓存。**切换不够快，往往是免费 ARP 发得不够或交换机有安全策略拦截。**

> 补充一句严谨性说明：ARP 到底算网络层还是链路层**存在争议**，因为它跨了两层的职责（用 IP 寻址、工作在链路层）。很多教材把它放在网络层，也有放在链路层的——面试时说明"它是个跨层协议"比硬选一边更稳。

### 6.2 ICMP：网络的差错与控制报文

ICMP 不传业务数据，只传"网络自己的状态"。两个最常用的工具都基于它：

| 工具 | 原理 | 能证明什么 |
|---|---|---|
| `ping` | 发 ICMP Echo Request，等 Echo Reply | **网络层可达性**：目标 IP 能被路由到并愿意回包 |
| `traceroute` | 依次发 TTL = 1,2,3… 的包，靠中途路由器回"TTL 超时"来逐跳暴露路径 | **路径**：数据实际经过哪些跳、哪一跳开始断裂或延迟陡增 |

**一个必须记住的边界**：`ping` 通**不代表服务可用**。ping 只验证到网络层，服务的可用性在传输层之上：

| 现象 | 说明 |
|---|---|
| ping 通，端口不通 | 网络层 OK；问题在传输层以后——服务没监听 / 被防火墙拦 / 绑错网卡 |
| ping 不通，端口通 | 少见但存在：ICMP 被安全策略禁了，业务端口是放行的。**这也是"禁 ICMP"最坑的地方** |
| 两者都不通 | 网络层以下的问题：路由、网关、ACL、安全组 |

## 七、对比辨析 {#compare}

| 对照 | A | B | 关键区别 |
|---|---|---|---|
| 模型 | OSI 七层 | TCP/IP 四层 | 前者是**描述语言**，后者是**实际实现**；排障工具按四层切 |
| 变大块数据的两种方式 | TCP 分段 | IP 分片 | 前者主动、可单独重传；后者被动、丢一片全重传，**应避免** |
| 翻译 | DNS | ARP | 都是"名字 → 地址"，但一个是域名→IP（跨网络）、一个是 IP→MAC（同一链路内） |
| 探测工具 | `ping` | `traceroute` | 前者验证"通不通"（网络层），后者验证"怎么走"（路径） |
| 地址 | 私有地址 | 公网地址 | 前者不唯一、需 NAT；后者唯一、可用于端到端直连 |
| 同网段判定 | 同网段 | 不同网段 | 前者直接 ARP 发帧；后者交给默认网关转发 |

## 八、使用场景与面试问答 {#interview}

### 8.1 按场景跳转

| 场景 | 去哪里 |
|---|---|
| 隧道 / 容器网络下"大包不通" | [PMTUD 与 ICMP 黑洞](#mtu-mss) |
| 跨机房传输慢、带宽跑不满 | [带宽时延积](#mtu-mss) |
| 内网通、公网不通 | [子网与默认网关](#ip-subnet) |
| VIP 切换后部分机器不通 | [免费 ARP](#arp-icmp) |
| 要判断问题在网络层还是应用层 | [ping 通不通能证明什么](#arp-icmp) |

### 8.2 高频问答

| 问题 | 答案要点 |
|---|---|
| 网络为什么要分层？ | 隔离变化（换介质不改上层）、层间接口标准化（多厂商互通）、**可逐层独立验证**（排障的依据） |
| 一次请求从输入网址到页面出现发生了什么？ | DNS → TCP 握手 → TLS 握手 → HTTP 请求 → 逐层封装 → 对端逐层解封装（完整版见[板块导览的旅程图](/fundamentals/#journey)） |
| 一个以太网帧最多能带多少数据？ | MTU 1500；扣掉 IP 头 20 + TCP 头 20，TCP 能带 **1460 字节**。用 UDP 则是 1500 − 20 − 8 = 1472 |
| 为什么尽量不要 IP 分片？ | 任一片丢失就要重传整个原始包；且很多设备直接丢弃分片包，导致静默故障 |
| 为什么 IPv6 取消中间路由器分片？ | 把分片成本推回源端，强制走 PMTUD；同时分片字段的可扩展性差、易被攻击利用 |
| 为什么会有 MTU 黑洞？ | PMTUD 依赖 ICMP 差错报文，而 ICMP 常被安全策略禁掉，发送方收不到"要调小 MTU"的通知 |
| IP 和 MAC 有什么区别？ | IP 是**跨网络的逻辑地址**（可变、可路由），MAC 是**网卡物理地址**（出厂固定、只在同链路有效） |
| 子网掩码的作用是什么？ | 按位与算出网段，判断"直接 ARP 还是交给网关" |
| 为什么私有地址要被 NAT？ | 私有段不唯一，无法直接路由到公网；NAT 在出口处做地址转换，代价是破坏端到端直连 |
| 为什么禁 ICMP 会埋坑？ | `ping` 失效让排障少一层验证手段；更严重的是破坏 PMTUD，引发"大包静默丢失" |
| 同一个交换机下的两台机器通信，要经过网关吗？ | 不要。同网段直接 ARP 拿 MAC 后发帧，网关不参与 |
