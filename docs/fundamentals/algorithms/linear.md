# 线性结构：数组、链表、栈、队列

> 上一篇：[复杂度分析](/fundamentals/algorithms/complexity)　|　下一篇：[树与索引结构](/fundamentals/algorithms/tree)

"线性结构"指的是数据元素之间存在**一对一**前后关系的一类结构。它们是最简单的一类，但**Java 集合框架里 90% 的类都建在这几个底座上**——所以这一篇读透了，[Java 集合](/java/collections/) 那一整块就变成了"查表"。

**先把结论放前面**：

1. **数组快，不只是因为 `O(1)` 寻址，更因为 CPU 缓存局部性**。「数组查询比链表快」这句话，量级差异只在查找特定元素时成立；而"顺序访问快多少倍"，答案是**硬件层面的、可达数倍到数十倍**。
2. **链表在真实硬件上经常比数组慢**，尽管教科书说它增删是 `O(1)`。"均摊复杂度相同、实测差一截"是这一篇最重要的工程结论。
3. **栈和队列不是"两种数据结构"，是"两种访问约束"**。同样一个数组，限制你能从哪一端进出，就变成了栈或队列。
4. **哈希表用「冲突概率」换取 `O(1)`**，它所有的工程细节（容量取 2 的幂、负载因子、树化）都在服务这一件事。

## 一、数组：用连续内存换随机访问 {#array}

数组的定义是：**一段连续的内存空间，存相同类型的数据**。

```java
int[] array = {22, 33, 88, 66, 55, 25};
```

### 寻址公式与「下标从 0 开始」 {#zero-based}

计算机靠**寻址公式**根据下标定位元素：

```text
a[i] = baseAddress + i * dataTypeSize

baseAddress  ：数组首地址
dataTypeSize ：元素类型大小，int 为 4 字节
```

这条公式解释了那个经典问题——**为什么下标从 0 开始**：

| 索引起始 | 寻址公式 | 代价 |
|---|---|---|
| 从 0 开始 | `baseAddress + i * size` | 一次乘加，无额外指令 |
| 从 1 开始 | `baseAddress + (i - 1) * size` | 每次寻址**多一条减法指令** |

不是"能不能"的问题，是**每条访问路径上多一条指令**的取舍。CPU 每秒执行几十亿条寻址，这条减法会被放大到可观的程度——所以 0 胜出。

> **一个常被混淆的点**：`a[i]` 的 `O(1)` 说的是**按已知下标访问**。如果不知道下标、要从头找，那是 `O(n)`；如果数组有序、用二分，那是 `O(log n)`。**"数组查询是 O(1)"这句话必须在"已知下标"的前提下才成立。**

### 真正的优势：缓存局部性 {#cache-locality}

这是我建议你**在面试里主动补上**的一句话——因为大部分人只会说 `O(1)`。

CPU 读内存不是一次读一个字节，而是按 **缓存行（cache line，通常 64 字节）** 整块搬进 L1/L2。一个 `int[]` 里连续 16 个元素正好占满一个缓存行：**访问 `a[0]` 时，`a[1]` 到 `a[15]` 已经被一起搬进缓存了**。

```text
int[] (每个元素 4 字节，缓存行 64 字节)

  内存:  [a0][a1][a2][a3]...[a15] | [a16]...
          └──── 一次缓存行加载 ────┘
  效果:  访问 a0 之后的 15 次访问，全部命中 L1（约 1ns）
```

对比链表：每个结点是**独立分配**的，物理地址可能相隔很远，每次 `next` 都可能是一次缓存未命中（约 100ns，是 L1 命中代价的 100 倍量级）。

**这就是"顺序遍历一个 `int[1000000]` 比遍历 `LinkedList<Integer>` 快一个数量级"的真正原因**——不是算法，是硬件。

### 插入与删除的代价 {#insert-delete}

为了保证内存连续，插入和删除后往往需要**成片挪动元素**：

- 最好：插在末尾 / 删在末尾，`O(1)`；
- 最坏：插在头部 / 删在头部，挪动全部 n 个元素，`O(n)`；
- 平均：`O(n)`。

**动态数组的扩容**是这套逻辑的延伸：容量不够时申请更大空间并把旧数据搬过去。因为采用**倍增策略**，`ArrayList` 尾部插入的**均摊复杂度是 `O(1)`**——推导见 [复杂度分析 · 均摊分析](/fundamentals/algorithms/complexity#amortized)。

## 二、链表：用指针换灵活性 {#linked-list}

链表在物理上**非连续、非顺序**，靠指针把散落的结点串起来。

### 单向链表 {#singly-linked}

每个结点两部分：**数据域** + **指针域**（指向后继的 `next`）。

```java
private static class Node<E> {
    E item;
    Node<E> next;

    Node(E element, Node<E> next) {
        this.item = element;
        this.next = next;
    }
}
```

结点 `B` 的后继是 `C`，记作 `B.next == C`。

**时间复杂度**：只有**头结点**是 `O(1)`；查其他结点要顺着 `next` 走，`O(n)`。增删同理——只有操作头结点 `O(1)`，其他结点得先遍历找到位置，`O(n)`。

### 双向链表 {#doubly-linked}

多一个**前驱指针 `prev`**，支持双向遍历。

```java
private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;

    Node(Node<E> prev, E element, Node<E> next) {
        this.item = element;
        this.next = next;
        this.prev = prev;
    }
}
```

**关键差异**：查头尾 `O(1)`；头尾增删 `O(1)`；而**给定某个结点时增删是 `O(1)`**（不用再遍历找前驱）。

**「给定结点」这四个字是关键**——它意味着只要上层结构额外维护了"指向某结点的引用"（比如哈希表里存了桶的位置），就能把增删降到 `O(1)`。这正是 **`LinkedHashMap` 实现 LRU 的原理**：哈希表负责 `O(1)` 定位，双向链表负责 `O(1)` 调整顺序。

### 单双向对比 {#singly-vs-doubly}

| 维度 | 单向链表 | 双向链表 |
|---|---|---|
| 指针 | 只有 `next` | `next` + `prev` |
| 空间 | 省（少一个指针） | 费（多一个指针） |
| 遍历 | 只能单向 | 支持双向 |
| 查询 | 头 `O(1)`，其他 `O(n)` | 头尾 `O(1)`，其他 `O(n)` |
| 增删 | 头 `O(1)`，其他 `O(n)` | 头尾 `O(1)`，**给定结点 `O(1)`**，其他 `O(n)` |

一句话：**双向链表用「一个指针的空间」换「双向遍历 + 给定结点 O(1) 增删」**——这正是 `LinkedList` 与 `LinkedHashMap` 都选双向链表的原因。

### 链表真的比数组快吗 {#linked-vs-array}

这是本篇最值得记住的一段。教科书的说法是：**数组增删 `O(n)`、链表增删 `O(1)`，所以频繁增删选链表**。但在真实硬件上，这个结论**经常是错的**：

| 场景 | 教科书结论 | 实测倾向 | 原因 |
|---|---|---|---|
| 尾部追加 | 数组 `O(n)`、链表 `O(1)` | **数组更快** | 数组均摊 `O(1)`；链表每次都要分配结点（内存分配器 + GC 压力） |
| 遍历求和 | 都是 `O(n)` | **数组快数倍到数十倍** | 缓存局部性：链表每次 `next` 都可能未命中，且结点还额外消耗内存 |
| 头部插入 | 数组 `O(n)`、链表 `O(1)` | 小数据量**数组更快**，大数据量链表胜出 | 数组搬移是连续内存的 `memmove`，极快；要到几十万元素链表才追上 |
| 中间插入（已知位置） | 链表 `O(1)` | 链表胜出 | 但前提是你**已经有那个结点的引用**——否则查找本身的 `O(n)` 抵消了收益 |

**所以正确的表述是**：

> **链表的价值不在"增删更便宜"这个抽象结论，而在于：当你已经持有目标结点的引用、且需要频繁在任意位置增删时，它能避免数组的搬移代价。** 如果你的访问模式是"遍历 + 尾部追加"，**数组（`ArrayList`）几乎总是更好的选择**——这也是 Java 里 `LinkedList` 实际使用率远低于 `ArrayList` 的原因。

## 三、栈与队列：两种访问约束 {#stack-queue}

栈和队列**不是新的存储结构**，而是**对同一份数据加上"只能从哪端进出"的约束**：

```text
栈（LIFO，后进先出）              队列（FIFO，先进先出）

   push ↓ ┌───┐                    出 ← ┌───┬───┬───┬───┐ ← 入
          │ C │                         └───┴───┴───┴───┘
          ├───┤                      队头                   队尾
   pop  ↑ │ B │
          ├───┤
          │ A │
          └───┘
       只能从同一端进出              两端各管一件事
```

底层实现可以是数组，也可以是链表：

| 实现 | 栈（`push`/`pop`） | 队列（`offer`/`poll`） |
|---|---|---|
| **数组** | 尾部操作，都是 `O(1)`，**缓存友好，首选** | 需要**循环队列**（见下），否则出队要搬移 |
| **链表** | 头部操作，`O(1)` | 头出尾入，`O(1)` |
| Java 实现 | `ArrayDeque`（推荐）、`Stack`（遗留，见下） | `ArrayDeque`、`LinkedList`、`LinkedBlockingQueue` |

> **`java.util.Stack` 已经被 `ArrayDeque` 取代**。原因：`Stack` 继承 `Vector`，**所有方法都是 `synchronized`**——单线程场景白白付锁开销，而且它暴露了 `get(i)` 这类破坏栈语义的方法。**新代码应该用 `ArrayDeque`。**

### 循环队列与环形缓冲区 {#circular-buffer}

用数组实现队列时，如果每次出队都搬移元素，就退化成了 `O(n)`。标准解法是**循环队列**：把数组首尾相接，用两个指针表示队头和队尾，**出队时只移动指针，不搬数据**。

```text
容量 8 的环形缓冲区（capacity = 8，用掩码 & 7 代替取模）

   ┌────┬────┬────┬────┬────┬────┬────┬────┐
   │    │ D  │ E  │ F  │    │    │    │    │
   └────┴────┴────┴────┴────┴────┴────┴────┘
     ↑              ↑
   head=1         tail=4
   读指针          写指针   （tail 追到 head 即"满"）

   写满后：新数据覆盖最旧数据（或阻塞/丢弃，取决于语义）
```

**环形缓冲区的三个工程要点**：

1. **容量取 2 的幂**，用 `index & (capacity - 1)` 代替 `% capacity`——取模是除法指令，几十个周期；位与只要一个周期。这与 `HashMap` 容量取 2 的幂是同一个理由。
2. **无锁场景下的读写指针要用 `volatile` + 序号（sequence）**，而不是简单地比较 `head == tail`——因为"满"和"空"在只有两个指针时无法区分。**Disruptor 用序号（sequence）解决这个问题**：写指针永远单调递增，`sequence - capacity` 就是最旧的可覆盖位置。
3. **Kafka / Netty / Disruptor / 日志缓冲**都在用它——**它把"队列"变成了一个不分配内存、不产生垃圾的固定结构**，这是高吞吐场景的必要条件（每次 `new Node` 都是一次分配器调用 + 一次 GC 负担）。

### 单调栈与单调队列 {#monotonic-stack}

栈和队列的**高级用法**是"维持单调性"，用来把一类 `O(n²)` 的暴力解法降到 `O(n)`：

| 结构 | 解决的问题 | 典型题目 |
|---|---|---|
| **单调栈**（递减） | 找每个元素**右边第一个更大的元素** | 每日温度、柱状图最大矩形、接雨水 |
| **单调队列**（递减） | 滑动窗口内的**最大值** | 滑动窗口最大值 |

**单调栈的核心直觉**：把"还没找到答案的元素"压在栈里；当新元素比栈顶大时，栈顶元素的答案就找到了——**因为它右边第一个更大的元素就是当前这个**。每个元素**最多进栈一次、出栈一次**，所以是 `O(n)`。

```java
// 每日温度：返回每一天之后第一次升温要等几天
public int[] dailyTemperatures(int[] t) {
    int[] res = new int[t.length];
    Deque<Integer> stack = new ArrayDeque<>();   // 存下标，栈内温度递减
    for (int i = 0; i < t.length; i++) {
        while (!stack.isEmpty() && t[i] > t[stack.peek()]) {
            int prev = stack.pop();               // prev 的答案找到了
            res[prev] = i - prev;
        }
        stack.push(i);
    }
    return res;                                   // 栈里剩下的是"以后再没升过温"的天
}
```

**"每个元素进出各一次"是这类技巧的通用判据**——看到单调栈/队列，先确认这条，就能确认复杂度是 `O(n)`。

### 两个栈实现队列 {#two-stacks}

经典面试题，关键是**摊还分析**：

```text
入队 → 压入 in 栈
出队 → 若 out 栈为空，把 in 栈全部倒进 out 栈；再弹出 out 栈顶

   in:  [1,2,3]        出队时 →      in:  []          out: [3,2,1]
                                                          ↑ 弹出 1（队头）
```

**单次出队最坏 `O(n)`（要倒栈），但均摊 `O(1)`**——每个元素最多被"从 in 搬到 out"一次。这与 `ArrayList` 扩容的均摊分析是同一个套路（见 [均摊分析](/fundamentals/algorithms/complexity#amortized)）。

## 四、哈希表：用概率换 O(1) {#hash-table}

哈希表是"最快"的查找结构，代价是**放弃了顺序**并接受了**冲突**。它的所有设计都在回答一个问题：**冲突了怎么办**。

### 两种冲突解决策略 {#collision}

| 策略 | 做法 | 优点 | 缺点 | 代表 |
|---|---|---|---|---|
| **链地址法**（拉链） | 每个桶挂一个链表，冲突元素串在链表上 | 实现简单；**负载因子可大于 1**；删除简单 | 链表有指针开销；缓存不友好 | **Java `HashMap`**、Redis 字典 |
| **开放寻址法** | 冲突了就按探测序列找下一个空位（线性/平方/双重散列） | **无指针开销、缓存友好**、内存紧凑 | 删除麻烦（要用墓碑标记）；负载因子必须 < 1 | Python `dict`、Go `map`、Java `ThreadLocalMap`（线性探测） |

**开放寻址法为什么在工程上更受欢迎**：它把数据都存在**同一个数组**里，没有指针跳转——**这是缓存局部性再次胜出**（同 [数组的缓存优势](#cache-locality)）。代价是删除时必须用"墓碑"标记，否则会截断后续探测链。

### 容量为什么取 2 的幂 {#power-of-two}

`HashMap` 的容量永远是 2 的幂，因为它把**取模**换成了**位与**：

```java
// HashMap 内部（java.util.HashMap#getNode）
// 桶下标 = (n - 1) & hash   而不是   hash % n
```

当 `n` 是 2 的幂时，`(n-1) & hash` 与 `hash % n` 结果**完全等价**，但位与只需一个 CPU 周期。这就是 `HashMap` 扩容时**总是翻倍**（而不是 1.5 倍）的原因——**必须保证容量始终是 2 的幂**。

### 负载因子与树化 {#load-factor}

| 参数 | JDK `HashMap` 取值 | 作用 |
|---|---|---|
| **默认负载因子** | `0.75` | 桶使用率超过它就扩容。**空间与时间的折中点**：太低浪费空间，太高冲突变多 |
| **树化阈值** | `TREEIFY_THRESHOLD = 8` | 单个桶的链表长度达到 8 → 转红黑树，查询从 `O(n)` 降到 `O(log n)` |
| **退化阈值** | `UNTREEIFY_THRESHOLD = 6` | 树太小就退回链表，避免频繁在两种结构间抖动 |
| **最小树化容量** | `MIN_TREEIFY_CAPACITY = 64` | 容量小于它时**优先扩容而不是树化**——因为桶少导致的长链，扩容易就能解决 |

**为什么是 8**：在负载因子 0.75 下，桶内元素数服从**泊松分布**，`λ ≈ 0.5`，链表长度达到 8 的概率约 **`6×10⁻⁸`**——正常情况下几乎不会触发。**所以树化的意义不是"经常用"，而是"防止被恶意构造的哈希冲突攻击（哈希碰撞 DoS）退化成 O(n)"**。这是一个防御性设计，不是性能优化。

### 哈希表没有完美答案 {#hash-limits}

哈希表有三个固有限制，遇到时必须换结构：

| 需求 | 哈希表能做到吗 | 该用什么 |
|---|---|---|
| **有序遍历 / 范围查询** | ❌ 顺序是随机的 | **平衡树**（`TreeMap`，见 [树](/fundamentals/algorithms/tree#bst)）、跳表 |
| **按顺序找最接近的键** | ❌ | `TreeMap.ceilingKey` 等 |
| **省内存的存在性判断** | ❌ 存原值太费 | **布隆过滤器 / 位图**（见 [海量数据处理](/fundamentals/algorithms/high-volume#bloom)） |
| **按键顺序做前缀扫描** | ❌ | Trie（见 [树](/fundamentals/algorithms/tree#trie)） |

## 五、字符串 {#string}

字符串是"字符的数组"，但有几个专属的算法与 Java 侧的坑。

### KMP：用「已匹配的前缀」加速 {#kmp}

暴力匹配是 `O(n·m)`（n 主串、m 模式串）。KMP 把主串指针变成**永不回溯**，达到 `O(n + m)`。

核心是 **`next` 数组（前缀函数）**：`next[i]` 表示"模式串前 i 个字符中，最长的、既是前缀又是后缀的长度"。

```text
模式串： a b a b a c
next:    0 0 1 2 3 0
             ↑ ↑ ↑
             匹配失败时，不用回到起点，直接跳到 next 指示的位置

直观理解：「aba」的前缀「a」和后缀「a」相同 → 失配时可以少比几个字符
```

**KMP 的直觉**：失配时，**主串已经匹配过的部分里，藏着模式串的一段前缀**——所以模式串可以整体右滑到那个位置，而不是从头再来。

> **面试注意**：KMP 在工程里**很少真的被使用**（因为需要"预处理 + 单模式匹配"这个组合的场景不多）。真要匹配多用 BM（从后往前比，实际更快）、或者直接上正则/自动机（多模式用 AC 自动机）。**但 KMP 的 `next` 数组思想是必考的**——它和"最长公共前后缀"这个话题一起，是字符串类题目的通用工具。

### Java 侧的三个坑 {#java-string-traps}

| 坑 | 说明 |
|---|---|
| **`String` 不可变** | 每次 `+=` 都新建对象并复制 => 循环拼接是 `O(n²)`。用 `StringBuilder` |
| **`substring` 在 JDK 6 是视图** | 共享底层 `char[]`，`O(1)` 但**小字符串持有大数组造成内存泄漏**；JDK 7 起改为拷贝，`O(k)` |
| **`HashMap` 的 key 必须是不可变对象** | 如果 key 的 `hashCode` 依赖可变字段，改完之后就再也找不到了 |

### 6.2 概念级速查

| 问题 | 一句话答案 | 详见 |
|---|---|---|
| 数组下标为什么从 0 开始？ | 寻址公式 `base + i × size` 无需额外减法指令，**CPU 少一条指令** | [#zero-based](#zero-based) |
| 数组查询一定是 `O(1)` 吗？ | 不是。**必须"已知下标"**；不知下标是 `O(n)`，有序二分是 `O(log n)` | [#array](#array) |
| 「数组查找比链表快」的真正原因？ | 不只是 `O(1)` 寻址，更是**缓存局部性**：一次缓存行加载带进相邻元素 | [#cache-locality](#cache-locality) |
| 数组插入删除的复杂度？ | 要挪动元素保证连续性：最好 `O(1)`、最坏 `O(n)`、平均 `O(n)` | [#insert-delete](#insert-delete) |
| 单双向链表的区别？ | 双向多一个 `prev` 指针，用空间换**双向遍历 + 给定结点 `O(1)` 增删** | [#singly-vs-doubly](#singly-vs-doubly) |
| 频繁增删就该用链表吗？ | **不一定**。若访问模式是"遍历 + 尾部追加"，数组（`ArrayList`）实测更快；链表的价值在**已持有结点引用 + 任意位置增删** | [#linked-vs-array](#linked-vs-array) |
| 栈和队列的本质区别？ | 不是存储结构差异，是**访问约束**：栈 LIFO（同一端进出）、队列 FIFO（两端各管一件事） | [#stack-queue](#stack-queue) |
| 为什么不用 `java.util.Stack`？ | 它继承 `Vector`，**所有方法 `synchronized`**，单线程白白付锁开销；用 `ArrayDeque` | [#stack-queue](#stack-queue) |
| 环形缓冲区为什么容量取 2 的幂？ | 用 `index & (capacity-1)` 代替取模，**位与只要一个周期，除法要几十个** | [#circular-buffer](#circular-buffer) |
| 单调栈为什么是 `O(n)`？ | 每个元素**最多进栈一次、出栈一次**，总操作数是 `2n` | [#monotonic-stack](#monotonic-stack) |
| 两个栈实现队列的复杂度？ | 单次出队最坏 `O(n)`（倒栈），**均摊 `O(1)`**——每个元素最多被搬一次 | [#two-stacks](#two-stacks) |
| 链地址法和开放寻址法怎么选？ | 链地址法负载因子可 > 1、删除简单；开放寻址法**无指针、缓存友好**但删除要用墓碑 | [#collision](#collision) |
| `HashMap` 容量为什么是 2 的幂？ | 把取模换成位与：`(n-1) & hash` 等价于 `hash % n`，但**只要一个 CPU 周期** | [#power-of-two](#power-of-two) |
| 负载因子为什么是 0.75？ | 空间与时间的折中点；配合泊松分布，链表长度达 8 的概率约 `6×10⁻⁸` | [#load-factor](#load-factor) |
| 树化阈值 8 是性能优化吗？ | **主要是防御性设计**——防止被构造的哈希冲突攻击（哈希碰撞 DoS）退化成 `O(n)` | [#load-factor](#load-factor) |
| 哈希表不能做什么？ | **有序遍历、范围查询、前缀扫描**；这些要用平衡树、跳表或 Trie | [#hash-limits](#hash-limits) |
| KMP 的核心是什么？ | `next` 数组（最长公共前后缀），让主串指针**永不回溯**，从 `O(n·m)` 降到 `O(n+m)` | [#kmp](#kmp) |

### 6.3 一句话总结

> **线性结构这一篇真正要你带走的，不是四个数据结构的操作复杂度表，而是两句话：**
> **① 数组的优势有一半来自硬件（缓存局部性），教科书上的抽象复杂度会低估它。**
> **② 栈和队列不是新结构，是约束——理解了这一点，`ArrayDeque`、`LinkedHashMap`、环形缓冲区这些看起来无关的类就有了共同的解释。**
