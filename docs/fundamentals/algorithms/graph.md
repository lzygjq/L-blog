# 图

> 上一篇：[树与索引结构](/fundamentals/algorithms/tree)　|　下一篇：[排序](/fundamentals/algorithms/sorting)

树是"没有环的图"。把环和方向加回来，就得到了**能描述依赖、路径、连通关系的结构**——而依赖和路径，恰恰是后端系统里最常出现的一类问题。

**先把结论放前面**：

1. **图的第一个决策不是算法，是表示法**。邻接矩阵查边 `O(1)` 但占 `O(V²)` 空间；邻接表省空间但查边要遍历。**稀疏图（大部分真实业务图）选邻接表。**
2. **BFS 求无权最短路、DFS 求连通性与拓扑**。这两句话决定了绝大多数题目的第一反应。
3. **拓扑排序的本质是「有向无环图的线性化」**，它的工程用途比面试用途大得多：**依赖解析、构建顺序、启动编排、循环依赖检测**——Spring 启动时就在做这件事。
4. **最短路径只有三个算法值得记**：Dijkstra（非负权、单源）、Bellman-Ford（含负权 / 判负环）、Floyd（多源、小图）。**选型看"有没有负权、是不是单源、图大不大"三个问题。**

## 一、图的表示：第一个决策 {#representation}

| 表示法 | 空间 | 查边 | 遍历邻居 | 适用 |
|---|---|---|---|---|
| **邻接矩阵** | **`O(V²)`** | **`O(1)`** | `O(V)` | **稠密图**、需要频繁判断"两点是否相连" |
| **邻接表** | **`O(V + E)`** | `O(度)` | `O(度)` | **稀疏图（绝大多数真实场景）** |
| 边集数组 | `O(E)` | `O(E)` | 不便 | Kruskal 之类按边处理的算法 |

**为什么"绝大多数真实场景"是稀疏图**：一个社交网络有上亿用户，人均好友几百——如果"有关系"就填 1，邻接矩阵会是个几乎全 0 的巨阵。**用 `O(V²)` 存 `O(V)` 量级的信息，是纯粹的浪费。**

```java
// 邻接表：V 个顶点的邻接表
List<List<Integer>> graph = new ArrayList<>(V);
for (int i = 0; i < V; i++) graph.add(new ArrayList<>());
graph.get(0).add(1);                    // 0 → 1 一条边

// 带权图：用 int[]{to, weight}
List<List<int[]>> weighted = new ArrayList<>(V);

// 邻接矩阵：适合小图或稠密图
int[][] matrix = new int[V][V];         // matrix[u][v] = 权重，0 表示无边（或按需约定）
```

**三个容易踩的坑**：

| 坑 | 说明 |
|---|---|
| **无向图要加两条边** | `add(u, v)` 时同时 `add(v, u)`，否则 BFS 走不过去 |
| **顶点编号可能不是 `0..V-1`** | 真实数据常是字符串 ID（服务名、IP），先做**映射（`HashMap<String, Integer>`）**再建图 |
| **重边与自环** | 业务数据里常见（重复调用、自己调自己），需要按场景去重或保留 |

## 二、BFS 与 DFS：两种遍历思维 {#traversal}

两者的区别**不是"用队列还是用栈"**，而是**探索的顺序**：

| 维度 | **BFS**（广度优先） | **DFS**（深度优先） |
|---|---|---|
| 数据结构 | **队列** | **栈 / 递归** |
| 探索方式 | 一层一层向外扩 | 一条路走到黑再回头 |
| 天然得到 | **无权图的`最短路径`（边数最少）** | 连通分量、拓扑序、环检测 |
| 空间 | `O(宽度)`（最宽那层） | `O(深度)` |
| 适合 | **找最短**、分层扩散 | **找所有解**、判断结构性质 |

```java
// BFS：注意"入队时标记 visited"，不是"出队时标记"
public int shortestPath(List<List<Integer>> g, int start, int target) {
    boolean[] visited = new boolean[g.size()];
    Deque<Integer> queue = new ArrayDeque<>();
    queue.offer(start);
    visited[start] = true;               // ← 关键：入队就标记
    int step = 0;
    while (!queue.isEmpty()) {
        int size = queue.size();          // 分层：一次处理完这一层
        for (int i = 0; i < size; i++) {
            int cur = queue.poll();
            if (cur == target) return step;
            for (int next : g.get(cur)) {
                if (!visited[next]) {
                    visited[next] = true;
                    queue.offer(next);
                }
            }
        }
        step++;
    }
    return -1;
}
```

**那个 `visited` 标记的位置是高频考点**：如果在**出队时**才标记，同一个节点可能被重复入队多次（不同路径都能到达它），队列会膨胀、复杂度劣化。**必须在入队时标记。**

**为什么 BFS 求的是"无权图最短路"**：BFS 按层扩散，第一次到达某节点时经过的边数**必然最少**。**一旦有边权，这个性质就没了**——因为"边数少"不等于"权重和小"，此时必须用 [Dijkstra](#shortest-path)。

**DFS 的两个易错点**：

| 易错点 | 说明 |
|---|---|
| **递归深度** | 链状图（长调用链）有 n 层，递归会 `StackOverflowError`。**真实的生产图动辄几十万节点，必须用显式栈迭代或加深度限制** |
| **环导致死循环** | 无 `visited` 会在环上转不出来；判环需要**三色标记**（见下） |

### 三色标记：用 DFS 判有向图的环 {#cycle-detection}

判断**有向图**是否有环，不能用简单的 `visited`（因为一个节点被访问过 ≠ 有环）。需要三种状态：

| 状态 | 含义 |
|---|---|
| **白**（未访问） | 还没碰到 |
| **灰**（在栈中） | 正在当前 DFS 路径上 |
| **黑**（已完成） | 它的所有后继都处理完了 |

**判环条件：访问到一个「灰色」节点，说明回到了当前路径上的祖先 → 有环。** 访问到黑色节点是无害的（那是另一条已完成的路径）。

这比"用拓扑排序判环"更能直接给出**环的具体位置**，所以在排查"循环依赖"时更实用。

## 三、拓扑排序：有向无环图的线性化 {#topo}

**拓扑排序**：把有向无环图（DAG）的顶点排成一个序列，使**每条边都从前面指向后面**。

两种实现，都要掌握：

### Kahn 算法（BFS 版，入度法） {#kahn}

```text
① 统计每个节点的入度
② 把所有入度为 0 的节点入队
③ 反复：出队一个节点 → 加入结果 → 把它所有邻居的入度减 1
        → 减到 0 的邻居入队
④ 若结果长度 < 节点总数 → 说明有环（剩下的节点互相依赖）
```

**优点**：**天然能判环**（第 ④ 步）、结果直观、可用队列保证同层顺序稳定。**工程实现几乎都用这个版本。**

### DFS 版（后序逆序） {#dfs-topo}

**DFS 的后序遍历结果，逆序就是拓扑序**——直觉是"所有依赖都在我之前完成，所以我最后被输出"。配合 [三色标记](#cycle-detection) 可以在同一趟里判环。

### 工程意义：这是真正天天在用的算法 {#topo-in-production}

拓扑排序在你的日常开发里出现的频率，比它作为面试题出现的频率高得多：

| 场景 | 图是什么 | 拓扑排序在做什么 |
|---|---|---|
| **Maven / Gradle 构建** | 模块依赖图 | 决定**编译顺序**（被依赖的先编译） |
| **容器启动编排** | 服务依赖图 | 决定**启动顺序**（DB 先起、再起应用） |
| **Spring Bean 依赖注入** | Bean 依赖图 | 计算**创建顺序**；**循环依赖时抛 `BeanCurrentlyInCreationException`** |
| **数据库外键 / 数据迁移脚本** | 表依赖图 | 决定建表与删表顺序（删表要反序） |
| **任务调度（Airflow / DolphinScheduler）** | DAG 任务图 | 按依赖触发下游任务 |
| **包管理器（npm / pip）** | 包依赖图 | 安装顺序 |

> **面试延伸点**：被问"Spring 怎么解决循环依赖"时，可以补一句——**三级的 `singletonFactories` 是"打破环"的手段，但 Spring 对构造器注入的循环依赖仍然直接失败**，因为构造器注入时对象还没创建出来，无法提前暴露引用。**能主动区分"setter 循环依赖能解、构造器循环依赖不能解"，是理解深度的分水岭。**

## 四、最短路径：三个算法覆盖所有场景 {#shortest-path}

| 算法 | 解决什么 | 复杂度 | 能处理负权 | 能判负环 |
|---|---|---|---|---|
| **BFS** | **无权图**单源最短路 | `O(V + E)` | — | — |
| **Dijkstra** | **非负权**单源最短路 | 朴素 `O(V²)`；**堆优化 `O((V+E) log V)`** | ❌ **不能** | ❌ |
| **Bellman-Ford** | 单源，**可含负权** | `O(V · E)` | ✅ | ✅ |
| **Floyd-Warshall** | **多源**（求所有点对） | `O(V³)` | ✅ | ✅（对角线为负） |

### Dijkstra：贪心的正确性来自"非负权" {#dijkstra}

**核心思路**：不断从"未确定的节点"里取出**当前距离最小**的那个，用它去松弛邻居。

**为什么要求非负权**：Dijkstra 的正确性建立在"**已确定的节点距离不会再有更短的路径**"这个假设上。**如果存在负权边，一条更长的路径可能因为后期出现负边而变得总权更小**，这个假设就崩塌了——贪心地"确定"下来的距离可能是错的。

**堆优化是标配**：朴素的 `O(V²)` 每次都要线性扫描找最小距离节点。用**优先队列**取最小后是 `O((V+E) log V)`——**对稀疏图（`E ≈ V`）来说，这是从 `O(V²)` 到 `O(V log V)` 的质变**。

> **一个工程细节**：Java 的 `PriorityQueue` **不支持"降低键值"**（没有 `decrease-key`）。标准做法是**"惰性删除"**——松弛时直接 `offer` 一个新条目，取出时检查"这个距离是不是已经过期"，过期就丢弃。**这个技巧叫 `lazy deletion`，是 Java 里实现 Dijkstra 的通行做法。**

**Dijkstra × 现实场景**：地图导航（路网非负）、网络路由（OSPF 用 Dijkstra；**BGP 用路径向量而非最短路径，因为它要按策略而非距离选路**）、游戏寻路（A\* 就是 Dijkstra 加启发式函数）。

### Bellman-Ford：用"迭代 V-1 轮"换负权 {#bellman-ford}

**核心思路**：对所有边做 **`V-1` 轮**松弛。为什么是 `V-1` 轮？因为**最短路径最多包含 `V-1` 条边**——每多一轮就多允许一条边。

**判负环**：如果**第 V 轮仍有边能被松弛**，说明存在从源点可达的负环（因为沿着负环绕圈可以无限变小，最短路径不存在）。

> **注意负环的语义**：有负环不代表"算法错了"，而是**这个问题的答案在数学上不存在**（最短路径是负无穷）。工程上，负权常用来表示"收益"或"补贴"，此时必须显式检查负环，否则会算出无意义的解。

### Floyd：`O(V³)` 换"所有点对" {#floyd}

三段循环，中间点在最外层：

```java
for (int k = 0; k < V; k++)            // 中间点 k 必须在最外层
    for (int i = 0; i < V; i++)
        for (int j = 0; j < V; j++)
            dist[i][j] = Math.min(dist[i][j], dist[i][k] + dist[k][j]);
```

**为什么 `k` 必须在最外层**（这是最经典的错误）：`dist[i][j]` 的语义是"**只允许经过前 k 个节点作为中间点**时的最短距离"。`k` 放在最外层，才能保证"第 k 轮用的是已经考虑过 1..k-1 的结果"。**如果 `k` 放在内层，会得到一个错误答案——而且不会报错，只是结果偏大。**

**`O(V³)` 的现实边界**：`V = 500` 时是 1.25 亿次操作，勉强可接受；`V = 5000` 时是 1250 亿次——**不能用了**。**Floyd 只适合小图（几百个节点）的全点对场景**，比如"计算一个小规模集群内所有实例间的网络延迟矩阵"。

## 五、最小生成树：连接所有点，代价最小 {#mst}

**MST 的语义**：在一个带权连通无向图里，选出一棵包含所有顶点、总权重最小的树（`V-1` 条边）。

| 算法 | 思路 | 复杂度 | 适合 |
|---|---|---|---|
| **Kruskal** | **按边权排序**，从小到大加边，**用并查集判断会不会成环** | `O(E log E)` | **稀疏图** |
| **Prim** | 从任一顶点出发，每次**选连接"已选集合"与"未选集合"的最小边** | `O(E log V)`（堆优化） | **稠密图** |

**Kruskal 依赖并查集**——这是两个知识点的交点，也是面试常见的组合考法：

```java
// Kruskal 骨架
Arrays.sort(edges, Comparator.comparingInt(e -> e.weight));   // ① 按权排序
UnionFind uf = new UnionFind(V);
int total = 0, used = 0;
for (Edge e : edges) {
    if (uf.find(e.u) == uf.find(e.v)) continue;               // ② 已成环，跳过
    uf.union(e.u, e.v);                                       // ③ 合并
    total += e.weight;
    if (++used == V - 1) break;                               // ④ 够了就停
}
```

**并查集在这里的作用是"判环"**：加边的两个端点如果本来就在同一集合里，加这条边就会形成环——**这一步是 `O(α(V))`，几乎免费**（见 [并查集](/fundamentals/algorithms/tree#union-find)）。

> **一个反直觉的点**：**Prim 与 Dijkstra 的代码结构几乎一样**（都是"取最小 + 松弛邻居"），但目标不同：**Dijkstra 最小化"到源点的累计距离"，Prim 最小化"连到生成树的单条边权"**。面试里被要求"手写一个"，写错了这一行的语义就会得到完全不同的结果。

**现实中的 MST**：网络布线（用最少的光缆连通所有机房）、电路板走线、聚类分析（**单链聚类**：不断合并最近的簇，就是 Kruskal 的逆过程）。

## 六、图遍历在工程里的隐蔽身影 {#engineering}

图算法有一批"用了但没被认出来"的应用，认出它们能显著提升解释问题的能力：

| 场景 | 本质是什么图遍历 | 说明 |
|---|---|---|
| **GC 可达性分析** | **从 GC Roots 出发的图遍历** | "标记-清除"的标记阶段就是在做 DFS/BFS；"三色标记法"与[判环的三色](#cycle-detection)同名同源 |
| **死锁检测** | 资源分配图的**环检测** | 银行家算法就是在判断"加这条边会不会成环" |
| **服务调用链追踪** | 有向图路径 | Trace 是一棵 DFS 树；**调用链成环 = 循环依赖**，要在架构上消除 |
| **循环依赖检测** | 有向图环检测 | Spring / Maven / npm 都在做（见 [拓扑排序](#topo-in-production)） |
| **推荐系统（图游走）** | 随机游走 / 邻居扩散 | "你可能认识的人"本质是二跳邻居 |
| **分布式任务编排** | DAG | 越算越流行的"工作流引擎"就是 DAG + 拓扑排序 |

**这一节的价值**：当你能说出"**GC 的标记阶段就是一次图遍历**"，你对 GC 的理解就从"背分代和收集器"进入了"理解它的算法骨架"。

### 7.2 概念级速查

| 问题 | 一句话答案 | 详见 |
|---|---|---|
| 邻接矩阵和邻接表怎么选？ | 矩阵查边 `O(1)` 但占 `O(V²)`；**稀疏图（真实业务图的常态）用邻接表 `O(V+E)`** | [#representation](#representation) |
| BFS 和 DFS 的本质区别？ | 探索顺序不同（层扩 vs 深探），不是"队列 vs 栈"；**BFS 天然给出无权最短路** | [#traversal](#traversal) |
| BFS 的 `visited` 什么时候标记？ | **入队时**（不是出队时），否则同一节点会被重复入队、队列膨胀 | [#traversal](#traversal) |
| 为什么 BFS 能求最短路而加了权就不行？ | BFS 的"第一次到达 = 边数最少"；**有权时"边数少 ≠ 权重和小"** | [#traversal](#traversal) |
| 有向图怎么判环？ | **三色标记**：访问到"灰色"（当前路径上的祖先）即有环；简单 `visited` 不够 | [#cycle-detection](#cycle-detection) |
| 拓扑排序的两种实现？ | **Kahn（BFS 入度法，天然判环，工程常用）**、DFS 后序逆序 | [#kahn](#kahn) |
| 拓扑排序在工程里哪里用？ | **Maven 编译顺序、容器启动编排、Spring Bean 创建顺序、任务调度 DAG** | [#topo-in-production](#topo-in-production) |
| 为什么 Dijkstra 不能有负权？ | 它的正确性依赖"**已确定节点不会再有更短路径**"；负权会推翻这个贪心假设 | [#dijkstra](#dijkstra) |
| Java 里怎么实现 Dijkstra 的堆优化？ | `PriorityQueue` **没有 `decrease-key`**，用**惰性删除**：直接 `offer` 新条目，取出时丢弃过期项 | [#dijkstra](#dijkstra) |
| Bellman-Ford 为什么迭代 `V-1` 轮？ | 最短路径最多含 `V-1` 条边；**第 V 轮还能松弛 = 存在可达负环** | [#bellman-ford](#bellman-ford) |
| Floyd 的 `k` 为什么必须最外层？ | `dist[i][j]` 的语义是"只允许前 k 个节点作中间点"；`k` 在内层会**静默算错**（结果偏大） | [#floyd](#floyd) |
| Kruskal 和 Prim 怎么选？ | **稀疏图 Kruskal（按边排序 + 并查集判环）**，稠密图 Prim（堆优化） | [#mst](#mst) |
| Prim 和 Dijkstra 代码几乎一样，差在哪？ | Dijkstra 最小化**到源点的累计距离**，Prim 最小化**连到树的单条边权** | [#mst](#mst) |
| GC 和死锁检测和图算法什么关系？ | **GC 标记是一次图遍历**；**死锁检测是资源分配图的环检测** | [#engineering](#engineering) |

### 7.3 一句话总结

> **图这一篇的落点不是"会写 BFS"，而是认出问题里的图**：依赖是图、调用链是图、引用关系是图、资源竞争也是图。**认出这是图问题之后，工具箱只有那么几个**——遍历、拓扑、最短路、生成树，选哪个由"有没有权、有没有环、是单源还是多源"决定。
