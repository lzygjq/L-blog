# 排序

> 上一篇：[图](/fundamentals/algorithms/graph)　|　下一篇：[动态规划与算法思想](/fundamentals/algorithms/dp)

排序是最"基础"的算法话题，也是最容易背成一堆表格的话题。这一篇的目标是**把八种排序串成一条推理链**：为什么比较排序有 `O(n log n)` 的下界、为什么快排理论上不如下界漂亮却实际最快、为什么 Java 对基本类型和对象用两套完全不同的算法。

**先把结论放前面**：

1. **比较排序的下界是 `O(n log n)`**，这是数学结论，不是"目前没找到更好的"。想要更快，**必须放弃"比较"这条路**——计数/桶/基数排序就是这么绕过去的。
2. **快排实际最快，不是因为复杂度低（它和归并一样），而是因为缓存友好**。这是硬件再次压过理论（同 [数组的缓存局部性](/fundamentals/algorithms/linear#cache-locality)）。
3. **Java 用两套算法**：基本类型用**双轴快排**（不稳定），对象数组用 **TimSort**（稳定）。**原因不是"哪个更快"，而是"对象数组必须稳定"**。
4. **稳定性只在"多轮排序"和"有相等键"时有意义**。单次排序、键唯一时，稳定性完全不影响正确性。

## 一、两条分界线：下界与稳定性 {#overview}

### 比较排序的下界：为什么是 `O(n log n)` {#lower-bound}

n 个元素共有 **`n!` 种排列**，排序算法要能区分出"哪一种排列才是正确的"。每次比较只产生两个结果（`<` 或 `>`），所以**k 次比较最多区分 `2^k` 种情况**。要让算法能覆盖所有排列：

```text
2^k ≥ n!   →   k ≥ log₂(n!)   →   k ≈ n log n      （斯特林公式）

例：n = 3 → 3! = 6 种排列 → k ≥ log₂6 ≈ 2.58 → 至少 3 次比较
```

**这条下界的关键在"比较"二字**：它假设算法**只能通过比较两个元素来获取信息**。只要跳出这个限制，下界就不成立了。

### 非比较排序：绕过下界的三条路 {#non-comparison}

| 算法 | 原理 | 复杂度 | 限制 |
|---|---|---|---|
| **计数排序** | 统计每个值出现的次数，按值回填 | **`O(n + k)`**（k 为值域） | **只适合值域小的整数**；值域大就退化成 `O(n²)` 级空间 |
| **桶排序** | 分桶 → 桶内排序 → 合并 | 平均 `O(n + n²/k + k)` | 要求数据**分布均匀**；分布不均时退化 |
| **基数排序** | 按位从低位到高位**多轮计数排序** | **`O(d(n + k))`**（d 为位数） | 只适合**可拆成位的**数据（整数、定长字符串） |

**它们的共同点**：**绕过了"比较"**——直接用值本身的信息（下标、位数）决定位置。**代价是适用范围收窄**：计数排序要求整数且值域可控，基数排序要求能按位切分。

**为什么基数排序要从低位开始**：低位排完后再排高位，**高位的优先级更高**（后一轮排序会覆盖前一轮的顺序）——而"后一轮不破坏前一轮的相对顺序"这个要求，**正是稳定性**。**所以基数排序必须是稳定排序。** 这是"稳定性为什么重要"的最硬的理由。

### 稳定性：什么时候真的会出错 {#stability}

**定义**：排序后，**相等元素的相对顺序不变**。

**只有在这两种情况下，稳定性才影响正确性**：

| 场景 | 说明 |
|---|---|
| **多轮排序** | 先按"部门"排、再按"工资"排——**第二轮必须稳定**，才能在同工资的人里保留部门顺序 |
| **基数排序 / 桶内排序** | 上面说的，低位轮次的结果必须被保留 |

**反过来说**：如果只排一次、或者排序键唯一（如 ID），**稳定性对结果没有任何影响**。这就是为什么 "基本类型数组不需要稳定" ——**两个 `int` 值相等时，它俩本来就是不可区分的**，交换它们不产生任何可观察的差异。

> **一句话记住**：**"稳定"的必要条件是"元素可区分"。** 基本类型值相等就完全等价，无稳定可言；对象即使值相等也是不同对象（有身份），稳定才有意义。**这正是 Java 对两者用不同算法的根本原因**——不是"对象排得慢所以要优化"，而是"语义上要求不同"。

## 二、八种排序放在一张表里 {#classic}

| 算法 | 平均 | 最坏 | 空间 | 稳定 | 关键特征 |
|---|---|---|---|---|---|
| **冒泡** | `O(n²)` | `O(n²)` | `O(1)` | ✅ | 相邻交换；**教学用，工程不用** |
| **选择** | `O(n²)` | `O(n²)` | `O(1)` | ❌ | **交换次数最少**（最多 n-1 次）；比较次数固定 |
| **插入** | `O(n²)` | `O(n²)` | `O(1)` | ✅ | **小数组和近乎有序时极快**；所有快排/归并的底层收尾都用它 |
| **希尔** | 取决于增量 | `O(n²)`（最差） | `O(1)` | ❌ | 插入排序的"分组版"；**增量序列决定性能** |
| **归并** | `O(n log n)` | `O(n log n)` | **`O(n)`** | ✅ | **最坏也是 `O(n log n)`**；稳定；适合**链表**和**外部排序** |
| **快速** | `O(n log n)` | **`O(n²)`** | `O(log n)` | ❌ | **实际最快**（缓存友好）；最坏可退化 |
| **堆** | `O(n log n)` | `O(n log n)` | **`O(1)`** | ❌ | **唯一"原地 + `O(n log n)` + 无最坏退化"** |
| **计数 / 基数 / 桶** | `O(n + k)` 等 | — | `O(n + k)` | ✅ | **非比较**，但要满足值域/分布前提 |

**从这张表里读三件事**：

- **插入排序不可替代**：所有工业级排序（TimSort、双轴快排）在小数组阶段都会**退化成插入排序**——因为在 `n < 47` 这个量级，插入排序的常数因子小到无人能敌。
- **归并是唯一"最坏也稳"的通用比较排序**（在 `O(1)` 空间限制之外）：**Java 的 `Collections.sort` 和对象数组排序都选它（TimSort）**，原因之一就是不能容忍 `O(n²)` 的最坏情况出现在基础库上。
- **堆排序的独特性**：它是**唯一同时满足"原地（`O(1)` 额外空间）+ 最坏 `O(n log n)`"的排序**（见 [堆](/fundamentals/algorithms/tree#heap-uses)）。所以它被用作快排的"兜底"——**递归过深时切到堆排序，防止最坏情况**。

## 三、快排：为什么实际最快 {#quicksort}

### 划分是它的全部灵魂 {#partition}

```java
// 单轴快排的核心：分区（这里用最朴素的 Lomuto 写法便于理解）
private int partition(int[] a, int lo, int hi) {
    int pivot = a[hi];                 // 选最后一个做轴
    int i = lo;
    for (int j = lo; j < hi; j++) {
        if (a[j] < pivot) {
            swap(a, i++, j);           // 比 pivot 小的换到左边
        }
    }
    swap(a, i, hi);                    // pivot 归位
    return i;                          // 返回最终位置
}
```

**快排的复杂度完全由"划分是否均衡"决定**：

| 情况 | pivot 位置 | 递归深度 | 复杂度 |
|---|---|---|---|
| 每次都平分 | 中间 | `log n` | **`O(n log n)`** |
| 每次都切在最边上 | 端点 | **`n`** | **`O(n²)`** |

**"切在最边上"不是罕见意外**：如果**固定选端点做 pivot**，那么**输入已经有序时每次都会切在最边上**——这就是"对已排序数组用朴素快排会退化成 `O(n²)`"的原因。

### 四个关键改进 {#quicksort-improvements}

| 改进 | 做法 | 解决的问题 |
|---|---|---|
| **随机化 / 三数取中** | 随机选轴，或取首中尾三个数的中位数 | **避免"有意构造"或"自然有序"导致的固定退化** |
| **三向切分**（荷兰国旗） | 把数组分成 `<pivot`、`=pivot`、`>pivot` 三段 | **大量重复元素**时避免"相等元素反复交换"（这是朴素快排的经典性能坑） |
| **小数组切换插入排序** | `n < 47` 时直接插入排序 | 递归到很小规模时，函数调用开销大于比较本身 |
| **递归过深切换堆排序** | 深度超阈值时改用堆排序 | **把最坏情况从 `O(n²)` 拉回 `O(n log n)`**（这是 JDK 的做法） |

### 快排为什么实际最快 {#why-quicksort-fast}

**它和归并同为 `O(n log n)`，但实测通常快 2~3 倍**。原因全是硬件与工程层面的：

| 原因 | 说明 |
|---|---|
| **原地、顺序访问** | 划分过程是**顺序扫描数组**，缓存命中率高；归并要来回读写两个数组 |
| **无额外分配** | 归并需要 `O(n)` 辅助数组（**大数组上是真的内存分配与 GC 压力**） |
| **常数因子小** | 内层循环只有比较、自增、交换三件事，无额外判断 |
| **平均情况极佳** | 随机输入下划分天然接近均衡，实测比较次数约为理论下界的 `1.39×` |

**归并的反向优势**：它是**稳定**的，而且是**最坏 `O(n log n)`**；更重要的——**它天然适合链表**（不需要随机访问，`O(1)` 空间就能做，只需改指针）和**外部排序**（可以分段排序后多路归并）。**所以"快排 vs 归并"不是谁取代谁，而是场景分工。**

## 四、TimSort：把"真实数据的结构"利用到极致 {#merge-timsort}

`TimSort`（Tim Peters 于 2002 年为 Python 设计，Java 7 起用于对象数组）不是一种新排序，而是**归并排序 + 插入排序的工程集成**，核心是两个洞察：

### 洞察一：真实数据里本来就有序段（run） {#run}

**现实数据很少是随机的**——日志按时间近似有序、交易记录按 ID 近似有序。TimSort 首先**扫描出天然有序的片段（run）**：

```text
输入:  [3, 5, 8, 1, 2, 9, 7, 6, 4]  →  弱递减（8,1）在合并时不需要反转
       └── run1 ──┘ └─run2─┘ └── run3 ──┘
```

- **升序 run**：直接使用；
- **严格降序 run**：**反转后**当作升序用（反正它内部有序，反一下就好）；
- 如果 run **太短**（< `minRun`，约 32~64），用**二分插入排序**把它补长到 `minRun`，然后入栈。

### 洞察二：两个 run 大小悬殊时，用二分代替线性比较（galloping） {#galloping}

归并两个 run 时，如果发现**一方连续"赢"了很多次**（说明它的元素整体更小），就切换到**指数搜索 + 二分查找**（galloping mode），**一次定位一批元素的位置**而不是逐个比较。

**效果**：在"一个 run 整体小于另一个"的情况下，从 `O(n)` 次比较降到 `O(log n)` 次。**这就是 TimSort 对近乎有序数据接近 `O(n)` 的原因。**

### TimSort 的保证 {#timsort-guarantees}

| 性质 | 值 |
|---|---|
| 最好情况 | **`O(n)`**（已经有序，只需一趟 run 扫描） |
| 平均 / 最坏 | `O(n log n)` |
| 空间 | **`O(n)`**（临时数组） |
| 稳定性 | **稳定**（归并的合并顺序保证了相等元素不换位） |

## 五、Java 的 `Arrays.sort` 到底做了什么 {#jdk-impl}

这是这一篇最"工程"的一节，也是面试的高频追问点。

### 两张入口，两套算法 {#two-entries}

```java
int[]   a = ...;  Arrays.sort(a);        // ① 基本类型 → 双轴快排（不稳定）
String[] s = ...; Arrays.sort(s);        // ② 对象数组 → TimSort（稳定）
List<T> list = ...; Collections.sort(list);   // ③ 转数组 → TimSort → 写回
```

| 入口 | 底层算法 | 稳定 | 为什么这样选 |
|---|---|---|---|
| `Arrays.sort(基本类型[])` | **双轴快排**（`DualPivotQuicksort`） | ❌ | 值相等的元素**不可区分**，不需要稳定；换取快排的**原地与缓存优势** |
| `Arrays.sort(对象[])` | **TimSort** | ✅ | **必须稳定**——对象即使字段相等也有身份，顺序变了是可观察的行为差异 |
| `Collections.sort(list)` | `list.toArray()` → TimSort → 写回 | ✅ | 同上；**注意这会产生一次数组拷贝** |

> **一个实践建议**：`Collections.sort(list)` 会拷贝一份数组再写回。如果列表本身是 `ArrayList` 且可改，**用 `list.sort(cmp)` 更直接**（内部同样走 TimSort，但少一层间接）。

### 双轴快排的分支逻辑 {#dual-pivot}

双轴快排的"双轴"指**一次划分用两个 pivot、把数组分三段**（比单轴减少约 10% 的比较次数）。更值得注意的是**它是按数据形态动态选算法的**（常量值以 JDK 源码为准，不同版本会有微调）：

| 输入规模 / 形态 | 实际使用的算法 |
|---|---|
| `n < 47` | **插入排序** |
| `47 ≤ n < 286` | **双轴快排** |
| `n ≥ 286` 且检测到**基本有序** | **归并排序**（`MAX_RUN_COUNT = 67` 判断"是否近似有序"） |
| **递归深度 > 64** | **堆排序**（兜底，防 `O(n²)`） |
| `byte[]` 较长 | **计数排序**（值域只有 256 种） |
| `short[]` / `char[]` 较长（> 3200） | **计数排序**（值域 65536 种） |

**这张表说明了三件事**：

1. **工业级排序不是"一种算法"，而是一个"按输入形态分派的策略树"**——这是"工程实现"与"教科书算法"最大的差别。
2. **`byte`/`short` 有专门的计数排序分支**：因为它们的值域小且有限，**非比较排序的"前提条件"被满足了**（见 [非比较排序](#non-comparison)）。
3. **递归深度超限切堆排序**是"把最坏情况兜住"的经典手法——**基础库不能接受 `O(n²)` 暴露给调用者。**

> **一个正在路上的变化**：JDK 有一个长期在评审中的改动（**JDK-8266431，Dual-Pivot Quicksort improvements**），为基本类型排序引入**基数排序**与 **AVX512 向量化**，官方基准显示 `char` 可快 4~7 倍、`int` 快 1.2~5 倍，并行排序最高可快 9 倍。**截至 2026 年 9 月，该改动仍处于评审阶段、尚未合入主线**——所以现在你用的 JDK 里，`Arrays.sort` 跑的仍是上面那张表里的逻辑。**这种"正在演进中的实现细节"值得知道，但不要当成既成事实来答。**

### `parallelSort` 什么时候值得用 {#parallel-sort}

| | `Arrays.sort` | `Arrays.parallelSort` |
|---|---|---|
| 实现 | 单线程 | **Fork/Join 并行归并** |
| 小数组 | 更快 | **更慢**（线程调度开销 > 排序本身） |
| 大数组（数十万以上，多核空闲） | — | **可能显著更快** |
| 前提 | — | **有可用核心**；如果是已被打满的服务器，**没有收益** |

**判断标准很朴素**：**数组够大（经验值 10 万以上）、机器有多余核心、且这不是热点路径上的高频调用**，才值得考虑。**在已经吃满 CPU 的服务里上 `parallelSort`，只是把排队换了个地方。**

| galloping 模式是什么？ | 一方连续获胜时切换**指数搜索 + 二分**，一次定位一批元素 | [#galloping](#galloping) |
| Java 对基本类型和对象为什么用不同算法？ | **对象有身份、必须稳定**（TimSort）；基本类型值相等即不可区分，可用更快的双轴快排 | [#two-entries](#two-entries) |
| `Arrays.sort(int[])` 是稳定排序吗？ | **不是**（双轴快排）；`Arrays.sort(Object[])` 才是（TimSort） | [#two-entries](#two-entries) |
| `byte[]` 排序用的什么算法？ | 较长时用**计数排序**——值域只有 256 种，**满足非比较排序的前提** | [#dual-pivot](#dual-pivot) |
| 链表的排序为什么用归并？ | 链表**不需随机访问**，归并只需改指针、`O(1)` 额外空间；快排反而需要随机访问 | [#why-quicksort-fast](#why-quicksort-fast) |
| `parallelSort` 一定更快吗？ | **不一定**。小数组更慢；多核已被打满时没有收益。经验阈值约 10 万以上 | [#parallel-sort](#parallel-sort) |

### 6.3 一句话总结

> **排序这一篇要带走的是「下界 + 前提」这个思维方式**：`O(n log n)` 的下界**只约束"靠比较"的算法**，前提一旦换成"整数且值域小"，计数排序就能做到 `O(n)`。
> **工程选型的每一步也都在看前提**：数据近有序 → TimSort、值域小 → 计数排序、元素不可区分 → 可以不要稳定、内存放不下 → 归并做外部排序。**"哪种排序最好"是个不成立的问题，问的应该是"我的数据有什么前提"。**
