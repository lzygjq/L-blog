# 树与索引结构

> 上一篇：[线性结构](/fundamentals/algorithms/linear)　|　下一篇：[图](/fundamentals/algorithms/graph)

数组和链表解决了"存和取"，但有一类需求它们都做不好：**在数据不断增删的同时，保持有序，并且能快速按范围查找。** 数组能找到下标但插入要搬移；哈希表插入很快但顺序是随机的。树就是为这个缺口而生的。

**先把结论放前面**：

1. **树的真正价值是「在动态增删下维持有序」**。如果数据是静态的，排序数组 + 二分（`O(log n)`）就够了；只有需要边查边改，才需要平衡树。
2. **AVL 和红黑树的分工是「读多还是写多」**。AVL 平衡更严（查询更快）；红黑树是**弱平衡**（插入删除旋转更少）。**Java 全套选了红黑树**，因为它的典型场景是动态增删。
3. **堆是"只关心极值"的树**，它的用途不止排序——**TopK、定时器、任务调度、合并 K 个有序链表**都是它的主场，而这些场景里"全排序"是多余的。
4. **Trie 与并查集是两种"专用树"**：前者用空间换前缀查询，后者用近乎 `O(1)` 的代价维护"连通性"。它们不属于通用容器，但都是面试常客。

## 一、为什么需要树 {#why-tree}

把三种基础结构的"查找 / 插入 / 有序性"放在一起看，缺口就很清楚了：

| 结构 | 查找 | 插入/删除 | 能否有序遍历 | 问题 |
|---|---|---|---|---|
| 有序数组 | `O(log n)` 二分 | **`O(n)`** | ✅ | 插入代价高（要搬移） |
| 链表 | `O(n)` | `O(1)` | 可以（如果有序） | 查找太慢 |
| 哈希表 | **`O(1)` 平均** | `O(1)` 平均 | ❌ **顺序随机** | **无法范围查询** |
| **平衡二叉搜索树** | **`O(log n)`** | **`O(log n)`** | ✅ **天然有序** | 实现复杂、有常数开销、缓存不友好 |

**树填的正是"既要动态增删、又要有序"这个格**。这也是为什么数据库索引在内存里用红黑树、在磁盘上用 B+ 树——都是同一个需求的两种硬件适配（磁盘版见 [MySQL 索引](/database/mysql/index)）。

## 二、二叉树的遍历 {#traversal}

遍历是树的一切操作的基础。

| 遍历 | 顺序 | 典型用途 |
|---|---|---|
| **前序**（根左右） | 根 → 左 → 右 | 复制树、序列化（先记自己再记子树） |
| **中序**（左根右） | 左 → 根 → 右 | **BST 的中序是升序序列**（最重要的性质） |
| **后序**（左右根） | 左 → 右 → 根 | 释放内存、计算子树聚合值（自底向上） |
| **层序**（BFS） | 逐层从左到右 | 求深度/宽度、按层处理 |

```java
// 中序递归：注意"访问位置"决定了是什么序
public void inorder(TreeNode node, List<Integer> out) {
    if (node == null) return;
    inorder(node.left, out);
    out.add(node.val);          // ← 中序把"访问自己"放在中间
    inorder(node.right, out);
}
```

**用一句话记住四种遍历**：把"访问节点本身"这个动作放在递归的**哪个位置**——最前是前序、中间是中序、最后是后序。**层序是另一套逻辑（队列 + BFS），不属于递归三兄弟。**

### 递归 vs 迭代 {#iterative}

面试常要求"用非递归实现"。迭代版的核心是**显式维护一个栈**（模拟函数调用栈）：

```java
// 中序迭代（统一模板：一直向左走，走到头就弹出并转向右）
public List<Integer> inorderIterative(TreeNode root) {
    List<Integer> out = new ArrayList<>();
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !stack.isEmpty()) {
        while (cur != null) {       // 一路向左，沿途压栈
            stack.push(cur);
            cur = cur.left;
        }
        cur = stack.pop();          // 弹出 → 访问
        out.add(cur.val);
        cur = cur.right;            // 转向右子树
    }
    return out;
}
```

**工程上要注意**：递归的深度就是**栈深度**。一棵退化成链的树有 n 层，递归会直接 `StackOverflowError`——所以在处理不可信数据的树上，**迭代版更安全**（或者用 [Morris](#morris) 那样的 `O(1)` 空间算法）。

### Morris 遍历：O(1) 空间的遍历 {#morris}

**不用栈、不用递归**，利用叶子节点空闲的右指针（**线索化**）实现 `O(1)` 额外空间：

```text
核心操作：找当前节点的"中序前驱"（左子树的最右节点）
  ① 如果前驱的 right 为空 → 让它指向当前节点（建立线索），然后向左走
  ② 如果前驱的 right 已经指向自己 → 说明左子树已处理完，切断线索，访问自己，向右走
```

**代价**：每个节点被访问两次，虽然时间复杂度仍是 `O(n)`（常数变大），且**遍历过程中树被临时修改**（不是线程安全的）。

> **要不要背 Morris？** 面试里被问到"如何 `O(1)` 空间遍历二叉树"时能说出来就够了。工程里几乎不用——因为它改动了树结构，可读性也差。

### 遍历序列能唯一确定树吗 {#reconstruct}

这是高频考点，结论是一张表：

| 已知 | 能否唯一确定 | 原因 |
|---|---|---|
| 前序 + 中序 | ✅ 能 | 前序的第一个是根，在中序里把左右子树切开，递归 |
| 中序 + 后序 | ✅ 能 | 后序的最后一个是根，同上 |
| 前序 + 后序 | ❌ 不能 | 无法区分"只有左子树"和"只有右子树" |
| 中序 + 层序 | ✅ 能 | 层序的第一个也是根 |

**关键洞察**：**必须有中序**，因为只有中序能把"根"与"左右"对应起来。这个结论解释了为什么序列化树时通常都带中序（或带空节点占位）。

## 三、二叉搜索树与它的致命缺陷 {#bst}

**BST（二叉搜索树）的定义**：对任意节点，**左子树全部小于它，右子树全部大于它**。

这条性质带来一个漂亮的结果：**中序遍历得到升序序列**（所以验证一棵树是不是 BST，就看中序是否递增）。

| 操作 | 平均 | **最坏（退化成链）** |
|---|---|---|
| 查找 | `O(log n)` | **`O(n)`** |
| 插入 | `O(log n)` | **`O(n)`** |
| 删除 | `O(log n)` | **`O(n)`** |

**最坏情况不是理论上的意外，而是现实中的常态**：按 1,2,3,4,5 的顺序插入，得到的是一棵**链**——`O(log n)` 完全失效。

```text
插入 1,2,3,4,5 得到的"二叉搜索树"：

   1
    \
     2
      \
       3        ← 这就是一个链表，
        \           所有操作退化为 O(n)
         4
          \
           5
```

**这就是平衡树存在的全部理由**：用插入删除时的额外维护（旋转），把树高锁在 `O(log n)`。

**删除节点的三种情况**（面试常问，容易漏）：

| 情况 | 处理 |
|---|---|
| 删**叶子** | 直接摘掉 |
| 删**只有一个孩子**的节点 | 用孩子顶替它 |
| 删**有两个孩子**的节点 | **用中序后继（右子树最左节点）替换它的值**，然后转化为"删除那个后继"（后继最多只有一个右孩子） |

## 四、AVL 与红黑树：平衡的两种标准 {#balanced}

### 两种平衡的定义 {#avl-vs-rb}

| 维度 | **AVL 树** | **红黑树** |
|---|---|---|
| 平衡条件 | 任何节点**左右子树高度差 ≤ 1**（严格） | **最长路径 ≤ 2 × 最短路径**（弱） |
| 树高 | **约 1.44 log n**（更矮） | 约 2 log n（更高） |
| 查找 | **更快**（树矮） | 稍慢 |
| 插入/删除 | **旋转更频繁**，代价高 | **旋转更少**（插入最多 2 次、删除最多 3 次旋转） |
| 适用 | **读多写少** | **写多**、通用 |
| 典型应用 | 少量内存索引场景 | **Java `TreeMap` / `TreeSet` / `HashMap` 树化**、Linux CFS 调度器、`epoll` 的 fd 集合 |

**一句话记法**：**AVL 更平、查得快；红黑树更松、改得快。**

### 红黑树的五条性质 {#rb-properties}

1. 每个节点是**红色或黑色**；
2. **根节点是黑色**；
3. 每个**叶子（NIL 空节点）是黑色**；
4. **红色节点的两个子节点必须是黑色**（不能有连续两个红节点）；
5. **从任一节点到其所有叶子的路径，包含相同数目的黑节点**（黑高相同）。

**这五条如何推出"最长 ≤ 2 × 最短"**：由性质 4，红色节点不能相邻，所以最长路径上红黑交替；由性质 5，任何路径的黑节点数相同。**于是最长路径（红黑交替）最多是最短路径（全黑）的两倍。**

**这个证明值得记住**——它把"五条看起来零散的规定"变成了一个清晰的结论：**红黑树是用"放松的平衡"换"更少的旋转"**。

### 为什么 Java 选红黑树 {#why-red-black}

`TreeMap`、`TreeSet`、以及 `HashMap` 的桶树化，**全都用红黑树而不是 AVL**。原因：

| 原因 | 说明 |
|---|---|
| **场景是动态增删** | `TreeMap` 要支持高频 `put`/`remove`；AVL 在这里旋转代价高 |
| **插入最多 2 次旋转、删除最多 3 次** | 红黑树的旋转次数是**常数**，与树规模无关；AVL 的旋转可能沿路径传播 |
| **查询慢一点可以接受** | 树高差 2 倍以内，`O(log n)` 的常数差异远小于旋转带来的写代价 |
| **实现已被充分验证** | TreeMap 从 JDK 1.2 起就是红黑树，稳定性有长期保证 |

**注意一个反直觉点**：`HashMap` 的桶树化阈值是 8，触发概率约 `6×10⁻⁸`——**树化几乎不会发生**。所以那里用红黑树**不是性能优化，而是防哈希碰撞攻击**（见 [哈希表的树化](/fundamentals/algorithms/linear#load-factor)）。

### 跳到跳表：另一种有序索引 {#skiplist}

平衡树有一个竞争对手：**跳表（Skip List）**。它用**多层链表**实现 `O(log n)` 的期望查找，而不是靠旋转维持平衡。

| 维度 | 红黑树 | 跳表 |
|---|---|---|
| 实现难度 | 高（旋转 + 变色，边界情况多） | **低**（就是多层链表） |
| 范围查询 | `O(log n + k)` | **`O(log n + k)`，且天然适合** |
| 并发 | 难（旋转影响大范围结构，需要锁） | **易（只需局部 CAS）** |
| 内存 | 省 | 费（多层的指针开销） |
| 代表 | Java `TreeMap`、`epoll` | **Redis 有序集合（zset）** |

**Redis 选跳表的核心原因是并发与实现简单**——这也解释了为什么"教科书说红黑树更高效"却不妨碍跳表在工程里广泛使用。**工程选择从来不是只比渐近复杂度。**

## 五、堆：只关心极值的树 {#heap}

堆是**完全二叉树**，且满足**堆序性质**（大顶堆：父 ≥ 子）。

### 为什么用数组存 {#array-heap}

完全二叉树的性质让它可以用数组紧凑存储，**不需要任何指针**：

```text
        a[1] (根)
       /        \
   a[2]         a[3]
   /   \        /   \
a[4]  a[5]   a[6]  a[7]

下标关系（以 1 为起点）：
  父 = i / 2        左 = 2i        右 = 2i + 1

若以 0 为起点（Java 的 PriorityQueue 用法）：
  父 = (i - 1) / 2  左 = 2i + 1    右 = 2i + 2
```

**没有指针是堆最大的工程优势**——这是"数组/缓存友好"在树结构上的又一次胜利（同 [缓存局部性](/fundamentals/algorithms/linear#cache-locality)）。

### 建堆为什么是 O(n) 而不是 O(n log n) {#build-heap}

这是**最容易答错的一个复杂度问题**。常见错误推理是"n 个元素，每个下沉 `O(log n)`，所以 `O(n log n)`"。

**正确的推导**：建堆是**从最后一个非叶节点往前**依次下沉。关键在于**越靠近底层的节点越多，但下沉深度越浅**：

```text
第 h 层有约 n / 2^(h+1) 个节点，每个最多下沉 h 层

总代价 = Σ (n / 2^(h+1)) · h
         h=0→∞
       = n/2 · Σ h / 2^h
       = n/2 · 2            （级数 Σ h/2^h 收敛于 2）
       = O(n)
```

**直觉版解释**：一半的节点是叶子（下沉 0 层），四分之一的节点只需下沉 1 层，八分之一只需 2 层……**加总的量级是 `n` 而不是 `n log n`。**

> **对比**：如果换成"逐个插入建堆"，那确实是 `O(n log n)`（每次插入都从底浮到顶）。**"建堆 `O(n)`" 只针对自底向上的 `buildHeap`。**

### 堆的三个任务 {#heap-uses}

| 任务 | 做法 | 复杂度 |
|---|---|---|
| **堆排序** | 建堆 + 反复取堆顶并调整 | `O(n log n)`、**原地（`O(1)` 额外空间）** |
| **TopK（最小 K 个）** | 维护**大小为 K 的大顶堆**，比堆顶小就替换 | `O(n log K)`，**空间 `O(K)`** |
| **优先队列 / 定时器** | 按优先级或到期时间出队 | 插入/取出 `O(log n)` |

**TopK 为什么用"大顶堆存 K 个"而不用"小顶堆存全部"**：因为目标是**只要 K 个**。用 `O(K)` 的空间筛掉绝大部分元素，这是"堆"相对"全排序"的降维打击——**全排序 `O(n log n)` 在这里是完全多余的**（详见 [海量数据处理 · TopK](/fundamentals/algorithms/high-volume#topk)）。

**堆不适合做什么**：**查找任意元素**（`O(n)`）。堆只保证**堆顶是极值**，其余位置无序。**需要"既快速取极值、又能按任意键查找"时，用 `TreeMap` 而不是 `PriorityQueue`。**

## 六、两种专用树：Trie 与并查集 {#trie}

### Trie（前缀树） {#trie-detail}

Trie 按**字符逐层**组织，每个节点代表一个前缀。

```text
插入 "cat"、"car"、"dog"：

        (root)
       /      \
      c        d
      |        |
      a        o
     / \       |
    t   r      g*
    *   *      (g 位置标记"是一个完整的词")

查找 "ca" → 能走到 a 节点 → 存在这个前缀
查找 "cab" → 走到 a 后无 b 分支 → 不存在
```

| 维度 | 说明 |
|---|---|
| 复杂度 | 查找/插入都是 **`O(m)`（m 为字符串长度）**，**与词表大小无关** |
| 优势 | **前缀查询天然高效**；哈希表做不到（无法按前缀找） |
| 代价 | **空间消耗大**（每个字符一个节点）；可用双数组 Trie / 压缩 Trie（Radix Tree）优化 |
| 典型应用 | 搜索框联想、**敏感词过滤（配 AC 自动机做多模式匹配）**、IP 路由表（前缀匹配） |

**为什么敏感词过滤要用 Trie 而不用哈希表**：因为哈希表只能判断"整个词是否命中"，而 Trie 能在**一次扫描**中同时匹配**成千上万个模式串**——这是 AC 自动机（Trie + 失败指针）的基础。**正则表达式做敏感词过滤的性能问题，本质上就是在做一次次独立匹配。**

### 并查集（Union-Find） {#union-find}

并查集维护一组**动态连通性**：只回答一个问题——**两个元素是否在同一个集合里**。

| 操作 | 含义 |
|---|---|
| `find(x)` | 找到 x 所在集合的**代表元**（根） |
| `union(x, y)` | 合并两个集合 |

**两个关键优化，缺一不可**：

| 优化 | 做法 | 效果 |
|---|---|---|
| **路径压缩** | `find` 时把沿途节点**直接挂到根上** | 树变扁平，后续 `find` 更快 |
| **按秩/按大小合并** | 把矮树挂到高树上（或小集合挂到大集合） | 避免合并出高树 |

**两个优化同时使用时，均摊复杂度是 `O(α(n))`（反阿克曼函数）**。`α(n)` 增长极慢——**在宇宙中原子数量级（10⁸⁰）下，`α(n) < 5`**。**所以工程上可以直接当作 `O(1)`。**

```java
// 最简实现：数组表示 + 路径压缩
class UnionFind {
    private final int[] parent;

    UnionFind(int n) {
        parent = new int[n];
        for (int i = 0; i < n; i++) parent[i] = i;   // 初始各自成集合
    }

    int find(int x) {
        if (parent[x] != x) {
            parent[x] = find(parent[x]);             // 路径压缩：顺手改写指向根
        }
        return parent[x];
    }

    void union(int x, int y) {
        parent[find(x)] = find(y);                   // 生产代码应加上按秩合并
    }
}
```

**典型应用**：Kruskal 最小生成树（判断加边会不会成环）、朋友圈/社交网络分组、图片连通区域标记、编译器符号表。

| 问题 | 一句话答案 | 详见 |
|---|---|---|
| 为什么需要树？ | 数组能二分但插入 `O(n)`、哈希能 `O(1)` 但无序；**树同时提供 `O(log n)` 增删与有序遍历** | [#why-tree](#why-tree) |
| 中序遍历 BST 得到什么？ | **升序序列**——这是 BST 最重要的性质，也是"验证是否为 BST"的方法 | [#traversal](#traversal) |
| 已知哪两种遍历能唯一确定树？ | **必须含中序**（前序+中序、中序+后序、中序+层序）；**前序+后序不行** | [#reconstruct](#reconstruct) |
| BST 的平均和最坏复杂度？ | 平均 `O(log n)`，**最坏 `O(n)`（退化成链）**——按序插入就是常态 | [#bst](#bst) |
| 删除有两个孩子的 BST 节点怎么做？ | 用**中序后继**（右子树最左节点）替换值，再删除那个后继 | [#bst](#bst) |
| AVL 和红黑树怎么选？ | **读多写少选 AVL**（更平、查得快）；**写多选红黑树**（旋转少） | [#avl-vs-rb](#avl-vs-rb) |
| 红黑树五条性质推出什么？ | **最长路径 ≤ 2 × 最短路径**：红不能相邻 → 最长红黑交替；黑高相同 → 最短全黑 | [#rb-properties](#rb-properties) |
| 为什么 Java 的 `TreeMap` 用红黑树？ | 动态增删场景：**插入最多 2 次、删除最多 3 次旋转**（常数），AVL 的旋转代价更高 | [#why-red-black](#why-red-black) |
| 跳表为什么能替代红黑树？ | **实现简单 + 并发友好**（局部 CAS 而非大范围旋转）；Redis zset 选它就是这个原因 | [#skiplist](#skiplist) |
| 建堆是 `O(n)` 还是 `O(n log n)`？ | **自底向上建堆是 `O(n)`**：层数越深节点越多但下沉越浅，级数收敛于 2n | [#build-heap](#build-heap) |
| 堆排序的空间复杂度？ | **`O(1)`**——它是唯一真正原地（无递归栈）的 `O(n log n)` 排序 | [#heap-uses](#heap-uses) |
| TopK 为什么要用堆？ | 维护**大小 K 的堆**，空间 `O(K)`、时间 `O(n log K)`；**全排序 `O(n log n)` 是多余的** | [#heap-uses](#heap-uses) |
| 堆不能做什么？ | **查找任意元素是 `O(n)`**——堆只保证堆顶是极值；需要按键查找用 `TreeMap` | [#heap-uses](#heap-uses) |
| 敏感词过滤为什么用 Trie？ | 哈希表只能判断**整词命中**；Trie 能一次扫描匹配**成千上万个模式**（AC 自动机的基础） | [#trie-detail](#trie-detail) |
| 并查集的复杂度是多少？ | 路径压缩 + 按秩合并后是 **`O(α(n))` 均摊**；`α(n) < 5`，可直接当 `O(1)` | [#union-find](#union-find) |

### 7.3 一句话总结

> **树这一篇要带走的是「顺序」这个维度的代价**：哈希表用放弃顺序换来了 `O(1)`，树把顺序买回来，代价是 `O(log n)`。而你选择哪种树（AVL / 红黑树 / 跳表 / B+ 树），取决于**读多写少、是否并发、内存在磁盘还是内存**——**同一个需求在不同硬件下的最优解是不一样的。**
