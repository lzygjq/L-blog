# 海量数据处理

> 上一篇：[动态规划与算法思想](/fundamentals/algorithms/dp)

前面六篇都默认了一个前提：**数据能装进内存**。这一篇处理前提不成立的情形——**数据量超过内存、甚至超过单机磁盘**。这类问题在面试里成体系地出现（"40 亿个整数找重复""10 亿 URL 去重""1TB 日志求 TopK"），而在工程里就是**日志去重、用户画像、缓存穿透防护、大表排序**。

**先把结论放前面**：

1. **所有海量问题的第一步都是问三个问题**：数据量到底多大？**能不能接受误差**？要不要精确结果？**这三个答案直接决定用什么武器**——选错的代价是几个数量级的内存或时间。
2. **「牺牲精确性换空间」是这一篇最重要的一类思路**：布隆过滤器、HyperLogLog 都是这个套路。**面试里主动提"如果允许误判，可以用布隆过滤器"，比硬算精确解更专业。**
3. **分治（切分）+ 单机算法 = 分布式方案的全部本质**。所谓"海量数据算法"，绝大多数就是"**先按某个规则把数据切成能处理的小块，再对每块用普通算法，最后合并**"。
4. **能落地的方案通常很朴素**：位图、堆、外部归并、哈希分桶。**不需要复杂算法，需要的是对"数据形状"和"空间预算"的准确判断。**

## 一、先问三个问题 {#why}

拿到"海量数据"的题，**不要立刻想算法**。先回答这三问：

| 问题 | 为什么关键 | 影响 |
|---|---|---|
| **① 数据量到底多大？** | "海量"是模糊词。是 `10⁶`、`10⁹` 还是 `10¹²`？ | 决定要不要分治、能不能单机 |
| **② 能否接受误差？** | 存在性判断允许假阳性吗？基数统计允许 1% 偏差吗？ | **允许误差 → 概率数据结构（省几个数量级内存）** |
| **③ 需要精确结果还是近似？** | "去重后有几个"和"这些是哪些"，难度完全不同 | 只求数量 → HyperLogLog；要求集合 → 必须精确 |

**三个问题问完，方案基本就定了**。这张表是这一篇的总纲：

| 需求 | 数据量级 | 方案 | 空间 / 复杂度 |
|---|---|---|---|
| **存在性判断**（允许假阳性） | `10⁹+` | **布隆过滤器** | 每元素约 **10 bit**（1% 误判） |
| **存在性判断**（精确，值域可控） | `10⁹+` | **位图** | **1 bit / 值** |
| **去重计数**（允许 1% 误差） | `10⁹+` | **HyperLogLog** | **固定 12 KB** |
| **找最大/最小 K 个** | 内存放不下 | **堆 + 分治** | `O(K)` 内存 |
| **排序（内存放不下）** | 大于内存 | **外排序（多路归并）** | 与内存同量级的缓冲区 |
| **找重复 / 找共同元素** | 内存放不下 | **哈希分桶 + 分治** | 单桶需能放进内存 |

## 二、位图：用 1 bit 表示一个"存在" {#bitmap}

**位图（Bitmap / BitSet）的洞察极其简单**：如果问题的答案只有"存在/不存在"两种，那 1 个 bit 就够了，**没必要存值本身**。

```text
判断 1 亿个整数是否重复

HashSet<Integer> 方案：
  1 亿个 Integer 对象 ≈ 每个 16 字节（对象头 + int + 引用）+ HashMap 桶开销
  → 4 GB 以上，而且大量 GC 压力

位图方案（值域 0 ~ 1 亿）：
  1 亿 bit = 12.5 MB
  → 小 300 多倍
```

```java
// 位图的核心操作（Java 的 BitSet 已封装）
void set(int x)   { bits[x >> 5] |=  (1 << (x & 31)); }   // 置 1
boolean get(int x){ return (bits[x >> 5] & (1 << (x & 31))) != 0; }
void clear(int x) { bits[x >> 5] &= ~(1 << (x & 31)); }   // 置 0
// x >> 5 = x / 32（属于哪个 int），x & 31 = x % 32（int 内的第几位）
```

**位图与布隆过滤器的区别（最容易混淆的一点）**：

| | **位图** | **布隆过滤器** |
|---|---|---|
| 精确性 | **精确**（无误差） | **有假阳性** |
| 前提 | **值域可控**（如用户 ID < 2³²） | **只要能哈希，值域多大都行** |
| 空间 | **1 bit / 值**（与值域大小成正比） | 约 10 bit / **元素**（与元素数成正比） |
| 能否删除 | **能**（精确清位） | **不能**（除非用计数布隆） |

**选择依据**：**值域是"有限的、可编号的" → 用位图（精确且更省）；值域无限或极大（字符串、URL）→ 用布隆过滤器。**

### 稀疏问题与 Roaring Bitmap {#roaring}

**朴素位图的致命弱点**：如果值域是 `0 ~ 2³²` 但只存了 1000 个值，位图仍要 `2³²` bit = **512 MB**——**99.99% 的空间是零。**

**Roaring Bitmap 的解法是"分块 + 按密度选表示"**：

```text
思想：把 32 位整数按高 16 位切成 65536 个块（chunk）
      每个块内部再根据"稠密还是稀疏"选择表示：

  稠密块（元素 > 4096）→ 用位图（2^16 bit = 8 KB）
  稀疏块（元素 ≤ 4096）→ 用有序数组（每个元素 2 字节）

效果：既能处理稠密数据（位图的优势），也不会为稀疏数据浪费空间
```

**Roaring Bitmap 已被广泛采用**：**Druid、ClickHouse、Spark、Elasticsearch 的聚合都用了它**。这是"同一个数据结构在不同数据密度下需要不同表示"的典型工程案例。

### 位图的工程用途 {#bitmap-uses}

| 场景 | 怎么用 |
|---|---|
| **日活 / 月活统计** | 每个用户一个 bit；多日"或运算"即得多日活跃并集 |
| **用户签到 / 打卡** | 一个月 31 天用 31 bit 就能表示，1 个用户 4 字节 |
| **标签圈人（交集/并集）** | 多个标签位图做 `AND` / `OR`，**位运算是 CPU 最擅长的操作** |
| **布隆过滤器的底层存储** | 布隆过滤器本身就是"多个哈希函数 + 一个位图" |

> **一个重要的替代方案**：如果**只要求"有多少个"，不要求"是哪几个"**，用 **HyperLogLog** 更好——它用**固定 12 KB**（Redis 实现）就能估算 `2⁶⁴` 量级的基数，标准误差约 **0.81%**。**位图的空间与值域成正比，HyperLogLog 与值域无关**——这是"基数统计"场景更优的选择。

## 三、布隆过滤器：用概率换空间 {#bloom}

**问题**：判断"这个 URL 是否已经爬过"，有 10 亿个 URL。**存下来要几百 GB**。

**布隆过滤器的思路**：不存数据本身，只存"**这个数据映射到的几个 bit 位置**"。

```text
插入 "example.com"：
  ① 用 k 个哈希函数算出 k 个位置（比如 3 个：2、5、9）
  ② 把这些位置全部置 1

查询 "example.com"：
  ① 同样算出 2、5、9
  ② 三个位置全是 1 → "可能存在"（也可能是别人置的，即假阳性）
  ③ 只要有一个是 0  → "一定不存在"（确定）

       位数组（m = 12）
  [0][0][1][0][0][1][0][0][0][1][0][0]
         ↑        ↑           ↑
         三个位置都为 1 → 判定"可能存在"
```

**布隆过滤器的三个确定性**（面试重点）：

| 结论 | 原因 |
|---|---|
| **判定"不存在" → 一定不存在** | 位是 0，说明没有任何元素的哈希覆盖到这里 |
| **判定"存在" → 可能存在（有假阳性）** | 那几个位可能被**其他元素**共同置 1 |
| **不会漏判（无假阴性）** | 插入过的元素，其所有位必然被自己置 1 |

**所以布隆过滤器的语义是**：**"可能包含" / "一定不包含"**。这个不对称性决定了它的用法。

### 参数公式 {#bloom-formulas}

三个参数：位数组长度 `m`、元素个数 `n`、哈希函数个数 `k`、误判率 `p`。

| 公式 | 表达式 | 用途 |
|---|---|---|
| **误判率** | `p ≈ (1 - e^(-kn/m))^k` | 已知 m、n、k 算误判率 |
| **最优哈希个数** | `k_opt = (m/n) · ln2 ≈ 0.693 · (m/n)` | 给定空间预算，k 取多少最优 |
| **最小位数组长度** | `m ≈ -n · ln p / (ln2)² ≈ -1.44 · n · ln p` | 给定 n 和 p，需要多少 bit |

**工程速查**：

| 目标误判率 | 每元素需要 bit 数 | 最优 k |
|---|---|---|
| 10% | 约 4.8 bit | 3 |
| **1%** | **约 9.6 bit** | **7** |
| 0.1% | 约 14.4 bit | 10 |

**从这张表能读出一个关键结论**：**误判率每降低一个数量级，成本只增加约 4.8 bit/元素**——**用误判率换空间是极其划算的交易**。这就是为什么布隆过滤器在工程里这么流行。

> **注意 `k` 不是越大越好**：`k` 太大时位数组被迅速填满，**误判率反而上升**。存在最优值 `k_opt`——这一点常被忽略。

### 不支持删除，以及三个替代方案 {#bloom-delete}

**为什么不能删除**：一个 bit 位是**多个元素共享的**。把它清 0，会**同时影响其他元素**，造成假阴性——而**假阴性是布隆过滤器唯一的"绝对错误"**（说"不存在"就必须真的不存在）。

| 方案 | 做法 | 代价 |
|---|---|---|
| **计数布隆过滤器（CBF）** | 每个位置用 4~8 bit 计数器代替 1 bit | **空间增加 4~8 倍**；需要防下溢 |
| **布谷鸟过滤器（Cuckoo Filter）** | 存指纹而非位，支持删除 | 空间效率更高、查询更快；**插入可能失败需重排** |
| **定期重建** | 离线重建整个过滤器 | 重建期间有窗口期；适合数据变化不频繁的场景 |

**选哪个**：需要删除且能接受重建窗口 → CBF；**追求空间与查询效率且能处理插入失败 → 布谷鸟**；数据基本只增不改（如"已爬 URL"）→ **原始布隆过滤器即可**。

### 工程用途：缓存穿透是第一大场景 {#bloom-uses}

| 场景 | 怎么用 |
|---|---|
| **缓存穿透防护** | 请求先过布隆过滤器；**判"不存在"就直接返回，不查库**——挡住"查一个不存在的 ID"这类恶意/异常流量 |
| **URL 去重（爬虫）** | 判"已爬过"就跳过；少量重复爬可接受，**但绝不能漏爬**（无假阴性正好满足） |
| **推荐系统去重** | "已看过的内容不再推荐"，允许少量误判 |
| **HBase / LevelDB / RocksDB 的 SSTable** | 用布隆过滤器**避免无效的磁盘查找**——这是 LSM-Tree 读放大的关键优化 |

> **缓存穿透的完整方案要配合空值缓存**：布隆过滤器挡的是"**从来不存在**的键"；如果键**曾经存在后被删除**，布隆过滤器仍判"存在"——所以实践里通常**布隆过滤器 + 短 TTL 的空值缓存**一起用。

## 四、TopK：为什么不需要排序 {#topk}

**问题**：从 10 亿个数里找最大的 100 个。

**核心洞察**：**全排序是多余的**。要 K 个，就不需要把 n 个都排好。

### 单机内存放得下（或流式）：维护大小为 K 的堆 {#topk-heap}

```text
找"最大的 K 个" → 维护一个【大小为 K 的小顶堆】

为什么是"小顶堆"？堆顶是这 K 个里【最小的】——
新元素只要比堆顶大，就替换堆顶；比堆顶小，直接丢弃。

  堆内：K 个当前最大的候选（堆顶 = 其中最小）
  新元素 x：
    x <= 堆顶 → 丢弃（x 进不了前 K）
    x >  堆顶 → 弹出堆顶，x 入堆
```

| 维度 | 值 |
|---|---|
| 时间 | **`O(n log K)`**（每个元素最多一次 `O(log K)` 的调整） |
| 空间 | **`O(K)`** |
| 对比全排序 | `O(n log n)` 时间 + `O(n)` 空间 |

**当 K 很小时（比如 100），`log K ≈ 7`，几乎是线性的**——这就是它比排序快一个数量级的来源。

### 内存放不下：分治 + 外排 {#topk-distributed}

```text
① 把 10 亿个数按哈希切成 100 份（每份约 1000 万，可放进内存）
② 每份单独求 TopK（用堆）——得到 100 × K 个候选
③ 把这 100 × K 个候选合起来再求一次 TopK（数据量很小）
```

**关键点**：**TopK 可以分治，因为"全局最大的 K 个"必然包含在"各分片最大的 K 个"里**——每个分片最多贡献 K 个，不可能有第 K+1 个进入全局前 K。**这个论证是这类分治方案正确性的依据，面试里能说出来就很加分。**

> **注意**：这个性质对 TopK **成立**，但对"求中位数"**不成立**（中位数不能靠各分片的中位数合成）——**"哪些问题可以分治合并"是这类题的核心考点**。

## 五、外排序：内存装不下怎么排 {#external-sort}

**问题**：1 TB 数据、只有 8 GB 内存，要排序。

**标准解法是"外部归并排序"**，四个步骤：

```text
① 【分段读入】把大文件切成能放进内存的块（比如每块 1 GB）
② 【块内排序】每块读进内存，用快排/归并排好，写成临时有序文件
      → 得到 1000 个有序的临时文件（每个 1 GB）
③ 【多路归并】用【最小堆】同时读这 1000 个文件，每次取最小输出
④ 【输出】写成一个完整有序的大文件
```

**第 ③ 步是整个算法的核心**，为什么用堆：

| 方式 | 每输出一个元素 | 总代价 |
|---|---|---|
| 每次线性扫描 1000 个文件的当前头 | `O(K)` | **`O(n·K)`** 不可接受 |
| **维护大小为 K 的最小堆** | `O(log K)` | **`O(n log K)`** ✅ |

**合并路数 K 怎么定**（一个真实的工程权衡）：

| K 太小 | K 太大 |
|---|---|
| 归并趟数变多 → **IO 次数增加** | 需要同时打开的文件描述符变多（**受 `ulimit -n` 限制**），且缓冲区被摊薄、随机读变多 |

**实践上 K 通常取几百**，并且会用**败者树**（一种比堆常数更小的"专用于多路归并"的结构）来优化堆的常数开销。**从这一个小细节可以看出：外排序的性能瓶颈不是比较次数，是 IO 次数。**

**工程里的身影**：数据库的 `ORDER BY` / `GROUP BY`（超出内存时自动走 external merge sort）、Linux 的 `sort` 命令（`--buffer-size` 就是第 ① 步的块大小）、MapReduce 的 shuffle 阶段。

## 六、分治哈希分桶：找重复与找共同元素 {#divide-hash}

**问题**：两个各 100 GB 的文件，找出共同出现的 URL。或者：100 GB 文件里找出出现次数最多的那个。

**核心手法是"按哈希值分桶"**，而不是简单地按行切分：

```text
为什么不能用"按文件前 1/10 切"？

  ❌ 按范围切：同一个 URL 可能出现在任意一段里
             → 两边的对应关系全乱了，无法做"共同元素"比较

  ✅ 按 hash(url) % 100 切：
     同一个 URL 必然落到同一个桶号（哈希的确定性）
     → 两个文件都按同样规则切，对应桶两两比较即可
     → 第 i 个桶的答案合并起来就是全局答案
```

**三种典型问题的解法**：

| 问题 | 解法 |
|---|---|
| **找共同元素**（两文件交集） | 两边都按 `hash % N` 分桶 → 对应桶放内存做哈希集合求交集 → 合并 |
| **找出现次数最多的元素** | 按 `hash % N` 分桶（**同一元素必在同一桶**）→ 桶内哈希计数 → 取各桶最大 → 再比一次 |
| **找重复/不重复的数** | 值域可控 → **位图**；值域不可控 → 哈希分桶后桶内哈希表判断 |

**关键论证**：**哈希的确定性保证"同一个键一定落进同一个桶"**——所以"同键的统计/比较"可以在桶内独立完成。**这是整个分治方案正确性的基础，也是为什么必须按哈希切而不是按范围切。**

> **一个常被追问的延伸**：如果桶的大小仍然不均衡（哈希倾斜），怎么办？答案是用**一致性哈希**或**两级分桶**（先按 hash 分，桶内再按另一个 hash 分）。这个问题在分布式缓存里有更完整的讨论——**那里要解决的不是"数据太大"，而是"节点会上下线"**。

## 七、方案对照速查 {#cheatsheet}

把这一篇的所有武器放在一张表里，遇到问题先查表：

| 需求 | 允许误差？ | 方案 | 空间量级 |
|---|---|---|---|
| 判断存在性（值域可控） | 精确 | **位图 / BitSet** | 1 bit / 值域 |
| 判断存在性（值域可控且稀疏） | 精确 | **Roaring Bitmap** | 与元素数成正比 |
| 判断存在性（值域不可控） | **允许假阳性** | **布隆过滤器** | 约 10 bit / 元素 |
| 判断存在性（值域不可控） | 精确 | 哈希分桶 + 桶内哈希表 | 与元素数成正比 |
| **去重计数** | 允许 ~1% | **HyperLogLog** | **固定 12 KB** |
| **去重计数** | 精确 | 哈希分桶（或位图，若值域可控） | 与元素数成正比 |
| 求最大/最小 K 个 | 精确 | **大小 K 的堆**（+ 分治） | `O(K)` |
| 求 Top1（最大/最小） | 精确 | 一次遍历 | `O(1)` |
| 排序 | 精确 | **外排序：分段排序 + 多路归并** | 与内存同量级 |
| 找重复 / 找交集 | 精确 | **哈希分桶** | 单桶需放进内存 |

**最后一句方法论**：**这张表的使用方式是"先定位需求行，再看误差列"**。问清"能不能接受误差"这一步的价值，比记住任何一个数据结构都大——**因为它直接决定了内存预算是 MB 级还是 GB 级。**

### 8.2 概念级速查

| 问题 | 一句话答案 | 详见 |
|---|---|---|
| 拿到海量数据题先做什么？ | **先问三件事**：多大？**能接受误差吗**？要精确结果还是近似？ | [#why](#why) |
| 位图和布隆过滤器怎么选？ | **值域可控、要精确 → 位图**（1 bit/值）；**值域不可控、允许假阳性 → 布隆过滤器**（约 10 bit/元素） | [#bitmap](#bitmap) |
| 1 亿个整数去重需要多少内存？ | **位图约 12.5 MB**；用 `HashSet` 要 4 GB 以上 | [#bitmap](#bitmap) |
| 朴素位图什么时候失效？ | **值域极大但数据稀疏**时（`0~2³²` 只存 1000 个值也要 512 MB）→ 用 **Roaring Bitmap** | [#roaring](#roaring) |
| 只统计"有多少个"不要求"是哪些"，用什么？ | **HyperLogLog**：固定 12 KB 估算 `2⁶⁴` 量级基数，标准误差约 0.81% | [#bitmap-uses](#bitmap-uses) |
| 布隆过滤器会漏判吗？ | **不会**（无假阴性）。插入过的元素所有位必然为 1；**只有假阳性**（说存在但可能不存在） | [#bloom](#bloom) |
| 布隆过滤器的误判率公式？ | `p ≈ (1-e^(-kn/m))^k`；**最优 k = (m/n)·ln2**；`m ≈ -1.44·n·ln p` | [#bloom-formulas](#bloom-formulas) |
| 1% 误判率要多少空间？ | **约 9.6 bit/元素**，最优 k = 7。**误判率降一个数量级只多 4.8 bit**——非常划算 | [#bloom-formulas](#bloom-formulas) |
| 哈希函数个数越多越好吗？ | **不是**。k 太大位数组迅速填满，误判率反而上升；存在最优值 `k_opt` | [#bloom-formulas](#bloom-formulas) |
| 布隆过滤器为什么不能删除？ | 位是**多元素共享**的，清 0 会影响其他元素，**造成假阴性（唯一不能犯的错）** | [#bloom-delete](#bloom-delete) |
| 要删除怎么办？ | **计数布隆过滤器**（空间 ×4~8）或**布谷鸟过滤器**（支持删除、更省空间，但插入可能失败） | [#bloom-delete](#bloom-delete) |
| TopK 为什么用小顶堆而不是大顶堆？ | **堆顶是 K 个候选里最小的**——新元素比堆顶大才替换；用大顶堆会把最大的挤出去 | [#topk-heap](#topk-heap) |
| TopK 的复杂度和空间？ | **`O(n log K)` 时间、`O(K)` 空间**；K 很小时接近线性 | [#topk-heap](#topk-heap) |
| TopK 能分治吗？为什么？ | **能**。全局前 K 个**必然包含**在各分片前 K 个里（每片最多贡献 K 个） | [#topk-distributed](#topk-distributed) |
| 求中位数能像 TopK 那样分治吗？ | **不能**。各分片的中位数合成不出全局中位数——**"可否分治"是这类题的核心考点** | [#topk-distributed](#topk-distributed) |
| 外排序的三个步骤？ | **分段读入 → 块内排序 → 多路归并**；归并用**最小堆**把 `O(n·K)` 降到 `O(n log K)` | [#external-sort](#external-sort) |
| 外排序的瓶颈是什么？ | **IO 次数**，不是比较次数——所以合并路数 K 要权衡（太小趟数多、太大受 `ulimit -n` 限制） | [#external-sort](#external-sort) |
| 大文件找共同元素为什么按哈希切？ | **哈希的确定性保证同一个键必进同一个桶**——按范围切会破坏这个对应关系 | [#divide-hash](#divide-hash) |
| 缓存穿透怎么防？ | **布隆过滤器**（挡"从来不存在"的键）+ **短 TTL 空值缓存**（挡"曾被删除"的键） | [#bloom-uses](#bloom-uses) |

### 8.3 一句话总结

> **这一篇要带走的是「空间预算意识」**：同样的需求，**"能不能接受误差"这一个问题，就能让内存需求相差几个数量级**——精确去重计数要 GB 级，HyperLogLog 只要 12 KB。
> **而所有"海量"方案的骨架都是同一个**：**按哈希切成能处理的小块 → 块内用普通算法 → 合并结果**。区别只在于"块内那一步用的是位图、堆，还是排序"。
>
> **至此计算机基础三域成篇**。回看这条线索：网络把数据送到机器（[网络](/fundamentals/network/)）→ 操作系统决定谁接住它（[操作系统](/fundamentals/os/)）→ 算法决定怎么算得又快又省（本域）。**三域合起来，就是"一次请求背后到底发生了什么"的完整答案。**
