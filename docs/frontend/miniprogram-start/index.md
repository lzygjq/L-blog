# 小程序起步

## 一、小程序与普通网页的本质区别

| 维度 | 网页 | 小程序 |
|---|---|---|
| 运行环境 | 浏览器 | 微信客户端（宿主环境） |
| DOM/BOM | 完整可用 | **没有**（不能操作 DOM） |
| 渲染与逻辑 | 同一个线程/进程 | **渲染层与逻辑层分离（双线程）** |
| 开发语法 | HTML/CSS/JS | WXML/WXSS/JS（闭源壳，思路上更接近 Vue） |

没有 DOM 不是能力阉割，而是设计使然——根源在双线程模型。

## 二、双线程模型：一切约束的根源

```
渲染层（WebView，多页多 WebView）  ←─→  微信原生（Native 中转） ←─→  逻辑层（JsCore，单一线程）
        WXML + WXSS                              通信桥                    你的 JS 全部跑这里
```

三个要点：

1. **逻辑层与渲染层物理隔离**：JS 跑在独立的 JsCore 里，渲染在 WebView 里，两者不直接通信，一切数据交换经 Native 中转（序列化传输）。这样 JS 的任何卡顿不会直接阻塞页面渲染，也天然禁止了 JS 操纵 DOM 带来的安全风险（小程序内容可嵌在聊天窗口等场景，安全边界必须由平台把控）。
2. **`setData` 是唯一的常态数据通道**：因为隔离，改数据必须走 `this.setData({...})`，由框架把数据序列化后传给渲染层做 diff 渲染。**代价是每次调用都有序列化 + 通信开销**——所以有「`setData` 传大数据、高频调用是性能大忌」的铁律，本质就是别把通信桥堵死。
3. **逻辑层单线程**：和小程序[「Redis 单线程」](/database/redis/internals)一个道理——无锁、简单、可预测，但任何同步长计算都会卡住整个逻辑层，重计算该交给服务端。

> 补充：微信近年推出的 Skyline 渲染引擎把渲染从 WebView 迁到自研渲染器，方向就是收窄这条通信桥的损耗，但「逻辑与渲染分离」的架构没有变。

## 三、注册与工具链

- 注册入口 `mp.weixin.qq.com`，个人/企业主体都能注册，**AppID 是项目的唯一身份**（一个项目一个 AppID，测试号可免注册用于本地学习）。
- 微信开发者工具四件套：模拟器预览、编辑器、调试器（WXML 面板/Console/Network）、上传发布。真机预览用「预览二维码」，局域网内真机调试支持断点。
- 常用设置：把「不校验合法域名」勾上才能在开发期连本地后端（正式版必须走 HTTPS + 备案域名白名单，见[模板与样式](/frontend/miniprogram-template/)的网络请求一节）。

## 四、项目结构

```
project
├── pages/               # 所有页面，每个页面一个目录四件套
│   └── index/
│       ├── index.wxml   # 结构（类似 HTML）
│       ├── index.wxss   # 样式（类似 CSS）
│       ├── index.js     # 逻辑（Page() 注册页面实例）
│       └── index.json   # 页面级配置
├── utils/               # 工具函数
├── app.js / app.json / app.wxss   # 全局逻辑 / 全局配置 / 全局样式
└── project.config.json  # 开发者工具的项目配置（AppID、编译选项）
```

要点：**页面四件套文件名必须同名**；`app.json` 的 `pages` 数组第一项就是首页——新增页面在数组里加路径即自动创建文件，调整顺序即换首页。

## 五、四类配置文件，各管一层

| 文件 | 层级 | 管什么 |
|---|---|---|
| `app.json` | 全局 | 页面路由注册、window 默认样式、tabBar、网络超时、权限声明 |
| `project.config.json` | 工具 | AppID、编译方式、ES6 转 ES5、域名校验开关 |
| `sitemap.json` | 平台 | 小程序内搜索的收录规则（哪些页面允许被微信索引） |
| `页面.json` | 页面 | 覆盖全局 window 配置（标题、导航栏颜色、是否允许下拉） |

就近覆盖原则：页面配置 > 全局配置。这和[Spring 的配置优先级](/java/spring/spring-boot/)是同一种设计思路。

## 六、宿主环境：微信提供了什么

宿主环境 = 程序赖以运行的环境。微信为小程序提供四层能力：

1. **通信模型与运行机制**：启动时下载代码包 → 解析 `app.json` → 注册 App → 注册全部页面；页面渲染 = 加载四件套 → 发送初始数据给渲染层 → 渲染层拼装 WXML + WXSS 出界面。
2. **组件**：view（容器）、scroll-view（滚动区）、swiper（轮播）、text（可选中文本）、rich-text（富文本）、button（比 HTML 多开放能力：获取手机号、分享等）、image（mode 裁剪缩放模式九选一）等。
3. **API 三大类**：事件通知（`wx.onXxx/wx.emit`）、同步（`Sync` 结尾，如 `wx.getStorageSync`）、异步（默认回调式，支持 promise 化——除个别 API 外，不传 success/fail 回调即返回 Promise）。
4. **限制**：无 DOM/BOM、包体积限制（主包 2MB，整包 20MB+，见[分包](/frontend/miniprogram-component/)）、网络请求必须 HTTPS 白名单域名。

## 七、从开发到上线：版本流程

```
开发者工具上传 → 开发版本 → 提交审核 → 审核版本 → 发布 → 线上稳定版本
                     ↓ 体验版二维码（给产品/测试）
```

- **成员管理**：后台可配运营者/开发者/数据分析者三种角色，体验成员单独管理——体验版只有项目和体验成员能扫。
- **发布后**靠小程序码推广（比普通二维码识别性好、可带参数），运营数据后台和 `wx.getAnalytics` 两条渠道可查。

这套版本语义（开发/体验/审核/线上）和后端的「环境分层」完全同构，团队协作时按[发布流程](/frontend/release/)走即可。

## 八、面试问答

**Q: 小程序为什么没有 DOM 操作？**
双线程架构下 DOM 在渲染层 WebView，JS 在逻辑层 JsCore，物理上够不着；平台刻意如此——防 XSS 类攻击、渲染不受 JS 卡顿影响、渲染 diff 由框架统一优化。替代方案是 `setData` 数据驱动的声明式渲染。

**Q: setData 为什么慢？怎么优化？**
慢在「序列化 → Native 中转 → 渲染层 diff」的跨线程链路。优化三则：一次 `setData` 批量合并、按路径精准更新（`'list[2].name'`）、纯展示数据用 WXS 在渲染层算，不过桥。

**Q: 小程序和 H5 的区别？**
宿主不同（微信 vs 浏览器）、线程模型不同（双线程 vs 单线程）、能力来源不同（微信组件与 API vs Web 标准）、入口不同（扫码/搜索 vs URL）。uni-app 这类框架解决的是「一套代码同时出小程序和 H5」的问题（见[uni-app 核心](/frontend/uniapp-core/)）。
