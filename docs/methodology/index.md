# 方法论 · 板块导览

先说清这个板块**不做什么**：

- 不重复**架构演进的两条主线**（数据侧的 V1~V4、应用与部署侧）——那是[架构演进地图](/projects/architecture-evolution/)的内容，本篇在拆分与部署形态处与它交叉引用；
- 不重复**分布式事务的机制与实现**（TCC / Saga / Seata / 本地消息表）——见[分布式事务](/java/spring/spring-cloud/transaction)；
- 不重复**消息中间件的投递语义与顺序机制**（Kafka 分区、RocketMQ 队列、副本）——那是[消息队列](/middleware/)的内容；
- 不重复**设计模式的实现细节**（适配器、外观、观察者）——见[Java 设计模式](/java/design-patterns/)；
- 不重复**可验证产出的写法模板**（ADR / 压测报告 / 架构图）——那是[产出工具](/projects/toolkit/)的内容。

这里讲的是**设计方法本身**：怎么把复杂业务划成边界、边界之内用什么元素建模、边界之间怎么组织依赖、边界在什么条件下才配演化成独立服务、跨边界的一致性靠什么达成、以及怎么让这一套在真实工程里不烂尾。这些内容**与语言和框架无关**，所以它属于底座层。

## 一、一条主线：边界先于模型，模型先于形式 {#thread}

方法论的所有内容可以压成一句话：**先把边界划对，再在边界内把规则放对位置，最后才谈代码长什么样。**

```text
① 边界（战略设计）          谁和谁不是一回事  →  DDD 战略设计
        ↓ 边界定了，才知道在哪建模
② 模型（战术设计）          规则应该放在谁身上  →  DDD 战术设计
        ↓ 模型定了，才知道依赖该往哪个方向指
③ 形式（架构风格）          目录与 import 的方向  →  架构风格
        ↓ 边界稳了，才谈要不要独立部署
④ 部署（拆分粒度）          一个进程还是 N 个进程  →  拆分粒度
        ↓ 拆了之后，一致性怎么来
⑤ 一致性（事件与 CQRS）      跨边界怎么达成一致  →  事件驱动与 CQRS
        ↓ 以上全部
⑥ 落地（改造与反模式）       怎么不被现实打败  →  落地与反模式
```

**这条顺序不能颠倒，这是本板块最重要的一条结论。**

| 颠倒的后果 | 说明 |
|---|---|
| 先定形式，再想边界 | 得到"目录很整齐但到处共享库"的伪架构——**形式上的六边形，实质上的大泥球** |
| 先拆服务，再想边界 | 得到**分布式单体**：拆的成本付了，收益为零，还多了一堆分布式一致性问题 |
| 先上事件驱动，再想一致性需求 | 把强一致的地方也改成最终一致，用复杂性换来了正确性下降 |

> **判断顺序是否被颠倒的一个问法**：**"这次改动之后，哪些代码必须一起改？"** 如果答案里出现了"跨模块/跨服务的一大堆"，那无论目录多漂亮，边界都是错的。

## 三、三条贯穿判据 {#criteria}

七篇的主题各不相同（建模、依赖、部署、事件、改造、算账），但有三条判据反复出现——**它们可以直接当评审问题用**：

**① 「语言的边界在哪？」**

战略设计用它划边界（一词多义处即边界），战术设计用它决定规则归属（规则属于哪个模型），落地篇用它判断是否只在换皮：

```text
读法：把相关的类名、方法名、字段名连起来读
  能读出一段业务规则        → 语言迁移成功
  只能读出"设置某某字段"     → 只换了形式，没换方法
  同一个词在两处含义不同     → 这里就是边界，或这里就该改词
```

**② 「依赖朝哪个方向指？」**

架构风格用它判断是不是真六边形，拆分粒度用它判断是不是分布式单体，落地篇把它变成 CI 里的断言：

```text
读法：只看 import
  领域层 import 了基础设施层   → 依赖反了，退化成普通分层
  服务 A 的接口返回服务 B 的领域对象 → 模型边界破了
  两个上下文共享一张表        → 边界是假的（最明确的信号）
```

**③ 「这个决策的代价算过吗？」**

方法论的每一次选择都有对称的代价。**没有代价的选择通常是没想清楚的选择：**

| 决策 | 收益 | 必须接受的代价 |
|---|---|---|
| 引入 DDD 建模 | 复杂业务规则可维护 | 学习成本 + 建模时间 + 需要业务方持续参与 |
| 上整洁架构 / COLA | 边界由编译期或测试守护 | 层数与转换代码增加，小项目是纯成本 |
| 拆成微服务 | 独立部署与伸缩 | 运维、调试、一致性、发布协调、组织成本 |
| 读写分离（CQRS） | 查询性能与模型纯净 | **最终一致**——它是产品问题不只是技术问题 |
| 事件溯源 | 完整审计、可回放、可重算 | 查询困难、版本演进、必须快照、团队门槛 |

> **可操作的做法**：评审时对每个架构决策追问三句——**收益是什么（用哪个指标衡量）？代价是什么（谁承担）？如果它错了，怎么退回去？** 第三句最容易被跳过，也最重要：**没有退路的架构决策不是决策，是赌博。**
>
> 这三句话的**量化版本**见[技术成本与 ROI](/methodology/tech-cost-roi)——那一篇把「收益 / 代价 / 退路」换成了**单位成本、隐性成本的显性化、以及退出成本**。方法论给你判据，那一篇给你账。
