# 对账与补偿：跨系统以谁为准

[接口幂等](/java/spring/spring-cloud/idempotency)解决的是**同一请求不要做两次**。对账解决的是**做完之后，两边的事实是否还一致**。两件事常被揉成一句「最终一致」，于是系统上了重试和唯一索引，账仍然平不了——因为没有人回答「以谁为准」。

分布式事务、Seata 四种模式、Kafka 副本，本篇不复述。它们回答「怎么尽量一起成功」；本篇回答「**没有一起成功时，以哪边为真相、差在哪一类、怎么收回来**」。能不用分布式事务硬拧的，本篇优先不拧——判据见[分布式事务](/java/spring/spring-cloud/transaction)。

> **主线：最终一致不是时间的函数，是对账闭环的函数。**
>
> 没有「以谁为准」，补偿就是在两个错误之间加减。没有差账分类，所有差异都会被当成「再试一次」。没有窗口，你会把正常延迟当成事故，或把事故当成延迟。

## 一、问题场景：幂等绿了，账不平 {#why}

| 现场 | 幂等已经保证了什么 | 对账要回答的 |
|---|---|---|
| 支付成功回调处理了一次，订单仍是待支付 | 回调没被处理两次 | **资金侧已收钱，订单侧没落状态**——少记 |
| 库存扣了两次，消息只投了一条 | 消费端去重键在 | **库存侧多扣，订单侧一笔**——多记，去重键可能不在库存这条链上 |
| 审批通过，站内信没有 | 事件没重复发 | **源有、投影无**——同步漏了 |
| 两边笔数相同，金额差一分 | 请求级幂等无用 | **状态分叉或口径分叉**——不是重试能修的 |

第四种最危险：监控上看「条数对齐」，业务上已经错了。所以对账不能只 count。

## 二、先定以谁为准 {#source-of-truth}

跨系统的每一对账本，必须先写死**真相源**。不定这一条，后面的补偿方向是随机的。

| 账本对 | 通常以谁为准 | 反例 |
|---|---|---|
| **资金 / 支付** | **资金事实**（渠道对账单、支付单终态） | 以本系统订单为准去「冲」渠道——渠道不会认 |
| **下单 / 库存** | **订单已支付成功**为业务事实；库存是派生 | 以库存缓存为准把已支付订单取消 |
| **消息 / 业务库** | **业务库本地事务已提交**（发件箱） | 以 Broker 积压为准认为「已经处理」 |
| **源系统 / 同步副本** | **源系统**（HR、支付渠道、主库） | 以 ES / 数仓为准回写源 |
| **写模型 / 读模型（CQRS）** | **写模型**；读侧可重放 | 在读库上改一笔当修复 |

> **判据：谁不能被你的补偿代码改写，谁就是真相源。** 渠道对账单、监管报送、用户已经看到的扣款短信，通常改不了；你的投影、缓存、消息积压，通常可以重放或冲正。

消息作为「发生过什么」的日志时，可以当**审计源**，仍不要当资金事实。事务消息与发件箱只保证「事件相对本地事务不丢」，不保证下游已经与上游同数——见[事件驱动 · 发件箱](/methodology/event-driven-cqrs)与 [RocketMQ 事务消息](/middleware/rocketmq/#transaction)。

## 三、差账分类：先定性再动手 {#classes}

发现不一致，先归到下面四类。类错了，手段就错。

| 类 | 含义 | 典型证据 | 第一反应 |
|---|---|---|---|
| **少记** | 真相源有，本侧无 | 渠道成功、本地无单；源表多一行 | **补**（重放 / 补单），不要先冲真相源 |
| **多记** | 本侧有，真相源无 | 本地已扣、渠道失败或未达；投影多一行 | **冲正或作废本侧**，不要再向下游重试加码 |
| **状态分叉** | 两边都有，终态打架 | 一方 PAID 一方 CLOSED | **按真相源改本侧状态机**；禁止两边各改一半 |
| **口径分叉** | 条数对、金额或维度不对 | 含税 vs 未税、时区、已取消是否计入 | **先统一口径**，再谈补数；补数解决不了定义 |

绩效系统里「数量 / 摘要 / 字段」三档，是**怎么发现**；本表是**发现之后怎么定性**。检测方法可以继续用[对账三档](/projects/perf-system/org-sync-100k/#three-checks)和[数仓对账](/projects/property-saas/data-warehouse/#reconciliation)，本篇不重写哈希分片怎么算。

## 四、收敛手段 {#converge}

定性之后，只允许这几类动作。**重试不是对账手段**——重试面向「同一请求尚未确认」；对账面向「两边已经各自落账」。

| 手段 | 适用 | 前提 | 禁止 |
|---|---|---|---|
| **重放** | 少记、读模型落后 | 消费幂等；事件可重放；按真相源顺序 | 对非幂等写无脑重放 |
| **冲正** | 多记、本侧多出来的终态 | 冲正单本身幂等；有业务凭证 | 用删除行冒充冲正（审计没了） |
| **人工工单** | 状态分叉说不清、金额级、超窗口 | 有 owner、有时限、有验收信号 | 「先手工改库再说」且不留单 |
| **停止补偿、升故障** | 同一位置连续 N 次同类差异 | 阈值事先写死 | 每天补偿同一批差异把指标刷绿 |

后一条与组织同步的纪律相同：补偿只能用于偶发。系统性差异被补偿抹平，等于把 bug 养在对账任务里。见[对账纪律](/projects/perf-system/org-sync-100k/#reconciliation)。

**不要靠分布式事务硬拧的信号**：

- 两个系统不属于你（支付渠道、监管、对方公司的主数据）；
- 长事务会把热点锁在协调器上；
- 失败模式需要「认一笔、冲一笔」，而不是「全成或全不成」。

这些场景里，本地事务 + 消息 + 幂等 + **本篇的对账闭环**，比引入 TCC/Saga 更可运维。机制对照仍回[分布式事务](/java/spring/spring-cloud/transaction)。

## 五、窗口、滞后与「看起来平了」 {#window}

对账必须带**时间窗口**，否则正常延迟与事故无法区分。

| 概念 | 作用 |
|---|---|
| **滞后容忍** | 源提交后 T 秒内，副本落后不算差账（同步延迟、投影延迟） |
| **对账窗口** | 只比对「窗口左端已经过了滞后」的数据，避免把飞行中的请求当少记 |
| **收敛时限** | 窗口内必须被重放/冲正/工单之一收口；超时升故障 |
| **冻结点** | 日切 / 结算以某个绝对时间为准，之后进入该日的差账不再用「再等一会儿」搪塞 |

CQRS 读库、数仓 ODS、搜索索引，都是「允许滞后的副本」。产品上要能解释「改完为什么还看到旧值」；对账任务不要在滞后窗口里报警，否则值班会关掉任务。

审批推送那种「实例状态应由节点状态推导、不要两处各写一份」——能从结构上消灭的差账，优先消灭，而不是加对账。见[审批推送](/projects/perf-system/approval-push/)。能消灭却去对，是在给设计失败发津贴。

## 六、一条可画出来的闭环 {#loop}

```
真相源（渠道 / 主库 / 写模型）
    │  周期抽取或事件
    ▼
比对（窗口内：条数 → 关键金额/状态 → 抽样字段）
    │
    ├─ 平          → 记录「对过」，不要省略
    ├─ 少记        → 重放 / 补单（幂等）
    ├─ 多记        → 冲正 / 作废
    ├─ 状态分叉    → 按真相源打状态机；说不清 → 工单
    └─ 口径分叉    → 停补偿，改定义
    │
    ▼
同一位置连续 N 次 → 停止补偿，当故障（进[复盘](/projects/toolkit/postmortem/)）
```

画不出来这条环，就还没有「最终一致」，只有「我们用了 MQ」。

## 七、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 幂等和对账差在哪？ | 幂等管**同一请求做多次结果不变**；对账管**做完之后两边事实是否一致**。只做前者，账仍可能不平 |
| 2 | 跨系统以谁为准？ | **谁不能被你的补偿改写，谁就是真相源**。资金看渠道，同步看源系统，CQRS 看写模型 |
| 3 | 差账有哪几类？ | 少记、多记、状态分叉、口径分叉。先定性再选重放 / 冲正 / 改口径 / 工单 |
| 4 | 条数对了为什么还要抽字段？ | 少一笔多一笔会抵消；口径分叉在 count 上是平的 |
| 5 | 补偿能不能当修复？ | **偶发可以，系统性不行。** 同一位置连续 N 次差异要停补偿、升故障 |
| 6 | 为什么不能用分布式事务替代对账？ | 渠道和对方主数据你改不了；长事务锁热点。最终一致靠闭环，不靠协调器硬拧 |
| 7 | 对账窗口是什么？ | 把正常滞后排除在差账之外，并给收敛时限。没有窗口，不是误报就是漏报 |
| 8 | 读模型落后算故障吗？ | 滞后容忍内不算。超时未收敛才算。产品上要能解释「为什么刚改完还是旧值」 |
| 9 | 消息能不能当真相源？ | 可当审计日志，不当资金事实。发件箱只保证相对本地事务不丢 |
| 10 | 怎么证明有对账闭环？ | 能画出：真相源 → 窗口内比对 → 分类动作 → 连续差异升故障。画不出就还没有最终一致 |
