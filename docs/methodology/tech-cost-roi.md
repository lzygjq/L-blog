# 技术成本与 ROI：把技术目标换算成一本账

> **架构师会算「要多少台机器」，负责人要算「这些机器值不值」。** 这两笔账之间的换算，就是这一篇。

[容量测算与压测方案](/projects/property-saas/capacity-and-perf/#derivation)那一篇已经给出了一条从业务量推导到机器数的链路，六步、每一步可被质疑——**它是本站最接近「算账」的一篇**。但它算出来的是**资源数**，不是**金额**。

这一篇做两件事：**把那条链延伸成成本链**，以及**把「值不值」变成一个可以被质疑的数字**。

## 一、为什么技术人算账总是算不准 {#why}

不是数学不好，是**成本这个东西天生就不服从技术人的直觉**。三个特性：

| 特性 | 表现 | 后果 |
|---|---|---|
| **不可直接归因** | 一次改动可能同时影响时延、可用性、人力、云账单 | 单点优化的收益经常被系统性成本吃掉 |
| **非线性** | 机器数不是「业务量 ÷ 单机能力」——有冗余、跨区、峰值、协议开销 | 按线性外推的预算，通常低估 2~3 倍 |
| **延迟显现** | 省下的技术债、省掉的监控、压掉的测试，账单在 2~4 个季度后才到 | **决策时看不见的成本，等于不存在** |

**还有一处更根本的不对称**：ROI 的**分母（投入）是确定的**——预算表上有数；而**分子（收益）是估算的**，且往往是别人（业务）给的假设。于是「这个项目 ROI 是 3」这个结论，**它的可信度基本等于分子假设的可信度**。

**所以第一条专业素养是：任何成本收益结论，都要同时给出「这个模型在什么条件下不成立」。** 这一节最后会专门讲怎么做到这一点（第八节）。

## 二、成本的四层结构：看得见的只有前两层 {#four-layers}

| 层 | 内容 | 在谁的预算表里 | 常被低估的原因 |
|---|---|---|---|
| **① 人力** | 研发、测试、运维、SRE、管理分摊 | ✅ 明确 | 通常只算「做这件事要几个人」，不算「维护它要几个人」 |
| **② 云资源** | 计算、存储、网络、数据库、中间件、可观测 | ✅ 明确 | 只算稳态，不算峰值、跨区、流量费、快照与备份 |
| **③ 软件与许可** | 商业组件、数据库许可、SaaS 订阅、支持服务 | ⚠️ 分散 | 分散在各团队，无统一视图；**随规模涨价**（按核/按节点计费） |
| **④ 隐性成本** | 协调、上手、技术债利息、机会成本 | ❌ **基本不可见** | 没有科目可记，于是被认为不存在 |

**第 ④ 层是 L4 与 L3 的真正分界。** 举三个具体例子：

```
协调成本：服务从 8 个变成 40 个之后，
          一次跨服务变更的平均协调人数从 2 变成 7
          → 这笔钱记在「人力」里，但没人知道它是因为服务数涨的

上手成本：新人达到可用状态的时间从 3 周变成 3 个月
          → 记在「招聘与培养」，但根因是架构复杂度

技术债利息：返工占研发产能的比例
          → 记在「研发投入」，完全不单列（见[研发效能度量](/cloud-native/cicd/engineering-metrics#beyond-dora)）
```

> **一个可操作的做法**：做技术方案对比时，**在第①②层之外强制写一行「它会让哪些第④层成本变化」**。哪怕只是定性写「运维对象从 3 个变 12 个」，这句话在评审里就有否决权——**很多方案的真正代价从来不是钱，是复杂度，而复杂度最终会变成钱。**

## 三、从业务量到金额：六步成本链 {#cost-chain}

这是本文的核心工具。它把[容量测算那条链](/projects/property-saas/capacity-and-perf/#derivation)**向右延伸一格**——从「多少台机器」延伸到「多少钱」：

| 步 | 容量链（已有） | 成本链（本步新增的问题） |
|---|---|---|
| **1. 业务量** | DAU、峰值 QPS、数据增长 | 业务量是**按什么维度**算的？（用户 / 订单 / 租户 / 请求） |
| **2. 单请求消耗** | 单次请求的 CPU / 内存 / IO | **单请求成本**：它由哪些资源项构成？哪些与量成正比、哪些是固定分摊？ |
| **3. 资源数** | 实例数、规格、副本 | 资源**规格**怎么选？（规格选错比数量算错更贵） |
| **4. 冗余与峰值** | 冗余系数、峰值系数 | **冗余也是有价格的**：多副本、多可用区、多机房的溢价是多少 |
| **5. 计价方式** | —— | 按量 / 预留 / 节省计划 / 竞价，**各自锁定多少量、省多少、风险是什么** |
| **6. 金额与单位成本** | —— | **月总额 + 单位成本**（每千次调用 / 每租户 / 每单） |

**这条链的价值不在算得准，而在每一步都可以被质疑。** 第 2 步的「单请求消耗」如果拿不出数据，就要**明确标成假设**；第 5 步的「预留多少」如果没把握，就要**写清楚锁定风险**。

```
一个能通过评审的成本结论长这样：

  业务量假设：峰值 QPS 800（来源：容量测算第 1 步，依据历史峰值 ×1.6 增长）
  单请求成本：¥0.00031 / 次（来源：压测实测 + 资源单价反算，误差 ±20%）
  月成本估算：¥24.8 万（含冗余 ×1.5、多可用区溢价 ×1.3）
  其中固定部分 ¥9.2 万（不可随量下降）
  模型不成立的条件：若峰值 QPS 低于 300，冗余系数应降为 1.2，
                    该模型高估约 ¥4 万/月
```

> **最后一行是这份文档最值钱的部分。** 没有它的成本估算，在评审里只是一串数字；有了它，评审可以讨论**假设是否合理**——**这才是评审该讨论的东西。**

## 四、单位经济学：唯一能和业务对话的口径 {#unit-economics}

**「这个月云花了 80 万」这句话在业务侧没有意义**——业务涨了成本涨是健康的，业务降了成本还涨才是问题。**总量不是指标，比例才是。**

| 口径 | 算法 | 它回答什么 |
|---|---|---|
| **每单成本** | 月总成本 ÷ 月订单数 | 规模上去之后，单位成本有没有下降？ |
| **每租户成本** | 月总成本 ÷ 活跃租户数 | 多租户 SaaS 最核心的健康指标 |
| **每千次调用成本** | （可变成本部分）÷ 调用量 | 边际成本是否可控 |
| **每活跃用户成本** | 月总成本 ÷ MAU | 与获客成本并列看，判断商业模式成立性 |

AI 的单位换成每千次 / 每座席 / 每成功任务，重试与长上下文必须进分母，见[AI 治理 · 账单](/ai/governance/#bill)。

**三个必须分清的概念：**

| 概念 | 含义 | 用错会怎样 |
|---|---|---|
| **平均成本** | 总成本 ÷ 总量 | 看起来在下降，但可能只是因为固定成本被摊薄 |
| **边际成本** | 多服务一个单位**额外**增加的成本 | **定价的依据**——低于边际成本卖一单，卖得越多亏得越多 |
| **固定成本** | 不随量变化的基线（多可用区、冗余、基础可观测） | 决定「业务量要多大才养得起这套架构」 |

**关键判据**：**单位成本随规模上升还是下降？**

```
健康：业务量 +80%，总成本 +35%  → 单位成本下降（有规模效应）
警戒：业务量 +80%，总成本 +85%  → 单位成本基本持平（架构没有规模化优势）
危险：业务量 +80%，总成本 +130% → 单位成本上升（某个环节是线性甚至超线性的）
```

**最后一种情况通常有具体病灶**：按租户建库的架构在租户数上千后会因基数增长而成本暴涨；按核计费的商业数据库在扩容时不受折扣；跨区流量费随着服务数增长呈 N² 关系。

> **对 L4 的意义**：单位成本曲线是**架构决策的长期反馈**。当它开始上升，说明架构到了该换的临界点——**这个信号比任何技术指标都更适合向上沟通**，因为它用的是财务语言。

## 五、云成本优化：顺序比手段更重要 {#cloud-optimization}

云上的成本优化手段就那么几种，**但顺序错了会白干甚至反效果**。

### 5.1 FinOps 三阶段

| 阶段 | 目标 | 主要动作 |
|---|---|---|
| **Inform**（看清） | 让成本可归因、可预测 | 标签规范、成本分摊（showback/chargeback）、异常检测、单位成本 |
| **Optimize**（优化） | 消除浪费、降低费率 | 规格调整、清理孤儿资源、承诺折扣、竞价实例、存储分层 |
| **Operate**（持续） | 把成本变成工程常态 | 预算与策略自动化、定期复盘、把成本纳入设计评审 |

三个阶段是**循环**，不是一次性项目。顺序不能颠倒：**没有 Inform 就做 Optimize，你砍掉的可能是有用的东西。**

### 5.2 优化手段按「可省空间 / 风险」排序

| 优先级 | 手段 | 典型幅度 | 前提与风险 |
|---|---|---|---|
| **① 清理浪费** | 孤儿资源（未挂载的盘、闲置 IP、停摆实例）、非生产环境 7×24 运行 | 先做，无风险 | 需要资产视图；**非生产环境定时关停是最高性价比的一步** |
| **② 用量优化** | 规格调整（长期低利用率就降配） | 单资源 30%~50% | 必须看**持续**利用率，不能看瞬时峰值；留足峰值余量 |
| **③ 费率优化** | 预留实例 / 节省计划 | **30%~72%**（视期限与预付） | **会锁定用量**——用量降了照样付钱 |
| **④ 竞价/抢占实例** | 容错型工作负载 | 最高 **90%** | 需要工作负载可中断（批处理、CI、离线计算） |
| **⑤ 存储生命周期** | 冷热分层、归档 | 视访问模式，可达数倍差异 | 需要真的了解访问模式，否则检索成本反超 |
| **⑥ 架构级优化** | 容器化、Serverless、缓存、并发模型 | 量级最大 | 周期最长，属于 L3 的活 |

**三条顺序原则：**

1. **先用量（usage），再费率（rate）。** 如果先买三年预留再去优化规格，**你会发现锁定的规格根本不该用**——锁定的是错误的用量。
2. **承诺折扣只覆盖「确定性基线」。** 承诺利用率维持在 80% 左右是常见目标——**买满会浪费，买少了没省到。**
3. **不要为省成本牺牲可观测性。** 这是最隐蔽的一处：砍掉监控与日志看起来立竿见影，代价是**下一次故障的定位时间翻倍**——而故障成本的量级远大于监控账单。

> **行业普遍数字**：缺乏成熟治理的组织，云支出中有 **30%~35% 属于浪费**（闲置、过量配置、孤儿资源、非生产环境常开）。**所以「先清浪费」几乎总是第一步，而且它不需要承诺任何东西。**

## 六、自建 vs 采购：TCO 要用同一个口径算 {#build-vs-buy}

这是 L4 最常被要求拍板的一类决定，也是最容易算错的一类——**因为两边的成本结构不同，而人们习惯只把自己看得见的那部分列出来。**

| 成本项 | 自建 | 采购 / SaaS |
|---|---|---|
| 一次性 | 设计、开发、集成 | 实施、集成、数据迁移 |
| 持续·人力 | 研发 + **运维 + 演进 + 值班** | 少量对接人力 |
| 持续·资源 | 服务器/云、许可 | 订阅费（**通常随规模涨价**） |
| 持续·隐性 | 上手成本、**关键人依赖** | 集成复杂度、能力受限于产品 |
| 风险 | 做不出来、做出来没人维护 | **锁定**、涨价、服务终止、合规责任划分 |

**四条对比规则：**

1. **对比周期要一致，且长到能看出差异。** 三年期比一年期更接近真相——**自建的成本曲线是先高后低，采购是先低后高**（订阅费随规模线性上涨）。用一年期对比，几乎总是采购赢。
2. **自建方必须把「维护」算进去。** 最常见的低估是**只算开发成本，不算此后每年 20%~30% 的维护与演进**。
3. **采购方必须把「退出成本」算进去**（见下）。
4. **两边都要算「关键人/关键供应商风险」。** 自建的风险是「只有一个人会改」，采购的风险是「只有一家供应商能供」。

### 6.1 退出成本的算法

**这是一个必须在签约前算清楚的数字**，也是 L4 面试里最常被追问的一题：

```
退出成本 = 数据迁移成本（导出、清洗、校验、回灌）
         + 替代方案的引入成本（选型、实施、并行期）
         + 并行运行期的双份成本
         + 业务中断与学习曲线成本
         + 合同约束成本（提前终止条款、最低消费）
```

**判断锁定的两个问题：**

- **「数据能不能完整、可理解地导出？」** —— 能导出但**字段含义只有供应商知道**，等于不能退出。
- **「退出需要多久、期间业务怎么运行？」** —— 需要停机三个月才能重的方案，实际锁定强度极高。

> **对 L4 的判断**：**锁定本身不是问题，锁定程度与议价能力才是。** 核心系统选一个便宜的方案但被深度锁定，通常比贵一倍但可替换的方案更危险——因为**第二年的价格不由你决定**。模型供应商还要带走提示词、评测集与微调件，见[AI 治理 · 退出](/ai/governance/#exit)。

## 七、技术债的量化：把「欠债」变成数字 {#tech-debt}

技术债最麻烦的地方是**它无法进入预算表**——没有科目，就争不过有新功能的需求。**量化的意义不是为了精确，是为了让它有一张入场券。**

一个够用的模型：

```
技术债利息 = 每次改动的额外成本 × 改动频率

  每次改动的额外成本 = 额外工时（对比「如果是干净架构要多久」）
  改动频率 = 这条链路上每年会发生多少次需求变更
```

**为什么用「利息」而不是「总额」**：技术债的总额几乎无法估算（也没人信），但**利息是可以被感知的**——开发同学成天抱怨「这块改一下要动五个地方」，那就是利息在发生。

**偿还节奏的三条判据：**

| 判据 | 说明 |
|---|---|
| **只还「高频高息」的债** | 三年没改过的模块，重构收益接近零；**决定债务价值的是改动频率，不是代码有多丑** |
| **随需求顺带还，而不是单独立项** | 单独立项的重构在排期上永远排在需求后面；**「改这块功能时顺手把它收拾了」是唯一稳定的偿还方式** |
| **先加护栏，再谈重构** | 在还完之前，先用架构断言/测试把边界守住，否则重构过程中会继续腐化 |

> **与[研发效能](/cloud-native/cicd/engineering-metrics)的衔接**：技术债利息在效能指标上的投影就是**返工率**。如果返工率持续高位，说明利息已经高到影响交付节律——**这时候「还债」不再是一个技术偏好，而是一个可被财务论证的投入。**

## 八、让数字可信：四条防自欺规则 {#credibility}

算账最危险的敌人不是算错，是**算出一个自己想看到的结果**。四条规则：

| # | 规则 | 违反后的典型表现 |
|---|---|---|
| 1 | **分子分母必须同口径** | 「投入」算增量人力，「收益」算全部产出——ROI 凭空翻倍 |
| 2 | **估算必须标不确定性** | 给出「节省 320 万」而不给区间和假设来源，无法被质疑所以必然被质疑 |
| 3 | **必须写「模型什么时候不成立」** | 只给结论不给失效条件，等于把风险转嫁给听的人 |
| 4 | **「省下的钱」不能直接算成收益** | 云账单降了 20%，不等于利润增加——**这笔钱要么被回收，要么必须明确再投入哪里** |

**规则 4 值得展开，它是企业里最常见的自欺：**

```
常见说法：「这个优化项目一年省 200 万」
真实情况：省下的 200 万如果留在部门预算里，会被花在别处；
          如果被财务回收，那它是「成本下降」，不是「收益」
正确说法：「年度运行成本下降 200 万（已由财务确认从下一年预算基数中扣除）」
```

**判断一个成本方案是靠论证还是靠包装，最快的办法是问一句**：

> **「如果这个方案的效果只有你预测的一半，我们会在什么时候、通过什么信号发现？」**

答不上来，说明这个方案没有反馈回路——**而没有反馈回路的投入，本质上是一次赌注。**

## 九、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 技术成本都包含哪些？最容易被漏掉的是什么？ | 四层：人力、云资源、软件与许可、**隐性成本**。最容易漏的是隐性成本——**协调成本**（服务数增长后单次变更的协调人数）、**上手成本**（新人达到可用状态的时间）、**技术债利息**。它们没有科目可记，所以被认为不存在，但它们最终都会转化为人力支出。 |
| 2 | 怎么把业务量换算成成本？ | 六步链：业务量 → 单请求成本 → 资源规格与数量 → 冗余与峰值溢价 → 计价方式（按量/预留/竞价）→ 月金额与单位成本。**这条链的价值不在精确，而在每一步都能被质疑**——容量测算篇给的是前几步，成本链补的是「计价方式」和「金额」两格。 |
| 3 | 为什么说「总量没有意义，单位成本才有」？ | 业务涨了成本涨是健康的，业务降了成本还涨才是问题。只有把成本除以某个业务量（每单、每租户、每千次调用）才能判断**规模效应是真有还是假有**：业务量 +80% 而成本 +35% 是健康，+130% 说明某环节是线性甚至超线性（常见病灶：按租户建库、按核计费、跨区流量费随服务数呈 N² 增长）。 |
| 4 | 云成本优化应该从哪开始？ | 顺序很重要：**① 清理浪费**（孤儿资源、非生产环境常开）——无风险、见效最快；**② 用量优化**（规格调整）；**③ 费率优化**（预留/节省计划，30%~72% 折扣）；**④ 竞价实例**；**⑤ 存储分层**；**⑥ 架构级优化**。**核心原则是先用量后费率**——先买预留再改规格，锁定的是错误的用量。行业普遍数字是**30%~35% 的云支出属于浪费**。 |
| 5 | 承诺折扣的风险是什么？ | **锁定用量**：用量降了照样付钱。所以它只应覆盖**确定性基线**，承诺利用率维持在 80% 左右是常见目标——买满会浪费，买少没省到。另一个坑是**顺序**：如果先锁三年再优化架构，锁定的规格可能根本不该用。 |
| 6 | 自建和采购怎么比？ | 四条规则：**对比周期要一致且足够长**（自建先高后低、采购先低后高，一年期对比几乎总是采购赢）；**自建必须算维护**（年 20%~30%，不是只算开发）；**采购必须算退出成本**；**两边都要算关键人/关键供应商风险**。判据不是「哪个便宜」，而是「**三年后的总成本与可替代性**」。 |
| 7 | 退出成本怎么算？ | 五项：数据迁移（导出、清洗、校验、回灌）+ 替代方案引入 + 并行期双份成本 + 业务中断与学习成本 + 合同约束成本。判断锁定的两个问题：**「数据能不能完整且可理解地导出」**（能导出但字段含义只有供应商知道 = 不能退出）、**「退出要多久、期间业务怎么跑」**。**锁定本身不是问题，锁定程度与议价能力才是。** |
| 8 | 技术债怎么量化？ | 用**利息**而不是总额：`每次改动的额外成本 × 改动频率`。总额几乎无法估算也没人信，利息是可以被感知的（开发抱怨「改一处要动五个地方」就是利息）。偿还的三条判据：**只还高频高息的**、**随需求顺带还而不是单独立项**、**先加护栏再谈重构**。它在效能指标上的投影是**返工率**。 |
| 9 | 怎么保证成本收益的测算不是自欺？ | 四条：**分子分母同口径**（投入算增量、收益也算增量）；**估算标不确定性**（给区间和假设来源）；**写清模型何时不成立**；**「省下的钱」不能直接算收益**（要么被回收要么明确再投入哪里）。最快的检验问法是：**「如果效果只有预测的一半，我们会在什么时候、通过什么信号发现？」**——答不上来说明没有反馈回路。 |
| 10 | 向业务讲技术投入，用哪套语言？ | **收入、成本、风险、时间**四个词，不用技术名词。具体的转换：不说「上了多级缓存」，说「**同样的服务器能撑的并发提升 4 倍，等价于推迟一次服务器扩容**」；不说「做了灰度发布」，说「**新版本出问题的爆炸半径从全量用户缩到 1%**」。**单位成本曲线与质量成本表**是两张最好用的沟通材料——它们本身就是财务语言。 |
