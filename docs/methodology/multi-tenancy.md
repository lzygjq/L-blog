# 多租户：隔离档位与上下文传播

「我们是不是多租户」是假问题。真问题是：**这一档隔离挡住了什么、漏了哪一个横切点、租户长大时升不升得上去。** 案例里的三级混合是一次取舍记录；本篇把可复用的判据抽出来。物业出账峰值、K8s 对象怎么写，不在这里——分别见[核心业务链路](/projects/property-saas/core-business/)与 [K8s 多租户](/cloud-native/kubernetes/#multi-tenant)。

> **主线：隔离强度按档买，上下文按点传。**
>
> 档位决定数据与计算放哪；横切点（缓存、消息、文件、异步、定时）漏一个，档位再高也会串租户。升档的前提是 L1 的数据模型里已经有干净的租户边界——没有这条，不是「以后再拆」，是永远拆不动。

案例中的约束与数字仍以[三级混合隔离](/projects/property-saas/microservice-to-k8s/#multi-tenant)为准；本篇只保留方法。

## 一、问题场景：共享成功了，串租户也成功了 {#why}

| 现场 | 库是隔离的吗 | 真正漏的 |
|---|---|---|
| A 租户读到 B 的缓存 | 表上有 `tenant_id` | Redis key 没带租户 |
| 定时对账把所有租户算进同一份 | 独立 Schema | 任务启动时没有租户上下文 |
| 大租户的报表把小租户接口打满 | 逻辑隔离 | 没有计算配额，**吵闹邻居** |
| 要升独立库，发现大量跨租户 join | 一开始图省事 | 边界一开始就不是租户 |

第四种会把「混合隔离」变成宣传：升档在结构上不可执行。

## 二、隔离是分档，不是是非 {#tiers}

三档足够做设计，不必发明第四种名字：

| 档 | 数据 | 挡住什么 | 挡不住什么 | 成本 |
|---|---|---|---|---|
| **共享库 + `tenant_id`** | 同行 | 无意识的交叉查询（若拦截器在） | 吵闹邻居、整库恢复、合规物理隔离 | 最低 |
| **独立 Schema** | 同实例不同库 | 误操作整表、按租户备份 | 实例级资源争抢、内核级逃逸 | 中 |
| **独立库 + 独立部署** | 实例级 | 邻居流量、独立升级节奏、多数合规口径 | 控制面仍可能共享（集群、账号体系） | 最高 |

**混合的意义是租户会长大**：新租户进共享档，到体量 / 合规 / 按租户恢复这些阈值再升。**分档能落地的前提，是共享档已经按租户切开了模型和任务。** 否则所谓升级是一次数据工程，不是配置。

| 决策倾向共享 | 决策倾向升档 |
|---|---|
| 租户多、单个小、成本敏感 | 单个租户体量大、或要按租户恢复 |
| 无物理隔离合规要求 | 合同或等保要求数据物理隔离 |
| 无定制版本 | 要独立配置甚至独立发布节奏 |

编排层的对应关系（共享 Namespace / 独立 Namespace+网络策略 / 独立集群）见 [K8s 多租户](/cloud-native/kubernetes/#multi-tenant)。**数据库分开但应用还混在一个 Deployment 里，等于档位只买了一半。**

共享档必须守住：**租户过滤不能靠人记得写。** MyBatis 拦截器或等价物在 SQL 拼装期注入条件，跨租户查询走显式白名单。这条在案例里写过，方法上它是唯一可审计的默认。

## 三、横切点：漏一个就串 {#context}

档位解决「数据放哪」。**当前请求属于谁**是另一件事，事故多发生在这里：

```
HTTP ──▶ 解析租户 ──▶ TenantContext
                          │
     同步调用 / 异步池 / 消息 / 定时 / 缓存 / 文件 / 检索
```

| 点 | 漏了会怎样 | 最低做法 |
|---|---|---|
| **HTTP / RPC** | 没进上下文，后面全凭参数 | 从令牌或网关头取，**禁止前端随便传 tenantId 当权威** |
| **异步 / 线程池** | 子线程 MDC 和租户一起丢 | 装饰器传递；与[应用日志 MDC](/java/spring/spring-boot/logging#mdc)同一类断点 |
| **消息** | 消费时没有租户，写入默认库 | 消息体或头带租户；消费入口第一件事恢复上下文 |
| **定时任务** | 一次扫全表 | 按租户分片调度，或任务参数带租户 |
| **缓存** | key 撞车 | key 前缀或独立前缀空间；本地缓存按租户分区 |
| **文件 / 对象存储** | 路径撞车或 ACL 共用 | 路径含租户；签名不要跨租户可猜 |
| **检索 / RAG** | 搜到别人的文档 | 元数据强制过滤，见 [Spring AI · RAG](/ai/spring-ai/#rag) |

测试上的最低断言：两个租户各插一条，交叉查询不可见。这不是测试岗的事，是[可验证性](/java/testing/)里架构必须留下的绿灯。

## 四、吵闹邻居 {#noisy-neighbor}

逻辑隔离默认分享 CPU、连接池、线程池、带宽。一个租户的慢报表或导入，会把共享档的所有人拖进同一条 P99。

| 手段 | 作用 | 不够的时候 |
|---|---|---|
| **按租户限流 / 配额** | 把「一个租户能吃多少」写成数 | 仍在同一池里排队 |
| **连接池 / 线程舱壁** | 按租户或按档隔离并发上限 | 虚拟线程下更要显式上限，见[出站超时 · 两套池](/java/spring/spring-framework/crosscutting/outbound-http#pools) |
| **把吵的租户升档** | 用独立部署买隔离 | 升档不可执行时，只能限流或拒绝新功能 |

容量不要只算总数。画像分档之后，基线按「最大那一档在共享池里能吵到什么程度」来配，而不是按平均值——案例里的算法见[容量测算](/projects/property-saas/capacity-and-perf/)，本篇只保留这条判据。

## 五、升级路径与灰度单元 {#upgrade}

升档是迁移，不是改配置：

```
共享库  →  独立 Schema  →  独立库/独立部署
   │            │                │
 双写+对账    双写+对账         流量按租户切
```

纪律与[扩展-收缩](/cloud-native/cicd/rollback-and-migration#expand-contract)相同：一次只加不减，对账窗口内两边可核对，再切读、再停写旧档。对账以源档为准还是以新档为准，要在切流前写死，方法见[对账 · 以谁为准](/methodology/reconciliation#source-of-truth)。

**灰度以租户为单元，不要以随机百分比切共享档里的行。** 一个租户的用户必须看到同一版拓扑；按请求百分比会把同一租户劈开，差账和缓存会一起炸。发布策略的其余部分不在本篇。

## 六、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 多租户是不是「做或不做」？ | **不是。** 是隔离档位：共享库 / Schema / 独立库，按体量、合规、恢复、成本选 |
| 2 | 为什么要混合而不是一档打天下？ | 租户会长大。共享接得住小的，升档接得住大的和合规；前提是共享档模型已经按租户切开 |
| 3 | 共享库最容易漏的是什么？ | **靠人记得写 `tenant_id`。** 必须在框架拦截层默认注入，跨租户走白名单 |
| 4 | 库隔离了为什么还会串？ | 缓存、消息、文件、异步、定时这些横切点没带租户 |
| 5 | tenantId 能不能让前端传？ | **不能当权威。** 从鉴权上下文取；前端可传只用于展示切换，服务端必须校验归属 |
| 6 | 什么是吵闹邻居？ | 逻辑隔离下，一个租户吃光共享的 CPU / 池 / 带宽。用配额、舱壁或升档 |
| 7 | 数据库独立了应用还混部行不行？ | **档位只买了一半。** 独立库应对独立部署与配额 |
| 8 | 升档为什么会失败？ | 一开始就有跨租户 join、全局表、无租户的定时任务——结构上不可迁移 |
| 9 | 灰度为什么按租户切？ | 同一租户必须落在同一版拓扑，否则缓存与对账一起分叉 |
| 10 | 怎么证明没串租户？ | 两个租户各写各读的集成测试必须绿灯；再加横切点清单（缓存/消息/文件/异步/定时）逐项有租户 |
