# DDD 战术设计：聚合是事务边界，不是对象分组

> **口径说明**：本文是方法论梳理，代码片段是**示意**而非可直接运行的工程代码，仅用于说明结构与依赖方向。不含企业标识与客户信息。

战略设计定了边界，战术设计解决"边界之内怎么写"。但战术设计在国内被误用得最厉害——**聚合被当成"把相关的表包在一起"**，值对象被当成"没有主键的表"。这一篇按元素逐个澄清，并给出可评审的清单。

## 一、先分清四种模型元素 {#elements}

DDD 的战术元素不多，但分界极清晰。**判据只有两个问题：有没有身份？变化由谁负责？**

| 元素 | 有身份（ID）吗 | 生命周期 | 相等性判据 | 一句话职责 |
|---|---|---|---|---|
| **值对象**（Value Object） | 无 | 随所属对象，无独立生命周期 | **属性全等** | 描述一个"值"，不可变 |
| **实体**（Entity） | 有（局部或全局 ID） | 有，会经历状态变化 | **ID 相等** | 承载"会变的东西" |
| **聚合根**（Aggregate Root） | 有（全局 ID） | 有，是外部访问的统一入口 | ID 相等 | 保护一组不变式 |
| **领域事件**（Domain Event） | 无 | 瞬时，已发生的事实 | 无 | 记录"已经发生"的业务事实 |

> **最常被搞错的**：值对象不是"小的实体"，实体不是"有 ID 的值对象"。**区别在语义**——"金额 100 元"是什么就是什么（值对象），"账户 A"即使余额变了还是同一个账户（实体）。

## 二、值对象：不可变，用属性相等 {#value-object}

### 2.1 值对象的三个特征 {#vo-traits}

| 特征 | 含义 | 不这么做的后果 |
|---|---|---|
| **不可变**（Immutable） | 一旦创建，属性不再改变；要"改"就换一个新的 | 两个对象共享同一个实例时，一方修改会静默影响另一方 |
| **无身份** | 不分配 ID，数据库里可能直接内嵌成列 | 没人能通过 ID 引用它，因此它必须靠值传递 |
| **整体替换** | 修改 = 用新值对象替换旧的 | 支持"替换"语义，天然线程安全 |

### 2.2 什么时候必须用值对象 {#vo-when}

不是"能包就包"，而是这三种情况**必须**：

| 情况 | 例子 | 不用值对象的代价 |
|---|---|---|
| **多个字段总是一起出现** | 金额（数值 + 币种）、区间（起 + 止）、地址（省市区 + 详细） | 每个方法都传 2~3 个参数，参数顺序写错编译器不报错 |
| **有格式或范围约束** | 手机号、金额非负、区间起 ≤ 止 | 校验散落各处；DB 里出现非法值没人知道 |
| **有自解释的行为** | `money.plus(other)`、`period.overlaps(other)`、`phone.masked()` | 同样的金额相加逻辑在 6 个 service 里各写一遍 |

### 2.3 Java 里的落地方式 {#vo-java}

```java
// 方式一：record（Java 16+，最简，天然不可变）
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount);
        if (amount.scale() > 2) throw new IllegalArgumentException("金额精度最多 2 位");
    }
    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("币种不一致");
        return new Money(amount.add(other.amount), currency);
    }
}

// 方式二：普通类（需要 Jackson 反序列化 / MyBatis 映射时更灵活）
// 全参构造 + 无 setter + 覆盖 equals/hashCode（按全部业务属性）
```

**与 ORM 的冲突要提前知道**：值对象嵌进实体时，MyBatis/JPA 的映射需要额外配置（`@Embedded` / 自定义 `TypeHandler`）。**这是 DDD 落地最常见的第一道摩擦**——很多团队在这里放弃，退回成"每个值对象也建一张表、也加个 ID"。但那样它就已经不是值对象了。

> **折中做法**：**领域层用值对象，持久化层保留扁平字段**（在仓储实现里做转换）。这个转换层的存在本身就是健康的——它就是[防腐层](/methodology/ddd-strategic#acl)在数据访问侧的形态。

## 三、实体：身份决定相等 {#entity}

实体的全部特殊性来自一句话：**它的身份不随属性变化。** 用户改了手机号、改了昵称、改了状态，还是同一个用户。

| 项 | 规则 |
|---|---|
| 相等性 | **只比 ID**。不要用 Lombok 的 `@Data` 给实体生成基于全部字段的 `equals`——那会导致"改了个字段就变成另一个对象"的诡异问题 |
| ID 来源 | 优先**业务无意义**的 ID（雪花/自增）。用手机号当用户 ID 会在用户换号时崩溃 |
| ID 生成时机 | 通常"创建时立即生成"（早标识，Early ID），便于事件里引用。少数场景（依赖数据库自增）才延迟到落库 |
| 可变性 | 允许可变，但**变化必须经过表达业务意图的方法**，不能直接 set。`order.cancel()` 而非 `order.setStatus(CANCELLED)` |

**为什么禁止裸 setter？** 因为 setter 只能表达"字段变成了什么"，无法表达"为什么允许变"。所有前置校验、副作用（发事件、改关联状态）都会被搬到 service 里，实体退化成数据容器——这就是[贫血模型](/methodology/ddd-tactical#anemic-vs-rich)的起点。

## 四、聚合：以不变式为圆心的边界 {#aggregate}

### 4.1 聚合解决的是「一致性」问题 {#aggregate-why}

先看没有聚合会怎样：一个订单有订单头、订单行、收货地址、优惠信息、支付记录。如果这些对象都能被任意修改，那么"订单总额 = 所有行金额之和 - 优惠"这条规则就**没有任何地方能保证**——任何一处代码都可能破坏它。

**聚合的作用就是：划定一个范围，在这个范围内的一条业务规则必须永远成立，并且这个范围是数据修改的原子单位。**

这条"必须永远成立的业务规则"叫**不变式**（Invariant）。**没有不变式，就不需要聚合。**

### 4.2 四条经典规则 {#aggregate-rules}

Vaughn Vernon 在《Implementing DDD》里给出的四条规则，是判断聚合划得对不对的标准：

| # | 规则 | 为什么 | 违反的后果 |
|---|---|---|---|
| 1 | **通过聚合根访问内部对象** | 根是唯一入口，才能在每次修改时检查不变式 | 外部绕过根改了内部对象，不变式失效 |
| 2 | **聚合根必须有全局唯一 ID** | 外部只能通过根引用，没有 ID 就无法引用 | 只能持有对象引用，导致跨聚合强耦合 |
| 3 | **聚合内部对象可以只有局部 ID** | 内部对象的身份只在聚合内有意义 | 给内部对象也发全局 ID，会诱使外部直接引用它 |
| 4 | **聚合外只能引用根，且引用 ID 而非对象** | 持有对象引用意味着跨聚合的生命周期绑定 | 一方加载时被迫加载整个关联图，性能与一致性一起崩 |

### 4.3 「小聚合」原则 {#small-aggregate}

Vernon 还给了两条更重要的经验规则，它们比上面四条更常被违反：

> **① 聚合要尽量小。** 一个聚合通常只包含：一个根 + 少量内部实体/值对象 + 少量必要的关联 ID。
>
> **② 一次事务只修改一个聚合。** 跨聚合的一致性用**领域事件 + 最终一致**达成，而不是用一个大事务。

**为什么必须小？** 因为聚合边界 = 事务边界 = 加锁范围：

| 聚合过大 | 后果 |
|---|---|
| 订单聚合里包含所有订单行 + 支付记录 + 物流信息 | 每次取消订单都要锁住整个大对象；改物流状态和改支付状态互相阻塞 |
| 用户聚合里包含所有地址 + 所有订单 | 用户改昵称时锁住了全部数据，高并发下直接成为瓶颈 |
| 聚合间对象引用 | 加载订单时顺带加载用户、商品、库存……加载抖动不可预测 |

**正确的切法**：把"必须立刻一致"的规则留在聚合内，把"可以晚几毫秒一致"的搬到外面。

```text
订单聚合（必须立刻一致）          跨聚合（最终一致，靠事件）
  订单头                            库存扣减
  订单行                            积分累加
  总额与优惠的计算                   优惠券状态变更
  ↑ 这些必须原子地一起变化           物流单创建
  ↑ 总额校验属于不变式
```

### 4.4 聚合的三类不变式 {#invariants}

设计聚合时先列出不变式，再决定边界。常见的三类：

| 类型 | 例子 | 是否适合放聚合内 |
|---|---|---|
| **单对象内约束** | 金额非负、区间起 ≤ 止 | 属于值对象自身，不用升级到聚合 |
| **聚合内跨对象约束** | 订单总额 = 行之和 − 优惠 | **典型聚合内不变式**，这是聚合存在的理由 |
| **跨聚合约束** | 用户积分不能超过某值（积分在另一聚合） | **不要**用大聚合解决，用最终一致 + 补偿 |

> **一条硬判据**：如果两条规则之间**不需要同时成立**，它们就不该在同一个聚合里。

## 五、领域事件：让跨聚合的一致性变得可管理 {#domain-event}

### 5.1 事件的四要素 {#event-anatomy}

| 要素 | 说明 | 反例 |
|---|---|---|
| **过去时命名** | 事件是"已发生的事实" | `CancelOrder` 是命令，`OrderCancelled` 才是事件 |
| **不可变** | 已发生的事不能改 | 提供 setter |
| **自包含** | 携带消费方需要的信息（至少 ID + 关键字段） | 只有一个 ID，消费方要回调反查 |
| **可追溯** | 含事件 ID、发生时间、聚合 ID、版本 | 只含业务数据 |

### 5.2 事件在哪里发：一个必踩的坑 {#event-publish-point}

**最危险的做法**是在聚合的 setter / 领域方法里直接调 `eventPublisher.publish()`：

```text
错误顺序：
  1. order.cancel()              → 内部直接 publish(OrderCancelled)
  2. repository.save(order)      → 事务提交
  3. ↑ 如果第 2 步失败/回滚，事件已经发出去了 —— 消费方按"订单已取消"处理，数据不一致

正确顺序：
  1. order.cancel()              → 只是在聚合内部记录事件（List<DomainEvent>）
  2. repository.save(order)      → 事务提交
  3. 事务提交成功后               → 统一发布（Spring 的 @TransactionalEventListener(AFTER_COMMIT) 或发件箱）
```

三种落地方式，按可靠性递增：

| 方式 | 机制 | 可靠性 | 适用 |
|---|---|---|---|
| **提交后同步发布** | `@TransactionalEventListener(AFTER_COMMIT)` | 中：进程崩溃会丢事件 | 单体内、事件只用于本地副作用（缓存失效、日志） |
| **事务性发件箱**（Outbox） | 事件与业务数据**同库同事务**写入 `outbox` 表，再由轮询/CDC 投递 | 高：不丢（可能重复，靠幂等去重） | **跨服务、需要至少一次投递的场景** |
| **事件溯源**（Event Sourcing） | 事件本身是唯一真相源 | 最高 | 审计/回放要求极高的领域，见[事件驱动与 CQRS](/methodology/event-driven-cqrs) |

**发件箱的关键点**：`outbox` 表的写入必须和业务数据在**同一个本地事务**里——这正是它比"先发消息再更新库"可靠的原因。投递环节用 Canal 抓 binlog 或定时轮询，语义是**至少一次**，因此消费方必须幂等（见[接口幂等](/java/spring/spring-cloud/idempotency)）。

## 六、仓储：不是 DAO，只为聚合根而存在 {#repository}

| 维度 | 仓储（Repository） | DAO / Mapper |
|---|---|---|
| **服务的对象** | **聚合根**（一个聚合一个仓储） | 数据库表（一表一 Mapper） |
| **接口语义** | 集合语义：`add` / `remove` / `findById` / `findByXxx` | 数据库语义：`insert` / `update` / `deleteById` / `selectList` |
| **返回类型** | 完整的聚合（内部一致） | 数据行 / POJO / 分页记录 |
| **定义位置** | **领域层定义接口，基础设施层实现** | 基础设施层，领域层不应依赖 |
| **数量** | 少（等于聚合数） | 多（等于表数） |

三条实践规则：

1. **只给聚合根建仓储**。给订单行建一个 `OrderLineRepository` 意味着订单行可以被独立修改——那它就不该在订单聚合里。
2. **不要用仓储做复杂查询**。跨聚合的联表、统计、报表**不属于仓储**，走专门的查询服务或读模型（这就是 [CQRS](/methodology/event-driven-cqrs) 的动机之一）。硬塞进仓储会把领域层绑死在 SQL 上。
3. **接口在领域层、实现在基础设施层**。这是[依赖倒置](/methodology/architecture-styles)在数据访问上的体现，也是判断一个项目"有没有真的分层"的试金石（见[架构风格](/methodology/architecture-styles#how-to-tell)）。

## 七、领域服务 vs 应用服务：两种完全不同的东西 {#service}

国内项目里通常只有一个 `XxxService`，它同时干两件事。DDD 把这两件事明确分开：

| 维度 | 领域服务（Domain Service） | 应用服务（Application Service） |
|---|---|---|
| **表达什么** | **业务规则**（不属于任何单个实体/值对象的规则） | **用例流程**（编排、事务、权限、日志） |
| **有状态吗** | 无状态 | 无状态（但会持有仓储、事件发布器等） |
| **包含业务决策吗** | **是**（"能不能"、"算多少"） | **否**（只决定"按什么顺序调用谁"） |
| **典型例子** | `transferFeeCalculator.calculate(amount, channel)` | `paymentAppService.pay(command)` |
| **依赖方向** | 依赖领域模型 | 依赖领域服务、仓储、外部网关 |
| **对外暴露** | 不直接对外（由应用服务调用） | **对 Controller / MQ 消费者暴露** |

**判断一个方法该放哪的判据**：

```text
这个方法里有 "if ... 业务条件 ... 则 ..." 吗？
  ├─ 有 → 它是业务规则 → 领域层（实体方法 / 值对象方法 / 领域服务）
  └─ 无，只是"先查、再改、再落库、再发通知" → 应用服务

这个方法返回的是"业务结论"还是"操作结果"？
  ├─ 业务结论（费用、资格、状态是否可流转）→ 领域层
  └─ 操作结果（成败、ID、分页）→ 应用层
```

> **贫血模型的症状**：`XxxService` 里全是 `if` 业务判断，实体类里只有 getter/setter。这正说明业务规则被从领域层搬到了应用层——**不是分层问题，是模型问题**。

## 八、贫血模型 vs 充血模型：真实代价对比 {#anemic-vs-rich}

这是国内面试**必问**的一道题，也是最有争议的一道。

### 8.1 两种模型的区别 {#anemic-vs-rich-def}

| 维度 | 贫血模型（Anemic Domain Model） | 充血模型（Rich Domain Model） |
|---|---|---|
| 实体类内容 | 只有字段 + getter/setter | 字段 + 业务方法（含校验与状态流转） |
| 业务规则位置 | 大量堆在 Service | 内聚在实体/值对象/领域服务 |
| 事务脚本风格 | 是（Transaction Script） | 是（Domain Model 风格） |
| 代码组织 | 按层（controller / service / dao） | 按领域（各上下文自成一包） |
| 上手成本 | **低**：符合三层架构的直觉 | **高**：要理解聚合、不变式、生命周期 |
| 规则复用 | 差：容易被复制到多个 Service | 好：规则跟着模型走 |
| 单元测试 | 测 Service 必须 mock 一堆依赖 | 测实体的业务方法几乎零依赖 |

### 8.2 为什么国内主流是贫血？（这是有理由的） {#why-anemic}

把它当成"落后"是不公平的。贫血模型在国内成为主流，有四个真实原因：

| 原因 | 说明 |
|---|---|
| **三层架构的惯性** | 从 Struts/SSH 时代起，"Controller → Service → DAO"就是标准答案，实体被定义为"数据传输的载体" |
| **ORM 与框架的引导** | MyBatis 面向 SQL、面向表；生成的实体天然是数据容器。JPA 的 `@Entity` 更像领域实体，但国内 JPA 用得少 |
| **前后端分离后的 DTO 文化** | 一个 `XxxVO`、`XxxDTO`、`XxxReq`、`XxxDO` 的体系里，领域实体没有位置 |
| **业务复杂度低** | 大量项目是 CRUD。**CRUD 场景下充血模型确实是负收益**——没有不变式，聚合就没有存在理由 |

**关键结论：模型选择应该跟着业务复杂度走，而不是跟着技术潮流走。**

| 场景 | 建议 |
|---|---|
| CRUD / 配置管理 / 后台管理 | **贫血模型 + 简单的分层**是更优解，别硬上 DDD |
| 有明确不变式、状态机、多规则计算的业务（计费、审批、订单、账务、库存） | **充血模型**，否则规则会散落并逐渐不一致 |
| 一个系统里两者共存 | **完全正常且推荐**：核心域充血、支撑域贫血 |

### 8.3 贫血模型被低估的代价 {#anemic-cost}

如果业务确实复杂，贫血的代价会以特定形式显现：

| 代价 | 具体表现 | 为什么会发生 |
|---|---|---|
| **规则复制** | "能不能退款"在 4 个 Service 里各写一遍，改一处忘三处 | 规则不属于任何对象，所以谁都可以"再写一遍" |
| **无法保证不变式** | 通过接口改了、通过脚本改了、通过 MQ 消费改了，只有一处做了校验 | 校验是 Service 的职责，绕过 Service 就绕过校验 |
| **测试成本高** | 测一个判断要启动 Spring 上下文、mock 5 个依赖 | 业务逻辑与框架/IO 绑在一起 |
| **改动恐惧** | 5000 行的 `XxxServiceImpl` 没人敢动 | 没有边界，任何改动的影响面不可估算 |

### 8.4 充血模型不是「把 setter 改成方法」 {#rich-not-just-methods}

最常见的伪充血：

```java
// 伪充血：只是把 setter 换了个名字，规则和校验全在外部
public class Order {
    private OrderStatus status;
    public void setStatusCancelled() { this.status = CANCELLED; }   // ← 仍然没有业务含义
}

// 真充血：状态机、前置条件、副作用都在里面，外部无法绕过
public class Order {
    public void cancel(CancelReason reason) {
        if (status != OrderStatus.PAID) {
            throw new IllegalStateException("只有已支付订单可取消，当前：" + status);
        }
        if (paidAt.isBefore(now().minusHours(24))) {
            throw new IllegalStateException("超过 24 小时需走售后流程");
        }
        this.status = OrderStatus.CANCELLED;
        this.cancelledAt = now();
        this.cancelReason = reason;
        registerEvent(new OrderCancelled(id, reason, cancelledAt));   // 记录事件，不直接发布
    }
}
```

**判据**：把实体上所有 public 方法的**方法名连起来读**，能否读出一段业务规则？只能读出"设置某某字段"就是伪充血。

## 九、聚合设计清单（可直接用于评审） {#checklist}

| # | 检查项 | 不合格的表现 |
|---|---|---|
| 1 | 每个聚合能说出**它保护的不变式** | 说不出不变式 → 这个聚合不该存在，它只是对象分组 |
| 2 | 聚合根是**唯一入口**，外部不持有内部对象引用 | 有 Getter 返回内部集合的可变引用 |
| 3 | 聚合外**只引用根 ID**，不引用对象 | 实体里直接持有另一个聚合根的对象引用 |
| 4 | **一次事务只改一个聚合** | 出现跨聚合的 `@Transactional` 大事务 |
| 5 | 聚合内**无跨聚合的强一致依赖** | 保存订单时必须同步校验用户状态（应改为最终一致） |
| 6 | 业务规则在**领域层**，应用服务只做编排 | Service 里有 `if` 业务条件 |
| 7 | 状态变化经过**表达意图的方法**，无裸 setter | 外部能 `setStatus` |
| 8 | 领域事件**在事务提交后发布**，跨服务用发件箱 | 在 setter 里直接发布事件 |
| 9 | 仓储**只服务聚合根**，复杂查询另走读模型 | 给订单行建了仓储 |
| 10 | 值对象**不可变**且按属性相等 | 值对象有 setter |

## 十、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "值对象和实体怎么区分？" | 有身份的是实体（按 ID 相等），无身份、按属性相等的是值对象；判据是语义不是大小 | [四种元素](/methodology/ddd-tactical#elements) |
| 2 | "什么情况下必须用值对象？" | 多字段总一起出现 / 有格式或范围约束 / 有自解释行为——三者占一就必须包 | [必须用 VO](/methodology/ddd-tactical#vo-when) |
| 3 | "值对象和 ORM 冲突怎么办？" | 领域层用值对象、持久化层保留扁平字段，转换放仓储实现里 | [落地摩擦](/methodology/ddd-tactical#vo-java) |
| 4 | "为什么不让实体有 setter？" | setter 只能表达"字段变成了什么"，无法表达"为什么允许变"；校验与副作用会被迫搬到 Service | [实体](/methodology/ddd-tactical#entity) |
| 5 | "聚合的边界怎么定？" | **以不变式为圆心**：先列出必须同时成立的规则，规则的作用范围就是聚合 | [聚合的理由](/methodology/ddd-tactical#aggregate-why) |
| 6 | "聚合的四条规则是什么？" | 通过根访问 / 根有全局 ID / 内部对象只需局部 ID / 外部只引用根 ID 不引用对象 | [四条规则](/methodology/ddd-tactical#aggregate-rules) |
| 7 | "跨聚合的一致性怎么保证？" | **一次事务只改一个聚合**，跨聚合用领域事件 + 最终一致 + 补偿，不用大事务 | [小聚合](/methodology/ddd-tactical#small-aggregate) |
| 8 | "聚合为什么必须小？" | 聚合边界 = 事务边界 = 加锁范围；聚合越大锁越久、加载抖动越不可控 | [小聚合](/methodology/ddd-tactical#small-aggregate) |
| 9 | "领域事件该在事务的哪个位置发？" | 在聚合内**只记录**，事务**提交后**才发布（`AFTER_COMMIT` 或发件箱）；在 setter 里直接发会导致回滚后事件已外泄 | [发布时机](/methodology/ddd-tactical#event-publish-point) |
| 10 | "事务性发件箱解决什么问题？" | 事件与业务数据同库同事务写入，解决"业务成功但消息丢失"；投递语义是至少一次，消费方必须幂等 | [发件箱](/methodology/ddd-tactical#event-publish-point) |
| 11 | "仓储和 DAO 有什么区别？" | 仓储面向**聚合根**、接口定义在领域层、返回完整聚合；DAO 面向**表**、在基础设施层、返回数据行 | [仓储](/methodology/ddd-tactical#repository) |
| 12 | "复杂查询该放仓储吗？" | 不该。跨聚合的联表统计走独立读模型/CQRS，硬塞会让领域层绑死 SQL | [仓储规则](/methodology/ddd-tactical#repository) |
| 13 | "领域服务和应用服务的区别？" | 领域服务表达**业务规则**、应用服务负责**用例编排**；判据是方法里有没有业务条件的 `if` | [两种服务](/methodology/ddd-tactical#service) |
| 14 | "你们项目是贫血还是充血？" | 关键在**业务复杂度**：CRUD 场景贫血更优（充血是负收益），有不变式与状态机的场景必须充血；两者共存是常态 | [贫血的合理性](/methodology/ddd-tactical#why-anemic) |
| 15 | "贫血模型有什么代价？" | 规则复制、不变式无法保证（绕过 Service 即绕过校验）、测试成本高、大 Service 没人敢动 | [贫血的代价](/methodology/ddd-tactical#anemic-cost) |
| 16 | "充血模型是不是就是别用 setter？" | 不是。判据是把实体 public 方法名连起来读**能否读出一段业务规则**，只能读出"设置字段"就是伪充血 | [伪充血](/methodology/ddd-tactical#rich-not-just-methods) |
