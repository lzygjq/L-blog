# 架构风格：依赖方向与边界归属

> **口径说明**：本文是方法论梳理，代码与目录结构是**示意**，用于说明依赖方向，不是某个真实工程的目录。不含企业标识与客户信息。

分层、六边形、洋葱、整洁架构、COLA——这五个名字经常被并列提起，也经常被混用。它们不是五个"可以随便挑一个"的选项，而是**同一条演化线上的五个节点**：每一代都在修上一代的某个具体问题。

这一篇讲清楚：**它们在争什么、每一代修了上一代的什么毛病、以及在 Java 工程里怎么落地。**

## 一、谱系：五个名字，一条主线 {#genealogy}

```text
分层架构（Layered, 1990s）
  ├─ 问题：业务逻辑依赖数据库，换存储要改业务代码
  ↓
六边形架构（Hexagonal / Ports & Adapters, 2005, Alistair Cockburn）
  ├─ 修法：业务核心定义接口（端口），技术实现挂在外面（适配器）
  ├─ 问题：只说了"内外"，没说内部怎么分
  ↓
洋葱架构（Onion, 2008, Jeffrey Palermo）
  ├─ 修法：把内部再分成同心圆——领域模型在最内，领域服务、应用服务依次向外
  ├─ 问题：同心圆画法和分层很像，容易被理解成"换了个画法的分层"
  ↓
整洁架构（Clean Architecture, 2012, Robert C. Martin）
  ├─ 修法：明确到"层 + 依赖规则"，并给出跨边界的数据传递纪律
  ├─ 问题：偏抽象，落地时的包结构/命名/脚手架没有统一答案
  ↓
COLA（Clean Object-oriented and Layered Architecture, 阿里开源）
  └─ 修法：给出 Java 工程可直接复制的四层结构与模块划分，代价是取舍固定
```

**读法**：不要问"哪个最好"，要问"**我的项目最痛的是哪个症状**"。症状不同，选不同的节点，甚至不选（小项目用朴素分层完全合理）。

## 二、它们真正在争的一件事 {#core-issue}

抛开画法，这五代架构风格只在争两个问题：

| # | 问题 | 分层架构的答案 | 六边形之后的答案 |
|---|---|---|---|
| 1 | **源代码的依赖方向朝哪？** | 上层依赖下层；业务层依赖数据访问层 | **只能向内**：技术细节依赖业务核心 |
| 2 | **边界归谁定义？** | 下层提供能力，上层调用 | **核心定义接口（端口）**，外围提供实现 |

### 2.1 为什么依赖方向这么重要 {#why-direction}

依赖方向决定了"改一处要动几处"。关键在于：**业务规则的变化频率远高于技术实现**。

| 变化来源 | 变化频率 | 如果业务依赖技术会怎样 |
|---|---|---|
| 框架升级、ORM 更换、存储更换 | 低 | 依赖方向反了的话，**业务代码要跟着改** |
| 业务规则调整 | 高 | 按正确方向，业务改动**不需要碰技术层** |

一句话：**依赖方向应该指向"稳定"的一侧。业务规则是稳定的（不是不变，是变化的原因单一），技术选型是易变的。** 所以让技术依赖业务，而不是反过来。

> 这和[依赖倒置原则](/java/design-patterns/principles/)（DIP）是同一个东西：**高层模块不依赖低层模块，二者都依赖抽象；抽象不依赖细节，细节依赖抽象。** 架构风格只是 DIP 在系统尺度上的表达。

## 三、分层架构：起点，也是问题的来源 {#layered}

### 3.1 经典形态 {#layered-shape}

```text
表现层（Presentation / Controller）    → 处理 HTTP、参数校验、DTO 转换
业务逻辑层（Service / Business）        → 业务规则
数据访问层（DAO / Mapper / Repository） → SQL、缓存、外部接口
```

### 3.2 它的两个结构性问题 {#layered-problems}

| 问题 | 具体表现 | 根因 |
|---|---|---|
| **业务层依赖数据访问层** | Service 里直接注入 Mapper，`OrderService` 的方法签名里出现 `OrderDO` | 依赖方向指向了数据库 |
| **业务层被框架细节污染** | Service 上挂着 `@Transactional`、方法里拼 SQL 条件、返回 `PageResult<OrderDO>` | 分层只约束了"谁调谁"，没约束"什么能进来" |

**后果**：换 ORM（MyBatis → JPA）要改业务层；测试业务规则必须准备数据库。

### 3.3 分层不是错的，是「不够」 {#layered-not-wrong}

要说清楚：**分层架构在 CRUD 项目里是最优解**。它的问题只在业务复杂时暴露。

| 场景 | 分层够用吗 |
|---|---|
| 后台管理、配置管理、表单增删改查 | **够用，且是最优**——引入更多层只会增加跳转成本 |
| 有复杂规则/状态机/计费的业务 | **不够**，业务规则会持续被技术细节污染 |

> **判据**：如果你的 Service 里已经有大量 `if` 业务判断，而实体类是纯 getter/setter，那就是分层不够了——但**第一步不该是换架构风格，而是先把业务规则挪回领域模型**（见[贫血与充血](/methodology/ddd-tactical#anemic-vs-rich)）。

## 四、六边形架构：端口与适配器 {#hexagonal}

### 4.1 核心思想 {#hex-core}

**应用的核心（业务逻辑）不知道外面是什么。** 所有外部交互都通过**端口**（Port，核心定义的接口）进行，**适配器**（Adapter，外围的实现）负责把具体技术转成端口的形状。

```text
        ┌───────────── 驱动方（Driving）─────────────┐
        │  HTTP Controller │ MQ Consumer │ 定时任务  │   ← 适配器
        └────────────┬────────────┬───────────┬────┘
                     ↓ 调用        ↓           ↓
        ┌────────────────────────────────────────────┐
        │           【端口：入站接口】                │
        │       （由核心定义，如 OrderUseCase）       │
        │  ┌──────────────────────────────────────┐  │
        │  │      应用服务 → 领域模型（核心）      │  │
        │  └──────────────────────────────────────┘  │
        │           【端口：出站接口】                │
        │    （由核心定义，如 OrderRepository）       │
        └────────────┬────────────┬───────────┬────┘
                     ↑ 实现        ↑           ↑
        ┌────────────┴────────────┴───────────┴────┐
        │  MySQL 仓储实现 │ 外部接口适配器 │ 消息发送 │  ← 适配器
        └───────────── 被驱动方（Driven）───────────┘
```

### 4.2 两侧的本质区别 {#two-sides}

| 侧 | 谁发起 | 端口方向 | 适配器例子 |
|---|---|---|---|
| **驱动方**（左侧） | 外部发起调用进来 | **入站端口**（核心实现它） | Controller、MQ 消费者、定时任务、命令行 |
| **被驱动方**（右侧） | 核心调用出去 | **出站端口**（核心定义、外部实现） | 仓储实现、第三方 API 客户端、消息发送器 |

**为什么叫"六边形"？** 只是想说"任何一侧都有多个面"，**六不是硬性的数字**。面试时如果被问"为什么是六边形"，答"图形本身无意义，重点是内外分离与端口/适配器"即可。

### 4.3 端口的两条纪律 {#hex-rules}

| 纪律 | 说明 | 违反的后果 |
|---|---|---|
| **入站端口由核心实现** | `OrderUseCase` 接口在核心，`OrderAppService` 实现它；Controller 只依赖接口 | Controller 直接依赖具体 Service 后，换个入口（MQ）就要再写一遍 |
| **出站端口由核心定义、外部实现** | `OrderRepository` 接口在领域层，`OrderRepositoryImpl` 在基础设施层 | 接口定义在 DAO 层 → 依赖方向反过来 → **退化成普通分层** |

**关键认知：端口不是一个"技术层"，它是依赖方向上的一个反转点。** 同一个接口，定义在哪一层，决定了架构是六边形还是分层。

## 五、洋葱架构：同心圆与内部层次 {#onion}

洋葱补上的是**"核心内部怎么分"**：

```text
        ┌──────────────────────────────────────────┐
        │ 基础设施 / 用户界面 / 测试（最外）        │
        │  ┌────────────────────────────────────┐  │
        │  │ 应用服务（用例编排）                │  │
        │  │  ┌──────────────────────────────┐  │  │
        │  │  │ 领域服务（跨实体的规则）      │  │  │
        │  │  │  ┌────────────────────────┐  │  │  │
        │  │  │  │ 领域模型（实体/值对象） │  │  │  │
        │  │  │  │      ← 最内层，零依赖   │  │  │  │
        │  │  │  └────────────────────────┘  │  │  │
        │  │  └──────────────────────────────┘  │  │
        │  └────────────────────────────────────┘  │
        └──────────────────────────────────────────┘
                   依赖方向：只能从外向内
```

**领域模型在最内层的含义**：这一层的类**不应该 import 任何框架的注解**（`@Service`、`@Entity`、`@Component` 都不该出现）。一旦出现，它就被绑死了。

> **落地上的现实取舍**：完全不引框架注解在 Java 里很别扭（序列化、持久化都要注解）。务实的做法是**允许基础设施注解出现在领域类上，但禁止领域类 import 基础设施的类**——**允许被注解，不允许被反向依赖**。

## 六、整洁架构：依赖规则与跨边界纪律 {#clean}

整洁架构把前面几代的共识整理成两条可执行的规则：

### 6.1 四层与依赖规则 {#clean-layers}

| 层 | 内容 | 例子 |
|---|---|---|
| **实体**（Entities） | 企业级业务规则，最稳定 | `Order`、`Money` |
| **用例**（Use Cases） | 应用级业务规则，编排实体 | `OrderAppService` |
| **接口适配器**（Interface Adapters） | 把外部数据转成用例需要的形式 | Controller、Presenter、Repository 实现 |
| **框架与驱动**（Frameworks & Drivers） | 具体技术 | Spring、MyBatis、Kafka、MySQL |

> **依赖规则（The Dependency Rule）**：**源代码的依赖只能由外向内。** 内层不能知道外层的任何东西——不能引用外层的类、方法、变量。

### 6.2 跨边界传数据：一条容易被忽略的纪律 {#cross-boundary-data}

整洁架构特别强调：**跨边界传递的数据不能是内层的实体对象。**

```text
❌ 错误：内层返回 Entity，外层直接序列化
   Controller → OrderAppService.getOrder() → Order（领域实体）
   → Jackson 序列化 Order → 接口契约与领域模型强绑定
   → 领域模型一加字段，接口就变；ORM 注解泄漏到 API 文档里

✅ 正确：跨边界用简单的数据结构（DTO / Response）
   Order（领域实体） → 在边界处转换 → OrderResponse（外层的数据结构）
```

**为什么？** 因为内层的实体可能带有内层才需要的东西（领域事件列表、延迟加载的关联、计算属性），直接外泄会：
1. 让接口契约被动跟着领域模型变；
2. 暴露不该暴露的内部结构（安全问题）；
3. 触发意外的懒加载（性能问题）。

这条纪律在 Java 工程里的对应物就是 **VO / DTO / Response 的分层转换**。国内项目的转换代码经常被吐槽"啰嗦"，但它的收益就是上面三条。

### 6.3 用例的输出该是什么 {#usecase-output}

| 做法 | 评价 |
|---|---|
| 返回领域实体 | ❌ 边界泄漏 |
| 返回 DTO | ✅ 推荐 |
| 返回 `Result<T>` 包装 | ✅ 常见做法，但注意 `Result` 属于接口适配层，不该出现在领域层 |

## 七、COLA：把整洁架构工程化 {#cola}

COLA（Clean Object-oriented and Layered Architecture）是阿里开源的 Java 架构规范，本质是**整洁架构 + 明确的模块与包结构 + 一些取舍**。

### 7.1 四层结构 {#cola-layers}

| 层 | 全称 | 职责 | 依赖 |
|---|---|---|---|
| **adapter** | 适配层 | Controller、MQ 消费者、定时任务；参数校验与 DTO 转换 | 依赖 app |
| **app** | 应用层 | 用例编排、事务边界、命令与查询对象 | 依赖 domain、infra（接口） |
| **domain** | 领域层 | 实体、值对象、领域服务、仓储**接口** | **不依赖任何其他层** |
| **infra** | 基础设施层 | 仓储**实现**、外部网关实现、Mapper | 实现 domain/app 的接口 |
| **client** | 客户端层（可选） | 对外暴露的 API 包（DTO + 服务接口），供其他模块依赖 | 无 |

### 7.2 COLA 的真实取舍 {#cola-tradeoff}

| 优点 | 代价 |
|---|---|
| 包结构与命名有统一答案，新人能看懂 | 层数多，一个简单 CRUD 也要穿过 4 层 |
| 模块边界清晰，便于按上下文拆服务 | 大量转换代码（DTO ↔ 实体 ↔ DO） |
| 有配套的 Archetype 脚手架与 Archeunit 校验 | 不符合国内"三层 + VO/DTO"的主流直觉，团队要培训 |
| 扩展点机制（Extension Point）便于多业态扩展 | 引入注解与 SPI，调试链变长 |

> **一条务实建议**：**COLA 的价值在大项目里，不在小项目里。** 一个只有 30 个接口的内部系统用 COLA，收益（边界清晰）几乎为零，成本（层数、转换、学习）却是实打实的。**判断标准仍然是业务复杂度与团队规模。**

## 八、五者对比 {#compare}

| 维度 | 分层 | 六边形 | 洋葱 | 整洁 | COLA |
|---|---|---|---|---|---|
| **核心主张** | 上层调下层 | 端口/适配器，内外分离 | 同心圆，领域在最内 | 依赖只能向内 | 整洁架构的工程化落地 |
| **依赖方向** | 上 → 下（业务依赖数据） | 外 → 内 | 外 → 内 | 外 → 内 | 外 → 内 |
| **领域模型位置** | 无独立领域层 | 核心（未细分） | **最内圈** | 实体层（最内） | domain 模块 |
| **接口/抽象定义在哪** | 无强制 | 核心 | 核心 | 内层 | domain / app |
| **实现成本** | 低 | 中 | 中 | 中高 | 高（有脚手架可降） |
| **适合场景** | CRUD、中小项目 | 有外部系统集成、需要可测试性 | 领域模型复杂的业务系统 | 大型长期演进系统 | 大型团队、多模块、多业态 |
| **主要收益** | 上手快、结构直观 | 换技术不改业务、易测试 | 领域模型纯净 | 边界清晰、契约稳定 | 有规范可复制、扩展点机制 |
| **主要代价** | 业务被技术污染 | 需要人为维护端口纪律 | 同心圆易被理解成"换画法" | 抽象、无统一脚手架 | 层多、转换多、学习成本 |

## 九、怎么判断一个项目是不是真的六边形 {#how-to-tell}

这是面试里最能区分"读过文章"和"真的做过"的一问。**只看一件事：接口定义在哪一层。**

| 观察点 | 是六边形/整洁 | 只是分层 |
|---|---|---|
| **仓储接口定义位置** | 领域层（`domain` 包） | 数据访问层（`dao`/`mapper` 包） |
| **领域层的 import** | 只有 JDK + 少量注解 | import 了 MyBatis、Spring Data、工具类库 |
| **Service 的方法签名** | 出入参是领域对象 / DTO | 出入参是 `OrderDO`、`PageResult<OrderDO>` |
| **Controller 依赖谁** | 依赖入站端口（接口） | 依赖具体 Service 类 |
| **换 ORM 要改哪些文件** | 只改 infra | 改到 service 甚至 controller |
| **领域模型能否脱离 Spring 单测** | 能，`new Order(...)` 直接测 | 不能，必须启动上下文 |

**一句话判据**：**`import` 的方向反过来没有？** 如果领域层 import 了基础设施的类，那就不是。

> **补充：可以用 [ArchUnit](/java/testing/) 把这条纪律写成测试**——在 CI 里断言"domain 包不得依赖 infra 包"。**纪律靠人不靠测试一定会腐化**，这是把架构约束变成可执行规则的最实用手段。

## 十、五个常见误解 {#misconceptions}

| # | 误解 | 事实 |
|---|---|---|
| 1 | "六边形架构有六层" | 六边形只是一个图形比喻（"任何一侧都有多个面"），**没有六层的含义** |
| 2 | "整洁架构 = 不能有任何依赖" | 依赖仍然存在，只是**方向被约束为向内**；跨边界依赖靠接口反转 |
| 3 | "DDD 必须配整洁架构" | 二者独立。DDD 是**建模方法**，整洁架构是**依赖组织方式**。可以只用其中一个（只是效果打折） |
| 4 | "用了 COLA 就是 DDD" | COLA 是**代码组织规范**，不包含战略设计（边界、通用语言）。只上 COLA 不改建模，得到的是"分得很整齐的贫血模型" |
| 5 | "洋葱/整洁架构只适合大项目" | 反过来：**大项目更需要它**，小项目用了是浪费。判据是业务复杂度与预期寿命，不是团队人数 |

## 十一、落地：包结构怎么组织 {#package}

架构风格最终要落到目录上。**两种组织方式，先按上下文分包。**

| 方式 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **按层分包** | `controller/` `service/` `dao/` `entity/` | 符合直觉、框架默认 | **边界被物理打散**——同一个上下文的代码散在 4 个包，改一处要跨 4 个目录；且没有任何机制阻止跨层直连 |
| **按上下文分包**（推荐） | `order/` `billing/` `tenant/`，每个内部再分层 | 边界可强制执行（包可见性 + ArchUnit）、改动集中、便于将来按上下文拆服务 | 需要团队接受非直觉结构；跨上下文的公共能力要显式建 `shared/` 并严控 |

**按上下文分包的两种典型形态**：

```text
// 形态一：单模块内按上下文分（模块化单体阶段）
com.example.app
├── order
│   ├── adapter        （Controller、MQ 消费者）
│   ├── app            （应用服务）
│   ├── domain         （实体、值对象、仓储接口）
│   └── infra          （仓储实现）
├── billing
│   └── ...（同构）
└── shared             （严格受控：只放真正跨上下文的通用能力）

// 形态二：多模块（Maven/Gradle 子模块），把边界交给编译期
app-order   { adapter, app, domain, infra }
app-billing { adapter, app, domain, infra }
app-shared  { 通用能力 }
```

**为什么形态二更可靠？** 因为**编译期约束比约定强**：`app-order` 的 `pom.xml` 里没有 `app-billing` 依赖，就不可能误调用——错误在编译时就暴露，而不是在上线后。这也是"先模块化单体、再微服务"的中间形态（见[拆分粒度](/methodology/service-granularity#modular-monolith)）。

## 十二、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "六边形、洋葱、整洁架构有什么区别？" | 同一条演化线：六边形解决"内外分离"、洋葱补"内部怎么分"、整洁把它整理成可执行的"依赖规则" | [谱系](/methodology/architecture-styles#genealogy) |
| 2 | "分层架构的问题是什么？" | 依赖方向指向数据库（业务依赖数据访问层），且业务层被框架细节污染 | [分层的问题](/methodology/architecture-styles#layered-problems) |
| 3 | "为什么依赖只能向内？" | 依赖应指向**稳定**的一侧；业务规则变化原因单一（比技术选型稳定），技术细节必须依赖它 | [依赖方向](/methodology/architecture-styles#why-direction) |
| 4 | "端口是什么？定义在哪？" | 核心定义的接口。**入站端口由核心实现**（Controller 依赖它），**出站端口由核心定义、外部实现**（仓储） | [端口纪律](/methodology/architecture-styles#hex-rules) |
| 5 | "为什么叫六边形？有六层吗？" | 没有。图形只是表示"每一侧都有多个面"，重点是内外分离，**六不是硬性数字** | [误解](/methodology/architecture-styles#misconceptions) |
| 6 | "怎么判断一个项目是不是真六边形？" | 看**仓储接口定义在哪层**、看领域层的 `import`、看换 ORM 要改几个模块 | [判据](/methodology/architecture-styles#how-to-tell) |
| 7 | "整洁架构的依赖规则是什么？" | 源代码依赖只能由外向内；内层不知道外层的任何东西 | [四层](/methodology/architecture-styles#clean-layers) |
| 8 | "跨层为什么不能返回实体？" | 接口契约会被领域模型绑死、暴露内部结构、触发懒加载；应转成 DTO | [跨边界数据](/methodology/architecture-styles#cross-boundary-data) |
| 9 | "COLA 和整洁架构什么关系？" | COLA 是整洁架构 + 明确的模块与包结构 + 固定取舍的工程化落地版 | [COLA](/methodology/architecture-styles#cola) |
| 10 | "COLA 有什么代价？" | 层多、转换代码多、与国内三层直觉不符、要培训；**价值在大型项目，小项目是纯成本** | [COLA 取舍](/methodology/architecture-styles#cola-tradeoff) |
| 11 | "架构约束怎么保证不腐化？" | **靠测试不靠人**：用 ArchUnit 在 CI 里断言包依赖，把约束变成可执行规则 | [判据](/methodology/architecture-styles#how-to-tell) |
| 12 | "DDD 必须和整洁架构一起用吗？" | 不必。DDD 是建模方法、整洁架构是依赖组织方式，可分开用，只是效果打折 | [误解](/methodology/architecture-styles#misconceptions) |
| 13 | "按层分包还是按上下文分包？" | **优先按上下文分包**——按层分包会把边界打散，且没有任何机制阻止跨层直连 | [包结构](/methodology/architecture-styles#package) |
| 14 | "为什么多模块比单模块内分包可靠？" | **编译期约束强于约定**：没有依赖声明就不可能误调用，错误在编译时暴露 | [包结构](/methodology/architecture-styles#package) |

> **本篇是本板块第 3 篇。** 聚合与不变式见 [DDD 战术设计](/methodology/ddd-tactical)；边界如何演化为服务拆分见[拆分粒度与部署形态](/methodology/service-granularity)；工程落地的改造路径与反模式见[落地、反模式与工程映射](/methodology/ddd-in-practice)。
