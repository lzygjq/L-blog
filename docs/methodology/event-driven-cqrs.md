# 事件驱动与 CQRS：把「不需要强一致」的部分真的解耦

> **口径说明**：本文是方法论梳理，不含企业标识与客户信息。文中的表结构、代码与拓扑是**示意**，用于说明机制与依赖方向。

[拆分粒度](/methodology/service-granularity)的结论里有一条反复出现：**"不需要强一致的地方才该拆"**。那么拆开之后，一致性靠什么达成？——**靠事件**。

事件驱动是方法论板块里最"跨栈"的一篇：它上接 DDD（领域事件是战术元素之一），下接消息队列（投递语义与顺序）、数据库（发件箱与 CDC），所以在每一处都只讲**为什么这么做**，具体机制的细节交给对应板块。

## 一、先分清三种事件 {#three-events}

"事件"这个词在架构讨论里被滥用得最厉害。**先分清三种，否则每次讨论都会歪。**

| 类型 | 范围 | 命名 | 目的 | 能否跨进程 |
|---|---|---|---|---|
| **领域事件**（Domain Event） | 限界上下文内 | 过去时业务事实（`OrderCancelled`） | 表达"领域里发生了什么"，驱动上下文内的反应 | ❌ 不直接跨 |
| **集成事件**（Integration Event） | 跨服务/跨上下文 | 过去时，但**面向订阅方设计** | 服务之间通信 | ✅ 是 |
| **应用事件**（Application Event） | 单个进程内 | 可以是任何粒度（`UserLoaded`） | 本地副作用（缓存失效、日志） | ❌ |

### 1.1 领域事件 → 集成事件：必须转换，不能直发 {#de-to-ie}

最常见的错误是**把领域事件直接发到 MQ**。为什么不行：

| 原因 | 说明 |
|---|---|
| **语义泄漏** | 领域事件是内部模型的一部分，字段会随内部重构变化；直接外发等于把内部模型变成公共契约 |
| **粒度过细** | 领域事件数量可能是集成事件的 3~5 倍（每次状态变化都发），订阅方会被淹没 |
| **信息不足或过多** | 领域事件通常只带变化的最小信息；集成事件需要**自包含**（订阅方不想回调反查） |
| **契约演进不同步** | 内部重构不应该需要协调所有下游 |

**正确姿势**：

```text
领域事件（内部，随模型自由演进）
        ↓  在边界处做「事件翻译」（本质是防腐层在事件维度的形态）
集成事件（对外契约，版本化、向后兼容、自包含）
        ↓  MQ
下游服务
```

> **结论**：**集成事件是接口，不是内部模型的一部分。** 把它当成接口来治理（版本、兼容、deprecation 流程），而不是当成"顺便发出去的领域事件"。

## 二、事件的三种语义：成本递进 {#event-semantics}

即便都是"事件"，用它们承载多少含义，决定了系统复杂度。**这是一个可以自由选择的档位，不是必须一路做到最右。**

| # | 语义 | 事件里带什么 | 订阅方要做什么 | 成本 | 适用 |
|---|---|---|---|---|---|
| 1 | **事件通知**（Event Notification） | 只有 ID + 事件类型 | **回调反查源服务** | 最低 | 简单的失效通知（"用户资料变了，缓存清一下"） |
| 2 | **事件携带状态转移**（ECST） | 事件里带上变化后的**完整状态** | 直接更新本地副本，不回调 | 中 | 需要本地冗余数据的场景（查询性能） |
| 3 | **事件溯源**（Event Sourcing） | 事件是**唯一真相源** | 状态由重放事件得出 | 最高 | 审计/回放要求极高（见[第七节](#event-sourcing)） |

**选择建议**：

| 你的需求 | 选哪个 |
|---|---|
| 只是通知，源数据获取方便 | 档位 1 |
| 下游频繁查询上游数据，但不想每次调用 | 档位 2 |
| 需要完整历史、时间旅行、审计追溯 | 档位 3（但要清楚代价） |

> **一个常见误区**：**用档位 1 做档位 2 的事**——发"订单已变更"然后让下游回调查订单。结果是下游与上游强耦合（上游接口变动会打断下游）+ 上游被反查打爆（**事件风暴变成回调风暴**）。**该带的状态要带上。**

## 三、可靠投递：为什么必须发件箱 {#reliable-delivery}

### 3.1 三个"一定不一致"的写法 {#three-broken-ways}

```text
❌ 先更新数据库，再发消息
   1. update order            ← 成功
   2. send message            ← 失败（网络/进程崩溃）
   → 数据库已改，下游永远不知道 → 数据永久不一致

❌ 先发消息，再更新数据库
   1. send message            ← 成功
   2. update order            ← 失败回滚
   → 下游按"订单已取消"处理，但订单其实没取消 → 更糟：下游基于假事实行动

❌ 用 MQ 事务消息解决
   → 能解决"消息与本地事务"的关系，但仍需实现事务回查（check）逻辑，
     且回查本身要能"从业务数据反查状态"——最终还是绕回发件箱/本地消息表
```

### 3.2 发件箱：把"两个动作"变成"一个事务" {#outbox}

**核心思路**：既然两件事不能原子地一起做，那就**把其中一件变成数据**。

```text
一个本地事务：
  BEGIN
    update order set status = 'CANCELLED' where id = ?
    insert into outbox(event_id, aggregate_id, type, payload, status, created_at)
  COMMIT
        ↓  （后续由独立流程投递）
  ① 轮询：定时扫 outbox 表 status='NEW' 的记录 → 发 MQ → 标记 SENT
  ② CDC：Canal 抓 binlog 的 outbox 表变更 → 投递（无需轮询，延迟更低）
        ↓
  消费方（必须幂等：至少一次投递 = 可能重复）
```

| 对比项 | 轮询发件箱 | CDC 发件箱 |
|---|---|---|
| 延迟 | 取决于轮询间隔（秒级） | 准实时（百毫秒级） |
| 对数据库压力 | 定时查询（可控） | 依赖 binlog，几乎无额外查询 |
| 实现复杂度 | 低 | 中（要部署与运维 Canal） |
| 依赖 | 无 | binlog 格式（ROW）、权限 |
| 参考 | —— | [Canal 数据同步](/bigdata/canal/) |

**发件箱的三个关键设计**：

| 点 | 做法 |
|---|---|
| **表要小** | 发完就归档/删除；只保留投递状态，不要当历史表用 |
| **幂等由消费方保证** | 投递语义是**至少一次**，发件箱保证的是"不丢"，不是"不重"。去重见[接口幂等](/java/spring/spring-cloud/idempotency) |
| **顺序要显式处理** | 同一聚合的事件必须按序（见[下一节](#ordering)），跨聚合无序可接受 |

### 3.3 与分布式事务方案的关系 {#vs-distributed-tx}

| 方案 | 一致性 | 复杂度 | 适用 |
|---|---|---|---|
| **2PC/XA** | 强一致 | 高（阻塞、协调者单点、性能差） | 极少，且只在同一个数据库/中间件支持 XA 时 |
| **TCC** | 最终一致（业务层面） | 高（要写 Try/Confirm/Cancel 三套） | 资金类、需要预留资源的场景 |
| **Saga** | 最终一致 | 中高（要写补偿） | 长流程、跨多个服务 |
| **本地消息表 / 发件箱** | 最终一致 | **低** | **最常用**：单向通知型（"我做完了，你接着做"） |
| **最大努力通知** | 弱 | 最低 | 对一致性要求最低的场景（如发通知） |

> **判据**：**如果业务流程是"我做完 → 通知别人也做"，用发件箱就够了；只有"我必须等别人确认"才需要 TCC/Saga。** 二者的机制细节见[分布式事务](/java/spring/spring-cloud/transaction)。

## 四、顺序与分区 {#ordering}

"消息有序"这个词必须带着范围说，否则没有意义。

| 顺序范围 | 可达性 | 怎么做 |
|---|---|---|
| **全局顺序** | 几乎不可达（要单分区 + 单消费者，等于放弃吞吐） | 不要做 |
| **单聚合顺序** | **必须保证**，且可达 | 用 `aggregateId` 作为**分区键**（Kafka partition key / RocketMQ MessageQueue 选择键） |
| **单业务键顺序** | 可达 | 同上，用业务键（订单号、租户 ID）分区 |

```text
同一 partition 内有序（Kafka 只保证 partition 内有序）
    partition 0: Order#1001 Created → Paid → Cancelled   ← 有序 ✅
    partition 1: Order#1002 Created → Paid
    ↑ partition 之间无序（1001 和 1002 的事件可能交错）—— 这通常无所谓
```

**三个必须注意的坑**：

| 坑 | 说明 |
|---|---|
| **分区数变更会打破有序** | Kafka 扩容分区后，同一 key 可能落到不同分区 → 新老消息可能交错。**扩容要选低峰并接受一次性乱序风险** |
| **重试会破坏顺序** | 消费失败重试（尤其带延迟的重试）会让后一条先处理。**要么失败即停（阻塞式），要么在消费侧按版本号丢弃旧事件** |
| **消费端并发度** | 单分区内多线程消费会乱序；要并发就按 key 分线程（同 key 同线程） |

**顺序问题的兜底做法**：**给事件带版本号/序号，消费侧比对本地版本，旧版本直接丢弃。** 这比追求"绝不乱序"更可靠——**乱序是可容忍的，只要能被识别并丢弃。**

## 五、CQRS：读写不对称的必然结果 {#cqrs}

### 5.1 为什么读写会不对称 {#cqrs-why}

| 维度 | 写（命令） | 读（查询） |
|---|---|---|
| **关注点** | 业务规则、不变式、一致性 | 组合、筛选、排序、聚合、分页 |
| **访问模式** | 单聚合、按 ID | 跨聚合、多维度、全表扫描 |
| **数据形态** | 规范化的领域模型 | 反规范化的宽表/视图 |
| **性能特征** | 低频、写少 | 高频、量级差异可达 100:1 |
| **扩展方式** | 垂直 + 分片 | 加从库/加缓存/换 OLAP |

**把两者塞进同一个模型的结果**：领域模型为了支持查询而加冗余字段、加懒加载、加各种"只给查询用"的 Getter——**领域模型被查询需求污染**，这正好是[整洁架构跨边界纪律](/methodology/architecture-styles#cross-boundary-data)要防的事。

**CQRS**（Command Query Responsibility Segregation，命令查询职责分离）就是承认这种不对称，把读写模型分开。

### 5.2 两种形态（成本差一个数量级） {#cqrs-forms}

| 形态 | 做法 | 一致性 | 成本 | 适用 |
|---|---|---|---|---|
| **同库读写模型分离** | 同一个数据库，写用领域模型、读用专门的查询服务/视图/SQL | **强一致**（同一事务可见） | 低 | **先做这个**——多数项目只需要这一步 |
| **读写库分离** | 写库 → 投影/同步 → 读库（从库、ES、Doris） | **最终一致**（有延迟） | 中高 | 读远多于写、查询形态复杂（多维度检索、聚合报表） |
| **读写模型 + 事件溯源** | 写侧是事件流，读侧是投影 | 最终一致 | 最高 | 见[第七节](#event-sourcing) |

> **最常见的误用**：一上来就做"读写库分离"。**但它的第一个成本项是"最终一致"**——用户改完资料立刻刷新页面看到旧数据，这是产品问题不是技术问题。**先确认业务能接受这个延迟，再拆读库。**

### 5.3 投影：读模型怎么维护 {#projection}

```text
写侧：Order（聚合）→ 领域事件 → 集成事件 → MQ
                                        ↓
读侧：投影器（Projector）消费事件 → 更新读模型
      读模型可能是：MySQL 宽表 / Redis / Elasticsearch / Doris / ClickHouse
```

| 投影要点 | 说明 |
|---|---|
| **可重放** | 投影器必须能从事件流重建读模型（否则读库丢了无法恢复）。**做法：记录消费位点 + 支持从某个 offset 重新消费** |
| **幂等** | 至少一次投递 → 投影器必须幂等 |
| **顺序** | 同聚合必须有序，否则读模型会退化成错误状态 |
| **可重建优于可修补** | 读模型出问题时，**重放一次比手工修数据更可靠** |

### 5.4 最终一致的三个产品化处理 {#eventual-consistency-ux}

技术上的最终一致必须翻译成用户体验，否则会被当成 bug：

| 做法 | 说明 | 适用 |
|---|---|---|
| **写回结果直接用** | 命令接口返回写入成功后的完整对象，前端直接用，不立刻查 | 最常见、成本最低 |
| **前端乐观更新** | 前端先按预期渲染，再对账 | 交互要求高的场景 |
| **读侧等待（read-your-writes）** | 写后的一小段时间内，查询强制走写库 | 用户"改完立刻看"的关键路径 |
| **降级提示** | 明确告知"数据同步中" | 数据延迟较长时（如报表） |

> **一条判据**：**如果这个"读不到"会引发用户投诉或数据误判（如看到旧余额就去转账），那这条路径就不该用最终一致。** 一致性级别应该按路径挑，而不是按整个系统一刀切。

## 六、事件溯源 {#event-sourcing}

### 6.1 核心思想与代价 {#es-core}

**事件溯源**（Event Sourcing）把"当前状态"这个存储目标换成"导致状态的所有事件"：

```text
传统做法：存当前状态
  account 表：id=1, balance=100
  → 不知道 100 是怎么来的；改错了无法回溯

事件溯源：存变化的事实，状态是推导结果
  AccountOpened(1, currency=CNY)
  MoneyDeposited(1, amount=200)
  MoneyWithdrawn(1, amount=100)
  → 当前 balance = 200 - 100 = 100
  → 完整历史、可回放、可审计、可时间旅行
```

| 收益 | 代价 |
|---|---|
| 完整审计历史（谁在什么时候改了什么，不可篡改） | **查询困难**：无现成宽表，必须配 CQRS 投影 |
| 可回放：修复 bug 后重放历史得到正确状态 | **事件版本演进**：schema 变更要做事件升级（upcasting），且**永不能改历史事件** |
| 可时间旅行：查"任意时点的状态" | **快照必要**：聚合事件多了以后重建要读上千条事件 |
| 天然的事件驱动，与 CQRS 天然契合 | **团队学习曲线陡**；与 ORM/CRUD 思维冲突 |
| 调试能力强（事件序列就是完整的因果链） | **删除/合规**：用户要求删除数据时，"不可变历史"与 GDPR/PIPL 冲突（需加密擦除等方案） |

### 6.2 什么时候值得用 {#es-when}

| 判据 | 说明 |
|---|---|
| **① 历史本身就是业务价值** | 账务流水、审计日志、交易记录——**"怎么变成现在这样"和"现在是什么"同样重要** |
| **② 需要回放/重算** | 规则变更后要按新规则重算历史（如费率调整后重算账单） |
| **③ 状态机复杂且需追溯** | 审批流、工单流转——需要完整的状态迁移轨迹 |
| **④ 团队有能力承担** | 有 CQRS、事件版本管理、投影重建的工程能力 |

**反向判据（不该用）**：

| 情况 | 为什么不该 |
|---|---|
| 只是 CRUD | 付出了全部代价，收益为零 |
| 需要频繁的复杂查询 | 每次查询都要投影，成本高 |
| 强一致的账务核心 | 事件溯源本身是最终一致（读侧），账务核心通常要强一致 |
| 团队没有事件驱动经验 | 会退化成"存了事件但没人会用" |

> **一句务实的话**：**事件溯源只适用于系统里很小的一块**（通常是核心域的账务/审计）。把整个系统做成事件溯源，是把最大的复杂度放在了最不需要它的地方。

## 七、组合：CQRS + ES + Saga {#combos}

| 组合 | 说明 | 注意 |
|---|---|---|
| **CQRS + ES** | ES 做写侧，CQRS 做读侧——**这是 ES 的标准配套**，因为 ES 自己不能查询 | 投影器要可重放 |
| **Saga + 事件** | 长流程跨多个服务，用 Saga 协调 | **编排（Orchestration）vs 编舞（Choreography）**：编排有一个中心协调者（易理解、易观测，但中心耦合）；编舞靠服务间互相订阅（解耦但难追踪） |
| **发件箱 + Saga** | 发起方用发件箱保证不丢，Saga 保证补偿 | 补偿操作必须幂等 |
| **CQRS + 缓存/搜索** | 读模型落在 Redis/ES | 见[多级缓存](/database/redis/multilevel-cache)与[搜索与检索](/search/) |

**编排与编舞的选择**：

| 维度 | 编排（Orchestration） | 编舞（Choreography） |
|---|---|---|
| 流程可见性 | **好**（协调者里有完整流程） | 差（要靠链路追踪拼） |
| 耦合 | 高（所有参与者依赖协调者） | 低 |
| 参与方数量 | 2~5 个合适 | 多且各自独立合适 |
| 流程变更 | 改协调者 | 改多方订阅关系（易漏） |

## 八、七条反模式 {#antipatterns}

| # | 反模式 | 问题 | 正确做法 |
|---|---|---|---|
| 1 | **把 CQRS 当默认架构** | 所有模块都做读写分离，成本剧增而收益为零 | **按模块选**：只有读写不对称明显的模块才做 |
| 2 | **事件当 RPC 用** | 发事件后同步等回复，等于用异步机制做同步调用 | 需要同步就用同步接口；事件只用于"不关心结果的后续动作" |
| 3 | **领域事件直发 MQ** | 内部模型变成公共契约，重构即破坏下游 | 边界处转换成**集成事件** |
| 4 | **事件不可重放** | 消费位点没记、投影器有副作用（发短信）→ 重放会重发通知 | 投影器**只改读模型**；外发动作另外走幂等通道 |
| 5 | **无版本管理** | 事件结构变了，老消息解析失败 | 事件带 `version`；新字段可空、老字段不删；用 upcasting 兼容旧事件 |
| 6 | **只用 id 不带状态** | 下游回调反查 → 回调风暴 + 强耦合 | 该带的状态要带上（[档位 2](#event-semantics)） |
| 7 | **忽略乱序** | 旧事件覆盖新状态 | 事件带序号/版本，消费侧比对后丢弃旧事件 |

## 九、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "领域事件和集成事件有什么区别？" | 领域事件是**内部模型**的一部分、不跨进程；集成事件是**对外契约**、需版本化与自包含。**不能把领域事件直接发 MQ** | [三种事件](/methodology/event-driven-cqrs#de-to-ie) |
| 2 | "事件的三种语义是什么？" | 事件通知（只带 ID，订阅方反查）→ 事件携带状态转移（带完整状态）→ 事件溯源（事件是唯一真相源），成本递增 | [三种语义](/methodology/event-driven-cqrs#event-semantics) |
| 3 | "只带 ID 的事件有什么问题？" | 下游反查导致强耦合 + 上游被打爆（**回调风暴**）；该带的状态要带上 | [档位选择](/methodology/event-driven-cqrs#event-semantics) |
| 4 | "先更新库再发消息有什么问题？" | 消息发送失败时数据库已改，下游永久不知道；**先发消息再更新库更糟**（下游基于假事实行动） | [三种错误写法](/methodology/event-driven-cqrs#three-broken-ways) |
| 5 | "事务性发件箱怎么保证不丢？" | 事件与业务数据**同库同事务**写入 outbox，再由轮询或 CDC 投递 | [发件箱](/methodology/event-driven-cqrs#outbox) |
| 6 | "发件箱的投递语义是什么？" | **至少一次**——保证不丢、不保证不重，因此消费方必须幂等 | [发件箱设计](/methodology/event-driven-cqrs#outbox) |
| 7 | "什么时候用发件箱、什么时候用 TCC/Saga？" | 流程是"我做完→通知别人做"用发件箱；"我必须等别人确认"才需要 TCC/Saga | [与分布式事务对比](/methodology/event-driven-cqrs#vs-distributed-tx) |
| 8 | "怎么保证消息有序？" | 全局有序不可达；保证**单聚合/单业务键有序**——用 `aggregateId` 当分区键；并用版本号兜底丢弃旧事件 | [顺序与分区](/methodology/event-driven-cqrs#ordering) |
| 9 | "什么会破坏顺序？" | 分区数变更、带延迟的重试、单分区内多线程消费 | [三个坑](/methodology/event-driven-cqrs#ordering) |
| 10 | "为什么要 CQRS？" | 读写关注点与访问模式完全不同（100:1 的量级差），塞进同一个模型会让领域模型被查询需求污染 | [读写不对称](/methodology/event-driven-cqrs#cqrs-why) |
| 11 | "CQRS 有哪两种形态？" | 同库读写模型分离（**强一致、成本低，先做这个**）与读写库分离（最终一致、成本中高） | [两种形态](/methodology/event-driven-cqrs#cqrs-forms) |
| 12 | "CQRS 最大的成本是什么？" | **最终一致**——它是产品问题不只是技术问题；读侧要处理"改完读不到"的体验 | [产品化处理](/methodology/event-driven-cqrs#eventual-consistency-ux) |
| 13 | "投影器要注意什么？" | **可重放**（记位点、能从 offset 重消费）、幂等、保序、只改读模型（不能有发短信这类副作用） | [投影](/methodology/event-driven-cqrs#projection) |
| 14 | "事件溯源解决什么问题？" | 把"存当前状态"换成"存导致状态的事件"——获得完整审计、可回放、可时间旅行、可重算 | [ES 核心](/methodology/event-driven-cqrs#es-core) |
| 15 | "事件溯源的代价是什么？" | 查询困难（必配 CQRS 投影）、事件版本演进、必须做快照、团队学习曲线、与"删除权"的冲突 | [ES 代价](/methodology/event-driven-cqrs#es-core) |
| 16 | "什么场景才值得用事件溯源？" | 历史本身是业务价值（账务/审计）、需要回放重算、状态机需完整追溯；**只适用系统里很小的一块** | [适用判据](/methodology/event-driven-cqrs#es-when) |
| 17 | "编排和编舞怎么选？" | 编排流程可见性好但中心耦合（2~5 个参与方合适）；编舞解耦但难追踪 | [组合](/methodology/event-driven-cqrs#combos) |
| 18 | "最终一致怎么保证不丢数据？" | 发件箱保证不丢 + 消费幂等保证不重复生效 + 投影可重放保证能修复 + 对账兜底 | [反模式](/methodology/event-driven-cqrs#antipatterns) |
