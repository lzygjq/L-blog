# Doris 数仓

## 一、问题场景：MySQL 撑不住分析查询 {#why-doris}

一个业务库在"能用"和"能分析"之间，隔着一条越来越宽的鸿沟：

| 场景 | MySQL 的表现 | 根因 |
|---|---|---|
| 全表聚合算日活 | 千万行级 `COUNT(DISTINCT)` 要秒级以上 | 行式存储必须**读完整行**才能取到一列 |
| 大宽表多维下钻 | 加一个维度就慢一截 | 没有列裁剪与向量化，全靠 B+ 树索引碰运气 |
| 高管看板并发打开 | 十几个看板查询把业务库 CPU 打满 | OLAP 与 OLTP 抢同一份资源 |
| 分库分表之后 | 跨分片聚合要靠应用层拼 | 中间件擅长路由，不擅长**大规模聚合** |

前三行是**存储模型与执行模型的差异**，第四行是**拆分带来的必然代价**。真正的解法是把分析负载**挪到另一个引擎**上去：数据仍然在 MySQL 里产生，但"算"发生在一个为列式与并行而生的系统里。

Doris 就是这个位置上的常见选择。它的取舍很清楚：**牺牲一部分极致的单表吞吐，换来 SQL 兼容性、并发能力与运维简单度**。

> **一句话定位**：Doris 是一个 MPP 架构的实时分析型数据库，兼容 MySQL 协议——"像 MySQL 一样用，但干的是数仓的活"。

## 二、架构：FE / BE 与两种部署形态 {#architecture}

### 2.1 只有两种进程 {#fe-be}

```
                    ┌──────────────────────────────────┐
      客户端 / BI ──▶│  FE（Frontend）                   │
      MySQL 协议     │  元数据 · SQL 解析 · 查询规划 · 权限 │
                    │  多 FE 之间走 Paxos 选主与日志复制   │
                    └───────────────┬──────────────────┘
                                    │  下发执行计划
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
      │  BE（Backend）│      │  BE（Backend）│      │  BE（Backend）│
      │  数据存储 +   │      │  数据存储 +   │      │  数据存储 +   │
      │  计算执行     │      │  计算执行     │      │  计算执行     │
      │  列式 + 向量化 │      │  多副本       │      │  Compaction  │
      └──────────────┘      └──────────────┘      └──────────────┘
```

| 角色 | 职责 | 关键点 |
|---|---|---|
| **FE** | 元数据管理、SQL 解析、查询规划、权限 | 不存数据；**多 FE 用 Paxos 保证高可用**（不用 ZooKeeper） |
| **BE** | 数据存储、计算执行、Compaction | 列式存储 + 向量化执行；数据按 Tablet 多副本分布 |

**"不依赖外部组件"是它相对传统大数据栈的最大工程优势**：一个实时数仓只需要部署 FE 和 BE 两组进程，不需要 ZooKeeper、不需要 Hadoop、不需要维护元数据服务。这一条直接决定了运维成本与故障面。

### 2.2 存算一体 与 存算分离 {#shared-nothing-vs-storage}

从 3.0 起，Doris 提供两种部署形态，**选错会直接反映在成本与延迟上**：

| | **存算一体**（Shared-Nothing） | **存算分离**（Shared-Storage，3.0+） |
|---|---|---|
| 数据位置 | BE 本地 SSD | 对象存储（S3 / OSS / HDFS） |
| BE 状态 | 有状态，数据在本地 | **无状态**，本地只做缓存 |
| 扩容 | 加节点要**搬迁数据**（rebalance） | 秒级弹性，加节点无需搬数据 |
| 多业务隔离 | 靠节点划分 | **计算组（Compute Group）** 共享一份数据、各自算力 |
| 成本 | 本地盘 + 多副本，成本随容量线性上升 | 冷数据沉到对象存储，**综合成本可降一半以上** |
| 尾延迟 | 更稳（本地读） | 受对象存储与缓存命中率影响 |
| 适合 | 30 节点以内、高 QPS、低延迟敏感 | PB 级、计算有潮汐、需要资源隔离 |

**存算分离不是没有代价的**，这一点常被忽略：BE 无状态后，Unique Key 模型的 Merge-on-Write 必须靠 Meta Service 的**分布式表锁**来消解"导入 / Compaction / Schema Change"之间的写写冲突。官方给出的工程约束是：

- 单表导入频率 **不超过 60 次/秒**，否则表锁争用明显；
- 分桶数 **8 ~ 64** 之间（Tablet 越多，锁争用越重）；
- 高写入压力下适当**降低 Compaction 频率**；
- 用**时间分区**（按天/按小时），让每次导入只落在少数分区上。

> 版本提示：3.1 对分布式表锁的实现做了显著优化。选存算分离时优先用较新的小版本。

## 三、表模型、分区与索引 {#table-model}

### 3.1 三种表模型：先选模型，再谈优化 {#models}

**表模型是性能的分水岭**——选错模型，后面所有调优都是在填坑。

| 模型 | 语义 | 用途 | 典型场景 |
|---|---|---|---|
| **Duplicate Key**（明细） | 完全不去重，追加写入 | 保留原始明细，写入吞吐最高 | 埋点日志、事件上报、链路追踪 |
| **Aggregate Key**（聚合） | 相同 Key 的 Value 列按 `SUM/MAX/MIN/REPLACE` 预聚合 | 写入即聚合，查询不再 `GROUP BY` | 固定报表、累计指标 |
| **Unique Key**（唯一） | 按主键唯一，新数据覆盖旧数据 | **行级更新**（UPSERT） | 订单状态、用户画像、OLTP 数据镜像 |

**关键版本事实**：Unique Key 模型在 3.x **默认走 Merge-on-Write（MOW）**——写入时即完成合并，做到**写入后秒级可查**，而不是查询时再去合并（Merge-on-Read 的读放大很大）。这让它从"能用"变成了"敢用"。

```sql
-- 唯一模型：适合"上游状态会变"的镜像表
CREATE TABLE ods_order (
  order_id     BIGINT       NOT NULL COMMENT '业务主键',
  status       VARCHAR(32)  REPLACE   COMMENT '状态，新值覆盖旧值',
  amount       DECIMAL(18,2) REPLACE,
  updated_at   DATETIME     REPLACE   COMMENT '作为 sequence 判新旧',
  dt           DATE         NOT NULL
)
UNIQUE KEY(order_id)
PARTITION BY RANGE(dt) ()                       -- 动态分区
DISTRIBUTED BY HASH(order_id) BUCKETS 16
PROPERTIES (
  "enable_unique_key_merge_on_write" = "true",
  "function_column.sequence_col"     = "updated_at",   -- 乱序到达时以它判新旧
  "dynamic_partition.enable"         = "true",
  "dynamic_partition.time_unit"      = "DAY",
  "dynamic_partition.start"          = "-30",
  "dynamic_partition.end"            = "3",
  "replication_num"                  = "3"
);
```

**`function_column.sequence_col` 是 Unique 模型最容易被忽略的一格**：CDC 或 MQ 场景下事件可能乱序到达，没有 sequence 列就会出现"旧值覆盖新值"。它解决的是[数据同步里的乱序问题](/bigdata/canal/#idempotency-order)。

### 3.2 分区与分桶 {#partition-bucket}

| 维度 | 作用 | 实务要点 |
|---|---|---|
| **分区（Partition）** | 数据裁剪的第一道闸门，也是**数据生命周期管理**的单位 | 按时间分区；`TRUNCATE PARTITION` 删整分区远比 `DELETE` 高效 |
| **分桶（Bucket）** | 决定数据在 BE 上的分布与并行度 | 键优先取 **JOIN / GROUP BY 的维度**，避免高基数列；**单桶 1~10 GB**，太多会加剧锁争用与小文件 |

**动态分区**（`dynamic_partition.*`）是把"按月手工建表"这件事消掉的关键：它自动预建未来分区、自动回收过期分区，是分区表能长期无人值守的前提。

### 3.3 四类索引 {#indexes}

| 索引 | 加速什么 | 备注 |
|---|---|---|
| **前缀排序索引**（Sorted Compound Key） | 排序列的前缀扫描 | 最多 3 列组成复合排序键，**字段声明顺序即排序顺序** |
| **Min/Max 索引** | 数值/日期的范围过滤 | 每个数据块记录极值，用于跳过 |
| **BloomFilter** | 高基数列的等值过滤 | 判断"一定不存在"，减少无效读 |
| **倒排索引**（Inverted Index） | 任意字段的全文检索与等值 | 3.1 引入 index v3 格式，**存储省约 20%**，并新增 ICU / IK / Basic 分词器 |

倒排索引是"要不要再单独上一套 ES"这个问题的分界线。它有明确的边界——**它替代的是"日志检索"这类场景，不是复杂的相关性排序**；但对"既能过滤又能全文搜"的混合查询，省掉一个组件就是净收益。

## 四、物化视图：把"重复计算"变一次计算 {#materialized-view}

| | **同步物化视图** | **异步物化视图**（3.0+ 成熟） |
|---|---|---|
| 基表范围 | 单表 | **多表 JOIN** |
| 刷新 | 随基表导入自动、增量 | 定时刷新 / 手动刷新，按分区增量 |
| 查询改写 | 优化器自动透明改写 | 自动透明改写（含跨分区补偿） |
| 存储 | 独立物理表 | 独立物理表 |

**`grace_period`（数据宽容期）是异步物化视图的必配项**：在宽容期内，即使基表有新数据、视图还没刷新，优化器也照样用视图作答。不设它，视图会频繁失效——刷新和查询互相追着跑，命中率趋近于零。

> 版本补充：3.1 把"异步物化视图的分区构建"与"透明改写分区补偿"引入了数据湖（Iceberg / Paimon），在湖与仓之间架了一座桥。

## 五、写入链路：四条路怎么选 {#ingest}

| 链路 | 形态 | 适合 | 注意 |
|---|---|---|---|
| **Stream Load** | HTTP 微批，客户端直推 | 业务服务直接写、文件导入 | **`label` 全局唯一保证幂等**；单批 100~500 MB、攒批 5~10 秒是常用区间 |
| **Routine Load** | Doris 主动从 Kafka 持续消费 | **CDC / 消息流落地** | 消费进度由 Doris 维护，不需要外部消费者 |
| **Broker Load** | 从对象存储 / HDFS 批量导入 | 历史数据回填、批量同步 | 适合大文件，延迟不敏感 |
| **INSERT INTO ... SELECT** | SQL 内部 ETL | 仓内层间加工（ODS → DWD） | 慎用在大表高频场景 |

**写入侧的三条纪律**（都是"别把分析库当业务库"的具体化）：

1. **不要高频单行 INSERT**（官方建议 > 100 TPS 就该换方式）。每次 INSERT 都是一个事务，开销远大于微批。要么攒批，要么开 **Group Commit** 让小批自动合并。
2. **不要用 UPDATE DML 做高频更新**，优先用**导入式更新**（Stream / Routine Load 写 Unique 模型）。3.x 的能力演进也在这条线上：**部分列更新** → 3.1 的**灵活列更新**（同一批里每行可更新不同的列），让"多数据源拼宽表"不需要先做实时 JOIN。
3. **不要用 `DELETE` 删整分区**，用 `TRUNCATE PARTITION`；Duplicate / Aggregate 模型上的高频 `DELETE` 会让谓词不断累积，拖慢后续所有查询。

## 六、查询加速与更新的代价 {#query-update}

查询侧的四个主要手段：

- **MPP + 向量化执行**：内存结构按列布局、利用 SIMD，宽表聚合场景比非向量化引擎快 5~10 倍；
- **Runtime Filter**：运行时把探测端（小表）的过滤条件下推到被探测端（大表），大幅减少 JOIN 的扫描量；
- **CBO + RBO 优化器**：结合代价与规则；
- **UV 类指标换算法**：用 `BITMAP_UNION_COUNT` 或 `APPROX_COUNT_DISTINCT` 替代 `COUNT(DISTINCT)`，能把这类查询从"秒级"拉到"毫秒级"——**这是成本最低的一次性优化**。

**更新不是免费的**：每一次写入都要付出 Compaction 的代价。Compaction 把增量文件合并成基线，合并跟不上写入速度就会堆积、查询变慢、最终写入受限。这是所有 LSM 系存储的共性，也是"分区分桶要合理 + 不要高频单行写"的根本原因。

> **4.0 的方向**（2026-09 时点）：一个引擎同时做结构化分析、全文检索与**向量检索**——向量索引（HNSW / IVF，支持 flat / sq8 / sq4 量化）+ SQL 内直接调用大模型的 AI 函数 + 类 Elasticsearch 的 `SEARCH()` 语法，对外叫 **HSAP（Hybrid Search and Analytics Processing）**；工程侧补上 **Spill Disk（算子落盘）** 让大 ETL 任务不再因内存爆掉失败。取向很明确：**让"再上一套向量库 / 检索引擎"变成不必要的开支**。

## 七、对比辨析 {#compare}

| 对比 | 差别 | 何时选后者 |
|---|---|---|
| **Doris / MySQL** | 列式 MPP 分析 vs 行式事务 | 需要事务、强一致单行读写 → MySQL；Doris 不提供 `FOR UPDATE` 等 OLTP 语义 |
| **Doris / ClickHouse** | 并发与多表 JOIN 强 vs 单表超大吞吐强 | 单表极宽、写入极大、几乎不 JOIN → ClickHouse |
| **Doris / StarRocks** | 引擎能力相近，差异更多在生态与社区 | 看团队既有技术栈与商业化支持 |
| **Unique / Duplicate 模型** | 主键覆盖 vs 追加不去重 | 只要明细、不需更新 → Duplicate（写入吞吐更高） |
| **Aggregate / 物化视图** | 写入时聚合 vs 查询时改写 | 维度组合多、需要灵活下钻 → 物化视图 |
| **存算一体 / 存算分离** | 本地盘低尾延迟 vs 弹性与低成本 | 数据量大、负载有潮汐 → 存算分离 |
| **同步 / 异步物化视图** | 单表自动增量 vs 多表定时刷新 | 需要跨表预计算 → 异步（记得配 `grace_period`） |

## 八、使用场景与面试问答 {#interview}

**Q1：Doris 的 FE 和 BE 分别做什么？为什么说它"部署简单"？**
FE 负责元数据、SQL 解析、查询规划与权限，不存数据，多 FE 之间用 **Paxos** 做高可用；BE 负责数据存储与计算执行，列式存储 + 向量化。**简单是因为它不依赖 ZooKeeper、Hadoop 这类外部组件**——整个集群只有两种进程，故障面与运维成本都远小于传统大数据栈。

**Q2：三种表模型怎么选？**
按"数据会不会被改"分：**纯追加、只要明细 → Duplicate**；**固定维度的指标、写入即聚合 → Aggregate**；**有主键、状态会变 → Unique**。Unique 模型在 3.x 默认 MOW，写入即合并、秒级可查，但**它适合慢变数据，不适合承接高频单行更新**——那种负载应该留在 MySQL。

**Q3：存算一体和存算分离怎么选？存算分离有什么代价？**
数据量小、高 QPS、延迟敏感 → 存算一体（本地 SSD，尾延迟更稳）；PB 级、计算有潮汐、要多业务隔离 → 存算分离（BE 无状态、数据落对象存储、计算组隔离）。**代价是 Unique 模型的 MOW 要走 Meta Service 的分布式表锁**：单表导入建议 ≤ 60 次/秒、分桶 8~64、必要时降低 Compaction 频率，否则锁争用会明显拖慢导入。

**Q4：分区分桶怎么设计？**
分区是**数据裁剪 + 生命周期管理**的单位，按时间（天/小时）分区，用动态分区自动建与回收；分桶决定分布与并行度，键优先取 JOIN / GROUP BY 的维度，**避免高基数列**，单桶控制在 1~10 GB。分桶过多会同时加剧小文件问题与锁争用。

**Q5：为什么不要用 DELETE 清理历史数据？**
因为 Duplicate / Aggregate 模型上的 `DELETE` 是通过**谓词累积**实现的，删一次就多留一份谓词，之后所有查询都要额外做判断。**删整分区一律用 `TRUNCATE PARTITION`**，既高效又不留副作用。

**Q6：物化视图为什么必须配 `grace_period`？**
异步物化视图按定时任务刷新，而查询随时可能到来。没有宽容期时，基表刚有新数据、视图还没刷新，优化器就认为视图不可用而回退到基表——视图命中率极低、等于白建。**`grace_period` 允许"用稍旧的数据作答"**，用可接受的数据新鲜度换稳定的查询加速。

**Q7：一个分析查询慢，你会按什么顺序排查？**
先看 **Query Profile**：扫描行数、各节点传输的数据量、是否发生数据倾斜。然后按刀口试：① 过滤字段是否命中前缀排序索引（索引列顺序对不对）；② 高基数列要不要加 BloomFilter / 倒排索引；③ UV 类指标有没有用 `BITMAP_UNION_COUNT` / `APPROX_COUNT_DISTINCT`；④ 分区裁剪是否生效（谓词写在分区列上、没有函数包住）；⑤ JOIN 有没有吃到 Runtime Filter；⑥ Compaction 分数是否偏高（说明写入侧积压把读拖慢了）。
