# 时间语义与水印

## 一、问题场景：批处理里根本不存在的问题 {#why-time}

先看一个对比。

批处理算"昨天的订单总额"，逻辑是一行 SQL：

```sql
SELECT sum(amount) FROM orders WHERE dt = '2026-09-15';
```

这里**时间是一个过滤条件**——数据落在哪一天，是数据的属性，永远不会变、也不会晚到。批处理之所以简单，是因为它有一个隐含前提：**算的时候，数据已经全了。**

流处理没有这个前提。它算的不是"昨天的总额"，而是"**每当有新订单，把最近 5 分钟的总额更新一次**"。这时会出现三个批处理里从未存在的问题：

| 问题 | 批处理的答案 | 流处理必须回答 |
|---|---|---|
| 数据**晚到**了怎么办 | 不存在（数据已全） | 等多久？等不到的怎么办？ |
| 用**哪个时间**算 | 数据的 `dt` 字段 | 事件时间？还是我收到它的时间？ |
| 什么时候**算一次** | 任务跑完就一次 | 凭什么说"这 5 分钟的数据齐了，可以算了" |

第三个问题最难。**流是无界的，你永远不知道"后面还有没有"**——一个 10:00:00 产生的订单，可能在 10:00:03 到达，也可能因为网络抖动在 10:00:40 到达，还可能因为上游补数在明天才到达。

所以流处理需要一个机制来回答："**我认为某个时间点之前的数据都到齐了。**" 这个机制就是**水印（Watermark）**。

> **本板块的主线可以压成一句话**：流处理的全部复杂性，来自"数据无界 + 到达乱序 + 系统会失败"这三件事。**这一篇讲第一件（时间），下一篇讲第二三件（状态与失败）。**

## 二、三种时间语义 {#time-semantics}

同一笔订单，在系统里至少有三个"时间"：

```
        订单在业务库生成          被 CDC 捕获            到达 Flink           被算子处理
              │                      │                     │                    │
   事件时间 ──┼──────────────────────┼─────────────────────┼────────────────────┤
 (Event Time) │                      │                     │                    │
              │                      │  摄入时间            │                    │
              │                      ├─────────────────────┤                    │
              │                      │ (Ingestion Time)    │                    │
              │                      │                     │  处理时间           │
              │                      │                     ├────────────────────┤
              │                      │                     │ (Processing Time)  │
         ─────┴──────────────────────┴─────────────────────┴────────────────────▶  真实世界时间
              │◀──── 传输延迟 ───────▶│◀──── 排队/背压 ─────▶│
```

| 语义 | 取值来源 | 结果可重放吗 | 适用 |
|---|---|---|---|
| **事件时间** | 数据自带的时间戳（业务发生时刻） | ✅ 同样输入必得同样输出 | **绝大多数场景的正确选择** |
| **摄入时间** | 数据进入 Flink 的机器时间 | ❌ 换台机器、重跑一次就不同 | 很少用——它既没有事件时间的确定性，也没有处理时间的简单 |
| **处理时间** | 算子在处理这条数据时的机器时间 | ❌ 完全不确定 | 只看"当下状态"的场景（如实时大屏的最新值）、以及不需要重放的监控 |

**为什么"可重放"这么重要**：一个流作业上线后，你一定会遇到三种需要"重跑"的情况——改逻辑后想验证结果对不对、故障恢复后想确认没算错、以及出了口径问题要定位是哪一步开始错的。**如果语义不确定，这三种情况都无法用"重跑一遍对账"来解决**，因为你没法知道差异是 bug 还是时间本身在变。

所以工程上的默认选择是：**能用事件时间就用事件时间**；只有明确不需要重放、且对延迟极度敏感的场景才用处理时间。

摄入时间在实践中几乎不选，它唯一的历史用途是"数据源没有可靠时间戳、又不想用处理时间"的折中——而这种情况下更常见的做法是**在源头补一个时间戳字段**。

## 三、水印到底是什么 {#what-is-watermark}

### 3.1 它不是一个"保证"，是一个"进度声明" {#watermark-def}

最常见的误解是把水印理解成"**水印之前的数据一定都到了**"。这个理解会直接导致一个错误的预期：以为配了水印就万无一失。

准确的定义是：

> **水印 `W = t` 表示：我认为**事件时间 ≤ t 的数据**已经到齐了。这是一个**由你配置的等待策略所做出的声明**，不是系统的事实。

区别在于：水印是**由你决定的赌注**。"我认为 5 秒的乱序够了"——如果真实世界出现了 30 秒的乱序（比如上游补数），那些数据就会在水印越过窗口之后才到，成为**迟到数据**。

水印的两个关键性质：

| 性质 | 含义 | 工程后果 |
|---|---|---|
| **单调递增** | 水印只会往前走，不会回退 | 一旦越过了某个窗口的结束时间，那个窗口就触发了；不可能"撤回" |
| **由配置决定而非事实** | 它是对乱序程度的假设 | 假设过松 → 结果错（丢迟到数据）；假设过紧 → 延迟高 |

**水印不是过滤器，是触发器。** 它不负责丢弃数据，只负责宣告"可以算了"。真正的丢弃发生在窗口关闭之后——这是理解 `allowedLateness` 的前提（见第六节）。

### 3.2 谁生成水印：策略 = 时间戳分配 + 水印生成 {#strategy}

Flink 里水印由 `WatermarkStrategy` 产生，它由两个可组合的部分构成：

| 部分 | 作用 | 常见实现 |
|---|---|---|
| **时间戳分配器** | 从每条记录里**取出**事件时间 | 读某个字段：`withTimestampAssigner((e, ts) -> e.getEventTime())` |
| **水印生成器** | 决定水印**怎么推进** | 周期性（默认，每 200ms）、标点式（遇特定标记才推进） |

最常用的一行是**有界乱序**：

```java
WatermarkStrategy<Event> strategy = WatermarkStrategy
    .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(5))   // 容忍 5 秒乱序
    .withTimestampAssigner((e, ts) -> e.getEventTime())
    .withIdleness(Duration.ofMinutes(1));                     // 空闲分区不顶住水印

env.fromSource(kafkaSource, strategy, "orders");
```

`forBoundedOutOfOrderness(Duration.ofSeconds(5))` 的语义必须逐字理解：

> **每来一条时间戳为 `t` 的记录，水印推进到 `t - 5s`。**

也就是说 **5 秒是"最大乱序容忍"，代价是每个窗口的输出都延迟 5 秒**。这是一个直接的交换，没有免费的选项：

| 容忍度配置 | 结果正确性 | 输出延迟 |
|---|---|---|
| 0（`forMonotonousTimestamps`） | 只要有任何乱序就会丢数据 | 最低 |
| 5 秒 | 乱序 ≤ 5 秒的数据不丢 | 每个窗口 +5 秒 |
| 1 小时 | 几乎不会丢，但也能容忍"上游停摆一小时才恢复" | 每个窗口 +1 小时，**实时性已经没了** |

**怎么定这个值**：不要拍脑袋。正确做法是**先量**——统计上游数据"事件时间"与"到达时间"的差值的 P99/P999，取一个略大于 P999 的值。这个数据可以从源头（如 Kafka 消息自带的时间戳）或链路日志里统计出来。

### 3.3 水印的传播：为什么多输入取最小值 {#propagation}

水印在 DAG 里向下游传播，规则有两条：

```
             上游 A 分区1   W=100  ─┐
             上游 A 分区2   W=120  ─┼─▶ min = 100
             上游 A 分区3   W=95   ─┘        │
                                            │  算子只在"所有输入的水印都越过"后才推进
             上游 B（维表广播）W=1000 ───────┼─▶ 取 min → 仍为 100
                                            ▼
                                    下游算子收到 W=100
```

| 场景 | 规则 | 为什么 |
|---|---|---|
| 单个算子的多个**输入分区** | 取**最小值** | 最慢的那个分区决定了整体进度——只要有一个分区还没到 100，就不能说 100 之前的数据齐了 |
| 算子的多个**上游算子** | 取**最小值** | 同上：任何一路没到，处理该时间点的数据就是不完整的 |
| 向下游**广播** | 所有下游都收到同一个水印 | 下游会各自与其它输入取 min |

**取 min 而不是取 max，是保守的选择**——取 max 会让慢的那一路的数据被当作"迟到"而无法进入窗口。代价是：**任何一路卡住，整个作业的输出都会停**。这就是下面这个生产中最常见的坑。

### 3.4 空闲分区顶住水印（生产环境最高频的"窗口不输出"根因）{#idleness}

**现象**：作业跑起来，来了数据，但**窗口一直不输出**；或者白天正常、夜里变成几小时才输出一次。

**机理**：假设按 `user_id` 分了 4 个分区消费 Kafka。夜里大部分用户不活跃，只有 1 个分区有数据：

```
  分区1  W=10:05  ← 有新数据，水印持续前进
  分区2  W=10:00  ← 没有新数据，水印永远停在最后一次读到的位置
  分区3  W=09:58  ← 同上
  分区4  W=10:02  ← 同上
        │
        ▼  取 min
   算子水印 = 09:58  ← 被三个"死"分区顶住，永远过不去
        │
        ▼
   窗口结束时间 10:00 的窗口要求 W ≥ 10:00 → 永不满足 → 永不输出
```

**这不是 bug，是语义的必然结果**：从算子的角度看，"分区 3 的水印停在 09:58"意味着"分区 3 可能有 09:58 之后的数据还没来"——它没有理由认为可以往前走了。

**解法是显式告诉它"这个分区暂时没数据，别等了"**：

```java
.withIdleness(Duration.ofMinutes(1))   // 超过 1 分钟没有数据的输入会被标记为 idle
```

标记为 idle 的分区**不再参与 min 计算**，水印就能继续前进。当它重新有数据时，idle 标记自动解除、重新参与。

| 配置 | 后果 |
|---|---|
| 不配 `withIdleness` | 空闲分区永久顶住水印；窗口只在"所有分区都有数据"时才输出 |
| 配得太短（如 10s） | 正常波动也被判为空闲 → 水印被"虚推"前进 → **迟到的数据变成真正的迟到数据（丢）** |
| 配得合理（如分区最大静默间隔的 2~3 倍） | 兼顾两者 |

⚠️ **`withIdleness` 是"用正确性换延迟"的又一处**：它主动放弃了"等待那个分区"的可能性。所以它的值必须大于业务上真实存在的空闲间隔——比如按小时调度的上游任务，它的分区每小时只活跃几秒，这种情况下 `withIdleness` 本身就说明**分区策略有问题**（应该让上游按事件时间均匀写，而不是让部分分区长时间空转）。

### 3.5 水印对齐 vs 不对齐：这是另一个层面的问题 {#alignment}

容易混淆：**水印对齐（watermark alignment）** 与 **检查点屏障对齐（barrier alignment）** 是两件事。

| 概念 | 解决什么 | 与什么相关 |
|---|---|---|
| **水印对齐** | 多个上游的水印推进速度差异过大时，快的一方被慢的一方拖住 | **时间进度**（本篇主题） |
| **屏障对齐** | 检查点期间需要等待所有输入到达同一个屏障位置 | **一致性**（下一篇主题） |

水印对齐的思路是：不让快的水印无限往前冲（那会积压大量状态），而是**限制它领先最慢的水印不超过某个阈值**：

```yaml
# config.yaml
execution.checkpointing.watermark-alignment.enabled: true
execution.checkpointing.watermark-alignment.max-drift: 30s
```

它在"某些上游数据量骤增"的场景下有用（否则快的那一路会攒下巨量窗口状态）。Flink 1.16 起支持。**注意 2.0 起配置文件已由 `flink-conf.yaml` 改名为 `config.yaml`**（见第四节）。

## 四、版本现状（2026-09）{#version}

这一节的内容与本文原理无关，但**直接影响你能不能照抄网上的配置**：

| 事实 | 说明 |
|---|---|
| **Flink 2.0.0 于 2025-03-24 GA** | 自 1.0 以来首次大版本；此后 2.1.0（2025-07-31）、2.2.0（2025-12-04）、2.2.1（2026-05-15 稳定版）、2.3.0（2026-06-25） |

| **1.x 与 2.x 状态不兼容** | 升级不能靠 savepoint 直接跨大版本恢复，需规划"无状态重建"或"全量重算"；官方建议存量作业留在 1.x LTS（1.x 最后版本线为 1.20.x） |

## 五、窗口：水印的消费方 {#windows}

### 5.1 窗口类型与它们的"代价" {#window-types}

水印是"什么时候可以算"的信号，而**"算什么"由窗口定义**。四类窗口的本质区别是**每个元素被放进几个窗口**：

```
滚动窗口（Tumbling）—— 每个元素属于 1 个窗口，窗口不重叠
  ├────────────┼────────────┼────────────┤
        W1           W2           W3

滑动窗口（Sliding，size=20s, slide=10s）—— 每个元素属于多个窗口，有重叠
  ├────────────┼────────────┤
       W1
            ├────────────┼────────────┤
                  W2

会话窗口（Session，gap=30s）—— 按数据间隔切分，长度不固定
  ├─W1─┤        ├───W2───┤   ├W3┤
       ↑gap 超过阈值就断开

累计窗口（Cumulate，1d / 每 1h 更新）—— 同一窗口内"步进式"累积
  [1h][1h+1h][1h+1h+1h] ... 到一天结束
```

| 类型 | 每个元素的窗口数 | 状态开销 | 典型用途 |
|---|---|---|---|
| 滚动 | 1 | 最小 | 定长统计（每分钟、每小时） |
| 滑动 | size / slide | **大**（slide 远小于 size 时成倍放大） | 平滑曲线、最近 N 分钟 |
| 会话 | 1 | 中（窗口数是数据决定的，可能很碎） | 用户行为会话、点击流 |
| 累计 | size / step | 大 | 当日累计（大屏的"今日累计"） |

⚠️ **滑动窗口的状态开销容易被低估**：`size=1h, slide=1s` 意味着每个元素存在于 **3600** 个窗口里。这不是"性能略差"，是会直接把状态撑爆。**判据：`size/slide > 10` 就要重新审视需求**（多数"最近一小时"的看板其实用 `slide=1min` 足够）。

### 5.2 窗口什么时候触发 {#trigger}

一个窗口输出，需要**同时满足两个条件**：

1. **水印越过了窗口的结束时间**（`watermark >= windowEnd`）
2. **窗口内有数据**（Flink 默认不输出空窗口；要输出空窗口需显式开启）

这里有一个必须记住的口径：

> **窗口的结束时间是"开区间"，即 `[start, end)`。** 10:00:00 的这条记录属于 9:55~10:00 那个 5 分钟窗口，**不属于 10:00~10:05**。

第二个容易踩的点：**分组聚合里，没有数据的分组不会输出**。如果业务上需要"某个 key 这一分钟计数为 0"，Flink 的窗口聚合给不出来（那需要另一个思路：先用一个固定 key 集合做左连接，或者由下游补零）。

## 六、迟到数据的三条出路 {#late-data}

水印过去了，但数据才到——这就是迟到数据。Flink 给了三条路，**它们不是并列的选择，而是"按迟到程度递进"的三档**：

```
   事件到达
      │
      ▼
  当前水印 是否已越过该窗口的 end？
      │
      ├── 否 ──────────────────▶ 正常进入窗口，正常输出
      │
      └── 是 ──▶ 窗口是否还在 allowedLateness 范围内？
                    │
                    ├── 是 ──▶ 进入窗口，**窗口重新输出一次**（结果被更新）
                    │
                    └── 否 ──▶ 走侧输出流（side output）或直接丢弃
```

### 6.1 第一档：正常入窗 {#late-normal}

水印还没过，说明"等待期"还没用完。这是绝大多数数据的归宿。

### 6.2 第二档：`allowedLateness` —— 允许窗口"反悔" {#allowed-lateness}

```java
.windowAll(TumblingEventTimeWindows.of(Duration.ofMinutes(5)))
.allowedLateness(Duration.ofMinutes(2))
.sideOutputLateData(lateTag)
```

语义：**窗口在水印越过之后，不立即销毁，而是再保留 2 分钟**。这 2 分钟内到达的属于该窗口的数据，会让窗口**基于完整数据重新计算并再输出一次结果**。

⚠️ **这里有两个必须理解的后果**：

| 后果 | 说明 |
|---|---|
| **同一个窗口会输出多次** | 下游必须能处理"同一 key、同一窗口、多条结果"，即**结果流是 upsert 语义而不是 append 语义** |
| **状态占用时间变长** | 窗口状态要多保留 2 分钟；`allowedLateness` 配得越大，状态越大、检查点越重 |

**所以 `allowedLateness` 不是"安全垫"**——它把正确性的问题转移给了下游（下游要么用 upsert 写入，要么自己再去重）。如果下游是只支持 append 的场景（如写日志文件），用 `allowedLateness` 会产生重复统计。

### 6.3 第三档：侧输出流 {#side-output}

超出 `allowedLateness` 的数据被送到一条**旁路**，主流程不受影响：

```java
OutputTag<Event> lateTag = new OutputTag<Event>("late") {};

SingleOutputStreamOperator<Stat> windowed = stream
    .keyBy(Event::getKey)
    .window(TumblingEventTimeWindows.of(Duration.ofMinutes(5)))
    .allowedLateness(Duration.ofMinutes(2))
    .sideOutputLateData(lateTag)
    .aggregate(new MyAgg());

// 主流程
windowed.sinkTo(mainSink);
// 旁路：迟到数据单独收集，用于对账 / 告警 / 补算
windowed.getSideOutput(lateTag).sinkTo(lateSink);
```

**旁路的价值不在"存起来"，而在"能被看见"**：迟到数据的量是**衡量水印配置是否合理的唯一客观指标**。

| 观测到的情况 | 说明 | 动作 |
|---|---|---|
| 迟到数据几乎为 0 | 水印配置偏保守（延迟白等了） | 可以适当收紧容忍度，降低延迟 |
| 迟到数据持续少量存在 | 正常 | 维持，保留旁路做对账 |
| 迟到数据周期性尖峰 | 上游有定时补数/批量回刷 | **不是水印问题，是上游行为问题**——应让补数走单独的批通道，不要混进实时流 |
| 迟到数据突然大量出现 | 上游变更、网络抖动、或作业本身发生长时间背压/重启 | 需要定位根因，而不是调大水印容忍度 |

> **一条纪律**：水印容忍度**不该靠"感觉"调**。先上线一个保守值（宁可延迟高），把侧输出流的量监控起来，再根据实际迟到分布收紧——**这是唯一有数据支撑的调法**。

## 七、对比辨析 {#compare}

### 7.1 水印 vs 窗口 vs 触发器 {#vs-trigger}

三个概念经常被混为一谈，它们是流水线上的三个角色：

| 概念 | 回答的问题 | 由谁决定 |
|---|---|---|
| **时间语义** | 用哪个时间 | 你在 `WatermarkStrategy` 里的选择 |
| **水印** | 什么时候认为"齐了" | 你配的乱序容忍度 + 空闲策略 |
| **窗口** | 每个元素属于哪几段 | 你的窗口类型与参数 |
| **触发器** | 满足什么条件时输出结果 | 默认是"水印越过窗口 end"，可自定义（如"每 1000 条输出一次"） |

**"窗口不输出"几乎总是水印的问题，"窗口输出太多"几乎总是触发器或 `allowedLateness` 的问题。** 这条判据能省掉大量排查时间。

### 7.2 事件时间 vs 处理时间：什么场景真的该用处理时间 {#vs-processing-time}

不要因为"事件时间更正确"就一律用它。少数场景处理时间更合适：

| 场景 | 建议 | 理由 |
|---|---|---|
| 业务口径的统计（订单、支付、行为） | 事件时间 | 必须可重放、可对账 |
| 系统自身的运行监控（"当前队列积压"） | 处理时间 | **关注的就是"此刻"**，用事件时间反而无意义 |
| 上游完全没有可靠时间戳 | 补一个来源，再用事件时间 | 用处理时间会把链路延迟当成业务时间 |
| 需要极低延迟、允许丢弃 | 处理时间 | 省掉等待容忍度的延迟 |

## 八、使用场景与面试问答 {#interview}

**Q1：水印是什么？它能保证数据不丢吗？**

水印是一条**单调递增的时间戳断言**，表示"我认为事件时间 ≤ 它的数据已经到齐了"。它**不能保证不丢**——它只是你配置的一个**等待策略**（"我以为最多乱序 5 秒"）。真实乱序超过这个假设时，数据就会成为迟到数据。要检查这个假设是否合理，唯一可靠的办法是**监控侧输出流的迟到数据量**。

**Q2：为什么多输入算子的水印取最小值？**

因为算子要处理某个时间点的数据时，必须确保所有输入在该时间点的数据都已到达。只要有一路没推进到那，处理就是不完整的。取 min 是保守但正确的选择。**代价是任何一路卡住都会拖住整体**——空闲分区必须用 `withIdleness` 显式排除，否则窗口永远不输出。

**Q3：作业白天正常，夜里几小时才输出一次，怎么排查？**

典型的水印被空闲分区顶住。判据：查看各输入分区的 **currentWatermark 指标**（WebUI 的水印页面或 Metrics），如果部分分区的水印长时间不动，而其它分区在推进，那就是它。修法是 `withIdleness`，值取该分区正常静默间隔的 2~3 倍。若分区按小时调度、静默本身就是常态，说明**分区策略应该改**（让上游按事件时间均匀写）。

**Q4：`allowedLateness` 和"把水印容忍度调大"有什么区别？**

两者都让更晚的数据被算进去，但作用面不同：

| | 影响范围 | 代价 |
|---|---|---|
| 调大水印容忍度 | **所有**窗口的触发时间都推迟 | 全局延迟上升 |
| `allowedLateness` | 只影响**指定窗口**在触发后的保留时长 | 该窗口可能输出多次，下游要有 upsert 能力 |

正确做法通常是**两者都不用去硬扛上游补数**——补数应该走单独的批通道回刷，而不是混进实时流里等。

**Q5：滑动窗口为什么会把状态撑爆？**

因为每个元素属于 `size / slide` 个窗口。`size=1h, slide=1s` 时每个元素同时存在于 3600 个窗口的状态里。判据：`size / slide > 10` 就要重新审视需求，多数"最近一小时"的看板用 `slide=1min` 已足够。

**Q6：Flink 2.0 之后，网上抄的配置为什么跑不通？**

因为 2.0 是一次**破坏性升级**：配置文件由 `flink-conf.yaml` 改名为 `config.yaml`；`DataSet` API、Scala `DataStream`/`DataSet` API、`SourceFunction`/`SinkFunction`/`Sink V1` 等被**彻底移除**（不是废弃）；per-job 部署模式移除；最低 Java 11。另外 **1.x 与 2.x 状态不兼容**，不要指望 savepoint 直接跨版本恢复。本文涉及的水印 API 本身没变，可以直接用。
