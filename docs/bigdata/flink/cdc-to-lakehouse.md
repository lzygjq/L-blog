# Flink CDC 与入湖入仓

## 一、问题场景：流处理的两个"接口" {#why}

前四篇讲的是**引擎内部**：时间怎么定义、状态怎么保命、SQL 怎么写、跑不住怎么调。

但一个作业要真正工作，还差两头：

```
   数据从哪来（上游接口）              数据到哪去（下游接口）
   ┌────────────────────┐            ┌────────────────────┐
   │  业务库的变更        │            │  分析引擎的写入      │
   │  MySQL / PG / Oracle│  ═══════▶  │  Doris / Paimon /   │
   │  MongoDB / SQLServer│   本篇      │  Iceberg / Kafka    │
   └────────────────────┘            └────────────────────┘
              │                                 │
              └──── 这两个接口的"语义"决定了 ────┘
                    端到端能不能做到一致
```

**这一篇的两个关键结论**：

| 结论 | 说明 |
|---|---|
| **入口用 Flink CDC 的最大收益是"无锁全量 + 增量自动接续"** | 不必先停业务导出全量、再配增量——这两件事本身就是最容易出错的地方 |
| **出口的两个阵营：写"库/仓"（Doris）与写"湖"（Paimon/Iceberg）** | 前者靠 Stream Load 的两阶段提交，后者靠湖格式的原子提交。**两者的 exactly-once 实现路径完全不同** |

## 二、Flink CDC：两种用法 {#two-usages}

### 2.1 用法一：Pipeline（声明式整库同步）{#pipeline}

Flink CDC 3.x 引入了 **Pipeline**：把"整库同步"写成一份 **YAML**，而不是一段 Flink SQL。

```yaml
# 整库同步的价值：几十张表不用手写几十个 CREATE TABLE
source:
  type: mysql
  hostname: mysql
  port: 3306
  username: cdc
  password: '******'
  tables: biz\.orders|biz\.payments   # 支持正则：一次声明一批表
  server-id: 5400-5404                # ⚠️ 必须与已有从库不冲突

sink:
  type: doris                        # 或 paimon / kafka / starrocks
  fenodes: doris-fe:8030
  # ...

pipeline:
  name: mysql-to-doris
  parallelism: 4
```

`flink-cdc.sh ./sync.yaml` 即可提交。它的三个价值：

| 价值 | 说明 |
|---|---|
| **表级自动建表** | 目标端没有对应的表时自动创建（类型映射），不必手工建 |
| **表结构变更自动跟随** | 上游 `ADD COLUMN` 能同步到下游（有边界，见 4.3） |
| **整库规模声明** | 用正则表达"要哪些表"，新增表不必改作业 |

**用 Pipeline 还是自己写 SQL**：

| 场景 | 选择 |
|---|---|
| 整库/大批表同步到同一个目标 | **Pipeline**（省掉几十份 DDL 与建表映射） |
| 需要在中间做复杂加工（多流 join、聚合） | SQL / DataStream（Pipeline 的表达能力有限） |
| 单表、或表结构差异需要精细控制 | SQL connector |

### 2.2 用法二：SQL connector（可加工）{#sql-connector}

```sql
CREATE TABLE orders (
  id        BIGINT,
  user_id   BIGINT,
  amount    DECIMAL(10,2),
  order_time TIMESTAMP(3),
  PRIMARY KEY (id) NOT ENFORCED
) WITH (
  'connector' = 'mysql-cdc',
  'hostname' = 'mysql',
  'port' = '3306',
  'username' = 'cdc',
  'password' = '******',
  'database-name' = 'biz',
  'table-name' = 'orders',
  'server-time-zone' = 'Asia/Shanghai'      -- ⚠️ 不加会用 UTC，时间整体差 8 小时
);

-- 完整能力：可以 join、聚合、写多目标
INSERT INTO dwd_order_wide
SELECT o.id, o.user_id, u.level, o.amount, o.order_time
FROM orders AS o
JOIN users FOR SYSTEM_TIME AS OF o.order_time AS u   -- 见上一篇的时态表 Join
  ON o.user_id = u.user_id;
```

⚠️ **`server-time-zone` 是第一个要检查的参数**。它决定 MySQL 的 `datetime`/`timestamp` 字段被解析成什么时间；不配时会按 UTC 处理，**所有时间列整体差 8 小时**——而窗口结果也会因此整体偏移（症状与上一篇的"时区坑"完全一致）。

## 三、增量快照：为什么可以不加全局锁 {#incremental-snapshot}

### 3.1 老做法的问题：全量阶段要加锁 {#old-approach}

早期 CDC 方案（以及很多自研脚本）的"全量 + 增量"是这样做的：

```
   ① 对业务库加**全局读锁**（FLUSH TABLES WITH READ LOCK）
   ② 记录此刻的 binlog 位点
   ③ 全量导出所有表（读的是快照，因为业务写不进来）
   ④ 释放锁
   ⑤ 从记录的位点开始读增量
```

**第 ③ 步期间业务是写不进去的**（严格说，写会阻塞）。几十 GB 的表导出要几十分钟——**这就是"CDC 上线要停业务"传闻的来源**。而且这个流程有个隐含要求：全量导出与位点记录之间不能有时间差，否则数据对不上。

### 3.2 无锁增量快照：分块 + 位点 + 变更回填 {#incremental}

Flink CDC 用的是**增量快照**思路，核心是把"一次大锁"拆成"多个小块各自记账"：

```
   把表按主键切成 N 个 chunk
   ┌─────────┬─────────┬─────────┬─────────┐
   │ chunk 1 │ chunk 2 │ chunk 3 │ chunk 4 │
   │ id<1000 │ 1000~   │ 2000~   │ 3000~   │
   └─────────┴─────────┴─────────┴─────────┘
        │ 每块**独立**做三件事：
        │
        ├─ ① 记下开始读这块时的 binlog 位点（低水位）
        ├─ ② 用**普通快照读**（无锁 SELECT）读出这块数据 ← 不加锁！
        ├─ ③ 读出这块结束时的 binlog 位点（高水位）
        │
        └─ ④ **回填**：把 [低水位, 高水位] 区间内、主键落在本块范围内的
               binlog 变更重放到刚读出的快照上 → 得到一致结果
```

**关键洞察**：一个 chunk 在被读的过程中，业务可能还在改它里面的行。但只要**把这段时间的变更事后重放上去**，最终结果就是一致的——**不需要阻止写入**。

| 收益 | 说明 |
|---|---|
| **无锁** | 全量阶段业务照常读写，没有"导出时停业务" |
| **可并行** | 每个 chunk 独立 → 全量阶段就能用多并行度读（老做法只有单线程导出） |
| **可断点续传** | 每个 chunk 的进度可以记录下来，作业重启不必从头读 |
| **无缝接续** | 所有 chunk 读完 → 直接从最后位点切到纯增量阶段，不需要"再对一次账" |

⚠️ **前提是表必须有主键（或能确定一个唯一的分块键）**。没有主键的表**无法分块**，只能退化成单线程读（Flink CDC 会给出相应提示）。这也是"为什么建表一定要有主键"在 CDC 场景下的另一重理由。

### 3.3 与 Canal / Debezium 的分工 {#vs-canal}

这三个不是"谁替代谁"，而是**三种不同位置的组件**。与 [Canal 那篇的对照表](/bigdata/canal/#compare)一起看：

| 维度 | Canal | Debezium | **Flink CDC** |
|---|---|---|---|
| 定位 | 变更捕获**服务** | 变更捕获**库**（Kafka Connect 生态） | **流处理引擎内置**的 source/sink |
| 部署 | 独立服务 + 客户端 | Kafka Connect 集群 | 就是 Flink 作业 |
| **全量阶段** | 需额外方案（Canal 只管增量） | 快照 + 增量（有锁版本与无锁版本） | **无锁增量快照，且全量阶段可并行** |
| 多下游 | 支持（一份变更给多方） | 支持（写 Kafka topic） | 需要下游自己扩（或在中间加 Kafka） |
| 适合 | 已有多下游、要解耦 | 已在 Kafka Connect 体系内 | **一条链直通到湖/仓，中间不需要落 Kafka** |

**一条实用判据**：

```
   变更数据要给**多个**下游消费吗？
        │
        ├─ 是 ──▶ 用 Canal / Debezium 落一份 Kafka（解耦），Flink 从 Kafka 读
        │         （这也是 canal 篇那条"位点只能前进，中间加 MQ 是必要而非优化"的理由）
        │
        └─ 否 ──▶ 直接 Flink CDC 读到目标端，少一跳、少一份运维
```

## 四、出口：写库、写湖，两条路径 {#sink}

### 4.1 两条路径的本质差别 {#two-paths}

```
   写「库/仓」（Doris / StarRocks）            写「湖」（Paimon / Iceberg）
   ┌────────────────────────────┐            ┌────────────────────────────┐
   │ 靠**导入接口**的预提交能力    │            │ 靠**湖格式**的原子元数据提交 │
   │                            │            │                            │
   │ Stream Load ①预提交(事务)   │            │ 数据文件先写入（不可见）      │
   │            ②成功后提交      │            │ 然后**原子切换元数据指针** →  │
   │ 失败 → 回滚                │            │ 一次性对外可见               │
   │                            │            │                            │
   │ 依赖：目标表的**主键模型**    │            │ 依赖：Catalog 与提交协议      │
   │      必须支持 upsert        │            │      （见 lakehouse 篇）     │
   └────────────────────────────┘            └────────────────────────────┘
```

**共同点**：两者都是"先写、后确认"。**这就是为什么说端到端的 exactly-once 一定需要 sink 配合**（回到上一篇的三段论）。

### 4.2 写 Doris：表模型必须先选对 {#sink-doris}

写 Doris 时最容易犯的错**不是连接器配置，而是表模型选错**：

| 上游数据特征 | Doris 表模型 | 为什么 |
|---|---|---|
| CDC 变更流（有 INSERT/UPDATE/DELETE） | **Unique 模型**（主键） | 变更需要用 UPSERT 表达；Duplicate 模型下"更新"会变成追加一条 |
| 只追加的日志/埋点 | Duplicate | 不涉及更新 |
| 写入即聚合的指标 | Aggregate | 明细不需要保留 |

**顺序问题**：CDC 流里 `-U`（撤回旧值）与 `+U`（写入新值）是**两条记录**。写进 Unique 模型时，两条都会按主键 upsert，最终值是 `+U` 那条——**结果正确**。但若写进 Duplicate 模型，旧值和新值都留在表里，**下游一查就能看到"同一个订单有两个金额"**。

> **判据：只要上游是 CDC，目标表就应该是 Unique 模型（主键 upsert）**。这条比连接器的任何参数都重要。

**另一个高频问题**：Doris 的 Unique 模型在**存算分离**下有**单表导入频率的硬约束**（回到 [Doris 篇的存算分离选型](/bigdata/doris/#shared-nothing-vs-storage)）。实时同步的表如果写入很频繁，选型时要先确认这一点。

### 4.3 写湖：Paimon / Iceberg {#sink-lake}

写湖的关键差别在于**湖表本身支持流式更新**：

| | 写 Iceberg | 写 Paimon |
|---|---|---|
| 定位 | 通用开放湖表格式 | **流式湖仓**，为实时更新设计 |
| 写入模式 | append / upsert（取决于实现与版本） | **主键表原生支持流式 upsert** |
| 小文件问题 | 需要定期 compaction（要外部调度） | **自带异步 compaction**（可在写入时持续整理） |
| 与 Flink 的关系 | 通过 connector 写入 | **与 Flink 深度集成**（同为社区主推组合） |

**Flink 2.0 把与 Paimon 的集成又推进了一步**（这是"流式湖仓"这个说法在 2.0 里的落地）：

| 增强 | 说明 |
|---|---|
| 嵌套投影下推 | 读复杂结构时只读需要的子字段，减少 IO |
| **Lookup Join 按分桶对齐** | Paimon 作为维表时，按分桶对齐输入分布，**大幅减少每个任务要拉取和缓存的数据量** |
| 维护操作 SQL 化 | compaction、snapshot/branch/tag 管理都能用 `CALL` 语句执行，不必写外部脚本 |
| 物化表 | **Paimon 是首个（也是目前唯一）支持物化表的 Catalog** |

⚠️ **"物化表只支持 Paimon"是一个真实的选型约束**：如果你的存储是 Iceberg 或 Hudi，**物化表这个能力就用不上**，不要按它来设计架构（回到 [SQL 篇的版本现状](/bigdata/flink/sql-and-joins#version)）。

### 4.4 整库同步的四个典型难点 {#difficulties}

| 难点 | 现象 | 处理 |
|---|---|---|
| **分库分表合并** | 同一张逻辑表散在 8 个库里 | 用 `table-name` 正则合并读；**冲突主键要加"分片标识"**（否则不同库的同 id 会互相覆盖）；合并后按主键 hash 重分布 |
| **DDL 同步** | 上游 `ADD COLUMN` 后下游报错 | 开表结构变更跟随；但**rename/drop column 这类操作支持有限**，复杂变更仍需人工介入 |
| **宽表打宽** | 同步过来的都是窄表，分析要 join 一堆 | 在 Flink 里做多流 join 落宽表（注意用 Interval Join 或 Temporal Join 控制状态，别用 Regular Join） |
| **顺序性** | 同一行的变更顺序错乱 → 结果错 | CDC 保证**单表内的变更有序**；**跨表 join 后的顺序不保证**——需要按业务键聚合的场景，要在 Flink 里按该键分组 |

**关于"顺序性"，最容易误解的一点**：

> **Flink CDC 保证的是"单表 + 单主键内的变更有序"，不是"全局有序"。** 所以：
> - 同一行的多次更新 → 顺序正确 ✅
> - 不同表之间的因果顺序（先插主表、再插从表）→ **不保证**
>
> 需要跨表因果一致的场景（如订单与订单明细的落库顺序），必须在 Flink 里**把相关数据聚到同一个 key 下**（如都按 `order_id` 分组），让它们进同一个 subtask，才谈得上顺序。

## 五、全景：这条链路在数据仓库板块里的位置 {#position}

把本篇接回板块导览那张图，五个部分的分工是：

```
   业务 MySQL
       │
       │  ① 变更怎么同步出来
       ▼
   ┌──────────────────────────────────────────────┐
   │  Canal（多下游解耦）  /  Flink CDC（直通）      │  ← canal 篇 + 本篇第二节
   └──────────────────────┬───────────────────────┘
                          │
                          │  ② 流上做什么加工
                          ▼
   ┌──────────────────────────────────────────────┐
   │  时间语义 · 状态与一致性 · SQL 与 Join · 调优   │  ← 本篇前四篇（Flink 板块正文）
   └──────────────────────┬───────────────────────┘
                          │
                          │  ③ 写到哪
                          ▼
   ┌───────────────────────┴──────────────────────┐
   │  Doris（明细与汇总，热）  │  Paimon / Iceberg   │  ← doris 篇 + lakehouse 篇
   │  读得快、聚合强           │  （冷，成本下沉）    │
   └───────────────────────┬──────────────────────┘
                          │
                          │  ④ 数据怎么组织才不产生口径分叉
                          ▼
              ODS → DWD → DWS → ADS（+ DIM）        ← warehouse-design 篇
```

**Flink 板块补上的正是那条"②"**——在此之前，板块导览里从"同步"到"存储"之间是断的：CDC 把变更送出来了，但"送到分析库之前做了什么"没有落点。

**三条跨篇的纪律**（把前四篇的结论接回整条链路）：

| 纪律 | 出处 |
|---|---|
| 水印容忍度要靠**侧输出流的迟到数据量**来定，不能拍脑袋 | [时间语义与水印](/bigdata/flink/time-and-watermark#late-data) |
| 端到端一致性是**三段**（source 可重放 + 状态一致 + sink 幂等/事务），缺一段就只能降级 | [状态与检查点](/bigdata/flink/state-and-checkpoint#three-parts) |
| 出口选表模型时，**"下游支持不支持撤回（upsert）"** 决定你能否写非窗口聚合 | [SQL 与 Join](/bigdata/flink/sql-and-joins#changelog) |

> **最后一条通用纪律**（与板块导览末尾那句呼应）：**链路上的每一步都要能被校验**。CDC 要能对账（比数量、比校验和）、入湖入仓要能回查、指标要有单一出处。**Flink 引入的不是"更快的链路"，而是"更多需要校验的环节"**——背压、水印、检查点、事务，每一个都是"看起来在跑"与"可以放心用"之间的分界线。

## 六、使用场景与面试问答 {#interview}

**Q1：Flink CDC 做全量同步要停业务吗？**

**不需要**。它用的是**增量快照**：把表按主键切成多个 chunk，每块独立地"记位点 → 无锁快照读 → 记录结束位点 → 把这段时间内的变更重放到快照上"。因为没有全局锁，业务照常读写；而且每个 chunk 独立，**全量阶段就能并行读**，还能断点续传。

**前提是表有主键**（或能确定唯一的分块键）——没有主键的表无法分块，只能退化成单线程读。这是"建表必须有主键"在 CDC 场景下的又一条理由。

**Q2：Flink CDC 和 Canal / Debezium 怎么选？**

一条判据：**变更数据要不要给多个下游消费**。

需要 → 用 Canal / Debezium 先把变更落一份 Kafka 解耦，Flink 从 Kafka 读。**CDC 的位点只能前进，中间加 MQ 是必要而非优化**（否则多个下游耦合在一起，一个出问题就都停）。

不需要 → 直接 Flink CDC 读到目标端，少一跳、少一份要运维的组件。

另外 Flink CDC 有一个 Canal 没有的能力：**内置的无锁全量快照**（Canal 本身只管增量，全量要另想办法）。

**Q3：写 Doris 为什么必须是 Unique 模型？**

因为 CDC 流里的"更新"是**两条记录**：`-U`（撤回旧值）+ `+U`（写入新值）。Unique 模型按主键 upsert，最终值就是 `+U` 那条，**结果正确**。而 Duplicate 模型是纯追加——旧值和新值都会留在表里，查出来就是"同一个订单有两个金额"。**只要上游是 CDC，目标表就该是 Unique 模型。**

**Q4：写 Doris 和写 Paimon/Iceberg 的 exactly-once 有什么不同？**

机制完全不同：写 Doris 靠**导入接口（Stream Load）的两阶段提交**——预提交后等检查点完成再提交，失败可回滚；写湖靠**湖格式的原子元数据提交**——数据文件先写成不可见的，最后原子切换元数据指针一次性对外可见。

共同点是**都是"先写、后确认"**，都需要 sink 侧配合。这也再次说明 **Flink 的 exactly-once 只覆盖状态，端到端需要 sink 参与**。

**Q5：整库同步最常踩的坑是什么？**

两个。**一是分库分表合并时的主键冲突**——不同分片里 id 相同的行会被互相覆盖，必须加"分片标识"参与主键，合并后按主键 hash 重分布。**二是对"顺序性"的预期过高**：Flink CDC 只保证**单表、单主键内的变更有序**，跨表的因果顺序（先主表后从表）**不保证**。需要因果一致的场景，必须把相关数据按同一个业务键聚到一起（进同一个 subtask），才谈得上顺序。

**Q6：`server-time-zone` 为什么必须配？**

它决定 MySQL 的时间字段被解析成什么时间。不配时按 UTC 处理，**所有时间列整体差 8 小时**（东八区），窗口结果也会跟着整体偏移。**症状是"窗口结果差了整数小时"**——与 SQL 里的时区坑是同一类问题，排查时优先查它，不要先怀疑水印。

**Q7：Flink 2.0 的"流式湖仓"具体是什么？**

指 **Flink 作为流批统一引擎 + Paimon 作为流批统一湖格式**的组合。2.0 上的具体增强包括：读 Paimon 时的嵌套投影下推、**Paimon 作维表时 Lookup Join 按分桶对齐**（大幅降低每个任务的拉取与缓存量）、维护操作（compaction / snapshot / branch）可以用 SQL `CALL` 执行、以及**物化表以 Paimon 作为首个也是唯一的 Catalog**。

最后这一条是真实的选型约束：**存储不是 Paimon，物化表就用不上**——不要按它设计架构。
