# 状态、检查点与端到端一致

## 一、问题场景：批处理里"不需要记着"的东西 {#why-state}

回到上一篇的对比。批处理算"昨天的总额"时，`sum` 是一个局部变量——每条记录加上去，跑完就是结果，**任务结束变量就没了，也不需要它还在**。

流处理不行。它算的是"**每当有新订单，把最近 5 分钟的总额更新一次**"。这个"最近 5 分钟的总额"必须一直记着——它不是中间变量，**它是结果本身的一部分**，而且要在下一条数据到达时还能读出来。

于是问题来了：

| 问题 | 为什么难 |
|---|---|
| 这些"记着的东西"放在哪 | 内存放不下怎么办（TB 级状态） |
| 作业挂了，这些数据还在吗 | 内存里的东西重启就没了 |
| 恢复之后会不会重复算 | 从哪个点恢复？恢复后上游要不要重放 |
| 恢复之后会不会少算 | 恢复点之前的处理结果，外部系统收到了吗 |

**这四个问题就是本篇的全部内容**：状态（放哪、多大）、检查点（怎么保命）、一致性语义（恢复后算重了还是算漏了）。

> **一句话概括**：Flink 的 exactly-once 不是"每条数据只处理一次"，而是"**每条数据对最终结果的影响只发生一次**"。理解这句话是理解整篇的钥匙——内部的**重放是允许且必然的**，靠的是**状态快照 + sink 幂等/事务**把重放的影响抹掉。

## 二、状态：有哪几种、各用在哪 {#state-types}

### 2.1 按作用域分三类 {#state-scope}

```
  ┌──────────────────────────── Keyed State ────────────────────────────┐
  │ 只能用在 keyBy 之后的流上；每个 key 一份独立的状态                    │
  │ user=A: {count: 12}   user=B: {count: 3}   user=C: {count: 88}      │
  │ ✔ 天然按 key 分区 → 与并行度绑定，可随 key 一起 rescale              │
  └─────────────────────────────────────────────────────────────────────┘
  ┌────────────────────────── Operator State ───────────────────────────┐
  │ 绑定在算子的并行实例上（不是 key 上），每个 subtask 一份              │
  │ 典型：Kafka source 记录"我这个 subtask 负责哪些分区、读到哪了"        │
  │ ✔ 支持 rescale 时重新分配（ListState 按元素轮询拆分）                 │
  └─────────────────────────────────────────────────────────────────────┘
  ┌────────────────────────── Broadcast State ──────────────────────────┐
  │ 一侧是数据流、一侧是规则/配置流；广播流被复制到**每个**并发实例       │
  │ 典型：动态风控规则、维表小配置、黑白名单                              │
  │ ⚠️ 所有实例各持一份**全量副本**，只适合"小且更新不频繁"的数据         │
  └─────────────────────────────────────────────────────────────────────┘
```

| 类型 | 作用域 | 与并行度的关系 | 典型用途 |
|---|---|---|---|
| **Keyed State** | 每个 key | 跟着 key 走，改并行度时可自动重分布 | 计数、去重、窗口聚合、会话 |
| **Operator State** | 每个并行实例 | 绑在 subtask 上，需实现重分配策略 | source 的偏移量、批量缓冲 |
| **Broadcast State** | 每个并行实例（全量副本） | 每个实例都有完整一份 | 动态规则、小维表 |

**Keyed State 有一个必须记住的前提**：它**只能在 `keyBy` 之后使用**。这不是限制，而是机制——状态是按 key 分区的，Flink 需要知道"这条数据属于哪个 key"才能找到它的状态。这也是为什么 `KeyedProcessFunction` 里能拿到 `TimerService`（定时器也是按 key 注册的状态）。

### 2.2 Keyed State 的五个具体形态 {#keyed-forms}

不要只记住 `ValueState`。**选错形态会直接影响状态体积与序列化开销**：

| 形态 | 存什么 | 何时用 |
|---|---|---|
| `ValueState<T>` | 单个值 | 只记"最后一个值"或"当前计数" |
| `ListState<T>` | 一个列表 | 需要按顺序保留多条（如最近 N 条） |
| `MapState<K,V>` | 一个 map | **按子键查改**（去重集合、按维度累积） |
| `ReducingState<T>` | 单个值，每次 `add` 就归约 | 只要聚合结果（累加、取最大） |
| `AggregatingState<IN,OUT>` | 单个值，类型可不同 | 输入输出类型不一样（如"输入订单、输出统计结构"） |

⚠️ **最常见的性能问题**：用 `ValueState<Map>` 或 `ValueState<List>` 代替 `MapState`/`ListState`。前者每次读写都要**序列化/反序列化整个集合**，后者是增量读写。数据量一上来（比如每 key 几千个元素），差别是数量级的。

### 2.3 状态存在哪：状态后端的演进 {#state-backend}

这是决定"能扛多大状态"的地方。三代形态：

```
 ① HashMapStateBackend          ② EmbeddedRocksDBStateBackend        ③ ForSt（Flink 2.0）
 ┌───────────────┐              ┌───────────────┐                   ┌──────────────────┐
 │  JVM 堆内存    │              │  本地磁盘      │                   │  远端 DFS          │
 │  状态对象直接  │              │  (LSM-Tree)    │                   │  (S3 / HDFS)      │
 │  是 Java 对象  │              │  内存做 block  │                   │  本地盘只做缓存    │
 │               │              │  cache         │                   │                   │
 └───────────────┘              └───────────────┘                   └──────────────────┘
  快，但受堆限制                 大，但有序列化与                     云原生友好
  GC 压力大                      compaction 尖峰                     但有网络延迟
```

| 后端 | 存储位置 | 上限 | 主要代价 |
|---|---|---|---|
| `HashMapStateBackend` | JVM 堆 | 堆大小（几十 GB 量级） | GC 停顿；超大状态直接不可行 |
| `EmbeddedRocksDBStateBackend` | 本地磁盘（LSM-Tree） | 受本地盘（可到 TB 级） | 每次访问都要序列化/反序列化；compaction 造成资源尖峰 |
| **`ForStStateBackend`（2.0 新增）** | **远端 DFS**，本地盘只做缓存 | 受对象存储（近似无限） | 远程访问延迟；缓存命中率低时性能下降 |

> **版本提示**：Flink **1.13 起**，老式的 `MemoryStateBackend` / `FsStateBackend` / `RocksDBStateBackend` 被 `HashMapStateBackend` / `EmbeddedRocksDBStateBackend` 取代（老名废弃）；同时**"状态存在哪"与"检查点存在哪"被拆成两件独立的事**——前者由状态后端决定，后者由 `state.checkpoints.dir` 配置。这一点常被写错。

**Flink 2.0 的 ForSt 值得单独记一句**：它把状态从计算节点上解耦，直接解决云原生容器的三个痛点——**本地盘不受限、作业快速扩缩容、检查点变轻**（状态已经在远端，检查点更接近"记一个确认点"而不是"搬运大文件"）。官方在 Nexmark 基准上的数据是：状态 1.2GB~4.8GB 的重 IO 查询、1GB 缓存下吞吐达到本地状态方案的 75%~120%；小状态（10MB~400MB）差距平均不超过 10%。**启用入口是 `table.exec.async-state.enabled`（对 SQL 作业，不用改代码）**。

但要注意：**它是有代价的选项，不是免费升级**。远端访问引入网络延迟，缓存命中率低时性能会掉；而且配套的异步执行模型与 State API V2 在 2.0 时仍被标注为实验性。**生产落地应按"灰度 + 可回滚"来做，先用真实状态规模在测试集群验证。**

## 三、检查点：把状态在某个"一致的时刻"存下来 {#checkpoint}

### 3.1 核心难点：怎么保证"所有算子的快照是同一时刻的" {#snapshot-problem}

朴素想法是"暂停整个作业，每个算子把自己状态存一份，再恢复"。这在流处理里不可行——**分布式系统没有全局时钟**，你在 t1 停了算子 A、t2 停了算子 B，这中间流过的数据算谁的？

Flink 采用的思路来自 **Chandy-Lamport 分布式快照算法**，用一句话概括：

> **不插入全局暂停，而是在数据流里插入一种特殊标记（屏障 barrier），让它像普通数据一样往下游流；每个算子等所有输入的屏障都到齐，就"对齐"到一个一致点，此时做快照。**

### 3.2 屏障是怎么走的 {#barrier-flow}

```
   JobManager 的 CheckpointCoordinator（周期性发起，如每 60s）
            │  ① 向所有 Source 注入 barrier（携带 checkpoint id = n）
            ▼
   ┌─────────────┐        barrier 与数据**同一条通道、排队流动**
   │  Source     │──[d1][d2][B(n)][d3]──┐
   └─────────────┘                      │
                                        ▼
                            ┌───────────────────────┐
                            │  算子（两个输入通道）    │
                     ─[B(n)]─▶  通道A：收到 barrier     │
                            │  → **阻塞通道 A**（后面的  │
                            │     d 先不处理，防止"越过  │
                            │     快照点"的数据被算进去） │
                            │  → 继续处理通道 B 的数据   │
                     ─[d][B(n)]▶ 通道B：barrier 也到了    │
                            │  → 两个通道都对齐 ✅        │
                            │  → **快照本地状态**（异步） │
                            │  → 向下游广播 B(n)        │
                            └───────────────────────┘
                                        │
                                        ▼  所有算子都完成 → 本次 checkpoint 成功
```

**为什么必须阻塞（这就是"对齐"）**：假设通道 A 的 barrier 已经到、通道 B 的还没到。此时通道 A 后续来的数据，在"快照含义上"属于 checkpoint n **之后**——如果现在就算进状态，那这份快照就同时包含了"B 在 n 之前"和"A 在 n 之后"的数据，**两个通道的状态不在同一个时间点上**，恢复后必然算错。所以必须等。

| 概念 | 含义 | 代价 |
|---|---|---|
| **屏障对齐** | 收到部分通道的 barrier 后阻塞该通道，等齐所有通道 | 阻塞期间该通道数据积压 → **延迟尖峰 + 背压** |
| **非对齐检查点**（unaligned） | 不等待，把"在途数据"也一并存进快照 | 快照体积变大（含在途数据）；但**消除延迟尖峰** |

**什么时候该用非对齐**：**背压严重导致检查点持续超时**的场景（对称——背压下 barrier 走不动，对齐等待时间被无限拉长，检查点永远超时）。配置项：

```yaml
# config.yaml（Flink 2.0 起；1.x 里是 flink-conf.yaml）
execution.checkpointing.unaligned.enabled: true
execution.checkpointing.aligned-checkpoint-timeout: 30s   # 超过就退化为非对齐
```

### 3.3 检查点的关键配置与它们之间的关系 {#checkpoint-config}

```yaml
execution.checkpointing.interval: 60s              # 发起间隔
execution.checkpointing.min-pause: 30s             # 两次之间的最小间隔（防"背靠背"）
execution.checkpointing.timeout: 10min             # 单次超时（超时算失败）
execution.checkpointing.tolerable-failed-checkpoints: 3   # 容忍连续失败次数
execution.checkpointing.mode: EXACTLY_ONCE         # 或 AT_LEAST_ONCE
state.checkpoints.dir: s3://bucket/checkpoints     # 快照存哪（与状态后端解耦）
state.backend.incremental: true                    # 增量（RocksDB/ForSt 支持）
```

三组关系必须理解：

| 关系 | 说明 |
|---|---|
| **interval 与延迟** | interval 越小，故障时**重放的数据越少**（恢复更快），但检查点开销越大。二者是直接交换 |
| **interval + min-pause 与 RPO** | 最坏情况下丢失的处理量 ≈ interval + min-pause。这是**对"能接受丢多少数据"的显式回答** |
| **timeout 与背压** | 背压时 barrier 流动变慢，检查点容易超时。**"检查点持续失败"往往是背压的症状，不是检查点配置的问题** |

⚠️ **`tolerable-failed-checkpoints` 不是"允许丢数据"**：它的含义是"连续失败 N 次内作业不重启，继续用上一个成功的检查点"。设得太大，会让作业在"检查点一直失败"的状态下带病运行——**这是掩盖问题，不是解决问题**。

### 3.4 Checkpoint 与 Savepoint 的分工 {#checkpoint-vs-savepoint}

两者格式相近但定位完全不同，**不要混用**：

| 维度 | Checkpoint | Savepoint |
|---|---|---|
| 触发 | 自动、周期 | **手动**（命令行/API） |
| 目的 | **故障恢复** | **人为变更**：升级、迁移、改并行度、换状态后端 |
| 生命周期 | 由作业管理，旧的在有更新的成功后自动清理 | 手动管理，**不会自动删除**，要自己清理 |
| 增量 | 可以（`state.backend.incremental`） | **全量**（格式要求自洽、可迁移） |
| 恢复限制 | 一般要求并行度等不变 | 允许部分算子改并行度（有重分配策略的） |
| 状态兼容性 | 跨大版本**不保证** | 跨大版本**不保证** |

> **Flink 2.0 的一条硬事实**：**1.x 与 2.x 之间不保证状态兼容**。升级不能靠保存点直接跨大版本恢复，需要规划"无状态重建"或"全量重算"。**这决定了升级窗口要按"重写 + 回归"来排，而不是"停 5 分钟换个 jar"**。

## 四、端到端一致：三段论 {#end-to-end}

### 4.1 exactly-once 拆成三段 {#three-parts}

一个从 Kafka 进、写到外部系统的作业，要做到端到端 exactly-once，**三段缺一不可**：

```
   ① Source 可重放且能定位        ② 内部状态一致              ③ Sink 幂等 或 事务
   ┌───────────────────┐        ┌───────────────────┐      ┌────────────────────┐
   │ 能从某个偏移重新读  │        │ checkpoint 保证    │      │ 重放时不会产生       │
   │ 且偏移本身被存进    │───────▶│ 状态一致，恢复后    │─────▶│ 重复的外部可见效果    │
   │ checkpoint 里       │        │ 结果与失败前一致    │      │                    │
   └───────────────────┘        └───────────────────┘      └────────────────────┘
     Kafka ✔（offset 可存）        Flink ✔（本篇第三节）        只有部分 sink ✔
```

| 段 | 需要什么 | 做不到会怎样 |
|---|---|---|
| Source | 可重放 + 偏移随检查点持久化 | 恢复后从"某个不知道对不对"的位置读 → 漏数据或重数据 |
| 内部 | 检查点机制 | 恢复后状态是脏的 |
| **Sink** | **幂等写入 或 事务性写入** | **恢复后上游重放的数据被再写一遍 → 外部可见重复** |

**第三段是最常被忽略的一段**。很多人以为"Flink 支持 exactly-once"就等于端到端 exactly-once，实际上：

> **Flink 保证的是"状态"的 exactly-once。端到端取决于 sink 的能力。** 如果下游是一个"只支持追加、没有主键去重、也不支持事务"的系统（如写普通日志文件），那么无论 Flink 侧怎么配，端到端都只能是 **at-least-once**。

### 4.2 Sink 的两条实现路径 {#sink-strategies}

**路径一：幂等写入**（适合有主键的下游）

```
  重放同一条数据 → UPSERT 覆盖同一个主键 → 最终状态一致
  典型：写 MySQL/ClickHouse/Doris（按主键 upsert）、写 Redis（SET）
```

- 优点：实现简单，不需要事务支持
- 代价：**要求下游有主键**；而且"中间过程"可能被看见（例如先写了 -100 又 +100，读者可能读到中间态）
- 边界：**只有"覆盖式"写才幂等**。`UPDATE balance = balance + 100` 这种累加式写入**不幂等**，重放就会多加一次。

**路径二：两阶段提交**（适合没有主键、或要求"不可见中间态"的下游）

```
  ① 预提交（pre-commit）         ② 收到「检查点完成」通知      ③ 正式提交（commit）
  ┌───────────────────────┐     ┌──────────────────────┐    ┌──────────────────┐
  │ 数据写到外部系统的      │     │ JobManager 确认本次    │    │ 事务真正生效       │
  │ "暂存区"，对外不可见    │────▶│ checkpoint n 成功      │───▶│ 对外可见          │
  │ Kafka：开启事务未提交   │     │ （事务 id 已在状态里） │    │ Kafka：commit     │
  │ 文件：写成隐藏临时文件  │     │                      │    │ 文件：改名为正式名 │
  └───────────────────────┘     └──────────────────────┘    └──────────────────┘
         失败 → 回滚（Kafka abort / 删除临时文件）
```

以 Kafka sink 为例的关键配置：

```java
KafkaSink.<String>builder()
    .setBootstrapServers("kafka:9092")
    .setRecordSerializer(...)
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)   // 开启事务
    .setTransactionalIdPrefix("flink-orders")               // ⚠️ 全局唯一，作业重启后要一致
    .setProperty("transaction.timeout.ms", "900000")        // ⚠️ 必须 > checkpoint 间隔 + 最大恢复时间
    .build();
```

**两个必踩的坑**：

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `transaction.timeout.ms` 小于"检查点间隔 + 恢复耗时" | broker 在提交前**主动中止**事务 → 数据丢或作业反复失败 | 设为 **15 分钟**一类的充裕值（Kafka broker 默认上限 15 分钟） |
| `transactionalIdPrefix` 每次发布都变 | 旧事务无法被恢复的作业认领 → **僵尸事务**锁住分区 | 前缀固定，且**同一作业的所有实例共用一个前缀** |

### 4.3 三种语义的完整对照 {#three-semantics}

| 语义 | 做法 | 结果 | 代价 |
|---|---|---|---|
| **at-most-once** | 不重放 | **可能丢** | 最低 |
| **at-least-once** | 重放 + 不做去重 | **可能重** | 低；需要下游能容忍重复 |
| **exactly-once** | 重放 + 状态快照 + sink 幂等/事务 | 外部可见效果**恰好一次** | 最高：需要事务/主键支持，且事务会引入**提交延迟**（数据要等检查点完成才可见） |

⚠️ **exactly-once 的隐性代价**：两阶段提交意味着**数据要等一个检查点周期才对外可见**（比如 60 秒），因为提交发生在"检查点完成"之后。如果业务要求"秒级可见"，端到端 exactly-once 与低延迟是**冲突的**——这时正确的选择往往是 **at-least-once + 下游幂等**（数据立即可见，重复由主键抹掉）。

## 五、大状态治理 {#state-management}

状态不会自己变小。三个常规手段：

| 手段 | 做法 | 适用 |
|---|---|---|
| **状态 TTL** | `StateTtlConfig` 设置存活时间，过期自动清理 | 去重集合、会话、临时缓存类状态 |
| **增量检查点** | `state.backend.incremental: true` | RocksDB / ForSt；大状态必开 |
| **控制状态规模的设计** | 少用"永久累积"的状态（如"用户历史所有行为"） | 从根本上避免 |

```java
StateTtlConfig ttl = StateTtlConfig
    .newBuilder(Duration.ofHours(24))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)  // 或 OnReadAndWrite
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .cleanupInRocksdbCompactFilter(1000)                        // RocksDB 下的后台清理
    .build();
ValueStateDescriptor<Long> desc = new ValueStateDescriptor<>("lastSeen", Long.class);
desc.enableTimeToLive(ttl);
```

**TTL 的三个必须知道的细节**：

1. **默认是"惰性清理"**——过期数据要等到**被访问到**才真正删除。所以状态大小不会随时间自动下降，除非配了后台清理（`cleanupInRocksdbCompactFilter`）或状态本来就会被覆盖。
2. **`OnReadAndWrite` 会让读操作也延长 TTL**，慎用——它会让"频繁读"的状态永不过期。
3. **TTL 是逻辑过期，不是物理删除**，所以内存/磁盘占用可能仍高于"有效数据量"。

**排查"状态为什么这么大"的固定动作**：在 WebUI 的 Checkpoint 详情页里，**按算子看 state size 排名**——通常是某几个算子占了绝大部分（如 `KeyedProcessFunction` 里一个没有上限的 `MapState`、或滑动窗口）。**先定位到算子，再谈治理。**

## 六、对比辨析 {#compare}

### 6.1 状态后端怎么选 {#vs-backend}

| 你的情况 | 选择 | 理由 |
|---|---|---|
| 状态 < 几 GB，key 数量可控 | `HashMapStateBackend` | 最快，无序列化开销 |
| 状态数十 GB ~ TB，已有本地 SSD | `EmbeddedRocksDBStateBackend` | 磁盘承载；注意 compaction 尖峰 |
| 跑在 K8s 上、状态大、需要快速扩缩容 | `ForStStateBackend`（2.0+） | 状态与计算解耦；但**先按真实规模验证** |
| 状态大小波动极大、扩缩容频繁 | ForSt 或"分桶 + 缩短状态生命周期" | 核心矛盾是"重分布成本" |

### 6.2 "重启后数据重复了"的三种可能 {#vs-duplicate}

这个现象有三个完全不同的根因，**定位方向不同**：

| 现象 | 根因 | 判据 |
|---|---|---|
| 恢复后**大量**重复 | sink 不是幂等的（或事务没生效） | 检查 sink 的 delivery guarantee 配置；下游有无主键 |
| 恢复后**少量**重复 | 上一次的 in-flight 数据在失败前已写出、未被记录 | 这是 at-least-once 的正常表现 |
| **一直**在重复 | 作业陷入"检查点失败 → 重启 → 从旧检查点恢复 → 再失败"的循环 | 看 WebUI 的检查点历史，是否持续失败 |

第三种是最危险的——**它看起来像"偶发重复"，实际是作业根本没稳定跑起来**。

## 七、使用场景与面试问答 {#interview}

**Q1：Flink 的 exactly-once 到底保证了什么？**

**保证的是"状态"的 exactly-once**：故障恢复后，算子状态与失败前某个一致的时间点完全相同。**端到端的 exactly-once 需要 sink 配合**——要么下游有主键可做幂等 upsert，要么 sink 实现两阶段提交。如果下游既没有主键也不支持事务，端到端只能是 at-least-once。这是最常被追问的一层。

**Q2：屏障对齐（barrier alignment）是干什么的？为什么必须等？**

为了确保**所有算子做快照时处在同一个逻辑时间点**。算子收到部分输入通道的屏障后，会**阻塞这些通道**（因为屏障之后到达的数据在语义上属于"快照之后"，若此时算进状态，快照就会混入未来数据）。等所有通道的屏障到齐，才算对齐、才做快照。

代价是**阻塞期间数据积压 → 延迟尖峰**。背压严重时，对齐等待被无限拉长，检查点持续超时——这时用**非对齐检查点**（把在途数据也存进快照，换取不等待），代价是快照体积更大。

**Q3：作业的检查点一直失败，怎么排查？**

**先把它当背压问题排查，而不是检查点配置问题。** 因为背压下 barrier 流动变慢，对齐等待超时是必然结果。顺序：

1. 看 WebUI 的**背压指标**，定位是哪个算子、哪条链路
2. 看检查点的**失败类型**（timeout / 对齐超时 / 状态写入失败）
3. 若是"对齐超时"→ 开非对齐检查点
4. 若是"状态太大导致上传慢"→ 开增量检查点、治理状态
5. 最后才考虑调 `interval` / `timeout`

**Q4：Checkpoint 和 Savepoint 有什么区别？**

Checkpoint 是**自动、周期、为故障恢复服务**的，增量、旧的可自动清理；Savepoint 是**手动触发、为人为变更服务**的（升级、迁移、改并行度），全量、不会自动删除。关键区别是**恢复时的约束**：Savepoint 允许部分算子改并行度（需重分配策略），Checkpoint 一般要求拓扑与并行度不变。另外 **1.x 与 2.x 之间状态不兼容**，保存点不能直接跨大版本恢复。

**Q5：两阶段提交 sink 有什么坑？**

两个：① **`transaction.timeout.ms` 必须大于"检查点间隔 + 最大恢复时间"**，否则 broker 会在提交前主动中止事务；② **`transactionalIdPrefix` 必须固定**，否则作业恢复后无法认领之前的未决事务，留下**僵尸事务**锁住下游分区。

另外要记住它的**固有代价**：提交发生在"检查点完成"之后，所以**数据要等一个检查点周期才对外可见**。业务要求秒级可见时，正确选择往往是 at-least-once + 下游主键幂等。

**Q6：`ValueState<Map>` 和 `MapState` 有什么差别？**

`ValueState<Map>` 每次读写都要序列化/反序列化**整个 Map**；`MapState` 是增量读写单个 key。数据量小时差别不明显，每个 key 有几千个元素时是数量级差距。同类问题也出现在 `ValueState<List>` 与 `ListState` 之间。**选形态时问自己一句："我是整体读写，还是按子键读写？"**

**Q7：状态越来越大怎么办？**

三个层次，按成本从低到高：① **状态 TTL**（注意默认惰性清理，要配后台清理）；② **增量检查点**（`state.backend.incremental`，大状态必开）；③ **改设计**——把"永久累积"的状态改成"有界窗口"或"分层聚合"。定位入口是 WebUI 检查点详情页的 **state size 排名**，先找到占大头的算子。
