# 部署、背压与调优

## 一、问题场景：跑得起来 ≠ 跑得住 {#why}

前几篇解决的是"结果对不对"。但一个作业上线后，真正让人熬夜的是另一类问题：

| 现象 | 通常的错觉 |
|---|---|
| 吞吐上不去、Kafka 积压持续增长 | "是不是 Flink 集群资源不够？"（加了资源还是不动） |
| 检查点开始持续超时 | "是不是检查点配置要调？"（调完还是超时） |
| 延迟忽高忽低 | "是不是网络抖动？" |
| 某个算子日志里没有任何异常，但它就是慢 | "是不是数据就是这样？" |

**这四个现象里，有三个的同一个根因是背压（backpressure）。** 而背压最反直觉的一点是：

> **背压在哪个算子出现，说明它下游有瓶颈——不是它自己有瓶颈。**

理解这句话，是这一篇的核心。其余内容（部署形态、并行度、内存）都是为它服务的工具。

## 二、部署形态 {#deploy}

### 2.1 三种运行模式的取舍 {#run-modes}

```
 ① Session 模式            ② Application 模式          ③ Per-Job 模式
 ┌──────────────┐          ┌──────────────┐           ┌──────────────┐
 │ 先起一个集群   │          │ 每个作业起一个 │           │ 每个作业起一个 │
 │ 多个作业共享   │          │ 独立集群      │           │ 独立集群      │
 │              │          │ main() 在集群 │           │ main() 在客户端│
 │              │          │ 内执行        │           │              │
 └──────────────┘          └──────────────┘           └──────────────┘
  资源利用率高               隔离性好                    ❌ 2.0 已移除
  但一作业崩可能影响别人      客户端不再承担提交压力
```

| 模式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **Session** | 提交快（集群已在）、资源利用率高 | **隔离差**：一个作业的异常（如同步提交大量 jar、内存打满）可能影响同集群其他作业；且所有作业共用 JobManager | 开发测试、短任务 |
| **Application** | 隔离好；`main()` 在集群内执行，**客户端不再需要上传依赖、不承担生成 JobGraph 的压力** | 每个作业一套 JobManager（少量开销） | **生产首选** |
| ~~Per-Job~~ | —— | —— | **Flink 2.0 已移除**，改用 Application |

**为什么 Application 模式成为生产首选**：它把"解析依赖、生成 JobGraph"的工作从客户端挪到了集群内。在此之前，Session 模式下客户端要负责生成整个 JobGraph，作业复杂时客户端压力很大——这也是早期"提交作业时客户端 OOM"的根源。

### 2.2 资源管理：Standalone / YARN / Kubernetes {#resource-manager}

| 方案 | 弹性 | 运维成本 | 说明 |
|---|---|---|---|
| Standalone | ❌ 固定 | 低 | 机器固定，扩容要改配置重启；适合稳定负载 |
| YARN | ✅ 按队列申请 | 中 | 与 Hadoop 体系共用资源池 |
| **Kubernetes（Operator）** | ✅ | 中高 | 云原生主流：`flink-kubernetes-operator` 管理生命周期、支持保存点自动升级 |

**K8s 上的两个关键概念**：

| 概念 | 作用 |
|---|---|
| **JobManager / TaskManager 都是 Pod** | JM 用 Deployment（稳定标识），TM 用 ReplicaSet 或由 Operator 直接管理 |
| **状态存哪必须外置** | 容器的本地盘不保证持久 → **`state.checkpoints.dir` 与 savepoint 必须指向对象存储（S3/OSS）**。这也正是 Flink 2.0 推出 ForSt（状态远端化）的动机 |

## 三、并行度与算子链 {#parallelism}

### 3.1 并行度有四种来源，优先级从高到低 {#parallelism-source}

```
   ① 算子级  .setParallelism(4)              ← 最高
   ② 执行环境 .setParallelism(4)
   ③ 提交时  flink run -p 4
   ④ 配置    parallelism.default: 4         ← 最低
```

**这四种来源常被混着用，导致"我明明改了配置但并行度没变"**。排查时按上面的顺序从高到低查。

**并行度怎么定**：

| 判据 | 说明 |
|---|---|
| 从 **source 的并行度**倒推 | Kafka 分区数是最硬的上限——source 并行度超过分区数时，多出的 subtask 空闲（除非开 `partition discovery`） |
| 从**瓶颈算子**倒推 | 让瓶颈算子的并行度尽量等于其上游数据分布的"可切分度" |
| **不要全局一个数** | 大状态算子与轻量算子对并行度的诉求不同（状态大 → 并行度太大反而加重检查点负担） |
| 无状态算子不必高并行 | 它们不是瓶颈，只是白白多占 slot |

### 3.2 算子链（operator chaining）{#chaining}

**默认行为**：把满足条件的相邻算子**合并进同一个线程**，数据在它们之间直接传对象（不序列化、不走网络）。

```
   未链化：                         链化后（默认）：
   ┌────┐  ┌────┐  ┌────┐         ┌────────────────────┐
   │map │─▶│filter│─▶│sink│        │ map → filter → sink│  ← 一个线程
   └────┘  └────┘  └────┘         └────────────────────┘
    线程切换 + 序列化 + 队列          无序列化、无切换
```

| 什么时候要断开链 | 做法 |
|---|---|
| 某个算子特别重，想单独设并行度 | `startNewChain()` |
| 排查时想看算子间的传递 | `disableChaining()` |
| 想让某算子独占 slot（避免和其他算子抢内存） | `slotSharingGroup("heavy")` |

⚠️ **链化把算子绑成了同一并行度**。所以"我想让 sink 并行度小一点、上游大一点"这件事，**必须先把链断开**，否则设置不生效。

## 四、背压：机制、定位、根因 {#backpressure}

### 4.1 背压是怎么产生的（从下游往上游看）{#mechanism}

背压不是错误，是**流控机制正常工作**的表现。它的传导链是：

```
   外部系统慢（如 sink 写 MySQL 慢）
            │
            ▼
   sink 算子的处理速度下降
            │
            ▼
   sink 的**输入缓冲**被填满（output buffer pool 耗尽）
            │
            ▼
   上游算子发现"sink 已经不能收数据了" → 停止发送、进而停止处理
            │
            ▼
   上游的输入缓冲也被填满 → 继续向上游传导
            │
            ▼
   …… 一路传到 source，**source 停止消费 Kafka** → 表现为 Kafka lag 增长
```

**这就是最重要的那条判据的来源**：

> **在哪个算子看到背压，瓶颈就在它的下游（或它自身读外部系统的环节）。** 所以定位时**要顺着数据流往下找**，而不是盯着报背压的那个算子看。

### 4.2 credit-based 流控：为什么不用 TCP 反压 {#credit}

这是 Flink 1.5 起的一次关键改造，理解它才能理解"为什么检查点会假超时"。

```
   ❌ 早期（TCP 反压）：数据直接推进 TCP 缓冲区
      ┌────────┐   TCP socket buffer 满了就阻塞   ┌────────┐
      │ 上游    │────────────────────────────────▶│ 下游    │
      └────────┘        ⚠️ 这条 TCP 连接上
                         —— 数据、checkpoint barrier、
                            心跳 —— 全部被阻塞
                         → 心跳超时 → JobManager 认为 TM 失联
                         → 表现为"检查点莫名超时/作业假死"

   ✅ 现在（credit-based）：
      ┌────────┐  ① 下游告诉上游："我还有 N 个 buffer 可用"（credit）
      │ 上游    │◀──────────────────────────────────│ 下游    │
      │        │  ② 上游只发不超过 credit 的数据量     │        │
      │        │───────────────────────────────────▶│        │
      └────────┘  ③ credit = 0 时上游等待，**但连接依然是活的**
```

**关键收益**：流控发生在**应用层**，而不是让数据在 TCP 层堆积。所以：

| 效果 | 说明 |
|---|---|
| 数据被"扣在"上游的 output buffer 里 | 而不是塞进 TCP 缓冲区 |
| **checkpoint barrier 与心跳不被数据堵住** | 检查点仍能推进（虽然慢），作业不会被误判为失联 |
| 反压可被**精确观测** | 有 `inPoolUsage` / `outPoolUsage` 这类指标可看 |

### 4.3 定位背压：三个观测入口 {#diagnose}

| 入口 | 看什么 | 判据 |
|---|---|---|
| **WebUI → 作业图** | 算子上是否有背压标记 | 有标记的算子 → 往**下游**找 |
| **WebUI → BackPressure 页** | 各 subtask 的"被背压时间占比" | **只是"忙"还是"被挡住"**：被挡住的时间占比高 = 上游把它堵住了 |
| **Metrics** | `inPoolUsage`（输入缓冲使用率）、`outPoolUsage` | **> 0.9 持续存在 = 该侧严重背压** |

还有一个**最容易被忽略但最有用的入口**：

```
   WebUI → 某个算子 → Metrics → numRecordsIn / numRecordsOut 的**各 subtask 对比**
```

**同一个算子内部，如果不同 subtask 的输入速率差几倍，那就是数据倾斜**——它与背压常常同时出现，但根因完全不同（见 4.5）。

### 4.4 背压的四种根因与各自的判据 {#root-causes}

| # | 根因 | 判据 | 解法 |
|---|---|---|---|
| 1 | **外部系统慢**（sink / lookup join 打外部库） | 背压出现在 sink 或 lookup 算子上游；`outPoolUsage` 高的算子紧邻外部调用 | 提吞吐（批写、异步、加连接池）；或降低调用频率（缓存） |
| 2 | **数据倾斜** | 同一算子的 subtask 之间 records 数差数倍 | 加盐打散、两阶段聚合、rebalance |
| 3 | **GC / 内存不足** | 有 GC 日志或 GC 时间指标异常；任务堆内存打满 | 状态后端起 RocksDB、降状态体积、调内存配比 |
| 4 | **状态访问/序列化慢** | 背压在重状态算子上；`serialization` 相关指标高 | 换状态形态（`MapState` 而非 `ValueState<Map>`）、开 mini-batch、RocksDB 调优 |

> **一个高频组合**：**根因 1 + 根因 2 同时出现**——外部系统慢造成背压，背压让"key 分布不均"的后果被放大（少数 subtask 承担了绝大部分积压）。**先解决倾斜，再解决外部系统**，否则加资源也没用（倾斜的分区只会在一个 subtask 上卡住）。

### 4.5 数据倾斜：定位与三种解法 {#skew}

**定位**（不需要额外工具）：

```
   WebUI → 算子 → Subtasks 标签页 → 对比各 subtask 的 numRecordsIn
   判据：最大 / 最小 > 3  →  倾斜；> 10  →  严重倾斜
```

**解法一：加盐打散（适用于"热点 key 天然存在"）**

```sql
-- 原来：按 user_id 聚合，某个大客户占了 60% 的数据
-- 改成：加一列随机前缀 → 先局部聚合 → 去掉前缀再全局聚合
SELECT user_id, sum(cnt)
FROM (
  SELECT user_id, sum(local_cnt) AS cnt
  FROM (
    SELECT CONCAT(user_id, '-', CAST(RAND() * 8 AS INT)) AS salted_key, user_id, count(*) AS local_cnt
    FROM orders GROUP BY CONCAT(user_id, '-', CAST(RAND() * 8 AS INT)), user_id
  ) GROUP BY user_id
) GROUP BY user_id;
```

**解法二：两阶段聚合（优化器开关，优先试它）**

```sql
SET 'table.optimizer.agg-phase-strategy' = 'TWO_PHASE';   -- 本地预聚合 + 全局聚合
```

它把"所有同 key 数据汇聚到一个 subtask"变成"先在本地各自预聚合一次，再汇聚预聚合结果"。**对 `sum`/`count` 这类可结合的聚合很有效**，对 `count(distinct)` 无效（那需要专门的去重方案）。

**解法三：`rebalance`（适用于"与 key 无关"的场景）**

```java
stream.rebalance()   // 轮询分发，把数据均匀打散到所有下游
```

⚠️ **`rebalance` 只在"聚合与 key 无关"时可用**（如纯写入、不需要按 key 有序的场景）。**按 key 聚合的流用 `rebalance` 会破坏正确性**——同一个 key 被分到不同 subtask，聚合结果就错了。这是最容易犯的错。

## 五、内存与网络缓冲 {#memory}

Flink 1.10 起采用统一内存模型，TaskManager 的内存被明确分段：

```
   Total Process Memory
   ├── JVM Metaspace
   ├── JVM Overhead
   └── Total Flink Memory
       ├── Framework Heap / Off-heap      （Flink 自身）
       ├── Task Heap / Off-heap           （算子里的用户对象）
       ├── Managed Memory                 （RocksDB 状态、批算子）
       └── Network Memory                 （⭐ 网络缓冲）
```

**为什么"网络缓冲"值得单独一提**：

| 配置 | 影响 |
|---|---|
| `taskmanager.network.memory.fraction` 太小 | buffer pool 小 → credit 很快耗尽 → **更容易出现背压**（即使下游其实跟得上） |
| buffer 大小（`taskmanager.memory.segment-size`）太小 | 每条消息的头部开销占比高，吞吐下降 |
| buffer 太多 | 挤占 Managed Memory → RocksDB 状态频繁刷盘 |

**判据**：如果**背压出现在几乎每个算子、且各 subtask 均匀**（不是倾斜），并且下游确实处理得过来——先怀疑**网络缓冲不足**，而不是去加并行度。

## 六、检查点调优与背压的联动 {#checkpoint-tuning}

这两个问题必须一起看，因为**背压会直接导致检查点超时**：

```
   背压 → barrier 在数据队列里排不上队 → 对齐等待时间变长 → 检查点超时
                                                          │
   如果只调大 timeout → 检查点"不再超时"，但耗时仍然很长 → 恢复时间变长
   如果只调小 interval → 检查点更频繁，加重负担
```

**正确的处理顺序**：

| 步骤 | 动作 | 判据 |
|---|---|---|
| 1 | **先解决背压** | 看 4.4 的四种根因 |
| 2 | 开**非对齐检查点** | 若背压无法立刻消除（如外部系统改不动），用 `execution.checkpointing.unaligned.enabled: true` 绕开对齐等待 |
| 3 | 开**增量检查点** | 大状态必开：`state.backend.incremental: true` |
| 4 | 调 `interval` / `min-pause` | 在 RPO 可接受的前提下放宽，减少检查点负担 |
| 5 | 最后才调 `timeout` | **调大 timeout 只是让失败变成"慢"，不解决问题** |

⚠️ **一个反模式**：把 `tolerable-failed-checkpoints` 调大。它只是让作业"带病继续跑"——检查点一直失败，意味着**一旦真出故障，恢复点是很久以前的**（RPO 无限大）。这是把问题藏起来的做法。

## 七、监控清单 {#monitoring}

一个可以照着配的最小监控集：

| 类别 | 指标 | 判据 |
|---|---|---|
| **端到端延迟（最重要）** | Kafka 消费 lag（`records-lag-max`） | **持续增长 = 作业跟不上**；这是唯一能反映"端到端"的指标 |
| 吞吐 | `numRecordsInPerSecond` / `numRecordsOutPerSecond` | 用于对比各算子的处理能力 |
| **背压** | `backPressuredTimeMsPerSecond`、`outPoolUsage` | 占比持续高 / 使用率 > 0.9 |
| 检查点 | 最近一次的成功耗时、大小、失败次数 | 耗时接近 timeout 就是预警 |
| 水印 | `currentInputWatermark` | 长时间不前进 = 上游空闲或卡住（见第一篇的空闲分区） |
| 资源 | TM 堆内存、GC 时间 | GC 时间占比高 → 状态后端起 RocksDB |
| **业务指标** | 结果表的数量、关键值 | 上面全部指标正常但业务结果不对，说明是**逻辑问题**（回到前几篇） |

> **最容易被忽略的一条：`records-lag-max` 才是"端到端延迟"。** Flink 内部所有指标都正常、但 lag 持续增长，说明瓶颈在 Flink 之外的某处（上游生产速度快于下游消费能力，或 sink 侧慢）。**只看 Flink 指标会得出"一切正常"的错误结论。**

## 八、使用场景与面试问答 {#interview}

**Q1：背压是什么意思？出现在某个算子上，说明什么问题？**

背压是**下游处理不过来时，向上游传导的流控信号**（"我暂时不能收数据了"）。关键判据是：**背压出现在哪个算子，瓶颈就在它的下游**——不是它自身。所以定位时要**顺着数据流往下游找**，一路找到第一个"没有被背压、但处理慢"的算子或外部系统。

**Q2：为什么 Flink 用基于 credit 的流控，而不是直接用 TCP 反压？**

TCP 反压会让数据堆积在 TCP 缓冲区，后果是**同一条连接上的所有内容都被阻塞——包括 checkpoint barrier 和心跳**。心跳被阻塞会让 JobManager 误判 TaskManager 失联，表现为"检查点莫名超时 / 作业假死"。credit-based 让流控发生在应用层：上游按下游宣告的可用 buffer 数发送，credit 为 0 时上游等待，**但连接保持活跃，barrier 和心跳仍能通过**。副产品是反压可以被精确观测（`inPoolUsage` / `outPoolUsage`）。

**Q3：Kafka 积压持续增长，怎么定位？**

按"从下游往上游找"的顺序：

1. **先看是不是倾斜**——对比瓶颈算子各 subtask 的 `numRecordsIn`，若最大/最小 > 3，先解决倾斜（加盐或两阶段聚合）
2. **看 sink 和 lookup join**——这两处会打外部系统，是"外部系统慢"的最常见来源
3. **看 GC 与状态**——GC 时间占比高说明状态该搬到 RocksDB
4. **最后才怀疑并行度与网络缓冲**——若背压出现在几乎所有算子且各 subtask 均匀，才考虑网络缓冲不足或并行度不够

**先解决倾斜再加资源**。否则加的资源只会分给空闲的 subtask，热点 subtask 依然卡着。

**Q4：`rebalance` 和加盐有什么区别？什么时候用哪个？**

`rebalance` 是**轮询分发，破坏 key 的分组语义**——所以它**只能用在"聚合与 key 无关"的场景**（如纯写入、不需要按 key 有序）。按 key 聚合的流用 `rebalance` 会**得出错误结果**（同一 key 落到不同 subtask，各自算各自的）。

**加盐（或两阶段聚合）保住了 key 语义**：先按"加盐后的 key"局部聚合，再按"原始 key"全局合并。所以**按 key 聚合的倾斜必须用加盐/两阶段，不能用 rebalance**——这是最容易犯的一个错。

**Q5：检查点一直超时，是不是该调大 timeout？**

不是。**检查点超时往往是背压的症状**——背压下 barrier 在数据队列里排不上队，对齐等待被拉长，必然超时。调大 timeout 只是让"失败"变成"慢"，没有解决问题（而且会让恢复变慢）。

正确顺序：① 先解决背压；② 若背压短期解决不了，开**非对齐检查点**绕开对齐等待；③ 大状态开**增量检查点**；④ 在 RPO 可接受的前提下放宽 `interval`；⑤ 最后才动 `timeout`。

另一个反模式是调大 `tolerable-failed-checkpoints`——那是让作业带病运行，真出故障时恢复点会非常旧。

**Q6：并行度设多少合适？**

从两头倒推：**下限**由 source 决定（Kafka 分区数是最硬的上限，超过只会让多出的 subtask 空闲）；**上限**由瓶颈算子的可切分度决定。三个原则：① 不要全局设一个数（大状态算子与轻量算子诉求不同）；② 无状态算子不是瓶颈，不必高并行；③ **状态大的算子并行度太高反而有害**——每个 subtask 的状态快照都要上传，检查点总负担会上升。

另外要记住**断开算子链才能给单个算子设不同并行度**（链化会把算子绑定成同一并行度）。

**Q7：为什么生产上优先用 Application 模式？**

隔离性好（每个作业独立 JobManager），且 **`main()` 在集群内执行**——客户端不需要上传依赖、不承担生成 JobGraph 的压力，解决了早期"提交大作业时客户端 OOM"的问题。**Session 模式适合开发测试**（提交快、资源利用率高），但一个作业的异常可能影响同集群的其他作业。**Per-Job 模式在 Flink 2.0 已被移除**，改用 Application。

还有一条 K8s 上的硬要求：**容器本地盘不保证持久，所以 checkpoint 与 savepoint 必须指向对象存储**——生产集群上没有"状态存本地"这个选项。
