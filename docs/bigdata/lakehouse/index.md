# Lakehouse：Iceberg / MinIO / 冷热分层

## 一、问题场景：数据湖缺的不是存储，是"事务" {#why-lakehouse}

把一个 Parquet 文件写进对象存储，再让引擎"把整个目录当成一张表来查"——这个做法在演示里没问题，一上生产就散架：

| 缺什么 | 具体表现 |
|---|---|
| **原子提交** | 一次任务写 200 个文件，中途失败留下 130 个。查询时把这 130 个也扫进去，得到一份**不存在的数据** |
| **隔离** | 正在读的任务与正在写的任务互相可见，读到半个批次 |
| **Schema 载体** | 表结构靠"目录 + 文件名约定"隐含表达；某天上游多写一列，下游按位置解析就错位 |
| **分区裁剪** | 要发现有哪些分区，只能**列举目录**（LIST）——对象存储上 LIST 是昂贵操作，分区一多就成瓶颈 |
| **表级统计** | 没有"这份数据范围内 min/max 是多少"的元信息，跳过数据块无从谈起 |
| **变更与回滚** | 想删一批数据得重写整个分区；想回到昨天的状态只能重新跑一遍 |

**这些缺口的共同根源是：文件系统只提供"文件"，不提供"表"。**

Lakehouse（湖仓）的思路是在文件之上**加一层表格式（Table Format）**：数据仍然是对象存储上的 Parquet，但另有一份**元数据**独立记录"当前的表由哪些文件组成、每个文件里是什么范围的数据"。所有事务语义都建立在这份元数据之上。

| 层 | 是什么 | 谁负责 |
|---|---|---|
| **存储** | 对象存储 / HDFS，只管放文件 | MinIO / S3 / OSS |
| **文件格式** | 列式编码，只管高效读一列 | Parquet / ORC / Avro |
| **表格式** | 元数据 + 快照 + 事务语义，**这才是"表"** | **Iceberg** / Hudi / Delta / Paimon |
| **计算引擎** | 读表格式、执行查询 | Spark / Flink / Trino / Doris |

> **一句话认知**：Lakehouse 没有发明新存储，也没有发明新文件格式。它把"表"这个概念**从存储层搬到了元数据层**——这恰好就是数仓相对于文件系统的全部定义。

## 二、Iceberg 的元数据分层与原子提交 {#iceberg-metadata}

### 2.1 四层元数据 {#metadata-layers}

```
              ┌──────────────────────────────────────────────┐
              │  Catalog（目录服务）                          │
              │  记录一件事：表的「当前元数据文件」是哪一个      │
              └───────────────────┬──────────────────────────┘
                                   │ 指向
              ┌───────────────────▼──────────────────────────┐
              │  Table Metadata（metadata.json）              │
              │  Schema 历史 · 分区规范 · 属性 · 快照列表       │
              └───────────────────┬──────────────────────────┘
                                   │ 快照 → 
              ┌───────────────────▼──────────────────────────┐
              │  Manifest List（清单列表，一个快照一份）        │
              │  该快照包含哪些 Manifest + 每个的统计信息        │
              └───────────────────┬──────────────────────────┘
                                   │
              ┌───────────────────▼──────────────────────────┐
              │  Manifest（清单文件）                          │
              │  该分组下有哪些数据文件 + 每文件的 min/max 统计  │
              └───────────────────┬──────────────────────────┘
                                   │
              ┌───────────────────▼──────────────────────────┐
              │  Data Files（Parquet 等）                      │
              └──────────────────────────────────────────────┘
```

**为什么是"树"而不是"平铺列表"**：Manifest 这一层同时解决了两件事——**增量**（一次提交只新增少量 Manifest，不必重写全表的文件列表）和**裁剪**（读之前先用统计信息排除无关 Manifest，不碰数据文件）。这也是 Iceberg 与"扁平事务日志"路线（早期 Delta）的核心架构差异。

### 2.2 ACID 是怎么做到的 {#atomic-commit}

**靠"原子地切换一个指针"。**

一次写入的完整过程：

```
1. 引擎写新的数据文件（此刻还「不属于」任何快照，对读者不可见）
2. 写新的 Manifest、Manifest List、metadata.json
3. 在 Catalog 中执行一次原子操作：让「当前元数据文件」从 M1 指向 M2  ← ★ 提交点
4. 老快照仍然被引用，随时可回滚或用于时间旅行
```

**第 3 步是全部语义的来源**：它是**单点、原子**的（依赖 Catalog 的 CAS / 重命名 / 元数据服务条件更新），所以要么全体读者一起看到 M2，要么都还在 M1，**不存在"看到一半"的状态**。

三个由此推出的结论：

- **提交点之前崩溃 = 无害**。孤儿文件（写了但未被任何快照引用）不会污染结果，只要事后清理。
- **并发写要靠乐观并发控制**。两个写入者都基于 M1 提交，后提交者会被检测到冲突并重试——**并发写不是靠锁，而是靠提交时的 CAS 失败重试**。
- **Catalog 是单点故障面**。元数据指针的原子性依赖 Catalog 的能力，所以"选哪个 Catalog"是个必须认真做的决定。

### 2.3 快照、时间旅行与两类"删除" {#snapshot-delete}

| 能力 | 机制 | 价值 |
|---|---|---|
| **时间旅行** | 每个快照一份 Manifest List，按快照 ID / 时间戳读取 | 复现"某天报表为什么是这个数" |
| **回滚** | 把当前指针指向历史快照 | 一次错误写入可以在秒级撤回，不必重跑数据 |
| **Schema 演化** | 用**列 ID**（不是列位置）标识字段 | 加列、删列、改名、类型提升都不会读错数据 |
| **分区演化** | 分区规范随元数据变化，**旧数据不重写** | 从"按天分区"改成"按小时分区"不再需要重跑历史 |
| **隐藏分区** | 分区值由列转换而来，查询里不需要显式写分区列 | 用户写 `WHERE ts > ...`，引擎自己完成裁剪——不会因为"忘了写分区条件"而全表扫 |

**删除有两类，混淆是常见的理解错误**：

- **Position deletes（按位置删除）**：记录"哪个数据文件的第几行被删了"，精确；
- **Equality deletes（按值删除）**：记录"某列等于某值的行都删"，写入便宜但读时要额外比对；
- **Deletion Vectors（删除向量）**：1.8 引入，是 position deletes 的紧凑位图形式，**把更新的代价压得更低**。

这三者都属于"**写时轻、读时补**"的路线（Merge-on-Read）：更新不重写数据文件，而是记一条删除 + 写一份新文件，读的时候再合并。代价是**读放大**——读得越频繁、合并压力越大，所以需要定期 **Compaction（`rewrite_data_files`）** 把碎片合并回基线。

## 三、格式版本演进：v1 → v2 → v3 {#format-version}

表格式的能力是**按版本逐步长出来的**，把版本与能力对上，是理解"这块能不能用"的关键：

| 版本 | 带来的能力 | 影响 |
|---|---|---|
| **v1** | 基础表语义：快照、清单、分区演化 | 只能"新增文件"，行级更新要重写整个分区 |
| **v2** | **行级删除**（position / equality deletes）、Merge-on-Read | 让"更新与删除"在湖上变得可行 |
| **v3** | **删除向量**、默认列值、行级血缘元数据 | 更新的代价进一步下降，审计与沿袭成为一等能力 |

**近期版本里程碑**（写这类内容时版本事实必须现查，不能凭记忆）：

| 版本 | 时间 | 关键内容 |
|---|---|---|
| **1.8.0** | 2025-02 | 删除向量（deletion vectors）、默认列值、行级血缘元数据 |
| **1.9.0** | 2025-04 | **`variant` 半结构化类型**、`geometry` 地理类型、纳秒时间戳、等值删除语义改进、**从 Delta Lake 迁移的模块**；**弃用 Hadoop 2 与 Spark 3.3** |
| **1.9.1 / 1.9.2** | 2025-05 / 2025-07 | 缺陷修复（含 Parquet 相关 CVE 的依赖升级） |
| **1.10.0** | 2025-09 | 加密密钥元数据、孤儿删除向量清理、**完整兼容 Spark 4.0**、分区统计改为增量计算 |
| **下一版（Format V4）** | 筹备中 | 目标是**原生索引**与**正式的缓存模型**；社区已决定把 Java 基线抬到 **JDK 17** |

**两条趋势值得记住**：

1. **Iceberg 与 Delta Lake 在收敛**——行级血缘、variant 类型这些原本是 Delta 的差异点，现在两边都有；Iceberg 甚至提供了从 Delta 迁移的路径。选型时的"功能清单对比"因此越来越不构成决定性差异，**更该看的是 Catalog 生态与引擎支持的广度**。
2. **`Hadoop 2` / `Spark 3.3` 被正式弃用**是一个明确信号：**湖仓是朝着"现代运行时 + 云原生存储 + 弹性计算"走的**，绑在旧 Hadoop 基础设施上的方案该规划退出了。

### 3.1 Catalog：被低估的关键选型 {#catalog}

Catalog 的作用只有一句话——**记录"当前元数据文件是哪一个"**。但它决定了三件事：谁能并发写、多引擎能不能共享、权限管在哪。

| 形态 | 特点 | 局限 |
|---|---|---|
| **Hive Metastore** | 存量系统最常见，兼容性最好 | 为 Hive 设计，对 Iceberg 的原子提交支持偏弱（这也是很多"提交冲突/元数据不一致"问题的源头） |
| **JDBC Catalog** | 单库自用，部署简单 | 并发能力受数据库限制 |
| **REST Catalog** | **跨引擎、跨厂商的事实标准接口**，认证与授权可插拔 | 需要独立部署与运维 |
| **对象存储直存（HadoopCatalog）** | 无需元数据服务 | 依赖对象存储的原子 rename 语义，**并发安全最弱** |

> **Apache Polaris** 是这一层上值得关注的新项目（incubating）：定位就是一个跨引擎共享的 Iceberg 目录与治理层，用 REST 协议对接 Spark / Flink / Trino / Doris 等。它在 2025 年连续发了 1.0.0-incubating / 1.1.0 / 1.2.0 三个版本，**1.1.0 起已支持 S3 兼容存储（含 MinIO）**，1.2.0 侧重治理（RBAC 细化、更新权限、事件日志）。REST Catalog 规范本身也在持续扩展，方向是让多引擎部署的行为更可预测。

## 四、对象存储与冷热分层 {#tiered-storage}

### 4.1 为什么是 MinIO 而不是 HDFS {#why-minio}

| 维度 | HDFS | MinIO（S3 兼容对象存储） |
|---|---|---|
| 元数据 | NameNode 承载全部元数据，规模上限与单点问题都在这里 | 扁平命名空间，无集中元数据瓶颈 |
| 扩容形态 | 加 DataNode 常要伴随数据迁移与再平衡 | 加节点即扩容 |
| 存算耦合 | 通常与计算同机房甚至同集群 | 天然存算分离 |
| 接口 | 自有 API 为主 | **S3 API**，生态即插即用 |
| 成本 | 三副本 + 高配机器 | 纠删码 + 通用硬件，**单位成本更低** |
| 部署 | 组件多、调优项多 | 单一二进制，运维面小 |

**选对象存储的代价**要一并说清——它的取舍不是免费的：

- **延迟高于本地盘**，且尾部延迟更明显。所以"热数据留本地、冷数据沉对象存储"不是优化，而是**前提**。
- **LIST 操作昂贵**。这正是 Iceberg 用元数据树替代"列目录"的直接动机。
- **重命名不是原子的**（现代 S3 语义下对象本身强一致，但"跨对象的 rename"仍然不是单次原子操作）。所以**只存指针、不靠搬文件**——这一点与 Iceberg 的提交模型正好契合。

### 4.2 三层数据温度模型 {#three-tiers}

| 层 | 典型承载 | 介质 | 访问特征 | 生命周期 |
|---|---|---|---|---|
| **热** | 在线事务、当日明细 | MySQL 主库 / Doris 本地 SSD | 高并发、低延迟 | 数天 ~ 数月 |
| **温** | 近期明细与汇总、看板 | Doris（SSD + HDD 混合） | 中等并发、允许秒级 | 数月 ~ 1 年 |
| **冷** | 归档明细、合规留存 | **对象存储 + Iceberg** | 低频、允许分钟级 | 1 年以上 |

**这张表才是"冷热分层"的全部内容**：不是"数据放两处"，而是**按访问特征把同一份数据的生命切成几段**，每段用最便宜且够用的介质承载。

### 4.3 TTL 自动迁移的三条实现路径 {#ttl-migration}

| 路径 | 做法 | 适合 |
|---|---|---|
| **Doris 自身分层** | 建表时声明冷热策略，过期分区自动从 SSD 迁到 HDD | 数据仍在 Doris 内，只想降存储成本 |
| **定期任务写 Iceberg** | 调度任务按月把过期分区导出为 Iceberg 表，成功后 `DROP PARTITION` | 数据要**真正离开**分析库、长期归档 |
| **表格式自己的 TTL** | 由 Iceberg / Hudi 的保留策略清理过期快照与数据文件 | 冷层内部的自我治理 |

**迁移任务必须做成"先写后删 + 幂等"**，顺序反了就是数据丢失：

```
1. 读源分区 → 写入 Iceberg（按分区写入，保持可重跑）
2. 校验目标分区（行数 + 关键指标 + 抽样）
3. 校验通过 → 删除源分区（TRUNCATE PARTITION）
4. 记录迁移台账（分区、时间、行数、校验结果）
```

第 2 步不能省。**"迁移"这类操作的事故几乎都发生在"删了源、才发现目标不全"**，而它同时又是一个天然幂等的任务（按分区重跑即可），所以正确做法永远是**先写、再验、最后删**。

### 4.4 小文件：湖仓的慢性病 {#small-files}

对象存储上小文件的代价是双重的：**每个文件一次请求**（读放大），以及**元数据膨胀**（Manifest 记录数暴涨，规划变慢）。

治理手段：

- **写入侧控制**：按分区大小与并行度调整写入批次，避免"每个微批一个文件"；
- **定期合并**：`rewrite_data_files`（Iceberg）/ Compaction（Hudi），把小文件并成目标大小的文件；
- **顺带清理孤儿文件**：1.10 引入的孤儿删除向量清理属于同一类例行运维。

> **一条容易被忽略的认知**：湖仓的元数据不是"越细越好"。分区过细、文件过小会把收益吃回去——**分区粒度是与查询模式绑定的设计决策**，不是可以事后随便调的开关。

## 五、对比辨析 {#compare}

| 对比 | 差别 | 何时选后者 |
|---|---|---|
| **数据湖 / Lakehouse** | 文件 + 目录约定 vs 文件 + 表格式 | 只要"存"、不做事务型分析 → 纯数据湖 |
| **Iceberg / Hudi** | 元数据树 + 引擎无关 vs 表服务 + 增量写优化强 | 以流式 Upsert 为主、已在 Hudi 生态 → Hudi |
| **Iceberg / Delta Lake** | 两边能力在收敛；Iceberg 引擎支持更广 | 已在 Databricks / Spark 单栈 → Delta |
| **Iceberg / Paimon** | 通用湖表 vs 为流式更新与 Flink 深度优化 | 以 Flink 为唯一入口、要求极高更新吞吐 → Paimon |
| **REST Catalog / Hive Metastore** | 标准接口、多云多引擎 vs 存量兼容 | 新建多引擎环境 → REST；只在既有 Hive 体系内 → HMS |
| **MinIO / 云对象存储** | 自建、可控、无出口费用 vs 免运维、容量无限 | 有合规或成本要求、数据不出机房 → MinIO |
| **Merge-on-Read / Copy-on-Write** | 写便宜读贵 vs 写贵读便宜 | 写多读少 → MoR；读多写少 → CoW |

## 六、使用场景与面试问答 {#interview}

**Q1：已经有了 Parquet 文件，为什么还需要 Iceberg？**
因为文件系统只有"文件"，没有"表"。直接写 Parquet 会同时缺六件事：原子提交、读写隔离、Schema 载体、分区裁剪、表级统计、变更与回滚。Iceberg 用一份独立元数据（快照 → Manifest List → Manifest → 数据文件）补上这六件事，**数据仍是 Parquet，但"表"的定义搬到了元数据层**。

**Q2：Iceberg 的 ACID 是怎么实现的？**
靠**一次原子的元数据指针切换**。写入时先写新的数据文件与清单，全部完成后再在 Catalog 里把"当前元数据文件"从旧换成新——这是提交点。读者要么全体看到旧快照、要么全体看到新快照，不存在中间态。因此：**提交前崩溃只留下无害的孤儿文件；并发写靠乐观并发控制在提交时检测冲突并重试，而不是靠锁。**

**Q3：格式 v2 和 v3 的关键区别？**
v1 只能新增文件，行级更新要重写整分区；**v2 引入行级删除**（position / equality deletes），让湖上的更新与删除变得可行；**v3 加入删除向量（1.8 落地）、默认列值、行级血缘**，把更新代价进一步压低，并让审计与沿袭成为一等能力。再往后（Format V4）的方向是**原生索引与正式的缓存模型**。

**Q4：为什么它比"列目录"方案快？**
Iceberg 把"有哪些分区/文件"提前写进了 Manifest，**读取时不需要 LIST 对象存储**，而是用 Manifest 里的 min/max 统计先做裁剪，只碰必要的数据文件。对象存储上 LIST 是昂贵操作，分区一多，"列目录"本身就会变成瓶颈。

**Q5：冷热分层怎么落地？TTL 迁移要注意什么？**
按**访问特征**分三层：热在 MySQL / Doris 本地 SSD，温在 Doris（SSD + HDD 混合），冷沉到对象存储 + Iceberg。TTL 迁移任务的正确顺序是**先写、再校验、最后删源**，并且做成按分区可重跑（幂等）。**事故几乎都出在"删了源才发现目标不全"**，所以校验步骤不能省，且要留迁移台账。

**Q6：为什么用对象存储而不是 HDFS？代价是什么？**
HDFS 的元数据集中压力、扩容要再平衡、存算耦合，都与"弹性 + 存算分离"的目标冲突；对象存储加节点即扩容、成本更低、S3 API 生态即插即用（MinIO 还能私有部署、数据不出机房）。代价是**延迟更高（尤其尾延迟）与 LIST / rename 的语义限制**——所以必须配"热数据留本地"，而且表格式只切换指针、不靠搬文件。

**Q7：Merge-on-Read 的读写代价怎么权衡？**
MoR 写时只记删除标记 + 写新文件，**写便宜、读要合并**；Copy-on-Write 写时直接重写数据文件，**写贵、读便宜**。所以写多读少（频繁 CDC 落湖）选 MoR，读多写少（归档与报表）选 CoW；选 MoR 就必须配定期 Compaction，否则读放大和文件碎片会一起恶化。
