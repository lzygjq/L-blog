# OLAP 引擎选型

## 一、问题场景：选型错一步最贵的地方在哪 {#why}

技术选型里最贵的错误不是"选了差一点的那个"，而是**把负载形态判断错了**：

```
             判断错负载形态
                   │
       ┌───────────┴───────────┐
       ▼                       ▼
  选了"单机极致"的引擎        选了"均衡好用"的引擎
  去做高频更新 / 高并发      去做超大规模单表扫描
       │                       │
       ▼                       ▼
  上线后无法收敛：           性能不达标但能活着：
  part 爆炸、mutation 堆积     加机器/调参还能撑
  → 被迫换引擎（最贵）
```

**所以本篇的顺序是"先分负载，再看引擎"。** 引擎的差异本质上是"**它为什么要那样设计**"，理解了这个，具体版本谁强谁弱就不那么重要了。

## 二、第一步：把负载分成四类 {#workload}

同一个"OLAP"标签下，其实是四种完全不同的负载：

| 负载 | 特征 | 对引擎的核心要求 |
|---|---|---|
| **A. 海量追加 + 单表扫描/聚合** | 日志、埋点、事件流；几乎不更新、不删除；查询是"宽表按时间范围扫 + 聚合" | 顺序扫描要极快、压缩率要高、成本要低 |
| **B. 实时更新的宽表** | 从业务库 CDC 同步；主键会反复更新；查询是"最新状态 + 多维分析" | **能按主键 upsert**、更新代价可控、查询要立即可见 |
| **C. 高并发的报表/服务化查询** | BI 看板、面向 C 端的接口化分析；每秒数十到数千次查询 | 并发能力、点查效率、稳定的尾延迟 |
| **D. 跨源联邦查询 / 湖上查询** | 数据留在对象存储或外部系统，不想搬进引擎 | 外部 Catalog 能力、谓词下推、不搬数据的查询效率 |

**这四类之间的差异比"引擎品牌"之间的差异更大。** 一个引擎在 A 上是冠军，在 B/C 上可能是灾难——这不是它不好，是**负载和它的根设计不匹配**。

## 三、第二步：看根设计，而不是看功能表 {#root-design}

功能表可以靠版本迭代追平（今年缺的多表 JOIN 明年可能就有了），但**根设计决定了它的长板与天花板**。

### 3.1 ClickHouse 的根设计 {#ch-root}

| 根设计 | 推出的能力 | 推出的短板 |
|---|---|---|
| **part 不可变 + 后台合并** | 写入路径极简（顺序写、压缩好）；无锁并发读 | 更新/删除代价高、去重只能"最终一致" |
| **稀疏主键索引（granule 级）** | 索引极小可常驻内存；顺序扫描极快 | 点查要读整个 granule；不适合"精确取单行" |
| **单机极致向量化 + 一个查询吃满全机** | 单表聚合速度无人能敌 | **不适合高并发**（资源被单个查询吃满） |
| **分布式表只做路由，JOIN 靠右表建哈希** | 部署与查询模型简单 | 大表 JOIN 大表易 OOM；多表复杂关联不占优 |

> **它的所有气质都是"为 A 类负载设计的"**：顺序扫描、纯追加、单表、低并发、极致吞吐。**选它就是在承认"我的负载长这样"。**

### 3.2 Doris / StarRocks 的根设计 {#mpp-root}

| 根设计 | 推出的能力 |
|---|---|
| **原生 MPP（FE 规划 + BE 执行，数据可 shuffle）** | 多表 JOIN 稳定可预测、大表关联不必靠"右表装进内存" |
| **显式的表模型（Duplicate / Aggregate / **Unique**）** | **按主键 upsert 是一等公民**，不用绕到"合并时去重" |
| **完整 CBO + Runtime Filter + Colocate Join** | 复杂查询的优化空间大、同分布数据可以本地关联 |
| **物化视图的透明改写** | 建好的预聚合**查询会自动匹配**，不要求改写 SQL |
| **两种进程、不依赖外部协调组件** | 运维模型简单（加 BE 即扩容） |

两者同源（StarRocks 由 Doris 分支演进而来），后期分化出不同侧重：Doris 侧更强调湖仓一体与国内生态成熟度，StarRocks 侧更强调向量化执行、CBO 与外部 Catalog 与存算分离。**能力已经非常接近，选择更多取决于团队既有栈与支持来源。**

### 3.3 一张根设计的对照 {#root-table}

| | ClickHouse | Doris / StarRocks |
|---|---|---|
| 更新语义 | 追加为主，去重靠合并（最终一致）/ 25.7 起有 patch parts | **主键模型天然 upsert** |
| 数据可见性 | 受合并影响（`FINAL` 才精确） | 主键模型下更新近实时可见 |
| 索引模型 | 稀疏主键 + 跳数索引（granule 级） | 排序键/前缀索引 + 各类索引（行级可直接定位） |
| JOIN | 右表建哈希（受内存约束） | MPP shuffle + CBO 重排 |
| 并发模型 | 单查询吃满全机（并发靠多副本） | 多查询并行调度（并发靠 BE 扩展） |
| 扩展方式 | 加分片要重分布；加副本不增写入 | 加 BE 扩容 |
| 外部协调 | 需要 Keeper（共享存储架构除外） | 无外部依赖 |

## 四、五个判据（按权重排序）{#criteria}

### 4.1 更新频率（权重最高）{#c1-update}

**这是最硬的一条，也是最常见的选型事故来源。**

| 你的更新形态 | 结论 |
|---|---|
| 纯追加，从不更新 | ClickHouse 完全胜任 |
| 有更新，但能接受"最终一致"（如 CDC 同步后查报表） | 两边都可以：ClickHouse 用 `ReplacingMergeTree`，Doris 用 Unique 模型 |
| **更新要"立刻可见且不重复"** | **优先 Doris / StarRocks** —— ClickHouse 的三条更新路径都有取舍（见[更新与写入](/bigdata/clickhouse/update-and-write#summary)） |
| 高频单行更新（接近 OLTP） | **都不该选**，回到行存或专门的 HTAP |

**判据的问法**：不要问"支持不支持更新"，要问"**更新后多久必须可见、能不能容忍重复**"。

### 4.2 并发形态 {#c2-concurrency}

| 并发量级 | 结论 |
|---|---|
| 几个到几十个并发（内部报表） | 都可以 |
| 数百并发（BI 看板 + 多用户） | Doris / StarRocks 更从容 |
| **上千 QPS（服务化点查）** | **两者都应付不了**，需要缓存层或专门的点查引擎 |

**ClickHouse 的并发短板不是"性能不够"，是资源模型**：一个查询默认吃满所有核（[原因](/bigdata/clickhouse/query-and-index#what-is-vectorized)），并发查询之间是排队关系。**加副本能缓解，但本质上是"用机器数量换并发"，成本曲线很陡。**

### 4.3 单表还是多表 {#c3-join}

| 查询形态 | 结论 |
|---|---|
| 单表大范围扫描 + 聚合（A 类） | **ClickHouse 优势最大**（列式 + 稀疏索引 + 向量化的合力） |
| 少量维度表关联（2~3 张，维表小） | 都可以，ClickHouse 用字典或 `IN` 也能扛 |
| **多表复杂关联为主（星型/雪花、5 张以上）** | **Doris / StarRocks** |

**如果多表关联是核心负载，最好的解法往往既不是换引擎也不是调参，而是"在写入侧打宽"** —— 用 Flink 或物化视图把维度打宽成宽表，让查询层不再 JOIN。这是数仓的常规做法，两个引擎都受益（见 [Flink · CDC 入湖入仓](/bigdata/flink/cdc-to-lakehouse#sink-doris)）。

### 4.4 数据规模与成本 {#c4-scale}

| 量级 | 结论 |
|---|---|
| 单机可容纳（几亿行以内） | **ClickHouse 单机极其划算**（部署简单、性能极高、成本最低） |
| 需多机（十亿~百亿） | 两者都可，差别在扩容方式（CH 加分片要重分布，Doris 加 BE） |
| 需要长期留存历史（年为单位） | **两边都要配冷热分层 + 对象存储湖表**（见 [Lakehouse](/bigdata/lakehouse/#three-tiers)） |

**ClickHouse 在"单机成本效率"上是明显优势项**：一台机器就能跑出别的方案一个小集群的效果，这对中小规模场景是决定性的。

### 4.5 团队运维能力与生态 {#c5-ops}

| 关注点 | 结论 |
|---|---|
| 运维组件越少越好 | Doris / StarRocks（两种进程，无外部依赖）；ClickHouse 要自己管分片/副本/Keeper |
| 需要外部 Catalog 直接查湖上数据 | Doris / StarRocks 的外部 Catalog 更顺手（D 类负载） |
| 中文资料与国内链路经验密集 | Doris / StarRocks 在国内实时数仓（Flink CDC → 引擎）链路的资料更密集 |

> **"生态偏薄"要说得更准确**：ClickHouse 的**国际化**生态其实非常丰富（集成多、第三方工具多、社区活跃），它的短板是**国内实时数仓链路的现成集成经验与中文资料相对少**。把这一点讲准确，比笼统说"生态差"更经得起追问。

## 五、四类负载的推荐矩阵 {#matrix}

| 负载 | 首选 | 次选 | 明确不适合 |
|---|---|---|---|
| **A. 海量追加 + 单表分析** | **ClickHouse** | StarRocks | 引入重组件的大数据栈（Hadoop 全家桶） |
| **B. 实时更新宽表** | Doris / StarRocks（主键模型） | ClickHouse（接受最终一致时） | 把 CH 当 OLTP 用 |
| **C. 高并发报表 / 服务化查询** | Doris / StarRocks | ClickHouse + 缓存 + 多副本 | 任何单引擎硬扛千级 QPS |
| **D. 湖上联邦查询** | Doris / StarRocks 外部 Catalog | Trino 一类纯查询引擎 | 为了查一次就把数据全搬进引擎 |

**组合形态也很常见**（而这一条最容易被忽略）：**ClickHouse 做明细/日志的高吞吐存储与单表分析，Doris/StarRocks 做面向 BI 的宽表与指标**。两者不是替代关系，可以分工。**判断依据仍是负载，不是"哪个更好"。**

## 六、什么情况不该选 ClickHouse {#when-not}

把上一节反过来写一遍——这一节比"它的优点"更有面试价值：

| 场景 | 为什么不该选 |
|---|---|
| 需要"更新后立刻可见且不重复" | 三条更新路径都有取舍：mutation 慢、轻量删除不省盘、patch parts 有版本与开关依赖；表引擎去重是最终一致 |
| 每秒上千次点查 | 单查询吃满全机 + granule 级读取，资源模型与点查负载相反 |
| 多表复杂 JOIN 是核心负载 | 默认算法受"右表装进内存"约束；大表关联稳定性不如原生 MPP |
| 需要跨行事务 / 强一致约束 | 不可变 part + 异步合并的模型里没有事务的位置 |
| 团队运维人手紧张、要求最少组件 | 分片、副本、Keeper 都要自己规划，扩容还涉及数据重分布 |
| 数据要频繁按主键部分更新（如用户画像实时刷新） | 每次更新都是一次"追加 + 等待去重"，读时还要处理重复 |

> **换个说法**：**只要你的负载里出现"改一行、马上要看、还不能重复"，就该认真考虑别的引擎。** 这句话几乎能覆盖上面全部六行。

## 七、一次真实的否决式选型演练 {#case}

把上面五个判据套到一个具体场景上，看它们怎么收敛（完整案例见[大数据架构方案 → 数仓落地](/projects/property-saas/data-warehouse/#selection)）：

| 判据 | 该场景的实际形态 | 指向 |
|---|---|---|
| 更新频率 | 业务库 CDC 同步，主键会反复更新（订单状态、缴费状态） | Doris / StarRocks |
| 并发形态 | 多个部门的报表 + 看板并发打开 | Doris / StarRocks |
| 单表 vs 多表 | 星型模型为主，报表常关联 4~6 张表 | Doris / StarRocks |
| 数据规模 | 中等规模，需要长期留存 | 两者都可（配对象存储归档） |
| 运维能力 | 团队规模有限，要求组件最少 | Doris / StarRocks |

**五条判据全部指向同一侧**，于是结论明确：选 Doris，**否决 ClickHouse 的理由不是"它不好"，而是"这个负载不在它的长板上"**——单表吞吐强但并发与多表 JOIN 弱、国内链路的资料密度也不占优。

> **这条演练的价值**：选型的产出物不是"选了谁"，而是**"为什么否决了其他"**——每一行都能在评审会上被追问，且都有本板块的机制解释兜底（更新为什么慢 → [不可变 part](/bigdata/clickhouse/storage-engine#why)；JOIN 为什么弱 → [右表建哈希](/bigdata/clickhouse/query-and-index#join-algorithm)）。

## 八、使用场景与面试问答 {#interview}

**Q1：ClickHouse 和 Doris 怎么选？**

先分负载：**纯追加、单表大范围扫描、低并发、单机可容纳 → ClickHouse**（它在这四项上是冠军，且单机成本效率极高）；**有主键更新、多表 JOIN 占比高、并发较高、要求组件最少 → Doris / StarRocks**。差异的根源是根设计：前者是"不可变 part + 稀疏索引 + 单机极致向量化"，后者是"MPP + 显式表模型 + CBO"。

**Q2：为什么说 ClickHouse 不适合高并发？**

一个查询默认吃满整机核数（`max_threads` = 核数），并发查询之间是资源竞争与排队关系。加副本能分摊，但那是"用机器换并发"。这一条是根设计决定的，不是调参能解决的。

**Q3：ClickHouse 的 JOIN 到底弱在哪？**

默认 `hash` 算法把**右表整体读进内存**建哈希表，且每个节点各建一份 → 大表 JOIN 大表容易 OOM。左表可以很大（流式探测）。缓解手段：写入侧打宽成宽表、用字典、`IN` 代替 JOIN、`grace_hash` / `partial_merge`。**26.x 在 JOIN 上投入很大（runtime filter、统计信息重排、IEJoin），这条结论在快速变化——回答时要带版本。**

**Q4：什么情况下"两个引擎都用"是对的？**

当负载天然分成两类时：**ClickHouse 承接高吞吐明细与单表分析，Doris/StarRocks 承接面向 BI 的宽表与指标**。这不是冗余，是分工。判断依据仍然是负载特征，不是"哪个引擎更先进"。

**Q5：怎么快速判断一个引擎适不适合？**

问三个问题：**同一主键会不会反复更新、更新后多久必须可见、查询是单表还是多表。** 这三问的答案基本就定死了选型方向。剩下的是成本与运维能力。

**Q6：为什么"引入组件容易、去掉很难"？**

因为组件一旦进入生产链路，就会有数据落上去、有报表依赖它、有人会写脚本调它——**迁移成本随时间指数上升**。所以选型时的正确姿势是"**先问它解决的是必需问题还是可能用到的问题**"，后者应当等到真的需要再加。这条原则同样适用于"要不要上 Hadoop 全家桶"这类更宏观的决策。

**Q7：单机 ClickHouse 能撑多大？**

取决于列数、压缩率与查询形态，无法给一个通用行数。可靠的做法是**用自己的 schema 与真实查询做压测**（这正是[压测报告](/projects/toolkit/perf-report/)的用途），而不是引用别人的"十亿行亚秒"——那些数字高度依赖具体表结构与硬件。

**Q8：选型结论该怎么记录？**

用否决式记录：**每个决策点写"结论 + 被否决的方案 + 否决理由"**（见[架构决策记录](/projects/toolkit/adr/)）。好处是半年后有人问"当时为什么不选 X"，答案在文档里、且带着当时的约束条件，而不是靠回忆。
