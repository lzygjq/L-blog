# 更新、删除与写入

## 一、问题场景：列存最不擅长的三件事 {#why}

业务上天天发生的三件事，在列存里都很难：

| 诉求 | 行存的答案 | 列存的困难 |
|---|---|---|
| 改一行的几个字段 | `UPDATE … WHERE id = 1` | 要同时改 N 个列文件，无法原子完成 |
| 删一行 | `DELETE FROM … WHERE id = 1` | 删掉某个位置，会让后续所有行的偏移都要重排 |
| 持续小批量写入（每秒几次） | 完全没问题 | 每次写入生成一个 part，part 数量爆炸 |

ClickHouse 的答案不是"把这三件事做快"，而是**给出三条不同代价的路径，让你按频率和容忍度选**。

```
        改/删频率低，能等            ┌──────────────────────────────────────┐
   ─────────────────────────────▶  │ 路径一：mutation（重写 part）          │  最慢、最彻底
                                    └──────────────────────────────────────┘
        删除要及时可见，改不急       ┌──────────────────────────────────────┐
   ─────────────────────────────▶  │ 路径二：lightweight delete（写掩码）   │  秒级可见、但残留
                                    └──────────────────────────────────────┘
        高频小批更新                ┌──────────────────────────────────────┐
   ─────────────────────────────▶  │ 路径三：patch parts（25.7 起）         │  增量、代价小
                                    └──────────────────────────────────────┘
        主键覆盖，读时能接受最终一致 ┌──────────────────────────────────────┐
   ─────────────────────────────▶  │ 旁路：表引擎去重（ReplacingMergeTree） │  写入零额外成本
                                    └──────────────────────────────────────┘
```

## 二、路径一：mutation —— 重写 part {#mutation}

```sql
ALTER TABLE events UPDATE amt = 0 WHERE city = 'SH';   -- 这就是 mutation
ALTER TABLE events DELETE WHERE ts < '2025-01-01';
```

执行过程：

```
① 找出所有可能含目标行的 part（**谓词不参与裁剪**，几乎总是全部 part）
② 逐个 part：读出 → 应用改动 → 写成新 part → 替换旧 part
③ 异步执行、串行排队，进度可在 system.mutations 里看
```

**三个必须记住的特征**：

1. **代价与"表/part 总大小"成正比，与"改了多少行"无关。** 十亿行的表改一行，要重写十亿行。
2. **它是异步的、且排队串行。** `is_done = 0` 期间数据处于"部分改完"的状态；多个 mutation 会互相等待。**一旦有一个卡住（比如 part 过大或磁盘紧张），后面的全部堆积。**
3. **它会把 part 重写一遍，等于人为制造一次全量合并。** 频繁使用会让后台合并压力剧增。

> **判据：`ALTER … UPDATE / DELETE` 只适合"低频、批量、一次性"的修正**（订正一批历史脏数据、按条件清理一批异常记录）。**只要它在你的日常路径上，就说明表设计或引擎选型有问题。**

## 三、路径二：lightweight delete —— 写掩码 {#lightweight-delete}

```sql
DELETE FROM events WHERE city = 'SH';       -- 注意：不是 ALTER
```

这条语句走的是**轻量级删除**：它不重写数据，而是给被删的行**打一个掩码**（内部维护一个 `_row_exists` 标记），查询时自动过滤掉被标记的行。

| | mutation（`ALTER … DELETE`） | lightweight delete（`DELETE FROM`） |
|---|---|---|
| 数据是否重写 | 是（重写 part） | **否**（只写掩码） |
| 可见延迟 | 要等 mutation 执行完 | **秒级可见** |
| 磁盘是否释放 | 是 | **否**——被标记的行还在，要等后续合并才真正清除 |
| 代价 | 与数据量成正比 | 与"被删行数/标记量"相关，很小 |

**它的定位很明确**：需要"立刻删掉、立即不可见"的合规类需求（如按用户撤销、按规则清理），**但不能指望它省磁盘**。滥用（高频删除）会让掩码越积越多，读放大增加、合并负担变重——**"轻量"指的是写入轻，不是长期零成本。**

## 四、路径三：patch parts —— 25.7 起的增量更新 {#patch-parts}

**ClickHouse 25.7（2025-07）引入了基于 patch parts 的更新路径**：不再是"重写整个 part"，而是把改动写成**一个很小的 delta part**（只含被改行的新值），查询时把 delta 与原数据合并呈现。

官方公布的数字是：在六亿行的基准上，批量更新比经典 mutation **快约 1,700 倍**，单行更新最多快约 **2,400 倍**。

**但它有几个必须一起记住的限制**（否则会误用）：

- 这条路径**最初是实验性的、需要显式开启**，后续版本逐步放开——**升级时务必确认当前版本的行为与开关状态**。
- patch part **需要与主数据一起被读取和合并**，所以 delta 累积多了，读取代价会上升（和轻量级删除是同一个道理）。
- 它优化的是"**更新的写入代价**"，**没有**把 ClickHouse 变成支持高频行级更新的 OLTP 引擎。真正的强更新负载仍应换引擎。

> **这条事实的行情会变**：25.7 之前所有资料都说"ClickHouse 不能 UPDATE"，26.x 的资料开始说"能 UPDATE 了"。**写任何选型结论时都要带版本号**，否则一年后就是错的（这也是本板块每篇都带「版本现状」的原因）。

## 五、旁路：表引擎去重（ReplacingMergeTree）{#replacing-strategy}

如果业务能接受"**最终一致**"，那么最高效的更新路径是**不做更新**——照常追加，让去重在合并时发生。这是 ClickHouse 处理"CDC 同步过来的变更"最主流的做法（与 [Flink · CDC 入仓](/bigdata/flink/cdc-to-lakehouse#sink-doris) 那条链路直接对接）。

### 5.1 版本列怎么设计 {#version-column}

```sql
ENGINE = ReplacingMergeTree(updated_at)      -- 版本列
ORDER BY order_id
```

**版本列是整个方案的正确性根基**，三条要求：

| 要求 | 原因 |
|---|---|
| **单调可比** | 去重比的是"谁大"，时间戳回退会让旧数据"赢" |
| **唯一（至少对同一主键唯一）** | 时间戳相同（同秒内的两次变更）时胜负不定 |
| **不可为 NULL** | 版本列为空时行为退化为"取决于合并顺序" |

**推荐组合**：`业务时间戳 + 单调递增的来源序号`（如 binlog 位点或 Flink 里的序列号），避免"同一秒内两次变更顺序颠倒"这类经典事故。

### 5.2 读时的去重代价 {#final-cost}

去重只在合并时发生，所以**查询时刻可能看到重复行**。三种应对：

| 做法 | 代价 | 适用 |
|---|---|---|
| `SELECT … FINAL` | **在查询时做合并**，性能显著下降（尤其是大表多列时） | 数据量小、或对正确性要求极高的校验场景 |
| `GROUP BY key` + `argMax(col, version)` | 自己写去重逻辑，可控且可利用索引 | 需要精确结果且不想吃 `FINAL` 的全量代价 |
| **接受近似，或在查询层做收敛** | 需要业务上能容忍"同一主键短暂出现多行" | 报表类负载（最主流） |

> **一个容易忽略的点**：`FINAL` 的代价随**列数**增长。如果表很宽，`FINAL` 会非常贵。这反过来说明：**能接受近似就别用 `FINAL`；一定要用，就让表窄一点**（只放参与去重的关键列 + 需要的指标）。

## 六、写入侧：part 数量的战争 {#write-path}

### 6.1 一次 INSERT 的完整链路 {#insert-path}

```
INSERT 请求
   │
   ├─ ① 攒成一个 block（受 max_insert_block_size 限制，默认约 104 万行）
   ├─ ② 按排序键排序、计算主键索引、写临时目录
   ├─ ③ 生成 part 目录 → **原子改名**提交（data part 的出现是原子的）
   └─ ④ 注册到元数据，后台合并开始关注它
```

**核心结论：一次 INSERT = 至少一个 part。** 这是 part 数量失控的唯一原因。

part 数量失控会依次引发：

```
part 太多
 ├─▶ 查询要做的多路归并变深 → 单查询变慢
 ├─▶ 后台合并任务排队、追不上写入 → part 更多（正反馈）
 └─▶ 触发保护阈值：
         parts_to_delay_insert（延迟插入）
         parts_to_throw_insert（直接报错 Too many parts）
```

### 6.2 async_insert：把攒批搬到服务端 {#async-insert}

原本需要客户端自己攒批；`async_insert` 让**服务端**先把小批攒起来、再合并成大的 part 落盘：

```sql
INSERT INTO events SETTINGS async_insert = 1, wait_for_async_insert = 1 VALUES (...);
```

两个参数的分工必须分清：

| 参数 | 含义 | 建议 |
|---|---|---|
| `async_insert = 1` | 服务端攒批 | 小批写入场景开启 |
| `wait_for_async_insert = 1` | 客户端**等服务端落盘后**才返回 | **默认且建议保持 1** |
| `wait_for_async_insert = 0` | 客户端不等、立即返回 | 吞吐最高，但**插入错误会被吞掉**（你拿不到失败反馈） |

> **版本提示**：**自 26.3 起 `async_insert` 默认开启**。这意味着升级到 26.x 后，"原来同步可见"的插入可能变成"攒一会才可见"（`wait_for_async_insert = 1` 时客户端仍等待落盘，但批内可见时机由服务端决定）。**升级前要在测试环境验证可见性语义**，必要时显式设 `async_insert = 0` 保住旧行为。

### 6.3 幂等与去重 {#dedup}

重试是分布式写入的常态（CDC 至少一次语义、网络超时重发）。ClickHouse 的插入去重是按"**同一批次内容相同**"判定的：

| 场景 | 去重是否有效 |
|---|---|
| 同一份数据**逐字节相同**地重发 | 有效（有专门的插入去重机制） |
| 数据被打乱、分批不同 | **无效**——会被当作不同批次 |
| 通过不同入口（如直接写本地表 vs 写分布式表）| 判定口径不同，容易失效 |

> **版本提示**：**26.2 起插入去重默认开启**（此前默认关闭）。这是升级时容易踩的一条——它可能改变"重复写入是否产生重复行"的行为。**但无论如何，都不要把去重当作幂等的替代品**：正确做法仍是"**主键 + 版本列**"（即 `ReplacingMergeTree` 那一套），插入去重只是"重试不产生脏数据"的一层额外保护。

## 七、四条路径的选择与反模式 {#summary}

| 你的场景 | 该走哪条 | 关键代价 |
|---|---|---|
| 订正一批历史脏数据（一次性） | mutation（`ALTER … UPDATE`） | 重写 part，慢但一次性 |
| 按规则清理一批数据（一次性、要立刻生效） | lightweight delete（`DELETE FROM`） | 磁盘不立刻释放 |
| 合规要求"立即不可见" | lightweight delete | 同上，要定期靠合并回收 |
| 高频小批更新（CDC 变更） | **写入侧追加 + `ReplacingMergeTree`** | 读时可能重复，需版本列设计 |
| 单条/少量行的实时更新 | patch parts（25.7+） | 需确认版本与开关；delta 累积会加读成本 |

**四个反模式**：

1. **在循环里逐行 `INSERT`** → part 爆炸，必然 `Too many parts`。攒批或开 `async_insert`。
2. **用 `ALTER … UPDATE` 做业务更新** → 每次都是一次全量重写 + 串行排队，最终拖垮整个集群的后台任务。
3. **版本列用 `now()` 或写入时间** → 重试与乱序会让版本"回退"，去重结果错误。要用**业务时间 + 来源序号**。
4. **依赖插入去重保证幂等** → 它只在"批次内容完全一致"时成立，数据分批变化就失效。幂等要靠主键语义。

## 八、使用场景与面试问答 {#interview}

**Q1：ClickHouse 到底能不能 UPDATE？**

能，但要分清三条路径：`ALTER … UPDATE` 是 mutation（重写 part，代价与数据量成正比）；`DELETE FROM` 是轻量级删除（写掩码，可见快、不省盘）；**25.7 起有了基于 patch parts 的增量更新路径**（官方口径：六亿行基准上比经典 mutation 快约 1,700~2,400 倍）。但**这都不改变"它不适合高频行级更新负载"这个结论**。

**Q2：`ALTER TABLE … DELETE` 和 `DELETE FROM` 有什么区别？**

前者是 mutation：重写 part、异步排队、磁盘立即释放、代价与数据量成正比。后者是轻量级删除：只写掩码、秒级不可见、**磁盘不释放**（等合并才清）。前者适合一次性清理，后者适合"必须立刻不可见"。

**Q3：`ReplacingMergeTree` 的版本列该怎么选？**

必须**单调、对同一主键唯一、非 NULL**。推荐"业务时间戳 + 来源单调序号"。用写入时间或 `now()` 会在重试与乱序时让版本回退，导致旧数据胜出——这是最常见的线上事故。

**Q4：为什么查 `ReplacingMergeTree` 还会看到重复行？**

因为去重发生在**合并时**，而合并是异步的。插入后合并前必然可能有多行。要精确结果用 `FINAL`（贵，且代价随列数增长）或 `GROUP BY + argMax`（可控）。报表类负载通常接受近似。

**Q5：`Too many parts` 是怎么造成的？**

每次 `INSERT` 至少产生一个 part，而合并是后台异步的。写入频率超过合并消化能力，part 数就会持续上涨，超过 `parts_to_throw_insert` 阈值直接报错。解法是**减少 part 的产生速度**：客户端攒批、开 `async_insert`、降低写入频率。**加机器不解决这个问题**（合并是按分区进行的）。

**Q6：`async_insert` 的 `wait_for_async_insert = 0` 有什么风险？**

客户端不等落盘就返回，吞吐最高，但**插入失败的信息你也拿不到**——数据可能静默丢失。除非你能接受"允许丢且能事后对账"，否则保持默认的 `1`。

**Q7：CDC 同步过来的变更，怎么在 ClickHouse 里落地成"最新状态"？**

主流做法：照常追加、表引擎用 `ReplacingMergeTree`、版本列用"业务时间 + 来源序号"，读取侧接受最终一致（必要时 `argMax` 收敛）。这样写入路径零额外成本，去重成本转移到后台合并——这正是列存擅长的分工方式。

**Q8：升级到 26.x 时，写入语义有哪些要注意的变化？**

两处：**26.2 起插入去重默认开启**（可能改变重复写入的行为）、**26.3 起 `async_insert` 默认开启**（可能改变数据可见时机）。这两项都会改变"看起来一样"的写入行为，**升级前必须在测试环境验证可见性与去重语义**。
