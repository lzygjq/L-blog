# 副本、分片与集群运维

## 一、问题场景：单机的三个天花板 {#why}

前面三篇讲的都是单机能跑多快。到了生产就有三个绕不过去的天花板：

| 天花板 | 表现 | 靠什么突破 |
|---|---|---|
| **容量** | 一块盘装不下、一台机器加不了盘 | **分片**（把数据横向切开） |
| **可用性** | 单机宕机 = 数据不可用 | **副本**（多份数据互为备份） |
| **查询并发** | 单个查询吃满全机核数 | **副本 + 并行查询**（读分摊到多台） |

**关键在于：网上大量"ClickHouse 集群"的故障，根因都是把前两个混为一谈。** 它们是两套独立机制，解决的是不同问题。

## 二、副本与分片：两套机制，别混 {#replica-shard}

### 2.1 副本：同一份数据的多个拷贝 {#replication}

```sql
ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/events', '{replica}')
ORDER BY (city, ts)
```

两个参数是 **Keeper 里的路径** 与 **本副本标识**，都用宏（`{shard}` / `{replica}`）在配置里区分。

副本之间怎么同步？**不是"主从复制"，是"通过协调服务达成共识后各自拉取"**：

```
      写入到达副本 A
            │
      ① 数据先落本地 part
      ② 向 Keeper 登记："我有了 part X"（写入队列）
            │
      ③ 其它副本从 Keeper 看到这条记录，**各自主动去 A 拉取数据**
      ④ 拉完、校验、登记完成
```

**推论（决定了它的运维特征）**：

- **没有唯一主副本**（多副本都可以写，靠 Keeper 协调去重）→ 不存在 MySQL 那种"主库是单点"的问题
- **副本落后是可以观测的**（`system.replicas` 的 `absolute_delay` / `queue_size`）→ 副本不健康时应该能从监控里立刻看到
- **副本数不改变写入吞吐**（每次写都要在副本间同步）→ **想扩写入必须分片，加副本没用**

### 2.2 分片：数据被切开放在不同机器上 {#sharding}

分片是**逻辑上的横向切分**：每个分片只持有全量数据的一部分（由 sharding key 决定）。

| | 副本 | 分片 |
|---|---|---|
| 存的是 | 同一份数据的**完整拷贝** | 全量数据的**一个子集** |
| 解决 | 可用性、读扩展 | **容量、写扩展** |
| 加机器后 | 读能力上升，容量不变 | 容量与写能力上升 |
| 查询时 | 任意一个副本都能独立回答 | **必须汇总所有分片的结果** |

### 2.3 标准拓扑：分片 × 副本 {#topology}

生产上两者叠加：

```
        ┌──────────── 分片 1 ────────────┐   ┌──────────── 分片 2 ────────────┐
        │  shard1-replica1  shard1-replica2 │   │  shard2-replica1  shard2-replica2 │
        │  （互为主备，数据相同）            │   │  （互为主备，数据相同）            │
        └──────────────────────────────────┘   └──────────────────────────────────┘
                 ▲                                        ▲
                 └──────────── Distributed 表 ───────────┘
                         （本身不存数据，只做路由与汇总）
```

**两个分片、每分片两副本 = 四台机器**，这是最常见的起步形态。分片数**建好后不要轻易改**（改分片数等于数据重分布，见第六节）。

## 三、协调服务：Keeper 与 ZooKeeper {#keeper}

`ReplicatedMergeTree` 需要一个协调服务来记录"谁有哪些 part、谁需要拉取、谁来做合并决策"。

| | ZooKeeper | **ClickHouse Keeper** |
|---|---|---|
| 实现 | Java | **C++**（ClickHouse 官方组件） |
| 兼容性 | 原生 | **协议兼容 ZooKeeper**，客户端无感 |
| 部署 | 独立 JVM 集群 | 可独立部署，也可与 `clickhouse-server` 同进程（省组件） |
| 现状 | 仍支持 | **新部署的推荐选择** |

**为什么推荐 Keeper**：少一套 JVM 组件、少一层运维负担、与 ClickHouse 一起升级、性能与资源占用更可控。

三个运维要点：

1. **Keeper 是三节点起步的有状态集群**，它的可用性决定了整个 ClickHouse 集群的"元数据面"可用性——**它宕了，副本间无法同步，但已存在的 part 仍可查询**（这是常见面试点：Keeper 故障是"部分降级"而不是"全站不可用"）。
2. **znode 数量与合并频率正相关**：part 越多、合并越频繁，Keeper 的压力越大。**part 数量失控会同时压垮 ClickHouse 和 Keeper**（两个问题经常一起出现）。
3. **共享存储架构下不再需要 Keeper**：ClickHouse Cloud 与部分自建共享存储场景使用 `SharedMergeTree`，元数据放在共享存储上，由轻量协调替代 Keeper 的角色。**如果你在自建环境，`ReplicatedMergeTree` + Keeper 仍是标准答案。**

## 四、写入路径：分布式表 vs 本地表 {#write-path}

### 4.1 Distributed 表是什么 {#distributed}

```sql
CREATE TABLE events_all AS events
ENGINE = Distributed('my_cluster', 'default', 'events', rand());   -- 最后是分片键
```

`Distributed` 引擎的表**自己不存数据**，只做两件事：**写入时按分片键路由**、**查询时下发到所有分片并汇总结果**。

```
INSERT INTO events_all  ──▶ 按 sharding key 拆分 ──▶ 分发到各分片的本地表
SELECT * FROM events_all ──▶ 下发到每个分片 ──▶ 各分片本地聚合 ──▶ 汇总（可能再做一次全局聚合）
```

### 4.2 `internal_replication`：唯一一个必须先搞懂的开关 {#internal-replication}

分布式表的集群定义里有个参数 `internal_replication`，它决定"写入时要不要复制"：

| 取值 | 行为 | 后果 |
|---|---|---|
| **`true`** | 每个分片**只挑一个副本**写入，其余副本由**副本机制**自己同步 | ✅ **正确做法**，写入量最小、一致性由副本机制保证 |
| `false` | 向分片的**每个副本都写一遍** | ❌ 数据被重复写入 N 次；如果表还是 `ReplicatedMergeTree`，会出现**重复数据** |

> **`internal_replication = true` 是绝大多数场景的唯一正确答案。** 配成 `false` 且底层又是副本表，就是"同一份数据写了两遍"，且副本机制还会再同步一遍——这是 ClickHouse 集群最经典的一类事故。

### 4.3 该写本地表还是分布式表 {#write-target}

| | 写本地表（应用自己算路由） | 写分布式表 |
|---|---|---|
| 写入路径 | 应用直连目标分片 | 经发起节点再转发 |
| 批量效率 | **高**（少一跳） | 略低（多一跳、且发起节点要拆分） |
| 复杂度 | 应用要知道分片拓扑 | 简单，应用只当一个表 |
| 大吞吐场景 | ✅ 推荐（配合客户端路由或写入代理） | 一般 |
| 简单场景 / 小规模 | 也可以 | ✅ 推荐 |

**判据**：写入吞吐是瓶颈时，用"应用侧路由 + 直接写本地表"；否则用分布式表换取简单性。

> **一条与前一节的呼应**：这条选择同时决定了**插入去重能不能生效**。写入入口不同（直写本地表 / 经分布式表），去重的判定口径就不同——**同一份数据从不同入口进来，可能被当作不同批次**。

## 五、查询路径与并行副本 {#query-path}

一次对分布式表的查询分三段：

```
① 发起节点解析 SQL，把"能在本地算的部分"下发到每个分片
② 每个分片**先在本地做部分聚合**（例如各自算出自己的 GROUP BY 结果）
③ 发起节点汇总（对上一步的结果再做一次聚合 / 排序 / LIMIT）
```

**两个由此推出的重要结论**：

1. **`GROUP BY` 基数越高，第三步的汇总压力越大。** 如果本地聚合后仍有百万级分组，汇总节点就成了瓶颈——**这就是"高基数聚合要慎重"的机器层面的原因**。
2. **`LIMIT` 必须两层**：各分片先各自取前 N，发起节点再取前 N。所以 `LIMIT` 在分布式表上**不减少扫描量**，只是减少传输量。

**并行副本（parallel replicas，仍在演进中）**：让**同一条查询在多个副本上并行执行**（每个副本处理一部分 granule），于是**加副本就能让同一个慢查询变快**。这让"副本只用于可用性"的认知需要更新——但代价是它会占用其它副本的资源，属于"读放大换吞吐"，需要明确配额。

## 六、扩容与数据重分布 {#scale}

三种扩容的资源要分清：

| 扩什么 | 做加法 | 数据是否要搬 |
|---|---|---|
| 读能力 | 加副本 | ❌ 不用（副本机制自动同步） |
| 写能力 / 容量 | 加分片 | ✅ **必须重分布** |
| 单查询速度 | 加副本 + 开并行副本 | ❌ 不用 |

**关键事实：加分片不会自动重新均衡数据。** `Distributed` 表的路由是基于分片键计算的，已有的分片数变了，**历史数据的归属不会自己变**。

重分布的标准做法（与分库分表那套是同一个问题）：

```
① 新拓扑建好（新分片 + 新副本）
② 建一张指向新拓扑的分布式表，重新写入"按新分片键路由"
③ 把历史数据按新规则搬迁：INSERT INTO new SELECT ... FROM old（可分批、可重跑）
④ 双写 / 对账期 → 切换查询入口
⑤ 验证一致后下线旧表
```

**这件事的成本很高，所以"分片数"属于要提前想清楚的设计决策**，而不是能随时调的参数。判据是**预估 1~2 年的数据量与写入速率**，宁可初期分片少、留出加的空间（加比减容易）。

## 七、冷热分层 {#tiered}

前面讲的 TTL 移动（`TO DISK` / `TO VOLUME`）在集群里通过 **storage policy** 统一配置：把本地 SSD、本地 HDD、对象存储组成"卷"，再按 TTL 规则让数据逐级下沉。

```
hot 卷（本地 NVMe）  ──7 天──▶  cold 卷（本地 HDD / 大容量 SSD）
                                        │
                                     30 天
                                        ▼
                              s3 卷（对象存储，成本最低）
```

**两个注意点**：

1. **下沉是"按 part"发生的**，一个 part 里的数据要全部过期才会整体搬走。所以 TTL 的粒度会受合并状态影响（跟分区粒度一起决定了"什么时候真正省下成本"）。
2. **冷数据查询会变慢**（对象存储的尾延迟显著高于本地盘）。对冷数据有查询需求时，要么接受慢，要么在查询层做"只查热数据"的裁剪——**别指望对象存储上的数据还能亚秒响应**。

## 八、关键监控与运维清单 {#ops}

ClickHouse 的"运维"很大程度上就是**盯住几张系统表**：

| 系统表 | 看什么 | 危险信号 |
|---|---|---|
| `system.parts` | 每个分区/表的活动 part 数与行数 | `count()` 持续上涨、出现大量小 part |
| `system.mutations` | mutation 是否完成 | `is_done = 0` 堆积、最新一条长时间不动 |
| `system.replicas` | 副本状态与延迟 | `absolute_delay` 增长、`queue_size` 膨胀 |
| `system.replication_queue` | 待拉取的 part | 长期不下降（副本追不上） |
| `system.distributed_ddl_queue` | `ON CLUSTER` DDL 的执行情况 | 有节点长期未完成（DDL 卡在半途） |
| `system.merges` | 正在进行的合并 | 合并任务长期排队 |
| `system.query_log` | 历史查询与资源消耗 | 单查询 `memory_usage` 逼近上限 |

**四条日常判据**：

1. **part 数**：单分区 part 数长期高于几十个就要查写入频率与合并是否被拖住。
2. **mutation 队列**：只要不为空且持续有新的，说明有人在日常路径上用 `ALTER … UPDATE/DELETE`。
3. **副本延迟**：`absolute_delay` 持续增长 = 副本追不上写入，先看网络与磁盘，再看是不是 part 太多。
4. **磁盘水位 + Keeper 规模**：两者都会被 part 数量连带影响。

**升级纪律**：ClickHouse 的版本兼容性有一条硬规则——**不能跨版本降级**（新版本写出的数据格式旧版本读不了）。所以升级要按 **LTS → LTS** 走，不要追每个月的稳定版；且升级前务必在测试环境验证写入语义（尤其是去重与可见性，见 [更新与写入](/bigdata/clickhouse/update-and-write#dedup)）。

## 九、使用场景与面试问答 {#interview}

**Q1：副本和分片分别解决什么问题？**

副本解决**可用性与读扩展**（同一份数据的多份拷贝，任意一份能独立回答查询），分片解决**容量与写扩展**（数据被切开，各持一部分）。**加副本不增加写入吞吐**（写要在副本间同步），**加分片才增写入能力**。两者的运维代价也完全不同：副本可以随时加，分片一改就要重分布数据。

**Q2：ClickHouse 的副本是"主从复制"吗？**

不是。没有唯一主副本：多副本都能写，通过 Keeper 登记"我有了某个 part"，其它副本**各自主动去拉取**。所以不存在 MySQL 那样"主库单点"的问题，但引入了"协调服务可用性"这个新依赖。

**Q3：Keeper 挂了会怎样？**

已经存在的 part **仍可查询**（查询不依赖 Keeper），但副本之间的同步会停滞、新的合并决策无法达成共识——属于**部分降级**，不是全站不可用。恢复 Keeper 后副本会自动追平。

**Q4：`internal_replication` 该设成什么？**

**`true`**。它让每个分片只写一个副本，其余副本由复制机制同步。设成 `false` 会向每个副本都写一遍，底层又是副本表时就会出现**重复数据**——这是集群配置里最经典的一类事故。

**Q5：为什么用分布式表写入比直接写本地表慢？**

分布式表只是路由层：数据要先到发起节点，由它按分片键拆分再转发，多了一跳且发起节点承担拆分开销。所以**写入吞吐是瓶颈时，用应用侧路由直接写本地表**；否则用分布式表换简单性。注意这也会改变插入去重的判定口径。

**Q6：加一个分片，数据会自动均衡吗？**

不会。`Distributed` 的路由按分片键计算，历史数据归属不会自己改变，必须显式做重分布（重建拓扑 → 建新路由 → 搬迁历史 → 对账 → 切换）。**所以分片数要提前按 1~2 年的量级规划**，"加比减容易"。

**Q7：分片数怎么定？**

按**预估数据量与写入速率**倒推：单分片能承受的容量与写入是有限的，加副本不解决写入问题。经验上"分片数 × 单分片容量"要留出增长空间，且分片数最好是便于路由与运维的整数（常见 2 / 4 / 8 起步）。

**Q8：为什么 `LIMIT` 在分布式表上不能减少扫描？**

因为每个分片都不知道"全局排前 N 的是谁"，只能各自先算出本地前 N，再由发起节点汇总取前 N。所以它减少的是**传输量**，不是扫描量。想真的少扫，要靠排序键 / 分区裁剪让每个分片一开始就读得少。
