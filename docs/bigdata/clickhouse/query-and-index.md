# 查询执行与索引体系

## 一、问题场景：同一份数据，两种引擎差在哪 {#why}

同一张十亿行明细表，`SELECT city, sum(amt) FROM t GROUP BY city`：

| | 行存（MySQL） | 列存（ClickHouse） |
|---|---|---|
| 读多少数据 | 全部列（含不参与计算的字符串大字段） | **只读 `city` 和 `amt` 两列** |
| 怎么读 | 逐行取 → 逐行判断 → 逐行累加 | 按 granule **批量**取 → **批量**运算 |
| 可用核数 | 单查询通常单核（或少量并行） | 一个查询默认吃满所有核 |
| 典型耗时 | 几十秒到几分钟 | **亚秒到几秒** |

差距不是"优化得好一点"，而是**量级**。它有四个来源，缺一个都到不了：**列式存储省 IO、向量化省 CPU、有序数据让过滤变便宜、多核并行摊薄时间**。

这篇讲后三条怎么在一台机器上串起来。

## 二、向量化执行 {#vectorized}

### 2.1 向量化到底在做什么 {#what-is-vectorized}

区别只在一句话：**按行处理还是按批处理。**

```
逐行（火山模型，MySQL）                    向量化（按块处理，ClickHouse）
for row in rows:                          for block in blocks:        # 一个 block 约 8192 行
    if row.city == 'SH':                      mask = (col_city == 'SH')   # 一条 SIMD 指令比 8192 次
        sum += row.amt                        sum += sumIf(col_amt, mask) # 批量求和
```

逐行执行有三个隐藏成本：**每次循环都要做一次虚函数调用（解释开销）、分支预测失败率高、无法使用 CPU 的 SIMD 指令。** 向量化把"每行一次决策"变成"每 8192 行一次决策 + 一次 SIMD 运算"，同样的数据，CPU 周期少一个量级。

### 2.2 支撑它的三个前提 {#three-premises}

向量化不是"想向量化就能向量化"，它依赖前面那条存储设计：

| 前提 | 带来的能力 |
|---|---|
| **列式存储**（同列同类型连续存放） | 一个 SIMD 寄存器能同时装下多个同类型值 |
| **数据有序**（排序键） | 过滤可以靠 granule 裁剪，不是全表扫 |
| **批处理模型**（block / granule） | 单个工作单元足够大，摊薄调度与函数调用开销 |

还有一个容易被忽略的**第四个前提**：**代码要用真的会跑满多核的调度**。ClickHouse 一个查询默认用 `max_threads`（= 核数）并行处理不同 granule，这是它"单表聚合极快"的另一半原因——**同时这也是它不适合高并发的原因**：一个查询就吃掉整机资源，十个并发查询只能排队。

> **一个反直觉的结论**：ClickHouse 的"快"和"不适合高并发"是**同一个设计的两面**。想两者兼得，就不能只要它一台机器。

## 三、索引体系：主键索引之外还有什么 {#index-system}

主键索引只能裁剪"排序键前缀"上的过滤。现实里还有大量"不能进排序键"的过滤条件（排序键只能有一套），于是有了**跳数索引**。

### 3.1 跳数索引在做什么 {#skip-index}

跳数索引（data skipping index）为每个 granule 记录一份**摘要**，查询时先看摘要，判断"这个 granule 里不可能有满足条件的数据"，直接跳过。

```sql
ALTER TABLE events ADD INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 4;
--                                                                  ↑ 每 4 个 granule 记录一份摘要
```

`GRANULARITY 4` 是精度与体积的权衡：**数值越小摘要越细、跳过越准，但索引越大**。

### 3.2 四类跳数索引怎么选 {#skip-index-types}

| 类型 | 摘要记什么 | 适合 | 不适合 |
|---|---|---|---|
| `minmax` | 该组 granule 内该列的**最小/最大值** | **与排序顺序相关**的列（时间、自增 ID） | 随机分布的值（每组的 min/max 几乎覆盖全域，等于没有） |
| `set(N)` | 该组内**不同值的集合**（超过 N 个就退化为"全都有"） | **低基数**列（状态、城市、枚举） | 高基数列（集合塞不下就失效） |
| `bloom_filter` | 布隆过滤器（判定"**一定不在**"） | 高基数等值过滤（`user_id = ?`） | 范围查询（布隆只支持等值语义） |
| `ngrambf_v1` / `tokenbf_v1` | 文本分词或 n-gram 的布隆过滤器 | `LIKE '%keyword%'` 之类文本包含 | 非文本列 |

**选择判据**：先问"这个过滤条件能不能进排序键"，能就进排序键（收益最好）；不能，再按**列的选择性与值的分布形态**选类型——低基数用 `set`，高基数等值用 `bloom_filter`，与顺序相关用 `minmax`。

> **26.x 的两个变化值得记**：`use_skip_indexes_on_data_read` 自 26.2 起默认开启（索引在**读取阶段**也能生效，不再只用于构建执行计划）；同一版本起 ClickHouse 会**自动为时间列创建 minmax 索引**（`add_minmax_index_for_time_columns`），所以时间过滤常常"什么都没配就已经在用了"。

### 3.3 PREWHERE：比 WHERE 更早的过滤 {#prewhere}

`PREWHERE` 是 ClickHouse 特有的两阶段过滤：

```sql
SELECT city, sum(amt)
FROM events
PREWHERE user_id = 12345          -- ① 先只读 user_id 这一列，算出命中行的掩码
WHERE    city = 'SH'              -- ② 只对掩码命中的行再读 city / amt
```

价值在**它让"读宽列"变成条件性的**：如果 `user_id` 的过滤很强（命中率 0.1%），那么只有 0.1% 的行需要真正读出 `city`、`amt` 这些参与计算的列，IO 省 99.9%。

**最优的 PREWHERE 列有两个特征**：过滤性强（留下的行少）、列本身窄（读它便宜）。**系统会自动把 `WHERE` 中"更划算"的条件提升为 `PREWHERE`**（由 `optimize_move_to_prewhere` 控制），所以手写 `PREWHERE` 多数时候只是"明确告诉优化器"。

### 3.4 验证索引真的生效了 {#explain}

索引"建了"不等于"用了"。判断手段是 `EXPLAIN indexes = 1`：

```
ReadFromMergeTree (events)
  PrimaryKey
    Keys: city
    Granules: 1/512                          ← 主键裁剪后只剩 1 个 granule
  Skip
    Name: idx_user
    Description: bloom_filter GRANULARITY 4
    Granules: 1/1                            ← 跳数索引又裁掉了剩下的
```

看两处即可：**每个索引的 `Granules` 是不是真的变小了**、以及**最终读了多少 granule**。如果显示 `Granules: 512/512`，说明这个索引一次都没裁掉东西——它只增加成本，不带来收益。

> **查不到的索引 = 负资产**：跳数索引要在查询时读、要占磁盘与内存、还会拖慢写入与合并。写完索引**必须用 `EXPLAIN` 验证它真的被用上**，否则删掉。

## 四、把计算前移：物化视图与投影 {#mv-projection}

跳数索引解决"少读数据"，还有一种思路是"**干脆别算**"——把聚合结果提前算好。

### 4.1 物化视图的本质是插入触发器 {#mv}

ClickHouse 的物化视图**不是**你熟悉的那种"查的时候透明重写"的 MV，而是：

```
INSERT INTO 源表
      │
      ├──▶ 写源表（数据照旧留一份）
      │
      └──▶ 触发物化视图的 SELECT，把【这一批新数据】的结果写入【目标表】
```

三个必须知道的推论：

1. **它只处理"新插入的数据"**，对历史数据不生效（要补历史得手工 `INSERT INTO … SELECT`）。
2. **它不保证查询时自动被使用**——你有没有用上这张预聚合表，取决于你的 SQL 有没有写那张表。所以常见做法是让上层查询直接查聚合表，而不是指望引擎自动改写。
3. **`AggregatingMergeTree` + 物化视图是标配组合**：因为聚合不可逆（`count` 不能"再加回"明细），源表持续插入时，目标表必须存**中间态**（`AggregateFunction` 类型）而不是最终值，查询时用 `-Merge` 后缀函数合并。

### 4.2 投影（projection）{#projection}

投影是"**同一张表内部**的另一份物理组织"——可以按不同排序键重新排列数据、也可以存聚合结果，由优化器**自动匹配**是否使用：

```sql
ALTER TABLE events ADD PROJECTION p_by_user (
  SELECT city, amt ORDER BY user_id
);
```

与物化视图的关键差异：

| | 物化视图 | 投影 |
|---|---|---|
| 物理位置 | **另一张表**，要自己写 SQL 去查 | 同一张表的内部结构，查询**自动**匹配 |
| 一致性 | 靠触发器，源表与目标表可能不一致 | 与源表同源，作为 part 的一部分原子写入 |
| 灵活性 | 可以跨表、可以做复杂变换 | 只能基于本表 |
| 适合 | 复杂的预聚合链路、跨表打宽 | "换一种排序键"或"存一份聚合"，主要解决**读取效率** |

> **投影的现代形态**：自 25.6 起，基于 `_part_offset` 的投影更接近"二级索引"——它不复制数据、只维护一份"偏移映射"，因此体积和写入代价都远小于"完整复制一份列"。实测能出现"扫描行数从三千万降到一万六"这种量级的效果（官方给出的例子是约 1,876 倍）。**具体收益随查询形态变化很大，必须用自己的数据实测，不要照搬别人的倍数。**

### 4.3 怎么选 {#mv-vs-projection}

| 你的诉求 | 用 |
|---|---|
| 上层要一张"已聚合的结果表"，可能还要跨表 | 物化视图 + `AggregatingMergeTree` |
| 只是想让**某类查询**更快，不改变查询入口 | 投影（优化器自动用） |
| 想把宽表的一部分列单独整理 | 投影 |
| 需要"插入时做复杂变换再分发到多个目标" | 物化视图（一个源表可以挂多个） |

## 五、JOIN：最容易被误判的能力 {#join}

### 5.1 为什么 ClickHouse 的 JOIN 是"右表广播" {#join-algorithm}

ClickHouse 的 JOIN 模型与其他 MPP 数据库不同：**没有"数据重分布（shuffle）"作为默认路径**，默认做法是把**右表整体读进内存建哈希表**，然后流式扫描左表探测。

```
              ┌────────────────┐
   右表 ────▶ │  构建哈希表     │  ← 整表装进内存
              └───────┬────────┘
                      │ probe
   左表 ──────────────▶│──────────▶ 结果（左表流式，不落内存）
```

**推论（这是它 JOIN 能力的真正边界）**：

- **右表必须能被单机内存装下**（因为要在每个节点上都建一份）→ **大表 JOIN 大表容易 OOM**
- 左表可以很大（流式）→ **"小表 JOIN 大表"完全没问题**
- 它不天然并行化 JOIN 本身（除非开并行副本或改算法）→ 多表复杂关联的性能不如原生 MPP

### 5.2 五种 JOIN 算法与边界 {#join-algorithms}

`join_algorithm` 可显式指定，也可以让引擎自动选：

| 算法 | 做法 | 什么时候合适 |
|---|---|---|
| `hash`（默认） | 右表建哈希表，左表探测 | 右表能装进内存（绝大多数场景） |
| `grace_hash` | 哈希表**分桶落盘**，分片处理 | 右表装不下内存，但还想要哈希 JOIN 的效率 |
| `partial_merge` | 两侧都按 JOIN 键排序后**归并** | 两侧都很大且内存紧张；代价是要排序 |
| `full_sorting_merge` | 完整排序归并 | 同上，且要求全量排序语义 |
| `direct` | 直接以右表为索引查找（不建哈希） | 右表是字典 / 主键查找型 |

**选择顺序**：默认 `hash` → 右表偏大就 `grace_hash` → 依然吃力再考虑 `partial_merge`（接受排序代价）。

> **26.x 在 JOIN 上投入很大**：运行期过滤（runtime filters，用构建侧的实际键值去过滤探测侧）、基于统计信息的 JOIN 重排（`use_hash_table_stats_for_join_reordering`）在 26.2 起默认启用；26.8 引入 **IEJoin** 让区间/范围 JOIN（如"时间重叠"类关联）从"没法用"变成可用。官方的口径是 22.4 → 26.4 在 JOIN 密集的 TPC-H SF100 上快了 26 倍。**这说明 ClickHouse 的 JOIN 短板在被持续填补——写选型结论时要标注版本，否则半年后就过时了。**

### 5.3 大表 JOIN 大表怎么办 {#big-join}

按代价从低到高：

1. **改成宽表**：在写入侧（Flink 或物化视图）就把维度打宽，让查询不必 JOIN —— 数仓里最主流也最省事的解法。
2. **用字典（Dictionary）**：维度表是"键 → 值"的映射且变化不频繁时，字典是内存里的查找结构，比 JOIN 便宜得多。
3. **小表用 `IN` / 子查询代替 JOIN**：ClickHouse 对 `IN` 的优化比 JOIN 成熟。
4. **`grace_hash` / `partial_merge`**：接受更低的效率换取不 OOM。
5. **换引擎**：如果多表复杂关联是**核心负载**而不是偶发需求，这本身就是选型信号（详见 [OLAP 引擎选型](/bigdata/clickhouse/olap-selection#criteria)）。

## 六、其他加速手段与它们的代价 {#other-accel}

| 手段 | 做什么 | 代价 / 注意 |
|---|---|---|
| **惰性物化**（lazy materialization，25.4 起默认开启） | 大列推迟到"确实需要"时才读（如 `ORDER BY … LIMIT 10` 只需少量行的宽列） | 默认开启、基本不用管；但它会让 `EXPLAIN` 的读列信息看起来"少读了" |
| **查询条件缓存**（query condition cache，默认开启） | 为每个 granule 缓存"某条件是否命中"的一 bit，重复的仪表盘查询可跳过主键索引裁不掉的数据 | 只对**条件重复率高**的负载有效 |
| **参数化视图** | 把视图参数化，避免为每种过滤组合各写一个视图 | 需要客户端配合传参 |
| **多副本并行查询**（parallel replicas） | 同一条查询分发到多个副本并行执行 | 把"读放大"变成"加副本即提速"，但会占用其他副本的资源 |
| **结果缓存**（query cache） | 缓存完全相同的查询结果 | 只对**逐字相同**的查询生效，含时间函数的仪表盘查询基本用不上 |

> **一条纪律**：**任何"加速手段"都要先测出它带来的收益，再决定是否保留。** ClickHouse 的加速手段很多，但每一个都有维护成本（索引要重建、视图要维护、缓存会失效）；**没有 `EXPLAIN` 或对照查询证明有效的加速手段，一律视为负资产。**

## 七、使用场景与面试问答 {#interview}

**Q1：向量化执行快在哪？**

把"逐行判断 + 逐行累加"变成"每 8192 行一次 SIMD 运算 + 批量求和"，同时消掉了逐行的函数调用与分支预测开销。它依赖三个前提：列式存储（同类型连续）、数据有序（过滤便宜）、批处理模型（单批足够大）。

**Q2：ClickHouse 为什么不适合高并发？**

一个查询默认吃满整机核数（`max_threads` = 核数），十个并发就是十份资源竞争。**"单查询极快"与"不适合高并发"是同一设计的两面**——它优化的是"一条查询尽快跑完"，不是"吞吐最大化"。

**Q3：跳数索引该给哪一列建？**

先别急着建——能进排序键的列**永远优先进排序键**（收益最大）。剩下的按分布选：与顺序相关用 `minmax`，低基数用 `set`，高基数等值用 `bloom_filter`，文本包含用 `ngrambf_v1`。建完必须用 `EXPLAIN indexes = 1` 看 `Granules` 是否真的变小。

**Q4：`PREWHERE` 和 `WHERE` 的区别？**

`PREWHERE` 先读"过滤用的窄列"算出命中掩码，只对命中的行再读宽列。收益来自"读宽列变成条件性的"，过滤越强收益越大。系统会自动提升，手写多是为了明确意图。

**Q5：物化视图为什么不是"透明加速"？**

因为它是**插入触发器**：只处理新插入的数据、只写入它自己的目标表，查询时**不会自动改写**你的 SQL。想用上预聚合结果，就得让你的查询去查那张聚合表。

**Q6：物化视图和投影怎么选？**

要跨表、要做复杂变换、要分发到多处 → 物化视图（另一张表，自己写 SQL 查）。只想让特定查询自动被加速、不改变查询入口 → 投影（同表内部结构，优化器自动匹配）。

**Q7：为什么 ClickHouse 的大表 JOIN 大表容易 OOM？**

默认的 `hash` 算法把**右表整体读进内存**建哈希表，且要在每个节点各建一份。左表可以流式所以很大也没事，右表大就危险。解法按代价排序：写入侧打宽成宽表 → 用字典 → `grace_hash` → `partial_merge` → 换引擎。

**Q8：怎么判断一个索引该不该留？**

看两点：`EXPLAIN indexes = 1` 里它的 `Granules` 是否真的从全量降到部分；以及保留它带来的写入/合并/内存成本是否值得。**裁不掉任何 granule 的索引只有成本没有收益。**
