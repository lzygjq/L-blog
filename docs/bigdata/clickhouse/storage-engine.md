# 存储引擎：MergeTree 与不可变 part

## 一、问题场景：列存为什么不能"改一行" {#why}

假设有一张十亿行的明细表，要改其中一行的 `status` 字段。

行式存储（MySQL）的做法你很清楚：找到那一行所在的页，改掉字段，写回。代价与"这一行"成正比。

列式存储做不了这件事，原因不在实现，在**组织方式**：

```
行式（按行切）                      列式（按列切）
┌────────────────────────┐         ┌────────────────────────┐
│ id=1  city=SH  amt=100 │         │ id:   1  2  3  4  5 …  │ ← 一整列连续存放
│ id=2  city=BJ  amt=200 │         │ city: SH BJ SH SH BJ … │ ← 一整列连续存放
│ id=3  city=SH  amt=300 │         │ amt:  100 200 300 …    │ ← 一整列连续存放
└────────────────────────┘         └────────────────────────┘
改一行 = 改一个页（几十字节）        改一行 = 动 N 列（N 个位置，可能跨块）
```

列式的优势来自**同一列的数据紧挨在一起**：压缩率高（同类型同分布）、扫描省 IO（不读无关列）、向量化友好（同类型批量运算）。改一行的代价则是**要同时改 N 个列文件里的对应位置**，而其中任何一处失败都会让这一行"半新半旧"。

所以 ClickHouse 的选择是：**不原地改。** 数据写入后就是只读的，修改靠"写一份新的、再丢掉旧的"。

## 二、根设计：part 不可变 {#immutable-part}

**这一条设计是全篇的源头。** 后面所有"奇怪"的行为——更新慢、删除延迟、写入必须攒批、`FINAL` 有代价——都从它推出来。

### 2.1 一次写入的产物：part 与 granule {#part-granule}

一次 `INSERT` 会生成一个 **part**（数据分片），落盘后**永不修改**：

```
INSERT INTO events VALUES (...), (...), ...      ──▶  part: all_1_1_0
                                                       ├── id.bin / city.bin / amt.bin   （每列一个文件）
                                                       ├── primary.idx                   （稀疏主键索引）
                                                       ├── count.txt / checksums.txt
                                                       └── .mrk（列内的 granule 标记）

再来一次 INSERT                                    ──▶  part: all_2_2_0
后台合并（merge）自动触发                          ──▶  part: all_1_2_1（前两个合为一个，旧的两个删除）
```

part 内部按**行**切成固定大小的 **granule**，默认每 **8192 行**一个（由 `index_granularity` 控制）。granule 是 ClickHouse 里**一切 IO 的最基本单位**：

> **读数据永远不是"读某一行"，而是"读某几个 granule"** —— 即使你只查一行，读到的也是整 granule（8192 行的对应列）。

这个事实解释了两个常见困惑：为什么 ClickHouse 单点查比不过行存（要读整 granule），以及为什么它单表聚合能快得离谱（同为 8192 行，扫描是顺序的、向量化的）。

### 2.2 后台合并在做什么 {#merge}

合并（merge）是 ClickHouse 的**后台常驻动作**，也是它名字的由来（MergeTree）。它做的事很朴素：挑几个小的 part，读出来、按排序键归并、写成一个大的 part，然后删掉旧的。

```
        写入 1 万行 × 100 次 = 100 个小 part
                     │
                     │  后台按"体积相近"选择合并对象，逐层归并
                     ▼
        1 个 100 万行的大 part

        → 查询时要打开的文件数从 100 降到 1，索引也变连续
```

合并**不是**为了节省空间（虽然顺带压缩更好），**首先是为了查询效率**：part 越多，每次查询要做的"多路归并"越深、要打开的索引段越多。这直接推出后面那条最重要的运维结论——**写入过于频繁会让 part 数量失控，查询和合并一起雪崩**。

### 2.3 这一条设计推出的五条结论 {#five-conclusions}

| 现象 | 从"part 不可变"怎么推出来 |
|---|---|
| `ALTER TABLE … UPDATE` 很慢 | 不是改行，是**重写整个 part**（叫 mutation）。十亿行的表改一行，代价与表大小成正比 |
| 删除的行不立刻消失 | 删除只能先"打标记"（lightweight delete 写掩码），真正的清理要等合并发生 |
| `ReplacingMergeTree` 去重是"最终"一致 | 去重发生在**合并时**，而合并时机不由你决定 → 同一主键在查询时刻可能仍有重复行 |
| `INSERT` 必须攒批 | 每批 = 一个 part。逐行插入 = 每秒几十个 part，合并追不上，`Too many parts` 报错 |
| 没有真正的事务性多行更新 | 不可变 + 异步合并的模型里，跨 part 的原子修改无处安放 |

> **与 Elasticsearch 的同构**：ES 的**段（segment）不可变**，CH 的 **part 不可变**，两条设计几乎一模一样，于是推出的结论也一一对应：删除是标记、更新是"新增 + 标记旧"，去重/清理靠后台合并，写入必须攒批（ES 的 `refresh_interval` 与 CH 的 `async_insert` 是同一个问题的两种解法）。对照见 [搜索与检索 · 写入与读取](/search/write-and-read)。

## 三、稀疏主键索引：为什么能在一秒内扫完十亿行 {#sparse-index}

### 3.1 索引的一条规则：每 8192 行一个标记 {#granularity}

ClickHouse 的主键索引**不是**每行一条记录，而是**每 8192 行记一条**：

```
primary.idx（常驻内存，极小）
   ├── granule 0：排序键 (2026-01-01, 1001)
   ├── granule 1：排序键 (2026-01-01, 9500)
   ├── granule 2：排序键 (2026-01-02, 2100)
   └── …
```

查询时二分找到候选 granule 区间，**只读这几段**。所以"稀疏索引"并不等于"精度低"——因为数据是按排序键物理有序的，落在两个标记之间的数据**必然**也落在对应的键值范围内。

代价与收益要一起看：

| | 稀疏索引（CH） | 稠密索引（B+ 树，MySQL） |
|---|---|---|
| 索引体积 | 行数的 1/8192，可常驻内存 | 行数的 ~1/16 起，通常远超内存 |
| 定位精度 | 到 granule（8192 行） | 到行 |
| 点查代价 | 读整 granule | 读一个页 |
| 顺序扫描代价 | **极低**（顺序 IO + 向量化） | 偏高（要顺着叶子链表跳页，且要读整行） |

**它是一台为"少读列、多读行"优化过的机器。** 反过来，要求"精确定位某一行"的场景（大量点查），它天生吃亏。

### 3.2 排序键与主键不是一回事 {#order-by-vs-primary-key}

这是 ClickHouse 最容易被误解的一处：

```sql
CREATE TABLE events (
  ts      DateTime,
  city    LowCardinality(String),
  user_id UInt64,
  amt     Decimal(18, 2)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (city, ts)          -- 排序键：决定物理顺序，也决定索引
PRIMARY KEY city             -- 主键：只决定索引，可以只是排序键的前缀
```

| | 作用 | 约束 |
|---|---|---|
| `ORDER BY`（排序键） | 决定**数据在 part 内的物理顺序**，也是稀疏索引的依据 | 必须是主键的**超集或相等** |
| `PRIMARY KEY` | 只决定**索引粒度**（索引里记哪些列） | 必须是排序键的**前缀** |

**没写 `PRIMARY KEY` 时它默认等于 `ORDER BY`。** 分开写只有一个用途：当排序键列很多、希望索引更小时，把主键收窄成"真正用于过滤的那几列"，但**物理顺序仍按完整排序键**——这样既保住了排序带来的压缩与裁剪，索引又更小。

**排序键的选择标准只有一条**：把**最常用于过滤、且基数递增**的列放前面（典型是"维度 + 时间"）。它同时决定了三件事：分区内的数据裁剪能力、压缩率（相邻行越相似压缩越好）、以及 `ReplacingMergeTree` 去重时的比较成本。

### 3.3 为什么 ClickHouse 不建 B+ 树 {#why-no-btree}

因为**建了也用不上**。B+ 树的收益是"精确定位到行"，而列存读数据的最小单位是 granule；把它细化到一行的代价是索引体积暴涨、内存放不下、扫描时要跳页——正好抵消列存的全部优势。

> 需要"精确到行的高并发点查"时，正确做法**不是**给 ClickHouse 加索引，而是承认它不适合这个负载（详见 [OLAP 引擎选型](/bigdata/clickhouse/olap-selection#criteria)）。

## 四、表引擎家族：把"去重/聚合"下沉到合并阶段 {#engine-family}

既然合并是必然发生的后台动作，那就可以**把一部分计算塞进合并里**。这就是 MergeTree 家族的全部思想：**用"合并时的额外动作"换取"查询时的免计算"。**

### 4.1 ReplacingMergeTree：去重，但是"最终"的 {#replacing}

```sql
ENGINE = ReplacingMergeTree(updated_at)      -- 参数是"版本列"
ORDER BY user_id
```

排序键相同的行（`ORDER BY` 相同）在**合并时**只保留版本列最大的一条。

**必须记住的三件事**：

1. **去重是最终的，不是实时的。** 两次插入之间、合并发生之前，同一主键**在查询结果里会出现多行**。这不是 bug，是设计。
2. **想立刻拿到去重结果，只有两条路**：`SELECT … FINAL`（查询时合并，代价是性能陡增）或 `GROUP BY` + `argMax`（手写去重）。生产里**更常见的是第三条路**——在自己的查询层接受"近似去重"，或改用 `AggregatingMergeTree` 存聚合态。
3. **它不保证"最新写入的胜出"，只保证"版本列最大的胜出"。** 版本列没给或给了空值，胜负取决于合并顺序（不确定）。所以版本列必须是**单调且唯一可比**的（时间戳 + 序列号，或 `_part` 序号）。

### 4.2 Summing / Aggregating / Collapsing / Coalescing {#others}

| 引擎 | 合并时做什么 | 典型用途 |
|---|---|---|
| `SummingMergeTree` | 排序键相同的行，**数值列相加** | 已经是"可加指标"的预聚合表 |
| `AggregatingMergeTree` | 合并 `AggregateFunction` 类型的**中间态** | 需要去重计数（`uniq`）、分位数等不可加指标 |
| `CollapsingMergeTree` | 用 `Sign` 列（+1 / -1）**抵消**成对的行 | 需要"撤销"语义的变更流（已被 `ReplacingMergeTree` 的 `is_deleted` 大量替代） |
| `CoalescingMergeTree` | 每个列**保留最新的非 NULL 值** | 把"部分字段更新"变成纯追加（26.x 起可用，社区贡献） |

> `CoalescingMergeTree` 是这几年的一个实用补丁：上游 CDC 常常只送变更字段，其它字段为空，用它可以**不写全量行**也能得到正确宽表。

### 4.3 家族选择的判据 {#family-choice}

一句话判据：**先问"同一主键会不会再来"，再问"再来时是要覆盖、要累加，还是要保留中间的聚合态"。**

| 同一主键再来时… | 选 |
|---|---|
| 不会再来（纯日志） | `MergeTree` |
| 要覆盖成最新 | `ReplacingMergeTree`（接受最终一致）或 `CoalescingMergeTree`（只补 NULL 字段） |
| 要把数值累加 | `SummingMergeTree` |
| 要保留"可以继续合并的中间态" | `AggregatingMergeTree` |

## 五、分区与 TTL {#partition-ttl}

### 5.1 分区键怎么选 {#partition-key}

分区是 **part 之上的组织单位**：不同分区的 part **永远不会被合并到一起**。这让分区成为最有效的两个手段：

- **裁剪**：`WHERE ts >= '2026-09-01'` 会直接跳过其它分区的全部 part
- **生命周期**：`ALTER TABLE … DROP PARTITION` 是**元数据操作**（删目录），与数据量无关；而 `DELETE WHERE` 是 mutation（重写）

**分区键的取舍**：

| 分区粒度 | 好处 | 代价 |
|---|---|---|
| 太粗（如按年） | 分区数少 | 裁剪粒度粗、淘汰粒度粗 |
| 太细（如按小时甚至更细） | 裁剪精确 | **每个分区内都要维持足够的 part 才能高效合并**，分区爆炸 → 小 part 满天飞、`Too many parts` |

**经验值**：单分区数据量控制在**几百万行以上**，总量级在**几千个分区以内**。按天或按月分区是最常见的稳妥选择。

> 分区键**不要用高基数列**（如 `user_id`）。分区数量会随数据增长爆炸，而且每个分区只有很少行，合并永远追不上写入。

### 5.2 TTL：按时间降级与删除 {#ttl}

TTL 是"分区裁剪"的自然延伸——既然数据有时间维度，就可以让它自己过期：

```sql
ALTER TABLE events
  MODIFY TTL ts + INTERVAL 90 DAY                    -- 90 天后删除
                TO VOLUME 'cold', ts + INTERVAL 7 DAY,   -- 7 天后下沉到冷卷
                TO DISK   's3',   ts + INTERVAL 30 DAY;  -- 30 天后挪到对象存储
```

三件事要清楚：

1. **TTL 是"后台按 part 粒度执行"的，不是精确到秒的定时器。** 一个 part 只有当**其中所有行都过期**时才会被整体删除或移动。
2. **`TO DISK / TO VOLUME` 让冷热分层不需要外部工具**——这是 ClickHouse 相比"自己写归档脚本"的显著优势。湖上的长期归档仍然交给 Iceberg 那套（见 [Lakehouse 与冷热分层](/bigdata/lakehouse/#three-tiers)）。
3. **TTL 移动会与合并互相影响**：大量 part 同时到期时，后台会有一波搬运。用 storage policy 的卷优先级来控制，不要指望"到期瞬间清空"。

## 六、代价与反模式 {#costs}

| 反模式 | 为什么会出事 | 正确做法 |
|---|---|---|
| 逐行 / 小批 `INSERT` | part 数量爆炸，合并追不上，报 `Too many parts` | 攒批（一次至少几万行）或开 `async_insert` 让服务端攒 |
| 用 `ALTER … UPDATE` 做高频更新 | 每次 mutation 重写整个 part，且**排队串行执行** | 用版本列 + `ReplacingMergeTree`，或改到支持行级更新的引擎 |
| 用 `DELETE WHERE` 清历史数据 | 谓词式删除是 mutation，代价与数据量成正比 | `DROP PARTITION`（元数据操作） |
| 为了"查得快"给每列建跳数索引 | 索引本身也要读、也占内存；低选择性的索引让查询更慢 | 只给"过滤性强、且经常用"的列建，并用 `EXPLAIN indexes = 1` 验证真的被用上 |
| 高并发点查（每秒数千次按主键取单行） | 每次都要读整 granule，且连接与查询调度开销放大 | 加缓存层，或换适合点查的引擎 |
| 排序键把高基数列排前面 | 相邻行不相似 → 压缩率崩、索引失效 | 低基数维度在前、时间在后 |

> **一条通用判据**：**ClickHouse 的性能来自"顺序读 + 向量化 + 稀疏索引"三件事的合力，任何让读取退回"随机、逐行、跳页"的用法，都会同时失去这三样。**

## 七、使用场景与面试问答 {#interview}

**Q1：ClickHouse 为什么更新慢？**

因为它不原地改。列存要改一行就得同时改 N 个列文件，于是 ClickHouse 选择"写入即不可变"，修改靠**重写整个 part**（mutation）。所以更新代价与表/part 大小成正比，与"改了几行"无关。

**Q2：`ReplacingMergeTree` 去重后为什么还能查到重复行？**

去重发生在**合并时**，而合并是后台异步的、时机不由查询决定。插入后合并前，同一主键就是有多行。要立刻去重只能 `FINAL`（贵）或 `GROUP BY + argMax`（手写）。

**Q3：排序键（`ORDER BY`）和主键（`PRIMARY KEY`）的区别？**

排序键决定**物理顺序**（进而决定压缩率、裁剪能力），主键只决定**索引里记哪些列**、必须是排序键的前缀。不写主键时它默认等于排序键。分开写是为了"物理顺序不变、索引更小"。

**Q4：为什么索引每 8192 行才记一条，却还能定位得准？**

因为数据物理上有序：落在两个索引标记之间的行，**必然**落在对应的键值区间内。二分找到区间后只读那几个 granule，精度损失换来的是"索引小到能常驻内存"。

**Q5：`ORDER BY` 该怎么设计？**

把"最常用于过滤且基数递增"的列放前面，典型是"维度 + 时间"。它一举决定三件事：数据裁剪能力、压缩率、去重时的比较成本。

**Q6：为什么分区分得太细反而更慢？**

不同分区的 part 永不合并，每个分区都得**独立**攒够 part 再合并。分区过多 → 每个分区里的 part 都很小 → 合并效率低、`Too many parts` 频发、元数据膨胀。

**Q7：`ALTER TABLE … DELETE` 和 `DROP PARTITION` 差在哪？**

前者是 mutation：要扫描并重写整个 part，谓词无法让任何 part 免于重写，代价与数据量成正比、且串行排队。后者是元数据操作：直接删掉分区目录，与数据量无关。**按时间清理一律分区化。**

**Q8：`CoalescingMergeTree` 解决什么问题？**

上游 CDC 常常只送变更字段、其余字段为 NULL。它让同一排序键的行在合并时**每列取最新非 NULL 值**，于是"部分更新"可以退化成纯追加，不必为了补全字段先读一次旧行。
