# 数仓分层建模

## 一、问题场景：为什么"直接连业务库查"迟早会失控 {#why-layered}

项目早期，报表直接查业务库是最合理的选择——省事、数据最新、不用同步。它真正失效的时点不是数据量变大，而是**查询的人变多**：

| 失控的表现 | 具体场景 |
|---|---|
| **口径不一致** | 财务的"成交额"含退款、运营的不含；两个看板对不上，谁也说不清哪个对 |
| **重复计算** | 三个报表各自实现一遍"活跃用户"，算法细节各不相同 |
| **业务库被拖垮** | 谁的报表跑得慢，谁就影响线上交易——而且没人知道是谁 |
| **改一处崩三处** | 业务表加了一列，下游所有报表任务全部要改 |
| **变更无追溯** | 昨天报表是 1200，今天是 1150，无法回答"数据变了还是口径变了" |

分层的本质不是"多建几张表"，而是**把责任切开**：

- **同一件事只算一次**（消除重复计算与口径分叉）；
- **不同层承担不同的稳定性承诺**（越往上层越面向业务、越容易变；越往下层越贴近原始、越稳定）；
- **让排查有路径**（数字不对，可以按层逐段定位，而不是在一条 SQL 里猜）。

> **一句话认知**：分层解决的不是性能问题，是**协作与口径问题**。它的收益随着"用数据的人数"增长，而不是随着数据量增长。

## 二、分层：每层各解决什么问题 {#layers}

```
 业务系统              ┌──────────────────────────────────────────────────────┐
  MySQL / PG ──CDC──▶  │  ODS  贴源层                                          │
  （binlog）           │  与源库同构、不做业务加工、保留原始与变更历史           │
                       └───────────────────────┬──────────────────────────────┘
                                               │  清洗 / 去重 / 标准化 / 维度补全
                       ┌───────────────────────▼──────────────────────────────┐
                       │  DWD  明细层                                          │
                       │  一行 = 一个业务事件；字段统一口径；派生维度算好         │
                       └───────────────────────┬──────────────────────────────┘
                                               │  按主题聚合、轻粒度汇总
                       ┌───────────────────────▼──────────────────────────────┐
                       │  DWS  汇总层                                          │
                       │  按「主题 + 粒度」预聚合（如 用户-日、商品-日）          │
                       └───────────────────────┬──────────────────────────────┘
                                               │  面向具体场景再加工
                       ┌───────────────────────▼──────────────────────────────┐
                       │  ADS  应用层                                          │
                       │  一张表服务一个报表/看板；结构跟着需求走                 │
                       └───────────────────────┬──────────────────────────────┘
                                               ▼
                                            BI / 看板 / 接口

  DIM  维度层（贯穿各层）：一致性与复用，解决「维度口径不统一」
```

| 层 | 一行代表什么 | 做什么 | **不做什么** |
|---|---|---|---|
| **ODS**（贴源） | 源库的一条记录 | 保持与源一致，保留原始值与变更 | 不做业务清洗、不做聚合、不写业务口径 |
| **DWD**（明细） | 一个业务事件 | 清洗、去重、标准化、类型与编码统一、派生维度 | 不做跨事件的聚合 |
| **DWS**（汇总） | 主题 + 粒度的一组统计 | 预聚合常用指标，减少重复计算 | 不面向单个报表定制 |
| **ADS**（应用） | 一个报表需要的形态 | 为具体场景裁剪、拼装、排序 | 不做通用逻辑（通用逻辑应该下沉） |
| **DIM**（维度） | 一个维度的当前/历史状态 | 提供一致的维度视图，供各层复用 | 不含事实度量 |

### 2.1 为什么一层都不能少 {#why-each-layer}

这是面试与设计评审里最常被追问的问题，答案要落到"删掉它谁会疼"：

- **去掉 ODS**：出了口径争议，无法回到源头核对；源库结构一变，整条链路跟着改，没有缓冲层。
- **去掉 DWD**：每张报表各自从 ODS 清洗一遍，同一份清洗逻辑出现 N 份，缺陷要在 N 个地方修。
- **去掉 DWS**：所有聚合都在查询时算，报表变慢；而且"活跃用户"这类指标的算法会在不同报表里分叉。
- **去掉 ADS**：BI 直接连 DWS，字段语义与权限边界都由 BI 承担——一旦 BI 工具更换或升级，所有依赖跟着重建。

**另一条常被忽略的边界**：ODS 是否需要"保留历史全量"。若源库会物理删除，ODS 就应该以**追加 + 变更日志**的形式保留，而不是简单镜像——否则一旦上游删除，历史就永久消失。这正是[CDC 同步](/bigdata/canal/#why-cdc)必须做对的原因。

## 三、维度建模：事实表与维度表 {#dimensional}

### 3.1 事实表的三种形态 {#fact-tables}

| 类型 | 一行代表 | 粒度 | 更新方式 | 例子 |
|---|---|---|---|---|
| **事务事实表** | 一次业务事件 | 事件发生即一行 | 只追加 | 下单、支付、点击 |
| **周期快照事实表** | 一个周期末的状态 | 每天/每月一行（即使当天无事件） | 周期性追加 | 每日库存余额、每日账户余额 |
| **累积快照事实表** | 一个流程的全生命周期 | 一个业务对象一行，随流程推进被更新 | **会被更新** | 订单从下单到签收的各环节时间戳 |

**累积快照是三者里最容易被漏掉的**：它的价值在于"漏斗分析"——每个环节耗时、卡在哪一步，都在这张表里。用事务事实表算漏斗要靠多次 JOIN，既慢又容易错。

### 3.2 星型 vs 雪花 {#star-snowflake}

| | **星型** | **雪花** |
|---|---|---|
| 结构 | 事实表直接连维度表，维度不再拆 | 维度表再规范化，拆成多级 |
| 查询 | JOIN 更少，更快 | JOIN 更多 |
| 冗余 | 有意冗余，换取性能与易用 | 减少冗余，节省存储 |
| 维护 | 维度更新更简单 | 层级变化影响面大 |

**优先星型**。理由是现在"存储便宜、计算相对贵"，而雪花省下来的那点存储远不足以抵消 JOIN 与复杂度成本。规范的例外是**维度层级确实很大且复用度极高**（如商品类目树）时才拆。

### 3.3 缓慢变化维（SCD）与拉链表 {#scd}

维度属性会随时间变化——用户改了手机号、商品改了类目、员工换了部门。**"报表按当时的属性归属"还是"按现在的属性归属"，结论完全不同**，这就是缓慢变化维要解决的问题：

| 类型 | 做法 | 能否回答"当时是什么" |
|---|---|---|
| **Type 1** | 直接覆盖旧值 | ❌ 历史被抹掉 |
| **Type 2** | **新增一行**，用生效/失效时间划分区间 | ✅ **这是拉链表的本质** |
| **Type 3** | 增加一列记录"上一个值" | 只能看一步 |

**拉链表的两个必须保持的执行契约**（落地时最容易出错的地方）：

1. **同一主键在同一时刻只能有一条 `[start_date, end_date)` 覆盖该时刻的记录**——区间不能有空洞、也不能重叠；
2. **每日合并要幂等**：重跑同一天，结果必须与跑一次相同（做法是把新数据里"已有变更的记录"先失效再插入，而不是无脑追加）。

### 3.4 一致性维度与一致性事实 {#consistency}

这两个概念是"数仓能不能横向对齐"的基石，也是分层之外第二个真正决定数据可信度的设计：

- **一致性维度**：同一个维度（如"日期"、"门店"）在所有事实表中**用同一份维度表、同一套编码**。否则"按门店汇总"在两张表里得到不同结果。
- **一致性事实**：同一个指标（如"销售额"）在所有事实表中**定义、口径、单位一致**。否则做不了跨主题的合并分析。

> 这两条是"维度建模"相对"一事一表"的核心优势：**它让不同主题的数据可以被放在一起看**。缺少一致性设计的分层，只是"分了层的孤岛"。

## 四、指标体系：把口径变成可管理的资产 {#metrics}

### 4.1 三级指标 {#metric-levels}

| 层级 | 定义 | 例 |
|---|---|---|
| **原子指标** | 不可再分的基础度量 + 聚合方式，与维度无关 | `支付金额 SUM`、`订单数 COUNT` |
| **派生指标** | **原子指标 + 业务限定 + 时间周期 + 修饰词** | "近 7 天 · 华东 · 新客 · 支付金额" |
| **复合指标** | 由多个指标运算得到 | 客单价 = 支付金额 / 支付订单数；转化率 = 支付用户数 / 访问用户数 |

**这个层级划分的实际价值在命名与治理上**：原子指标少而稳定（几十个），派生指标多而组合（成千上万个）。把两者分开，才能做到"原子指标改了，所有派生指标自动跟着对"——否则就会出现几个报表里"支付金额"的算法各不相同。

**四个限定要素缺一不可**，缺了哪个都会让指标变成"看起来一样、其实不一样"：

```
派生指标 = 原子指标  +  时间周期（近 7 天）
                    +  业务限定（支付成功、非退款）
                    +  修饰词（新客、华东）
                    +  （隐含）统计粒度（按用户 / 按门店）
```

### 4.2 命名与分层规范 {#naming}

| 层 | 命名模式 | 例 |
|---|---|---|
| ODS | `ods_<源库>_<表名>` | `ods_order_order` |
| DWD | `dwd_<主题>_<粒度>_<描述>` | `dwd_trade_order_detail` |
| DWS | `dws_<主题>_<粒度>_<周期>` | `dws_trade_user_1d` |
| ADS | `ads_<场景>_<报表>` | `ads_sales_daily_report` |
| DIM | `dim_<维度>` | `dim_date`、`dim_store` |

**分区字段与统计周期要显式写进表名或注释**。命名规范的价值不在于好看，而在于**让人在不看 SQL 的情况下就知道这张表的粒度**——粒度不清楚是口径争议的第一来源。

## 五、实时与离线：两条链路怎么分工 {#realtime-batch}

| | **离线（T+1 批量）** | **实时（流式）** |
|---|---|---|
| 链路 | 批量抽取 / 导出 → 数仓分层加工 → 报表 | binlog → CDC → MQ → 流计算 → 分析库 |
| 延迟 | 小时 ~ 天 | 秒 ~ 分钟 |
| 成本 | 低 | 明显更高 |
| 适用 | 财务报表、结算、长期趋势、合规 | 大屏、监控告警、实时推荐、风控 |
| 数据完整性 | 可重跑、可回溯 | 需额外处理乱序、重复、迟到数据 |

**三条路线的取舍**：

| 架构 | 做法 | 问题 |
|---|---|---|
| **Lambda** | 离线与实时各一套逻辑 | 同一指标两套实现 → **长期必然口径分叉** |
| **Kappa** | 只有流，历史靠重放 | 重放成本高，复杂批处理不擅长 |
| **流批一体** | 同一套 SQL/逻辑跑两种模式 | 是方向，但对引擎与团队能力要求高 |

**现实中的常见折中**：**实时只做"能接受近似"的部分**（大屏、监控、告警），**精确口径仍由离线产出**，并明确标注两者差异。原因很直接——实时链路要处理乱序、重复、迟到数据，做成"精确"的代价远高于"近似 + 明确标注"。

**必须配的一件事：一致性对账。** 每天用离线结果校验实时结果（行数 + 关键指标 + 抽样明细），差异超阈值告警。没有对账的实时链路，出问题时无法判断是"业务真的变了"还是"链路丢了数据"。

## 六、对比辨析 {#compare}

| 对比 | 差别 | 何时选后者 |
|---|---|---|
| **ODS / DWD** | 与源同构 vs 已清洗统一 | 需要回到原始值核对 → ODS |
| **DWD / DWS** | 事件粒度 vs 主题聚合粒度 | 需要灵活下钻、维度组合不定 → DWD |
| **DWS / ADS** | 通用预聚合 vs 场景定制 | 只有一张报表、且需求稳定 → ADS |
| **星型 / 雪花** | 少 JOIN、有意冗余 vs 规范化、多 JOIN | 维度层级极大且复用度极高 → 雪花 |
| **SCD Type 1 / Type 2** | 覆盖（看现值）vs 拉链（看历史值） | 需要回答"当时归属"→ Type 2 |
| **实时 / 离线** | 秒级、成本高、需处理乱序 vs 可重跑、成本低 | 大屏监控 → 实时；结算合规 → 离线 |
| **宽表 / 维度建模** | 一次拼好、查询快、但加工重 vs 灵活、复用高 | 面向固定场景的 ADS 适合宽表；DWD/DWS 必须规范化 |

## 七、使用场景与面试问答 {#interview}

**Q1：为什么要分层？不分层会怎样？**
分层的收益是**协作与口径**，不是性能。不分层会同时出现五种失控：口径不一致（同一指标多个算法）、重复计算、业务库被报表拖垮、上游变更导致下游全改、数字变了无法追溯。分层的本质是把责任切开——**同一件事只算一次，各层承担不同的稳定性承诺**。

**Q2：能不能省掉 DWD，直接从 ODS 出报表？**
短期可以，长期会疼：每张报表各自从 ODS 清洗一遍，同一份清洗逻辑出现 N 份，缺陷要在 N 个地方修；而且没有统一的事件粒度，跨主题的合并分析做不了。**DWD 的价值是"把清洗与口径统一到一处"**。

**Q3：事实表有哪几种？累积快照有什么用？**
事务事实表（一个事件一行、只追加）、周期快照事实表（一个周期末一行、即使无事件也记）、累积快照事实表（一个业务对象一行、随流程被更新）。**累积快照专门为漏斗与流程分析设计**——订单从下单到签收各环节的时间戳都在同一行，算各环节耗时不用多次 JOIN。

**Q4：SCD Type 2 和拉链表是什么关系？落地要注意什么？**
Type 2 就是"新增一行、用生效/失效时间划区间"，它的**物理实现就是拉链表**。两个必须守住：① 同一主键在同一时刻**只能被一条区间覆盖**，不能有空洞或重叠；② 每日合并要**幂等**——重跑同一天结果不变（做法是先失效再插入，而不是无脑追加）。

**Q5：原子指标和派生指标怎么区分？为什么要分开？**
原子指标是"不可再分的基础度量 + 聚合方式"（如 `支付金额 SUM`），派生指标是"原子指标 + 时间周期 + 业务限定 + 修饰词"（如"近 7 天·华东·新客·支付金额"）。分开治理的价值是：**原子指标少而稳定，派生指标多而组合**——原子指标口径变了，所有派生指标能自动跟着对，避免"同一个词在几个报表里算法不同"。

**Q6：实时数仓能替代离线数仓吗？**
不能替代，只能分工。实时链路要处理乱序、重复、迟到数据，做成"精确口径"的代价远高于"近似"。实务做法是：**实时只承接能接受近似的场景**（大屏、监控、告警），**精确口径（结算、财务、合规）仍由离线产出**，并且必须配**每日对账**——否则出问题时无法区分"业务真的变了"还是"链路丢了数据"。

**Q7：Lambda 架构最大的问题是什么？**
**同一指标有两套实现**（离线一套、实时一套），而两套逻辑会随时间各自演进，**口径分叉是必然结果**。Kappa 用"只有流"消除了这个分叉，代价是历史重放成本高、复杂批处理不擅长；流批一体是方向，但对引擎与团队能力要求更高。所以小团队的现实选择往往是"实时做近似、离线做精确 + 对账"，而不是一步到位。

> 三篇串起来看：数据怎么进湖/仓（[Canal 数据同步](/bigdata/canal/)）→ 进来后怎么存与怎么算（[Doris 数仓](/bigdata/doris/)）→ 长期数据放哪儿（[Lakehouse](/bigdata/lakehouse/)）→ 数据怎么组织才可信（本篇）。
