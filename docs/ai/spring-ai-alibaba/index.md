# Spring AI Alibaba

[Spring AI](/ai/spring-ai/) 解决的是"**原子能力**"：怎么调模型、怎么检索、怎么让模型调我的方法。但它**不管编排**——"先分类，再按分类走不同处理分支，其中一个分支需要人工确认后继续"这种流程，用 Spring AI 得自己写一堆 `if-else`。

Spring AI Alibaba 就是补这一层的。一句话概括两者的关系：

```text
Spring AI          = 砖头 + 水泥    （原子抽象：模型、向量库、工具、记忆）
Spring AI Alibaba  = 精装修方案     （编排 + 国产模型 + 企业配套）
```

**它完全兼容 Spring AI 的核心 API**，在其上增加三样东西：**Graph 工作流引擎**、**百炼/通义的原生适配**、**一整套企业级配套**（MCP 注册中心、可观测、控制台）。

## 一、版本体系与时间线 {#versions}

它的版本号是**四位**，前三位对应 Spring AI 的主版本——这个设计很实用，一眼能看出该配哪个 Spring AI：

| Spring AI Alibaba | 发布时间 | 对应 Spring AI | 对应 Spring Boot | 关键特性 |
|---|---|---|---|---|
| `1.0.0.0` | 2025-05 | 1.0.0 GA | 3.2.x / 3.4.x | GA 正式版，基础模型接入 |
| `1.0.0.4` | 2025-09 | 1.0.1 | 3.x | 重建 Agent Graph Engine、A2A 通信、Nacos 集成 |
| `1.1.0.0` | 2025-12 | 1.1.0 | 3.5.x | 生产级 **Agent Graph Runtime** |
| `1.1.2.0` | 2026-02-02 | 1.1.2 | 3.5.x | **Agent Skills**、多智能体并行执行、Graph 并行条件边 |
| `1.1.2.2` | 2026-03-10 | 1.1.2 | 3.5.x | AgentScope 集成、Voice Agent |
| `2.0.0-M1.1` | 2026 | 2.0.0-M1 | **4.0.0** | 跟进 Boot 4 基线 |

**注意它比 Spring AI 慢半拍**——Spring AI 2.0 在 2026-06 已经 GA，而 Spring AI Alibaba 当时还在 `1.1.2.x` 与 `2.0.0-M1.x` 之间。**这意味着"Boot 4 + Spring AI 2.0 + Spring AI Alibaba"这个组合在 2026 年并不是随时可用的**，选型前必须先核对三者的兼容矩阵，别想当然。

## 二、Graph：多智能体编排的核心 {#graph}

Graph 是 Spring AI Alibaba 区别于 Spring AI 的最大亮点，思路来自 LangGraph：**把 Agent 应用建模成一张有向图**。

```text
        ┌──────────┐
        │  START   │
        └────┬─────┘
             ▼
      ┌──────────────┐
      │  classify    │  节点 = 一个 Agent / 一次模型调用 / 一段业务逻辑
      │ （意图分类）   │
      └──────┬───────┘
             ▼
      ┌──────────────────────────────┐
      │  条件边（conditional edge）    │  ← 按分类结果决定走哪条路
      └──┬───────────┬───────────┬───┘
         ▼           ▼           ▼
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │ 投诉处理 │ │ 咨询回答 │ │ 人工介入 │   ← 多条分支可并行执行
   └────┬────┘ └────┬────┘ └────┬────┘
        │           │           │
        └───────────┴───────────┘
                    ▼
              ┌──────────┐
              │  END     │
              └──────────┘
```

### 四类元素

| 元素 | 说明 |
|---|---|
| **节点（Node）** | 一个处理单元：调模型、执行工具、跑业务逻辑 |
| **边（Edge）** | 固定流转：A 之后必到 B |
| **条件边** | 按运行时结果动态选路（`addConditionalEdges`） |
| **状态（State）** | 在节点之间流转的共享数据，是图的"内存" |

### 为什么"固定流程用图、不固定才用自主 Agent"

这是理解 Graph 价值的关键。回顾 [Agent 与 Harness](/ai/agent-harness/#multi-agent) 里那条判据——**流程能固定的部分应该用编排**。Graph 就是这个编排层：

| | 纯自主 Agent | Graph 编排 |
|---|---|---|
| 流程 | 模型自己决定下一步 | **开发者画出流程**，模型只在节点内决策 |
| 可复现性 | 差（同一输入可能走不同路径） | **好**（路径由边决定） |
| 可测试性 | 难 | **每个节点可单独测试** |
| 适合 | 探索性任务 | **业务流程有确定性的场景** |

**大部分企业场景属于后者。** 客户投诉处理要走什么流程，是业务规定的，不是模型该决定的——模型只在"这一步该怎么回答/该怎么分类"上发挥作用。

### 生产级能力

`1.1.0.0` 起 Graph 变成"生产级 Runtime"，配套能力包括：

| 能力 | 解决什么 |
|---|---|
| **检查点（Checkpoint）** | 图跑到一半挂了能恢复，不用从头重跑 |
| **状态持久化** | 长流程的状态存在外部，支持跨实例 |
| **并行条件边** | 多分支同时跑，再汇总（`1.1.2.0` 起） |
| **人机协同（Human-in-the-Loop）** | 流程中插入"等人确认"节点——**AI 决策失控时的兜底机制** |
| **流式输出** | 图执行过程可以边跑边推给前端 |
| **Agent Skills** | 把可复用的能力固化成技能单元（`1.1.2.0` 起） |

> **Human-in-the-Loop 是最该被重视的一条。** 企业落地 AI 最大的阻力往往不是技术，而是"**出了事谁负责**"。在关键节点强制人工确认，是让业务方愿意用起来的前提——技术上它是一个节点，组织上它是一道免责边界。

## 三、什么时候用 Spring AI，什么时候上 Alibaba {#when-to-use}

| 你的情况 | 选择 |
|---|---|
| 只是给现有服务加"问答/摘要/抽取"能力 | **Spring AI 就够**，不用引入额外框架 |
| 需要多轮对话 + 知识库检索（RAG） | Spring AI（`ChatClient` + Advisor + `VectorStore`） |
| 要调通义/百炼系列模型，且希望零适配成本 | Spring AI Alibaba 的 `dashscope` starter 更省事 |
| 业务流程有明确分支、需要可复现可测试 | **上 Graph 编排** |
| 多 Agent 分工协作 | Spring AI Alibaba（Graph 是它的强项） |
| 要可视化配置、要能看模型调用耗时与 token 消耗 | Alibaba 配套的 Admin 控制台 + ARMS 可观测 |
| 已在用 Nacos 做微服务注册 | Alibaba 的 **Nacos MCP Registry** 能直接复用现有治理体系 |

**一条务实的路线**：先用 Spring AI 把单点能力跑通（这一步的抽象是通用的，将来换框架也不用改业务逻辑），当业务真的复杂到需要编排时，再引入 Graph。**一开始就上编排框架，往往是为想象中的复杂度付学费。**

## 四、国产模型接入：百炼与 dashscope {#dashscope}

Spring AI Alibaba 原生对齐阿里云**百炼**与灵积 MaaS 体系，接入方式就是"一个 starter + 一行配置"：

```xml
<dependency>
    <groupId>com.alibaba.cloud.ai</groupId>
    <artifactId>spring-ai-alibaba-starter-dashscope</artifactId>
</dependency>
```

```yaml
spring:
  ai:
    dashscope:
      api-key: ${AI_DASHSCOPE_API_KEY}
```

```java
// 业务代码只依赖 ChatClient —— 换模型不改一行 Java
@Autowired
private ChatClient chatClient;

String reply = chatClient.prompt("你好").call().content();
```

覆盖范围：**通义千问全系列对话模型、图像生成、语音合成、多模态理解**。

**为什么这件事在国内不是"锦上添花"而是刚需？** 三个理由：

| 理由 | 说明 |
|---|---|
| **合规与数据出境** | 政企/金融场景不能用境外模型服务；国产模型是硬约束 |
| **适配成本** | 各家 API 参数、报错格式、多模态协议都不同，手写适配层是持续的维护负担 |
| **能力对等** | 在中文场景下，国产模型的可用性已经不需要"退而求其次"了 |

## 五、企业级配套：这才是它真正的差异 {#enterprise}

Graph 是亮点，但**决定能不能在生产跑起来的，是配套**：

| 配套 | 作用 | 为什么重要 |
|---|---|---|
| **Nacos MCP Registry** | MCP Server 的分布式注册与发现 + 自动路由 | 微服务架构里 MCP 工具也需要注册中心；已在用 Nacos 的团队可复用现有治理体系 |
| **可观测（ARMS / Langfuse）** | 模型调用耗时、token 消耗、工具执行记录、异常告警 | 没有可观测就没有优化的抓手，也回答不了"为什么这个月账单涨了" |
| **Admin 控制台** | 可视化搭 Agent、编排工作流、配 RAG 知识库、可视化管 MCP、模型效果评测 | 降低门槛，让不写代码的角色也能参与 |
| **Human-in-the-Loop** | 关键节点人工确认 | 组织层面的免责边界（见第二节） |
| **上下文工程** | 长会话的上下文压缩与维护 | 长周期会话下控制 token 消耗 |
| **云原生适配** | 与 ACK、MSE 等集成，K8s 内自动扩缩容、链路追踪 | Agent 服务本质还是一个需要弹性伸缩的服务 |

> **一个判断框架**：评估任何 AI 框架时，问三个问题——**能不能接我的模型**（合规）、**能不能看见它干了什么**（可观测）、**流程能不能被约束**（编排 + 人机协同）。三个都能答上的框架才可能上生产。只看 demo 效果是选不对框架的。

## 六、整个 Java Agent 生态的位置 {#landscape}

Spring AI Alibaba 不是孤例。2026 年 Java 侧的 Agent 框架已经形成了一条谱系，**它们的设计哲学差别很大**：

| 框架 | 主导者 | 核心哲学 | 适合 |
|---|---|---|---|
| **Spring AI** | Spring 官方 | 原子抽象，不碰编排 | 给现有服务加 AI 能力 |
| **Spring AI Alibaba** | 阿里 | **编排优先**（Graph）+ 企业配套 | 企业级多 Agent、国产模型、要可视化 |
| **AgentScope Java** | 阿里 | **自主规划优先**：给目标，Agent 自己规划步骤、调工具、处理异常 | 探索性任务、通用 Agent |
| **Embabel** | Rod Johnson（Spring 创始人） | 结构化 Agent + **GOAP 目标导向行动规划**，强调强类型安全与可解释 | 需要可控、可解释的生产级 Agent |

**这几条路线值得对着看，因为它们回答的是同一个问题：Agent 的自主性应该给到哪一层？**

```text
Spring AI          自主性最低：你写代码，模型只做单点转换
      ↓
Spring AI Alibaba  中等：你画流程，模型在节点内决策
      ↓
AgentScope         较高：你给目标，模型自己规划路径
      ↓
Embabel            另一种切法：用目标导向规划 + 强类型约束来"驯服"自主性
```

**越往下，能力上限越高，但可预测性越差。** 选哪个不是比谁先进，而是比"你的业务能承受多少不确定性"——**受监管的业务场景应该往上选，创新探索应该往下选**。

## 七、常见坑 {#pitfalls}

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 想当然认为"Spring AI 2.0 能用，Alibaba 也就能用" | 两者版本节奏不同步，**先核对兼容矩阵**（四位版本号前三位才有意义） |
| 2 | 简单场景就上 Graph | 单点能力用 Spring AI；**编排复杂度还没出现时不要预支框架成本** |
| 3 | Agent 服务不做弹性伸缩设计 | Graph 节点会调模型，单次请求耗时是秒级——它本质是**长耗时服务**，要按这个前提设计超时、线程池、HPA |
| 4 | 关键决策节点不设人工确认 | 受监管/涉资金的流程必须 Human-in-the-Loop，这也是业务方愿意用的前提 |
| 5 | 没有可观测就上生产 | 先接 ARMS/Langfuse：看不到 token 消耗与工具调用，就无从优化 |
| 6 | 把 Graph 状态放在 JVM 内存里 | 长流程必须持久化 + 检查点，否则实例重启就全丢 |
| 7 | 依赖 Admin 控制台做"全部配置" | 控制台适合探索；**生产环境的图定义应该进代码库、走评审**，否则无法追溯谁改了什么 |
| 8 | MCP 工具数量放开增长 | 工具注册中心要治理（Nacos MCP Registry），并做按需下发 |
| 9 | 忽略模型调用的超时与重试 | 模型调用是外部依赖，必须有自己的超时、重试、降级，不能顺着业务线程池一路堵上去 |
| 10 | 用 Graph 编排"本来就该写代码"的逻辑 | 纯计算/纯查询不需要过模型，别为了"统一"把确定性逻辑塞进图里 |

## 八、高频问答 {#interview}

| 问题 | 一句话答案 |
|---|---|
| Spring AI Alibaba 和 Spring AI 是什么关系？ | 前者建立在后者之上：Spring AI 提供原子抽象，Alibaba 增加**Graph 编排**、国产模型适配与企业级配套，且**兼容 Spring AI 核心 API** |
| 版本号四位是什么意思？ | 前三位对应 Spring AI 主版本——`1.1.2.2` 表示对应 Spring AI `1.1.2`，第四位是自己的补丁号 |
| 什么时候该引入它？ | 出现"**流程需要编排**"的需求时（分支、并行、需要人工确认、要求可复现），单点能力用 Spring AI 就够 |
| Graph 的核心价值是什么？ | 把流程**从模型手里收回到开发者手里**：路径由边决定，模型只在节点内决策 → 可复现、可测试、可插入人工确认 |
| 为什么说"流程能固定的就别用自主 Agent"？ | 业务规定的流程不该让模型即兴发挥；自主性越高可预测性越差，受监管场景应优先选编排 |
| Human-in-the-Loop 的意义？ | 技术上是一个"等人确认"的节点，**组织上是 AI 决策失控的兜底与免责边界**——常常是业务方愿意用的前提 |
| 长流程挂了怎么办？ | 靠**检查点 + 状态持久化**恢复；状态放 JVM 内存里实例一重启就全丢 |
| Nacos MCP Registry 解决什么？ | MCP 工具的**分布式注册发现与自动路由**——让 MCP 工具也纳入微服务治理体系 |
| 为什么国产模型适配在国内是刚需？ | 合规与数据出境约束 + 各家 API 差异带来的持续适配成本；且中文场景下能力已经够用 |
| 评估一个 AI 框架该问什么？ | 三问：能接我的模型吗（合规）、能看见它干了什么吗（可观测）、流程能被约束吗（编排 + 人机协同） |
| Java Agent 框架怎么选？ | 本质是选"**给模型多少自主性**"：Spring AI（最低）→ Alibaba（你画图）→ AgentScope（它自己规划）；按业务能承受的不确定性来选 |
