# 第三方 AI 能力集成清单

接入第三方 AI 能力（数字人、语音、OCR、大模型、地图……）是后端与全栈开发者的高频任务。这类工作的难点通常不在编码，而在**信息不对称**：能力边界、配额、兼容性、授权方式都掌握在对方手里，而工期与稳定性责任在自己这边。

本文把[实时互动数字人](/ai/digital-human/interactive-avatar/)那次集成的过程抽象成一套可复用流程。它与具体厂商无关，换个能力同样适用。

## 一、适用场景

满足以下任一条件时，走这套流程：

- 能力由外部提供，核心实现闭源，只能通过 SDK / API 集成
- 涉及凭证、授权、配额，存在安全与成本风险
- 需要与自有终端或系统做工程整合（不只是调个接口）
- 交付后要长期运维，且故障时可能无人现场处理

## 二、五阶段流程

```
① 定义约束  →  ② 筛选方案  →  ③ 盘点边界  →  ④ 对接管理  →  ⑤ 验收上线
   （先写清）      （可对比）      （防误判）      （要物料）      （可复现）
```

### 阶段 ① 定义约束

**产出**：一张填满的约束表。填不满的单元格 = 待调研清单。

| 类别 | 约束项 |
|---|---|
| 终端 | 设备形态、操作系统与版本、CPU 架构（ABI）、内存与算力 |
| 环境 | 网络条件（有线/WiFi/移动）、是否可拉专线、供电与放置条件 |
| 使用 | 是否有人值守、单次运行时长、每日启停次数 |
| 交互 | 单向/双向、实时性要求、是否需打断 |
| 规模 | 并发终端数、峰值时长、增长预期 |
| 外设 | 音频输入输出设备、屏幕/投影数量与分辨率、接口类型 |
| 合规 | 数据是否含敏感信息、是否要求私有化部署、行业资质要求 |

> **这一步的常见错误**：跳过约束直接看方案对比。结果是每个方案都"看起来行"，反复摇摆。约束写清后，多数方案会自然被排除。

### 阶段 ② 筛选方案

**产出**：候选方案对比表 + 明确的排除理由。

对比维度建议固定为以下几项，避免每次换一套口径：

| 维度 | 关注点 |
|---|---|
| 能力匹配度 | 是否覆盖必需能力，有哪些缺口 |
| 部署形态 | 公有云 / 混合云 / 私有化 |
| 集成方式 | SDK / API / 协议接入（如 MCP），是否支持目标终端 |
| 成本模型 | 计费口径（按时长/按次/按并发/按量），能否预估规模下的成本 |
| 稳定性与运维 | SLA、配额与限流策略、故障通知机制 |
| 生态与耦合 | 是否绑定特定云或平台，迁移成本如何 |
| 交付与支持 | 是否提供 Demo 与技术支持通道 |

**重要**：把被排除的方案连同**排除理由**一起记录。三个月后有人问"为什么不用另一个"，答案应该在文档里，而不是记忆里。

### 阶段 ③ 盘点能力边界

**产出**：一张"谁负责什么"的表，与供应方逐项确认。

这是防止工期估错的**唯一有效手段**。做法很简单——把整个链路拆开，逐项问一句"这个归谁"：

| 能力项 | 归属 | 确认状态 |
|---|---|---|
| 核心能力本体（渲染/识别/推理） | 供应方 | 已确认 |
| 鉴权与账号管理 | 供应方 | 已确认 |
| 终端集成与适配 | **我方** | — |
| 终端稳定性（自启/自愈/看门狗） | **我方** | — |
| 业务逻辑与内容（话术、知识库） | **我方** | — |
| 外设适配与现场调试 | **我方** | — |
| 运维监控与故障响应 | 双方边界需明确 | 需确认 |

经验规律：**供应方负责"能力"，我方负责"产品"**。Demo 到产品之间的所有工作都在我方。

### 阶段 ④ 对接管理

**产出**：一份对接清单，作为与供应方的沟通依据。

#### 必须索要的物料

- [ ] SDK 包与**可运行的 Demo 源码**（有源码才能评估改造量）
- [ ] 接入文档（含鉴权、接口、事件、错误码）
- [ ] 兼容性说明：支持的系统版本、CPU 架构、依赖库版本
- [ ] 形象/资源清单（若涉及可选资源库）
- [ ] 授权文件获取流程（license 申请方式、绑定规则、有效期）
- [ ] 配额与计费说明，以及超额后的行为
- [ ] 技术支持通道与响应时效

#### 必须确认的兼容性问题

- [ ] 目标设备的系统版本是否在支持范围内
- [ ] 目标设备的 CPU 架构是否支持
- [ ] 构建工具与运行时版本要求（例如构建工具版本对 JDK 版本的约束）
- [ ] 包体积增量
- [ ] 外设兼容性（音频设备的采集与播放是否已验证）
- [ ] 网络要求（带宽下限、是否要求固定出口 IP、是否依赖特定协议）

> 前面几项特别适合**拍照/截图**给供应方确认：设备型号、系统版本、硬件接口布局。文字描述容易失真，图最省事。

#### 沟通原则

- **约束先行**：先说明场景约束，再让对方给建议，而不是开放问"你们支持吗"
- **要物料清单，不要口头承诺**：把"能支持"落到"提供哪些文件"
- **留痕**：结论以书面形式确认（工单、邮件、文档），避免口头承诺无法追溯

### 阶段 ⑤ 验收上线

**产出**：可复现的验收记录（截图/日志），一份上线检查表。

| 验收层 | 检查内容 |
|---|---|
| 功能 | 核心能力可用、异常路径有提示 |
| 稳定 | 长时间运行不崩、断网恢复、断电重启自愈 |
| 安全 | 凭证不落客户端、日志不泄露敏感信息 |
| 成本 | 用量监控与告警已配置，有余额/配额预警 |
| 运维 | 故障应急路径明确，值守人员知道怎么操作 |
| 真实环境 | **在目标设备上实测**，而不是开发机 |

最后一条要单独强调：开发机跑通与现场可用之间，隔着硬件兼容、网络质量、环境噪声、实际光照等一堆变量。**只在开发机验证过的集成，不算完成。**

## 三、把选型结论写成 ADR

集成类决策建议落成一份轻量的 **ADR（Architecture Decision Record）**——一页纸，回答四个问题：

```markdown
# ADR-00X：<决策标题>

## 状态
已采纳 / 已废弃（日期）

## 背景与约束
<场景是什么，硬约束有哪些>

## 决策
<选了什么>

## 理由
<为什么是它：约束如何推出结论>

## 被否决的方案与原因
<方案 B/C 为什么不选 —— 这部分最有价值>

## 后果
<接受哪些代价、后续需要做什么>
```

**为什么值得写**：① 决策依据沉淀下来，人员/需求变动时不必重推；② "被否决方案及原因"能挡住重复讨论；③ 对个人而言，ADR 是"可验证产出"——它展示的不是"我会用什么技术"，而是"我为什么这样选"。后者才是架构能力的证据。

## 四、六种常见失败模式

| 失败模式 | 表现 | 预防 |
|---|---|---|
| 约束未定义 | 方案反复摇摆，每次讨论都从头开始 | 阶段 ① 的约束表必须填满 |
| 边界误判 | 工期估算翻倍，上线前发现一堆"没人做"的事 | 阶段 ③ 逐项确认归属 |
| 凭证失控 | 长期密钥进前端源码或仓库 | 凭证分层模型；上线前扫描仓库 |
| 只验 Demo | 开发机正常，现场不可用 | 目标设备实测 + 环境变量清单核对 |
| 授权到期 | 上线数周后能力突然失效 | 把授权有效期写进运维日历 |
| 无成本监控 | 账单异常增长才被发现 | 上线即配置用量告警 |

## 五、一页速查

```
① 约束填满再选型       → 约束表
② 对比表固定维度       → 方案对比 + 排除理由
③ 能力边界逐项确认     → 归属表（防工期误判）
④ 要物料不要口头承诺   → 对接清单 + 书面留痕
⑤ 目标设备实测才算完   → 验收表 + 运维日历
⑥ 决策写成 ADR         → 可追溯、可复用、可证明
```
