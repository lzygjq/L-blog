# 接入宿主选型：Web 与原生 App

选定云渲染路线后，第一个落地问题就是：**数字人跑在什么宿主上？** 同一朵"云端渲染"的云，落到终端只有两种主流形态——**Web 模式**（浏览器/Electron 里跑 JS SDK）和**原生 App 模式**（Android/iOS 工程里集成原生 SDK）。这一篇把两条路线的差异、各自的硬约束和选型判据一次讲清。

**一句话结论**：给人"看和点"的场景选 Web 模式；设备要"自己活下来"（自启、全屏、常亮、长期无人值守）的场景选原生 App 模式。这不是技术偏好问题，而是宿主能力边界问题。

## 一、两种模式总对比

| 维度 | Web 模式（JS SDK） | 原生 App 模式（Android/iOS SDK） |
|---|---|---|
| 宿主 | 浏览器页面 / WebView / Electron 渲染进程 | 原生 App（Android Studio / Xcode 工程） |
| 集成方式 | 引入 JS SDK（npm 包或脚本） | 引入 aar / framework 依赖 |
| 运行环境 | 现代浏览器，需支持 WebRTC、媒体采集 API | 指定 OS 版本与 CPU 架构（以 SDK 兼容性说明为准） |
| 页面协议 | 生产环境强制 HTTPS，本地可用 localhost | 无此概念 |
| 音视频采集 | 浏览器权限体系（首次需用户授权） | 系统权限弹窗 + 清单声明 |
| 系统能力 | 沙箱内，自启/常亮/保活基本不可控 | 完整控制：自启、全屏、常亮、后台保活、开机广播 |
| 升级分发 | 发版即生效（Web 天然热更新） | 需发版升级 App，license 有效期到点强制更新 |
| 额外凭证 | 服务端签发短期 token 即可 | token + **license 文件**（绑定包名与签名） |
| 调试 | 浏览器 DevTools 直接用 | Android Studio / Xcode + 真机日志 |
| 典型场景 | 客服网页、营销页、后台内嵌、桌面端（Electron） | 展厅终端、无人值守设备、车载、硬件一体机 |

## 二、Web 模式：快，但活在浏览器的规则里

### 2.1 环境硬约束

- 浏览器必须支持 **WebRTC** 与媒体采集 API（如 `getUserMedia`）——这是实时音视频链路的地基，老浏览器和部分国产浏览器内核不在支持范围。
- **生产环境必须 HTTPS**：媒体采集 API 在非安全上下文直接不可用。反过来说，这也是 Web 模式"安全性底线"的一部分。
- Electron 桌面端只能跑在**渲染进程**，主进程 / Node.js 服务端环境不可用——它本质还是"页面"。

### 2.2 最大的坑：自动播放与授权策略

浏览器的自动播放策略和权限模型决定了：**进房、开播、采集麦克风这类动作，尽量由用户点击手势触发**，否则会被浏览器静默拦截。对"用户主动打开的网页"这不是问题；对"无人操作就要出声出画"的设备，这是致命伤——这正是 Web 模式不适合无人值守场景的根因。

### 2.3 适合谁

- 已有网站/管理后台，想嵌一个数字人客服或讲解员；
- 用户主动访问、人在屏幕前的场景；
- 要求发版快、跨平台一份代码。

## 三、原生 App 模式：重，但设备能力完全可控

### 3.1 集成形态

供应商交付的是 **aar/framework + Demo 工程**（核心 SDK 闭源，没有开源替代），集成动作是：建原生工程 → 引依赖 → 填凭证 → 放 license → 跑 Demo → 做产品化改造。

### 3.2 license：原生模式特有的强约束

原生 SDK 通常额外要求 **license 文件**，且绑定**应用包名 + 签名指纹**。这意味着：

- 换包名或换签名 = license 失效，需重新申请；
- license 有**有效期**，到期前必须完成 App 更新，否则线上设备直接失效——无人值守设备散布在外时，这是一定要纳入运维计划的硬时间点。

### 3.3 产品化改造才是开发量大头

原生模式的价值在系统能力，这些也正是它的开发量清单：

| 改造项 | 手段 |
|---|---|
| 全屏展示 | 隐藏状态栏/导航栏，画面铺满 |
| 开机自启 | 监听系统开机广播拉起 App |
| 防息屏/常亮 | 屏幕常亮标记 + 电源策略豁免 |
| 循环播报 | 待机话术轮播 |
| 断线恢复 | 监听网络与推流状态，自动重连 |
| 异常看护 | 进程被杀后自动拉起（保活/看门狗） |

### 3.4 适合谁

- 无人值守终端（展厅导览、大屏、一体机）；
- 需要开机即用、长期运行、断网自愈的设备；
- 需要与本地硬件（麦克风阵列、投屏、串口设备）深度配合的场景。

## 四、鉴权：同一条链路，两种终端参数

两种模式的鉴权**架构完全一致**，差异只在参数与附加凭证：

```
长期凭据(sk) ──只存服务端──▶ 服务端按 HMAC 签名调用签发接口
                                │  platform: web / android / ios
                                ▼
                        短期 accessToken（分钟级有效期）
                                │
            ┌───────────────────┴──────────────────┐
            ▼                                      ▼
      Web：JS SDK 初始化                原生：SDK 初始化 + license 校验
      （过期前刷新/更新 token）          （token 刷新 + license 有效期管理）
```

三条不变的原则（两种模式通用）：

1. **sk 永不下发到前端/客户端**——泄露即可被冒用签发 token，只能存在服务端；
2. token 是**短期凭证**，客户端要在到期前主动刷新（提前量与并发合并刷新都应在 SDK 封装层处理）；
3. 原生模式多一层 license 与签名绑定，凭证管理从"一维"变"二维"（token 的时效 + license 的周期）。

## 五、选型判据

按顺序自问，答案基本唯一：

1. **谁在屏幕前？** 人主动操作 → Web；没人操作、设备自己活着 → 原生。
2. **要开机自启/常亮/防误触吗？** 要 → Web 模式做不到，原生。
3. **发版节奏是什么？** Web 页面随时上；原生升级要考虑设备可达性与 license 周期。
4. **是否桌面端？** Electron 属于 Web 模式的特例（渲染进程），但分发方式接近原生。

> 反向提醒：不要因为"团队熟 Web"就选 Web 模式去啃无人值守场景——浏览器策略不是工程努力能绕过的产品级限制。同理，普通网页客服也没必要上原生 App，集成成本与发版成本完全不匹配。

## 六、面试问答

**Q1：数字人 SDK 选 Web 还是原生，你怎么决策？**
答：先看宿主与运营形态：用户主动访问的页面选 Web（HTTPS + 用户手势触发进房）；无人值守设备选原生（自启、常亮、保活、license 绑定）。核心判据是浏览器沙箱能力边界，不是团队技术栈偏好。

**Q2：为什么 token 要服务端签发而不能放在前端？**
答：签发 token 需要长期凭据 sk，sk 一旦下发到前端即可被任何人提取并冒用签发 token，等于鉴权体系失效。正确模型是 sk 只存服务端，服务端按签名协议换取短期 token 下发，客户端到期前刷新。

**Q3：原生模式里 license 绑定包名和签名，会带来什么工程问题？**
答：证书更换、渠道包多签名、License 到期三件事都会触发失效。工程上要提前把 license 有效期纳入发版日历、避免签名体系中途变更，并对散布在外的设备做远程版本监控，防止到期后批量黑屏。
