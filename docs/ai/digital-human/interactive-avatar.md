# 实时互动数字人：选型与集成落地

本文以**云渲染互动数字人**为例，完整走一遍从场景判断到终端上线的过程。所有结论都建立在一条原则之上：**先写清场景约束，再谈技术选型**。

## 一、场景先行：把约束写下来

选型摇摆的根源，往往不是资料不够，而是**约束没写成文字**。集成开始前，先把下面这张表填满——填不满的部分，就是还没调研清楚的地方。

| 约束项 | 需要明确的内容 | 对选型的影响 |
|---|---|---|
| 终端形态 | 安卓设备 / 网页 / 大屏 / 手机 | 决定 SDK 类型（安卓 vs Web vs H5） |
| 是否有人值守 | 有无现场人员操作、能否手动重启 | 决定是否需要自启、看门狗 |
| 交互形态 | 单向播报 / 双向对话 / 直播 | 决定是否走实时音视频链路 |
| 网络条件 | 有线 / WiFi / 4G，是否可拉专线 | **云渲染的关键前置条件** |
| 硬件配置 | CPU / GPU / 内存 / 系统版本 / ABI | 决定 SDK 兼容性与渲染模式可行性 |
| 音频设备 | 麦克风与扬声器型号、接口类型 | 影响采集与播放链路能否跑通 |
| 形象来源 | 公共形象库 / 定制克隆 | 影响交付周期与成本 |
| 并发规模 | 同时在线的终端数 | 云渲染路线的成本模型核心变量 |

### 一个典型的推理链

以"展厅无人值守终端 + 实时对话"为例，约束推着选型走：

```
无人值守（现场无人操作）
  └─▶ 必须开机自启 + 崩溃自愈        ← 这是原生 App 的强项，Web 的软肋
        └─▶ 走原生 App 而非网页
              └─▶ 选安卓原生 SDK，而非 Web SDK / H5 / 跨端框架
网络可拉有线
  └─▶ 云渲染可行（云渲染强依赖稳定网络 + WebRTC）
        └─▶ 画面质量交给云端，终端只需能解码
```

**反向结论同样重要**：如果终端是一台性能尚可的电脑、网络不可控、且要多路并发，那么同一场景应该选**端渲染**，而不是照搬上面的结论。**没有普适的最优解，只有与约束匹配的解**——这也是为什么本章第一节要求先把约束列表写满。

## 二、渲染模式：云渲染的收益与代价

云渲染 ≠ 更高级，它是一组明确的交换：

| 用云渲染换来的 | 付出的代价 |
|---|---|
| 终端无需渲染算力，老旧设备也能出高画质 | 每路会话独占云端 GPU，**并发数直接绑定成本** |
| 形象与算法在云端迭代，终端不用升级 | **断网即中断**，网络质量成为体验上限 |
| 支持 3D 超写实等重渲染形象 | 端到端延迟多出"上下行网络"两段 |

**成本估算的抓手**：云渲染的边际成本 ≈ 单路 GPU 时长成本 × 并发路数 × 服务时长。终端数量一多、在线时长一长，这条曲线会陡峭上升——这也是端渲染方案存在的根本理由。

**协议选择**：实时互动优先 WebRTC（低延迟、抗丢包、自带 NAT 穿透），RTMP 更适合单向直播（兼容性好、延迟较大）。双向对话场景用 RTMP 会明显感到"抢话"的迟滞。

## 三、集成链路：五步走，每步都要能验收

原则是**逐步验证，每步有可观测的验收标准**，不要等全部做完再联调。

### 第 1 步 · 开通账号与能力

拿到平台账号（建议完成企业认证，额度更充足），确认所需能力组件的试用或正式额度已到账。

| 验收标准 | 明确点 |
|---|---|
| 控制台可见所需组件条目，且额度大于 0 | 这一步失败的最常见原因是"组件未勾选"或"额度未领取" |

### 第 2 步 · 创建应用，取业务凭证

在控制台创建应用，绑定所需能力组件，记录生成的凭证（通常是一组 AppID / AppKey，或 ak / sk 形式）。

| 验收标准 | 明确点 |
|---|---|
| 拿到凭证字符串并妥善保存 | **凭证是机密，不得进入代码仓库、日志、前端产物** |

### 第 3 步 · 获取 SDK 与 Demo 工程

向平台或供应商索取 **SDK 包 + 可运行 Demo 源码**（安卓场景通常是 aar + Demo 工程）。

需要注意的现实：**核心 SDK 一般闭源**，不存在开源替代——这不是调研不足，而是这类能力的商业形态。所以"能不能拿到 Demo 并跑通"是供应商交付能力的第一个验证点。

| 验收标准 | 明确点 |
|---|---|
| SDK 包与 Demo 源码到手，导入 IDE 无报错 | 若这一步受阻，后续所有排期都会被拖住，应尽早升级沟通 |

### 第 4 步 · 本地跑通 Demo

| 前置项 | 典型要求 |
|---|---|
| 工具链 | 与 Demo 匹配的构建工具版本（Gradle 版本往往绑定 JDK 版本要求，例如 Gradle 8.x 需 JDK 17+） |
| 平台 SDK | 对应安卓版本平台包 |
| 运行设备 | 模拟器或真机 |
| 授权文件 | 部分 SDK 需要 license 文件（常打包进 `assets/` 并在代码中匹配文件名） |

| 验收标准 | 明确点 |
|---|---|
| 屏幕出现数字人画面，可用文本驱动播报 | 先跑通"能出画面"，再考虑双向对话 |

> **license 的两个坑**：一是通常**绑定包名 + 签名指纹**，更换签名或改包名都会失效；二是**有有效期**，到期需要更新，否则终端上已部署的应用会突然不可用——这一条必须写进运维计划，而不是等出事再处理。

### 第 5 步 · 产品化改造（真正的开发量）

Demo 能跑不等于产品可用。这一步才是自有开发量所在，详见第五节。

## 四、凭证与鉴权：三层模型

这是整个集成中最容易埋安全隐患的地方，值得单独说清。第三方 AI 能力的凭证体系普遍分为三层：

| 层级 | 典型形式 | 存放位置 | 生命周期 |
|---|---|---|---|
| **长期凭证** | AppKey / sk / Secret Key | **仅服务端** | 长期有效，泄露即失控 |
| **短期凭证** | accessToken | 服务端签发后下发给终端 | 短（分钟~小时级），需**定时刷新** |
| **业务标识** | AppID、形象 ID（agent_id）、用户标识（cuid） | 终端可持有 | 长期，但不宜硬编码在源码中 |

### 三条硬性规则

1. **长期凭证绝不进前端/终端**。终端可被反编译、网络可被抓包，一旦长期凭证落到客户端，等于把账号交给第三方。正确做法是：服务端持长期凭证，按需换取短期 token 下发给终端。
2. **短期 token 必须支持持续刷新**。长会话场景（数字人终端往往一开就是一整天）若只在初始化时取一次 token，中途失效会导致会话中断。SDK 一般提供 `updateAccessToken` 之类的接口，配合客户端定时器使用；服务端要能承受对应的换取频率（可加缓存，避免每次请求都打平台接口）。
3. **业务参数不要走 URL query 长期传递**。URL 会进日志、进浏览器历史、进代理记录，参数应通过请求体、配置系统或构建期环境变量注入。

### 安全自查清单

- [ ] 长期凭证只存在于服务端配置（环境变量 / 配置中心 / 密钥管理）
- [ ] 代码仓库与构建产物中搜索不到凭证字符串
- [ ] 短期 token 有刷新机制，且刷新失败有降级策略（如重进会话）
- [ ] 日志中不打印完整凭证（需要排查时打前几位 + 掩码）
- [ ] 终端与平台的通信使用加密协议

## 五、能力边界：先划清 SDK 管什么

**误判 SDK 的能力范围，是工期估算失准的头号原因。** 集成前应当和供应商逐项确认下表——这张表在商务对接时同样有用，能把"我以为你负责"变成白纸黑字。

| 能力项 | 通常归属 |
|---|---|
| 数字人画面渲染与推流 | ✅ SDK / 云端 |
| 语音链路（采集 → ASR → LLM → TTS → 播放） | ✅ SDK 内置 |
| 表情、口型、动作驱动 | ✅ 云端渲染自带 |
| 鉴权、应用与形象管理 | ✅ 平台 |
| **终端开机自启、全屏、防息屏** | ❌ **自己做** |
| **断线重连、异常自愈、看门狗** | ❌ **自己做** |
| **业务对话内容（话术、知识库）** | ❌ 自己做（或接自有 RAG） |
| **硬件适配（音频设备、屏幕布局）** | ❌ 自己做 |
| **物理机械动作控制** | ❌ 视场景，纯投屏形态下不存在 |

下半张表就是"真正的开发量"。如果只按上半张表估工期，实际工作量会翻倍。

## 六、无人值守终端的四件事

如果终端是长期无人值守的设备，以下四项几乎是必备的——它们与数字人技术无关，却决定了设备能不能"自己活着"。

| 能力 | 实现要点 | 失效后果 |
|---|---|---|
| **开机自启** | 监听系统开机广播，自动拉起应用 | 断电重启后黑屏，现场无人可救 |
| **全屏常驻** | 隐藏状态栏与导航栏，禁用返回 | 误触退出、露出系统界面 |
| **防息屏常亮** | 保持屏幕唤醒（注意长时间静止画面的烧屏风险） | 屏幕熄灭，设备形同宕机 |
| **断线自愈** | 网络监听 + 自动重进会话 + 指数退避重试 | 一次网络抖动导致设备长时间离线 |

补充两条经验：

- **看门狗机制**：用一个独立进程或系统级定时任务监测主应用存活，异常时重启应用。无人值守场景里，"应用崩了没人知道"比"应用崩了"更致命。
- **弱网降级**：网络恢复后应自动重进会话，而不是停在错误页等人工干预。

## 七、避坑清单

| 坑 | 现象 | 应对 |
|---|---|---|
| license 失效 | 已部署终端突然不可用 | 把有效期纳入运维日历，提前更新并重新发包 |
| 包体积膨胀 | 集成的 SDK 让安装包显著变大 | 提前评估包体积，必要时按 ABI 拆分发布 |
| 额度耗尽 | 对话突然全线失败 | 控制台监控用量 + 服务端告警，预留余量 |
| 权限未授予 | 麦克风采集失败、对话无输入 | 首次运行即申请权限；设备可能需系统级预授权 |
| 音频设备不匹配 | 有画面无声、或声音从错误设备输出 | 落地前实测目标硬件；接口类型（USB / 3.5mm / 蓝牙）需提前确认 |
| 硬编码凭证 | 源码泄露导致凭证失效或被盗用 | 走第四节的凭证三层模型 |
| 单点并发估算 | 上线即触发平台限流 | 提前与平台确认并发上限与配额策略 |

## 八、验收清单

按此清单逐项确认，全部通过才算集成完成：

**账号与凭证**
- [ ] 所需能力组件已开通，额度充足
- [ ] 应用已创建，凭证已获取并存于服务端
- [ ] 短期 token 可正常签发与刷新

**SDK 与 Demo**
- [ ] SDK + Demo 源码已获取，导入无报错
- [ ] 本地跑通 Demo，画面与播报正常
- [ ] license（若需要）已申请，有效期已知悉

**产品化改造**
- [ ] 开机自启、全屏常驻、防息屏、断线自愈四项已实现并实测
- [ ] 循环播报话术已配置
- [ ] 访客对话链路（含打断）已实测
- [ ] 目标硬件上音频采集与播放正常

**上线前**
- [ ] 目标设备实机验证通过（不是只在开发机）
- [ ] 用量监控与告警已配置
- [ ] 故障应急路径明确（现场人员如何恢复设备）
