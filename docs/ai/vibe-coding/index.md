# Vibe Coding 与 AI 辅助研发

到 2026 年，AI 编程工具已经完成了一次形态迁移：从编辑器里的**补全插件**，变成能读代码库、改多个文件、跑测试、提 PR 的**智能体（Agent）**。所以"AI 能不能写代码"这个争论已经过时了。

真正的问题变成：**把 AI 放进什么样的流程里。**

同一款工具，在"随手提一句需求、写完不测就提交"的用法下会持续制造事故；在"先写验收标准、任务切成两小时颗粒、提交必过评审"的用法下，能把一个人变成一个小队的产能。**差距不在模型，在流程。**

本文要回答的就是这个流程怎么搭——以及为什么它的核心其实不是"提示词技巧"，而是**上下文工程**。

## 一、先分清四种模式 {#four-modes}

"AI 辅助开发"是一顶大帽子，底下至少有四种差别巨大的实践。把它们混为一谈，是讨论效率问题的第一道坎：

| 模式 | 规格（Spec）的生命周期 | Agent 承担的角色 | 适用场景 | 主要风险 |
|---|---|---|---|---|
| **Vibe coding** | 没有规格——意图只活在对话历史里 | 边猜边改，人来判断对不对 | 原型、调研探针、一次性的演示 | **不可维护**：没有规格就没法回头改 |
| **Spec-first** | 写一次，之后逐渐漂移 | 结构化开工，后续随意发挥 | 短小的功能、单个迭代内能完成的事 | 规格变成"写完即弃"的文档 |
| **TDD** | 测试套件就是规格（单元级） | 面向失败的测试去实现 | 库、SDK、边界清晰的模块 | 只覆盖到单元级；集成与业务语义没人管 |
| **Spec-driven（SDD）** | **持久、可执行、进版本库** | 契约驱动的自主执行 + 闸门把关 | 绿地功能、受监管代码、基础设施 | 前期投入大；规格本身写错会放大错误 |

**这四者不是"先进程度的排序"，而是风险承受度的选择。** 关键判据就三问：

```
1. 这段代码要活多久？        —— 一次性的 → vibe coding 足够
2. 出错谁承担？              —— 只有我自己、且随时能重来 → 可以放松
3. 我能不能写出验收标准？     —— 写不出来 → 说明需求本身没想清楚，
                                此时上 SDD 只是把模糊提前固化
```

> **最常见的误用**：拿 vibe coding 的用法去做要长期维护的模块。表现是——三天做出一个能跑的功能，然后花三周把 AI 留下的"看不懂但能跑"的代码重写一遍。**这不是 AI 的问题，是模式选错了。**

TDD 与 SDD 也不是替代关系：**SDD 在单元之上运作，把测试套件当作规格的一项产出，而不是规格本身。**

## 二、上下文才是真瓶颈 {#context-files}

如果只能记住本文一句话，就是这句：**在 2026 年，Agent 写不好代码的原因，绝大多数不是模型不够聪明，而是它不知道你要什么。**

模型能力的差距在缩小，而"上下文给得对不对"的差距在放大。于是工程化的重点从"怎么写提示词"转向了**怎么把项目上下文固化成文件、进版本库**：

| 载体 | 作用 | 五个平台的对应实现 |
|---|---|---|
| **项目指令文件** | 约定技术栈、约定禁止事项 | `AGENTS.md`（Codex）、`CLAUDE.md`（Claude Code）、`.cursor/rules`（Cursor）、`RepoWiki`（Qoder） |
| **分层规则** | 按目录/模块给不同规则 | `.claude/rules/`（按目录分层） |
| **Skills / 可复用工作流** | 把"读 Excel""生成 SQL""跑数据迁移"这类流程预组装好，像积木一样调用 | Codex Skills、Claude Code Skills、Cursor Skills、Qoder 能力市场 |
| **Hooks / 确定性约束** | 在特定事件上强制执行检查，不依赖模型自觉 | Cursor Hooks、Kiro hooks |
| **MCP 工具接入** | 让 Agent 能访问外部系统（数据库、工单、文档） | 五家均支持 |

**写法上只有三条，但都很容易被违反：**

1. **写"禁止项"比写"要求"更有效。** "请遵循最佳实践"几乎不产生约束力；`禁止修改生产环境的认证代码`、`不要新增第三方依赖`、`不要动 xxx 目录` 才是真的能拦住行为的句子。
2. **一屏能读完。** 上下文文件不是项目文档，塞进整个 README 等于把噪声一起喂进去——**无关内容会稀释真正关键的约束**。
3. **进版本库、随代码审查。** 放在本地不入库的规则，等于团队里每个人都在用不同约定的 AI。

> **判断上下文文件写得好不好，有个很直接的办法**：把文件删掉，让 Agent 做同一个任务。如果两次产出差别不大，说明这份文件**没有提供任何有效约束**——它只是让你感觉良好了。

## 三、2026 年的工具格局 {#landscape}

### 三条路线之争

```
① CLI 派（终端优先，向 IDE 渗透）      Claude Code、Codex
② IDE 派（独立 AI 原生 IDE 为根基）    Cursor
③ 全形态覆盖（IDE + 插件 + CLI）       国内三家：CodeBuddy、Trae、Qoder
```

国内三家不约而同选了第③条路，并各自绑定自家云生态（腾讯云 / 火山引擎 / 阿里云）。**这个差异不是审美问题**：CLI 派擅长长任务无人值守与脚本化；IDE 派擅长高频小步编辑；全形态覆盖适合"一个团队统一入口"。

### 六款速览（2026 年）

| 工具 | 厂商 | 主力形态 | 一句话定位 | 上下文机制 |
|---|---|---|---|---|
| **Claude Code** | Anthropic | 终端 CLI（含 IDE 集成） | 大型/遗留代码库的深度推理与多文件重构 | `CLAUDE.md` + `.claude/rules/` + Skills + 子代理 + 记忆 |
| **Codex** | OpenAI | CLI + IDE 扩展 + 云端任务 | **云端并行**多个编码任务，打通 ChatGPT 生态 | `AGENTS.md` + 可组合 Skills |
| **Cursor** | Anysphere | AI 原生 IDE（VS Code 分支） | 代码库级上下文 + 多文件编辑，社区热度最高 | Rules + MCP + Skills + Hooks + 后台 Agent |
| **CodeBuddy** | 腾讯 | IDE + 插件 + CLI | 覆盖需求→编码→发布全流程，国内免费额度友好 | 智能体 / Builder 模式 + 腾讯云部署联动 |
| **Trae** | 字节跳动 | AI 原生 IDE + 独立端 | 性价比与中文体验 | SOLO 全自主模式 + MCP |
| **Qoder** | 阿里 | IDE + CLI + Agent 平台 | **Spec 驱动的 Quest Mode** + 代码库知识图谱 | Spec-Driven Workflow + RepoWiki + Expert Mode |

> 价格与额度变动极快，本文不给数字，一律以各家官网为准。**选型时该比的是"上下文机制"和"与现有工具链的摩擦"，不是价格表。**

### 几个值得记住的行业数据

| 事实 | 数值 | 说明 |
|---|---|---|
| Claude Code 开发者满意度 | JetBrains 2026.1 调查 **CSAT 91% / NPS 54** | AI 编程助手类目里的最高分 |
| Codex 周活跃用户 | 2026 年 6 月**突破 500 万，其中 20% 是非开发者** | 规格驱动不再只是研发团队的事 |
| GitHub Copilot 付费订阅 | 2026 年 1 月约 **470 万** | Fortune 100 中约 **46%** 的代码由 AI 生成 |
| Qoder 路线 | 2025-08 发布 → **2026-05-15 到 1.0**，重定位为"自主 Agent 开发工作台" | 从"AI IDE"改口为"Agent 平台"，是行业共识的缩影 |

**那个"20% 是非开发者"的数据最值得琢磨**：它说明上下文文件（AGENTS.md 之类）已经从"工程团队内部约定"变成了**整个组织对 AI 的协作契约**——产品、运营、风控都在写自己那份。这个视角下，"会不会写提示词"是个伪命题，**"能不能把一件事的要求写清楚"**才是真门槛。

### 双 Agent 组合

2026 年一个高频出现的实际配置是：

```
主 Agent（CLI 派）      ← 承担长任务、多文件重构、无人值守
辅助 Agent（IDE 派）    ← 承担高频小步编辑、前端样式微调
     │
     └─ 两者共享同一份规格文件与规则目录
```

选型的目标不是"选出最强的那一个"，而是**让它们共用同一份上下文**——否则你会得到两套风格，反而更难维护。

## 四、Agent 干活的循环与人的介入点 {#human-gates}

理解 Agent 怎么干活，才能知道**哪一步可以放手、哪一步必须看**：

```
你给出目标
   │
   ▼
① 读上下文 ── 项目指令文件 / 规则 / Skills / 已有的代码
   │              ← 上下文没给对，从这里就开始跑偏
   ▼
② 规划 ──────── 拆成若干步，可能列一个 todo
   │              ← 【介入点 1】拆分不合理时，这里纠正最便宜
   ▼
③ 执行 ──────── 改文件、跑命令、调工具（MCP）
   │              ← 【介入点 2】危险操作要授权：删文件、连生产库、装依赖
   ▼
④ 观察 ──────── 看测试结果、看报错、看命令输出
   │              ← 关键：Agent 的"观察"质量取决于你给它的验证手段
   ▼
⑤ 修正 ──────── 回到 ③，直到自认为完成
   │              ← 【介入点 3】"自认为完成"≠完成，必须验收
   ▼
你验收
```

**三个介入点里，最容易被忽略的是"观察"这一步。** Agent 只能看到你允许它看到的东西：

- 没有可运行的测试 → 它只能靠"看起来对不对"来判断，等于把正确性交给概率；
- 没有编译/lint 命令 → 它无法发现语法级错误；
- 没有日志与复现步骤 → 它在猜 bug 在哪。

**所以有一个反直觉的结论：想让 AI 干得好，先把项目的可验证性做好。** 测试覆盖率、一键构建、可复现的本地环境——这些"传统工程实践"在 AI 时代不是被取代了，而是变成了**AI 产出质量的直接决定因素**。

### 权限要白名单化，写进上下文文件

放手不等于放任。可行的做法是把权限显式写出来，而不是靠事后检查：

```text
允许：读写 src/ 与 docs/ 下的任何文件、运行 mvn test / npm run build
需要确认：新增或升级依赖、改动 CI 配置、执行数据库变更脚本
禁止：触碰生产配置与凭据、访问线上数据库、修改 .github/workflows/ 的发布任务
```

**判据只有一条：这一步的产物能不能被自动验证？**

| 任务类型 | 能否自动验证 | 出手程度 |
|---|---|---|
| 写单元测试、重命名、格式化、补文档 | ✅ 完全能 | 基本可以放手 |
| 实现有明确验收标准的功能 | ✅ 能（验收测试） | 给标准后放手，结果过评审 |
| 性能优化 | ⚠️ 部分（要有基准测试） | 必须给基准，否则"感觉更快了" |
| 架构决策、技术选型 | ❌ 不能 | AI 出选项与权衡，**人决策** |
| 涉及资金/权限/合规的边界逻辑 | ❌ 不能 | 人工逐行看 |

## 五、把 AI 纳入可控流程：五道闸门 {#five-gates}

这是本文最该被抄走的部分。把上面所有原则落成五个**可执行的检查点**：

| # | 闸门 | 具体做法 | 拦住了什么 |
|---|---|---|---|
| 1 | **Spec 门** | 没有验收标准的任务不接。标准要能被测出来 | 需求模糊被固化成一堆代码 |
| 2 | **任务粒度门** | 每个任务约 **2 小时**量级，超了就切 | 一次让 AI 改太多导致无法复核 |
| 3 | **PR 评审门** | Agent 提交的每个 PR 都要人工评审；**加密、编解码、认证、数据处理类代码由领域专家评审** | 无人复核的产出直接进主干 |
| 4 | **规格漂移 CI 门** | CI 解析规格与合并的 PR：代码是否满足每一条验收标准？不满足就**让构建失败** | 规格与实现长期脱节 |
| 5 | **分阶段发布门** | Agent 产出的代码先进 staging，过真实链路测试与监控/SLO 检查后才上生产 | "能跑"被当成"能上线" |

**第 4 条是最容易被忽略、也最有价值的一条。** 它把"规格"从文档变成了**可执行的约束**——没有它，规格在第二个迭代就会开始腐烂。

### 一个必须说清的成本真相

SDD / 严格流程**不是"消灭工作量"，而是"把工作量前移"**。多家实践团队的经验值一致：**要预留 25%~40% 的交付时间用于评审与把关。**

所以"AI 让交付变快"的准确表述应该是：

```
模糊需求 + 无验收标准 + 不评审   →  前期极快，后期大量返工（总账更慢）
清晰规格 + 有验收标准 + 必评审   →  前期更慢，后期几乎无返工（总账更快）
```

**如果你的团队只感受到"变快了"，多半是在花后期返工的预算。**

## 六、常见坑 {#pitfalls}

| # | 坑 | 表现 | 正确做法 |
|---|---|---|---|
| 1 | **一次让 AI 改太多** | 一个任务涉及 20 个文件，评审时无从下手 | 按 2 小时颗粒切；宁多几轮 |
| 2 | **上下文文件过期** | 技术栈已经从 Spring Boot 3 升到 4，文件里还写着 3 的约定 | 上下文文件与代码同一次 PR 更新 |
| 3 | **没有验收标准就开工** | "帮我做个报表导出"→ 做出来发现要的不是这个 | 先写"怎样算做完" |
| 4 | **不跑测试就相信产出** | Agent 说"已完成"，实际没编译过 | 让 Agent 自己跑；不通过不许说完成 |
| 5 | **让 AI 自由访问网络与凭据** | 顺手 `curl` 了生产接口、把密钥写进日志 | 权限白名单化 + 凭据不进上下文 |
| 6 | **用 AI 写边界判断** | 金额边界、权限判定、费率计算交给 AI 自由发挥 | 这类逻辑必须人定规则、AI 只做填充 |
| 7 | **省掉 review** | "AI 写的它自己最懂"是错觉 | 越自动，越要评审——这是并行关系 |
| 8 | **低估工具切换成本** | 频繁换工具，规则文件全部重写 | 优先选能复用同一份 `.md` 约定的方案 |
| 9 | **把对话历史当规格** | 换个会话就全部丢失，无法交接 | 规格落文件、进版本库 |
| 10 | **只衡量生成量** | 用"AI 生成了多少行"当指标 | 指标应该是**返工率、缺陷率、评审耗时** |

## 七、高频问答 {#interview}

| 问题 | 一句话答案 |
|---|---|
| Vibe coding 和 Spec-driven 的本质区别是什么？ | **规格的生命周期**：前者只活在对话历史里，后者是持久、可执行、进版本库的契约。前者适合原型，后者适合要长期维护的东西 |
| AI 辅助研发的瓶颈在哪？ | **上下文，不是模型**。模型不知道你的约定、边界、禁止项，就会持续产出"看起来对"的代码 |
| 上下文文件该写什么？ | 技术栈与约定、**禁止项**、验证命令（怎么构建、怎么跑测试）、目录职责。一屏能读完，进了版本库 |
| 为什么强调"可验证性"？ | Agent 的自我修正完全依赖它能观察到的信号。没有测试/构建/日志，它只能靠概率判断对错 |
| 什么样的任务可以放手给 AI？ | **产物能被自动验证的**。写测试、重构、格式化基本可放手；架构决策与资金/权限边界逻辑必须人把关 |
| 上了 AI 为什么没感觉快？ | 多半是把工作量后移了。真正的提速来自"返工减少"，不是"生成变快" |
| 为什么 Agent 提交也要人工评审？ | 自动化程度越高，评审越重要——两者是**并行**关系，不是替代关系。评审时间要预算 25%~40% |
| 规格漂移 CI 门解决什么问题？ | 让规格从"文档"变成"可执行的约束"：代码不满足验收标准就让构建失败，否则规格在第二个迭代就开始腐烂 |
| 多 Agent 组合的价值在哪？ | 不同形态各有所长（CLI 擅长长任务、IDE 擅长小步编辑）；关键是**共享同一份规格与规则**，否则会产出两套风格 |
| 该用什么指标衡量 AI 辅助的效果？ | 返工率、缺陷率、评审耗时。**不要用生成代码行数**——它鼓励的是量而不是质 |
