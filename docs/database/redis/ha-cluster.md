# 持久化、主从与集群

单点 Redis 有四个先天问题，每个问题对应一层架构演进——这张映射表是整个高可用体系的目录：

| 单点问题 | 解法 | 对应小节 |
|---|---|---|
| 数据丢失（内存存储，重启即失） | 持久化 RDB/AOF | 一 |
| 故障恢复（宕机服务不可用） | 主从 + 哨兵自动切换 | 二、三 |
| 并发能力（读多时单点扛不住） | 主从读写分离 | 二 |
| 存储能力（内存放不下海量数据） | 分片集群 | 四 |

注意演进顺序有依赖关系：持久化是主从全量同步的基础，主从是哨兵的前提——不是四个孤立选项。

## 一、持久化：RDB 与 AOF

### RDB：某一时刻的全量快照

`bgsave` 触发主进程 **fork 子进程**，子进程遍历内存写临时快照文件。主进程继续服务靠**写时复制（Copy-On-Write）**：fork 后父子共享内存页，主进程修改某页时才复制该页。

- 优点：紧凑的二进制文件，恢复快（直接载入），适合做定期备份与灾难恢复。
- 缺点：两次快照之间的数据宕机即丢；fork 瞬间内存翻倍风险（页复制量与写入量相关）；数据集大时 fork 本身有毫秒到秒级停顿。

### AOF：追加写命令日志

每条写命令追加到日志文件。三个 fsync 策略：

| 策略 | 丢数据窗口 | 性能 |
|---|---|---|
| always | 0（最多丢一条正在写的事件） | 每条命令刷盘，最慢 |
| everysec（默认/推荐） | ≤1s | 折中 |
| no | 不可控 | 最快，交给 OS |

写多了文件膨胀，靠 **AOF 重写**（`bgrewriteaof`）压缩：fork 子进程按当前内存的最终状态生成等价最小命令集（如 100 次 INCR 合并为一次 SET），期间新写入进重写缓冲区。

### 混合持久化（4.0+，生产推荐）

`aof-use-rdb-preamble yes`：重写后的 AOF = 前半段 RDB 全量 + 后半段增量命令。恢复速度接近 RDB，丢数据窗口接近 everysec 的 AOF——**两全，没有明显理由关掉它**。

## 二、主从复制：全量与增量

从库执行 `replicaof <master> <port>` 后：

```
首次同步（全量）：
从库 → PSYNC ? -1 → 主库 → bgsave 生成 RDB → 传输 → 从库清库载入
         ↑ 期间主库新写入进入 replication buffer → RDB 载入完成后补发

断线重连（增量）：
从库 → PSYNC <replid> <offset> → offset 仍在主库 repl_backlog 环形缓冲区内
     → 只补发缺失部分；被覆盖则退化为全量
```

关键参数是 `repl-backlog-size`（默认 1MB，生产必须调大）：缓冲区太小 + 网络抖动稍久 = 频繁退化全量，全量 = 主库 bgsave = 主库压力。这是主从环境最常见的事故链。

读写分离的红线：**从库只做读**。写入从库会造成数据分叉；主从延迟客观存在，读己之写（改完立刻查）的请求要路由主库。

## 三、哨兵：自动故障转移

主库挂了不能靠人半夜起来切换，哨兵（Sentinel）解决「发现 + 决策 + 切换 + 通知」：

1. **监控**：每秒 ping。多数哨兵（≥quorum）在 `down-after-milliseconds` 内无响应 → **主观下线**升级为**客观下线**（防止单个哨兵的网络抖动误判）。
2. **选举**：哨兵之间 Raft 式选出一个 leader 哨兵执行切换（需要超过半数哨兵同意，因此**哨兵至少 3 个且为奇数**）。
3. **转移**：按优先级（`replica-priority`）→ 复制偏移量最大 → runid 最小，选出新主库，其余从库改挂新主。
4. **通知**：客户端通过订阅哨兵的 `+switch-master` 事件感知新地址（Spring 的 Lettuce 哨兵模式自动完成）。

实践锚点：本机开发环境用 Docker Compose 起「1 主 2 从 + 3 哨兵」，重点验证两件事——kill 主库后 10 秒级自动切换；切回原主库后它以从库身份重新加入。这个环境复现了生产的绝大部分故障语义。

## 四、分片集群：16384 个插槽

主从解决了可用性和读并发，但**所有数据仍在每个主库的内存里**。数据量超单机内存就要分片：

```
          ┌─ master0: 槽 0~5460    ─ replica0
key → CRC16(key) % 16384 → 落槽 → 槽归属节点
          ├─ master1: 槽 5461~10922 ─ replica1
          └─ master2: 槽 10923~16383 ─ replica2
```

- **为什么是 16384**：心跳包里携带槽位图，16384 bit ≈ 2KB 够用；节点上限建议 ≤1000，不需要更大空间。
- **MOVED 与 ASK**：key 不归我 → 回 `MOVED`（槽已永久迁移，客户端更新路由表）；迁移中 → `ASK`（本次去目标节点试，不改路由）。
- **扩容**：把某些槽整体从老节点搬到新节点，迁移期间该槽请求按 ASK 重定向，业务无感。
- **smart client**：客户端本地缓存「槽 → 节点」映射，直连目标节点，不走代理层。
- **hash tag**：`{user1001}:orders` 花括号内的部分参与取模，可让相关 key 落同一节点以支持 MGET/Lua 多 key——但用多了会人为制造数据倾斜，谨慎。

## 五、面试问答

**Q: RDB 和 AOF 怎么选？**
不是二选一：生产开混合持久化。追求极致写性能且能容忍分钟级丢失的纯缓存场景可只留 RDB；回答的关键是说出「fork/COW 的内存翻倍风险」和「AOF everysec 丢 1 秒」这两个量化点。

**Q: 主从复制什么时候全量、什么时候增量？**
看 offset 是否还在 repl_backlog 环形缓冲区内。所以生产容量规划要把 backlog 调大到能覆盖最长预期断线时间内的写入量。

**Q: 哨兵为什么至少三个？**
客观下线和 leader 选举都需要**多数派**。两个哨兵任一挂掉就凑不齐多数，等于单点；三个允许坏一个。必须奇数不是为了好看，是多数派协议的自然结果。

**Q: 分片集群下 MGET 多个 key 会怎样？**
不同槽的 key 落在不同节点，要么客户端按节点分组分别请求，要么用 hash tag 强制同槽。这也是「集群不是透明加速器」的例证——多 key 命令、Lua 多 key、事务在集群下都有跨槽限制。
