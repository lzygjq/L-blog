# 多级缓存：亿级流量架构

当单靠 Redis 缓存也扛不住时（目标 QPS 进入十万/百万级），优化的方向只有一个：**在请求到达后端之前，让每一跳都尽可能终结它**。这就是多级缓存——它不是「多加一层 Redis」，而是把缓存下推到请求链路的每个环节。

## 一、传统链路的两处瓶颈

```
客户端 → Nginx(反代) → Tomcat → Redis → DB
                          │
                 所有请求都要过 Tomcat 进程
```

1. **Tomcat 是性能天花板**：Servlet 模型每请求一线程（或用虚拟线程调优），其连接与线程成本比 Nginx 的事件模型高一个数量级。静态热点数据也要走到 Java 进程，Tomcat 就成了整个链路最贵的一跳。
2. **缓存失效冲击集中**：Redis 未命中（或 Redis 故障）时，全部压力瞬间落到 DB，之前的[三大问题](/database/redis/cache-patterns)在更高 QPS 下被放大。

**为什么瓶颈是 Tomcat 而不是 Redis**：Redis 单实例 10 万级 QPS，而一台 Tomcat 处理一个带 JSON 序列化的接口通常只有几千 QPS。**差距不在同一个数量级上**——所以「Redis 够快，为什么要加本地缓存」的答案是：**本地缓存省的不是 Redis 的计算，是这次网络往返和 Tomcat 线程的占用**。

## 二、多级缓存的分层与各自职责

```
浏览器缓存(HTTP 头)
   → CDN / 边缘节点(静态与不可变内容)
      → Nginx 集群本地缓存(OpenResty + Lua / shared_dict)
         → Redis(共享层)
            → Tomcat 进程缓存(Caffeine)
               → MySQL
```

每一层负责的**数据性质**不同，这是分层的核心，而不是「多缓存几层」：

| 层 | 存什么 | 容量 | 生效范围 | 失效方式 |
|---|---|---|---|---|
| 浏览器 / CDN | 静态资源、可公开且不可变的响应 | 无上限（客户端） | 全体用户共享 | `Cache-Control` / 刷新 URL |
| Nginx `shared_dict` | 个性化但读多的动态数据（商品详情、店铺信息） | 固定（配置时指定，通常 100MB~1GB） | **单台 Nginx 的所有 worker** | 版本号 / 主动删除 |
| Redis | 全量热点数据 | 受内存策略控制 | **全集群共享** | `DEL` + TTL |
| Caffeine | 实时性高、访问极热的数据（库存余量、配置） | JVM 堆的一小部分 | **单个 JVM 实例** | 主动失效 + TTL |
| DB | 权威数据 | — | — | — |

两条设计原则：

1. **越靠前的层越快、越钝**：浏览器和 Nginx 层存的是「相对稳定」的数据，命中即终结请求，根本不产生后端流量。
2. **越靠后的本地缓存越准、越短**：Caffeine 存的是「一个进程几秒内的真理」，天然靠 TTL 兜底，允许短暂陈旧。

> **一个常被忽略的账**：多级缓存的总内存 ≈ `Nginx 台数 × shared_dict 容量 + Tomcat 实例数 × 堆内缓存`。**它的边际成本随实例数线性增长，而收益是「单位请求的后端成本下降」**——实例数很大时，本地缓存的「热上热」命中率会下降（每台的访问样本变小），要按实测命中率决定还值不值得加。见[第七节](#verification)的验收口径。

## 三、Nginx 层：OpenResty + Lua

OpenResty = Nginx + LuaJIT，让 Lua 脚本在 Nginx 进程内执行业务逻辑，请求不必转发到 Tomcat：

- **`shared_dict`**：Nginx worker 间共享的内存字典，做本地热点缓存，读写微秒级。**容量在配置里写死**（`lua_shared_dict goods 512m;`），满了按 LRU 淘汰——所以它天然是一个「自动收敛到热点」的容器，但**必须预估容量**，写太小会让命中率骤降。
- **Lua 查 Redis**：本地未命中时由 Lua 直连 Redis（cosocket，**非阻塞**），命中则直接返回 JSON——整条「本地缓存 → Redis → 响应」都在 Nginx 进程内闭环。

### 3.1 这一层要自己解决的三个问题

| 问题 | 做法 |
|---|---|
| **缓存击穿**（热点 key 刚过期、瞬时大量回源） | `lua-resty-lock`——用共享内存做一把轻量互斥锁，**只放一个请求回源，其余等待后重读缓存**。这是 Nginx 层自带的能力，不必依赖应用层 |
| **key 设计** | 加上**版本号前缀**（`goods:v37:1001`），失效时只改版本号即可让整批缓存自然过期——**避免「删 N 台机器上的同一个 key」这个分布式删除问题** |
| **降级** | Redis 不可达时必须**快速失败而不是阻塞**，并把「降级到直连 Tomcat」或「返回兜底数据」写成显式策略。cosocket 的超时必须配，否则 Nginx worker 会被挂住 |

### 3.2 部署形态

业务 Nginx 按流量横向扩展，前面挂纯反代层做负载均衡。**关键点是「每台 Nginx 的本地缓存是独立的」**——它们之间不一致，所以这一层只能放「允许秒级陈旧」的数据，一致性靠版本号 / TTL，不靠同步。

这一层的本质：**把「查详情」这种读接口的实现从 Java 下沉到边缘节点**。

## 四、Tomcat 层：Caffeine

JVM 进程内缓存的当前标准解（Guava Cache 的继任者）：

```java
Cache<String, Shop> cache = Caffeine.newBuilder()
        .maximumSize(100_000)                       // 容量上限，防 OOM
        .expireAfterWrite(Duration.ofSeconds(60))    // 写后过期
        .recordStats()                               // 打开统计，否则看不到命中率
        .build();
```

### 4.1 淘汰策略：W-TinyLFU 与 Guava 的差别

Caffeine 的默认淘汰算法是 **W-TinyLFU**（Window TinyLFU），它解决的是 LRU 的结构性缺陷：

| 算法 | 缺陷 | 后果 |
|---|---|---|
| LRU | 一次性的全表扫描 / 冷数据遍历会把热门条目挤出去 | **缓存污染**（cache pollution），命中率骤降且难以复现 |
| LFU | 老热点长期占位，新热点进不来；计数不衰减 | 应对不了「热点迁移」 |
| **W-TinyLFU** | —— | 用**窗口（LRU）+ 频率素描（Count-Min Sketch）**两层：新条目先进窗口，要晋升到主区必须「比主区的候选者更常被访问」；频率计数带**衰减**周期性减半，因此能跟着热点迁移走 |

对使用者而言，**唯一需要记住的结论是：不要指望「调大缓存容量」线性换命中率**。命中率主要由**访问分布**（是否真有热点、热点是否稳定）决定；访问分布长尾时，容量加一倍命中率可能只涨一两个点。

### 4.2 三个配置维度的区别

| 配置 | 语义 | 什么时候用 |
|---|---|---|
| `expireAfterWrite(60s)` | 写入后 60s 失效（无论是否被访问） | **默认选择**，等价于「最多陈旧 60s」，与缓存同步链路配套 |
| `expireAfterAccess(60s)` | 最后一次访问后 60s 失效 | 会话类「访问即续命」的场景；热点数据用它会**永不失效**，慎用 |
| `refreshAfterWrite(30s)` | 到点后**异步刷新**，刷新期间旧值继续服务 | 希望「永不阻塞请求 + 数据尽快更新」的读接口，代价是可能长期服务旧值 |

`refreshAfterWrite` 是最符合多级缓存诉求的一个：**它把「回源」从请求路径上摘掉了**——请求永远立刻返回旧值，后台异步加载新值。配 `CacheLoader` 时这是「无阻塞缓存」的标准写法。注意它**必须与 `expireAfterWrite` 搭配**（否则条目没有硬过期，可能永久陈旧）。

### 4.3 两个必须回答的问题

- **多实例一致性**：每台 Tomcat 各有一份本地缓存，DB 更新后其他实例的副本是陈旧的。解法不靠轮询，靠**主动失效传播**——下一节。
- **为什么不用 JVM 缓存替代 Redis**：内存容量受限于单机（且与业务对象争堆）、无持久化、实例间不共享。**进程缓存永远是 Redis 前面的「热上热」，不是替代品**（Spring 侧的缓存抽象与本地缓存配置见[横切能力：本地缓存的多实例不一致](/java/spring/spring-framework/crosscutting/cache#multi-instance)）。

## 五、本地缓存的失效传播：四种方案

「DB 变了，N 台 Nginx + M 台 Tomcat 的本地缓存都要失效」——这是多级缓存真正的难点。四种方案按代价递增：

| 方案 | 机制 | 不一致窗口 | 代价 |
|---|---|---|---|
| **TTL 自愈** | 什么都不做，等本地缓存过期 | = TTL（秒级~分钟级） | 零。**但它是所有其他方案的兜底，必须保留** |
| **版本号轮询** | 定期从 Redis 读一个「数据版本号」，变了就整批清空本地缓存 | = 轮询间隔 | 实现最简；轮询本身有 QPS 成本与精度上限 |
| **消息广播** | 写路径主动发一条失效消息，各实例消费后删本地 key | 毫秒级 | 需要 MQ 或 PubSub 基础设施；**要处理消息丢失与实例离线** |
| **Canal 事件驱动** | 订阅 MySQL binlog，任何来源的写（含 DBA 手工改）都能触发失效 | 毫秒级 | 基础设施最重（Canal + MQ），但对业务代码零侵入 |

**选型判据**：

- 数据 5 分钟内变了也没关系 → **TTL 自愈**，不要为了「更实时」引入广播链路。
- 写路径集中、能埋点 → **消息广播**（工具最省事的是 Redis PubSub，但**它不持久化，实例启动瞬间的离线消息会丢**——见 [PubSub 只适合在线广播](/database/redis/lock-and-mq#pubsub)，所以仍需 TTL 兜底）。
- 写入来源分散（多个服务 + 后台管理 + 定时任务）、要求「一处改、处处立刻失效」 → **Canal 事件驱动**。
- 只需要整批失效、不需要精确删 key → **版本号前缀**最省事（改一次版本号，全链路的一次性失效就完成了）。

## 六、Canal 驱动的失效闭环

工程标准答案是事件驱动，理由与[数仓入仓](/bigdata/canal/)完全一致——**binlog 是唯一的、完整的变更真相**：

```
MySQL binlog → Canal（伪装成 MySQL 从库）
            → MQ（RabbitMQ / Kafka）
            → 各服务实例消费 → 删本地缓存（Nginx shared_dict / Caffeine）
```

收益与代价：

| 收益 | 代价 |
|---|---|
| 对业务代码零侵入（不用在写逻辑里埋失效调用） | 引入 Canal + MQ 两个中间件，运维复杂度上升 |
| binlog 完整性保证不漏（含 DBA 手工改数据） | 事件乱序需处理（**携带时间戳 / 版本号，只接受更新的**） |
| 延迟毫秒级，远优于 TTL 自愈 | 本地缓存仍需 TTL 兜底（链路故障时不至于永久陈旧） |

四个落地细节：

1. **广播粒度**：按「表 + 主键」发事件，消费端算出受影响的缓存 key。**不要发「整表变了」**——那会导致全量失效（等价于缓存雪崩，见[缓存雪崩](/database/redis/cache-patterns)）。若确实要整批失效，用**版本号**而不是逐 key 删除。
2. **广播风暴**：一次批量更新（如批量改价 1 万条）会产生 1 万个事件 → 消费端要把短时间内同一 key 的事件**合并（去重 / 节流）**，否则删除操作本身的 QPS 会超过业务读取。
3. **只删不写**：消费端**只删除本地缓存，绝不「顺手把新值写进去」**——写值需要还原业务对象、跨表组装，很容易写出半成品；删除让下一次读按正常路径回源，逻辑单一。
4. **消费幂等**：同一事件可能被重复投递，删除操作天然幂等（删不存在的 key 无害），但**版本号比较必须单调**，否则旧事件会覆盖新状态。

这套链路与本站 [Canal 数据同步](/bigdata/canal/) 和 property 数仓入仓是同一套基础设施——**一个 Canal 实例可以多路下游分发**，这是中间件复用的典型样板。

## 七、效果验证：怎么证明「流量确实前移了」 {#verification}

多级缓存的验收标准不是「加了」，而是**流量分布确实前移了**。上线前后用同一压测脚本对比三组数据：

| 指标 | 期望 | 说明 |
|---|---|---|
| Nginx 层命中率 | > 90%（读接口） | **低于 80% 说明 shared_dict 太小、key 设计粒度太细，或数据本身不够热点** |
| 到达 Tomcat 的 QPS | 大幅下降 | 这是多级缓存的**唯一核心收益**，其余指标都是它的因 |
| Redis QPS | 仍高但可控 | 若 Redis QPS 不降反升，说明 Nginx 层的命中率没起来，白加了一层 |
| Caffeine 命中率 | 单实例看趋势不求高 | **实例数越多命中率越低**，这是数学必然，不要拿它当 KPI |

### 7.1 压测对比的三个纪律

1. **同一份数据、同一份脚本、同一并发曲线**，只改部署形态——否则数字不可比。
2. **预热后再测**：冷启动阶段的命中率没有意义，要跑够时间让各层收敛到稳态。
3. **必须测「缓存全失效」的极端场景**：手动清空所有层，观察 DB 是否被打穿。**多级缓存的安全水位不是稳态 QPS，而是「全失效瞬间的 DB 承压」**——这才是它真正的风险面。

### 7.2 多级缓存自身的故障模式

| 故障 | 现象 | 防护 |
|---|---|---|
| Nginx `shared_dict` 写满 | 命中率下降，但服务正常 | LRU 自动淘汰；监控命中率而非内存 |
| Canal / MQ 链路中断 | 本地缓存永久陈旧 | **TTL 兜底**（这是它不可省的原因） |
| 广播风暴 | 删除 QPS 超过读 QPS | 事件合并与节流 |
| Caffeine 缓存大对象 | Full GC、堆压力 | 只缓存小型 DTO，不缓存聚合根；用 `maximumWeight` + `weigher` 限制 |

## 八、面试问答

**Q1：多级缓存和 Redis 集群扩容怎么选？**

先看瓶颈在哪：Redis 本身扛不住（CPU / 带宽 / 内存）→ 扩分片集群；Redis 不是瓶颈、Tomcat 与链路才是 → 多级缓存。多数「亿级」叙事里两者共存：**集群保数据层容量，多级化砍链路流量**。判断依据是压测里的分段耗时，不是感觉。

**Q2：本地缓存的一致性怎么保证？**

事件驱动失效（Canal → MQ → 广播删）为主，TTL 兜底为辅，整批失效优先用版本号前缀而不是逐 key 删除。要坦白承认：**只要有多副本就有不一致窗口，工程目标是把窗口压到业务可接受，不是消灭它**。若业务不能容忍任何陈旧，本地缓存就该退出（回到纯 Redis + 读写锁，见[一致性三档](/database/redis/scenarios#一致性三档)）。

**Q3：为什么第一层缓存放 Nginx 而不是直接上 CDN？**

静态资源和不常变的页面片段直接上 CDN 更前置；Nginx 层放的是「个性化但读多」的动态数据（带鉴权、按城市 / 类目聚合），CDN 覆盖不了（且 CDN 无法按业务事件失效）。两者是互补不是替代。

**Q4：Caffeine 的淘汰策略和 LRU 有什么不同？**

Caffeine 默认用 **W-TinyLFU**：窗口区（LRU）做短期缓冲，主区用**频率素描（Count-Min Sketch）**记录访问频率做准入判断，且频率计数**周期性衰减**。它同时解决了 LRU 的「缓存污染」（一次性遍历挤掉热点）和 LFU 的「老热点占位、新热点进不来」。**对使用者的实际影响是：命中率提升不是靠加大容量，而是靠访问分布本身有稳定性。**

**Q5：`expireAfterWrite` / `expireAfterAccess` / `refreshAfterWrite` 怎么选？**

`expireAfterWrite` 是默认选择（「最多陈旧 N 秒」的硬承诺）；`expireAfterAccess` 适合会话（访问即续命），**热点数据用它会永不失效**，要小心；`refreshAfterWrite` 把回源从请求路径上摘掉——请求立刻返回旧值、后台异步刷新，是读接口「不阻塞 + 尽快更新」的标准写法，但**必须与 `expireAfterWrite` 搭配**保证有硬过期。

**Q6：多级缓存上了之后命中率不达标，怎么排查？**

按层往下查：① Nginx `shared_dict` 是否写满（看命中率随时间的衰减曲线）；② key 是否过细（维度太多导致样本分散，每台机器的命中率都低）；③ 数据是否真的热点（长尾分布下任何缓存的命中率上限都不高）；④ TTL 是否过短（失效频率高于访问频率，缓存等于没有）；⑤ 版本号是否被频繁改写（整批失效过于频繁，等价于缓存不存在）。
