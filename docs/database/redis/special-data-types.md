# 特种类型：BitMap / HyperLogLog / GEO

五大基础结构之外，Redis 还有一批「为特定统计场景而生」的形态。它们的共同设计哲学：**放弃不必要的精度或通用性，换 2~3 个数量级的内存节省**。做选型时先问一句：业务要的到底是精确值，还是趋势？

## 一、BitMap：签到与布尔统计

BitMap 不是独立类型，是 String 的位视角——**一个 String 就是一个最多 2³² 位（512MB）的位数组**。所以 BitMap 的所有命令都以 `BIT` 开头，底层没有任何新结构。

### 1.1 签到场景的三个命令

```bash
SETBIT  sign:u1001:202609 8 1     # 9 月 9 日（offset=8）签到
GETBIT  sign:u1001:202609 8       # 单点查询
BITCOUNT sign:u1001:202609        # 本月签到总天数
BITPOS  sign:u1001:202609 0       # 第一个未签到位 → 算连续签到
```

1 亿用户的签到状态，按「用户 + 月份」拆 key，单个 key 30 位、1 亿个 key 合计约 **12MB**（1e8 位 = 12.5MB）。**为什么按用户拆而不是按天拆**：按用户拆才能用 `BITCOUNT` 直接算「本月签到几天」，按天拆（`sign:20260909` 存 1 亿用户的位）则能算「今天有多少人签到」——**key 的拆分方向由「你想聚合什么」决定**，两个方向都要就只能存两份。

连续签到的计算：`BITPOS key 0` 找到**第一个为 0 的位**，与当天 offset 比较即可，不需要拉全量数据。跨月连续签到要读相邻两个月的 key 拼接判断（`BITFIELD` 取跨字节的位段，或者直接读两个 key 的原始字节拼接）。

### 1.2 三个进阶命令

| 命令 | 用途 | 注意 |
|---|---|---|
| `BITCOUNT key [start end [BYTE\|BIT]]` | 区间统计 | **默认按字节计**（`BYTE`）。要按「第 5 到第 10 天」统计必须显式写 `BIT`（7.0+），否则 `BITCOUNT k 5 10` 统计的是第 5~10 个字节 = 第 40~87 位 |
| `BITOP AND\|OR\|XOR\|NOT dest k1 k2 ...` | 位图运算 | `NOT` 只接受一个源 key。典型用途：**活跃用户交集 / 并集**（`BITOP AND active:20260912 active:20260913` → BITCOUNT 得连续两天活跃人数）。**代价是它会创建一个新 key**，两个 12MB 的位图 AND 后结果也是 12MB |
| `BITFIELD key GET/SET/INCRBY u8/i16/... offset` | 把位数组当**定长整数数组**用 | 一个 String 里存 100 万个 8 位计数器，比 100 万个 String key 省下全部 key 开销。`OVERFLOW WRAP\|SAT\|FAIL` 决定溢出行为（默认 WRAP 回绕，`FAIL` 返回 nil 不回绕） |

`BITFIELD` 是 BitMap 里最被低估的一个：**它把「位数组」升级成了「任意位宽整数的紧凑数组」**——多字段联合编码、区间计数、紧凑计数器都能用它。

### 1.3 适用边界

- **位与实体必须能一一映射**。用户 id 连续（或能映射到连续区间）时高效；id 是 uuid / 雪花号且稀疏时，要在应用层建 `id → offset` 映射表，否则位空间浪费远超收益。
- **`SETBIT` 的 offset 上限是 2³²−1**，写一个超大 offset 会让 String 立即膨胀到那个长度（Redis 会补零）。**别拿用户 id 的绝对值当 offset**——一个 19 位雪花 ID 直接当 offset 需要 2³⁶ 字节，直接 OOM。
- **`BITCOUNT` 是 O(N)**（按字节扫），单 key 千万位级别要留意；需要频繁统计时靠「按用户 / 按天拆分 + 只统计小 key」控制成本。

## 二、HyperLogLog：亿级 UV 的近似去重

统计 UV（独立访客）：Set 去重精确但内存与成员数线性——1 亿访客约需数 GB；HyperLogLog 固定 **12KB**，误差标准差 **0.81%**。

```bash
PFADD   uv:20260912 "ip:1.2.3.4" "ip:5.6.7.8"
PFCOUNT uv:20260912                          # 近似 UV
PFCOUNT uv:20260912 uv:20260911              # 多 key = 临时合并后计数
PFMERGE uv:202609 uv:20260912 uv:20260911    # 合并出月 UV（写入目标 key）
```

### 2.1 12KB 是怎么算出来的

对元素哈希后取前缀做「抛硬币」观测：连续 0 的位数越长说明样本越多。为了提高精度，把哈希前 14 位当**桶号**，把剩下位数的「最长前导零 +1」存进桶：

```
位数分配： | 14 bit 桶号（2^14 = 16384 个桶） | 剩余位用于观测前导零 |
内存：      16384 个桶 × 6 bit = 98304 bit = 12288 B ≈ 12KB
误差：      标准误差 ≈ 1.04 / √16384 = 1.04 / 128 ≈ 0.81%
```

**误差与内存是一组绑死的数**：桶数加密 4 倍，内存变 4 倍，误差只减半（误差 ∝ 1/√桶数）。所以「HLL 为什么不用 20KB 把误差降到 0.3%」的答案是：**不值得**——把误差从 0.81% 降到 0.4% 要多花 3 倍内存，而业务对 UV 的容忍度通常在 5% 以上。

### 2.2 两个实现细节（面试加分点）

- **稀疏编码 → 密集编码**：刚创建时 HLL 只有少量非零桶，Redis 用**稀疏表示**（一段段 `ZERO/XZERO/VAL` 指令）省内存，通常只占几十字节；当稀疏表示超过阈值（约 3000 字节）或 `PFADD` 触发的转换条件满足时，才转成固定的 12KB 密集编码。**所以「HLL 一创建就是 12KB」是错的**，小基数的 HLL 其实极小。
- **`PFCOUNT` 单 key 时走缓存**：Redis 4.0+ 在 HLL 对象头里缓存了基数，**只要没被 `PFADD` 改过就直接返回缓存值（O(1)）**；多 key 的 `PFCOUNT` 不能走缓存，需要临时 merge（O(N)，N 是 key 数）后计算，开销显著。高频统计多 key 合并值时，应该**先用 `PFMERGE` 落一个中间 key**，再对它单独 `PFCOUNT`。

### 2.3 边界：HLL 不能做什么

| 做不到 | 原因 | 替代 |
|---|---|---|
| 取出成员明细 | 只存桶的统计量，原始元素哈希后即丢弃（**不可逆**） | Set / BitMap |
| 精确计数 | 本身是概率估算 | `SCARD` / `BITCOUNT` |
| 减去一个元素 | **没有 `PFREM`**，只有加法 | 用 Set，或按时间分桶后合并 |
| 精确名次（「第 100 万访客」） | 估出来的数没有可比顺序 | 计数器 + 唯一索引 |

## 三、GEO：地理位置与附近检索

GEO 底层是 SortedSet：把经纬度经 GeoHash 编码为 **52 位交错整数**当 score，编码后**相邻的地理位置 score 也相邻**，于是「附近的人」变成 ZSet 的范围查询：

```bash
GEOADD      shop 116.48 39.99 shop:1001
GEODIST     shop shop:1001 shop:1002 km           # 两点距离
GEOSEARCH   shop FROMLONLAT 116.48 39.99 BYRADIUS 5 km ASC COUNT 20
GEOSEARCHSTORE result shop FROMMEMBER shop:1001 BYRADIUS 3 km   # 结果落到另一个 ZSet
```

### 3.1 52 位是怎么来的

```
经度范围 [-180, 180]  → 26 bit  →  精度约 0.6 m（赤道）
纬度范围 [-85.0511, 85.0511]  → 26 bit   ← 注意不是 ±90
两者交错（interleave）拼成 52 bit 整数  →  作为 ZSet 的 score
```

两个必须记住的细节：

1. **纬度上限是 ±85.05112878**，不是 ±90——这是 Web Mercator 投影的有效范围（超出部分在墨卡托平面上趋于无穷）。**给 Redis 传超出范围的纬度会被拒绝**，从别的系统（GPS 原始数据）导入时要先做校验。
2. **交错编码让「前缀相同 = 同一块格子」**：这就是 GeoHash 的「递进网格」性质。缩短编码位数 = 放大格子范围。这个思想是通用的——ES 的 `geohash_grid` 聚合、H3、S2 都建立在同一性质上。

### 3.2 「附近」为什么需要九宫格

一个直接的想法是：把查询点编码成格子，取该格子的 score 区间。**但这会漏掉边界外的邻居**——目标点可能在相邻格子里，距离却比本格内某些点更近。

Redis 的处理是**同时计算查询点所在的格子及其 8 个邻居格子（九宫格），对这 9 个区间各做一次 ZSet 范围查询，再合并后按真实距离过滤排序**。所以「GEO 查附近」的实际成本是：

```
9 次 O(log N + M) 的范围扫  +  候选集上的 Haversine 距离计算与排序
```

Redis 6.2 起 `GEOSEARCH` 会做优化——**当半径明显小于格子尺寸时才扩展邻居**，半径很大时格子本身已经覆盖，就不需要九宫格。距离计算用的是 **Haversine 公式**（把地球当球体），所以长距离会与真实椭球距离有千分之几的偏差。

### 3.3 使用边界

- **没有独立的删除命令**，用 `ZREM`（本质就是 ZSet）；也没有「只查成员坐标」的命令，用 `ZSCORE` 拿回编码值后需要应用层解码（或用 `GEOPOS`）。
- **不支持范围之外的查询语义**：按「行政区」、按「多边形的围栏」检索它做不到——那是 PostGIS / MongoDB GeoJSON 的地盘。
- **成员数线性占内存**，且 score 是 8 字节 double → 每个成员约 100 字节级（受 `zset-max-listpack-entries` 影响）。百万级成员约数十 MB，量级上没问题；**但它是全量内存的，不适合「附近的历史轨迹点」这类无限增长的场景**。

## 四、SortedSet 与 Set：点赞、关注与榜单

- **点赞列表**：`SADD like:blog:1001 u1 u2`（去重天然满足）、`SISMEMBER` 判断是否点过、`SCARD` 计数（**O(1)**，Set 内部维护了 size）。
- **点赞排行榜**：需要「最先点赞」排序时升 ZSet：`ZADD/ZINCRBY like:blog:1001 <ts> u1`，`ZREVRANGE ... LIMIT 0 10` 拿前 10。
- **共同关注**：`SINTER follow:u1 follow:u2`——把「关注」存 Set 而不是 DB 关联表，就是为了让交集运算下推到 Redis（**O(N) 内存运算 vs DB 的 JOIN**）。Redis 7.0+ 可用 `SINTERCARD numkeys follow:u1 follow:u2 LIMIT 1000`——**只要交集大小不需要成员明细**（「你和 TA 有几个共同好友」），`SINTERCARD` 免去构造结果集的成本。
- **Set 的编码会悄悄变**：小整数集合用 `intset` / `listpack` 紧凑存储，超过阈值（`set-max-intset-entries` 512 或 `set-max-listpack-entries` 128）才转成 `hashtable`。**转换是单向的**——一个 10 万元素的 Set 删到只剩 10 个，编码仍是 `hashtable`，内存不会退回。排查「为什么这个 Set 占这么多内存」时要先看 `OBJECT ENCODING`。
- **大 Set 的删除代价**：`DEL` 一个百万元素的 Set 会阻塞主线程（逐个释放），要用 `UNLINK` 做异步删除——同样适用于大 ZSet / Hash。见[最佳实践](/database/redis/best-practices)。

## 五、统计口径的三个陷阱

这三个问题不是 Redis 的坑，是**统计本身的坑**——但因为用了 Redis 的近似结构，它们会被放大：

1. **「去重口径」要在需求方确认**：UV 按 IP、按设备、按账号去重，结果可能差一倍。HLL 是「按你 `PFADD` 进去的元素」去重——**口径错了，Redis 算得再准也没用**。
2. **跨周期去重的正确姿势是「查的时候合并」，不是「累加」**：月 UV 不能用「每天 UV 相加」（同一个人会被算 30 次），必须 `PFMERGE` 所有日 key 再 `PFCOUNT`。所以**日粒度 key 必须保留**，不能只留月 key——这是 HLL 场景最常见的设计错误。
3. **近似结构的「不可撤回」要与业务对齐**：HLL 没有 `PFREM`，BitMap 的 `SETBIT 0` 只是把位清掉（BITCOUNT 会变，但「历史曾签到」的信息丢了）。凡是业务上需要「取消 / 回滚 / 明细核对」的统计，**要么用精确结构，要么在流水层保留原始记录**——Redis 里的统计值只当作「大盘展示」。

## 六、统计场景选型速查

| 需求 | 方案 | 精度 | 内存量级 | 关键约束 |
|---|---|---|---|---|
| 每日签到 / 连续签到 | BitMap | 精确 | 1 亿用户 × 1 月 ≈ 12MB | id 要能映射到连续 offset |
| 活跃用户交集 / 并集 | BitMap + `BITOP` | 精确 | 与位空间线性 | 运算会产生新 key |
| 紧凑多字段计数器 | `BITFIELD` | 精确 | 位宽 × 元素数 | 位宽与偏移量要预先规划 |
| UV / 搜索量趋势 | HyperLogLog | ±0.81% | **恒定 12KB/key** | 无法取明细、无法做减法 |
| 在线名单 / 点赞去重 | Set | 精确 | 与成员数线性 | 大 Set 删除要用 `UNLINK` |
| 共同关注「有几个」 | `SINTERCARD` | 精确 | 不落中间结果 | 7.0+ |
| 排行榜 / 延迟队列 | ZSet | 精确 | 与成员数线性 | 元素多时注意 listpack→skiplist 转换 |
| 附近的人 / 商户 | GEO（ZSet） | 网格近似 | 与成员数线性 | 纬度 ±85.05；重查询是 9 次范围扫 |

**一句话判据**：**「要精确成员 → Set / BitMap；只要数量 → HyperLogLog；要顺序 → ZSet；要二维邻近 → GEO。」** 精度换内存是这一节的唯一主题。

## 七、面试问答

**Q1：1 亿用户的签到系统怎么设计？**

按「用户 + 月份」拆 BitMap（`sign:{uid}:{yyyyMM}`）：`SETBIT` 记录、`BITCOUNT` 月统计、`BITPOS 0` 求连续签到。合计约 12MB。id 不连续就先建 `id → offset` 映射。跨月连续签到要读相邻两个月 key 拼接判断。**追问「今天有多少人签到」时要点出：那需要另一个方向的拆分（按天拆 key），key 的拆分方向由聚合维度决定。**

**Q2：HyperLogLog 为什么 12KB 就能数到亿级？**

16384 个桶，每桶 6 bit 记录该桶观测到的「最长前导零」。14 bit 哈希前缀选桶 → 16384 × 6 bit ≈ 12KB。基数越大，各桶出现长前导零的概率分布越能反映规模，调和平均消除离群值。**误差标准差的公式是 `1.04/√m`，m=16384 时约 0.81%**。

**Q3：HLL 和 Set 怎么选？**

先问「要不要明细」。要精确 id 集合（风控、对账、去重名单）→ Set；只要数量趋势（UV 大盘）→ HLL。**注意 HLL 没有删除操作**，若业务需要「减去某个元素」或「查某个人是否算过」，HLL 直接出局。

**Q4：GEO 查「附近的」为什么快？九宫格是干什么的？**

GeoHash 把二维坐标交错编码成一维 52 位整数，附近 = score 区间查询，落到 ZSet 的 O(log N + M) 范围扫。单格查询会漏掉格子边界外的邻近点，所以 Redis 会同时查查询点及其 8 个邻居格子（九宫格），再对候选集做 Haversine 精确距离过滤与排序。6.2 起当半径远大于格子尺寸时会跳过九宫格扩展。

**Q5：`BITCOUNT` 按天统计时踩过什么坑？**

`BITCOUNT key start end` **默认是按字节**（`BYTE`），不是按位。要按「第 5 到第 10 天」统计必须显式写 `BITCOUNT key 5 10 BIT`（7.0+）。按字节理解时会算成第 40~87 位，结果完全不对——这是 BitMap 场景最容易静默出错的一处。

**Q6：为什么 BitMap 不能用雪花 ID 直接当偏移量？**

`SETBIT` 的 offset 上限是 2³²−1，而写一个超大 offset 会让 String **立即按该长度分配并对齐补零**。一个 19 位雪花 ID 当 offset 会要求 TB 级内存，直接 OOM。必须先做 `id → 连续 offset` 映射（用 Hash 或 DB 维护）。

**Q7：月 UV 为什么不能用每天的 UV 相加？**

同一个人跨天会重复计数。正确做法是保留日粒度 HLL key，查询时 `PFMERGE` 出月 key 再 `PFCOUNT`。设计上要保证**日 key 不被裁剪**——只留月 key 的写法在需要跨周期统计时会彻底无解。
