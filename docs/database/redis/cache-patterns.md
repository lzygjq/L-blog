# 缓存模式：三大问题与一致性

这一篇是 Redis 面试出现率最高的内容。要点不是背「穿透/击穿/雪崩」三个名词，而是理解它们同根同源：**缓存层与存储层的数据永远存在时间差，所有方案都在管理这个时间差的后果**。

## 一、Cache Aside：旁路缓存的读写路径

应用同时持有缓存和数据库两条路径，缓存只是旁路：

```
读：请求 → 查缓存 ─命中→ 返回
              └未命中→ 查 DB → 回填缓存（带 TTL）→ 返回
写：请求 → 更新 DB → 删除缓存
```

两个必须想清楚的细节：

1. **为什么写是「删缓存」而不是「更新缓存」**：更新缓存在并发写下会出现后写的旧值覆盖先写的新值（A 更新 DB=1，B 更新 DB=2，B 先写缓存 2，A 后写缓存 1，缓存永久停在 1）。删除是幂等的，下次读自然回填最新值。
2. **为什么先更新 DB 再删缓存**：反过来「先删缓存再更新 DB」的窗口里，一个读请求会把旧值重新填回缓存，且 TTL 内不再自愈。

## 二、一致性残留与两层兜底

「先更新 DB 再删缓存」也有缝隙：删缓存失败，或读写交错（读请求在旧值上查完 DB，写请求完成更新+删除，读请求回填旧值）。概率极低但非零，两层兜底：

| 方案 | 做法 | 适用 |
|---|---|---|
| 延迟双删 | 删缓存 → 更新 DB → 睡眠 N ms（覆盖一次读回填的耗时）→ 再删一次 | 写后强一点要求的场景，N 要按业务读耗时估 |
| **Canal 订阅 binlog 异步删除**（推荐） | DB 变更由 Canal 捕获，MQ 通知删除/更新缓存 | 把一致性与业务代码解耦，漏删兜底交给 binlog 的完整性 |

Canal 链路与本站[数据仓库板块的 Canal 同步](/bigdata/canal/)是同一套基础设施，一套 Canal 可以同时服务「缓存失效」和「数仓入仓」两个下游。此外，**给缓存设 TTL 是最终一致的最后一道闸**：哪怕所有主动失效全失败，TTL 到期也会自愈。TTL 长短 = 不一致窗口上限，按业务容忍度定。

## 三、缓存穿透：查「不存在的数据」

特征：请求的 key 在缓存和 DB 里都**永远不存在**（恶意伪造 id），每次都穿透到 DB。与「缓存未命中」的区别：未命中是一次性的，穿透是持续性的。

| 方案 | 做法 | 权衡 |
|---|---|---|
| 缓存空值 | 查不到也缓存 `""`/null，短 TTL（如 60s） | 简单可靠；占少量内存；空值期间该 key 真实产生了也读不到（TTL 换来自愈） |
| 布隆过滤器 | 启动时把全量合法 id 灌入过滤器，查询先过它 | 内存极省；有误判率（存在性判断「可能存在」）；删除困难，适合 id 集合稳定的场景 |
| 接口校验 | id 格式/范围/鉴权拦截 | 第一道防线，和上面两个组合使用 |

**选型经验**：id 可枚举（如商品 id 连续）→ 布隆过滤器；不可枚举或偶尔有空值 → 缓存空值足够。

## 四、缓存击穿：热点 key 失效的瞬间

特征：某个**热点** key 过期的一瞬间，海量并发同时 miss、同时压向 DB。与穿透的区别：数据是存在的，问题是「重建缓存」这个动作被并发放大。

| 方案 | 做法 | 权衡 |
|---|---|---|
| 互斥锁 | miss 后先 `SET lock NX EX` 抢锁，抢到的查 DB 回填，抢不到的睡眠重试 | DB 只承受一次重建；未抢到锁的请求有等待延迟；要处理锁超时（见[分布式锁](/database/redis/lock-and-mq)） |
| 逻辑过期 | 缓存**永不设 TTL**，Value 里带逻辑过期时间；读到「已逻辑过期」的值，异步线程重建，当前请求先返回旧值 | 无等待、无阻塞；短暂返回旧数据（可容忍陈旧的热点才适用）；内存不释放 |

**组合拳**：互斥锁保证 DB 不被打穿，逻辑过期保证用户不等待，按「DB 安全 > 用户体验」选前者，「体验 > 秒级新鲜度」选后者。

## 五、缓存雪崩：大面积同时失效

特征与击穿的区别：**范围**——大量 key 同时失效，或 Redis 整体不可用，DB 被整体冲垮。三条对策分别对应三种成因：

1. **TTL 打散**：过期时间加随机量（`base + random(0, 300s)`），防止同一批预热门市同时到期。
2. **高可用**：主从 + 哨兵自动切换（见[持久化与集群](/database/redis/ha-cluster)），防止 Redis 宕机型雪崩。
3. **多级缓存 + 熔断限流**：Nginx 本地缓存 + 进程缓存挡在 Redis 前面（见[多级缓存](/database/redis/multilevel-cache)），DB 前置限流兜底——Redis 全挂时保住 DB 不死，宁可降级不可崩盘。

## 六、三问题对照速查

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 数据是否存在 | 不存在 | 存在（热点） | 存在（大批） |
| 范围 | 单 key 持续 | 单 key 瞬时 | 大范围 |
| 根因 | 恶意/异常请求绕过缓存 | 重建缓存被并发放大 | 失效时间扎堆/实例宕机 |
| 首选方案 | 布隆过滤器或缓存空值 | 互斥锁/逻辑过期 | TTL 随机 + 高可用 + 限流 |

## 七、面试问答

**Q: 为什么是「先更新数据库，再删除缓存」，能反过来吗？**
反过来会在删缓存与写库之间留下旧值回填窗口且不自愈；正序的缝隙只剩「删失败」和极小概率读写交错，用 TTL + Canal 异步删兜底即可。

**Q: 缓存空值和布隆过滤器怎么选？**
看 id 集合是否可枚举、是否会删除。可枚举且稳定 → 布隆；否则空值 + 短 TTL 更简单。两者可叠加：布隆挡 90%，穿透进来的再被空值兜住。

**Q: 逻辑过期返回旧值，业务能接受吗？**
看业务。营销页、榜单类可容忍分钟级陈旧；库存、余额类不行——所以库存类热点不用逻辑过期，用互斥锁 + DB 层防超卖（见[锁](/database/redis/lock-and-mq)）双保险。
