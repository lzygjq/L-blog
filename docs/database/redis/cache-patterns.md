# 缓存模式：三大问题与一致性

这一篇是 Redis 面试出现率最高的内容。要点不是背「穿透/击穿/雪崩」三个名词，而是理解它们同根同源：**缓存层与存储层的数据永远存在时间差，所有方案都在管理这个时间差的后果**。

## 一、Cache Aside：旁路缓存的读写路径

应用同时持有缓存和数据库两条路径，缓存只是旁路：

```
读：请求 → 查缓存 ─命中→ 返回
              └未命中→ 查 DB → 回填缓存（带 TTL）→ 返回
写：请求 → 更新 DB → 删除缓存
```

两个必须想清楚的细节：

1. **为什么写是「删缓存」而不是「更新缓存」**：更新缓存在并发写下会出现后写的旧值覆盖先写的新值（A 更新 DB=1，B 更新 DB=2，B 先写缓存 2，A 后写缓存 1，缓存永久停在 1）。删除是幂等的，下次读自然回填最新值。
2. **为什么先更新 DB 再删缓存**：反过来「先删缓存再更新 DB」的窗口里，一个读请求会把旧值重新填回缓存，且 TTL 内不再自愈。

## 二、一致性：四档选型，代价递增 {#一致性四档}

「先更新 DB 再删缓存」也有缝隙：删缓存失败，或读写交错（读请求在旧值上查完 DB，写请求完成更新+删除，读请求回填旧值）。概率极低但非零。按「业务能容忍多久不一致」分四档：

| 档 | 方案 | 做法 | 不一致窗口 | 代价 |
|---|---|---|---|---|
| 1（默认） | 先更库后删缓存 + TTL | 写路径删缓存；读回填时带 TTL | ≤ TTL | 零额外组件 |
| 2 | 延迟双删 | 删缓存 → 更新 DB → 睡眠 N ms（覆盖一次读回填的耗时）→ 再删一次 | 更小，但仍非零 | N 靠估算；睡眠占用线程 |
| 3（推荐） | Canal 订阅 binlog 异步删 | DB 变更由 Canal 捕获，MQ 通知删除/更新缓存 | 毫秒级 | 多两个中间件 |
| 4 | Redisson 读写锁 | 读加共享锁（读读不互斥），写加排他锁（写时阻塞读写） | 无（强一致） | 吞吐骤降 |

**第 3 档为什么是工程标准解**：把失效逻辑从业务代码里彻底搬走——写业务只负责写库，缓存的删除由 binlog 事件驱动。业务漏写失效调用这个最常见的 bug 直接被消灭，因为 binlog 不会漏。代价是链路变长（Canal + MQ），且事件可能乱序（要靠时间戳/版本号比较），本地缓存仍需 TTL 兜底。

Canal 链路与本站[数据仓库板块的 Canal 同步](/bigdata/canal/)是同一套基础设施，一套 Canal 可以同时服务「缓存失效」和「数仓入仓」两个下游。

**第 4 档什么时候才值得**：库存、余额、券码这类「读到旧值就是事故」的场景。它的本质是**用分布式锁把「读缓存」和「写库」串行化**，所以锁粒度就是 key，QPS 被锁串行化——只适合热点范围极小、单次操作极轻的场景。注意它也有边界：拿到写锁后仍然是「更新 DB + 删缓存」，只是这段时间没有读者能回填旧值。

**最后一道闸是 TTL**：哪怕前面所有主动失效全部失败，TTL 到期也会自愈。**TTL 长短 = 不一致窗口的上限**，按业务容忍度定——这一条是四档方案的共同底座。

## 三、缓存穿透：查「不存在的数据」

特征：请求的 key 在缓存和 DB 里都**永远不存在**（恶意伪造 id），每次都穿透到 DB。与「缓存未命中」的区别：未命中是一次性的，穿透是持续性的。

| 方案 | 做法 | 权衡 |
|---|---|---|
| 缓存空值 | 查不到也缓存 `""`/null，短 TTL（如 60s） | 简单可靠；占少量内存；空值期间该 key 真实产生了也读不到（TTL 换来自愈） |
| 布隆过滤器 | 启动时把全量合法 id 灌入过滤器，查询先过它 | 内存极省；有误判率（存在性判断「可能存在」）；删除困难，适合 id 集合稳定的场景 |
| 接口校验 | id 格式/范围/鉴权拦截 | 第一道防线，和上面两个组合使用 |

**选型经验**：id 可枚举（如商品 id 连续）→ 布隆过滤器；不可枚举或偶尔有空值 → 缓存空值足够。

⚠️ **缓存空值的 TTL 必须短**。它是「用一个 key 换一次 DB 查询」的交易，TTL 设长了，攻击者用大量伪造 id 就能把 Redis 内存撑爆——穿透没打垮 DB，反倒撑爆了缓存。

## 四、布隆过滤器：原理、参数与边界 {#布隆过滤器}

穿透的根因是「查一个根本不存在的东西」。布隆过滤器就是那个能在访问缓存之前就断定「这个 id 不可能存在」的判断器。

### 1. 结构：一个位数组 + k 个哈希函数

```
写入 x：h1(x)=2, h2(x)=5, h3(x)=9  → bit[2]=bit[5]=bit[9]=1

查询 y：h1(y)=2, h2(y)=5, h3(y)=7  → bit[7]=0  → y 一定不存在
查询 z：h1(z)=2, h2(z)=5, h3(z)=9  → 全为 1    → z 可能存在（也可能是 x 的位碰巧全命中）
```

三条结论，第三点是它最大的限制：

- **说不存在，一定准**（一票否决：k 个位置里任意一个是 0，说明从没写入过）。
- **说存在，可能不准**（误判 / false positive）——这是它唯一的错误方向，也正是它能做到极小内存的原因（不存元素本身，只存「有没有被哈希过」）。
- **没有删除操作**：把某一位清 0 会连坐所有共享该位的元素。真需要删就用**计数布隆过滤器**（每位换成计数器，删除时减一）或**布谷鸟过滤器**（支持删除、空间效率更高）。

### 2. 误判率由什么决定

m（位数组大小）、n（元素个数）、k（哈希函数个数）三者共同决定误判率。直觉是：**数组越小 / 元素越多 → 位被填得越满 → 误判越多**；而 k 不是越大越好，哈希次数多了会让位数组更快被填满，反而推高误判率。

工程口径不需要背公式，记住**位数组按元素数的 10 倍左右开、k 取 6~8**，误判率就落在千分之几——对「挡穿透」这个用途绰绰有余。剩下那千分之几会漏到 DB，正好由上一节的缓存空值兜住。

### 3. 两个容易被忽略的边界

- **只能加不能删，所以「DB 里的数据被删了」它并不知道** → 会出现「过滤器说存在、实际已删」的漏判。要么接受（放它去查一次 DB、拿到空值后被缓存空值接管），要么定期重建。
- **重建成本不低**：全量预热要遍历一遍 DB，大表就是一次全表扫。所以它适合 **id 集合稳定**的场景（商品、用户、门店），不适合频繁增删的场景。

### 4. 落地方式

| 实现 | 说明 |
|---|---|
| Redisson `RBloomFilter` | 分布式共享同一份过滤器，底层是 Redis BitMap，多实例天然一致 |
| Guava `BloomFilter` | 进程内，每实例一份副本 → 预热重复、内存浪费、各实例状态不一致（多实例场景不推荐） |
| 自己用 `SETBIT`/`GETBIT` 拼 | 位数组本质就是 String 的位视角（见[特种类型](/database/redis/special-data-types)），适合学习与单机验证 |

## 五、缓存击穿：热点 key 失效的瞬间

特征：某个**热点** key 过期的一瞬间，海量并发同时 miss、同时压向 DB。与穿透的区别：数据是存在的，问题是「重建缓存」这个动作被并发放大。

| 方案 | 做法 | 权衡 |
|---|---|---|
| 互斥锁 | miss 后先 `SET lock NX EX` 抢锁，抢到的查 DB 回填，抢不到的睡眠重试 | DB 只承受一次重建；未抢到锁的请求有等待延迟；要处理锁超时（见[分布式锁](/database/redis/lock-and-mq)） |
| 逻辑过期 | 缓存**永不设 TTL**，Value 里带逻辑过期时间；读到「已逻辑过期」的值，异步线程重建，当前请求先返回旧值 | 无等待、无阻塞；短暂返回旧数据（可容忍陈旧的热点才适用）；内存不释放 |

**组合拳**：互斥锁保证 DB 不被打穿，逻辑过期保证用户不等待，按「DB 安全 > 用户体验」选前者，「体验 > 秒级新鲜度」选后者。

## 六、缓存雪崩：大面积同时失效

特征与击穿的区别：**范围**——大量 key 同时失效，或 Redis 整体不可用，DB 被整体冲垮。三条对策分别对应三种成因：

1. **TTL 打散**：过期时间加随机量（`base + random(0, 300s)`），防止同一批预热门市同时到期。
2. **高可用**：主从 + 哨兵自动切换（见[持久化与集群](/database/redis/ha-cluster)），防止 Redis 宕机型雪崩。
3. **多级缓存 + 熔断限流**：Nginx 本地缓存 + 进程缓存挡在 Redis 前面（见[多级缓存](/database/redis/multilevel-cache)），DB 前置限流兜底——Redis 全挂时保住 DB 不死，宁可降级不可崩盘。

**降级是三类问题的通用保底手段**：穿透、击穿、雪崩的终极方案都会回到「限流 + 返回兜底值」。宁可显示「稍后重试」，也不能让 DB 被打穿——DB 挂了是整个系统挂，缓存挂了至少还能降级。

## 七、三问题对照速查

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 数据是否存在 | 不存在 | 存在（热点） | 存在（大批） |
| 范围 | 单 key 持续 | 单 key 瞬时 | 大范围 |
| 根因 | 恶意/异常请求绕过缓存 | 重建缓存被并发放大 | 失效时间扎堆/实例宕机 |
| 首选方案 | 布隆过滤器或缓存空值 | 互斥锁/逻辑过期 | TTL 随机 + 高可用 + 限流 |

## 八、面试问答

**Q: 为什么是「先更新数据库，再删除缓存」，能反过来吗？**
反过来会在删缓存与写库之间留下旧值回填窗口且不自愈；正序的缝隙只剩「删失败」和极小概率读写交错，用 TTL + Canal 异步删兜底即可。

**Q: 布隆过滤器的原理是什么？为什么能 100% 拦掉不存在的请求？**
底层是位数组，写入时用 k 个哈希算出 k 个位置置 1；查询时重算，**只要有一位是 0 就一定不存在**——这个方向是确定的，所以「不存在的请求」能被 100% 拦住；但反过来，全是 1 只是「可能存在」，会有误判。代价是不能删除（要删得用计数布隆或布谷鸟过滤器）。

**Q: 缓存空值和布隆过滤器怎么选？**
看 id 集合是否可枚举、是否会删除。可枚举且稳定 → 布隆；否则空值 + 短 TTL 更简单。两者可叠加：布隆挡 90%，穿透进来的再被空值兜住。

**Q: 缓存一致性有几种方案？**
按业务容忍度分四档：普通业务「先更库后删缓存 + TTL」；读多写少加 Canal 订阅 binlog 异步失效（推荐，业务零侵入）；要求更强的用延迟双删；涉及库存余额这类不许读旧值的才上 Redisson 读写锁，代价是吞吐。**所有档的共同底座是 TTL 兜底**。

**Q: 逻辑过期返回旧值，业务能接受吗？**
看业务。营销页、榜单类可容忍分钟级陈旧；库存、余额类不行——所以库存类热点不用逻辑过期，用互斥锁 + DB 层防超卖（见[锁](/database/redis/lock-and-mq)）双保险。
