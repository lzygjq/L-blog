# 场景地图与选型叙事

前面 8 篇是纵向拆解：一个主题讲透。这一篇横向收口，回答两个问题——**遇到一个业务需求，该用 Redis 的哪一部分、边界在哪**；以及**这些选型在面试里怎么讲清楚**。

## 一、用法地图：Redis 在业务里都干什么 {#用法地图}

「你们项目里 Redis 用来做什么」几乎是最高频的开场题。答案不是罗列五种数据类型，而是**业务问题 → 用哪个结构 → 关键点**：

| 用法 | 解决什么问题 | 用什么 | 关键点 |
|---|---|---|---|
| 缓存 | 热点数据减轻 DB 压力 | String / Hash | 必须配 TTL；穿透/击穿/雪崩要兜底（见[缓存模式](/database/redis/cache-patterns)） |
| 分布式锁 | 并发下互斥，防超卖 | `SET NX EX` 或 Redisson | 原子加锁 + 唯一值 + Lua 释放 + 自动续期（见[分布式锁](/database/redis/lock-and-mq)） |
| 原子计数 | 点赞数、阅读量、库存余量 | String `INCR/DECR` | 单命令原子，天然无锁 |
| 会话与令牌 | 登录凭证、验证码 | String + TTL | 过期自动失效，不用自己清理 |
| 消息队列 | 削峰、异步解耦 | List `LPUSH/BRPOP` 或 Stream | 要可靠投递用 Stream（有 ACK 和消费者组）；PubSub 不持久化、离线即丢 |
| 延迟队列 | 定时关单、延迟通知 | ZSet（score = 执行时间戳） | 轮询 `ZRANGEBYSCORE 0 now` 取到期任务，取出时 `ZREM` 保证只被一个消费者拿到 |
| 榜单与统计 | 排行榜、UV、签到 | ZSet / HyperLogLog / BitMap | 精度可让就让（见[特种类型](/database/redis/special-data-types)） |

一句话口径：**「热点数据做缓存、并发扣减加锁、计数和令牌用原子命令、异步和延迟用 List/ZSet/Stream。」** 面试官若追问，就顺着表里任一行往下展开——这比背「String/Hash/List/Set/ZSet」高一个层次，因为它是从**问题**出发而不是从**结构**出发。

## 二、一致性：三档选型，代价递增 {#一致性三档}

缓存与 DB 的一致性没有银弹，只有「业务能容忍多久」的取舍：

| 档 | 业务特征 | 方案 | 不一致窗口 |
|---|---|---|---|
| 普通 | 商品详情、文章内容，容忍秒级陈旧 | 先更库后删缓存 + TTL | ≤ TTL |
| 热点 | 首页榜单、活动页，读极多写极少 | 上面 + Canal 订阅 binlog 异步失效 | 毫秒级 |
| 强一致 | 库存、余额、券码，读到旧值就是事故 | Redisson 读写锁（写时阻塞读写） | 无（代价是吞吐骤降） |

选型口诀：**「能容忍陈旧就用 TTL 兜底，读多写少加 Canal，涉及钱和库存才上锁。」** 四档方案的完整做法、延迟双删的位置、以及 TTL 为什么是共同的最后一道闸，见[缓存模式](/database/redis/cache-patterns)。

## 三、容量与集群：三套方案的分界线 {#集群边界}

| 方案 | 组成 | 解决的问题 | 适用规模 |
|---|---|---|---|
| 主从 | 1 主 N 从 | 读并发 + 数据冗余 | 单节点内存 ≤ 10GB |
| 哨兵 | 主从 + 3 哨兵 | 在主从之上加自动故障转移 | 中小规模，要求高可用 |
| 分片集群 | 多组主从，16384 槽分布 | 海量存储 + 高并发写 | TB 级数据 |

演进依赖不能跳：**持久化是主从全量同步的基础，主从是哨兵的前提**，而分片集群里每个分片自己也可以有从库——三套方案是叠加关系，不是替代关系。机制细节见[持久化、主从与集群](/database/redis/ha-cluster)。

实践口径：**「中等规模用主从 + 哨兵，单节点内存控制在 10G 以内；数据量再涨就上分片集群，或者按业务拆成独立实例。」** 后一种是很多团队的真实做法——按业务隔离实例，故障域小、扩容简单，代价是机器利用率低、运维实例变多。**说出这个取舍，比只答「我们用了集群」更能体现判断力。**

## 四、把选型讲成项目故事 {#项目叙事}

技术点再熟，面试官最后总会落到「你项目里怎么用的」。叙事骨架只有五步：

```
业务背景 → 遇到的问题 → 为什么这么选 → 兜底方案 → 结果与代价
```

以缓存一致性为例的完整口径：

> 「商品详情是典型读多写少，但对实时性要求不高，所以用**先更新库再删缓存 + TTL 兜底**。后来运营改价后用户要等 TTL 才看到，就上了 **Canal 监听 binlog 异步失效**，改成毫秒级，而且业务代码零侵入。抢券库存这类不能读旧值，我们用 **Redisson 读写锁**保证写时阻塞读——代价是这块 QPS 上不去，所以它只用在库存这么小的热点范围上。」

同样的骨架换成任意一个用法都成立。**关键是把「取舍」说出来**：只讲「我用了 Redis 缓存」是背书；讲出「为什么不用另一个方案、代价是什么、我为此做了什么兜底」才是工程判断。

### 常见追问的准备清单

把下面这些数字和边界记熟，追问就不慌：

| 追问 | 要能立刻答出 |
|---|---|
| QPS 能到多少？ | 单实例 10 万级；瓶颈通常在网络带宽与单实例内存，不是 CPU |
| 缓存怎么失效？ | 写路径删缓存 + TTL；热点用 Canal 订阅 binlog 异步失效 |
| 锁怎么保证不误删？ | 值存唯一标识，释放时用 Lua 先校验再删 |
| 集群怎么分数据？ | `CRC16(key) % 16384` 落槽；跨槽多 key 靠 hash tag |
| 为什么不用本地缓存？ | 多实例一致性难保证；本地缓存是 Redis 前面的「热上热」，不是替代品（见[多级缓存](/database/redis/multilevel-cache)） |
| 数据丢了怎么办？ | 混合持久化（RDB 全量 + AOF 增量），启动优先用 AOF 恢复 |
| 热 key 打满一个节点怎么办？ | 拆 key 加随机后缀分散、本地缓存挡一层、或者读写分离扩从库 |
| 内存满了怎么办？ | `allkeys-lru` 淘汰冷数据，剩下的自然就是热点 |

## 五、面试口径

- **使用场景**：热点缓存、并发锁、原子计数、会话令牌、异步队列、延迟任务——先一句「缓存 + 锁 + 队列」概括，再按追问展开。
- **选型原则**：先问业务的容忍度（能陈旧多久、能不能丢、能否降级），再定方案；**所有缓存必须有 TTL 兜底**。
- **集群口径**：中小规模主从 + 哨兵、单节点 ≤10G；TB 级上分片集群；也可以按业务拆实例。
- **最容易失分的地方**：只答了「用了什么」，没答「为什么不用另一个」和「代价是什么」。
