# 场景地图与选型叙事

前面 8 篇是纵向拆解：一个主题讲透。这一篇横向收口，回答两个问题——**遇到一个业务需求，该用 Redis 的哪一部分、边界在哪**；以及**这些选型在面试里怎么讲清楚**。

## 一、用法地图：Redis 在业务里都干什么 {#用法地图}

「你们项目里 Redis 用来做什么」几乎是最高频的开场题。答案不是罗列五种数据类型，而是**业务问题 → 用哪个结构 → 关键点 → 最容易踩的坑**：

| 用法 | 解决什么问题 | 用什么 | 关键点 | 最容易踩的坑 |
|---|---|---|---|---|
| 缓存 | 热点数据减轻 DB 压力 | String / Hash | 必须配 TTL；穿透/击穿/雪崩要兜底（见[缓存模式](/database/redis/cache-patterns)） | **TTL 加得太长**（等价于没有兜底）或干脆不设；序列化器不统一导致「存进去读不出来」 |
| 分布式锁 | 并发下互斥，防超卖 | `SET NX EX` 或 Redisson | 原子加锁 + 唯一值 + Lua 释放 + 自动续期（见[分布式锁](/database/redis/lock-and-mq)） | **锁粒度太粗**（`lock:order` 锁全部订单）；**`finally` 里不判断持有者就 `unlock`** |
| 原子计数 | 点赞数、阅读量、库存余量 | String `INCR/DECR` | 单命令原子，天然无锁 | 用「先 GET 再 SET」代替 `INCR`——**把原子操作写成了竞态** |
| 会话与令牌 | 登录凭证、验证码 | String + TTL | 过期自动失效，不用自己清理 | 忘了**续期**策略（滑动过期 vs 固定过期）导致用户被登出 |
| 消息队列 | 削峰、异步解耦 | List `LPUSH/BRPOP` 或 Stream | 要可靠投递用 Stream（有 ACK 和消费者组）；PubSub 不持久化、离线即丢 | **用 List 却要求不丢**；`MAXLEN` 不设导致 Stream 无限增长 |
| 延迟队列 | 定时关单、延迟通知 | ZSet（score = 执行时间戳） | 轮询 `ZRANGEBYSCORE 0 now` 取到期任务，用 `ZREM` 的返回值保证只被一个消费者拿到 | 用「先查出来再删」的两步写法 → **同一条任务被多个消费者执行** |
| 榜单与统计 | 排行榜、UV、签到 | ZSet / HyperLogLog / BitMap | 精度可让就让（见[特种类型](/database/redis/special-data-types)） | **月 UV 用每日 UV 相加**；BitMap 拿雪花 ID 直接当 offset |
| 限流 | 接口防刷、防止打穿下游 | String `INCR` + `EXPIRE` 或 Lua 令牌桶 | 计数窗口要原子；分布式下限流计数必须共享 | 「先 `INCR` 再判超限」**不设过期** → 计数器永不清零 |
| 去重 | 幂等键、已读/已领判断 | Set / BitMap / String `SET NX` | 幂等场景用 `SET NX EX` 最省事 | 用 `SISMEMBER` + `SADD` 两步 → 并发下重复放行 |

一句话口径：**「热点数据做缓存、并发扣减加锁、计数和令牌用原子命令、异步和延迟用 List/ZSet/Stream。」** 面试官若追问，就顺着表里任一行往下展开——这比背「String/Hash/List/Set/ZSet」高一个层次，因为它是从**问题**出发而不是从**结构**出发。**能接着说出一句「这里的坑是……」则是又高一档**：它证明你踩过或至少推演过。

## 二、一致性：三档选型，代价递增 {#一致性三档}

缓存与 DB 的一致性没有银弹，只有「业务能容忍多久」的取舍：

| 档 | 业务特征 | 方案 | 不一致窗口 | 实现成本 | 性能代价 |
|---|---|---|---|---|---|
| 普通 | 商品详情、文章内容，容忍秒级陈旧 | 先更库后删缓存 + TTL | ≤ TTL | 极低（业务代码两行） | 无 |
| 热点 | 首页榜单、活动页，读极多写极少 | 上一档 + Canal 订阅 binlog 异步失效 | 毫秒级 | 中（引入 Canal + MQ） | 无（失效在旁路） |
| 强一致 | 库存、余额、券码，读到旧值就是事故 | Redisson 读写锁（写时阻塞读写） | 无 | 中（但**要处理锁本身的失效边界**） | **高**：写时阻塞读，该范围 QPS 被压平 |

**三档的关键差别不在「准不准」，在「代价花在哪」**：

- 第一档的代价是**产品的**——用户可以容忍一个 TTL 的延迟。所以它能不能用，取决于**业务方能不能签字**，不取决于技术。
- 第二档的代价是**基础设施的**——多两个中间件（Canal + MQ），换来「业务代码零侵入 + 毫秒级」。它有一个隐藏优点：**binlog 覆盖所有写入来源**（服务、后台管理台、DBA 手工改、定时任务），而「写路径删缓存」只覆盖你自己写的那些路径。
- 第三档的代价是**性能的**——写锁会阻塞读，这块范围的吞吐直接被压到很低。**所以强一致方案必须限定在很小的热点范围内**（某几个 SKU 的库存），范围一大自己就成了瓶颈。

**为什么不追求「全站强一致」**：CAP 在缓存这一层的体现是「一致性与可用性二选一」。把全站都做成强一致，等于把 Redis 降级成一个「更慢的 DB」——那不如不要这一层。**工程的正确姿势是「按业务分级」，而不是「拉齐到最高标准」**。四档方案的完整做法、延迟双删的位置、以及 TTL 为什么是共同的最后一道闸，见[缓存模式](/database/redis/cache-patterns)。

## 三、容量与集群：三套方案的分界线 {#集群边界}

| 方案 | 组成 | 解决的问题 | 适用规模 |
|---|---|---|---|
| 主从 | 1 主 N 从 | 读并发 + 数据冗余 | 单节点内存 ≤ 10GB |
| 哨兵 | 主从 + 3 哨兵 | 在主从之上加自动故障转移 | 中小规模，要求高可用 |
| 分片集群 | 多组主从，16384 槽分布 | 海量存储 + 高并发写 | TB 级数据 / 单机放不下 |

演进依赖不能跳：**持久化是主从全量同步的基础，主从是哨兵的前提**，而分片集群里每个分片自己也可以有从库——三套方案是叠加关系，不是替代关系。机制细节见[持久化、主从与集群](/database/redis/ha-cluster)。

### 3.1 「单实例 10G」这个数是怎么来的

它不是 Redis 的限制，是**运维经验的产物**，四笔开销决定了它：

| 开销 | 说明 |
|---|---|
| RDB `fork` 的写时复制（COW） | 生成快照时 fork 子进程，父进程的写操作会产生新页。**写密集时额外内存可能接近一整个数据集** |
| AOF 重写缓冲 | `AOF` 重写期间新产生的写命令要同时写进缓冲区 |
| 复制输出缓冲 | 从库消费不及时时，主库要为主从复制缓冲数据 |
| 客户端缓冲 | 输出缓冲不受 `maxmemory` 管理，`client-output-buffer-limit` 不设时可能被慢客户端吃光内存 |

**所以 `maxmemory` 不等于进程占用内存**——工程口径是 **`maxmemory` ≤ 物理内存的 50%~60%**。一台 16G 的机器，给 Redis 8~10G 是合理的；再往上，单点故障的恢复时间（全量同步、重启加载 AOF）也会变得不可接受。

### 3.2 按业务拆实例 vs 分片集群

很多人默认「数据大了就上集群」，实际有两套方案：

| 维度 | 分片集群 | 按业务拆独立实例 |
|---|---|---|
| 扩容 | 需要 reshard、槽迁移，操作重 | 加一组新实例即可，业务自己选 |
| 故障域 | 集群整体是"一个逻辑库"，运维要懂槽与 MOVED | 每个业务独立故障，**互不影响** |
| 多 key 操作 | **受跨槽限制**，要靠 hash tag 或客户端聚合 | 无限制（同实例内随便用） |
| 集群模式特有成本 | Lua 脚本所有 key 必须同槽；`MGET` 跨槽要拆；事务只能在同槽 | 无 |
| 机器利用率 | 高（槽可按需分配） | 低（每个实例都要留冗余） |
| 运维复杂度 | 高（节点多、槽状态要监控） | 中（实例数变多） |

**实践口径**：**「中等规模用主从 + 哨兵，单节点内存控制在 10G 以内；数据量再涨，先考虑按业务拆独立实例，真的单业务数据大到装不下再上分片集群。」** 后一种是很多团队的真实做法——按业务隔离实例，故障域小、扩容简单，代价是机器利用率低、运维实例变多。**说出这个取舍，比只答「我们用了集群」更能体现判断力。**

### 3.3 内存怎么估

顺序是「先估数据集，再算附加开销，最后定实例数」：

1. **单条数据大小**：`key 长度 + value 大小 + 每个对象约 50~100 字节的结构开销`（RedisObject + dictEntry + SDS 头）。**小对象场景下「结构开销」往往超过数据本身**——这也是 Hash 存小对象比 String 省内存的原因（见[最佳实践](/database/redis/best-practices)）。
2. **总数据集 = 条数 × 单条大小 × 冗余系数**（Redis 7 起 Hash/ZSet 用 listpack 编码，小数集更省；但一旦超过阈值会转成 hashtable/skiplist，**单个 key 的编码转换会让内存出现台阶式跳变**）。
3. **加上附加开销**：复制缓冲、AOF 缓冲、碎片率（`mem_fragmentation_ratio` 正常 1.0~1.5，长期 > 1.5 要考虑重启或 `activedefrag`）。
4. **除以 (1 − 余量)**：留 30%~40% 给 COW 与缓冲。

**面试里能说出「`maxmemory` 要留一半、因为 fork 的 COW 可能翻倍」这句，比背「我们用了 16G 内存」有用得多。**

## 四、把选型讲成项目故事 {#项目叙事}

技术点再熟，面试官最后总会落到「你项目里怎么用的」。叙事骨架只有五步：

```
业务背景 → 遇到的问题 → 为什么这么选 → 兜底方案 → 结果与代价
```

以缓存一致性为例的完整口径：

> 「商品详情是典型读多写少，但对实时性要求不高，所以用**先更新库再删缓存 + TTL 兜底**。后来运营改价后用户要等 TTL 才看到，就上了 **Canal 监听 binlog 异步失效**，改成毫秒级，而且业务代码零侵入。抢券库存这类不能读旧值，我们用 **Redisson 读写锁**保证写时阻塞读——代价是这块 QPS 上不去，所以它只用在库存这么小的热点范围上。」

**这段之所以有效，是因为它把三档方案串成了一条演进链**：每一段都给出「当时的约束 → 换方案的原因」。同样的骨架换成任意一个用法都成立。**关键是把「取舍」说出来**：只讲「我用了 Redis 缓存」是背书；讲出「为什么不用另一个方案、代价是什么、我为此做了什么兜底」才是工程判断。

### 4.1 三种常用骨架

| 场景 | 骨架 | 关键的「代价」句 |
|---|---|---|
| 缓存选型 | 读多写少 → TTL 兜底 → 加 Canal 提实时性 → 强一致处上锁 | 「强一致的代价是吞吐，所以只圈了小范围」 |
| 锁选型 | 超卖 → 原子命令 → 不行才上锁 → 看门狗续期 → 失效边界用 DB 兜底 | 「锁只能降低概率，钱和库存最终还是要 DB 条件更新兜底」 |
| 队列选型 | 削峰 → List → 要求不丢改 Stream → 规模上来了换专业 MQ | 「多引一个中间件是负债，规模没到就先用已有依赖」 |

### 4.2 常见追问的准备清单

把下面这些数字和边界记熟，追问就不慌：

| 追问 | 要能立刻答出 |
|---|---|
| QPS 能到多少？ | 单实例 10 万级；瓶颈通常在网络带宽与单实例内存，不是 CPU |
| 缓存怎么失效？ | 写路径删缓存 + TTL；热点用 Canal 订阅 binlog 异步失效；整批失效用版本号前缀 |
| 锁怎么保证不误删？ | 值存唯一标识，释放时用 Lua 先校验再删；**并且 `finally` 里有持有者判断** |
| 看门狗会不会失效？ | 会——显式传 `leaseTime` 会关掉续期；GC 长停顿 / 网络分区时续期必然失败 |
| 集群怎么分数据？ | `CRC16(key) % 16384` 落槽；跨槽多 key 靠 hash tag；Lua 脚本所有 key 必须同槽 |
| 为什么不用本地缓存？ | 多实例一致性难保证；本地缓存是 Redis 前面的「热上热」，不是替代品（见[多级缓存](/database/redis/multilevel-cache)） |
| 数据丢了怎么办？ | 混合持久化（RDB 全量 + AOF 增量），启动优先用 AOF 恢复 |
| 热 key 打满一个节点怎么办？ | 拆 key 加随机后缀分散、本地缓存挡一层、或者读写分离扩从库 |
| 内存满了怎么办？ | `allkeys-lru` 淘汰冷数据，剩下的自然就是热点 |
| 单实例为什么建议 ≤10G？ | `maxmemory` 之外还有 fork COW / AOF 与复制缓冲 / 客户端缓冲四笔开销，要留一半余量 |

## 五、面试口径

- **使用场景**：热点缓存、并发锁、原子计数、会话令牌、异步队列、延迟任务——先一句「缓存 + 锁 + 队列」概括，再按追问展开。
- **选型原则**：先问业务的容忍度（能陈旧多久、能不能丢、能否降级），再定方案；**所有缓存必须有 TTL 兜底**。
- **一致性口径**：按业务分三档（TTL / Canal / 锁），**代价花在产品、基础设施还是性能上，要能说出来**；不追求全站强一致。
- **集群口径**：中小规模主从 + 哨兵、单节点 ≤10G；再涨先按业务拆实例，最后才上分片集群；`maxmemory` 留一半给 fork 与缓冲。
- **最容易失分的地方**：只答了「用了什么」，没答「为什么不用另一个」和「代价是什么」。
