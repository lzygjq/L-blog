# 分布式锁与消息队列

这一篇讲 Redis 被用到「数据库本职之外」的两件事：锁和队列。共同主题是**原子性**——单条命令原子，组合命令不原子，所有坑都长在组合命令上。

## 一、从超卖问题说起

并发扣库存的经典事故：线程 A、B 同时读到库存 1，各自判断充足，各扣一次，卖超。

**三种解法，代价递增、能力递减**：

| 路线 | 做法 | 代价 | 适用 |
|---|---|---|---|
| 乐观锁（无锁） | `UPDATE ... SET stock=stock-1 WHERE stock>0`，看影响行数 | 热点行会打爆 DB（同行的写串行化 + 大量失败重试） | 并发低、写冲突少 |
| 悲观锁 | `SELECT ... FOR UPDATE` 或 Redis 分布式锁包住「判断 + 扣减」 | 持锁期间吞吐被压平；锁的可用性成为新故障点 | 临界区里有多次 IO、无法压成一条 SQL |
| 原子脚本 | Lua / `DECR` 一条命令内完成「判断 + 扣减」 | 只适用于能塞进脚本的纯内存逻辑 | 热点计数、预扣库存 |

**先问一句：真的需要锁吗？** 锁解决的是「互斥」，而互斥的很多诉求其实能被**原子命令**或**条件更新**消化掉——原子命令无锁、无续期、无死锁，可靠性高一档。真正非上分布式锁不可的场景，是「临界区里有多次外部调用 / 需要跨多个资源」那种没法压成单条命令的逻辑。这条判据的展开见[分布式协调：先问这个场景真的需要分布式锁吗](/distributed/coordination/coordination-lock#do-you-need)。

下面几节只讲「确实要上锁」之后的事。

## 二、分布式锁的演进：一个 SETNX 的四个坑

### 坑 1：SETNX 和 EXPIRE 分两条命令

```bash
SETNX lock:order 1     # 加锁成功
EXPIRE lock:order 10   # ← 若进程在这两条之间宕机，锁永不过期（死锁）
```

修复：`SET lock:order <uuid> NX EX 10`，一条命令同时完成加锁和设 TTL。注意返回值——`SET ... NX` 成功返回 `OK`、失败返回 **`nil`**，客户端要判空而不是判异常。

### 坑 2：误删别人的锁

业务执行超过 TTL：A 的锁过期自动释放 → B 拿到锁 → A 执行完 `DEL`，把 B 的锁删了。修复：**值存唯一标识，释放前校验**——校验和删除又必须是原子的，于是需要 Lua：

```lua
-- KEYS[1]=锁 key  ARGV[1]=本线程的唯一标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

Lua 脚本在 Redis 中原子执行（整个脚本算一个命令），这是 Redis 解决「组合操作原子性」的通用手段。

### 坑 3：业务没执行完，锁先过期

锁的 TTL 是拍脑袋定的：定短了锁提前失效回到坑 2，定长了持有者宕机后别人干等。根治方案是**自动续期**——这超出了手写的合理复杂度，交给成熟实现（下一节）。

### 坑 4：不可重入导致的自我死锁

同一个线程在外层方法加锁后，内层方法再对同一 key 加锁——如果是「值存 uuid」的简单实现，内层这次加锁会失败，然后一直等到超时。**同一线程的第二次加锁必须是「计数 +1」而不是「抢占」**。这个坑不致命但极常见，Spring 里一个 `@Transactional` + 自调用就能触发。

> 四个坑的共同根源是：**`TTL` 只能表示「过期」，不能表示「持有者还活着」**。这是所有基于超时的锁的结构性缺口，完整解法见[第四节](#lock-boundary)。

## 三、Redisson：生产级的锁实现

```java
RLock lock = redissonClient.getLock("lock:order:" + orderId);
try {
    boolean got = lock.tryLock(3, 30, TimeUnit.SECONDS); // waitTime / leaseTime
    if (got) { /* 业务 */ }
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

### 3.1 三个核心机制

| 机制 | 实现 |
|---|---|
| 可重入 | 锁不是 String 而是 Hash：`field = UUID:threadId`，`value = 重入计数`。重入 `HINCRBY` 加计数，解锁减到 0 才真删 key |
| 看门狗自动续期 | 未显式指定 `leaseTime` 时默认锁期 30s，后台线程每 **1/3 锁期（10s）**检查持有状态并续期 |
| 阻塞等待 | 等锁线程订阅锁的 pub/sub channel，释放时 pub 通知唤醒，避免轮询空转 |

`unlock()` 同样是一段 Lua：先判断 `hexists(KEYS[1], ARGV[3])`（是不是我的锁），再 `hincrby -1`，减到 0 才 `del` 并 `publish` 唤醒等待者。**整个解锁过程在建锁时就被算好字节长度、随锁一起注册**——这是 Redisson 的一个工程细节：避免每次解锁都重新计算脚本长度（`EVALSHA` 传脚本摘要而非全文）。

### 3.2 看门狗的三个细节（最容易被问穿的地方）

1. **不是「定时续期」而是「按需续期」**：看门狗任务（`renewExpiration`）在加锁成功后注册一个延迟任务，每 10s 跑一次，**只续自己还持有的锁**；释放后任务被取消。
2. **显式传 `leaseTime` = 关掉看门狗**。`tryLock(3, 30, SECONDS)` 里的 `30` 是写死的锁期，到期即释放、**不会续期**。这一条是生产事故高发点：业务偶尔超过 30s 时，坑 2（误删）就回来了。**要续期就不要传 `leaseTime`**，或者把 `leaseTime` 设成业务 P99 的若干倍并接受「宕机后最长等这么久」。
3. **看门狗续期不了就放弃**：进程被 `SIGSTOP`、GC 长停顿、网络分区时续期失败，锁到期易主——这不是 bug，是超时型锁的物理极限（见[第四节](#lock-boundary)）。

### 3.3 锁的种类：不止一把互斥锁

| 锁 | 语义 | 典型用途 |
|---|---|---|
| `RLock` | 互斥 + 可重入 | 通用临界区 |
| `RFairLock` | 按请求顺序排队（用 ZSet 记录排队时间戳） | 要防饥饿的顺序任务 |
| `RReadWriteLock` | 读读并行、读写 / 写写互斥 | 缓存与 DB 的强一致读（[一致性三档](/database/redis/scenarios#一致性三档)的第三档） |
| `RMultiLock` | 多个独立锁全部成功才算成功 | 跨多个分片 / 多个资源的原子操作 |
| `RSemaphore` / `RCountDownLatch` | 信号量与倒计数 | 限流、并发编排（严格说不是锁） |

`RMultiLock` 与 **Redlock** 看着像但不同：Redlock 是「多个独立节点上各加一把，过半成功」，MultiLock 是「每个锁对象都是独立的业务资源，必须全部拿到」。前者为了提高锁本身的可用性，后者为了跨资源互斥。

### 3.4 三个常见误用

- **锁的粒度太粗**：`lock:order` 一把锁锁住全部订单 → 全部请求串行。正确的粒度是「一个业务实体一把锁」：`lock:order:{orderId}`。
- **锁内做长耗时操作**：锁内跑远程调用、发消息、跑批，锁期被拉到秒级以上。**锁只包住必须互斥的那几行**，IO 挪到锁外。
- **`unlock()` 不判断持有者**：`isHeldByCurrentThread()` 缺失时，锁已过期易主的情况下 `unlock()` 会发出 `IllegalMonitorStateException`（Redisson 会拦），或者在更粗糙的实现里直接删掉别人的锁。**`finally` 里要么判断、要么吞掉这个异常**，别让它盖住业务异常。

> **加锁顺序问题**：如果临界区里还要开事务，注意顺序——先加锁、再开事务、事务提交后释放锁。反过来（先开事务再加锁）会让锁的持有时间被事务提交的 IO 拉长，且事务因超时回滚时锁已经释放，后续请求读到未提交的回滚数据。

## 四、锁的边界：为什么锁无法自证「持有者还活着」{#lock-boundary}

前三节的所有机制都在绕开同一个事实：**基于 TTL 的锁，无法区分「持有者还活着但很慢」和「持有者已经死了」**。看门狗靠「我还活着就续期」逼近这个目标，但续期本身依赖网络与进程调度——一旦发生 GC 长停顿或网络分区，续期失败就是必然。

由此引出两个必须知道的结论：

- **Redlock 的两面性**：在 n 个互相独立的 Redis 节点上各加一把锁、过半成功才算成功，能抵御「单节点故障 + 主从切换导致的双持锁」。但工业界争议很大（Kleppmann 的主要批评是**它依赖各节点的时钟不能大幅漂移，而现实分布式系统中时钟恰恰不可信**），结论是绝大多数场景**单实例 + 哨兵 + 看门狗已经足够**。完整论战与正确定位见[Redlock 的争议](/distributed/coordination/coordination-lock#redlock)。
- **真正要极端正确性的互斥**（资金、券码核销）不该依赖超时型锁，两条出路：① 把互斥下沉到**存储层**，用单调递增的 fencing token 让存储拒绝过期持有者的写入；② 换用 **ZooKeeper / etcd**（临时顺序节点 + 会话，会话断开即自动释放，不存在「锁还在但人没了」）。两者的语义对照见[三种实现的互斥是怎么保证的](/distributed/coordination/coordination-lock#three-ways)与[fencing token](/distributed/coordination/coordination-lock#fencing)。

> 面试口径：**能主动说出「Redis 锁在这里的失效边界是什么、我拿什么兜底」，比背熟 Redisson 的 API 高一个层次**。诚实地说「这块 QPS 不高，所以我们用 DB 乐观锁兜底，根本没上分布式锁」同样是加分答案。

## 五、秒杀链路：Lua + MQ 的组合

单用锁解决不了秒杀的吞吐，标准链路是「Lua 原子预扣 + MQ 异步下单」：

```lua
-- KEYS[1]=库存  KEYS[2]=已购集合  ARGV[1]=userId
if tonumber(redis.call('GET', KEYS[1])) <= 0 then return -1 end         -- 售罄
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -2 end     -- 重复下单
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

一次网络往返内原子完成「库存判断 + 去重 + 扣减」，资格通过后发 MQ，由消费者慢慢完成创建订单 + 扣 DB 库存。DB 永远只承受与真实库存量级的写入，而不是请求量级的写入。

三个落地细节：

1. **集群下必须用 hash tag**：`KEYS[1]` 与 `KEYS[2]` 若落在不同槽，脚本会被集群拒绝（`CROSSSLOT`）。用 `{sku:1001}:stock` 与 `{sku:1001}:bought`，让 `{}` 内的部分决定槽位，两个 key 必然同槽。
2. **脚本必须短**：Redis 执行脚本是原子的 = 脚本期间阻塞其他命令。**禁止在脚本里遍历大集合**，否则「原子性工具」变成「自己制造的慢命令」。
3. **预扣必须有回补与对账**：Redis 预扣成功、MQ 投递失败或下单最终失败时，要有一条路径把库存还回去（补偿消息或定时对账任务扫「已预扣未成单」的记录）。**没有回补的预扣就是慢性库存泄漏**。
4. **不能只靠 Redis 计数**：库存是钱，Redis 的持久化（RDB 快照 + AOF）在极端情况下仍有丢数据的窗口。常见做法是 **Redis 挡流量、DB 做终局**——DB 层再加一层 `WHERE stock >= 1` 的条件更新兜底。

## 六、List 做队列：能用，但有三个坑 {#list-queue}

```bash
LPUSH queue:order '{"id":1}'      # 生产者
BRPOP  queue:order 5              # 消费者：阻塞 5s 等消息
```

| 坑 | 说明 | 破法 |
|---|---|---|
| **弹出即丢** | `BRPOP` 一旦返回，消息就从 List 消失了。消费者拿到后崩溃 → 这条消息永久丢失 | 用 `BRPOPLPUSH` / `BLMOVE ... LEFT RIGHT` 先把消息**原子搬到一个处理中的 List**，处理成功再 `LREM` 删除；失败则由巡检任务搬回原队列 |
| **无确认、无重投** | 没有任何「投递次数 / 上次投递时间」的概念，无法做重试上限 | 需要这些就一定换 Stream |
| **无消费者组语义** | 多个消费者共享一个 List，天然是竞争消费，但**无法知道谁消费到哪** | 同上 |

另外两个工程细节：`BRPOP` 的超时不要设成 0（永久阻塞）——连接被中间设备静默掐断时无法自愈；空队列下的阻塞连接不消耗 CPU 但**占用连接数**，消费者实例多了要注意 Redis 的 `maxclients`。

**结论**：List 适合「允许丢、只求削峰」的场景（日志搬运、非关键通知）。**只要业务上「丢了要发现、失败要重试」，就该用 Stream。**

## 七、PubSub：只适合在线广播 {#pubsub}

```bash
SUBSCRIBE channel:config          # 订阅
PUBLISH   channel:config '{"v":2}' # 发布
```

PubSub 的语义是**「此刻在线的人听到了就听到了」**：

| 特性 | 后果 |
|---|---|
| 不持久化 | 消息发出去就没了，离线订阅者永久错过 |
| 无确认 | 发布者无法知道有没有人收到 |
| 无消费者组 | 所有订阅者都收到全量消息（广播，不是竞争消费） |
| 不占内存 | 没有堆积能力——这也意味着**它无法削峰** |

**它唯一不可替代的价值是「低延迟 + 纯广播」**：配置变更通知、集群节点心跳、以及 **Redisson 用它唤醒等锁线程**（锁释放即 `PUBLISH`，等待者立刻被叫醒，不必轮询）。

> 对比记忆点：**PubSub 是电话（在线才通），Stream 是短信（关机也能收）。**

## 八、Stream：轻量可靠队列的正确用法 {#stream}

Stream 是 5.0 引入的**追加日志**结构，把「消费者组 + 确认 + 重投」这一套消息中间件的核心语义做进了 Redis。

### 8.1 一条消息的完整生命周期

```bash
# 生产
XADD order:stream * orderId 1001 amount 99        # * = 自动生成时间戳 ID（如 1726-0）

# 建组（from 0 = 从头消费所有历史；$ = 只消费之后的新消息）
XGROUP CREATE order:stream g1 0

# 消费：> 表示「给我还没投递给本组的新消息」
XREADGROUP GROUP g1 consumer-1 COUNT 10 BLOCK 5000 STREAMS order:stream >

# 处理成功 → 确认
XACK order:stream g1 1726-0
```

### 8.2 PEL：可靠投递的全部秘密

**消息被投递给某个消费者后、在 `XACK` 之前，会一直躺在消费者组的 PEL（Pending Entries List）里。** 这带来三个必须会用的命令：

| 命令 | 用途 |
|---|---|
| `XPENDING order:stream g1` | 看这条组里有多少条未确认、分别属于谁、闲置了多久 |
| `XCLAIM order:stream g1 c2 60000 1726-0` | 把闲置超过 60s 的消息**认领给消费者 c2** 重新处理（消费者宕机后的标准恢复手段） |
| `XAUTOCLAIM order:stream g1 c2 60000 0-0 COUNT 10` | 批量版认领，从哪条游标继续（Redis 6.2+ 推荐用这个） |

所以 **Stream 的「不丢」= PEL 兜底 + 消费者崩溃后由别人 `XAUTOCLAIM` 接管 + 业务幂等**（消息可能被重复投递，至少要保证至少一次）。

### 8.3 三个使用边界

1. **`MAXLEN` 必须设**。Stream 是内存结构，不裁剪就会无限增长。`XADD order:stream MAXLEN ~ 100000 * ...`——`~` 表示近似裁剪（按内部宏节点整块删，效率远高于精确裁剪）。
2. **消费者组不会自动清理**：`XGROUP DELCONSUMER` 手动删；创建了不用的组会让 `XPENDING` 一直有数据。
3. **它不是 RocketMQ / Kafka 的替代品**。超过以下任一边界就该出域：需要事务消息、死信队列、延迟分级、堆积到磁盘、每秒十万级吞吐、多租户隔离。对比见[消息队列板块的选型](/middleware/#selection)。

### 8.4 与 List / PubSub 的语义照

| 能力 | List | PubSub | Stream |
|---|---|---|---|
| 持久化 | 消息即数据，可持久化 | 无 | 追加日志，可持久化 |
| 确认（ACK） | 无 | 无 | **有**（`XACK`） |
| 消费者组 | 无 | 无 | **有**（组内竞争、组间独立进度） |
| 崩溃后重投 | 无 | 无 | **有**（`XAUTOCLAIM`） |
| 堆积 | 可以，但全量内存 | 不支持 | 可以，`MAXLEN` 控制 |
| 延迟 | 微秒级 | 微秒级 | 毫秒级（含组状态维护） |

## 九、延迟队列：ZSet 方案与三个细节 {#delay-queue}

定时关单、延迟通知、超时补偿——这类「N 分钟后做某事」的需求，第一反应容易写成「定时任务扫表」，代价是 DB 压力与精度二选一。Redis 的标准解法是 **ZSet + score = 执行时间戳**：

```bash
# 投递：score 是到期时间（毫秒时间戳）
ZADD delay:order <executeAt> '{"orderId":1001,"action":"close"}'

# 取到期任务：只取 score ≤ 现在的，一次 10 条
ZRANGEBYSCORE delay:order 0 <now> LIMIT 0 10

# 取出后用 ZREM 删除，靠返回值判断「这条是我抢到的吗」
ZREM delay:order '{"orderId":1001,"action":"close"}'
```

三个细节决定它能不能上生产：

1. **`ZREM` 是去重的关键**：多个消费者会同时 `ZRANGEBYSCORE` 到同一条，`ZREM` 返回 1 的那个才是真正拿到任务的（返回值 0 说明被别人抢走了）。用 `ZPOPMIN` 也能原子弹出，但它不校验 score 是否到期——**先到期的任务若排在后面，会被提前弹出**，需要弹出后判断并塞回去，反而更绕。生产里更常用 Lua 把「范围查询 + 逐条删除」封成一个原子脚本。
2. **轮询间隔 = 延迟精度的上限**。1s 轮询 → 精度 1s。想更准要多消费者短轮询，代价是空转 QPS；`ZRANGEBYSCORE` 本身是 O(log N + M)，空轮询的成本主要在网络往返。
3. **单点与分片**：所有消费者抢同一个 ZSet，量级大时这把 ZSet 本身是热点（[BigKey](/database/redis/best-practices)）。按业务 ID 取模拆多个 key，或按时间分桶（`delay:order:2026091210`），让不同消费者负责不同桶。

**替代方案**：RocketMQ 的延迟消息（固定档位）、RabbitMQ 的 `DLX + TTL` 或 `DelayExchange` 插件（见[死信与延迟队列](/middleware/rabbitmq/dead-letter)）、时间轮（Netty `HashedWheelTimer`，进程内、不跨实例）。**只要延迟精度要求不高（秒级）、量级中等，Redis ZSet 是成本最低的那一档**；一旦要「精确到毫秒 + 超大吞吐 + 可查询」，就该交给专业 MQ 或调度系统。

## 十、四种方案对照与选型

| 维度 | List（BRPOP/BLMOVE） | PubSub | Stream | ZSet（延迟） |
|---|---|---|---|---|
| 核心语义 | 任务队列 | 在线广播 | 可靠队列 | 定时触发 |
| 丢消息环节 | **弹出即丢**（消费者崩溃） | **离线即丢** | 无（靠 PEL 重投） | 无（到点才可被取） |
| 消费确认 | 无 | 无 | `XACK` + PEL | `ZREM` 的返回值 |
| 消费者组 | 无 | 无 | 有 | 无（靠 ZREM 竞争） |
| 堆积能力 | 有（全内存） | 无 | 有（`MAXLEN` 控制） | 有（全内存） |
| 顺序性 | FIFO | 无 | 按 ID 递增 | 按 score |
| 典型场景 | 非关键削峰 | 配置变更、锁唤醒 | 订单异步、事件分发 | 关单、超时补偿 |

**选型口诀**：**允许丢、只削峰 → List；在线广播 → PubSub；要 ACK 与重投 → Stream；到点执行 → ZSet。** 再往上（事务消息、死信、延迟分级、大吞吐堆积、多租户）就出域了——那是[专业消息中间件](/middleware/)的地盘。从零搭建的微服务项目里，MQ 选型最终会落到 RocketMQ / Kafka，Redis Stream 只承担轻量异步场景，原因正在这张表里。

## 十一、面试问答

**Q1：手写分布式锁要处理哪些问题？**

至少五个：加锁与设 TTL 原子（`SET NX EX`）、值存唯一标识防误删、释放用 Lua 保证「校验 + 删除」原子、锁超时与业务时长的关系（自动续期）、以及可重入。答全五个的候选人不多，这题是分层信号题。

**Q2：为什么释放锁必须用 Lua？**

`GET` 校验和 `DEL` 是两条命令，中间锁可能恰好过期易主。Lua 脚本整体原子，等价于把「if 我才是持有者 then 删除」变成不可分割的操作。

**Q3：Redisson 的看门狗是怎么续期的？有什么前提？**

不指定 `leaseTime` 时，默认锁期 30s，后台任务每 1/3 锁期（10s）检查并续期回 30s。**关键前提是「不要显式传 leaseTime」**——传了就等于关掉看门狗，锁到期不续，业务超时就会踩「误删别人的锁」那个坑。另外续期依赖进程能被调度、网络可达，GC 长停顿或分区时续期会失败，这是超时型锁的物理极限。

**Q4：Redis 分布式锁在什么情况下会失效？**

三种：① 主从切换导致双持锁（主库加锁成功但未同步到从库，主库宕机后从库提升，另一线程在新主上加锁成功）；② 持有者 GC 长停顿或网络分区，看门狗续期失败，锁被他人获得，而原持有者恢复后仍以为自己在临界区内；③ 时钟漂移让 Redlock 的「过期判断」失真。**根治手段是 fencing token（让存储层拒绝过期持有者的写入）或换 ZooKeeper / etcd**。

**Q5：Lua 脚本有什么使用禁忌？**

Redis 执行脚本是原子的 = 脚本执行期间阻塞其他命令。脚本要短小（判断 + 写回级别），禁止循环遍历大集合——否则它就从「原子性工具」变成「自己制造的慢命令」。集群下还要保证脚本里所有 key 同槽（用 hash tag）。

**Q6：Redis Stream 消费了没 ACK 会怎样？**

消息留在消费者组的 PEL 里，`XPENDING` 可查、`XCLAIM` / `XAUTOCLAIM` 可转给其他消费者重投——这正是可靠投递的基础，也是它与 PubSub 的本质区别。所以「不丢」是 PEL + 重投 + 业务幂等三件事合起来的结果，Stream 本身不保证「只投一次」。

**Q7：为什么用 Redis 而不是直接上 RocketMQ 做异步？**

按边界判断。Redis Stream 的优势是**零新增中间件**（已有依赖）、延迟低、运维成本为零；代价是持久化能力弱于专业 MQ（内存为主）、堆积能力有限、没有事务消息 / 死信 / 延迟分级 / 多租户。**规模没到那条线之前，多引一个中间件是纯负债**；到了那条线就该迁移，重审条件写进 ADR（见[ADR 模板](/projects/toolkit/adr/)）。

**Q8：延迟队列为什么用 ZSet 而不是定时扫表？**

扫表是 O(表 × 轮询频次) 的 DB 压力，且精度的上限就是轮询间隔；ZSet 的 `ZRANGEBYSCORE` 是 O(log N + M)，只在到点时取出，成本与「到期任务数」相关而不是与「总任务数」相关。代价是它全内存、且需要处理多消费者的竞争——靠 `ZREM` 的返回值或 Lua 脚本解决。
