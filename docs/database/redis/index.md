# Redis · 导览

Redis 是「数据存储」板块里工程含量最高的一块：它既是缓存组件，又是分布式锁与轻量消息队列的实现，还是高可用架构（主从/哨兵/分片）与数据结构的完整样本。

## 一、五层能力模型 {#layers}

本板块不是按「数据类型」组织的，而是按**能力递进**分成五层。每一层都能独立成题，且**面试问法不同**：

| 层 | 能力 | 对应篇目 | 面试怎么问 |
|---|---|---|---|
| **会用** | 知道该用哪种结构解决哪种问题 | [基础篇](/database/redis/basics) | 「这个场景你用什么结构、为什么不用另一种」 |
| **懂原理** | 命令背后的编码与调度机制 | [底层原理](/database/redis/internals) | 「为什么这么快 / 为什么跳表不用红黑树」——考的是因果链 |
| **会设计** | 在并发与一致性约束下做方案取舍 | [缓存模式](/database/redis/cache-patterns)、[分布式锁与消息队列](/database/redis/lock-and-mq)、[特种类型](/database/redis/special-data-types) | 「怎么保证不超卖 / 一致性怎么保证」——考的是取舍与失效边界 |
| **能扛量** | 从单机走到集群与多级缓存 | [持久化、主从与集群](/database/redis/ha-cluster)、[多级缓存](/database/redis/multilevel-cache) | 「瓶颈在哪 / 翻十倍怎么办」——考的是容量与故障判断 |
| **会表达** | 把上述所有东西讲成一段可信的项目叙事 | [场景地图与选型叙事](/database/redis/scenarios) | 「你项目里 Redis 怎么用的」——考的是有没有真的做过决策 |

**为什么把「会表达」单独列一层**：前四层是知识，第五层是把知识变成**可验证的判断**。面试里最常见的失分不是「不知道」，而是「只说了用了什么，没说是怎么选的、放弃了什么」。第五层就是专门为这个问题准备的。

## 三、板块约定

- 命令示例基于 **Redis 7.x / 8.x**（标注版本号的是新命令）；客户端示例基于 Spring Data Redis（Lettuce）。
- 高可用部分与本地 Docker Compose「1 主 2 从 + 3 哨兵」环境对应，可直接复现。
- 多级缓存一篇与[数据仓库板块的 Canal](/bigdata/canal/)共享数据同步链路，交叉引用不重复展开。
- **分布式锁的「正确性缺口」不在这里展开**——`fencing token`、Redlock 争议、ZK/etcd 的语义对照归[分布式协调](/distributed/coordination/coordination-lock)；本板块只讲「Redis 侧怎么把锁写得尽量对」。
- **Spring 注解层的缓存抽象**（`@Cacheable` 家族、`CacheManager`、序列化器）归[横切能力：缓存抽象](/java/spring/spring-framework/crosscutting/cache)；本板块讲的是「缓存本身怎么设计」。
- 每篇末尾统一给「面试问答」，第 9 篇再给「面试口径」式的整体叙事框架——正文负责把「为什么」讲透，可背的短句只保留在小结里。

## 五、版本现状 {#versions}

Redis 的版本与许可在近两年变化很大，面试也常问「你怎么看 Redis 的许可变更」。当前（2026-09）的事实：

**版本与支持窗口**

| 版本线 | 首发 | 状态 | OSS 支持截止 |
|---|---|---|---|
| **8.10**（当前主推） | 2026-07-29 | 活跃 | — |
| 8.8 | 2026-05-25 | 维护 | 2026-07-29（已交由 8.10 承接） |
| 8.6 | 2026-02-11 | 维护 | 2026-05-25 |
| 8.4 | 2025-11-18 | 维护 | 2026-02-11 |
| 8.2 | 2025-08-04 | 维护 | **2030-09-01**（长期） |
| 8.0 | 2025-05-02 | 维护 | **2026-12-01** ← 生产仍在 8.0.x 的要排升级 |
| 7.4 | 2024-07-29 | 维护 | 2029-12-01 |
| 7.2（最后一个 BSD 版） | 2023-08-15 | 维护 | 2029-12-01 |
| 6.2 | 2021-02-22 | 收尾 | 2027-04-01 |

**许可的三次转折**（这是「为什么会有 Valkey」的完整答案）：

1. **≤ 7.2.x：BSD-3-Clause**，随便用。
2. **7.4.x ~ 7.8.x：RSALv2 / SSPLv1 二选一**——不再是 OSI 认可的开源许可，云厂商不能直接提供托管服务。社区随即在 Linux 基金会下分叉出 **Valkey**（BSD-3，多厂商治理）。
3. **≥ 8.0：RSALv2 / SSPLv1 / AGPLv3 三选一**——AGPLv3 是 OSI 认可的开源许可，**Redis 重新回到「开源软件」的定义内**，但 AGPLv3 带网络服务 copyleft 义务（改了又对外提供网络服务，通常需要公开修改）。

**Redis 8 的能力变化（面试加分项）**

- **「One Redis」：模块并入核心**。原 Redis Stack 的 RediSearch、JSON、TimeSeries、Bloom/Cuckoo/Count-min sketch/Top-k/t-digest **全部内置**，无需再单独装模块；Redis Stack 这个发行版已于 2025-12 停止维护。新增 **Vector set** 数据类型（HNSW 图做向量相似检索），是 Redis 进入 AI 检索场景的入口。
- **I/O 多线程**：`io-threads` 配置项重写，官方基准给出 8.6 单节点吞吐为 7.2 的 **5 倍以上**；8.4 起 JSON 数值数组内存下降最高 92%，8.6 起 ZSet 命令延迟最高降 35%、内存最高降 30.5%（**均为官方基准，实际以自测为准**）。
- **8.0 的 ACL 破坏性变更**：Search / JSON / TimeSeries / 概率类型的命令被并入既有的 `@read` / `@write` 等类别——**`+@read +@write` 会放开比 7.x 更多的命令**，升级前必须复核 ACL 规则。
- **8.0 起的新命令**：`HGETDEL` / `HGETEX` / `HSETEX`（哈希字段级 TTL）；8.10 增加 **compact hash 编码**（同 schema 的哈希只存一份字段名）与批量导入 `HIMPORT`、节点侧 `BACKUP`、`LMOVEM` / `BLMOVEM`、`SUNIONCARD` / `SDIFFCARD`、`XREAD`/`XREADGROUP` 的 `MAXCOUNT`/`MAXSIZE`。

**Valkey 侧（常被追问「你怎么选」）**

- 当前稳定线 **9.1**（2026-05-19 首发，补丁 9.1.2 / 2026-08-31）；上一稳定线 9.0（2025-10-21）；8.0 / 8.1 仍在维护（8.0 到 2027-09-15）。
- 9.1 的关键能力：**数据库级 ACL**（`db=0,1` 把权限收敛到具体库）、**Lua 引擎模块化**（可以整个关掉）、TLS 证书自动重载与过期时间查询、JSON 格式日志、主线程 / IO 线程真实使用率指标、`CLUSTERSCAN`；另有 Valkey Search、Valkey Admin、Valkey GLIDE（客户端，支持客户端缓存）。
- **选型口径**：功能与生态跟着 Redis 走、需要企业支持与托管 → Redis 8（注意 AGPLv3 的义务）；只想要一个「永久 BSD、无单厂商治理风险」的兼容替代 → Valkey。**两者命令层高度兼容，迁移成本主要在模块能力（Valkey 的 JSON / 时序 / 概率结构依赖官方模块而非内置）**。

> 本地 Docker 环境对应 7.x/8.x，命令示例都可直接复现；升级到 8.x 前请对照上表的 ACL 变更与支持窗口。
