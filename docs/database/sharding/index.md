# 分库分表：时机、策略与代价

> 本文是[架构路线](/projects/architecture-evolution/)的**分片分册**，对应数据层 **[分片集群](/projects/architecture-evolution/data/#shard)**——什么时候该走到这一档、要付什么代价、怎么验收。这一档可永远不到。

## 一、问题场景

单表数据量持续增长，优化手段用尽之后，性能依然上不去：

| 已经做过的优化 | 为什么到极限了 |
|---|---|
| 加索引 | B+ 树层数变高、Buffer Pool 命中率下降，IO 次数压不下去 |
| 主从读写分离 | 解决了读瓶颈，但**写还是落在同一个主库** |
| SQL 调优 | 查询已经是最优写法，慢在数据量本身 |
| 归档冷数据 | 热数据仍在增长，只是延后了问题 |

这时候才轮到**分库分表**。**结论先行**：分库分表不是性能优化的起点，而是**最后手段**——它用"应用复杂度、分布式一致性、运维成本"去换"单机容量上限"。所以面试问"什么时机分"时，真正的考点是**你能不能说出"什么时候不该分"**。

## 二、拆分时机

**三个前提条件**（都满足才考虑）：

```
① 业务数据确实在持续快速增长（不是"可能会增长"）
② 常规优化手段已经用到极限
   —— 索引、SQL 调优、主从读写分离、缓存、归档，全部做过且仍有瓶颈
③ 出现了明确的资源瓶颈
   —— IO 瓶颈（磁盘 IO、网络 IO）或 CPU 瓶颈（聚合查询、连接数过多）
```

**经验值参考**：

| 指标 | 阈值 | 说明 |
|---|---|---|
| 单表行数 | **1000 万** | 业界通行参考线。注意：**不是硬性红线**——如果都是主键查询，3000 万也能跑得很好；如果全是聚合查询，500 万就够呛 |
| 单表数据量 | **20G** | 对应备份恢复时间、DDL 时间都变得不可接受 |
| 单库并发 | 连接数 / 写入 QPS 打满 | 加从库也救不了写 |

> **重要提醒**：**先确认瓶颈真的是"数据量"，而不是"查询写法"**。生产中大量"以为是数据量大"的慢查询，最后发现只是缺一个联合索引。**在分库分表之前，必须让 `EXPLAIN` 和 [慢查询日志](/database/mysql/diagnosis) 出具"优化已到极限"的证据。**

## 三、四种拆分策略

拆分分两大方向：**垂直（按业务/字段切）** 和 **水平（按数据行切）**。

| 策略 | 拆分依据 | 解决的问题 | 注意点 |
|---|---|---|---|
| **垂直分库** | 按**表/业务**拆到不同库（用户库、订单库、商品库） | 提高磁盘 IO 与连接数上限；**业务分级管理**，故障隔离 | 拆完就**跨库 JOIN 了**——要改成服务间调用或数据冗余 |
| **垂直分表** | 按**字段**拆，冷热分离，大字段（`text` / `blob`）拆到附表 | 减少单页行数 → **提高 Buffer Pool 命中率**；两表 IO 互不影响 | 主键冗余存两份；查完整对象要两次查询 |
| **水平分库** | 同一张表按**路由规则**拆到多个库 | 解决**单库**的数据量和并发瓶颈 | 跨库事务、跨库分页问题 |
| **水平分表** | 同一张表的数据拆到**同一库内的多张表** | 解决**单表**数据量过大的性能问题 | 表名动态化（`t_order_0` ~ `t_order_9`） |

**一句话区分**：

```
垂直 = 按"列"或"业务"切（把宽表切窄、把大库切小）
水平 = 按"行"切（每张表结构相同，各存一部分数据）
```

### 实际项目中的组合

生产上通常是**组合使用**，典型路径：

```
第 1 步：垂直分库    → 用户库 / 订单库 / 商品库，按业务隔离
第 2 步：垂直分表    → 订单主表 + 订单详情表（大字段挪走）
第 3 步：水平分表    → 订单表拆成 t_order_0 ~ t_order_9
        （如果单库扛不住写入）
第 4 步：水平分库    → 10 张表分散到 2~4 个库
```

## 四、路由规则

水平拆分的核心是"一条数据该落到哪个库/表"，由路由算法决定：

| 规则 | 算法 | 优点 | 缺点 |
|---|---|---|---|
| **取模** | `hash(user_id) % 4` | **数据分布均匀** | ⚠️ **扩容时几乎全量数据要迁移**（模数一变，所有记录位置都变） |
| **范围** | `user_id` 在 1~100 万 → 库 1，100 万~200 万 → 库 2 | 扩容方便（加新库承接新数据）；范围查询友好 | ⚠️ **数据倾斜**——新库热、老库冷；递增 ID 下热点全在最后一个分片 |
| **一致性哈希** | 哈希环 + 虚拟节点 | **扩容时只迁移约 1/N 的数据** | 实现复杂；需虚拟节点解决数据倾斜 |
| **按时间** | 按月分表 `t_order_202609` | 归档极其方便（整表删除） | 热点集中在当前月；跨月查询要合并多表 |

**工程实践**：

- 用 `user_id`（或 `tenant_id`）作为**分片键**，比用 `order_id` 更常见——因为业务查询通常带 `user_id`，能**避免跨库查询**。
- **先按范围分库，库内再取模分表**——兼顾"扩容方便"与"分布均匀"，是常见的折中方案。
- **分片键与主键分离**：`order_id` 用雪花算法保证全局唯一，`user_id` 做分片键，两者都要在表里。

## 五、分库分表之后：四个必须解决的问题

这是"分库分表真正的成本"，也是面试区分度最高的部分——**敢分的人多，能说清代价的人少**。

| # | 问题 | 现象 | 解决方案 |
|---|---|---|---|
| 1 | **分布式事务一致性** | 一笔订单扣库存 + 扣余额 + 写订单，跨了 3 个库，无法用一个本地事务 | ① **尽量避免跨库事务**——按业务边界设计，让一个事务落在一个库里（最优解）；② 必须跨库时用 **Seata** 的 AT/TCC 模式，或**本地消息表 + 最终一致性**；③ 对账兜底 |
| 2 | **跨节点关联查询（JOIN 困难）** | 订单在库 1、用户详情在库 2，无法 `JOIN` | ① **冗余字段**——把高频关联字段（用户名、商品名）写进订单表（空间换时间）；② **应用层组装**——分别查再在 Service 层拼装；③ **宽表**——通过 Canal 同步到 [Doris](/bigdata/doris/) 做宽表，复杂分析走数仓 |
| 3 | **跨节点分页、排序** | `order by create_time limit 10, 10` 在 4 个库各取 10 条不够，可能都不在前 10 | ① **各分片各取前 `offset + limit` 条，在内存中归并排序后再截取**（深分页代价高）；② 引入 **ES / Doris** 承接复杂分页排序；③ 业务上限制分页深度 |
| 4 | **主键避重** | 不同库/表不能生成重复 ID；自增 ID 在多库下会冲突 | **雪花算法（Snowflake）**——见下节 |

### 主键避重：为什么是雪花算法

| 方案 | 做法 | 问题 |
|---|---|---|
| 自增 ID | 各库各自自增 | ❌ 直接冲突 |
| 步长错开 | 库 1 从 1 开始步长 2、库 2 从 2 开始步长 2 | ⚠️ 扩容时要改步长，且 ID 可被推算 |
| UUID | 全局唯一 | ❌ **无序**，作为 InnoDB 主键会导致页分裂和随机 IO（见 [索引底层](/database/mysql/index-structure)） |
| **雪花算法** | 时间戳 + 机器 ID + 序列号 → 64 位 long | ✅ **全局唯一 + 趋势递增**，8 字节，适合做主键 |

```
雪花算法 ID 结构（64 bit）
┌─┬───────────────────────────────┬──────────────┬──────────────┐
│0│        时间戳（41 bit）         │   机器 ID     │   序列号      │
│ │  毫秒级，可用约 69 年           │  （10 bit）   │  （12 bit）   │
└─┴───────────────────────────────┴──────────────┴──────────────┘

  容量：1024 台机器 × 每毫秒 4096 个 ID ≈ 全局每毫秒 419 万个 ID
  特性：趋势递增（时间戳在高位）→ 插入是顺序的，不引起页分裂
```

**唯一要小心的坑**：**时钟回拨**——机器时间往回跳会导致生成重复 ID。标准解法是检测到回拨时**等待到时间追平**，或**抛出异常由上层重试**。

## 六、ShardingSphere：主流中间件

| 方案 | 定位 | 优点 | 缺点 |
|---|---|---|---|
| **ShardingSphere-JDBC** | **客户端直连**（增强版驱动，以 jar 包引入） | **无额外部署**、性能高（无网络跳转） | 与语言/框架耦合；配置分散在各应用 |
| **ShardingSphere-Proxy** | **数据库代理**（独立部署，应用连它如同连 MySQL） | **对应用透明**、跨语言 | 多一跳网络；代理本身要保证高可用 |
| MyCat | 数据库代理 | 社区较老、资料多 | 维护活跃度下降，新项目不建议 |

**Apache ShardingSphere** 是 Apache 顶级项目，核心能力包括：**数据分片、读写分离、数据加密、影子库压测**。5.x 版本同时提供 JDBC 与 Proxy 两种模式，且**可以混合部署**（Proxy 承担跨语言接入、JDBC 承担高性能场景）。

配置示例（Spring Boot + ShardingSphere-JDBC，YAML 口径）：

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0: { url: jdbc:mysql://127.0.0.1:3306/order_db0 }
      ds1: { url: jdbc:mysql://127.0.0.1:3306/order_db1 }
    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..9}   # 2 库 × 10 表
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: db-inline
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
        sharding-algorithms:
          db-inline:
            type: INLINE
            props: { algorithm-expression: ds$->{user_id % 2} }
          table-inline:
            type: INLINE
            props: { algorithm-expression: t_order_$->{order_id % 10} }
```

> **关键认知**：**ShardingSphere 不会自动解决跨库 JOIN 和分布式事务**——它能路由 SQL、归并结果，但**跨库事务仍需配合 Seata**，跨库 JOIN 也应**尽量避免而不是依赖框架归并**。

## 七、扩容：分完之后怎么加机器

**取模路由最大的痛点**：从 2 库扩到 4 库，几乎**全量数据都要迁移**。三种应对：

| 方案 | 做法 | 代价 |
|---|---|---|
| **停机迁移** | 停服 → 导出 → 按新规则导入 → 改配置 → 启动 | 简单，但**要停机**，大表可能数小时 |
| **双写迁移**（业界主流） | ① 新旧两套规则**双写**（旧库为主，新库同步写）；② 后台程序按新规则**搬历史数据**并校验；③ 数据追平后**灰度切换读**到新库；④ 确认无误后**停止双写**、下线旧库 | 无需停机，但需开发双写逻辑、数据校验与回滚预案 |
| **提前多分**（最优） | 一开始就规划**足够多的逻辑分片**（如 32 张表），但只部署少量物理库 | 需要前期规划，但后期扩容成本最低 |

> **最省事的策略是"提前多分"**：一开始就分 32 张表但只部署 2 个库，每库挂 16 张表；未来加库时只需把**整张表搬到新库**，**路由规则完全不变**，无需数据重算。这叫**逻辑分片数远大于物理节点数**。

## 八、面试问答

**Q1：分库分表的时机是什么？**

两个前提 + 一个经验值。**前提一**：业务数据确实在持续快速增长；**前提二**：常规优化手段**已经用到极限**——索引、SQL 调优、主从读写分离、缓存、冷数据归档都做过，仍然存在瓶颈；**并且出现了明确的资源瓶颈**，如 IO 瓶颈（磁盘/网络 IO）或 CPU 瓶颈（聚合查询、连接数过多）。**经验值**是单表数据量达到 **1000 万行或超过 20G**。但要强调：**1000 万不是硬性红线**——如果都是主键查询，两三千万也能跑得很好；如果大量聚合查询，几百万就到极限。而且**分库分表前必须先确认瓶颈真的是数据量，而不是查询写法**——生产中大量"以为是数据量大"的慢查询，最后发现只是缺一个联合索引。

**Q2：分库分表有哪些策略？**

分两大方向四种策略。**垂直方向**：① **垂直分库**——按业务把不同表拆到不同库（用户库、订单库、商品库），提高磁盘 IO 和连接数上限，实现业务隔离；② **垂直分表**——按字段拆，冷热分离，把 `text`/`blob` 这类大字段挪到附表，减少单页行数、提高 Buffer Pool 命中率。**水平方向**：③ **水平分库**——同一个库的数据按路由规则拆到多个库，解决单库的数据量和并发瓶颈；④ **水平分表**——同一张表的数据拆到同库内的多张表，解决单表数据量过大的问题。一句话概括：**垂直是按"列/业务"切，水平是按"行"切**。实际项目通常组合使用：先垂直分库隔离业务，再垂直分表拆大字段，最后对数据量最大的表做水平分表 + 水平分库。

**Q3：分库分表后会带来哪些问题？怎么解决？**

四个核心问题：① **分布式事务一致性**——跨库操作无法用一个本地事务，**最优解是让一个事务落在一个库里**（按业务边界设计）；必须跨库时用 Seata 的 AT/TCC 或本地消息表 + 最终一致性，并做对账兜底。② **跨节点 JOIN**——订单在库 1、用户详情在库 2 无法 JOIN，方案是**冗余高频关联字段**（用户名、商品名写进订单表）、应用层分别查询后组装，或同步到 Doris 做宽表。③ **跨节点分页排序**——各分片各取前 `offset+limit` 条再内存归并截取（深分页代价高），复杂场景交给 ES/Doris。④ **主键避重**——用**雪花算法**生成全局唯一且趋势递增的 ID。

**Q4：分片键怎么选？路由规则有哪些？**

**分片键的选择原则是"让高频查询不跨库"**——通常选 `user_id` 或 `tenant_id`，因为业务查询大多带这个条件；如果选 `order_id` 做分片键，则"查某用户的全部订单"就变成跨所有库的查询。**路由规则**主要有四种：① **取模**（`hash(key) % N`）分布均匀，但**扩容时几乎全量数据要迁移**；② **范围**（1~100 万一个库）扩容方便，但**数据倾斜**，递增 ID 下热点集中在最后一个分片；③ **一致性哈希**扩容时只迁移约 1/N 的数据，但实现复杂、需要虚拟节点解决倾斜；④ **按时间分表**归档方便，但热点在当期。工程上常见做法是**先按范围分库、库内再取模分表**，兼顾扩容便利与分布均匀。

**Q5：分库分表后怎么扩容？**

关键是**避免"取模扩容导致全量迁移"**。三种方案：① **停机迁移**——停服、按新规则导出导入，简单但要停机；② **双写迁移**（业界主流）——新旧两套规则**双写**，后台程序按新规则搬历史数据并校验，数据追平后**灰度切换读**，确认无误后停止双写、下线旧库，全程不停机；③ **提前多分**（最优）——一开始就规划**足够多的逻辑分片**（如 32 张表）但只部署少量物理库，未来加库时只需把**整张表搬到新库**，路由规则完全不变，无需重算数据。核心思想是让**逻辑分片数远大于物理节点数**。

**Q6：用什么中间件？ShardingSphere 的 JDBC 和 Proxy 怎么选？**

主流是 **Apache ShardingSphere**（Apache 顶级项目，提供数据分片、读写分离、数据加密、影子库压测），另有 MyCat（社区活跃度下降，新项目不建议）。**ShardingSphere-JDBC 是客户端直连**，以 jar 包引入，无额外部署、性能高（无网络跳转），适合 Java 应用；**ShardingSphere-Proxy 是数据库代理**，独立部署，应用像连普通 MySQL 一样连它，**对应用透明、跨语言**，代价是多一跳网络且代理本身要高可用。选择上：**单一 Java 技术栈、追求性能选 JDBC；多语言异构、要求对应用透明选 Proxy**，两者也可混合部署。最后要强调——**中间件不会自动解决跨库 JOIN 和分布式事务**，跨库 JOIN 应尽量避免而非依赖框架归并，跨库事务仍需配合 Seata。
