# 与 MySQL 的差异：两个根设计

## 一、问题场景

选型会上被问「为什么这个项目用 PostgreSQL 不用 MySQL」，最常见的两种回答都拿不到分：

- 「PG 功能更强、更标准」——**强在哪、标准体现在哪个具体决策上？**说不出来就是没选过。
- 「PG 性能更好」——这是错的说法。**同等场景下两者的差距通常小于一个数量级，而各自有明确的优势区**。

要答好这道题，得先答另一道更基础的：**这两个数据库在存储层的两个根设计上，选择了相反的路**。差异清单不是背下来的，是从这两个选择推出来的。

## 二、根设计一：多版本放在哪里 {#root-one}

两者都叫「MVCC」，但**旧版本存放的位置完全相反**，这是后面一半差异的源头。

```
【MySQL / InnoDB】旧版本挪走，行内只留指针
   ┌─────────────────────────────────┐
   │ 聚簇索引页（按主键组织）           │
   │  ┌───────────────────────────┐  │
   │  │ id=100 │ ... │ DB_ROLL_PTR │──┼──▶ undo 回滚段
   │  └───────────────────────────┘  │    ┌──────────┐
   │         行内只有「当前版本」       │    │ 旧版本链  │
   └─────────────────────────────────┘    └──────────┘
                                          由 purge 线程异步清理

【PostgreSQL】旧版本不动，新版本另写一行
   ┌─────────────────────────────────────────────┐
   │ 堆表页（heap，物理顺序，与主键无关）            │
   │  ┌──────────────────────────┐               │
   │  │ ctid=(0,1) xmin=100 xmax=150 │ ← 旧版本，还占着位  │
   │  ├──────────────────────────┤               │
   │  │ ctid=(0,2) xmin=150 xmax=0   │ ← 新版本        │
   │  └──────────────────────────┘               │
   └─────────────────────────────────────────────┘
      旧版本要等 VACUUM 来标记可复用
```

一句话概括两者的分工哲学：

| | MySQL | PostgreSQL |
|---|---|---|
| 旧版本位置 | undo 回滚段（**表外**） | 堆表页内（**表内**） |
| 写入路径 | 原地修改 + 写 undo | 写新版本 + 标记旧版本 |
| 清理动作 | `purge` 线程异步清理 undo，**对用户透明** | `VACUUM` 后台任务，**需要监控和调参** |
| 空间归还 | undo 空间自动截断 | `VACUUM` 只标记复用、**不还给 OS**；要还须 `VACUUM FULL`（排他锁）|

### 2.1 这条设计推出的五条差异 {#root-one-diff}

**① 表会膨胀，且膨胀是常态而非事故。** MySQL 的 `ibd` 文件在大量删除后也可能不缩，但那是因为页内空洞；PG 是**死元组实打实占着页**。一张反复更新的表，逻辑上 100 万行、物理上占 300 万行的空间，是 PG 的典型状态。

**② 长事务的代价完全不同。** MySQL 里长事务的风险是 undo 涨、历史版本链变长、锁持有久。PG 里多一层更硬的约束：**VACUUM 只能清理「比所有活跃快照都旧」的版本**——一个开了两小时不提交的事务，会把清理水位钉在两小时前，**这两小时内全库产生的所有死元组都清不掉**。所以「长事务拖死库」在 PG 上是可以真实发生的，见 [MVCC 与 VACUUM](/database/postgresql/mvcc-and-vacuum#long-transaction)。

**③ UPDATE 的真实成本更高。** MySQL 的 UPDATE 若没改索引列，是页内原地改 + 写一条 undo。PG 的 UPDATE 是**写一个全新行版本**（可能触发新页分配），并且**每个索引都插入一条新索引项**（主键索引、所有二级索引都要改）。所以 PG 表上索引越多，写放大越重。

**④ 于是有了 HOT 更新这个补丁。** PG 有一条重要优化：如果**被更新的列没有被任何索引引用**，且新版本能放进**同一页**，就不动索引，只改行版本指针（Heap-Only Tuple）。这就是 PG 建索引时要考虑「这个列值不值得上索引」的现实理由——**每一个多余索引都在剥夺 HOT 的机会**。

**⑤ count(\*) 不会更快，但可以靠索引免回表。** PG 的 `count(*)` 同样要扫描，但若表做过 VACUUM（维护了可见性映射），`Index Only Scan` 可以完全不回表。

## 三、根设计二：索引里存什么 {#root-two}

第二个根设计决定了两者「回表」的成本结构。

| | MySQL / InnoDB | PostgreSQL |
|---|---|---|
| 表的组织 | **聚簇索引即表**（按主键有序） | **堆表无序**，主键只是其中一个索引 |
| 二级索引叶子存 | **主键值** | **行指针 `ctid`**（页号 + 行偏移）|
| 回表方式 | 拿主键回聚簇索引做**第二次 B+ 树查找** | 拿 `ctid` **直接定位物理页** |
| 「二级索引自带主键」 | 是（天然覆盖） | 否 |
| 覆盖索引怎么写 | 让查询列被索引包含即可 | 必须显式 `INCLUDE (col)` |
| 无主键的表 | 隐式建 6 字节 rowid，仍是聚簇 | 就是普通堆表，**没有隐式主键** |
| 随机主键的代价 | 聚簇索引页分裂、写放大 | 堆表不受影响，只影响主键索引自己 |

**推论一：PG 的回表是「一次定位」，MySQL 是「二次查找」。** 单行回表 PG 通常更便宜——因为 `ctid` 是物理地址，不需要再走一遍 B+ 树。但 PG 没有「二级索引自带主键」这条便利，所以**同样的查询在 MySQL 上碰巧是覆盖索引，在 PG 上就不是**。

**推论二：PG 上「主键选什么」的约束比 MySQL 松。** MySQL 用 UUID 做主键是典型的性能反模式（无序插入撕裂聚簇索引）；PG 的堆表插入顺序与主键无关，**UUID 主键不会造成堆表页分裂**——但你仍要权衡 UUID 作为索引键的体积与比较成本。

**推论三：PG 的 `CLUSTER` 是一次性动作，不是持续状态。** MySQL 的聚簇是结构性的、永久有效；PG 的 `CLUSTER` 按某个索引重排一次物理顺序，**后续写入又会打乱**，需要反复执行（或交给 `pg_repack`）。所以「表按时间范围查得快」在 MySQL 上靠聚簇，在 PG 上通常靠 BRIN 索引或分区——见 [索引体系与数据类型](/database/postgresql/index-and-types#brin)。

## 四、完整差异清单 {#diff-table}

把两个根设计能推出的差异集中在一张表里，剩下的是产品层面的选择：

| 维度 | MySQL 8.0 | PostgreSQL 16 | 根源 |
|---|---|---|---|
| **默认隔离级别** | `REPEATABLE READ` | `READ COMMITTED` | 产品选择 |
| **隔离级别实现** | 快照读（ReadView） | 快照读（快照 xmin/xmax） | 同源不同实现 |
| **可串行化** | 加锁，易死锁、性能差 | **SSI**（乐观检测，冲突才 abort） | 产品选择 |
| **事务 ID** | 48 位 `trx_id` | **32 位 XID，会回卷** | 存储设计 |
| **DDL 的事务性** | 隐式提交，**不可回滚** | **DDL 在事务内，可回滚** | 产品选择 |
| **加列带默认值** | 8.0 起 INSTANT | **11 起也是元数据操作** | 两者都已解决 |
| **连接模型** | 一连接一线程 | **一连接一进程（更重）** | 进程 / 线程模型 |
| **数据类型** | 较少，JSON 支持较晚 | **JSONB / 数组 / 范围 / 几何 / 自定义类型** | 产品定位 |
| **索引类型** | B+ 树、全文、哈希（内存） | **B-tree / Hash / GIN / GiST / SP-GiST / BRIN** | 产品定位 |
| **部分索引 / 表达式索引** | 8.0 有函数索引，**无部分索引** | 两者都支持 | 产品定位 |
| **UPSERT** | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT DO UPDATE` | 语法 |
| **返回写入结果** | 需再查一次 | **`RETURNING`** | 语法 |
| **复制主体** | binlog（逻辑）为主 | **WAL 物理流复制**为主 + 逻辑复制 | 存储设计 |
| **从库回放并行度** | 支持并行（组提交 / 写集） | **物理复制回放是单进程**（逻辑复制 16 起支持并行） | 产品选择 |
| **在线 DDL 生态** | `gh-ost` / `pt-online-schema-change` 成熟 | 场景较少，`pg_repack` 解决膨胀 | 生态 |

> **读这张表的正确方式**：不要把它读成「PG 赢了几格」。每一格都是一次取舍 —— PG 拿到了 DDL 事务性和类型系统，代价是 VACUUM 这套必须有人管的运维面；MySQL 拿到了从库并行回放和成熟的在线 DDL 生态，代价是 DDL 不可回滚、类型系统保守。**能说出代价的那一格，才是你真正理解的那一格。**

## 五、选型判据 {#selection}

面试里问「你选哪个」，标准答案不是某个名字，而是**判据 + 代价**。

| 场景特征 | 建议 | 判据 |
|---|---|---|
| 复杂查询多（多表 Join、窗口函数、CTE、递归） | **PG** | 优化器更强，连接算法与统计信息都更完备 |
| 数据形态复杂（JSON 需要索引与查询、数组、范围、地理） | **PG** | `JSONB` + GIN 是真正的可索引方案，不是"存个字符串" |
| 需要强事务语义的 DDL 迁移（多步变更要原子） | **PG** | DDL 可回滚，迁移脚本能放进一个事务 |
| 已有大量 MySQL 运维经验 / 云厂商托管生态绑定 | **MySQL** | 运维能力是真实成本，换库要重买 |
| 单实例高并发短连接（大量小事务） | **MySQL** | 连接模型更轻（线程 vs 进程） |
| 读多写少、主从扩展为主 | 两者皆可 | MySQL 从库并行回放略优 |
| 写入极频繁且表上索引多 | 需实测 | PG 的写放大更重（每个索引都要改） |
| 需要 `ON CONFLICT` / `RETURNING` 简化应用逻辑 | **PG** | 少一次往返，少一个竞态 |

**一句话收口**：**PG 是「数据库能力更全、运维责任更重」，MySQL 是「能力够用、运维更省心」。**选哪个取决于团队能不能承担那份额外责任——**答不出"谁来管 autovacuum"，就不该选 PG。**

## 六、代价与反模式 {#costs}

选型题的高分答法一定包含「我们放弃了什么」。PG 侧的代价清单：

| 代价 | 具体表现 | 缓解手段 |
|---|---|---|
| **VACUUM 必须有人管** | 膨胀、事务 ID 回卷、autovacuum 拖 IO | 监控 `n_dead_tup` 与 `age(datfrozenxid)`；关键表单独设 autovacuum 参数 |
| **写放大** | UPDATE 写新版本 + 改所有索引 | 精简索引；利用 HOT；大批量更新分批做 |
| **连接成本高** | 一进程一连接，几百连接就吃满内存 | 必须上 PgBouncer（见 [复制与运维](/database/postgresql/replication-and-ops#pool)）|
| **`work_mem` 是每个操作** | 一个查询里多个排序/哈希各占一份 | 按「并发 × 操作数」估算，不是按连接数 |
| **人才与生态** | 国内 DBA 以 MySQL 为主 | 自建监控与巡检脚本 |
| **从库回放单进程** | 大事务回放慢，延迟陡增 | 控制单事务规模；逻辑复制分流 |

**三个典型反模式**：

1. **拿 MySQL 的经验直接管 PG** —— 不加连接池、不配 autovacuum、不做 VACUUM 监控。**PG 不是"换个语法的 MySQL"。**
2. **给每个查询条件都建索引** —— 直接摧毁 HOT 的机会，把 20% 的写性能换成 5% 的读收益。
3. **用 `VACUUM FULL` 做日常膨胀清理** —— 它要 `ACCESS EXCLUSIVE` 锁，**等于停表**。日常该调 autovacuum，极端场景用 `pg_repack`。
