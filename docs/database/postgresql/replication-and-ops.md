# 复制、高可用与运维调优

## 一、问题场景

三个上线后才暴露的运维问题：

1. **从库延迟越滚越大**，主库 CPU 才 30%，从库的磁盘却写满了——**找不到谁在拖慢它**。
2. **偶尔有查询在从库上被"莫名取消"**，报 `canceling statement due to conflict with recovery`。
3. **连接数一涨就变慢**，`max_connections` 调到 2000 之后内存直接被吃光。

这三个问题有一个共同背景：**PG 是「一连接一进程」+「物理复制回放单进程」的架构**。这套架构在正常情况下很稳，但它的瓶颈位置与 MySQL 完全不同——**照 MySQL 的直觉去优化，会优化错地方**。

## 二、两种复制方式 {#replication}

PG 同时提供两条复制路径，定位完全不同：

| | **物理流复制** | **逻辑复制** |
|---|---|---|
| 传输内容 | **WAL 字节流**（物理页改动）| **逻辑变更**（解码后的行级增删改）|
| 粒度 | **整个实例**（所有库、所有表、索引、系统表）| **表级**（publication / subscription）|
| 从库可写？ | ❌ 只读 | ✅ **可写** |
| 跨大版本 | ❌ 必须同版本（小版本可异）| ✅ 可跨版本、跨平台 |
| 复制 DDL | ✅ 自动（物理一致）| ❌ **不复制**，表结构要手动同步 |
| 复制序列 | ✅ 自动 | ❌ **不复制**，需自行处理 |
| 典型用途 | **高可用、只读扩展** | **数据汇聚、跨版本迁移、异构同步** |

**这张表最重要的一行是「DDL」**：物理复制天然带着一切（包括索引、序列、系统视图），所以它是**做高可用的默认选择**；逻辑复制灵活，但**你必须自己保证两边表结构一致**——这是它最常见的翻车点。

```
【物理流复制】
   主库 ──walsender── WAL 字节流 ──▶ walreceiver ──▶ startup 进程回放
                                                      ▲
                                          从库：字节级一致的完整副本
                                               只读、可承接读流量

【逻辑复制】
   主库 ──逻辑解码── 行级变更 ──▶ 订阅端 apply worker
                                    ▲
                       可选择哪些表、可写到可写库
                       但 DDL / 序列 / 大对象不在其中
```

> **补充一点**：PG 16 起，逻辑复制支持**并行应用**，并且可以从备库做逻辑解码（减轻主库解码负担）。物理复制的回放则始终是单进程——见[下一节](#lag)。

## 三、同步提交级别：synchronous_commit 的五个档 {#sync}

同步复制不是开关，是**五个级别**——它决定"提交返回时，数据到底安全到了哪一步"：

| 级别 | 提交返回时数据到哪 | 宕机丢失窗口 | 延迟代价 |
|---|---|---|---|
| `off` | 本地 WAL 交给 OS（**未 fsync**）| 可丢若干秒（OS 崩溃）| 最低 |
| `local` | 本地已 fsync | 本地安全，**从库可能没收到** | 低 |
| `remote_write` | 从库**收到并写入 OS 缓冲** | 从库 OS 崩溃会丢 | 中 |
| **`on`（默认）** | 从库**收到并完成 fsync** | 最常用的同步档 | 中高 |
| `remote_apply` | 从库**已回放**（查询可见）| 最强 | 最高 |

**一个能直接把候选人区分开的细节**：

> `synchronous_commit` 的默认值是 `on`，但**只有在配置了 `synchronous_standby_names` 时，同步语义才真正生效**。没配的话，它就是一个异步集群——**"我配了 synchronous_commit=on 所以不会丢数据"是一句错的陈述**。

配置形态也有三种，取舍不同：

| 写法 | 语义 | 适用 |
|---|---|---|
| `FIRST 1 (s1, s2)` | 按列出的**优先级**取第一个可用的 | 有明确主备优先级 |
| `ANY 1 (s1, s2)` | **任意一个**确认即可（10+）| 多从库平权，追求可用性 |
| `ANY 2 (s1, s2, s3)` | **法定人数**（12+）| 要求"至少两份副本"才返回 |

## 四、从库延迟与查询冲突 {#lag}

### 4.1 两个 PG 特有的成因

**成因 A：物理复制回放是单进程。**

主库可以开 64 核并行提交事务，**从库只有一个 `startup` 进程在做回放**。主库并行度越高，从库越容易追不上——这不是"从库配置差"，而是**架构决定的回放上限**。

| | MySQL | PostgreSQL |
|---|---|---|
| 回放机制 | 支持**并行**（基于组提交 / 写集）| **物理复制单进程**（PG 16 起逻辑复制才支持并行）|
| 缓解手段 | 调并行度参数 | **控制单事务规模**；逻辑复制分流 |

**成因 B：大事务要等 WAL 到齐。**

一个改了 2000 万行的事务，从库要等这一整段 WAL 收完才能开始回放，体感上就是"延迟突然飙到几分钟又突然归零"。缓解办法是**应用侧把大事务拆小**——这在 PG 上不是风格偏好，是**硬性运维要求**。

### 4.2 查询冲突：从库上最反直觉的一件事

在从库上跑一个长查询时，**回放进程可能与它冲突**：回放要清理旧版本，而那个长查询的快照还需要那些版本。PG 必须在两者中选一个——它的默认选择是**牺牲查询**：

```
从库上的长查询  ─┐
                ├─▶ 冲突！
WAL 回放要清理  ─┘
                       │
        默认行为：等 max_standby_streaming_delay（默认 30s）
                       │
                       ▼
        超时就把从库上的查询「取消掉」：
        ERROR: canceling statement due to conflict with recovery
```

三个参数决定这个行为：

| 参数 | 默认 | 作用 |
|---|---|---|
| `max_standby_streaming_delay` | 30s | 等待查询结束的上限，超时就取消查询 |
| `max_standby_archive_delay` | 30s | 归档恢复场景的同类参数 |
| `hot_standby_feedback` | `off` | **打开后从库会告诉主库"我还有查询在跑，别清那些版本"** |

**`hot_standby_feedback` 是一个典型的取舍**：

| | 关闭（默认）| 打开 |
|---|---|---|
| 从库长查询 | 可能被取消 | 不会被取消 |
| 主库 | 正常清理 | **清理水位被从库拖住 → 主库膨胀** |

**换句话说：这个参数是把「从库查询被中断」的风险，换成了「主库膨胀」的风险。** 这是个纯粹的取舍，没有"更好的那个"——取决于你的从库是"只跑报表的长查询"还是"承接线上读流量"。**能说清这个取舍，比记住参数默认值有价值得多。**

### 4.3 延迟怎么量

```sql
SELECT client_addr, state, sync_state,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

三个 lag 分别对应"写到 OS / 完成 fsync / 已回放"三个阶段的落后时间（PG 10+）。**`replay_lag` 才是业务可见的延迟**——只看 `write_lag` 会低估问题。

## 五、高可用与故障转移 {#ha}

PG **自身不提供自动故障转移**（与 MySQL 一样需要外挂）。主流方案：

| 方案 | 仲裁依赖 | 特点 |
|---|---|---|
| **Patroni** | etcd / Consul / ZooKeeper | 当前最主流；支持自动切换、回调脚本（改 VIP / 通知 LB）、REST API 查状态 |
| repmgr | 无强仲裁（可选）| 更轻量，配置简单，但防脑裂能力弱于 Patroni |
| 云托管 | 厂商负责 | RDS / 云原生 PG，把切换交给平台 |

**故障转移真正的难点不在"切"，而在"确认旧主真的不会再写"**。切换动作本身几秒钟就能做完；做错的是**没有完成隔离就提升新主**，结果两个节点都在接受写入。

所以这道题的标准结构是：

```
① 判定（心跳 / 仲裁）—— 谁来判、判多快（对应 RTO）
        │
② 隔离（fencing）—— ⚠ 最容易被跳过的一步
        必须让旧主彻底无法写：关机 / 断网 / 吊销存储
        │
③ 提升（promote）—— 把从库切成可写
        │
④ 引流（VIP / DNS / 中间件重定向）
        │
⑤ 补齐（旧主回来时如何重新加入，是否需要重建）
```

**第 ② 步的完整讨论见 [冗余与故障转移 · 脑裂与 fencing](/high-availability/redundancy-failover#split-brain)**——那里的结论对 PG 完全适用：**没有 fencing 的自动切换，是把"可用性事故"换成"数据一致性事故"，而后者更贵。**

## 六、连接池：PG 绕不过去的一层 {#pool}

这一节的结论很硬：**生产环境的 PG 不配连接池是不可接受的**。

原因在进程模型：

| | MySQL | PostgreSQL |
|---|---|---|
| 连接单位 | 线程 | **进程** |
| 单连接基础开销 | 较小（线程栈）| **较大**（独立进程，含各自的内存结构）|
| 几百个空闲连接 | 可接受 | **吃掉大量内存，且上下文切换成本高** |
| 调大 `max_connections` | 常见做法 | **反模式**——连接数是"成本"不是"能力"|

### 6.1 PgBouncer 的三种模式

| 模式 | 服务端连接何时归还 | 兼容性 | 适用 |
|---|---|---|---|
| `session` | 客户端断开时才归还 | ✅ 完全兼容 | 连接数不多、或有大量会话级状态 |
| **`transaction`** | **事务结束就归还** | ⚠️ 有会话级限制 | **绝大多数场景的推荐** |
| `statement` | 每条语句后归还 | ❌ 限制最严 | 特殊场景，极少用 |

### 6.2 `transaction` 模式的五条限制

这是面试常追问的点——**用 `transaction` 模式就放弃了"会话"这个概念**：

| 不能用 | 为什么 |
|---|---|
| **会话级 `SET`**（如 `SET search_path`）| 下一条语句可能落在另一个服务端连接上 |
| **`PREPARED STATEMENT`** | 预处理语句绑定在具体连接上（PgBouncer 1.21+ 有 `max_prepared_statements` 支持，需显式开启）|
| **临时表** | 会话结束即消失，而会话已经被复用 |
| **`LISTEN` / `NOTIFY`** | 通知是会话级的 |
| **`WITH HOLD` 游标、advisory lock** | 都依赖会话存续 |

**实践口径**：应用里凡是要用这些特性，就必须显式避开 `transaction` 模式（单独走一个 `session` 模式的池，或改设计）。**这属于"引入连接池时必须一起改的应用侧约束"**，漏了就会在生产上以"偶发、看起来毫无规律"的形式暴露。

### 6.3 池大小怎么定

**不是越大越好**。判断依据是**数据库能并行处理的真实请求数**，而不是应用侧的并发数：

```
   应用并发 1000 个请求
        │
        ├─ 其中 950 个在做业务计算 / 等下游 RPC（不需要数据库连接）
        │
        └─ 真正同时打数据库的只有 50 个
                │
                ▼
        池大小应该围绕「50 + 余量」来定，
        而不是围绕 1000 定
```

连接数超过数据库的并行能力后，多出来的连接只会**排队 + 抢锁 + 争 CPU**，吞吐反而下降。**"连接池越小，系统越快"在 PG 上是常态而非反直觉。**

## 七、参数调优清单 {#tuning}

按"影响面 × 常见误配"排序：

| 参数 | 建议起点 | 常见误配 |
|---|---|---|
| **`shared_buffers`** | 内存的 **25%** | 设得过小（默认 128MB），把压力全推给 OS 缓存 |
| **`work_mem`** | 4~16 MB，谨慎 | **最大的坑：它是「每个排序/哈希操作」的量，不是每连接** |
| **`random_page_cost`** | SSD 上 **1.1** | 留默认 4.0（按机械盘设的）→ 优化器高估索引成本、误选全表扫 |
| `effective_cache_size` | 内存的 50~75% | 误解为"要分配这么多"——它**只是给优化器的提示**，不占内存 |
| `maintenance_work_mem` | 512 MB~1 GB | 太小 → VACUUM / 建索引极慢 |
| `max_connections` | 保持小 + 上连接池 | 盲目调大（见[上一节](#pool)）|
| `max_wal_size` / `checkpoint_timeout` | 按写入量调大 | 太小 → checkpoint 频繁、IO 抖动 |

### 7.1 `work_mem` 为什么会吃爆内存

这是 PG 上最容易算错的一个参数，因为它的语义是"**每个操作**"：

```
   总内存峰值 ≈ 并发查询数 × 单个查询里的「排序 + 哈希」节点数 × work_mem
                ─────┬─────    ────────────┬────────────
                     │                    │
                不是连接数              一个复杂查询可能有 3~5 个
```

代入数字：`max_connections = 200`，每个查询平均 3 个内存敏感节点，`work_mem = 64MB`：

```
   200 × 3 × 64 MB ≈ 38 GB       ← 物理内存只有 32 GB
```

**所以 `work_mem` 应该按「并发 × 节点数」反推，而不是"内存大就设大点"。** 需要大内存的单条查询，正确的做法是**在那条语句上临时 `SET LOCAL work_mem`**，而不是抬全局默认值。

> **一句话**：`shared_buffers` 是"给定就用"，`work_mem` 是"**用了可能同时用好几份**"。这两者的差别是 PG 内存事故的主要来源。

## 八、巡检与慢查询 {#monitoring}

### 8.1 慢查询

| 工具 | 用途 |
|---|---|
| `pg_stat_statements` 扩展 | **按总耗时 / 平均耗时 / 调用次数排序**，找出真正的问题 SQL（比单条慢日志更有价值：一条 10ms 但每秒 1 万次的 SQL 比一条 5s 的更值得优化）|
| `log_min_duration_statement` | 记录超过阈值的语句到日志 |
| `auto_explain` | **自动把慢查询的执行计划写进日志**——排查线上"偶发慢"的关键工具 |

### 8.2 七项日常巡检

| # | 检查项 | 语句要点 | 风险 |
|---|---|---|---|
| 1 | **事务 ID 年龄** | `max(age(datfrozenxid))`（库级）+ `age(relfrozenxid)`（表级）| **回卷停服**，见 [回卷](/database/postgresql/mvcc-and-vacuum#wraparound) |
| 2 | **膨胀** | `n_dead_tup` TOP 10 + `last_autovacuum` | 性能持续劣化 |
| 3 | **长事务** | `now() - xact_start > 5 min` | 顶住清理水位，全库膨胀 |
| 4 | **复制延迟** | `pg_stat_replication.replay_lag` | 读旧数据 |
| 5 | **复制槽积压** | `pg_replication_slots` 的 `pg_wal_lsn_diff` | **⚠ WAL 撑爆磁盘**，主库直接满盘 |
| 6 | **连接数使用率** | `count(*) / max_connections` 与 `pg_stat_activity.state` 分布 | 雪崩前兆 |
| 7 | **无用索引** | `pg_stat_user_indexes.idx_scan = 0`（排除约束类）| 无谓写放大 |

**第 5 项值得单独强调**：逻辑复制用复制槽记录消费位置，**如果订阅端停了而槽还在，主库会无限保留 WAL**，直到磁盘写满——**主库宕机**。这是逻辑复制最常见的生产事故，且它和"复制延迟"是两件事：延迟大但不积压 WAL 是慢，槽积压是**要爆盘**。

```sql
-- 复制槽积压量（应纳入告警）
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;
```

> **本板块收口**：PostgreSQL 的五篇串成一条因果链——**多版本留在行里**（[差异根源](/database/postgresql/vs-mysql#root-one)）→ 所以需要 **VACUUM**（[版本与清理](/database/postgresql/mvcc-and-vacuum)）→ 所以**长事务会拖死全库**、**事务 ID 会回卷** → 所以**索引与类型要按语义选**（[索引体系](/database/postgresql/index-and-types)）→ 而**锁的层次与连接模型**又决定了高可用与运维的形态（本篇）。**这条链的每一环都不是独立知识点。**
