# 事务：ACID 与隔离级别

## 一、问题场景

两个用户同时对同一条账户记录转账，如果没有事务：

```
时刻  会话 A（转出 100）              会话 B（转入 100）            balance
 t1   read balance → 1000                                          1000
 t2                                   read balance → 1000          1000
 t3   write balance = 900                                          900
 t4                                   write balance = 1100         1100  ← 少了 900 那一步
```

A 扣的 100 被 B 的写入**覆盖**了。事务要解决的就是这类问题：**让一组操作要么全部生效，要么全部不生效，并且并发执行时互相不干扰。**

**结论先行**：ACID 是四个特性，但面试真正的分水岭在于——**能把每个特性对应到具体的实现机制**（原子性→undo log、持久性→redo log、隔离性→锁+MVCC），以及**能说清 InnoDB 的 RR 级别到底解不解决幻读**（这是最容易答错的一题）。

## 二、ACID 四大特性

| 特性 | 含义 | 通俗理解 |
|---|---|---|
| **原子性**（Atomicity） | 事务是不可分割的最小操作单元，要么全部成功，要么全部失败 | 转账的"扣款"和"入账"必须同时成立 |
| **一致性**（Consistency） | 事务完成后，数据必须保持一致的业务状态 | 转账前后两人**总额不变** |
| **隔离性**（Isolation） | 并发事务之间相互不受影响，如同串行执行 | A 的事务中间状态不能被 B 看到 |
| **持久性**（Durability） | 事务一旦提交或回滚，对数据的改变是永久的 | 提交成功后即使断电也不丢 |

### 重点：每个特性靠什么实现

这是把 ACID 从"背概念"变成"懂机制"的关键：

| 特性 | 实现机制 |
|---|---|
| **原子性** | **undo log**——记录修改前的数据，回滚时反向执行 |
| **持久性** | **redo log**——WAL 机制，先写日志再刷数据页，宕机后重放恢复 |
| **隔离性** | **锁 + MVCC**——写写之间靠锁，读写之间靠 MVCC |
| **一致性** | **前三者共同保证的结果**，不是某个独立机制 |

> **注意最后一行**：一致性不是一个"实现"，而是原子性 + 持久性 + 隔离性都做到位之后**自然达成的状态**。面试如果被问"一致性靠什么保证"，答"靠 undo log 保证原子性、redo log 保证持久性、锁和 MVCC 保证隔离性，三者共同保证一致性"，比答"靠 XXX 机制"要准确。日志细节见 [日志体系](/database/mysql/log)，隔离性的实现见 [MVCC 与锁](/database/mysql/mvcc)。

## 三、并发事务的三大问题

用**一条记录**（`id = 1, name = '张三', balance = 1000`）把三个问题串起来，最容易记住：

### ① 脏读（Dirty Read）——读到了"没提交"的数据

```
会话 A                                会话 B
begin;
update balance = 900                   
                                       begin;
                                       select balance → 900   ← 读到 A 未提交的数据
rollback;                              commit;  ← 实际用 900 做了决策，但那个值消失了
                 ↓
       B 读到的是一个【从未真正存在过】的值
```

**本质**：读到了别的事务**尚未提交**的中间状态。

### ② 不可重复读（Non-Repeatable Read）——同一事务内两次读结果不同

```
会话 A                                会话 B
begin;
select balance → 1000
                                       update balance = 900;
                                       commit;
select balance → 900    ← 同一个事务里，两次读同一行，结果变了
```

**本质**：其他事务**修改并提交**了，导致本事务两次读到不同值。焦点在**同一行的内容变化**。

### ③ 幻读（Phantom Read）——"查不到但插不进去"

```
会话 A                                        会话 B
begin;
select * from t where id > 10 → 3 行
                                              insert into t(id) values (11);
                                              commit;
insert into t(id) values (11);  ← 报错：主键冲突
                 ↓
       "我刚才明明查了没有 id=11，为什么插不进去？"
select * from t where id > 10 → 4 行   ← 再查，多出一行"幻影"
```

**本质**：其他事务**插入并提交**了新记录，导致本事务按条件查询的**结果集行数**发生变化。焦点在**结果集的行数**，不是某一行的内容。

### 三个问题的区分表

| 问题 | 读到什么 | 焦点 | 根因 |
|---|---|---|---|
| **脏读** | 其他事务**未提交**的数据 | 单行内容 | 没有隔离未提交事务 |
| **不可重复读** | 其他事务**已提交的修改** | 单行内容变化 | 同一行被改 |
| **幻读** | 其他事务**已提交的插入/删除** | **结果集行数变化** | 有新行进入查询范围 |

> **一句话区分"不可重复读 vs 幻读"**：不可重复读是"**同一行的值变了**"，幻读是"**多出一行（或少了一行）**"。前者靠行锁解决，后者必须靠**间隙锁**——这就是为什么幻读更难解决。

## 四、四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| **Read Uncommitted**（读未提交） | ✅ 会 | ✅ 会 | ✅ 会 | 几乎不用，等于没隔离 |
| **Read Committed**（读已提交） | ❌ 不会 | ✅ 会 | ✅ 会 | Oracle / PostgreSQL 默认 |
| **Repeatable Read**（可重复读） | ❌ 不会 | ❌ 不会 | ⚠️ **理论会，InnoDB 实际基本不会** | **MySQL 默认** |
| **Serializable**（串行化） | ❌ 不会 | ❌ 不会 | ❌ 不会 | 全加锁，并发性能最差 |

**规律**：隔离级别越高，数据越安全，但**并发性能越低**。级别之间是"用并发换一致性"的取舍。

### 重点纠正：MySQL 的 RR 到底会不会幻读

**标准 SQL 规范里，RR 级别确实无法避免幻读**（SQL 标准只要求 RR 解决脏读和不可重复读）。但 **InnoDB 在 RR 级别下已经很大程度上解决了幻读**，靠的是两条路径：

| 读类型 | 触发方式 | 解决幻读的机制 |
|---|---|---|
| **快照读** | 普通 `select`（不加锁） | **MVCC**——RR 下 ReadView **只在第一次 `select` 时生成并复用**，整个事务看到的数据快照一致，新插入的行不在快照里，**看不到** |
| **当前读** | `select ... for update` / `lock in share mode` / `update` / `insert` / `delete` | **临键锁（Next-Key Lock）= 记录锁 + 间隙锁**——锁住记录**之间的间隙**，其他事务无法在间隙中插入新数据，**插不进来** |

```
间隙锁示意：索引上有 10, 20, 30 三条记录

      间隙 (-∞,10)   间隙 (10,20)   间隙 (20,30)   间隙 (30,+∞)
    ────────●─────────●─────────●─────────
            10        20        30

  执行 select * from t where id > 10 for update
  → 锁住 (10, +∞) 的所有间隙
  → 其他事务【无法在 10 到 20 之间插入 id=15】，幻读被阻止
```

**面试口径**：**"MySQL InnoDB 的 RR 级别通过 MVCC 和间隙锁，基本上已经解决了幻读问题"**——不要直接说"RR 还会幻读"，那是标准 SQL 的结论，不是 InnoDB 的实际行为。

> **补充一个边界**：快照读和当前读**混用**时仍可能出现幻读（先快照读看不到，再当前读就看到了）。所以严谨表述是"**基本解决**"，而不是"完全解决"。

### 怎么设置 / 查看隔离级别

```sql
-- 查看当前会话与全局隔离级别（MySQL 8.0）
select @@transaction_isolation;         -- 当前会话
select @@global.transaction_isolation;  -- 全局

-- 设置（8.0 写法；5.7 及以前用 tx_isolation）
set session transaction isolation level read committed;   -- 只影响当前会话
set global  transaction isolation level read committed;   -- 影响新连接

-- 配置文件（my.cnf，推荐的口径）
[mysqld]
transaction-isolation = READ-COMMITTED
```

**RC 与 RR 的差别怎么理解**：本质上是 **ReadView 的生成时机不同**——RC 每次 `select` 都生成新 ReadView（所以能看到别人新提交的数据，即不可重复读），RR 只在事务第一次 `select` 时生成并复用（所以整个事务看到一致快照）。这一点在 [MVCC 与锁](/database/mysql/mvcc) 里会展开。

**为什么有些互联网公司把默认改成 RC？** 因为 RR 的间隙锁会**显著增加锁冲突和死锁概率**，而很多业务场景对不可重复读不敏感。这是"隔离级别 vs 并发性能"的典型工程取舍。

## 五、面试问答

**Q1：事务的 ACID 特性是什么？底层怎么实现？**

ACID 是四大特性：**原子性**——事务是不可分割的最小操作单元，要么全成功要么全失败；**一致性**——事务前后数据必须保持一致的业务状态（如转账前后总额不变）；**隔离性**——并发事务之间互不影响；**持久性**——事务提交后数据永久保存。**底层实现**：原子性靠 **undo log**（记录修改前的数据用于回滚）；持久性靠 **redo log**（WAL 机制，先写日志再刷数据页，宕机后重放恢复）；隔离性靠**锁和 MVCC**（写写靠锁，读写靠 MVCC）；而一致性是**前三者共同保证的结果**，不是某个独立机制。

**Q2：并发事务会带来哪些问题？**

三个：① **脏读**——一个事务读到了另一个事务**尚未提交**的数据，如果对方回滚，读到的就是从未存在过的值；② **不可重复读**——同一事务内两次读**同一行记录**结果不同，因为其他事务修改并提交了，问题焦点在**单行内容**；③ **幻读**——同一事务内按条件查询，发现没有某行，但插入时提示已存在（其他事务插入并提交了），问题焦点在**结果集行数变化**。区分"不可重复读"和"幻读"的关键：前者是"同一行的值变了"，后者是"多出一行"——**后者靠行锁解决不了，必须用间隙锁**。

**Q3：四种隔离级别分别解决什么问题？MySQL 默认是哪个？**

从低到高：**读未提交**——三个问题都避免不了；**读已提交**——解决脏读，仍有不可重复读和幻读（Oracle、PG 默认）；**可重复读**——解决脏读和不可重复读，幻读在标准 SQL 里仍存在（**MySQL 默认**）；**串行化**——三个问题全解决，但事务串行执行，并发性能最差。规律是**隔离级别越高越安全，但并发性能越低**。

**Q4：MySQL 的 RR 级别能解决幻读吗？**

这是容易答错的一题。**标准 SQL 规范里 RR 确实无法避免幻读**，但 **InnoDB 在 RR 级别下已经基本解决了幻读**，靠两条路径：① **快照读**（普通 `select`）走 **MVCC**——RR 下 ReadView 只在事务第一次 `select` 时生成并复用，整个事务看到的数据快照一致，其他事务新插入的行**不在快照里，所以看不到**；② **当前读**（`select ... for update` / `update` / `insert` / `delete`）走**临键锁（Next-Key Lock）= 记录锁 + 间隙锁**，锁住记录之间的间隙，其他事务**无法在间隙中插入新数据**。所以面试时建议说"**MySQL InnoDB 的 RR 通过 MVCC 和间隙锁基本解决了幻读**"——但要注意快照读与当前读**混用**时仍可能出问题，所以是"基本"而非"完全"。

**Q5：为什么有公司把隔离级别从 RR 调整成 RC？**

因为 RR 为了防幻读引入了**间隙锁**，而间隙锁会**扩大锁的范围**——不仅锁住存在的记录，还锁住记录之间的间隙，导致**锁冲突和死锁概率显著上升**，并发写入性能下降。很多业务场景（如电商的读多写少业务）对"不可重复读"并不敏感，所以把默认改为 RC，用更小的锁范围换取更高的并发。这是典型的"**一致性 vs 并发性能**"的工程取舍，不是谁绝对更好。
