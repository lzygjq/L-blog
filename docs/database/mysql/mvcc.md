# MVCC 与锁

## 一、问题场景

一个事务在读 100 万行数据，同时另一个事务在改其中的几行——**为什么读不会阻塞写、写也不会阻塞读**？

如果只靠锁，读要加共享锁、写要加排他锁，两者天然互斥，并发度会非常低（这正是 `Serializable` 级别的问题）。MySQL 在**读已提交（RC）**和**可重复读（RR）**级别下能做到读写不阻塞，靠的就是 **MVCC**。

**结论先行**：MVCC（Multi-Version Concurrency Control，多版本并发控制）的思路是——**不改数据、只留版本**。每行记录带隐藏的事务字段，修改时把旧版本存进 undo log 并用回滚指针串成链表；读取时根据 **ReadView** 判断"哪个版本对我可见"，从而**读到属于自己的那个历史版本**。写操作照常改最新数据，两端各行其道。

## 二、MVCC 的三大核心组件

```
┌─────────────────────────────────────────────────────────────────┐
│  ① 隐藏字段        每行记录自带：事务ID / 回滚指针 / 隐藏主键      │
│  ② undo log 版本链  每次修改存一个旧版本，用回滚指针串成链表        │
│  ③ ReadView        快照读时判断"哪个版本可见"的依据                │
└─────────────────────────────────────────────────────────────────┘
```

### ① 隐藏字段

InnoDB 会在每行记录上**额外加三个隐藏字段**（用户看不到，但真实存在）：

| 隐藏字段 | 含义 |
|---|---|
| **`DB_TRX_ID`** | **最近修改该行的事务 ID**——最近一次 `insert` 或 `update` 它的事务 |
| **`DB_ROLL_PTR`** | **回滚指针**——指向 undo log 中该行的**上一个版本** |
| `DB_ROW_ID` | 隐藏主键（**仅当表没有主键且没有唯一索引时**才生成，见 [索引底层](/database/mysql/index-structure)） |

### ② undo log 版本链

对同一行做多次修改，undo log 会把每个旧版本都保留下来，通过**回滚指针**串成链表：

```
                        当前记录（最新版本）
                  ┌──────────────────────────┐
                  │ id=1  name='张三'         │
                  │ DB_TRX_ID = 30           │   ← 事务 30 改的
                  │ DB_ROLL_PTR ─────┐       │
                  └──────────────────────┼───┘
                                         ▼
                        undo log 中的版本 2
                  ┌──────────────────────────┐
                  │ name='李四'   TRX_ID=20   │
                  │ DB_ROLL_PTR ─────┐       │
                  └──────────────────────┼───┘
                                         ▼
                        undo log 中的版本 1
                  ┌──────────────────────────┐
                  │ name='张三'   TRX_ID=10   │   ← 最早，链表尾部
                  │ DB_ROLL_PTR = NULL       │
                  └──────────────────────────┘

        链表方向：头部最新 ──────────────▶ 尾部最早
        遍历方向：从头开始，沿回滚指针往前走，直到找到"对自己可见"的版本
```

**关键理解**：**undo log 里的旧版本永远不动**。新事务不断在链表头部追加新版本，而读操作根据自己的 ReadView 从头部往尾部找。

### ③ ReadView（读视图）

ReadView 是**快照读时生成的一个"判断依据"**，记录**生成这一刻**哪些事务还活着。四个核心字段：

| 字段 | 含义 |
|---|---|
| **`m_ids`** | 生成 ReadView 时，**当前活跃（未提交）的事务 ID 集合** |
| **`min_trx_id`** | `m_ids` 中的**最小值**——最小活跃事务 ID |
| **`max_trx_id`** | **下一个将要分配的事务 ID**（即当前最大事务 ID + 1） |
| **`creator_trx_id`** | **创建这个 ReadView 的事务 ID**（也就是"我"） |

## 三、可见性判断：五步定序

拿到一个版本（沿版本链逐个检查），按下面的顺序判断它是否可见：

```
给定：当前版本的 DB_TRX_ID = trx_id

① trx_id == creator_trx_id ?
      → 可见 ✅（这是我自己改的，当然能看见）
   否则继续

② trx_id < min_trx_id ?
      → 可见 ✅（该事务在我生成 ReadView 之前就已提交，是既定事实）
   否则继续

③ trx_id >= max_trx_id ?
      → 不可见 ❌（该事务在我生成 ReadView 之后才开始，它的修改与我无关）
   否则继续（落在 [min_trx_id, max_trx_id) 区间）

④ trx_id 不在 m_ids 中 ?
      → 可见 ✅（创建 ReadView 时它已提交）
   否则

⑤ trx_id 在 m_ids 中
      → 不可见 ❌（创建 ReadView 时它还在活跃，未提交）
      → 沿 DB_ROLL_PTR 往前找上一个版本，回到 ① 重新判断
```

**用一句话概括这五步**：

> **"比我小的都可见（已提交），比我大的都不可见（还没开始），中间的看它在不在活跃集合里——在就不提交、不可见，不在就说明已提交、可见。"**

**为什么要往前走版本链**：如果当前版本不可见（写它的事务当时还没提交），说明这个版本的"前一个版本"才是本事务应该看到的状态——所以顺着 `DB_ROLL_PTR` 往前走，直到找到一个可见版本，或者走到 `NULL`（说明这行在本次快照里**不存在**，表现为查不到）。

## 四、RC 与 RR 的本质差异

**这是 MVCC 最核心的一问**：同一套机制、同一份版本链，为什么 RC 会不可重复读、RR 不会？**差别只有一个——ReadView 的生成时机。**

| 隔离级别 | ReadView 生成时机 | 结果 |
|---|---|---|
| **Read Committed（RC）** | **每次 `select` 都生成新的 ReadView** | 每次读到"最新已提交"的状态 → 别人提交了就能看到 → **不可重复读** |
| **Repeatable Read（RR）** | **事务第一次 `select` 时生成，之后复用同一个** | 整个事务固定看同一份快照 → 别人提交了也看不到 → **可重复读** |

```
RC：  select ──▶ 生成 ReadView₁ ──▶ 读到版本 A
         （其他事务提交）
      select ──▶ 生成 ReadView₂ ──▶ 读到版本 B      ← 两次不一致

RR：  select ──▶ 生成 ReadView₁ ──▶ 读到版本 A
         （其他事务提交）
      select ──▶ 【复用 ReadView₁】 ──▶ 仍然读到版本 A   ← 两次一致
```

> **由此可以直接解释"RR 为什么基本没有幻读"**：RR 复用同一个 ReadView，其他事务在快照生成**之后**插入的新行，其 `DB_TRX_ID` 比 `max_trx_id` 大（或落在活跃集合里），**判定为不可见**——所以快照读看不到"幻影行"。而当前读走的是间隙锁路径，见下节。

## 五、快照读与当前读

MVCC 只对**快照读**生效。区分这两类读是理解"什么时候会读到最新数据"的关键：

| 类型 | 触发方式 | 读什么 | 是否加锁 |
|---|---|---|---|
| **快照读**（一致性读） | 普通 `select` | ReadView 判定出的**可见版本**（可能是历史数据） | **不加锁，非阻塞** |
| **当前读** | `select ... for update`、`select ... lock in share mode`、`update`、`insert`、`delete` | **最新版本** | **加锁**（阻塞其他写） |

**注意**：`update` / `delete` / `insert` **本身就是当前读**——它们必须基于最新数据操作，否则会出现"更新丢失"。

> **实践含义**：如果在一段逻辑里需要"读到的数据绝对是最新的，且不能被别人改"，必须用 `select ... for update`（当前读 + 加锁）。用普通 `select` 读到的是快照，可能在下一毫秒就被别人改了。

## 六、InnoDB 的锁：快照读之外的那一半

MVCC 解决读写冲突，**写写冲突必须靠锁**。

### 三种行锁

| 锁类型 | 锁什么 | 作用 |
|---|---|---|
| **记录锁**（Record Lock） | 锁**单条存在的记录** | 阻止其他事务修改这条记录 |
| **间隙锁**（Gap Lock） | 锁**记录之间的间隙**（不含记录本身） | **阻止在间隙中插入新记录 → 防幻读** |
| **临键锁**（Next-Key Lock） | **记录锁 + 该记录之前的间隙锁** | **RR 默认的加锁单位**，同时防修改和防插入 |

```
索引记录：  10        20        30

  间隙锁：    (10,20)         —— 锁住这个区间，别人不能插入 id=15
             
  记录锁：    10             —— 只锁 id=10 这一行
             
  临键锁：  (10,20]  或  (20,30]  —— 左开右闭：既锁间隙又锁右端点记录
```

**为什么 RR 默认用临键锁**：只有锁住**间隙**才能阻止插入，从而在**当前读**场景下防住幻读。这就是"MVCC 防快照读幻读、间隙锁防当前读幻读"的分工。

### 还有表级锁

| 表级锁 | 说明 |
|---|---|
| **意向锁**（IS / IX） | **表级**的"意图声明"——事务要对某行加共享锁/排他锁前，先在表上加意向锁。作用是让"表锁"能快速判断"表里是否已有行锁"，**避免逐行扫描** |
| 表共享锁 / 表排他锁 | `lock tables ... read/write`，一般不用 |
| **自增锁**（AUTO-INC） | 保证自增 ID 分配的唯一性；`innodb_autoinc_lock_mode` 控制粒度 |

### 加锁规则：IN 存不存在，结果完全不同

**这是"锁的范围"最容易被忽略的一点**——`where` 条件能否走到索引、命中的记录存不存在，决定了锁住的是"记录"还是"间隙"：

| `where` 条件 | 记录存在 | 加锁情况 |
|---|---|---|
| `where id = 10`（唯一索引等值） | ✅ 存在 | **退化为记录锁**（唯一索引等值命中时不需要间隙锁） |
| `where id = 10`（唯一索引等值） | ❌ 不存在 | **加间隙锁**（锁住该值应落入的间隙） |
| `where name = 'x'`（普通索引等值） | ✅ 存在 | **临键锁** + 向后扫描到第一个不满足条件的记录为止 |
| **无索引列** | — | ⚠️ **退化为锁全表所有记录**（见 [存储引擎](/database/mysql/storage-engine) 第四节） |
| **范围查询** `where id > 10` | — | **临键锁**，锁住范围内所有记录及间隙，直到第一个不满足条件的记录 |

> **最后两行是生产事故的高发区**：`where` 没走索引 → 逐行加锁 → 并发写入全面阻塞；范围更新漏加 `limit` → 锁住大片间隙 → 其他事务插入全部等待。**排查锁等待的第一步永远是看执行计划。**

### 死锁

行锁 + 间隙锁会带来**死锁可能**（两个事务以相反顺序持锁并互相等待）：

```sql
-- 会话 A                          -- 会话 B
begin;                             begin;
update t set x=1 where id=1;       update t set x=1 where id=2;
update t set x=1 where id=2;  ←等待  update t set x=1 where id=1;  ←等待
        ↓                                   ↓
             双向等待，死锁
```

**InnoDB 的处理**：开启死锁检测（`innodb_deadlock_detect = ON`，8.0 默认）时，发现环路立即**回滚代价较小的事务**并抛 `Deadlock found` 错误；检测开销大时可改为依赖 `innodb_lock_wait_timeout`（默认 50 秒）超时释放。**应用侧要做的**：捕获该异常并重试，以及**统一多表/多行的加锁顺序**从根源上避免环路。

## 七、面试问答

**Q1：MVCC 是什么？怎么实现的？**

MVCC 是**多版本并发控制**，作用是让**读写操作不冲突**——读不阻塞写、写不阻塞读。实现靠三个组件：① **隐藏字段**——每行有 `DB_TRX_ID`（最近修改它的事务 ID）和 `DB_ROLL_PTR`（回滚指针，指向上一个版本）；② **undo log 版本链**——每次修改都把旧版本存进 undo log，通过回滚指针串成链表，**头部最新、尾部最早**；③ **ReadView**——快照读时生成的可见性判断依据，记录生成那一刻的活跃事务集合。读的时候沿版本链找**对自己可见**的那个版本，从而读到属于自己的快照，不用加锁也不影响别人写。

**Q2：ReadView 里有哪些字段？可见性怎么判断？**

四个字段：**`m_ids`**（当前活跃未提交的事务 ID 集合）、**`min_trx_id`**（活跃集合中的最小值）、**`max_trx_id`**（下一个将要分配的事务 ID）、**`creator_trx_id`**（创建该 ReadView 的事务 ID，即"我自己"）。判断顺序：① 版本的事务 ID **等于 `creator_trx_id`** → 可见（自己改的）；② **小于 `min_trx_id`** → 可见（生成 ReadView 前已提交）；③ **大于等于 `max_trx_id`** → 不可见（生成 ReadView 后才开始）；④ 落在 `[min_trx_id, max_trx_id)` 区间且 **不在 `m_ids` 中** → 可见（当时已提交）；⑤ **在 `m_ids` 中** → 不可见（当时还活跃），**沿 `DB_ROLL_PTR` 往前找上一个版本重新判断**，直到找到可见版本或链表结束（表现为查不到该行）。

**Q3：RC 和 RR 在 MVCC 上的区别是什么？**

**唯一区别是 ReadView 的生成时机**：**RC 每次 `select` 都生成新的 ReadView**，所以每次都能读到"最新已提交"的数据 → 出现**不可重复读**；**RR 只在事务第一次 `select` 时生成，之后一直复用**，整个事务看到的数据快照固定 → 实现**可重复读**，同时因为新插入行的 `DB_TRX_ID` 落在快照范围之外而**看不到新行，也就基本避免了快照读下的幻读**。机制完全相同，只是一个"每次重新拍照"、一个"只拍一次照"。

**Q4：快照读和当前读有什么区别？**

**快照读**是普通 `select`，读的是 **ReadView 判定出的可见版本**（可能是历史数据），**不加锁、非阻塞**，由 MVCC 支撑。**当前读**包括 `select ... for update`、`select ... lock in share mode` 以及 **`update` / `insert` / `delete`**，读的是**最新版本并加锁**。之所以增删改本身就是当前读，是因为它们必须基于最新数据操作，否则会出现更新丢失。**实践含义**：要求"读到最新且期间不被修改"时必须用当前读加锁，普通 `select` 读到的是快照。

**Q5：InnoDB 有哪些行锁？间隙锁解决什么问题？**

三种：**记录锁（Record Lock）**锁单条存在的记录；**间隙锁（Gap Lock）**锁记录之间的间隙（不含记录本身）；**临键锁（Next-Key Lock）= 记录锁 + 该记录之前的间隙锁**，是 **RR 级别的默认加锁单位**。间隙锁解决的是**当前读场景下的幻读**——只有锁住记录之间的**间隙**，才能阻止其他事务在区间内 `insert` 新行。配合 MVCC 解决快照读的幻读，这就构成了 InnoDB 在 RR 下"基本解决幻读"的两条完整路径。

**Q6：为什么唯一索引等值查询加的是记录锁，普通索引加的是临键锁？**

因为**唯一索引的等值查询最多命中一行**，不存在"范围内还有别的行"的问题，所以 InnoDB 会**退化为记录锁**，不需要间隙锁。而**普通索引的等值查询可能命中多行**，且需要保证插入新值时不破坏语义，所以要加临键锁并且**向后扫描到第一个不满足条件的记录**为止。另外有个容易踩的坑：**唯一索引等值查询如果记录不存在**，InnoDB 会退化为**间隙锁**（因为要防止别人插入这个值）。**如果没有索引，则退化为锁全表所有记录。**

**Q7：什么是死锁？怎么避免？**

死锁指两个或多个事务**以相反顺序持有并等待对方的锁**，形成环路。InnoDB 的处理是：开启死锁检测（`innodb_deadlock_detect`，8.0 默认开启）时，发现环路立即**回滚其中代价较小的事务**并报 `Deadlock found when trying to get lock`；若检测开销过大（高并发下很常见），可以关闭检测并依赖 `innodb_lock_wait_timeout`（默认 50 秒）超时释放。**避免手段**：① **统一加锁顺序**——多表、多行操作按固定顺序（如按主键升序）加锁，从根源消除环路；② 缩小事务范围、缩短持锁时间；③ **避免大范围 `update`**——务必走索引并加 `limit`，否则会锁住大量间隙；④ 应用层捕获死锁异常并**安全重试**。
