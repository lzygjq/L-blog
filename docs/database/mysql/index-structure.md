# 索引底层：B+ 树与聚簇索引

## 一、问题场景

一张 2000 万行的订单表，`select * from t_order where id = 12345678` 依然是**毫秒级**返回。

如果靠遍历，2000 万行至少要几百毫秒到几秒；而它只用了 **3 次磁盘 IO**。这不是"优化得好"，而是**数据结构选对了**——索引的本质是"用有序结构把全表扫描的 O(N) 降成树高的 O(log N)"，剩下的问题只是：**为什么是 B+ 树，而不是其他树**。

**结论先行**：索引的底层结构是 **B+ 树**（含义是"非叶子节点只存索引和指针、所有数据在叶子、叶子之间用双向链表串联"）。二叉树和红黑树太"高"（磁盘 IO 次数多），B 树的节点"太胖"（一个页装的索引项少，树依然高），只有 B+ 树能在**有限的 IO 次数**内完成定位，并且顺带把**范围查询**也做得很便宜。

## 二、数据结构演进：为什么一层层换掉

### ① 二叉搜索树 —— 会退化成链表

```
插入有序数据 1,2,3,4,5 →  1
                            \
                             2
                              \
                               3   ...  查找退化为 O(N)
```

极端情况下树退化成链表，效率从 `O(log N)` 掉到 `O(N)`。**根因**：没有自平衡机制。

### ② 红黑树 —— 自平衡了，但"太高"

红黑树通过旋转保证树高在 `O(log N)`，不会退化成链表。但问题变成了**树的高度本身还是太大**：

| 数据量 | 红黑树高度（近似） | 需要几次磁盘 IO |
|---|---|---|
| 100 万 | ~20 层 | 最多 20 次 |
| 2000 万 | ~25 层 | 最多 25 次 |

**关键认知**：二叉树是**二叉**的——每个节点最多 2 个子节点，数据量翻倍树高就加 1。而**磁盘 IO 是数据库里最贵的操作**，20+ 次随机 IO 意味着几十毫秒。**减少 IO 次数 = 降低树高 = 每个节点能挂更多子节点**，这就是"多路"的由来。

### ③ B 树（B-Tree）—— 多路平衡查找树

B 树让每个节点挂**远多于 2 个**子节点（多路），树高骤降。但 B 树有个问题：

```
B 树的节点
┌────────────────────────────────┐
│  key1  │  data1  │  ptr1        │   每个节点同时存 key + data + 指针
│  key2  │  data2  │  ptr2        │   → 单个节点能塞下的 key 数量被 data 挤占
└────────────────────────────────┘
```

一个节点的容量是固定的（等于一个页），**数据（data）占了位置，就装不下更多索引项**。树降低了但没降到极致。

### ④ B+ 树 —— 把数据全部下沉到叶子

B+ 树对 B 树做了两处改动，正是这两处让它成为赢家：

| 改动 | 带来什么 |
|---|---|
| **非叶子节点只存 key + 指针，不存 data** | 同一页能装下**上千个**索引项 → 树更矮 → IO 更少 |
| **所有 data 都在叶子节点，且叶子间用双向链表连接** | ① 查询路径长度一致（都走到叶子）→ **效率稳定**；② 范围查询和全表扫描可以**顺着链表扫**，不用反复回到上层 |

```
                     ┌───────────┐
                     │  根（常驻内存）│           ← 只存 key + 指针
                     └─────┬─────┘
            ┌──────────────┼──────────────┐
        ┌───▼───┐      ┌───▼───┐      ┌───▼───┐
        │ 内部节点│      │ 内部节点│      │ 内部节点│     ← 只存 key + 指针
        └───┬───┘      └───┬───┘      └───┬───┘
     ┌──────┼──────┐        │              │
  ┌──▼─┐ ┌──▼─┐ ┌──▼─┐                                                        ← 叶子节点
  │1..5│⇄│6..10│⇄│11..15│⇄ ...          ⇄ 双向链表：叶子之间顺序相连，范围查询顺链扫
  │整行 │ │整行 │ │整行 │                                                     ← 存的是整行数据
  └────┘ └────┘ └────┘
```

## 三、量化推演：三层 B+ 树为什么能装 2000 万行

这一步是理解"为什么千万级数据依然高效"的关键，面试时把数字报出来，比说"B+ 树比较矮"有说服力得多。

**前提**：InnoDB 中每个页（page）默认 **16KB**，一次页读取 = 一次磁盘 IO。

**① 非叶子节点能存多少索引项？**

假设主键是 `bigint`（8 字节），InnoDB 的页指针约 6 字节：

```
单个索引项 = 8B(key) + 6B(ptr) = 14B
一页可存索引项 ≈ 16384 ÷ 14 ≈ 1170 个
```

**② 叶子节点能存多少行？**

叶子存整行数据，假设每行 1KB：

```
一页可存行数 = 16384 ÷ 1024 = 16 行
```

**③ 三层树能覆盖多少行？**

```
第 1 层（根）     :        1 个节点
第 2 层（内部）   :    1 × 1170 = 1,170 个节点
第 3 层（叶子）   : 1170 × 1170 = 1,368,900 个叶子页
叶子页承载行数    : 1,368,900 × 16 ≈ 2,190 万行

磁盘 IO 次数 = 树高 = 3 次
```

**这就是答案**：三千万行以内的表，B+ 树高度通常只有 **3~4 层**，主键查询只需要 **3~4 次 IO**。而根节点常驻 Buffer Pool（内存），实际往往只有 **2~3 次真实磁盘 IO**。

> **反过来算也成立**：如果换成一棵红黑树，2000 万行需要约 25 层，也就是 25 次 IO。**3 次 vs 25 次**——这就是"扇出（fan-out）"带来的差距。B+ 树的扇出是 1170，二叉树是 2，差了近 600 倍。

## 四、聚簇索引 vs 二级索引

| 维度 | 聚簇索引（聚集索引） | 二级索引（非聚簇索引） |
|---|---|---|
| 含义 | **数据与索引放在一起**，叶子节点保存**整行数据** | 数据与索引**分开存储**，叶子节点保存**主键值** |
| 数量 | **有且只有 1 个** | 可以有多个 |
| 由谁决定 | InnoDB 按规则自动选取 | 由你 `create index` 指定 |
| 查一次能否拿到整行 | ✅ 能 | ❌ 拿到主键后还需**回表** |
| 别名 | 主键索引 / 一级索引 | 辅助索引 / 非聚簇索引 |

**聚集索引的选取规则**（按优先级）：

```
① 有主键                      → 主键索引就是聚集索引
        ↓ 没有主键
② 有第一个唯一索引（UNIQUE）   → 用它作为聚集索引
        ↓ 也没有
③ InnoDB 自动生成隐藏列 rowid  → 用 rowid 作为聚集索引
```

> **这就是"为什么建议每张表都建主键"的底层原因**：没有主键时 InnoDB 会生成一个**用户不可见的 `rowid`（6 字节）**，你既无法控制它的生成顺序（可能加剧页分裂），也没法用它做业务查询。**代价是隐形的，但真实存在。**

## 五、回表：二级索引的必然代价

```
用二级索引查 select * from t where name = 'Arm'

① 走 name 的二级索引（B+ 树）
       ┌─────────────┐
       │ name → 主键id │   叶子节点存的是主键值，不是整行
       └──────┬──────┘
              │ 拿到 id = 2
              ▼
② 再到聚簇索引（主键 B+ 树）里按 id = 2 查
       ┌─────────────┐
       │ id=2 → 整行数据│   这一步才拿到 name、gender、... 全部字段
       └─────────────┘

上面的 ①→② 两步，就是【回表】
```

**回表意味着两颗 B+ 树各走一遍**。如果 `where` 命中的是 900 万行，理论上要回表 900 万次——这是"超大分页"性能灾难的直接成因，解法见 [索引设计](/database/mysql/index-design) 与 [慢查询定位](/database/mysql/diagnosis)。

## 六、延伸：为什么推荐自增主键

这是面试的加分项，因为它是从"B+ 树是有序结构"直接推出来的结论。

| 主键类型 | 插入行为 | 后果 |
|---|---|---|
| **自增 bigint** | 新值永远追加到**最右侧叶子页** | 顺序写入，页利用率高，几乎不分裂 |
| UUID / 随机字符串 | 新值**随机落在中间某页** | ① 目标页可能不在内存 → 随机 IO；② 页满后**页分裂**（一页拆两页，还要维护父子指针）；③ **所有二级索引的叶子都存主键**，主键变长 → 二级索引整体膨胀 |

**一句话**：主键不只是唯一标识，它还**决定了整张表的数据物理排列顺序**，以及所有二级索引的体积。

## 七、面试问答

**Q1：索引的底层数据结构是什么？为什么用 B+ 树？**

InnoDB 用 **B+ 树**。对比来看：**二叉搜索树**没有自平衡，极端情况退化成链表，`O(log N)` 变 `O(N)`；**红黑树**虽然自平衡，但每个节点只有 2 个分支，2000 万数据树高约 25 层，意味着最多 25 次磁盘 IO；**B 树**是多路的，但每个节点同时存 key、data 和指针，data 挤占了空间，一个页能放的索引项少，树依然偏高。**B+ 树做了两处关键优化**：① 非叶子节点只存 key 和指针，不存 data，所以一页能放上千个索引项；② 所有数据下沉到叶子节点，叶子之间用双向链表连接。带来的好处是：**树矮**（一般 3~4 层）、**查询稳定**（每次都要走到叶子，路径长度一致）、**范围查询快**（顺叶子链表扫）。

**Q2：为什么说千万级数据 B+ 树依然高效？**

按 InnoDB 的 16KB 页算：非叶子节点每个索引项 `8B 主键 + 6B 指针 = 14B`，一页约存 `16384/14 ≈ 1170` 个；叶子节点按每行 1KB 算，一页存 16 行。三层树的容量是 `1170 × 1170 × 16 ≈ 2190 万行`，**而只需要 3 次 IO**。而且根节点常驻 Buffer Pool，实际磁盘 IO 常是 2~3 次。对比红黑树的约 25 次 IO，差距来自**扇出**：B+ 树扇出 1170，二叉树扇出 2。

**Q3：什么是聚簇索引和非聚簇索引？**

**聚簇索引**把数据和索引放在一起，B+ 树的叶子节点保存**整行数据**，一张表**只能有一个**——InnoDB 会按"主键 → 第一个唯一索引 → 隐藏 rowid"的顺序挑一个。**非聚簇索引**（也叫二级索引）数据与索引分开存储，叶子节点保存的是**主键值**而不是整行，可以有多个。因此在 InnoDB 里，用二级索引查到主键后，还需要再去聚簇索引里查完整数据，这个过程叫**回表**。

**Q4：什么是回表？怎么避免？**

回表就是"**通过二级索引拿到主键值，再回到聚簇索引查整行数据**"的两步过程——本质上是两颗 B+ 树各走一遍。避免它的唯一办法是**覆盖索引**：让 `select` 要返回的列全部落在索引里，就不用回聚簇索引了（详见 [索引设计](/database/mysql/index-design)）。所以 `select *` 是回表的高发写法。

**Q5：为什么主键建议用自增 ID 而不是 UUID？**

三个原因：① **写入是顺序的**——自增主键永远追加到最右侧叶子页，UUID 随机插入会导致页分裂和随机 IO；② **页利用率高**——顺序写入时页填充紧凑，随机写入会留下大量空页；③ **所有二级索引的叶子都存主键值**，UUID 是 36 字节字符串而 bigint 只有 8 字节，主键变长会让**每一棵二级索引都跟着膨胀**，一次 IO 能读到的索引项减少。

**Q6：为什么建议显式指定主键？**

没有主键时，InnoDB 会按"第一个唯一索引"作聚簇索引；连唯一索引也没有，才会自动生成 **6 字节的隐藏 `rowid`**。隐藏 rowid 的问题在于：**用户不可见、不可控**——既无法控制它的生成顺序（可能加剧页分裂），也不能在业务查询里使用它。所以每张表都应该显式定义主键。
