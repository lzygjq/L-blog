# 主从复制与读写分离

## 一、问题场景

单台 MySQL 会依次撞上四面墙：

| 问题 | 表现 |
|---|---|
| **读性能瓶颈** | 读请求是写请求的几倍到几十倍，单机 CPU 先到顶 |
| **单点故障** | 宕机 = 服务不可用，且没有热备可切换 |
| **备份影响业务** | 在线上做全量备份会占用大量 IO |
| **扩展性受限** | 无法通过加机器提升读吞吐 |

**主从复制（Replication）是对这四件事的统一解法**：让从库持续同步主库的数据变更，从而支撑**读写分离、高可用切换、离线备份**。理解它的关键只有一句话：**一切基于 binlog**。

## 二、复制的核心：binlog

回顾 [日志体系](/database/mysql/log)：**binlog 是 MySQL Server 层的日志，记录所有 DDL 和 DML 语句（不含 SELECT）**，采用**追加写**。

| 特性 | 为什么对复制重要 |
|---|---|
| Server 层日志 | 所有引擎都能复制，不局限于 InnoDB |
| 记录所有数据变更 | 从库可以完整重放主库的每一次变更 |
| **追加写、不覆盖** | 从库可以按位点（position）严格顺序消费，断点续传 |
| 有固定结束标志（`XID event`） | 可以可靠判断"一个事务的 binlog 是否写完整"（两阶段提交的裁判依据） |

## 三、复制的三步流程

```
        ┌──────────────────────── 主库 Master ────────────────────────┐
        │                                                             │
        │   事务提交                                                   │
        │      │  ①  数据变更写入 binlog（按事务顺序）                  │
        │      ▼                                                      │
        │   ┌──────────────┐                                          │
        │   │   binlog     │                                          │
        │   └──────┬───────┘                                          │
        └──────────┼──────────────────────────────────────────────────┘
                   │ ② 从库 IO 线程拉取（dump 请求 → 主库 dump 线程推送）
                   ▼
        ┌──────────────────── 从库 Slave ─────────────────────────────┐
        │                                                             │
        │   ┌──────────────┐                                          │
        │   │  Relay Log   │  ← 中继日志：IO 线程写入的本地中转文件      │
        │   │  （中继日志）  │                                          │
        │   └──────┬───────┘                                          │
        │          │ ③ SQL 线程重放（replay）                          │
        │          ▼                                                  │
        │   应用到从库自己的数据文件                                    │
        └─────────────────────────────────────────────────────────────┘
```

**三步的文字版**：

| 步骤 | 执行者 | 动作 |
|---|---|---|
| **①** | **主库** | 事务提交时，把数据变更**写入 binlog** |
| **②** | **从库的 IO 线程** | 连接主库，读取主库 binlog，写入本地 **Relay Log（中继日志）** |
| **③** | **从库的 SQL 线程** | 重放 Relay Log 中的事件，把变更**应用到从库自己的数据** |

> **两个线程的名字必须记住**：**IO 线程**（拉取 binlog → 写 relay log）和 **SQL 线程**（重放 relay log → 应用数据）。只笼统说"从库读取、从库重做"是不够的——**主从延迟的根因就在 SQL 线程是单线程这件事上**。

**关键设计理解**：

- **为什么要 Relay Log 而不直接应用**：把"接收"和"应用"解耦。IO 线程可以持续拉取（不怕短暂的应用慢），SQL 线程按自己的节奏重放，还能在从库重启后从 relay log 的位点续做。
- **为什么复制是"异步"的默认语义**：主库写完 binlog **不等**从库确认就返回提交成功——所以**主库永远是最新的**，从库可能滞后。

## 四、三种复制模式

| 模式 | 主库何时返回提交成功 | 数据安全性 | 性能 | 使用情况 |
|---|---|---|---|---|
| **异步复制**（默认） | 写完 binlog **立即返回**，不等从库 | ⚠️ 主库宕机可能**丢数据**（从库还没收到） | 最高 | MySQL 默认；对丢失不敏感的场景 |
| **半同步复制**（semi-sync） | 写完 binlog 后**至少等一个从库确认收到 relay log** 才返回 | ✅ 至少有一份副本 | 中（多一次网络往返） | **性能与安全的折中**，生产常用 |
| **全同步复制** | 等**所有**从库都**执行完**才返回 | ✅ 最高 | 最低（受最慢从库拖累） | 基本不用 |

**半同步的细节**：由插件 `rpl_semi_sync_master` / `rpl_semi_sync_slave` 实现。要注意一个"退化"行为——**半同步有超时机制**：如果等不到从库确认超过 `rpl_semi_sync_master_timeout`（默认 10 秒），主库会**自动退化为异步复制**，避免整个集群被一个慢从库拖死。所以它是"尽力而为的同步"。

**怎么选**：

```
能接受主库宕机丢少量数据？            → 异步（简单、快）
不能接受丢数据，但能容忍短暂性能下降？  → 半同步（推荐）
数据绝对不能丢，且集群规模小？          → 全同步（罕见）
```

## 五、主从延迟：原因与解法

**根因**：从库的 **SQL 线程是单线程重放**的。主库可以并发多个事务同时写入 binlog，而从库只能一个事务接一个事务地串行重放。**主库写入并发越高，从库越跟不上。**

```
主库：事务T1 ─┐
      事务T2 ─┼─▶ 并发写入 binlog（多线程）
      事务T3 ─┘
                ↓
从库：T1 ───▶ T2 ───▶ T3 ───▶   串行重放（单线程）← 瓶颈在这里
```

**其他加剧因素**：① 从库配置低于主库；② 从库上还有大量查询（读写分离后从库也在扛读流量）；③ **大事务**（一次更新几十万行，重放要很久）；④ 大表 DDL；⑤ 网络延迟。

### 六大治理手段

| # | 手段 | 说明 |
|---|---|---|
| 1 | **并行复制**（最重要） | MySQL **5.7+** 支持**基于组提交（Group Commit）的并行重放**——`slave_parallel_workers = 8`、`slave_parallel_type = LOGICAL_CLOCK`，让 SQL 线程变成多线程，**这是解决延迟的根本手段** |
| 2 | **拆分大事务** | 避免一次 `update` 影响几十万行；分批处理，减少单事务的重放时间 |
| 3 | **从库配置不低于主库** | 特别是 `innodb_buffer_pool_size` 和磁盘类型（SSD） |
| 4 | **一主多从 / 级联复制** | 分散读压力；用中间层从库做"中继"减轻顶层主库的 dump 压力 |
| 5 | **减少从库上的查询压力** | 读写分离时给从库留出重放余量；或用**专用从库**（一部分只做同步不做查询） |
| 6 | **业务层规避** | 见下节 |

### 业务层的两个实用规避

| 场景 | 解法 |
|---|---|
| **写后立即读**（下单后马上查订单） | ① **强制走主库**——这类"写完立刻要读"的请求打标，路由到主库；② 利用**半同步**保证从库已收到；③ 写入后用**缓存**承接这次读取 |
| 读不敏感的历史数据 | 允许读从库，接受秒级延迟 |

> **这不是"延迟必须消灭"，而是"延迟必须被业务感知到"**。主从延迟普遍在**毫秒到数百毫秒**级别，绝大多数查询可以接受；真正会出问题的是"同一个请求内写完立刻读"的路径——这类路径**必须显式走主库**。

## 六、GTID：位点管理的进化

**传统复制**靠 `binlog file + position`（位点）来定位同步进度：

```sql
change master to master_host='...', master_log_file='mysql-bin.000003', master_log_pos=154;
```

**问题**：主库故障切换时，需要人工找到新主库的位点——容易出错，也容易**重复执行事务**。

**GTID（Global Transaction Identifier，全局事务标识）** 给每个事务分配一个全局唯一 ID，格式是 `server_uuid:transaction_id`（如 `3E11FA47-71CA-11E1-9E33-C80AA9429562:23`）：

| 维度 | 位点复制 | **GTID 复制** |
|---|---|---|
| 定位方式 | 文件名 + 偏移量 | **全局唯一的事务 ID** |
| 主从切换 | 需人工找位点 | **自动定位**，无需人工干预 |
| 重复执行 | 可能重复执行同一事务 | **自动跳过已执行过的事务**（幂等） |
| 配置 | `master_log_file` + `master_log_pos` | `MASTER_AUTO_POSITION = 1` |
| 故障恢复 | 复杂 | 简单 |

**结论**：MySQL 5.6 引入 GTID，**5.7 起已是生产标配**，配合 MHA / Orchestrator 等工具可实现自动化主从切换。

## 七、面试问答

**Q1：MySQL 主从复制的原理是什么？**

核心是 **binlog**。复制分三步：**① 主库**在事务提交时把数据变更写入 binlog；**② 从库的 IO 线程**连接主库读取 binlog，写入本地 **Relay Log（中继日志）**；**③ 从库的 SQL 线程**重放 Relay Log 中的事件，把变更应用到从库自己的数据。默认是**异步复制**——主库写完 binlog 就返回，不等从库确认，所以性能高但主库宕机可能丢数据。对一致性要求高的场景可以用**半同步复制**：主库至少等一个从库确认收到 relay log 才返回提交成功。**常见问题是主从延迟**，根本原因是从库的 SQL 线程**单线程重放**，跟不上主库的并发写入，MySQL 5.7 之后支持**基于组提交的并行复制**来缓解。

**Q2：从库有几个线程？分别做什么？**

两个（严格说还有一个 dump 相关，但关注这两个）：**IO 线程**负责与主库建立连接、拉取 binlog 并写入本地的 **Relay Log**；**SQL 线程**负责读取 Relay Log 并**重放**，把变更应用到从库的数据文件。这个分工的意义在于**把"接收"和"应用"解耦**：IO 线程可以持续快速拉取（不怕应用慢），SQL 线程按自己的节奏重放，从库重启后还能从 relay log 的位点续做。而 SQL 线程单线程，正是**主从延迟的根因**。

**Q3：主从延迟怎么解决？**

先明确根因：**从库 SQL 线程单线程重放，跟不上主库的并发写入**。治理分五类：① **并行复制**——MySQL 5.7+ 基于组提交的并行重放（`slave_parallel_workers` 设为 8 左右、`slave_parallel_type = LOGICAL_CLOCK`），这是根本手段；② **拆分大事务**——避免一次更新几十万行，大事务重放极慢；③ **从库配置不低于主库**（尤其是 `innodb_buffer_pool_size` 和 SSD）；④ **降低从库查询压力**——读写分离后从库也在扛读流量，需留出重放余量，或用**专用从库**；⑤ **业务层规避**——"写后立刻读"的请求**强制走主库**，或用缓存承接这次读取。

**Q4：读写分离后，为什么会出现"刚写入就查不到"？**

因为默认是**异步复制**，主库提交后立即返回，从库可能还没收到 binlog 或还没重放完 —— 这时读从库就会读到旧数据。**解法**：① 这类"写后立即读"的请求**强制路由到主库**（按事务标记或注解路由）；② 使用**半同步复制**，至少保证从库已收到 relay log；③ 写入后把结果**放缓存**，这次读取走缓存而不走从库；④ 在应用层做**位点校验**（读之前确认从库已追上主库的 GTID/位点，未追上则走主库）。要强调的是：**主从延迟是架构的固有特性，不是 bug**——设计上必须让业务感知到"哪些读可以容忍延迟、哪些不能"。

**Q5：什么是 GTID？比传统复制好在哪？**

GTID 是**全局事务标识符**，格式为 `server_uuid:transaction_id`，给每个事务一个全局唯一的 ID。传统复制靠 `binlog 文件名 + 位点`定位同步进度，主库故障切换时需要人工找新主库的位点，**容易出错且可能重复执行事务**。GTID 的优势有两点：① **切换自动化**——新主库只需 `MASTER_AUTO_POSITION = 1`，从库会自动寻找未执行过的事务，无需人工算位点；② **幂等**——从库会自动跳过已经执行过的事务，避免重复应用。MySQL 5.6 引入，**5.7 起成为生产标配**。
