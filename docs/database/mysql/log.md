# 日志体系：redo / undo / binlog

## 一、问题场景

事务提交返回成功，客户端认为数据已经安全了。但如果此刻拔掉电源：

- 数据页可能还在 **Buffer Pool（内存）** 里没刷盘；
- 已经提交的事务可能**丢失**；
- 未提交的事务的部分修改可能**已经被写进数据文件**。

**MySQL 靠三类日志解决这三个问题**，而它们的名字经常被混着答。本文的核心是把三者的**定位分工**讲清——尤其是最高频的追问：**binlog 和 redo log 到底差在哪、为什么还需要两阶段提交**。

## 二、Buffer Pool 与 WAL：为什么"先写日志"

InnoDB 的读写都走内存：

```
        update balance = 900
                │
                ▼
     ┌──────────────────────┐
     │    Buffer Pool        │  内存中缓存磁盘数据页的区域
     │  （数据页的副本）      │  增删改先在这里进行
     └──────────┬───────────┘
                │ 以一定频率刷回磁盘（不是每次提交都刷）
                ▼
     ┌──────────────────────┐
     │      磁盘数据文件      │
     └──────────────────────┘
```

**问题**：如果只在内存改完就返回成功，宕机就丢数据。但如果**每次提交都把数据页刷盘**，代价又太大——数据页是**随机写**。

**WAL（Write-Ahead Logging，预写日志）** 的解法：

> **先把修改写进日志（顺序写，快），事务就可以返回提交成功；数据页稍后再以一定频率刷盘。**

```
不用 WAL：改数据页 → 随机写磁盘        （每次提交都随机 IO，慢）
用了 WAL：改数据页 → 写 redo log（顺序写）→ 返回成功
                                    → 数据页择机刷盘（批量、合并，减少随机 IO）
```

**这就是"为什么 redo log 能同时保证持久性和性能"的答案**。崩溃后重启，InnoDB 用 redo log 把已提交但没刷盘的数据页变更**重放**回来。

## 三、三类日志的定位

| 维度 | **redo log** | **undo log** | **binlog** |
|---|---|---|---|
| **所属层** | **InnoDB 引擎层** | InnoDB 引擎层 | **MySQL Server 层** |
| **日志类型** | **物理日志**（改了哪个页的什么偏移） | **逻辑日志**（记录反向操作） | **逻辑日志**（记录 DDL/DML 语句或行变更） |
| **记录内容** | 数据页的物理修改 | 修改**前**的数据；`insert` 对应 `delete`，`update` 对应**反向 update** | 所有 DDL 和 DML（**不含 SELECT**） |
| **主要作用** | **崩溃恢复**，保证**持久性** | **事务回滚** + **MVCC 读旧版本** | **主从复制** + **数据备份恢复** |
| **写入方式** | **循环写**（固定大小，写满就覆盖最旧的） | 随机写，事务结束后可清理 | **追加写**（append，不断增长） |
| **生命周期** | 空间复用，被覆盖 | 提交后按需清理（有长事务则不能清） | 由 `expire_logs_days` / `binlog_expire_logs_seconds` 决定保留时长 |
| **保证的特性** | 持久性 | **原子性**、一致性 | 复制与恢复（不参与单机 ACID） |

**一句话记法**：

```
redo log  = 保证"提交了就不丢"      → 持久性
undo log  = 保证"没提交就撤销"      → 原子性
binlog    = 让"别的机器也有这份数据" → 复制
```

### redo log 的细节

| 项 | 说明 |
|---|---|
| 文件 | `ib_logfile0`、`ib_logfile1`（8.0 起由 `innodb_log_files_in_group` 与 `innodb_redo_log_capacity` 控制） |
| 循环写 | 固定容量、环形结构，`write pos` 追 `check point`；两者之间的空间是**可复用**的 |
| 组提交（Group Commit） | 多个事务的 redo log 合并成一次 fsync，**大幅降低刷盘次数**，是高并发写的关键优化 |
| 刷盘参数 | `innodb_flush_log_at_trx_commit`：`1`（每次提交都刷，最安全，**默认**）/ `0`（每秒刷，可能丢 1 秒）/ `2`（写到 OS cache，每秒刷） |

### undo log 的细节

- **逻辑日志**：记录的是"如何撤销"，而不是"页的前像"。`insert` 的 undo 是 `delete`，`update` 的 undo 是一次**反向 `update`**。
- **两个用途**：① 事务 `rollback` 时反向执行；② **MVCC 版本链**——多个版本的 undo 通过回滚指针（`DB_ROLL_PTR`）串成链表，供快照读查找历史版本（见 [MVCC 与锁](/database/mysql/mvcc)）。
- **长事务的代价**：undo 只有在**没有事务需要它**时才能清理。一个跑了很久的事务会**撑大 undo 表空间**，并**加剧主从延迟**。

### binlog 的细节

| 项 | 说明 |
|---|---|
| 层次 | **Server 层**——所以**所有引擎**（含 MyISAM）都会写 binlog，而 redo log 只有 InnoDB 有 |
| 格式 | `STATEMENT`（记 SQL 语句，日志小但**某些函数如 `now()` 主从不一致**）/ `ROW`（记行变更，**一致性好**，日志大，**8.0 默认**）/ `MIXED`（自动切换） |
| 刷盘参数 | `sync_binlog = 1`（每次提交都刷，最安全）/ `0`（交给 OS）|
| 关键用途 | **主从复制**的唯一数据来源（见 [主从复制](/database/mysql/replication)）；`mysqlbinlog` 可解析它做**基于时间点的恢复**（PITR） |

## 四、两阶段提交：redo log 与 binlog 怎么保持一致

**问题的由来**：redo log 和 binlog 是**两个独立的日志系统**，一个在引擎层、一个在 Server 层。如果它们对同一个事务的记录不一致，就会出现：

- redo log 写了、binlog 没写 → **主库有新数据，从库没有** → 主从不一致；
- binlog 写了、redo log 没写 → **从库有新数据，主库没有** → 主从不一致。

**解法：两阶段提交（2PC）**，把 redo log 写成两个阶段：

```
        ┌─────────────────────────────────────────────┐
        │  事务提交                                     │
        └───────────────────┬─────────────────────────┘
                            ▼
   ① 写 redo log，标记为 【prepare】 状态
                            │
                            ▼
   ② 写 binlog（此时 binlog 是完整的）
                            │
                            ▼
   ③ 提交事务，把 redo log 改为 【commit】 状态
```

**崩溃恢复时怎么判断**（这是面试追问的重点）：

| 崩溃时刻 | redo log 状态 | binlog 状态 | 恢复动作 |
|---|---|---|---|
| ① 之后、② 之前 | `prepare` | **不完整 / 没有** | **回滚**（binlog 不完整，从库拿不到，主库也回滚） |
| ② 之后、③ 之前 | `prepare` | **完整** | **提交**（redo log 虽然还是 prepare，但 binlog 完整 → 说明该事务应生效） |

**判定规则一句话**：

> **redo log 处于 `prepare` 时，看 binlog 是否完整**——完整就提交，不完整就回滚。

**为什么是"看 binlog"而不是"看 redo log"**：因为 binlog 是**一份完整的、有固定结束标志（`XID event`）的日志**，可以可靠地判断"这个事务的 binlog 是否写完了"。拿这个确定的事实去决定另一个日志的归属，才能保证两边一致。

## 五、刷盘参数：真正的"数据安全等级"

生产上"会不会丢数据"由两个参数共同决定：

| `innodb_flush_log_at_trx_commit` | `sync_binlog` | 安全性 | 性能 | 适用 |
|---|---|---|---|---|
| **1** | **1** | ✅ **最安全**：提交即刷两处日志，宕机不丢已提交事务 | 最低 | **金融、订单等核心业务（默认）** |
| 1 | 0 | 较安全：redo 刷了，binlog 可能丢 | 中 | — |
| 2 | 1000 | ⚠️ 可能丢 1 秒内的事务 | 高 | 一般业务 |
| 0 | 0 | ❌ 宕机可能丢 1 秒 | 最高 | 对丢失不敏感的场景 |

**"双 1 配置"** 指的就是 `innodb_flush_log_at_trx_commit = 1` + `sync_binlog = 1`——**这是 MySQL 保证不丢数据的标准配置**，也是"为什么 MySQL 能当金融级数据库"的参数层面答案。

## 六、面试问答

**Q1：undo log 和 redo log 的区别？**

| 维度 | redo log | undo log |
|---|---|---|
| 类型 | **物理日志**——记录数据页的物理修改 | **逻辑日志**——记录修改前的数据，如 `insert` 对应 `delete`、`update` 对应反向 `update` |
| 作用 | **宕机后恢复数据**（崩溃恢复） | **事务回滚** + **MVCC 读旧版本** |
| 保证的特性 | **持久性** | **原子性** |
| 写入方式 | **循环写**（固定容量、环形复用） | 随机写，提交后按需清理 |

一句话：**redo log 保证"提交了就不丢"，undo log 保证"没提交就撤销"**。此外 redo log 配合 **WAL 机制**（先写日志再刷数据页）在保证持久性的同时把随机写变成了顺序写，这是它同时兼顾安全与性能的关键。

**Q2：binlog 和 redo log 有什么区别？**

四点核心差异：① **所属层不同**——binlog 是 **MySQL Server 层**的日志，所有引擎都会写；redo log 是 **InnoDB 引擎层**的日志，只有 InnoDB 有。② **记录内容不同**——binlog 记录所有 **DDL 和 DML 语句**（不含 SELECT）；redo log 记录**数据页的物理变化**。③ **写入方式不同**——binlog 是**追加写**（文件不断增长，靠过期策略清理）；redo log 是**循环写**（固定容量，写满覆盖最旧的）。④ **用途不同**——binlog 用于**主从复制和数据恢复（PITR）**；redo log 用于**崩溃恢复**。**两者的一致性由两阶段提交保证。**

**Q3：什么是两阶段提交？为什么需要它？**

因为 redo log（引擎层）和 binlog（Server 层）是两套独立日志，如果一个写了另一个没写，就会出现**主从不一致**（主库有新数据从库没有，或反之）。两阶段提交的流程是：**① 写 redo log 并标记为 `prepare` 状态 → ② 写 binlog → ③ 提交事务，把 redo log 改为 `commit` 状态**。崩溃恢复时的判定规则是：**redo log 处于 `prepare` 状态时，检查 binlog 是否完整——完整则提交，不完整则回滚**。之所以用 binlog 当裁判，是因为 binlog 有固定的结束标志（`XID event`），能可靠判断"这个事务写完了没有"。

**Q4：WAL 机制是什么？为什么能提升性能？**

WAL（Write-Ahead Logging）即**预写日志**：修改数据时**先写日志，再写数据页**。事务提交时只把修改写入 redo log 就返回成功，数据页稍后择机批量刷盘。性能提升来自两点：① **顺序写替代随机写**——redo log 是顺序追加，而数据页刷盘是随机写，磁盘顺序写快得多；② **合并刷盘**——多个事务的修改可以攒在一起批量刷，配合**组提交（Group Commit）**把多次 fsync 合并成一次。而数据安全性由 redo log 兜底：宕机后重放 redo log 就能恢复已提交的数据。

**Q5：长事务有什么危害？**

四个层面：① **undo 无法清理**——只要还有事务需要读旧版本，undo log 就不能删，导致 **undo 表空间持续膨胀**；② **加剧主从延迟**——长事务的 binlog 在从库上是**大事务重放**，期间从库的查询会看到陈旧数据；③ **锁持有时间长**——长事务持有的行锁/间隙锁不释放，阻塞其他事务，**死锁概率上升**；④ **回滚代价大**——回滚一个长事务要反向执行所有 undo，可能比执行还慢。实践上要限制事务时长、避免在事务里做远程调用。
