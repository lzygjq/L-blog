# 存储引擎：InnoDB 与 MyISAM

## 一、问题场景

同样一条 `update t set status = 1 where id = 100`，在两张结构完全相同的表上：

- 表 A（MyISAM）：**别的会话在改 id = 200 的那一行，也会被卡住**；
- 表 B（InnoDB）：只锁住 id = 100 这一行，其余行照常读写。

差异不在 SQL，而在**存储引擎**。存储引擎是 MySQL 里"表级别"的插件，决定了数据怎么存、锁加在哪、事务有没有、崩溃后能不能恢复。

**结论先行**：新项目一律用 InnoDB。它是 MySQL 5.5 之后的默认引擎，也是唯一同时支持**事务 + 行级锁 + 外键 + 崩溃恢复**的选择。MyISAM 只在读多写极少、且明确不需要事务的历史场景里还有残留价值。

## 二、三种引擎的横向对比

| 特性 | MyISAM | **InnoDB** | MEMORY |
|---|---|---|---|
| 事务安全 | ❌ 不支持 | ✅ 支持 | ❌ 不支持 |
| 锁机制 | 表锁 | **表锁 + 行锁**（默认行锁） | 表锁 |
| 外键 | ❌ | ✅ | ❌ |
| 崩溃后恢复 | ❌ 需 `myisamchk` 修复，可能丢数据 | ✅ 靠 redo log 自动恢复 | ❌ 数据全丢 |
| 数据存储位置 | 磁盘（索引与数据分离） | 磁盘（数据与索引同放） | **内存**（不落地） |
| 聚簇索引 | ❌ 没有（索引和数据分开） | ✅ 有（见 [索引底层](/database/mysql/index-structure)） |
| 全文索引 | ✅ 原生支持 | 5.6+ 支持 | ❌ |
| `count(*)` | 快（内置计数器直接返回） | 慢（需遍历索引统计） | 快 |
| 默认引擎 | MySQL 5.5 **之前** | MySQL 5.5 **之后** | — |

> **`count(*)` 的差异常被拿来当"MyISAM 更快"的证据，这是片面的**：MyISAM 的表级计数器省掉了扫描，但代价是任何一行被改都要锁全表。InnoDB 的 `count(*)` 之所以要扫，是因为它必须做 MVCC 可见性判断（见 [MVCC 与锁](/database/mysql/mvcc)）——**这不是缺陷，是支持并发事务的成本**。

## 三、文件结构：数据到底存在哪

以一张表 `t` 为例，MySQL 8.0 下的落盘文件：

| 引擎 | 文件 | 内容 |
|---|---|---|
| **InnoDB** | `t.ibd` | **表空间文件**：表结构 + 数据 + 索引（8.0 起全在这里） |
| InnoDB（8.0 之前） | `t.frm` + `t.ibd` | `frm` 存表结构，`ibd` 存数据与索引 |
| MyISAM | `t.frm` / `t.MYD` / `t.MYI` | 表结构 / 数据 / 索引，**三者分离** |
| MEMORY | 无 | 全在内存，重启即空 |

**"数据与索引是否分离"是理解后续一切差异的钥匙**：

```
InnoDB（聚簇）                        MyISAM（非聚簇）
┌──────────────┐                     ┌──────────────┐   ┌──────────────┐
│  t.ibd       │                     │  t.MYI       │   │  t.MYD       │
│  主键索引     │                     │  索引文件     │   │  数据文件     │
│  └─ 叶子存整行│                     │  叶子存行地址 │──▶│  实际的整行   │
└──────────────┘                     └──────────────┘   └──────────────┘
  按主键查一次到位                       按索引拿到地址，再回数据文件取行
```

MyISAM 的**所有**索引都是"二级索引"——都要多一跳。InnoDB 的主键索引能"一次到位"，代价是必须选一个聚簇索引键（详见索引篇）。

> **8.0 的变化**：`.frm` 被并入 `ibd`，表结构改为存在数据字典表（`information_schema` 背后的 InnoDB 系统表）里。所以 8.0 建表后目录下只剩 `.ibd`，这是正常现象。

## 四、锁粒度：行锁与表锁的真实代价

| 维度 | 表锁（MyISAM） | 行锁（InnoDB） |
|---|---|---|
| 锁的对象 | 整张表 | 索引上的记录（**注意：锁加在索引上，不是数据行上**） |
| 并发写 | 同一表**串行** | 不同行可并行 |
| 开销 | 小（锁少） | 大（锁多、需管理） |
| 冲突概率 | 高 | 低 |
| 死锁 | 不会 | **可能**（需靠 `innodb_lock_wait_timeout` 与死锁检测处理） |
| 典型场景 | 读多写极少 | 高并发读写 |

**一个高频追问**：InnoDB 的行锁是加在**记录行**上还是**索引项**上？

答案：**加在索引项上**。所以——

> 如果 `update` 的 `where` 条件**没走索引**，InnoDB 无法定位到具体索引项，就会**退化成锁全表所有记录**（逐行加锁，效果等同于表锁，但更慢）。这也是[索引失效](/database/mysql/index-design)在生产上最危险的后果之一：**不只是慢，还会把并发拖垮**。

## 五、InnoDB 为什么成为默认引擎

| 理由 | 说明 |
|---|---|
| **事务** | 支持 ACID，业务系统绕不开（见 [事务](/database/mysql/transaction)） |
| **行级锁** | 高并发写入的基础；表锁在写多的场景会直接成为瓶颈 |
| **崩溃恢复** | 靠 redo log 做 crash-safe，断电后自动恢复到最后一致状态 |
| **聚簇索引** | 主键查询一次 IO 到位；二级索引虽需回表但叶子更紧凑 |
| 外键约束 | 数据完整性可由数据库兜底 |

对比之下 MyISAM 的短板是系统性的：**不支持事务 → 无法做金融类业务；表锁 → 写并发上不去；无崩溃恢复 → 断电可能表损坏**。

## 六、选型决策

```
需要事务 / 高并发写 / 需要崩溃恢复？
        │
        ├─ 是 ──▶ InnoDB（99% 的场景，不要犹豫）
        │
        └─ 否 ──▶ 表是只读或极少写的统计/日志归档表？
                     │
                     ├─ 是 + 需要原生全文索引（5.6 之前版本）──▶ MyISAM
                     │
                     └─ 数据可丢、追求极致读速（如临时中间表）──▶ MEMORY
```

**实践建议**：

- 建表时**显式写 `ENGINE=InnoDB`**，不要依赖默认值——迁移到老版本或改过 `my.cnf` 的环境默认值可能不是 InnoDB。
- 单表**绝不混用引擎**：跨引擎的 JOIN 无法使用事务，且外键不生效。
- MEMORY 表的真实用途是**临时计算中间表**，不是"加速缓存"——缓存请用 [Redis](/database/redis/)。
- 查看当前引擎：`show table status like 't'\G`（看 `Engine` 列）或 `show engines;`。

## 七、面试问答

**Q1：MySQL 有哪些存储引擎？InnoDB 和 MyISAM 的区别？**

常见三种：**InnoDB**（5.5 后默认）、**MyISAM**（5.5 前默认）、**MEMORY**（内存表）。InnoDB 与 MyISAM 的核心差异有四点：① **事务**——InnoDB 支持，MyISAM 不支持；② **锁粒度**——InnoDB 支持行锁（默认）和表锁，MyISAM 只有表锁，高并发写场景差距巨大；③ **崩溃恢复**——InnoDB 靠 redo log 自动恢复，MyISAM 需手动修复且可能丢数据；④ **索引结构**——InnoDB 是聚簇索引（主键索引叶子存整行），MyISAM 索引与数据分离（叶子存行地址，每次都多一跳）。所以生产环境一律选 InnoDB。

**Q2：MyISAM 的 `count(*)` 比 InnoDB 快，为什么还用 InnoDB？**

MyISAM 维护了一个表级行数计数器，`count(*)` 直接返回；InnoDB 必须扫描索引逐行做 **MVCC 可见性判断**（因为不同事务看到的行数可能不同），所以更慢。但这是**支持并发事务的必然成本**——MyISAM 换来这个"快"的代价是全表锁。真实业务里 `count(*)` 也很少直接对全表执行，通常用缓存计数或汇总表替代。

**Q3：InnoDB 的行锁是加在行上还是索引上？**

加在**索引项**上。这带来一个重要推论：如果 `where` 条件没有走索引，InnoDB 定位不到具体索引项，会退化成**对所有记录逐行加锁**，效果接近表锁但开销更大。所以"索引失效"不仅是性能问题，更是**并发问题**——这也是 DBA 排查锁等待时第一步就看执行计划的原因。

**Q4：MySQL 8.0 后表结构存在哪？**

8.0 之前存在 `.frm` 文件里；8.0 起 InnoDB 的表结构被并入**数据字典**（InnoDB 系统表，通过 `information_schema` 暴露），`.frm` 文件被移除，建表后目录下只剩 `.ibd` 表空间文件。MyISAM 至今仍使用 `.frm` + `.MYD` + `.MYI` 三文件结构。
