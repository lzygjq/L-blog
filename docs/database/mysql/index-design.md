# 索引设计：原则、覆盖索引与失效

## 一、问题场景

索引建了，`EXPLAIN` 里 `key` 列却是 `NULL`——**索引就在那儿，但优化器没用它**。

这是 MySQL 面试里仅次于"B+ 树"的高频题，因为它同时考三件事：**你懂不懂索引的结构（最左前缀的本质）、懂不懂优化器的行为（为什么不走）、有没有实际排查经验（怎么确认）**。

本文解决四个问题：**怎么让索引被用上（最左前缀）→ 怎么让查询不回表（覆盖索引）→ 什么情况索引会失效（9 种场景）→ 索引该建在哪些列上（创建原则）**。

## 二、覆盖索引：让二级索引一步到位

回顾 [索引底层](/database/mysql/index-structure)：二级索引的叶子只存主键值，所以用它查数据要**回表**。但如果 `select` 要返回的列**全都在索引里**，就不用回聚簇索引了——这叫**覆盖索引**。

用同一条查询的三种写法对比（表 `tb`，主键 `id`，`name` 上有索引）：

| SQL | 走哪个索引 | 是否回表 | 说明 |
|---|---|---|---|
| `select * from tb where id = 2` | 聚簇索引 | ❌ 不用 | 主键查询，叶子就是整行，**天然覆盖** |
| `select id, name from tb where name = 'Arm'` | `name` 二级索引 | ❌ 不用 | `id` 和 `name` 都在索引里 → **覆盖索引** |
| `select id, name, gender from tb where name = 'Arm'` | `name` 二级索引 | ✅ 要回表 | `gender` 不在索引里，必须回聚簇索引取 |

**判断标准一句话**：`EXPLAIN` 的 `Extra` 出现 **`Using index`** 就是覆盖索引（**不出现 `Using where`**）。

**为什么覆盖索引收益巨大**：回表是"逐行回到聚簇索引查"，100 万行命中就是 100 万次随机 IO。覆盖索引把这一步整体省掉，**代价只是一次顺序扫描二级索引**。

> **实践结论**：`select *` 是回表的最大来源。业务代码里**显式列出需要的字段**，不只是规范问题，是性能问题。

## 三、最左前缀法则

联合索引 `idx_a_b_c (a, b, c)` 在 B+ 树里的排序方式是**先按 a 排，a 相同再按 b 排，b 相同再按 c 排**——和电话簿"先按姓、同姓再按名"完全一样。

**由这个排序方式可以直接推出**：

| 查询条件 | 能否用索引 | 用到了哪几列 |
|---|---|---|
| `where a = 1` | ✅ | a |
| `where a = 1 and b = 2` | ✅ | a, b |
| `where a = 1 and b = 2 and c = 3` | ✅ | a, b, c（全用上） |
| `where b = 2 and c = 3` | ❌ 完全失效 | —（**跳过了最左列 a**） |
| `where a = 1 and c = 3` | ⚠️ 部分失效 | 只有 a（**b 被跳过，c 用不上**） |
| `where a = 1 and b > 2 and c = 3` | ⚠️ 部分失效 | a, b（**范围查询右侧的 c 失效**） |
| `where a like 'x%' and b = 2` | ✅ | a, b（前缀匹配等价于范围，但 `like 'x%'` 后 b 仍可用需谨慎验证） |

**两条铁律**：

1. **必须从最左列开始，不能跳过中间列**。跳过的那一列**之后的列全部失效**。
2. **范围查询（`>` `<` `between` `like 'x%'`）右侧的列失效**——因为范围之后的排序被打乱了。

**字段顺序怎么排**（这一点常被问）：联合索引 `(a, b, c)` 的字段顺序应该按 **"等值条件优先、区分度高的靠前、范围条件放最后"** 来排。比如常见查询是 `where status = 1 and user_id = 5 and create_time > '2026-01-01'`，索引应该建 `(status, user_id, create_time)` 或 `(user_id, status, create_time)`——**把两个等值列放前面，范围列放最后**。

## 四、索引失效的 9 种场景

前 5 种是高频标配，后 4 种是面试追问时拉开差距的地方：

| # | 场景 | 示例 | 原因 |
|---|---|---|---|
| 1 | **违反最左前缀法则** | 联合索引 `(a,b,c)`，查 `where b = 2` | 索引按 a 有序，跳过 a 无法定位 |
| 2 | **范围查询右侧的列失效** | 索引 `(a,b,c)`，查 `where a=1 and b>2 and c=3` | 范围之后排序失效，c 用不上 |
| 3 | **索引列上做运算或函数** | `where id + 1 = 10`、`where date(create_time) = '2026-01-01'` | 索引存的是**列原始值**，运算后的结果不在索引里。应改为 `id = 9` / `create_time >= '2026-01-01' and < '2026-01-02'` |
| 4 | **字符串不加引号（隐式类型转换）** | `where name = 123`（name 是 varchar） | MySQL 会把列转成数字再比较 → **等价于在列上做函数** → 索引失效 |
| 5 | **以 `%` 开头的 LIKE** | `like '%abc'` 失效；`like 'abc%'` 不失效 | 前缀未知，无法在 B+ 树里定位起点。`'abc%'` 是**范围查询**，可以用索引 |
| 6 | **OR 连接的列有一侧没索引** | `where a = 1 or b = 2`，a 有索引 b 没有 | 必须**两侧都有索引**才可能用上；否则只能全表扫 |
| 7 | **不等于 `!=` / `<>`** | `where status != 1` | 优化器评估后可能认为**扫索引还不如直接全表扫**（当不等号命中的比例很高时） |
| 8 | **`IS NOT NULL` / `NOT IN`** | `where name is not null` | 取反类条件命中行数多，优化器倾向全表扫；实际取决于数据分布 |
| 9 | **优化器主动选择全表扫描** | 表数据量很小，或索引**区分度极低** | 走索引要"索引 + 回表"两步，全表扫一步到位时更划算 |

> **第 9 条是最容易被误判的**：索引没被用**不等于**索引有问题。优化器是基于**成本**决策的——数据量小、区分度低、或查询命中的行占比很高（经验上超过 20%~30%）时，全表扫描反而更快。**不要当成 bug 去"修"**。

**排查流程**（这一步是面试最想听的实操）：

```sql
EXPLAIN select * from tb where name = 'Arm';
-- ① 看 key        → 是否为 NULL？NULL = 没走索引
-- ② 看 possible_keys → 有值但 key 为 NULL = 有索引但优化器没选（对应第 9 条）
-- ③ 看 type       → all = 全表扫描；index = 扫整棵索引树
-- ④ 看 key_len    → 判断联合索引用到了前几个字段（变长字段注意 +2B 长度、允许 NULL 再 +1B）
-- ⑤ 看 Extra      → Using where（需回表） / Using index（覆盖索引，不回表）
```

## 五、索引创建原则

按决策顺序组织成一张清单：

| # | 原则 | 判断依据 |
|---|---|---|
| 1 | **数据量大且查询频繁的表才建** | 单表建议 **10 万条以上**；小表全表扫更快 |
| 2 | **建在 `where` / `order by` / `group by` 的列上** | 这三类子句才是索引的用武之地；`select` 列表里的列靠**覆盖索引**顺带解决 |
| 3 | **选区分度高的列，尽量建唯一索引** | 区分度 = `count(distinct col) / count(*)`。用户 ID 接近 1，性别只有 0.5 → 性别建索引几乎无收益 |
| 4 | **长字符串建前缀索引** | `create index idx_name on t(name(10))`，只索引前 N 个字符，显著减小索引体积 |
| 5 | **优先联合索引，少建单列索引** | 一个 `(a,b,c)` 能顶 `(a)`、`(a,b)`、`(a,b,c)` 三个查询场景，还能做覆盖索引 |
| 6 | **控制索引数量** | 索引越多，`insert`/`update`/`delete` 越慢（每个索引都要维护 B+ 树），且优化器选择成本更高 |
| 7 | **字段尽量 `NOT NULL` 并设默认值** | ① `NULL` 会让索引多占 1 字节标志位；② `NULL` 参与比较时语义复杂，优化器更难选索引；③ `count(col)` 会忽略 NULL |

**区分度怎么查**：

```sql
select count(distinct user_id) / count(*) as user_id_sel,
       count(distinct status)  / count(*) as status_sel
from t_order;
-- 越接近 1 越适合建索引；接近 0 的列（如性别、状态只有几种值）单独建索引意义不大
```

> **联合索引 vs 多个单列索引，MySQL 怎么选？** 同一张表上如果既有 `(a)` 又有 `(a,b)`，优化器会倾向选择**能覆盖更多条件的那一个**。但这不代表建得越多越好——**每多一个索引，写入就多一次 B+ 树维护**。原则是：**用最少的联合索引覆盖最多的查询模式**。

## 六、实战：把超大分页从 5 秒降到 50 毫秒

`limit 9000000, 10` 的写法，MySQL 会**先排序取出前 9000010 条，再丢弃前 900 万条**——真正要的只有最后 10 条。这就是上面"回表 + 排序"两种代价的叠加。

**解法一：覆盖索引 + 子查询（延迟关联）**

```sql
-- ❌ 慢：既回表又排序 900 万行
select * from tb_sku order by id limit 9000000, 10;

-- ✅ 快：子查询只走主键索引（天然覆盖），排序代价极小；
--        外层再用这 10 个 id 回表取整行，只回表 10 次
select t.* from tb_sku t,
       (select id from tb_sku order by id limit 9000000, 10) a
where t.id = a.id;
```

**核心思想**：**把"排序 900 万行并回表"改成"排序 900 万个主键（覆盖索引，不回表）+ 只回表 10 行"**。

**解法二：游标 / 书签式分页（推荐用于无限下拉）**

```sql
-- 记住上一页最后一条的 id，下一页从它之后开始
select * from tb_sku where id > 9000000 order by id limit 10;
```

**这是最优解**——直接用 `where` 定位起点，不需要"跳过并丢弃"，代价与页码无关（恒定为 O(1) 定位 + 10 行扫描）。代价是**不能跳页**，适合"下一页"式的无限滚动。

**解法三：限制页码**

产品层面限制最大页数（如最多 100 页），或把深度分页改成"按条件筛选缩小范围"。这是工程上最省事也最常被忽略的一招。

## 七、面试问答

**Q1：什么是覆盖索引？**

查询要返回的列**全都能从索引里取到**，不需要回表，就是覆盖索引。判断标志是 `EXPLAIN` 的 `Extra` 出现 `Using index`（不出现 `Using where`）。典型例子：`name` 上建了索引，`select id, name from tb where name = 'Arm'` 就是覆盖索引；而 `select id, name, gender from tb where name = 'Arm'` 因为 `gender` 不在索引中，必须回表。所以实践中要**避免 `select *`**——它是回表的最大来源。

**Q2：什么情况下索引会失效？**

主要 9 种：① 违反最左前缀法则（联合索引未从最左列开始，或跳过中间列）；② 范围查询右侧的列失效；③ 索引列上做运算或函数（`id+1=10`、`date(create_time)=...`）；④ 字符串不加引号导致隐式类型转换；⑤ `like '%abc'` 以百分号开头；⑥ `or` 连接时有一侧没索引；⑦ 使用 `!=` / `<>`；⑧ `is not null` / `not in`；⑨ **优化器主动选择全表扫描**（表小或索引区分度低）。实际排查时用 `EXPLAIN` 看 `key` 是否为 `NULL`，并对比 `possible_keys` 判断是"没有可用索引"还是"有索引但优化器没选"。

**Q3：`like 'abc%'` 和 `like '%abc'` 有什么区别？**

`'abc%'` 是**前缀匹配**，属于范围查询，可以用索引（在 B+ 树里定位到 `abc` 开头的起点，然后顺叶子链表扫）；`'%abc'` 前缀未知，无法确定索引树的查找起点，**只能全表扫描**。如果业务必须做后缀或中间匹配，方案是：① 把后缀查询改写成前缀查询（**存一份反转字段**，查 `%abc` 变成查 `cba%`）；② 交给他方检索组件（ES / 全文索引）。

**Q4：联合索引的字段顺序怎么定？**

按三条优先级排：① **等值条件优先**——`where a=1 and b=2 and c>3` 应建 `(a,b,c)`，把范围列放最后，因为**范围查询右侧的列会失效**；② **区分度高的列靠前**——能让索引在树的早期就快速收敛；③ **考虑覆盖索引**——如果有个高频查询 `select a,b,c`，把这三列放进同一个联合索引就能顺带覆盖。**顺序不是凭感觉，是由查询模式倒推出来的。**

**Q5：索引是不是建得越多越好？**

不是。每个索引都是一棵独立的 B+ 树，**所有写操作（insert/update/delete）都要同步维护**——表上 5 个索引，一次插入要更新 5 棵树。此外索引越多，优化器评估候选索引的成本越高，还可能选错。原则是：**用最少的联合索引覆盖最多的查询模式**，并通过 `sys.schema_unused_indexes` 之类的视图定期清理从未被使用的索引。
