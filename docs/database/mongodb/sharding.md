# 分片集群与扩展

副本集解决了"一台机器挂了怎么办"，没解决"一台机器装不下、写不动怎么办"。后者要靠分片——**把同一份数据按某个键切开，放到多组机器上。**

分片的所有难题集中在同一个地方：**按什么键切。** 这个决定在数据量小的时候做，代价却在数据量大的时候显现；改它的成本极高，所以它是这套体系里最需要"想清楚再动手"的一步。

## 一、三个组件各干什么 {#topology}

```
                    ┌──────────────────────────────────────────┐
   客户端 ──────▶   │  mongos（路由器，无状态，可多个）          │
                    └───────────────┬──────────────────────────┘
                                    │  ① 查元数据：这个 key 属于哪个分片
                                    │  ② 把请求转发过去；散射时归并结果
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      ┌───────────────┐     ┌───────────────┐     ┌───────────────┐
      │  Shard A      │     │  Shard B      │     │  Shard C      │
      │ （副本集）     │     │ （副本集）     │     │ （副本集）     │
      │ 数据片段 1     │     │ 数据片段 2     │     │ 数据片段 3     │
      └───────────────┘     └───────────────┘     └───────────────┘
              ▲                     ▲                     ▲
              └─────────────────────┼─────────────────────┘
                                    │  存"哪个片段在哪"的元数据
                    ┌───────────────┴──────────────────────────┐
                    │  Config Server（副本集，3 节点）           │
                    └──────────────────────────────────────────┘
```

| 组件 | 有无状态 | 关键点 |
|---|---|---|
| **mongos** | 无状态 | 只做路由与结果归并；**可以水平加，因为它们之间不通信** |
| **Config Server** | 有状态（元数据） | 必须是副本集（生产 3 节点）；**挂了不影响已有读写，只影响分片决策与迁移** |
| **Shard** | 有状态（数据） | **每个分片本身就是一个副本集**——所以"分片"与"副本"是两层叠加，不是二选一 |

8.0 起 Config Server 也可以承载应用数据（**config shard**），小规模部署可以把元数据和数据合到一组节点上，省掉一组机器。这是一条"起步成本下降"的路径，但**代价是把元数据的可用性和业务数据绑在了一起**。

### 与"外挂式分库分表"的差别

| | 中间件分片（如 ShardingSphere） | MongoDB 原生分片 |
|---|---|---|
| 数据分布信息 | 在中间件配置 / 注册中心里 | **在集群自己维护的元数据里** |
| 扩缩容 | 需要迁移任务 + 双写 + 校验 | 有 balancer 自动均衡 |
| 改分片规则 | 通常要停服或走复杂迁移 | 5.0 起支持在线 reshard |
| 代价 | 应用侧要理解中间件的限制（跨库 JOIN、分布式事务） | **绑定在 MongoDB 上，跨引擎不可移植** |

**没有免费的方案**：外挂式的代价在"应用要迁就中间件"，原生的代价在"你必须用这个数据库"。

## 二、分片键：唯一一个事后代价极高的决定 {#shard-key}

### 四条判据

| 判据 | 要避免什么 | 好分片键的特征 |
|---|---|---|
| **① 基数（cardinality）** | 值太少 → 分不到几个分片 | 有足够多不同的值（百万级） |
| **② 频率分布** | 某几个值特别"热" → 数据倾斜 | 各值对应的文档数大致均匀 |
| **③ 单调性** | 新写全落同一个 chunk → **写热点** | 不随时间单调递增 |
| **④ 查询覆盖** | 查询不带分片键 → 每次都要问所有分片 | **常用查询都带它** |

四条里，**③ 和 ④ 是实战中真正决定成败的两条**，而且它们经常互相打架。

### 单调递增键：为什么它是灾难

这是最容易理解、也最容易踩的一条。设想按 `order_id`（自增）或 `createdAt` 分片：

```
   分片键范围：  [0, 1000)  [1000, 2000)  [2000, 3000)
   落在哪片：     Shard A     Shard B      Shard C
                    ▲
                    │
        新的写入永远落在"值最大"的那个 chunk 上
                    │
                    ▼
   结果：① 任何时刻，所有写都只打到同一个分片（写吞吐上限 = 单分片上限）
        ② 该分片上的 chunk 不断分裂、被迁走，迁移的开销也集中在这一片
        ③ 加再多的分片，写吞吐都不会提升
```

**这就是"分片了但没扩容"的典型症状**：数据库明明分了 6 片，写入延迟和单机一样。

> **注意**：默认的 `_id`（ObjectId）**前 4 字节是时间戳，整体近似单调递增**——所以"用 `_id` 当分片键"和"用 `createdAt` 当分片键"是同一个问题。区别只在于你是有意踩的还是无意踩的。

### ranged 还是 hashed

| | 范围分片（ranged） | 哈希分片（hashed） |
|---|---|---|
| 写法 | `{ userId: 1 }` | `{ userId: 'hashed' }` |
| 写分布 | 键单调时有热点 | **天然均匀**（哈希打散） |
| 范围查询 | **只打到相关的少数分片** | ✗ **必须广播到所有分片**（相邻哈希值不在同一片） |
| 查询定向量 | 高（范围与等值都能定向） | 等值能定向，范围不能 |
| 适用 | 查询带范围、键本身均匀 | 键单调、或只需点查 |

**哈希分片是把"范围查询的效率"换成"写分布的均匀"**。所以选它的前提是：**你的查询几乎都是等值点查，没有按分片键的范围查询**。如果既有范围查询又要均匀分布，正解是**复合分片键**。

### 复合分片键：一个常见的折中

```js
// 多租户场景的经典写法
db.orders.createIndex({ tenantId: 1, _id: 1 })
sh.shardCollection('app.orders', { tenantId: 1, _id: 1 })
```

- `tenantId` 提供**查询隔离**：几乎所有查询都带租户，于是请求只打到少数分片；
- `_id` 提供**足够基数**：同一租户内还能继续切分，避免"某个大租户把一片撑爆"；
- 组合之后，**单租户的写入不再集中在一个 chunk 上**（`_id` 避免了单调性带来的热点）。

**代价**是分片键变长、chunk 分裂粒度变细（管理开销略增）。**这是"知道取舍在哪"的答案，而不是"标准答案"**——单租户数据量很小的场景，`{ tenantId: 1 }` 单独就够。

### 两条硬限制

**① 分片键索引不能是某些类型**：不能是**降序索引**、**部分索引**、**地理索引**、**文本索引**、**通配符索引**。分片键索引只能是"分片键本身升序的单字段索引"、"以分片键开头的复合索引"或"哈希索引"。

**② 分片集合上，唯一索引必须以分片键为前缀。**

```js
// 分片键是 { tenantId: 1 }
db.users.createIndex({ email: 1 }, { unique: true })              // ✗ 被拒绝
db.users.createIndex({ tenantId: 1, email: 1 }, { unique: true }) // ✓ 可以
```

原因很直接：**唯一性检查没法跨分片做**。同一集群里 Shard A 看不到 Shard B 上有没有同一个 `email`——**只有把分片键放进唯一索引前缀，唯一性才被限制在分片内、可被本地校验**。

> 这条限制会传导到建模：如果"邮箱全局唯一"是硬需求，那么分片键就必须包含它或者另想办法（比如把唯一性检查上提到应用层，用一个专门的集合做"唯一性令牌"）。**这类约束要在选分片键的时候一起想，不能等分了之后再发现建不了索引。**

## 三、chunk 与 balancer {#chunk-balancer}

分片集合被切成 **chunk**（默认 128MB 一片），每个 chunk 是一个**连续的分片键范围**，完整地放在某一个分片上。

| 机制 | 做什么 | 触发条件 |
|---|---|---|
| **split** | 把过大的 chunk 一分为二 | chunk 超过阈值大小 |
| **balancer** | 把 chunk 从"多的分片"搬到"少的分片" | 各分片 chunk 数量不均衡 |
| **migration** | 实际的搬迁过程 | 由 balancer 发起 |

三条运维要点：

**① balancer 可以设时间窗**，让它只在低峰期搬（迁移会消耗两端分片的 IO）：

```js
use config
db.settings.update(
  { _id: 'balancer' },
  { $set: { activeWindow: { start: '01:00', stop: '05:00' } } },
  { upsert: true }
)
```

**② jumbo chunk 是"搬不动的大块"**。当某个 chunk 超过大小阈值、却因为**内部所有文档的分片键值相同**而无法再 split 时，它被标记为 jumbo。**jumbo chunk 不能被迁移**——于是它所在的分片会持续偏重，均衡机制对它失效。

jumbo 的两个成因与修法：

| 成因 | 表现 | 修法 |
|---|---|---|
| **分片键基数不足** | 某个键值下有几十万文档，全在一个 chunk 里 | 加后缀字段细化分片键，或 reshard 换键 |
| **键值分布极不均匀** | 恰好一个"大客户"占了绝大多数数据 | reshard 换成哈希分片，或改复合键 |

**③ 迁移遗留的孤儿文档**（已经在目标分片的迁移过程中被复制过去、但源分片还没删掉的文档）会导致**统计数虚高**。从 4.4 起**自动清理**默认开启，一般不用手工干预；但在排查"为什么 `count()` 和实际对不上"时要知道有这个来源。

### 8.0 的分片运维改进

| 能力 | 说明 |
|---|---|
| **数据分布约快 50 倍** | 官方口径：初始分布与再平衡速度大幅提升，起步成本下降 |
| `moveCollection` | **迁移未分片的集合**到指定分片 |
| `unshardCollection` | **把一个分片集合改回未分片**（数据集中到一个分片） |
| `abortMoveCollection` / `abortUnshardCollection` | 中止上述操作 |
| `reshardCollection` 支持 `forceRedistribution` | 在同一分片键上重新分布数据（不换键也能重新洗牌） |

`unshardCollection` 这条特别值得记住：**它让"分错了"不再是单向决定**——数据量回落到单机能扛的时候，可以收回来。

## 四、定向查询与散射查询 {#targeted-vs-scatter}

mongos 收到查询后的分岔只有两条：

```
   查询条件里有没有分片键？
        │
        ├── 有 → 定位到具体分片（targeted）        ← 延迟与单分片相当
        │
        └── 没有 → 广播给所有分片，再归并结果（scatter-gather）
                     │
                     └── 延迟 ≈ 最慢的那个分片 + 归并开销
```

**散射查询的代价不是"除以分片数"，而是"取最慢值"。** 所以有两条反直觉的结论：

| 结论 | 原因 |
|---|---|
| **加分片不会让散射查询变快，只会变慢** | 参与的分片越多，"最慢的那个"出现概率越高，归并的数据量也越大 |
| **散射查询上的 `LIMIT` 不能减少扫描量** | 每个分片都必须扫到自己那部分，mongos 才能保证全局前 N 条是对的 |

第二条和 [ClickHouse 分布式表的 `LIMIT`](/bigdata/clickhouse/cluster-and-replica#query-path)是同一个道理——**"全局有序 / 全局前 N"这件事，在分片架构上天生要付全量扫描的成本**。两者是同一类问题的两种实现。

**判断一个分片键选得好不好，最直接的办法就是看它能不能让主查询定向：**

```
   在 explain 的输出里看 shards 字段：
       只出现一个分片  → 定向，分片键选对了
       出现全部分片    → 散射，分片键与查询不匹配
```

**如果一个系统的绝大多数查询都是散射的，那么它做了分片，却没有获得分片的好处**——只是一次性地把数据摊开了，每次查询都要付"问所有分片"的成本。**这种系统应该停下来重新考虑分片键，而不是继续加机器。**

## 五、改分片键的代价 {#resharding}

5.0 起支持**在线改分片键**（`reshardCollection`），不用停服。但它不是免费的：

| 代价 | 说明 |
|---|---|
| **存储翻倍** | 切换期新旧两份数据同时存在，峰值存储需求约为 2× |
| **持续时长与数据量成正比** | 大集合上是小时级甚至更久的操作 |
| **期间写入受影响** | 有额外的同步与校验开销 |
| **不能随便反复改** | 它是"纠错手段"，不是"迭代手段" |

所以正确的态度是：**分片键在数据量还小的时候就要想清楚，把 reshard 当成保险而不是常规操作。**

判断"该 reshard 还是该细化分片键"的判据：

```
   问题症状是什么？
        │
        ├── 写热点（新写总落在一片）  → 分片键单调 → 换键或改哈希（reshard）
        │
        ├── 查询散射（主查询不带分片键）→ 换键，让分片键覆盖主查询（reshard）
        │
        └── jumbo chunk（基数不足）   → 优先"细化分片键"（加后缀字段）
                                         基数还不够才考虑 reshard
```

## 六、与分库分表的对照 {#vs-sharding-middleware}

| 维度 | 应用层分库分表（ShardingSphere 等） | MongoDB 原生分片 |
|---|---|---|
| 路由在哪 | 应用/中间件，按配置计算 | mongos，按集群元数据 |
| 扩容 | 迁移 + 双写 + 校验，通常要专门方案 | balancer 自动，可设时间窗 |
| 跨片查询 | 中间件归并（能力受限于其支持度） | mongos 归并，语义一致 |
| 跨片事务 | 依赖中间件的分布式事务 | 原生二阶段提交（有[四条边界](/database/mongodb/consistency-and-transactions#transactions)） |
| 分片键可改吗 | 变更通常意味着重建 | 5.0 起支持在线 reshard |
| 主要代价 | 应用要迁就中间件的限制 | **与引擎绑定** |

共性要记住：**两者的分片键选择判据是同一套**（基数 / 分布 / 单调性 / 查询覆盖）。所以[分库分表](/database/sharding/)那篇里的思路在这里全部适用，**只是执行者从中间件换成了数据库自己**。

## 七、面试高频（10 题）{#interview}

| # | 问题 | 一句话答案 | 详见 |
|---|---|---|---|
| 1 | mongos 是无状态的吗？挂了会怎样？ | 是——它只做路由与归并，多个 mongos 之间不通信；挂一个不影响数据，客户端换一个连即可 | [§1](#topology) |
| 2 | Config Server 挂了，读写还能进行吗？ | 能——已有分片的读写不受影响；受影响的是**分片决策与 chunk 迁移** | [§1](#topology) |
| 3 | 分片键该怎么选？ | 四条判据：基数、频率分布、**单调性**、**查询覆盖**；后两条最容易打架，也最决定成败 | [§2](#shard-key) |
| 4 | 为什么自增 ID / 时间戳做分片键是灾难？ | 新写永远落在"值最大"的那个 chunk，任何时刻写只打到一片——**分了片但写吞吐没有提升** | [§2](#shard-key) |
| 5 | 哈希分片的代价是什么？ | 牺牲范围查询：相邻哈希值不在同一分片，**按分片键的范围查询必须广播到所有分片** | [§2](#shard-key) |
| 6 | 为什么分片集合的唯一索引必须以分片键为前缀？ | 唯一性检查无法跨分片进行——**只有把分片键放进前缀，唯一性才被限制在分片内、可本地校验** | [§2](#shard-key) |
| 7 | jumbo chunk 是怎么来的？ | 某个 chunk 超阈值、但因**内部所有文档分片键值相同**而无法再 split，于是**不能被迁移**，均衡对它失效 | [§3](#chunk-balancer) |
| 8 | 散射查询为什么加机器也不会快？ | 它的延迟由**最慢的那个分片**决定而非平均值；分片越多越容易撞上慢分片，归并量也更大 | [§4](#targeted-vs-scatter) |
| 9 | 分片集合上的 `LIMIT` 能减少扫描吗？ | 不能——每个分片都要扫，mongos 才能保证全局前 N 条正确；与 [ClickHouse 分布式表](/bigdata/clickhouse/cluster-and-replica#query-path)同理 | [§4](#targeted-vs-scatter) |
| 10 | 分片键选错了怎么办？ | 5.0 起可在线 `reshardCollection`，代价是**峰值存储翻倍 + 时长与数据量成正比**；所以它该是保险而非常规操作 | [§5](#resharding) |
