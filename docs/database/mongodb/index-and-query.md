# 索引与查询优化

索引设计在文档数据库里的权重比关系型更高。原因不在"它更重要"，而在**查询形态更自由**：关系型里 SQL 是声明式的，规划器有更多重排空间；文档库里查询文档与管道顺序基本就决定了执行路径，**写错就是慢，而且慢得没有救**。

## 一、索引只有一个本质：它是有序的 {#ordered}

抛开类型与实现，索引的价值可以用一句话概括：**它是按某个键排好序的一份副本**。所有加速效果都是这句话的推论：

| 查询形态 | 为什么能加速 | 靠的是有序的哪一面 |
|---|---|---|
| 等值匹配 `{ status: 'paid' }` | 直接定位到那一段 | 有序 → **二分定位** |
| 范围 `{ createdAt: { $gte: X } }` | 从起点连续往后读 | 有序 → **相邻值挨在一起** |
| 排序 `.sort({ createdAt: -1 })` | **顺着读出来就是有序的，不用再排** | 有序 → **顺序即结果** |
| 覆盖查询（只返回索引里的字段） | 根本不用回表 | 有序副本里**已经带了这些值** |

第三行是这一篇所有设计的出发点：**索引之所以能让排序免费，是因为"索引里的顺序"和"你要的顺序"是同一个顺序。** 一旦这个一致性被破坏（后面 ESR 讲的就是破坏它的一种方式），排序就要另外花代价——退回内存里排。

## 二、复合索引与 ESR 规则 {#esr}

复合索引（多个键组成的索引）才是日常主力。**键的顺序不是随便写的**——它决定了索引能否同时承担"过滤"和"排序"两件事。

### 2.1 规则

**等值字段在前 → 排序字段居中 → 范围字段在后（Equality, Sort, Range）。**

推理链条只有两步：

```
① 等值匹配会选中索引里连续的一段，而"段内"的后续键仍然保持有序
        │
        └──▶ 所以等值字段排前面，不会破坏后面字段的有序性

② 范围匹配选中的是一"片"值，片内的后续键
   —— 不再全局有序（值分布是散的）
        │
        └──▶ 所以范围字段一旦排在排序字段前面，排序就用不上索引了
```

### 2.2 一个完整的例子

查询语义：找出某状态下、某套餐的、近 30 天的用户，按创建时间倒序。

```js
db.users.find({
  status: 'active',              // 等值
  plan: 'pro',                   // 等值
  createdAt: { $gte: cutoff }    // 范围
}).sort({ createdAt: -1 })       // 排序
```

| 索引 | 判定 | 说明 |
|---|---|---|
| `{ createdAt: -1, status: 1, plan: 1 }` | ✗ 最差 | 范围在最前，后面的等值字段完全用不上（无法缩小扫描段） |
| `{ status: 1, createdAt: -1, plan: 1 }` | ✗ | 等值只用了半个，`plan` 排在排序键后面，`totalDocsExamined` 远大于 `nReturned` |
| `{ status: 1, plan: 1, createdAt: -1 }` | ✓ **ESR** | 两个等值先收窄，`createdAt` 既做范围又提供排序——**排序键与范围键是同一个字段时，一个位置满足两个角色** |

最后一行那句加粗是实战里最常遇到的简化：**当范围条件与排序用的是同一个字段时，`{ 等值..., 该字段: -1 }` 就够了**。

### 2.3 例外：范围极强选择性时反过来排（ERS）

官方文档明确给了这条例外：**如果范围谓词的选择性非常强**（能把结果砍到极少），把范围放在排序前面反而更好——因为内存排序此时只需要处理很少的文档。

```js
// 例：status 覆盖了 90% 的文档（选择性差），但 traceId 唯一定位一条（选择性极强）
db.logs.find({ status: 'ok', traceId: { $gte: 'a', $lte: 'b' } }).sort({ createdAt: -1 })

// ERS：先用范围把数据砍到几条，再对这几条内存排序，代价可以忽略
db.logs.createIndex({ status: 1, traceId: 1, createdAt: -1 })
```

**判据是"排序的文档数量"**：如果走 ESR 之后要排序的文档仍然很多，ERS 就是错的。**这条例外必须用 `explain` 验证，不能凭感觉**——它的收益来自数据分布，而数据分布会变。

### 2.4 三条配套规则

**① 排序方向必须匹配（或完全取反）**。索引本身可以被反向遍历，所以"索引升序、查询降序"没问题；但**多字段排序的方向组合必须一致**：

```js
db.t.find({ status: 'a' }).sort({ name: 1, createdAt: -1 })
db.t.createIndex({ status: 1, name: 1, createdAt: -1 })  // ✓ 与查询方向逐字段一致
db.t.createIndex({ status: -1, name: -1, createdAt: 1 }) // ✓ 完全取反，可反向遍历
db.t.createIndex({ status: 1, name: 1, createdAt: 1 })   // ✗ createdAt 方向不匹配 → 内存排序
```

**② 前缀复用**。`{ a: 1, b: 1, c: 1 }` 天然也能服务 `{ a }` 与 `{ a, b }` 的查询（仍受 ESR 约束）。所以**设计时要想"一个索引能不能同时覆盖两种查询形态"**，而不是给每个查询各建一个——索引不是免费的，每个索引都在写入时被维护一次。

**③ 覆盖查询必须显式排除 `_id`**。这是文档库特有的坑：

```js
// ✗ 看起来只查了两个字段，但 _id 默认会返回 → 仍然要回表
db.users.find({ status: 'active' }, { name: 1, email: 1 })

// ✓ 显式排除 _id，索引 { status: 1, name: 1, email: 1 } 就能完全覆盖
db.users.find({ status: 'active' }, { _id: 0, name: 1, email: 1 })
```

判据在 `explain` 里看 `winningPlan` 是否出现 `PROJECTION_COVERED`、且没有 `FETCH` 阶段。

> **多键索引（数组字段）不能覆盖查询**——索引项对应的是数组元素，无法还原完整文档的投影结果。这条限制在给数组字段建索引时要先想到。

## 三、explain 怎么读 {#explain}

`explain()` 的字段很多，但**判断索引好不好只需要三个数**：

```js
db.users.find({ status: 'active', plan: 'pro' })
  .sort({ createdAt: -1 })
  .explain('executionStats')
```

| 指标 | 含义 | 判据 |
|---|---|---|
| `totalKeysExamined` | 扫描了多少个索引项 | 应接近 `nReturned` |
| `totalDocsExamined` | **回表读了多少个文档** | 应接近 `nReturned`；远大于说明索引选择性不足 |
| `nReturned` | 最终返回几条 | 分母 |

**三个数应该在一个数量级上。**`totalDocsExamined / nReturned` 是 1 最好、10 可接受、1000 说明索引基本没起作用——**但这条判据有一个例外：查询本身就是范围型的（例如"取某用户最近 100 条"），那 `totalKeysExamined / nReturned` 略大是正常的**，因为它是靠"多点定位 + 合并"实现的。

`winningPlan` 里的关键 stage：

| stage | 含义 | 是否健康 |
|---|---|---|
| `COLLSCAN` | 全集合扫描（一个索引都没用上） | ✗ 除非集合只有几百条 |
| `IXSCAN` | 走了索引 | ✓ |
| `FETCH` | 根据索引项回表取文档 | ✓ 正常，但配合大 `totalDocsExamined` 就是问题 |
| `PROJECTION_COVERED` | 覆盖查询，无需回表 | ✓ 最优 |
| `SORT` | **在内存里排序** | ✗ 出现即说明索引没帮上排序 |
| `SORT_MERGE` | 多个索引扫描结果按序合并（`$in` 小数组时常见） | ✓ 通常健康 |
| `COUNT_SCAN` | 只从索引数数，不读文档 | ✓ |

**`SORT` 是唯一一个"看到就要改"的 stage。** 它有两个直接代价：一是要把结果全部收进内存（单次排序上限 100MB），二是这份数据本来在索引里有顺序，白扔了。

> **MongoDB 6.0 起新增 `allowDiskUseByDefault`**：排序/分组超过 100MB 内存时的行为从"直接报错"变成"默认落盘"。落盘意味着能用（不中断业务），但**慢一个量级**。所以诊断口径是看执行统计里的 `usedDisk` 标记——**出现 `usedDisk: true`，等价于"这里有个索引该建而没建"**。测试环境可以把 `allowDiskUseByDefault` 关掉，让问题立刻暴露。

## 四、`$in` 的 201 元素分界：一个不该依赖的行为 {#in-operator}

先把操作符分成两类，这是判断能否走 ESR 的前提：

| 类别 | 操作符 | 在索引里怎么用 |
|---|---|---|
| **等值类** | `$eq`、单值 `$in` | 定位到连续一段，后续键仍有序 |
| **范围类** | `$gt` / `$gte` / `$lt` / `$lte`、**`$ne` / `$nin`**、**`$regex`** | 选中一片值，**后续键不再有序** |

`$ne` 与 `$nin` 特别容易被当成"不等于是过滤条件"——它们**是范围操作符**，选择性通常极差（扫描索引的大部分），**不应该指望它们承担收窄作用**。`$regex` 同理（非前缀锚定的正则更是如此）。

`$in` 的行为则取决于规模，官方文档给了一个明确的门槛：

| `$in` 元素个数 | 与 `.sort()` 配合时的行为 | 在 ESR 里的角色 |
|---|---|---|
| < 201 | 展开成多次等值查找，结果按索引顺序**归并**（`SORT_MERGE`） | **等同等值**——可以放在索引前部 |
| ≥ 201 | 按范围操作符处理 | **等同范围**——应放在索引后部，后面的键不能用于排序 |

```js
// 小数组：$in 可以放前面
db.cars.find({ manufacturer: { $in: ['GM', 'Ford'] }, price: { $gt: 15000 } })
         .sort({ model: 1 })
db.cars.createIndex({ manufacturer: 1, model: 1, price: 1 })   // ESR：等值类 → 排序 → 范围

// 大数组：$in 已经退化成范围，排序字段必须排在它前面
db.cars.createIndex({ model: 1, manufacturer: 1, price: 1 })
```

**这一节真正的价值不在 201 这个数字**，而在于官方文档在那一节末尾加了一句脚注：**这个分界行为不保证在所有版本中保持一致。**

> **通用纪律**：凡是"官方明确说不保证长期不变"的优化行为，都可以拿来做**当下的性能优化**，但不能写进架构决策——更不能在面试里当成"原理"讲。**正确的讲法是"我知道这个优化存在、也知道它没有被承诺"。**

## 五、索引类型谱系与两条硬限制 {#index-types}

| 类型 | 建法 | 用途 | 关键限制 |
|---|---|---|---|
| 单字段 | `{ a: 1 }` | 最基础 | —— |
| 复合 | `{ a: 1, b: -1 }` | 主力，见 [§2](#esr) | 键顺序即语义 |
| 多键（数组字段） | `{ tags: 1 }` | 数组元素匹配 | 见下方限制 ① |
| 文本 | `{ body: 'text' }` | 分词检索 | 每个集合**只能有一个**文本索引；中文分词能力弱于专用搜索引擎 |
| 地理 | `{ loc: '2dsphere' }` | 附近的人 / 范围内的点 | 不能作为分片键索引 |
| 通配符 | `{ 'attrs.$**': 1 }` | 字段名事先未知 | 只适合"字段名不固定但访问很少"的场景 |
| TTL | `{ expireAt: 1 }, { expireAfterSeconds: 0 }` | 自动过期删除（会话、验证码、日志） | 单字段索引，**不能是复合**；后台每约 60 秒扫一轮，**不是精确定时** |
| 唯一 | `{ email: 1 }, { unique: true }` | 替代外键的一部分职责 | 跨集合做不到 |
| 稀疏 | `{ a: 1 }, { sparse: true }` | 只索引"字段存在"的文档 | 已不推荐，被部分索引取代 |
| 部分 | `{ a: 1 }, { partialFilterExpression: { status: 'active' } }` | 只索引满足条件的子集 | **查询必须包含同样的条件**才能用上 |
| 哈希 | `{ a: 'hashed' }` | 分片时均匀分布 | **不支持范围查询**，见[分片篇](/database/mongodb/sharding#shard-key) |

### 限制 ①：一个复合索引里只能有一个数组字段

对两个数组字段建同一个复合索引会直接报错（`cannot index parallel arrays`）：

```js
// 集合文档：{ tags: ['a','b'], categories: ['x','y'] }
db.p.createIndex({ tags: 1, categories: 1 })
// ✗ CannotIndexParallelArrays: cannot index parallel arrays [categories] [tags]
```

原因是多键索引会把数组**展开成多个索引项**（笛卡尔积），两个数组一起展开会让索引项数爆炸。**修法**：拆成两个单字段索引让查询规划器自己选，或者改数据模型（把组合关系预先物化成单个数组字段）。

### 限制 ②：部分索引的"条件必须写全"

部分索引很容易建了却没被用上——**查询里必须包含与 `partialFilterExpression` 完全一致的条件**：

```js
db.orders.createIndex(
  { createdAt: -1 },
  { partialFilterExpression: { status: 'pending' } }
)

db.orders.find({ status: 'pending' }).sort({ createdAt: -1 })   // ✓ 用得上
db.orders.find({ status: { $in: ['pending'] } }).sort({ createdAt: -1 })  // ✓ 等价写法可以用
db.orders.find({}).sort({ createdAt: -1 })                      // ✗ 无该条件 → 走全扫或别的索引
```

它的价值场景很清楚：**集合里 95% 的数据是"已完成"、只有 5% 是"待处理"，而查询只关心那 5%**——部分索引能把它从几百万条缩到几万条，写入时也只维护那 5%。

> 集合的索引数量有上限（**64 个**）。超过之后写入要维护的索引太多，写性能会显著下降——**"多加几个索引试试"不是可行策略**。

## 六、聚合管道：顺序就是代价 {#aggregation}

聚合管道与 SQL 的对应关系大致如下，**但执行模型不同**：

| 需求 | SQL | 聚合管道 |
|---|---|---|
| 过滤 | `WHERE` | `$match`（**能走索引，必须前置**） |
| 投影 | `SELECT` | `$project` |
| 分组聚合 | `GROUP BY` + 聚合函数 | `$group` |
| 排序 | `ORDER BY` | `$sort`（前置才有机会走索引） |
| 关联 | `JOIN` | `$lookup`（见[文档模型篇](/database/mongodb/document-model#embed-or-reference)） |
| 展开数组 | `unnest` | `$unwind` |
| 窗口函数 | `OVER (...)` | `$setWindowFields` |
| 多路并行统计 | 多个查询 | `$facet`（一次扫描出多份结果） |

三条工程纪律：

**① `$match` 与 `$sort` 必须尽量前置。** 管道是逐阶段流式的，但 `$group` / `$sort` 这类阶段**必须先收齐全部输入才能输出**——一旦它们出现在前面，后面所有阶段的输入规模已经被定死了。判据：`explain` 里如果 `$match` 之后的 `nReturned` 与集合大小同量级，说明过滤来晚了。

**② `$lookup` 的位置决定它是"索引查找"还是"嵌套循环"。** 正确形态是"先 `$match` 把左集合砍到几十上百条，再 `$lookup`"。

**③ 100MB 是内存阶段的共同上限，1000 是管道阶段数的上限。** 超过 100MB 的 `$group` / `$sort` / `$bucket` / `$setWindowFields` 会落盘（6.0 起的默认行为），`usedDisk` 标记会出现在日志与 profiler 里。**管道阶段上限 1000** 则是硬性拒绝——它通常意味着"这段逻辑该在应用层写循环，而不是塞进一个管道"。

> **`$group` 的常见高估**：它常被当成"文档库也能做分析"的证据。放在**几十万到几百万条**、且前面已经过滤过的规模上，这个说法成立；再往上，正确的做法是把数据同步到列式分析引擎（[Doris / ClickHouse](/bigdata/)），而不是把文档库的分析能力往上顶。

## 七、与 MySQL 索引的对照 {#vs-mysql-index}

| 维度 | MySQL | MongoDB |
|---|---|---|
| 结构 | B+ 树，叶子节点链成链表 | 有序树（官方口径 B-tree） |
| 复合索引规则 | **最左前缀** | **ESR**（排序键是显式设计的中间层） |
| 排序能否走索引 | 符合最左前缀即可 | 需满足 ESR，且多字段方向要匹配 |
| 回表 | 二级索引 → 聚簇索引，最多一次 | `FETCH`；**覆盖查询要显式排除 `_id`** |
| 排序失败的表现 | `Using filesort`（有时可接受） | `SORT` stage（**基本都要改**） |
| 索引类型 | 聚簇 / 二级 / 前缀 / 函数 / 全文 | 多键 / 文本 / 地理 / 通配符 / TTL / 部分 / 哈希 |
| 索引数量上限 | 单表 16 个（含主键） | 单集合 64 个 |

**本质差异只有一句**：MySQL 的索引顺序要满足"最左前缀"这条**关于查询能取到哪些键**的规则；MongoDB 的 ESR 则在最左前缀之上多了一条——**因为文档库的排序是显式可设计的，所以排序键可以被刻意插在等值与范围之间**。理解这一点，两边都不会记混。

### 索引设计检查清单

- [ ] 每个高频查询都有对应索引，且**键顺序符合 ESR**（或已用 `explain` 证明确实该用 ERS）
- [ ] `explain('executionStats')` 里**没有 `SORT` stage**，`totalDocsExamined ≈ nReturned`
- [ ] 没有 `COLLSCAN`（除非集合真的只有几百条）
- [ ] 排序方向与索引逐字段一致（或完全取反）
- [ ] 数组字段：确认没有出现"两个数组字段共用一个复合索引"
- [ ] 部分索引的条件与查询条件**逐字对齐**
- [ ] 索引总数远小于 64，且每个索引都能说出"它在服务哪个查询"
- [ ] 聚合管道里 `$match` / `$sort` 已前置；没有 `usedDisk` 标记

## 八、面试高频（8 题）{#interview}

| # | 问题 | 一句话答案 | 详见 |
|---|---|---|---|
| 1 | 复合索引的字段顺序怎么定？ | ESR：等值在前、排序居中、范围在后；**范围一旦排在排序前面，排序就用不上索引了** | [§2.1](#esr) |
| 2 | ESR 有没有例外？ | 有——范围谓词选择性极强时用 ERS 更好，因为内存排序的输入已经被砍到很小；**必须用 `explain` 验，不能凭感觉** | [§2.3](#esr) |
| 3 | 怎么判断一个查询的索引好不好？ | 看 `totalKeysExamined` / `totalDocsExamined` / `nReturned` 三个数是否同量级；`winningPlan` 里**有没有 `SORT`** | [§3](#explain) |
| 4 | 覆盖查询为什么没生效？ | 大概率是没排除 `_id`（默认会返回）；另外**多键索引不能覆盖查询** | [§2.4](#esr) |
| 5 | `$ne` / `$nin` / `$regex` 能靠索引加速吗？ | 它们是**范围操作符**，选择性通常极差，不该承担收窄作用 | [§4](#in-operator) |
| 6 | 一个复合索引能不能同时含两个数组字段？ | 不能，会报 `cannot index parallel arrays`——多键索引展开成笛卡尔积会让索引项爆炸 | [§5](#index-types) |
| 7 | 部分索引建了却没被用上，为什么？ | 查询条件必须与 `partialFilterExpression` 对齐；缺了那个条件就走不了 | [§5](#index-types) |
| 8 | 排序落到磁盘（`usedDisk`）说明什么？ | 等价于"这里有个索引该建而没建"；6.0 起默认允许落盘所以不报错，但慢一个量级 | [§3](#explain) |
