# 文档模型与模式设计

文档数据库最容易被误解的地方是"它不用设计"。事实正好相反：**关系型把建模的决策交给了 DDL（写表结构时定死），文档型把同样的决策交给了你，而且没有编译器帮你检查。**

这一篇讲的是那条主线，以及顺着主线推出来的所有结论。

## 一、一条主线：文档是原子单位 {#thread}

关系型的原子单位是**一行**，文档型的原子单位是**一棵文档树**（含内嵌子文档与数组）。这一个差异推出了后面的全部。

```
   ① 文档是读写与加锁的最小单位（WiredTiger 是文档级并发控制）
        │
        ├──▶ 单文档更新天然原子：一次 updateOne 里改多个字段、
        │    改内嵌子文档、往数组里 push，要么全成、要么全败
        │       └── 收益：绝大多数场景根本不需要事务（官方口径覆盖 80~90% 的需求）
        │
        ├──▶ 建模目标变成「一起访问的数据放一起」
        │       └── 收益：读一个聚合根只需一次查询，没有 JOIN
        │
        ├──▶ 但「放一起」有硬顶：单个文档上限 16MB
        │       └── 代价①：数组不能无界增长 —— 这是头号建模反模式
        │
        ├──▶ 跨文档的一致性要显式买（4.0 起的多文档事务）
        │       └── 代价②：见[复制、一致性与事务](/database/mongodb/consistency-and-transactions#transactions)
        │
        └──▶ 集合之间没有外键、没有跨集合唯一约束、没有 CHECK
                └── 代价③：校验责任前移到应用层（见下一节）
```

**与关系型的分野可以浓缩成一句话**：

| | 关系型 | 文档型 |
|---|---|---|
| 先想什么 | 实体是什么、实体之间什么关系（**先规范化，再按需 JOIN**） | 谁会一起读、谁会一起写（**先看访问模式，再决定放哪**） |
| 代价落在 | 查询时的 JOIN 与规划器负担 | 建模时的一次性判断 + 写入时的冗余 |
| 判断错了会怎样 | 加索引、改 SQL 还能救 | 往往只能改数据模型并做数据迁移 |

> **这条差异的直接推论**：拿关系型的那套"第三范式"去建文档模型，会得到一堆两三个字段的集合，然后到处 `$lookup`——那是**用文档数据库写 SQL**，是所有用法里最贵的一种。反过来，把一起访问的数据硬塞进一个文档、不管它会不会无限增长，则是另一个方向的翻车。

## 二、"无模式"是一个误解：schema-on-read 的代价 {#schema-on-read}

准确的说法不是"没有模式"，而是**校验时机从写入挪到了读取**：

| | 关系型（schema-on-write） | 文档型（schema-on-read） |
|---|---|---|
| 谁来定义形状 | DDL，数据库强制 | 应用代码，**靠约定** |
| 什么时候发现脏数据 | 写入那一刻就被拒绝 | 读到的时候才发现（可能已经是三个月后） |
| 加一个字段 | `ALTER TABLE`，有成本但要过一遍 | 直接写，历史文档没有这个字段 |
| 改一个字段的类型 | 迁移脚本 + 锁表考量 | 新旧两种类型**同时存在**，读取端要都能处理 |
| 查询的影响 | 无 | 索引建在"部分文档没有"的字段上时，选择性与统计都会失真 |

**形状漂移（shape drift）是文档库最常见的隐性债务**：同一集合里只要出现过三种形状的同名文档，后面的每一次查询、每一个索引、每一段聚合都要额外考虑"那种老数据怎么办"。

三个应对手段，按代价从低到高：

**① 应用层约定 + DTO 校验**（成本最低，适合单一服务写入的场景）。所有写入都经过同一层，用代码里的实体类保证形状。**前提是"只有一个写入方"**——一旦有第二个服务或一个脚本绕过它，约定就破了。

**② 数据库校验器 `$jsonSchema`**（第二道闸门，MongoDB 原生支持）：

```js
db.createCollection('orders', {
  validator: {
    $jsonSchema: {
      bsonType: 'object',
      required: ['tenantId', 'status', 'createdAt'],
      properties: {
        tenantId:  { bsonType: 'string' },
        status:    { bsonType: 'string', enum: ['created', 'paid', 'shipped', 'closed'] },
        amount:    { bsonType: ['double', 'decimal'], minimum: 0 },
        createdAt: { bsonType: 'date' }
      }
    }
  },
  // strict：连更新已存在的不合规文档也拦；moderate：只拦"更新后仍不合规"的
  validationLevel: 'moderate',
  // error：拒绝写入；warn：放行但记日志（灰度期先用 warn）
  validationAction: 'warn'
})
```

它的定位是**闸门而不是约束系统**：它能保证"新写入的形状正确"，但既给不了外键，也管不了"跨集合的一致性"。而且**校验器能拦住的和关系型 DDL 能拦住的差着一个量级**——没有唯一约束、没有级联、没有 CHECK 跨字段表达式。

**③ 显式版本字段 + 惰性迁移**。在文档里放一个 `schemaVersion`，读取端按版本分支处理；后台任务在低峰期逐批升级老文档。**它的价值在于把"大爆炸式迁移"换成"渐进式迁移"**——对线上系统，这个差别往往是"能不能改"的差别。

> **面试口径**：被问"文档库没有 schema 怎么保证数据质量"，正确答法是**"schema 没有消失，只是从写入时校验变成了读取时解释"**，然后给出上面三层（应用约定 → `$jsonSchema` 闸门 → 版本字段 + 惰性迁移），并说明**每一层的边界在哪里**。只答"我们代码里保证"会被追问"那别人直接连库写呢"。

## 三、嵌入还是引用：四条判据 {#embed-or-reference}

这是文档建模唯一的核心决策。四条判据，前两条最重要：

| 判据 | 指向**嵌入** | 指向**引用** |
|---|---|---|
| **① 访问模式** | 查询几乎总是连父带子一起读 | 子文档经常被单独查询、单独分页 |
| **② 更新模式** | 总是同时更新，或不常更新 | 子项**高频更新**（嵌入会让父文档频繁被改写） |
| **③ 基数** | 一对一、一对少（几十个以内） | 一对多（几百以上）、**无界增长** |
| **④ 生命周期** | 同生同死，一起归档一起删 | 独立创建、独立删除、独立保留期 |

**「一对多」要按基数分三档处理**，这是建模时最容易一刀切的地方：

| 基数 | 做法 | 例 |
|---|---|---|
| 一对少（≤ 几十） | 嵌入数组 | 订单里的商品行、用户档案里的收货地址 |
| 一对多（几百 ~ 几千） | **父引用**：子文档存父 `_id`，配复合索引 `{ parentId: 1, createdAt: -1 }` | 一篇文章的评论、一个设备的告警 |
| 一对巨多（无界） | 父引用 + 按时间分桶或分集合，绝不放数组 | 订单流水、审计日志、指标点 |

**16MB 是唯一不可协商的硬约束**，而它几乎总是以"数组"的形式被撞上：

```js
// ✗ 最常见的翻车写法：把流水灌进订单文档
//   前三个月一切正常，第四个月某天突然开始报 document too large
{ _id: ObjectId('...'), orderNo: 'A20260916001',
  timeline: [ { at: ISODate('...'), event: 'created' },
              { at: ISODate('...'), event: 'paid' } /* ... 一路增长 ... */ ] }

// ✓ 改成子集合：父文档存摘要，明细单独放
//   orders:        { _id, orderNo, status, lastEventAt, eventCount }
//   order_events:  { _id, orderId, at, event, operator }   ← 索引 { orderId: 1, at: -1 }
```

**关于 `$lookup`，要建立正确的预期**：

| | SQL 的 JOIN | MongoDB 的 `$lookup` |
|---|---|---|
| 执行模型 | 规划器可自由选择哈希连接 / 嵌套循环 / 排序合并，还能重排顺序 | **对左集合的每个文档做一次"到右集合的索引查找"** |
| 优化能力 | 统计信息驱动的重排、谓词下推 | 优化空间小，管道顺序基本决定代价 |
| 适用规模 | 大表 JOIN 大表是常态 | **左集合必须已经被过滤到很小**，且右集合查找字段要有索引 |

> **一句话记住**：`$lookup` 不是不能用，而是**它只能出现在管道的后段**（前面已经 `$match` 把左集合缩小到几十上百条）。**在它前面没有 `$match`，等于把一个嵌套循环写在了全表上。**

## 四、五个建模反模式 {#anti-patterns}

| # | 反模式 | 症状 | 修法 |
|---|---|---|---|
| 1 | **无界数组** | 运行几个月后开始报文档超限；即使没超，读整个文档的 IO 也在持续变大 | 拆子集合，父文档只保留摘要（`count` / `lastAt` / 少量热数据） |
| 2 | **先范式化再 `$lookup`** | 集合数量与关系型一样多，每个查询都挂两三个 `$lookup`，延迟随数据量线性上升 | 回到①的判据：**按访问模式**重定边界，该嵌入的嵌入 |
| 3 | **把文档当预计算缓存** | 一个"汇总字段"被十几个写入路径更新，写冲突与写放大都在这个字段上 | 问："这个字段多久失效一次？" 高频失效的就别存，改成读时算或异步物化 |
| 4 | **多态集合没有判别字段** | 同一集合里三种形状混放，查询要靠 `$exists` 试探，索引选择性极差 | 显式加 `type` 字段并**放进复合索引的第一位** |
| 5 | **用 `_id` 承载业务语义** | `_id` 就是订单号/时间戳，于是它单调递增，**分片后所有新写落在一个 chunk 上** | `_id` 用默认 ObjectId 或随机值；业务编号另存字段并单独建唯一索引 |

第 5 条还有第二重代价：**它把内部标识暴露成了外部契约**。一旦业务编号规则要变，你得改所有存过它的地方——而 `_id` 是不可变的，只能删了重插。

> 关于第 5 条的分片部分，机制见[分片集群与扩展](/database/mongodb/sharding#shard-key)。

**ObjectId 本身也是单调的**（前 4 字节是秒级时间戳），所以"用默认 `_id` 做分片键"和"用时间戳做分片键"会撞上同一个问题。区别只在于：默认 `_id` 是你无意中选的，时间戳是你主动选的。

## 五、与关系模型的正面对照 {#vs-relational}

| 维度 | 关系型（MySQL / PostgreSQL） | 文档型（MongoDB） |
|---|---|---|
| 数据形状 | 表 = 二维，列的类型固定 | 文档 = 树，字段可嵌套、可有可无 |
| 模式时机 | 写入时强制（DDL） | 读取时解释（应用负责） |
| 关联 | **JOIN 是一等公民**，规划器会重排优化 | 靠嵌入（少 JOIN）或 `$lookup`（受左集合规模约束） |
| 原子单位 | 事务（默认就有） | 单文档（天然）；跨文档要显式开事务 |
| 扩展方向 | 垂直为主，读靠副本，写靠分片中间件 | **原生分片**，写扩展是内建能力 |
| 一致性旋钮 | 隔离级别 + 提交语义（实例级/事务级） | 读关注 / 写关注 / 读偏好（**每操作可调**） |
| 查询语言 | SQL（声明式、可组合、生态成熟） | 查询文档 + 聚合管道（表达力够，但可组合性弱于 SQL） |
| 约束 | 外键、唯一、CHECK、触发器 | 无外键；唯一索引、`$jsonSchema`、应用层 |

**文档模型真正占优的四个场景**（其余场景要么打平、要么关系型更好）：

| 场景 | 为什么 | 典型例子 |
|---|---|---|
| 形状天然是树、且**同一层的字段随类别变化** | 建表要几十个可空列，或者要一张"属性表"（EAV） | 商品目录（每类目属性完全不同）、CMS 内容块 |
| 读模式是**"按 id 取一整个聚合"** | 一次查询拿到全部，没有 JOIN | 用户档案 + 偏好 + 地址、文档版本 |
| **写入形态多变的半结构化数据** | 新增字段不需要迁移 | 设备上报、事件采集、第三方回调原始报文 |
| 需要**原生水平写扩展** | 分片是内建能力，不必外挂中间件 | 多租户且数据量注定超过单机 |

对应地，**下面这些场景文档型是错误选择**：多表关联是常态的报表与即席查询、资金账务这类事务是核心的场景、需要严格跨表约束的场景。[NoSQL 选型与边界](/database/mongodb/nosql-selection#when-not)把否决理由单独列了一节。

## 六、面试高频（8 题）{#interview}

| # | 问题 | 一句话答案 | 详见 |
|---|---|---|---|
| 1 | 文档数据库不用设计 schema，对吗？ | 不对——schema 从"写入时校验"变成"读取时解释"，校验责任转到应用层，形状漂移是主要债务 | [§2](#schema-on-read) |
| 2 | 为什么 MongoDB 大部分场景不需要事务？ | 单文档更新（含内嵌子文档与数组元素）本身就是原子的，把一起改的数据放一个文档里就不需要事务 | [§1](#thread) |
| 3 | 什么时候该嵌入、什么时候该引用？ | 看访问模式与更新模式；一对少嵌入、一对多父引用、无界绝不进数组——**16MB 是唯一不可协商的约束** | [§3](#embed-or-reference) |
| 4 | 什么是最常见的建模翻车？ | 无界数组：把流水写进父文档，三个月后撞 16MB；其次是先范式化再到处 `$lookup` | [§4](#anti-patterns) |
| 5 | `$lookup` 能不能当 JOIN 用？ | 能跑，但对左集合每个文档做一次索引查找；**前面没有 `$match` 就是全表上的嵌套循环** | [§3](#embed-or-reference) |
| 6 | 文档库怎么保证数据质量？ | 三层：应用层约定（前提是单一写入方）+ `$jsonSchema` 校验器（闸门，不是约束系统）+ `schemaVersion` 惰性迁移 | [§2](#schema-on-read) |
| 7 | 为什么 `_id` 不要承载业务语义？ | 一是单调递增会造成分片热点，二是把内部标识变成了不可变的外部契约 | [§4](#anti-patterns) |
| 8 | 什么情况下文档模型比关系型更好？ | 形状天然是树且字段随类别变化、读模式是"按 id 取整个聚合"、写入形态多变、需要原生水平写扩展 | [§5](#vs-relational) |
