# 复制、一致性与事务

前面两篇都是单节点视角。这一篇的问题是：**数据在多个节点上的时候，"写成功"和"读到了什么"分别是什么意思？**

关系型里这两个问题的答案基本是固定的（提交就是提交、主库读就是最新）。文档库把它们做成了**每操作可调的旋钮**——这既是它的表达能力，也是它最容易被配错的开关。

## 一、副本集解决的三件事 {#replica-set}

| 目标 | 机制 | 代价 |
|---|---|---|
| **高可用** | 主节点故障后自动选出新主 | 选举期间**写不可用**（读通常仍可） |
| **数据冗余** | 每个节点一份完整数据 | 存储成本 ×N |
| **读扩展** | 从节点承接读流量 | **从节点可能落后 → 读到旧数据** |

**关键认识**：这三件事里，第二件是"顺带"的——副本集的设计目标是可用性，**不是写吞吐**。加副本不会提高写入能力（每一份写都要复制到多数派），只会提高读能力与容错能力。

需要写吞吐，那是[分片](/database/mongodb/sharding#topology)要解决的问题。**这两个机制的职责不要混**。

### 副本集的组成

| 角色 | 有数据 | 有投票权 | 说明 |
|---|---|---|---|
| Primary | ✓ | ✓ | **唯一接受写入**的节点；读也可以走它 |
| Secondary | ✓ | ✓ | 复制 oplog；可承接读（需读偏好配合） |
| Arbiter | ✗ | ✓ | 只为凑够投票多数派而存在，不持数据 |

### oplog：记录的"结果"而不是"操作"

oplog 是一个**固定大小的 capped 集合**（存在 `local` 库里），复制就是"从节点持续拉取并重放"。

它有一个和 binlog 形态不同的关键特性：**记录的是操作的结果状态，而不是操作本身。**

```
业务侧执行：  db.counters.updateOne({ _id: 'x' }, { $inc: { n: 1 } })
                    ↓
写进 oplog：  { op: 'u', o: { $set: { n: 42 } } }     ← 被改写成幂等形式
```

`$inc` 被转成 `$set`，是因为**重放必须幂等**：一个 `$inc` 被重放两次结果就错了，而 `$set` 重放多少次结果都一样。这条"幂等化"是 oplog 能在故障恢复、节点重同步时被反复应用的前提。

**oplog 的大小决定了"从节点最多能落后多久"**——超过这个窗口，从节点就再也追不上了，只能走**全量重新同步（initial sync）**。

```js
// 看 oplog 的容量余量：log length 与 used bytes 的差距
rs.printReplicationInfo()
db.getReplicationInfo()
```

| 现象 | 含义 |
|---|---|
| `timeDiff` 持续增长 | 从节点追不上（要么网络/磁盘不够，要么有长事务占着快照） |
| `timeDiff` 超过 oplog 覆盖窗口 | 该从节点迟早要全量重同步——**这是容量问题，不是配置问题** |

> **运维经验**：oplog 该开多大，取决于"能容忍一个从节点离队多久"。默认值通常在几十 GB 量级，但在写入量大的集合上可能只够覆盖几十分钟——**改大小需要重启，所以要在上线时一次性定对**。

## 二、选举与故障切换 {#election}

发生以下情况会触发选举：主节点失联（心跳超时）、优先级更高的节点重新加入等。

规则有三条：

1. **必须拿到多数派选票**：`N / 2 + 1`（N = 有投票权的节点数）。所以**3 节点副本集能容忍 1 个节点故障，2 节点不能容忍任何故障**——这也是为什么生产环境最小是 3 节点。
2. **优先级（priority）越高越优先**当选，同优先级时比较谁的数据更新（oplog 位置靠前）。
3. **仲裁者只投票，不参与数据复制**。它能帮 2 数据节点 + 1 仲裁者的架构凑够多数派，代价是**这个架构的数据冗余度只有 2 份**。

### PSA 架构的隐患

**Primary-Secondary-Arbiter 是成本敏感场景的常见选择**（省一台机器），但它有个必须知道的后果：**数据节点只有 2 个，其中任意一个不可用，`w: majority` 的写就永远无法满足**（多数派需要 2 票确认，而只剩 1 个数据节点）。同理，副本集降级为单数据节点时，`readConcern: 'majority'` 也无法满足。

官方为此提供了一个开关，可以关闭 majority 读关注。**但这个开关的代价是"因果一致性与跨分片事务都会受影响"**——所以它属于"知道有、但不到万不得已不用"的选项。

### 回滚（rollback）

故障切换时可能出现这种情况：旧主上有一批写**还没复制到多数派**就挂了，新主上任后没有这些数据。当旧主恢复加入时，它必须**把这批写撤销掉**——这就是回滚，被撤销的数据会落到 `rollback/` 目录下。

**回滚是理解读关注的一把钥匙**：`readConcern: 'local'` 的定义里那句"返回的数据**可能被回滚**"，说的就是这件事。**读到过、后来消失了**，在 `local` 语义下是合法的。

> 所以要建立这个判断：**如果一个读的结果会被下游用来做不可撤销的动作**（扣款、发货、发消息），就不该用 `local`。

## 三、写关注：写到什么程度才算写成功 {#write-concern}

| 取值 | 语义 | 数据会丢吗 | 适用 |
|---|---|---|---|
| `w: 0` | 不等待任何确认（fire-and-forget） | 会，且客户端不知道 | 可丢失的埋点/日志 |
| `w: 1` | 主节点内存确认即返回 | **主节点挂了可能丢** | 允许少量丢失的次要数据 |
| **`w: 'majority'`** | 多数派节点确认后才返回 | 单节点故障不丢 | **默认，也是绝大多数场景该用的** |
| `j: true` | **额外要求写入磁盘日志（journal）**后才确认 | 抵御"节点掉电"而不只是"节点下线" | 与 `w` 组合使用 |

三条容易搞错的地方：

**① 从 5.0 起，默认写关注就是 `majority`。** 不需要手动加 `{ writeConcern: { w: 'majority' } }`——**但你要知道它已经是了**。面试里问"你的 MongoDB 怎么保证不丢数据"，答"默认就是 majority"比"我配了 majority"更准确。

**② `w` 与 `j` 是两件事**：`w` 管"多少个节点确认"，`j` 管"有没有落盘"。`w: 'majority'` 且 `j: false` 时，多数派是在**内存**里确认的——节点进程崩溃（crash）能扛住，**整个机器掉电**则可能丢。要抗掉电必须 `j: true`。

**③ 8.0 里 `majority` 写关注变快了，原因值得记住**：它现在**在 oplog 写入后即确认，而不再等待从节点完成 apply**。

```
  8.0 之前：主节点写 → 复制到多数派 → 从节点 apply 完成 → 才确认    ← 慢在"等 apply"
  8.0 起：  主节点写 → 复制到多数派（oplog 落地）        → 就确认    ← 快在"不等 apply"
```

这个改动的隐含意义是：**多数派确认保证的是"数据已进入多数派的日志"，而不是"已在多数派可查"**——所以从节点上的可见性仍然可能滞后，`readConcern` 依然要照旧考虑。

**另外 8.0 让从节点可以并行 apply oplog**，直接改善了从节点落后（`timeDiff`）的问题。

## 四、读关注与读偏好：两个正交的旋钮 {#read-concern}

这是整套里最容易混的地方——**它们回答的是两个完全不同的问题**：

| 旋钮 | 回答的问题 | 取值 |
|---|---|---|
| **读偏好**（readPreference） | **从哪个节点读** | primary / primaryPreferred / secondary / secondaryPreferred / nearest |
| **读关注**（readConcern） | **读到的是什么状态的数据** | local / available / majority / linearizable / snapshot |

**"读偏好选 secondary"和"读关注选 majority"是可以同时用的**，而且这一组合恰恰是"从节点读，但仍要求数据不回滚"的正确写法。

### 读偏好五档

| 取值 | 行为 | 用于 |
|---|---|---|
| `primary` | 只从主节点读 | 必须读最新的场景（读己之写、扣款校验） |
| `primaryPreferred` | 优先主，主不可用时读从 | 高可用优先、能容忍切换期读到略旧数据 |
| `secondary` | 只从从节点读 | 报表、分析——但主不可用时读也失败 |
| `secondaryPreferred` | 优先从，从都不可用时读主 | **分析类查询的推荐值** |
| `nearest` | 按网络延迟选最近的（含主） | 跨地域部署、延迟敏感且能容忍旧数据 |

### 读关注五档

| 取值 | 返回什么 | 会被回滚吗 | 限制 |
|---|---|---|---|
| `local` | 该节点上的最新数据 | **可能** | **主节点读的默认值** |
| `available` | 同上，但延迟最低 | **可能** | **不能用于因果一致会话与事务**；**分片集合上可能返回孤儿文档** |
| `majority` | 多数派已确认的数据 | 不会 | 要求 WiredTiger |
| `linearizable` | 反映读开始前所有多数派确认的写 | 不会 | **只能读主节点**；**只对"唯一定位单个文档"的查询有效**；建议配 `maxTimeMS` |
| `snapshot` | 跨分片某个时间点的多数派数据快照 | 不会 | **基本只在多文档事务里用** |

三处必须记住的例外：

- **`available` 在分片集合上会返回孤儿文档**（迁移遗留的、已经不归属该分片的数据）。所以它是"延迟最低但语义最弱"的档——**官方建议分片场景改用 `local`**。
- **`linearizable` 只对唯一标识单文档的读有效**。一份"查出来是几条"的查询用 `linearizable` 是**没有意义**的——这条限制非常反直觉，但它是定义的一部分。
- **`local` 是主节点的默认读关注**，而**从节点的默认值是 `available`**（非因果一致会话时）。所以"同一个查询，走主和走从，语义默认值就不一样"。

## 五、因果一致性：读己之写的正解 {#causal}

"写完立刻读却读不到"在读写分离架构里是经典问题。MySQL 侧的常见解法是"关键路径强制走主库"；MongoDB 侧有一个更细的机制：**因果一致性会话（causally consistent session）**。

机制不复杂：会话记录已完成的写对应的 `operationTime`，**后续的读带上 `afterClusterTime`**，从节点会等到自己复制的进度超过那个时间点才返回结果。

```
session1 = client.startSession({ causalConsistency: true })

session1.withTransaction(...)  // 或者普通写
  db.orders.insertOne({...}, { session: session1 })

// 同会话内的后续读：即使读偏好是 secondary，也不会读到旧数据
  db.orders.findOne({ _id: newId }, { session: session1 })
```

**但它的成立有前提**，这个前提经常被漏掉：

> 因果一致性只在**读操作使用 `majority` 读关注、写操作使用 `majority` 写关注**时才成立。

也就是说，如果为了压延迟把读关注降成 `local`，**因果一致性的保证就没了**——会话还在，语义已经不同了。

| | MySQL 读写分离 | MongoDB |
|---|---|---|
| 问题的产物 | 主从延迟导致读旧数据 | 同左 |
| 粗暴解法 | 关键查询强制走主库 | 读偏好设 `primary` |
| 细粒度解法 | 无原生机制 | **因果一致性会话**（`afterClusterTime`） |
| 前提 | —— | 读写都必须是 `majority` |

## 六、多文档事务：四条硬边界 {#transactions}

事务在 4.0 支持副本集、4.2 扩展到分片集群，提供**快照隔离**。它和关系型事务的用法几乎一样，但有四条边界必须先记住——**越界不会报错，只会慢或者莫名失败**：

| # | 边界 | 具体 | 为什么 |
|---|---|---|---|
| 1 | **默认 60 秒自动中止** | `transactionLifetimeLimitSeconds`；`commitTransaction` 上可传 `maxTimeMS` | 防止长事务长期占资源 |
| 2 | **单事务建议不超过 1000 个文档修改** | 读没有硬限制，**写有"工程上限"** | 超过就分批 |
| 3 | **长事务会压 WiredTiger 缓存** | 事务持有一个固定快照，**此后所有新写都无法被刷出缓存** | 见下方解释 |
| 4 | **跨分片事务是二阶段提交** | 延迟随参与分片数上升；**任何涉及分片含仲裁节点时，跨分片事务会直接中止** | 协调成本 |

### 为什么长事务压的是"缓存"而不是"锁"

这条机制值得单独讲清楚，因为它解释了"为什么文档库的事务比关系型更怕长"：

```
  事务 T 开始 → 拿到一个快照 S
        │
        ├──▶ 事务运行期间，T 必须能看到"以 S 为基准的一致视图"
        │
        └──▶ 所以从 S 之后产生的所有新写版本，都不能被清理
                │
                └──▶ WiredTiger 缓存必须一直持有它们
                        │
                        └──▶ 事务越久 → 不能刷的版本越多 → 缓存被顶满 → 全局慢下来
```

**这就是"单个长事务拖慢整个实例"的完整链条**——它不是在锁上，而是在缓存的可用空间上。修法只有两个：**把事务拆小**，或者**确保事务内的查询都走索引**（跑得快，占用窗口就短）。

### 一个反直觉的收益：事务反而能降低写延迟

事务不只有代价。当一次业务操作要写多份文档、且用的是 `w: majority` 时：

```
  不用事务： 10 次独立 update  → 每次都要等一轮"复制到多数派"  → 10 轮往返
  用事务：   10 次 update 放进一个事务 → 提交时一起复制      → 1 轮往返
```

**提交延迟降到约 1/10。** 所以"事务一定更慢"是错的——**批量语义的事务在 `majority` 写关注下往往更快**，慢的是它的边界成本（快照、缓存、跨分片协调）。

### 必须写的重试逻辑

事务会因为两类原因失败，而这两类的处理方式完全不同：

| 错误标签 | 含义 | 正确做法 |
|---|---|---|
| `TransientTransactionError` | 事务内部的**操作**失败（写冲突、网络抖动、主节点切换） | **整个事务重试** |
| `UnknownTransactionCommitResult` | 提交的结果**不确定**（提交阶段网络中断） | **只重试提交**，不要重跑整个事务 |

驱动对 `commitTransaction` 有自动重试，但**整个事务的重试必须由应用写**。**漏掉这段重试逻辑的事务代码，在生产环境里一定会遇到失败**——而且是没有日志的那种失败。

### 最该记住的一条判据

> **如果一段业务代码"经常需要多文档事务"，说明[文档模型](/database/mongodb/document-model#thread)没建对。**

官方口径是单文档原子性覆盖 80~90% 的事务需求。真实需要事务的是"值在不同主体之间转移"的场景（转账、库存扣减、账单与明细一起落库）——**这类场景本来就该是事务**。而如果发现"几乎每个写操作都要开事务"，那通常意味着把本该嵌入的数据拆成了多个集合，**该改模型，不是该加事务**。

## 七、常见错配 {#matrix}

把三个旋钮和场景对齐，下面是四组最容易配错的组合：

| 场景 | 读偏好 | 读关注 | 写关注 | 常见错法 |
|---|---|---|---|---|
| 用户刚写完就要看到（下单后跳订单详情） | `primary` | `local` 或 `majority` | `majority` | ✗ 读偏好给了 `secondaryPreferred`，跳页后看不到刚下的单 |
| 报表 / 分析查询 | `secondaryPreferred` | `local` | —— | ✗ 用 `secondary` 而不是 `secondaryPreferred`，主节点故障时报表也一起不可用 |
| 资金流水（不可撤销的读） | `primary` | `majority` 或 `linearizable` | `majority` + `j: true` | ✗ 用 `local`，遇到回滚就读到了不存在的数据 |
| 埋点 / 可丢失的日志 | `nearest` | `local` | `w: 0` | ✗ 用了 `majority`，把写入吞吐白白压掉一半 |

## 八、与关系型的对照 {#vs-rdbms}

| 维度 | MySQL / PostgreSQL | MongoDB |
|---|---|---|
| 复制日志 | binlog（可配 ROW / STATEMENT / MIXED） | oplog（**幂等，记录结果状态**） |
| 提交语义 | 由 `sync_binlog` / `synchronous_commit` 等参数决定 | **5.0 起默认 `w: majority`**，每操作可覆盖 |
| 读的粒度 | 主库强一致 / 从库可能延迟，二选一 | 读偏好 + 读关注**两个正交旋钮** |
| 读己之写 | 强制走主库 | **因果一致性会话**（`afterClusterTime`） |
| 故障切换 | MHA / MGR / 编排工具 | **内建选举**（多数派 + 优先级） |
| 事务默认性 | 默认就有，是常态 | **opt-in**，且被建议尽量不用 |
| 事务的独特代价 | 锁、undo 膨胀、长事务拖 MVCC | **WiredTiger 缓存压力**（快照钉住不可刷版本） |

**一句话总结这一篇**：关系型把一致性做成了"实例级的配置"，文档库把它做成了"每操作的旋钮"——**表达能力强了，配错的机会也多了**。所以用 MongoDB 的项目，评审时应该专门看一眼：**每个读路径的读偏好与读关注，是不是都有人能说出为什么。**

## 九、面试高频（12 题）{#interview}

| # | 问题 | 一句话答案 | 详见 |
|---|---|---|---|
| 1 | 副本集解决什么、不解决什么？ | 解决高可用、数据冗余、读扩展；**不解决写吞吐**——加副本不增写入，那是分片的事 | [§1](#replica-set) |
| 2 | oplog 和 binlog 有什么本质不同？ | oplog 记录的是**结果状态**（`$inc` 被改写成 `$set`），因此重放幂等；这也是它能被反复用于重同步的前提 | [§1](#replica-set) |
| 3 | oplog 太小会怎样？ | 从节点落后超过 oplog 覆盖窗口就再也追不上，只能全量重新同步——**这是容量问题不是配置问题** | [§1](#replica-set) |
| 4 | 选举需要几票？PSA 架构有什么隐患？ | 多数派 `N/2+1`；PSA 只有 2 个数据节点，**任一个不可用 `w: majority` 就永远无法满足** | [§2](#election) |
| 5 | 什么叫回滚？和读关注有什么关系？ | 旧主上未复制到多数派的写被撤销；`readConcern: local` 允许返回**可能被回滚**的数据 | [§2](#election) |
| 6 | `w: majority` 和 `j: true` 是一回事吗？ | 不是：`w` 管几个节点确认，`j` 管是否落盘；只有 `w: majority` 且 `j: false` 时，整机掉电仍可能丢 | [§3](#write-concern) |
| 7 | 8.0 的 `majority` 写为什么变快了？ | 现在**在 oplog 写入后即确认，不再等从节点 apply**——所以"确认"的含义是"进了多数派的日志"，不是"在多数派可查" | [§3](#write-concern) |
| 8 | 读偏好和读关注的区别？ | 前者决定**从哪个节点读**，后者决定**读到的是什么状态**；两者正交，可同时用 | [§4](#read-concern) |
| 9 | 因果一致性在什么条件下才成立？ | 读写**都必须是 `majority`**；为了压延迟把读关注降成 `local`，保证就没了 | [§5](#causal) |
| 10 | 长事务为什么拖慢整个实例？ | 事务持快照 → 之后的写版本都不能被刷出 WiredTiger 缓存 → 缓存被顶满；**问题在缓存不在锁** | [§6](#transactions) |
| 11 | 多文档事务一定比不开事务慢吗？ | 不一定——`majority` 写关注下，N 次写包进一个事务只需一轮复制往返，**提交延迟反而降到约 1/N** | [§6](#transactions) |
| 12 | 什么时候说明文档模型建错了？ | 当"几乎每个写都要开事务"时——正确做法是改模型（把一起更新的数据嵌进同一文档），不是加事务 | [§6](#transactions) |
