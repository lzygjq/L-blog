# NoSQL 选型与边界

前面四篇讲的是"它怎么工作"。这一篇讲"什么时候该用它"——包括**什么时候千万别用**。

这一节的价值不在给出答案，而在给出**判断顺序**：先看数据形状，再看访问模式，最后才看产品。顺序反了，就会变成"先选了一个数据库，再想办法把数据塞进去"。

## 一、先分类，再选型 {#families}

"NoSQL"是一个**否定式标签**（Not Only SQL），它把差异极大的几类系统装进了同一个词里。所以第一步不是挑产品，而是**判断自己的数据属于哪一类形状**：

| 家族 | 数据形状 | 核心访问模式 | 为了扩展性放弃了什么 | 代表 |
|---|---|---|---|---|
| **文档** | JSON/BSON 树，字段可变 | 按 id 取整个聚合、按字段过滤 | 跨文档 JOIN、跨集合约束 | MongoDB、Couchbase |
| **键值** | 黑盒 value（也可有结构） | 按 key 读写，超低延迟 | 复杂查询（基本只能按 key） | Redis、Memcached、etcd |
| **宽列** | 行键 + 稀疏列族 | 按行键范围扫、海量写入 | 关系表达力（无 JOIN、事务弱） | Cassandra、HBase |
| **图** | 点 + 边 | **多跳遍历**（"朋友的朋友"） | 大规模全表统计 | Neo4j、JanusGraph |

另外还有两类**按用途划分**（不是按形状），它们各有自己的板块：

| 类别 | 形状 | 什么时候用它 | 站内 |
|---|---|---|---|
| **检索** | 倒排索引 | 全文检索、相关性排序、日志检索 | [搜索与检索](/search/#interview) |
| **列式分析** | 列存 + 向量化执行 | 聚合分析、报表、大宽表扫描 | [Doris / ClickHouse](/bigdata/#faq) |

> 如果只需要"SQL 与 NoSQL 该按哪些维度做选择"这一层的判断，[Redis 篇的第一节](/database/redis/basics#nosql-vs-sql)从键值存储的角度给过一个更简的版本（含一张 SQL / NoSQL 的维度对照表）。**本节的增量是"把 NoSQL 内部再分四类"**——因为把它们混在一起谈，选型必然含糊。

**一条经验**：真实系统里"选哪个数据库"的正确答案通常是**"几个存储各管一段"**。所以选型题的正确答法是**分工**，不是排名。

## 二、MongoDB 真正的优势区 {#strengths}

四条，全部源自[文档模型的原子单位](/database/mongodb/document-model#thread)：

| # | 优势场景 | 为什么关系型会别扭 |
|---|---|---|
| 1 | **形状天然是树、且同层字段随类别变化** | 关系型要么几十个可空列，要么退回 EAV 属性表 |
| 2 | **读模式是"按 id 取一整个聚合"** | 关系型要 JOIN 若干张表再拼装 |
| 3 | **写入形态多变的半结构化数据** | 新增字段就要跑迁移（有成本、有风险） |
| 4 | **需要原生水平写扩展** | 关系型要外挂分片中间件，并接受它的限制 |

典型实例：商品目录（每个类目属性完全不同）、CMS 内容块、用户档案 + 偏好 + 地址、设备上报、第三方回调的原始报文。

**还有一条权重在上升的能力：把检索与向量检索收进同一个系统**（Atlas Search / Vector Search）。对"既要业务数据又要全文检索或相似度检索"的中小规模场景，它省掉了一整条索引同步链路。**边界是规模与成本**——到了某个数据量，专用检索引擎在相关性调优、聚合能力、查询 DSL 表达力上的优势会重新显现。

**关于 8.0 的性能数字，要有正确的使用方式**（官方口径）：吞吐最多 +32%、批量写 +56%、复制期并发写 +20%、时序数据操作 +200% 以上、分片数据分布约快 50 倍。

> 这些数字的**对照组是它的上一个版本，不是其他产品**。它们能说明"升级 8.0 有收益"，不能说明"它比 X 快"——**要写进方案的数字，必须自己在自己的数据和查询形状上压测**。

## 三、什么时候不该选它 {#when-not}

这一节比上一节更重要。**六条否决理由，命中任何一条都该停下来重新评估：**

| # | 否决理由 | 为什么 | 该选什么 |
|---|---|---|---|
| 1 | **多表关联是常态** | 报表、即席查询、数十张表互相 JOIN——文档库只能用 [`$lookup`](/database/mongodb/document-model#embed-or-reference) 模拟，而它只能出现在管道后段 | 关系型；分析量大再加列式引擎 |
| 2 | **事务是核心语义** | 资金、账务、库存这类"值在主体之间转移"，且模型无法通过嵌入收敛 | 关系型（事务是一等公民） |
| 3 | **需要跨集合的强约束** | 外键、跨集合唯一、CHECK——文档库[只有分片内可校验的唯一索引](/database/mongodb/sharding#shard-key) | 关系型 |
| 4 | **需要复杂 SQL 表达力** | 窗口函数、CTE、递归查询、复杂聚合 | 关系型 |
| 5 | **选它的理由是"不想设计 schema"** | **这是最贵的动机**——见下方展开 | 关系型 + JSONB |
| 6 | **需要私有化部署且团队有开源许可红线** | 见[下一节](#license) | PostgreSQL，或确认协议兼容层的缺口 |

第 5 条值得单独展开，因为它是**唯一一条"技术上都能跑、但动机从一开始就错了"的否决理由**：

```
   动机："用 MongoDB 就不用设计 schema 了"
        │
        ├── 收益：项目前两周确实快
        │
        └── 代价：半年后你会发现自己在应用层
                 手写 JOIN、手写引用完整性检查、手写多文档事务
                    │
                    └──▶ 比当初设计一套 schema 更慢、更容易出错、
                         而且没有数据库帮你拦住任何脏数据
```

正确的问题不是"哪种数据库能让我少设计"，而是**"我的数据形状真的适合文档模型吗"**。如果答案是"其实挺规整的，只是有几个字段不定"——**关系型 + JSONB 列反而更省事**：既能存能索引半结构化字段，又保留了事务、约束与 SQL。

## 四、SSPL：许可的真实边界 {#license}

这是选型里最容易被跳过、又最容易在合规评审上卡住的一节。

### 事实链

| 时间 | 事件 |
|---|---|
| ≤ 2018-10 | MongoDB 使用 **AGPL**（OSI 认可的许可） |
| **2018-10-16** | 转为 **SSPL v1**，**至今（2026-09）未变** |
| 直接后果 | **OSI 未认可 SSPL** → Community 版属于"源码可见（source-available）"，不是严格意义的开源 |
| 连锁反应 | Debian / Fedora / RHEL 因此把 MongoDB 移出官方仓库 |

### 触发条件的准确边界

这是最常被误解的一点——**"用 MongoDB 会不会被传染"的答案取决于一个很具体的动作**：

```
   SSPL Section 13 的触发条件：「把 MongoDB 的功能作为服务提供给第三方」
        │
        ├── ✅ 触发：做一个托管 MongoDB 的云服务卖给客户
        │            （要求公开整个服务栈：管理、监控、备份、存储、托管软件）
        │
        ├── ❌ 不触发：自己的应用把数据存在 MongoDB 里
        │            （卖的是业务服务，不是数据库服务）
        │
        ├── ❌ 不触发：公司内部使用（员工不构成"第三方"）
        │
        └── ❌ 不触发：引用官方驱动（**驱动是 Apache 2.0**，无 copyleft 义务）
```

**所以准确结论是："对绝大多数应用不构成法律风险，但构成合规流程风险"**——卡点出现在有"许可白名单"的组织的评审环节，而不是法庭。

### 四条出路

| 出路 | 做法 | 代价 |
|---|---|---|
| ① 继续用 Community | 守在 Section 13 不触发的边界内 | 可能过不了合规评审；高可用与运维要自建 |
| ② Enterprise Advanced | 买商业许可，**不受 SSPL 约束** | 费用 |
| ③ Atlas 托管 | 用官方云服务 | 数据不在自己机房；成本随规模上升 |
| ④ 换引擎 | 换数据库，或换**协议兼容层** | 迁移成本；兼容层有能力缺口 |

第 ④ 条的形态值得知道：有一类**协议兼容层**——对外说 MongoDB 协议（应用与驱动基本不改），底层跑在关系型数据库上。**它的典型缺口正是多文档事务**，所以它只适合"用得很浅"的迁移场景，不适合依赖[事务](/database/mongodb/consistency-and-transactions#transactions)的系统。

### 同一波许可变更的对照

MongoDB 不是孤例。把同期几次放在一起，规律比个案更有用：

| 项目 | 变更 | 现状（2026-09） |
|---|---|---|
| **MongoDB** | 2018-10 从 AGPL 转 **SSPL v1** | **仍是 SSPL**，未被 OSI 认可 |
| **Elasticsearch** | 2021-01 从 Apache-2.0 转 SSPL + Elastic License | 后**加回 AGPLv3**，现为三许可并存（AWS 的 OpenSearch 分支已站稳） |
| **Redis** | 2024-03 从 BSD 转 SSPL / RSAL | **Redis 8（2025-05）回归 AGPLv3**；基金会侧的 Valkey 分支持续发展 |
| Terraform / Vault | 2023 从 MPL-2.0 转 BSL 1.1 | **未回退**（OpenTofu / OpenBao 分支） |

**起因是同一个**：云厂商把这些软件做成托管服务、却不回馈社区。**但应对与结局各不相同**——有收紧不回的、有部分回退的、有彻底回退的。

> **工程结论不是"别用这些软件"，而是"选型清单里要有一列：许可类型与它的实际约束"**。这一列在纯内部项目上可以省，在**商用交付与私有化部署**场景里不能省。

## 五、与站内其他存储的分工 {#division}

把"存储 · 消息 · 检索"这个侧边栏里的成员摆在一起，边界一目了然：

| 存储 | 数据形状 | 它最擅长 | **别用它做** | 站内 |
|---|---|---|---|---|
| **MySQL** | 二维表 + 约束 | 事务、JOIN、强一致、生态成熟 | 全文检索；海量写扩展（要外挂分片） | [MySQL](/database/mysql/#interview) |
| **PostgreSQL** | 二维表 + JSONB + 扩展 | 复杂 SQL、扩展生态、JSONB 兼顾半结构化 | 超大规模写扩展（要 Citus 一类方案） | [PostgreSQL](/database/postgresql/#interview) |
| **MongoDB** | 文档树 | 半结构化、迭代快、"按 id 取聚合"、原生分片 | 多表 JOIN 常态、跨集合强约束、复杂 SQL | 本板块 |
| **Redis** | 键值 + 结构 | 缓存、分布式锁、轻量 MQ、计数与排行榜 | 当权威主存储（持久化与容量都不是为它设计的） | [Redis](/database/redis/#interview) |
| **Elasticsearch** | 倒排索引 | 全文检索、相关性排序、日志检索 | 当权威主存储、当强一致账本 | [搜索与检索](/search/#interview) |
| **Doris / ClickHouse** | 列存 | 聚合分析、大宽表扫描、报表 | 高频单行更新、高并发点查 | [数据仓库](/bigdata/#faq) |
| **消息队列** | 追加日志 | 解耦、削峰、异步、顺序消费 | 长期存储与查询 | [消息队列](/middleware/#interview) |

> **这张表的正确用法**：架构评审里"我们用什么数据库"这个问题，应该被改写为**"这份数据由谁负责、为什么"**。同一个系统里出现多个存储是正常的；**同一份数据有两个权威源，才是问题**。

## 六、一条决策路径 {#decision-flow}

```
   起点：这批数据，谁是它的权威源？
        │
        ├─ 只是"分析用"的副本？ ──▶ 列式引擎（Doris / ClickHouse）
        │         └─ 别让分析查询打业务库 —— 见 数据仓库板块
        │
        ├─ 只是"检索用"的副本？ ──▶ 检索引擎（ES）；权威源仍在业务库
        │
        ├─ 只是"缓存 / 锁 / 计数器"？ ──▶ Redis；权威数据必须在别处
        │
        └─ 是权威业务数据 ──▶ 继续：
                 │
                 ├─ 形状规整、实体关系多、事务是核心？
                 │        └──▶ 关系型（MySQL / PG）
                 │                 └─ 只是有几个字段不定？ → 用 JSONB 列，不必换引擎
                 │
                 ├─ 形状是树、字段随类别变、读主要是"取整个聚合"？
                 │        └──▶ 文档型（MongoDB）
                 │                 └─ 先过一遍【[六条否决理由](#when-not)】
                 │
                 ├─ 需要多跳关系遍历（社交关系、血缘、风控路径）？
                 │        └──▶ 图数据库
                 │
                 └─ 单机装不下、写是瓶颈？
                          ├─ 查询天然带租户/用户维度 → 原生分片或分库分表
                          └─ 查询不带明确维度 → **先别分片**：
                                   先确认瓶颈真的是单机上限，
                                   而不是缺索引或 N+1 查询
```

**最后那条分叉值得单独记一句**：绝大多数"我们该分片了"的判断，真实原因是缺索引或 N+1 查询。**分片是单向的复杂度增加**——在它之前，先把索引和慢查询过一遍。这个判断顺序在[分库分表](/database/sharding/)与[分片集群](/database/mongodb/sharding)两边都成立。

## 七、面试高频（10 题）{#interview}

| # | 问题 | 一句话答案 | 详见 |
|---|---|---|---|
| 1 | NoSQL 有哪几类？怎么选？ | 文档 / 键值 / 宽列 / 图四类，按**数据形状 + 访问模式**选；检索与列式分析是另两类"按用途划分"的系统 | [§1](#families) |
| 2 | MongoDB 真正的优势场景？ | 形状是树且字段随类别变、读是"按 id 取聚合"、写入形态多变、需要原生水平写扩展 | [§2](#strengths) |
| 3 | 什么时候不该选 MongoDB？ | 六条：多表 JOIN 常态 / 事务是核心 / 需跨集合强约束 / 需复杂 SQL / 动机是"不想设计 schema" / 许可红线 | [§3](#when-not) |
| 4 | 用 MongoDB 最贵的错误是什么？ | 为了"不设计 schema"而选它，然后半年后在应用层手写 JOIN、引用检查和事务 | [§3](#when-not) |
| 5 | 8.0 提升 32% 吞吐，能说明它比别的库快吗？ | 不能——那些数字的对照组是它的上一个版本，**要写进方案的数字必须自己压测** | [§2](#strengths) |
| 6 | PostgreSQL 的 JSONB 会取代文档库吗？ | 会让"数据其实规整、只是几个字段不定"的场景不再需要文档库；但替代不了"聚合是一等公民 + 原生分片" | [§3](#when-not) |
| 7 | MongoDB 是开源软件吗？ | 严格说不是——2018-10 起是 SSPL，**OSI 未认可**，属"源码可见" | [§4](#license) |
| 8 | 用 MongoDB 会不会被 SSPL 传染？ | 自己应用存数据、公司内部使用、引用 Apache 2.0 的驱动，**都不触发 Section 13**；触发的是"把数据库做成服务卖给第三方" | [§4](#license) |
| 9 | 有开源许可红线的组织怎么选？ | Community 守边界 / 买 Enterprise Advanced / 用 Atlas；或换引擎（含协议兼容层，但要确认它不支持多文档事务这个缺口） | [§4](#license) |
| 10 | 一个系统里用几个存储合适？ | 看分工：**权威源只能有一个**，分析副本、检索副本、缓存各归其位——多个存储不是问题，"一份数据两个权威源"才是 | [§5](#division) |
