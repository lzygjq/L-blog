# 认证方式全景与选择

> **口径说明**：这一篇讲的是**机制与取舍**，不是某个框架的教程。框架用法（Spring Security / Shiro 的过滤器链与配置）见 [授权模型与权限落地](/security/authorization#frameworks)；项目里的落地形态见 [发布、安全与运维](/projects/property-saas/release-and-ops/)。

## 一、先划清一条线：认证 ≠ 授权 {#problem}

这两个词在日常对话里经常被混用，但在协议层它们决定了**两个不同的状态码**：

| 概念 | 回答的问题 | 失败时 | 典型错误 |
|---|---|---|---|
| **认证**（Authentication） | 你是谁 | **401 Unauthorized** | 未登录取不到身份 |
| **授权**（Authorization） | 你能做什么 | **403 Forbidden** | 身份明确，但无权 |

混淆的代价不是学术性的：**把 401 和 403 混用会让前端无法区分"该去登录页"还是"该提示无权限"**——前者需要跳登录、清本地令牌，后者什么都不用做。这也是很多系统在令牌过期时体验诡异的根因。

还有一条容易忽视的边界：**认证解决"身份可信"，不解决"身份被滥用"**。账号被盗后攻击者就是合法身份，认证层拦不住——那要靠风控与行为分析，是另一个问题域。

## 二、凭据的四种形态：多因素的门槛是"跨形态" {#credentials}

| 形态 | 例子 | 强度 | 被攻破的方式 |
|---|---|---|---|
| 你知道什么 | 密码、PIN、密保问题 | 低 | 撞库、钓鱼、泄露库比对 |
| 你拥有什么 | 手机、U 盾、TOTP、证书 | 中高 | 设备丢失、SIM 劫持、中间人 |
| 你是什么 | 指纹、人脸、声纹 | 中 | 伪造（照片/录音/3D 打印）、不可重置（**泄露即永久**） |
| 你在什么环境 | IP 白名单、设备指纹、地理位置 | 辅助 | 代理、设备伪造 |

**多因素认证（MFA）的门槛是"跨形态组合"，同一形态叠加两个不算**：

| 组合 | 算 MFA 吗 | 为什么 |
|---|---|---|
| 密码 + 密保问题 | ❌ | 都是"你知道什么"——泄露库往往两个都在里面 |
| 密码 + 短信验证码 | ✅（弱） | 跨形态，但短信可被 SIM 劫持 / 补卡攻击 |
| 密码 + TOTP / 硬件密钥 | ✅（强） | TOTP 密钥不出设备；硬件密钥还能防钓鱼域名 |
| 人脸 + 指纹 | ✅（形式上是） | 都是"你是什么"，且**不可重置**——泄露的后果比密码严重得多 |

最后一条值得单独说：生物特征的**不可重置性**决定了它不该作为唯一凭据。密码泄露可以改，指纹泄露不能换手指。所以工程上更稳的用法是把生物特征作为**本地解锁**（把密钥解出来），而不是把特征本身传到服务端做比对。

## 三、会话 vs 令牌：一个架构分界 {#session-vs-token}

这是认证设计里最实质的一次取舍。**它不是"新技术淘汰旧技术"，而是状态放在哪一边。**

```
服务端会话（Session）                无状态令牌（JWT）
客户端只持一个 ID ──┐              客户端持有全部状态 ──┐
                    │                                  │
服务端存真实状态 ◀──┘              服务端不存 ◀─────────┘
（Redis / 内存）                   （每次请求自校验签名）
```

| 维度 | 服务端会话 | 无状态令牌 | 说明 |
|---|---|---|---|
| 横向扩展 | 需共享存储（Redis）或粘性会话 | 天然无状态 | 令牌方案下网关可独立完成校验 |
| 跨域 / 多端 | 受 Cookie 域限制 | 头部携带，天然跨域 | 小程序、原生 App 只有令牌方案可选 |
| **主动失效** | ✅ 删掉即失效 | ❌ **签出去就收不回** | 令牌方案的根本代价 |
| 单次请求开销 | 查一次存储 | 验签（HMAC 微秒级 / RSA 数十微秒） | 高频接口上 RSA 验签也会成为可观开销 |
| 令牌体积 | 几十字节 | 数百字节 ~ 数 KB | 每请求都带，过大会挤占带宽与头部限额 |
| 泄露影响面 | 需要同时拿到 ID | **拿到即用，且无法撤销** | 决定了令牌寿命必须短 |

> **结论性的取舍**：多端（小程序 / App / 第三方）接入的现实下，令牌方案几乎是唯一选择；但**必须用"短命访问令牌 + 可撤销刷新令牌"把"无法主动失效"这个代价补回来**——把有状态的部分收敛到一个点上管理。

## 四、JWT 的完整剖析 {#jwt}

### 4.1 三段结构，以及一个必须记住的结论 {#jwt-structure}

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxMDAxIiwiZXhwIjoxNzY4NTQwMDAwfQ . dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
└──── header ────┘   └──────────── payload ────────────┘   └──────────── signature ────────────┘
     算法与类型            声明（claims）                        前两段的签名
```

**「Base64URL 编码」不是「加密」**——这是 JWT 使用中最普遍、后果最严重的一个误解：

| 误解 | 事实 |
|---|---|
| payload 是密文，别人看不到 | **任何人把中段 Base64 解码就能看到全部内容**，不需要任何密钥 |
| 所以可以把用户信息放进去 | 可以放**标识**（user_id、tenant_id），**绝不能放敏感数据**（手机号、身份证、密钥） |

签名保证的是**完整性**（内容没被篡改），不是**机密性**（内容不被看到）。这两件事经常被混为一谈。

### 4.2 签名算法的选择：对称 vs 非对称 {#jwt-alg}

| 算法 | 密钥 | 适用场景 | 代价 |
|---|---|---|---|
| HS256 | 单一共享密钥 | 单体应用、签发方与校验方是同一服务 | 密钥必须分发给**所有**校验方，任一处泄露即可伪造令牌 |
| RS256 / ES256 | 私钥签发、公钥验签 | 多服务校验（网关 + 各微服务） | 验签开销高一个量级；ES256 签名字更短、性能更好 |

**判据**：校验方多于一个时，用非对称——把公钥广发出去没有风险，而共享密钥做不到这一点。

### 4.3 必须校验的字段（漏一个就是一个漏洞） {#jwt-claims}

| 字段 | 不校验会怎样 |
|---|---|
| `alg` | **必须白名单校验，且显式拒绝 `none`** —— 算法混淆攻击（把 RS256 改成 HS256、用公钥当 HMAC 密钥）就发生在这里 |
| `exp` | 过期令牌永久有效 |
| `nbf` / `iat` | 提前签发的令牌可被立即使用 |
| `iss` | 别家签发的令牌在本站可用 |
| `aud` | 面向 A 系统的令牌可在 B 系统使用 |
| `jti` | 无法做单令牌撤销 |

这些都是**库的默认行为之外**的一层责任：多数库默认校验 `exp`，但 `aud` / `iss` 常常需要显式开启。

### 4.4 令牌放哪里：一个真实的权衡，没有免费解 {#jwt-storage}

| 存储位置 | 可被 XSS 读取 | 自动随请求发送（可被 CSRF） | 跨域 | 结论 |
|---|---|---|---|---|
| `localStorage` | ✅ **能** | ❌ 不会 | ✅ 方便 | 一旦有 XSS 即失守 |
| `sessionStorage` | ✅ 能 | ❌ 不会 | 同标签页 | 同上，仅缩小窗口 |
| `httpOnly` Cookie | ❌ **不能** | ✅ **会** | 需 SameSite/CORS 配置 | 需防 CSRF（见 [Web 攻击防护](/security/web-attack#csrf)） |
| 内存变量（不持久化） | 仍受 XSS 影响（同页面可取） | ❌ 不会 | — | 刷新即丢，需配合刷新令牌 |

**这张表的正确读法**：它不是一个"选哪个"的问题，而是**「你更怕 XSS 还是更怕 CSRF」**——而两者都要靠其他手段缓解。所以真正的结论是：**存储位置的选择不能替代对 XSS / CSRF 本身的防护**，把安全完全押在"令牌放哪"上是错的。

## 五、令牌的失效与刷新：把"收不回"补回来 {#expiry-refresh}

无状态令牌不能主动失效，工程上用**两层时间**把损失控制在一个小窗口内：

| 令牌 | 寿命 | 存储侧 | 作用 |
|---|---|---|---|
| 访问令牌（access） | 5–15 分钟 | **无状态**，自校验 | 高频校验，短命意味着泄露的可用窗口短 |
| 刷新令牌（refresh） | 7–30 天 | **服务端存**（Redis/库） | 可撤销，一次一换 |

### 5.1 刷新必须轮换，且要检测复用 {#refresh-rotation}

```
第 1 次刷新：refresh_1 → 换取 access_2 + refresh_2（refresh_1 立即作废）
攻击者拿着被别人盗走的 refresh_1 来刷新 → 服务端发现「已作废的令牌被再次使用」
                                        → 判定为泄露 → 吊销该用户全部令牌 → 强制重新登录
```

**复用检测（reuse detection）是这套机制的价值所在**：它把一个"悄无声息的长期劫持"变成"一次可见的强制登出"。不做轮换的刷新令牌，等价于一张长期有效、无法撤销的通行证。

### 5.2 登出与时钟偏移 {#logout-skew}

- **登出**：无状态令牌做不到真正的登出。实践做法是「客户端删掉 + 服务端把该 `jti` 放进黑名单，黑名单 TTL 设为访问令牌的剩余寿命」——**因为访问令牌最多活 15 分钟，黑名单只需要记 15 分钟**，这个空间代价是可接受的。
- **时钟偏移**：分布式部署下各节点时间不一致，校验过期时间时必须留容差（通常 30–120 秒），否则会出现"刚签发就被判过期"的间歇性故障。

## 六、单点登录的四代方案 {#sso}

| 代 | 方案 | 凭据形态 | 适用 | 代价 |
|---|---|---|---|---|
| 1 | **CAS** | 服务端票据（ST/TGT） | 早期企业内部 | 协议专用、生态收窄 |
| 2 | **SAML 2.0** | XML 断言 + 签名 | 企业级 SaaS 对接、跨国组织 | XML 签名校验复杂、报文体积大 |
| 3 | **OAuth2** | access token | **授权场景**（第三方访问资源） | ⚠️ **它本身不是认证协议** |
| 4 | **OIDC** | ID Token（JWT）+ access token | 现代标准解法 | 需理解 OAuth2 的四种模式（见 [OAuth2 与开放授权](/security/oauth2)） |

**第三行是本节最需要记住的一句**：用 OAuth2 做登录本身是**误用**——它只回答"这个应用能访问哪些资源"，不回答"这个人是谁"。OIDC 正是在 OAuth2 之上补了认证能力（多一个 `id_token`），这才是"用 OAuth2 登录"的正确形态。

## 七、多端登录与互踢 {#multi-device}

```
会话登记（Redis）：
  user:1001:sessions → { "web-7f3a": exp1, "ios-91bc": exp2, "mp-2d0e": exp3 }
                       └─ 按设备维度登记，值记过期时间
```

| 策略 | 做法 | 适用 |
|---|---|---|
| 多端并存 | 同用户允许多设备同时在线，各自独立令牌 | 绝大多数 C 端产品 |
| 同端互踢 | 同设备类型只保留最新一次登录 | 安全要求高的后台、付费账号防共享 |
| 全端互踢 | 新登录使所有旧令牌失效 | 改密码、检测到泄露后的处置 |

**实现要点**：踢人时不能只删会话记录——如果访问令牌是无状态的，被踢设备仍能用旧令牌活动直至过期。所以要么**在网关层加一道"会话存在性校验"**（牺牲部分无状态收益），要么**接受一个不超过访问令牌寿命的滞后窗口**。这是"无状态"与"可即时撤销"之间永远存在的张力。

## 八、常见坑 {#pitfalls}

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 把 Base64 当加密 | 敏感信息泄露（payload 人人可读） | payload 只放标识，不放敏感数据 |
| 不校验 `alg`、放行 `none` | 攻击者可自行签发任意身份令牌 | 算法白名单 + 显式拒绝 `none` |
| HS256 密钥分发给所有校验方 | 任一服务被攻破即可伪造全网令牌 | 多校验方场景改用非对称算法 |
| 刷新令牌不轮换、不做复用检测 | 令牌被盗后长期静默可用 | 轮换 + 复用即吊销 |
| 把角色 / 权限写进 JWT | 权限调整后旧令牌仍持旧权限，**直到过期才生效** | JWT 只放身份，权限实时查（见 [权限缓存](/security/authorization#cache)） |
| 用 OAuth2 当登录协议 | 拿不到可信身份声明，容易实现出漏洞 | 用 OIDC |
| 只做认证不做会话登记 | 无法踢人、无法查看登录设备 | 维护会话表 |
| 忽略时钟偏移 | 间歇性"刚登录就过期" | 校验留 30–120s 容差 |

## 九、面试口径 {#interview}

**Q1：Session 和 JWT 到底怎么选？**
不是选技术新旧，是选状态放哪边。Session 把状态放在服务端，好处是**可即时撤销**、令牌体积小，代价是需要共享存储或粘性会话。JWT 把状态放在客户端，好处是**无状态、天然跨域、适配多端**，代价是**签出去就收不回**。多端接入的现实下通常选令牌，但要用「短命 access + 可撤销 refresh + 复用检测」把撤销能力补回来。

**Q2：JWT 能主动失效吗？**
严格说不能——这是无状态设计的固有代价。工程上只有三种缓解：① 访问令牌做得很短（5–15 分钟），把窗口压小；② 用 `jti` + 黑名单记录已登出的令牌，TTL 只需等于访问令牌剩余寿命；③ 在网关加会话存在性校验，等于放弃一部分无状态收益。**说"能主动失效"而没有说明代价的答案是不完整的。**

**Q3：为什么说 OAuth2 不是认证协议？**
因为它回答的是"这个应用被授权访问哪些资源"，不回答"这个用户是谁"。用 OAuth2 拿到的 access token 是给资源服务器用的，不适合当身份凭据——身份声明由 OIDC 的 `id_token` 提供，所以"用 OAuth2 登录"的正确形态是 OIDC。

**Q4：JWT 存在 localStorage 还是 Cookie？**
这是一个"更怕 XSS 还是更怕 CSRF"的权衡，没有免费解：localStorage 不会被 CSRF 利用，但任何 XSS 都能读走令牌；httpOnly Cookie 脚本读不到，但会自动随请求发送，需要 SameSite + CSRF Token 防护。**更重要的结论是：这个选择不能替代对 XSS / CSRF 本身的防护。**

**Q5：多因素认证为什么不能是"密码 + 密保问题"？**
因为两者都是"你知道的东西"——属于同一个形态。而真实泄露场景（撞库、拖库）恰恰会同时暴露这两类信息，所以它们不构成独立的两道防线。MFA 的实质是**跨形态组合**。
