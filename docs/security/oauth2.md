# OAuth2 与开放授权

> **为什么单列一篇**：OAuth2 是**第三方接入**的唯一主流标准，也是实现漏洞最集中的地方——它的规范里写满了"必须"，而多数事故恰恰出在这些"必须"被省略的地方。认证与令牌的通用机制见 [认证方式全景与选择](/security/authentication)；授权模型见 [授权模型与权限落地](/security/authorization)。

## 一、四个角色，以及一句必须记住的话 {#roles}

| 角色 | 是谁 | 在"用微信登录某网站"里的对应 |
|---|---|---|
| 资源所有者 | 数据的主人 | 用户本人 |
| 客户端 | 想访问数据的应用 | 那个网站 |
| 授权服务器 | 发令牌的一方 | 微信开放平台 |
| 资源服务器 | 存数据、验令牌的一方 | 微信的用户信息接口 |

> **OAuth2 是授权框架，不是认证协议。** 它回答"这个应用被授权访问哪些资源"，**不回答"这个用户是谁"**。用 OAuth2 做登录之所以能"看起来能用"，是因为拿到了 access token 之后又去调了用户信息接口——但**这条路径没有标准**，各家实现不一，且拿到的身份信息无法携带可信的认证声明。**要登录，用 OIDC**（第 5 节）。

## 二、四种授权模式与它们的淘汰史 {#flows}

| 模式 | 适用 | 现状 | 淘汰原因 |
|---|---|---|---|
| **授权码**（authorization code） | 有后端的 Web 应用 | ✅ **推荐**（必须配 PKCE） | — |
| **客户端凭据**（client credentials） | 服务端到服务端，**无用户参与** | ✅ 仍然有效 | — |
| 隐式（implicit） | 纯前端 SPA | ❌ **已废弃** | 令牌直接出现在 URL fragment 里 → 浏览器历史、Referer、日志都可能泄露；且无法安全地发 refresh token |
| 密码（password / ROPC） | 曾用于第一方 App | ❌ **已废弃** | 客户端直接拿到用户密码（违反 OAuth2 的初衷）；无法与 MFA、验证码等流程配合 |

OAuth 2.1 草案的方向很明确：**只保留授权码 + 客户端凭据，并把 PKCE 从"可选"提升为"必须"**。

**这条淘汰史有一个可迁移的判断**：当一个协议模式要求"令牌经过 URL 传递"或"客户端接触用户密码"时，它一定会在某个环节泄露——这两件事没有安全实现。

## 三、授权码 + PKCE 的完整时序 {#auth-code}

```
① 客户端生成 code_verifier（随机串）
   code_challenge = BASE64URL( SHA256(code_verifier) )

② 浏览器重定向到授权服务器
   /authorize?response_type=code&client_id=...&redirect_uri=...&scope=...
             &state=<随机值>&code_challenge=<...>&code_challenge_method=S256

③ 用户在授权服务器上完成认证并同意授权

④ 授权服务器回调：redirect_uri?code=<授权码>&state=<原样返回>

⑤ 客户端校验 state 与②中生成的一致（防 CSRF）

⑥ 客户端用授权码换令牌（这一步直接与授权服务器通信，不经过浏览器）
   POST /token { code, redirect_uri, client_id, code_verifier }

⑦ 授权服务器校验：code 有效 + code_verifier 的 SHA256 == ②中的 code_challenge
   → 返回 access_token（+ refresh_token + id_token）
```

### 3.1 两道防线分别在防什么 {#state-vs-pkce}

| 参数 | 防的攻击 | 攻击过程（不设防时） |
|---|---|---|
| `state` | **CSRF**（授权请求伪造） | 攻击者先获取一个自己的授权码，诱导受害者访问带该 code 的回调 → 受害者的账号被绑定到攻击者的身份上；`state` 让"这次回调必须对应我发起的这次请求" |
| `code_verifier` | **授权码拦截**（PKCE 的核心） | 公开客户端（SPA、原生 App）无法保存 `client_secret`；若恶意 App 抢注了同一个自定义 scheme，就能截获回调里的授权码。**只有最初的发起方持有 verifier**，所以即便授权码被截获，也换不到令牌 |

**PKCE 对公开客户端是刚需**，对有 `client_secret` 的服务端应用同样是纵深防御（OAuth 2.1 要求全部使用）。这里有一个常见的误解需要澄清：**PKCE 保护的是"授权码 → 令牌"这一跳**，不是保护令牌本身。

## 四、三种令牌各给谁用 {#tokens}

这是最容易搞混的一组概念，而它直接决定了"为什么我拿不到用户信息"这类问题的答案：

| 令牌 | 给谁 | 谁的资产 | 形态 | 怎么校验 |
|---|---|---|---|---|
| `access_token` | **资源服务器** | 授权服务器签发 | 不透明串或 JWT | 资源服务器本地验签，或调授权服务器的 introspect 端点 |
| `refresh_token` | **客户端** | 授权服务器 | 通常是不透明串 | **只对授权服务器有意义**，不能拿去访问资源 |
| `id_token` | **客户端** | 授权服务器 | **必须是 JWT** | 客户端自行验证签名与 `iss`/`aud`/`exp` |

**一句话记住**：`access_token` 是给**别人**（资源服务器）用的通行证，`id_token` 是给**自己**（客户端）读的身份声明。把 `access_token` 当身份凭据去解析用户信息，就是第一节说的那个误用。

## 五、OAuth2 与 OIDC 的分界 {#oidc}

```
┌──────────────────────────── OIDC ────────────────────────────┐
│  认证层：回答"你是谁"                                          │
│  必须带 scope=openid ｜ 返回 id_token（JWT）｜ 标准 /userinfo 端点 │
├──────────────────────────── OAuth2 ──────────────────────────┤
│  授权层：回答"能访问什么"                                       │
│  scope 自定义 ｜ 返回 access_token ｜ 规范 RFC 6749             │
└──────────────────────────────────────────────────────────────┘
```

| 对比项 | OAuth2 | OIDC |
|---|---|---|
| 解决的问题 | 授权 | 认证 |
| 请求标记 | `scope` 自定义 | **必须包含 `openid`** |
| 返回内容 | `access_token` | `access_token` + **`id_token`** |
| 用户信息 | **无标准端点** | 标准 `/userinfo` |
| 用户登出 | 无定义 | 有（RP-Initiated Logout） |

**实践判据**：需求是"用第三方账号登录我的系统" → 用 OIDC，检查返回里有没有 `id_token`；需求是"我的系统要访问第三方资源（读云盘文件、发消息）" → 用 OAuth2 的授权码模式拿 `access_token`。两者可以同时发生（一次授权同时拿到三种令牌）。

## 六、实现中的七个必查点 {#checklist}

按"出事概率 × 后果"排序，这是评审第三方接入时应该逐条对照的清单：

| # | 检查项 | 不做的后果 |
|---|---|---|
| 1 | **`redirect_uri` 精确匹配白名单**（不允许前缀匹配、通配符、动态子域） | 授权码被重定向到攻击者域名 → 账号被劫持。**这一条是 OAuth2 事故的头号来源** |
| 2 | 校验 `state` 且一次性使用 | CSRF：受害者账号被绑定到攻击者会话 |
| 3 | 全流程启用 PKCE | 授权码拦截（公开客户端尤其危险） |
| 4 | `scope` 最小化 | 申请了远超需要的权限，一旦令牌泄露影响面被放大 |
| 5 | 授权码**一次性**且寿命短（≤ 10 分钟） | 重放的授权码可被反复兑换令牌 |
| 6 | 校验令牌的 `iss` / `aud` / `exp`，密钥从 JWKS 取且**支持轮换** | 接受别家签发的令牌；密钥轮换时服务中断 |
| 7 | **任何情况下不接触用户密码** | 一旦客户端持有密码，OAuth2 的安全模型即失效（等于退回已废弃的密码模式） |

> 第 1 条值得再强调一次：`redirect_uri` 的校验必须**按完整字符串精确匹配**。曾经出现过"允许子路径"或"允许任意子域"的实现，攻击者注册 `https://app.example.com.attacker.com` 或利用开放重定向端点，就能把授权码引导到自己手里——**整个 OAuth2 的安全模型都建立在这个回调地址可信的前提上**。

## 七、常见坑 {#pitfalls}

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 把 `access_token` 当身份凭据 | 拿不到可信身份，实现随各家而异 | 用 OIDC 的 `id_token` |
| `redirect_uri` 前缀/通配匹配 | 授权码被导向攻击者域名 | 精确字符串白名单 |
| 不校验 `state` | CSRF 绑定攻击者账号 | 生成、校验、一次性 |
| SPA 用隐式模式 | 令牌经 URL 泄露，无法安全刷新 | 授权码 + PKCE（BFF 架构更佳） |
| 客户端保存用户密码 | 违反 OAuth2 安全模型，密码扩散 | 任何模式都不接触密码 |
| 客户端把 `client_secret` 打进前端包 | 密钥公开，可冒充应用 | 公开客户端不配 secret，改用 PKCE |
| 只验签名不验 `aud` / `iss` | 接受面向其他系统的令牌 | 全字段校验 |
| 硬编码授权服务器公钥 | 密钥轮换后全线失效 | 走 JWKS 端点并缓存 |

## 八、面试口径 {#interview}

**Q1：OAuth2 和 OIDC 什么关系？为什么说"用 OAuth2 做登录"是误用？**
OIDC 是构建在 OAuth2 之上的**认证层**。OAuth2 只解决"应用被授权访问哪些资源"，它签发的 `access_token` 是给资源服务器用的，本身不承诺任何身份声明。所以拿它当登录凭据时，各家只能在"拿 access token 再调用户信息接口"这条非标准路径上自行发挥。OIDC 补上了 `id_token`（JWT 格式的身份声明）和标准 `/userinfo` 端点，这才是认证的正确形态。

**Q2：PKCE 解决什么问题？**
解决公开客户端（SPA、原生 App）的**授权码拦截**问题。这类客户端无法安全保存 `client_secret`，而自定义回调 scheme 可能被恶意 App 抢注，导致授权码在重定向过程中被截获。PKCE 让发起方生成一对 `code_verifier`/`code_challenge`，**只有持有原始 verifier 的一方才能把授权码换成令牌**，从而让被截获的授权码失去价值。注意它保护的是"授权码换令牌"这一跳。

**Q3：`state` 参数防的是 CSRF，具体怎么攻击？**
攻击者先在自己的账号上走一遍授权，拿到一个合法的授权码（但不在自己的浏览器完成回调），然后诱导受害者访问带这个 code 的回调地址。如果客户端不校验 `state`，就会把这个 code 换成令牌并**当成受害者的会话建立登录**——结果是受害者的账号绑定了攻击者的第三方身份，之后攻击者可用自己的第三方账号登录受害者系统。

**Q4：为什么隐式模式和密码模式被废弃？**
隐式模式把令牌放在 URL fragment 里，会进入浏览器历史、Referer 头与中间日志，且无法安全下发 refresh token；密码模式让客户端直接接触用户密码，既违反最小暴露原则，也无法与 MFA、验证码流程配合。OAuth 2.1 的方向是只保留**授权码（强制 PKCE）+ 客户端凭据**两种。

**Q5：第三方接入评审，你最先看哪个配置？**
`redirect_uri` 的校验方式。因为它**精确匹配还是模糊匹配**，直接决定授权码会不会被引导到攻击者域名——而拿到授权码就等于拿到令牌。其次看 `state` 是否校验、PKCE 是否启用、`scope` 是否最小化。
