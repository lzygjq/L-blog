# 授权模型与权限落地

> **边界说明**：这一篇讲**授权模型与工程落地**。多租户的**数据隔离**（共享库 / 独立 Schema / 独立库、`tenant_id` 拦截）是另一条线，见 [微服务 → K8s 云原生演进](/projects/property-saas/microservice-to-k8s/)；接口层的**数据安全与合规**见 [发布、安全与运维](/projects/property-saas/release-and-ops/)。

## 一、授权的三代模型 {#models}

| 模型 | 判定依据 | 表达能力 | 性能 | 可审计性 | 典型场景 |
|---|---|---|---|---|---|
| **RBAC** | 用户 → 角色 → 权限 | 中 | 高 | **好** | 绝大多数后台系统 |
| **ABAC** | 主体/资源/环境属性的表达式 | **高** | 低（需评估表达式） | 差（结果难解释） | 云平台策略、精细化风控 |
| **ReBAC** | 实体之间的**关系图** | 高 | 中（图遍历 + 缓存） | 中 | 协作文档、共享空间 |

### 1.1 RBAC 的四个层级与一个退化形态 {#rbac}

RBAC 不是一个模型，而是一族（RBAC0 → RBAC3）：

| 级别 | 增加的能力 | 解决什么 |
|---|---|---|
| RBAC0 | 用户-角色-权限三元关系 | 基础 |
| RBAC1 | 角色**继承**（上级角色含下级权限） | 避免给"部门经理"重复勾选"专员"的全部权限 |
| RBAC2 | **约束**（互斥角色、基数限制） | 财务与审核不能是同一人 |
| RBAC3 | 继承 + 约束 | 完整形态 |

**它的退化形态是"角色爆炸"**：当业务需要"华南区 A 类项目的审核员"这种组合时，纯 RBAC 的解法是**为每种组合新建一个角色**——角色数量随之按维度乘积增长，最终没人能说清某个角色到底有哪些权限。**出现这个信号时，说明该引入属性（ABAC）或关系（ReBAC）来分解维度，而不是继续加角色。**

### 1.2 三代模型的判据 {#model-choice}

```
问：权限判定的依据，是"这个人固定属于哪个组"，还是"取决于资源与情境"？
  ① 相对固定、组数有限        → RBAC（默认选它）
  ② 取决于资源属性/时间/环境   → ABAC
  ③ 取决于"我和这个资源的关系" → ReBAC
```

**实践中的常见答案是混合**：主干用 RBAC（菜单、按钮、接口级权限），在数据范围这一层引入属性或关系（"我能不能看这条记录"）。**不要因为 ABAC 更"先进"就整体换掉 RBAC**——ABAC 的代价是可审计性：出了越权事故，RBAC 能直接回答"谁在什么时候给了这个角色"，ABAC 只能给出一条求值为 `true` 的表达式。

## 二、权限粒度的四个层次 {#granularity}

| 层次 | 控制什么 | 实现位置 | 是否可作为安全边界 |
|---|---|---|---|
| ① 菜单 | 侧边栏显示哪些入口 | 前端 | ❌ **不是** |
| ② 按钮 | 页面上哪些操作可见 | 前端 | ❌ **不是** |
| ③ 接口 | 这个请求允不允许执行 | 服务端（注解 + 拦截器） | ✅ 是 |
| ④ 数据 | 这一次能操作哪些数据 | 服务端（SQL 条件 / 归属校验） | ✅ 是 |

**这张表最重要的一行是「是否可作为安全边界」**：①② 是**体验层**——它们的价值是"不让用户看到点了会报错的东西"，而不是安全。

> **只控前端等于没控。** 前端代码在用户机器上运行，任何人都能直接构造请求。这个判断有一个很实用的推论：**前端权限校验的代码写得多精细，都不影响服务端必须独立校验一次**——两者不是"二选一"或"防重复"，而是两个不同目的。

接口层的常见实现（两种写法，语义一致）：

```java
// 声明式：在方法上标注所需权限点（Spring Security）
@PreAuthorize("hasAuthority('billing:invoice:issue')")
public void issueInvoice(Long id) { ... }

// 声明式：标注所需角色/权限（Shiro 风格）
@RequiresPermissions("billing:invoice:issue")
public void issueInvoice(Long id) { ... }
```

> **权限点命名规范**值得单独定：`模块:资源:动作`（如 `billing:invoice:issue`）三段式——它让"给某个角色勾权限"时的列表可读，也让代码里的注解能自解释。命名混乱是权限系统腐化的第一个信号。

## 三、数据权限：最难的一层 {#data-scope}

接口层回答"能不能调用这个接口"，数据层回答"调用了之后，能碰哪些数据"。**后者是越权事故的高发区**——因为它无法靠一个注解解决，必须进入查询条件。

### 3.1 两种形态 {#data-scope-types}

| 形态 | 语义 | 典型实现 |
|---|---|---|
| **范围型**（横向） | 我的 / 本部门 / 本部门及下级 / 本单位 / 全部 | 权限注解声明范围 → 在 SQL 上拼接 `WHERE` 条件 |
| **规则型**（纵向） | 按业务规则动态判定，如"只能看自己创建或参与审批的工单" | 查询条件由业务规则生成，常需在 Service 层组装 |

范围型的落地通常在数据访问层做**统一拦截**（MyBatis 拦截器改写 SQL，把 `data_scope` 条件注入 `WHERE`），规则型则因业务而异、难以统一抽象——这也是为什么它更容易出现遗漏。

### 3.2 一个必须分清的区分：数据权限 ≠ 租户隔离 {#scope-vs-tenant}

| 维度 | 租户隔离 | 数据权限 |
|---|---|---|
| 目的 | **A 公司的数据不能出现在 B 公司** | **同一个公司内，这个人不能看那个部门的数据** |
| 强制程度 | **绝对**——漏了就是数据事故 | 按业务需要，可配置 |
| 实现 | `tenant_id` 强制注入，不可绕过 | `data_scope` 按角色配置，可被授权调整 |
| 越权的性质 | 跨租户泄露（合同/合规问题） | 内部越权（管理问题） |

**两者在代码里常常挨着实现（都在 SQL 改写层），但绝对不能合并成一个开关**——租户条件必须是无条件注入的，而数据权限条件是随角色变化的。把租户隔离做成"权限点"（可以被某个角色关掉），是这类系统里最危险的一个设计失误。

### 3.3 归属校验：不信任任何来自客户端的标识 {#ownership}

最容易被漏掉的一类：

```java
// ❌ 水平越权的经典写法：直接按前端传来的 id 查
@GetMapping("/orders/{id}")
public OrderVO get(@PathVariable Long id) {
    return orderService.getById(id);      // 换个 id 就能看别人的订单
}

// ✅ 查询条件里带上"归属"这一条
@GetMapping("/orders/{id}")
public OrderVO get(@PathVariable Long id) {
    Long uid = SecurityUtils.getUserId();          // 从令牌取，不从前端参数取
    Order order = orderService.getByIdAndOwner(id, uid);
    if (order == null) throw new BizException(403, "无权访问");
    return OrderVO.of(order);
}
```

**核心原则：身份从令牌来，不从参数来；权限条件进查询，不进判断分支。** 前一句防的是"前端传个 ownerId 就能冒充"，后一句防的是"先查出来再判断，中间隔着一段忘了判断的代码"。

## 四、越权的两类与防护 {#broken-access}

| 类型 | 含义 | 例子 | 防护位置 |
|---|---|---|---|
| **垂直越权** | 低权限用户调用高权限功能 | 普通员工调用"删除用户"接口 | 接口层权限注解（第 2 节③） |
| **水平越权** | 同权限用户访问他人数据 | 把 `orderId=1001` 改成 `1002` 看别人订单 | **数据层归属校验**（第 3.3 节） |

OWASP 的 API 安全榜单里，**失效的授权（Broken Access Control / BOLA）长期位居第一**，而水平越权是其中最主要的形式。原因不难理解：

- 垂直越权可以靠**框架注解**统一解决，写一次覆盖全部接口；
- 水平越权**每个查询都要单独想**——框架不知道"这条记录属于谁"，只有业务知道。

### 4.1 否定式验证：安全测试的测试思想与功能测试相反 {#negative-testing}

功能测试问"**该能做的能不能做**"，安全测试必须额外问"**不该能做的能不能做**"。这类用例在常规测试里天然缺失——因为需求文档只写前者。

| 用例类型 | 常规测试 | 必须补的否定式用例 |
|---|---|---|
| 接口权限 | 管理员能删除用户 ✅ | **普通用户调删除接口应返回 403** |
| 数据归属 | 用户能看到自己的订单 ✅ | **用户 A 用用户 B 的订单 ID 应查不到** |
| 租户边界 | A 租户能查自己的账单 ✅ | **A 租户的令牌查 B 租户的账单应为空** |
| 参数篡改 | 正常参数返回正确 ✅ | **改 `tenantId` / `ownerId` 参数应无效** |

最后一行尤其值得强调：**否定式用例要包含"篡改参数"这一类**——很多实现把 `tenant_id` / `user_id` 设计成前端可传参数（为了"灵活性"），这等于把安全边界交给了客户端。

## 五、权限缓存的失效难题 {#cache}

权限是高频读取（每个请求都要判断）、低频变更（改角色时才动）的数据，天然适合缓存。但缓存的难点不在读，而在**变更时怎么失效**。

| 方案 | 做法 | 代价 |
|---|---|---|
| 短 TTL 兜底 | 缓存 1–5 分钟自然过期 | 权限变更后有延迟窗口；高频回源 |
| 版本号（推荐） | 每次权限变更使 `user:perm:ver:{uid}` 自增；缓存 key 带版本，旧 key 自然失效 | 需维护版本号，多一次读取 |
| 消息广播失效 | 变更时广播，各节点清本地缓存 | 依赖消息可靠性，广播风暴风险 |
| 本地缓存 + 长 TTL | 性能最好 | **变更后不生效，且难以排查** |

**版本号方案值得展开一句**：它把"清缓存"这个分布式难题转化成了"换 key"这个本地动作——旧 key 不再被访问，靠 TTL 自然回收，**不需要任何节点间通信**。这是 CAP 权衡上的一个漂亮取法。

还有一条硬规则：**不要缓存"权限判断的结果"**（如"用户 1001 能否访问资源 X"）——判断的组合是用户数 × 资源数，会爆炸，而且失效逻辑无法维护。**要缓存的是"用户有哪些权限点/数据范围"这个事实，判断本身应实时计算。**

## 六、两个框架的机制对照 {#frameworks}

存量系统里 **Shiro** 与 Spring 生态的 **Spring Security** 都很常见，两者概念可一一映射——**掌握一个之后迁移到另一个的实质成本很低**：

| 关注点 | Shiro | Spring Security |
|---|---|---|
| 核心主体 | `Subject` | `Authentication` / `SecurityContextHolder` |
| 身份来源 | `Realm`（`doGetAuthenticationInfo` / `doGetAuthorizationInfo`） | `UserDetailsService` + `AuthenticationProvider` |
| 拦截机制 | `Filter` 链（`ShiroFilterFactoryBean`） | `SecurityFilterChain`（新版为组件式配置） |
| 认证凭据 | `UsernamePasswordToken` 等 Token 类 | `Authentication` 实现类 |
| 授权注解 | `@RequiresPermissions` / `@RequiresRoles` | `@PreAuthorize` / `@PostAuthorize` |
| 会话管理 | 自带 `SessionManager`（**容器无关**，可脱离 Web 使用） | 依赖 Spring 上下文与 Web 环境 |
| 配置风格 | 代码/Servlet 过滤器为主 | 组件化配置 + 自动装配 |

**三条实质差异**，决定了它们的适用分化：

1. **Shiro 不依赖 Spring**——这让它在非 Spring 的存量项目（含传统 MVC 框架的项目）里成为默认选择；
2. **Shiro 的权限模型内建**（Realm 里直接返回权限集合），Spring Security 则需要自己决定"权限从哪来"（数据库 / 内存 / 外部服务）——**后者更灵活，前者上手更快**；
3. **Spring Security 的方法级授权与表达式能力更强**（`@PreAuthorize` 支持 SpEL 组合条件），Shiro 的注解相对朴素。

> **从存量项目迁移到 Spring 生态时的映射思路**：先在 Shiro 侧把**权限点清单与命名规范**理出来（这是真正的资产，与框架无关），再把它作为新体系的权限来源。**先迁移权限模型，再迁移鉴权代码**——反过来做会在两套权限定义之间来回对账。

## 七、常见坑 {#pitfalls}

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 只控前端菜单与按钮 | 接口裸奔，任何请求都可直达 | 服务端接口层独立校验 |
| 把租户隔离当权限点配置 | 某个角色可"关闭"租户条件 → 跨租户泄露 | 租户条件**无条件注入**，与数据权限分开 |
| 身份从请求参数取 | 改个 `userId` 即冒用身份 | 身份一律从令牌/上下文取 |
| 查询不带归属条件 | 水平越权（OWASP API 第一风险） | 归属进 `WHERE`，不查出来再判断 |
| 缓存权限判断结果 | 缓存空间爆炸、失效无法维护 | 缓存"权限点/范围"，判断实时算 |
| 角色与权限点硬编码 | `if (role.equals("ADMIN"))` 散布全代码 | 统一权限点 + 注解 |
| 超管拥有所有权限点 | 测试时永远通过，**越权缺陷测不出来** | 用最小权限账号跑越权用例 |
| 权限变更后不失效缓存 | 撤销权限后旧权限仍可用 | 版本号或短 TTL |
| 只测"该能做的能做" | 越权缺陷不会被发现 | 补**否定式验证**用例 |

## 八、面试口径 {#interview}

**Q1：RBAC 有什么问题，什么时候该换？**
它的退化形态是"角色爆炸"——当权限组合来自多个维度（区域 × 项目类型 × 岗位）时，纯 RBAC 只能为每种组合建角色，角色数按维度相乘，最终无人能说清某个角色的权限边界。**出现这个信号时应引入属性或关系来分解维度**，而不是继续加角色。但也不必整体换 ABAC：它以可审计性为代价换灵活性，出事时只能给出一条求值为 `true` 的表达式。

**Q2：为什么"只控前端"等于没控？**
前端代码运行在用户机器上，接口地址、参数格式对使用者都是公开的。菜单与按钮级权限的真实价值是**体验**（不让用户看到点了会报错的东西），不是安全。安全边界只有在服务端才有——这个判断的实用推论是：前端校验做得多细，服务端都要独立再校验一次。

**Q3：水平越权和垂直越权的防护有什么不同？**
垂直越权可以由框架统一解决（接口加权限注解，写一次覆盖全部）；水平越权**必须逐个查询处理**，因为框架不知道"这条记录属于谁"，只有业务知道。所以水平越权的正确写法是**把归属条件写进查询**（`getByIdAndOwner`），而不是"先查出来再判断"——后者会在代码演进中漏掉判断分支。

**Q4：租户隔离和数据权限为什么不能合并？**
租户隔离是**绝对的合规边界**（A 公司的数据不能出现在 B 公司），必须无条件注入；数据权限是**同一租户内的管理策略**，可随角色调整。如果把租户条件做成可配置的权限点，就会出现"某个角色能关掉租户过滤"这种设计——它直接等于跨租户数据泄露。

**Q5：Shiro 和 Spring Security 怎么选？**
看项目底座：Shiro 不依赖 Spring 且自带容器无关的会话管理，是存量非 Spring 项目的默认解；Spring Security 与 Spring 生态深度集成、方法级表达式能力更强，是 Spring 项目的默认解。**两者的概念可一一映射（Subject↔Authentication、Realm↔UserDetailsService、Filter↔SecurityFilterChain），迁移的实质成本很低**——真正要迁移的不是框架代码，而是与框架无关的**权限点清单与命名规范**。
