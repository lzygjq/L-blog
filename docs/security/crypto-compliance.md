# 加密、脱敏与合规边界

> **范围声明**：这一篇讲**技术侧的可落点**——把"要合规"翻译成"改哪行代码"。它不构成法律意见，具体义务的判定需走专业渠道。项目里的落地形态（接口数据安全九项、四条合规边界）见 [发布、安全与运维](/projects/property-saas/release-and-ops/)；传输层的主力是 TLS，与网络层的关系见 [计算机网络](/fundamentals/network/) 的 HTTP 一篇。

## 一、先分清三个目标，它们由不同工具负责 {#goals}

安全需求被笼统说成"要加密"，是很多设计失误的起点。**加密只解决其中一个目标**：

| 目标 | 回答 | 工具 | 对应的错误做法 |
|---|---|---|---|
| **机密性** | 别人看得到内容吗 | **加密**（对称/非对称） | 用哈希"加密"数据（不可逆就还原不了） |
| **完整性** | 内容被改过吗 | 哈希 / HMAC / 签名 | 只加密不校验——密文被篡改后解密出乱码甚至被定向攻击 |
| **不可否认** | 做过这事能抵赖吗 | **数字签名**（非对称） | 用 HMAC 当签名（双方都能生成 → 无法防抵赖） |

还有一条必须先排除的混淆：**编码不是加密**。Base64 无密钥、可逆、任何人可解——它只解决"二进制数据放不进文本协议"的传输问题。**把 Base64 当加密保护敏感数据，等同于把原始数据直接写出来。**

## 二、对称与非对称：分工，不是二选一 {#symmetric-asymmetric}

| 维度 | 对称（AES） | 非对称（RSA / ECC） |
|---|---|---|
| 速度 | **快数个数量级** | 慢 |
| 密钥分发 | 难——n 方互信需约 n² 个密钥 | 容易——公钥可公开 |
| 典型用途 | **数据加密主体** | **密钥交换**与**签名** |
| 推荐参数 | AES-128 / **AES-256-GCM** | RSA ≥ 2048（新系统建议 3072）或 ECC 256 |

**实践中的答案永远是混合加密**：

```
用非对称算法保护一个「对称密钥」→ 用对称密钥加密真正的数据
        （慢，但只做一次）              （快，数据量再大也扛得住）
```

这不是取巧——**TLS 就是这么工作的**（握手阶段协商出会话密钥，之后用对称加密传输）。理解这一点，就理解了两类算法的真实分工位置。

### 2.1 分组模式的选择：为什么默认该用 GCM {#aes-mode}

| 模式 | 问题 | 结论 |
|---|---|---|
| ECB | 相同明文块产生相同密文 → **泄露内容的模式**（经典演示：加密后的图片仍能看出轮廓） | ❌ 永不使用 |
| CBC | 需要 IV，**IV 复用会泄露明文关系**；且不提供完整性校验 | 可用，但需 IV 随机 + 额外 HMAC |
| GCM / CCM（AEAD） | 同时提供加密与完整性校验，且性能好 | ✅ **默认选它** |

**"加密 + 完整性"是一个整体需求**：只加密不校验，攻击者可以篡改密文，轻则解出乱码（DoS），重则配合协议特征做定向攻击（padding oracle 类）。AEAD 模式把这两件事合成一步，免去"自己拼 HMAC"的犯错空间。

## 三、哈希、加盐，以及为什么 SHA-256 存密码是错的 {#hash-password}

### 3.1 密码存储的正确解法 {#password-storage}

```
存储值 = 慢哈希( 密码 , 每用户随机的盐 )
        ↑          ↑
     bcrypt /      salt 与散列值一起存（salt 不是秘密）
     scrypt /
     Argon2id
```

三个要素缺一不可，各自解决一个问题：

| 要素 | 防的是什么 | 不做的后果 |
|---|---|---|
| **哈希（不可逆）** | 库被拖走后无法直接得到密码 | 明文存储 → 全量泄露 |
| **盐（每用户随机）** | 彩虹表；**相同密码产生不同散列** | 不加盐：两个同密码用户散列相同，可批量破解；预计算表直接命中 |
| **慢（可调迭代成本）** | 暴力破解的性价比 | 用 SHA-256 这类"为快速设计"的算法：GPU 每秒可尝试数十亿次 |

**一个高频追问**：`sha256(password + salt)` 算不算合格？——**算"加了盐"，但不合格**。问题不在加盐方式，而在**哈希本身太快**。专用密码哈希算法（bcrypt / scrypt / Argon2id）通过**迭代次数或内存开销**人为抬高每次尝试的成本，让离线暴力破解变得不经济。

| 写法 | 评价 |
|---|---|
| `md5(pwd)` | ❌ MD5 已碰撞、且极快 |
| `md5(md5(pwd))` | ❌ "双重哈希"不改变任何性质，仍是快哈希 |
| `sha256(pwd + 固定盐)` | ❌ 固定盐等于无盐（一张表可破全站） |
| `sha256(pwd + 每用户盐)` | ⚠️ 有盐但仍太快，仅勉强及格 |
| `bcrypt(pwd, cost=12)` / `Argon2id(...)` | ✅ 正确解法 |

**参数要能升级**：随着硬件变强，cost / 内存参数需要上调——所以存储格式里要带算法标识与参数（bcrypt 的散列值自带，Argon2 的 PHC 字符串格式自带），这样**老用户登录时可透明重算升级**。

### 3.2 哈希的其他用途与边界 {#hash-other}

| 用途 | 合适的算法 | 注意 |
|---|---|---|
| 校验文件完整性 | SHA-256 | 防意外损坏可以，**防恶意篡改不够**（攻击者可同时改文件与校验值） |
| 数据去重 / 等值比对 | SHA-256（加固定盐或不加） | 低熵数据（手机号）可被枚举反推——**需评估** |
| 消息完整性（有密钥） | **HMAC-SHA256** | 必须用 HMAC 结构，不要用 `hash(key + msg)`（长度扩展攻击） |

## 四、数字签名：与 HMAC 的边界在哪 {#signature}

```
签名：  散列(数据) → 用「私钥」签名         → 对方用「公钥」验证
HMAC：  HMAC(共享密钥, 数据)                → 对方用同一个共享密钥验证
```

| 维度 | 数字签名 | HMAC |
|---|---|---|
| 密钥 | 非对称（私钥签、公钥验） | 单一共享密钥 |
| **不可否认** | ✅ **只有私钥持有者能生成** | ❌ 双方都能生成，出纠纷无法定责 |
| 性能 | 慢 | 快 |
| 适用 | 对外接口、支付回调、证书、JWT(RS256) | 内部服务间、会话令牌、防篡改 |

**判据**：需要向**第三方**证明"这条数据确实是我发的"→ 用签名；只在**双方之间**做完整性保护 → 用 HMAC（更快）。

### 4.1 验签时必须配套做的三件事 {#verify-checklist}

只验签名是不够的，一个完整的对外接口签名方案还要：

| 项 | 防的问题 |
|---|---|
| 时间戳 + 有效期窗口 | **重放**（把抓到的合法请求重发一次） |
| nonce / 流水号去重 | 窗口内的高频重放 |
| 公钥来源可信（预置或证书链校验） | 攻击者用自己的密钥签一条数据、并把对应公钥给你 |

> **重放攻击是签名方案最常被漏掉的一环**：签名只保证"内容没改、来源可信"，不保证"这是新请求"。所以支付回调、开放接口这类场景，时间戳与去重存储是必需的组成部分。

## 五、数据脱敏的四级手段与选择判据 {#masking}

| 手段 | 可逆 | 可等值检索 | 典型用例 | 代价 |
|---|---|---|---|---|
| **掩码** | ❌ | ❌ | 界面展示 `138****8888` | 无 |
| **哈希** | ❌ | ✅（确定性） | 去重、比对（如"这个手机号是否已注册"） | 低熵数据可被枚举反推 |
| **加密** | ✅ | ⚠️ 需确定性加密才可 | 需要还原（发短信、对账） | 密钥管理；确定性加密会泄露"相同明文" |
| **令牌化** | ✅（换回） | ✅ | 银行卡、身份证等最高敏感数据 | 需额外的映射存储与鉴权 |

**两个判据决定选型**：

1. **需要还原吗？** 不需要 → 掩码或哈希；需要 → 加密或令牌化。
2. **需要等值查询吗？** 需要 → 只能用确定性手段（固定盐哈希 / 确定性加密），并接受"相同输入产生相同输出"带来的模式泄露；不需要 → 用随机 IV 加密，安全性更高。

还有一条容易被低估的分层：**展示脱敏 ≠ 存储脱敏**。

| 层 | 要求 | 漏掉的后果 |
|---|---|---|
| 展示层 | 界面/导出按角色掩码 | 越权查看（见 [授权模型](/security/authorization)） |
| **日志层** | **敏感字段一律不落日志** | ⚠️ **这是最高发的泄露路径**——日志被集中采集、长期保留、权限宽松、还常被贴进工单与聊天 |
| 存储层 | 加密 / 令牌化 + 密钥分离 | 库被拖走即全量泄露 |
| 数仓 / 备份层 | 同步脱敏或分级授权 | **删除了主库记录，备份与数仓里还在**（删除的传播问题） |

## 六、密钥管理：加密里真正难的部分 {#key-management}

加密算法的选择是一次性的，**密钥的生命周期管理才是长期风险**。

| 原则 | 做法 | 反面做法 |
|---|---|---|
| 不硬编码 | 由配置中心 / 密钥管理服务（KMS）/ 硬件模块（HSM）提供 | 写在代码、配置文件、镜像里 |
| **分层** | 主密钥（KMS 保管）→ 数据密钥（信封加密）→ 业务数据 | 一把密钥加密所有数据 |
| **轮换** | 定期轮换 + 事件驱动（人员离职、怀疑泄露） | 一把密钥用到项目结束 |
| **可解密历史数据** | 保留旧版本密钥（带版本号，解密时按版本取） | 轮换后旧数据无法解密 |
| 审计 | 记录"谁在何时用了哪个密钥" | 无任何使用记录 |
| 最小权限 | 只有需要的服务能取到密钥 | 全环境共用同一套密钥 |

**信封加密（envelope encryption）值得单独理解**：用它加密数据的是"数据密钥"，而数据密钥本身被"主密钥"加密后与数据一起存放——**这样轮换主密钥时不必重新加密全部业务数据**，只需重新加密数量有限的数据密钥。这是大规模系统能承受密钥轮换的关键设计。

## 七、合规边界：把要求翻译成工程动作 {#compliance}

### 7.1 两条主要的合规框架 {#frameworks}

| 框架 | 性质 | 与工程最相关的部分 |
|---|---|---|
| **网络安全等级保护（等保 2.0）** | 分级测评（一至五级） | 身份鉴别、访问控制、**安全审计**、数据完整性与保密性、备份与恢复。面向政企客户交付的系统通常至少需二级，涉及大量个人信息时可能要求三级 |
| **个人信息保护法（PIPL）** | 法律 | 告知—同意、**最小必要**、敏感个人信息需**单独同意**、跨境传输限制、个人的查阅/复制/更正/**删除**权利 |

**敏感个人信息的范围**（需单独同意、更强保护）：生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹，以及**不满十四周岁未成年人的个人信息**。

### 7.2 六件可以落到代码上的事 {#engineering-actions}

| # | 动作 | 工程落点 |
|---|---|---|
| 1 | **数据分类分级打标** | 字段级标注（敏感等级）→ 驱动后续脱敏、审计、导出控制 |
| 2 | 最小权限 + 审计日志 | 谁访问了哪些敏感数据要留痕，且日志权限独立（见 [发布、安全与运维](/projects/property-saas/release-and-ops/)） |
| 3 | 传输与存储加密 | 全站 TLS（内部服务间也别裸奔）+ 敏感字段落库加密 |
| 4 | 脱敏与去标识化 | 按第 5 节选型；**日志脱敏是第一优先** |
| 5 | 保留期限与删除机制 | 到期清理 + 支持"删除某人的全部数据" |
| 6 | 跨境传输判定 | 明确数据存哪、有没有出境路径（含第三方 SDK、CDN、云服务地域） |

> **第 5 件最容易被漏，也最容易被客户问**：「我要注销账号，我的数据能不能删干净？」——难点不在主库（`DELETE` 而已），而在 **备份、数仓、日志、缓存、搜索索引、对象存储**里的副本。**在设计期就把"数据的全部落脚点"列出来，比事后被要求删除时再去找要便宜得多。**

## 八、常见坑 {#pitfalls}

| 坑 | 后果 | 正确做法 |
|---|---|---|
| Base64 当加密 | 敏感数据等同明文 | 用真正的加密，Base64 只做编码 |
| MD5 / SHA-1 存密码 | 碰撞 + 极快，易被破解 | bcrypt / scrypt / Argon2id |
| 用 SHA-256 直接存密码 | 太快，GPU 每秒数十亿次尝试 | 慢哈希 + 每用户盐 |
| 固定盐 / 全局盐 | 等于没盐，一表破全站 | 每用户随机盐 |
| AES 用 ECB 模式 | 泄露明文结构（图片可见轮廓） | GCM（AEAD） |
| IV 固定或复用 | CBC 下泄露明文关系 | 每次随机 IV |
| 只加密不校验完整性 | 密文可被篡改，DoS 或定向攻击 | AEAD 模式，或加密 + HMAC |
| 用 HMAC 做对外签名 | 无法防抵赖（双方都能生成） | 对外用非对称签名 |
| 签名不带时间戳 / nonce | 重放攻击 | 时间窗口 + 去重存储 |
| 密钥硬编码在代码或镜像 | 一处泄露全量失守 | KMS / 配置中心 + 分层密钥 |
| 密钥轮换后旧数据解不开 | 数据不可用 | 密钥带版本，保留历史版本 |
| 只做展示脱敏，日志打印明文 | **日志成为最大泄露源** | 日志层强制脱敏 |
| 认为删了主库就等于删干净 | 备份 / 数仓 / 索引里仍有副本 | 列出全部数据落脚点，逐个处理 |

## 九、面试口径 {#interview}

**Q1：对称加密和非对称加密怎么配合？**
混合加密：用非对称算法保护（或协商）一个对称密钥，再用对称密钥加密真正的数据。原因是性能差数个数量级，而数据量可能很大——**TLS 就是这么做的**（握手协商会话密钥，之后对称加密）。两类算法的真实分工是：非对称负责**密钥交换与签名**，对称负责**数据加密主体**。

**Q2：为什么不能用 SHA-256 存密码？加了盐行不行？**
加盐解决的是"彩虹表与同密码同散列"的问题，但**解决不了"太快"**：SHA-256 为速度而设计，GPU 每秒可尝试数十亿次。密码存储必须用**专为慢速设计的算法**（bcrypt / scrypt / Argon2id），通过迭代次数或内存开销抬高每次尝试的成本。所以"每用户盐 + SHA-256"只是勉强及格，正确解法是慢哈希。

**Q3：数字签名和 HMAC 有什么区别，什么时候用哪个？**
根本区别在**不可否认性**：HMAC 用共享密钥，通信双方都能生成，出纠纷无法定责；数字签名用私钥生成、公钥验证，**只有一方能签**。所以需要向第三方证明来源的场景（对外接口、支付回调、证书）用签名，只在双方之间做完整性保护时用 HMAC（更快）。

**Q4：只做签名会不会有重放问题？**
会，而且这是最常被漏的一环。签名保证"内容未改、来源可信"，**不保证"这是新请求"**——攻击者可以原样重发抓到的合法请求。所以完整方案必须配**时间戳 + 有效期窗口 + nonce 去重**。

**Q5：数据脱敏怎么选手段？**
两个判据：**需不需要还原**（需要 → 加密或令牌化；不需要 → 掩码或哈希）、**需不需要等值检索**（需要 → 只能用确定性手段，并接受"相同明文产生相同密文"的模式泄露；不需要 → 用随机 IV 加密）。另外要分清**展示脱敏与存储脱敏**——最容易被忽略的是**日志层**，它权限宽松、长期保留、还常被复制进工单与聊天，是实际泄露的高发路径。

**Q6："删除用户数据"这件事难在哪？**
难在**数据的落脚点不止一处**：主库 `DELETE` 只是开始，备份、数仓、日志、缓存、搜索索引、对象存储里都可能有副本。所以正确做法是**在设计期就列出敏感数据的全部落脚点**，并为每一处定好保留期限与清理方式——否则收到删除请求时才发现找不到副本在哪。这也是合规里最容易被客户问到、技术上最容易失分的一项。
