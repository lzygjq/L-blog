# Web 攻击防护

> **定位**：这一篇按**攻击面**组织，讲清每类攻击的成立条件与对应的根治手段；越权（水平/垂直）属于授权范畴，见 [授权模型与权限落地](/security/authorization#broken-access)；限流与防刷属于容量与防护链路，见 [容量测算与压测方案](/projects/property-saas/capacity-and-perf/#protection)。

## 一、攻击面：按数据流向划分 {#surface}

防护手段记不住，通常是因为按"攻击名字"去背。**按数据流向分类**会让手段自然浮现：

| 流向 | 攻击类型 | 根治手段 | 位置 |
|---|---|---|---|
| 用户 → 服务端 | SQL / NoSQL / 命令注入 | **参数化**（把数据与代码分开） | 数据访问层 |
| 用户 → 服务端 → 存储 → 其他用户 | **XSS（存储型）** | **输出点按上下文转义** | 渲染层 |
| 用户 → 自己的浏览器 → 服务端 | **XSS（DOM / 反射型）** | 输出转义 + 安全 DOM API | 前端 |
| 攻击者站点 → 受害者浏览器 → 服务端 | **CSRF** | Token / SameSite / Origin 校验 | Web 层 |
| 用户 → 服务端 → 内网 | **SSRF** | 出站白名单 | 服务端 |
| 用户 → 服务端文件系统 | 上传 / 路径穿越 | 白名单 + 重命名 + 隔离存储 | 服务端 |

> **两条贯穿全篇的原则**：① **把不可信数据当数据，永远不当代码**（注入类的统一解）；② **在正确的边界上做防护**——转义要在输出点、权限校验要在服务端、SSRF 白名单要在发起请求的那一处。

## 二、XSS：三种类型与一个反直觉的结论 {#xss}

### 2.1 三种类型 {#xss-types}

| 类型 | 恶意脚本从哪来 | 是否落库 | 谁中招 | 危险度 |
|---|---|---|---|---|
| **存储型** | 攻击者提交的内容被存进数据库 | ✅ 是 | **所有访问该页面的用户** | 最高（可蠕虫式传播） |
| **反射型** | 藏在 URL 参数里，服务器"反射"回页面 | ❌ 否 | 点了恶意链接的人 | 中 |
| **DOM 型** | 完全在前端发生：JS 把 URL / `location` 的内容写进 DOM | ❌ 否 | 点了恶意链接的人 | 中（**服务端日志里看不到**） |

第三类常被忽略的原因很实际：**它不经过服务端渲染**，所以服务端的转义、WAF、日志全都挡不住它——责任完全在前端代码。

```javascript
// ❌ DOM 型 XSS 的入口：把不可信内容当 HTML 写进去
document.getElementById('tip').innerHTML = new URLSearchParams(location.search).get('msg');

// ✅ 按文本写入，浏览器不会解析为 HTML
document.getElementById('tip').textContent = new URLSearchParams(location.search).get('msg');
```

**危险 API 清单**（见到就要确认数据来源）：`innerHTML`、`outerHTML`、`document.write`、`eval`、`Function()`、`setTimeout(string)`、`location.href = userInput`，以及现代框架里的逃生舱——Vue 的 `v-html`、React 的 `dangerouslySetInnerHTML`（名字里带 `dangerously` 是有意的）。

### 2.2 一个反直觉的结论：在输出点转义，不在输入点过滤 {#xss-escape-where}

多数人第一反应是"在入库存之前把 `<script>` 过滤掉"。**这是错的**，三个理由：

| 理由 | 说明 |
|---|---|
| **同一份数据在不同上下文需要不同的转义** | 放进 HTML 文本、HTML 属性、JS 字符串、URL、CSS 里，转义规则各不相同。输入时无法预知它未来会被用在哪里 |
| **输入过滤会破坏合法数据** | 用户的真实姓名里可能有 `<`，备注里可能有 `&`、引号——过滤会让正常业务受损，且这类"脏数据"无法还原 |
| **过滤总有绕过** | 大小写、双重编码、Unicode 变体、SVG/MathML 命名空间……黑名单是一场打不赢的军备竞赛 |

**正确的模型**：数据在存储时**原样保存**（这样它永远可还原、可审计），在**输出到具体上下文的那一刻**按该上下文的规则转义。现代模板引擎（Thymeleaf、Vue、React 的插值）默认就是这样做的——**要警惕的恰恰是那些"关闭转义"的语法**。

### 2.3 富文本是唯一例外，处理方式是白名单净化 {#xss-richtext}

业务需要保留部分 HTML（富文本编辑器、评论带格式）时，无法整体转义——这时必须**净化**，规则与输入过滤相反：

| 要求 | 说明 |
|---|---|
| **白名单**，不是黑名单 | 只允许已知安全的标签与属性（`p`/`b`/`i`/`a[href]` 等），其余一律丢弃 |
| **服务端也要净化** | 只在前端净化等于没净化——请求可以绕过前端直接提交 |
| 属性值也要校验 | `href="javascript:..."`、`src="data:..."` 这类要单独拦 |
| 用成熟库，不自己写 | OWASP Java HTML Sanitizer、DOMPurify 等经过对抗性验证 |

### 2.4 CSP：纵深防御，不是替代品 {#csp}

内容安全策略（Content-Security-Policy）通过限制脚本的来源与执行方式，**降低 XSS 成功后的危害**（例如禁止内联脚本、限制只允许白名单域加载 JS）。

它值得部署，但要说清它的定位：**CSP 是第二道防线，不能替代转义**。理由：CSP 配置复杂、绕过方式已知（JSONP 端点、白名单域上的开放重定向、`unsafe-inline` 的历史包袱），且大量存量站点需要 `unsafe-inline` 才能运行——那等于没有防护。

## 三、CSRF：为什么浏览器会自动带上凭据 {#csrf}

### 3.1 成立条件（三个同时满足才可能） {#csrf-conditions}

```
① 认证凭据是「浏览器自动携带」的（Cookie / Basic Auth）
② 攻击者能让受害者的浏览器发出请求（表单自动提交、img src、fetch）
③ 服务端只凭「凭据有效」就执行了状态变更
```

**注意 ①**：CSRF 的攻击者**不需要读到 Cookie**——他只需要让受害者的浏览器"替他去请求"。这是 CSRF 与 XSS 的根本区别：XSS 偷数据，CSRF 借手脚。

**由此得到一条重要推论**：**如果认证不用 Cookie，而是用请求头（`Authorization: Bearer`）承载令牌，CSRF 天然不存在**——因为浏览器不会自动把自定义头加到跨站请求上。这也解释了 [令牌存储位置的权衡](/security/authentication#jwt-storage) 为什么直接影响 CSRF 的风险面：**选 `localStorage` 就基本没有了 CSRF，代价是把风险转移给了 XSS。**

### 3.2 四种防御手段与各自边界 {#csrf-defense}

| 手段 | 原理 | 边界与注意 |
|---|---|---|
| **CSRF Token**（同步器模式） | 服务端生成随机 token 与会话绑定，要求请求携带并校验 | 最可靠；**不要把 token 放在 URL 里**（会进 Referer 与日志） |
| **SameSite Cookie** | `Lax`（现代浏览器默认）：跨站 POST 不带 Cookie | 简单有效；`Lax` 仍允许顶层 GET 导航携带，所以**GET 不能有副作用** |
| **校验 `Origin` / `Referer`** | 拒绝来自非预期来源的请求 | `Origin` 比 `Referer` 可靠（后者可能被裁剪）；可作为补充而非唯一手段 |
| 双重提交 Cookie | token 同时放在 Cookie 与请求参数，服务端比对 | 无需服务端存储；但**子域能写 Cookie**时会被攻破，需谨慎 |

### 3.3 一条容易被忽视的加固：让 GET 无副作用 {#csrf-get}

如果"删除"是一个 `GET /user/delete?id=1`，那么一张 `<img src="https://site.com/user/delete?id=1">` 就能完成攻击——**img 标签天然发起跨站 GET**。所以：

- **状态变更必须用 POST / PUT / DELETE**（SameSite=Lax 的保护范围正是跨站非顶层请求）；
- **GET 语义上必须幂等**——这是 HTTP 语义要求，同时也是 CSRF 防护的一部分。

## 四、注入类攻击：参数化是唯一根治手段 {#injection}

### 4.1 SQL 注入 {#sqli}

```java
// ❌ 拼接：用户输入成了 SQL 代码的一部分
String sql = "SELECT * FROM orders WHERE name = '" + name + "'";

// ✅ 参数化：SQL 结构在编译期确定，参数只作为数据传入
String sql = "SELECT * FROM orders WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, name);
```

**为什么参数化能根治，而"过滤关键字"不能**：参数化让**语句结构在解析阶段就已固定**，后续传入的值无论包含什么字符都只能是"值"，无法改变语法结构。而关键字过滤是黑名单——`SELECT`/`select`/`SeLeCt`/`%53ELECT`/注释插入……绕过方式无穷。

MyBatis 用户的一条实操红线：

| 语法 | 行为 | 用法 |
|---|---|---|
| `#{param}` | **预编译参数**，安全 | 一切来自用户的**值**都用它 |
| `${param}` | **字符串拼接**，有注入风险 | 仅用于**非用户输入**的动态结构，且必须白名单校验 |

### 4.2 参数化覆盖不到的三个位置（最常被漏） {#sqli-gaps}

参数化只能替换"值"，**不能替换标识符与结构**。所以下面三处必须单独处理：

| 位置 | 为什么不能参数化 | 正确做法 |
|---|---|---|
| `ORDER BY` 的列名 / 方向 | 列名是标识符，不是值 | **白名单映射**（`sortKey → 真实列名`），拒绝其余 |
| 表名 / 库名（如分表路由） | 同上 | 白名单 + 命名规范约束（分片后缀来自服务端计算，不来自入参） |
| `IN (...)` 的列表长度、`LIMIT` 值 | 结构由入参决定 | 参数在循环中绑定；`LIMIT` 用参数化 + 服务端上限校验 |

**分库分表场景要多一层注意**：分片键若参与 SQL 拼接（选表名），必须走内部计算——**分片键来自用户入参时，它就是一个注入点**。

### 4.3 其他注入面（同一原理的不同载体） {#other-injection}

| 类型 | 载体 | 根治手段 |
|---|---|---|
| NoSQL 注入 | MongoDB 查询对象（如 `{"$ne": null}` 绕过密码校验） | 校验入参类型，拒绝对象型入参 |
| 命令注入 | `Runtime.exec("ping " + ip)` | **避免拼接**，用数组形式传参；严格校验入参格式 |
| 表达式注入 | SpEL / OGNL / 模板表达式 | 不把用户输入当表达式求值 |
| ORM 查询语言 | HQL / JPQL 字符串拼接 | 同样用参数绑定，**ORM 不是免疫** |

**一条通用判据**：只要代码里出现"用户输入 + 字符串拼接 + 被解释执行"这个三元组合，就是注入。**修复的方向永远是"让数据无法成为代码"**，而不是"过滤危险字符"。

## 五、SSRF、文件上传与反序列化 {#others}

### 5.1 SSRF：让服务器替你访问内网 {#ssrf}

典型入口：远程图片下载、Webhook 回调、URL 预览、导入外部数据。攻击者提交一个指向内网的 URL，**服务端就成了他的代理**——可以探测内网拓扑，在云环境里还能读到元数据服务（`169.254.169.254`，可能含临时凭据）。

| 防护 | 说明 |
|---|---|
| **出站白名单**（域名 / IP 段） | 最有效；黑名单必漏 |
| 禁止跟随重定向 | 否则"先给公网地址、再 302 到内网"可绕过校验 |
| 解析后校验真实 IP | 防 DNS Rebinding（先解析到公网，请求时变内网） |
| 禁用危险协议 | 只允许 `http/https`，挡掉 `file://`、`gopher://`、`dict://` |
| 独立网络出口 + 最小权限 | 纵深防御：即便被绕过，也拿不到关键服务 |

### 5.2 文件上传 {#upload}

| 检查 | 常见错误做法 | 正确做法 |
|---|---|---|
| 类型 | 黑名单（`.php`/`.jsp`） | **扩展名白名单** |
| 内容 | 只信 `Content-Type` | 头部可伪造，**要校验文件魔数 + 必要时重编码** |
| 文件名 | 直接使用原名 | **重命名**（防 `../` 路径穿越与覆盖） |
| 存储位置 | 放在 Web 可执行目录 | **独立存储（对象存储 / 非执行目录）** |
| 访问方式 | 直接静态暴露 | 鉴权代理或签名 URL（**上传件常含敏感信息**） |

### 5.3 反序列化 {#deserialization}

Java 原生反序列化（`ObjectInputStream`）遇到不可信数据时，攻击者可以构造恶意对象链触发任意代码执行。要点：

- **不要把不可信数据交给原生反序列化**——优先换成 JSON（无对象构造语义）；
- 必须用时加 `ObjectInputFilter` 白名单；
- 注意"隐蔽的入口"：缓存、MQ 消息、Session 序列化、RMI、第三方组件的协议解析。

## 六、浏览器侧防线：六条响应头 {#headers}

| 响应头 | 作用 | 建议值 |
|---|---|---|
| `Content-Security-Policy` | 限制脚本/资源来源，降低 XSS 危害 | 按站点定制（逐步收紧，别一开始就上最严） |
| `X-Content-Type-Options` | 禁止浏览器猜 MIME 类型 | `nosniff` |
| `X-Frame-Options` 或 CSP `frame-ancestors` | 防点击劫持（iframe 套壳） | `DENY` / `SAMEORIGIN` |
| `Strict-Transport-Security` | 强制后续请求走 HTTPS | `max-age=31536000; includeSubDomains` |
| `Referrer-Policy` | 控制 Referer 泄露（防令牌/内部路径外泄） | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | 关闭不需要的浏览器能力（摄像头/定位） | 按需最小化 |

**部署顺序建议**：先上 `nosniff` / `HSTS` / `frame-ancestors` / `Referrer-Policy` 这四个低风险项（几乎不会破坏现有功能），CSP 最后上且用报告模式先观察。

## 七、常见坑 {#pitfalls}

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 在输入点做 XSS 过滤 | 绕过、脏数据、上下文不匹配 | **输出点按上下文转义** |
| 只在前端净化富文本 | 直接构造请求即绕过 | 服务端也净化，白名单 |
| 用 `${}` 接收用户参数 | SQL 注入 | `#{}` 参数化；动态结构走白名单 |
| 认为 ORM 免疫注入 | HQL 拼接同样可注入 | 统一用参数绑定 |
| `ORDER BY` / 表名用参数化却忘了白名单 | 参数化在这里无效 → 注入 | 白名单映射 |
| 远程请求用户给的 URL | SSRF（探测内网、云元数据） | 出站白名单 + 禁重定向 + 禁内网段 |
| 上传只校验 `Content-Type` | 伪造类型即绕过 | 魔数校验 + 扩展名白名单 + 重命名 |
| 上传件放 Web 目录且直接暴露 | 可执行 / 敏感文件泄露 | 独立存储 + 签名 URL |
| 把不可信数据交给原生反序列化 | RCE | 改 JSON，或加 `ObjectInputFilter` |
| 状态变更走 GET | CSRF 只需一个 `<img>` | 变更用 POST，GET 保持幂等 |
| 只依赖 SameSite | 旧浏览器 / 顶层 GET 仍有缺口 | Token 为主，SameSite 为辅 |
| 只测"正常功能" | 不做否定式用例，注入与越权都测不出 | 把恶意输入与越权用例纳入回归 |

## 八、面试口径 {#interview}

**Q1：XSS 为什么要在输出点转义，而不是在输入时过滤？**
三个理由：① **同一份数据在不同上下文需要不同转义**（HTML 文本、属性、JS、URL、CSS 规则都不同），输入时无法预知它将来用在哪；② 输入过滤会**破坏合法数据**（真名里的 `<`、备注里的 `&`），且不可还原；③ 关键字黑名单**总有绕过**。正确模型是"存储时原样保存，输出到具体上下文时按该上下文规则转义"，现代模板引擎的默认插值就是这么做的——要防的是"关闭转义"的语法（`v-html`、`dangerouslySetInnerHTML`）。

**Q2：CSRF 的成立条件是什么？什么情况下不需要担心它？**
三个条件同时满足才可能：凭据由浏览器自动携带（Cookie）、攻击者能让浏览器发出请求、服务端仅凭凭据有效就执行状态变更。**推论是：如果认证用 `Authorization` 头承载令牌（而非 Cookie），CSRF 天然不存在**——浏览器不会自动给跨站请求加自定义头。所以令牌存储位置的选择（Cookie vs localStorage）本质是"更怕 CSRF 还是更怕 XSS"的权衡。

**Q3：SQL 注入为什么参数化能根治，"过滤关键字"不能？**
参数化让 SQL **结构在解析阶段就已固定**，之后传入的值只能是数据、无法改变语法结构——这是"把数据与代码分离"这个原则的直接实现。而关键字过滤是黑名单，大小写变形、编码变形、注释插入等绕过方式无穷，且会误伤正常数据。**修复方向永远是让数据无法成为代码。**

**Q4：参数化有什么覆盖不到的地方？**
三处：`ORDER BY` 的列名与方向、表名/库名（分表路由）、`IN` 列表长度与 `LIMIT` 值——它们都是**标识符与结构**，不是值。这些位置必须用**白名单映射**，或者由服务端计算得出。分库分表场景尤其要注意：**分片键若来自用户入参并参与选表，它就是一个注入点。**

**Q5：SSRF 怎么防？为什么不跟随重定向很重要？**
核心是**出站白名单**（域名/IP 段），黑名单必然漏。不跟随重定向是因为"先返回公网地址、再 302 到内网"可以绕过校验；同理还要在 DNS 解析后校验真实 IP，防 DNS Rebinding（解析与请求之间切换目标）。此外禁用 `file://`/`gopher://` 等协议、独立出口网络并最小化权限，构成纵深防御。
