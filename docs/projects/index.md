# 项目实战 · 板块导览

其他板块回答「**这东西是什么、为什么这样设计**」；这个板块回答另一个问题：**「你做过什么，拿什么证明。」**

面试里前一类问题有标准答案，后一类没有。区分候选人的不是「做过」这个词，而是**能不能说清当初的约束、放弃的选项、付出的代价，以及哪些部分还没验证过**。这个板块的全部内容都是围绕这一点组织的。

## 一、五个子板块的分工 {#modules}

| 子板块 | 回答的问题 | 形态 | 状态 |
|---|---|---|---|
| [**成长路线**](/projects/architect-roadmap/) | 「我在哪一级、下一步读什么」——成长 L1–L4 能力路线**自检清单** | 计划层：四级阶梯 + 领域依赖链，每项挂本站对应页与「读到哪一层」 | ✅ 已成篇 |
| [**架构路线**](/projects/architecture-evolution/) | 「什么时候该动哪一层」——架构 L1 共址拆机之后，架构 L2–L6 五层各走各的 | **方法层**：总览记因果，层页给触发 / 包络 / 可跳过；[层账](/projects/architecture-evolution/ledger/)填档 | ✅ 已成篇 |
| [**可验证产出工具箱**](/projects/toolkit/) | 「凭什么信你说的」——立项三件套（ADR / 压测 / 架构图）+ 方案评审 + 运行期复盘；自用入口是[闭卷模拟盘](/projects/toolkit/drill/) | **方法层**：Why → What → How；卷子先写后对照 | ✅ 方法成篇；案例已抽出 ADR-002～006 与两份**未实测**口径 |
| [**绩效系统**](/projects/perf-system/) | 「最难的地方你怎么解的」——四个难点专题 | **案例层**：背景 → 方案对比 → 落地 → 效果 → 复盘 | ✅ 已成篇（4 篇） |
| [**智慧物业 SaaS**](/projects/property-saas/) | 「**某一个系统**具体怎么演的」——业务链路、微服务到 K8s、单库到数仓、容量与发布 | **案例层**：同上 | ✅ 已成篇（5 篇） |

**为什么方法层排在案例层前面**：先学会「怎么产出证据」，再看案例怎么用这些证据。反过来看，案例里最关键的几句话（为什么否决另一个方案、拐点在哪）会被当成「作者的个人习惯」而忽略掉。

## 二、一条主线：自检 → 方法 → 案例 {#mainline}

```text
① 能力自检（计划层）
   成长路线：四级阶梯（开发 → 高级开发 → 架构师 → CIO）+ 领域依赖链
        │  产出：一张「我会什么、我不会什么」的清单
        │  遗留问题：知道自己会，但拿不出证据
        ▼
② 产出方法（方法层）
   可验证产出工具箱：闭卷模拟盘 → ADR / 压测口径 / 架构图；拍板走方案评审；出事之后追加故障复盘
   架构路线：共址拆机之后按层走；档位记在层账（已上线 / 已验证 / 仅方案）
        │  产出：填过的层账 + 写过的卷子 + 立项三件套
        │  遗留问题：方法会了，但没有用自己的约束填进去
        ▼
③ 项目案例（案例层）
   绩效系统（4 个难点专题） + 智慧物业 SaaS（5 篇专题）
        │  产出：带约束、带备选、带代价、带未验证部分的完整叙事
        ▼
   回到 ①：案例里暴露的知识缺口，指回各知识板块的正文
```

> **这条主线的意义**：环上的每一步都在**减少「形容词」、增加「可检验的事实」**。全程只有形容词的简历段落（「高并发」「高可用」「大幅提升」）是零信息量的——面试官无法验证，也就无法采信。

## 三、面试官在问什么，拿什么答 {#review-map}

项目面的问题看似随意，实际只在这四类之间切换。**每类都有对应的证据形态**：

| 面试官的问题 | 他在验证什么 | 拿什么答 |
|---|---|---|
| 「这个系统多大？」 | 你有没有**规模感**（量级、增长曲线、峰值） | [压测报告](/projects/toolkit/perf-report/)：环境、数据量、拐点、安全水位 |
| 「为什么用这个技术？」 | 你是**选过**还是**抄的** | [ADR](/projects/toolkit/adr/)：备选方案、否决理由、重审条件 |
| 「最难的地方在哪？」 | 你有没有**判断力**（能否识别真难点） | [绩效系统的难点专题](/projects/perf-system/)：现象 → 假设 → 证据 → 结论 |
| 「这套东西长什么样？」 | 你能不能**把复杂结构讲清楚** | [架构图](/projects/toolkit/arch-diagram/)：分层、边界、关键路径 |
| 「如果量再翻十倍？」 | 你知道**现在的瓶颈在哪**吗 | 压测报告的容量结论 + [可观测](/cloud-native/observability/)的容量指标 |
| 「这个方案今天能不能拍？」 | 你有没有**否决理由和散会条件** | [方案评审](/projects/toolkit/review/)：会前三件材料、会上四问 |
| 「线上出过什么事？」 | 你是否把一次失败写成**可复核的机制改动** | [故障复盘](/projects/toolkit/postmortem/)：时间线、否决掉的假设、止血与修复分列 |
| 「哪些地方做得不够好？」 | 你是否**诚实且清醒**（这题最容易被忽略） | 每篇案例的「设计目标与尚未验证的部分」小节 |

> **最后一行是分水岭**。承认「这部分我只在方案层验证过、没有生产数据」不会减分；把方案说成已上线成果，一旦被追问细节就会全面崩盘。

## 四、案例层的两个系统 {#cases}

两个案例刻意选了不同的侧重面——一个偏**单点深挖**，一个偏**架构演进**：

| 系统 | 侧重 | 难点专题 | 状态 |
|---|---|---|---|
| [**大型集团绩效系统**](/projects/perf-system/) | **单点性能与一致性** | [十万人组织架构同步](/projects/perf-system/org-sync-100k/)（树形结构批量同步）<br>[高峰期并发填报](/projects/perf-system/peak-filling/)（流量尖峰与限流）<br>[多级审批消息实时推送](/projects/perf-system/approval-push/)（最终一致与不丢不重）<br>[报表预计算](/projects/perf-system/report-precompute/)（预聚合与查询性能） | ✅ 已成篇（4 篇） |
| **智慧物业 SaaS** | **架构演进与多租户** | [核心业务链路](/projects/property-saas/core-business/)（出账峰值与强一致、门禁弱网离线、交易状态机）<br>[微服务 → K8s 云原生演进](/projects/property-saas/microservice-to-k8s/)（框架聚合、三级混合租户隔离、租户上下文传播）<br>[大数据架构方案 → 数仓落地](/projects/property-saas/data-warehouse/)（Canal 同步、Doris 分层、冷热分层与 TTL 迁移）<br>[容量测算与压测方案](/projects/property-saas/capacity-and-perf/)（六步推导链、五层防护链路、压测方案）<br>[发布、安全与运维](/projects/property-saas/release-and-ops/)（四种发布策略、扩展—迁移—收缩、合规边界） | ✅ 已成篇（5 篇） |

**案例写作的固定结构**（便于横向对比）：背景与约束 → 方案对比（含被否决的） → 落地实现 → 效果数据 → 复盘与面试问答。两个系统都严格按此结构，读第二篇时可以直接跳到关心的那一节。

## 五、项目题的答法与三条红线 {#interview}

| # | 红线 | 为什么 | 正确做法 |
|---|---|---|---|
| 1 | **不编造数值** | 面试官会追问「怎么测的、环境是什么、瓶颈在哪」——编的数字答不上第二问 | 没测过就说「这部分只在方案层验证过」，并说明**打算怎么测** |
| 2 | **不只说结论** | 「我们用了 Redis 做缓存」是零信息量 | 给出**约束 → 备选 → 取舍 → 代价**四段式 |
| 3 | **不把方案说成成果** | 需求评审通过 ≠ 已上线；压测验证 ≠ 生产稳定 | 明确区分「已上线 / 已验证 / 仅方案」，三者价值不同但都可信 |

**四段式的具体示范**（以「异步事件为什么用 Redis Stream 而不是引入消息中间件」为例，完整版见 [ADR-001](/projects/toolkit/adr/adr-001-event-bus-stream)）：

```text
① 约束：事件量级不高、消费方只有两个、团队没有独立中间件的运维力量
② 备选：RabbitMQ / Kafka / Redis Stream / 数据库轮询 / 同步调用
③ 取舍：Stream 已有依赖、支持消费组与 ACK，省掉一套运维成本；
        代价是持久化能力弱于专业 MQ、堆积能力有限
④ 重审条件：事件量增长一个数量级，或消费方超过 5 个 → 重新评估
```

**四段里最加分的是 ④**——它证明你知道这个决策的**失效边界**。只讲 ①②③ 的人是在讲「当时」，讲出 ④ 的人是在讲「现在我会怎么做」。

## 七、与相邻板块的边界 {#boundary}

| 相邻板块 | 它负责什么 | 本板块负责什么 |
|---|---|---|
| 各知识板块 | **原理层**：机制、对比、最佳实践 | **证据层**：这些原理在我的项目里留下了什么可检验的产物 |
| [面试专题](/interview/) | **检索层**：成长 L2→L3 先卡[一包](/interview/#pack)；1236 题是库存 | 提供项目面的**答案素材**（面试专题只把项目题指过来，不代答） |
| [云原生](/cloud-native/) / [数据仓库](/bigdata/) | 通用方法论（怎么做容器化、怎么分层建模） | 特定约束下**为什么这样选**（案例里的取舍与代价） |

> **一条纪律**：这个板块里所有涉及具体系统的内容都**脱敏到只保留技术取舍**——不写公司名、不写真实业务量级、不写内部代号。判断标准很简单：**读者应该能把方法用在自己的项目上，但认不出这是谁的项目。**
