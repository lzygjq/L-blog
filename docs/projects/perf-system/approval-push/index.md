# 多级审批消息实时推送

> **口径说明**：本文是架构设计记录，不是生产运行报告。文中的连接数、消息量与耗时都是**按参数区间推导的设计目标**，标注为「推导值」；全文已脱敏，不含企业标识、真实人员数据与内部代号。

## 一、背景：三个要求彼此打架 {#background}

### 1.1 实时、不丢、不重 {#three-requirements}

审批推送的三个要求，单独看都很简单，放在一起就互相冲突：

| 要求 | 含义 | 与其他的冲突 |
|---|---|---|
| **实时** | 下级提交后，上级几秒内就该看到待办 | 实时要用长连接 → 连接会断 → **影响"不丢"** |
| **不丢** | 每条审批事件都必须送达 | 要保证不丢，最稳的是落库 + 拉取 → **影响"实时"** |
| **不重** | 同一事件不能重复提醒 | 重试保不丢 → 必然产生重复 → **影响"不重"** |

```
        实时（快）
        ╱      ╲
       ╱        ╲
  不丢 ────────── 不重
  （可靠）      （准确）
     三者只能两两优化；要三个都要，得靠"分层"而不是"挑一个"
```

**破解思路不是三选二，而是分层**：

```
推送通道 ──▶ 只负责"快"（尽力而为，允许丢）
数据库   ──▶ 只负责"不丢"（事件持久化，可重放）
幂等判据 ──▶ 只负责"不重"（事件 ID + 状态机）
```

> **这是本篇的第一条主线**：**不要让一个组件同时承担"快"和"可靠"两个目标。** 长连接做不到可靠（它自身就是会断的），数据库做不到实时。分开之后，每个组件只需要把自己那件事做对。

### 1.2 客户端形态决定通道能力 {#clients}

选通道之前必须先回答"客户端是什么"，因为不同形态的能力边界完全不同：

| 客户端 | 能保持长连接吗 | 后台能收推送吗 | 可用通道 |
|---|---|---|---|
| PC 浏览器（管理端） | 能（页面打开期间） | 不能 | WebSocket / SSE / 长轮询 |
| 移动端 App | 能（前台） | 能（依赖系统推送通道） | 长连接 + 厂商推送 |
| H5 / 小程序 | 能（页面前台） | 不能 | WebSocket（小程序） / SSE（H5，受限） |

**本系统的客户端是「PC 管理端 + 移动端 App」两套**，这直接决定了通道不能只选一个：

| 端 | 场景 | 通道选择 |
|---|---|---|
| PC 管理端 | 审批人在办公桌前处理待办 | WebSocket（双向、需要心跳与"正在输入"类交互） |
| 移动端 App（前台） | 审批人在会议间隙处理 | WebSocket / 长连接 |
| 移动端 App（后台） | 需要"响铃提醒" | **系统推送通道**（APNs / 厂商推送）——这不是我们自己的长连接 |

> **一条容易漏掉的区分**：**App 在后台时，我们自己的长连接会被系统挂起**。所以"App 后台收到提醒"这件事，只能依赖操作系统厂商的推送通道，而不是自己维护的 WebSocket。这两条路的能力、延迟、可靠性完全不同，**不能当成一条链路来设计**。

## 二、通道选型：四种方案 {#selection}

### 2.1 四种通道对比 {#four-channels}

| 通道 | 方向 | 实时性 | 服务端状态 | 网关/代理友好度 | 实现复杂度 |
|---|---|---|---|---|---|
| **短轮询** | 拉 | 差（取决于间隔） | 无状态 | 最好 | 最低 |
| **长轮询** | 拉（挂住请求） | 好 | 要"挂住"连接，**半状态** | 好 | 中 |
| **SSE** | **单向推**（服务端→客户端） | 好 | 有状态 | 较好（纯 HTTP，但需禁用缓冲） | 低 |
| **WebSocket** | **双向** | 最好 | **有状态**（要维护连接表） | 需支持 `Upgrade` | 中高 |

**本方案的选择**：PC 管理端用 **WebSocket**，移动端前台用 **WebSocket**，后台走**厂商推送**，同时保留**短轮询作为降级通道**。

为什么不用 SSE——SSE 在"服务端单向推送"这个场景下其实更省事（纯 HTTP、内置自动重连、无需自定义协议）。**否决 SSE 的原因是本系统的审批列表需要"已读回执"和"批量已处理"，这是客户端到服务端的方向**，SSE 做不到，硬要凑就得再开一路 HTTP 接口，反而更复杂。

### 2.2 被否决的方案与否决理由 {#rejected}

| 被否决的方案 | 否决理由 |
|---|---|
| **纯短轮询（如 5 秒一次）** | 6 万人 × 1.2 端 = 7.2 万客户端，5 秒轮询 = **1.44 万 QPS 的纯无效请求**（大多数返回"无新消息"）。这个量级不是"省点资源"，而是**要为一堆什么都不做的请求建一套集群** |
| **纯长轮询** | 服务端要把请求"挂住"直到有事件或超时。7.2 万挂起请求 = **7.2 万个被占用的连接**，在服务端资源上与长连接几乎等价，却**多了一轮请求-响应的协议开销**，且"挂住"的实现要处理各种超时与重连边界 |
| **纯系统推送（APNs / 厂商推送）** | 只适合移动端，PC 浏览器收不到；且厂商推送的延迟与到达率不可控（厂商限流、用户关闭通知、设备离线）。**把审批的实时性押在第三方通道上，等于把 SLA 交给别人** |
| **推送即状态（推送里带上完整的待办数据）** | 见 [5.1 节](#push-signal-not-state)。**这是最危险的方案**：一旦丢一条推送，客户端的状态就永久错了，而且客户端不知道它错了 |

## 三、审批流状态机 {#state-machine}

### 3.1 状态与事件 {#states}

审批流是**两级状态机**——实例级和节点级，两级各管各的：

| 层级 | 状态 | 迁移事件 |
|---|---|---|
| **实例级** | 草稿 → 待提交 → 审批中 → 通过 / 驳回 / 撤回 / 终止 | 提交、同意、驳回、撤回、终止 |
| **节点级** | 待处理 → 处理中 → 已同意 / 已驳回 / 已跳过 | 开始处理、同意、驳回、跳过（前序驳回后） |

```
草稿 ──提交──▶ 待提交 ──发起──▶ 审批中 ──┬─全部节点通过──▶ 通过
                                │        ├─任一节点驳回──▶ 驳回
                                │        ├─发起人撤回────▶ 撤回
                                │        └─管理员终止────▶ 终止
                                │
                                └─ 节点级（实例内可多个并存）
                                   待处理 ─▶ 处理中 ─▶ 已同意 / 已驳回
                                       └──前序驳回──▶ 已跳过
```

**实例状态由节点状态推导，不独立维护**：

```
实例处于"审批中" ⟺ 存在节点处于「待处理 / 处理中」
实例的最终态       ⟸ 所有节点都已终结（同意/驳回/跳过），再按规则归纳
```

> **为什么不独立维护实例状态**：两处状态一旦分开维护，就必然出现"节点都说完了，实例还显示审批中"这类不一致——**而修复它需要对账，对账需要写更多代码**。让实例状态成为一个**推导量**（由节点状态算出），不一致在结构上就不可能发生。这类"把状态改成派生量"的手法，与 [状态机方案的幂等性](/java/spring/spring-cloud/idempotency#state-machine) 是同一个思路。

### 3.2 会签 / 或签 / 加签 / 转签 {#countersign}

这四种机制是审批流复杂度的主要来源，也是面试里最容易问出深度的地方：

| 机制 | 语义 | 节点终结条件 | 关键注意点 |
|---|---|---|---|
| **会签（all）** | 全部通过才算通过 | 全部同意 → 通过；任一驳回 → 驳回（可配置） | **驳回的语义要显式定义**：一票否决 vs 全部驳回才否决 |
| **或签（any）** | 任一通过即通过 | 首个同意 → 通过；其余转"已跳过" | 其余人的"已跳过"必须落库，否则待办列表永远不清 |
| **加签** | 运行时临时插入审批人 | 插入的节点也要终结 | **前加签 / 后加签语义不同**：前加签是自己审完之后给别人审，后加签是自己审之前先给别人审 |
| **转签 / 委托** | 把自己的待办转给别人 | 原节点结束，新节点开始 | **要留痕**：谁在什么时间转给了谁，审计必须能查到 |

> **"或签"里最容易被漏掉的一条**：**任一通过后，其余待处理节点必须显式终结为"已跳过"**。如果只是"逻辑上忽略"，这些节点会一直停留在"待处理"，于是：待办列表里永远有这条、未读数永远清零不了、按时完成率统计全部算错。**"逻辑上忽略"和"状态上终结"是两件事——凡是参与统计的状态，都必须显式终结。**

### 3.3 状态机是幂等的载体 {#idempotency-carrier}

消息一定会重复（重试保不丢的必然代价），所以在**应用事件之前**必须有一道判据。状态机天然提供了它：

```
收到事件 E（如「同意」）作用于实例 I
   ├─ 当前状态允许 E 迁移？ ── 允许 ──▶ 应用，写状态流转记录，投递下一节点事件
   └─                        不允许 ──▶ 直接丢弃（不是错误，是幂等命中）
```

| 场景 | 状态机的表现 |
|---|---|
| 重复收到"同意"事件 | 实例已是"审批中"且该节点已"已同意" → 迁移不允许 → 丢弃 |
| 迟到的"驳回"事件（实例已通过） | 已通过 → 不允许再驳回 → 丢弃，**并记录一条异常审计**（这种不该丢，要能查） |
| 乱序的"开始处理"（节点已同意） | 不允许 → 丢弃 |

> **注意区分"幂等命中"和"非法迁移"**：两者都会走到"丢弃"，但**语义完全不同**。前者是正常现象（重试的必然结果），后者是数据异常（说明上游有 bug 或事件顺序真的错了）。**实现上必须分开计数**——否则你在监控里看到的"丢弃数"永远是正数，无法判断系统是否在正常范围。**把两类不同原因的事件合并成一个计数器，等于把告警变成了噪音。**

## 四、消息可达性：不丢 {#reliability}

### 4.1 本地消息表（事务性发件箱） {#local-message-table}

问题很经典：**"业务数据写库"和"消息发出去"不能放在同一个事务里**（消息中间件不参与数据库事务；"先发消息再写库"会在写库失败时产生幽灵消息）。

解法是**本地消息表**，把"发消息"这个动作也变成一次本地写：

```
【本地事务】                                          【异步投递】
┌──────────────────────────────────────┐
│ ① 更新审批节点状态                    │
│ ② INSERT INTO outbox(event_id, ...)  │  ──▶ 投递线程扫描未确认记录
│    （与业务表在同一个数据库，同一个事务）│       ├─ 投递成功 → 标记已确认
└──────────────────────────────────────┘       ├─ 投递失败 → 退避重试
                                                └─ 超上限 → 死信 + 告警
```

**为什么这样就"不丢"了**：业务状态与"待发消息"在同一个事务里，要么都成功要么都失败——**不存在"状态改了但消息没记下"的窗口**。投递失败无所谓，因为消息**已经落在库里**，重扫即可。

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 扫描方式 | 按主键递增扫描未确认记录 | 避免全表扫；顺序与插入顺序一致 |
| 幂等 | `event_id` 唯一索引 + 消费端去重 | 重复投递不可避免 |
| 清理 | 已确认记录延迟删除（保留 N 天） | 便于排查；且要防止"还没投递就被清掉" |
| 并发 | 单实例扫描 + 分片（多实例各扫一段 ID） | 避免多实例重复扫描同一批 |

> 与 RocketMQ 的**事务消息（半消息 + 回查）**是同一个问题的另一种解法，取舍见 [RocketMQ 事务消息](/middleware/rocketmq/#transaction)。**判据是"要不要引入额外组件"**：已经有 MQ 且支持事务消息时用它更省事；没有则本地消息表零依赖。

### 4.2 推送失败的三级兜底 {#three-fallbacks}

推送只是"快"，它一定会失败。所以每一级都要有下一级接住：

| 级别 | 手段 | 覆盖什么 | 延迟 |
|---|---|---|---|
| ① **长连接推送** | WebSocket / 厂商推送 | 在线且连接正常的用户 | 秒级（推导值 < 3s） |
| ② **站内信落库** | 事件写入站内信表，客户端下次拉取时看到 | **离线用户、连接断开、推送失败** | 下次打开页面时 |
| ③ **关键节点额外通道** | 短信 / 邮件 / 企业 IM | 超时未处理的关键审批（如截止前 2 小时仍未处理） | 分钟级 |

**第 ③ 级为什么要限"关键节点"**：外部通道有成本、也有限流（第三方按条计费且有频控）。**全量走短信等于把成本变成一个随消息量线性增长的项**，而它的价值只体现在"这个审批真的不能拖"的时刻。

### 4.3 推拉结合：推送是加速，不是唯一通道 {#push-pull}

**这是本篇最重要的设计原则**，也是开头"分层"思路的落地：

```
客户端启动 / 进入应用
    ├─ ① 拉取：按本地游标请求增量事件（权威）
    │     → 补齐所有错过的事件，纠正本地状态
    └─ ② 建立推送：订阅后续变化（加速）
          → 只负责"更快知道"，不负责"知道得对"
```

| 如果推送是唯一通道 | 如果推送只是加速 |
|---|---|
| 丢一条 → **状态永久错**，且客户端不知道 | 丢一条 → 用户晚几秒/几分钟才知道，**下次拉取自动补齐** |
| 需要服务端维护"每条消息的送达确认" | 只需要维护"用户的游标" |
| 故障后果 = 数据错误 | 故障后果 = **延迟上升** |

> **判据一句话**：**推送负责时延，拉取负责正确性。** 把这两个职责绑在同一个通道上，就是让"会断的长连接"去承担"不能错"的任务——**这在结构上注定要出事**。

## 五、不重与有序 {#dup-and-order}

### 5.1 推送只传"信号"，不传"状态" {#push-signal-not-state}

推送的载荷设计有一个决定性的选择：

| 方案 | 载荷 | 丢一条的后果 |
|---|---|---|
| ✗ 推送即状态 | `{未读数: 7, 待办: [...]}` | 本地未读数永久错（下一条推送是 8，跳过了 7 那次） |
| ✓ **推送即信号** | `{事件: "有变化", 版本: 1024}` | 客户端知道"有变化"，去拉一次权威数据；**丢一条只是晚知道** |

**未读数为什么不能"收到一条 +1"**——因为它把"推送到达"与"业务状态"绑成了一件事。而推送的本质是**尽力而为**，用一个尽力而为的通道去累积精确的状态，误差只会单方向累积（只多不少或只少不多），**永远无法自愈**。

**正确做法**：未读数由服务端计算，推送只是"通知你去看"：

```
推送载荷：{ type: "TODO_CHANGED", seq: 1024 }
客户端收到 ──▶ 调用 /api/todo/summary ──▶ 拿到服务端计算的未读数与待办列表
```

这样，**"丢推送"的后果从"数据错误"降级为"感知延迟"**——而感知延迟是可接受的、且下次拉取就能纠正。

### 5.2 事件 ID 与客户端去重 {#event-id}

即使只传信号，重复推送也会造成重复的界面动作（两次弹窗、两次响铃）。所以事件本身要带 ID：

| 层次 | 去重手段 |
|---|---|
| **事件 ID** | 每个事件有全局唯一 ID，客户端维护"最近处理的 ID 集合"（滑动窗口） |
| **游标** | 更省事：服务端事件有**单调递增 `seq`**，客户端只记"我处理到哪个 seq 了"，`seq <= 本地` 一律忽略 |
| **幂等键** | 业务侧（如"标记已读"）用 `(用户ID, 实例ID)` 做幂等 |

> **游标优于 ID 集合**：ID 集合需要维护窗口大小、且无法判断"中间漏了没有"；单调 `seq` 一个数字就同时解决了去重、断点续传和漏发检测（本地 seq=100、新收到 seq=105 → 中间 101~104 可主动补拉）。**能用单调序号表达的顺序，就不要用"集合+时间戳"去模拟。**

### 5.3 顺序：按审批实例分区 {#ordering}

审批事件必须**按实例有序**——"先收到通过、再收到提交"会让状态机直接错乱。但**跨实例无序是可接受的**（两个不同的审批流之间没有因果关系）。

| 做法 | 说明 |
|---|---|
| 分区键 = **审批实例 ID** | 同一实例的事件落同一分区 → 分区内有序 → 满足需求 |
| 不要用全局有序 | 全局单分区会成为吞吐瓶颈，且**跨实例有序是不必要的需求**（典型的多度约束） |

顺序消息的机制与代价见 [Kafka 的顺序性](/middleware/kafka/ordering) 与 [RocketMQ 顺序消息](/middleware/rocketmq/#ordering)。**注意点**：分区内有序是"投递有序"，**消费端并发处理仍会乱序**——所以消费侧也要按实例串行（同一个实例的事件交给同一个线程/同一把锁处理）。

## 六、离线与多端 {#offline}

### 6.1 多端已读同步 {#multi-device}

用户在手机上看过的审批，PC 端打开时不该再显示为未读。这要求**已读状态存在服务端**：

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 已读存哪 | 服务端（`(用户ID, 实例ID, 已读时间)`） | 存在客户端则无法跨端同步 |
| 多端冲突 | **已读是"或"关系**：任一端已读 → 全局已读 | 已读不需要"最新的赢"，一旦读了就不该退回未读 |
| 同步方式 | 已读动作写服务端 → 通过推送通知其他端（只传信号） | 避免"本地标记已读、实际没同步" |

> **"已读"是单调的**（未读 → 已读，不可逆），所以多端合并用"或"就够了，**不需要任何冲突解决机制**。判断一个状态能不能用简单合并，看它是否单调——**单调状态不需要 CRDT，只需要取并集。**

### 6.2 离线补偿 {#offline-compensation}

| 离线时长 | 补偿策略 |
|---|---|
| < 1 小时 | 按游标拉取增量事件即可 |
| 1 小时 ~ 1 天 | 同上；但**未读数已无意义**，直接显示最新总数（回归"状态由服务端算"的原则） |
| > 1 天 | 不试图"重放所有事件"，直接**全量拉取当前待办列表**——用户关心的是"现在要做什么"，不是"期间发生了什么" |

> **补偿的判据**：**补"状态"永远优于补"过程"。** 离线一天的客户端要重放几百条事件，既慢又无意义；直接拉一份最新的待办列表，用户要的信息一模一样。**只有审计场景需要完整过程，界面不需要。**

## 七、容量与效果（推导值） {#capacity}

| 指标 | 设计目标 | 推导依据 |
|---|---|---|
| 长连接数 | 约 7.2 万 | 6 万用户 × 1.2 端（PC + 移动，部分重叠） |
| 单节点连接数 | 3 万 | 按单机 4C8G、每连接约 20–40 KB 内存估；留水位 |
| 连接节点数 | 3 台 + 1 备 | 7.2 万 ÷ 3 万 ≈ 2.4，取 3 台留 60% 水位 |
| 心跳间隔 | 30s | 兼顾 NAT 超时（常见 60–300s）与心跳流量 |
| 心跳放大 | 7.2 万 ÷ 30s ≈ 2,400 QPS | **心跳流量必须单独计量**，它比业务消息还多 |
| 峰值业务事件量 | 约 30 万 / 日、峰值 200 / 秒 | 审批动作在截止日集中；单事件平均触达 2–3 个接收人 |
| 推送延迟 | P99 < 3s | 长连接直推；不含厂商通道（第三方不可控） |
| 站内信落库 | 100% 事件 | 与推送并行，不依赖推送成功 |

> **心跳是长连接方案里最容易被漏算的成本**：7.2 万连接、30 秒心跳 = **2,400 QPS 的恒定负载**，与业务量无关，且**用户什么都不做的时候它也在**。评估长连接方案时，这笔账必须先算进去。

## 八、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标 | 现状 | 验证方式 |
|---|---|---|---|
| 推送时延 | P99 < 3s | 设计完成 | 生产埋点：事件产生 → 客户端接收 |
| 消息不丢 | 站内信 100% 覆盖 | 设计完成 | 对账：已发生的审批事件数 vs 站内信记录数 |
| 幂等命中率 | 幂等命中与非法迁移分开计数 | 设计完成 | 人为注入重复事件，断言状态不变且"非法迁移"计数为 0 |
| 多端已读 | 任一端已读，其他端一致 | 设计完成 | 两端并发标记已读；一端标记后另一端拉取校验 |
| 断线重连 | 重连后按游标补齐，无重复无遗漏 | 设计完成 | 人为断网 5 分钟，恢复后比对本地与服务端事件集合 |
| 单机连接数 | 3 万连接稳定 | **推导值** | 需压测实测（连接数与内存、心跳 QPS 的关系） |
| 滚动更新不中断 | 发布期间连接不丢失、消息不丢 | 设计完成 | 发布期间持续产生事件，验证重连后补齐 |
| 厂商推送到达率 | — | **不可控（第三方）** | 只能观测，不能承诺 |

> **必须诚实说明两点**：① 连接数与心跳 QPS 都是推导值，**长连接的真实验证只能靠压测**（连接数与内存、句柄、GC 的关系并非线性，且高连接数下的行为与低连接数完全不同）；② **厂商推送的到达率我们无法承诺**——所以它只作为"后台提醒"的增强，关键审批的兜底必须落在站内信与第 ③ 级通道上。

## 九、复盘与面试问答 {#interview}

**Q1：推送要"实时、不丢、不重"，这三个要求怎么同时满足？**
不是三选二，而是**分层**：推送通道只负责"快"（尽力而为、允许丢），数据库只负责"不丢"（事件持久化、可重放），幂等判据只负责"不重"（事件 ID + 状态机）。**核心原则是不要让一个组件同时承担"快"和"可靠"两个目标**——长连接天生会断，做不到可靠；数据库天生有延迟，做不到实时。

**Q2：为什么最终没用 SSE？它看起来更简单。**
SSE 在"服务端单向推送"下确实更省事（纯 HTTP、内置重连）。**但本系统的审批列表需要"已读回执"和"批量已处理"，这是客户端到服务端的方向**，SSE 做不到；硬要凑就得再开一路 HTTP 接口，反而比 WebSocket 更复杂。**判据是"有没有反向流量"，不是"哪个协议更时髦"。**

**Q3：推送里为什么不直接带上未读数和待办列表？**
因为那会把"推送到达"和"业务状态"绑在一起。推送的本质是**尽力而为**，用它累积精确状态，误差会单方向累积且**永远无法自愈**（下一条推送是 8，永远补不上丢掉的 7）。正确做法是**推送只传信号**（`{type, seq}`），客户端收到后去拉服务端计算的权威数据。这样丢推送的后果从"数据错误"降级为"**感知延迟**"——下次拉取自动纠正。

**Q4：审批事件为什么会乱序，怎么保证顺序？**
用**分区**：分区键取审批实例 ID，同一实例的事件落同一分区 → 分区内有序。**不要追求全局有序**——那是典型的多度约束：全局单分区会成为吞吐瓶颈，而"两个不同审批流之间的顺序"根本不是需求。另外要注意：分区保证的是**投递有序**，消费端如果并发处理仍会乱序，所以消费侧也要按实例串行。

**Q5：消息重复投递时，怎么判断"该丢弃"还是"该报警"？**
靠状态机：当前状态不允许该事件迁移时丢弃。但**必须区分两类原因**——① **幂等命中**（正常现象，重试的必然结果）；② **非法迁移**（数据异常，说明上游有 bug 或事件顺序真错了，比如"实例已通过却收到驳回"）。两者都走到"丢弃"，但**必须分开计数**：合并成一个计数器，你在监控里看到的就是一个永远非零、无法判断正常范围的数字——**等于把告警变成了噪音。**

**Q6：离线一天的客户端，怎么补偿？**
**补"状态"而不是补"过程"。** 离线一天可能积压几百条事件，逐条重放既慢又无意义——用户关心的是"现在要做什么"，不是"期间发生了什么"。所以直接**全量拉取当前待办列表**。只有审计场景需要完整过程，界面不需要。

**Q7：评估长连接方案时最容易漏算的成本是什么？**
**心跳流量**。7.2 万连接、30 秒心跳 = **2,400 QPS 的恒定负载**，与业务量无关，用户什么都不做时它也在。很多方案评估时只算了"业务消息量"，上线后发现连接层的开销比业务本身还大。另外两个容易漏的是：单机连接数与内存**不是线性关系**（高连接数下行为完全不同，必须压测），以及**长连接把服务端从无状态变回了有状态**——这正是它对 K8s 滚动更新、扩缩容不友好的根源。
