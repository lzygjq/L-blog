# 高峰期并发填报

> **口径说明**：本文是架构设计记录，不是生产运行报告。文中的 TPS、耗时与容量数字都是**按参数区间推导的设计目标**，标注为「推导值」；全文已脱敏，不含企业标识、真实人员数据与内部代号。

## 一、背景：三个约束把问题框死了 {#background}

绩效填报不是"随时可以填"的功能，它有明确的**窗口期**。这一点决定了整个容量问题的形状。

### 1.1 窗口期集中 {#window}

```
常规业务（如缴费）：        ▲ 流量
                          │   ╭──╮
                          │  ╱    ╲
                          │ ╱      ╲
                          └──────────────▶ 时间（天）
                            波动平缓，峰值 ≈ 均值 × 2~3

绩效填报：                  ▲ 流量
                          │            ╱│╲
                          │           ╱ │ ╲
                          │          ╱  │  ╲
                          └──────────────▼─────▶ 时间（天）
                            窗口开启日 + 截止前 2 天 = 双峰
                            峰值 ≈ 均值 × 10 以上
```

窗口期集中在两端：**开放首日**（大家抢着先填）与**截止前 1~2 天**（拖延的集中补交）。中间几天流量接近零。

### 1.2 填报与审批的依赖关系 {#dependency}

这是填报区别于普通表单提交的地方——**提交不是终点，而是链路的起点**：

```
下级提交 ──▶ 上级才能开始评分 ──▶ 上级提交 ──▶ 更上一级评分
    │                                                  │
    └── 一串依赖意味着：截止时间的压力会沿着链条向后传导 ──┘
```

| 依赖形态 | 对容量的影响 |
|---|---|
| 下级必须先提交 | 提交量在"截止前 2 小时"极度集中（等靠要），**峰值的峰值** |
| 上级评分依赖下级完成 | 读操作（拉取待办、查看下级进度）远多于写操作，**读写比约 20:1** |
| 截止时间不可协商 | 不能在截止前做"限流排队 10 分钟"这种有明显感知的操作 |

> **一条关键结论**：填报期的主要流量不是"提交"，而是"**查看**"——反复打开待办列表、反复刷新下级进度、反复打开表单看要不要改。**只盯着写入做容量设计，会在压测时发现"提交没问题、但列表页把数据库打挂了"。**

## 二、流量预估：五步推导 {#estimation}

### 2.1 完整链路 {#chain}

```
① 在册人数 ──× 参与率──▶ 参与填报人数
② 参与人数 ──× 人均表单数──▶ 表单总数
③ 表单总数 ──× 人均提交次数（含修改重提）──▶ 窗口期提交总量
④ 提交总量 ──× 高峰集中比例 ÷ 高峰持续秒数──▶ 峰值提交 TPS
⑤ 峰值 TPS ──× 读写比──▶ 峰值查询 QPS
```

每一步的参数与取值依据：

| 步 | 推导量 | 参数 | 经验区间与说明 |
|---|---|---|---|
| ① | 参与人数 | 参与率 | 约 85%–95%（试用期、长期休假不参与） |
| ② | 表单总数 | 人均表单数 | 约 2–5 张（目标表 / 自评表 / 互评表 / 述职表） |
| ③ | 提交总量 | 人均提交次数 | 约 1.5–3 次/张（**首次提交 + 截止前修改重提**，这是最容易被漏算的一项） |
| ④ | 峰值提交 TPS | 高峰集中比例、高峰秒数 | 截止前 2 小时可承载 30%–50% 的当日提交量；**集中系数是决定峰值的关键** |
| ⑤ | 峰值查询 QPS | 读写比 | 约 20:1；**列表页与进度页是查询大头** |

### 2.2 最容易被低估的参数：高峰集中系数 {#peak-factor}

按「窗口期提交总量 ÷ 窗口期秒数」算出的均值会小得让人安心——**然后上线后截止日当天必然崩**。

```
峰值 TPS = 提交总量 × 高峰集中比例 ÷ 高峰持续秒数

例（推导值）：窗口期 5 天、提交总量 18 万次
  按均值算：180,000 ÷ (5 × 24 × 3600) ≈ 0.4 TPS      ← 看起来随便扛
  按截止日算：单日 8 万次、集中在前 2 小时、其中 40% 在前 30 分钟
              → 32,000 ÷ 1,800 ≈ 18 TPS              ← 45 倍差距
```

> 与 [容量测算与压测方案](/projects/property-saas/capacity-and-perf/#peak-factor) 里的结论一致：**同一份总量，按不同的高峰集中系数算出的峰值可以差一个数量级以上**。区别在于缴费类业务的集中是"自然形成"的，而填报的集中**有相当一部分是可以被产品手段人为削掉的**——这正是下一节的内容。

### 2.3 分批放号：把集中系数当成可优化的架构问题 {#batch-release}

| 手段 | 作用对象 | 效果（推导值） | 代价 |
|---|---|---|---|
| **按部门分批开放** | 集中系数 | 集中系数由 ~12 降到 ~5 | 需要业务侧同意"不同部门不同开放时间" |
| **错峰截止** | 集中系数 | 削掉截止日的峰 | 需要给不同部门不同截止日 |
| **排序展示"待办"而非全量** | 查询 QPS | 列表页查询量降一个数量级 | 产品改造 |
| **进度页缓存 + 主动推送** | 查询 QPS | 轮询式刷新改为推送 | 需引入推送能力（见 [多级审批消息实时推送](/projects/perf-system/approval-push/#selection)） |

> **这是本篇的第一条主线**：**人数是业务目标、不可控；而高峰集中系数是纯架构与产品问题、可控。** 通过分批放号把集中系数从 12 压到 5，等于用产品流程换来一倍的硬件余量——**比买机器便宜得多，也比买机器更可靠**（因为硬件扩容有上限，流程削峰没有）。

## 三、方案对比：削峰三路 {#selection}

### 3.1 三种削峰做法 {#peak-shaving}

| 做法 | 原理 | 用户感知 | 复杂度 | 适用 |
|---|---|---|---|---|
| **同步直写** | 请求直接落库，靠数据库扛 | 无 | 最低 | 峰值 TPS < 数据库承载能力的 50% |
| **限流 + 排队** | 超出阈值的请求返回 429 + 重试提示 | 明确（"请稍后重试"） | 低 | 峰值短促、可接受少量失败 |
| **预排队 + 异步落库** | 请求先受理进队列，异步消费落库 | 低（返回"已受理"） | 中高 | **本方案** |

**本方案选"预排队 + 异步落库"**，理由是一条业务约束：**截止时间不可协商**。

| 做法 | 在"截止前 30 分钟"这个场景下的表现 |
|---|---|
| 限流排队 | 用户被 429 拒绝，**但他没有别的时间可以改**——这等于业务失败，不是技术降级 |
| 预排队异步落库 | 用户拿到"已受理"凭证，**提交这件事已经成功**，落库只是时间问题 |

> **判据**：**能不能拒绝请求，取决于"用户有没有第二次机会"。** 常规流量高峰（如秒杀）拒绝是合理的——用户下次再来就好；**有硬截止时间的场景，拒绝等于把技术问题转嫁给业务**。这时唯一正确的做法是"先收下，再慢慢处理"。

### 3.2 被否决的方案与否决理由 {#rejected}

| 被否决的方案 | 否决理由 |
|---|---|
| **同步直写 + 数据库垂直扩容** | 峰值是 45 倍均值，按峰值配硬件意味着**98% 的时间在浪费**。而且截止日的峰值连年增长，这是一条没有终点的成本曲线 |
| **前端防重 + 同步直写** | 前端禁用按钮在**刷新页面、多标签页、弱网重发、脚本重放**四种情况下全部失效（见 [5.2 节](#frontend-not-enough)）。把它当防线是**把校验放在了不可信的客户端** |
| **全量走消息队列，提交即返回成功** | 校验也异步化 → 用户会收到"提交成功"，但 5 分钟后被告知"权重之和不等于 100%"。**校验必须同步，落库才异步** |

## 四、提交链路：同步校验 + 异步落库 {#submit-flow}

### 4.1 受理与校验的边界 {#validating}

链路的切分点是**"哪些判断必须在返回成功前完成"**：

```
① 鉴权与幂等令牌校验 ─── 同步（必须）
② 业务规则校验 ───────── 同步（必须）
     权重之和 = 100%、目标数量上限、必填项、时间窗内
③ 受理落库（轻）───────── 同步（写入"受理单"，不是业务表）
④ 业务表写入 ─────────── 异步（消息队列消费）
⑤ 通知与统计更新 ─────── 异步
```

**为什么校验必须同步**：校验失败是**业务失败**，用户需要立刻知道并修改。如果校验异步化，用户会先看到"提交成功"、再看到"校验不通过"，**这在体验上是欺骗**；更糟的是用户可能已经关掉页面走了，等他回来发现没提交上时已经过了截止时间。

### 4.2 异步化的代价与交互设计 {#async-cost}

异步落库换来了容量，代价是**"提交成功"与"数据落库"之间出现了一个窗口**。这个窗口必须用交互补齐：

| 风险 | 用户看到的现象 | 交互设计 |
|---|---|---|
| 受理成功、落库失败 | 界面显示已提交，重进却在"待提交" | **受理单可查**：提交后返回受理号，页面展示"处理中 → 已成功"的状态流转 |
| 用户重复提交 | 生成两张表单 | 受理幂等（见第五节） |
| 用户提前离开、想知道结果 | 无反馈 | 提供"我的提交记录"页，状态可回查；关键节点短信/站内信通知 |

> **一条交互设计纪律**：**异步化的前提是"状态可查"。** 只要用户能随时查到一个明确的最终状态，"已受理"就不是欺骗；反之，如果既异步化、又没有状态查询，那用户永远不知道自己的提交到底算不算数——**这种设计下，用户会反复提交，反过来把洪峰再放大一次。**

## 五、防重复提交：三重防线 {#dedup}

### 5.1 三层防线各管什么 {#three-layers}

| 防线 | 机制 | 能防住 | 防不住 |
|---|---|---|---|
| 第一层：**幂等令牌** | 服务端发放一次性 token，提交时校验并删除（`SET NX`） | 重复点击、页面重发、脚本重放 | token 失效后的重试 |
| 第二层：**唯一索引** | `(周期ID, 员工ID, 表单类型)` 唯一 | 任何绕过令牌的重复写入 | 已存在时如何返回"成功"而非报错 |
| 第三层：**状态机** | 表单状态只能按 `待提交 → 已提交 → 审批中` 单向流转 | 已提交后再提交 | 首次并发提交 |

**三层不是备选，是叠加**——每一层防的是另一层防不住的情况（完整讨论见 [接口幂等](/java/spring/spring-cloud/idempotency#solutions) 的四类方案）。

**唯一索引这一层有个容易忽略的细节**：唯一索引冲突会**抛异常**，而用户视角下"重复提交"应该表现为**成功**（因为他要的效果已经达成了）。所以正确写法是捕获冲突后查询已有记录并**返回成功**，而不是把 500 抛给用户：

```java
try {
    formMapper.insert(form);
    return Result.ok(form.getId());
} catch (DuplicateKeyException e) {
    // 重复提交 = 目标状态已达成 → 对用户而言就是成功
    PrefForm exist = formMapper.selectByUniqueKey(cycleId, empId, formType);
    return Result.ok(exist.getId());
}
```

> **这是"幂等"的语义要点**：**幂等的返回语义是"目标状态已达成"，不是"这次调用成功"。** 前者对用户友好且可重放，后者会让重试变成报错。

### 5.2 为什么前端禁用按钮不算防线 {#frontend-not-enough}

前端防重复提交（点击后置灰、加 loading）只能拦住**同一次页面会话内的重复点击**。以下四种情况全部绕过它：

| 场景 | 前端置灰为什么失效 |
|---|---|
| **刷新页面** | 状态重置，按钮又可点 |
| **多标签页 / 多设备** | 各页面独立，互相不知道 |
| **弱网重发** | 用户以为没成功，手动再点一次；或客户端自动重试 |
| **接口被直接调用** | 前端逻辑根本不参与 |

> **判据**：**任何"只在前端实现"的校验，都只是体验优化，不是防线。** 真正的防线必须在服务端、且不依赖调用方的配合。

## 六、写入热点：先分清"插入热点"与"更新热点" {#hotspot}

这一节是本篇最容易出错、也最值得完整讲清的一段。

### 6.1 一条反直觉结论：随机主键更慢 {#random-pk}

"用自增主键会造成写入热点，所以要用 UUID / 雪花 ID 打散"——**这个说法把方向搞反了**。

| 主键策略 | 插入位置 | 对 B+ 树的影响 | 写入表现 |
|---|---|---|---|
| **自增 / 趋势递增** | 始终在最右侧叶子页追加 | 只在末页分裂，其余页稳定 | **顺序写，最优** |
| **随机（UUID / 纯随机数）** | 每次落在随机叶子页 | 随机页分裂、页填充率下降、脏页分散 | **随机写，更差** |
| **雪花 ID** | 趋势递增（时间戳在高位） | 接近顺序追加 | 好（次优） |

```
自增：  页1[100%] 页2[100%] 页3[100%] 页4[60%] ◀── 只在末页追加
随机：  页1[72%]  页2[68%]  页3[81%]  页4[55%] ◀── 每页都被随机插入，全员低填充
        ↑ 页分裂频繁、缓冲池命中率下降、写放大上升
```

> **结论**：**"打散主键"不是优化写入的手段，而是损害写入的手段。** 唯一真正的"自增争用"是**取下一段 ID 这一步**（在 MySQL 8 上已是轻量锁，影响远小于随机插入的代价）。用随机主键去换那一点点自增锁，是**用小收益换大损失**。

### 6.2 真正的热点是"更新热点"：行锁争用 {#row-lock}

热点不在插入侧，在**更新侧**——**多条并发事务争抢同一行**。填报系统里这类"天然唯一"的计数对象特别多：

| 热点行 | 为什么会被并发争抢 | 后果 |
|---|---|---|
| 本周期的"已提交人数" | 每次提交都 `+1` | 所有提交串行化等待同一把行锁 |
| 审批流实例的"当前序号" | 生成下一个节点序号 | 同上 |
| 批次任务的"处理进度" | 每个任务更新一次进度 | 长事务 + 锁等待 |
| 表单的"版本号" | 每次修改 `+1` | 修改集中在截止日 |

### 6.3 打散手段：按"争用类型"选 {#sharding-hotspot}

| 争用类型 | 打散手段 | 代价 |
|---|---|---|
| **计数类**（提交人数、通过人数） | ① 拆成 N 行（`counter_0..N-1`），写入随机挑一行，**读取时求和**；② 计数放 Redis，定时异步落库 | ① 读变复杂（要聚合）；② 引入最终一致 |
| **序号类**（审批节点序号） | 号段模式（一次取 1,000 个，内存分配） | 需要处理"应用重启后未用完的号段"（允许空洞即可） |
| **状态类**（表单状态） | 用状态机条件更新（`WHERE status = '待提交'`），**让失败者直接返回**，不要 `SELECT` 后再 `UPDATE` | 需要调用方处理"更新失败"的语义 |
| **进度类** | 不实时更新，改为"**定期快照 + 计算**"（如每 30 秒算一次），或只在完成时更新最终状态 | 进度展示不再实时 |

**"先查后改"为什么必须换成"条件更新"**——这是最实用的一条：

```sql
-- ✗ 有竞态：两个事务同时读到"待提交"，都通过检查，都去更新
SELECT status FROM pref_form WHERE id = 1;      -- 返回 待提交
UPDATE pref_form SET status = '已提交' WHERE id = 1;

-- ✓ 条件更新：数据库的行锁把并发变成串行，失败者拿到 0 行受影响
UPDATE pref_form
   SET status = '已提交', submitted_at = NOW()
 WHERE id = 1 AND status = '待提交';
-- affectedRows = 0 → 说明已被别人改过 → 返回"重复提交"
```

> **这一条把"并发控制"从应用层搬回了数据库**：应用层的"查—判断—改"三步在并发下必然有窗口，而条件更新把"判断"和"改"合并成一个原子操作。**凡是能用一条带条件的 `UPDATE` 表达的并发控制，就不要用应用层代码去模拟。**

### 6.4 热点为什么会变成尖峰 {#hotspot-amplify}

行锁争用有一个恶性的放大效应：

```
持锁事务变慢（如因为磁盘 IO）
    → 等待行锁的事务堆积
    → 连接池被占满
    → 其他无关请求也拿不到连接
    → 整站不可用（不是"慢"，是"打不开"）
```

> **所以热点的危害不在"慢"，在"锁等待把连接池吃光后，故障从一行数据扩散到整个应用"。** 这也是压测必须观察**连接池水位**而不只是 TPS 的原因——TPS 看起来还行的时候，连接池可能已经在排队了。

## 七、限流与排队 {#ratelimit}

即使做了削峰，仍需限流作为最后一道闸门。填报期的限流要**同时按三个维度**设：

```
按用户：  单用户 2 TPS（防脚本刷）      → 超限 429 + Retry-After
按接口：  POST 提交   50 TPS           （核心写入，阈值要"真实可达"）
         GET  待办列表 800 QPS         （读多，放宽）
         GET  进度统计 200 QPS         （要聚合，收紧）
按全局：  总上限 1,200 QPS             （保护后端总容量）
```

| 只设一维的后果 | 说明 |
|---|---|
| 只按用户 | 一个部门的 300 人同时提交就能吃掉为全局预留的写入配额 |
| 只按接口 | 无法阻止某个用户的脚本刷接口 |
| 只按全局 | 无法区分"读"和"写"，慢的读把快的写挤掉 |

配置方式与动态刷新见 [网关限流的分层](/java/spring/spring-cloud/gateway#ratelimit)。有一条纪律与 [容量测算](/projects/property-saas/capacity-and-perf/#ratelimit) 相同：

> **限流阈值是"承诺"，不是"猜测"**——对外宣称的承载能力必须建立在压测验证过的数字上。没有压测背书的阈值，只是"一个不会报警的数字"。

## 八、压测数据与容量结论 {#load-test}

### 8.1 压测必须先解决"数据分布" {#data-distribution}

| 坑 | 为什么致命 |
|---|---|
| **用均匀分布压** | 真实场景里热点极其集中：80% 的流量来自 20% 的部门，且集中在少数几个"大部门"上。**均匀分布压不出热点** |
| **数据量不足** | 用 1 万行表单压出的结论，在 18 万行时**索引选择与执行计划都会变** |
| **只压写不压读** | 填报期的读写比是 20:1，**只压写会得出"容量很充足"的错误结论** |
| **只压单接口** | 真实流量是混合的：列表页、详情页、提交、进度统计同时发生 |

**构造压测数据的三条要求**：

1. **按真实组织分布**：人数分布按部门规模的长尾比例生成，不要平均分配
2. **保留热点**：人为让 20% 的部门承担 80% 的提交量
3. **量级到位**：表单总数、历史周期数据都要到接近生产的量级（数据量不足时索引评价全不可信，详见 [慢查询诊断](/database/mysql/diagnosis)）

### 8.2 容量结论（推导值） {#conclusion}

| 指标 | 设计目标 | 推导依据 |
|---|---|---|
| 峰值提交 TPS | 20 TPS（瞬时可到 30） | 见 [2.2 节](#peak-factor)推导；分批放号后集中系数由 ~12 降到 ~5 |
| 峰值查询 QPS | 约 400 | 峰值提交 × 读写比 20:1 |
| 全局限流阈值 | 1,200 QPS | 峰值查询 + 提交 + 30% 余量 |
| 受理单写入延迟 | P99 < 100ms | 单表插入，仅索引维护 |
| 异步落库延迟 | P95 < 3s、P99 < 30s | 队列消费常态 3s 内追平 |
| 单批消费 | 200 条 / 批 | 批量写库摊薄单条开销，同时控制单批事务时长 |

> 以上均为参数区间的组合推导，尚无完整压测背书。

## 九、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标 | 现状 | 验证方式 |
|---|---|---|---|
| 提交链路 | 峰值 20 TPS 下受理 P99 < 100ms | 设计完成 | 混合场景压测（含读流量） |
| 异步落库 | 队列不积压、P95 < 3s | 推导值 | 压测中同屏观察队列深度与消费速率 |
| 削峰收益 | 分批放号把集中系数压到 ~5 | **依赖业务侧配合，尚未落地** | 需要产品与业务共同确认分批方案 |
| 防重三道防线 | 四种绕过场景全部被兜住 | 设计完成 | 人为构造：刷新重发、多标签页、弱网重试、直连接口重放 |
| 热点打散 | 计数行拆 N 行后无锁等待 | 设计完成 | 压测中观察行锁等待与连接池水位 |
| 条件更新 | 并发提交只有一次生效 | 设计完成 | 并发压测同一表单，断言只有一条更新成功 |
| 限流阈值 | 与实测承载能力一致 | **待定** | **阈值必须在压测之后才写进承诺** |

> **必须诚实说明**：本页所有 TPS 都是**推导值区间**，尚无一次混合场景压测为之背书。尤其"分批放号"这一项——它是本篇收益最大的措施，但它**不是一个技术改动，而是需要业务侧同意的流程改动**，因此在设计记录里只能标注为「依赖外部配合」。

## 十、复盘与面试问答 {#interview}

**Q1：为什么不能按"窗口期提交总量 ÷ 窗口期秒数"算峰值？**
因为填报的流量天然集中在窗口期的两端——开放首日和截止前 1~2 天。对同一份总量，按集中系数 5 和 12 算出的峰值差一倍以上。按均值配容量，等于赌"截止日当天没人赶时间"。完整的推导链见 [2.2 节](#peak-factor)。

**Q2：为什么选"预排队 + 异步落库"，而不是"限流 + 让用户重试"？**
因为**这个场景有硬截止时间，用户没有第二次机会**。判据是"能不能拒绝请求"——常规流量高峰（如秒杀）拒绝是合理的，用户下次再来即可；有硬截止时间时，429 等于把技术问题变成业务失败。正确做法是"先收下（受理），再慢慢处理（异步落库）"。

**Q3：既然异步化了，用户在页面上看到的"提交成功"算不算欺骗？**
不算，前提是**状态可查**。异步化的配套是"受理单 + 状态流转可回查"：用户拿到受理号，能随时看到"处理中 → 已成功"。**反过来说，如果既异步化又没有状态查询，那才是欺骗**——而且会造成用户反复提交，把洪峰再放大一次。

**Q4："自增主键会造成写入热点，所以要用 UUID 打散"——这句话对吗？**
反了。自增主键是**顺序插入**，只在最右侧叶子页追加，页分裂少、缓冲池命中高；UUID 是**随机插入**，每次落在随机页，导致频繁页分裂、页填充率下降、写放大上升。**"打散主键"损害写入，不是优化写入。** 唯一真正的自增争用是"取下一段 ID"，MySQL 8 上已是很轻的锁，用随机插入去换它不划算。

**Q5：那填报系统里真正需要打散的热点是什么？**
**更新热点**——多条事务争抢同一行。填报系统里天然的"唯一计数对象"特别多：本周期已提交人数、审批实例序号、批次进度。这些是行锁争用的来源，而且会恶性放大：**持锁事务变慢 → 锁等待堆积 → 连接池被占满 → 整站不可用**（从"慢"变成"打不开"）。打散手段按类型选：计数拆 N 行读时求和、序号用号段、状态用条件更新。

**Q6：为什么"先查状态再更新"必须换成"带条件的 UPDATE"？**
因为应用层的"查—判断—改"三步在并发下**必然有窗口**：两个事务可能同时读到"待提交"，都通过检查。带条件的 `UPDATE ... WHERE status = '待提交'` 把判断和修改合并成一次原子操作，由数据库的行锁保证只有一个成功，另一个拿到 0 行受影响。**凡是能用一条带条件 UPDATE 表达的并发控制，都不要用应用层代码模拟。**

**Q7：压测时最容易自欺的一点是什么？**
**数据分布**。用均匀分布压，永远压不出热点——而真实场景里 20% 的部门承担 80% 的流量。其次容易被忽略的是**只压写不压读**：填报期读写比约 20:1，只压写会得出"容量很充足"的错误结论，上线后是列表页把数据库打挂的。
