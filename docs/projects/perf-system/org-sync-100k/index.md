# 十万人组织架构同步

> **口径说明**：本文是架构设计记录，不是生产运行报告。文中的节点数、耗时、事件量都是**按参数区间推导的设计目标**，标注为「推导值」；全文已脱敏，不含企业标识、真实组织名称与内部代号。
>
> **一个先要澄清的口径**：系统覆盖约 6 万人，但本篇按「十万人组织架构」设计。原因在第 1.1 节——**组织树的节点不等于人头**。

## 一、背景：难的不是搬数据，是"冻口径" {#background}

组织架构同步在很多人眼里是"把一张表从 A 系统搬到 B 系统"，属于纯工程活。但真正让这个模块反复出事的是另一件事：**绩效系统需要的不是"最新的组织架构"，而是"某个时刻的组织架构快照"。**

### 1.1 三条约束 {#constraints}

| 约束 | 具体含义 | 违反的后果 |
|---|---|---|
| **口径一致性** | 绩效周期一旦启动，考核范围必须冻结 | 月初算出的"某人的考核单元"与月末审批时的汇报线不一致 → **审批流走错人** |
| **量级** | 组织树节点按 10 万量级设计 | 一次全量同步不能"一把梭"，必须分批 |
| **可对账** | 同步失败不能静默 | 少了 3 个部门没人知道，直到有人问"我的下属怎么不在名单里" |

**为什么节点数是 10 万而人员是 6 万**——组织树的节点不只包含人：

| 节点类型 | 数量级（推导值） | 说明 |
|---|---|---|
| 部门 / 组织单元 | 约 8 千 | 实际有层级关系的管理单元 |
| 岗位 / 职级节点 | 约 2 万 | 岗位也挂在树上，参与"考核单元"计算 |
| 人员节点 | 约 6 万 | 在职 + 待入职 |
| 虚拟组织 | 约 5 千 | 项目组、临时委员会——**汇报关系与行政线不同** |
| 历史版本快照 | 按版本数放大 | 考核期需要回看"当时"的组织结构 |
| 预留增长（3 年） | — | 集团扩张与并购带来的新增 |

> **这张表本身就是一条面试答案**：被问"你们组织架构多大"时，回答"6 万人"会让面试官以为只是人员表；回答"10 万节点，因为部门、岗位、虚拟组织和历史快照都在同一棵树上"，才说明你**真的碰过这个数据模型**。

### 1.2 为什么"同步"必须是两条链路 {#two-links}

单条链路必然缺一样东西：

| 只有…… | 缺什么 | 具体怎么出事 |
|---|---|---|
| 只有增量 | **没有归零点** | 漏一个事件、乱序一次，错误就**永久留在**目标库里。而且漂移是累积的——今天少 1 个节点，三个月后少 200 个 |
| 只有全量 | **实时性不够** | HR 上午改了部门，绩效系统要到明天才看到。组织调整期"改了不生效"会被反复投诉 |

所以本方案是**全量 + 增量并存**，两者分工明确：

```
        HR 主数据平台（唯一权威源）
                 │
        ┌────────┴────────┐
        │                 │
   增量链路            全量链路
   （事件驱动）        （定时 T + 影子表切换）
   延迟 < 1 分钟        周期 1 天 / 组织调整期临时触发
        │                 │
        ▼                 ▼
   实时性与时效          纠偏与归零
        └────────┬────────┘
                 ▼
        绩效系统组织树（含版本）
```

**分工的判据**：**增量的职责是"快"，全量的职责是"对"。** 让增量承担正确性责任是设计错误——它做不到，因为它的输入本身可能缺失。

## 二、方案对比：选型被组织边界决定 {#selection}

### 2.1 四种同步方式 {#four-ways}

| 方式 | 实时性 | 对源端侵入 | 顺序保障 | 成本 | 适用前提 |
|---|---|---|---|---|---|
| 定时全量 | 小时 / 天级 | 无（只需只读接口） | 天然（快照） | 低 | 兜底纠偏 |
| **全量 + 增量** | 分钟级 | 无 | 需增量侧自行处理 | 中 | **本方案** |
| CDC（订阅 binlog） | 秒级 | 无侵入 | 天然（binlog 本身有序） | 中高 | **源端是自家库，且 DBA 允许第三方订阅** |
| 事件订阅（源端推送） | 秒级 | **需源端改造** | 依赖源端实现 | 中 | 源端有开放平台且愿意配合 |

**本方案选择了"全量 + 增量"**，不是因为它在技术上最优，而是因为一条外部约束：

> **HR 主数据平台是集团统一建设的系统，对绩效系统而言是一个"外部系统"**——它只暴露接口，不暴露数据库。

这一条把 CDC 直接排除掉了。**这是"技术选型被组织边界决定"的典型案例**：同一个问题，如果 HR 系统是自家团队建的，答案应该是 CDC（binlog 天然有序、无侵入、秒级）；但它是别人的系统，CDC 就不是一个可选项，而是"一个需要跨三个团队协调、而且大概率被 DBA 否决的方案"。

### 2.2 被否决的方案与否决理由 {#rejected}

| 被否决的方案 | 否决理由 |
|---|---|
| **纯 CDC** | 拿不到 binlog。**不是技术不行，是边界不允许**——需要 HR 团队开放数据库权限、DBA 同意第三方订阅、还要处理 HR 库的 DDL 变更通知。三项都要跨团队 |
| **纯增量（不要全量）** | 增量会漂移且不可自愈。**没有归零点的同步，等于把数据正确性押在"上游从不漏发"上** |
| **实时查 HR 接口（不落地）** | 看似最省事：每次都问源端。但绩效系统的**考核范围计算是高频读**——打开填报页、算一次考核单元就要算一次。把高频读绑在外部接口上，等于把"绩效系统能不能打开"这件事交给另一个团队的可用性。**判据不是数据新鲜度，而是"能不能自主掌控可用性"** |
| **双写（HR 和绩效各写一份）** | 跨团队双写没有原子性：HR 写成功、绩效写失败 → 两边长期不一致，且**没有任何一方知道** |

### 2.3 树形存储：四种模型怎么选 {#tree-models}

| 模型 | 表示 | 查子树 | 查祖先链 | 移动子树 | 写放大 |
|---|---|---|---|---|---|
| **邻接表** | `parent_id` 一个指针 | 递归，代价随深度增长 | 递归 | 改 1 行 | 无 |
| 路径枚举 | `path = '1/3/7'` | `LIKE '1/3/%'` | 字符串切分 | **改整棵子树** | 高 |
| 嵌套集 | `lft` / `rgt` 左右值 | `BETWEEN`，一次查出 | 包含关系判断 | **改大半张表** | 极高 |
| **闭包表** | 独立关系表 `(ancestor, descendant, depth)` | 一次等值 JOIN | 一次等值 JOIN | 增删 `O(深度)` 行 | 中 |

**结论：邻接表做权威存储 + 闭包表做查询加速。** 判断依据是读写模式：

- **读模式**：以「某个节点及其所有下级的集合」为主——考核范围计算的本质就是这个集合。闭包表把"递归下探"变成一次 `WHERE ancestor = ?` 的等值 JOIN，**从"深度依赖"变成"索引依赖"**。
- **写模式**：以"少量节点的父子关系变更"为主，且组织树的深度通常 ≤ 6。闭包表的写放大是 `O(深度)` = 常数级，可以接受。

被否决的两个各有明确的死因：

| 被否决 | 死因 |
|---|---|
| 路径枚举 | **子树移动要改整棵子树**。而组织调整恰恰是"整块搬迁"——把 200 人的部门挂到另一个中心下，路径枚举要改 200 行。组织调整期就是写入尖峰期，两件事撞在一起 |
| 嵌套集 | **任何一次插入都要改大半张表**（插入点右侧所有节点的 `lft`/`rgt` 都要 +2）。与"组织调整集中在年末"的写入尖峰正面冲突，且并发写会大面积锁表 |

## 三、全量链路：影子表 + 原子切换 {#full-sync}

### 3.1 为什么不能"先删后写" {#shadow-table}

全量同步最容易踩的坑是按直觉写成"清空目标表 → 逐批写入"。这会留下一个**非原子的中间态窗口**：

```
时间轴 ─────────────────────────────────────────────▶
清空 ──┬─写第1批─┬─写第2批─┬─ ... ─┬─写第64批─┬─ 完成
       │         │         │        │          │
       └─────────┴─────────┴────────┴──────────┘
              这整段时间里，读到的是"半棵树"
              ↑ 此时有人打开填报页 → 考核范围算出错
```

正确做法是**影子表 + 一次原子切换**：

```
① 分批拉取源端全量 ──▶ org_node_shadow（影子表）
② 在影子表上跑四项树形校验（第五节）
③ 校验通过 ──▶ 【一次事务】切换生效指针
                 ├─ 旧表重命名为 org_node_old_<ts>
                 └─ 影子表改名为 org_node
④ 延迟删除 org_node_old_<ts>（保留一个周期用于回滚）
```

**为什么不是"标记删除 + 增量覆盖"**：判断"哪些节点应该被删"需要先把源端全量与目标端做 diff，而 diff 的结论与"直接切换"完全等价——但过程多了两步（算 diff、按 diff 打删除标记），且**中途状态依然非原子**：删了一批、还没删第二批时，读到的仍是不一致的树。**用更复杂的写法得到更差的原子性，是纯粹的亏本买卖。**

### 3.2 全量的幂等：可重放 {#full-idempotency}

全量本身是幂等的（快照覆盖写，跑两遍结果相同），但**"切换"这一步不是**——如果没有保护，同一批次跑两次会切换两次，第二次会把第一轮的旧表覆盖成"已切换"状态。

做法是用**同步批次号做乐观锁**：

```sql
-- 只有批次号比当前生效版本更新时才允许切换
UPDATE org_sync_meta
   SET active_batch = :newBatch, prev_batch = active_batch
 WHERE id = 1 AND active_batch < :newBatch;
-- 受影响行数 = 0 说明这一批已经切过（或来了一个更旧的批次）→ 直接跳过
```

> **一条通用规律**：**幂等不是"操作本身的属性"，而是"操作 + 判据"的属性。** 覆盖写幂等的前提是"同一个输入"；一旦引入"当前状态"（哪个批次生效），就必须显式比较版本。

## 四、增量链路：版本号同时解决两件事 {#incremental}

### 4.1 事件模型与顺序 {#event-order}

四类事件：

| 事件 | 载荷要求 |
|---|---|
| `OrgNodeCreated` | 节点全字段 |
| `OrgNodeUpdated` | 变更后的**关键字段快照**（不传"变更了哪个字段"的差量） |
| `OrgNodeMoved` | **必须携带变更后的完整祖先路径**，不能只给新的 `parent_id` |
| `OrgNodeDeleted` | 节点 ID + 删除版本 |

`Moved` 事件为什么要带完整路径——这是乱序场景下的关键：

```
消费端收到 Moved(nodeId=7, parentId=3)
  ├─ 如果只给 parentId：无法判断这个 parentId 是"哪个版本的 3"
  │   → 若本地 3 已被删除/移动，这次移动是否该应用？无从判断
  └─ 带完整路径 "1/3/7"：
      → 本地树里 1 是否存在？3 是否挂在 1 下？都能验证
      → 验证通过才应用，否则进待定队列
```

**分区与顺序**：按节点 ID 哈希分区（`nodeId % N`），保证**同一节点的事件严格有序**；跨节点无序——而跨节点无序在树形结构里是可容忍的，因为节点之间只通过 `parent_id` 关联，而关联的校验由"父存在性检查"兜住。

**引用完整性：父事件必须先到。** 解法不是"等一会重试"，而是**待定队列**：

```
收到事件 → 校验引用的父节点是否存在
   ├─ 存在 → 正常应用
   └─ 不存在 → 不丢弃、不进死信，进「待定队列」
              （记录：我等的是哪个 parentId）
                     │
        父节点事件到达时 → 从待定队列捞出依赖它的节点，重放
```

> **待定队列 vs 直接重试的区别**：重试是"过一会再来问一次"，在父事件迟迟不到时会耗尽重试次数、把事件推进死信；待定队列是**事件驱动**的——它不消耗重试预算，也不会误判为失败。**这类"依赖未就绪"的问题，用事件驱动比用时间驱动更可靠。**

### 4.2 增量的幂等：版本号一箭双雕 {#inc-idempotency}

每个事件携带源端的 `version`（行版本号，或"时间戳 + 单调序号"）。消费端只做一件事：

```sql
UPDATE org_node
   SET name = :name, parent_id = :parentId, /* ... */ version = :version
 WHERE id = :id AND version < :version;
```

这一条件同时解决两个问题：

| 问题 | 为什么这个条件能解决 |
|---|---|
| **重复投递**（同一事件收到两次） | 第二次 `version < :version` 不成立 → 0 行受影响，天然去重 |
| **旧事件覆盖新状态**（乱序） | 迟到的旧事件版本更小 → 同样不成立，不会把新状态改回旧值 |

> **这是本篇最值钱的一个设计**：很多人把"去重"和"防乱序"当成两个机制来做（一个去重表 + 一个顺序队列），但**只要事件带单调版本号，"版本更大才写"这一个条件就同时覆盖了两者**。代价是要求源端提供单调版本——而这正好是行级 `update_time` 或 `row_version` 能满足的。

## 五、树形校验：四项必查 {#tree-validation}

全量切换前必须全查，增量按批次查增量部分。

| 校验 | 检查什么 | 不做的后果 |
|---|---|---|
| **环检测** | 沿 `parent_id` 链上溯，能否回到自身 | 递归计算考核范围时**死循环**（不是报错，是挂死） |
| **孤儿节点** | `parent_id` 指向不存在的节点 | 节点不可达 → **考核范围漏人**，且从界面上看不出异常 |
| **深度上限** | 层级是否超过约定上限（如 20） | 递归爆栈；报表层级维度溢出 |
| **父子状态矛盾** | 子节点启用、父节点停用 | 停用部门下挂着启用员工 → **考核范围口径分裂**（算不算这个人？） |

**环检测的实现细节**：不要逐节点上溯判断（那是 `O(n × 深度)`，10 万节点 × 平均 6 层 = 60 万次查询）。正确做法是**一次遍历染色**：

```
遍历所有节点，对每个未访问节点沿 parent 链上溯并标记颜色
  ├─ 遇到"本次路径上已标记"的节点 → 发现环
  ├─ 遇到"历史遍历中已确认无环"的节点 → 提前终止（剪枝）
  └─ 遇到不存在的 parent → 孤儿

复杂度 O(n)，且天然给出所有环的成员
```

> 这类"树上的全局校验"有个共同特征：**逐点做是 O(n·深度)，一次遍历是 O(n)**。10 万节点时前者要几十秒甚至分钟级，后者是亚秒级——差别不在常数，在数量级。

## 六、一致性对账：三道闸门与一条纪律 {#reconciliation}

### 6.1 三档对账：成本与精度递增 {#three-checks}

| 层次 | 对什么 | 能发现什么 | 代价 |
|---|---|---|---|
| **数量对账** | 各状态节点计数（启用 / 停用 / 已删除） | 大批量丢失或多余 | 极低（两次 `count`） |
| **摘要对账** | 节点 ID 集合的**分片哈希** | 单点丢失 / 多余，且能定位到分片 | 低（一次全量 ID 比对） |
| **字段对账** | 抽样比对 `name` / `parent_id` / `status` | 字段级漂移（ID 都在，内容不对） | 高（需逐字段取数） |

**分片哈希是对账里最实用的一招**：把 ID 空间按范围切成 64 桶，两边各自算每桶的哈希值，只上报"第几桶不一致"。排查范围立刻从"10 万条里找差异"变成"在 1600 条里找差异"——**把 O(n) 的排查压成 O(n/64)**。

**为什么必须分三档**：只有数量对账，会漏掉"少 1 个、多 1 个"的抵消情况；只有字段对账，成本高到没人会每天跑。三档的配合是：**每天跑数量 + 摘要（便宜），差异出现时才对该分片做字段级深挖**。

### 6.2 差异处理：以谁为准，以及一条纪律 {#diff-handling}

**权威源唯一**：HR 主数据平台是唯一权威源（single source of truth）。**差异一律以源端为准，消费端永不反向修正**——一旦允许双向，就出现了两个真相源，冲突无处仲裁。

| 差异形态 | 判断 | 处理 |
|---|---|---|
| **一次性差异**（出现一次，补偿后不再复现） | 偶发：网络抖动、事件丢失、切换竞态 | **补偿**：按差异 ID 集合单点拉取源端最新值 |
| **重复性差异**（同一位置反复出现） | 系统性：消费端有 bug，或源端口径与消费端理解不一致 | **报警**，不许用补偿掩盖 |

> **这是本篇的第二条运营纪律，也是面试里最能区分人的一句**：
>
> **补偿只能用于"偶发"，不能用于"系统性"。** 如果对账每天都报同一批差异、而每次都用补偿抹平，那么补偿机制就变成了"把 bug 藏起来的工具"——**指标是绿的，问题一直在，而且再也没人会去看它。** 正确做法是：**同一位置连续 N 次（如 3 次）出现差异 → 升级为故障，停止补偿，转人工分析。**

## 七、失败重试与幂等 {#retry-idempotency}

### 7.1 重试的四个前提 {#retry-preconditions}

重试不是"失败了再来一次"这么简单，它需要四个前提同时成立（方法级重试的完整讨论见 [方法级重试与并发限制](/java/spring/spring-framework/crosscutting/resilience#preconditions)）：

| 前提 | 本方案怎么满足 |
|---|---|
| **幂等** | 全量靠批次号乐观锁；增量靠 `version <` 条件更新 |
| **错误可判定** | 网络超时、5xx、限流 → 可重试；4xx 业务错误（如"节点不存在"）→ **不重试**，直接进死信 |
| **退避 + 抖动** | 指数退避 + 随机抖动。**不加抖动只是把洪峰整体推后**——上游一起失败、一起重试，等于人为制造一次尖峰 |
| **上限 + 死信** | 重试次数上限（如 5 次）后进死信，不允许无限重试 |

### 7.2 死信必须可重放 {#dead-letter}

死信表不是垃圾桶，它需要三样东西才能被称为"机制"而不是"堆积"：

1. **可重放入口**：运维侧能按批次/时间范围一键重放
2. **原因分类**：区分"上游数据问题（要上游改）"和"我们自己的问题（改完可重放）"
3. **告警与定期清理**：死信量超阈值告警；已处理且过期的记录定期归档

> **判据**：**一个不可重放的死信表，和一个删除操作没有区别**——只是把"丢弃"换成了"占存储"。

## 九、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标 | 现状 | 验证方式 |
|---|---|---|---|
| 全量原子切换 | 切换期间读不到"半棵树" | 设计完成 | 切换过程中并发读，校验结果集合的一致性 |
| 全量耗时 | 10 万节点 < 10 分钟 | **推导值** | 用源端全量真实数据跑一次，记录分批与切换各段耗时 |
| 增量幂等 | 重复投递与乱序均不产生副作用 | 设计完成（`version <` 条件） | **人为注入**重复事件与逆序事件，比对最终状态 |
| 待定队列 | 父事件迟到时子节点不丢失 | 设计完成 | 构造"子先到、父后到"的事件序列 |
| 环检测 | 10 万节点亚秒级 | 推导值（`O(n)` 遍历） | 构造含环的测试数据实测 |
| 对账纪律 | 同一位置连续 3 次差异升级为故障 | **流程约定，尚未跑过完整周期** | 需至少一个完整同步周期观察误报率 |
| 增量延迟 | P95 < 1 分钟 | 推导值 | 生产埋点：事件产生时间 → 落库完成时间 |

> **必须诚实说明的一点**：本页的耗时与容量数字**全部是推导值**，尚无一次规模接近真实的演练为之背书。这类模块的风险不在"设计错"，而在"**规模没到之前，所有断言都只是假设**"——索引选择、分批粒度、锁竞争，只有真跑过才知道。把它变成证据的方法见 [压测报告](/projects/toolkit/perf-report/) 的 8 个要素。

## 十、复盘与面试问答 {#interview}

**Q1：为什么不直接实时查 HR 系统的接口，非要落地一份？**
因为**读的频率与可用性责任不对等**。绩效系统算一次考核范围要读一次组织树，是高频读；而 HR 系统是另一个团队维护的外部系统。落地一份，等于把"绩效系统能不能打开"这件事从别人的可用性里摘出来。**这里的判据不是"数据新不新鲜"，而是"我能不能自主掌控"**——差一分钟的延迟可以接受，被别人拖挂不可接受。

**Q2：全量同步为什么用影子表切换，而不是"标记删除 + 增量覆盖"？**
两者得到的最终状态一样，但原子性完全不同。标记删除需要先算 diff、再按 diff 打标记，中途状态**依然是不一致的树**（删了一批还没删第二批）。影子表把"不一致"关在影子表里，对外只在一次事务的瞬间切换——**用更简单的写法拿到更强的原子性，没有理由选复杂的那个**。

**Q3：树形结构为什么选邻接表 + 闭包表，而不是路径枚举或嵌套集？**
回到读写模式：组织树的读以「某节点及全部下级」为主，闭包表把递归变成一次等值 JOIN；写以"少量父子关系变更"为主，闭包表的写放大是 `O(深度)`，而深度 ≤ 6，可接受。路径枚举死在"子树移动要改整棵子树"，嵌套集死在"插入要改大半张表"——**而组织调整期正好是写入尖峰，这两个缺陷会集中在最不该出事的时候暴露**。

**Q4：增量同步收到一个事件的父节点还没到，怎么处理？**
不丢弃，也不进死信，进**待定队列**，并记录"它在等哪个 `parentId`"；父节点事件到达时把它捞出来重放。区别在于：**直接重试是时间驱动**（过一会再问一次），父事件迟迟不到会耗尽重试次数、误判为失败；**待定队列是事件驱动**，不消耗重试预算，也不会误报。树形结构天然存在"父先子后"的依赖，这类问题的正确解法是排队等待而不是重试。

**Q5：对账发现有差异，为什么有时候要报警而不是补偿？**
因为差异要分**偶发**和**系统性**两类。一次性差异（网络抖动、事件丢失）用补偿是对的；但同一位置反复出现差异，说明是消费端 bug 或双方口径不一致——**这时候补偿只是在抹平症状**。持续补偿的危险在于：**监控是绿的，问题一直在**，而且从此再没人会去看它。所以纪律是：**同一位置连续 N 次差异 → 升级为故障，停止补偿，转人工分析。**

**Q6：全量同步跑两遍会有问题吗？**
全量写入本身幂等（同样的快照覆盖两次，结果相同），但"切换"这一步不是——所以用**批次号做乐观锁**（`WHERE active_batch < :newBatch`），受影响行数为 0 就跳过。**这引出一条通用规律：幂等不是操作本身的属性，而是"操作 + 判据"的属性**——一旦引入"当前状态"，就必须显式比较版本。
