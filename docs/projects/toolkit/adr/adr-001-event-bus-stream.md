# ADR-001：服务间异步事件用 Redis Stream，不引入独立消息中间件

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 Accepted |
| 日期 | 2026-09-10 |
| 决策人 | 架构 / 后端（1 人） |
| 关联 | 操作日志模块、租户配置中心、缓存失效广播 |

## 1. 背景与约束

自建微服务脚手架走到「服务间异步解耦」这一步，出现三类跨服务的低频事件：**操作日志落库**（各服务拦截写操作后异步汇总）、**租户配置变更通知**（通知已缓存配置的服务失效）、**缓存失效广播**（数据字典、权限规则变更后广播给所有实例）。

量级预估**日均几千条**，要求**可靠投递**（操作日志丢一条，审计链就断）、允许秒级延迟。硬约束有三条：① 开发者 **1 人**，无专职运维，每多一个要独立部署/监控/排障的组件就多一份长期认知负债；② 栈内**已有一个 Redis 实例**，本地与 CI 都靠它；③ 工期紧，中间件选型**不能占用主线时间** —— 这个阶段的目标是业务骨架跑通。

## 2. 备选方案

### 方案 A：RocketMQ
- 思路：引入标准消息中间件，NameServer + Broker 双组件部署。
- 优点：事务消息、顺序消息、死信队列、堆积能力强，是"标准答案"，面试与业界认知度最高。
- 缺点 / 代价：需额外部署与监控两个组件；本地开发链路变重；排障要懂其存储模型与刷盘策略。能力上限比本项目需求高**两个数量级**。
- 适配条件：事件量达到百万级/天，或需要事务消息、严格顺序消费的场景。

### 方案 B：RabbitMQ
- 思路：引入成熟 AMQP 中间件，用交换机 + 队列做路由。
- 优点：模型清晰、路由灵活、社区成熟、有管理台。
- 缺点 / 代价：仍需独立容器与 vhost / exchange / queue 规划；延迟消息要额外插件；运维面同样要人管。
- 适配条件：需要复杂路由（topic / header 分发）、多语言消费者共存。

### 方案 C：Kafka
- 思路：引入高吞吐分布式日志系统。
- 优点：吞吐与生态最强，天然支持多消费组回放，适合流式数据管道。
- 缺点 / 代价：分区 / 副本 / 消费者组语义重，运维与调优成本最高；低频业务事件与它的强项（高吞吐流数据）严重错配。
- 适配条件：日均千万级事件、需要与大数据管道对接（如 Canal → Kafka → 数仓）。

### 方案 D：Redis Stream（栈内已有 Redis）
- 思路：用 Redis 5+ 原生 Stream 类型（`XADD` / `XREADGROUP` / `XACK`）承载事件总线，在上层封装与实现无关的接口，把 Redis Stream 当作**可替换的实现细节**。
- 优点：**零新增部署组件**；原生消费组支持多实例轮询分摊；`XPENDING` 可查未确认消息、`XAUTOCLAIM` 可接管故障实例的积压，从而获得"至少一次"语义；消息 ID 自带时间戳，天然可回溯。
- 缺点 / 代价：无原生死信队列，需自行实现"重试 N 次后转 DLQ"；消息不自动清理，必须配 `XTRIM` 或定时裁剪，否则持续吃内存；不具备事务消息与顺序消息语义；与业务缓存**共用同一实例**时存在内存争用风险。
- 适配条件：事件量中小、要求可靠不丢、能接受秒级延迟，且团队运维人力有限。

### 方案 E：数据库表轮询
- 思路：事件写本地事件表，消费者定时轮询状态机。
- 优点：零新概念、可读可查、与业务事务天然同库。
- 缺点 / 代价：有轮询延迟与空转压力；"已读未确认"状态机要自己维护；高频轮询污染主库。
- 适配条件：事件量极低（日均百条级）、对延迟不敏感。

## 3. 决策

**选方案 D。** 核心依据一句话：当能力需求远低于所有候选的下限时，**决定因素就不再是能力上限，而是谁引入的长期认知成本最低** —— 而 Redis 已经在这个技术栈里，学习成本早就付过了。

| 对比维度 | A. RocketMQ | B. RabbitMQ | C. Kafka | **D. Redis Stream** | E. DB 轮询 |
|---|---|---|---|---|---|
| 实现成本 | 高（双组件部署） | 中（容器 + vhost 规划） | 高 | **零新增** | 最低 |
| 运维复杂度 | 高 | 中 | 最高 | **低（复用现有）** | 低但污染主库 |
| 扩展性 / 上限 | 百万~千万级 | 十万级 | 千万级 | **万~十万级** | 百条级 |
| 可靠投递 | ✅ 强 | ✅ 强 | ✅ 强 | **✅ 消费组 + ack** | ⚠️ 需自维护 |
| 对「1 人 + 工期紧」的适配 | ❌ 差 | ❌ 差 | ❌ 差 | **✅ 好** | ⚠️ 延迟不可控 |

## 4. 否决理由

- **否决 A（RocketMQ）**：为日均几千条事件承担 NameServer + Broker 的部署、监控与排障成本，**能力超出需求两个数量级**，属于为 0.1% 的用量付 100% 的运维成本。（估算，待验证 —— 需压测确认事件量级）
- **否决 B（RabbitMQ）**：本项目消费者只有内部几个服务、路由规则简单，用不上它的路由灵活性；而延迟消息等想要的特性还要额外插件，净增运维面。约束不足，先不引入。
- **否决 C（Kafka）**：用例错配 —— 它是高吞吐流式管道，我们是低频业务事件；分区与副本语义带来的认知成本无法被收益覆盖。
- **否决 E（DB 轮询）**：轮询延迟与空转压力不可控，且会把事件表的读写压力叠到主库上；审计日志对主库的额外负担不可接受。

**注**：A/B/C 三个方案并非"错"，而是**为当前约束下的过度设计**。它们的适配条件已写在各方案内，一旦触发即按第 5 节重审。

## 5. 后果与风险

- **收益**：零新增部署组件，本地 `docker run redis` 一条命令即通全链路，CI 无需额外编排；消费组天然支持多实例扩展与轮询分摊；`XPENDING` 让"有没有消息卡住"变成可查询指标，可观测性不靠猜。
- **引入的新问题 / 技术债**：
  - 需自研**死信队列**（重试计数 + 超限转 `xxx:dlq` Stream），否则一条毒消息会被无限重投；
  - 需自定**消息清理策略**（`MAXLEN ~ N` 或按保留时间裁剪），否则内存持续增长；
  - 需处理**至少一次语义下的重复消费**（每条事件带业务幂等键）；
  - **与业务缓存共用 Redis 实例**：若 `maxmemory-policy` 设为 `allkeys-lru`，极端情况下事件可能被当作缓存淘汰 —— 这是当前最大的隐性风险，需靠独立 DB 或独立实例隔离。
- **触发重审的条件（Revisit when）**：
  1. 日均事件量持续超过 **50 万条**，或出现消费者长期追不上生产的堆积；
  2. 单条事件体积超过 **1 MB**；
  3. 出现**事务消息 / 延迟消息 / 严格顺序消费**的硬需求；
  4. Redis 因事件堆积触发过淘汰，或内存水位频繁触及上限；
  5. 团队扩充到有专人维护中间件，运维成本的边际压力消失。
