# ADR-004：审批通道推拉结合；推送只传信号，状态永远靠拉取

## 1. 背景与约束

多级审批依赖下级先提交。审批人经常不在 PC 前。列表需要已读回执和批量已处理（客户端→服务端）。客户端会断、会多端、会离线数天。设计目标量级约 6 万人、略大于 1 的端倍数（估算，待验证）。

长连接会让服务端重新有状态（连接表）。这是推送的真实代价，不是协议选择的边角。

## 2. 备选方案

### 方案 A：纯短轮询
- 思路：客户端每隔几秒问有无新待办。
- 优点：无状态，网关友好。
- 缺点 / 代价：万人 × 端 × 轮询频率 = 大量空转 QPS，要为一堆无新消息的请求扩集群。（估算，待验证）
- 适配条件：人数少，或实时性要求松到分钟级以上。

### 方案 B：纯长轮询
- 思路：请求挂到有事件或超时。
- 优点：比短轮询实时。
- 缺点 / 代价：挂起连接数与长连接同量级，还多协议开销与超时边界。
- 适配条件：连接数很小。

### 方案 C：SSE 单向推
- 思路：纯 HTTP 服务端推送，自带重连。
- 优点：实现轻，单向场景几乎是默认解。
- 缺点 / 代价：没有客户端→服务端通道；已读、批量已处理要再开一路 HTTP，两套协议。
- 适配条件：只推、不收回执。

### 方案 D：只靠 APNs / 厂商推送
- 思路：操作系统通道。
- 优点：移动端省电、系统级。
- 缺点 / 代价：PC 浏览器不在这通道上；到达率与延迟不可控（限流、关通知、离线）。SLA 交给第三方。
- 适配条件：只做移动端弱提示，不承担审批正确性。

### 方案 E：WebSocket（前台）+ 厂商推送（移动后台）+ 短轮询降级；推送只带信号（本方案）
- 思路：实时用推；待办列表、未读数、状态机**永远 HTTP 拉**。本地消息表保证「库写成功 ⇒ 信号发出」。实例状态由节点状态推导，不双写。
- 优点：丢一条推送只变成「晚几秒看到」，不会让客户端状态永久错且自己不知道。
- 缺点 / 代价：要维护连接表、心跳、多端、降级；至少一次投递下业务必须幂等。
- 适配条件：既要实时感知，又要已读等上行，且不能把 SLA 押给厂商。

## 3. 决策

**选 E。** 实时和可靠拆开：推管时延，拉管正确。否决「推送即状态」比否决某一条协议更重要。

## 4. 否决理由

- **否决 A**：空转 QPS 随人数线性膨胀，成本长在「什么都没发生」的请求上。（估算，待验证）
- **否决 B**：资源代价接近长连接，语义更差。
- **否决 C**：缺上行。硬凑第二路 HTTP 比直接双向通道更复杂。
- **否决 D**：覆盖不全，到达率不可控。
- **否决「推送体带待办和未读数」**：尽力而为的通道累积精确状态，误差不能自愈。未读数尤其不能「收到一条 +1」。

## 5. 后果与风险

- **收益**：通道故障从数据错误降级为延迟感知；离线补状态不补过程。
- **引入的新问题**：网关必须支持 Upgrade；连接水平扩展要粘滞或共享连接登记；降级短轮询的频率要单独限流，避免降级日打出 A 的空转。
- **触发重审**：已读回执取消、通道退回单向，可重评 SSE；人数降到短轮询成本可忽略；或连接表成为比审批本身更大的故障源。
