# ADR-002：组织架构同步用全量 + 增量双链路，不订阅 HR 的 binlog

## 1. 背景与约束

绩效系统的组织树、汇报线、考核单元以集团 HR 为主数据。考核周期一旦开始，口径必须冻住：周期内组织调整不能让审批流走错人。打开填报页、计算考核范围是高频读。

硬约束：HR 是**外部系统**，只暴露接口，不暴露数据库。跨团队要 binlog 权限，通常过不了 DBA。绩效必须在 HR 不可用时仍能打开填报。

## 2. 备选方案

### 方案 A：CDC 订阅 HR binlog
- 思路：读变更日志，秒级、天然有序、对源端无侵入。
- 优点：技术上通常最优。
- 缺点 / 代价：要 HR 开放库、DBA 同意第三方订阅、处理对方 DDL。
- 适配条件：源端是自家库，且允许订阅。

### 方案 B：纯增量（源端推事件或拉变更接口，不要全量）
- 思路：只消费变更，省全量成本。
- 优点：快、省。
- 缺点 / 代价：漏发不可自愈；正确性押在「上游从不漏」。
- 适配条件：源端有强保证的事件总线，且你能对账。

### 方案 C：不落地，每次实时查 HR
- 思路：绩效不存组织，用时问源端。
- 优点：无同步、永远新鲜。
- 缺点 / 代价：高频读绑在对方可用性上；考核范围算不出来时填报打不开。
- 适配条件：读很少，且可以接受源端挂了自己也挂。

### 方案 D：两边双写
- 思路：HR 写自己库时同步写绩效。
- 优点：看起来实时。
- 缺点 / 代价：跨团队无原子性；一边成功一边失败长期不一致，且没人知道。
- 适配条件：几乎没有。同进程同事务才谈双写。

### 方案 E：定时全量 + 增量接口（本方案）
- 思路：增量管快（分钟级），全量管对（影子表切到新树）；权威存邻接表，闭包表加速「某节点全体下级」。
- 优点：不碰对方的库；有归零点；高频读走自己的库。
- 缺点 / 代价：增量要自己处理乱序与重复（版本号）；全量窗口要避免读到半棵树；比 CDC 慢一个数量级。
- 适配条件：源端只给接口，读必须自主可控。

## 3. 决策

**选 E。** 核心依据：在当前约束下 CDC 不是候选，是协调问题。同一问题若 HR 是自己的系统，答案应退回 A。

树存储随本决策绑定：**邻接表做权威 + 闭包表做查询**。否决路径枚举（整块搬家改整棵子树）和嵌套集（插入改大半张表）——组织调整期就是写入尖峰期。

## 4. 否决理由

- **否决 A**：拿不到 binlog。不是 CDC 不行，是边界不允许。（组织事实，不是估算）
- **否决 B**：没有全量归零，增量漂移不可自愈。
- **否决 C**：判据是自主掌控可用性，不是新鲜度。考核范围高频读不能交给另一个团队的 SLA。
- **否决 D**：跨团队双写无原子性，故障不可观测。

## 5. 后果与风险

- **收益**：填报可用性与 HR 解耦；周期口径可冻（组织树版本列）；对账有全量可做差。
- **引入的新问题**：增量版本号与待定队列；全量必须影子表原子切换，禁止先删后写；闭包表写放大 O(深度)，深度通常 ≤ 6 可接受。
- **触发重审**：HR 开放 binlog 且 DBA 书面同意；或增量对账持续发现系统性漏发而全量窗口不可接受。

> 专题里的容量与耗时是设计目标，见原文「尚未验证」。本 ADR 只锁同步形态。
