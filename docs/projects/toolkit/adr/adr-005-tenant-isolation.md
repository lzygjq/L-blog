# ADR-005：多租户按三级混合隔离；共享库的租户条件在框架注入

## 1. 背景与约束

物业 SaaS 一套代码服务很多物业公司。租户规模从几个小区到上千项目。账单、门禁、交易都带租户。大客户会要单独备份、单独恢复、甚至合规物理隔离。新租户几乎都是小的，必须便宜接进来。

## 2. 备选方案

### 方案 A：全部共享库 + 租户字段（一刀切 L1）
- 思路：所有表 `tenant_id`，一个实例。
- 优点：成本最低，运维一个库。
- 缺点 / 代价：无法按租户恢复；合规物理隔离做不到；大租户噪声影响所有人。
- 适配条件：租户体量接近，且无隔离条款。

### 方案 B：全部独立库 + 独立部署（一刀切 L3）
- 思路：每租户一套。
- 优点：隔离最强。
- 缺点 / 代价：小租户数量上去后，实例数和成本先把平台拖死；升级变成 N 次。
- 适配条件：租户少而大，或从第一天就只做私有化。

### 方案 C：全部独立 Schema（一刀切 L2）
- 思路：同实例不同库。
- 优点：备份粒度比 L1 好，比 L3 便宜。
- 缺点 / 代价：小租户仍偏贵；连接与迁移工具链变复杂；仍解决不了「要独立计算配额」的大客户。
- 适配条件：中等体量、数量可控。

### 方案 D：三级混合，默认 L1，可升 L2 / L3（本方案）
- 思路：数据模型从第一天就有干净租户边界。过滤在框架拦截注入，白名单才能跨租户。横切（缓存键、消息、文件路径、任务分片）一律带租户。L3 同时独立命名空间与配额，不只是库分开。
- 优点：小租户进得来，大租户升得上去。
- 缺点 / 代价：路由与迁移要设计；L1 漏过滤就是串租户事故；升档是项目而不是开关。
- 适配条件：规模差一个数量级，且会有人提出合规。

## 3. 决策

**选 D。** 多租户是隔离强度的选择，不是是非题。分档的目标是让迁移可执行：L1 模型没有租户边界，就永远升不上去。

横切收敛成一个框架 JAR（接入成本压过依赖图优雅）是伴随决策，细节见案例；本 ADR 只锁隔离与过滤归属。

## 4. 否决理由

- **否决 A 一刀切**：无法满足按租户恢复与物理隔离，大租户会逼出一次无法执行的迁移。
- **否决 B 一刀切**：为长尾小租户付 L3 成本，平台先死在运维上。
- **否决 C 一刀切**：挡不住 L3 需求，又比 L1 贵，作为唯一档不划算。
- **否决「开发在 SQL 里手写 tenant_id」**：漏一次就是串租户。绕过必须是显式白名单。

## 5. 后果与风险

- **收益**：新租户默认 L1；升档有路径；串租户从「纪律」变成「框架默认」。
- **引入的新问题**：ThreadLocal 租户上下文在线程池、异步、消息消费、定时任务上都会断，要逐个横切点传播；文件路径与签名 URL 漏租户段可被枚举。
- **触发重审**：绝大多数租户都升到 L3（混合失去意义）；或框架注入被证明有系统漏洞，隔离模型要退到物理层才能睡得着。

> 升档阈值、配额数字是容量与商务问题，见[容量测算](/projects/property-saas/capacity-and-perf/)，本 ADR 不锁数字。
