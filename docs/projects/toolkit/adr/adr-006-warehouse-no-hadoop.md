# ADR-006：分析负载迁出在线库；不上 Hadoop 全家桶

## 1. 背景与约束

收缴率、欠费账龄、经营看板要多维下钻和长期留存。查询压在账单所在的 MySQL 上，和缴费写入抢 IO。团队没有专职数据平台组。业务要分钟级可查，不是 T+1。在线事务（缴费、下单、门禁）必须继续强一致。

## 2. 备选方案

### 方案 A：报表继续跑在线 MySQL
- 思路：加只读从库或加大实例。
- 优点：无新组件。
- 缺点 / 代价：行式库不擅长大范围聚合；分析与交易抢资源，两边都做不好。
- 适配条件：报表很轻、很少，且可接受打慢在线。

### 方案 B：Hadoop 全家桶（HDFS / YARN / Hive / Spark）
- 思路：按「大数据默认栈」建平台。
- 优点：生态完整，什么都能做。
- 缺点 / 代价：组件多、版本兼容、要专人；延迟形态是批处理；能力超出「支撑业务分析」。（与团队规模不匹配）
- 适配条件：要建数据平台，且有平台团队。

### 方案 C：只上 Elasticsearch 做分析
- 思路：检索集群兼看板。
- 优点：运维面相对熟。
- 缺点 / 代价：擅长检索，不擅长多表 JOIN 与分析型聚合。
- 适配条件：主需求是搜日志或搜文档。

### 方案 D：CDC 读 binlog → Kafka → Doris；冷数据对象存储 + Iceberg（本方案）
- 思路：在线库只留事务。变更以行事件出去，多下游可重放。分析用列式、MySQL 协议、多表 JOIN。冷层按 TTL 下沉。同步链路不用轮询、不应用双写。业务解耦仍用 RocketMQ，和这条变更流分工。
- 优点：分钟级可查；组件面比全家桶小；历史成本不跟本地盘线性涨。
- 缺点 / 代价：要运维 CDC、Kafka、Doris、对象存储；位点超过 binlog 保留期只能全量重跑；对象存储尾延迟不适合当热查询。
- 适配条件：分析是刚需，但建平台不是目标。

ClickHouse 作为分析引擎的备选：单表吞吐强，并发与多表 JOIN 弱、生态偏运维向，看板 + 多表场景不如 Doris。否决写在第 4 节，不单列成主方案。

## 3. 决策

**选 D。** 引入组件前先问：它解决的是必需问题还是可能用到的问题。全家桶大量能力属于后者。加组件容易，去掉很难。

## 4. 否决理由

- **否决 A**：分析与交易争抢，报表页能把缴费打慢。
- **否决 B**：运维成本、延迟形态、团队规模三项都不匹配；真正要用的列式、JOIN、物化视图、湖表已经能覆盖需求，不为剩余能力付数倍复杂度。
- **否决 C**：检索 ≠ 分析。
- **否决「定时轮询在线库」**：看不见物理删除与字段级变更，还加压在线。
- **否决「应用双写进仓」**：业务代码侵入，失败无法补偿。
- **否决「历史只留分析库本地盘」**：成本随容量线性上升。
- **否决 HDFS 当主历史介质**：元数据集中、扩容再平衡、存算耦合。

## 5. 后果与风险

- **收益**：在线库回到写优化职责；分析有独立容量；冷热可分层。
- **引入的新问题**：口径治理是组织问题——分层解决不了「指标定义谁负责」；TTL 迁移必须先写、再校验、最后删源；CDC 停久了位点失效。
- **触发重审**：出现全家桶才有的刚需（例如必须与现有 Hadoop 资产对接）；或 Doris 并发 / JOIN 在真实报表下不够（要用压测证明，不是感觉）；或团队编制变成独立数据平台。
