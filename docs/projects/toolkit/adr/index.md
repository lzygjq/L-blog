# ADR 架构决策记录

## Why —— 为什么要用 ADR

技术决策的成本不在"选"的那一天，而在**选完之后**。没有留下记录，会在三个场景里付出代价：

| 场景 | 没有 ADR 会怎样 | 有 ADR 会怎样 |
|---|---|---|
| **半年后的自己** | 只记得"当时用了 Redis Stream"，忘了为什么不用 RocketMQ；想优化时无处下手，甚至推翻一个本来正确的决定 | 翻出当天的约束与否决理由，判断"约束变了没有"——变了就写新篇，没变就照旧 |
| **面试官 / 评审人** | 被追问"为什么不用 XX"答不上来，前面讲的架构一起被打折 | 直接给出否决理由与代价，**证明的不是"我知道"，而是"我权衡过"** |
| **接手的人** | 不知道当初被否决的方案与被接受的代价，要么不敢动，要么改回已被否决的路 | 先读 ADR 再动手，改动成本最低 |

**最典型的症状是这种会议纪要**：

> "经讨论，决定采用 Redis Stream 做服务间事件总线。" —— 三个月后，没人记得为什么。

它记录了**结论**，丢掉了**推理**。而结论会过时，推理不会 —— 这正是 ADR 存在的理由。

## What —— ADR 是什么

**ADR（Architecture Decision Record）= 一页纸，记录一个决策的：面对什么约束、权衡了哪些备选、为什么选这个、否决了谁、代价是什么、什么条件下要重审。**

### 两条硬规则

> **① 没有备选方案对比的 ADR 不算 ADR。**
> 只写选中方案 = 调研报告；写了 A/B 却没有否决理由 = 没写完。
>
> **② 没有数据支撑的否决理由，必须显式标注「（估算，待验证）」。**
> 禁止"感觉不合适""网上说不推荐"这类不可验证表述 —— 面试官和评审者第一个追问的就是这里。

### ADR 不是什么

| 不是 | 区别 |
|---|---|
| 设计文档 | 设计文档讲"系统怎么搭"；ADR 讲"为什么这么搭、为什么不那么搭" |
| 技术教程 | 教程讲"X 是什么、怎么用"；ADR 讲"在我们的约束下为什么用 X" |
| 选型调研报告 | 调研报告罗列候选；ADR 必须**收口到一个结论 + 一份否决理由** |
| 会议纪要 | 纪要记结论；ADR 记推理 + 代价 + 重审条件 |

### 五节结构

| # | 小节 | 必须回答什么 |
|---|---|---|
| 1 | **背景与约束** Context | 3~6 句：面临什么问题？硬约束是什么（团队规模 / 工期 / 成本 / 技术债 / 规模预期）？**这一段决定读者对"你面对的真实问题质量"的判断** |
| 2 | **备选方案** Options | 至少 2 个（理想 3 个），每个写：思路 / 优点 / 缺点与代价 / 适配条件 |
| 3 | **决策** Decision | 一句话结论 + 选择的核心依据；必要时附对比维度表 |
| 4 | **否决理由** Rejected | 逐个说明为什么没选，必须是**代价 / 风险 / 数据**层面的理由 |
| 5 | **后果与风险** Consequences | 收益 / 引入的新技术债 / **触发重审的条件（Revisit when）** |

第 4、5 节是这一层的精髓：否决理由让决策**可被追问**，重审条件让它**可被证伪**。这两样东西把一篇"想法"变成了可验证资产。

### 状态流转

```
提议 Proposed ──采纳──> 已采纳 Accepted ──重审条件触发──> 被取代 Superseded（被 ADR-0YY 取代）
                    │
                    └──不做了──> 已废弃 Deprecated
```

原则：**已发布的 ADR 只改状态，不改内容**。想法变了不回头改旧文，而是新写一篇、在旧文状态栏标「被 ADR-0YY 取代」—— 决策的演进过程本身就是最有价值的证据。

## How —— 怎么用

### 第一步：判断该不该写

| 该写的信号 | 例子 |
|---|---|
| **选了 A 放弃 B**，且差异半年后会被人追问 | 「为什么不用 RocketMQ」 |
| **引入了新的运行组件 / 依赖 / 中间件** | 每条新依赖一篇 |
| **定了一条工程级约定**，别人不知道就会违反 | 「为什么所有表必须有 tenant_id」 |
| **做了会痛的取舍**（性能换简单、成本换隔离、工期换架构） | 「为什么先单体后拆分」 |
| **推翻了自己以前的做法** | 写新 ADR 取代旧篇 |

**不该写**：编码规范、目录结构、一眼能看明白的选型（「为什么用 Spring Boot」）、纯知识整理。

> 判据一句话：**如果这个决策必然有人会问「为什么不用那个？」，就写；否则不写。**

### 第二步：按五节填，写不下去就是没想清

| 写不出来的地方 | 说明什么 |
|---|---|
| 第 1 节（背景与约束） | **约束没搞清** —— 此时做的决策是碰运气 |
| 第 2 节（备选方案只有 1 个） | **没有真的调研** —— 只是"第一个想到的就是它" |
| 第 4 节（写不出否决理由） | **方案对比停留在名词层面** —— 没比过代价 |
| 第 5 节（写不出重审条件） | **没想过它什么时候会失效** —— 这篇 ADR 会变成教条 |

### 第三步：命名与存放

```
projects/toolkit/adr/
├── index.md                     本页（Why / What / How）
├── template.md                  空模板，复制即用
└── adr-001-<slug>.md            正式记录：三位序号 + 英文短横线 slug
```

- 序号**三位、递增、只增不减**；被取代的旧篇保留原号不删。
- **文件名全小写**（`adr-001-event-bus-stream.md`）；正文 H1 与标题用大写编号 `ADR-001：…`（URL 由文件路径生成，大写容易在大小写敏感环境出死链）。
- 一篇 ADR **不超过两屏**。写不下说明你在写设计文档，该拆。
- 同一篇可存两处：项目仓库（源，可带内部编号与链接）+ 本站（对外镜像，脱敏后发布）。

frontmatter：

```yaml
---
title: 'ADR-001 · 事件总线：Redis Stream vs 独立消息中间件'
order: 1
date: 2026-09-10
status: 已采纳
---
```

`status` 取值：`提议` / `已采纳` / `被取代` / `已废弃`。
