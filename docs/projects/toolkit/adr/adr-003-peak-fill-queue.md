# ADR-003：高峰填报预排队 + 异步落库；校验必须同步

## 1. 背景与约束

考核填报有硬截止。流量挤在开放首日和截止前 1～2 天，峰值相对均值可达几十倍（推导，待压测）。截止后用户没有第二次机会。弱网、刷新、多标签、脚本重放都会重复提交。

## 2. 备选方案

### 方案 A：同步直写 + 按峰值配库
- 思路：请求直接落业务表，硬件扛峰值。
- 优点：实现最简单，无「已受理未落库」窗口。
- 缺点 / 代价：按峰值配硬件，大部分时间空转；峰值还在涨，成本没有终点。（估算，待验证）
- 适配条件：峰值低于库承载的一半，且截止可延期。

### 方案 B：超限返回 429，让用户重试
- 思路：限流排队，典型秒杀做法。
- 优点：保护系统，实现便宜。
- 缺点 / 代价：用户被拒绝时已经没有别的时间可改，等于业务失败。
- 适配条件：用户有下一次机会（秒杀、抢券）。

### 方案 C：进队即返回成功，校验也异步
- 思路：提交只丢消息。
- 优点：入口最轻。
- 缺点 / 代价：用户看到成功，稍后被告知权重 ≠ 100%；人走了，截止过了。
- 适配条件：失败可事后补偿且用户还在线。

### 方案 D：预排队 + 同步校验 + 异步落业务表（本方案）
- 思路：鉴权、幂等、业务规则同步做完；写受理单后返回「已受理」；业务表由队列消费。前端防重只做体验，不算防线。
- 优点：截止前收下请求；非法输入当场失败；库写被削峰。
- 缺点 / 代价：成功与落库之间有窗口，要用状态可查补齐；要防重三层（令牌 / 唯一索引 / 状态机）；队列积压要可观测。
- 适配条件：不能拒绝，且校验失败必须立刻让用户改。

## 3. 决策

**选 D。** 判据一句话：能不能拒绝，取决于用户有没有第二次机会。硬截止下拒绝是把技术问题转嫁给业务。

分批放号能压集中系数，但是**流程改动，不是技术改动**，本决策不把它当成已经落地的前提。

## 4. 否决理由

- **否决 A**：峰值倍数高，按峰值买硬件是没有终点的成本曲线。（估算，待验证）
- **否决 B**：与硬截止冲突。
- **否决 C**：校验失败是业务失败，异步化在体验上是欺骗。
- **否决「前端禁用按钮当防线」**：刷新、多标签、弱网、直连接口四条都能绕过，校验放在不可信客户端。

## 5. 后果与风险

- **收益**：截止前「提交这件事」已经成立；库写速率与到达速率解耦。
- **引入的新问题**：受理单与业务表终态要对账；限流三维（用户 / 接口 / 全局）阈值必须压测后才写进承诺，现在只是设计；插入热点与更新热点要分开处理，随机主键解决不了更新热点。
- **触发重审**：压测证明峰值低于直写承载的 50%；或业务同意延期截止，429 变得可接受；或队列 P99 落库超过业务能容忍的窗口（设计目标见压测口径页，尚未实测）。
