# 方案评审

ADR 回答「当时为什么这么选」。缺的是**选之前那一小时**：材料够不够上会、会上必问什么、什么情况下今天不拍板。没有这一层，ADR 会变成会后补写的会议纪要——结论有了，推理是编的。

[落地反模式的 12 条](/methodology/ddd-in-practice#checklist)管**建模与边界**（共享库、依赖方向、规则在哪一层）。本页管**系统方案能不能拍板**：容量、故障、回滚、成本、职责。两边都过，才叫评审过了；只过一边，会在另一边翻车。

> **主线：评审不是投赞成票，是找否决理由。**
>
> 找不到否决理由，说明方案还没被追问过，不是说明它正确。散会条件写清楚，比「原则上同意、细节会后再说」值钱。

发布策略怎么配、压测命令怎么跑、DDD 十二条怎么逐条解释，不在本页——链到已有正文。

## Why —— 为什么要单独写评审

多数「评审过了」的方案，事后对不上这三件事里的至少一件：

| 会后对不上 | 会上实际发生了什么 |
|---|---|
| 半年后没人记得为什么否决 B | 只记了选 A，否决理由留在某个人脑子里 |
| 上线后不会退 | 「回滚」被理解成回代码，数据变更与开关没人认领 |
| 出事不知道找谁 | 容量、成本、值班被当成「上线后再说」 |

**最典型的不及格产物**是这种纪要：

> 「经讨论，原则同意该方案，细节会后对齐。」

它记录了**气氛**，丢掉了**拍板所需的四问**。会后对齐的细节，往往就是会上不敢问的否决点。

**一句话**：评审的价值不在「过了」，在于**留下一份能在三个月后被追问的推理，以及明确的「今天不拍」条件**。

## What —— 评审是什么

**定义：一次有材料、有四问、有散会条件的决策会议。产出不是口头同意，是一篇 ADR（或明确的「不拍、缺什么」清单）。**

### 会前必须有的三件材料

| 材料 | 最低内容 | 缺了会怎样 |
|---|---|---|
| **[架构图](/projects/toolkit/arch-diagram/)**（当前 + 拟议） | 边界、依赖、关键路径；标出这次要动的分叉 | 会上在画白板，评的是现场灵感 |
| **2–3 个方案 + 否决理由** | 每个方案：思路 / 代价 / 适配条件；**没有否决理由的对比不算对比** | 只会听到「我们觉得 A 更好」 |
| **容量与回滚草稿** | 峰值从哪来、失败时怎么退到上一版拓扑 | 把「先上再说」伪装成迭代 |

压测数字可以是估算，但必须标「估算，待验证」——与 ADR 的硬规则相同。容量怎么从业务量推到机器数，用[六步推导链](/projects/property-saas/capacity-and-perf/#derivation)，本页不重写公式。

**不该上会的**：编码规范、目录美化、一眼能看懂的选型（「为什么用 Spring Boot」）、还没有两个方案的调研报告。

判据一句话：**如果这个决策必然有人会问「为什么不用那个？出了事怎么退？」，就上会；否则写一页 ADR 或直接做。**

### 会上四问 {#four-questions}

材料齐了，会上只追这四句。答不上来就还没到拍板的时候：

| # | 问 | 合格答案长什么样 | 不合格 |
|---|---|---|---|
| 1 | **最坏怎么坏？** | 单点 / 级联 / 雪崩各举一个现场，以及第一道防线 | 「我们会监控」 |
| 2 | **放弃了什么？** | 点名被否决的方案，以及**代价 / 风险 / 数据**层面的理由 | 「那个不流行了」 |
| 3 | **怎么退？** | 代码、数据、开关、流量四条里，哪些能退、窗口多长、谁按按钮 | 「回滚发版」四个字 |
| 4 | **谁付钱？** | 机器、人力、值班、错误预算，由哪条业务线的哪个数字承担 | 「成本不大」 |

第 3 问最容易被跳过。回滚代码盖不住「已经写出的行」和「已经扩出去的副本」——数据变更走[扩展-收缩](/cloud-native/cicd/rollback-and-migration#expand-contract)，发布策略细节不在本页展开。

第 1 问里，下面几条是**常见否决理由**（失败模式不单开篇，评审时拿来用）：

| 否决 | 现场 | 去哪看机制 |
|---|---|---|
| **分布式单体** | 拆了进程，共享库 / 共享领域对象还在 | [拆分粒度](/methodology/service-granularity) |
| **重试风暴** | 超时叠加三层重试，下游被放大成脉冲 | [出站超时](/java/spring/spring-framework/crosscutting/outbound-http#retry-budget)、[重试前提](/java/spring/spring-framework/crosscutting/resilience#preconditions) |
| **缓存当数据库** | 以缓存为真相，重启或击穿后对不上账 | [缓存模式](/database/redis/cache-patterns) |
| **为 DDD 而 DDD** | CRUD 模块上聚合、事件、CQRS，改一处崩三处 | [落地反模式](/methodology/ddd-in-practice#antipatterns) |

建模 12 条仍按[那份清单](/methodology/ddd-in-practice#checklist)勾；本页不粘贴原文。

### 散会条件 {#adjourn}

下面任一成立，**今天不拍板**，带着「缺什么」散会：

1. 只有一个方案，或有两个方案但写不出否决理由。
2. 最坏情况讲不清，或防线是「会小心」。
3. 回滚只覆盖代码，数据或开关没有主人。
4. 容量数字没有来源（连估算标签都没有）。
5. 会上出现「原则上同意、细节会后对齐」——细节就是否决点。

散会不是失败。把缺的材料写成清单，下次带着证据再来，比强行过会便宜。

### 会后：必须落成 ADR

口头同意不作数。会后 24 小时内：

- **拍了** → 按[ADR 五节](/projects/toolkit/adr/)写一篇，状态「已采纳」，关联架构图版本与压测编号（或「待验证」）。
- **没拍** → 写「提议」状态的 ADR，或一页「缺什么才能再上会」。不要只改日历。

评审记录可以引用复盘：[故障复盘](/projects/toolkit/postmortem/)是运行期打穿假设之后的输入，下一次同类方案必须把它当作第 1 问的证据。

## How —— 怎么主持

### 角色

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **提案人** | 会前交出三件材料；会上只回答四问 | 现场改方案、用新白板顶替材料 |
| **主持** | 卡住四问与散会条件；记录否决 | 替提案人圆场 |
| **拍板人** | 说「采纳 / 不拍 / 授权范围」 | 会后用聊天消息改结论 |

什么票必须上会、什么可以授权给做设计的人：涉及跨服务数据归属、不可逆数据变更、新的运行组件、会改变错误预算的可用性目标——上会。模块内实现、可逆配置、已有 ADR 覆盖且约束没变——授权。这一条是给拍板人用的，不是给提案人用来躲评审的。

### 90 分钟怎么用

```
0–10   核对材料是否齐（不齐直接散）
10–40  提案人按「约束 → 方案对比 → 拟议」讲，禁止从实现细节开场
40–75  四问。每一问有否决点就停，不要四个问一起滑过去
75–90  拍板或散会条件；指定 ADR 作者与截止
```

超时就散。延长会议补材料，等于没有散会条件。

### 自检

1. 没参加会的人只读 ADR，能否说出「为什么不选另一个、出事怎么退」？
2. 架构图上的关键分叉，是否都能指到会上讨论过的否决？
3. 「谁付钱」有没有落到一个数字或一个预算科目——而不是「技术部消化」？
