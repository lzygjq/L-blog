# 故障复盘

立项时留下 ADR、压测报告、架构图，解决的是「当时为什么这么选、选完能不能跑」。系统跑起来之后还会出事。出事之后如果只口头同步「已经修好了」，半年后只剩下传说——同一个坑会再踩一遍，面试时也讲不清「那次到底是检测慢还是处置慢」。

> **复盘是运行期的可验证产出。** 立项三件套回答设计与容量；复盘回答一次真实失败里，机制在哪一层断了、下次靠什么挡住。

混沌演练、告警规则怎么配，不在本页——演练见[混沌与演练](/high-availability/chaos-drills)，告警合法性见 [SLO · 应急](/cloud-native/observability/slo-and-alerting#incident)。本页只规定：**一次故障写什么，怎样才算写完。**

## Why —— 为什么要写复盘

故障的成本不在当晚的加班，而在**没有留下可复核的推理**：

| 不写复盘 | 代价 |
|---|---|
| 只记得「那天 Redis 有点问题」 | 下次同类症状仍从零猜；不知道该加的是超时、是熔断，还是禁止某次发布 |
| 结论是「某人要更小心」 | 人不能被当机制。换班、换人后同样的操作还会再来一次 |
| 面试 / 评审被追问「你们怎么保证不再发」 | 只能讲故事。听的人无法判断你改的是机制还是运气 |

**最典型的不及格产物**是这种会议纪要：

> 「经排查为下游超时，已重启恢复，后续加强监控。」

它记录了**症状和动作**，丢掉了**时间线与否决掉的假设**。重启能止血的故障，根因通常不在「需要重启」；「加强监控」没有 owner、没有具体信号，等于没写。

**一句话**：复盘的价值不在「我们反思了」，在于**一份精确到分钟的时间线 + 一条被证据支撑的根因 + 若干条能进任务跟踪的机制改动**。

## What —— 复盘是什么

**定义：对一次用户可感知的故障，用证据重建「发生了什么」，并产出机制层改动。**

### 必须有的 7 个要素

| # | 要素 | 主要内容 | 缺了会怎样 |
|---|---|---|---|
| 1 | **标题与影响面** | 哪条链路、多久、谁受损（接口 / 租户 / 错误率） | 无法判断严重程度，也无法和 SLO 对上 |
| 2 | **时间线** | 精确到分钟：开始、发现、每个动作、当时以为是什么 | 分不清是检测慢还是处置慢 |
| 3 | **范围证据** | 哪个接口、哪些实例、拐点是否对齐发布 | 根因会写成感觉 |
| 4 | **一条典型请求** | `traceId` + 哪一跳吃掉了时间 | 讨论停留在「系统慢」 |
| 5 | **根因与否决** | 采用的根因 + **排除了哪些假设、凭什么排除** | 看起来像复盘，其实是第一印象 |
| 6 | **止血 vs 修复** | 当晚做了什么、根因要改什么，必须分开 | 把重启当成修复 |
| 7 | **行动项** | owner、截止、验收信号；进入正常任务跟踪 | 下次同一故障再来 |

第 2 条和第 5 条是精髓。时间线决定改进方向（MTTD 还是 MTTM，口径见 [SLO · 应急](/cloud-native/observability/slo-and-alerting#incident)）；否决掉的假设决定这篇东西能不能被追问——只写「是数据库」和 ADR 只写「选了 Redis」是同一类残缺。

### 复盘不是什么

| 不是 | 区别 |
|---|---|
| 追责报告 | 人名可以出现在时间线里（谁在什么时候做了什么），**不能出现在根因里**（「因为某某大意」） |
| 监控建设方案 | 可以产出「补一条告警」，但本页不设计 SLO |
| 慢请求现场笔记 | [慢请求剧本](/cloud-native/observability/slow-request)是当晚怎么查；复盘是查完怎么写成可复核资产 |
| ADR | ADR 记「为什么选 A 不选 B」；复盘记「一次失败里哪条假设被现实打穿」。打穿了选型，再开一篇 ADR |

**三条纪律**（与 SLO 篇一致，这里是写作判据）：

1. **无责。** 结论里的行动项如果是「某人要更小心」，这篇白写——它必须落到超时、门禁、发布开关、预算这类机制。
2. **行动项有 owner 与验收。** 「加强监控」不是行动项；「为支付出站补 `readTimeout=1s`，下游 hang 住时本服务 1s 内失败、网关不再先 504」才是。
3. **已发布的复盘不改事实段。** 后续发现根因判错，加一节「更正」或写续篇，不回头改时间线——演进本身是证据。

## How —— 怎么写

### 第一步：判断该不该写

| 该写 | 可以不写 |
|---|---|
| 用户可感知（错误率 / 超时 / 错误数据） | 单实例探活失败、自动拉起、无用户影响 |
| 用了错误的止血（重启当修复、加池当根因） | 已有复盘覆盖的同一机制，只补一条行动项 |
| 打穿了某条「我们认为不会发生」的假设 | 纯文档笔误、纯本地事故 |

判据一句话：**如果半年后的自己会问「那天到底怎么查的」，就写。**

### 第二步：当晚先留时间线，第二天再写根因

时间线的原料来自[慢请求剧本](/cloud-native/observability/slow-request#output)的现场。格式固定，避免事后回忆：

```
12:07  P99 从 200ms 升到 3s（看板，成功请求）
12:09  值班收到延迟告警（MTTD = 2 min）
12:11  以为是发布，核对 12:00 的发布窗口——无发布
12:14  挑 trace abc123：时间在出站 HTTP，下游 span 很短
12:18  发现客户端未配 readTimeout（当时以为是下游慢）
12:25  紧急配上 1s 超时并滚动 —— 用户侧恢复
12:40  确认 HTTP 池在 12:07 已打满（根因：下游抖动 + 无限等待）
```

「当时以为是什么」必须写。它暴露的是检测与决策质量，不是丢脸。

### 第三步：按七节填，写不下去就是证据不够

| 写不出来的地方 | 说明什么 |
|---|---|
| 时间线对不齐分钟 | 当晚没留图、没留 `traceId`，在凭记忆写小说 |
| 否决不了「就是流量大了」 | 没有范围证据（单接口 vs 全站、是否对齐发布） |
| 分不开止血和修复 | 还没找到根因，只是服务又活了 |
| 行动项没有验收信号 | 改动无法被下次故障或演练证伪 |

### 第五步：写完用三条自检

1. 换一个没参加当晚的人，只看这篇，能否说出「下一回同一症状先看什么」？
2. 行动项能否在任务系统里被勾掉，而不是留在 Wiki 底部？
3. 根因段里有没有人名当原因？有，就还没写完。

## 与立项三件套的关系

```
架构图 / ADR / 压测     ← 立项与演进（事前）
        │
        │  线上打穿了某条假设
        ▼
     故障复盘           ← 运行期（事后）
        │
        ├── 选型被证伪 → 新写一篇 ADR（旧篇标被取代）
        ├── 容量被证伪 → 补一次压测，更新拐点
        └── 结构变了   → 改架构图版本
```

**一个项目专题仍然以立项三件套收尾。** 复盘不是第四件「每个专题必须预写」的作业，而是**出事之后强制留下的一份**。没有故障的专题缺复盘是正常的；出过用户可感知故障却没有复盘，三件套再齐也补不上运行期的那一环。
