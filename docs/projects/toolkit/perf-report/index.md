# 压测报告

## Why —— 为什么要写压测报告

性能问题的成本，从来不在于"慢"，而在于**不知道**：

| 不知道 | 会付出什么代价 |
|---|---|
| 不知道能扛多少 | 容量靠猜 → 上线靠运气 → 出事只能紧急扩容救火 |
| 不知道瓶颈在哪 | 优化靠感觉 → 改了三个月，TPS 没动 |
| 不知道拐点在哪 | 只知道"200 并发没问题"，500 并发时是线性下降还是断崖，完全没底 |

**三个必须有的场景**：

1. **上线前** —— 这个峰值我扛得住吗？多少才算够？
2. **出问题时** —— 先动哪一块？凭什么说是数据库而不是应用？
3. **面试 / 评审时** —— 从「我做过」升级为「**这条链路单机 1200 TPS，P99 280ms，瓶颈在 MySQL 的行锁竞争**」。

**最典型的不及格产物**是这样一句话：

> "我们做过压测，性能还可以。"

没有数字、没有口径、没有环境、没有瓶颈 —— 换个人无法判断**够不够**，也无法**复现**。所以它不构成证据。

**一句话**：压测报告的价值不在"测过"，在于**产出一个可复现的数字结论 + 一条能站住的瓶颈证据链**。

## What —— 压测报告是什么

**定义：一份能被人复现的性能结论 —— 包含目标、场景、环境、分档数据、瓶颈证据链与容量结论。**

### 必须有的 8 个要素

| # | 要素 | 主要内容 | 缺了会怎样 |
|---|---|---|---|
| 1 | **被测对象与版本** | commit / 构建号 / 配置 | 数字无法复现，等于没有 |
| 2 | **目标与验收指标** | 压哪条链路、达到多少算通过 | 没有"够不够"的判据 |
| 3 | **场景与流量模型** | 接口组合、读写比、数据分布 | 压的不是真实流量，结论无效 |
| 4 | **环境与数据量** | 机器规格、数据规模、网络拓扑、隔离说明 | 数字脱离环境毫无意义 |
| 5 | **执行记录** | 加压策略（阶梯/恒定）、档位、时长、次数 | 无法判断是否摸到拐点 |
| 6 | **分档结果表** | 每档的吞吐、延迟分位、错误率、资源水位 | 只有单点数据，看不出趋势 |
| 7 | **瓶颈定位** | 证据链：现象 → 排查 → 归因 | 变成"数字展示"，不是"分析报告" |
| 8 | **结论与整改** | 容量数字 + 拐点 + 改进项与预期收益 | 读完不知道该做什么 |

### 指标口径

| 指标 | 看什么 | 常见错误 |
|---|---|---|
| **吞吐** TPS / QPS | 单位时间处理量 | 与并发数混为一谈（并发 ≠ 吞吐） |
| **延迟分位** P50 / P95 / P99 | 用户体验的真实分布 | **只报平均值** —— 平均值会把长尾抹平，而线上投诉全部来自长尾 |
| **错误率** | 超时、5xx、业务失败 | 只统计 HTTP 5xx，漏掉业务异常 |
| **资源水位** | CPU / 内存 / IO / GC / **连接池** | 不看连接池，最容易漏掉真瓶颈 |
| **拐点** | 吞吐不再随并发上升的临界点 | 没测到拐点 = 没测出容量 |

> **拐点才是容量的真正答案**。只测"200 并发没问题"等于什么都没测 —— 你要回答的是"多少并发开始不行，那时发生了什么"。

## How —— 怎么写

### 五步法

```
① 定目标    明确链路 + 验收指标（如：峰值 500 并发下 P99 < 500ms、错误率 0）
      │
② 造场景    接口组合与比例、参数分布、数据量对齐生产
      │
③ 隔离变量  一次只改一个因素；压测机与被测机分离；关掉无关干扰
      │
④ 阶梯加压  200 → 400 → 800 → 1600，记录每档数据，直到吞吐不再上升
      │        （拐点出现的档位，就是这套环境的容量上限）
      ▼
⑤ 定位归因  现象 → 假设 → 采集证据 → 排除 → 结论（一条完整证据链）
```

### 七个常见坑

| 坑 | 为什么是坑 | 正确做法 |
|---|---|---|
| 只报平均 RT | 长尾被抹平，线上照样雪崩 | 必报 P95 / P99 |
| 不写数据量 | 空表压出来的数字毫无意义 | 数据量对齐生产量级 |
| 压测机与被测机同机 | 压测工具自己抢资源，数字失真 | 分离部署，或明确标注混部 |
| 一次改多个参数 | 无法归因是哪个改动起的作用 | 隔离变量，单因素对照 |
| 只压一次 | 偶然波动被当成结论 | 每档重复 3 次，取稳定值 |
| 结论没有容量数字 | 读了不知道能扛多少 | 明确"安全水位 X TPS / 拐点在 Y 并发" |
| 不记版本与环境 | 数字不可复现，后续无法对比 | 版本 + 配置 + 数据量三件套必须写 |

### 与另外两件套的联动

- **上游**：[架构图](/projects/toolkit/arch-diagram/) 上的**关键路径**，就是压测的对象清单 —— 没有图，压测容易挑错目标（压了不重要的接口）。
- **下游**：压测暴露的取舍（为性能牺牲了什么），往往需要回写一篇 [ADR](/projects/toolkit/adr/) 记录"为什么接受这个代价"。
- **互引**：ADR 的「关联」字段引用压测报告编号；压测报告的「被测版本」标注对应的架构图版本。
