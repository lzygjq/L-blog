# 架构图

## Why —— 为什么要画架构图

用文字描述结构，是**信息传递效率最低**的方式。一段"我们的系统分为网关层、服务层、存储层，网关负责鉴权与限流，服务层按业务域拆分……"读三遍，听的人脑子里还是没有一个形状。

而一张对的图，能替代二十分钟的口头解释。三个场景：

| 场景 | 没有图会怎样 | 有图会怎样 |
|---|---|---|
| **讲给别人听**（评审 / 面试） | 边讲边被追问"这块在哪一层""它连的是哪个库"，讲到第三遍还没讲完 | 图一放，**对方自己就能定位问题**，提问从"这是什么"变成"这里为什么这样" |
| **自己梳理** | 靠脑子记，直到撞上"这块到底归谁管"的边界问题才返工 | **画的过程本身就是设计** —— 画不出来，通常意味着还没想清 |
| **接手 / 半年后回看** | 面对几百行代码重新建立心智模型 | 先看图，再决定读哪几个模块 |

**最典型的症状**：架构只存在于某个人脑子里和几句口头描述里。换人接手时，只能靠读代码反推。

> **画图最大的收益不在交付，在画的过程**。当你被迫给每条连线标注语义时，"这里为什么要同步调用"这类问题会自己浮出来。

## What —— 架构图是什么

**定义：用统一符号与固定图层级，把系统的组成、边界、依赖关系可视化出来，使读者能独立还原系统的形状。**

### 分层：C4 模型（推荐主干）

| 层级 | 叫什么 | 画什么 | 读者 |
|---|---|---|---|
| **L1** | 系统上下文图 | 系统与**外部**（用户、第三方系统）的交互 | 非技术人员、决策者 |
| **L2** | 容器图 | **可独立部署/运行**的单元：服务、数据库、缓存、消息队列、前端 | 研发、运维 |
| **L3** | 组件图 | 单个容器内部的**模块划分**与依赖 | 该服务的开发者 |
| **L4** | 代码图 | 类图（**通常不画**，代码即文档） | — |

### 三类补充视图

| 视图 | 回答的问题 | 什么时候必须画 |
|---|---|---|
| **部署图** | 这些东西跑在哪几台机器 / 哪个集群上？ | 涉及多节点、容器编排、机房与网络分区 |
| **时序图** | 一次调用走了哪条链路？谁同步等谁？ | 链路长、跨服务、有异步与回调 |
| **数据流图** | 数据从哪来、经过什么加工、最后落到哪？ | 有数据同步、ETL、数仓与冷热分层 |

### 一张合格架构图的六个要素

| # | 要素 | 说明 |
|---|---|---|
| 1 | **标题 = 议题** | 不是"系统架构图"（废话），而是"**订单支付链路 · 容器视图**"——标题就该说清这张图回答什么问题 |
| 2 | **图例** | 颜色 / 形状 / 线型各代表什么。没有图例的图，读者只能猜 |
| 3 | **边界** | 系统边界、信任边界、网络区域。**边界是架构图最重要的信息**——它决定了哪些调用是跨信任域的 |
| 4 | **方向语义一致** | 箭头方向统一表示依赖（或统一表示数据流），不能一张图里两种混用 |
| 5 | **粒度一致** | 同一张图不混层级（L2 容器图里不要出现 L3 的类） |
| 6 | **标注关键点** | 关键路径、单点、瓶颈、同步/异步、降级开关 |

### 好图与坏图的差别

| 坏图 | 好图 |
|---|---|
| 一张图想讲完全部 | **一图一议题**，需要就多画几张 |
| 箭头没有标签，纯粹"连一下" | 每条边都有语义：HTTP 调用 / 异步消息 / 数据复制 |
| 没有边界，所有东西平铺 | 明确画出系统边界与信任边界 |
| 粒度混杂：网关和某个工具类同框 | 同一张图同层同粒度 |
| 只画 happy path | 标出单点、降级路径、失败处理 |
| 没有版本与日期 | 有版本号与日期，能对应到 ADR 与压测报告 |

## How —— 怎么画

### 五步法

```
① 定议题    这张图要回答什么问题？（是"谁依赖我"还是"我内部怎么拆"？）
      │
② 定层级    选 C4 的哪一层（L1 / L2 / L3）+ 是否需要补充视图
      │
③ 先边界    由外向内：先画系统边界与外部交互，再填内部组件
      │        （边界错了，内部画得再漂亮也是废图）
      ▼
④ 连边定语义 每条线写清是什么：同步调用 / 异步消息 / 数据同步 / 复制
      │
⑤ 标关键点  关键路径加粗、单点打标记、瓶颈与降级单独标注
```

### 工具选型

| 工具 | 适合 | 优缺点 |
|---|---|---|
| **draw.io（diagrams.net）** | 正式交付、要精细控制 | 免费、可存进 Git（`.drawio` 是文本 XML，可 diff）、模板丰富 |
| **Excalidraw** | 讨论、快速草稿 | 手绘风降低"已经定稿"的压迫感，适合评审前对齐 |
| **Mermaid / PlantUML** | 需要版本化、频繁变更的图 | 文本即图，可进 Git 做 diff；但布局不可控、复杂图会难看 |

**建议**：讨论期用 Excalidraw，定稿用 draw.io 存仓库；**链路时序与数据流优先用 Mermaid**（变更频繁，文本化收益最大）。

> 本站未启用 Mermaid 渲染插件，页面里以内嵌图片或 ASCII 图呈现 —— ASCII 图的好处是能跟着 Markdown 一起 diff。

### 交付前检查清单

- [ ] 标题写的是**议题**，不是"系统架构图"
- [ ] 有图例，读者不需要猜符号
- [ ] **边界**清晰（系统边界 / 信任边界 / 网络区域）
- [ ] 每条箭头都有语义，方向表示一致
- [ ] 同图同粒度，没有层级混杂
- [ ] 标出了关键路径与**单点**
- [ ] 标了版本与日期（能与 ADR、压测报告对应）
- [ ] **拿走文字说明，读者能看懂七成**

### 与另外两件套的联动

- **下游**：[ADR](/projects/toolkit/adr/) 是图上的**分叉点**。画完图，把每个"为什么走这条路"的分叉抽出来写 ADR。
- **下游**：[压测报告](/projects/toolkit/perf-report/) 的**对象清单**来自图上标出的关键路径。没有图，容易压错目标。
- **互引**：图上有版本号，ADR 与压测报告都标注所依据的架构图版本 —— 三者构成同一时间点的证据快照。
