# 架构路线

> **口径说明**：这一页回答两个问题——「**现在各层分别在哪一档**」和「**该不该动那一层**」。[成长路线](/projects/architect-roadmap/)是**人**的深度轴，本路线是**系统**的形态轴。文中的容量与阈值是**行业经验值包络**，**不含生产实测数据**。全文脱敏。

四个东西**不是一起演进的**。单体时期它们只是挤在同一台机器上共命运——那时候常常还没有文件服务器，Redis 也可以没有。一起走的只有共址；拆机也是串行的。之后看谁先撞墙。

```text
① 共址            一台机器上：应用 + 数据库 + 缓存 + 本地文件
② 物理拆开        先迁库、再迁缓存；文件可以晚，直到要起第二台应用
③ 各层自己走      应用 / 数据 / 缓存 / 文件 / 部署 —— 档位不必对齐
```

**不要给系统贴一个总版本号。** 「我们是 V3」没有信息量；「应用还是单体、数据已主从、图片已经走 CDN」才有。判断该不该升，看**那一层的瓶颈**，或看**被别的层逼着动**。

技术细节不在这一页。复制协议、槽位、切分策略、流水线怎么配，都在分册。各层页只回答「上一档死在哪、凭什么拆、怎么拆、拆完能撑什么、新上限在哪、哪一档可以跳过」。

## 一、只有一段一起走 {#start}

量还小的时候，四件套共址是成本最优。该拆的信号不是「看起来不够企业级」，而是它们开始互相伤害：备份把接口拖死、Redis `fork` 把 JVM 打死、上传把库的盘写满。

拆机买的是**隔离**，不是高可用，也不是分片。顺序几乎总是 **先 MySQL（盘），再 Redis（内存）**；文件可以继续留在应用机上。正文、触发表和「拆完仍是四台单机之和」见 [架构 L1 共址与拆机](/projects/architecture-evolution/colocation/)。

## 二、谁先撞墙、谁先拆 {#triggers}

这张表才是演进顺序。不是版本号到了，是**某一层的墙到了，或被另一层逼着动**。

| 先发生的事 | 被逼先动的层 | 此时其他层通常还在 |
|---|---|---|
| 备份 / 磁盘把整机打停 | [架构 L3 数据](/projects/architecture-evolution/data/)迁走 | 应用仍单体、文件仍本地 |
| 内存 / `bgsave` 打停 JVM | [架构 L4 缓存](/projects/architecture-evolution/cache/)迁走 | 同上 |
| 要起第二台应用 | [架构 L5 文件](/projects/architecture-evolution/file/)必须离开本机盘 | 库可以还是单机；应用还不是微服务 |
| 图片慢、下载带宽贵 | [架构 L5 文件 · CDN](/projects/architecture-evolution/file/#cdn)（可提前） | 库可以还是单机——早期系统就是这样 |
| 读把单库 CPU 打满 | [架构 L3 数据 · 主从](/projects/architecture-evolution/data/#replica) | 应用仍单体，非常常见 |
| 第一次真宕机、受不了人工切 | [架构 L3 数据 · 自动切主](/projects/architecture-evolution/data/#failover) / [架构 L4 缓存 · 哨兵](/projects/architecture-evolution/cache/#sentinel) | 经常被跳过，或买 RDS 时和主从一起买掉 |
| 模块变多、横切各写各的 | [架构 L2 应用 · 父子聚合](/projects/architecture-evolution/app/#modular) | 和库有没有主从无关 |
| 某一块要独立发、独立升配 | [架构 L2 应用 · 垂直拆分](/projects/architecture-evolution/app/#vertical) | 库还经常是共享的 |
| 单表体量 / 写 IO 顶死 | [架构 L3 数据 · 分片](/projects/architecture-evolution/data/#shard) | 文件和 CDN 可能早就走完了；分片可永远不到 |
| 人盯脚本搞不定副本和回滚 | [架构 L6 部署](/projects/architecture-evolution/deploy/) | 可以套在单体上，不必等微服务 |

> 再往后是多机房与单元化，属于地域与容灾，见[高可用](/high-availability/)，不在本路线。

| 层 | 这一层自己的梯子 | 入口 |
|---|---|---|
| **架构 L1 共址与拆机** | 四件套共命运 → 串行迁走（先库后缓存，文件可晚） | [架构 L1 共址与拆机](/projects/architecture-evolution/colocation/) |
| **架构 L2 应用** | 单体 → 父子聚合 → 垂直拆分 → 微服务 | [架构 L2 应用](/projects/architecture-evolution/app/) |
| **架构 L3 数据** | 独立单机 → 主从 → 自动切主（可跳）→ 分片（可不到） | [架构 L3 数据](/projects/architecture-evolution/data/) |
| **架构 L4 缓存** | 独立单机 → 主从 → 哨兵（可跳）→ Cluster（可不到） | [架构 L4 缓存](/projects/architecture-evolution/cache/) |
| **架构 L5 文件** | 本机盘 → 对象存储 → CDN（可提前）；独立文件机**可跳过** | [架构 L5 文件](/projects/architecture-evolution/file/) |
| **架构 L6 部署** | 手工 → 脚本多实例（可跳）→ CI → 云原生；与应用结构解绑 | [架构 L6 部署](/projects/architecture-evolution/deploy/) |

读法只有两种：**横向读一层**（那一层自己的梯子），**对照第六节**（真实系统里各层不必齐步）。不要纵向读成「系统处于某一档」。

## 四、层不是系统的属性 {#levels-as-relation}

成长路线的 **成长 L1–L4** 是人的级别。本路线的 **架构 L1–L6** 是系统形态的入口（先共址，再五层），不是同一把尺子。不要把「成长 L2」和「架构 L2」读成同一个阶段。

| 层 | 这一层在买什么 | 不要和别的层绑死 |
|---|---|---|
| **架构 L2 应用** | 工程边界 → 部署边界 → 数据边界 | 聚合不是微服务；库没独立，微服务只买了一半 |
| **架构 L3 数据 / 架构 L4 缓存** | 先买「活下来」（副本、切主），再买「装得下」（分片 / Cluster） | 加从库提升不了写吞吐。两轴见下节 |
| **架构 L5 文件** | 离开本机盘，换介质；读慢再上 CDN | 没有主从这一档；CDN 可以比库更早 |
| **架构 L6 部署** | 可重复 → 可追溯 → 声明式自愈 | 单体可以上 K8s，微服务可以仍手工发 |

## 五、两档买「活下来」，一档买「装得下」 {#two-axes}

这句话**只属于数据层和缓存层**。不要压成「单机 → 集群」一步，也不要套到应用或文件上。

| 档 | 动的轴 | 触发 |
|---|---|---|
| **主从** | **可用性 + 读** | 读把单机 CPU / 内存打满，或备份必须停业务 |
| **自动切主 / 哨兵** | **可用性**（可跳） | 无法接受人工切换的停机窗口 |
| **分片 / Cluster** | **扩展性**（可不到） | 单机磁盘 / 内存 / 写 IO 打满 |

```text
        ┌─────────── 可用性轴（坏了怎么办）───────────┐
单机 ──▶ 主从 ──▶ 自动切主（可跳）──────────────▶ 分片 / Cluster
 │       ↑ 读扩展      ↑ 停机窗口从小时到分钟         ↑ 容量与写吞吐
 │       └─ 有副本、有备份 ─┘                       │
 └─────────────────────────────────────────────────┘
                         换成扩展性轴
```

**加从库永远提升不了写吞吐。** 从库也不会自己变成主库。上云之后，主从和自动切主经常是买一台 RDS / 云 Redis 一步完成，路线上仍要分清买的是哪一根轴。细则在 [架构 L3 数据](/projects/architecture-evolution/data/#two-axes)和 [架构 L4 缓存](/projects/architecture-evolution/cache/#two-axes)。

应用线不是这条轴：父子聚合买的是工程约定，垂直拆分才第一次出现多个部署单元。部署线和应用程序结构正交。

## 六、这些选择在我做过的系统里长什么样 {#my-path}

同一个人的两个系统，正好落在**不同层的不同档**——错位本身就是最有价值的部分：

| 层 | 早期单体系统（已上线，真实运行） | 多租户 SaaS 平台（方案层，部分验证） |
|---|---|---|
| **应用** | 单体（按模块分子模块，同一进程） | 聚合 JAR + 往微服务走 |
| **数据** | 独立单机（未分片） | 一主二从 + MHA（方案层） |
| **分片** | 未到 | ShardingSphere（方案层） |
| **缓存** | 单机 Redis | 主从 + 哨兵 |
| **文件** | 本机目录，图片已经 **CDN（提前）** | 统一对象存储 |
| **部署** | 单机 Tomcat + 手工发版 | 往容器化 + K8s |
| **可观测** | 日志文件 | 指标 + 日志 + 链路 |

**注意文件那一行**：左边数据库停在独立单机，图片却已经走 CDN。瓶颈到来的时间不同——数据量还没到分片，图片延迟先来了。独立文件机这一档两边都没有走，直接从本机（加 CDN）或对象存储解决问题。

> **演进从来不是整体推进的。** 没走到该层的最后一档不等于落后：单机数据库在体量还没碰到写墙时，就是成本最优解。

按[项目实战](/projects/)的纪律区分三者：早期系统的「单体 + 单机库 + 本机文件 + 图片走 CDN」是**已上线**形态；多租户那一列里，聚合与容器化有本地验证，MHA、分片、K8s 编排属于**方案层**——写出来是判断依据，**不是声称已具备生产规模**。见[项目题的三条红线](/projects/#interview)。

**带状态列的表、以及下一套系统的空表，记在[层账](/projects/architecture-evolution/ledger/)。** 本节约叙事；改档只改层账，避免两处打架。

## 七、面试问答 {#interview}

**Q1：主从和分片解决的不是同一个问题，区别在哪？**

主从（[数据 · 主从](/projects/architecture-evolution/data/#replica)）解决**可用性与读扩展**；自动切主只是把切主从人换成流程，**写仍然是一台主**。分片（[数据 · 分片](/projects/architecture-evolution/data/#shard)）解决**写扩展与容量**。加从库永远提升不了写吞吐。读扛不住 → 加从库；写或容量扛不住 → 只能分片。

**Q2：已经有了主从，为什么还需要 MHA / 哨兵？**

**从库不会自己变成主库。** 发现故障 → 提升从库 → 改地址 → 重启应用，窗口通常是几十分钟到数小时。自动切主用稳定入口把换主对客户端变透明。代价是仲裁组件和脑裂。验收是故障演练，不是配置里有没有开哨兵。这一档**可以跳过**（或买云数据库时和主从一起买掉）。见[数据 · 自动切主](/projects/architecture-evolution/data/#failover)。

**Q3：什么时候该分库分表？**

先穷尽归档、索引、读写分离、冷热进数仓。量化经验值：**单表约 1000 万行或约 20G**（点查可更宽，聚合更窄），或单机磁盘 / 写 IO / 连接数打满。最大代价是跨片 JOIN 和事务没了。分片不可逆，**可以永远不到**。细则见[分库分表](/database/sharding/) 与 [数据 · 分片](/projects/architecture-evolution/data/#shard)。

**Q4：文件为什么不走主从？独立文件机必须上吗？**

文件副本是全量拷贝，不产生新容量。主轴是**离开本机盘、换介质**。独立文件机（NFS 等）是可选过渡，不是必经——本机可以直接上对象存储。CDN 可以提前：库还是单机、文件还在本机时，图片就可以走 CDN。触发点经常是**应用变成多实例**或**静态资源延迟**，不是文件先变得很大。见 [架构 L5 文件](/projects/architecture-evolution/file/)。

**Q5：父子聚合工程算微服务吗？为什么还要垂直拆分？**

**不算。** 聚合工程收的是依赖和横切，部署单元还是一个。垂直拆分才出现多个部署单元。微服务再加独立数据和治理。跳过中间两档，边界没想清楚，结果是一群难改的系统和一套分布式事务。见 [架构 L2 应用](/projects/architecture-evolution/app/)。

**Q6：Redis 哨兵和 Cluster 哪个先上？**

哨兵买自动切主，数据集仍 ≤ 单主内存，**可跳**。Cluster 买内存和写的横向扩展，**可不到**。读不够先加从库；挂了要人切再上哨兵；**内存墙或写墙**才上 Cluster。不要用 Cluster 解决「懒得配哨兵」。见 [架构 L4 缓存](/projects/architecture-evolution/cache/)。

**Q7：为什么先拆到独立服务器，而不是直接上主从或 K8s？**

共址时瓶颈是**资源争抢**，主从和编排都解决不了「dump 把应用盘打满」。先拆机，每件按自己的规格垂直升。在一台机器上同时上集群，只是把事故变成分布式的。见 [架构 L1 共址与拆机](/projects/architecture-evolution/colocation/)。

**Q8：你经历过的系统演进到哪个阶段了？**

按层答，不要给一个总版本号。例如：应用仍是单体、数据仍是单机未分片，**文件已经对象存储 + CDN**——因为各层瓶颈不是一起到的。单机库在写墙到来之前就是合理档位。打开[层账](/projects/architecture-evolution/ledger/)按格念。叙事对照[第六节](#my-path)。
