# 架构演进地图

> **口径说明**：本文是演进路线的方法整理，含设计目标与容量估算，**不含生产实测数据**。全文脱敏，不含企业标识、内部代号与客户信息。

一个系统从单机长到集群，要走的**不是一段路，而是五段并行的路**。

数据库、缓存、文件、应用、部署与交付——它们各有各的瓶颈、各有各的档位，而且**瓶颈到来的时间不一样**。这一页只做一件事：**把五段路的时序关系串起来**。

技术细节不在这一页。每一档的机制、参数、故障处理，都在各自板块的分册里——这里给的是「**什么时候该升、升了失去什么、怎么算升成了**」。

## 一、先看这张矩阵 {#matrix}

| 层 | V1 起步 | V2 读扩展 | V3 高可用 | V4 规模化 |
|---|---|---|---|---|
| **应用** | 单体 | — | 垂直拆分 | 微服务 |
| **数据（MySQL）** | 单机 | [主从 + 读写分离](/database/mysql/replication) | [主从 + MHA](/database/mysql/replication#failover) | [分库分表](/database/sharding/) |
| **缓存（Redis）** | 单机 / 本地缓存 | [主从](/database/redis/ha-cluster) | [主从 + 哨兵](/database/redis/ha-cluster#sentinel) | [Cluster](/database/redis/ha-cluster#cluster) |
| **文件** | 本机磁盘 | 独立文件服务 | 对象存储 | 对象存储 + CDN |
| **部署与交付** | 单进程 + 手工发版 | 多实例 + 脚本 | [容器化](/cloud-native/docker/) + [流水线](/cloud-native/cicd/) | [K8s](/cloud-native/kubernetes/) + GitOps |

**三种读法**：

| 读法 | 得到什么 |
|---|---|
| **横向读一行** | 某一层自己的演进线（MySQL 从单机到分片要走哪几步） |
| **纵向读一列** | 某个阶段所有层的样子（V3 阶段整体长什么样） |
| **看「—」** | 这一层在**这个阶段不需要动**——不是遗漏 |

> **第四列（V4）不是终点**。再往后是「多机房」与「单元化」，但那属于另一个维度的问题（地域与容灾），不在这一页的范围内。

**每档都要回答四个问题**，这是全篇的统一格式：

| 问题 | 为什么它最重要 |
|---|---|
| **触发信号** | 什么指标到了就该升——这考的是**判断力**，不是知识 |
| **新增了什么** | 拓扑与组件的变化清单 |
| **代价** | 升级后**失去**什么 |
| **验收标准** | 怎么算升成了（对应[压测报告](/projects/toolkit/perf-report/)与故障演练记录） |

> 多数技术文章只写第二项。而真实决策与面试追问里，**第一项和第三项才是分水岭**——「别人都上了」不是触发信号，「我知道它会让我失去什么」才是想清楚了的证据。

## 二、两档买「活下来」，一档买「装得下」 {#two-axes}

「单体 → 主从 → 集群」这个常见写法，把**两件不同的事压成了一条线**：

| 档位 | 新增了什么 | 它动的是哪条轴 | 触发信号 |
|---|---|---|---|
| 单机 | —— | —— | 项目起步，量还小 |
| **主从** | 从库 + 复制链路 + 读路由 | **可用性**：有了副本，读也扩了 | 读 QPS 打满主库 CPU |
| **主从 + 哨兵 / MHA** | 仲裁组件 + 自动切换 + VIP | **可用性**：不用人爬起来切主 | 无法接受人工切换的停机窗口 |
| **分片集群** | 分片中间件 + 路由规则 + 分布式 ID | **扩展性**：写与容量能横向加 | 单表过亿 / 单机磁盘打满 |

```text
        ┌─────────── 可用性轴（坏了怎么办）───────────┐
单机 ──▶ 主从 ──▶ 主从 + 哨兵 / MHA ────────▶ 分片集群
 │       ↑ 读扩展      ↑ 自动故障转移            ↑ 容量与写吞吐
 │       └─ 有副本、有备份 ─┘                    │
 └──────────────────────────────────────────────┘
                          换成扩展性轴
```

**一句话**：**前两档买的是「活下来」，最后一档买的是「装得下」。**

这两件事的触发条件完全不同，中间还夹着**最容易被跳过的一档**——很多团队上了从库就以为自己「高可用」了，其实主库挂掉仍然要人工介入。**从库解决的是「读」和「备份」，不解决「谁来切主」。**

## 三、V1 起步：单机不是落后，是成本最优 {#v1}

| 项 | 内容 |
|---|---|
| **形态** | 单应用 + 单库 + 本机磁盘 + 手工发版 |
| **为什么它是正确选择** | 在没有量的阶段，**复杂度本身就是成本**。一套 MHA 的运维成本，远高于它所防的那点停机风险 |
| **触发信号** | ① 读请求把主库 CPU 打满；② 备份需要停业务；③ 宕机损失已经超过引入高可用的运维成本 |
| **代价（留在这一档）** | 单点故障、无热备、扩容只能垂直升配（且升配有上限） |

> **这一档最该做的不是"提前上集群"，而是把出口留出来**：配置外置、不做本地会话、文件不写本地盘。这三条做对了，后面每一档的迁移成本都会大幅下降——具体见[迁移期的兼容设计](/projects/property-saas/microservice-to-k8s/#coexistence)。

## 四、V2 读扩展：主从与读写分离 {#v2}

| 项 | 内容 |
|---|---|
| **触发信号** | ① **读 QPS 打满主库 CPU**（读通常是写的几倍到几十倍）；② 需要一个不影响业务的备份窗口 |
| **新增了什么** | 从库 + binlog 复制链路 + **读写分离路由**（应用层注解或中间件） |
| **代价** | ① **主从延迟**导致「写完立即读」读到旧数据；② **切换仍需人工**；③ 多了一套要监控的东西（延迟、追平、位点） |
| **验收标准** | ① 从库稳定承担既定比例的读流量；② 复制延迟的 P95 在业务可接受区间；③ **"写后立即读"的路径已逐一识别并强制走主库**（这条最容易被漏，也最容易变成线上事故） |

**分册**：[主从复制与读写分离](/database/mysql/replication)（binlog 三步流程、三种复制模式、延迟的六大治理手段、GTID）· [Redis 持久化与主从](/database/redis/ha-cluster)

## 五、V3 高可用：没人能接受半夜爬起来切主 {#v3}

**这一档最容易被跳过。** 上了从库只意味着「有副本」，不意味着「会自动顶上」——主库挂了，从库不会自己变成主库。

| 项 | 内容 |
|---|---|
| **触发信号** | ① 无法接受**人工切换的停机窗口**（从发现到切完，几十分钟到数小时）；② 已经因为主库宕机造成过真实业务中断；③ 有明确的 RTO 要求写进了 SLA |
| **新增了什么** | **仲裁 / 管理组件**（哨兵、MHA、Orchestrator、MGR 之一）+ 自动切换流程 + 一个稳定入口（VIP / 代理层，让客户端不用改地址） |
| **代价** | ① **多了仲裁组件**——它自己也要高可用，否则变成新的单点；② **脑裂**风险（被隔离的旧主仍在接受写入）；③ 切换瞬间有一个**写失败窗口**，客户端必须能重连重试；④ 从库延迟大时切换会**丢数据** |
| **验收标准** | **做一次故障演练**：手动 kill 主库 → 记录自动切换耗时、客户端重连是否成功、有没有数据丢失。演练报告就是 V3 的验收物 |

**三条必须一起配的措施**（缺一个就会在切换时丢数）：

| 措施 | 作用 |
|---|---|
| [**半同步复制**](/database/mysql/replication#modes) | 保证切换时至少有一个从库收到了全部 binlog |
| [**GTID**](/database/mysql/replication#gtid) | 切换后从库自动定位同步点，不用人工算位点、不会重复执行事务 |
| **fencing（隔离旧主）** | 防止被网络隔离的旧主继续接受写入，造成双主 |

**分册**：[MySQL 自动故障转移](/database/mysql/replication#failover)（MHA / Orchestrator / MGR 三选一）· [Redis 哨兵](/database/redis/ha-cluster#sentinel)

## 六、V4 规模化：写扩展只能靠分片 {#v4}

**最关键的判据**：**从库扩的是读，写只能靠分片。** 加再多从库也无法提升写吞吐——这是很多人误判的地方。

| 项 | 内容 |
|---|---|
| **触发信号** | ① **单表数据量过亿**（B+ 树层高增加、索引与 DDL 成本上升）；② **单机磁盘或写 IO 打满**；③ 单机连接数成为瓶颈 |
| **新增了什么** | 分片中间件 + **分片键与路由规则** + 分布式 ID 方案 + 跨片查询的替代路径（宽表 / 数仓） |
| **代价** | ① **跨片事务与 JOIN 没了**——这是最硬的代价，它会把一批业务写法直接判死；② **扩容要搬数据**（一致性哈希 vs 取模，决定扩容时搬多少）；③ SQL 有使用限制、运维复杂度显著上升；④ 分布式 ID 带来额外组件 |
| **验收标准** | **做一次扩容演练**：加一个分片节点 → 记录迁移的数据量、耗时、期间对业务的影响。**以及跨片查询的替代链路是否真的跑通** |

**分册**：[分库分表：时机、策略与代价](/database/sharding/)（拆分时机的量化判据、四种策略、路由规则、雪花算法、扩容）

> **先想清楚能不能不分。** 分片是**不可逆**的复杂度——一旦拆开，回头的成本比拆的还高。在 V4 之前，先穷尽归档、读写分离、索引优化、以及「冷热数据分离到数仓」这几条路。

## 七、矩阵里另外两行：文件与「应用 + 部署」 {#side-lines}

### 7.1 文件：为什么没有「主从」这一档 {#file-line}

**因为文件系统的从节点是全量副本，解决的是「备份」和「读」，不解决「装得下」。** 它跟数据库主从不是一回事——数据库可以靠分片把数据摊到多台，文件副本只是让同一份数据多存几份。

| 档位 | 形态 | 触发信号 | 代价 |
|---|---|---|---|
| **V1** | 本机磁盘 | 单实例部署 | 换实例文件就丢；磁盘满即写失败 |
| **V2** | 独立文件服务（NFS / SMB） | **多实例部署后本地盘不一致**（这是最直接的信号） | 多了一个要维护的存储服务；它自己也是单点 |
| **V3** | 对象存储 | 需要容量弹性、跨可用区容灾 | 从「写本地文件」改成「上传到远端」：网络依赖、失败重试、权限模型都要重做 |
| **V4** | 对象存储 + CDN | 静态资源访问延迟成为体验瓶颈 | 缓存刷新与回源策略成为新问题 |

**分册**：[Docker](/cloud-native/docker/)（为什么"容器一删数据就没了"）· [Kubernetes 编排](/cloud-native/kubernetes/) · [DNS 与 CDN](/fundamentals/network/dns-cdn)

> **这一行的排序与数据库不同**：文件往往在人还没觉得「量大」的时候就必须先走——**因为它的触发点是「部署形态变了」，不是「数据量大了」**。这条差别正是「每层瓶颈到来的时间不一样」的第一个例子。

### 7.2 应用与部署：另一条主线 {#app-line}

应用线的演进**不是「单体 → 微服务」一步**，中间还有一档：

```text
单体（一个部署单元）
  └─▶ 垂直拆分（按业务边界分成几个独立部署单元，仍各自是单体）
        └─▶ 微服务（服务粒度更细 + 独立数据 + 治理能力）
```

**跳过「垂直拆分」直接上微服务**，是很多团队卡住的地方——因为拆不出干净的业务边界时，微服务只会把「一个难改的系统」变成「一群难改的系统」，同时额外引入分布式事务、链路追踪、配置治理。

部署线同理：**单进程 + 手工发版 → 多实例 + 脚本 → 容器化 + 流水线 → K8s + GitOps**，四阶段各自有独立的验收标准，不必一次跳到位。

**分册**：[微服务 → K8s 云原生演进](/projects/property-saas/microservice-to-k8s/)（框架聚合的收益与代价、多租户隔离、部署形态迁移的四个阶段与验收标准）

## 八、这些选择在我做过的系统里长什么样 {#my-path}

同一个人的两个系统，正好落在矩阵的不同位置——**而这个错位本身就是最有价值的部分**：

| 层 | 早期单体系统（已上线，真实运行） | 多租户 SaaS 平台（方案层，部分验证） |
|---|---|---|
| **应用** | 单体（按模块分子模块，同一进程） | 微服务 + 框架能力聚合成一个 JAR |
| **数据** | 单机 MySQL | 一主二从 + MHA |
| **分片** | 未分片 | ShardingSphere 分片（方案层） |
| **缓存** | 单机 Redis | 主从 + 哨兵 |
| **文件** | **本机目录 + 图片走 CDN** | 统一对象存储 |
| **部署** | 单机 Tomcat + 手工发版 | 容器化 + K8s |
| **可观测** | 日志文件 | 指标 + 日志 + 链路 |

**注意「文件」那一行**：左边这个系统的数据库还停在 V1（单机未分片），文件却已经走到了 V4（CDN 分发）。

**为什么？因为瓶颈到来的时间不同。** 那个系统的数据量还没大到需要分片，而图片资源的访问延迟问题先来了——于是它只在文件这一层往前走了三档。

**这就是为什么矩阵要按「层」分行、按「档」分列**：

> **演进从来不是整体推进的，而是每一层各自走到自己的档位。** 判断该不该升档，看的是**那一层的瓶颈**，而不是「别人都上了」。

**按[项目实战](/projects/)的纪律，这里必须区分三者**：早期系统的「单体 + 单机数据库 + 本机文件 + 图片走 CDN」是**已上线**的真实形态；多租户 SaaS 那一列里，多租户隔离与容器化有本地验证，而 MHA、分片、K8s 编排属于**方案层**——写出来是为了讲清判断依据，**不是声称已具备生产规模**。这类「已上线 / 已验证 / 仅方案」的三分法，见[项目题的三条红线](/projects/#interview)。

## 九、面试问答 {#interview}

**Q1：主从和分片解决的不是同一个问题，区别在哪？**

主从解决的是**可用性与读扩展**——有副本、能备份、读可以分流到从库；分片解决的是**写扩展与容量**——把数据摊到多个节点，让写吞吐和存储上限能横向加。**关键区别在于：加从库永远提升不了写吞吐。** 所以判据很清楚：读扛不住 → 加从库；**写或容量扛不住 → 只能分片**。把这两个当成"同一条路上的两档"，会导致在写瓶颈时错误地加从库、或者在本该分片时迟迟不动。

**Q2：已经有了主从，为什么还需要 MHA / 哨兵这一档？**

**因为从库不会自己变成主库。** 主从只保证「数据有一份副本」，故障切换在默认配置下仍是人工流程：发现故障 → 确认 → 提升从库 → 改客户端地址 → 重启应用，这个窗口通常是几十分钟到数小时。这一档的价值就在把这段流程自动化，并且**用一个稳定入口（VIP / 代理）把"换主"对客户端变得透明**。代价是引入了仲裁组件（它自己也要高可用）和脑裂风险。验收方式是**做一次故障演练**，而不是看配置文件里有没有开哨兵。

**Q3：什么时候该分库分表？**

先看**是不是真的分不了别的办法**——归档、索引优化、读写分离、冷热分离到数仓，这几条能解掉大部分"看起来需要分片"的问题。确实要用分片时，量化判据是三条：**单表数据量过亿**（B+ 树层高、DDL 与索引维护成本显著上升）、**单机磁盘或写 IO 打满**、**单机连接数成为瓶颈**。分片是不可逆的复杂度，**先确认代价能接受再动手**——最大的代价是跨片 JOIN 和事务没了，这会直接判死一批业务写法。

**Q4：文件存储为什么不走「主从」？**

因为文件的多副本解决的是**备份与读**，不是**容量**——它是同一份数据的全量副本，不产生新的存储空间。所以文件那条线的主轴不是「主从」，而是**换存储介质**：本机磁盘 → 独立文件服务 → 对象存储 → 对象存储 + CDN。它的触发点也跟数据库不同：**不是数据量大了，而是部署形态变了**——一旦应用多实例部署，"写本地盘"就意味着用户上传的文件在另一台机器上找不到。

**Q5：微服务为什么不建议一步到位？**

因为从单体直接到微服务，会**跳过"垂直拆分"这一档**，而这一档解决的是最难的问题：**业务边界在哪里**。边界没想清楚就拆，结果是「一个难改的系统」变成「一群难改的系统」，同时额外背上分布式事务、链路追踪、配置治理的成本。合理路径是：先在单体内部理清模块边界（模块化）→ 再按业务边界垂直拆成几个独立部署单元 → 最后才在拆分收益明确的地方做服务化。

**Q6：你经历过的系统，演进到哪个阶段了？**

按层回答，不要给一个笼统的结论——**因为各层的档位本来就不一致**。以我做过的系统为例：应用层是单体（按模块划分，同一进程），数据层是单机未分片，**但文件层已经走到了对象存储 + CDN**。原因是那个系统的数据量还没到需要分片，而图片资源的访问延迟问题先暴露了。这说明两件事：**一是演进按层独立判断，二是"没升到最高档"不等于落后**——单机数据库在小数据量下就是成本最优解。
