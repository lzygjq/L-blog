# 架构 L3 数据

> **口径说明**：这一页是[架构路线](/projects/architecture-evolution/)的架构 L3 **数据层**（MySQL）。档位只在本页内可比。前置是 [架构 L1 共址与拆机](/projects/architecture-evolution/colocation/)——先迁走、再谈主从。自动切主可跳；分片可永远不到。上云之后，主从和自动切主经常是买一台 RDS 一步完成，但仍要分清买的是哪一根轴。

## 一、两档买「活下来」，一档买「装得下」 {#two-axes}

不要压成「单机 → 集群」一步：

| 档 | 动的轴 | 触发 | 能否跳过 |
|---|---|---|---|
| **主从 + 读写分离** | **可用性 + 读** | 读把单机 CPU 打满，或备份必须停业务 | 读墙到了就该上，不要用分片代替 |
| **自动切主** | **可用性** | 无法接受人工切换的停机窗口 | **可跳**；或买云数据库时和主从一起买掉 |
| **分片集群** | **扩展性** | 单机磁盘 / 写 IO / 连接数打满 | **可不到**。加从库到不了这里 |

**一句话：主从和自动切主买的是「活下来」，分片买的是「装得下」。** 加从库永远提升不了写吞吐。从库也不会自己变成主库。

## 二、独立单机 {#standalone}

<span id="mysql"></span>

拆机之后，库已经独占磁盘，但仍是一台、一份。

| 项 | 内容 |
|---|---|
| **解决了上一档什么** | 与应用、缓存抢 IO / CPU（共址） |
| **触发信号（经验值）** | 共址期备份或写入已经互相打停 |
| **怎么拆** | 库迁独立机，规格按库自己升 |
| **升完能撑什么** | 库独占磁盘与连接；垂直升配直到单机天花板 |
| **新上限** | 读 QPS 把**主库 CPU** 打满；备份仍要和业务抢这台机的窗口 |

应用在这一档通常还是单体。不要因为「别人都主从了」就升。

## 三、主从 + 读写分离 {#replica}

| 项 | 内容 |
|---|---|
| **解决了上一档什么** | 单机的读和备份窗口 |
| **触发信号（经验值）** | 读通常是写的几倍到几十倍，主库 CPU 先到顶；需要不停业务的备份 |
| **怎么拆** | 加从库 + binlog 复制 + 读路由（注解或中间件）。写后立即读的路径**强制走主库** |
| **升完能撑什么** | **读**可随从库个数近似摊开（还要付复制延迟）；**写 = 仍然一台主** |
| **新上限** | 主库宕机仍要人切（几十分钟到数小时）；写 IO / 单表体量没被这一档放大 |

分册：[主从复制与读写分离](/database/mysql/replication)。

## 四、自动切主（可跳） {#failover}

| 项 | 内容 |
|---|---|
| **解决了上一档什么** | 人工切换窗口 |
| **触发信号（经验值）** | 已有真实宕机损失，或 SLA 写了 RTO，无法再靠人半夜操作 |
| **怎么拆** | 仲裁组件（MHA / Orchestrator / MGR 之一）+ 稳定入口（VIP / 代理）+ 半同步 + GTID + **fencing 旧主** |
| **升完能撑什么** | 体量**不变**（写仍单主）。换来的是切换从「人」变成「分钟级流程」 |
| **新上限** | 写仍等于一主；从库延迟大时切主可能丢数；仲裁组件自己要高可用，否则新单点 |
| **为何可跳** | 能接受人工窗口就不必上；云 RDS 的多可用区往往已经包含这一档，不必自建 MHA |

机房维度的切换不在本档，见[高可用](/high-availability/)。

## 五、分片集群（可不到） {#shard}

| 项 | 内容 |
|---|---|
| **解决了上一档什么** | 单主的写与容量 |
| **触发信号（经验值）** | 常规优化用尽之后仍慢。经验值：**单表约 1000 万行或约 20G**（主键点查可以更宽，聚合查询更窄）；或单机磁盘 / 写 IO / 连接数打满 |
| **怎么拆** | 先垂直分库（按业务拆库），再水平分表 / 分库。分片键、分布式 ID、跨片查询改走宽表或数仓。**先确认能不能归档、读写分离、冷热进数仓** |
| **升完能撑什么** | **写和存储**随片数涨，直到热点片或跨片查询卡住 |
| **新上限** | 跨片 JOIN / 事务没了；扩容要搬数据。分片不可逆，复杂度比拆的时候更高 |
| **为何可不到** | 多数系统写墙永远到不了。文件和 CDN 先走完、应用仍单体、库仍单机，是正常形态 |

分册：[分库分表](/database/sharding/)（含 1000 万 / 20G 的前提与「什么时候不该分」）。
