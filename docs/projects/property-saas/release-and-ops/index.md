# 发布、安全与运维

> **口径说明**：本文是架构设计记录，数值均为**设计目标与容量估算**，不是生产实测数据。可验证产出的写法见 [产出工具](/projects/toolkit/)；全文已脱敏，不含企业标识与客户信息。

## 一、背景：能力与节奏是两件事 {#background}

一套架构的真正水位，由两个互相独立的东西决定：

| 维度 | 决定什么 | 缺失时的表现 |
|---|---|---|
| **架构能力** | 系统能跑多快、扛多少 | 流量一上来就崩 |
| **发布节奏** | 你敢多久发一次版 | 系统没事，但**功能三个月不敢上线** |

第二种更常见，也更难被察觉——因为它的症状不是故障，而是"团队开始害怕发版"。而"怕发版"会反向塑造技术决策：不敢改结构、不敢换依赖、不敢动数据库，最后架构能力也一起退化。

这一篇记录三件配套的事：**敢发版的前提（发布与回滚）**、**发得起版的前提（安全与合规）**、**发完知道好不好（监控与告警）**。

## 二、安全设计：先定信任边界 {#security}

### 2.1 认证授权为什么集中在网关 {#gateway-auth}

```
登录（业主 / 员工）──▶ 网关 ──▶ 用户服务校验
    │
    └─▶ 签发令牌：访问令牌 2 小时 + 刷新令牌 7 天
              │
    网关统一校验 ──▶ 解析出「用户 + 租户」──▶ 转发下游
              │
    下游服务直接从上下文取当前用户，不再验签
```

| 方案 | 问题 |
|---|---|
| 每个下游服务各自解析令牌 | ① 每次调用多一次验签开销；② **信任边界被稀释**——只要有一个服务漏配，整条链路形同虚设 |
| 集中在网关（本方案） | 下游只需信任内部网络，边界清晰、策略统一收紧 |

> **一个容易被忽略的推论**：信任边界收敛到网关之后，"内部网络可信"就成了**必须由基础设施兑现的假设**。所以网络策略（只允许网关访问业务服务）、服务间鉴权（内部调用携带租户上下文）这两层不能省——否则"集中鉴权"只是把风险从应用层挪到了网络层。

### 2.2 接口与数据安全：一张措施清单 {#data-security}

| 措施 | 方案 | 落在哪一层 |
|---|---|---|
| API 鉴权 | 网关校验令牌 + **租户状态**（冻结/过期即拒绝） | 网关 |
| 接口限流 | 按接口 + 用户 + 租户三维限流 | 框架（缓存） |
| 防重提交 | 幂等令牌 | 框架（缓存） |
| SQL 注入 | 参数化查询；**禁止字符串拼接 SQL** | 框架（数据访问） |
| 敏感数据加密 | 身份证号加密存储；手机号展示脱敏（`138****8888`） | 框架（核心） |
| 数据权限 | 按角色/组织自动追加数据范围条件（如只能看本小区） | 框架（数据访问） |
| 支付安全 | 统一收银台 + 回调验签 + 防重放（nonce + 时间戳） | 交易域 |
| 文件安全 | 上传类型白名单 + 病毒扫描 + **私有 Bucket 签名 URL 访问** | 基础设施域 |
| 操作审计 | 关键操作记录审计日志，含操作人 / IP / 前后值 | 框架（日志） |

这张表的意义在于：**九项里有六项落在框架层**。安全能力的覆盖率取决于"能不能被顺手用上"，而不是取决于"制度要求必须做"。

### 2.3 合规边界：决定哪些功能能做 {#compliance}

SaaS 平台的合规要求不是"技术上加个开关"，而是**决定哪些功能能做、哪些必须外部合作**。四条边界：

| 合规领域 | 关键要求 | 对本架构的约束 |
|---|---|---|
| **金融业务持牌** | 保险经纪、理财推荐、放贷均需牌照 | 只做引流推荐与佣金分成，**不自营金融业务**；分期需对接持牌机构；佣金结算需完整对账流水 |
| **个人信息保护** | 告知同意、最小必要、可删除、可导出 | 人脸/身份证/手机号属敏感个人信息：单独同意 + 加密存储 + 访问审计 + 支持注销删除；**人脸特征值不建议落库，只存第三方返回的比对结果** |
| **数据安全** | 分级分类、跨境限制 | 租户数据物理隔离（企业级独立库）；数据不出境；备份加密 |
| **等保要求** | 平台级系统通常需过等保三级 | 影响架构：**日志留存 ≥6 个月**、双因素认证、传输加密、漏洞扫描与渗透测试常态化、变更留痕 |
| **行业规范** | 收费公示、账目可查 | 账单与收支明细需支持业主查询与导出；**收费规则变更需留痕** |

> **最容易被忽略的一条**：日志里会泄露个人信息。开发期习惯把请求体整条打日志（含身份证、手机号、人脸的图片地址），一旦聚合进日志平台，就等于把敏感数据复制了一份到另一个系统——而那个系统的访问控制通常比业务库宽松得多。
>
> 正确做法是在**日志切面**就完成字段掩码，而不是指望"日志系统里没人看"。这条必须在 Day 1 做：事后清理历史日志的成本极高（要跨多个索引、多次滚动删除，且无法证明清干净了）。

## 三、监控与告警：指标要分三层，告警要分两级 {#monitoring}

### 3.1 三层监控 {#three-layers}

| 层次 | 监控内容 | 为什么必须分开看 |
|---|---|---|
| 基础设施 | CPU / 内存 / 磁盘 / 网络 | 判断"是资源不够还是代码有问题" |
| 中间件 | 缓存命中率 / 消息积压 / 慢查询 | **应用层指标正常但中间件已经积压**是最常见的事故形态 |
| 应用 | QPS / RT / 错误率 / JVM / 链路 | 定位到具体服务与具体接口 |

三层缺任何一层，故障定位都会退化成猜。**链路追踪把三层串起来**：一次请求的耗时分布能落到具体的服务、方法、SQL。

### 3.2 告警分级：可执行性决定级别 {#alert-levels}

| 告警项 | 条件 | 级别 |
|---|---|---|
| 服务宕机 | 就绪副本数低于期望，持续 1 分钟 | P0（电话） |
| 接口错误率 | 5xx > 5%，持续 2 分钟 | P0（电话） |
| 支付异常 | 支付失败率 > 3% | P0（电话） |
| 安防告警 | 消防 / 周界告警 | P0（电话 + APP） |
| 接口响应慢 | P99 > 3s，持续 5 分钟 | P1（群消息） |
| 消息积压 | 积压 > 10,000，持续 10 分钟 | P1（群消息） |
| 缓存内存 | 使用率 > 80% | P1（群消息） |

> **告警的价值取决于"可执行性"**：P0 用电话、P1 用群消息，这条分界线不是形式主义——把不紧急的事叫醒人，等于让所有告警一起贬值。而且**每条告警都应配 Runbook**（怎么查、怎么处置、怎么回滚），否则半夜被叫起来的人还是要从零排查，"24 小时响应"就只是一个人的失眠。

### 3.3 日志规范：三个必带字段 {#logging}

```json
{
  "timestamp": "2026-08-07T12:00:00Z",
  "level": "INFO",
  "service": "billing",
  "traceId": "a1b2c3d4",     // ← 全链路贯通，由框架自动注入
  "tenantId": "1001",        // ← 多租户系统必备，否则无法按租户排查
  "userId": "10086",
  "method": "POST /api/bill/pay",
  "message": "缴费成功",
  "cost": 156
}
```

| 字段 | 缺了会怎样 |
|---|---|
| `traceId` | 跨服务排查变成盲人摸象——只能靠时间戳猜哪些日志属于同一次请求 |
| `tenantId` | 多租户系统里无法回答"是某个租户的问题还是全局问题" |
| 脱敏后的请求体 | 不是字段，而是一条纪律：**敏感字段在切面层掩码后再落盘**，而不是全量落盘再靠权限管控 |

采集链路：文件采集 → 消息队列 → 解析 → 搜索索引 → 看板。中间走消息队列而不是直连索引，是为了**让日志洪峰不至于拖垮存储**（日志量在故障时恰好是峰值）。

## 四、发布策略：四种方式与各自的代价 {#release}

### 4.1 策略对比 {#strategy-compare}

| 策略 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **滚动发布** | 逐批替换实例，配合就绪探针与优雅停机 | 常规业务迭代（绝大多数场景） | 发布期间新旧版本并存，**需保证接口兼容** |
| **蓝绿发布** | 部署一套完整新环境，验证后一次性切流量 | 涉及数据库结构变更、风险较高的版本 | 资源翻倍；**切换瞬间所有长连接断开** |
| **金丝雀发布** | 先放 5% 流量到新版本，观察错误率与 RT 后逐步放量 | 核心链路（缴费、支付） | 需要流量染色与按比例路由能力 |
| **灰度发布** | 按租户/用户维度放量 | **SaaS 场景** | 需处理多版本共存的数据兼容 |

### 4.2 SaaS 的灰度有天然优势 {#gray-release}

单体应用做灰度，要自己处理用户维度的路由，成本高且容易漏；而**多租户系统里租户本身就是最优的灰度单元**：

```
选定一家「合作关系好、业务量适中、愿意配合」的租户
        │
        ▼
   先行升级 → 观察 24 小时（错误率 / RT / 业务反馈）
        │
        ├─ 无异常 ──▶ 按租户规模分批放量 ──▶ 全量
        └─ 有异常 ──▶ 只回滚该租户 → 影响面被限制在一家
```

> 这条路径比技术手段更可靠，因为它**自带真实业务回归**——你不需要构造测试数据来验证业务流程，那家租户的日常操作就是最真实的用例。前置条件是租户配置与功能开关要能按租户维度下发（见 [多租户三级混合隔离](/projects/property-saas/microservice-to-k8s/#isolation-levels)）。

### 4.3 数据库变更是发布中最容易出事的一环 {#db-migration}

**代码可以秒回滚，数据库结构变更不行。** 所以数据库变更必须遵循"扩展—迁移—收缩"三步走，且每一步都可独立上线：

| 阶段 | 动作 | 为什么不能合并 |
|---|---|---|
| **① 扩展** | 只加新字段/新表，**不改不删旧结构**；新旧代码同时兼容 | 此时旧版本代码仍在跑，删旧字段会直接导致线上报错 |
| **② 迁移** | 双写新旧字段 + 后台任务回填历史数据，**校验一致性** | 历史数据是分批的，必须验证"新旧字段查出来一致"才能继续 |
| **③ 收缩** | 确认无代码依赖后，再删除旧字段 | 删除动作通常要等一两个版本周期，**不能与业务发布同步做** |

三条红线：

| 红线 | 说明 |
|---|---|
| 版本化 DDL | 用迁移工具管理，**禁止手工改生产库结构** |
| 大表 DDL 评估 | 加字段必须评估锁表时间；加索引走在线 DDL（`ALGORITHM=INPLACE`），必要时用在线改表工具 |
| 禁止发布窗口刷数 | 全表 UPDATE 这类操作必须走独立异步任务，与发布解耦 |

## 五、回滚：不是"按下按钮就回去" {#rollback}

| 故障类型 | 回滚手段 | 前置条件 |
|---|---|---|
| 应用逻辑错误 | 声明式编排回退到上一个 Git 版本 | 镜像按版本打标且长期保留 |
| 配置错误 | 配置中心回滚（保留历史版本，一键还原） | **所有配置走配置中心**，不留"手工改的配置" |
| 数据库结构错误 | **无法快速回滚**——只能通过前向修复脚本恢复 | 因此 4.3 的三步法必须严格执行 |
| 数据被错误写入 | 依赖 binlog 回档 + 人工核对 | 必须有 binlog 全量保留 + **定期恢复演练** |

> **最关键的一条**：如果新版本已经写入了旧版本不认识的数据（新字段、新状态枚举），回滚后旧版本读到这些数据会**直接报错**。所以"可回滚"必须作为发布评审的一项检查项，而不是出事时才想起来问"能不能回滚"。

### 5.1 发布检查清单 {#release-checklist}

| 检查项 | 要点 |
|---|---|
| 兼容性 | 接口是否向后兼容？新旧版本能否同时运行（滚动发布期间必然并存）？ |
| 数据库变更 | 是否遵循扩展—迁移—收缩？是否有大表锁表评估？ |
| 配置 | 新配置项是否已配好？有没有遗漏导致启动失败？ |
| **可回滚** | 有无新数据被写入导致无法回滚？镜像与配置的历史版本是否可获取？ |
| 可观测 | 新增能力是否有对应的监控与日志？**错误率、RT 的基线是否已知**？ |
| 容量 | 本次发布是否改变了资源画像（新增定时任务、增加查询）？扩容上限够不够？ |
| 发布窗口 | 是否避开业务高峰（月末缴费期）与行业高峰时段？ |

> **"基线是否已知"这条常被跳过**：如果发布前不知道正常错误率是多少，发布后看到 0.5% 的错误率就无法判断是好是坏——**没有基线的监控等于没有监控**。

## 六、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标 | 现状 | 验证方式 |
|---|---|---|---|
| 集中鉴权 | 下游零令牌解析，内部网络不可直接访问业务服务 | 设计完成 | 需网络策略配合验证（尝试绕过网关直连服务） |
| 日志脱敏 | 敏感字段在切面层掩码，日志系统内不含明文 | 设计完成 | 抽样比对日志平台内容，**尚未验证** |
| 告警有效性 | P0 告警全部可执行、且均配 Runbook | 设计完成 | 需一次完整的故障演练 |
| 灰度发布 | 可按单个租户升级与回滚 | 设计完成 | 需功能开关按租户下发的完整链路先落地 |
| 数据库变更 | 三步法全流程走通且可回滚 | 方案完成 | 在预发环境完整演练一次 |
| 备份恢复 | binlog 全量保留 + 可恢复到任意时间点 | **未验证** | 恢复演练必须定期做——**没演练过的备份等于没有备份** |

## 七、复盘与面试问答 {#interview}

**Q1：为什么鉴权要集中在网关，而不是每个服务都做？**
重复做有两个坏处：一是每次调用多一次验签开销；二是**信任边界被稀释**——只要有一个服务漏配，整条链路的鉴权就形同虚设。集中在网关后，下游只需信任内部网络。但要点是：这同时把"内部网络可信"变成了对基础设施的要求，网络策略这一层不能省。

**Q2：数据库变更为什么必须分三步做？**
因为**代码和数据不是同时切换的**。滚动发布期间新旧代码并存，删旧字段会让仍在跑的旧版本直接报错；历史数据是分批回填的，不校验一致性就不知道迁移是否完整。三步法的本质是"把一次高风险变更拆成三次低风险变更"。

**Q3：什么情况下"能回滚"是假的？**
当新版本写入了旧版本不认识的数据时。代码回退成功、数据库里却留着旧代码读不懂的字段或状态，回滚后立刻报错。所以"可回滚"要在发布评审里作为检查项，而不是出事后的期望。

**Q4：SaaS 做灰度为什么比单体容易？**
因为租户是天然的灰度单元。单体要按用户维度做流量染色和路由，SaaS 只需按租户下发开关——而且灰度期间那家租户的真实操作就是最好的回归测试，不需要另造测试数据。

**Q5：告警分级的意义是什么？**
保护 P0 的有效性。如果所有告警都发电话，一周之后就没有人认真对待任何一条。分级的前提是**每条告警都可执行**（配 Runbook），否则级别只是"打扰程度"的排序。
