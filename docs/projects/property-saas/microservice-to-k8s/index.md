# 微服务 → K8s 云原生演进

> **口径说明**：本文是架构设计记录，数值均为**设计目标与容量估算**，不是生产实测数据。可验证产出的写法见 [产出工具](/projects/toolkit/)；全文已脱敏，不含企业标识与客户信息。

## 一、背景：拆完之后，新的问题从哪来 {#background}

单体拆成微服务的动机通常只有一个——**让不同模块可以独立变更与扩容**。拆完之后，原来的问题解决了，但立刻换上来四类新问题，而且它们都不在"业务代码"里：

| 新问题 | 表现 | 如果不管 |
|---|---|---|
| **依赖漂移** | 每个服务各自声明 Spring Cloud 版本，跑着跑着版本就不一致了 | 同一个 BUG 在不同服务表现不同，排查要先确认版本 |
| **横切能力重复实现** | 鉴权、日志、异常、链路、限流、幂等，每个服务抄一遍 | N 份实现 N 套缺陷，安全策略无法统一收紧 |
| **租户维度无处安放** | SaaS 里"当前是哪个租户"要贯穿每一次数据库访问、缓存、消息、文件 | 漏一个点就串租户——**这是 SaaS 最严重的事故类型** |
| **部署形态失控** | 有人手工 `nohup`，有人写脚本，环境之间配置靠改文件 | 发布不可回滚、扩容靠加班、故障无法复现 |

这一篇记录的就是这四件事的应对方式，以及**它们的代价**——架构方案里最值得讲清楚的部分，恰恰是"我为此付出了什么"。

## 二、工程结构：框架能力为什么要聚合成一个 JAR {#framework-aggregation}

### 2.1 结构 {#structure}

```
                        ┌───────────────────────────────┐
                        │  parent POM                    │
                        │  统一 dependencyManagement      │
                        │  统一插件 / 编码 / JDK 版本      │
                        └───────────────┬───────────────┘
                                        │ 继承
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
┌───────────────┐              ┌───────────────┐              ┌───────────────┐
│  api 模块      │              │  框架聚合模块  │              │  biz 模块      │
│  对外契约       │              │  framework     │              │  业务实现       │
│  （DTO / 接口） │              │  ↓ 聚合 N 个能力│              │  依赖 api +    │
│  不依赖任何人   │              │  子模块为 1 个  │              │  framework     │
└───────────────┘              │  JAR           │              └───────────────┘
                               └───────────────┘
        ▲ 依赖方向严格单向：biz → framework → 三方库
        │ biz 之间禁止互相依赖（要通信走 api / RPC）
```

**聚合起来的那些能力**（都是"每个服务都要、且写法必须一致"的东西）：

| 能力 | 不统一会怎样 |
|---|---|
| 租户上下文与数据权限 | 串租户、越权看数据 |
| 统一响应体与全局异常 | 每个服务返回结构不同，前端要写 N 套适配 |
| 操作日志与审计 | 出事后无法追溯"谁改了什么" |
| 链路追踪与埋点 | 跨服务排查变成盲人摸象 |
| 缓存 / 分布式锁封装 | key 命名冲突、锁粒度不一致 |
| 消息发送与消费封装 | 幂等与重试策略各写各的 |
| 幂等组件 | 支付、下单这类链路重复执行 |
| 文件存储抽象 | 换存储要改所有服务 |
| 加解密与脱敏 | 敏感字段处理不一致 |
| 监控指标接入 | 指标命名与维度不统一，看板无法合并 |

### 2.2 收益与否决的替代方案 {#aggregation-tradeoff}

| 方案 | 做法 | 结论 |
|---|---|---|
| **每个服务自己引三方依赖** | 谁用谁声明 | ❌ 版本漂移、能力重复实现，回不到统一治理 |
| **每个能力一个 starter，业务按需引入** | 依赖清晰、可裁剪 | ⚠️ 设计上更"正确"，但**接入成本高**：新服务要引十几个坐标，且很容易漏引导致能力缺失 |
| **聚合成一个 JAR**（本方案） | 业务侧只引一个坐标 | ✅ 接入成本最低、能力演进对业务透明 |

**选聚合的理由是"接入成本"这一项压倒性重要**：在一个服务数量持续增长、且开发人员会轮换的项目里，**"漏引一个 starter 导致某个能力静默失效"**的风险远高于"多引了几个用不到的包"。让正确的事情变成默认行为，比让依赖图更优雅更重要。

### 2.3 代价：必须明说的四条 {#aggregation-cost}

这是这一节真正的重点——**聚合不是免费的**：

| 代价 | 具体表现 | 缓解手段 |
|---|---|---|
| **传递依赖不透明** | 业务方不知道引一个坐标会带进什么 | 输出依赖树做基线；用 `<exclusions>` 收敛冲突；BOM 统一版本 |
| **无法按需裁剪** | 不用消息队列的服务也被带进 MQ 客户端 | 可选能力用**条件装配**（`@ConditionalOnClass` / `@ConditionalOnProperty`）而非硬编码依赖 |
| **升级即全量回归** | 改一处框架，所有业务服务都要重新验证 | 框架版本语义化 + **灰度升级**（先非核心服务）+ 变更影响面清单 |
| **与 Spring Boot 版本强绑定** | Boot 大版本升级会被框架拖住 | 框架不封装 Boot 已有的能力；只做"编排与约定"，不做"替代" |

**一条硬约定**（写进工程规范，否则结构会腐化）：

> **框架模块只允许依赖三方库，禁止依赖任何业务模块。** 业务模块之间也禁止互相依赖，跨服务通信只走 `api` 契约。

违反它的后果不是"不好看"，而是**依赖图里出现环**——一旦成环，构建顺序、版本发布、甚至能不能单独编译都变成问题。

### 2.4 什么时候该拆回 starter {#when-to-split}

聚合是**当前规模下的最优解**，不是终点。出现下面任一信号，就该把可选能力拆成独立 starter：

1. 框架 JAR 的体积或依赖面成为业务方的负担（例如明显拖慢了启动或镜像体积）；
2. "按需引入"变成刚性需求（不同技术栈的服务要复用同一套能力）；
3. 框架升级的影响面已经大到无法一次性回归。

**演进路径**：`一个聚合 JAR` → `核心 JAR + 若干可选 starter`。第一步的聚合是必要的（先把约定建立起来），第二步的拆分才有意义。

## 三、多租户：三级混合隔离 {#multi-tenant}

### 3.1 三档隔离级别 {#isolation-levels}

"多租户"不是一个是非题，而是一个**隔离强度的选择**：

| 级别 | 数据存放 | 隔离强度 | 成本 | 适合 |
|---|---|---|---|---|
| **L1 共享库 + 租户字段** | 同一库同一表，靠 `tenant_id` 区分 | 逻辑隔离（最弱） | 最低 | 小租户、内部系统 |
| **L2 独立 Schema** | 同实例、独立库/Schema | 中等 | 中 | 中租户、需要单独备份 |
| **L3 独立库 + 独立部署** | 独立实例 + 独立运行单元 | 强 | 最高 | 大租户、合规要求 |

**混合的意义在于"租户会长大"**：新入驻的小物业公司按 L1 承接，规模上来后迁移到 L2，达到阈值或提出合规要求时再升到 L3。**分档的设计目标就是让这个迁移是可执行的**——如果 L1 的数据模型里没有干净的租户边界，将来就升不上去。

| 决策维度 | 倾向 L1 | 倾向 L2 / L3 |
|---|---|---|
| 租户规模 | 小、数量多 | 单个租户体量很大 |
| 合规与审计 | 无特殊要求 | 要求数据物理隔离 |
| 备份与恢复 | 可接受整库恢复 | 要求按租户恢复 |
| 成本敏感度 | 高 | 低 |
| 定制化程度 | 无定制 | 需要独立配置甚至独立版本 |

### 3.2 落地点 {#isolation-implementation}

| 环节 | L1（共享库） | L2（独立 Schema） | L3（独立库/部署） |
|---|---|---|---|
| **路由** | 无（同一数据源） | 按租户切换数据源 | 完全独立 |
| **过滤** | 所有查询自动追加 `tenant_id` | 无需过滤 | 无需过滤 |
| **备份** | 整库 | 按 Schema | 按实例 |
| **升级** | 一次完成 | 一次完成 | 独立节奏 |

**共享库模式下必须守住的一条**：**租户过滤不能靠开发人员记得写。** 任何"要人在每次查询前加条件"的方案最终都会漏。正确做法是**在框架层拦截**（MyBatis 拦截器 / 数据权限组件）——在 SQL 拼装阶段自动注入租户条件，并保留"显式声明跨租户"的白名单出口（用于平台运营侧统计），让绕过成为**需要显式声明的例外**，而不是默认行为。

**L3 与编排层的配合**：独立库的租户同时应该是**独立命名空间 + 独立部署 + 配额约束**的组合，而不是"数据库分开了、应用还混在一起"。隔离的四维度（计算配额、网络策略、RBAC、存储类）见 [Kubernetes 多租户隔离](/cloud-native/kubernetes/#multi-tenant)。

## 四、横切点的租户传播：漏一个就串租户 {#tenant-context}

隔离级别解决的是"数据放哪"，**上下文传播**解决的是"当前请求属于谁"。后者才是事故高发区。

```
HTTP 请求 ──▶ 拦截器解析租户标识 ──▶ TenantContext（ThreadLocal）
                                          │
        ┌──────────────┬──────────────┬────┴─────────┬──────────────┐
        ▼              ▼              ▼              ▼              ▼
    同步业务调用    异步线程池      消息消费        定时任务       缓存 / 文件
    ✔ 天然继承     ⚠ 线程复用会串   ⚠ 需从消息头恢复 ⚠ 需显式设定    ⚠ key 必须带租户
```

| 横切点 | 风险 | 处理 |
|---|---|---|
| **异步线程池** | 线程复用导致上下文残留（A 租户的请求跑到 B 租户的线程上） | 用可传递的上下文（如 `TransmittableThreadLocal` + 线程池装饰），或**提交任务时显式捕获并传入**，任务结束务必清理 |
| **消息消费** | 消费线程没有 Web 请求上下文 | 租户标识**写进消息头**，消费侧先恢复上下文再处理 |
| **定时任务** | 任务无租户概念，要么全租户跑一遍，要么漏跑 | 任务按租户**分片遍历**，每个分片显式设定上下文；同时保证同一任务不被多副本重复执行（见 [分布式任务调度](/java/spring/spring-cloud/scheduling#no-dup)） |
| **缓存 key** | 不拼租户前缀 → 跨租户读到别人的数据 | key 统一由框架拼装租户前缀，业务侧禁止手写完整 key |
| **文件与对象存储** | 路径不隔离 → 可枚举到其他租户的文件 | 路径强制包含租户段；签名 URL 也要带租户校验 |
| **连接池与事务** | 切了数据源但事务已开启，切不回来 | 数据源切换必须在**事务开启之前**完成；跨租户事务一律禁止 |
| **日志与链路** | 排查时无法判断归属 | MDC 里带上租户标识，与 traceId 一起输出 |

> **一条经验**：租户上下文这种东西，**"默认正确 + 显式例外"才是可维护的形态**。任何依赖"开发人员记得处理"的横切点，早晚会出事故；而出事故时通常已经写进了别人的数据库。

## 五、部署形态迁移路线 {#migration}

从"手工发版"到"声明式编排"**不要一次跳到位**。分四阶段，每阶段有独立收益与验收标准：

| 阶段 | 做什么 | 验收标准 | 参考 |
|---|---|---|---|
| **① 容器化** | 应用打成镜像；**配置与镜像分离**；本地与测试环境用同一镜像 | 同一镜像在本地与测试环境行为一致；配置全部来自环境变量/配置中心 | [Docker](/cloud-native/docker/) |
| **② 上编排** | Deployment + Service + Ingress；配三类探针；资源 requests/limits 显式声明 | Pod 挂掉自动重建；发版可滚动、可回滚；探针能让流量只进健康实例 | [Kubernetes](/cloud-native/kubernetes/) |
| **③ 弹性与自愈** | HPA + 就绪门控 + 优雅停机 + 中断预算 | 峰值能自动扩容；缩容不丢在途请求；节点维护不中断服务 | [Kubernetes](/cloud-native/kubernetes/#hpa) |
| **④ 交付链路** | 流水线构建 → 镜像 → 部署；镜像标签不可变；环境配置分离；GitOps 或等价机制 | 一次提交可自动走到测试环境；回滚是一次版本切换而不是重新构建 | [CI/CD](/cloud-native/cicd/) |

### 5.1 迁移顺序的两条原则 {#migration-order}

1. **先无状态，后有状态。** 应用服务（API / 定时任务 / 消费者）先上，数据库、缓存、消息这些有状态组件**初期不搬**——迁移的是应用形态，不是数据。有状态组件进编排需要 Operator 与更完整的运维能力，属于后续独立议题。
2. **先读路径，后写路径。** 灰度先从查询类流量开始（出问题只影响看），写路径（缴费、开门、下单）最后切——它们的失败代价不对称。

### 5.2 迁移期的兼容设计（最容易被忽略的一段） {#coexistence}

迁移不是"切开关"，**新旧两套形态会长时间并存**，这期间的设计决定迁移能不能平滑：

| 问题 | 处理 |
|---|---|
| 两套环境都要能跑 | 应用**不假设自己跑在哪里**：配置全部外置，不读本机路径、不绑定固定 IP |
| 会话与登录态 | 登录态放到共享存储（Redis），**不做本地会话**，否则滚动发布时会掉线 |
| 定时任务重复执行 | 迁移期新旧同时在线 → 必须靠**调度侧互斥**保证只有一个执行者 |
| 文件上传 | 统一走对象存储，不落本地盘——否则实例换了文件就找不到 |
| 日志与指标 | 一律输出到标准输出/采集端，**不写本地文件**，与容器形态保持一致 |
| 灰度与回滚 | 按**功能开关**而非"部署哪套"来控制，回滚不依赖重新发版 |

## 六、发布与回滚 {#release}

| 关注点 | 做法 | 反例 |
|---|---|---|
| **镜像标签** | 不可变（提交号/构建号）；**禁用 `latest`** | 用 `latest` → 回滚时不知道该回哪个 |
| **配置** | 与镜像分离，按环境注入 | 配置打进镜像 → 一个镜像只能跑一个环境 |
| **发布策略** | 滚动更新（常规）/ 金丝雀（高风险变更） | 全量替换 → 出问题影响所有用户 |
| **回滚** | 切回上一个**不可变版本**；数据库变更用**扩展-收缩**（先加列兼容，双写期后再删旧列） | 回滚时执行反向 DDL → 数据可能已经不一致 |
| **健康判定** | 就绪探针决定能否接流量；存活探针只判断"进程是否卡死" | 存活探针查依赖 → 依赖抖动导致全部实例重启（雪崩） |

## 七、设计目标与尚未验证的部分 {#targets}

**这一节是这类文档里最有价值的一节**——它把你的方案从"看起来很完整"变成"边界清楚"。

| 项 | 设计目标（估算，非实测） | 验证方式 |
|---|---|---|
| 多租户隔离 | 小租户共享、中租户独立 Schema、大租户独立部署，且 L1→L2→L3 的迁移路径可执行 | 按租户规模分布的压测 + 一次真实的跨级迁移演练 |
| 峰值写入（批量出账） | 月初峰值下出账任务可在维护窗口内完成，且任务**重跑幂等** | 造数压测 + 重跑验证（见 [压测报告模板](/projects/toolkit/perf-report/)） |
| 租户上下文零泄漏 | 所有横切点（异步/消息/定时/缓存/文件）都不串租户 | **多租户并发用例**：多租户同时跑同一批接口，交叉校验结果归属 |
| 发布可回滚 | 任意一次发布可在数分钟内切回上一不可变版本 | 演练：制造一次"坏版本"，测回滚耗时 |
| 容量弹性 | 峰值自动扩容、峰后回收，缩容不丢在途请求 | 压测 + 缩容观察（重点看优雅停机） |

**明确未验证 / 待补**：

- 上述数值均为**估算**，尚未用真实流量标定——**没有压测数据的容量数字不应该对外当结论讲**；
- 多租户跨级迁移（L1 → L2）目前只设计了路径，**没有做过完整演练**；
- 有状态组件（数据库/消息/缓存）仍运行在容器之外，其高可用与编排化是独立议题，不在本文范围。

## 八、复盘与面试问答 {#interview}

**Q1：框架能力为什么要聚合成一个 JAR？代价是什么？**
收益是**接入成本最低**：新服务只引一个坐标就拿到全部横切能力，能力演进对业务透明。在一个服务数量持续增长、人员会轮换的项目里，"漏引某个 starter 导致能力静默失效"的风险远高于"多引了几个用不到的包"。代价有四条：传递依赖不透明、无法按需裁剪、升级即全量回归、与 Spring Boot 版本强绑定。缓解手段是条件装配、BOM 统一版本、灰度升级，以及一条硬约定——**框架只能依赖三方库，不能依赖业务模块**。

**Q2：多租户隔离级别怎么选？**
按"租户规模 + 合规要求 + 成本"三轴分档：小租户共享库靠 `tenant_id` 过滤（成本最低）；中租户独立 Schema（可单独备份）；大租户独立库 + 独立部署（强隔离）。**关键是混合而不是选一个**——租户会长大，所以 L1 的数据模型必须留清洁的租户边界，否则将来升不上去。共享库模式下有一条底线：**租户过滤必须在框架层自动注入，不能靠开发人员记得写**，并把跨租户查询做成需要显式声明的例外。

**Q3：为什么说"异步和消息消费"是租户隔离的事故高发区？**
因为租户上下文通常存在 `ThreadLocal` 里，而它是**线程绑定**的。异步线程池存在线程复用——A 租户的上下文会残留到 B 租户的任务上；消息消费线程没有 Web 请求上下文，不主动恢复就等于"没有租户"。同理还有定时任务（无请求上下文）、缓存 key（不拼租户前缀就会读串）、文件路径（不隔离就能被枚举）。**处理原则是"默认正确 + 显式例外"**：由框架统一处理，而不是靠人记得。

**Q4：微服务上 K8s，迁移顺序怎么定？**
两条原则：**先无状态、后有状态**（先搬应用，数据库/消息/缓存初期不动——迁移的是应用形态不是数据）；**先读路径、后写路径**（灰度从查询流量开始，写路径最后切，因为失败代价不对称）。分四阶段：容器化（配置与镜像分离）→ 上编排（探针 + 资源声明）→ 弹性自愈（HPA + 优雅停机）→ 交付链路（不可变标签 + 可回滚）。

**Q5：迁移过程中最容易忽略的是什么？**
**新旧两套形态会长期并存**，这期间的设计决定迁移能不能平滑：应用不能假设自己跑在哪里（配置全外置、不读本机路径、不绑固定 IP）；登录态必须放共享存储（否则滚动发布掉线）；定时任务要靠调度侧互斥（新旧同时在线会重复执行）；文件必须落对象存储、日志必须输出到标准输出（本地文件在实例切换后就丢了）；灰度用功能开关而不依赖"部署了哪套"。

**Q6：发布的"不可回滚"通常是怎么造成的？**
两个常见根因：**镜像标签用 `latest`**（回滚时不知道该回哪个版本），以及**数据库变更不可逆**（回滚应用时执行反向 DDL，而数据状态已经变了）。所以要做两件事：标签不可变；数据库变更走**扩展-收缩**——先加新列并双写兼容，等新版本稳定后再删旧列，让"回滚应用"永远不需要"回滚数据"。
