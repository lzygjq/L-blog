# 核心业务链路：账单、门禁与交易

> **口径说明**：本文是架构设计记录，数值均为**设计目标与容量估算**，不是生产实测数据。可验证产出的写法见 [产出工具](/projects/toolkit/)；全文已脱敏，不含企业标识与客户信息。

## 一、背景：架构是被业务约束逼出来的 {#background}

物业 SaaS 的功能清单很长——基础物业、品质安防、设备能耗、增值服务、电商金融、运营决策，拆下来是十几个领域模块。但**模块多不等于架构难**：真正决定这套系统能不能撑住的，只有三条链路。

| 分类 | 领域模块 | 优先级 | 架构上真正难的地方 |
|---|---|---|---|
| 基础物业 | 房产 / 收费 / 报修 / 门禁 / 车辆 / 设备 / 合同 | P0（车辆、设备 P1） | 出账的峰值写入与金额强一致 |
| 品质安防 | 品质巡检 / 安防消防 | P0 / P1 | 高频短请求（打卡、通行）与硬件接入 |
| 设备能耗 | 能耗采集与分析 | P1 | 物联网协议差异、指标口径统一 |
| 社区增值 | 家政 / 邻里 / 投票 / 装修 | P1 | 低频，复杂度低 |
| 电商金融 | 社区电商 / 团购 / 积分 / 支付 | 新增 | 库存一致性、状态机、退款对账 |
| 运营决策 | 数据大屏 / 事件调度 / 报表 / 告警 | P0 | 分析负载不能压业务库 |

### 1.1 三条关键链路，以及它们各自强加的约束 {#three-flows}

把"业务特点"翻译成"架构约束"，是整条设计链的起点。**跳过这一步，后面所有选型都是在猜。**

| 链路 | 业务特点 | 强加的架构约束 |
|---|---|---|
| **账单与缴费** | 每月 1 号批量出账，缴费集中在月末 2~3 小时 | 批量任务必须**可重跑、幂等**；写入要**异步削峰**；金额必须**定点类型**；支付回调必须**防重复入账** |
| **门禁与访客** | 硬件协议各异，早高峰瞬时并发高，弱网常见 | 设备接入层要**收敛协议**；验证路径必须**多级缓存**；网络断开时**必须可用** |
| **社区交易** | 秒杀式抢购、预扣库存、退款与分账 | 库存**不能超卖**；订单是**状态机**；退款与分账需要**可对账的流水** |

### 1.2 三条链路共用的两块地基 {#shared-foundation}

三条链路的实现方式完全不同，但都压在同样两块地基上：**数据模型（谁的库、谁的表、租户列在哪）** 和 **公共框架（幂等、缓存、消息、审计怎么统一）**。先把地基讲清楚，再讲链路。

## 二、数据模型：先定边界，再写代码 {#data-model}

### 2.1 一个基类解决四件事 {#base-entity}

所有业务实体继承同一个基类，它强制带来四组字段——这四组字段是"约定"，不是"建议"：

```java
public abstract class BaseEntity {
    private Long id;

    @TableField(fill = FieldFill.INSERT)
    private Long tenantId;          // ① 租户列：由拦截器自动填充，业务代码不得手写

    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createTime;   // ② 审计四件套
    @TableField(fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updateTime;
    private Long createBy;
    private Long updateBy;

    @TableLogic
    private Integer deleted;        // ③ 逻辑删除：所有查询自动带上条件
}
```

| 字段组 | 为什么必须由框架写，不能由业务写 |
|---|---|
| `tenantId` | 一旦允许业务手写，就必然出现"某个 Service 忘了填"的串租户缺陷。**框架填充 + 查询拦截器自动追加条件**，才是双保险 |
| 审计四件套 | 出事时要能回答"谁在什么时候改的"。分散在各业务里实现，覆盖率永远到不了 100% |
| `deleted` | 物理删除会让历史账单、通行记录对不上账。物业系统的数据**几乎不允许真删** |

### 2.2 服务独占自己的库 {#db-ownership}

**每个服务独立一个数据库，服务之间只能走 API 或消息，禁止跨库 JOIN。**

| 做法 | 结论 |
|---|---|
| 所有表挤在一个库，按表名前缀区分 | ❌ 看似省事，实际是"分布式单体"——任何一次表结构变更都要全站评审 |
| 服务独占库 + API 交互（本方案） | ✅ 边界清晰、可独立演进；代价是**跨域查询要额外设计**（走数仓或聚合接口） |
| 服务独占库 + 允许跨库只读 | ⚠️ 折中方案，但要明确"只读"这条红线，否则会退化成第一种 |

### 2.3 分片：先算清楚什么时候才需要分 {#sharding}

分片不是越早越好——**过早分片会把复杂度提前塞进每一次查询**。判据是单表行数与写入压力。

| 表 | 分片键 | 起始分片数 | 为什么用这个键 |
|---|---|---|---|
| 账单 / 支付流水 | 租户 + 小区 取模 | 4 | 账单按小区批量生成、按小区对账，**同小区同分片**才能保住批量事务 |
| 报修工单 | 租户 + 业主 取模 | 4 | 查询以"我的报修"为主 |
| 电商订单 | 租户 + 业主 取模 | 4 | 同上 |
| 抄表读数 | 租户 + 小区 取模 | 4 | 按月批量写入，量大且模式固定 |
| 告警事件 / 巡检记录 | 租户 + 小区 取模 | 4 | 写入频繁、查询都以小区为单位 |

**关键约定：账单与支付流水必须同分片键、同分片数** —— 否则"更新账单状态 + 写支付流水"这件事就跨库了，本地事务直接失效。

演进路径按用户规模走，每一档都有明确的触发条件：

| 阶段 | 用户规模 | 数据库形态 |
|---|---|---|
| Phase 1 | 万级 | 单机 MySQL，**不分片** |
| Phase 2 | 十万级 | 1 主 2 从 + 高可用切换 + 4 分片 |
| Phase 3 | 三十万级 | 8 分片 + 读写分离 + CDC 同步数仓 |
| Phase 4 | 六十万级 | 16 分片 + 冷热分离 + 独立 OLAP |

分片扩容走**双写迁移**，不停服：新老分片同时写 → 后台回填 → 校验一致 → 切读 → 停旧写。

### 2.4 归档：只分片不归档，成本会失控 {#archive}

这是最容易漏、也最贵的一步。**账单、支付流水、通行记录、巡检记录、告警事件**这五类表年增量最大，运行三年后单表可达千万行。

> **归档不是优化项，是必选项。** 只分片不归档，分片数会一路膨胀到成本失控——因为分片解决的是"单表太大"，而不是"数据太老"。

| 项 | 做法 |
|---|---|
| 触发 | 定时任务每月执行，迁移 12 个月前的数据 |
| 去向 | 冷库（对象存储 / 搜索引擎索引），**只读不写** |
| 查询 | 热数据走关系库索引，历史数据走冷库索引；对外提供统一查询入口 |
| 红线 | **先写、再验、最后删** —— 迁移任务必须校验条数与金额合计后才允许删源数据 |

## 三、账单生成与缴费：峰值写入与强一致 {#billing}

### 3.1 出账是一条异步链路，不是一个事务 {#billing-flow}

```
每月 1 号  定时任务（分片执行，避免多副本重复跑）
   │
   ├─▶ 按小区批量生成账单 ──▶ 写账单表（分片键保证同小区同片）
   │
   └─▶ 发消息 ──▶ 通知服务 ──▶ APP 推送 + 短信
```

三个设计点：

| 点 | 做法 | 不管会怎样 |
|---|---|---|
| 定时任务防重复 | 调度平台分片 + **执行权互斥** | 多副本同时跑，账单翻倍生成 |
| 批量写入的粒度 | 按小区分批提交，**单批固定条数** | 一个小区几万条放一个事务，回滚代价与锁持有时间都不可控 |
| 失败重跑 | 以"租户 + 小区 + 账期"为**业务唯一键**做幂等 | 重跑即重复出账，这是最严重的资金类事故 |

详见 [分布式任务调度](/java/spring/spring-cloud/scheduling#no-dup)。

### 3.2 三个正确性问题，比性能更优先 {#billing-correctness}

| 问题 | 错误做法 | 本方案 |
|---|---|---|
| **金额精度** | 用 `double` 存金额 | 定点类型（`DECIMAL` / `BigDecimal`），**分位为最小单位**，禁止浮点参与金额运算 |
| **回调重复** | 收到支付回调就更新状态 | 业务唯一键 + 状态机（待支付 → 已支付 → 已退款）+ 幂等表；**重复回调必须返回成功而不是报错**，否则第三方会持续重推 |
| **并发修改** | 读出来判断再写回去 | 状态流转用**条件更新**（`WHERE status = 期望值`），靠受影响行数判断是否抢占成功 |

详见 [接口幂等](/java/spring/spring-cloud/idempotency#solutions) 与 [分布式事务](/java/spring/spring-cloud/transaction#mq-idempotent)。

### 3.3 缴费链路：每一步都要能重放 {#payment}

```
业主 APP ──▶ 网关（鉴权 + 租户解析）
   │
   ├─▶ 收费服务：创建支付单（幂等键 = 租户 + 账单号 + 请求号）
   │       └─▶ 分布式锁防止同一账单重复发起
   │
   ├─▶ 统一收银台 ──▶ 第三方支付
   │
   └─▶ 回调 ──▶ 验签 + 防重放（nonce + 时间戳）──▶ 更新账单状态
            │
            ├─▶ 发消息 ──▶ 通知服务（推送成功通知）
            └─▶ 异步 ──▶ 生成电子发票 ──▶ 文件服务
```

**这条链路上写入必须"不降级"**：查询类接口在依赖服务故障时可以返回缓存或基础信息，但资金链路只能**限流排队**，绝不能降级成"稍后重试"（详见 [容量测算与压测方案](/projects/property-saas/capacity-and-perf/#protection)）。

## 四、门禁与访客：把不确定性挡在业务之外 {#access}

门禁的难点不在业务逻辑，在**硬件**：协议各异、网络不稳、时间不可控。

### 4.1 通行验证：两级缓存 + 异步落库 {#access-cache}

```
刷卡 / 刷脸 ──▶ 门禁服务
   ├─ 一级：本地缓存（设备侧白名单，断网也能开）
   ├─ 二级：Redis（租户 + 人员 + 权限，TTL 分钟级）
   └─ 三级：关系库（兜底 + 写缓存）
                 │
                 └─▶ 开闸 + 通行记录异步入消息队列 ──▶ 批量入库 / 冷库
```

| 设计点 | 为什么 |
|---|---|
| 记录**异步**落库 | 早高峰通行是高频短请求，同步写库会把峰值直接压到数据库上 |
| 缓存**分层** | 设备侧缓存是"断网可用"的物理保证，Redis 是"低延迟"的性能保证 |
| 权限变更**主动失效** | 只靠 TTL 会导致"已注销人员仍能开门"——变更时必须主动清缓存 |

### 4.2 访客邀请码：一个 TTL 就够了吗 {#visitor}

访客码是"临时凭证"，看上去一行 `SET key value EX 86400` 就能实现，实际有四个边界：

| 边界 | 处理 |
|---|---|
| 有效期 | Redis TTL（如 24 小时），**过期即失效**，不依赖定时清理 |
| 一次性 | 首次验证通过后立即删除（或标记已用），防止转发复用 |
| 范围 | 码与"小区 + 门禁点 + 业主"绑定，不能跨小区使用 |
| 追溯 | 验证记录必须落库（谁邀请的、谁用了、什么时候），Redis 不承担审计职责 |

### 4.3 弱网与离线降级 {#offline}

**离线可用是门禁的硬需求，不是可选项**——小区断网时不能把业主关在门外。策略是"降级但要留痕"：

| 策略 | 做法 | 恢复后 |
|---|---|---|
| 设备侧白名单 | 定期下发本门禁点的高频通行人员到设备本地 | 网络恢复时同步版本号 |
| 离线放行 | 设备本地判定 + 记录到本地队列 | 恢复后**补传**记录，服务端按时间戳合并 |
| 时间一致性 | 设备定期校时；补传记录以**设备时间**入账，同时记服务端接收时间 | 便于事后排查"时间对不上" |
| 熔断 | 后台服务连续失败时，设备降级为本地判定 | 避免"服务慢导致开门慢" |

## 五、社区交易：库存、状态机与退款 {#commerce}

社区电商的形态是"低 SKU、高频次、强信任"，技术上重点在三处：

| 环节 | 做法 | 关键约束 |
|---|---|---|
| **下单** | 创建订单（待支付）→ **预扣库存**（Redis 预减，防超卖）→ 消息队列排队 | 预扣不落库，只保证"名额"；真实扣减在支付成功后 |
| **支付超时** | 定时任务扫超时未支付订单 → 关单 + **回补预扣** | 回补必须幂等，重复回补等于凭空加库存 |
| **退款** | 发起 → 审核 → 退回原渠道 + 回退积分 | **必须与原支付单一一对应**，退款流水独立成表 |
| **分账** | 团购达标后按规则结算给团长 / 商户 | 分账依赖完整流水，**先有账再有钱** |

订单状态用**状态机**表达，而不是散落的布尔字段——状态机的好处是"非法流转在编译期/校验期就被拒绝"，而不是上线后靠数据修复。

### 5.1 一条业务链路的完整剖面：框架层在哪几个点介入 {#framework-in-flow}

把框架能力标在链路上，才能看出"公共框架"到底省掉了什么：

```
业主缴费请求
  ① 网关          → JWT 鉴权 + 租户解析
  ② 租户过滤器     → 恢复租户上下文到当前线程
  ③ 控制器         → 权限注解校验 → 全局异常处理
  ④ 业务服务
      ├── 数据访问  → 多租户拦截器自动追加 tenant_id
      ├── 缓存      → 分布式锁防止重复缴费
      ├── 消息      → 事务消息推送通知
      └── 远程调用  → 获取业主信息
  ⑤ 操作日志       → 注解式自动记录审计日志
  ⑥ 统一响应       → 统一返回结构
```

这六步里，**业务代码只写了第 ④ 步**。这就是把横切能力聚合成一个框架 JAR 的收益——接入成本低、且能力演进对业务透明。代价与拆分时机见 [微服务 → K8s 云原生演进](/projects/property-saas/microservice-to-k8s/#aggregation-cost)。

## 六、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标 | 现状 | 验证方式 |
|---|---|---|---|
| 出账幂等 | 同一租户同一小区同一账期重复执行不产生重复账单 | 设计完成 | 用压测环境的重复调度 + 账单条数对比验证 |
| 缴费链路 | 目标峰值下 P99 < 1s、重复回调不产生重复入账 | 设计完成 | 见 [压测方案](/projects/property-saas/capacity-and-perf/#pressure-test) |
| 门禁离线降级 | 断网 30 分钟内正常放行，恢复后记录补传无丢失 | 设计完成 | 需现场设备配合演练，**尚未验证** |
| 分片扩容 | 双写迁移过程不停服、数据零丢失 | 方案完成 | 需在预发环境完整演练一次（含回填校验） |
| 归档任务 | 迁移后可校验条数与金额合计，且先写再验最后删 | 方案完成 | 用 12 个月以上的模拟数据验证一轮 |

**明确不做的**：AI 视觉算法（陌生人识别、高空抛物溯源）不自研，走第三方能力接入；物业行业大模型不自研。理由不是技术不可行，而是**这类能力是重资产**（自研投入以年计、需要大量现场数据喂养），与"把研发集中在多租户与工程化"的策略冲突。

> 这一节不是"方案不完整"，而是**边界声明**：面试里最能证明你想清楚了的地方，往往是你明确说"这个我不做、以及为什么"。

## 七、复盘与面试问答 {#interview}

**Q1：为什么账单和支付流水要用同样的分片键？**
因为"更新账单状态 + 写支付流水"必须在一个本地事务里。分片键不同就意味着跨库，本地事务直接失效，只能退到分布式事务——用一次分片键设计就能避免的事，不要用分布式事务去补。

**Q2：出账任务为什么不能只靠分布式锁防重复？**
锁只解决"同时只有一个人在跑"，解决不了"跑了一半失败后重跑"。真正的防线是**业务唯一键 + 幂等**：即使同一账期被生成两次，数据库也只接受一条。

**Q3：门禁为什么要把权限缓存放到设备本地？**
因为门禁的核心指标是"断网也必须能开门"。Redis 再可靠，链路断了就是不可用；设备本地白名单是唯一不受网络影响的防线。代价是权限变更会有延迟，所以必须做**主动失效 + 版本号同步**。

**Q4：支付回调为什么重复了还要返回成功？**
因为第三方支付平台的重推机制以"是否收到成功响应"为准。重复回调返回失败，会引发无限重推，把一个小概率事件放大成持续故障。正确做法是**认出来、不重复入账、然后返回成功**。

**Q5：归档为什么不能等到数据多了再做？**
因为归档的执行依赖"数据还不太多"这个前提——存量数据一旦到亿级，第一次全量迁移本身就是一次高风险操作。归档要从有数据增长的那天开始做，而不是从有性能问题的那天开始做。
