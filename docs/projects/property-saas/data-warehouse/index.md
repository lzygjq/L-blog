# 大数据架构方案 → 数仓落地

> **口径说明**：本文是架构设计记录，数值均为**设计目标与容量估算**，不是生产实测数据。选型部分的写法可对照 [ADR 架构决策记录](/projects/toolkit/adr/)；全文已脱敏，不含企业标识与客户信息。

## 一、背景：报表把业务库压垮了 {#background}

系统的分析需求是**逐步长出来的**：先是几张固定报表，然后是可下钻的看板，再然后是"能不能按项目、按收费项、按时间段任意组合查一下"。每一步都合理，但叠加起来的负载形态与在线交易完全不同：

| 现象 | 后果 |
|---|---|
| 看板查询与在线缴费抢同一份 CPU 和 IO | **高峰期缴费变慢**，直接影响收入与体验 |
| 一个 `COUNT(DISTINCT)` 级别的查询就能跑数十秒 | 无法支撑"随时打开、随时下钻"的看板 |
| 报表需要的历史跨度越来越长 | 业务库不敢删数据，容量与备份成本持续上升 |
| 报表口径散落在各服务的 SQL 里 | 同一个"收缴率"在不同报表里算法不同 |

**转折点的判断标准很简单**：当"分析查询会不会影响在线交易"这个问题**无法干脆地回答"不会"**时，分析负载就该迁出了。

三条明确的设计目标（后面所有选型都服务于它们）：

1. **隔离**：报表再慢也不影响在线交易；
2. **统一口径**：指标定义只存在一处，报表不再各自实现；
3. **可长期留存**：历史数据能留得住，且成本可控。

## 二、选型：为什么是这套组合 {#selection}

选型的价值不在于"选了谁"，而在于**为什么否决了其他**——下面每一行都能在评审会上被追问。

### 2.1 五个决策点 {#decisions}

| 决策点 | 结论 | 否决的方案与否决理由 |
|---|---|---|
| **是否引入 Hadoop 全家桶** | **不引入** | 组件多（HDFS/YARN/Hive/Spark…）、运维重、批处理延迟以小时计；团队规模与实时性要求都不匹配 |
| **分析引擎** | **Doris** | ❌ 继续用 MySQL：列式能力缺失、并发撑不住；❌ ClickHouse：单表吞吐强但并发与多表 JOIN 弱、生态偏薄；❌ 只上 ES：擅长检索不擅长聚合分析 |
| **历史数据的存储介质** | **对象存储 + 湖表（Iceberg）** | ❌ HDFS：元数据集中压力、扩容要再平衡、存算耦合；❌ 只留分析库本地盘：成本随容量线性上升 |
| **同步方式** | **CDC（读 binlog）→ 消息队列 → 数仓** | ❌ 定时轮询：看不见物理删除与字段级变更，还会给业务库加压；❌ 应用双写：业务代码侵入、失败无法补偿 |
| **消息中间件** | **Kafka（同步链路）+ RocketMQ（业务解耦）** | 两者分工明确：Kafka 承接"多下游订阅同一份变更流"，RocketMQ 承接"业务解耦与定时/事务消息" |

### 2.2 不用 Hadoop 的四条理由 {#why-not-hadoop}

这是这份方案里最需要讲清楚的一条，因为在很多人的默认认知里"大数据 = Hadoop"：

| 理由 | 说明 |
|---|---|
| **组件数量与运维成本** | 一个实时链路要同时维护 HDFS、YARN、Hive、Spark，还要处理它们之间的版本兼容；而 Doris 只要 FE + BE 两组进程 |
| **延迟形态不匹配** | 业务要的是"分钟级可查"，而不是"T+1 报表"；批处理栈的调优目标与这个诉求不同 |
| **团队规模不匹配** | 平台化能力需要专门的人力，而这条链路的定位是"支撑业务分析"，不是"建一个数据平台" |
| **真正需要的能力已经具备** | 列式存储、向量化、多表 JOIN、物化视图、对象存储上的事务型湖表——这些已经覆盖了需求，**没有理由为剩余 10% 的能力付出 3 倍的复杂度** |

> **选型的一条通用原则**：引入一个组件之前，先问"它解决的是**必需**问题还是**可能用到**的问题"。后者应该等到真的需要时再加——**加组件容易，去掉很难**。

### 2.3 技术栈定稿 {#final-stack}

| 环节 | 选型 | 承担什么 |
|---|---|---|
| 在线事务 | MySQL（一主多从 + 高可用切换） | 缴费、下单、门禁等强一致写入 |
| 变更捕获 | CDC 工具（读 binlog） | 把变更以行级事件形式送出 |
| 变更分发 | Kafka | 削峰、多下游订阅、可重放 |
| 分析计算与存储 | Doris | 明细与汇总的存储、多维分析、看板查询 |
| 长期归档 | 对象存储 + Iceberg | 冷数据留存、时间旅行、成本下沉 |
| 编排与运行 | Kubernetes | 上述所有组件的部署与弹性 |

## 三、同步链路：业务库变更怎么进数仓 {#pipeline}

```
   ┌──────────────┐
   │ 业务 MySQL    │  在线事务（缴费 / 下单 / 门禁）
   │  一主多从     │
   └───────┬──────┘
           │ binlog（ROW 格式）
           ▼
   ┌──────────────┐   伪装从库、订阅变更   ┌──────────┐   多下游、可重放
   │ CDC 工具      │ ─────────────────────▶│  Kafka   │──────────────┐
   │ （读 binlog） │                        └──────────┘              │
   └──────────────┘                                                  │
                                            ┌────────────────────────┘
                                            ▼
                                   ┌──────────────────┐
                                   │ 消费端：攒批 + 幂等 │
                                   └────────┬─────────┘
                                            │ Stream / Routine Load
                                            ▼
                     ┌──────────────────────────────────────────┐
                     │  Doris                                    │
                     │  ODS ──▶ DWD ──▶ DWS ──▶ ADS              │
                     │  （贴源）  （明细）  （汇总）  （应用）      │
                     └───────────────┬──────────────────────────┘
                                     │
                          BI / 看板 / 接口查询
```

### 3.1 为什么中间要加一层消息队列 {#why-mq}

因为 binlog 的位点**只能前进，不能重放**。一旦下游写失败，没有 MQ 就只能回退位点、把下游的重放范围一起拉大。加一层 MQ 换来三件事：

- **削峰**：出账期的变更洪峰不会直接打到分析库；
- **多下游**：同一份变更流可以同时供实时看板、告警、归档使用；
- **可重放**：下游失败可以重新消费，而不必惊动上游。

### 3.2 幂等与乱序 {#idempotency}

CDC 的语义是"至少一次"，所以**重复必然发生**，幂等必须做在写入侧：

```sql
-- 目标表用 Unique Key 模型，主键 UPSERT；
-- 关键是 sequence 列：用 binlog 时间戳 / 事务序号判断新旧，
-- 防止"先到的旧事件覆盖后到的新事件"。
UNIQUE KEY(order_id)
PROPERTIES ("function_column.sequence_col" = "source_ts")
```

- **同一份 binlog 流内事件有序**，但**按表拆分提高吞吐后顺序不再成立**；
- 下游并发消费也会引入乱序，**因此光靠主键 UPSERT 不够，必须有版本列**。

> 原理与坑见 [Canal 数据同步](/bigdata/canal/#idempotency-order)——包括位点形态、`server_id` 冲突、大事务、binlog 过期这些运维要点。

### 3.3 DDL 变更策略 {#ddl-strategy}

同步链路最脆弱的环节是**上游改表结构**。方案里定的规则是"**只在平台侧登记兼容变更**"：

| 允许 | 禁止 |
|---|---|
| 新增可空列 | 改列类型、改列名 |
| 加索引（不影响 binlog 结构） | 删除列、重命名列 |
| 扩大 `varchar` 长度 | 收缩长度、拆分/合并表 |

配套动作：**平台侧维护一张"上游表结构变更登记表"**，同步链路按表校验列集合是否匹配，不匹配即告警并暂停该表的同步（**宁可停一张表，不要写脏一片数据**）。

### 3.4 对账：同步链路的最后一道闸门 {#reconciliation}

| 层次 | 校验内容 | 频率 |
|---|---|---|
| 行数对账 | 按天分区比对源表与 ODS 行数 | 每日 |
| 指标对账 | 关键指标（金额合计、订单数）源库与数仓比对 | 每日 |
| 抽样明细对账 | 随机抽样若干主键，逐字段比对 | 每日 |
| 差异归因 | 差异超阈值时区分"业务真的变了"还是"链路丢了数据" | 触发式 |

> **没有对账的同步链路，出问题时无法判断归因**——这是"看起来很稳"与"真的可靠"之间的差别。

## 四、仓内分层：Doris 里怎么组织 {#layers}

| 层 | 落地形态 | 关键设计 |
|---|---|---|
| **ODS** | 与源表同构，Duplicate Key 模型 | **只追加、不做加工**，保留原始值与变更历史 |
| **DWD** | 一行一个业务事件，Unique / Duplicate 按场景选 | 清洗、去重、类型统一、派生维度算好 |
| **DWS** | 主题 + 粒度预聚合（如"项目-日"、"租户-月"） | 分桶键取 JOIN / GROUP BY 维度 |
| **ADS** | 一张表服务一个看板 | 结构跟着需求走，不与通用逻辑混放 |
| **DIM** | 维度表（日期、项目、收费项、组织） | **一致性维度**：所有事实表复用同一份编码 |

| 设计点 | 做法 | 原因 |
|---|---|---|
| **分区** | 按时间（天/月）分区，开动态分区自动建与回收 | 数据裁剪 + 生命周期管理 |
| **分桶** | 按高频 JOIN/GROUP BY 维度哈希，避免高基数列 | 减少数据 shuffle，单桶控制在合理区间 |
| **表模型** | ODS 用 Duplicate；状态会变的镜像表用 Unique | 追加写入吞吐更高；Unique 适合慢变数据 |
| **看板加速** | 高频看板用异步物化视图，**必须配 `grace_period`** | 不配则视图频繁失效、命中率趋近于零 |
| **UV 类指标** | 用位图聚合或近似去重替代 `COUNT(DISTINCT)` | 成本最低的一次性优化 |

> 分层的完整逻辑（每层"不做什么"、事实表三种形态、缓慢变化维与拉链表、指标体系）见 [数仓分层建模](/bigdata/warehouse-design/)；表模型与索引细节见 [Doris 数仓](/bigdata/doris/#table-model)。

## 五、冷热分层与 TTL 迁移 {#tiered}

### 5.1 三层数据温度 {#trimodal}

| 层 | 承载 | 介质 | 访问特征 |
|---|---|---|---|
| **热** | 在线事务、当月明细 | MySQL / Doris 本地 SSD | 高并发、低延迟 |
| **温** | 近一年明细与汇总、看板 | Doris（SSD + HDD 混合） | 中等并发、允许秒级 |
| **冷** | 归档明细、合规留存 | **对象存储 + Iceberg** | 低频、允许分钟级 |

**这不是"数据放两处"，而是按访问特征把同一份数据的生命切成几段**，每段用"够用且最便宜"的介质承载。介质差异与对象存储的取舍见 [Lakehouse](/bigdata/lakehouse/#three-tiers)。

### 5.2 迁移任务的执行顺序：先写、再验、最后删 {#migration-order}

```
1. 读源分区 ──▶ 写入湖表（按分区写入，天然可重跑）
2. 校验目标：行数 + 关键指标 + 抽样明细
3. 校验通过 ──▶ TRUNCATE 源分区
4. 写迁移台账：分区、时间、行数、校验结果、执行人
```

**第 2 步不能省。** "迁移"类操作的事故几乎都发生在"删了源、才发现目标不全"，而它同时又天然幂等（按分区重跑即可）——所以正确做法永远是**先写、再验、最后删**，并留台账。同样的思路见 [Iceberg 的 TTL 迁移](/bigdata/lakehouse/#ttl-migration)。

### 5.3 保留策略 {#retention}

| 数据 | 在线保留 | 归档保留 | 依据 |
|---|---|---|---|
| 明细（缴费、开门记录） | 近期热查询区间 | 长期 | 合规与纠纷追溯 |
| 汇总（日/月报表） | 长期在线 | 长期 | 报表需要连续历史 |
| 中间层（ODS/DWD 中间结果） | 可短 | 可清理 | 能重算就不必留 |

> **一条原则**：**能重算的数据不必长期占在线存储**，但"能不能重算"要在设计时就确认（依赖的原始数据是否还在）。

## 六、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标（估算，非实测） | 验证方式 |
|---|---|---|
| 报表与在线交易隔离 | 看板任意查询不影响在线缴费的响应时间 | 在压测环境对业务库与分析库**同时加压**，观察业务接口 P99 |
| 同步延迟 | 分钟级可查（业务可接受区间） | 端到端打点：源库写入 → 数仓可查的耗时分布 |
| 不丢不重 | 每日对账零差异（行数 + 指标 + 抽样） | 连续运行期的对账报告 |
| 归档成本 | 冷数据单位存储成本显著低于本地盘方案 | 按容量估算 + 实际用量回填 |
| 长期可查 | 归档数据可通过湖表直接查询，无需回灌 | 抽查历史分区做一次查询验证 |

**明确未验证 / 待补**：

- 延迟与隔离目标**尚无实测数据**，属于设计值——**没有压测数据的容量数字不应作为结论对外讲**；
- 消息队列与 CDC 的**故障切换演练**（CDC 停机超过 binlog 保留期）尚未做过；
- 归档链路的**恢复演练**（从冷层回取历史数据）尚未做过；
- 对象存储的**尾延迟**对"温层查询"的影响需要实测标定。

## 七、复盘与面试问答 {#interview}

**Q1：为什么报表不能继续查业务库？转折点怎么判断？**
不是"数据量大了"就该迁，而是**当"分析查询会不会影响在线交易"这个问题无法干脆回答"不会"时**就该迁。四个具体后果：看板与交易抢资源导致高峰期缴费变慢；大聚合查询数十秒无法支撑随时下钻；历史跨度变长迫使业务库不敢删数据、备份成本上升；报表口径散落在各服务 SQL 里，同一指标算法不同。

**Q2：为什么不上 Hadoop 全家桶？**
四条理由：组件多、运维成本高（HDFS/YARN/Hive/Spark 要一起维护并处理版本兼容）；延迟形态不匹配（要的是分钟级可查，不是 T+1 批处理）；团队规模不匹配（平台化需要专门人力，而这条链路的定位是支撑业务分析）；**而真正需要的能力已经具备**——列式存储、向量化、多表 JOIN、物化视图、对象存储上的事务型湖表已经覆盖需求，没有理由为剩余能力付出数倍复杂度。**加组件容易，去掉很难。**

**Q3：为什么同步链路中间要加消息队列，不能 CDC 直写数仓？**
因为 **binlog 的位点只能前进、不能重放**。CDC 直写时，一旦下游写失败就只能回退位点，把下游的重放范围一起拉大。加一层 MQ 换来削峰、多下游复用同一份变更流、以及可重放——这三件事在大规模同步里都不是"优化"，是前提。

**Q4：CDC 同步的重复和乱序怎么处理？**
CDC 是"至少一次"语义，**重复必然发生**，所以幂等做在写入侧：目标表用 Unique Key 模型按主键 UPSERT。但光有 UPSERT 不够——**乱序会让旧事件覆盖新值**，必须再加一个**单调的 sequence 列**（binlog 时间戳或事务序号），由存储引擎按它判新旧。同一份 binlog 流内有序，但按表拆分提高吞吐、或下游并发消费之后，顺序就不再成立。

**Q5：上游改表结构怎么办？**
定"**只做兼容变更**"的规则：允许新增可空列、加索引、扩大 `varchar`；禁止改类型、改名、删列、收缩长度。同时平台侧维护"上游表结构变更登记表"，同步链路按表校验列集合，不匹配就**告警并暂停该表同步**——宁可停一张表，不要写脏一片数据。

**Q6：冷热分层怎么落地？迁移任务怎么写才安全？**
按访问特征分三层：热（在线事务 + 当月明细，本地 SSD）、温（近一年，SSD+HDD 混合）、冷（归档，对象存储 + 湖表）。迁移任务必须严格按**先写、再校验、最后删源**的顺序执行，并按分区做成可重跑（幂等），同时记录迁移台账。**事故几乎都出在"删了源才发现目标不全"**，所以校验步骤不能省。

**Q7：这个方案最大的风险是什么？**
三个：① **CDC 停机超过 binlog 保留期**会导致位点失效、只能重新全量——必须配位点落后告警并保留全量重跑通道；② **对象存储的尾延迟**会拖慢"温层"查询，需要实测标定后再决定哪些数据留在本地；③ **口径治理是组织问题不是技术问题**——分层与一致性维度能提供机制，但如果"指标定义谁负责"这件事没有明确归属，分层建好了口径依然会分叉。
