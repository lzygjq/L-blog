# 容量测算与压测方案

> **口径说明**：本文是架构设计记录。**文中的容量数字来自参数区间的组合推导，是设计目标与容量估算，不是生产实测数据**；压测方案是要把它变成实测数据的手段。可验证产出的写法见 [压测报告](/projects/toolkit/perf-report/)；全文已脱敏，不含企业标识与客户信息。

## 一、背景：容量为什么必须推，不能猜 {#background}

容量问题在项目里通常以两种方式出现：

| 出现方式 | 表现 | 后果 |
|---|---|---|
| "先上线再说" | 按开发机上的感觉配资源 | 第一个缴费日就崩，且**崩的时候不知道该加什么** |
| "按十倍余量配" | 直接拍一个很大的数 | 成本失控；且十倍余量对**不同链路的意义完全不同**——有的链路十倍也不够，有的两倍就浪费 |

两者共同的缺陷是：**没有推导链**。推不出来源的数字，既不能扩容也不能优化——因为不知道该动哪个参数。

这一篇记录的是三个层次：**怎么推**（六步链路）→ **推出来配什么**（画像与容量评估）→ **怎么验证推得对不对**（压测）。

## 二、六步推导链：从在管面积到峰值 QPS {#derivation}

### 2.1 完整链路 {#chain}

容量测算的完整链路是六步。**跳过任何一步，得出的 QPS / 存储 / 节点数都是拍脑袋。**

```
① 在管面积 ──÷ 户均面积──▶ 户数
② 户数     ──× 户均人口──▶ 居民数
③ 居民数   ──× 注册转化率─▶ 注册用户数
④ 注册用户 ──× 日活率────▶ DAU
⑤ DAU      ──× 人均请求数 ÷ 高峰集中系数 ──▶ 峰值 QPS
⑥ 各业务表年增量 ──▶ 存储容量与分片数
```

每一步用到的参数，以及**取值范围为什么是它**：

| 步 | 推导量 | 参数 | 经验区间与说明 |
|---|---|---|---|
| ① | 户数 | 户均建筑面积 | 住宅约 90–120 ㎡/户（含公摊）；商业/办公按"联系人"而非"户"核算 |
| ② | 居民数 | 户均人口 | 约 2.5–3.0 人/户 |
| ③ | 注册用户 | APP 注册转化率 | 差异极大：新盘/年轻社区可达 60%–80%，老旧小区可能低于 30%。**这是最不确定的一环** |
| ④ | DAU | 日活率 | 工具型 APP 约 12%–25%；缴费日与公告日会显著抬升 |
| ⑤ | 峰值 QPS | 人均请求数、高峰集中系数 | 人均日请求 8–20 次；**高峰集中系数是决定峰值的关键** |
| ⑥ | 存储 | 户均账单数、单条记录大小、附件量 | 账单约 12–24 条/户/年；单条业务记录 < 1 KB；**图片与发票是存储大头** |

### 2.2 最容易被低估的参数：高峰集中系数 {#peak-factor}

多数人算峰值 QPS 时用「日请求总数 ÷ 86400」，得到一个很小的数字，然后按这个数字配容量——**上线后第一个缴费日就崩**。

正确的算法是：

```
峰值 QPS = 日请求总数 × 高峰集中比例 ÷ 高峰持续秒数
```

对缴费类业务，**同一份日请求量，按不同集中系数算出的峰值可以差 10 倍以上**：月末缴费期请求会挤在 2~3 小时内，集中系数可达 8~15。

> **这是整篇最值钱的一句话**：租户数是业务目标，**不可控**；而高峰集中系数是**可优化的架构问题**。通过消息队列异步削峰、缴费期分批放号、缓存预热，可以把集中系数从 12 压到 5——等于用软件手段换来一倍的硬件余量，比买机器便宜得多。

### 2.3 敏感性排序 {#sensitivity}

三年后规模 = 存量租户自然增长（在管面积扩张，年增 20%–40%）+ 新增租户接入。

对峰值 QPS 的影响从大到小：

| 排序 | 参数 | 性质 |
|---|---|---|
| ① | 新增租户数 | 业务目标，不可控 |
| ② | **高峰集中系数** | **架构可优化** ← 优先动它 |
| ③ | APP 注册转化率 | 产品与运营侧 |
| ④ | 户均人口与面积 | 影响最小 |

## 三、三档租户画像与容量评估 {#personas}

### 3.1 三档画像 {#profiles}

多租户 SaaS 的容量不能只算一个总数——**租户之间的规模差异决定了隔离级别，也决定了容量基线该按谁配**。

| 画像 | 在管面积 | 项目数 | 注册用户 | 峰值 QPS | 年数据增量 |
|---|---|---|---|---|---|
| 单项目小区 | 10–30 万 ㎡ | 1–3 | 0.3–2 万 | 50–300 | 约 30–80 GB |
| 区域物业公司 | 100–500 万 ㎡ | 10–30 | 3–15 万 | 1,000–3,000 | 约 0.5–1.5 TB |
| 集团型物业企业 | 500 万 ㎡ 以上 | 30+ | 10–50 万 | 3,000–8,000 | 约 1–5 TB |

> 以上为**参数区间的组合结果**，非任何具体企业的实测数据。同一档位内的差异主要来自业态（住宅 vs 商业）与 APP 渗透率。

三档画像对应的隔离级别不同（共享库 / 独立 Schema / 独立库），映射关系见 [多租户三级混合隔离](/projects/property-saas/microservice-to-k8s/#isolation-levels)。

### 3.2 按最大画像做容量评估 {#sizing}

| 层次 | 集团型画像所需配置 | 评估依据 |
|---|---|---|
| K8s | 8–10 节点（16C32G） | 16 个服务 × 2 副本 + 中间件 ≈ 30 Pod；按单节点承载 4–6 Pod 估算 |
| 关系库 | 1 主 2 从 + 4 分片 | 峰值 3–8K QPS、年增约 80 GB |
| Redis | 6 节点集群 | 缓存量 8–12 GB（约为热数据集的 1.5–2 倍） |
| 网关 | 2–8 副本 | 单副本约 1.5–2K QPS，留 30% 余量 |
| 消息队列 | 3 节点 | 日均消息量 15 万–50 万条 |
| 对象存储 | 4 节点分布式 | 图片/文件年增 200–500 GB |

> **这套配置对集团型租户是"够用但不宽裕"**：能扛住上述规模，但在缴费峰值日、或同时接入多个同档租户时会接近上限。设计上已为每一层预留了明确的扩容路径，**不需要改架构，只需要加节点/加分片**——这是"容量测算"真正的产出：不是一组数字，而是一张"往哪扩"的地图。

## 四、五层防护链路：扛不住时会不会雪崩 {#protection}

高并发不是"能不能扛住"的问题，而是"**扛不住时会不会雪崩**"的问题。五层防护的目标是：即使某一层被击穿，也不会造成连锁崩溃。

```
请求流入
  ├─▶ ① 网关限流（网关 + 流控组件）
  ├─▶ ② 服务熔断降级
  ├─▶ ③ 缓存三防
  ├─▶ ④ 异步削峰
  ├─▶ ⑤ 弹性伸缩（HPA）
  └─▶ DB / 中间件
```

| 层次 | 防护目标 | 降级策略 |
|---|---|---|
| ① 网关限流 | 拦截超出阈值的请求 | 429 排队 / 友好提示 |
| ② 熔断降级 | 服务间调用失败不连锁 | 查缓存 / 返回基础值 / 转异步 |
| ③ 缓存三防 | 数据库不被缓存失效冲垮 | 空值缓存 / 互斥锁 / 随机 TTL |
| ④ 异步削峰 | 高并发写入不直压数据库 | 先入消息队列，消费者批量写库 |
| ⑤ 弹性伸缩 | 自动扩 Pod 应对流量洪峰 | CPU 或自定义指标触发扩容 |

### 4.1 第一层：限流的三维口径 {#ratelimit}

限流必须**同时按三个维度**设，只设一个维度必然出问题：

```
按租户：  企业级 5,000 QPS ｜ 中型 1,000 QPS ｜ 小型 200 QPS
         → 超限返回 429 + Retry-After

按接口：  POST 缴费     500 QPS   （缴费高峰）
         GET  账单列表 2,000 QPS  （查询类放宽）
         POST 报修     200 QPS
         POST 团购下单 1,000 QPS

按全局：  总上限 30,000 QPS（保护后端总容量）
```

| 只设一维会怎样 | 后果 |
|---|---|
| 只按租户 | 一个大租户的查询流量就能吃掉为缴费预留的配额 |
| 只按接口 | 无法阻止单个租户刷爆某个接口 |
| 只按全局 | 小租户被大租户挤死，而 SLA 是按租户承诺的 |

规则存在配置中心、由流控组件动态推送，**不需要重启网关**。但有一条必须记住：

> **限流阈值是"承诺"，不是"猜测"。** 对外宣称的 SLA 必须建立在压测验证过的承载能力上——没有压测背书的限流阈值，只是一个好看的数字。

### 4.2 第二层：降级要按业务语义分四类 {#degrade}

降级最危险的做法是"统一返回 null"——它比不熔断更糟：不熔断至少是个慢故障，**NPE 是快速失败的雪崩源**。

| 调用场景 | 降级策略 | 原因 |
|---|---|---|
| 查询类（用户、房产信息） | 查缓存 → 返回基础信息 | 查询可容忍短暂不一致 |
| 写入类（缴费、报修、下单） | **不降级** → 限流排队 → 转异步 | 写入必须保证不丢数据 |
| 核心资金链路（支付） | **不降级不熔断** → 限流 → 排队等待 | 资金不容忍任何不一致 |
| 非核心（通知、推送） | 直接丢弃 → 记录日志 → 稍后补偿 | 通知可延迟，不能影响主流程 |

```java
// 远程调用接口的降级实现（框架提供基类，业务按语义实现）
@Component
public class UserApiFallback implements UserApi {
    @Override
    public Result<UserVO> getById(Long id) {
        UserVO cached = cacheService.get("user:" + id, UserVO.class);
        if (cached != null) return Result.ok(cached);   // 策略 1：查缓存
        return Result.ok(UserVO.basic());               // 策略 2：只返回 id + tenantId
        // 策略 3（核心写入）：不降级，交给限流排队
    }
}
```

### 4.3 第三层：缓存三防，业务代码应该无感知 {#cache-defense}

| 防护 | 问题场景 | 方案 | 业务代码 |
|---|---|---|---|
| 防穿透 | 查询不存在的数据，每次都打到数据库 | 查不到 → 缓存空值 60s | 无感知 |
| 防击穿 | 热点 Key 失效瞬间，大量请求同时查库 | 互斥锁：只让 1 个请求查库，其他等待 | 无感知 |
| 防雪崩 | 大量 Key 同时过期，数据库瞬间被压垮 | TTL = 基准值 + 随机(0~300s) | 无感知 |

**这段封装有个常见隐患**：等待方"睡 50ms 后递归重试"如果没有深度上限，一旦持锁线程异常退出或数据库持续超时，等待方会无限递归直到栈溢出。生产写法必须加**递归深度上限（如 3 次）+ 超时兜底值**。

> 这类"看起来对的封装"最容易在压力下暴露——它是压测的必查项之一。

### 4.4 第四层：异步削峰能抬多少 {#async-peak}

| 场景 | 同步 QPS 上限 | 异步后 QPS 上限 | 消费策略 |
|---|---|---|---|
| 缴费 | ~500 | ~5,000 | 批量写库 + 幂等校验 |
| 通行记录 | ~1,000 | ~10,000 | 定时批量入库 |
| 报修工单 | ~200 | ~2,000 | 单条入库 + 推送 |
| 团购下单 | ~1,000 | ~10,000 | 缓存预减库存 + 排队 |

幂等通过"消费前检查消息是否已处理"实现（`SET NX` 标记），保证重复消费不产生副作用；事务消息保证"本地事务 + 消息发送"的原子性。**异步不是免费的**：它把"实时一致"换成了"最终一致"，所以资金类链路只能削峰、不能异步确认。

### 4.5 第五层：弹性伸缩的两个前提 {#hpa}

```yaml
minReplicas: 2      # 最低 2 副本（高可用）
maxReplicas: 8      # 最高 8 副本（成本上限）
metrics:
  - CPU 利用率 70%
  - 自定义指标：每秒请求数 500
```

| 前提 | 不满足会怎样 |
|---|---|
| 集群还有可调度资源 | 节点打满时 HPA 扩容出来的 Pod 会 Pending——**这就是"扩容了但还是挂了"** |
| 扩缩容节奏是"慢扩快缩" | 扩容 30 秒内 Ready；缩容等 5 分钟稳定期，避免流量波动导致反复伸缩 |

高峰期提前扩容（定时策略 + Cron）：每月最后 3 天缴费高峰提前扩到上限。

## 五、典型高并发场景与防护匹配 {#scenarios}

把"预估量级"和"防护链路"对上的表，是复盘和压测的靶子：

| 场景 | 峰值量级 | 防护链路 | 预估表现 | 瓶颈点 |
|---|---|---|---|---|
| 月底集中缴费 | ~2,000 QPS | 限流 + 缓存 + 异步 | 用户排队 1–3s，数据库不被压垮 | 支付回调（串行） |
| 早高峰门禁通行 | ~5,000 QPS | 异步 + 缓存批量扣费 | 通行无延迟，记录秒级入队列 | 设备端重连 |
| 社区团购抢购 | ~10,000 QPS | 限流 + 预减库存 + 排队 | 5% 用户排队 5s，95% 秒级响应 | 库存一致性 |
| 停电恢复设备重连 | ~50,000 连接 | 网关限流 + 退避重连 | 分批重连 30s 内完成 | 消息消费积压 |
| 大促全量推送 | ~100,000 消息 | 削峰 + 消费者限速 | 5 分钟内推完 | 第三方推送限流 |

> **口径说明**：本表 QPS 是**单一场景拆分口径**，与第 3.1 节画像表的"平台整体峰值区间 3,000–8,000 QPS"**不是同一口径**，两者可叠加而非相互矛盾。对外表述时务必标明口径——两个不同口径的数字放在一份材料里而不加说明，是这类文档最常见的自相矛盾。

## 六、压测方案：把估算变成结论 {#pressure-test}

上面所有 QPS 都是估值，落地后必须用真实压测验证。**压测不是为了"跑个报告"，而是为了拿到三样东西：真实容量上限、调参依据、故障时的行为基线。**

| 环节 | 做法 |
|---|---|
| **压测目标** | ① 找出各链路的**容量拐点**（QPS 上升而 RT 突然抬升的点）；② 验证限流/熔断/降级在压力下的**真实表现**；③ 验证扩容策略能否及时生效 |
| **工具选型** | JMeter（分布式、生态成熟、脚本可视化）或 Gatling（DSL 简洁、报告细致）。**两者取一，不要混用**——混用会导致结果无法横向比较 |
| **环境要求** | ① 尽量贴近生产配置（节点数可缩减，但中间件版本与参数必须一致）；② **数据量要接近真实**；③ 与生产隔离 |
| **必压场景** | ① 缴费链路（核心资金链路）；② 团购抢购（最高瞬时并发）；③ 全量推送（消息积压极限）；④ 门禁早高峰（高频短请求）；⑤ 大报表查询（慢 SQL 与缓存穿透） |
| **采集指标** | TPS/QPS、P50/P95/P99、错误率，以及**各层资源水位**（CPU / 内存 / 连接池 / GC / 消息积压 / 缓存命中率 / 慢查询） |
| **验收标准** | ① 目标 QPS 下 **P99 < 1s、错误率 < 0.1%**；② 峰值 1.5 倍流量下**不雪崩**（允许排队，不允许服务不可用）；③ 压测停止后能**自动恢复** |
| **闭环** | 结果反向调优：限流阈值、扩容阈值、线程池与连接池大小、GC 参数、索引与慢 SQL |

> **架构师的价值不在画图，在调参**——同一套架构图，参数调得好坏能差出一倍容量。这也是压测报告比架构图更硬的原因：架构图是设计意图，压测报告是实测证据。写法见 [压测报告](/projects/toolkit/perf-report/)。

### 6.1 压测的三个常见坑 {#pressure-test-pitfalls}

| 坑 | 为什么是坑 | 正确做法 |
|---|---|---|
| **只压单接口** | 真实流量是混合的，单接口压得再高也说明不了问题 | 必须做**链路级混合场景**压测 |
| **用固定参数压** | 真实请求的租户、小区、用户分布不均，**热点 Key 只有在真实分布下才会出现** | 压测数据按真实分布构造 |
| **压测期间不看中间件** | 应用层指标正常、但消息已积压百万、缓存命中率掉到 60% 的情况很常见 | 中间件指标必须同屏监控 |

另外有一条环境侧的坑：**用 100 万行的表压出 1 万行表的结论，是压测最常见的自欺**。数据量不足时，索引选择、执行计划、分页性能全都不具参考性。

## 七、设计目标与尚未验证的部分 {#targets}

| 项 | 设计目标 | 现状 | 验证方式 |
|---|---|---|---|
| 集团型画像整体峰值 | 3,000–8,000 QPS 下 P99 < 1s | 估算 | 压测环境按真实数据分布构造 |
| 缴费链路 | 2,000 QPS 下滑峰有效、数据库不被打穿 | 估算 | 混合场景压测 + 中间件同屏监控 |
| 缓存三防 | 热点 Key 失效不引发数据库尖峰 | 设计完成 | 压测中人为制造热点失效 |
| 限流阈值 | 阈值与实测承载能力一致 | 待定 | **阈值必须在压测之后才写进 SLA** |
| 扩容策略 | 负载上升 30s 内完成扩容 | 设计完成 | 压测中观察扩容是否 Pending |
| 降级策略 | 依赖故障时核心链路不雪崩 | 设计完成 | 混沌演练（人为停依赖服务）**尚未验证** |

> **一个必须诚实说明的现状**：本页所有容量数字都是**推导值区间**，尚无一次完整压测为之背书。这正是 [压测报告](/projects/toolkit/perf-report/) 这套产出工具存在的理由——**在你跑完压测之前，这些数字只是假设；跑完之后，它们才是证据。**

## 八、复盘与面试问答 {#interview}

**Q1：为什么不能按"日均请求 ÷ 86400"算峰值？**
因为它假设流量均匀分布，而缴费类业务的流量天然极度集中。对同一份日请求量，按高峰集中系数 5 和 15 算出的峰值差三倍。按均值配容量等于赌"缴费当天没人用"。

**Q2：容量测算里哪个参数最值得优化？**
高峰集中系数。租户数是业务目标、转化率是产品问题，只有集中系数是纯架构问题——削峰、分批放号、缓存预热都能压它。这是"用软件换硬件"性价比最高的一处。

**Q3：限流、熔断、降级三者的顺序为什么是限流在最前？**
限流是**入口处的确定性保护**，成本最低、效果最直接；熔断是"已经出问题了"的止损；降级是"止损之后还能提供什么"。把降级放最前面，等于放弃了最便宜的那道闸门。

**Q4：为什么资金链路不能降级？**
因为降级的前提是"业务可以接受不一致"。查询可以返回旧值、通知可以延迟，但**资金链路的任何一种"近似正确"都是事故**。所以资金链路的正确策略是限流排队（拒绝一部分、保证进来的都正确），而不是降级放行。

**Q5：压测最容易被自欺的一点是什么？**
数据量。用 1 万行的表压出来的结论，在 100 万行时完全不成立——索引选择变了、执行计划变了、分页深度变了。压测环境的**数据量**比**并发数**更容易被忽略，也更容易让结论失效。
