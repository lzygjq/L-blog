# 服务网格

## 一、问题场景：治理代码长在业务里 {#why-mesh}

微服务的每个服务都需要同一批能力：超时、重试、熔断、限流、灰度、加密、指标埋点。传统做法是**用 SDK 把能力装进每个应用**，于是有三个逃不掉的问题：

| 问题 | 具体表现 |
|---|---|
| **与语言绑定** | Java 用 Spring Cloud、Go 用 go-micro、Node 用 NestJS——**治理语义在各语言里各不相同** |
| **升级要动业务** | 改一次熔断策略，要重新构建、发布所有服务的镜像 |
| **策略不可见** | 谁能调用谁、超时是几秒，散落在几十个配置文件里，没人能说清全貌 |

这些能力的共同点是：**它们只关心"进程之间的通信"，不关心业务逻辑**。既然如此，为什么不把它从应用进程里**拿出来**，放到一个所有流量都必须经过的独立进程里去？

> **服务网格的一句话定义**：以**基础设施**的方式（而不是以 SDK 的方式）统一提供微服务之间的**通信治理**能力——超时、重试、熔断、灰度、mTLS、可观测，全部对应用**透明**。

## 二、架构：数据面与控制面 {#architecture}

```
┌─────────────────── 控制面（Control Plane）───────────────────┐
│  istiod                                                      │
│   ├── Pilot   ：把 VirtualService/DestinationRule 翻译成      │
│   │             Envoy 能懂的配置，通过 xDS 协议下发            │
│   ├── Citadel ：签发与轮换证书（mTLS 的身份根）               │
│   └── 配置校验与注入（Sidecar 自动注入的 webhook）             │
└───────────────────────────┬──────────────────────────────────┘
                            │ xDS（gRPC 长连接，配置变更实时推送）
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
┌─────── Pod A ────────┐               ┌─────── Pod B ────────┐
│  App ──▶ Envoy        │  ← mTLS →     │  Envoy ──▶ App       │
│  （出站 15001）        │               │  （入站 15006）       │
└───────────────────────┘               └──────────────────────┘
        数据面（Data Plane）：每个 Pod 一个 sidecar 代理
```

| 面 | 是什么 | 关键点 |
|---|---|---|
| **数据面** | 每个 Pod 里的代理（Istio 用 Envoy），**真正转发流量、执行策略** | 无状态、可水平扩展；是延迟与资源开销的来源 |
| **控制面** | 把用户声明的策略翻译成数据面配置并下发 | 挂了不影响已有流量（配置已在数据面内存里），但**新的变更无法生效** |

### 2.1 流量是怎么被劫持的 {#traffic-hijack}

应用代码一行没改，流量为什么会经过 Envoy？答案是 **iptables 规则**：

```
① Pod 启动时，先跑一个初始化容器 istio-init（需要 NET_ADMIN 权限）
② 它写入 iptables 规则：
     - 出站流量 → REDIRECT 到 15001 端口（Envoy 出站监听）
     - 入站流量 → REDIRECT 到 15006 端口（Envoy 入站监听）
③ 应用发起 connect("orders:8080")
     → 被内核规则改写 → 实际连到本 Pod 的 Envoy
④ Envoy 按控制面下发的路由规则选择目标，再发起一条真实连接
```

三个由此推出的结论，都是面试高频：

1. **"透明"是靠内核规则实现的，不是靠应用配合**——所以任何语言、任何框架的服务都适用，这是服务网格最根本的价值。
2. **排障时"网络不按预期走"要想到 iptables**：`istioctl` 或进入 Pod 看规则，能确认流量是否真的被劫持（例如 Pod 未注入 sidecar 时，流量会直连，表现为"策略不生效"）。
3. **`istio-init` 需要 `NET_ADMIN`**——在受限的 Pod Security 策略下会被拒绝，这是生产上常见的接入阻碍。

## 三、Sidecar、Ambient 与 eBPF：三种形态 {#sidecar-modes}

| 形态 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **Sidecar**（经典） | 每个 Pod 注入一个代理 | 隔离彻底（一 Pod 一代理，故障域最小）、能力完整 | 每个 Pod 一份资源开销；**每跳多一次代理**；升级代理要重启业务 Pod |
| **Ambient / Sidecarless**（无 sidecar） | L4 由**节点级** ztunnel 承担，L7 能力按命名空间/服务**按需**部署 waypoint 代理 | 资源大幅下降、**升级不动业务 Pod**、接入门槛低（无需注入 init 容器） | L7 能力要显式开启；生态与工具链成熟度低于经典模式 |
| **eBPF（Cilium 等）** | 在内核层面做 L4/L7 处理，不依赖用户态代理 | 性能最好、无代理开销 | 对内核版本有硬要求，能力边界受内核可观测点限制 |

> **怎么答"为什么会有 Ambient"**：经典 Sidecar 的**运维代价**（每个 Pod 都要注入、代理升级要滚一遍全集群业务）在大规模下变得难以承受。Ambient 把"必付的 L4 成本"下沉到节点级共享，把"可选的 L7 能力"改为按需部署——**这是对"代理是否必须在业务 Pod 里"这个前提的重新回答**。

## 四、服务网格到底提供了什么 {#capabilities}

| 能力 | 具体内容 | 传统方案在哪做 |
|---|---|---|
| **流量管理** | 超时、重试、熔断、**按权重/Header 灰度**、故障注入、流量镜像、流量复制 | 应用内的框架（Sentinel / Resilience4j）+ 网关 + 代码 |
| **安全** | **自动 mTLS**、服务身份（SPIFFE 标准）、L4/L7 授权策略 | 各服务自行配置 TLS + 自研鉴权 |
| **可观测** | 统一指标（请求数/错误率/延迟）、访问日志、**无侵入链路追踪** | 每个服务埋点接入 SDK |
| **策略执行** | 限流、配额（需扩展组件） | 网关 |

### 4.1 最实的收益是 mTLS {#mtls}

手工实现双向 TLS 的完整成本包括：**证书签发、分发、轮换、吊销、身份到服务名的映射、对端校验**。在几百个服务的环境里，这套东西的维护成本高于它保护的价值，于是多数团队停在"集群内不加密"。

服务网格把它变成**声明式配置**：

| 项 | 网格的做法 |
|---|---|
| 身份 | 服务身份由 K8s ServiceAccount 派生（SPIFFE 格式 URI），**不是 IP、不是域名** |
| 证书 | 控制面（Citadel）自动签发与**定期轮换**，应用零参与 |
| 校验 | sidecar 间双向校验，**开启后明文请求直接失败** |
| 授权 | `AuthorizationPolicy` 按身份/命名空间/方法/路径控制"谁能调谁" |

> 这是"**零信任**"在工程上真正可落地的形态：**默认不信任任何调用方，每次调用都校验身份**。对合规场景（等保、金融行业审计）而言，`PeerAuthentication` 一行配置换来的收益，往往就是上网格的最强理由。

### 4.2 核心资源对象 {#resources}

| 对象 | 管什么 | 关键字段/概念 |
|---|---|---|
| `VirtualService` | **路由规则**：请求怎么分发 | `hosts`、`http.route[].match`（按 Header/URI/来源）、`weight`、`timeout`、`retries` |
| `DestinationRule` | **目标侧策略**：子集与保护 | `subsets`（按 label 分组）、`trafficPolicy`（负载均衡算法、连接池、**`outlierDetection` 异常点驱逐**＝熔断） |
| `Gateway` | 网格的入口/出口 | 与 K8s 原生 `Gateway API` 同名但**是不同 API**，容易混淆 |
| `PeerAuthentication` | mTLS 模式 | `STRICT` / `PERMISSIVE` / `DISABLE` |
| `AuthorizationPolicy` | 访问控制 | 按 `source.principals`（服务身份）、`methods`、`paths` |
| `ServiceEntry` | 把集群外服务纳入网格 | 外部依赖也获得超时/重试/指标 |

**灰度发布的完整写法**（两个对象配合，缺一不可）：

```yaml
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata: { name: orders }
spec:
  host: orders
  subsets:                                  # 先把"版本"定义为子集
    - { name: v1, labels: { version: v1 } }
    - { name: v2, labels: { version: v2 } }
  trafficPolicy:
    outlierDetection:                       # 熔断：连续失败则驱逐该实例
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: orders }
spec:
  hosts: [orders]
  http:
    - match:
        - headers: { x-canary: { exact: "true" } }   # 先按 Header 定向测试
      route:
        - destination: { host: orders, subset: v2 }
    - route:                                         # 默认按权重分流
        - destination: { host: orders, subset: v1 }
          weight: 90
        - destination: { host: orders, subset: v2 }
          weight: 10
```

> **注意 `DestinationRule` 定义子集、`VirtualService` 引用子集**——只写 VirtualService 而不定义 subset，会得到"路由指向不存在的子集"这类报错。这是最常见的配置错误。

## 五、代价：什么时候不该上网格 {#tradeoffs}

| 代价 | 表现 | 量级参考 |
|---|---|---|
| **延迟** | 每跳多两次代理（出站 + 入站） | 单跳增加**亚毫秒到个位数毫秒**，链路越长乘数越大 |
| **资源** | 每个 Pod 一个代理进程 | 每个代理数十 MB 内存 + 少量 CPU，**乘以 Pod 数量** |
| **复杂度** | 多了一层"要懂、要升级、要排障"的东西 | 排障时要判断"慢在业务还是慢在网格" |
| **接入门槛** | 需要 `NET_ADMIN`、自动注入、代理版本与集群版本匹配 | 受限 Pod Security 环境会受阻 |

**判据（这一节比能力清单更重要）**：

| 值得上 | 不值得上 |
|---|---|
| **多语言技术栈**，治理能力要统一 | 单一语言 + 已有成熟治理框架（如纯 Java + Spring Cloud） |
| 有**强合规要求**（mTLS、审计、服务间访问控制） | 服务数量少（十几个以内），手工治理还管得住 |
| 服务数量大、跨团队，手工治理不现实 | 团队规模小，没有余力维护又一层基础设施 |
| 需要**请求级灰度**且不想改业务代码 | 已有的网关注入式灰度已够用 |

> **避免"为了技术先进性上网格"**：如果你的系统是单一 Java 技术栈、服务不到二十个、也没有加密合规要求，那么网格带来的治理能力与 Spring Cloud + 网关高度重叠，**收益基本等于"多维护一套基础设施"**。

## 六、与 Spring Cloud 的分工 {#vs-spring-cloud}

这是 Java 团队最该想清楚的一节——**两者不是替代关系，而是层次不同**：

| 能力 | Spring Cloud（应用内） | 服务网格（进程间） |
|---|---|---|
| 服务发现 | 注册中心（Nacos / Eureka）+ 客户端负载均衡 | K8s Service / 网格 |
| 超时重试熔断 | Sentinel / Resilience4j，**策略在应用配置里** | `DestinationRule`，**策略在基础设施里** |
| 灰度 | 需要网关注入 + 代码配合（Header 透传、链路染色） | `VirtualService` 声明式，**对业务透明** |
| mTLS | 需自行配置证书与信任链 | 自动签发与轮换 |
| 可观测 | 各服务接入 SDK 埋点 | 代理层统一采集，**无侵入** |
| 业务级降级 | ✅ 能感知业务语义（如"库存服务不可用则走本地缓存"） | ❌ 只懂协议，不懂业务 |

**分工结论**：

- 网格擅长**通用的、协议层的、可声明式表达的**治理（超时/重试/熔断/加密/灰度/指标）；
- 框架擅长**业务感知的**治理（降级到哪个兜底逻辑、幂等重试、事务性补偿）；
- 生产上的常见组合是：**K8s + Spring Cloud 负责服务发现与业务级容错，网格负责 mTLS、统一灰度与统一可观测**。真正被网格替代的，是"**每语言一套治理 SDK**"这种模式。

## 七、对比辨析 {#compare}

| 对比 | 差别 | 何时选后者 |
|---|---|---|
| **Sidecar / Ambient** | 一 Pod 一代理 vs 节点级 L4 + 按需 L7 | 大规模、无法承受"升级代理要滚全集群业务" |
| **服务网格 / API 网关** | 东西向（服务间） vs 南北向（外部入口） | 两者通常**并存**：网关做入站，网格做内部 |
| **Istio `Gateway` / K8s `Gateway API`** | 网格自有 API vs K8s 标准 API | 新项目优先 K8s 标准，减少厂商绑定 |
| **`VirtualService` / `DestinationRule`** | 路由（怎么分发） vs 目标策略（子集与保护） | 灰度必须两个都配 |
| **mTLS `STRICT` / `PERMISSIVE`** | 只接受加密 vs 兼容明文 | 迁移期用 `PERMISSIVE`，稳定后切 `STRICT` |
| **网格 / SDK 治理** | 基础设施层、语言无关 vs 应用层、语言绑定 | 多语言栈选前者，单语言且需业务降级选后者 |

## 八、使用场景与面试问答 {#interview}

**Q1：服务网格解决了什么问题？一句话说。**
把微服务的**通信治理能力**（超时、重试、熔断、灰度、mTLS、可观测）从**应用进程里的 SDK** 下沉到**基础设施层的代理**，从而做到**语言无关、业务无侵入、策略集中可见**。根本动机是：治理语义不该与业务代码、编程语言绑定。

**Q2：应用代码一行没改，流量怎么会经过代理？**
靠 **iptables 重定向**。Pod 启动时由 `istio-init` 初始化容器（需要 `NET_ADMIN`）写入规则：出站流量重定向到 Envoy 的 15001、入站到 15006。应用发起连接时被内核规则改写到本 Pod 的代理，代理再按控制面下发的路由发起真实连接——**"透明"来自内核，不来自应用配合**。

**Q3：控制面挂了会怎样？**
**已有流量不受影响**——路由与策略配置早已下发并缓存在各数据面代理的内存里。但**新的配置变更无法生效**，新扩容的 Pod 也拿不到配置。所以控制面通常是多副本部署的关键组件。

**Q4：上服务网格有什么代价？什么时候不该上？**
代价四项：**延迟**（每跳多两次代理）、**资源**（每 Pod 一个代理）、**复杂度**（多一层要维护与排障）、**接入门槛**（需 `NET_ADMIN`、注入、版本匹配）。若系统是**单一语言 + 已有成熟治理框架**（纯 Java + Spring Cloud）、服务数量少、无加密合规要求，网格的能力与现有框架高度重叠，**收益不抵维护成本**。

**Q5：服务网格会替代 Spring Cloud 吗？**
不会——**层次不同**。网格管"进程间的通信语义"（协议层、可声明式表达），Spring Cloud 管"应用内的调用逻辑"，尤其**能感知业务语义的降级**（库存不可用则走本地缓存这类逻辑，代理无法表达）。常见组合是 K8s + Spring Cloud 做服务发现与业务级容错，网格做 mTLS、统一灰度与无侵入可观测。

**Q6：服务网格里的 mTLS 是怎么实现的？**
身份来自 **K8s ServiceAccount**（映射为 SPIFFE 格式 URI），不是 IP 或域名；控制面（Citadel）自动**签发与定期轮换**证书；数据面代理之间双向校验，开启 `STRICT` 后**明文请求直接失败**。授权则由 `AuthorizationPolicy` 按服务身份/命名空间/方法控制。业务代码零参与——这是它在合规场景（等保、金融审计）里最有说服力的一处收益。

**Q7：Sidecar 和 Ambient（无 Sidecar）的区别？为什么要做 Ambient？**
经典 Sidecar 是"每 Pod 一个代理"，隔离彻底但**每个 Pod 都付一份资源与一跳延迟，且代理升级要重启全部业务 Pod**——在大规模下运维代价难以承受。Ambient 把**必付的 L4 成本**下沉到节点级共享代理（ztunnel），**L7 能力按需部署**（waypoint）。它是对"代理必须在业务 Pod 里"这一前提的重新回答。

**Q8：怎么用服务网格做灰度发布？**
两个对象配合：`DestinationRule` 先用 label 把不同版本定义成 `subsets`，`VirtualService` 再按 `match`（Header/来源）或 `weight` 把流量分到不同 subset。可以先按 Header 定向验证，再切小比例权重，观察指标后逐步放量——**不需要改业务代码，也不需要在应用里做开关**。

> **下一篇**：[CRD 与 Operator](/cloud-native/operator/) —— 网格解决了"服务之间怎么通信"，但"有状态中间件怎么运维"（备份、扩缩容、故障切换）还得有人盯着；把这套运维知识写成控制器，就是 Operator。
