# 慢请求剧本：从告警走到那一次调用

面试里「一次请求经历了什么」是**检索题**：把 DNS 到探针按层背出来，见[面试 · 一次请求的旅程](/interview/#thread-request)。线上的慢请求是**决策题**：同一条链路上，你先看哪一层、什么情况下才允许打开下一层。

[SLO · 应急](/cloud-native/observability/slo-and-alerting#incident)给出顺序的一句话：**指标确认范围 → 链路定位哪一跳 → 依赖自身 → 最后才看代码。** 本篇把这句话展开成可执行的分支。PromQL 怎么写、SLI 怎么定、错误预算怎么向业务解释，仍在指标篇与 SLO 篇——**本篇不读那些。**

> **主线：慢是症状，不是诊断。**
>
> 先回答两个问题就能砍掉 80% 的瞎翻：① **范围**（一个接口还是全站、一个实例还是全部、从哪一分钟开始）；② **哪一跳**（本进程、出站 HTTP、数据库、缓存、消息）。跳过这两问直接 `jstack` 或翻日志，会把一次 10 分钟能收口的故障拖成两小时。

## 一、先定范围，再允许下钻 {#scope}

告警响了或用户说「慢了」，第一屏只看这四格——用已有看板即可，不必写新查询：

| 问题 | 看什么 | 切出的结论 |
|---|---|---|
| **哪个接口** | 延迟 / 错误率按 `uri` 模板（不是原始 URL） | 单接口 → 这条链路；多接口同时 → 共享依赖 |
| **哪几个实例** | 按 `instance` / Pod | 单实例 → 该实例资源、GC、坏连接；全实例 → 下游或数据 |
| **从哪一分钟开始** | 延迟曲线的拐点 | 拐点对齐发布、扩容、开关、下游变更 |
| **失败还是成功变慢** | 成功请求 vs 失败请求的延迟 | 失败很快、成功很慢 是两种病 |

四格看完，禁止做的两件事：

1. **不要先重启。** 重启抹掉现场（线程栈、连接状态、GC 日志），只在确认是单实例卡死且已保留证据之后才作为止血。
2. **不要先翻应用日志。** 没有 `uri` + 时间窗 + 实例，日志没有筛选条件，会变成关键词搜索。

范围判定的指标口径见[指标篇 · 范围](/cloud-native/observability/metrics-prometheus#scope)。本篇借用它的结论，不重复怎么写查询。

## 二、决策树：哪一跳吃掉了时间 {#tree}

范围是「某接口、全体实例、从 12:07 开始、成功请求 P99 从 200ms 到 3s」。下一步用**一条链路**（一个 `traceId`）看时间花在哪一跳：

```
挑一条慢请求的 trace
        │
        ▼
┌─ 时间几乎都在本服务 span 内，没有下游？ ───────────────┐
│    看本进程：线程池排队 / 锁 / GC / CPU / 本地 IO        │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─ 时间在出站 HTTP span？ ───────────────────────────────┐
│    → [出站超时](/java/spring/spring-framework/crosscutting/outbound-http)     │
│    下游 span 也慢 → 问题在下游，转下游的同一棵树         │
│    本侧等待很长、下游 span 很短或没有 → 卡在借连接 / DNS │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─ 时间在 DB span / JDBC？ ──────────────────────────────┐
│    → [连接池](/database/mysql/connection-pool#leaks)     │
│    `pending` 高而 DB `Threads_running` 低 → 池太小      │
│    两者都高 → 慢 SQL 占住连接，加池无效                  │
│    单条 SQL 慢 → [慢查询](/database/mysql/diagnosis)     │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─ 时间在 Redis / MQ？ ───────────────────────────────────┐
│    缓存：命中率断崖还是单 key 变慢                       │
│    消息：同步等待消费结果？那是设计问题，不是调参问题     │
└─────────────────────────────────────────────────────────┘
```

**链路断了怎么办？** 只看到本服务一个 span、明明有出站——先当传播断点（网关丢头、线程池丢 MDC、MQ 没传 context），不要当「没有下游」。断点清单在[链路篇](/cloud-native/observability/tracing-otel#propagation)。

挑 `traceId` 的原则：挑 **P99 附近的成功请求** 和 **一条失败请求** 各一条。只盯失败容易把「下游 500」和「本服务排队」混成一种慢。

## 三、四个高频分支 {#branches}

树走到某一跳之后，用这一节收口。每一支只保留**判别信号**和**错误动作**。

### 3.1 出站 HTTP {#branch-http}

| 信号 | 含义 | 不要做的 |
|---|---|---|
| 下游 span 与本侧出站 span 几乎一样长 | 慢在下游，把树交给下游 | 在本服务加线程、加本池 |
| 本侧出站 span 长、下游很短或缺失 | 卡在连接池 / DNS / 连上之前 | 把 `readTimeout` 再加大 |
| 网关 504，本服务无超时日志 | **外层先超时** | 先搜业务异常 |

对齐方法见[出站 HTTP](/java/spring/spring-framework/crosscutting/outbound-http#timeouts)。

### 3.2 数据库与 Hikari {#branch-db}

| 信号 | 含义 | 不要做的 |
|---|---|---|
| `pending > 0` 持续，DB 侧很闲 | 池小或泄漏 | 先加 `maximumPoolSize` 而不看 `active` 是否单调涨 |
| `pending` 与 `Threads_running` 都高 | 慢查询占连接 | 加池（会把锁竞争搬到数据库） |
| 重启后恢复、过一段时间再满 | 泄漏 | 当「偶发」忽略 |

四种根因见[连接池 · 池打满](/database/mysql/connection-pool#leaks)。

### 3.3 本进程：线程、锁、GC {#branch-local}

只在「时间花在本服务、没有下游 span」时进入。L2 的工具链是现成的：

| 信号 | 下一步 |
|---|---|
| 入口排队（Tomcat `acceptCount` / 工作线程打满） | [内嵌容器三参数](/java/spring/spring-boot/web-server#three-params)；常是下游慢反推回来的，先回 3.1 / 3.2 |
| 大量线程卡在同一把锁 / `TIMED_WAITING` 在连接池 | [jstack 六种形态](/java/jvm/troubleshooting-cli#division) |
| GC 停顿与 P99 尖刺对齐 | [调优与线上排查](/java/jvm/tuning)；容器里先核对[堆 ≠ RSS](/cloud-native/docker/#jvm-in-container) |
| CPU 打满且无 GC | 火焰图 on-CPU；不要先加副本 |

### 3.4 日志能回答、指标不能回答的 {#branch-log}

定位到那一次之后，才需要日志：**入参非法值、下游原始错误体、本服务抛出的那一行。** 前提是日志里有独立的 `traceId` 字段——约定见[应用日志](/java/spring/spring-boot/logging#fields)。

用日志算 P99、用日志当调用链，都是在用最贵的信号做便宜信号的工作。指标负责范围，链路负责哪一跳，日志负责那一次的内容。

## 四、和面试检索题怎么分工 {#vs-interview}

| | [一次请求的旅程](/interview/#thread-request) | 本篇 |
|---|---|---|
| 问题类型 | 「经历了什么」——按层报清单 | 「这一次慢在哪」——按证据选分支 |
| 正确姿势 | 挑自己熟的一段讲深 | 先范围后哪一跳，禁止从代码开查 |
| 容易答漏 | 某一层没报（epoll、探针） | 跳过范围、拿错池、外层 504 当业务 bug |

两道题可以在同一场面试里前后出现。先答旅程，再被问「那线上 P99 从 200ms 变成 3s 你怎么办」——切到本篇的树，不要把旅程再背一遍。

## 五、收到现场之后的产出 {#output}

决策树的终点不是「我觉得是数据库」。终点是三件可交接的东西：

| 产出 | 最低内容 |
|---|---|
| **时间线** | 精确到分钟：拐点、发布、你做的每个动作、当时以为是什么 |
| **证据** | 一条 `traceId`、一屏范围图、一个池指标或一段栈 |
| **动作** | 止血（限流 / 回滚 / 扩容 / 关开关）与根因修复分开写 |

时间线是给[故障复盘](/projects/toolkit/postmortem/)用的原料。没有时间线的复盘只能写成「某人要更小心」。演练、混沌、告警是否响，不在本篇——见[混沌与演练](/high-availability/chaos-drills)与 [SLO · 应急](/cloud-native/observability/slo-and-alerting#incident)。

## 六、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 接口慢了第一步看什么？ | **范围**：哪个接口、哪几个实例、从哪一分钟、成功还是失败变慢。确认之前不翻代码、不重启 |
| 2 | 为什么不要先看日志？ | 没有时间窗和 `traceId`，日志没有筛选条件。指标定范围，链路定哪一跳，日志看那一次的内容 |
| 3 | 怎么定位「哪一跳」？ | 挑一条 P99 附近的 `trace`，看时间花在本服务、出站 HTTP、DB 还是缓存。断链先当传播问题 |
| 4 | 网关 504、应用没有超时日志？ | 外层先超时。对网关超时与出站/JDBC 超时，见[出站 HTTP](/java/spring/spring-framework/crosscutting/outbound-http) |
| 5 | 连接池打满一定是池太小吗？ | **不是。** 泄漏、慢 SQL 占连接、池小、数据库侧连满，四种处理完全不同 |
| 6 | 什么时候才 `jstack`？ | 时间花在本服务且没有下游 span，或线程池/锁已经被范围证明是候选。用它验证分支，不拿它开场 |
| 7 | 单实例慢和全实例慢有什么差别？ | 单实例偏向该进程（GC、坏连接、CPU）；全实例偏向共享依赖或刚发布的共同变更 |
| 8 | 成功请求变慢和失败变慢？ | 必须分开看。失败快速返回会把混合 P99 拉低，掩盖成功路径变慢 |
| 9 | 这道题和「一次请求经历了什么」有何不同？ | 后者是检索清单；这道是决策树。被追问线上怎么查时，不要把清单再背一遍 |
| 10 | 查完应该留下什么？ | 精确到分钟的时间线、一条 `traceId`、范围证据、止血与根因修复分列。这是复盘的输入 |
