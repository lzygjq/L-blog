# 日志管道：从"打日志"到"能检索"

指标告诉你"哪里不对"，链路告诉你"慢在哪一跳"，但**"到底发生了什么错"只有日志能回答**——异常堆栈、参数的非法值、下游返回的原始错误码，这些细节在任何聚合视图里都看不见。

代价是日志是三个支柱里**最贵的**：按行数计价、按字节存储、按保留期付费。一条 INFO 日志写十次不难，难的是三个月后它还查得回来、而账单没失控。

> **日志的成本与价值，都由同一个东西决定：结构。**
>
> 结构化决定**能不能查**（字段可筛选、可聚合、可关联）；分级与采样决定**花多少钱**。这两个决定都不是"日志框架"的问题，而是**在写第一行日志之前就要定下来的约定**。
>
> 而一旦结构定错——比如把 `traceId` 拼进 `message` 字符串——你会在排查事故的那天，才发现**日志系统根本没法按它检索**。

## 一、日志在三个支柱里的位置 {#position}

| 支柱 | 回答 | 数据量 | 成本 |
|---|---|---|---|
| 指标 | 趋势与"是否异常" | 小（可长期留存） | 低 |
| 链路 | "慢在哪一跳、谁调用了谁" | 中（与采样率成正比） | 中 |
| **日志** | **"具体发生了什么"** | **最大** | **最高** |

这个成本结构决定了分工：**不要让日志去做指标和链路该做的事**。

- 用日志算 QPS、算 P99 —— 成本高几个数量级，且精度还不如直方图；
- 用日志重建完整调用链 —— 你在用最贵的方式复制链路系统已有的能力；
- 把每条日志都当"未来可能有用的证据"全量留 —— 这就是账单失控的起点。

**日志唯一的不可替代性，是"内容"本身**：那次请求的入参是什么、异常栈的第三行是什么、下游返回的错误原话是什么。**所有设计都应围绕"让这些内容可被精确定位"**。

## 二、结构化：字段规范是唯一的地基 {#structured}

结构化的意思不是"输出 JSON"，而是**字段名与语义全站统一**——否则每个服务一套 JSON，聚合时还是要写正则。

| 层次 | 做法 | 解决的问题 |
|---|---|---|
| 格式 | **结构化（JSON）**，不拼接字符串 | 机器可解析、字段可筛选 |
| 字段 | 统一字段名：`timestamp` / `level` / `service` / `traceId` / `spanId` / `message` | **跨服务关联** |
| 上下文 | 请求级字段（用户、租户、接口）随请求注入，不手工传参 | 避免"漏打一个参数" |
| 输出 | 写到 **stdout**，由平台统一采集 | 容器哲学：应用不关心日志去哪 |

**最低限度的字段约定**（跨语言、跨团队都成立）：

```
timestamp  时间戳（ISO 8601 带时区，不用本地时间）
level      日志级别（统一大写，且限定枚举）
service    服务名（与指标里的 service 标签、链路的 service.name 一致）
traceId    贯穿整次请求的标识（关联链路的钥匙）
spanId     当前跨度（定位到"是这段代码"）
message    人类可读的描述
error.*    异常类型 / 堆栈（结构化，不要塞进 message）
```

> **关键：`service` 与 `traceId` 这两个字段，必须和指标、链路用同一套取值。** 三个支柱能否互相跳转，完全取决于这几个字段是否对齐——这是"可观测"与"三个独立工具"的唯一分界线。

应用进程内怎么落到 Logback / Boot（级别纪律、stdout、MDC、禁止拼进 `message`），见[应用日志约定](/java/spring/spring-boot/logging)。**本篇从字段离开进程之后接着讲。**

**`traceId` 怎么进日志？** 靠 MDC（Mapped Diagnostic Context）+ 链路库自动写入，而不是手写：

```xml
<!-- logback 的 pattern 里加上 %X{traceId:-} -->
<pattern>%d{ISO8601} %-5level [%X{traceId:-},%X{spanId:-}] %logger{36} - %msg%n</pattern>
```

用 Micrometer Tracing（Spring Boot 3 的官方路线）或 OTel 的 Java Agent 时，**当前 span 的上下文会自动进 MDC**，业务代码一个字都不用改。手工开线程、线程池、`@Async` 是常见的断点——上下文不会自动跨线程传递，需要显式包装（详见[链路篇](/cloud-native/observability/tracing-otel#propagation)）。

## 三、一条日志的旅程：从应用到可检索 {#pipeline}

```
应用 → stdout（结构化 JSON）
  → 节点级采集 agent（DaemonSet / sidecar）
  → 缓冲与处理（解析字段、脱敏、批量、重试）
  → 存储与索引（全文索引 或 标签索引）
  → 查询界面 → 与指标/链路互相跳转
```

每段的职责与坑：

| 段 | 关键点 | 常见坑 |
|---|---|---|
| **应用 → stdout** | 应用不写文件、不管轮转 | 直接写容器内文件 → 容器重启即丢，且 `kubectl logs` 看不到 |
| **采集 agent** | 节点级 DaemonSet 覆盖所有 Pod；采集端做**第一道解析** | agent 挂了 → **日志静默丢失**，且没有任何告警（因为告警本身依赖日志） |
| **缓冲** | 端到端要有背压或磁盘缓冲 | 后端抖动导致 agent 内存涨爆，进而拖垮节点 |
| **处理** | 字段解析、脱敏、丢弃明确无用的 DEBUG | 脱敏放在存储之后 = 敏感数据已经落盘了 |
| **存储** | 见下节两条路线 | 索引策略没定 → 三个月后存储成本翻倍 |

**采集组件的现状（2026-09，这条最容易照抄过期资料）**：

- **Promtail 已在 Loki 3.7 线被移除**（它的代码并入 **Grafana Alloy**，后者现在是 Grafana 系的第一方采集器）。网上大量"用 Promtail 采集"的教程对应的是 3.6 及更早；
- **Fluent Bit** 轻量（C 实现、内存占用小），适合节点级 DaemonSet；**Fluentd**（Ruby）插件生态更大但更重；
- **OpenTelemetry Collector** 是跨信号的统一管道（可以同时收 metrics/logs/traces 并做 tail-based sampling），**如果你已经在用 OTel，优先它**——少维护一套采集配置。它**也是 Apache-2.0**。

## 四、两条存储路线：全文索引 vs 标签索引 {#two-architectures}

这是日志系统选型里唯一真正重要的分野，因为它决定了成本曲线和查询能力的形状。

| | **全文索引**（ELK / OpenSearch） | **标签索引**（Loki） |
|---|---|---|
| 索引什么 | **每个字段、每个词** | **只有标签**（流级别的元数据） |
| 检索能力 | 任意字段的全文检索、复杂聚合 | 按标签缩小范围后，**在日志行上做过滤** |
| 存储成本 | **高**（索引往往比原文还大） | **低**（原文压缩后放对象存储） |
| 查询延迟 | 稳定、可预期 | **与"扫描多少日志量"成正比** |
| 运维复杂度 | 高（分片、生命周期、JVM 调优） | 低（无状态 + 对象存储） |
| 许可 | Elasticsearch/Kibana 为 **SSPL + Elastic License**（非 OSI）；OpenSearch 为 **Apache-2.0** | **AGPLv3**（客户端与部署资产另有 Apache-2.0 豁免） |

**用一句话概括这个分野**：ELK 是"**先建索引，查询快但要为索引付存储费**"；Loki 是"**不建内容索引，省下存储费，代价是每次查询都要扫**"。

> **所以它们的适用边界不同**：需要"任意维度即席检索、审计取证、复杂聚合"→ ELK（成本可接受时）；需要"成本可控地存大量日志、且主要按服务/Pod/时间定位"→ Loki。
>
> **ES 的存储与检索机制（倒排索引、分片、ILM 生命周期）不在本篇展开**，见[搜索与检索](/search/#thread)与其中的[日志检索栈与生命周期](/search/operations-and-log-stack#elk)（含 ILM 的 `#ilm` 策略配置）。

## 五、Loki 的结构性矛盾：想按 traceId 查，但它最不适合 {#loki-paradox}

这一节单独立出来，因为它是**在真实选型中最容易踩空的地方**，而且踩空的方式很隐蔽。

Loki 的模型是「**标签 + 日志流**」：同一组标签的日志属于同一个流，被压缩成一个 chunk 存进对象存储。查询时先用标签把候选流缩小，再在流上做过滤。**这意味着标签的组合数就是流的数量**——而**流的数量直接决定索引大小与查询时要打开的 chunk 数**。

于是出现一个尖锐的矛盾：

> **可观测性要求"任何信号都能按 `traceId` 关联"，而 `traceId` 恰恰是教科书级的高基数标签——每个请求一个值，永不重复。**

如果我们真的把 `traceId` 放进 Loki 标签，会发生什么？日志流数量会等于请求数量级，索引爆炸，写入与查询双双崩塌。**Grafana 官方文档明确说明：Loki 不是为高基数标签值设计的**，高基数标签（用户 ID、`traceId`、订单号）会显著降低性能。

**那怎么解决"从日志按 traceId 反查"？** 有三条现实路径，按推荐度排序：

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **结构化元数据（structured metadata）** | Loki 3.x 支持**不参与索引的元数据字段**（如 `traceId`），查询时作为过滤条件 | 需要较新的 schema；它不是标签，**不能用于"列出所有 traceId"这类聚合** |
| **留在日志内容里 + 过滤器** | 日志 JSON/SQL 里本就带 `traceId`，查询时写 `{service="order"} \|= "traceId=8f3a"` | **必须先用标签把范围缩小**，否则就是全量扫描——这正是 Loki 成本模型的边界 |
| **由链路侧发起，而不是日志侧** | 排查永远从链路开始（链路知道慢的那次请求），拿到 `traceId` 后再**精确跳到日志** | 反向（日志→链路）依然弱；这要求团队把链路作为排障入口 |

> **判据：`traceId` 是"关联字段"，不是"检索维度"。** 任何把 `traceId` 当标签/分区键的做法，无论在 Loki 还是 Prometheus 里，都是同一个错误的两种表现——**把"取值无限增长"的东西当成了索引维度**（这个判据与[指标篇的标签基数](/cloud-native/observability/metrics-prometheus#model)是同一条）。

**Loki 的其他现状（2026-09）**，同样容易照抄过期资料：

- **当前版本 v3.7.7（2026-08）**，3.6.x 线并行维护（v3.6.16）；3.5.x 已停止，**只有两条线在维护**；
- **`store: boltdb-shipper` 已废弃**，且**无法承载结构化元数据与原生 OTLP 接收**，将在 4.0 移除；不满足 **`tsdb` + schema v13** 的实例**会直接拒绝启动**；
- **Grafana Enterprise Logs（GEL）已进入长期支持（LTS，3.6 线）**，只有安全与缺陷修复，**EOL 定在 2029-02**——即自建方向的"企业版"不再是有前景的路径，开源版不受影响；
- 官方在 GrafanaCON 2026 公布了 Loki 的新架构（代号 **Thor**，Kafka 支撑的摄取 + 重写查询引擎），宣称聚合查询扫描量下降约 20 倍、性能提升约 10 倍，**代价是引入 Kafka 作为新的基础设施依赖**。

## 六、成本控制：四个手段，按顺序做 {#cost}

日志成本失控几乎从不是"某个配置错了"，而是**没人对"写多少"负责**。四个手段的性价比依次递减，**前两个做完通常就够**：

| 顺序 | 手段 | 做法 | 效果 |
|---|---|---|---|
| **① 分级** | 把"打给开发看的"降级 | `INFO` 只留关键业务流转；`DEBUG` 默认关闭、按需开 | 通常能砍掉大部分噪音 |
| **② 采样** | 普通请求按比例、**错误全留** | 在日志框架或采集端做 | 直接把总量按比例降下来 |
| **③ 降低单条开销** | 异步 Appender、避免高频循环内打日志、不打印大对象 | 代码与配置层 | 降低 CPU 与序列化开销 |
| **④ 分层存储** | 热数据留短、冷数据压缩归档 | 索引生命周期（如 ES 的 ILM：热 → 温 → 冷 → 删） | 降长期存储费 |

**两条纪律**：

- **高频循环里打日志是把自己拖垮的最快方式**——一次批量处理打十万行，比一次事故写的日志还多；
- **脱敏必须在落盘之前**。日志系统一旦存了身份证/手机号/令牌，后面所有补救都只是"在泄露过的数据上加了一层访问控制"。

> **不要先扩存储。** 那只会让成本跟着日志量一起涨，而**噪音日志不会因为存得下就变得有价值**。

## 七、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 日志在三个支柱里的不可替代性是什么？ | **"内容"本身**：异常堆栈、入参、下游原始错误——这些在任何聚合视图里都看不见。反过来，**用日志算 QPS/P99 是成本最高、精度最差的方案** |
| 2 | 结构化日志的关键是什么？ | 不是"输出 JSON"，而是**字段名与语义全站统一**（`timestamp`/`level`/`service`/`traceId`/`spanId`/`message`），且 `service` 与 `traceId` **必须与指标、链路取同一套值**——这是三个支柱能互相跳转的唯一前提 |
| 3 | `traceId` 怎么进日志？ | **MDC + 链路库自动写入**（Logback pattern 里 `%X{traceId:-}`），业务代码不改。注意**手工开线程、线程池、`@Async` 不会自动传递上下文**，需要显式包装 |
| 4 | 应用该往哪写日志？ | **stdout**。容器哲学是"应用不关心日志去哪"；写容器内文件会随容器重启丢失，且 `kubectl logs` 看不到 |
| 5 | ELK 与 Loki 的根本分野？ | **索引什么**。ELK 索引全文（查询快、存储贵、运维重）；Loki **只索引标签**（存储省、运维轻、但查询要扫）。前者适合即席检索与审计取证，后者适合"按服务/时间定位 + 成本可控" |
| 6 | 为什么不能把 `traceId` 当 Loki 标签？ | 它是**高基数**的（每请求一个值），放进标签会导致流数量等于请求量级 → 索引爆炸、写入与查询崩塌。Grafana 官方明确说明 Loki 不是为高基数标签设计的。**正解：放结构化元数据、或留内容里靠过滤器（前提是先用标签缩小范围）、或干脆由链路侧发起跳转** |
| 7 | 那句判据可以推广吗？ | 可以，而且**它与 Prometheus 的标签基数是同一条**：**凡"取值随业务量增长"的字段，都不能当索引维度**。区别只是 Prometheus 表现为 OOM，Loki 表现为查询变慢 |
| 8 | 采集端怎么选？ | **Promtail 已在 Loki 3.7 线被移除**，代码并入 **Grafana Alloy**；Fluent Bit 轻量适合节点级；**OpenTelemetry Collector 是跨信号统一管道，已在用 OTel 就优先它**（也便于做 tail-based sampling） |
| 9 | 日志成本怎么控？ | 按顺序：**① 分级**（`DEBUG` 默认关）→ **② 采样**（普通请求采样、**错误全留**）→ **③ 降低单条开销**（异步 Appender、不在高频循环里打）→ **④ 分层存储**（ILM 热温冷归档）。**不要先扩存储** |
| 10 | 日志系统有什么"隐性故障"？ | **采集 agent 挂了会静默丢日志**——因为告警本身依赖日志，这个故障往往在事故复盘时才被发现。所以要对"日志摄入量骤降"本身告警（如"某服务 5 分钟内零日志"） |
| 11 | 脱敏应该放在哪一步？ | **落盘之前**（应用侧或采集端处理阶段）。日志系统一旦存了敏感数据，后续所有补救都只是"在已泄露的数据上加了访问控制" |
| 12 | ELK 与 Loki 的许可有什么差别？ | **Elasticsearch/Kibana 是 SSPL + Elastic License（非 OSI 认证）**，OpenSearch 是其 Apache-2.0 分支；**Loki 是 AGPLv3**（客户端与部署资产另有 Apache-2.0 豁免）。做"内嵌、二次分发、对外提供服务"的判断时，两者的边界完全不同 |
