# 成本、许可与落地路线

前面四篇讲的是"每个支柱怎么做对"。但真到落地时，决定成败的往往不是技术细节，而是两个更朴素的问题：**要花多少钱**，以及**这些组件能不能这么用**。

> **可观测性不是"装了什么"的问题，而是"愿意为多少信息付多少钱"的问题。**
>
> 每个支柱都有明确的成本曲线：指标几乎免费、链路与请求量成正比、日志按字节计价。**不理解这条曲线，就会做出"日志全量留三年"这类决定**——它在设计阶段看不出问题，在账单到来的那个季度才显形。

## 一、成本结构：三条曲线决定策略 {#cost-curve}

| 支柱 | 成本与什么成正比 | 曲线形状 | 控制手段 |
|---|---|---|---|
| **指标** | 时间序列数（标签组合） | **近似平缓**（可降采样、长期留存） | 控标签基数；远端存储做降采样与冷热分层 |
| **链路** | 请求量 × **采样率** | **线性**（采样率直接是成本开关） | 采样：头部定基线、尾部保重点 |
| **日志** | 日志**字节数** × 保留期 | **最陡**（原始数据量最大、索引可能比原文还大） | 分级 → 采样 → 降单条开销 → 分层存储 |

**三条推论**：

1. **"能不能长期留存"和"数据量"成反比**：指标留两年很常见，链路留 30 天是常态，日志留 7~30 天最常见。**想让日志留得久，唯一的办法是让它变少**（而不是"买个便宜的存储"——查询成本会替代存储成本出现）。
2. **指标的省钱要点在"基数"而不在"频率"**：把抓取间隔从 15s 改成 60s 只省 75% 的存储，但把基数失控的一个标签删掉可能省 90%。
3. **链路的成本开关是采样率，且它必须与"排查能力"平衡**。10% 采样意味着 90% 的问题请求查不到完整链路——所以**错误与慢请求必须强制采样**。

**数据量怎么估？** 落地前先算一遍，避免"上线即超支"：

```
日志   = 日均请求数 × 每请求日志条数 × 平均单条字节 × 保留天数
链路   = 日均请求数 × 采样率 × 平均 span 数/请求 × 单 span 字节 × 保留天数
指标   = 时间序列数 × (86400 / 抓取间隔) × 单样本字节 × 保留天数
```

**算完通常会发现**：日志一项往往比其他两项加起来还大一个量级——**这就是为什么日志必须是第三个做的支柱，而且第一件事就是定分级与采样**。

## 二、许可：三档差异，会直接否决技术选型 {#license}

可观测性栈的组件分散在三种许可下，**它们的差异不是法律细节，而是"能不能这么用"的硬约束**：

| 许可 | 组件 | 自建使用 | 修改后分发 | 对外提供服务 | 内嵌进商业产品 |
|---|---|---|---|---|---|
| **Apache-2.0** | **Prometheus**、**OpenTelemetry**（含 Collector）、**Jaeger**、**SkyWalking**、**Zipkin**、**Fluent Bit**、**OpenSearch** | ✅ | ✅（需保留声明） | ✅ | ✅（最宽松） |
| **AGPL-3.0** | **Grafana**、**Loki**、**Tempo** | ✅ | ✅ | ⚠️ **向网络用户提供修改版服务时须提供源码** | ⚠️ 需评估，部分公司直接禁用 |
| **SSPL / Elastic License** | **Elasticsearch**、**Kibana**、**Logstash** | ✅ | ❌（**非 OSI 认证**） | ❌ 限制 | ❌ |

**三条必须知道的事实**：

- **Grafana 与 Loki 在 2021-04 从 Apache 2.0 改为 AGPLv3**（Loki 额外给客户端与部署资产留了 Apache-2.0 豁免）。**AGPL 的关键特征是"网络服务也算分发"**——所以"把 Grafana 内嵌进 SaaS 卖给客户"这件事，与"自己装一套看板"是完全不同的法律情形。
- **Elasticsearch/Kibana/Logstash 在 2021-02 改为 SSPL + Elastic License 双许可，不再是 OSI 认证的开源**。这也是 **OpenSearch**（Apache-2.0 分支）存在的原因——**如果你的场景需要"把日志检索能力嵌进产品对外提供"，OpenSearch 是许可上更安全的选择**。
- **AGPL 有明确的商业风险案例**：部分大型企业（如 Google）**内部直接禁止使用 AGPL 组件**。如果你的目标是大厂或金融客户，**技术选型时"用的是不是 AGPL"会变成一个绕不过去的问题**。

> **给个人与中小团队的实用判据**：
> **自己用、不对外提供修改版服务** → AGPL 组件（Grafana / Loki / Tempo）**完全可用**，这是绝大多数场景；
> **要把观测能力包装成产品/服务卖出去** → 优先 **Apache-2.0 那一列**（Prometheus + OTel + Jaeger/Tempo 之外的替代 + OpenSearch），或购买商业授权。

## 三、三条可落地的路线 {#routes}

不必从零设计，按团队现状选一条：

### 路线 A：最小可用（一个人、一台机器、一个 Java 服务）

```
Spring Boot Actuator + micrometer-registry-prometheus
  → Prometheus（单机，本地 TSDB）
  → Grafana（看板 + 告警）
日志：先做到"结构化 + traceId 入 MDC"，暂不上日志平台
链路：暂不上，需要时用 SkyWalking（零侵入、单机可跑）
```

**收益**：一天内可用，覆盖 80% 的日常排查（指标看趋势、日志用 `kubectl logs` + grep）。
**何时升级**：当日志已经"必须跨多个 Pod 查"时，才需要日志平台。

### 路线 B：Grafana 一体化（中小团队的主流选择）

```
应用（OTel SDK/Agent 或 Micrometer Tracing）
  → OTel Collector（统一收 metrics/logs/traces）
  → Prometheus（指标） + Loki（日志） + Tempo（链路）
  → Grafana（三者同一 UI，靠 traceId 互相跳转）
告警：Grafana Alerting 或 Prometheus Alertmanager
```

**收益**：**三支柱在同一 UI 里互跳**，这是"可观测"落地的关键体验；组件全是开源、可自建。
**注意**：全套都是 **AGPLv3**（Grafana/Loki/Tempo）——自用无碍，对外提供修改版服务需评估。

### 路线 C：Java 无侵入（存量系统、不想改代码）

```
各服务挂 -javaagent（SkyWalking / OTel Java Agent）
  → SkyWalking OAP（含拓扑图与告警）或 OTel Collector
  → 存储（SkyWalking 用 BanyanDB；OTel 侧可接 Prometheus + Jaeger）
```

**收益**：**不改一行业务代码**就有链路与拓扑，对"8 年老系统"这类场景收益最大。
**代价**：Agent 有性能开销（需实测）；绑定其数据模型；**进程内的线程池与 MQ 断点依然需要人工处理**（见[链路的传播断点](/cloud-native/observability/tracing-otel#propagation)）。

> **选路线的判据**：**看团队规模与"谁值班"**。一个人维护、且没有专职运维 → 路线 A 起步，别一上来铺全套；有 2~3 人能维护基础设施 → 路线 B；存量系统占比大、改造意愿低 → 路线 C 优先。

## 四、自建还是托管：临界点在哪 {#self-hosted}

自建的成本不只是机器：

| 项 | 自建 | 托管 |
|---|---|---|
| 硬件/云资源 | 显性，可算 | 按量计费，随数据量涨 |
| **人力** | **隐性但最大**——升级、容量、故障处理都要人 | 由厂商承担 |
| **数据主权** | 完全可控 | 取决于厂商与合规要求 |
| 升级与故障 | 自己跟版本、自己踩坑 | 厂商处理，但**你无法控制节奏** |
| 长期成本曲线 | 随规模**次线性**（摊薄人力） | 随规模**线性**（按量付费） |

**临界点判据**：

- **数据量小、团队小** → 托管更划算（自建的人力成本远超机器钱）；
- **数据量大、且已有基础设施团队** → 自建开始划算（托管的线性成本会超过自建）；
- **有数据出境/合规要求** → 只能自建或选支持本地化的方案；
- **只想快速验证** → 先用托管跑通流程，**别为了"省钱"在验证阶段自建**（那时最大的成本是时间）。

## 五、保留与采样的统一设计 {#retention}

三个支柱的保留策略应该**一起定**，否则会出现"指标留着但日志删了"这种"看得到异常、查不到原因"的尴尬：

| 支柱 | 典型保留 | 采样/降采样 | 设计要点 |
|---|---|---|---|
| 指标 | 原始 15 天 + 降采样 1 年 | 原间隔 → 5min / 1h 聚合 | 长期看趋势，不需要秒级精度 |
| 链路 | 7~30 天 | 头部采样 + 错误/慢请求强制留 | **保留期应 ≥ 一次典型故障的追溯窗口** |
| 日志 | 7~30 天（热），更久只留归档 | 普通采样、错误全留、按级别分流 | **热数据的保留期要覆盖"发现问题"的延迟** |

**两条纪律**：

1. **保留期由"追溯需求"决定，不由存储价格决定**。先问"我们一般在故障发生后多久才发现"——如果平均 3 天后才发现，保留 1 天的日志等于没有。**（这也是"发现能力"和"存储成本"之间的真实耦合点。）**
2. **错误路径永远全留**。所有采样策略都要把"错误与慢请求"排除在外——**采样是为了省钱，不是为了省掉最有价值的数据**。

## 六、落地顺序：不要一次上全套 {#sequence}

按"收益 / 成本"排序，**一次做一层，每层都能独立产生价值**：

| 阶段 | 做什么 | 立刻拿到的能力 | 别做什么 |
|---|---|---|---|
| **1** | **结构化日志 + `traceId` 入 MDC** | 能按请求串起单服务的日志；**这一步零基础设施成本** | 别急着上 ELK/Loki |
| **2** | **指标 + 看板 + 值班告警**（Prometheus + Grafana） | 知道"现在好不好"、异常时能叫人 | 别一上来配 200 条告警 |
| **3** | **定义 SLI / SLO / 错误预算** | 告警从"拍阈值"变成"算预算"，**有依据停止发布** | 别把 SLA 当 SLO |
| **4** | **链路**（OTel 或 SkyWalking） | 知道"慢在哪一跳"，与前两层互跳 | 别指望自动埋点覆盖业务语义 |
| **5** | **日志平台**（Loki 或 ELK） | 跨 Pod 检索、与链路互跳 | **别在全量日志下开第一个月** |
| **6** | **采样优化 / 尾部采样 / 成本治理** | 在保住排查能力的前提下压成本 | 别为了省钱把错误路径也采掉 |

> **为什么日志排在第 5 而不是第 1？** 因为**它是成本最高、且依赖前四层才能发挥价值的**：没有 `traceId` 规范，日志平台只是一堆更贵的文本；没有链路，你知道"报错了"但不知道"错在哪一跳"，日志检索只能靠猜关键词。**先把便宜的做透，再上贵的。**

## 七、六种常见误用 {#misuse}

| # | 误用 | 后果 | 正解 |
|---|---|---|---|
| 1 | **把三个支柱当三个独立工具** | 排查时要靠时间戳人工对账 | 统一 `service` + `traceId` 字段，先做关联再谈工具 |
| 2 | **`traceId` 当索引维度** | Prometheus 基数爆炸 / Loki 查询崩 | 它是关联字段不是检索维度（[指标](/cloud-native/observability/metrics-prometheus#model) / [日志](/cloud-native/observability/logging-pipeline#loki-paradox) 同一条判据） |
| 3 | **日志全量留、越久越好** | 账单失控，且噪音数据拖慢查询 | 分级 → 采样 → 分层存储 |
| 4 | **告警盯原因不盯症状** | 告警疲劳，真故障被淹没 | 盯四个信号的症状，见[告警三原则](/cloud-native/observability/slo-and-alerting#principles) |
| 5 | **只看技术指标，不看业务信号** | "订单创建量掉了一半"在四个黄金信号上可能全部正常 | 补业务信号兜底 |
| 6 | **默认"新版本肯定更好"就升级** | Prometheus 3.x 有静默行为变化（`le` 值规范化会让看板查空） | 升级前读 breaking changes 并在 CI 重跑规则测试，见[升级 checklist](/cloud-native/observability/metrics-prometheus#upgrade-30) |

## 八、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 三支柱的成本曲线有什么不同？ | **指标近似平缓**（可降采样、长期留存）、**链路与请求量线性**（采样率就是成本开关）、**日志最陡**（按字节计价，索引可能比原文还大）。所以"日 志留三年"是设计期看不出、账单期才显形的决定 |
| 2 | 指标省钱的关键是什么？ | **控标签基数，不是降采集频率**。抓取间隔 15s→60s 只省 75% 存储，而删掉一个失控的高基数标签可能省 90% |
| 3 | 链路成本怎么控？ | **采样率**（10% 就是 90% 的省钱），但**错误与慢请求必须强制采样**——采样是为了省钱，不是省掉最有价值的数据 |
| 4 | 开源许可在这个领域分几档？ | 三档：**Apache-2.0**（Prometheus / OTel / Jaeger / SkyWalking / Fluent Bit / OpenSearch，最宽松）、**AGPL-3.0**（Grafana / Loki / Tempo，**网络服务也算分发**）、**SSPL/Elastic License**（Elasticsearch / Kibana，**非 OSI 认证，限制对外提供服务**） |
| 5 | AGPL 的实务影响是什么？ | 自用、不改、不对外提供修改版服务 → 完全可用（绝大多数场景）；**把观测能力内嵌进 SaaS 对外卖** → 需评估，且**部分大厂内部直接禁用 AGPL**，这会成为选型的硬约束 |
| 6 | 为什么会有 OpenSearch？ | 因为 **Elasticsearch/Kibana 在 2021-02 从 Apache 2.0 改为 SSPL + Elastic License（非 OSI）**，AWS 用 Apache-2.0 分支保住了"可自由使用"的路径。**需要把检索能力嵌进产品时，OpenSearch 在许可上更安全** |
| 7 | 自建还是托管，临界点在哪？ | 自建的成本大头是**人力**（升级/容量/故障），规模大时摊薄、**次线性**；托管按量付费、**线性**。判据：**数据量与团队规模都小 → 托管**；数据量大且已有基础设施团队 → 自建开始划算。**验证阶段不要自建**，那时最贵的是时间 |
| 8 | 三个支柱的保留期怎么定？ | **一起定，且由"追溯需求"而不是存储价格决定**：先问"故障平均多久才发现"，如果 3 天后才发现，留 1 天日志等于没留。同时保证**错误路径永远全留** |
| 9 | 可观测性该按什么顺序搭？ | **① 结构化日志 + traceId → ② 指标 + 告警 → ③ SLI/SLO/错误预算 → ④ 链路 → ⑤ 日志平台 → ⑥ 采样与成本优化**。**日志排在第 5 位**：它最贵，且没有前四层的关联规范时，只是一堆更贵的文本 |
| 10 | 最常见的结构性误用是什么？ | **把三个支柱当三个独立工具**——排查时靠时间戳人工对账。可观测与"三个工具"的唯一分界线是**关联字段是否统一**（`service` + `traceId` 全站一致） |
