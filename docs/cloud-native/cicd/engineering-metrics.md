# 研发效能度量：从 DORA 指标到团队原型

> **这一篇回答的不是「怎么算得快」，而是「怎么知道快没快」**——以及更重要的：**为什么几乎所有效能度量最后都变成了指标游戏。**

前四篇讲的都是「怎么把东西送上线」：分支怎么管、流水线怎么搭、流量怎么放、错了怎么退。这一篇换一个位置站——**你不在流水线里，你在看流水线**。

这个位置和 L3 的架构视角不同。L3 问「这套发布方案值不值」，L4 问的是「**这套发布体系的产出，值不值它占用的编制和预算**」。要回答后者，你需要把「交付」变成可比较的数字——而一旦变成数字，它就同时变成了一种可以被操纵的东西。

## 一、为什么效能度量几乎总是变成「指标游戏」 {#goodhart}

**当一个指标变成目标，它就不再是一个好指标。** 这句话（古德哈特定律）在工程效能上的表现格外直白：

| 你把什么当目标 | 会得到什么 | 真实损失 |
|---|---|---|
| 部署频率 | 拆分部署：一次发布拆成十次空发布 | 部署这个动作失去意义，出问题时无法定位「哪一次变坏的」 |
| 变更失败率 | **不上报失败**：回滚改叫「计划内回退」，热修不算失败 | 数据变好看，事故照旧 |
| 前置时间 | 提前建分支、提前提交（代码写完前就开 PR） | 指标从「交付速度」退化成「建 PR 的速度」 |
| 恢复时间 | 先恢复再找原因（掩盖根因） | 故障复发率上升，MTTR 好看但可用性没变 |
| 个人产出 | 一切团队指标变成个人 KPI | **数据全面失效**——没人会如实上报自己的坏消息 |

**最危险的不是上表任何一行，而是「这五项一起被当成 KPI」**：前四行还只是某个指标失真，第五行直接让整套度量失去可信度——一旦数据要用来评价人，上报者就会开始按「上报后会发生什么」来决定填什么，而不是按事实。

> **DORA 团队自己说过很多年**：那是一套**模式探测器（pattern detector）**，不是一把**尺子（ruler）**。它用聚类分析找出「哪些能力和哪些结果一起出现」，从不定义固定的性能阈值。

**所以这一篇的用法是**：拿它来**提出改进假设**，不是拿它来**排名**。下面每一节都会同时说「这个指标测什么」和「它会怎么被骗」。

## 二、五项指标：三项吞吐，两项不稳定 {#five-metrics}

DORA 的指标体系在 2024 年做过一次方法调整，2025 年沿用——**但大部分二手材料还在讲四年前的四项**。现行分组是：

| 分组 | 指标 | 测的是 | 一句话口径 |
|---|---|---|---|
| **吞吐** | 部署频率（Deployment Frequency） | 交付的节律 | 单位时间内成功进入生产的部署次数 |
| **吞吐** | 变更前置时间（Lead Time for Changes） | 从「决定改」到「改好了」的墙钟时间 | 从代码提交（commit）到在生产中运行 |
| **吞吐** | 失败部署恢复时间（Failed Deployment Recovery Time） | 出错后的恢复能力 | 从部署失败到服务恢复（原 Time to Restore） |
| **不稳定** | 变更失败率（Change Failure Rate） | 变更的「爆炸率」 | 需要立即干预（回滚/热修）的部署占比 |
| **不稳定** | 返工率（Rework Rate，2024 新增） | 被事故挤占的产能 | 因生产问题而**非计划发生**的部署占比 |

**两处需要特别说明的调整：**

**① 恢复时间被移进了「吞吐」组。** 直觉上它是稳定性指标，但数据里它和部署频率、前置时间一起变化——**能快速恢复，前提是能快速交付**（回滚本身也是一次部署）。这个重新分组本身就是一个结论：**稳定性不是速度的对立面，它是速度的一部分。**

**② 返工率是变更失败率的「补集」。** 两者的分母相同（总部署数），但分子不同：

- **变更失败率**数的是「这次部署搞砸了」；
- **返工率**数的是「这次部署是**被迫**做的」——修上次捅的娄子。

**为什么必须补这一个**：一个团队可以变更失败率很低（很少直接炸），却返工率很高——因为缺陷没炸，只是「差点对」：用户投诉、数据对不上、逻辑漏了一种情况。这类问题不会体现在「有没有回滚」里，但会**吃掉大量排期**。

```
变更失败率低 + 返工率高 = 最容易被误判的一种状态
  看板：一片绿，没有事故
  排期：新需求永远延期，因为 40% 的产能花在修「上一版差一点」的地方
```

> **这类团队的特征话术**：「我们没出过什么大事，就是一直在优化和补齐。」——如果「优化和补齐」占比持续超过三成，那是返工，不是优化。

## 三、口径比数值重要：五个指标各自能被怎么改 {#measurement}

**在真实组织里落地这套指标，80% 的工作量在定口径，而不是取数。** 同一家公司换一套口径，可以从「行业垫底」变成「行业前列」——这不代表团队变好了，代表口径变松了。

| 指标 | 必须先定的口径问题 | 松口径（好看） | 紧口径（真实） |
|---|---|---|---|
| 部署频率 | **什么算一次部署？** | 合并到主干就算 | 真正对用户生效（含灰度全量） |
| 前置时间 | **起点从哪算？** | 从 PR 创建 / 从进入迭代 | 从**第一次提交**（人开始动手） |
| 恢复时间 | 终点是「服务恢复」还是「根因找到」？ | 服务恢复即停表 | 服务恢复即停表（**根因另计，不混入**） |
| 变更失败率 | **什么算失败？** | 只算回滚 | 回滚 + 热修 + 紧急降级（任何「需要立即干预」） |
| 返工率 | 计划外部署怎么识别？ | 靠人标注 | 靠**工单关联**：修复类工单触发的部署 |

**三条定口径的原则：**

1. **口径要能被自动化复现**——靠人标注的口径活不过三个月（一开始很准，三个月后没人填）。
2. **改口径要留痕**——把口径变更写进 ADR 或演进记录。否则半年后没人能解释「为什么三月的数据和四月不可比」。
3. **宁要粗而稳，不要细而虚**——**能自动取到的近似值，胜过一个准确但没人维护的精确值。**

> **实践建议**：第一次推行时，部署频率与前置时间直接从 CI/CD 系统取数（那是流水线天然的副产物），变更失败率与返工率从**工单系统**关联。**四项里至少要有一项是「零人工」的**，否则数据一旦需要人工收集，就一定会在第一个忙季断供。

## 四、2025 年的两个变化：五项指标与七个原型 {#archetypes}

2025 年的 DORA 报告有两个结构性变化，**它们比任何单个数字都重要**。

### 4.1 报告改名了

从 *State of DevOps Report* 改成了 **《AI 辅助软件开发现状》**（State of AI-assisted Software Development）。这不是文案调整，是调研范围的改变——**AI 从「一个话题」变成了「默认前提」**。

### 4.2 取消 Elite / High / Medium / Low 分档，改为七个团队原型

过去十年最被引用的就是那四档。**但它被引用得越多，错得越离谱**——因为它本来就是**聚类分析的结果**（每年根据「哪些指标一起变化」重新聚类），不是固定阈值线。阈值每年都在动，而无数组织的看板把它做成了红黄绿灯。

2025 年，DORA 直接取消了分档，改为**七个团队原型（archetypes）**，依据八个维度聚类：

**八个聚类维度**：吞吐 · 稳定 · 团队绩效 · 产品绩效 · 个人效能 · 有价值工作时间 · 摩擦 · 倦怠

**七个原型**：

| 原型 | 特征 | 通俗说法 |
|---|---|---|
| **和谐高绩效者** | 交付与稳定性俱佳，且没有靠倦怠换 | 心流状态 |
| **稳定而有序** | 稳定但节奏中等 | 安全但可以更快 |
| **高影响、低节奏** | 产出质量好但发布少，靠个人英雄撑 | 肾上腺素陷阱 |
| **务实执行者** | 速度与稳定平衡，但不出挑 | 舒适区 |
| **受流程约束** | 稳定是**因为流程挡住了速度** | 官僚陷阱 |
| **遗留瓶颈** | 高投入低回报，一直在救火 | 仓鼠轮 |
| **基础性挑战** | 各维度都吃力，先求撑住 | 纸牌屋 |

**这个改动为什么值得 L4 注意：**

1. **两个团队可以有几乎相同的 DORA 数字，但处于完全不同的处境。** 一个「稳定而有序」和一个「受流程约束」，五项指标可能一模一样——**区别在于是有能力快而不快，还是想快但快不起来**。分档只看数字，原型看得到原因。
2. **倦怠（burnout）被正式列为聚类维度。** 这是对一个长期误区的纠正：**用「高影响、低节奏」的方式拿到的产出，是用人的损耗换的**，而这笔损耗迟早要以离职率、招聘成本、知识断层的形式还回来——**它只是一笔没有记在技术预算里的成本**。
3. **它承认了「速度」不是唯一目标。** 产品绩效（做的是不是对的事）和有价值工作时间（有没有在做无用功）被并列进来——这两件事**任何交付指标都测不到**。

## 五、AI 时代最反直觉的结论：个人变快，交付变慢 {#ai-paradox}

2025 年报告里最值得记住的一组数字，是 AI 采用率与交付结果的关系：

| 维度 | AI 采用率提升 25% 的关联变化 |
|---|---|
| 文档质量 | **+7.5%** |
| 代码质量 | +3.4% |
| 代码审查速度 | +3.1% |
| **交付性能** | **−1.5%** |
| **交付稳定性** | **−7.2%** |

同时，90% 的受访者表示在工作中使用 AI，超过 80% 认为它提升了自己的效率。**两者并不矛盾**——它们测的是两个位置的东西：

```
开发者感受的「快」          → 写代码、查资料、补文档这一段
交付体系体现的「快」        → 从提交到上线、并且不出事这一段
```

**中间被跳过的那一段就是解释**：代码产出量上升之后，**评审、测试、集成、回归的负载跟着上升，但它们的容量没变**。账单与返工怎么进同一本账，见[AI 治理 · 账单](/ai/governance/#bill)。于是：

- 一次评审要看的代码变多了 → 评审变成走过场（速度指标还涨了 3.1%）；
- 单次变更的「面积」变大 → 变更失败率上升；
- 缺陷更隐蔽（AI 生成的代码「看起来对」）→ 修复周期变长。

**DORA 把这个现象总结成一句话：AI 不修复团队，它放大团队已有的样子。** 基础扎实的团队，AI 让好的更好；流程本来就在打补丁的团队，AI 让补丁打得更快——**债务以更高的速度累积**。

报告里还有一个被反复引用的观察——**AI 信任悖论**：开发者主观感觉更快，但约三成的人不信任自己交付的代码。**主观速度感与客观稳定性在这里第一次出现了系统性劈叉。**

> **对 L4 的直接含义**：**不要用「AI 提效」单独作为预算理由**。提效发生在个人任务层，而你要为交付结果负责——在这个层级上，AI 的净效果取决于**配套的评审、测试与灰度能力能否同步扩容**。一份只算「代码产出提升多少」的方案，会漏掉后面那笔为了接住这些产出而必须追加的投入。

## 六、DORA 覆盖不到的三块：流动、质量成本、拓扑 {#beyond-dora}

五项指标测的是**「交付这件事做得怎么样」**。有三件事它天然测不到，而 L4 恰好都要管：

### 6.1 流动效率：排队时间比处理时间长得多

DORA 的前置时间告诉你「一共多久」，不告诉你**这段时间花在哪**。把它拆开：

```
总前置时间 = 活跃时间（真的有人在处理）+ 排队时间（在等评审、等环境、等窗口）
```

**绝大多数团队的排队时间占大头**——常见比例是 70~90%。这意味着：

> **把「活跃时间」优化一倍，总前置时间只缩短 5%~15%。** 而绝大多数效能改进动作（换工具、加自动化、让工程师更熟练）优化的都是活跃时间。

**改善排队时间的手段完全不同**：限制在制品数量、扩大评审人池、提高环境可用性、把发布窗口从「每周二晚」改成按需。**这不是技术问题，是流程与权力问题**——所以它常常是 L4 能推动而 L3 推不动的。

### 6.2 质量成本：预防的钱看得见，失败的钱看不见

把质量相关的支出分成四类（这是质量管理里沿用几十年的框架，**放到软件上依然成立**）：

| 类别 | 软件里的对应 | 谁在预算里看见它 |
|---|---|---|
| **预防成本** | 代码规范、评审、设计评审、单元测试、培训 | ✅ 看得见（人力与工具预算） |
| **评估成本** | 集成测试、性能测试、安全扫描、灰度观察 | ✅ 看得见（环境与流水线预算） |
| **内部失败成本** | 返工、缺陷修复、环境重建 | ⚠️ **混在研发产能里，不单独统计** |
| **外部失败成本** | 线上事故、客户赔付、应急加班、口碑损失 | ❌ **几乎从不进入技术预算表** |

**这张表最重要的读法是从下往上**：预防与评估是**可以压缩的**（预算紧时第一个被砍），而外部失败成本是**不可压缩的、且量级最大的**。于是形成一个经典的错配：

```
砍掉预防 → 缺陷流到生产和线上 → 用「内部失败 + 外部失败」的成本去补救
                                                ↑
                                    这笔钱不出现在技术预算里，
                                    所以决策时看不见
```

**L4 的杠杆恰恰在这里**：把「内部失败成本」从研发产能里**显式拆出来**（返工工单占比 × 人力成本），把「外部失败成本」按事故复盘**估出量级**。**一旦这两笔钱被写进同一张表，预防投入就不再是一笔「看不到回报的支出」。**

> **和 DORA 的关系**：返工率是这张表的**代理指标**。返工率上升 = 内部失败成本在涨。所以第五节那组 AI 数据（稳定性 −7.2%）换算成钱，就是**质量成本结构的整体右移**。

### 6.3 团队拓扑：能力按认知负荷切，不按人头切

这是本节最容易被当成「管理黑话」的一块，但它有一个很硬的工程依据：**一个团队的认知负荷是有上限的，超过之后，所有指标一起变坏。**

四种团队类型（各自解决不同的问题）：

| 类型 | 负责什么 | 典型形态 |
|---|---|---|
| **流动对齐团队** | 直接交付业务价值 | 面向一个业务域（订单、账单、门禁） |
| **平台团队** | 提供自助式内部能力 | 提供的是**产品**，不是工单服务 |
| **赋能团队** | 帮流动团队补上能力缺口 | 临时性，**成功标志是自己消失** |
| **复杂子系统团队** | 维护高门槛模块 | 需要专家长期在场（如自研调度、引擎） |

三种交互模式：**协作**（短期高摩擦，用于探索）、**X-as-a-Service**（低摩擦，用于稳定边界）、**促进**（赋能用）。

**一个团队在任何时刻只应处于一种主导模式。** 长期同时「协作 + 提供服务 + 被依赖」，就是排队时间的来源——**和 §6.1 的排队是一回事：一个团队成了别人的队列。**

> **与[拆分粒度](/methodology/service-granularity)的关系**：那一篇讲的是**系统边界怎么划**，这一节讲的是**团队边界怎么划**。两者必须一致——**团队边界与系统边界错位的地方，就是协作成本最高、指标最差的地方**（这也是康威定律的真正用法：不是「系统会长成组织的样子」，而是**你要主动让它们对齐**）。

## 七、四条度量铁律与落地节奏 {#rollout}

### 7.1 铁律

| # | 铁律 | 违反后的症状 |
|---|---|---|
| 1 | **不用于个人考核**，也不用于团队排名 | 数据失真（第六节的第一行就是它的结果） |
| 2 | **看趋势，不看绝对值** | 拿自己的数去比行业基准，得出错误结论——**DORA 自己已经取消分档了** |
| 3 | **五项一起看，永不单独汇报一项** | 单项指标必被扭曲；只有组合起来才「不容易既好看又真实」 |
| 4 | **先定口径，再取数，口径变更要留痕** | 半年后无法解释数据的跳变 |

### 7.2 落地节奏：从零人工开始

**不要等「工具建好」再开始。** 这四个阶段每一阶都能独立产生价值：

| 阶段 | 做什么 | 需要什么 | 能回答什么 |
|---|---|---|---|
| **0. 手工起步** | 拿最近 20 次发布手工复盘一遍，算部署频率与前置时间 | 一张表 | 首先会暴露「口径根本没定义」 |
| **1. 自动化两项** | 部署频率 + 变更失败率从流水线取数 | CI/CD 系统（见[流水线设计](/cloud-native/cicd/pipeline-design)） | 交付节律有没有变化 |
| **2. 补上另一半** | 前置时间 + 恢复时间 | 提交记录 + 事故工单 | 变慢发生在哪一段 |
| **3. 补返工与流动** | 返工率 + 排队/活跃时间拆解 | 工单关联 + 流程埋点 | **质量成本与排队成本** |

**顺序不能倒的原因**：第 1 阶段的四项是最容易自动化的（流水线天然有数据），第 3 阶段的两项必须动流程。**先做能自动化的，是为了让数据在第一次忙季就能活下来。**

### 7.3 和这个板块其他篇的关系

```
流水线设计  → 让每一项变更都被记录（数据的源头）
     ↓
研发效能度量 ←── 本篇：从记录里读出节律与稳定性
     ↓
渐进式交付  → 用指标做放量判定（同一批指标的实时用法）
     ↓
回滚与变更  → 恢复时间的构成（一次恢复由哪几段组成）
```

> **本板块的指标是同一套**：渐进式交付篇讲的是**毫秒到分钟级**的指标（放量判定），本篇讲的是**周到季度级**的指标（组织效能）。**它们必须同源**——否则会出现「发布看板一片绿，季度效能报告一片红」的荒诞场面，而这在真实组织里并不少见。

## 八、给 L4 的三条可操作建议 {#for-cio}

1. **把「口径定义」当成一项正式交付物。** 五项指标各自的取数方式、边界、例外，写成一页纸并持续维护。**没有这一页，所有效能讨论都会退化成对数字的争论。**
2. **建立一条「从指标到动作」的链路。** 指标本身不产生价值：返工率上升 → 谁负责分析 → 采取什么动作 → 多久后复测。**没有这条链路的度量，第三个月就会变成没人看的看板。**
3. **用质量成本表和技术投入对话，而不是用效能指标。** 效能指标是**对内的**（工程师看），质量成本与技术投入回报是**对上的**（业务与董事会看）——后者的口径见[技术成本与 ROI](/methodology/tech-cost-roi)。

## 九、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | DORA 四项还是五项？分别是什么？ | 现行是**五项**，分两组。吞吐三项：部署频率、变更前置时间、失败部署恢复时间（2024 年从稳定性组移入）。不稳定两项：变更失败率、返工率（2024 年新增）。**只答四项是过时口径**；如果面试官坚持四项，可以补充说明 2024 年的方法调整，这本身就是加分项。 |
| 2 | 返工率和变更失败率有什么区别？为什么要有返工率？ | 两者分母相同（总部署数），分子不同：变更失败率数「这次部署搞砸了」，返工率数「这次部署是被迫做的」（修上次的娄子）。**返工率能捕捉「没炸但不对」的缺陷**——一个团队可以变更失败率很低却长期用 40% 的产能修复「差一点」的功能，只看前者会误判成健康团队。 |
| 3 | 为什么 DORA 2025 取消了 Elite 分档？ | 因为**分档从来不是 DORA 的本意**。它用聚类分析找出「哪些指标一起变化」，档位和阈值**每年都在变**，是描述性结果；但业界把它当成了固定阈值的记分卡。2025 年改为**七个团队原型**，依据八个维度（吞吐、稳定、团队绩效、产品绩效、个人效能、有价值工作时间、摩擦、倦怠）聚类——**两个原型可以有相同的数字但完全不同的处境**（「稳定而有序」vs「受流程约束」）。 |
| 4 | AI 让团队更快了吗？ | **在个人任务层更快，在交付层未必。** 实测数据：AI 采用率提升 25%，文档质量 +7.5%、代码质量 +3.4%、审查速度 +3.1%，但交付性能 −1.5%、交付稳定性 −7.2%。原因是产出量上升后，**评审、测试、集成的容量没同步扩容**。报告的总结是：**AI 不修复团队，它放大团队已有的样子。** |
| 5 | 怎么防止效能指标被「玩」？ | 四条：**不用于个人考核与团队排名**（一考核数据就废）、**看趋势不比绝对值**、**五项一起看不单独汇报**、**先定口径再取数且变更留痕**。其中第一条是前提——**一旦上报者开始按「上报后会发生什么」填数据，后面三条都失去意义。** |
| 6 | 为什么说稳定性不是速度的对立面？ | 因为 DORA 在 2024 年把**恢复时间移进了吞吐组**——数据上它和部署频率、前置时间一起变化。机制也说得通：**快速恢复的手段就是快速交付**（回滚本身就是一次部署）。所以「要么快要么稳」是个假选择，真实世界里它们同向。 |
| 7 | 上游排队时间为什么比干活时间更值得优化？ | 因为**它占比更大**：常见团队的前置时间里，排队（等评审、等环境、等发布窗口）占 70%~90%。于是把活跃时间优化一倍，总时长只降 5%~15%。而且两者的改善手段完全不同——排队要靠**限制在制品、扩大评审人池、提高环境可用性、去掉固定发布窗口**，这些是流程问题，不是工具问题。 |
| 8 | 质量成本的四类是什么？为什么这张表重要？ | 预防、评估、内部失败、外部失败。**重要的读法是从下往上**：前两类在预算表里看得见、且可以被砍；后两类主要是隐性成本（内部失败混在研发产能里、外部失败几乎不进技术预算）。砍掉预防，成本只是从「看得见的地方」转移到「看不见的地方」并且放大。 |
| 9 | 团队拓扑里的四种团队类型是什么？ | 流动对齐团队（交付业务价值）、平台团队（提供自助式内部能力，产品化而非工单化）、赋能团队（补能力缺口，成功标志是自己消失）、复杂子系统团队（高门槛模块的长期专家）。配合三种交互模式：协作、X-as-a-Service、促进。**一个团队同一时间只应处于一种主导模式**——长期多重角色，就是排队时间的来源。 |
| 10 | 如果一个团队五项 DORA 指标都很好，还需要看什么？ | 至少三样：**① 「高影响、低节奏」型团队可能五项都好但靠倦怠撑着**（2025 年报告把倦怠列为聚类维度正是为此）；**② DORA 测不出「做的是不是对的事」**（产品绩效），也测不出「有没有在做无用功」（有价值工作时间）；**③ 返工率低不代表没有质量成本**，它只是内部失败成本的一个代理——完整的账在质量成本四类里。 |
| 11 | 效能度量的数据从哪里来？ | 优先**「零人工」来源**：部署频率与前置时间来自 CI/CD 系统（[流水线设计](/cloud-native/cicd/pipeline-design)），变更失败率与恢复时间来自发布记录与事故工单，返工率靠**工单与部署的关联**自动识别。**四项里至少要有一项是完全自动的**，否则数据一定会在第一个忙季断供——**靠人标注的指标活不过三个月。** |
| 12 | 向业务解释效能度量时，怎么避免听起来像「刷数据」？ | 换一套语言：不说「部署频率提升了」，说「**从提出需求到用户能用上，平均时间从 21 天降到 9 天**」；不说「变更失败率降低」，说「**因上线导致的生产事故从每月 3 起降到 0.5 起**」。**指标的对外版本永远是「对业务意味着什么」，对内版本才是过程指标。** |
