# Git 协作：分支模型、提交粒度与可追溯性

CI 的输入是**提交**。流水线的门禁再严，也只是一个筛子——如果进来的是"一次改了 47 个文件"的提交，红灯只能告诉你"这批东西有问题"；至于哪里有问题、谁引入的、能不能只回退其中一块，全都答不出来。

所以这一篇放在 [CI/CD 与发布](/cloud-native/cicd/) 板块的**最前面**，先于[流水线设计](/cloud-native/cicd/pipeline-design)。原因很简单：**自动化只会放大既有的实践**。提交粒度粗、分支寿命长的团队上了流水线，得到的只是"更快的红灯"和"所有人都学会点一下重跑"。

> **主线：Git 的价值不是"能回退"，而是让每一次变更可追溯、可评审、可定点撤销。**
>
> 三个词各对应一件具体的事：**可追溯**靠提交与制品的一一对应（[用提交 SHA 作镜像标签](/cloud-native/cicd/pipeline-design#tag-strategy)）；**可评审**靠提交粒度与评审规模；**可定点撤销**靠历史有没有被改写。

## 一、分支模型的争论为什么总是没有结论 {#models}

"主干开发还是 Git Flow"这类讨论经常吵不出结果，因为它被当成了**品味问题**。它其实是**约束问题**——分支持续时间、合并频率、自动化程度、发布节奏，这四个约束一旦确定，模型基本就唯一了。

三种主流形态：

| 模型 | 分支结构 | 分支寿命 | 合并到主干 | 适合的前提 |
|---|---|---|---|---|
| **主干开发**（Trunk-Based） | 只有主干 + 极短的功能分支（或直接在主干上小步提交） | 小时 ~ 天 | 每天多次 | 测试可信、能快速回滚、有功能开关 |
| **GitHub Flow** | 主干 + 功能分支 | 天 ~ 周 | 每个 PR 一次 | CI 完备、评审及时、发布频繁 |
| **Git Flow** | 主干 + develop + feature + release + hotfix | 周 ~ 月 | 版本节点集中合并 | **有明确版本发布周期**、多版本并行维护、无法快速发布的产品 |

**判据只有一条：你能不能接受"主干在任意时刻都是可发布的"。**

- 能 → 主干开发或 GitHub Flow 都行，选分支数量更少的那种；
- 不能（比如要给客户交付 1.2 和 1.3 两个维护版本）→ Git Flow 的分支结构不是多余的，它是**版本并行维护**这个业务的投影。

> **分支寿命是这里唯一的隐变量。** 分支活得越久，它偏离主干的程度越大，而冲突的规模与解决成本**不是线性增长**——冲突的数量随偏离度上升，且冲突一旦涉及重构，解决冲突的人往往不理解对方为什么那么改。**"我合并一下主干"这句话每次出现，都在给这个账本上再加一笔。**

因此**主干开发不是"更先进"，而是"代价前置"**：它要求你先具备三件能力，否则会把风险从合并时刻挪到上线时刻：

| 能力 | 缺了会怎样 | 相关篇目 |
|---|---|---|
| **测试可信** | 小步提交没法验证，等于把未验证的改动持续灌进主干 | [测试与质量](/java/testing/) |
| **能快速回滚** | 出问题只能向前修，主干永远是"半坏"状态 | [回滚与数据库变更](/cloud-native/cicd/rollback-and-migration) |
| **开关能拆发布与上线** | 未完成的功能会直接暴露给用户 | [Feature Flag](/cloud-native/cicd/progressive-delivery#feature-flag) |

**反过来说**：如果你暂时没有这三件能力，那**分支模型不该是你先动的东西**——先补其中一样，再改模型。这就是为什么这一篇和[流水线设计](/cloud-native/cicd/pipeline-design)是同一条链上的上下游。

## 二、提交：粒度决定回退的分辨率 {#commits}

判断一个团队有没有工程习惯，看提交历史 30 秒就够了。

**"一次提交只做一件事"不是洁癖，它决定了两件事的可行性：**

1. **能不能只回退其中一块。** 一个"重构 + 新功能 + 顺手改了配置"的提交，出问题时你只有两个选择：全退（连带把重构也退了）或向前修（在生产上排查一个混合体）。
2. **能不能定位引入点。** [`git bisect`](#traceability) 之所以有效，前提是提交之间是"可独立判定的最小变化"。

实测一下自己的仓库：

```bash
# 改动行数最大的 10 个提交 —— 它们就是最难回退的那批
git log --pretty=format:'%h %s' --shortstat -n 200 \
  | awk '/files? changed/{print prev"  "$0} {prev=$0}' \
  | sort -t'(' -k2 -rn | head -10

# 平均提交规模（看趋势，不看单点）
git log --shortstat --oneline -n 500 | grep -o '[0-9]* insertion' | awk '{s+=$1;n++} END{print s/n}'
```

**一次提交里混了什么，是有客观信号的**：如果一个提交的 `--shortstat` 同时命中 `src/**` 与 `pom.xml`，且信息是"优化"两个字，它大概率是混合提交。

| 提交内容 | 该不该在一起 | 判据 |
|---|---|---|
| 一个功能 + 它的单元测试 | ✅ 在一起 | 测试是对同一行为的验证 |
| 重构 + 行为变更 | ❌ 分开 | 重构应当能独立证明"行为未变" |
| 格式化 + 逻辑修改 | ❌ 分开 | 否则 diff 淹没在空白改动里，评审失效 |
| 依赖升级 + 适配代码 | ⚠️ 看情况 | 升级必须与适配同批（否则主干编译不过），但要说明 |
| 修 bug + 顺手改配置 | ❌ 分开 | 回退 bug 修复时不该带着配置一起走 |

**"提交必须能编译"是一条硬线**（对主干开发而言），所以"依赖升级 + 适配"这类无法拆开的情况要在提交信息里写明原因——**不是所有粒度问题都能两全，但"为什么必须一起"必须被记录。**

### 提交前的三件小事

```bash
git diff --staged          # 我要提交的到底是什么（不是 git diff）
git add -p                 # 一个文件里混了两件事时，按块挑选
git stash                  # 临时切分支时用，不要用 WIP 提交代替
```

`git add -p` 是"提交粒度"这件事上最高杠杆的一个命令：**它让"一个文件里混了两件事"变成可以拆的**。没有它，颗粒度的下限就是"按文件拆"。

## 三、提交信息：写给三个月后的自己和自动化 {#messages}

提交信息有两个读者，而且第二个读者常被忘记：

| 读者 | 读它为了什么 | 因此必须包含 |
|---|---|---|
| 三个月后的你（或同事） | 为什么这么改、有没有别的方案 | **动机**，不是"改了什么"（diff 已经说了） |
| 自动化工具 | 生成 changelog、推导版本号、关联 issue | **结构化前缀**（机器可解析） |

**约定式提交（Conventional Commits）**正是为第二个读者设计的：

```
<type>(<scope>): <subject>

<body: 为什么这么改、排除了哪些方案>
<footer: BREAKING CHANGE / Closes #123 / Refs #456>
```

| type | 含义 | 触发语义化版本 |
|---|---|---|
| `feat` | 新功能 | minor |
| `fix` | 缺陷修复 | patch |
| `perf` | 性能优化 | patch |
| `refactor` / `style` / `docs` / `test` / `chore` / `build` / `ci` | 不改变外部行为 | 不触发 |
| 任意类型 + `BREAKING CHANGE:` | 破坏性变更 | **major** |

**收益是具体的**：`feat`/`fix` 能自动生成 changelog，`BREAKING CHANGE` 能自动推导大版本号，`Closes #123` 能在合并时自动关闭 issue。**这些都是"结构化的提交信息"换来的，不是"写得好看"换来的。**

**反面样本与它的真实代价**：

| 写法 | 三个月后你要付出的 |
|---|---|
| `fix bug` / `update` / `优化` | 靠 `git log -p` 逐条看 diff 才能想起改了什么 |
| `修复了用户反馈的一个问题` | 不知道是哪个问题、影响哪个模块 |
| 只写"改了什么"（粘贴 diff 摘要） | 缺动机——最需要的恰恰是"为什么"，因为它不在代码里 |
| 一个提交 30 条 bullet | 说明它本该被拆成若干个提交 |

> **一条实用判据**：写提交信息时，如果"为什么"这一栏写不出东西，**这次改动可能不该独立成提交**——它要么是上一件事的延续，要么本就是一次无关改动，后者应该拆出去。

**历史要不要整理？** 分界线是**有没有推送**：

```
推送到共享分支之前  → 随便改（amend / rebase / squash），历史干净是好事
推送到共享分支之后  → 不改写历史，用新提交去纠正
```

理由是成本：改写公共历史会让**别人的本地分支与远端分叉**，他们下次 pull 时会拿到一份"自己的提交不见了"的历史，轻则冲突重来，重则丢掉别人正在做的工作。**这条规则在下一节会以"黄金法则"的形式再出现一次。**

## 四、代码评审：评审什么、评审多大 {#review}

评审是**唯一能在合并前拦住设计问题**的环节。测试拦不住设计问题——一个设计错的模块照样能通过全部单测。

### 4.1 该评审什么

评审的注意力是有限资源，所以必须**明确它不该花在哪**：

| 维度 | 谁负责 | 说明 |
|---|---|---|
| 格式、命名风格、import 顺序 | ❌ 不该由人评审 | 交给 formatter 与 linter（`pre-commit` 直接跑），**人要花在机器做不了的事上** |
| 逻辑正确性、边界条件 | ✅ 评审者 | 空值、并发、异常路径 |
| **设计意图** | ✅ 评审者 | 这个抽象是不是对的、放在这一层合不合适 |
| 可测试性 | ✅ 评审者 | 一个难以测试的设计，通常也是一个耦合过重的设计 |
| 安全与权限 | ✅ 评审者 | 越权、注入、敏感信息泄漏 |
| **是否该做这件事** | ✅ 评审者 | 最高价值的评审意见往往是"这个需求应该用另一种方式满足" |

### 4.2 该评审多大

这是最容易被忽略的一条，也是最容易量化的一条：**缺陷发现率随单次评审规模下降**。

业界经验值（来自代码评审的实证研究）：**单次评审 200~400 行时缺陷发现率最高；超过 400 行后明显下降；上千行的评审基本退化成"扫一眼点通过"。**

它带来的实践约束：

| 规模 | 评审质量 | 建议 |
|---|---|---|
| < 100 行 | 高，能逐行看设计 | 理想区间 |
| 100~400 行 | 中高，能看逻辑 | 可接受 |
| 400~1000 行 | 低，多半只看结构 | **拆分**（按"可独立合并的最小单元"） |
| > 1000 行 | 几乎为零，只剩仪式 | 拆分或改成分阶段提交 |

**"改动就是大怎么办"**——三种可行的拆法：

1. **按"可独立合并"切**：先合接口与空实现，再合第一个实现，再合第二个实现（每一步主干都是可运行的）；
2. **重构与行为变更分离**：先合纯重构（附"行为未变"的证明），再合行为变更；
3. **用 Feature Flag 隐藏**：代码先合入但关闭开关，最后一次性打开——这是[渐进式交付](/cloud-native/cicd/progressive-delivery#feature-flag)里的同一个开关。

**评审者侧的清单**（比"看一遍"有效得多）：

- 这个改动**没有覆盖**的场景是什么？
- 出错路径有没有被处理，还是只写了 happy path？
- 有没有更简单的做法？（**最常被跳过、也最值钱的一问**）
- 如果三个月后要改这个逻辑，我能从代码里看出当初的约束吗？

**作者侧的清单**：

- 描述里写清**动机**，而不只是"我改了 A 和 B"；
- 自我评审一遍（很多平台支持在提 PR 前先看 diff）——**能自己发现的问题不要占用别人的时间**；
- 指明希望评审者重点看哪里（"第 3 个文件里的状态机是这次的关键"）。

> **评审不是"批准"，是"共同承担"。** 一个"看起来没问题"的 approve 和没有评审的合并，对生产的作用几乎一样——差别只在出事之后，责任归属是否清晰。

## 五、整合历史：rebase、merge 与 squash {#integrate}

三种把功能分支合回主干的方式，产出三种不同的历史：

```
原始分支：      A --- B --- C        (main)
                 \
                  D --- E --- F     (feature)

① merge（保留分支结构，多一个合并提交）
      A --- B --- C ------- M       (main)
           \              /
            D --- E --- F

② rebase（把你的提交重放到主干顶端，线性历史）
      A --- B --- C --- D' --- E' --- F'   (main)

③ squash（把整个分支压成一个提交）
      A --- B --- C --- S           (main)
```

| 方式 | 历史形态 | 优点 | 代价 |
|---|---|---|---|
| **merge** | 分叉可见，保留"这批改动是一起的" | 上下文完整、可整批回退（`git revert -m 1`） | 历史有噪声，`git log --oneline` 会被合并提交淹没 |
| **rebase** | 线性，像一直在主干上开发 | 历史干净、便于 `bisect` 与阅读 | **重写了提交 SHA**；冲突可能反复出现（每个提交都要解一次） |
| **squash** | 一个分支 = 一个提交 | 主干历史最干净，回退最粗但最简单 | **丢掉分支内的演进过程**（调试思路、失败的尝试） |

**三者的核心差别是"保留什么信息"**：

- `merge` 保留**结构**（谁和谁一起进来的）；
- `rebase` 保留**顺序**（每一步改动是什么），丢掉结构；
- `squash` 只保留**结果**，丢掉结构与过程。

> **选哪个取决于你们怎么用历史**：如果发布靠"合一个分支就发一次"，`squash` 让"一次发布对应一个提交"最清晰；如果经常要 `bisect` 定位，`rebase` 后的线性历史最快；如果一次 PR 里有多个逻辑独立的小改动、且希望它们各自可回退，那就用 `merge`（或 rebase 后快进合并）。

### 5.1 冲突处理与那个反转陷阱

**rebase 遇到冲突时，`ours` 和 `theirs` 的含义与 merge 时是反的。**

这一点几乎没有人第一次就记住，但它是**改错代码**的高危操作（因为 `git checkout --ours .` 一句话就可能把你的改动全丢掉）：

| 场景 | `ours` 指 | `theirs` 指 | 为什么 |
|---|---|---|---|
| `git merge`（feature → main） | **main**（当前所在分支） | feature（被合进来的） | 你的工作区是 main |
| `git rebase`（feature 重放到 main） | **main（上游）** | **feature（你的提交）** | rebase 是"以主干为基底重放你的提交"，所以基底变成了"我们的" |

记忆方式：**`ours` 永远是"你正在重放到的那个基线"，`theirs` 永远是"被重放的那些提交"**——在 rebase 里，你的提交是"外来者"。

**判断"该保留哪边"的正确方法是看语义，不是看方向**：

```bash
git status                      # 先看清是 merge 还是 rebase
git diff                        # 看冲突标记的实际内容
git checkout --conflict=diff3 <file>   # 显示"共同祖先"，比只看两边更有用
```

`--conflict=diff3`（或配置 `merge.conflictStyle = zdiff3`）会把**共同祖先**也显示出来，于是冲突从"两个版本打架"变成"两边各自改了什么"——多数情况下答案一眼可见。

**两个提效命令**：

- `git rerere`（reuse recorded resolution）：记录你解决过的冲突，**同样的冲突再次出现时自动应用**。rebase 长分支时会反复遇到同一处冲突，开启它能让第二遍以后变成零成本；
- `git rebase --onto`：只把一段提交移到目标分支上（"把 B 分支上从 X 之后的提交挪到 C 上"），是清理错误分支基底的常用手段。

### 5.2 黄金法则

**不要 rebase 已经推送到共享分支的提交。**

它的代价不是"别人的本地仓库会冲突"这么轻——是**别人的提交会从远端历史上消失**，而对方如果没注意，`git push` 时可能把自己的版本又推回去，形成更乱的局面。团队里如果一定要清理远端历史，正确做法是**全体约定时间点 + 通知 + 停止推送**，而不是随手 `push --force`。

配套的强制手段（见[第八节](#enforcement)）：把共享分支的 force push 关掉。**只靠"大家记得"的规则会破，靠平台开关的规则不会。**

## 六、撤销：三件套与 reflog {#undo}

Git 的"撤销"没有单一命令，因为**"撤销什么"有三个层次**：改错文件内容、提交错了、提交已经推送了。

```
                    HEAD        索引(staged)     工作区(文件)
git reset --soft     ← 移动        不动             不动        → 撤销提交，改动仍在暂存区
git reset --mixed    ← 移动        ← 重置           不动        → 撤销提交与暂存，改动留在文件（默认）
git reset --hard     ← 移动        ← 重置           ← 重置      → 全部丢弃（危险）
```

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 文件改错了，想复原 | `git restore <file>` | 只动工作区，不影响历史 |
| 暂存多了 | `git restore --staged <file>` | 只从索引里拿出来 |
| **提交的**信息写错/漏了文件 | `git commit --amend` | **前提：未推送** |
| 提交早了，想重新组织 | `git reset --soft HEAD~1` | 回到"改动都在暂存区"的状态 |
| **已推送**的提交要撤销 | `git revert <sha>` | 生成一个反向提交，**不改写历史** |
| 误重置、丢了提交 | `git reflog` | 找到旧位置，`git reset --hard <sha>` 回去 |

**`reset` 与 `revert` 的分界就是"有没有推送"**：

```
本地未推送  → reset / amend / rebase（改写历史，别人看不见）
已推送共享  → revert（追加历史，所有人都看得见）
```

**`reflog` 是最后一道保险**：它记录 HEAD 的每一次移动，默认保留 90 天。哪怕 `reset --hard` 丢掉了一整个分支，只要还能在 reflog 里找到那个 SHA，就能救回来。

```bash
git reflog                       # 我最近做过什么（按时间倒序）
git reset --hard HEAD@{3}        # 回到三次操作之前
git branch rescue <sha>          # 更稳的做法：先建个分支指向它，再慢慢处理
```

> **`reflog` 救不回来的只有两种情况**：提交从未被任何 ref 引用过（比如 `git commit` 后立刻 `reset --hard`，且已过期被 GC），以及**文件从未被 `git add` 过**（那属于工作区，Git 从未见过它）。**所以"先 add 再操作"是一个免费的保险。**

## 七、可追溯性：从提交到制品 {#traceability}

这一节和[流水线设计的制品治理](/cloud-native/cicd/pipeline-design#artifacts)是同一件事的两端：一边是"怎么让制品带上出处"，一边是"怎么用出处做事"。

**前提是在流水线里把提交 SHA 打进产物**（镜像标签、`MANIFEST` 里的 `git.commit.id`、启动日志里打一行 build 信息）。打通之后，三个具体能力才成立：

| 能力 | 命令/手段 | 用在哪 |
|---|---|---|
| **从上往下**：这个提交改了哪些发布 | `git log <old-sha>..<new-sha>` | 发布前生成变更清单、判断波及面 |
| **从下往上**：线上这个版本对应哪次提交 | 制品元数据 → `git show <sha>` | 被问"线上跑的是哪版"时有答案 |
| **定位引入点** | `git bisect` / `git blame` | 故障归因 |

**`git bisect` 是"排查看代码、而是一堆提交里找一个"的正解**，它的效率是二分——1000 个提交只需约 10 次验证：

```bash
git bisect start
git bisect bad                 # 当前版本有问题
git bisect good v1.7.0         # 这个 tag 是好的
# Git 自动检出中间的提交 → 你测一下 → 说 good / bad
git bisect good                # 或 git bisect bad
# ... 约 log2(N) 次后
git bisect reset               # 结束，回到原分支

# 有自动化脚本时全自动（脚本退出码 0 = good）
git bisect run ./scripts/check-regression.sh
```

**`git blame` 的正确用法**：它找的是"**这一行最后一次是谁改的**"，不是"这段逻辑是谁写的"。所以看到可疑责任人之前，先排除两类噪声：

```bash
git blame -w <file>            # 忽略空白改动（格式化提交会污染结果）
git blame -C -C <file>         # 追踪跨文件复制（移动代码的场景）
git log --follow -p <file>     # 跟随重命名，看文件完整历史
```

更关键的是：**归因的产物应该是"那次改动为什么这么做"，而不是"谁改的"**。前者能修问题，后者只会让评审气氛变差——这也是一句很有名的实践建议"`blame` 用来找提交，不用来找人"的由来。

**提交签名**（`git commit -S`，支持 GPG 与 SSH 两种格式）解决的是"这个提交确实来自声称的人"。它和[制品的 Sigstore 签名](/cloud-native/cicd/pipeline-design#artifacts)是同一思路：**来源可验证**。实践上更常用的是"只对打 tag 的提交强制签名"——普通提交强制签名会带来密钥管理成本，收益有限。

## 八、团队落地：分支保护与钩子 {#enforcement}

**约定 + 强制，两条都要有。** 只有约定，它会随人员流动和赶工期而崩；只有强制（比如平台不提供合并按钮），团队会绕过它——比如把流水线写成一跑就绿。

| 目标 | 约定 | 强制（平台/工具） |
|---|---|---|
| 提交信息规范 | 团队文档写清 type 列表 | `commit-msg` 钩子 / `commitlint` 在 CI 里校验 |
| 代码格式统一 | 说好用什么风格 | formatter + `pre-commit`，**评审不再提格式问题** |
| 主干始终可构建 | "不要直接推主干" | **分支保护：禁止直接 push（含管理员）** |
| 变更有人看过 | "至少一人评审" | **required approvals ≥ 1** |
| 红灯不能合 | "CI 过了才能合" | **required status checks** |
| 评审不过期 | "改了要重新看" | **dismiss stale approvals on new commits** |
| 历史不被改写 | "不要 force push" | **关闭 force push / 打开线性历史 / 签名提交** |

**"含管理员"这一条常被忽略**：如果管理员可以绕过分支保护，那么紧急情况下所有人都会去找管理员——保护策略就退化成了一道社会关系题。**正确的做法是给"紧急通道"一个显式流程（比如允许 hotfix 分支合并 + 事后补评审记录），而不是留一个隐形的后门。**

`pre-commit`（钩子管理器）的配置示例，把机器能做的事全部前移：

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    hooks: [trailing-whitespace, end-of-file-fixer, check-merge-conflict]
  - repo: https://github.com/commitizen-tools/commitizen
    hooks: [{id: commitizen, stages: [commit-msg]}]   # 校验提交信息格式
```

> **钩子的定位要说清楚**：它是**本地快速反馈**，不是门禁——`--no-verify` 可以绕过，且新人的机器上可能没装。**同一套检查必须也在 CI 里跑一遍**，那才是门禁。这和[门禁三档](/cloud-native/cicd/pipeline-design#test-gates)里"阻断档必须由流水线强制"是同一条原则。

## 九、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | `rebase` 和 `merge` 的区别？ | **merge 保留分支结构**（多一个合并提交，能看出"这批改动是一起进来的"）；**rebase 把你的提交重放到目标分支顶端，得到线性历史，但提交 SHA 会变**。选哪个取决于你们怎么用历史——要 `bisect` 与可读性选 rebase，要整批回退与上下文选 merge |
| 2 | 为什么不 rebase 公共分支？ | 因为它**改写了已推送的提交**。别人本地的分支会与远端分叉，对方推送时可能把旧版本推回去，甚至覆盖别人的工作。规则：**未推送随便改，已推送只用 `revert`** |
| 3 | rebase 冲突时 `ours` / `theirs` 是谁？ | **和 merge 时相反**：rebase 的 `ours` 是**上游/主干**，`theirs` 是**你自己的提交**。记忆方式：rebase 是"以主干为基底重放你的提交"，你的提交是外来者。改错会直接丢掉自己的代码 |
| 4 | `reset --soft` / `--mixed` / `--hard` 的区别？ | 三者都移动 HEAD，区别在**是否重置索引、是否重置工作区**：`--soft` 都保留（改动进暂存区）；`--mixed`（默认）重置索引、保留文件；`--hard` 三者全重置，**未提交的改动直接丢失** |
| 5 | `revert` 和 `reset` 的区别？ | `revert` **追加一个反向提交**，不改写历史，适用于已推送的公共提交；`reset` **移动分支指针**，改写历史，只适用于本地未推送。判断依据就一句：**有没有推送** |
| 6 | 误 `reset --hard` 了怎么救？ | `git reflog` 找 HEAD 的移动记录，`git reset --hard HEAD@{n}` 回去（更稳的是先 `git branch rescue <sha>`）。**注意它救不回"从未 `add` 过的文件"**——那些内容 Git 从未记录 |
| 7 | `git bisect` 怎么用？ | 二分查找引入问题的提交：`bisect start` → 标记 `bad` 与 `good` → 逐个验证 → 约 log₂(N) 次定位。有自动化用例时 `git bisect run <script>`（退出码 0 = good）可全自动。**前提是提交粒度足够细** |
| 8 | `squash` 合并有什么代价？ | 丢掉分支内的**演进过程**（调试思路、被否决的中间方案），且分支内的多个独立改动**无法单独回退**。适合"一次 PR = 一个逻辑变更"的团队，不适合需要细粒度归因的场景 |
| 9 | 为什么要 `merge --no-ff`？ | 快进合并（默认 FF）不会留下合并提交，**"这批改动是一个功能"这个信息就消失了**，`git log` 里分支的首尾无法辨认。`--no-ff` 强制生成合并提交，保住结构与"整批回退"的能力 |
| 10 | 分支模型怎么选？ | 看约束不看潮流：主干开发/GitHub Flow 要求**主干随时可发布**（测试可信 + 能快速回滚 + 有功能开关）；Git Flow 适合**多版本并行维护、有明确发布周期**的产品。**分支寿命越长，合并成本越非线性上升** |
| 11 | 提交信息规范的实际收益是什么？ | 两个：**给人**——三个月后能读懂"为什么这么改"；**给机器**——`feat`/`fix` 自动生成 changelog、`BREAKING CHANGE` 自动推导 major 版本、`Closes #123` 自动关 issue |
| 12 | 代码评审该控制在多大？ | 经验值是**单次 200~400 行以内缺陷发现率最高**，超过 400 行明显下降，上千行基本失效。大改动要么按"可独立合并"拆、要么重构与行为变更分离、要么用 Feature Flag 先合后开 |

> **这 12 题里，第 1、2、3、5 题是"改错代码"级别的高危题**——它们问的不是概念，而是你会不会**在真实操作中丢掉别人的或自己的代码**。
