# 流水线设计：从提交到不可变制品

"我们有 CI"这句话的含金量差别极大。装了 Jenkins、挂了个 webhook、每次 push 跑一次 `mvn package`——很多人管这叫有 CI 了。但如果构建排队两小时、一周才合并一次主干、失败了没人看，那**它只是把手工打包自动化了**，并没有"持续集成"。

"持续"指的不是 7×24 在跑，而是**节律**：每次提交都能在几分钟内拿到"能不能合"的结论。这个节律决定了团队敢不敢小步提交，而小步提交又决定了故障的定位成本——一次改了 12 个文件的提交，和一次改了 800 行的提交，出问题后的排查代价不是一个量级。

> **主线：CI 的价值是"把反馈压到分钟级"，交付的价值是"把产物变成不可变的制品"。**
>
> 前者靠门禁设计（快的在前、失败的立即停、红灯必须有人管），后者靠制品治理（标签不可变、来源可追溯、来源可验证）。
>
> **这两件事都和"用了哪个 CI 工具"关系不大。** 换了工具不会让节律变好，也不会让制品变得不可变。

## 一、问题场景：手工发布的三笔成本 {#why-pipeline}

手工发布不只是"慢"。它有三笔隐性成本，而且都不体现在发布那一刻：

| 成本 | 具体表现 | 后果 |
|---|---|---|
| **不可重复** | 每人一套步骤、每处环境一份"发布文档" | 换个人就出错；出了错也不知道哪一步与上次不同 |
| **反馈延迟** | 编译错误、漏提交的文件、写错的配置，到上线才暴露 | 修复成本随发现时间上升——同样的错，编译期发现是 1 分钟，生产发现是几小时 |
| **恢复靠人** | 回滚要现场回忆"上一版是哪个包、在哪台机器上" | **故障时长 = 人的反应时间**，而不是系统的切换时间 |
| **不可追溯** | 被问"线上跑的是哪个提交"时没人答得出来 | 定位问题从"看代码"退化成"考古" |

流水线的价值不是"自动化了部署"，而是**把发布变成一个可重复、可追溯、可回滚的动作**。这个定义里的三个词，各自对应上表的一笔成本。

从提交到上线是一条链，每一环都会往下一环传递"不确定性"：

```
写代码 ──▶ 提交 ──▶ 构建 ──▶ 测试 ──▶ 制品 ──▶ 部署 ──▶ 观察
   │         │        │        │        │        │        │
   │         │        │        │        │        │        └─ 出问题看得见吗？
   │         │        │        │        │        └─ 出问题多久能回退？
   │         │        │        │        └─ 这个产物可追溯、可验证吗？
   │         │        │        └─ 缺陷能在这里被拦住吗？
   │         │        └─ 每次提交都给结论吗？
   │         └─ 小步提交，还是攒一批？
   └─ 本地能跑，等于环境能跑吗？
```

**这条链的强度由最弱的一环决定。** 只把"部署"自动化了、而制品不可追溯、或者测试不可信，那只是把风险从发布时刻推迟到了故障时刻。

## 二、CI 与 CD 的边界：节律比工具重要 {#concepts}

三个词经常被混用，但它们的分界线很清楚：

| 阶段 | 做什么 | 关键节律 | 前提 |
|---|---|---|---|
| **CI（持续集成）** | 每次提交自动构建 + 跑测试 | **每次提交**——不是每天一次 | 主干上的代码始终可构建 |
| **持续交付（Continuous Delivery）** | 产物随时可发布，**发布到生产需人工确认** | 保证"随时能发" | 测试可信 + 回滚可用 |
| **持续部署（Continuous Deployment）** | 通过验证即自动发布到生产 | 全自动 | 上面两条 + 监控能发现问题 + 回滚是自动的 |

> **最常见的误区**：认为"有台 Jenkins 在跑构建"就等于 CI。CI 的核心是**节律**——每次提交都验证、十分钟内给出结论。如果构建排队两小时、一周合并一次分支，那只是"自动化了打包"，不是持续集成。

**分档看自己在哪一级**，比争论"算不算 CI/CD"有用：

| 档位 | 特征 | 卡在哪 |
|---|---|---|
| 手工发布 | 有文档、有 checklist，靠人执行 | 一切 |
| 自动构建 | 有流水线，但只跑到打包 | 测试不可信、无自动化部署 |
| 自动部署到测试 | 每次提交自动到测试环境 | 环境不一致、无回滚 |
| **持续交付** | 随时能发，生产需点一下确认 | 差"敢不敢自动发" |
| **持续部署** | 通过验证即上线 | 依赖监控与自动回滚 |

**能不能走到最后一档，不取决于流水线，取决于"出错了多久能发现、多久能回退"。** 一个平均 20 分钟才被发现的故障，是配不上自动发布的——那 20 分钟里新版本已经全量了。这也是为什么这个板块的后三篇（发布策略、渐进式交付、回滚）都要先于"自动化到生产"想清楚。

## 三、五个阶段：为什么快的必须在前面 {#stages}

```
提交 ──▶ ① 构建 ──▶ ② 测试 ──▶ ③ 打包镜像 ──▶ ④ 推送仓库 ──▶ ⑤ 部署
         │            │              │                │            │
         └────────────┴──────────────┴────────────────┴────────────┘
                              任一步失败 → 立即中断（fail fast）
```

| 阶段 | 做什么 | 失败意味着 | 耗时量级 | 能否并行 |
|---|---|---|---|---|
| ① 构建 | 编译、依赖解析、静态检查 | 代码有问题 | 秒~分钟 | 静态检查与编译可并行 |
| ② 测试 | 单测（必须）→ 集成、契约 | 逻辑或接口不兼容 | 分钟 | **可切片并行** |
| ③ 打包镜像 | 多层构建、打标签、附 SBOM | 构建脚本或基础镜像问题 | 分钟 | 依赖 ①，不可并行 |
| ④ 推送仓库 | 推送到镜像仓库 | 网络、权限、仓库容量 | 分钟 | 可与 ⑤ 前置准备并行 |
| ⑤ 部署 | 更新集群、等就绪、冒烟 | 环境、配置、资源问题 | 分钟 | 依赖 ③④，串行 |

**排序原则：快的放前面。** 让人在 30 秒内知道"拼写错了"，而不是等 10 分钟跑完集成测试才在构建阶段报错。

两个容易被忽略的设计点：

1. **静态检查与单测要和编译并行，而不是串行。** 多数流水线把它们顺序排，白白把反馈时间加起来。只有在"编译不过时静态检查的结论没有意义"这种情况下，串行才合理。
2. **镜像构建不能与测试并行。** 它依赖编译产物；强行并行只会让两个阶段各自编译一遍，两倍资源换零收益。

**"fail fast" 的具体含义是：不给后续阶段发车。** 一条已经知道构建失败的流水线，不应该继续去跑 20 分钟的集成测试，也不应该推一个坏镜像进仓库——后者更糟，因为它会污染制品库，让"仓库里有哪些可用版本"这个问题的答案变得不可靠。

## 四、测试门禁：拦得住什么，拦不住什么 {#test-gates}

测试是整个流水线里唯一"能拦住缺陷"的环节。但它也是最容易变得不可信的环节。

### 4.1 测试金字塔：不是口味问题，是成本问题

| 层 | 数量 | 速度 | 依赖 | 能拦住 |
|---|---|---|---|---|
| **单元测试** | 大量 | 毫秒~秒 | 无（或全 mock） | 逻辑分支、边界、空值 |
| **集成测试** | 中等 | 秒~分钟 | 真实依赖（DB/MQ） | 序列化、SQL、事务、连接池 |
| **契约测试** | 少量但关键 | 秒 | 无需真实对端 | **接口不兼容** |
| **端到端** | 极少 | 分钟 | 完整环境 | 装配错误、配置错误 |

**为什么必须"大量单测 + 少量端到端"**：端到端用例的执行成本是单测的几百倍，而它能多抓到的缺陷类型其实很窄（主要是装配与配置）。把验证主力押在 E2E 上，会得到一个"跑得慢、还经常因环境问题误报"的流水线——最后所有人都学会"红灯先重跑一次"，门禁彻底失效。

### 4.2 门禁的三档：不是所有失败都该拦提交

| 档 | 什么放这里 | 失败时的行为 |
|---|---|---|
| **阻断** | 编译、单测、镜像构建、镜像扫描高危 | 立即失败、禁止合并 |
| **警告** | 覆盖率下降、中低危漏洞、代码风格 | 记录、评论、不拦 |
| **定时** | 全量集成、E2E、性能基线、依赖更新扫描 | 夜间跑，次日处理 |

> **判据（一条就够）：这条用例失败了，我知不知道该怎么办？** 知道 → 放进阻断档；不知道 → 它现在只是一个噪声源，要么把它修到"知道怎么办"，要么删掉。

### 4.3 三种让门禁失效的做法

| 做法 | 表面理由 | 真实代价 |
|---|---|---|
| **跳过测试换速度** | "这次改动小，先发" | 把成本从流水线挪到线上，且挪的时候没告诉任何人 |
| **容忍 flaky 用例** | "重跑一次就好了" | **比没有测试更糟**——它训练全员忽略红灯，等真红灯出现时没人看 |
| **只追覆盖率** | "覆盖率要到 80%" | 覆盖率衡量"执行过"，不衡量"断言过"。可以写出 90% 覆盖率、断言为零的测试 |

**关于"用真实依赖还是 mock"**：单元测试用 mock 是对的；但**集成测试如果也全 mock，它就退化成了一层更慢的单测**。判断标准是"这个测试能不能发现 SQL 写错、事务边界错、序列化差异"——不能的话，它没在测集成。把真实依赖跑起来，可以用 [Testcontainers](https://testcontainers.com/) 起一次性容器，让集成测试有真实的 DB 与 MQ，同时保持"任何机器上都能跑"，这和 [Docker 的镜像一致性](/cloud-native/docker/#why-container) 是同一个思路的两面。

**契约测试解决一个单元与集成都覆盖不了的问题**：上游加了个必填字段，下游没同步，集成测试各自都过，线上才炸。契约测试让"消费者期望"变成可执行的文件，上游改接口时直接在 CI 里失败——**把"跨团队接口约定"从文档和口头同步，变成流水线上的一道门禁**。

## 五、构建提速：缓存是对的，缓存错的东西是灾难 {#build-speed}

流水线慢是"节律"的头号杀手。构建超过 10 分钟，人就开始切去做别的事，反馈的有效性就掉了一半。

| 手段 | 原理 | 效果 | 陷阱 |
|---|---|---|---|
| **依赖描述文件前置** | 先 `COPY pom.xml` 再 `COPY src`，让依赖层不随业务代码变化 | 命中时省掉整个依赖下载阶段 | 顺序写反（先拷全部源码）会让缓存永远不命中 |
| **构建缓存挂载** | BuildKit 的 `RUN --mount=type=cache,target=/root/.m2` | 依赖下载接近归零 | 需要 BuildKit（新 Docker 默认开启） |
| **镜像仓库作缓存** | `--cache-from` / `--cache-to` 拉取上次的层 | CI 每次都是干净环境，也能命中 | 缓存会持续增长，要定期清理 |
| **矩阵并行** | 多模块、多架构同时构建 | 与耗时最长的分支对齐 | 并行度超过 runner 数量会互相抢资源 |
| **只构建受影响的模块** | 按变更路径做增量 | 大仓收益最大 | 依赖关系必须准确，漏了会发出"少模块"的镜像 |

一个最小的分层示例，注意**顺序**才是关键：

```dockerfile
# 依赖层：只依赖 pom.xml，业务代码变了也命中缓存
FROM maven:3.9-eclipse-temurin-17 AS deps
WORKDIR /build
COPY pom.xml ./
RUN --mount=type=cache,target=/root/.m2 mvn -B dependency:go-offline

# 编译层：源码在这里才进来
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -B -DskipTests package

# 运行层
FROM eclipse-temurin:17-jre
COPY --from=deps /build/target/app.jar /app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
```

> **缓存的安全边界**：缓存的是"依赖"和"构建中间产物"，**不能**缓存"密钥、环境注入的值、以及带 `latest` 语义的东西**。一个被缓存的过期依赖，可以安静地跑过所有测试、所有扫描，最终上到生产——它不会让流水线变红，只会让门禁失去意义。

## 六、配置与环境分离：build once, deploy anywhere {#build-once}

原则一句话：**镜像只包含"与版本绑定的东西"，环境差异从外部注入。**

| 配置类型 | 放在哪 | 变更要不要重新构建 |
|---|---|---|
| 代码、依赖、JRE 版本 | 镜像内 | 要 |
| **环境差异**（数据库地址、开关、日志级别） | 环境变量 / ConfigMap | 不要 |
| **密钥**（数据库密码、Token） | Secret / 密钥管理服务 | 不要 |
| 启动参数（堆大小、GC 策略） | 部署清单（随 Pod 规格） | 不要 |
| **静态资源与前端产物** | 镜像内 | 要 |

> **典型反模式**：为每个环境构建一个镜像（`app:test`、`app:prod`）。这样"测试过的镜像"和"上线的镜像"其实是两个产物，验证过的结论不能直接继承——**发布风险凭空增加一档**。

**区分"配置"和"代码"的实用判据是变更频率**：比代码变得还勤的东西（开关、阈值、费率表）不该进镜像，因为每次改都要走一遍完整流水线；和代码一起评审才有意义的东西（SQL、路由规则）就该进镜像。

一个常见的灰色地带是**前端产物**：`config.js` 里的后端地址算配置，但它被打进了静态文件。处理办法是保留一份"运行时注入"的入口（容器启动时用脚本替换占位符），或者接受"前端按环境各打一版"并明确它只影响静态资源、不影响业务逻辑镜像——**关键是显式决策，而不是默认复制一份构建脚本**。

## 七、制品与镜像治理：从"能跑"到"可验证" {#artifacts}

流水线的产出不是一个"能跑的包"，而是一个**可追溯、可验证的制品**。这一节是这个板块里最容易被跳过、也最能体现工程成熟度的部分。

### 7.1 标签策略 {#tag-strategy}

| 方案 | 例子 | 评价 |
|---|---|---|
| `latest` | `app:latest` | ❌ 禁止用于生产：内容会变，回滚时不知道回到哪 |
| **Git 提交短 SHA** | `app:a1b2c3d` | ✅ 首选：与代码一一对应，可追溯到提交 |
| 语义化版本 | `app:1.7.3` | ✅ 适合对外发布的制品，需决定版本号由谁定 |
| 分支 + 构建号 | `app:main-1024` | ⚠️ 可追溯性弱于 SHA，但便于人读 |
| 时间戳 | `app:20260916-1030` | ⚠️ 能排序，但看不出对应哪次提交 |

两条硬规则：

1. **镜像标签不可变**——同一个 tag 绝不覆盖推送。主流镜像仓库都提供了"不可变标签"开关，**应该打开它**，而不是靠人自觉。
2. **部署时引用具体标签**（SHA），不要用浮动标签。浮动标签让"当前跑的是哪个版本"变成需要登机器查的问题。

### 7.2 多架构：一个标签，两套镜像

`app:1.7.3` 背后其实可以是一个**清单列表（manifest list）**，按节点架构分发不同镜像。ARM 服务器（包括国内常见的 ARM 云主机与鲲鹏、以及开发者的 M 系列 Mac）上，忽略这一点会让镜像只能靠 QEMU 模拟跑，性能损失可观。

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t app:1.7.3 --push .
```

**注意 `--push` 与 `--load` 的取舍**：多架构镜像无法 load 到本地 daemon，必须直接推仓库；本地验证用单架构构建即可。

### 7.3 SBOM：制品里到底有什么

SBOM（软件物料清单）是一份机器可读的组件清单。它不防攻击，**它记录攻击面**——但没有它，"这个刚爆出的 CVE 我们受影响吗"这个问题就无法回答，尤其是埋在四层传递依赖里的组件。

| 格式 | 维护方 | 标准身份 | 优势场景 | 生成工具 |
|---|---|---|---|---|
| **SPDX** | Linux Foundation | **ISO/IEC 5962:2021** | 法律、许可合规 | Syft、Trivy |
| **CycloneDX** | OWASP | 事实标准（容器/安全） | 安全、漏洞元数据丰富 | Syft、Trivy |

实践要点：

- **在构建时生成，不要事后生成**——事后扫描会漏掉传递依赖，且编译产物可能已无源码可依；
- **把 SBOM 作为 OCI 制品附在同一仓库**（`cosign attest` 或仓库原生支持），让"清单"和"制品"永远在一起；
- **持续扫描**，而不只是构建时扫一遍——新 CVE 是在制品存活期间才出现的。

### 7.4 签名与来源：从"我信任这个仓库"到"我验证这个来源"

传统做法的信任基础是"仓库里的镜像应该是我们推的"。这在供应链攻击面前很脆弱。**Sigstore** 提供了不需要管理长期密钥的签名方式：

| 组件 | 作用 |
|---|---|
| **cosign** | 签名与验证镜像、OCI 制品、SBOM、证明（attestation） |
| **Fulcio** | 证书颁发机构，基于 OIDC 身份签发**短期证书** |
| **Rekor** | 不可篡改的透明日志，所有签名公开可审计 |

**关键特性是 keyless（免密钥）**：私钥只在签名的那几毫秒存在，用完即弃。这消除了"私钥泄漏是静默的、几个月后才知道"这个最麻烦的问题——签名身份直接来自 CI 的身份（GitHub Actions / GitLab CI 的 OIDC token），**可追溯、不可伪造**。

```bash
cosign sign --yes registry.example.com/app:a1b2c3d
cosign verify --certificate-identity=ci@example.com \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com \
  registry.example.com/app:a1b2c3d
```

**签了名还要有人验。** 落地闭环的最后一步是准入控制：用 Kyverno 或 OPA Gatekeeper 在集群入口拦截"未签名 / 签名身份不符 / 来源 commit 不符"的镜像。**只签名不验证，等于只写不读。**

### 7.5 SLSA：构建过程的完整性分级

SBOM 回答"软件里有什么"，**SLSA 回答"它是怎么被构建出来的，以及这个过程能不能被证明"**。

| 级别 | 要求 | 挡住的是什么 |
|---|---|---|
| **L1** | 构建过程有记录、产出 provenance | 成本极低的"至少可追溯" |
| **L2** | 托管构建 + **签名 provenance**（由构建服务签名） | 开发者机器被攻陷后伪造产物 |
| **L3** | **隔离、临时、加固**的构建环境；签名密钥构建 worker 碰不到 | 构建 worker 被攻陷后伪造 provenance |
| **L4** | 可复现构建 + 双人评审（实际极罕见） | 最高保证 |

**务实目标通常是 L3**：用云厂商的托管构建 + 官方 provenance 生成器（如 `slsa-github-generator`），标准工作流可以在一天内达到 L2，再补隔离环境到 L3。

> **合规背景正在从"加分项"变成"硬要求"**：欧盟 CRA 的漏洞报告义务自 **2026-09** 起生效，SBOM 的强制提供要求落在 **2027-12**；美国 EO 14028 早已把 SBOM 作为联邦采购条件。**这也是一份工程文档需要写清"制品治理到哪一档"的现实原因。**

## 八、工具选型：选的是组合，不是单点 {#tools}

| 工具 | 定位 | 优势 | 代价 |
|---|---|---|---|
| **Jenkins** | 通用 CI 引擎 | 插件生态最全、可高度定制、能接任何内部系统 | 维护成本高（插件兼容、安全补丁、主从管理） |
| **GitLab CI** | 与代码仓库一体 | 配置即代码、开箱即用、DevOps 面全 | 与 GitLab 绑定 |
| **GitHub Actions** | 与仓库一体、生态大 | 上手最快、复用社区 Action、OIDC 身份内建 | 复杂流水线成本高；私有 runner 需自管 |
| **Argo CD / Flux** | 部署侧（GitOps） | 漂移检测、可视化、多集群 | 需接受"拉模式"与集群内组件（见[下一篇](/cloud-native/cicd/progressive-delivery#gitops)） |

最常见的组合是**CI 用仓库自带（Actions / GitLab CI）+ CD 用 Argo CD**——前者负责"从代码到镜像"，后者负责"从清单到集群"。这个分工的边界很清晰：**CI 的产出是制品，CD 的职责是让集群状态与期望一致**。

选型时值得先问三个问题：**① 团队的合规要求是否允许代码与流水线放在一起（内网/私有化）；② 有没有必须接入的内部系统（这是 Jenkins 仍然活着的主要原因）；③ 谁来看部署状态（有 UI 需求就会选 Argo CD 而不是 Flux）。**

## 九、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | CI 和 CD 的区别？ | CI 是**每次提交**都自动构建与测试，目标是尽早发现集成问题、关键在于节律与反馈速度；CD 是把通过验证的产物**交付/部署**到环境。**持续交付**要求"随时可发布但生产需人工确认"，**持续部署**是全自动 |
| 2 | 为什么生产不能用 `latest`？ | 它是**浮动**标签：同一标签的内容会变，于是"回滚到上一版"和"当前跑的是哪一版"都无法确定。生产必须引用不可变标签（首选 Git 提交 SHA） |
| 3 | 镜像标签不可变怎么保证？ | 两层：**约定 + 强制**。约定是"同一 tag 不覆盖推送"；强制是打开**镜像仓库的不可变标签开关**，让违反约定的推送直接失败。只靠人自觉的做法迟早会破 |
| 4 | 为什么依赖要分层缓存？ | 依赖层不随业务代码变化。`COPY pom.xml` 在 `COPY src` 之前，业务改动时依赖层仍命中缓存。顺序写反会让缓存永远不命中，这是 Dockerfile 里最常见的一处性能浪费 |
| 5 | 构建缓存有什么风险？ | 缓存了**不该缓存的东西**（密钥、注入的环境值、浮动依赖）会让过期或被污染的内容安静地通过所有测试与扫描。缓存是性能手段，不是"跳过验证"的手段 |
| 6 | `build once, deploy anywhere` 是什么意思？ | 同一个镜像产物在测试、预发、生产**复用**，环境差异通过环境变量、ConfigMap、Secret 注入，而不是重新构建。这样"测试通过的那个产物"就是"上线的那一个"，验证结论可以继承 |
| 7 | 每个环境各构建一个镜像有什么问题？ | 它们**不是同一个产物**。测试环境的 `app:test` 与生产的 `app:prod` 是两次构建的结果，镜像层、依赖版本、构建时间都可能不同——"测试通过"这个结论无法直接继承 |
| 8 | 为什么要写 SBOM？ | 为了回答"刚公布的 CVE 我们受不受影响"，尤其是埋在四层传递依赖里的组件。**它在构建时生成才准**（事后扫描漏传递依赖），并应与制品放在一起（OCI 制品或签名证明） |
| 9 | SBOM 能防供应链攻击吗？ | **不能**。它只记录攻击面。真正的防护是**签名 + 验证 + 策略强制**（cosign 签名 → 准入控制验签），只签名不验证等于只写不读 |
| 10 | Sigstore 的 keyless 解决了什么？ | 消除了长期私钥的管理与泄漏风险。私钥只存在签名那几毫秒，身份来自 CI 的 OIDC token 并由 **Fulcio** 签发短期证书，签名记录进 **Rekor** 透明日志——**没有密钥可以泄漏、轮换或丢失** |
| 11 | SLSA 各级挡住什么？ | L1 有构建记录；L2 **签名 provenance 由构建服务签发**（挡住开发者机器被攻陷）；L3 **隔离环境且签名密钥 worker 碰不到**（挡住构建 worker 被攻陷）。**L3 是务实目标**，L4（可复现构建）实际极罕见 |
| 12 | 流水线太慢怎么优化？ | 先测出各阶段耗时再动手，四招：① **快慢分离**（静态检查与单测前置并并行，集成/E2E 后置）；② **缓存依赖与构建层**；③ **只构建受影响的模块**；④ **矩阵并行**。**别用"跳过测试"换速度**，那是把成本挪到线上 |
