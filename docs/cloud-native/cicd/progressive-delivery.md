# GitOps 与渐进式交付：从"推一次命令"到"指标决定放量"

前两篇解决的是"产物怎么做出来"和"流量怎么切"。但还有一个没答的问题：**是谁在把期望状态同步到集群，以及同步失败时会发生什么。**

传统流水线的答案是"CI 系统执行一条 `kubectl apply`"。这个动作的本质是**推一次命令**——它成功与否取决于那一刻的网络、权限与集群状态，执行完就结束了，**没有人在持续确认"现在集群还是不是那个样子"**。只要有人手工 `kubectl edit` 一下，Git 里的声明与集群的实际状态就永久分叉了，而且没人知道。

> **主线：GitOps 解决的是"声明状态被持续对齐"，它不解决"流量怎么逐步切"——后者是渐进式交付层的事。**
>
> 这两层经常被混为一谈。Argo CD 和 Flux 是**对齐引擎**，Argo Rollouts 和 Flagger 才是**放量引擎**。搞清分层，就不会出现"我们上了 GitOps，为什么还是没有金丝雀"这种困惑。

## 一、问题场景：自动化之后，剩下的是什么 {#why}

流水线自动化了"从代码到集群"的动作，但留下了三类问题：

| 问题 | 具体表现 | 后果 |
|---|---|---|
| **漂移不可见** | 有人为了救火手工改了副本数、镜像标签、环境变量 | 下次部署把这些改动"莫名其妙"地覆盖掉，或者它们永远留在集群里 |
| **凭证外放** | CI 系统里存着集群的 kubeconfig 或 ServiceAccount token | 它是"能改整个集群"的凭证，而它待在一个被频繁触发的系统里 |
| **审计分散** | 谁在什么时候改了什么，要看流水线的执行日志 | 流水线日志会轮转、会被清理，它不是一个可靠的审计源 |

注意这三个问题的共同点：**它们都不是"自动化程度不够"，而是"缺少持续对齐与单一事实源"。** 再加一层自动化（"再写个脚本定时 `kubectl apply`"）无法解决漂移——因为它仍然不检测分叉，只是把推命令的频率提高了。

## 二、推模式与拉模式：方向反转带来的四个变化 {#gitops}

| 维度 | Push 式（传统流水线） | **Pull 式（GitOps）** |
|---|---|---|
| 谁发起部署 | CI 系统执行 `kubectl apply` | 集群内的控制器**主动拉取** Git 并比对 |
| 集群凭证 | 存在 CI 系统里（泄漏面大） | **不出集群** |
| 漂移检测 | 没有，手工改动无人知晓 | **持续比对，手工改会被自动纠偏** |
| 审计 | 看流水线日志 | 看 Git 提交历史 |
| 回滚 | 重新跑一次流水线 | `git revert` |
| 代表工具 | Jenkins / GitLab CI | **Argo CD / Flux** |

**最关键的差异是方向**：GitOps 里"部署"不再是"推一次命令"，而是"**声明状态被持续对齐**"。这一点与 K8s 的控制器循环是同一个思想——Deployment 控制器持续让实际副本数收敛到期望副本数，GitOps 控制器持续让集群的实际状态收敛到 Git 里的期望状态。**它只是把这个循环从"对象级"提升到了"整个应用级"。**

由此推出的几个实用结论：

**1. 手工改动会被自动回滚，这是特性不是 bug。** 但它会带来一个组织摩擦："我改了配置救火，五分钟后又变回去了"。所以必须同时提供**合法的应急通道**——要么现场改 Git（快修），要么临时禁用自动同步（承认分叉）并设定恢复时限。**没有应急通道的 GitOps 一定会被人绕过。**

**2. "回滚"的手段从"重跑流水线"变成"`git revert`"。** 这在 [Helm 篇](/cloud-native/helm/#helm-in-cicd)里提到过：CI 只负责把新的 image tag 写回 Git 仓库，由集群内的控制器拉取并渲染；此时 `helm rollback` 不再是回滚手段，因为控制器会立刻把集群拉回 Git 描述的状态——**不 revert Git，任何集群内的回滚都是临时的**。

**3. 多集群的成本大幅下降。** 拉模式下，新增一个集群是"在集群里装一个 agent 并给它授权"，而不是"给 CI 配一套新凭证 + 改流水线分支"。这让"每环境一个集群""每租户一个集群"这类拓扑变得可维护。

**4. 密钥不能进 Git——这不是 GitOps 的缺陷，是它的纪律。** 标准做法是把"密钥的引用"放进 Git（如 External Secrets Operator 的资源声明、Sealed Secrets 的加密值），由集群内的组件在运行时去密钥服务取真实值。**任何"先把密码提交上去以后再说"的做法，都会在仓库历史里永久留痕** ——而 Git 历史是设计上不可篡改的，这正是它作为审计源的价值所在，也是它作为密钥载体绝对不可行的原因。

## 三、稳态与门槛：GitOps 不是"装个 Argo CD" {#gitops-cost}

GitOps 带来的复杂度是实实在在的，值得提前判断：

| 代价 | 具体表现 | 缓解 |
|---|---|---|
| **多一层组件** | 集群内多了一个需要高权限、需要被运维的控制器 | 它获得的权限就是"能改集群里的一切"，要纳入同一套安全基线 |
| **调试链路变长** | "我提交了为什么没生效"要多查一层（同步状态、渲染结果、diff） | 用控制器的 UI 或 CLI 看 diff 与事件，不要靠猜 |
| **环境差异要重新组织** | 单仓库多目录、多分支、还是多仓库？ | 主流做法是**单仓库 + 目录分层**（`apps/{dev,staging,prod}/`），或用 ApplicationSet 批量生成 |
| **同步风暴** | 一次改动触发大量应用重建 | 用同步波次（wave）与依赖声明控制顺序 |
| **镜像 tag 谁写回** | 需要"新镜像 → Git 更新"这一步 | Flux 内置 image automation；Argo CD 需要独立的 **Image Updater** 组件 |

**判断要不要上 GitOps 的两个问题**：

1. **集群凭证能不能安全地待在 CI 系统里？** 单集群、内网、CI 与集群同一信任域 → 推模式完全够用，上 GitOps 是净增复杂度。多集群、多环境、凭证不宜集中 → 拉模式的价值立刻显现。
2. **有没有"分叉必须被消灭"的诉求？** 强审计、强合规、多团队改同一个集群 → GitOps 的持续对齐是刚需。一个人维护一两个服务 → 收益不抵成本。

## 四、渐进式交付：让指标决定放量，而不是让人决定 {#progressive}

渐进式交付（Progressive Delivery）是把"发布"变成一个**受控的实验**：

```
部署新版本（不接流量）
   → 引 1% 流量 → 观察 N 分钟（错误率 / 延迟分位 / 业务指标）
   → 通过 → 引 5% → 观察 → 通过 → 25% → 50% → 全量
   → 任一环节指标越界 → 自动把流量切回旧版本 + 停止推进
```

它与"金丝雀"的差别在**判定的自动化程度**：

| 方式 | 判定 | 表现 |
|---|---|---|
| 手工金丝雀 | 人看板 + 人决策 | 半夜发布没人看；看漏了指标继续放量 |
| **渐进式交付** | **指标查询 + 自动判定** | 越界自动回退，且回退是秒级、不需要人醒着 |

**判定用的查询与告警同源**——都是 [Prometheus 的 PromQL](/cloud-native/observability/metrics-prometheus#promql)。这让渐进式交付有一个硬前提：**指标得算得对**。用一个 P99 桶设计粗糙的直方图做金丝雀判定，会让"延迟是否变差"这个判断本身不可信——**在这种情况下，自动回退会变成一个随机中断发布的机制**。

判定条件通常要覆盖三类：

| 类别 | 例子 | 说明 |
|---|---|---|
| **正确性** | 5xx 率、业务异常计数、消息处理失败数 | 最该有的，但需要业务埋点才能覆盖 |
| **性能** | 延迟分位、超时率、线程池饱和 | 用服务端指标即可 |
| **饱和度** | CPU / 内存 / 连接池 / 队列长度 | 用来拦住"能跑但会把资源吃光"的版本 |

**最容易漏的是"样本量"问题**：1% 流量在低峰期可能每分钟只有几个请求，此时错误率的分母太小，任何一次偶发失败都会让比率飙到 20% 并触发回退。**渐进式交付的策略要包含"最小样本量"条件**——样本不足时继续等待而不是判定失败。这条和[告警篇的 `for` 持续时间](/cloud-native/observability/slo-and-alerting#principles)是同一个思想：**不要用瞬时值做决策。**

## 五、Argo Rollouts 与 Flagger：两套生态的分工 {#rollouts-flagger}

渐进式交付不在对齐引擎的能力范围内，需要单独的放量引擎：

| | **Argo Rollouts** | **Flagger** |
|---|---|---|
| 归属生态 | Argo（与 Argo CD 同项目群） | Flux |
| 资源形态 | 自定义资源 `Rollout`（替代 `Deployment`） | 以 `Canary` CR 包装现有的 Deployment |
| 流量接入 | Service Mesh（Istio / Linkerd）、Ingress、**Gateway API（社区插件）** | 同一批基础设施 |
| 指标来源 | AnalysisRun（Prometheus、Datadog 等） | Prometheus、Datadog 等 |
| 与 UI 的关系 | **与 Argo CD 仪表盘一体**（放量进度可视化） | 靠 CLI 与指标 |

**怎么选，一句话**：已经在用 Argo CD 且团队需要看放量进度 → **Argo Rollouts**；已经在用 Flux → **Flagger**（它在 Flux 生态里是自然选择，且同样成熟）。

> **一个常见的架构误判**：以为用了 Argo CD 就自动有了金丝雀。**Argo CD 只负责把清单同步到集群**，它同步的是一个普通 Deployment，滚动还是滚动。要金丝雀必须再装 Argo Rollouts 并把 Deployment 换成 Rollout 资源。

**渐进式交付的代价也要说清楚**：它要求服务是**多副本 + 无状态 + 会话不粘连**的。如果一个服务的实例各自持有内存态（本地缓存、会话），按流量比例切分就会让用户体验"时好时坏"——这一半请求命中新版本、一半命中旧版本，而它们的状态不同步。

## 六、Feature Flag：把"发布"和"上线"拆开 {#feature-flag}

前面所有策略都在回答"怎么让新版本安全地接管流量"。还有一种思路是**让新代码先上去、但先不生效**：

| | 部署形态切换 | **Feature Flag** |
|---|---|---|
| 切换的对象 | 流量（请求走到哪个版本） | **行为**（同一个版本里的哪条分支） |
| 需要两套实例吗 | 金丝雀/蓝绿需要 | **不需要** |
| 粒度 | 请求级 / 比例 | **业务维度**（租户、用户、地区、套餐） |
| 回滚速度 | 秒级（切流量） | **秒级（改开关）** |
| 代价 | 基础设施复杂度 | **代码里的分支会长期存在** |

**它的独特价值是"能按业务维度灰度"**：先放给内部账号 → 再放给 1% 的免费用户 → 再放给某个城市。这是网关和网格都做不到的，因为它们看不到业务语义。

**代价是开关会变成技术债**：一个上线后没人清理的开关，会让代码里长期存在两条路径，而且**没人记得哪条是当前生效的**。纪律是：**每个开关在创建时就写下"清理条件"与"负责人"**，上线满一个观察期后必须删除——把"删开关"当成发布流程的一个收尾步骤，而不是"以后有空再说"。

**两者的正确关系是分层而不是替代**：

```
流量维度：金丝雀（新版本先接 1% 流量）  ← 验证"这个版本本身有没有问题"
   ↓
业务维度：Feature Flag（新功能先对 1% 用户开启）  ← 验证"这个功能业务上对不对"
```

## 七、度量交付能力：DORA 指标该怎么读 {#dora}

DORA（DevOps Research and Assessment）用四个指标衡量一条交付链路的健康度。它们是**衡量系统、不是衡量人**的——这一点必须先说清楚，否则很容易被拿来考核个人，然后迅速失真。

| 指标 | 定义 | 它反映什么 | 怎么变好 |
|---|---|---|---|
| **部署频率** | 多久部署一次到生产 | 批量大小与流程摩擦 | **缩小批量**，而不是催人加班 |
| **变更前置时间** | 首次提交到生产运行 | 从代码到价值的全链路耗时 | 减少评审等待、并行化门禁 |
| **变更失败率** | 导致劣化或需要补救的变更比例 | 测试与评审的质量 | 更早的验证（静态检查、契约测试） |
| **失败部署恢复时间** | 服务恢复耗时（原 MTTR） | 监控、回滚与预案 | 自动化回滚、可信的告警、现成的 runbook |

**2025 年的报告里有三处变化值得注意**：

1. **取消了 "Elite / High / Medium / Low" 分档，改为百分位分布。** 因为固定的档位阈值会让人去"够线"，而百分位让人关注"在哪个位置、往哪移动"。比如部署频率达到"按需（每天多次）"的只占 **16.2%**，变更前置时间小于一天的占 **15%**——**这种分布说明"精英"是少数，而不是一个容易达成的门槛**。
2. **新增第五个指标：返工率（Rework Rate）**，衡量"因生产事故而临时插入的、非计划内的工作"占比。它补上了前四个指标的一个盲区——**一个团队可以"部署很频繁、恢复也很快"，但一直在救自己的火**。
3. **AI 是放大器，不是修复器。** 报告的结论是：AI 会放大团队已有的优势与缺陷。在流程本身不健全的团队里，引入 AI 会让交付变得更不可预测；而在 DORA 指标表现好的团队里，达到组织目标的可能性高出一倍左右。

**使用 DORA 的三条纪律**：

- **四（五）个指标要一起看，不能单看一个。** 只追部署频率会得到"发得又快又破"；只追变更失败率会得到"什么都不敢发"。
- **趋势比绝对值有意义。** 每个团队的基线不同，重要的是"这个季度有没有变好"。
- **不要用来考核个人或团队排名。** 一旦和绩效挂钩，数据必然被优化——减少小改动、把一次大发布拆成多次"无意义部署"、把 incident 不记为 incident。**指标一旦成为目标，就不再是好的指标。**

> **它们与本板块的关系**：这四个指标衡量的是**这条链路（流水线 → 制品 → 部署 → 回滚）的整体表现**。所以它们不是"另一套东西"，而是**前面几篇所有设计的验收标准**——门禁设计影响变更失败率，渐进式交付影响恢复时间，制品治理影响回滚能力。

## 八、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | GitOps 的推模式和拉模式差在哪？ | 差在**方向**。推模式是 CI 执行一次 `kubectl apply`（一次性动作，不检测分叉）；拉模式是集群内控制器**持续拉取并比对**，把手工改动自动纠偏。由此带来凭证不出集群、审计看 Git、回滚变 `git revert` 三个衍生好处 |
| 2 | GitOps 的"回滚"为什么是 `git revert`？ | 因为控制器会持续把集群拉回 Git 描述的状态。**不 revert Git，任何集群内的回滚都只是临时的**——下一次同步就会覆盖回去 |
| 3 | 手工改了集群，GitOps 会怎样？ | 被自动纠偏（这是特性）。所以必须同时提供**合法应急通道**：现场改 Git 快修，或临时禁用自动同步并设定恢复时限。**没有应急通道的 GitOps 一定会被绕过** |
| 4 | 密钥怎么放进 GitOps？ | 不放进 Git。Git 里放的是**密钥的引用**（External Secrets 的资源声明、Sealed Secrets 的加密值），由集群内组件在运行时取真实值。Git 历史设计上不可篡改——这既是它作为审计源的价值，也是它不能承载密钥的原因 |
| 5 | 什么情况下不该上 GitOps？ | 单集群、内网、CI 与集群同一信任域时，推模式够用，上 GitOps 是净增复杂度。它的价值随"集群数量""环境数量""分叉必须被消灭的合规诉求"上升 |
| 6 | 用了 Argo CD 就有金丝雀了吗？ | **没有**。Argo CD 只是把清单同步到集群，同步的是普通 Deployment，滚动还是滚动。要金丝雀必须再引入**放量引擎**（Argo Rollouts 或 Flagger）并换成对应资源 |
| 7 | Argo Rollouts 和 Flagger 怎么选？ | 看生态：已经在用 Argo CD 且需要可视化放量进度 → **Argo Rollouts**（与仪表盘一体）；已经在用 Flux → **Flagger**。两者能力相当、都成熟 |
| 8 | 渐进式交付的硬前提是什么？ | **指标得算得对**。判定用的查询和告警同源（PromQL），用一个桶设计粗糙的直方图做判定，会让"延迟是否变差"这个判断本身不可信，**自动回退就退化成随机中断发布** |
| 9 | 金丝雀在低峰期为什么会误判？ | **样本量不足**。1% 流量在低峰期每分钟只有几个请求，分母太小，一次偶发失败就让比率飙到 20% 并触发回退。策略里必须有**最小样本量**条件——和告警的 `for` 持续时间是同一个思想：不用瞬时值做决策 |
| 10 | Feature Flag 和金丝雀是什么关系？ | **分层，不是替代**。金丝雀验证"这个版本本身有没有问题"（流量维度）；Feature Flag 验证"这个功能业务上对不对"（业务维度，可按租户/地区灰度，且不需要两套实例）。代价是开关会变技术债，**创建时就该写下清理条件与负责人** |
| 11 | DORA 有哪几个指标？ | 四（五）个：**部署频率、变更前置时间、变更失败率、失败部署恢复时间**，2025 年报告新增**返工率**（因事故临时插入的非计划工作占比）。**一起看才有意义**——只追频率会得到"发得又快又破" |
| 12 | DORA 2025 报告有什么重要变化？ | 三处：① **取消 Elite 分档改为百分位分布**（避免"够线"）；② **新增返工率**，补上"一直在救自己的火"这个盲区；③ **AI 是放大器不是修复器**——它放大团队已有的优势与缺陷，流程不健全时引入 AI 会让交付更不可预测 |
