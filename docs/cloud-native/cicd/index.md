# CI/CD 流水线

## 一、问题场景：手工发布的三种成本 {#why-cicd}

手工发布不只是"慢"，它有三笔隐性成本：

| 成本 | 具体表现 | 后果 |
|---|---|---|
| **不可重复** | 每人一套步骤、每处环境一份文档 | 换个人就出错，出错了还不知道哪步不一样 |
| **反馈延迟** | 编译错误、漏提交文件到上线才暴露 | 修复成本随发现时间指数上升 |
| **恢复靠人** | 回滚要现场回忆"上一版是哪个包、在哪台机器" | 故障时长 = 人的反应时间 |

流水线的价值不是"自动化了部署"，而是**把发布变成一个可重复、可追溯、可回滚的动作**。

## 二、CI 与 CD 的边界 {#concepts}

| 阶段 | 做什么 | 关键节律 |
|---|---|---|
| **CI（持续集成）** | 每次提交都自动构建 + 跑测试 | **每次提交**——不是每天一次 |
| **持续交付（Continuous Delivery）** | 产物随时可发布，**发布到生产需人工确认** | 保证"随时能发" |
| **持续部署（Continuous Deployment）** | 通过验证即自动发布到生产 | 全自动，要求测试与监控足够强 |

> **最常见的误区**：认为"有台 Jenkins 在跑构建"就等于 CI。CI 的核心是**节律**——每次提交都验证、十分钟内给出结论。如果构建排队两小时、一周合并一次分支，那只是"自动化了打包"，不是持续集成。

## 三、流水线的五个阶段 {#pipeline}

```
提交 ──▶ ① 构建 ──▶ ② 测试 ──▶ ③ 打包镜像 ──▶ ④ 推送仓库 ──▶ ⑤ 部署
         │            │              │                │            │
         └────────────┴──────────────┴────────────────┴────────────┘
                              任一步失败 → 立即中断（fail fast）
```

| 阶段 | 做什么 | 失败意味着 | 耗时量级 |
|---|---|---|---|
| ① 构建 | 编译、依赖解析、静态检查 | 代码有问题 | 秒~分钟 |
| ② 测试 | 单元测试（必须）→ 集成测试、契约测试 | 逻辑/接口不兼容 | 分钟 |
| ③ 打包镜像 | 多层构建、标签、SBOM | 构建脚本或基础镜像问题 | 分钟 |
| ④ 推送仓库 | 推送到镜像仓库 | 网络/权限/仓库容量 | 分钟 |
| ⑤ 部署 | 更新集群、等待就绪、冒烟验证 | 环境、配置、资源问题 | 分钟 |

**排序原则：快的放前面。** 让人在 30 秒内知道"拼写错了"，而不是等 10 分钟跑完集成测试才在构建阶段报错。这也是为什么**测试要做金字塔**（大量单测 + 少量集成 + 极少量端到端），而不是全靠 E2E 验证。

## 四、镜像构建与版本策略 {#image-version}

### 4.1 标签怎么打 {#tag-strategy}

| 方案 | 例子 | 评价 |
|---|---|---|
| `latest` | `app:latest` | ❌ 禁止用于生产：内容会变，回滚时不知道回到哪 |
| **Git 提交短 SHA** | `app:a1b2c3d` | ✅ 首选：与代码一一对应，可追溯到提交 |
| 语义化版本 | `app:1.7.3` | ✅ 适合对外发布的制品，需人工/自动决定版本号 |
| 分支 + 构建号 | `app:main-1024` | ⚠️ 可追溯性弱于 SHA，便于人读 |
| 时间戳 | `app:20260915-1030` | ⚠️ 能排序，但看不出对应哪次提交 |

两条硬规则：

1. **镜像标签不可变**——同一个 tag 绝不覆盖推送。否则"回滚到 v1.2"可能回到一个和昨晚不同的内容。
2. **部署时引用具体标签**（SHA），不要用浮动标签（`latest` / `stable`）——浮动标签让"当前跑的是哪个版本"变成需要登机器查的问题。

### 4.2 构建提速 {#build-cache}

| 手段 | 原理 | 效果 |
|---|---|---|
| **指令分层 + 先拷依赖描述文件** | 依赖层不随业务代码变化 | 命中时省掉整个 `mvn dependency` 阶段 |
| BuildKit 缓存挂载 | `RUN --mount=type=cache,target=/root/.m2` 复用本地 Maven 仓库 | 依赖下载几乎归零 |
| 镜像仓库作构建缓存 | `--cache-from` / `--cache-to` 拉取上次的层 | CI 干净环境下也能命中 |
| 并行矩阵构建 | 多模块/多架构并行 | 与耗时最长的分支对齐 |

### 4.3 配置与环境分离 {#config-separation}

原则是 **build once, deploy anywhere**：镜像只包含"与版本绑定的东西"，环境差异从外部注入。

| 配置类型 | 放在哪 | 变更要不要重新构建 |
|---|---|---|
| 代码、依赖、JVM 版本 | 镜像内 | 要 |
| **环境差异**（数据库地址、开关、日志级别） | 环境变量 / ConfigMap | 不要 |
| **密钥**（数据库密码、Token） | Secret / 密钥管理服务 | 不要 |
| 启动参数（堆大小、GC 策略） | 部署清单（随 Pod 规格） | 不要 |

> **典型反模式**：为每个环境构建一个镜像（`app:test`、`app:prod`）。这样"测试过的镜像"和"上线的镜像"其实是两个产物，验证过的结论不能直接继承——**发布风险凭空增加一档**。

## 五、四种发布策略 {#deploy-strategy}

| 策略 | 原理 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **重建（Recreate）** | 先停旧、再起新 | 最简单，无版本共存 | **有中断** | 内部工具、可停服系统 |
| **滚动（Rolling）** | 逐步替换，新起一个/停一个 | 不中断、资源占用小、K8s 原生支持 | 新旧版本**短时共存**，接口需兼容 | 绝大多数无状态服务（默认选择） |
| **蓝绿（Blue-Green）** | 部署全新一套，流量整体切换 | 切换瞬间、回滚只需切回 | **双倍资源**；数据库需兼容两版 | 关键系统、要求秒级回滚 |
| **金丝雀（Canary）** | 先引一小部分流量到新版本，观察后逐步放量 | 风险可控，能拿真实流量验证 | 需要流量切分能力 + 完善的指标观察 | 大流量、变更风险高的服务 |

金丝雀的**流量切分**可以在三个层次做，能力与代价递增：

| 层次 | 手段 | 粒度 |
|---|---|---|
| 网关/Ingress | 按权重或 Header 路由 | 请求级，实现最简单 |
| 服务网格 | 按比例分发 + 自动分析指标 | 请求级，可遥测驱动 |
| 应用内 | Feature Flag | **不需要两套部署**，可随时开关 |

> **选择顺序**：先问"能不能承担两套环境的成本"（不能 → 滚动），再问"回滚速度要求"（要求秒级 → 蓝绿），最后问"能不能按流量验证"（能且流量足够 → 金丝雀）。**不要为了"高级"而跳过滚动更新**——多数服务的发布风险，靠"就绪探针 + 优雅停机 + 灰度观察窗口"就已经足够。

## 六、回滚与数据库变更 {#rollback}

**应用回滚的前提是两条**：镜像不可变（回到确定的产物）+ 部署是声明式的（`kubectl rollout undo` 或把清单里的镜像标签改回去）。

真正的难点是**数据库**——DDL 和数据迁移本质上不可逆。做法是**扩展-收缩（expand-contract）**：

```
① 扩展：加新字段/新表（旧代码不感知，可回滚）
      ↓
② 双写：新旧字段同时写（两个版本都能跑）
      ↓
③ 迁移：把历史数据回填，校验一致性
      ↓
④ 切读：代码改为只读新字段（此时才不可轻易回滚）
      ↓
⑤ 收缩：确认稳定后，删除旧字段
```

| 变更类型 | 可回滚性 | 应对 |
|---|---|---|
| 加字段 / 加索引（在线） | ✅ 高 | 直接做，注意大表加索引的锁与耗时 |
| 改字段类型 / 重命名 | ⚠️ 中 | 走扩展-收缩 |
| 删字段 / 删表 | ❌ 不可逆 | 先"停止使用"，观察一个发布周期后再删 |
| 数据回填 | ⚠️ 需要可重入 | 脚本要幂等、可断点续跑 |

> 一句话原则：**数据库变更与应用发布解耦**——先让数据库"能同时兼容新旧两个版本"，再发应用。

## 七、GitOps：把 Git 当唯一事实源 {#gitops}

| 维度 | Push 式（传统流水线） | **Pull 式（GitOps）** |
|---|---|---|
| 谁发起部署 | CI 系统执行 `kubectl apply` | 集群内的控制器**主动拉取** Git 并比对 |
| 集群凭证 | 存在 CI 系统里（泄漏面大） | 不出集群 |
| 漂移检测 | 没有，手工改动无人知晓 | 持续比对，**手工改会被自动纠偏** |
| 审计 | 看流水线日志 | 看 Git 提交历史 |
| 回滚 | 重新跑一次流水线 | `git revert` |
| 代表工具 | Jenkins / GitLab CI | Argo CD / Flux |

关键差异是**方向**：GitOps 里"部署"不再是"推一次命令"，而是"**声明状态被持续对齐**"——这一点与 K8s 的控制器循环是同一个思想。

## 八、工具选型 {#tools}

| 工具 | 定位 | 优势 | 代价 |
|---|---|---|---|
| **Jenkins** | 通用 CI 引擎 | 插件生态最全、可高度定制 | 维护成本高（插件兼容、安全补丁） |
| **GitLab CI** | 与代码仓库一体 | 配置即代码、开箱即用 | 与 GitLab 绑定 |
| **GitHub Actions** | 与仓库一体、生态大 | 上手最快、复用社区 Action | 复杂流水线成本高，私有 runner 需自管 |
| **Argo CD** | 部署侧（GitOps） | 漂移检测、可视化、多集群 | 需接受"拉模式"与集群内组件 |

组合最常见：**CI 用仓库自带（Actions / GitLab CI）+ CD 用 Argo CD**——前者负责"从代码到镜像"，后者负责"从清单到集群"。

## 九、使用场景与面试问答 {#interview}

**Q1：CI 和 CD 的区别？**
CI 是**每次提交**都自动构建与测试，目标是尽早发现集成问题；CD 是把通过验证的产物**交付/部署**到环境。持续交付要求"随时可发布但生产需人工确认"，持续部署则是全自动。CI 的关键是节律与反馈速度，不是有没有 CI 工具。

**Q2：为什么生产不能用 `latest` 标签？**
因为它是**浮动**的：同一标签的内容会变，于是"回滚到上一版"和"当前跑的是哪一版"都无法确定。生产部署必须引用不可变标签（首选 Git 提交 SHA），保证镜像与代码一一对应、可追溯、可复现。

**Q3：蓝绿和金丝雀的区别？**
蓝绿是**两套完整环境 + 整体切换**，切换瞬间完成、回滚只需切回流量，代价是双倍资源；金丝雀是**同一环境内按比例引流**，用真实流量小步验证，代价是需要流量切分与指标观察能力。**蓝绿解决"回滚速度"，金丝雀解决"变更风险"。**

**Q4：回滚怎么做？数据库怎么回滚？**
应用回滚靠"镜像不可变 + 声明式部署"，改回上一个标签即可（或 `rollout undo`）。数据库是真正的难点：DDL 与数据迁移不可逆，所以要用**扩展-收缩**——先加新结构（兼容双版本）、双写与回填、切读、验证稳定后再删旧结构。删字段/删表要单独延后一个发布周期再做。

**Q5："一次构建，多处部署"是什么意思？**
同一个镜像产物在测试、预发、生产**复用**，环境差异通过环境变量、ConfigMap、Secret 注入，而不是重新构建。这样"测试通过的那个产物"就是"上线的那一个"，验证结论可以继承。反之（每个环境各自构建）会让测试结论与实际发布的产物脱钩。

**Q6：流水线太慢怎么优化？**
先测出各阶段耗时再动手，常见四招：① **快慢分离**——静态检查与单测前置，集成/E2E 放后并允许并行；② **缓存依赖与构建层**（BuildKit 缓存挂载、镜像仓库作缓存）；③ **减少重复构建**——只构建受影响的模块（增量/矩阵）；④ **并行化**——多模块、多架构、多环境并行。注意别用"跳过测试"来换速度，那是把成本挪到线上。
