"回滚"这个词暗示了一个对称的动作：既然能发上去，就应该能退回来。但真实情况是——**回滚的可行性在发布开始的那一刻就已经决定了**，而不是在需要回滚的那一刻。

决定它的是一个很朴素的问题：**这一步能不能被撤销？** 镜像换回上一个标签当然可以；但已经新建的表、已经回填的数据、已经被消费掉的消息、已经对外发出的通知，都不能。**发布链上唯一真正不可逆的部分，是数据。**

> **主线：回滚的上限由"这一步能不能被撤销"决定，而应用与数据库要分开处理。**
>
> 应用的回滚是"换个引用"，秒级完成；数据库的回滚是"重新组织数据"，几乎不可能在线完成。所以正确的策略不是"想好怎么回滚数据库"，而是**设计一条永远不需要回滚数据库的路径**。

## 一、问题场景：为什么"回滚"经常失败 {#why}

线上同一个故障，两种发布方式的结局差别很大：

| 情形 | 应用层回滚 | 数据层 | 结果 |
|---|---|---|---|
| 改了代码逻辑，无 DDL | 秒级切回上一个标签 | 无需处理 | ✅ 顺利回滚 |
| 加了字段，新旧代码都兼容 | 秒级切回 | 新字段留着，旧代码不读 | ✅ 顺利回滚 |
| 改了字段**语义**（如金额单位从元改成分） | 切回旧标签 | **新旧数据混在一起，旧代码读新数据全错** | ❌ 回滚后错误依旧，甚至更糟 |
| 已执行数据回填 + 切读 | 切回旧标签 | 旧代码需要的旧字段已停写 | ❌ 回滚等于第二场故障 |

第三条和第四条是最危险的：**它们的表现是"回滚了但没好"，于是误判为"回滚不管用"，转而在生产上直接改数据**——这是把一次可控的发布事故升级成数据事故的典型路径。

## 二、应用回滚的两个前提 {#app-rollback}

应用回滚能"秒级完成"，依赖两个前提，缺一个都不成立：

| 前提 | 为什么必需 | 缺失后的表现 |
|---|---|---|
| **镜像不可变** | 必须能回到一个**确定的、与上次验证过的一模一样**的产物 | 用了浮动标签（`latest`），"回滚到上一版"回到的可能是另一个内容 |
| **部署是声明式的** | 回滚是"改一个引用并让它生效"，而不是"登机器换包" | 手工部署的环境里，回滚靠人回忆步骤，恢复时间 = 人的反应时间 |

具体手段：

```bash
# K8s 原生
kubectl rollout undo deployment/app
kubectl rollout status deployment/app --timeout=300s

# 声明式（推荐）：把清单里的 image tag 改回上一个 SHA
# 若走 GitOps，则是 git revert —— 否则控制器会立刻把集群拉回 Git 状态
```

> **一个必须显式确认的问题："回滚到哪个版本"这件事本身有没有答案？** 如果团队的答案是"看谁记得上次是哪个包"，那即使有回滚命令也救不了场。做法很简单——**每次发布自动记录"上一个已知良好版本"**（流水线里把上一个 tag 写进环境或制品元数据），让回滚的目标是一个可查询的事实，而不是一段记忆。

**回滚窗口是存在的**：发布后过了多久，回滚就不再是首选。典型的分界是"数据是否已经按新结构写入"——只要开始写入新结构，回滚的成本就跳升一档。所以实践中有一个重要习惯：**发布后的观察期内不做数据迁移**，把"应用上线"和"数据切换"分成两次独立的、各自可回滚的操作。

## 三、数据库：唯一真正不可逆的部分 {#expand-contract}

数据库变更的不可逆来自三个事实：**DDL 会改变结构（旧代码读不了）、数据一旦被转换就有信息损失（单位变更、字段拆分）、删除是不可逆的。**

标准解法是**扩展-收缩（expand-contract）**，把一次破坏性变更拆成五次各自可回滚的变更：

```
① 扩展：加新字段 / 新表        （旧代码不感知，可随时回滚）
      ↓
② 双写：新旧字段同时写          （两个版本都能跑，是"共存期"的核心）
      ↓
③ 迁移：回填历史数据 + 校验一致  （幂等、可断点续跑）
      ↓
④ 切读：代码改为只读新字段      （此时才不可轻易回滚 —— 回滚窗口关闭）
      ↓
⑤ 收缩：确认稳定后，删除旧字段   （延后一个发布周期再做）
```

**每一步都是一次独立的、可回滚的发布**，而不是"一次发布做完五件事"。这是这个模式的全部价值：**把不可逆的动作切成若干可逆的小步。**

| 步骤 | 可回滚？ | 回滚动作 |
|---|---|---|
| ① 扩展 | ✅ | 删掉新字段（如果还没人写） |
| ② 双写 | ✅ | 回滚代码，新字段留着不用 |
| ③ 迁移 | ⚠️ 需要幂等 | 重跑不受影响；但**回填前的值需要保留**才能真回退 |
| ④ 切读 | ❌ 不易 | 旧字段可能已停写，回滚后数据是"旧字段不完整"的状态 |
| ⑤ 收缩 | ❌ **不可逆** | 只能从备份恢复 |

> **注意第 ③ 步的一个细节**：迁移如果**原地覆盖**（把旧字段的值改写成新格式），那就失去了回退能力。保命做法是**新字段写新值、旧字段保持原样**，让两个版本各自读各自的字段；此时回滚只是"代码读回旧字段"，数据无需任何操作。

## 四、变更类型与可回滚性分级 {#ddl-matrix}

| 变更类型 | 可回滚性 | 处理要点 |
|---|---|---|
| 加字段（可空 / 有默认值） | ✅ 高 | 直接做；**注意 MySQL 加列在大表上可能触发表重建** |
| 加索引（在线） | ✅ 高 | 用 `ALGORITHM=INPLACE` / `ONLINE=1`；大表加索引仍有 IO 压力，避开高峰 |
| 加表 | ✅ 高 | 无风险 |
| **改字段类型** | ⚠️ 中 | 走扩展-收缩；**类型收窄（`VARCHAR(255)→VARCHAR(64)`）可能截断，需先校验** |
| **重命名** | ⚠️ 中 | 不要真重命名。做法是**新增一个字段**，双写、回填、切读、最后删旧字段 |
| **改字段语义**（单位、编码） | ❌ 低 | 必须走完整扩展-收缩，且**保留原字段原值**以便回退 |
| **拆分 / 合并表** | ❌ 低 | 同"改语义"，是成本最高的一类 |
| 删字段 / 删表 | ❌ **不可逆** | 先"停止写入并停止读取"，观察一个完整发布周期，再删 |
| 数据回填 | ⚠️ 需幂等 | 见下一节 |
| 加约束 / 唯一索引 | ⚠️ 中 | 存量数据可能违反约束，**先查再建**，否则会锁表或建失败 |

**三个数据库侧的操作纪律**：

1. **DDL 与应用发布解耦，且先于应用发布。** 顺序永远是"先让数据库能同时兼容新旧两个版本，再发应用"。反过来的后果是：新代码上线时字段还不存在，直接报错。
2. **大表 DDL 要单独评估锁与耗时。** 一次误操作的表重建可能锁表数分钟，把发布事故变成全站故障。评估方式是在**同量级的影子表**上先跑一遍。
3. **删表/删字段是最后一个动作，且要延后。** 它的价值是"清理"，成本是"永久失去退路"。多数团队把它排到下一个迭代——**这不是拖延，这是给回滚留窗口。**

## 五、回填脚本的工程要求 {#backfill}

数据迁移脚本是最容易被当成"一次性脚本"来写的部分，而它恰恰是在生产主库上跑、影响面最大的部分。

| 要求 | 为什么 | 具体做法 |
|---|---|---|
| **幂等** | 必须能重跑（失败重试、部分完成再跑） | 用 `WHERE new_col IS NULL` 之类的条件限定，让重复执行不产生副作用 |
| **可断点续跑** | 大表迁移可能跑几小时，中途任何原因都可能中断 | 按主键区间分批（`WHERE id > ? ORDER BY id LIMIT 1000`），记录进度 |
| **限速** | 全速回填会打满主库 IO、拖垮在线业务 | 每批之间 sleep；或用 `pt-online-schema-change` / `gh-ost` 这类工具自带限流 |
| **可观测** | 需要知道"跑到哪了、还剩多少" | 输出进度指标；**同时盯主库的延迟与 QPS** |
| **可回退** | 回填出错要能撤销 | 保留原字段原值（见上节），或导出变更前的数据快照 |
| **不对抗在线流量** | 主库要优先服务线上请求 | 避开业务高峰；必要时从库读取、异步回填 |

> **判断脚本是否合格的实用标准**：把它**中途 kill 掉，再重新跑一遍**，最终数据仍然正确。做不到这一点的回填脚本，本质上没有重试能力——而生产环境里"需要重跑"是常态，不是意外。

**回填结束后必须做的事是校验，而不是继续往前走。** 至少要核对：行数是否一致、抽样比对关键字段、业务口径的汇总值是否对得上（比如总金额、订单数）。**校验不通过就不进入切读阶段**——已经在双写状态下，退回去的成本几乎为零；而切读之后再发现问题，成本就跳一档。

## 六、五类"发布即故障" {#release-incidents}

有一类故障的特点很鲜明：**它只在发布时刻出现，平时的监控曲线完全正常。** 下面是五类最常见的原因。

### 6.1 优雅停机缺失：连接被重置

表现是发布窗口内少量 5xx、连接重置。原因和修法在[发布策略篇](/cloud-native/cicd/release-strategies#prestop-race)已经展开：**摘流路径是最终一致且不受控的**，需要 `preStop` 等待 + 三者超时对齐（应用排空超时 < 终止总预算 − preStop）。更详细的停机语义见[优雅停机](/high-availability/redundancy-failover#graceful)。

### 6.2 连接池与线程池耗尽

新版本改了并发模型（引入新的下游调用、把同步改异步、调小了连接池上限），在发布期间新旧版本并存、副本数还在波动，资源使用出现**叠加**。

判断标志是"发布时下游报连接超时，但下游自身指标正常"。**新版本发布前要重新核一遍它依赖的每个下游的连接池上限 × 副本数，是否还在下游的承受范围内。**

### 6.3 缓存击穿：发布把缓存清空了

滚动发布时如果每个新实例都**清空并重建本地缓存**，那么一个原本被缓存挡住的查询会瞬间打到数据库上。这个动作在单个实例上无害，但**多个副本在几分钟内轮流重建缓存**，就会把数据库打成峰值。

对策有三条：**让新实例"预热后再就绪"**（readiness 检查缓存加载完成）、**共享缓存（Redis）承接穿透**、**给缓存加"随机过期的抖动"避免同时失效**。

### 6.4 配置漂移：新版本依赖一个生产没有的配置

新版本读了一个新配置项（`feature.x.enabled`），测试环境有、生产漏配。表现取决于实现：**如果配置缺失时用默认值**，那就是"功能静默不生效"（比报错更难查）；**如果直接抛异常**，就是启动失败。

做法是把**配置项的清单纳入发布检查**（新版本新增了哪些必需配置、生产有没有），并让"缺失必需配置"在启动时就失败（fail fast），而不是用默认值糊过去。

### 6.5 发布顺序错误：上下游依赖倒置

服务 A 的新版本依赖服务 B 的新接口，但先发了 A。表现是 A 在发布后开始报"未知方法/字段缺失"。**多服务联调发布必须有明确的顺序**，并优先设计成"向后兼容"以避免顺序依赖——**能通过"先加接口、后调用"消除顺序依赖的，就不要靠发布手册去约定顺序。**

## 七、发布检查清单 {#checklist}

一份可以贴进发布流程的清单。它的作用是**把"想清楚"变成一个可勾选的动作**。

| 类别 | 检查项 |
|---|---|
| **制品** | 镜像标签是不可变的、能追溯到具体提交；本次发布的制品已在预发验证过同一份 |
| **兼容性** | 新旧版本能否共存（接口双向兼容、消息格式兼容、表结构双方可读） |
| **数据库** | 本次有无 DDL / 回填；若有，是否已走完"扩展"（新结构先于代码上线）；回填脚本是否幂等且已在小样本验证 |
| **配置** | 新版本新增的**必需**配置项，生产是否已配；缺失时是否 fail fast |
| **依赖** | 上下游服务的发布顺序；是否存在"必须先发对方"的依赖 |
| **容量** | 新版本的资源画像有无变化（内存、连接数、并发）；蓝绿/滚动期间的容量余量够不够 |
| **容器** | `preStop` 等待、`terminationGracePeriodSeconds`、排空超时三者是否对齐；探针是否检查真实依赖 |
| **观察** | 发布后要看哪几个指标（错误率、延迟分位、**业务指标**、队列积压）、看多久 |
| **回滚** | 回滚命令是什么、谁有权执行、预计耗时；**上一个已知良好版本是哪个**（要有确定的答案） |
| **数据** | 本次发布是否进入"回滚窗口关闭"的阶段（已切读）；若是，回滚方案是什么 |
| **沟通** | 谁需要知道这次发布；选在什么时间（避开业务高峰与值班薄弱时段） |

> **最容易被跳过、又最该做的是"观察窗口"这一项**。很多团队的发布流程在"部署完成、冒烟通过"就结束了，而真正的问题可能在 10~30 分钟后才显形（缓存逐步失效、连接池逐步增长、消息逐步积压）。**没有观察窗口的发布，等于把验证工作交给了用户。**

## 八、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 回滚怎么做？ | 应用侧靠**镜像不可变 + 声明式部署**（切回上一个标签或 `rollout undo`）；用了 GitOps 则是 **`git revert`**，否则控制器会把集群拉回 Git 状态。关键是**"上一个已知良好版本"是一个可查询的事实**，不是一段记忆 |
| 2 | 数据库怎么回滚？ | **基本不能"回滚"，只能设计成不需要回滚。** DDL 与数据迁移不可逆，所以走**扩展-收缩**：先加新结构（兼容双版本）→ 双写 → 回填校验 → 切读（此时回滚窗口关闭）→ 稳定后再删旧结构。**每一步是独立的可回滚发布** |
| 3 | 为什么改字段语义最危险？ | 因为它让**新旧数据在同一张表里混存且无法区分**。回滚代码后，旧代码读到的是按新语义写入的数据，结果全错——表现是"回滚了但错误还在"，容易被误判为"回滚不管用"而转去生产改数据 |
| 4 | 回滚窗口是什么？ | 发布后过了某个点，回滚不再是首选——**典型分界是"数据是否已按新结构写入"**。所以实践习惯是**发布观察期内不做数据迁移**，把"应用上线"与"数据切换"分成两次各自可回滚的操作 |
| 5 | 回填脚本要做到什么？ | 六个要求：**幂等、可断点续跑、限速、可观测、可回退、不对抗在线流量**。最实用的验收标准是**中途 kill 掉再重跑，最终数据仍然正确** ——生产里"需要重跑"是常态 |
| 6 | 大表加索引要注意什么？ | 用在线方式（`ALGORITHM=INPLACE` / `ONLINE=1`）；**但"在线"不等于"无开销"**，大表加索引仍有 IO 压力，要避开高峰。改字段类型与加唯一约束更危险：**类型收窄可能截断、约束可能因存量数据不满足而建失败或锁表** |
| 7 | 删字段为什么要延后一个周期？ | 因为它是**唯一真正不可逆**的动作。先"停止写入并停止读取"，观察一个完整发布周期确认无人依赖，再删。延后不是拖延，是给回滚留窗口 |
| 8 | 为什么数据库变更要先于应用发布？ | 因为顺序必须是"**先让数据库能同时兼容新旧两个版本**，再发应用"。反过来（代码先上、字段还没加）会直接报错。同理，删旧结构必须等代码完全不再依赖之后 |
| 9 | 什么故障只在发布时出现？ | 五类：**优雅停机缺失**（连接重置）、**连接池/线程池耗尽**（并存期资源叠加）、**缓存击穿**（副本轮流重建本地缓存把 DB 打穿）、**配置漂移**（生产漏配新配置项）、**发布顺序倒置**（上下游依赖反了） |
| 10 | 缓存击穿为什么会由发布引起？ | 滚动发布时每个新实例清空并重建本地缓存，单个实例无害，但**多个副本在几分钟内轮流重建**，原本被缓存挡住的查询会集中打到 DB 上。对策是预热后再就绪、共享缓存承接、加随机过期抖动 |
| 11 | 发布清单里最容易漏哪一项？ | **观察窗口**。多数流程在"部署完成 + 冒烟通过"就结束，而真问题常在 10~30 分钟后才显形（连接池渐进增长、消息渐进积压）。**没有观察窗口的发布，等于把验证交给了用户** |
| 12 | 怎么让发布不依赖"顺序正确"？ | 优先设计成**向后兼容**：新增接口先发布、调用方后发；新字段先加、代码后读。**能通过设计消除顺序依赖的，就不要靠发布手册去约定顺序** ——手册会被忘、会被绕过，而兼容性约束不会 |
