发布策略这个词容易让人以为在选择"用哪种方式上线"。其实四种策略真正的差别只有一个：**出问题时，故障半径有多大，以及退回去要多久。**

重建是"全体一起上"，滚动是"一个一个上"，蓝绿是"两套并存、整体切换"，金丝雀是"先让一小撮流量上"。从重建到金丝雀，风险的暴露面在缩小、回退速度在加快，代价则是资源占用与实现复杂度的上升。

> **主线：发布策略选的是"故障半径"，而"不中断"不靠策略，靠"终止路径"与"摘流路径"的对齐。**
>
> 这是两个独立的维度——选对了策略，服务依然可能在发布时丢请求；选错了策略，也可能因为对齐做得好而平稳。**前半句是设计选择，后半句是工程细节，后者才是线上最常见的坑。**

## 一、问题场景：为什么"滚动更新"还会掉请求 {#why-downtime}

假设一个 Spring Boot 服务，3 个副本，配置了 readiness 探针，代码里已经处理了 `SIGTERM`（Spring Boot 的 `server.shutdown=graceful` 会等现有请求结束）。听上去万无一失，但发布时监控里仍然会出现少量 `502` / `connection refused`。

原因在于**删掉一个 Pod 时，集群里同时发生了两件事，而它们不是同一时刻完成的**：

| 路径 | 内容 | 完成时间 |
|---|---|---|
| **终止路径**（kubelet） | `terminationGracePeriodSeconds` 开始计时 → 执行 `preStop` → 发 `SIGTERM` → 超时发 `SIGKILL` | 相对快，可控 |
| **摘流路径**（控制面 + 网络） | 从 Service 的 EndpointSlice 摘除 → kube-proxy / ingress 控制器**同步路由表** | **最终一致，慢** |

两条路径并行，谁先完成不确定。所以有一小段时间窗口：**某个节点上，请求还会被路由到一个已经收到 `SIGTERM`、已经关闭监听端口的 Pod 上**。

关键点在于：**"应用优雅停机做得再好也救不了这个窗口"**——问题不是应用不肯处理请求，而是上游还在把新请求发给它。这正是"不中断"与"策略选择"无关的原因。

## 二、四种发布策略 {#strategies}

| 策略 | 原理 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **重建（Recreate）** | 先停旧、再起新 | 最简单，无版本共存 | **有中断**；且中断时长 = 新版本启动时间 | 内部工具、可停服系统、批处理任务 |
| **滚动（Rolling）** | 逐步替换，新起一个/停一个 | 不中断、资源占用小、K8s 原生支持 | 新旧版本**短时共存**，接口需双向兼容 | 绝大多数无状态服务（默认选择） |
| **蓝绿（Blue-Green）** | 部署全新一套，流量整体切换 | 切换瞬间、回滚只需切回 | **双倍资源**；两套并存期间数据库需兼容两版 | 关键系统、要求秒级回滚 |
| **金丝雀（Canary）** | 先引一小部分流量到新版本，观察后逐步放量 | 风险可控，能用真实流量验证 | 需要流量切分能力 + 完善的指标观察 | 大流量、变更风险高的服务 |

四个容易忽略的细节：

**1. 重建的"中断时长"常被低估。** 它不只是"重启那几秒"，还包括镜像拉取、JVM 启动、连接池预热、缓存加载。一个冷启动 40 秒的 Java 服务，用重建策略意味着每次发布停服 40 秒起步。

**2. 滚动的"新旧共存"是接口兼容问题，不是时间问题。** 共存窗口内，新旧版本会**互相调用**（尤其在多服务同时发布时）。所以滚动发布的隐含前提是：**新旧版本能同时消费同一份消息、读同一张表、理解同一份响应**。这条前提在"加字段"时成立，在"改字段语义"时不成立——那种变更必须走[扩展-收缩](/cloud-native/cicd/rollback-and-migration#expand-contract)。

**3. 蓝绿的双倍资源不是"多花一倍"这么简单。** 大内存服务在蓝绿期间可能直接把集群撑满，触发其他服务被驱逐。上蓝绿前要先确认**集群有没有容纳两套的余量**，否则切换本身就会引发故障。

**4. 金丝雀的前提是"能观察"。** 没有可信的指标（错误率、延迟分位、业务成功率），金丝雀就退化成"手动切 5% 然后凭感觉"，风险控制能力与滚动更新没有本质区别，却多了实现复杂度。**金丝雀的价值来自"指标驱动的自动判定"，而那个判定要用到[可观测](/cloud-native/observability/)那套东西。**

## 三、金丝雀的流量切分：三个层次，能力与代价递增 {#traffic-split}

| 层次 | 手段 | 粒度 | 代价 |
|---|---|---|---|
| **网关 / Ingress** | 按权重或 Header 路由 | 请求级 | 实现最简单；但与具体网关绑定，多协议（gRPC、MQ）覆盖不全 |
| **服务网格** | 按比例分发 + 自动分析指标 | 请求级 | 可遥测驱动；代价是引入网格（见[服务网格](/cloud-native/service-mesh/#capabilities)） |
| **应用内 Feature Flag** | 代码里判开关 | 业务维度 | **不需要两套部署**、可随时开关；代价是应用要改造、且开关本身会变成技术债 |

**三个层次的本质差别在于"谁在做决定"**：网关只看得到 L7 请求，网格能拿到指标并驱动放量，应用内则能看到业务语义（比如"只放给免费用户""只放给某城市")。

一个常见的组合是：**网关做初筛（1% 流量）→ 网格或应用层做业务维度细分 → 指标异常时自动回滚流量**。注意最后一环——**没有自动回滚的金丝雀，只是"更慢的发布"**，因为出事时仍然要人发现、人决策、人操作。

补充一条容易被忽略的覆盖问题：**金丝雀很难覆盖异步链路。** 网关的权重路由对 HTTP 请求有效，但 MQ 消费者、定时任务、CDC 同步这些"非请求驱动"的路径不在它的控制范围内。一个服务同时提供 HTTP 接口和消费 MQ 时，金丝雀只保护了前者。异步侧的灰度要靠独立的开关（消费端按比例跳过）或按租户/分片维度隔离。

## 四、选择顺序：先问代价，再问速度，最后问流量 {#choose}

按下面的顺序问，三步就能定下来：

```
① 能承担"两套环境"的成本吗？ ── 不能 ──▶ 滚动更新
         │ 能
         ▼
② 回滚速度要求是"秒级"吗？ ── 是 ──▶ 蓝绿
         │ 否
         ▼
③ 流量足够大、指标足够可信吗？ ── 是 ──▶ 金丝雀
         │ 否
         ▼
   滚动更新 + 就绪探针 + 优雅停机 + 观察窗口
```

几条判据：

- **多数服务停在"滚动 + 三件事"就够了。** 发布风险的大头不是"版本切换方式"，而是**探针配置错、优雅停机没做、连接没排空**。把这些修好，比上金丝雀的收益更直接。
- **不要为了"高级"跳过滚动更新。** 见过不少团队一上来就搭金丝雀，结果基础的就绪探针都没配对——金丝雀只放 1% 的流量到新版本，而新版本因为探针没配而在启动中就被判定"可用"，1% 的流量全打到未就绪的进程上。
- **蓝绿适合"回滚速度 > 资源成本"的场景**：支付、认证、核心交易。它的价值是"回滚只需切一次流量"，而不是"发布更安全"——**蓝绿不验证新版本，它只提供快速退路**。
- **金丝雀适合"能用真实流量发现，而测试发现不了"的问题**：某个只有特定数据形态才触发的 NPE、某个慢查询在真实基数下才暴露。这类问题越多，金丝雀越值。

| 你的处境 | 建议 |
|---|---|
| 三人小队、单体应用、无状态 | 滚动 + 探针正确 + 优雅停机 |
| 核心交易、要求秒级回退 | 蓝绿（先确认集群有两倍余量） |
| 大流量、多租户、变更频繁 | 金丝雀（先确认指标可信、自动回滚可达） |
| 有状态服务（DB / MQ / 缓存） | 不用以上任何一种，走专门的 Operator 流程 |

## 五、滚动更新不中断，靠的是三件事 {#rolling-safe}

K8s 的 `RollingUpdate` 本身只是"逐步替换副本"，它不保证不中断。**真正让请求不丢的是三件配置的组合**：

| 手段 | 它解决什么 | 配错的后果 |
|---|---|---|
| **readiness 探针** | 保证"只把流量发给已就绪的 Pod" | 配错/缺失 → 流量打到还在启动的进程，报错但不是"发布故障"，混在正常错误里更难查 |
| **优雅停机**（排空连接） | 已收到的请求要处理完再退出 | 缺 → 长请求被 `SIGKILL` 切断，表现为偶发的"超时"与"连接重置" |
| **PDB（PodDisruptionBudget）** | 限制**自愿中断**时同时被摘除的副本数 | 缺 → 一次 `kubectl drain` 或节点缩容可能同时干掉多个副本，容量瞬间不足 |

三个容易踩的细节：

**1. `maxUnavailable` 与 `maxSurge` 的取向。** 保守配置是 `maxUnavailable: 0` + `maxSurge: 1`——**先起新的、再停旧的**，容量永远不低于期望值，代价是发布期间多占一个副本的资源。反过来（`maxUnavailable: 1` + `maxSurge: 0`）省资源，但发布期间容量会少一个副本，在流量高峰做发布就会引发延迟升高。

**2. `minReadySeconds` 是"就绪之后再看一会儿"。** 探针只判断"此刻能不能服务"，`minReadySeconds` 让它在判定为可用后再稳定若干秒才继续推进。**这个参数能拦住"启动后 3 秒才崩"的问题**——没有它，滚动更新会飞快地把所有副本换成那个会崩的版本。

**3. PDB 管的是另一类事件。** `maxUnavailable` 管的是**你自己触发的发布**；PDB 管的是**别人触发的驱逐**（节点升级、集群缩容、节点故障转移）。两者不重叠，**都要配**。PDB 的常见写法是 `minAvailable` 设为期望副本数的多数（3 副本 → `minAvailable: 2`），并注意：**PDB 只约束自愿中断，节点宕机这类非自愿中断它拦不住**。

## 六、preStop 的双路径竞态：为什么必须"睡一会儿" {#prestop-race}

回到第一节那个窗口。标准修法是在 `preStop` 里加一段等待，**让摘流先于终止完成**。

```
Pod 被删除
   │
   ├─▶ 【kubelet 路径】开始计时 → 执行 preStop（sleep 15s）
   │                              → SIGTERM → 应用排空 → 退出
   │
   └─▶ 【网络路径】EndpointSlice 摘除 → kube-proxy / ingress 同步路由表
                    （通常几百毫秒 ~ 数秒，但不受控）

   preStop 的 sleep 就是在等第二条路径完成 —— 期间进程仍然在服务
```

K8s **1.34 起原生支持 `preStop` 的 sleep 动作**（`lifecycle.preStop.sleep.seconds`），不再需要镜像里有 `sh` 和 `sleep` 二进制，**distroless 镜像也能用**：

```yaml
spec:
  template:
    spec:
      # 必须 > preStop 的等待 + 最长请求处理时间
      terminationGracePeriodSeconds: 45
      containers:
        - name: web
          lifecycle:
            preStop:
              sleep:
                seconds: 15      # v1.34+ 原生；更早的集群用 exec: ["/bin/sh","-c","sleep 15"]
```

**参数怎么定，比"抄一个 15 秒"重要得多**：

| 参数 | 起什么作用 | 定法 |
|---|---|---|
| `preStop` 的 sleep | 等摘流完成 | 略大于"路由表同步最坏耗时"，一般 5~15 秒；**贪大没必要，它直接加长发布总时长** |
| `terminationGracePeriodSeconds` | **整个终止流程**的总预算 | **必须 > preStop + 应用排空最长时间**。官方口径很直白：preStop 用 55 秒、应用还要 10 秒，那它低于 65 就会 `SIGKILL` |
| 应用内的排空超时 | 停止收新请求、处理完在途请求 | 略小于"总预算 − preStop"，让应用自己有序退出而不是被强杀 |

> **三个超时的关系必须显式对齐**：`排空超时 < 终止总预算 − preStop`。任何一处配反，表现都是"发布时偶发 5xx"，且**没有任何一条日志会直接指向它**——只会看到连接被重置的时间点恰好和发布窗口重合。

**滚动发布中还有一个隐蔽问题：新 Pod 的就绪判定过早。** 如果 readiness 探针只测 `/healthz` 返回 200，而实际依赖（数据库连接池、下游服务、缓存预热）还没准备好，那么第一批请求就会打到"自称就绪但还没准备好"的实例上。做法是让 readiness **检查真实依赖**（Spring Boot Actuator 的 `readiness` 组可以包含 `db`、`redis`），并配合 `initialDelaySeconds` + `failureThreshold` 给足预热时间。

## 七、策略之外：三类服务的特殊处理 {#stateful}

前面讲的都是无状态 HTTP 服务。另外三类需要单独说：

### 7.1 长连接服务（gRPC / WebSocket）

HTTP 短连接下，"排空连接"是几秒的事。但 gRPC 的流式连接、WebSocket 连接可能存活几十分钟——**优雅停机若等它自然结束，发布会被拖住；不等，就会切断在线会话。**

| 做法 | 说明 |
|---|---|
| **先摘流，再通知客户端重连** | 服务端主动发一个"该重连了"的信号，客户端换到别的实例，而不是被硬断 |
| **给连接设最大生命周期** | 服务端强制在 N 分钟后断开，让客户端定期重连（重连时天然会重新负载均衡） |
| **终止预算加大** | 长连接服务需要更长的 `terminationGracePeriodSeconds`，且要接受"发布窗口内不保证零中断" |

### 7.2 MQ 消费者

消费者不在 Service 的负载均衡里，**摘流机制对它无效**。它的等价动作是：

1. **停止拉取新消息**（`SIGTERM` 后先暂停消费）；
2. **处理完手上这批**（含未 ack 的消息）；
3. **超时未完成就放弃并退出**——让消息重新入队由别的实例接管，这是"至少一次"语义的正确用法。

> **消费端最容易出的发布事故是"发布期间消费积压"**：新版本的消费逻辑变慢，加上滚动期间副本数减少，积压快速上涨。所以消费端发布要**单独看消费延迟这个指标**，它不在发布流水线的冒烟检查里。

### 7.3 有状态服务

数据库、消息中间件、缓存集群**不适合用上面的任何策略**。副本之间有主从关系、数据有唯一归属，替换一个节点涉及选主、数据追平、客户端重连，不能靠"逐个替换"解决。

这类服务的正确处理是**交给 Operator 固化运维流程**（见 [CRD 与 Operator](/cloud-native/operator/)），发布走"版本升级"而不是"滚动替换"，并由 Operator 负责探活、故障转移与容量校验。

## 八、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 蓝绿和金丝雀的区别？ | 蓝绿是**两套完整环境 + 整体切换**，切换瞬间完成、回滚只需切回流量，代价是双倍资源；金丝雀是**同一环境内按比例引流**，用真实流量小步验证，代价是需要流量切分与指标观察。**蓝绿解决"回滚速度"，金丝雀解决"变更风险"** |
| 2 | 为什么配了探针、也做了优雅停机，发布还是会掉请求？ | 因为**摘流路径是最终一致且不受控的**。kubelet 的终止路径与 EndpointSlice 的路由同步并行执行，存在一个"路由表还在指向已终止 Pod"的窗口。标准修法是 `preStop` 里等待一段时间，让摘流先完成 |
| 3 | `preStop` 为什么用 sleep？睡多久？ | 它存在的唯一目的就是**等路由表同步完成**，应用本身不会因此被停止（`preStop` 执行完才发 `SIGTERM`）。时长取"略大于路由同步最坏耗时"，一般 5~15 秒；**贪大只会加长发布总时长** |
| 4 | `terminationGracePeriodSeconds` 怎么定？ | 它是**整个终止流程的总预算**（preStop + 应用排空），所以必须 `> preStop 等待 + 最长请求处理时间`。三者要显式对齐：**应用排空超时 < 总预算 − preStop**；配反了就是"发布时偶发 5xx"，而且没日志指向它 |
| 5 | 滚动更新的 `maxUnavailable` 和 `maxSurge` 怎么配？ | 保守配置是 `maxUnavailable: 0` + `maxSurge: 1`——**先起新的再停旧的**，容量永远不低于期望，代价是多占一个副本。反过来省资源但会有容量缺口，高峰发布就会引发延迟升高 |
| 6 | `minReadySeconds` 有什么用？ | 让 Pod 在"被判定就绪"之后再稳定若干秒才继续推进。**它能拦住"启动后几秒才崩"的版本**——没有它，滚动更新会飞快地把所有副本都换成会崩的版本 |
| 7 | PDB 和 `maxUnavailable` 有什么区别？ | 管的是**不同事件**。`maxUnavailable` 管你自己触发的发布；PDB 管**别人触发的自愿驱逐**（节点 drain、集群缩容）。两者不重叠，都要配。注意 **PDB 不约束节点宕机这类非自愿中断** |
| 8 | 发布策略怎么选？ | 按顺序问三步：**① 能承担两套环境的成本吗（不能→滚动）；② 回滚要求秒级吗（是→蓝绿）；③ 流量够大、指标够可信吗（是→金丝雀）**。多数服务停在"滚动 + 三件事（探针/优雅停机/PDB）"就够了 |
| 9 | 金丝雀的"自动回滚"为什么重要？ | 没有它，金丝雀只是**更慢的发布**——出事仍要人发现、人决策、人操作。金丝雀的价值来自"指标驱动的自动判定"，所以它依赖可信的指标与告警体系 |
| 10 | 金丝雀覆盖不到哪些场景？ | **异步链路**。网关的权重路由只对请求驱动的流量有效，**MQ 消费者、定时任务、CDC 同步**都不在它的控制范围内。异步侧的灰度要靠独立的开关或按租户/分片隔离 |
| 11 | 蓝绿发布最容易忽略什么？ | **集群有没有容纳两套的余量**。双倍资源不是"多花钱"这么简单——内存型服务在并行期可能直接把节点撑满，导致其他服务被驱逐。上蓝绿前先确认容量 |
| 12 | 有状态服务为什么不适用这些策略？ | 副本间有主从关系、数据有唯一归属，替换节点涉及选主、数据追平、客户端重连。正确处理是**交给 Operator 固化运维流程**，走"版本升级"而非"滚动替换" |
