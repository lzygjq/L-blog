# 可用性目标：把「高可用」变成一个可计算的数

「高可用」这个词在评审会上几乎每次都会出现，但它通常是一个形容词——**说的人心里没有数，听的人也没法反驳**。所以第一件事是把形容词换成数字：可用性 = 一段时间内**可用的比例**，而「可用」这个口径本身就要先定义清楚。

## 一、几个 9 到底是多长时间 {#nines}

先把量级刻进直觉，后面所有取舍都要靠它判断：

| 可用性 | 俗称 | 年度允许停机 | 月度允许停机 |
|---|---|---|---|
| 99% | 两个 9 | **3.65 天** | 7.2 小时 |
| 99.9% | 三个 9 | **8.76 小时** | 43.2 分钟 |
| 99.95% | — | 4.38 小时 | 21.6 分钟 |
| 99.99% | 四个 9 | **52.6 分钟** | 4.32 分钟 |
| 99.999% | 五个 9 | **5.26 分钟** | 25.9 秒 |
| 99.9999% | 六个 9 | 31.6 秒 | 2.6 秒 |

这张表最该读出来的不是数字，而是**成本曲线不是线性的**：

| 目标 | 需要做的事 | 代价的性质 |
|---|---|---|
| 从 99% 到 99.9% | 别让单机故障直接停服：多实例 + 负载均衡 | **一次性工程成本** |
| 从 99.9% 到 99.99% | 故障自动转移 + 无状态化 + 消除所有人工环节（半夜不需要人爬起来） | **架构复杂度 + 人力** |
| 从 99.99% 到 99.999% | 多机房 + 数据同步 + 全链路无单点**包括依赖** | **数量级的成本 + 组织能力** |

而这里有一条最容易被忽略的天花板：

> **你的可用性上限 = 最弱依赖的可用性上限。**

云厂商整体 SLA 常见 99.95%、某个第三方支付或短信通道可能只有 99.9%。**在没有降级路径的前提下，你承诺 99.999% 是给自己埋的一个必输的官司**。所以看到"我们要做五个 9"这种目标时，第一个该问的问题不是"要几台机器"，而是"**哪几个依赖拖住了上限，它们有没有降级路径**"。

## 二、可用性的算式：MTBF 与 MTTR {#mtbf-mttr}

可用性有一个非常朴素的表达式：

```text
可用性 = MTBF / (MTBF + MTTR)

MTBF（Mean Time Between Failures）：平均无故障时长
MTTR（Mean Time To Repair）    ：平均修复时长（从发生到恢复）
```

这个式子有两个自变量，于是有两条改进路线：

| 路线 | 手段 | 成本落点 | 典型动作 |
|---|---|---|---|
| **提高 MTBF** | 更可靠的组件、冗余、消除单点 | 硬件 + 架构 | 多副本、多机房、去掉单点依赖 |
| **降低 MTTR** | 更快发现、更快定位、更快恢复 | 工程 + 流程 | 监控告警、可观测、自动切换、Runbook、演练 |

**实务判据：MTTR 是性价比更高的杠杆。** 原因是数字上的不对称——假设一个系统 MTBF 是 30 天、MTTR 是 30 分钟，把 MTBF 翻倍（到 60 天，工程难度极大）只能把可用性从 99.93% 抬到 99.97%；而把 MTTR 从 30 分钟压到 3 分钟（靠监控 + 自动化 + Runbook，通常一个季度内能做到）直接得到 99.993%。**前者要重构，后者要工程纪律。**

再把 MTTR 拆开看，它其实是三段之和，每段可以独立优化：

| 阶段 | 含义 | 优化手段 | 常见耗时占比 |
|---|---|---|---|
| 发现时间 | 从故障发生到有人知道 | 监控告警、健康检查、合成拨测 | 往往是最大的一段 |
| 定位时间 | 从知道到找到原因 | 日志、链路追踪、指标下钻、变更记录关联 | 第二段 |
| 恢复时间 | 从定位到业务恢复 | 自动切换、回滚、限流止血、Runbook | 取决于自动化程度 |

> 这三段里**最贵的是"发现"**：很多事故的真实时长不是 5 分钟，而是"从 03:10 挂到 06:30 有用户投诉才被发现"。所以"降低 MTTR"的第一步通常不是自动化切换，而是**让故障自己喊出来**（[监控与可观测](/cloud-native/observability/)）。

## 三、口径陷阱：同一个 99.99% 可以差 100 倍 {#caliber}

这是本节里最实用的一条。**可用性不是一个数，是一个"数 + 口径"**，口径不同，同样的系统可以算出完全不同的结果：

| 口径 | 怎么算 | 差异来自哪 |
|---|---|---|
| **按时间** | 不可用时长 / 总时长 | 适合衡量整体，但一个边缘功能挂一天和核心链路挂一分钟结果可能相同 |
| **按请求** | 失败请求数 / 总请求数 | 高频接口的短暂抖动会迅速吃掉预算；低频接口长期不可用可能毫无察觉 |
| **按用户** | 受影响用户数 / 总用户数 | "1% 的用户全挂" 与 "所有用户挂 1%" 的体验与损失完全不同 |

还有四个必须写进 SLA 的定义项，否则复盘时一定扯皮：

| 待定义项 | 两种常见取向 | 建议 |
|---|---|---|
| 计划内维护算不算 | 算 / 不算 | **不提前通知的维护一律算故障**；提前公告的窗口单列 |
| **部分可用怎么算** | 降级模式（能浏览不能下单）算不算可用 | 单列「**降级可用**」口径，并明确降级期间哪些功能是承诺的 |
| 统计窗口 | 月 / 季 / 年 | 短窗口更容易达标，但短窗口达标不能掩盖长事故；**SLA 用月度、复盘用年度** |
| 长尾 vs 集中 | 52 分钟集中挂一次 / 52 次 1 分钟抖动 | 后者对用户更痛。可加一条"**单次中断不超过 X 分钟**"的附加约束 |

> **一句话判据**：SLA 文档里如果没写清这四项，那它写的是愿望，不是承诺。

## 四、RTO 与 RPO：故障之后能退到哪 {#rto-rpo}

可用性回答"一年能停多久"，RTO / RPO 回答"**真出事时停多久、丢多少**"：

| 指标 | 含义 | 由什么决定 |
|---|---|---|
| **RPO**（Recovery Point Objective） | 能容忍丢多少数据（回退到哪个时间点） | **复制方式**：同步复制 RPO≈0，异步复制 RPO=延迟窗口 |
| **RTO**（Recovery Time Objective） | 能容忍停多久（从故障到恢复服务） | **恢复方式**：自动切换秒级、人工切换分钟级、备份恢复小时级 |

两者**独立设计**，且要按业务分级，不要一刀切：

| 等级 | RPO | RTO | 典型手段 | 成本 |
|---|---|---|---|---|
| L0 关键（资金、交易） | 0 | 秒 ~ 分钟 | 同城双活 + 同步复制 + 自动切换 | 最高 |
| L1 重要（核心业务数据） | 秒级 | 分钟 ~ 半小时 | 同城热备 + 半同步 | 高 |
| L2 一般（报表、日志） | 小时级 | 小时 ~ 天 | 异地异步 + 定期备份 | 中 |
| L3 可重建（缓存、派生数据） | 不要求 | 天级 | 定期全备 / 干脆不备，重建 | 低 |

这里有两条容易踩的认知错误：

- **成本从 L1 到 L0 是跳变的，不是渐变的**。因为 L0 要求"跨故障域同步写 + 自动切换"，这一跳要引入跨城延迟（见[多机房架构](/high-availability/multi-datacenter#physics)）与多数派仲裁（见[共识协议](/distributed/consensus#quorum)），复杂度直接上一个台阶。
- **"有备份"≠"能恢复"**。备份是文件，恢复是一条要演练的流程；**没有实测过恢复时间的 RTO 是书面数字**。这条是[混沌与演练](/high-availability/chaos-drills)整篇存在的理由。

## 五、可用性会相乘：为什么微服务化先降低可用性 {#series-parallel}

这是把"高可用"从口号变成算术的关键一步。

```text
【串联】A 依赖 B 依赖 C（B、C 挂了 A 就不完整可用）
A_total = A × B × C

0.999 × 0.999 × 0.999 ≈ 0.997     三个「三个 9」串起来，只剩 99.7%

【并联】n 个副本，任一可用即可，且故障相互独立
A_total = 1 - (1 - A)^n

1 - (1 - 0.999)^2 = 0.999999      两个 99.9% 并联 ≈ 99.9999%
```

推下去有两个很反直觉的结论：

**① 拆微服务会先让可用性下降。** 单体时代一次请求只在进程内调用；拆成 8 个微服务后，一次请求要串 5 层——串联项从 1 变成 5，可用性按公式必然下降。**这不是微服务的缺陷，是分布式的本质代价**，架构师要做的是补偿它，而不是假装它不存在。

补偿手段恰好三种，都对应上面的公式：

| 手段 | 作用在公式的哪里 | 说明 |
|---|---|---|
| **减少同步调用** | 减少串联项 | 能异步的异步（消息）、能合并的合并、能并行的并行（并行之后该环节按**并联**算，不再继续相乘） |
| **关键节点冗余** | 把单项从 A 抬到 1-(1-A)^n | 多实例 + 负载均衡 + 自动摘除 |
| **降级切断依赖** | **把串联变成可选** | 这是降级真正的架构含义 |

**第三条值得单独强调**：降级不只是"少返回几个字段"，而是**改变调用拓扑**。一个非关键的推荐服务挂掉时，如果调用方写好兜底，那这个因子在可用性公式里就从 `A` 变成了 `1`——**降级是把"必须"变成"可选"，这才是它能提升可用性的原因**。（应用层熔断与降级的实现见 [服务容错](/java/spring/spring-cloud/resilience)；防护链路的落地视角见[容量测算与压测方案](/projects/property-saas/capacity-and-perf/#protection)。）

## 六、故障域：冗余只对「独立故障」有效 {#fault-domain}

并联公式里有一个容易被跳过的前提：**故障相互独立**。如果两个实例挂在同一个故障源下，它们就不是两个独立的因子，而是同一个——**冗余只在跨故障域时才有意义**。

| 层级 | 故障域 | 影响面 | 概率 |
|---|---|---|---|
| 进程 / 容器 | 单个实例 | 极小 | 高 |
| Pod / 部署单元 | 一组实例 | 小 | — |
| 节点 | 一台机器 | 该机所有实例 | 中 |
| 机架 / 交换机 | 一组机器 | 机架内全部 | 低 |
| 可用区（AZ） | 一个数据中心 | 该 AZ 全部 | 很低 |
| 地域（Region） | 一个城市 | 该地域全部 | 极低，但影响面最大 |
| 云厂商 | 一个供应商 | 全部 | 极低 |
| **依赖服务 / 团队** | 上下游 | 取决于依赖度 | **中，且最常被忽略** |

对齐关系一句话：**架构设计的本质，是让"冗余的边界"与"故障域的边界"一致。**

| 常见误解 | 为什么不成立 |
|---|---|
| 同一台机器起两个实例 | 故障域相同（同一内核、同一网卡、同一次 OOM Killer） |
| 同一个 AZ 内两个机房 | 云厂商的 AZ 内网络与存储是共享的，许多故障在 AZ 级别相关 |
| 同城双 AZ 能挡城市级故障 | 挡不住。城市级要异地 |
| 多副本但都在同一存储 | 存储挂了副本一起挂 |

还有一个**自造故障域**的概念特别值得记住：

> **发布是最常见的自造故障域。**

一次全量发布让所有实例同时重启、同时加载新配置、同时打满连接池——**它把一个"应该很小"的故障域人为放大到了全站**。这就是发布必须分批、必须先小流量验证、必须能回滚的原因（[发布与交付策略](/projects/property-saas/release-and-ops/)）。同一类的自造故障域还有：**同一份配置中心推送**、**同一个证书到期**、**同一个云账号欠费**、**同一个第三方密钥被限流**。

## 七、单点清单：单点不只是「机器」 {#single-point}

排查单点时，只问"这台机器挂了我还能服务吗"是不够的。完整的单点有五类：

| 类别 | 检查问题 | 常见答案（容易漏的） |
|---|---|---|
| **实例单点** | 某个实例挂了，流量会不会自动走掉？ | 摘除靠探针，探针配错就退化成单点 |
| **数据单点** | 主库挂了能切吗？切了多久？ | "配了主从" ≠ "能自动切"；切换要演练 |
| **配置/元单单点** | 配置中心、注册中心、网关挂了会怎样？ | **缓存兜底往往没配** → 配置中心抖动导致全站启动失败 |
| **依赖单点** | 第三方接口挂了，业务能降级到什么程度？ | 支付、短信、地图、对象存储、CDN、DNS 都是外部单点 |
| **流程与人单点** | 只有一个人会操作切换吗？半夜谁有权限？ | **文档过期、权限不在值班人手上**是演练最常暴露的问题 |

用法上有个小技巧：**清单里每一行不只写"有没有单点"，还要写"失效时的表现"**。例如"注册中心：挂了之后新实例无法注册，但**已有调用因为本地缓存可以继续**，表现为"发布时扩容失败"而不是"全站不可用"。——**只标了风险没标表现，等于没排查**。

## 八、目标怎么分下去 {#budget}

自上而下拆解，避免"所有服务都许愿 99.99%"：

```text
入口 / 网关                        99.99%
  ├── 核心链路（下单、支付、门禁）   99.99%    ← 与入口同档，因为它决定了入口
  ├── 一般功能（查询、列表、详情）   99.9%     ← 可有降级路径
  │     └── 依赖的非核心服务          99.5%     ← 挂了只影响局部功能
  └── 报表 / 批量 / 导出             99%       ← 允许排队与延后
```

两条判据：

- **内部服务的等级不必高于入口**。入口只承诺 99.99%，把内部某个服务做成 99.999% 是纯粹的浪费——**预算要花在串联链路上最短的那块板，而不是最亮的那块**。
- **降级路径的可用性要单独算**。B 档功能的真实可用性 = 正常路径可用率 + 降级路径可用率。**如果降级路径从没演练过，它的可用性应当记为 0**——这是让"我们有降级方案"这句话变得诚实的最简单办法。

## 九、常见坑 {#pitfalls}

| 坑 | 正确认识 |
|---|---|
| 承诺高于依赖的 SLA | 上限由最弱的依赖决定。要么降低承诺，要么给依赖配降级路径 |
| 只优化 MTBF | MTTR 才是多数团队的性价比杠杆，且拆成"发现/定位/恢复"三段更好下手 |
| 用平均值掩盖长尾 | 52 分钟集中挂一次与 52 次 1 分钟抖动，用户的痛感完全不同 |
| 冗余不跨故障域 | 同机房、同 AZ 的"双活"不是双活 |
| 把"有备份"当"能恢复" | 未实测恢复时间的 RTO 是书面数字 |
| 忽略"人"这一段 | 半夜能不能爬起来、有没有权限，都在 MTTR 里 |
| 一次全量发布 | 发布是最常见的自造故障域，必须分批 + 可回滚 |
| 所有服务都定 99.99% | 预算要花在最短的板上；内部高于入口是浪费 |

## 面试口径 {#interview}

- **几个 9 的量级**：99.9% 年停 8.76 小时、99.99% 年停 52.6 分钟、99.999% 年停 5.26 分钟。**每加一个 9，成本不是线性增长**，从 99.99% 到 99.999% 的跳变来自"多机房 + 消除全部人工环节 + 依赖也必须同档"。
- **可用性上限**：由最弱依赖决定。所以"要不要做五个 9"先看依赖清单，而不是先看机器数量。
- **可用性算式**：`MTBF / (MTBF + MTTR)`。**降低 MTTR 通常更划算**，且 MTTR = 发现 + 定位 + 恢复，三段独立优化；其中"发现时间"常是最大的一段。
- **口径**：同一个 99.99% 可以按时间、按请求、按用户算出不同结果。SLA 必须写清**维护窗口算不算、降级期怎么算、统计窗口多长、单次中断是否设上限**。
- **RTO 与 RPO**：RPO 由复制方式决定、RTO 由恢复方式决定，两者独立分级。**成本从"异地异步"到"同城同步"是跳变而非渐变**（引入跨城延迟与多数派）。
- **为什么微服务化会降低可用性**：串联可用性是**乘法**。补偿手段三条——减少同步调用（减少因子）、冗余（`1-(1-A)^n`）、**降级（把因子从 A 变成 1）**。降级的架构含义是**改变调用拓扑**。
- **冗余的前提**：故障必须**跨故障域且相互独立**。同机、同 AZ 的"两个实例"不是冗余。**发布是最常见的自造故障域**。
- **单点识别**：实例 / 数据 / 配置元单 / 依赖 / 流程与人，五类。清单里要写"失效时的表现"，不写等于没排查。
- **延伸**：故障怎么检测、切换怎么做见[冗余与故障转移](/high-availability/redundancy-failover)；跨机房方案见[多机房架构](/high-availability/multi-datacenter)；"目标是否真的达成"靠[混沌与演练](/high-availability/chaos-drills)验证。
