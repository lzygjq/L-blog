# 多机房架构：从主备到单元化

如果只允许留一句话，应该是这句：

> **多机房难的不是"多部署一套"，而是"数据怎么写"。**

应用层是无状态的，多部署一套就是复制粘贴；数据层是有状态的，写只能有一个落点、复制有延迟、冲突要解决。所以这一篇的绝大部分篇幅都在讲数据，而不是讲机房。

## 一、六代拓扑：每一代在解决上一代的什么 {#generations}

把业界方案按"数据同步的边界"排列，会发现它是一条很清晰的演进线：

| 代 | 拓扑 | 解决了什么 | 遗留问题 | 典型 RTO / RPO |
|---|---|---|---|---|
| 1 | **单机房** | — | 机房级故障 = 全站不可用 | — |
| 2 | **冷备 / 定期备份** | 数据不会整体丢 | 恢复要人工数小时，业务停摆 | RTO 小时级 / RPO 至上次备份 |
| 3 | **主备热备**（同城） | 备端数据持续同步，可切换 | **备端平时不承载业务 → 没验证过的切换等于没有切换**；切换多为人工 | RTO 分钟级 / RPO≈0~秒 |
| 4 | **同城双活** | 两个可用区同时承载，流量可漂移 | 写仍是单点（或需双写）；AZ 全挂依然不可用 | RTO 秒级 / RPO 0（同步复制） |
| 5 | **两地三中心** | 城市级故障可恢复（两地 = 同城两中心 + 异地一中心） | 异地是异步 → RPO>0；异地不承载 → 又回到"没验证" | 同城秒级 / 异地 RTO 小时级 |
| 6 | **异地多活 / 单元化** | 多地同时承载、就近接入、城市级故障基本无感 | 数据最终一致，架构与成本最高 | 秒级 / 单元内≈0 |

**读法**：每一代的推进，都是把"数据同步的边界"往外推一层；而**每往外推一层，一致性代价就上升一档**——冷备（丢一段数据）→ 热备（同步但备端闲置）→ 同城双活（同步复制，延迟 +2ms 量级）→ 异地多活（放弃强一致）。

所以选择不是"越新越好"，而是"**你能接受多大的 RPO，就选到哪一代**"。

## 二、难点只有一个：数据怎么写 {#data-first}

把"多机房要做的事"列全，会发现其中大部分都是数据相关：

```text
数据复制方式（同步 / 半同步 / 异步）
数据切换与一致性（切到哪、切了丢什么、怎么校验）
冲突解决（两端都写了同一条数据怎么办）
跨机房事务（一个业务动作要改两地数据）
跨机房延迟（能不能放到同步链路里）
数据迁移与回填（新机房上线时怎么灌数据、怎么校验）
双跑校验（切换前后要不要比对、怎么比对）
```

而应用层的事情相对简单：镜像分发、配置分环境、多套部署、流量调度。**这也是为什么"多机房方案评审"通常 80% 的时间在讨论数据库。**

## 三、物理定律是硬边界：跨城复制的延迟账 {#physics}

先算一笔账。光纤中信号速度约为真空光速的 2/3（约 20 万 km/s），而实际链路有绕路与设备转发开销：

| 链路 | 直线距离 | 理论单向最小 | 实际常见 RTT |
|---|---|---|---|
| 同城两可用区 | 数十 km | < 0.2 ms | **< 2 ms** |
| 深圳 ↔ 上海 | ≈ 1200 km | ≈ 6 ms | 25 ~ 35 ms |
| 深圳 ↔ 北京 | ≈ 1950 km | ≈ 10 ms | 35 ~ 45 ms |
| 华南 ↔ 新加坡 | ≈ 2600 km | ≈ 13 ms | 50 ~ 70 ms |
| 跨太平洋 | ≈ 10000 km+ | ≈ 50 ms | 150 ~ 250 ms |

同步复制意味着**每一次写都要等远端确认**，于是写延迟变成：

```text
写延迟 = 本地处理 + 跨机房 RTT + 远端落盘确认
```

推论非常直接：

| 场景 | 可行性 |
|---|---|
| **同城两 AZ 同步复制** | ✅ 可行。写延迟增加 2ms 量级，多数在线业务可以接受 |
| **跨城同步复制** | ❌ 通常不可行。每次都抬高 30ms+，写密集业务（下单、扣减、日志）直接不可接受 |
| **跨城异步复制** | ✅ 异地多活的唯一选择。代价是 RPO>0，且要处理冲突 |
| **跨城同步用于"低频写"** | ⚠️ 有例外：配置、元数据这类写频率极低的场景可以接受（判据：**写频率 × 延迟容忍度**） |

还有一条与[共识协议](/distributed/consensus#pitfalls)重合的推论：**如果让 Raft 这类多数派协议跨城部署，写延迟由最慢的节点决定**，且跨城抖动容易触发"选举风暴"。所以**多数派应落在同城低延迟区**，异地只部署非投票副本或异步备。

> **一句话总结这一节**：异地多活只能异步/最终一致，**这不是技术选型，是物理定律**。任何号称"跨城强一致"的方案，要么写延迟不可接受，要么"强一致"的其实是另一套东西。

## 四、同城双活：三个必须回答的问题 {#same-city}

同城双活（双 AZ 同时承载业务）必须先回答三个问题，缺一个都会在上线后暴露：

### 4.1 写在哪

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **单写** | 只有一端接受写，另一端只读 | 最简单可靠，逻辑与单机房一致 | 切换写端 = 一次主备切换（分钟级）；写端是逻辑单点 |
| **双写** | 两端都接受写，按规则分流 | 写能力翻倍、就近写延迟低 | **必须解决冲突**；跨端一致性难以保证 |
| **分片写** | 按业务键（用户/租户）路由，各端只写自己那部分 | **逻辑最干净**，无冲突 | 需要接入层路由与数据分片能力（≈ 同城版单元化） |

### 4.2 数据怎么同步

| 方式 | RPO | 写延迟 | 适用 |
|---|---|---|---|
| 同步复制 | ≈ 0 | +RTT（同城可接受） | 资金、交易、核心数据 |
| 半同步（至少一份确认） | ≈ 0 | +1 个 RTT | 通用推荐 |
| 异步复制 | > 0（= 复制延迟） | 无额外开销 | 非核心、异地 |

### 4.3 故障时怎么办

必须明确四件事：**判定标准**（什么信号算故障，多快算）、**切流机制**（谁把流量搬过去）、**切换前校验**（数据延迟是否可接受、复制位点是否跟上）、**回切流程**（怎么切回来、要不要比对）。

> **「同城双活」这个词被严重滥用。** 真正的双活要同时满足三条：
> ① 两端都在承载生产流量；
> ② **任一端故障后，另一端能接管全量**（所以备端容量必须按 100% 规划，而不是 50%）；
> ③ 切换有自动化与演练记录。
> 只满足第一条的，叫"双机房部署"或"双写"，**它的切换从未被验证过**。

## 五、异地多活与单元化：让请求在一个单元内闭环 {#units}

异地多活的核心不是"多地部署"，而是**单元化（SET 化）**——把系统按业务键切成若干个**自包含**的单元，每个单元只服务一部分用户。

```text
              ┌───────────── 接入层（按 uid 路由）─────────────┐
              │   DNS/GSLB 就近解析 + 网关按 uid 取模路由      │
              └───────┬──────────────┬──────────────┬─────────┘
                      │              │              │
                 ┌────▼────┐    ┌────▼────┐    ┌────▼────┐
                 │ 单元 A  │    │ 单元 B  │    │ 单元 C  │
                 │ 华南    │    │ 华东    │    │ 华北    │
                 │         │    │         │    │         │
                 │ 网关    │    │ 网关    │    │ 网关    │
                 │ 服务    │    │ 服务    │    │ 服务    │
                 │ 数据库  │    │ 数据库  │    │ 数据库  │
                 │ 缓存/MQ │    │ 缓存/MQ │    │ 缓存/MQ │
                 └────┬────┘    └────┬────┘    └────┬────┘
                      │              │              │
                      └────── 跨单元异步同步（消息）──────┘
                             最终一致 + 幂等去重
```

四步走：

**① 分片维度选择。** 必须按"**用户 / 租户**"切，因为它是业务请求的自然边界——一个用户的所有数据（他的订单、账单、门禁记录）都在同一单元。**不能按订单号切**，否则"查我的订单列表"这类请求必然跨单元。

**② 路由。** 分片在**入口**就完成：DNS/GSLB 就近 → 单元网关 → 按 uid 取模路由到单元。**一旦进入单元，单元内调用不再跨单元**。路由表要能被配置中心动态下发（扩容新单元时不必改客户端）。

**③ 数据自包含。** 每个单元拥有自己完整的库表；全局性的数据（字典、配置、商品目录）用"各单元只读副本 + 异步同步"或"只写主单元、其他单元消费变更"。

**④ 最终一致。** 跨单元的写走消息 + 幂等去重；冲突按策略解决。

**本节的判据（也是全篇最值钱的一句）**：

> **「这一次用户请求，能不能只在一个单元内完成？」**
> 能 → 单元化可行。
> 不能 → 先把那个跨单元调用改成**异步**或**本地化**（数据冗余一份到本单元），否则不要做单元化——**那只是把单机房内部的耦合，原样搬成了跨机房耦合，延迟与故障面都被放大。**

冲突解决的手段与它们的代价：

| 手段 | 做法 | 适用 |
|---|---|---|
| **规避冲突（首选）** | 设计上让同一份数据只有一个单元可写 | 最优解——**最好的冲突解决是没有冲突** |
| 时间戳 / 版本号（LWW） | 后写覆盖先写 | 可容忍短暂不一致的数据（如用户资料） |
| 业务优先级 | 按业务规则裁决（如"归属单元优先"） | 有明确业务语义时 |
| 全局序号 | 用共识或全局发号器定序 | 需要确定性顺序，代价高 |
| 人工介入 | 冲突落表、人工处理 | 低频高价值场景（对账差异） |

单元化的成本清单（比技术方案更容易被低估）：

```text
中间件都要支持分片路由（MQ、缓存、任务调度、分布式锁）
配置要按单元隔离（一个单元配错不能影响其他单元）
发布要按单元分批（先小单元灰度，再全面推进）
监控与日志要按单元维度聚合（否则定位不出"是哪个单元的问题"）
新单元上线是一次项目，而不是一次扩容（数据初始化 + 校验 + 路由切换）
```

## 六、流量调度与切流：DNS 切换为什么不像想的那么快 {#traffic}

先看调度的层级，以及各自适用的场景：

| 层级 | 机制 | 生效粒度 | 适用 |
|---|---|---|---|
| 客户端 | SDK 就近接入、客户端负载均衡 | 快（连接级） | 自研客户端、App |
| DNS | 多 A 记录 / GSLB 按地域解析 | **慢且不可控** | 低频、需秒级以下精度的场景不适用 |
| Anycast + BGP | 同一 IP 多地宣告，路由收敛 | 较快（分钟级） | 接入层、DNS 本身、CDN |
| 四层 LB | VIP + 健康检查 | 秒级 | 同城切换 |
| 七层网关 | 按 Header / 比例 / 租户分流 | 秒级，最灵活 | 灰度、按租户切流 |

**DNS 切换的真相**（这一条几乎每次架构评审都会被误解）：

```text
实际生效时间 = TTL + 各级缓存 + 已建连接的存续

① TTL 只约束"能缓存多久"，不能清空别人的缓存
② 递归 DNS、运营商 DNS、客户端 OS/JVM 都有自己的缓存
③ 【长连接与连接池根本不重新解析 DNS】——TCP 建好之后与服务端 IP 绑定
④ 因此实际生效时间通常是分钟到小时级，且不可控
```

结论有两条：**DNS 适合"切换频率低、允许分钟级生效"的场景；要求秒级必须靠应用层或网关层调度。** 而长连接的存在意味着"改了 DNS"不等于"流量真的切走了"——必须配合主动断连或客户端重连策略（这也是服务网格与客户端负载均衡的价值所在）。

**切流三态**（顺序不能颠倒）：

| 状态 | 做什么 | 判定信号 | 恢复条件 |
|---|---|---|---|
| **正常** | 全量功能 | — | — |
| **降级** | 只保核心功能，关掉非核心接口 | 容量不足、依赖异常、指标越线 | 指标回到阈值内并稳定一段时间 |
| **隔离** | 把故障单元摘除（只读或完全停用） | 单元级故障确认 | 故障单元恢复 + 数据校验通过 |

**顺序判据：先降级、再摘除、最后切流。** 切流是最后手段而不是第一手段——它的副作用（备端容量是否够、数据是否已同步、回切成本）必须写进预案。而**回切往往比切过去更难**：数据已经在新端写入，要同步回去还要比对校验，**许多事故的"二次伤害"就发生在回切阶段**。

## 七、代价与决策：要不要多活 {#cost}

| 业务规模 / 要求 | 建议方案 | 理由 |
|---|---|---|
| 小系统、停机可接受 | 备份 + 快速重建（脚本化恢复） | 多活的长期成本远高于停机损失 |
| 中型、要求分钟级恢复 | **同城双活（或同城热备）** | 性价比拐点，覆盖绝大多数机房级故障 |
| 大型、要求城市级容灾 | **两地三中心** | 异地必须存在，但要接受 RPO>0 |
| 超大 / 用户分布广 / 就近接入 | **单元化多活** | 收益来自"延迟 + 容灾"双份，否则不值得 |

**成本的大头不是机器，而是"数据一致性 + 发布复杂度 + 长期人力"。** 这句话的实操含义是：**多活的收益是"少停几十分钟"，成本是"长期多养一个方向的人与复杂度"**——用数字算，不要用"高可用"三个字说服自己。

## 八、常见坑 {#pitfalls}

| 坑 | 正确认识 |
|---|---|
| 备端按 50% 容量规划 | 接管时接不住全量，等于没有双活。**双活的前提是任一端能承载 100%** |
| 只有一端承载流量也叫"双活" | 那是双机房部署，切换从未验证 |
| 跨城同步复制 | 物理延迟决定写延迟，写密集业务不可行 |
| 用 DNS 做秒级切换 | TTL ≠ 生效时间；**长连接不会重新解析 DNS** |
| 跨单元调用留在同步链路 | 单元化失效——只是把耦合搬到跨机房，延迟与故障面双双放大 |
| 没有回切预案 | 回切是二次事故高发区，且需要数据校验 |
| 双写不做冲突解决 | 冲突迟早出现，且事后难以回溯判定 |
| 跨机房调用没有约束 | 应对跨机房调用设"白名单 + 监控 + 告警"，否则延迟与故障面会悄悄扩散 |
| 两地三中心的"异地"从没切过 | 与第 3 代同样的病——**没验证过 = 没有** |

## 面试口径 {#interview}

- **多机房的难点是什么**：**数据怎么写**。应用无状态容易复制，数据有状态——写只能有一个落点、复制有延迟、冲突要解决。多机房 80% 的复杂度在数据层。
- **为什么异地多活只能最终一致**：物理定律。跨城 RTT 30ms 量级、跨洲 150ms+，**同步复制会把每次写都抬高一个 RTT**。同城两 AZ（<2ms）同步复制可行，跨城不可行。例外是写频率极低的配置/元数据类。
- **六代拓扑**：单机房 → 冷备 → 主备热备 → 同城双活 → 两地三中心 → 异地多活/单元化。**每往外推一层，一致性代价上升一档**，选择取决于能接受多大 RPO。
- **同城双活要回答的三个问题**：写在哪（单写 / 双写 / 分片写）、数据怎么同步（同步 / 半同步 / 异步）、故障时怎么办（判定、切流、校验、回切）。
- **"双活"的三条判据**：两端都承载流量、**任一端能接管全量**、切换有自动化与演练。只满足第一条的是"双机房部署"。
- **单元化的核心与判据**：按**用户/租户**分片、入口路由、单元内数据自包含、跨单元异步最终一致。判据是「**这次请求能否只在一个单元内完成**」；不能闭环就不该做单元化。**最好的冲突解决是没有冲突**（设计上让一份数据只有一个单元可写）。
- **DNS 切换**：实际生效时间 = TTL + 各级缓存 + **已建长连接（不重新解析）**，通常分钟到小时级且不可控。秒级切换必须靠应用层/网关层。
- **切流三态**：正常 → 降级 → 隔离（摘除），**顺序不可颠倒，切流是最后手段**；**回切比切过去更难**，预案必须包含。
- **要不要做多活**：用数字算。收益是"少停几十分钟"，成本是"长期人力 + 复杂度 + 备端 100% 容量"。
- **延伸**：目标与 RTO/RPO 的定义见[可用性目标](/high-availability/availability-targets)；切换机制与 fencing 见[冗余与故障转移](/high-availability/redundancy-failover)；这些方案是否真的有效，只能靠[混沌与演练](/high-availability/chaos-drills)验证。
