# 冗余与故障转移：难的是「怎么判断对方死了」

故障转移（failover）听起来是个很朴素的动作：备机顶上。但把所有翻过车的方案摊开看，**出事的从来不是"怎么顶上"，而是三件事**：

1. **它真的死了吗**——检测；
2. **它会不会"诈尸"**——隔离与 fencing；
3. **顶上之后数据对不对**——一致性、幂等、重试。

这三件事恰好对应本节的前半部分，而后半部分讲的是**被转移打乱的调用链怎么收尾**（超时、重试、幂等），以及**该自动还是该人工**。

## 一、故障检测：判定延迟与误判之间的取舍 {#detection}

检测机制只有三种，工程上把它们组合使用：

| 机制 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **心跳**（被检测方主动上报） | 被检测方周期性上报，超时未到即认为异常 | 实现简单、开销可控 | 网络抖动会造成误判 |
| **主动探测**（检测方发起） | 定时请求健康接口 / TCP 探测 | 判断的是"能不能服务"而非"进程还在不在" | 探测本身也会超时，且要防止探测流量过大 |
| **第三方仲裁**（旁观者判定） | 由独立组件（注册中心、控制面）统一判定 | 避免"双方都以为对方死了" | 仲裁者自身不能是单点 |

真正要设计的是三个参数——**间隔、单次超时、连续失败次数**，它们共同决定判定延迟：

```text
判定延迟 ≈ 探测间隔 × 失败次数 + 单次超时
例：间隔 2s、连续 3 次失败、单次超时 1s  →  最快 7s 判定为故障
```

于是就有两个方向的错，而且**两个方向的性质完全不同**：

| 调得不合适 | 后果 | 性质 |
|---|---|---|
| 太灵敏（间隔短、次数少） | **误判** → 双主 → 数据被两边同时写 | **数据级破坏，难以回溯** |
| 太迟钝（间隔长、次数多） | 真正的故障要等很久才切换 → 长时间不可用 | 可用性损失，可量化 |

**判据：宁可慢 10 秒，也不要错一次。** 因为"多停 10 秒"在可用性账本上是可计算的损失，而"误切一次"可能造成数据分叉、对账差异、人工修复——**它的代价不在可用性里，在业务损失里**。这条取向决定了后面的所有设计（多数派仲裁、fencing、人工闸门）都倾向于"保守"。

> 一个实用细节：**探测要探"关键依赖"，但关键依赖抖动时不能连锁误判**。所以健康检查通常做两级——`live` 只表明进程没死（不查依赖），`ready` 才检查依赖。原因见[第四节](#graceful)。

## 二、误判的代价：脑裂与 fencing {#split-brain}

网络分区（或极端 GC / 假死）时，两边都可能认为对方已死、都升自己为主，这就是**脑裂**。防御要分三层，而且**这三层解决的不是同一个问题**：

| 层次 | 手段 | 解决什么 | 不解决什么 |
|---|---|---|---|
| **仲裁** | 多数派（quorum）、租约（lease）、法定票数 | **谁是主**——只有拿到多数票的一方能提供服务 | 旧的写请求可能还在路上 |
| **隔离** | fencing token / epoch / term、STONITH（强制下线） | **旧主还能不能写**——存储侧拒绝携带旧令牌的写 | 需要存储侧配合校验 |
| **恢复** | 数据比对、回补、对账 | 已经分叉的数据怎么收拾 | 成本高、可能丢数据 |

```text
网络分区发生（左边 2 台、右边 1 台，共 3 副本）

  左分区 [A][B]          右分区 [C]
      │                     │
      ├─ A/B 能凑多数派 → A 继续做主，正常服务
      │
      └─────────────────────┴─ C 只有 1 票 = 少数派 → 【主动拒绝写】
                                  （宁可不可用，不失一致）

假死场景（C 进程 hang 住但没崩，网络仍通）

  左分区 [A][B]          右分区 [C：hang]
      │                     │
      ├─ A/B 凑多数派 → A 升主，开始接受写
      │                     │
      │                     └─ C 在收到请求【时才可能醒】
      │                          → 若存储不认识"新主"，C 会照写
      └───────── 于是两边同时写 ─────────┘
                 ↑ 仲裁挡不住，只有 fencing 能挡
```

**这张图的结论非常值钱：仲裁解决"谁是主"，fencing 解决"旧主还在写"。** 只做仲裁不做 fencing 的系统，在"假死"（进程 hang 而非 crash——长 GC、IO 阻塞、死锁都会这样）场景下依然双写。这正是很多自研高可用方案在上线后出问题的地方。

各系统里的对应实现：

| 系统 | 仲裁 | 隔离/防护 |
|---|---|---|
| Raft 类（etcd、Kafka KRaft） | term + 多数派投票 | **term 号**：携带旧 term 的写被拒绝（[共识协议](/distributed/consensus#split-brain)） |
| Redis Sentinel | `quorum` 判定客观下线 | `min-replicas-to-write`（副本不够时旧主拒写） |
| MySQL 主从 | 多数派判定 / 半同步 ACK | `super_read_only`、切换前先降级旧主、GTID 校验 |
| K8s | node lease + 心跳 | 控制面用 `resourceVersion` 做乐观锁 |
| 传统集群（Pacemaker 等） | 心跳 + 法定票 | **STONITH**：直接把旧主电源断掉/封网 |

> **STONITH 为什么叫"爆头"**：它的思路是"既然不确定旧主会不会写，那就让它物理上写不了"——**用最暴力的手段换取最确定的结果**。反过来看，如果你的切换方案里没有任何"让旧主绝对写不了"的机制，那就只能依赖"旧主恰好不会醒"这个假设。

## 三、无状态与有状态：转移难度的分水岭 {#stateful}

| | 无状态服务 | 有状态服务 |
|---|---|---|
| 转移动作 | 在其他实例上重启 / 直接改用另一个实例 | 选主 → 数据同步 → 提供服务 |
| 转移时间 | 秒级（启动时间） | **检测 + 选主 + 追赶** |
| 数据风险 | 无 | 有（丢失窗口、分叉） |
| 难点 | 容量是否够、启动是否快 | **数据一致性 + 追赶时长** |

关键结论：**有状态服务的故障转移时间 ∝ 需要同步的数据量**。所以：

```text
副本数据量 1 GB   → 追赶可能几秒
副本数据量 500 GB → 追赶可能几十分钟
```

**这正是分片（sharding）除了"写扩展"之外的第二个价值：把每片的数据量压小，恢复时间随之变短。**（[分布式理论 · 数据分布](/distributed/data-partition)）

还有一类夹在中间的"**半状态**"服务，最典型的是会话与本地缓存：

| 做法 | 转移时表现 | 代价 |
|---|---|---|
| 会话粘滞（按用户固定到某实例） | 该实例挂掉 → **该用户掉线重登** | 实现简单，但故障对用户可见 |
| 会话外置（Redis / 共享存储） | 转移无感 | **引入新的单点**——共享存储必须自己也是高可用的 |
| 本地缓存 | 转移后缓存冷启动 → **数据库瞬时压力上升** | 常见"重启即雪崩"的根因；要配预热或限流 |

## 四、优雅停机：K8s 里最常见的一类「发布即故障」 {#graceful}

这一类故障的特征很好认：**发布期间偶发 502 / 连接重置，发布结束自动恢复，监控上看不到持续性异常**。根因几乎总是"停机时序"与"endpoint 摘除"没对齐：

```text
【错误时序】滚动发布时丢请求

① kubelet 发 SIGTERM
② 进程立即退出、停止监听
③ 但 Service endpoints 的摘除【还没传播到】kube-proxy / Ingress / 客户端
④ 这段时间内仍有人在往这个 IP 转发 → 连接被拒（502 / connection reset）

【正确时序】

① 先让 readiness 失败（或 preStop 里 sleep），使实例【先被摘出流量】
② 等待摘除传播完成（kube-proxy / Ingress / 客户端 DNS 缓存 / 连接池）
③ 再停止接收新连接（关闭监听 / 从 LB 注销）
④ 处理完在途请求（graceful shutdown，有超时上限）
⑤ 超时兜底后强制退出
```

对应的配置要点（`terminationGracePeriodSeconds` 必须容得下整个第 ②~④ 步）：

```yaml
# 关键字段与其含义
spec:
  terminationGracePeriodSeconds: 60     # 必须 ≥ preStop 等待 + 最长请求处理时间
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]   # 留出 endpoint 摘除的传播时间
      readinessProbe:                     # 摘流量的开关
        httpGet: { path: /actuator/health/readiness, port: 8080 }
        periodSeconds: 2
        failureThreshold: 2
      livenessProbe:                      # 只探"进程是否死了"
        httpGet: { path: /actuator/health/liveness, port: 8080 }
      startupProbe:                       # 慢启动应用的保护
        httpGet: { path: /actuator/health/liveness, port: 8080 }
        failureThreshold: 30
        periodSeconds: 5
```

```properties
# Spring Boot 侧配套：接住 SIGTERM，处理完在途请求再退出
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
```

**探针的三个判据**（这一组设计错误造成的故障比时序问题更多）：

| 探针 | 只该探什么 | 常见错误 | 错误后果 |
|---|---|---|---|
| `livenessProbe` | **进程是否还活着** | 探数据库/下游可用性 | 依赖抖动 → 全部实例被重启 → **自己制造雪崩** |
| `readinessProbe` | **现在能不能服务**（含关键依赖） | 只探端口 | 依赖挂了还在收流量，错误率飙升 |
| `startupProbe` | 启动是否完成 | 不配，用 liveness 兼 | 慢启动应用被反复重启，永远起不来 |

> **「liveness 探依赖」是本节最值得记住的一条红线。** 它的逻辑是自噬的：下游挂了 → 所有实例 liveness 失败 → K8s 重启所有实例 → 重启期间下游压力更大、连接风暴 → 故障从"局部"升级为"全局"。**liveness 的职责只有一个：这个进程已经无药可救了，重启它。**

## 五、超时与重试：重试是故障放大器 {#timeout-retry}

故障转移会打乱调用链，而调用链上有两个参数一旦配错，就会把"局部故障"变成"全局故障"。

**① 超时预算（timeout budget）**：调用链上各层的超时必须逐层收窄，且总和不超入口。

```text
网关 3s
  └── 服务 A 2s
        └── 服务 B 1s
              └── 数据库 500ms

判据：下游超时 < 上游超时（留出网络与序列化开销）
反例：上游 1s、下游 3s → 上游早已放弃返回错误，
      下游还在跑 → 资源被占用 + 上游重试叠加 → 雪崩
```

**② 重试的放大效应**：一次远端故障会引来成倍的流量。

```text
每层重试 3 次、链路 3 层 → 最坏情况 3 × 3 × 3 = 27 倍流量打向故障节点
```

所以重试必须遵守一组约束：

| 约束 | 具体做法 |
|---|---|
| **只重试幂等操作** | 查询可以重试；扣款、下单这类必须靠幂等键保护（见下节） |
| **只重试可恢复错误** | 连接失败、超时、5xx 可重试；**参数错误、业务拒绝、4xx 不重试**（重试也不会成功） |
| **指数退避 + 抖动** | 退避避免持续冲击；**抖动（jitter）避免所有客户端同步重试**（同一秒齐冲） |
| **限制重试预算** | 如"重试请求不超过总请求的 10%"，超了就快速失败 |
| **只在一层重试** | "最外层做一次"优于"每层都做"，避免放大 |
| **配合熔断** | 连续失败直接快速失败，把重试挡在门外（[服务容错](/java/spring/spring-cloud/resilience)） |
| **重试要有时间上限** | 重试时长不能超过上游的超时预算，否则重试的意义为零 |

## 六、幂等：故障转移必然带来重复请求 {#idempotent}

一次切换、一次重试、一次消息重投，都会让**同一个请求被执行两次**。所以幂等不是"优化"，是**故障转移的前置条件**。

常见的错误做法与正确做法：

| 做法 | 为什么不够 |
|---|---|
| "先查再写" | **check-then-act 有并发窗口**：两个请求同时查到"不存在"，然后都写 |
| 用时间戳去重 | 同毫秒并发、时钟回拨都会失效 |
| 只在应用层去重 | 多实例 + 负载均衡下内存去重无效，必须落到共享存储 |

**幂等三件套**（三层都要有，任何一层都不能单独兜住）：

```text
① 幂等键：业务侧生成全局唯一号（订单号 / 请求 ID / 支付流水号）
         由调用方携带，服务端以此为准
② 唯一索引：数据库层最后一层兜底 —— 并发写入时由 DB 保证只有一个成功
         捕获唯一约束冲突 → 按"已处理"返回，而不是报错
③ 状态机前置校验：只允许特定前置状态的流转
         「已支付」不能再被「支付成功」推进一次
```

拿支付回调举例：**重复回调是常态而非异常**——第三方在没收到确认时会不断重试，网络抖动也会造成重复投递。所以回调接口的正确写法是"**按流水号幂等 + 状态机校验 + 唯一索引兜底**"，而不是"希望它只来一次"。（这条链路在项目里的落地见[核心业务链路](/projects/property-saas/core-business/)。）

消息场景同理：投递语义通常是"至少一次"，**重复消费是设计前提**。做法是在消费端落去重表，或把幂等键作为业务表唯一索引的一部分。

## 七、切换的三种触发方式与人工闸门 {#switch-modes}

| 触发方式 | 谁决定 | 适用动作 | 理由 |
|---|---|---|---|
| **被动（自动）** | 系统按探针/指标判定 | **保护性动作**：限流、降级非核心、摘除坏实例、熔断 | 快速止血，错了也容易恢复 |
| **主动（人工）** | 值班长按 Runbook 决策 | **有数据后果的动作**：切主、切机房、封禁、数据修复 | 判断指标本身可能被故障污染（监控挂了、分区时判断不可信） |
| **条件式（预案）** | 预先写死的判定条件 | 明确且可逆的切换（如"主库不可用超过 30 秒且多数派达成"） | 介于两者之间，必须有自动中止 |

**判据：自动适合"保护性动作"，人工适合"有数据后果的动作"。** 这条界线划错的代价是双向的——该自动的做成人工，MTTR 里多出"等人醒来"的半小时；该人工的做成自动，一次误判就造成数据分叉。

人工闸门要成立，必须同时具备三件事：

```text
① 谁有权决策 —— 明确到岗（值班长），不是"看谁在群里"
② 依据什么决策 —— Runbook 里的判定树（什么信号 → 什么动作 → 预期结果）
③ 谁来执行 —— 【人只按按钮，不由人手敲命令】
                执行脚本必须预先写好并演练过（含回滚）
```

> 演练里最常暴露的问题恰好是第 ③ 条：**值班人没有执行权限，或脚本从来没人跑过**。这类问题的修复成本极低、收益极高，但只有演练能发现（[混沌与演练](/high-availability/chaos-drills)）。

## 八、常见坑 {#pitfalls}

| 坑 | 正确认识 |
|---|---|
| 只做仲裁不做 fencing | "假死"场景下依然双写。仲裁管"谁是主"，fencing 管"旧主还能不能写" |
| `liveness` 探依赖 | 依赖抖动 → 全量重启 → **自己制造雪崩**。liveness 只探进程 |
| 重试不设上限、每层都重试 | 最坏放大到 2^n 倍，把局部故障变成全局故障 |
| 超时逐层变长 | 上游放弃、下游还在跑，资源占用 + 重试叠加 |
| "先查再写"当幂等 | 并发窗口下必失效，必须靠唯一约束兜底 |
| 切换后不校验数据 | 不考虑数据位置/延迟的主从切换可能丢数据；切换前要看复制位点 |
| 备端容量按 50% 规划 | 双活失效时接不住全量（见[多机房架构](/high-availability/multi-datacenter#cost)） |
| 自动切换没有人工闸门 | 判断指标被污染时，自动切换会放大事故 |
| 切换没演练过 | **没验证过的切换等于没有切换** |

## 面试口径 {#interview}

- **故障转移最难的一步**：不是"备机顶上"，而是**怎么判断对方死了**。判定延迟 ≈ 间隔 × 失败次数 + 单次超时，且**宁可慢 10 秒也不可误判一次**——多停 10 秒是可用性损失，误切一次是数据级破坏。
- **脑裂怎么防**：三层——**仲裁**（多数派/租约，决定谁是主）、**fencing**（term/epoch/STONITH，阻止旧主继续写）、**恢复**（数据比对回补）。**只做仲裁不做 fencing，在"进程 hang 而非崩"的场景下依然双写。**
- **有状态服务切换为什么慢**：转移时间 = 检测 + 选主 + **数据追赶**，而追赶时长 ∝ 数据量。这也是分片除了写扩展之外的第二个价值——**把恢复时间压短**。
- **优雅停机**：先让 `readiness` 失败 → 等 endpoint 摘除传播 → 再停监听 → graceful shutdown 处理在途请求 → 超时兜底。`terminationGracePeriodSeconds` 必须 ≥ preStop 等待 + 最长请求处理时间。
- **探针设计**：`liveness` 只探进程（探依赖会造成**全量重启式雪崩**）；`readiness` 探"能不能服务"（含关键依赖）；`startupProbe` 保护慢启动应用。
- **超时预算**：各层超时逐层收窄，下游 < 上游。上游先放弃而下游还在跑，是资源泄漏与重试叠加的根源。
- **重试**：只重试**幂等**且**可恢复**的错误；指数退避 + 抖动；限制重试预算；只在一层重试；配合熔断。
- **幂等三件套**：幂等键（业务唯一号）+ **唯一索引兜底** + 状态机前置校验。"先查再写"因并发窗口不可靠。**重复回调、重复消费是常态**。
- **自动 vs 人工**：自动做保护性动作（限流/降级/摘除），人工做有数据后果的动作（切主/切机房）。人工闸门三要素：谁决策、依据什么（Runbook）、谁执行（**人按按钮，不敲命令**）。
