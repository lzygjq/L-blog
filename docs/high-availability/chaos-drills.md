# 混沌工程与故障演练：把「以为」变成「知道」

前面三篇讲的都是"应该怎么设计"。这一篇讲的是：**怎么知道设计真的有用。**

## 一、四个「以为」，和演练的唯一作用 {#why}

几乎所有"设计上高可用、实际上一击就倒"的系统，都栽在同样四个假设上：

| 我们以为 | 演练暴露的现实 |
|---|---|
| 自动切换会自动生效 | 探针配错、VIP 漂移不了、客户端不重连、连接池没刷新 → **自动切换从未真正跑过** |
| 监控会报警 | 告警规则没覆盖这个维度、通知发到了没人看的群、被其他告警淹没 |
| 预案有人会执行 | 只有一个人会、文档已过期、**权限不在值班人手上** |
| 容量够 | 备端按 50% 规划、连接池/线程池成为新瓶颈、缓存冷启动压垮数据库 |

推下去就是这一篇的核心命题：

> **演练不生产可用性，它生产"确定性"。**
> 而"没演练过的预案等于没有预案"——因为预案的价值不在文档里，在**执行它的那个人的手上**。

## 二、混沌工程五原则 {#principles}

混沌工程（Chaos Engineering）是一套方法论，业界公认的五条原则：

| 原则 | 含义 | 落地要点 |
|---|---|---|
| **① 建立稳态假设** | 先用可度量指标定义"正常" | 3~5 个核心指标 + 阈值。**没有稳态定义，就无法判断实验是否安全** |
| **② 多样化真实事件** | 不只是"杀进程" | 真实故障还有网络、磁盘、依赖、时钟、配置错误 |
| **③ 在生产环境运行** | 预发的流量与规模永远不同 | **最有争议也最关键**，但前提见下节 |
| **④ 持续自动化** | 季度手工拔线不是工程实践 | 要能按需、可重复地运行 |
| **⑤ 最小爆炸半径** | 从小范围开始 | 单实例 → 单服务 → 单 AZ，且有自动中止 |

第 ③ 条需要额外说明：**"在生产演练"是有前提的**——没有可观测性、没有中止能力、没有回滚手段时，生产实验就是事故。所以正确的做法不是"跳过生产"，而是**先满足前提，再从影子流量、单实例、小比例开始**。

## 三、前提条件：没有可观测性就是随机故障 {#prerequisites}

这一节是整篇最重要的一节，也是最容易被跳过的一节：

| 缺什么 | 会发生什么 |
|---|---|
| **可观测性** | 无法定义稳态、无法判断影响范围 → **等于在生产随机制造故障** |
| **自动中止（kill switch）** | 故障蔓延，实验变成事故 |
| **可恢复手段** | 只能靠人工抢修，演练成本不可控（越演越不敢演） |
| **Runbook** | 演练变成"现场发明流程"，不可复现、不可传承 |
| **明确责任人** | 没人有权喊停 → 止损被拖延 |

由此得到一条成熟度顺序（**倒过来做必出事**）：

```text
监控与可观测  →  预案与 Runbook  →  故障演练  →  混沌工程自动化
   ①                ②                ③              ④
```

① 与 ② 分别见[监控与可观测](/cloud-native/observability/)与[发布与交付策略](/projects/property-saas/release-and-ops/)（Runbook 与告警分级）；本篇讲 ③ 与 ④。

## 四、成熟度四级 {#maturity}

| 级别 | 特征 | 频率 | 产出 |
|---|---|---|---|
| **L1 手工演练** | 人肉拔线 / 杀进程 / 手工切流量，照着文档走 | 季度 | 发现第一批量级问题（往往是"根本切不过去"） |
| **L2 场景化演练** | 预定义故障场景 + 判定标准 + Runbook 驱动 | 月度 | 可复现的恢复流程、Runbook 版本化 |
| **L3 混沌平台** | 自动化注入、按需执行、有统计报告与实验库 | 按需/周 | 实验资产化、按服务维度评估韧性 |
| **L4 持续混沌** | 在生产常驻，小剂量持续注入 + 自动中止 | 持续 | 韧性成为常态指标，异常自动暴露 |

**重要提醒：L3 不是起点。** 前两级用**手工 + 脚本**就能拿到大部分收益——一次"手工拔掉主库网络"的演练，往往比一套没被真正使用的混沌平台有价值得多。**平台化是第四级，先有流程再有平台。**

## 五、实验设计六要素 {#experiment}

一个不会变成事故的实验，必须写清六件事（可以直接当模板用）：

| 要素 | 要回答的问题 | 示例 |
|---|---|---|
| **① 稳态指标** | 用什么判断"正常"？ | 入口成功率 ≥ 99.9%、下单接口 P99 ≤ 800ms、消息积压 ≤ 1 万、错误日志速率 |
| **② 假设（可证伪）** | 预期发生什么？ | "注入后成功率不低于 99%、P99 不超过 1200ms、**10 分钟内自动恢复**" |
| **③ 爆炸半径** | 影响多少？ | 1 个实例 → 1 个服务 → 1 个 AZ，**逐级放大** |
| **④ 中止条件** | 什么情况下立刻停？ | 成功率 < 95% 或 P99 > 3s → 自动停止注入 + 回滚 |
| **⑤ 时间窗** | 什么时候做？ | 避开业务高峰与发布窗口；业务方知情；预留观测时间 |
| **⑥ 回滚路径** | 怎么恢复、多久、谁执行？ | 脚本化恢复步骤 + 执行人 + 预期恢复时间 |

**完整样例**（可直接套用）：

```text
实验名称：单 AZ 故障下订单链路能否在 5 分钟内恢复
────────────────────────────────────────────────
稳态指标：下单成功率 99.95% / P99 380ms / MQ 积压 0
假    设：把 A 可用区的订单服务实例全部下线后，
          流量应在 30 秒内漂移到 B 可用区，
          成功率不低于 99%，P99 不超过 800ms，5 分钟内各项指标回到基线

爆炸半径：仅订单服务的 1 个 AZ（约占该服务 1/2 实例）
中止条件：成功率 < 95% 持续 60 秒，或 P99 > 3s → 立即恢复实例
时间窗  ：周二 14:00-15:00（非高峰），业务方已成人在群
回滚路径：kubectl 恢复副本数（脚本已演练过），预期 60 秒内恢复
────────────────────────────────────────────────
```

> 判据：**② 必须是可证伪的**。"看系统还稳不稳"不是假设，"成功率不低于 99% 且 10 分钟内恢复"才是。**不可证伪的假设 = 不可判定的演练。**

## 六、故障注入的类型库与工具 {#fault-library}

按注入层次分类，**越往下越贴近真实事故，也越少被演练**：

| 层次 | 典型故障 | 能验证什么 | 落地难度 |
|---|---|---|---|
| **进程** | kill / panic / 挂起（`kill -STOP`，模拟假死） | 摘除、重启、连接重连 | 低 |
| **资源** | CPU 打满、内存耗尽（OOM）、磁盘写满、IO 延迟 | 限流、降级、退避是否真的生效 | 低 |
| **网络** | 延迟、丢包、分区、DNS 故障、连接重置 | 超时与重试链路、注册中心失效降级 | 中 |
| **依赖** | 依赖返回错误 / **返回慢**（不是失败）/ **返回错误数据** | 熔断、降级、数据校验 | 中 |
| **数据** | 主从延迟、只读切换、副本落后 | 读写分离的一致性、切换后的数据校验 | 中高 |
| **基础设施** | 节点下线、AZ 隔离、DNS 与证书过期 | 多机房切换、容量接管 | 高 |
| **配置** | 推送错误配置、开关误开 | 配置回滚、灰度能力 | 中 |

**最容易被忽略的是"依赖"与"配置"两类。** 真实事故里占比很高，但演练往往只做"杀进程"：

- **依赖返回慢**——比"返回失败"危险得多，因为它不触发熔断（很多熔断只统计错误率），只会慢慢耗尽线程池；
- **依赖返回错误数据**——代码不报错，只是算错了（对账才发现）；
- **配置推送错误**——一份配置中心推送同时影响所有实例，是典型的**自造故障域**（[可用性目标 · 故障域](/high-availability/availability-targets#fault-domain)）；
- **证书/DNS 过期**——几乎每次都是"从来没演练过"的那一类，且影响 100%。

工具选型（**从手工开始**）：

| 工具 | 定位 | 适用 |
|---|---|---|
| **手工组合** | `kill -STOP` / `tc netem`（网络延迟丢包）/ `stress-ng`（CPU 内存）/ `iptables`（分区） | **L1~L2 首选**，零平台成本 |
| **Chaos Mesh** | K8s 原生（CRD 定义实验），覆盖面广 | K8s 环境、L2~L3 |
| **ChaosBlade** | 阿里开源，支持 OS/JVM/中间件多维注入 | Java 技术栈、L2~L3 |
| **Litmus** | K8s + 工作流编排，实验可组合 | L3 |
| **云厂商故障注入** | AZ 级、网络级故障 | 基础设施层验证 |
| **自研脚本** | 按业务语义注入（如"让支付回调超时"） | 与业务结合最紧，价值最高 |

## 七、GameDay 怎么组织 {#gameday}

"游戏日"（GameDay）是把演练组织成一次有始有终的活动。角色与流程：

| 角色 | 职责 |
|---|---|
| **指挥者** | 控制节奏、决定中止、宣布结论 |
| **执行者** | 按脚本注入故障（**只知道"做什么"，不完全知道后果**） |
| **观测者** | 盯稳态指标与日志，记录现象与时间点（**这是最重要的记录**） |
| **业务方** | 确认业务影响可接受、提供损失口径 |
| **记录者** | 时间线、发现的问题、待办 |

三条组织原则：

1. **必须有一个有权喊停的人，且他不事先知道要注入什么**——否则测出来的是"排练"而不是"响应"；
2. **提前通知的范围要小**（只通知需要知情的人），否则真正该被检验的响应链路会被提前"打点"；
3. **节奏：全局季度一次、局部月度一次**，每次都留复盘窗口。

**产出四件套**（缺一件这次演练就白做）：

```text
① Runbook 更新（把演练中"现场想出来的步骤"固化进去）
② 缺陷单（按严重度排入迭代，不是记在会议纪要里）
③ 监控补齐清单（这次没看出来，是因为哪个指标没采集/没告警）
④ 自动化脚本沉淀（把手工步骤写成脚本，下次由脚本执行）
```

> **判据：一场"什么也没发现"的演练是失败的演练。** 说明要么范围太小（只演了最容易恢复的链路），要么判定标准太松（只看"切换成功"，不看业务指标）。

## 八、反模式 {#antipatterns}

| 反模式 | 为什么错 |
|---|---|
| **只演不练** | 看"切换成功"就收工。切换成功 ≠ 业务可用，必须看业务指标（成功率、P99、对账） |
| **演完不修** | 发现的问题不进待办，下次必然复现。**演练的价值在修复，不在演练本身** |
| **只演最容易恢复的链路** | 演练价值与链路难度成正比。**要演"没把握的那条"** |
| **没有中止条件** | 把演练变成事故，且会严重打击团队后续演练意愿 |
| **在无监控下演** | 无法判定影响，收益为零（还可能是负的） |
| **预发环境演完就当生产没问题** | 流量规模、数据量、依赖行为、缓存状态全不同 |
| **只演技术不演人** | 预案、权限、通知链路同样要演——"演练才发现值班人没有执行权限"是最高频的发现 |
| **一次演全部** | 爆炸半径失控，问题互相掩盖，无法归因 |

## 面试口径 {#interview}

- **为什么要做混沌工程**：把"以为"变成"知道"。**没演练过的预案等于没有预案**——预案的价值在执行它的那个人手上，不在文档里。演练不生产可用性，生产**确定性**。
- **五原则**：建立稳态假设、多样化真实事件、在生产环境运行、持续自动化、最小爆炸半径。**"在生产演练"有前提**，不是无条件照搬。
- **前提条件（成熟度顺序）**：**可观测 → Runbook → 演练 → 混沌自动化**。没有可观测性就做混沌工程 = 在生产随机制造故障；没有中止条件就可能把实验变成事故。
- **成熟度四级**：手工演练 → 场景化演练 → 混沌平台 → 持续混沌。**平台是第四级，从手工 + 脚本开始**，前两级能拿到大部分收益。
- **实验设计六要素**：稳态指标、**可证伪的假设**、爆炸半径、中止条件、时间窗、回滚路径。**不可证伪的假设 = 不可判定的演练。**
- **故障类型**：进程 / 资源 / 网络 / 依赖 / 数据 / 基础设施 / 配置。**最容易被忽略的是"依赖返回慢""依赖返回错误数据""配置推送错误""证书过期"**，真实事故里占比很高。
- **为什么"依赖返回慢"更危险**：它不触发只统计错误率的熔断，只会慢慢耗尽线程池，表现为"系统没有报错但越来越慢"。
- **GameDay 的判据**：必须有一个**事先不知道注入内容**的有权喊停者；产出四件套 = **Runbook 更新 + 缺陷单 + 监控补齐 + 脚本沉淀**；**一场什么也没发现的演练是失败的演练**。
- **反模式**：只演不练、演完不修、只演最容易的链路、没有中止条件、无监控演练、只演技术不演人。
- **延伸**：目标与故障域见[可用性目标](/high-availability/availability-targets)；切换机制的验证对象见[冗余与故障转移](/high-availability/redundancy-failover)；多机房切换是最值得演练的一类，见[多机房架构](/high-availability/multi-datacenter)。
