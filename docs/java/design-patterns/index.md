# 设计模式 · 导览

设计模式是**面向对象设计原则在反复出现的问题上的固定解法**。它不是语法特性，而是一套被反复验证过的代码设计经验——用于解决可扩展性、可维护性与复用性问题。

本板块按 GoF（*Design Patterns: Elements of Reusable Object-Oriented Software*, 1995）的三大分类组织：**5 个创建型 + 7 个结构型 + 11 个行为型 = 23 种**。

## 一、知识地图

| 分类 | 关注点 | 包含模式 | 数量 |
|---|---|---|---|
| **创建型** | 对象**如何被创建** | 单例、工厂方法、抽象工厂、原型、建造者 | 5 |
| **结构型** | 类与对象**如何组合成更大结构** | 代理、适配器、装饰者、桥接、外观、组合、享元 | 7 |
| **行为型** | 对象间**职责如何分配与通信** | 模板方法、策略、命令、责任链、状态、观察者、中介者、迭代器、访问者、备忘录、解释器 | 11 |

记忆锚点：**创建型管"生"，结构型管"搭"，行为型管"跑"**。

## 二、学习主线（顺序不要跳）

1. **[设计原则与 UML](/java/design-patterns/principles/)** — 六大原则是判断"该不该用模式"的标尺；UML 类图是描述模式结构的语言。跳过这一步直接背模式，会在面试被"为什么这么设计"问穿。
2. **[创建型模式](/java/design-patterns/creational/)** — 从 `new` 的耦合问题出发，理解工厂族的层层演进；单例是最常被追问的一个。
3. **[结构型模式](/java/design-patterns/structural/)** — 代理与装饰者、适配器与外观这两对最容易混淆，重点在辨析。
4. **[行为型模式](/java/design-patterns/behavioral/)** — 数量最多，但多数围绕"把变化的算法/状态/请求从调用方剥离"这一条主线。

## 三、每个模式的写作结构

每篇按同一套骨架展开，便于横向对比，也便于面试速查：

| 段落 | 回答的问题 |
|---|---|
| 问题场景 | 不用这个模式，代码会烂成什么样 |
| 结构与角色 | 有哪几个类，各自职责是什么（ASCII 类图） |
| 代码实现 | 可运行的最小实现，含关键细节注释 |
| 对比辨析 | 与最相似的 1–2 个模式的边界在哪 |
| **源码剖析** | **真实框架 / JDK 里这段代码怎么写的，与教科书写法差在哪** |
| 使用场景与面试问答 | 什么业务里真的用了它 + 高频追问 |

两点说明：

- **「源码剖析」是本站着力的段落，也是区分「背过模式」与「读过框架」的地方。** 它只引用真实存在的类与方法（`AbstractApplicationContext#refresh`、`ApplicationFilterChain`、`FutureTask#run`、`SqlNode#apply`、`ClassVisitor#visitMethod` 等），并点出真实实现与教科书写法的差异——**这些差异才是「这段源码为什么这样写」的答案。**
- **创建型与结构型是同一骨架的展开版**：把「对比辨析」按对手拆成多节（如「桥接 vs 继承」「桥接 vs 策略」），把「使用场景与面试问答」拆成两节，并单列「优缺点」。**段名与切分粒度不同，回答的问题相同**；这 11 篇的框架对照同样收在各自的「源码剖析」节里。

| 结构型 | 代理、适配器、装饰者、桥接、外观、组合、享元（7 篇） | **已全部补齐** —— 见各篇「源码剖析」 |
| 行为型 | 模板方法、策略、命令、责任链、状态、观察者、中介者、迭代器、备忘录、访问者、解释器（11 篇） | **11 篇已全部补齐** —— 见各篇「五、源码剖析」 |

**23 种模式已全部成篇**（5 创建型 + 7 结构型 + 11 行为型），**每篇的「源码剖析」也都已补齐**——对照 Spring / JDK / MyBatis / Netty / Servlet / ASM / Tomcat / Jackson / 数据库 的真实实现，逐篇点出「真实写法与教科书写法差在哪」。

## 五、面试高频（先看结论） {#interview}

- **单例**：DCL 为什么要加 `volatile`？哪三种方式能破坏单例？
- **工厂族**：简单工厂为什么不算 GoF 23 种？工厂方法与抽象工厂的边界在哪？
- **代理 vs 装饰者**：同样是"包装"，目的和调用链有什么不同？
- **策略 vs 状态**：结构几乎一样，区别只在"谁决定切换"。
- **模板方法 vs 策略**：继承复用骨架 vs 组合替换算法，Spring 里两种都用。
- **责任链**：Servlet Filter、Spring Interceptor、Netty Pipeline 是同一套思想吗？
- **观察者**：Spring 的 `ApplicationEvent` 是多播还是观察者？

- **Spring 的 `@Scope("prototype")` 是原型模式吗？** 不是——它是「每次 `getBean` 都新建」的工厂语义，一次 `clone()` 都没有。原型模式在 Spring 内部的真实位置是 `BeanDefinition#cloneBeanDefinition`（定义继承靠克隆）。
- **Spring 的单例是单例模式吗？** 机制不同——GoF 用静态字段保证「类加载器内唯一」，Spring 用容器里的 `singletonObjects` 按 **beanName** 保证「容器内唯一」。约束更弱，换来的是可测试与可替换。

> 面试口径提醒：模式的价值在于**权衡**，不在于"用得多"。能说清"这里为什么不用模式"往往比列举模式名称更加分。
