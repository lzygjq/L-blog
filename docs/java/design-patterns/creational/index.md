# 创建型模式 · 导览

创建型模式解决的是同一个问题：**把"对象怎么造出来"这件事，从使用者的代码里挪走**。

不使用创建型模式时，创建逻辑会以 `new` 的形式散落在业务代码中，导致三类后果：① 更换实现要改多处；② 复杂对象的构造参数泄漏到调用方；③ 创建成本（如重复读写文件、重复查询）无法被控制。

## 一、五个模式的定位

| 模式 | 解决的问题 | 一句话方案 | 复杂度 |
|---|---|---|---|
| [单例](/java/design-patterns/creational/singleton) | 全局唯一实例 | 把构造器私有化，对外只暴露一个实例 | ★★ |
| [工厂族](/java/design-patterns/creational/factory) | 创建与使用解耦 | 把 `new` 移到工厂里，按需产出对象 | ★★★ |
| [原型](/java/design-patterns/creational/prototype) | 创建成本高 / 需要副本 | 复制已有对象，而不是重新构造 | ★★ |
| [建造者](/java/design-patterns/creational/builder) | 构造参数多、组装步骤复杂 | 分步组装，最后一步产出成品 | ★★★ |

## 二、怎么选

```
需要保证全局只有一个实例？
  └─ 是 → 单例

创建的对象是"某一族/某一类"，且只有一层选择？
  └─ 是 → 工厂方法（简单场景可用简单工厂）

需要创建"一整套相互关联的对象"，且有多套产品族？
  └─ 是 → 抽象工厂

对象的创建成本很高（读配置、查库、算力密集），或需要大量相似副本？
  └─ 是 → 原型（克隆）

对象的构造参数多、可选参数多，或组装需要固定步骤？
  └─ 是 → 建造者
```

## 三、容易混淆的两组边界

### 3.1 工厂方法 vs 抽象工厂

- **工厂方法**：一个工厂负责**一种产品**的创建，产品维度只有一条线。扩展方式是"加一个工厂 + 加一个产品"，成对增长。
- **抽象工厂**：一个工厂负责**一整套产品**（如"小米工厂"要同时生产手机、路由、电视）。扩展方式是"加一个产品族"，但**新增产品种类会污染所有工厂**——这是抽象工厂最大的缺点。

### 3.2 工厂 vs 建造者

| 维度 | 工厂 | 建造者 |
|---|---|---|
| 关注点 | **造什么**（产出对象的类型选择） | **怎么造**（产出对象的组装过程） |
| 产出 | 一步到位，返回成品 | 多步组装，最后 `build()` 返回成品 |
| 参数形态 | 通常少量参数 | 参数多、可选参数多 |
| 典型场景 | 按类型/环境选择实现 | 组装复杂对象（如订单、SQL、HTTP 请求） |
