# 结构型模式 · 导览

结构型模式关注**类与对象如何组合成更大的结构**。它分为两类：**类结构型模式**（靠继承组织接口与类）与**对象结构型模式**（靠组合/聚合组织对象）。由于组合的耦合度低于继承（符合合成复用原则），**对象结构型模式的灵活性更高**，也是 7 个模式中的主流。

共 7 个模式，按"包装 / 解耦 / 简化 / 共享"四种意图分组。

## 一、知识地图

| 意图 | 模式 | 一句话 | 状态 |
|---|---|---|---|
| **包装增强** | [代理 Proxy](/java/design-patterns/structural/proxy) | 控制对目标对象的访问，在调用前后插入横切逻辑 | ✅ |
| | [装饰者 Decorator](/java/design-patterns/structural/decorator) | 动态叠加职责，功能可任意组合 | ✅ |
| | [适配器 Adapter](/java/design-patterns/structural/adapter) | 转换接口，让不兼容的类能协作 | ✅ |
| **结构解耦** | [桥接 Bridge](/java/design-patterns/structural/bridge) | 把抽象与实现拆成两条独立变化的维度 | ✅ |
| | [组合 Composite](/java/design-patterns/structural/composite) | 用树形结构统一对待"单个对象"与"对象容器" | ✅ |
| **接口简化** | [外观 Facade](/java/design-patterns/structural/facade) | 为一组复杂子系统提供统一入口 | ✅ |
| **对象共享** | [享元 Flyweight](/java/design-patterns/structural/flyweight) | 复用细粒度对象，把状态外置以节省内存 | ✅ |

## 二、最容易混淆的两组（面试高频）

### 2.1 代理 vs 装饰者

| 维度 | 代理 | 装饰者 |
|---|---|---|
| 目的 | **控制访问**（鉴权、事务、懒加载、远程调用） | **增强功能**（可叠加的职责扩展） |
| 与目标的关系 | 通常一对一，代理**知道**具体目标 | 一对多嵌套，装饰者只知道抽象组件 |
| 对象构建 | 由代理方或框架决定 | 由调用方**逐层包装**决定 |
| 典型实现 | Spring AOP、`MapperProxy`、静态代理 | `BufferedInputStream`、`HttpServletRequestWrapper` |
| 关注点 | 把"不该出现在业务里的逻辑"挪出去 | 把"可选功能的排列组合"从继承里解放出来 |

一句话记忆：**代理是"代你去做"，装饰者是"给你加料"**。

### 2.2 适配器 vs 外观

- **适配器**：接口**不兼容**，要转换——目标是"能让老代码接上新接口"，**面向现有接口做转换**。
- **外观**：接口**太多太乱**，要收拢——目标是"给调用方一个简单入口"，**面向子系统做封装**，不改变任何已有接口。

## 三、面试高频速答

- **Spring AOP 用的是代理还是装饰者？** 代理（JDK 动态代理 / CGLIB），目的是插入横切逻辑。
- **JDK 里哪里是适配器？** `InputStreamReader`（`InputStream` → `Reader`）、`Collections.list()`、`Arrays.asList()`。
- **MyBatis 的 `MapperProxy` 属于哪种？** 动态代理——把"接口调用"转换为"SQL 执行"。
- **`HashMap` 哪里用了享元？** 见后续享元篇（`Integer` 缓存、字符串常量池是更典型的例子）。
- **组合模式在业务里的真实场景？** 组织架构树、菜单树、文件系统、审批流节点树——**任何"树形 + 需要统一处理叶子与容器"的场景**。

## 四、学习顺序建议

```
代理 → 适配器 → 装饰者        （包装三兄弟，先建立"包装"直觉，再辨析差异）
  ↓
桥接 → 外观 → 组合 → 享元     （各解决一类结构问题，独立性较强，可跳跃阅读）
```

其中**代理与适配器**是工程中出现频率最高的两个，建议优先吃透；**享元**与**组合**在业务代码中较少手写，但属于面试常问的"你是否理解模式的适用边界"。
