# 覆盖率与质量门禁

前四篇讲的是「怎么写测试」。这一篇讲**怎么让测试真正起作用**——覆盖率该看什么、CI 该卡在哪、坏测试怎么治理、难测的代码怎么改。

这一篇是 L3 层的内容：**它考的不是你会不会写测试，而是你能不能为一群人定标准。** 到了 30K 以上的面试，质量这一问基本都是这个角度。

## 一、覆盖率该怎么读 {#coverage}

### 1.1 先分清几种覆盖率

| 指标 | 含义 | 说明 |
|---|---|---|
| **行覆盖** | 执行过的代码行占比 | 最常用，也最容易被「刷」 |
| **分支覆盖** | `if` / `switch` 的每个分支走过没有 | **比行覆盖有意义得多** |
| **指令覆盖** | 字节码指令级别的覆盖 | JaCoCo 的原始数据，粒度最细 |
| **路径覆盖** | 所有分支组合 | 组合爆炸，实践中不追求 |
| **方法 / 类覆盖** | 有多少方法/类被执行过 | 适合做「有没有完全没碰过的模块」的粗筛 |

JaCoCo 报告里这几项是并列给出的。**看报告时优先看分支覆盖**——因为 `if (a && b)` 这种写法，行覆盖可能显示 100%，但 `b` 为假的分支从没走过。

### 1.2 为什么追 100% 是错的

不是「做不到」，是**这个目标会诱导错误的行为**：

```java
// 为了让覆盖率好看，给 getter 加断言
@Test
void testGetName() {
    User u = new User();
    u.setName("张三");
    assertNotNull(u.getName());
}
```

这段测试让覆盖率 +3 行、让质量 **+0**。而如果有人把 `setName` 改成「写入时脱敏」，这个测试依然绿——**它什么都没保护**。

更糟的是**反向激励**：当覆盖率成为考核指标，最省力的达标方式就是「写没有断言的测试」和「把复杂逻辑拆成难测的部分然后 `@Disabled`」。**指标一旦被当成目标，它就不再是好指标**（这是古德哈特定律在工程上的典型体现）。

### 1.3 覆盖率真正有用的两个场景

1. **发现「完全没被碰过」的区域**——某个 Service 的分支覆盖是 0%，那就是一个从未验证过的代码路径。这是**风险定位**，不是质量评分。
2. **发现「改了代码但没改测试」**——新增了分支但覆盖率没动，说明改动没有配套测试。

### 1.4 该怎么定指标

实践里比较可行的组合：

| 范围 | 建议 |
|---|---|
| 核心模块（金额、权限、状态机、并发控制） | 设较高门槛（如分支覆盖 60%~80%） |
| 一般业务模块 | 不设硬指标，只做趋势观察 |
| 生成的代码、DTO、配置类 | **显式排除**（JaCoCo 的 `excludes`），别让它污染读数 |
| **新增 / 变更代码** | **设门槛**——这是最有效的一条 |

最后一条是关键：**「本次改动的代码必须有测试」比「全仓 80%」可执行得多**。全仓指标一旦达标就变成了遗产，而增量指标每次都在起作用。

### 1.5 覆盖率测不出「断言够不够强」——变异测试才是

覆盖率只能说明「这行被执行过」，不能说明「执行结果被检查了」。想量化「断言强度」，用的是**变异测试**（mutation testing）：

> 工具（Java 生态里是 PIT）自动把代码做小改动——把 `>` 改成 `>=`、把 `return x` 改成 `return x + 1`、删掉一次方法调用——然后跑测试。
> **如果测试仍然全绿，说明这个变异「存活」了**，也就是这段逻辑没有被任何断言真正保护住。

「变异存活率」是一个比覆盖率诚实得多的指标。它的代价是慢（每个变异都要跑一遍测试），所以实践中只对**核心模块**启用。

> 面试里如果被问「覆盖率能完全代表测试质量吗」，答「不能，覆盖率只度量执行，不度量断言；要度量断言强度得用变异测试」——这一句就能把讨论拉到另一个层次。

## 二、CI 门禁怎么设计 {#pipeline}

### 2.1 分层：快反馈在前，慢验证在后

```text
① 静态检查（格式化 / 静态分析 / 依赖漏洞扫描）     秒级
② 编译 + 单元测试                                  分钟级
③ 集成测试（起容器，跑关键路径）                    分钟级到十分钟级
④ 构建镜像 / 产物                                  分钟级
⑤ 部署到测试环境 + 冒烟                            分钟级
⑥ 人工审批 → 生产                                   —
```

**顺序原则**：**越便宜、越早失败的检查越往前放**。让一个格式错误在 3 秒内失败，而不是跑完十分钟集成测试再告诉你。

### 2.2 卡点该卡在哪

| 阶段 | 是否阻断 | 理由 |
|---|---|---|
| 静态检查 | **阻断** | 零成本，没有放过的理由 |
| 单元测试 | **阻断** | 单测失败说明代码本身有问题 |
| 集成测试 | **阻断** | 都到这一步了还红，合进去就是事故 |
| 覆盖率（增量） | 可阻断 | 对**新增代码**设门槛是有效的 |
| 覆盖率（全局） | **不阻断** | 只能作为趋势看板 |
| 镜像构建 | **阻断** | 构不出来就没有可部署物 |

**底线只有一条**：**测试失败的流水线不允许合并**。这条一旦松动，后面所有设计都没有意义——因为大家会学会「红灯了等一会儿重跑」。

### 2.3 让门禁「可执行」的三个细节

1. **必须快**：主分支的一次完整验证控制在 **5~10 分钟**内。超过 15 分钟，开发者就会开始并行提交、绕过检查。速度本身就是门禁有效性的一部分。
2. **失败信息必须指向原因**：报告要能看到「哪个类、哪个方法、期望什么实际什么、完整日志在哪」。只给一句 `BUILD FAILED` 等于没有门禁。
3. **区分「必过」与「仅供参考」**：把所有检查都设成必过会导致「天天有红灯」，然后所有人开始无视。**只把真正会拦住合并的项设为必过**。

### 2.4 缓存与并行

CD 流水线变慢的常见原因是可以缓存的东西没缓存：Maven/Gradle 依赖、构建产物、Docker 层。另外测试本身可以**分片并行**（按类或按标签切分），这是把 10 分钟压到 3 分钟最直接的办法。

代价是并行执行会让**数据隔离问题暴露出来**（见[集成测试的数据隔离](/java/testing/integration-test#isolation)）——这其实是好事，它把隐患提前了。

## 三、flaky 与测试债务 {#flaky}

### 3.1 flaky 的真正代价

一个测试「十次里有一次红」，看起来只是 10% 的噪音。但它的真实影响链是这样的：

```text
偶发红灯 → 大家学会「重跑一下就好」 → 真红灯也被重跑 → 门禁形同虚设
```

**flaky 摧毁的不是那一个测试，是整个套件的可信度。** 所以它的优先级高于「多写几个新测试」——**可信度是测试体系的地基**。

### 3.2 数据：测试债务长什么样

我看过一个成熟的开源工程（yudao）的测试现状，用脚本数出来是这样：

| 指标 | 数量 |
|---|---|
| 测试类总数 | 140 |
| **带 `@Disabled` 的测试类** | **48（34%）** |
| `@Disabled` 出现总次数 | **157** |
| 其中**类级禁用**（整个类不跑） | 41 |
| 禁用理由为「裸 `@Disabled`」无说明 | **86** |

理由的分布更能说明问题：

```text
86  @Disabled                                    ← 连理由都没写
21  @Disabled // TODO 后续 fix 补充的单测          ← 「以后补」
14  @Disabled // TODO 请修改 null 为需要的值…      ← 脚手架生成后没填的空壳
 5  @Disabled // TODO 临时注释                    ← 「临时」
 4  @Disabled // TODO 后续修复
 2  @Disabled("集成测试，暂时忽略")
```

**这不是在批评某个项目**——恰恰相反，这是一个测试覆盖率相当高的工程，出现这些是**正常的演化结果**。它的价值在于揭示了一条规律：

> **`@Disabled` 会累积，而且「临时」永远不临时。**

「86 条无理由禁用」和「21 条 TODO 以后补」几乎出现在每一个有年头的项目里。它们的共同特征是：**没有任何机制保证它们会被处理**。

### 3.3 治理：三步，且必须强制

| 步骤 | 动作 |
|---|---|
| **① 识别** | CI 里统计 `@Disabled` 数量，作为**趋势指标**（不是考核指标）。只要它在涨，就在欠债。 |
| **② 定性** | 分成三类打标签：**待修**（有明确修复计划）、**环境依赖**（需要外部条件，用 `@EnabledIfEnvironmentVariable` 之类条件化，而不是禁用）、**废弃**（对应的功能已删，直接删测试）。 |
| **③ 有期限** | 「待修」的必须带**负责人 + 期限**。没有期限的禁用等同于删除——那就干脆删掉，至少让覆盖率数字诚实。 |

**最该禁止的一种做法是把 `@Disabled` 当作解决 flaky 的手段**。那等于把「不可信」变成「不可见」。

### 3.4 关于「失败重试」

Surefire 支持自动重试失败测试：

```xml
<configuration>
    <rerunFailingTestsCount>2</rerunFailingTestsCount>
</configuration>
```

它有明确的争议：

- **支持方**：把「环境抖动」这类真噪音挡掉，让门禁更稳定
- **反对方**：它会**掩盖真 flaky**——一次失败被重试掩盖，而那个测试的问题依然存在

比较稳妥的态度是：**默认不开；如果开，必须记录「哪些测试发生过重试」并进入治理队列**。它可以是创可贴，但不能是治疗。

## 四、契约测试：跨服务边界的另一种验证 {#contract}

### 4.1 它要解决什么问题

微服务架构下一个经典的失效模式：

- 提供者（Provider）改了接口：删了个字段、把枚举值改了大小写
- 消费者（Consumer）的集成测试**全绿**——因为它测的是「真实 Provider」的那个旧行为（或者它 Mock 了 Provider）
- 上线后消费者炸

**两端各自的测试都通过，合起来却是错的。** 而跨服务跑完整的端到端测试成本又太高（要起所有服务）。

### 4.2 契约测试怎么做

以 Pact 这类工具为例，流程是**双向的**：

```text
① 消费者侧：写测试时用 Mock 服务，但把「我期望的请求/响应」记录下来
   → 生成一份契约文件（pact.json）

② 提供者侧：拿到契约文件，用它去驱动真实的 Provider
   → 验证「我现在的实现是否满足这份期望」

③ 任何一侧不满足 → 双方 CI 都红
```

这带来一个关键性质：**契约是版本化的产物，它可以进 CI、可以被追溯**。Provider 改了字段，在**它自己**的流水线里就会失败——而不是等 Consumer 上线才炸。

### 4.3 它和集成测试的关系

| | 集成测试 | 契约测试 |
|---|---|---|
| 验证对象 | 我这一侧的行为 | **两侧的约定本身** |
| 需要起多少服务 | 我 + 依赖 | 各自独立（不互相启动） |
| 适合 | 层内协作、真实 SQL | **跨团队 / 跨服务的接口边界** |
| 成本 | 中 | 需要双方都接入，有组织成本 |

**适用条件**：有稳定的团队边界（比如 A 团队提供 API、B/C 团队消费）。**如果只是一个单体应用内部，契约测试的收益远小于成本**——那种场景直接写集成测试就够了。

### 4.4 轻量替代方案

没条件上 Pact 时，也有更低成本的兜底：

- **Provider 侧做响应 schema 测试**：用 JSON Schema 或 OpenAPI 校验真实响应结构
- **对外接口做「兼容性」检查**：显式定义「不允许删除字段、不允许收紧枚举」这类规则，在 CI 里比对前后版本的接口定义
- **消费者侧不用手写 Mock 数据**：从 Provider 的真实响应录制一份（避免「我假设它返回什么」）

## 五、可测性设计：难测的代码是设计问题 {#testability}

写不出测试，通常不是「测试技巧不够」，而是**代码本身耦合太重**。可测性差是设计的味道，不是测试的锅。

### 5.1 难测的代码长什么样

```java
// 典型：不可测
public class OrderService {
    public void create(OrderRequest req) {
        // ① 直接 new 依赖 —— 无法替换
        UserApi userApi = new UserApi();
        // ② 静态方法调用 —— 无法替换
        String id = IdUtils.uuid();
        // ③ 直接读当前时间 —— 结果不可复现
        if (LocalDateTime.now().isAfter(promoEnd)) { ... }
        // ④ 构造器或方法里做 IO
        // ⑤ 依赖全局/静态状态
        Config.INSTANCE.get("rate");
    }
}
```

### 5.2 六个改造手法

| # | 手法 | 做法 |
|---|---|---|
| 1 | **构造器注入** | 把 `new` 换成注入，依赖从「写死在内部」变成「由外部提供」 |
| 2 | **端口-适配器** | 外部系统（HTTP / SDK）包成一个自己的接口，测试替换实现 |
| 3 | **时钟注入** | 用 `Clock` 替代 `LocalDateTime.now()`，测试里给固定时钟 |
| 4 | **生成器注入** | ID / 随机数 / Token 生成器做成接口，测试里给可预测实现 |
| 5 | **把逻辑从副作用里抽出来** | 复杂计算抽成纯函数（输入→输出，无 IO），直接测 |
| 6 | **缩小职责** | 一个类 5 个依赖时先拆类，而不是硬写 5 个 `@Mock` |

第 5 条常常被忽略，但它收益最高：**纯函数不需要任何测试替身**。

### 5.3 改造前后对比

```java
// 改造前：不可测
public BigDecimal calcFinalPrice(Long userId, BigDecimal price) {
    int level = new UserApi().getLevel(userId);            // 真调用
    if (LocalDateTime.now().isAfter(promoEnd)) { ... }      // 真时间
    return ...
}

// 改造后：可测
@Service
public class PriceCalculator {
    private final UserPort userPort;       // ① 注入
    private final Clock clock;             // ③ 注入时钟

    public BigDecimal calcFinalPrice(Long userId, BigDecimal price) {
        int level = userPort.getLevel(userId);
        BigDecimal rate = rateOf(level);                    // ⑤ 纯函数，单独测
        if (clock.instant().isAfter(promoEnd)) { ... }
        return price.multiply(rate);
    }

    BigDecimal rateOf(int level) { ... }   // 纯函数：直接参数化测试，不需要容器
}
```

改造之后的测试成本下降是几倍级的：**纯函数用参数化测试覆盖几十组数据**，只留一个集成测试验证「装配是否正确」。

> 反过来说：**如果一个类需要 5 个 Mock 才能测，问题在设计，不在测试。**

## 六、怎么把质量讲清楚

到了技术专家/架构的面试，这一块的问题会变成「**你们团队的质量是怎么保障的**」。回答不好，通常是因为只会描述工具，不会描述**机制**。

一个可用的表达框架是「**四层 + 一个闭环**」：

| 层 | 你在做什么 | 关键指标 |
|---|---|---|
| 编码时 | 单元测试 + 静态检查 | 增量覆盖率、静态检查通过率 |
| 提交时 | 门禁：单测 + 集成测试 | 主分支绿灯率、流水线时长 |
| 发布前 | 回归 + 冒烟 + 灰度 | 缺陷逃逸率、回滚次数 |
| 线上 | 监控 + 告警 + 快速回滚 | 平均恢复时间 |
| **闭环** | **缺陷复盘 → 补回归测试** | 同一个问题**不出现第二次** |

最后一行是重点：**每个线上缺陷都应该变成一条回归测试**。这条机制比任何覆盖率指标都有效——因为它是**用真实事故喂出来的测试**，命中率极高。

> 一个诚实提醒：上面这些指标**如果你没有真实数据，就不要编**。面试里说「我们主要靠增量覆盖率和缺陷回归」是可信的；编造「我们的缺陷逃逸率是 0.3%」被追问一句「怎么统计的」就会露馅。

## 七、常见坑 {#pitfalls}

1. **把覆盖率当考核指标**：会立刻催生无断言测试和 `@Disabled`。指标一旦成为目标就失效。
2. **只看行覆盖不看分支覆盖**：`a && b` 的分支情况在行覆盖里是看不出来的。
3. **让生成的代码、DTO、配置类混进覆盖率读数**：分母被污染，读数失去意义，应显式排除。
4. **只卡全局覆盖率、不卡增量**：全仓达标后就变成遗产，不再起作用。
5. **门禁太慢**：超过 15 分钟的流水线会被开发者绕过，门禁自动失效。
6. **所有检查都设必过**：天天红灯 → 集体无视。只把真正拦合并的项设成必过。
7. **用 `@Disabled` 处理 flaky**：把「不可信」变成「不可见」，是最糟的处理方式。
8. **`@Disabled` 不带理由和期限**：实测数据里 86 处裸 `@Disabled`，说明它们在事实上永远不会被处理。
9. **默认开启失败重试**：掩盖真 flaky。开就要有记录和治理队列。
10. **在单体应用内部做契约测试**：组织成本高于收益，直接写集成测试更合适。
11. **靠"写测试技巧"解决难测代码**：需要 5 个 Mock 才能测的类，应该拆类或抽纯函数。
12. **断言依赖当前时间/随机值**：注入 `Clock` 与生成器，否则测试不可复现。
13. **把「测试通过」当成「质量达标」**：测试证明的是「已知场景没坏」，质量还包括可观测性、回滚能力、容量验证。

## 八、面试口径 {#interview}

1. **覆盖率要求多少合适？** 覆盖率是**发现盲区**的工具，不是质量评分。可行做法：核心模块（金额、权限、状态机、并发）设较高分支覆盖门槛，一般模块只看趋势，生成代码/DTO 显式排除，**同时对新增代码设门槛**——增量指标比全局指标有效得多。
2. **为什么说追 100% 覆盖率是错的？** 因为它诱导的行为是「写没有断言的测试」和「把难测的部分禁用掉」。而且 100% 行覆盖不代表 100% 分支覆盖，更不代表断言有效。**它度量的是执行过没有，不是检查过没有。**
3. **覆盖率高但质量差，怎么解释？** 覆盖率只说明代码被执行过，不说明结果被断言过。举个极端例子：一个没有断言的测试能让覆盖率 100% 而质量 0。要度量「断言强度」得用变异测试。
4. **什么是变异测试？** 工具把代码做小改动（`>` 改 `>=`、改返回值、删调用），再跑测试；测试仍绿说明这个变异「存活」，即该逻辑没被有效保护。变异存活率比覆盖率诚实，代价是很慢，只对核心模块启用。
5. **CI 门禁该怎么分层？** 按「越便宜越靠前」排：静态检查 → 编译 + 单测 → 集成测试 → 构建产物 → 部署冒烟。总时长控制在 5~10 分钟。**唯一的硬底线是「测试失败不允许合并」**，这条松动则所有设计失效。
6. **覆盖率在 CI 里该不该阻断？** 增量覆盖率可以阻断（有效且可执行），全局覆盖率不建议阻断（会催生刷数字），只作为趋势看板。
7. **什么是 flaky 测试？为什么必须治？** 偶发失败、重跑就绿的测试。它的真正代价是**摧毁整个套件的可信度**——一旦大家习惯「重跑一下就好」，真红灯也会被重跑，门禁形同虚设。治理三步：识别（CI 统计趋势）、定性（待修／环境依赖／废弃）、有期限（负责人 + 期限）。
8. **用失败重试解决 flaky 行不行？** 可以作为临时创可贴，但必须记录「哪些测试重试过」并进入治理队列。默认开启会让真 flaky 隐身，属于把问题从「不可信」变成「不可见」。
9. **契约测试和集成测试什么区别？** 集成测试验证「我这一侧的行为」，要么起真依赖要么 Mock；契约测试验证「**两侧的约定本身**」，消费者侧生成契约、提供者侧用契约驱动验证，双方 CI 都会红。它适合有明确团队边界的跨服务接口，单体内部做它收益小于成本。
10. **难测的代码怎么办？** 先承认这是**设计问题**而不是测试技巧问题。六个手法：构造器注入替代 `new`、外部依赖包端口接口、注入 `Clock`、注入 ID/随机生成器、把逻辑抽成纯函数、拆掉职责过多的类。**需要 5 个 Mock 才能测的类应该拆，而不是硬测。**
11. **你们团队的质量怎么保障的？** 用「四层 + 一个闭环」回答：编码时单测与静态检查、提交时门禁、发布前回归与灰度、线上监控与回滚，最后用**「每个线上缺陷都补一条回归测试」**闭环。这一条比任何覆盖率数字都有效，因为它是用真实事故喂出来的。
12. **测试体系怎么衡量有没有效？** 不看「写了多少测试」，看四件事：主分支绿灯率、流水线时长、缺陷逃逸率（生产发现的问题里有多少本该被测试拦住）、平均恢复时间。**衡量的是「拦住了什么」，不是「写了多少」。**
