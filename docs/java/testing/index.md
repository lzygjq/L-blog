# 测试与质量 · 板块导览

先说清这个板块**不做什么**：它不是测试工程师的培训材料。等价类划分、边界值、判定表这些用例设计方法，Selenium / Appium 这类 UI 自动化，缺陷生命周期管理——那些是测试岗的 KPI，后端面试基本不问，这里也不覆盖。

它解决的是另一个问题：**你怎么证明自己写的东西是对的，以及你怎么让别人写的东西也不出错。**

## 一、为什么这不是「软性话题」

「测试跟开发有什么关系」——答案取决于你把「测试」理解成什么：

- 理解成「**写测试用例**」→ 那是另一个岗位的事，跟开发确实没关系
- 理解成「**代码的可验证性**」→ 那它就是开发的核心问题之一

看几个后端岗的真实追问，它们都不是「测试知识」，但**全都只能靠测试来回答**：

| 面试官会问 | 答案从哪来 |
|---|---|
| 多租户隔离会不会串数据？ | 两个租户各插一条，断言互不可见 |
| MQ 消息重复消费了怎么办？ | 同一条消息投两次，断言只落一条 |
| 数据权限注解真的生效了吗？ | 换用户上下文跑一遍，断言 SQL 真被拼上了条件 |
| 你说这方案扛得住，凭什么？ | 压测报告 + 关键路径的回归测试 |

架构图是纸面的，测试是**能跑出绿灯**的。这是项目证据里最硬的一层：可复现、可截图、可让别人在你机器之外跑一遍。

## 二、测试金字塔不是比例，是判据

「金字塔」被讲烂了，但它经常被误读成一个比例（70/20/10），然后变成毫无意义的配额。它真正的意思是**一个成本递减的排序**：

```text
        单元测试          毫秒级 · 无外部依赖 · 定位到方法
      集成测试            秒级 · 起真依赖   · 定位到模块
   端到端 / 验收测试       分钟级 · 全链路    · 定位到「有东西坏了」
```

越往上越慢、越脆、越贵，但越接近「用户真的能用」。所以判据不是「该写多少百分比」，而是三句话：

1. **能用单元测试说清的，不要用集成测试**（因为慢、且失败时定位成本高）
2. **只靠单元测试说不清的，必须上集成测试**（比如 SQL、事务、序列化、多租户隔离）
3. **端到端只留给关键旅程**（登录、下单、支付这种断了就是事故的路径）

> 过度追求「纯单元测试」的团队会写出一堆绿色但没意义的东西——所有依赖都被 Mock 掉，测的是 Mock 的行为，不是系统的行为。这是本板块反复要纠的一个反模式。

## 三、五篇地图

按「框架 → 替身 → 切片 → 真依赖 → 门禁」递进，每篇都能独立看：

| # | 篇目 | 解决的问题 | 一句话答案 |
|---|---|---|---|
| 1 | [测试基础与 JUnit](/java/testing/junit) | 框架怎么用、JUnit 6 变了什么、哪些代码根本不值得测 | 测试是设计工具，不是验收工序 |
| 2 | [Mock 与替身技术](/java/testing/mockito) | 什么时候该 Mock、什么时候 Mock 是自欺欺人 | Mock 掉协作者，不要 Mock 掉内部实现 |
| 3 | [Spring Boot 测试与上下文](/java/testing/spring-boot-test) | 全量启动太慢、切片怎么切、上下文为什么被复用 | 按「要验证哪一层」选切片，不是按习惯 |
| 4 | [集成测试与真实依赖](/java/testing/integration-test) | H2 能不能代替 MySQL、容器成本怎么压 | 方言和事务语义不能靠假装 |
| 5 | [覆盖率与质量门禁](/java/testing/quality-gates) | 覆盖率看什么、CI 卡在哪一层 | 门禁要卡「能不能合」，不是卡「写了没有」 |

## 四、一条主线：从「会写」到「能定标准」

这五篇的难度是递进的，恰好对应三个层次：

| 层次 | 能力 | 谁具备 |
|---|---|---|
| L1 | 会用 JUnit 写 `@Test`，会让断言通过 | 绝大多数后端 |
| L2 | 会划 Mock 边界、会用切片、会起真实依赖 | 约三成 |
| L3 | 能定质量门禁、能解释为什么不该追覆盖率、能治理 flaky | 不到一成 |

L1 到 L2 是**技术问题**（知道 API 就行），L2 到 L3 是**判断问题**（要能做取舍）。面试里真正拉开差距的是后者——因为前者可以现学，后者只能靠想过。

## 五、与其他板块的关系

- **写测试要用到并发**：并发场景的测试（`CountDownLatch` 控制时序、`Awaitility` 轮询断言）依赖 [Java 并发](/java/concurrent/)
- **写测试要用到 Spring**：切片测试本质是「控制 Spring 容器装多少东西」，前提是懂 [IoC](/java/spring/spring-framework/ioc/) 与 [自动配置](/java/spring/spring-boot/configuration)
- **集成测试用到容器**：Testcontainers 依赖 [Docker](/cloud-native/docker/)，这与 [CI/CD](/cloud-native/cicd/) 的门禁设计是同一件事的两面
- **测试是项目证据**：[面试专题](/interview/) 里「怎么保证质量」这一问，落点就在本板块
- **架构留下的绿灯**：多租户交叉查询不可见，是隔离档位的最低断言，见[多租户 · 横切点](/methodology/multi-tenancy#context)
