# 出站 HTTP：超时对齐与调用预算

一次入站请求在应用里往往会再打出去：调支付、调库存、调另一个内部服务。**入站超时是预算，出站超时是花销。** 花销加总超过预算，用户看到的是网关 504，你的日志里却没有超时——因为应用还在等。

数据库侧同一条原则已经写在[连接池 · 超时对齐](/database/mysql/connection-pool#timeouts)：内层必须先于外层生效。本篇把这条原则接到 **HTTP 出站**，并把它和[重试的四个前提](/java/spring/spring-framework/crosscutting/resilience#preconditions)算在同一笔预算里。

> **主线：出站调用不是「再发一次 HTTP」，而是一次占用入站线程、入站超时窗口、以及下游连接池名额的交易。**
>
> 超时、重试、连接池三者必须放在同一张表里对齐。只配其中一个，另外两个会把它抵消掉。

本篇不讲服务名解析、负载均衡、Feign 契约——那是[客户端负载均衡](/java/spring/spring-cloud/loadbalancer)的职责。这里假设你已经拿到了一个 URL，只回答：**这次调用最多等多久、失败了能不能再试、池不够时会怎样。**

## 一、问题场景：504 但没有超时日志 {#why}

| 现场 | 配置上实际发生了什么 | 用户看见 | 日志里 |
|---|---|---|---|
| 网关 10s，出站 `readTimeout=60s` | 网关先切断 | 504 | 应用仍在读 socket，**没有超时异常** |
| 出站 3s 超时，重试 3 次无间隔 | 最坏 12s 才返回 | 上游已 504 | 三次独立失败，第一次才是根因 |
| HTTP 客户端池耗尽 | 借连接等待默认很长 | 接口「偶发变慢」 | 业务代码还没执行到 |
| 出站无限等待（超时没配） | 下游卡住 | 线程与入站连接被占住 | 一段时间后表现为**入站池 / 线程池打满** |

第四种会把出站问题伪装成「我们自己的连接池打满」。排查时若先去调大 Hikari，只会把症状延后。

## 二、一次出站经过的超时 {#timeouts}

```
① 调用方 / 浏览器超时
        ↓
② 网关 / 反向代理超时          ← 入站预算的天花板
        ↓
③ 本服务：处理时间 + 出站调用
        │
        ├─ HTTP 客户端：借连接等待（连接池）
        ├─ connectTimeout（TCP 建连）
        └─ readTimeout / responseTimeout（等响应）
        ↓
④ 若启用重试：③ × 次数 + 退避
        ↓
⑤ 下游自己的入站超时、以及它再出站的预算
```

**对齐原则与数据库那一条相同：内层必须短于外层，内层先失败、带明确错误返回。**

一套能讲清楚的数字（按「网关 8s、本服务还要写库」举例，不是推荐全集）：

| 层 | 建议量级 | 它保护什么 |
|---|---|---|
| 网关 | 8s | 用户侧天花板 |
| 本服务入站（容器 / 业务超时） | 6s | 必须短于网关，否则 504 无日志 |
| 出站 `connectTimeout` | 200ms~1s | 下游挂了要快失败，不要在 SYN 上耗预算 |
| 出站 `readTimeout` | 1s~3s | 单次调用上限；**必须小于「入站剩余 − 写库 − 余量」** |
| 重试总时长 | **整段仍 < 入站剩余** | 见下一节 |
| HTTP 客户端借连接等待 | 百毫秒级 | 池不够应快速失败，把背压暴露出来 |

`readTimeout` 不是「下游 P99 再加一点心情」：它是**你愿意为这一跳花掉的入站预算**。下游 P99 已经 2s、你的入站只剩 2s，这一跳就不该同步等——改异步、拆接口、或让网关给这条链路单独的更长预算（并显式记录）。

## 三、客户端怎么配：RestClient 与超时项 {#client}

2026 年的默认选择是 **`RestClient`**（Boot 3.2 引入，Boot 4 继续）。`RestTemplate` 仍能跑，但新代码不要再往上堆。响应式路径用 `WebClient`，超时模型不同（`responseTimeout`），原则一样。

```java
@Bean
RestClient paymentClient(RestClient.Builder builder) {
    return builder
        .baseUrl("https://payment.internal")
        .requestFactory(httpComponentsFactory())  // 显式工厂，才能设超时与池
        .build();
}
```

Apache HttpClient 5 上要**分开设**的几项（JDK `HttpClient` 项名不同，语义对应）：

| 参数 | 含义 | 默认陷阱 |
|---|---|---|
| **connectTimeout** | TCP 建连 | 有的栈默认几秒到十几秒，下游挂了会把入站窗口吃光 |
| **responseTimeout / readTimeout** | 等响应体 | **漏配 = 无限等**，与 JDBC `socketTimeout=0` 是同一类故障 |
| **connectionRequestTimeout** | 从**本池**借一条连接的等待 | 漏配则池耗尽时线程挂在「还没发出去」 |
| **连接池 max / 每路由 max** | 出站并发上限 | 默认偏小或偏大都会出问题，见第四节 |
| **连接存活 / 空闲回收** | 避免拿到对端已关掉的连接 | 云环境对端空闲掐连接很常见 |

> **不要对每个调用 `new RestClient()` / `new RestTemplate()`。** 那等于每次新建连接池（或根本不池化），对端 `TIME_WAIT` 堆积、本进程文件句柄上涨。客户端是 Bean，超时是配置，不是随手 new 的参数。

服务发现、`@LoadBalanced`、Feign 的契约与拦截器不在本篇展开——那些决定**打到哪一台**。本篇只决定**打过去之后等多久**。两边都要配：解析很快但超时是 60s，仍然会 504 无日志。

## 四、两套连接池，不要调错 {#pools}

入站路径上有 Hikari（以及 Tomcat 线程）；出站路径上**另有一套** HTTP 客户端池。它们的指标、打满原因、调参方向都不一样：

| | 入站：Hikari | 出站：HTTP 客户端池 |
|---|---|---|
| 保护谁 | 数据库 | 下游 HTTP 服务 |
| 打满时 | `pending` 上升，请求卡在借库连接 | 请求卡在**发出去之前** |
| 先看什么 | `Threads_running` vs `pending` | 下游延迟、本池等待、文件句柄 |
| 调大的代价 | 数据库会话与锁竞争 | 下游被放大的并发 |

**虚拟线程把「线程数 ≈ 出站并发上限」这条隐性背压拿掉了。** 开了虚拟线程却不给 HTTP 客户端设池上限和超时，等于用无限并发去打下游——这与[重试篇](/java/spring/spring-framework/crosscutting/resilience)里 `@ConcurrencyLimit` 要补的那块是同一类缺口。容器侧的注意见[虚拟线程](/java/spring/spring-boot/web-server#virtual-threads)。

出站池的大小仍按 Little's Law 估：`目标 QPS × 该跳平均耗时`，再与下游能承受的并发取小。**不要用 Hikari 的 `maximumPoolSize` 去「带动」HTTP 池**——数据库并行能力和支付网关并行能力不是同一个数。

## 五、重试吃的是同一笔预算 {#retry-budget}

超时配短了，失败率会上去，下一步几乎总会有人加重试。重试合法的前提仍是[四个前提](/java/spring/spring-framework/crosscutting/resilience#preconditions)；本篇只补一条算术：

```
单次上限 × 次数 + 退避总和  <  入站剩余预算
```

| 写法 | 最坏耗时（举例） | 结果 |
|---|---|---|
| 读超时 3s，重试 3 次，无退避 | 12s | 网关 8s 已 504，后两次是幽灵请求 |
| 读超时 1s，重试 2 次，退避 200ms+抖动 | ~2.5s | 还能把错误返回给入站 |
| 读超时 1s，遇到 400 也重试 | 同左 | 浪费预算；业务拒绝不可恢复 |

HTTP 层特别容易踩的两点：

1. **只重试幂等动词，或显式幂等的写。** `GET`/`HEAD` 默认可重试；`POST` 支付、扣减，除非有幂等键，否则超时成功 + 重试 = 重复下单。
2. **客户端重试 + 网关重试 + 服务端 `@Retryable` 不要叠三层。** 每一层都 ×3，下游看到的是 27 倍脉冲。整条链路只允许**一层**负责重试，其它层快速失败。

RPC 出站的超时预算与重试风暴，口径与这里相同，展开见 [RPC 可靠性 · 超时](/middleware/rpc/rpc-reliability#timeout)。

## 六、怎么确认对齐已经生效 {#verify}

配置写了不等于链路上生效。核对这三件事：

| 核对 | 做法 |
|---|---|
| 单次超时先于网关 | 把下游 hang 住（测试桩 sleep），本服务应在 `readTimeout` 内返回明确错误，网关侧**不应**先 504 |
| 重试总时长仍在预算内 | 看链路：同一次入站下面有几次出站 span；次数 × 单次延迟应小于网关超时 |
| 池打满走快速失败 | 把客户端 `max` 压到很小，压测应看到借连接超时，而不是入站线程被挂死 |

压测数字进[压测报告](/projects/toolkit/perf-report/)；一次具体的慢请求怎么走决策树，见[慢请求剧本](/cloud-native/observability/slow-request)。

## 七、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 为什么出站超时必须短于入站 / 网关？ | **内层先超时才能留下明确错误。** 外层先 504，应用还在读 socket，日志里没有超时，是最难查的一类故障 |
| 2 | `connectTimeout` 和 `readTimeout` 差在哪？ | 前者管 TCP 建连，后者管等响应。漏配读超时 ≈ 无限等待，和 JDBC `socketTimeout=0` 同类 |
| 3 | 还有第三种超时？ | **从本池借连接的等待**（`connectionRequestTimeout`）。池耗尽时请求还没出进程，表现却像「接口慢」 |
| 4 | 504 但没有超时日志说明什么？ | 多半是**外层先超时**。先对网关超时与出站读超时，不要先翻业务代码 |
| 5 | 出站超时配短了要不要靠重试补？ | 可以，但**次数 × 单次 + 退避 < 入站剩余**。补完仍超预算，只是把 504 无日志延迟到第 N 次 |
| 6 | HTTP 客户端连接池和 Hikari 是不是一回事？ | **不是。** 一个护数据库，一个护下游 HTTP。打满原因与调大代价都不同；调错池会把背压送到更脆弱的那一侧 |
| 7 | 为什么不能每次 `new RestTemplate()`？ | 连接不复用，对端 `TIME_WAIT` 与本机句柄一起涨。客户端应是进程内单例 Bean |
| 8 | 虚拟线程下出站调用要注意什么？ | 线程数不再是并发上限。必须给 HTTP 客户端显式池上限与超时，否则等于无限并发打下游 |
| 9 | POST 超时了能不能重试？ | **默认不能。** 超时不代表失败。没有幂等键的写操作，重试会造成重复下单 / 重复扣款 |
| 10 | 客户端、网关、`@Retryable` 都可以重试，怎么选？ | **整条链路只留一层。** 三层各 ×3 是 27 倍脉冲 |
| 11 | Feign / 负载均衡要在这篇配吗？ | **不。** 那些决定打到哪一台；本篇只决定打过去之后等多久。两边都要配 |
| 12 | 怎么证明超时对齐已经生效？ | 下游 hang 住时，本服务在读超时内返回，网关不先 504；链路上重试次数与总耗时可核对 |
