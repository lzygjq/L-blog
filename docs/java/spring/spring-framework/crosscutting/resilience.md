# 重试与并发限制：从 spring-retry 到框架内建

重试是**"看起来最简单、实际最容易造成二次事故"**的容错手段。一个典型的事故链条是：下游支付接口偶发超时 → 加三次重试 → 下游被打成三倍流量 → 彻底雪崩 → **重试把一个抖动放大成了故障**。

更隐蔽的一类问题是：**重试了一个不该重试的操作**。扣款超时不代表扣款失败——它可能已经成功了，只是响应丢了。

> **主线：重试不是"再试一次"，而是一次"以放大流量为代价、换取更高成功率"的交易。**
>
> 这笔交易有三个前提：**错误是可恢复的**（不是参数错、不是权限错）、**操作是幂等的**（重复执行不出错）、**放大后的流量下游能承受**。
>
> 缺任何一个前提，重试都在制造新问题。**而"能不能重试"首先是业务判断，其次才是技术选型。**

## 一、问题场景：重试制造的三种故障 {#why-retry}

| 故障 | 成因 | 表现 |
|---|---|---|
| **流量放大导致雪崩** | 下游已经过载，重试再叠 3 倍流量 | 一个抖动演变成全面不可用 |
| **重复执行业务** | 超时但操作已成功 | **重复扣款、重复发货、重复计费** |
| **重试掩盖真实问题** | 每次都是第 2 次成功 | 慢查询、连接泄漏被"重试好了"盖住，容量悄悄下降 |

第三种最危险，因为它**看起来是"重试生效了"**。健康的重试应该是"偶发成功率提升"，而不是"每次都要重试才成功"——后者说明下游有稳定的问题，应该修它而不是重试它。

**一个必须建立的意识：重试是最后一道防线，不是第一道。** 上游的超时时间、连接池、限流、熔断，任何一个配置错了，都不该用重试来补。

## 二、重试的四个前提 {#preconditions}

在写任何 `@Retryable` 之前，先把这四个问题答完：

| # | 前提 | 判断方法 | 不满足时 |
|---|---|---|---|
| 1 | **错误可恢复** | 是网络抖动、超时、下游临时不可用？还是参数非法、权限不足、业务规则拒绝？ | 只重试**临时性**异常（超时、连接失败、5xx） |
| 2 | **操作幂等** | 重复执行一次，业务结果是否相同？ | **先做幂等**，见[接口幂等](/java/spring/spring-cloud/idempotency) |
| 3 | **下游能承受放大** | 重试次数 × 正常流量 = 下游峰值？ | 加限流 / 减少重试次数 / 只重试部分请求 |
| 4 | **重试有终止** | 有最大次数和总超时？ | 必须显式设置，**禁止无限重试** |

第 1 条的实践落法是**白名单式重试**——只列要重试的异常，而不是"除了这些都不重试"。因为异常类型会随依赖升级增加，白名单的默认行为（不重试）更安全：

```java
@Retryable(includes = {SocketTimeoutException.class, ResourceAccessException.class})
public PaymentResult charge(String paymentId) { ... }
```

## 三、内建重试：Spring Framework 7 的变化 {#built-in}

**Spring Framework 7.0（随 Spring Boot 4.0，2025-11 GA）把重试与并发限制移进了 `spring-core`**，用注解直接可用，不再需要引入 `spring-retry` 或 `Resilience4j`：

```java
@Service
@EnableResilientMethods                        // 开启内建弹性方法支持
public class PaymentService {

    @Retryable(maxAttempts = 3, delay = 100)   // 最多 3 次（含首次），间隔 100ms
    public PaymentResult charge(String paymentId) {
        return gateway.charge(paymentId);
    }

    @ConcurrencyLimit(2)                       // 同时最多 2 个并发调用（舱壁模式）
    public Report generateReport(Long id) {
        return reportGenerator.generate(id);
    }
}
```

**这次变化的意义不只是"少一个依赖"**：

| 维度 | 之前（spring-retry / Resilience4j） | 现在（Framework 7 内建） |
|---|---|---|
| 依赖 | 额外的第三方库 + 各自独立的配置模型 | **`spring-core` 自带** |
| 与 AOP 的关系 | 通过 `Advisor` 织入，顺序需人工对齐 | **与框架其他拦截器共享同一套排序模型** |
| 与响应式 | Resilience4j 单独维护 Reactor 适配 | **同一注解可适配响应式方法** |
| 生态采纳 | — | Spring AMQP、Kafka、Integration、Batch 均已采纳 |

第三行对已经上了 WebFlux 的项目价值最大——此前"命令式用 A、响应式用 B"的割裂被消除。

> **属性名请以所用版本的官方 API 为准。** 内建重试的注解属性在 7.0 系列中仍有过调整（如次数属性的命名），本篇的示例表达的是**语义**：最大尝试次数、初始间隔、包含的异常类型。写代码前请对照当前版本的 Javadoc。

### 3.1 与 `spring-retry` 的迁移对照 {#migrate}

已在用 `spring-retry` 的项目不需要立刻迁移——它仍是可用的第三方库。但如果要迁，对照关系是：

| `spring-retry` | 内建 | 注意 |
|---|---|---|
| `@EnableRetry` | `@EnableResilientMethods` | 开关位置变了 |
| `@Retryable(maxAttempts = 3)` | `@Retryable(...)` | 语义相同，属性名需核对 |
| `@Backoff(delay = 100, multiplier = 2)` | 退避参数直接在注解上 | **嵌套的 `@Backoff` 不再需要** |
| `@Recover` | 保留对应机制 | 恢复方法的匹配规则需重新验证 |
| `@CircuitBreaker` | **不在内建范围** | 熔断仍属**服务级**能力，见[服务保护](/java/spring/spring-cloud/resilience#resilience4j) |

**最后一行是分工的关键**：内建提供的是**方法级重试与并发限制**（进程内、无状态、无跨实例协调）；**熔断、服务级限流、隔离**仍属于 Spring Cloud 的职责。两者不是替代关系。

## 四、退避与抖动：为什么固定间隔是错的 {#backoff}

**固定间隔重试有一个结构性缺陷：它会把重试流量对齐到同一个时间点。**

假设 1000 个请求在下游抖动时同时失败：

```
固定间隔 100ms：                         指数退避 + 抖动：
t=0    1000 个失败                        t=0    1000 个失败
t=100  1000 个重试  ← 同一瞬间             t=100  分散在 50~150ms
t=200  1000 个再重试 ← 又一波洪峰          t=200  分散在 100~500ms
        ↓                                        ↓
   下游被三次同步洪峰冲击                    压力被摊平，下游有机会恢复
```

| 策略 | 特点 | 适用 |
|---|---|---|
| 固定间隔 | 简单，但会形成同步洪峰 | 几乎不用 |
| **指数退避** | 间隔逐次翻倍，给下游恢复时间 | 默认选择 |
| **指数退避 + 抖动（jitter）** | 在退避基础上加随机偏移，**打散洪峰** | **分布式场景的标准做法** |
| 固定退避上限 | 防止间隔无限增长 | 必须配（否则第 10 次重试要等到天荒地老） |

**抖动（jitter）为什么必配**：重试的触发原因（下游抖动）通常是**同时影响大量请求**的，所以它们的重试时间天然同步。不加抖动，指数退避只是把"三次洪峰"变成"三次间隔更长的洪峰"——**并没有解决同步问题**。

**还要给重试设总时长上限**。最大次数与退避相乘可能超出上游的超时时间，导致**上游已经超时放弃了，下游还在重试**——纯粹浪费资源。

## 五、幂等：重试的唯一前提 {#idempotency}

**"超时"不等于"失败"**。这是重试最危险的认知盲区：

```
客户端 ──请求──▶ 服务端 ──扣款──▶ 数据库 ✓
   │                              │
   └────── 响应丢失/超时 ◀────────┘

客户端视角：失败 → 重试 → 又扣了一次
服务端视角：第一次已经成功了
```

**因此可重试的操作必须是幂等的。** 常见的三条实现路径：

| 手段 | 做法 | 适用 |
|---|---|---|
| **业务唯一键** | 用业务单号做唯一索引，重复插入直接失败 | 创建类操作（最可靠） |
| **状态机** | 只有特定状态才允许推进（`待支付 → 已支付`） | 流程类操作 |
| **幂等号 / Token** | 客户端生成 `requestId`，服务端记录已处理的 ID | 通用方案 |

> 幂等的完整设计与 Redis/数据库两种实现见[接口幂等](/java/spring/spring-cloud/idempotency)。**本篇只强调一条**：`@Retryable` 的正确使用顺序是"**先确认幂等，再加重试**"，而不是反过来。

**一个实用的判断句式**：如果重试后产生的结果是"多了一条记录 / 多扣了一笔钱 / 多发了一条消息"，那它就不幂等，**不能加 `@Retryable`**。

## 六、`@Retryable` 与 `@Transactional` 的顺序 {#with-transaction}

这是重试最容易出错的地方。两种写法的语义完全不同：

```java
// 写法 A：重试在外，事务在内 —— 每次重试都是新事务
@Retryable(maxAttempts = 3)
@Transactional
public void process(Long id) { ... }
```

```java
// 写法 B：事务在外，重试在内 —— 重试发生在同一个事务里，几乎无意义
@Transactional
@Retryable                                   // ⚠️ 内层注解通常因自调用失效
public void process(Long id) { ... }
```

| 写法 | 每次重试的事务 | 问题 |
|---|---|---|
| A：重试外 + 事务内 | **新事务** | ✅ 正确。前一次失败的事务已回滚，重试是干净的一次 |
| B：事务外 + 重试内 | 同一事务 | ❌ **事务已被标记 rollback-only**，重试也回滚；且内层注解大概率因自调用失效 |

**写法 B 的核心问题是"事务标记（rollback-only）"**：一旦内层方法抛异常，Spring 会把当前事务标记为"只能回滚"。此后即使重试成功，**提交时仍会抛 `UnexpectedRollbackException`**——表现为"日志显示重试成功了，但数据没进库"。

**正确的做法是让重试包住事务**（写法 A），并且**重试方法本身不加 `@Transactional`**：

```java
@Service
public class OrderService {

    @Retryable(includes = SocketTimeoutException.class, maxAttempts = 3)
    public void submit(Long orderId) {
        self.submitInTx(orderId);            // 走代理，每次重试开一个新事务
    }
}
```

**另一个必须注意的点：重试不能跨"已经产生副作用"的边界重新执行。** 如果一次事务里既写库又发消息，重试会**重复发消息**（库回滚了，消息发出去了）。这类"外部副作用"要放到事务提交之后（`afterCommit`），或必须靠幂等消费端兜底。

## 七、`@ConcurrencyLimit`：线程池的背压消失之后 {#concurrency-limit}

这是一个**新问题**，来自虚拟线程的普及。

传统线程池有一个隐性的好处：**池大小天然就是并发上限**。8 个线程的池，最多 8 个任务同时打向下游——这是一层**免费的保护**。

换成虚拟线程后，这个上限消失了：

```
平台线程池（8 个线程）:
  1000 个任务 ──▶ 排队 ──▶ 最多 8 个并发打向下游     ← 天然的背压

虚拟线程（每个任务一个）:
  1000 个任务 ──▶ 1000 个虚拟线程同时打向下游        ← 下游瞬间被打穿
```

**这正是 `@ConcurrencyLimit` 存在的原因**——它把"池大小"这个隐含的并发上限**显式地表达出来**：

```java
@ConcurrencyLimit(5)              // 同时最多 5 个并发，超出的调用会等待
public Balance fetchBalance(String accountId) { ... }
```

| 场景 | 背压来源 | 是否需要 `@ConcurrencyLimit` |
|---|---|---|
| 平台线程池 | **池大小** | 通常不需要（池大小已限制） |
| **虚拟线程** | **无** | **需要**，否则下游承受全部并发 |
| CPU 密集 + 虚拟线程 | 无 | 需要（虚拟线程对 CPU 密集无收益） |

这是在[虚拟线程的边界](/java/spring/spring-boot/web-server#virtual-threads)（连接池成新瓶颈）之外，**第二处被虚拟线程"拿掉"的保护**：第一处是数据库连接数的天然限制，第二处是线程池的并发上限。

## 八、方法级 vs 服务级：三层容错的分工 {#boundary}

重试、限流、熔断经常被混为一谈，但它们的**作用范围**不同：

```
调用方服务                                     下游服务
┌────────────────────────────────┐
│ 方法级（进程内）                │
│  @Retryable      重试失败的调用 │
│  @ConcurrencyLimit 限制本进程并发│
│            │                    │
│            ▼                    │
│ 服务级（跨实例）                │
│  限流：本服务总 QPS 上限        │
│  熔断：下游持续失败时快速失败   │ ──▶ 不再发起调用
│  隔离：按下游划分配额           │
└────────────────────────────────┘
```

| 层次 | 手段 | 作用范围 | 协调需求 |
|---|---|---|---|
| **方法级** | `@Retryable` / `@ConcurrencyLimit` | 单个 JVM 内的单次调用 | **无**（不需要跨实例协调） |
| **服务级** | 限流 / 熔断 / 隔离 | 整个服务实例或集群 | 通常需要（Sentinel 有集群模式） |
| **架构级** | 降级预案 / 流量调度 / 多活 | 跨系统 | 需要 |

**分工的判据很简单：需不需要知道"其他地方有多少请求在打同一个下游"。**

- **不需要 → 方法级**：单机重试、单机并发限制，各自独立即可
- **需要 → 服务级**：熔断必须知道"整体失败率"，限流必须知道"整体 QPS"

**这条判据也解释了为什么内建重试**没有**提供熔断**——熔断的状态需要跨实例共享才有意义（每个实例各自熔断会导致"部分实例拒绝、部分实例继续打"的碎片化状态）。

> **服务级方案的完整对照**（Hystrix 为什么被移除、Sentinel 与 Resilience4j 的定位差异、降级逻辑写在哪）见[服务保护](/java/spring/spring-cloud/resilience#resilience4j)。本篇讲的是它下面那一层。

## 九、不该重试的清单 {#anti-patterns}

**"什么不该重试"比"怎么重试"更重要。** 六类明确不该重试的：

| # | 场景 | 原因 |
|---|---|---|
| 1 | **参数校验失败、类型错误** | 重试一百次结果相同，纯浪费 |
| 2 | **认证/授权失败（401/403）** | 凭证不会因为重试而变对 |
| 3 | **业务规则拒绝（余额不足、库存不足）** | 这是**正常的业务结果**，不是故障 |
| 4 | **非幂等写操作**（未做幂等） | 重复执行会造成脏数据 |
| 5 | **下游已熔断 / 已明确不可用** | 重试就是往熔断器上撞，加速恶化 |
| 6 | **客户端主动取消 / 上游已超时** | 上游已经不要结果了，重试是纯浪费 |

**第 3 条最容易被误做成重试**：余额不足抛出的异常如果被包进了 `@Retryable` 的捕获范围，会出现"重试 3 次然后报余额不足"的诡异日志——**3 倍的下游压力，换一个必然的失败**。

第 6 条在实践中常被忽略。**重试的总时长必须小于上游的超时时间**，否则会出现"调用方早已超时返回、服务端还在重试链里"的资源空转。这类"幽灵请求"在链路追踪里表现为**没有父 span 的孤立调用**。

## 十、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 什么时候该重试？ | 四个前提全满足时：**错误可恢复**（临时性故障而非业务拒绝）、**操作幂等**、**下游能承受放大后的流量**、**有明确的次数与总时长上限**。缺一个都不该重试 |
| 2 | 重试最危险的场景是什么？ | **超时但实际成功**。客户端看到超时就去重试，而第一次已经扣款了 → **重复扣款**。所以**重试的前提是幂等**，而不是先加重试再补幂等 |
| 3 | 为什么必须配抖动（jitter）？ | 重试的触发原因（下游抖动）通常**同时影响大量请求**，所以重试时间天然同步。指数退避只是把洪峰间隔拉长，**没有打散洪峰**；加随机抖动才能真正摊平 |
| 4 | 固定间隔重试有什么问题？ | 会形成**同步洪峰**：所有失败请求在同一时刻重试，下游被周期性冲击，反而更难恢复 |
| 5 | Spring Framework 7 在这块有什么变化？ | 把**重试与并发限制移入 `spring-core`**（`@Retryable` / `@ConcurrencyLimit` / `@EnableResilientMethods`），不再需要 `spring-retry` 或 Resilience4j，并且**同一注解可适配响应式方法** |
| 6 | 内建重试能替代 Resilience4j / Sentinel 吗？ | **不能**。内建提供的是**方法级**重试与并发限制（进程内、无需跨实例协调）；**熔断、服务级限流、隔离**需要知道"整体失败率/整体 QPS"，属于**服务级**能力，仍属 Spring Cloud 职责 |
| 7 | `@Retryable` 和 `@Transactional` 谁在外层？ | **重试在外、事务在内**。反过来的话重试发生在同一事务中，而事务一旦被抛异常标记为 `rollback-only`，**即使重试成功，提交时仍会抛 `UnexpectedRollbackException`**——表现为"重试成功了但数据没进库" |
| 8 | 重试时重复发了消息怎么办？ | 重试会重新执行方法体，**已产生的外部副作用不会回滚**（库回滚了、消息已发出）。解法是把发消息挪到 `afterCommit`，或由幂等消费端兜底 |
| 9 | `@ConcurrencyLimit` 解决什么问题？ | 虚拟线程普及后，**"线程池大小 = 并发上限"这个天然的背压消失了**——1000 个任务会同时打向下游。`@ConcurrencyLimit` 把这个隐含上限**显式表达出来**（舱壁模式） |
| 10 | 哪些情况明确不该重试？ | 参数校验失败、认证授权失败、**业务规则拒绝**（余额/库存不足，这是正常结果不是故障）、非幂等写、下游已熔断、上游已超时。后两类会造成纯粹的资源浪费 |
| 11 | 上限只在异常类型上白名单还是黑名单？ | **白名单更安全**——只列出要重试的临时性异常（超时、连接失败），因为依赖升级会引入新的异常类型，白名单的默认行为（不重试）不会意外放大流量 |
| 12 | 重试的总时长该设多少？ | **必须小于上游的超时时间**。否则出现"调用方早已超时、服务端还在重试链里"的幽灵请求，在链路追踪里表现为**没有父 span 的孤立调用** |
