# REST 接口设计：状态码、错误契约、分页与演进

[Spring MVC 的执行流程](/java/spring/spring-mvc/)解决的是"**一个请求怎么被处理**"，这一篇解决的是另一个问题：**接口该长什么样**。

两者的区别很实在：流程写错了，错误只发生在一个服务里；接口设计错了，代价由**所有调用方**长期分摊——前端要为你的分页写一套特殊逻辑，网关的重试因为你返回 `200` 而没有生效，监控图上永远看不到真实的错误率，而这些成本都不会出现在任何一次验收里。

> **主线：接口的产出不是"能调通的 URL"，而是一份让调用方不必读你源码就能正确使用的契约。**
>
> 契约要满足三条：**可预测**（同样的输入得到同样的语义）、**可演进**（加东西不破坏调用方）、**可诊断**（出错时能定位到那一次请求）。

## 一、问题场景：接口的"隐性契约" {#why}

调用方真正依赖的东西，比接口文档写的多得多。下面这些**从来没有写在文档里，但一旦改变就会出事**：

| 隐性契约 | 一旦打破的后果 |
|---|---|
| "这个字段永远是整数，不会是字符串" | 前端 `parseInt` 结果变成 `NaN` |
| "这个数组的顺序是稳定的" | 分页出现重复/漏项 |
| "同一个请求重发一次，结果一样" | 网络重试导致重复下单 |
| "错误响应里一定有 `message`" | 前端统一错误处理的代码全部失效 |
| "金额是元，两位小数" | 差 100 倍的资损 |

**接口设计的本质工作，就是把这些隐性约定变成显式约定**（写进类型、写进文档、写进校验规则），并且**在不需要它们改变时提供演进的余地**。

## 二、资源建模：URL 是名词，动词交给 HTTP 方法 {#resource}

REST 的核心不是"用不用 JSON"，而是**把"操作"表达成"对资源的方法调用"**：

```
✅ 资源是名词，动作由方法承担
GET    /orders              列出订单（过滤条件进查询串）
POST   /orders              创建订单
GET    /orders/123          取某一个
PUT    /orders/123          整体替换
PATCH  /orders/123          部分修改
DELETE /orders/123          删除

✅ 归属关系用层级表达
GET    /orders/123/items    订单 123 的明细
GET    /users/42/orders     用户 42 的订单

❌ 动作进了 URL，方法语义丢失
GET    /getOrderList
POST   /createOrder
POST   /deleteOrderById
```

**四条实操规则**：

1. **资源名用复数**（`/orders` 而不是 `/order`）——它的语义是"集合"，`/orders/123` 才是元素；
2. **过滤、分页、排序进查询串**，不进路径：`/orders?status=PAID&page=2&sort=-createdAt`；
3. **路径不要出现文件后缀**（`/orders.json`）——用 `Accept` 头协商；
4. **命名用小写加连字符**（`/order-items`），不用下划线或 camelCase。

### 什么时候可以"破例"用动词

**当这个操作确实不是 CRUD 时，硬套资源化反而更糟**。业界公认的两种破例形态：

```
POST /orders/123/cancel          # 状态迁移，不是"替换整个订单"
POST /orders/123/refund          # 触发一个流程
POST /payments/123/capture       # 支付行业惯例
```

判据很清晰：**如果这个操作有副作用、不幂等、且不能表达成"把资源改成某个样子"，就用动词子资源。** 反面教材是把"修改状态"塞进 `PUT`：

```java
// ❌ 用 PUT 表达状态迁移：语义上是替换，实际只改了一个字段，且不幂等
PUT /orders/123   // body: {"status":"CANCELLED"}
```

### 方法的语义：幂等与安全

| 方法 | 安全（无副作用） | 幂等 | 请求体 | 典型用途 |
|---|---|---|---|---|
| `GET` | ✅ | ✅ | ❌ | 查询 |
| `HEAD` | ✅ | ✅ | ❌ | 只取头（探测存在性、取长度） |
| `POST` | ❌ | ❌ | ✅ | 创建、动作 |
| `PUT` | ❌ | ✅ | ✅ | 整体替换（重复发送结果相同） |
| `PATCH` | ❌ | ❌（默认） | ✅ | 部分修改 |
| `DELETE` | ❌ | ✅ | ❌ | 删除（重复删除应返回 404 或 204） |

**幂等性是"重试"这件事的前提**——网关、服务网格、HTTP 客户端都会在超时后重试。**一个不幂等的接口被重试，就是一次重复业务。** 所以：

- `PUT` 天然安全（结果只取决于 body）；
- `POST` **需要幂等键**（见[第七节](#idempotency)）；
- `GET` 绝不能有副作用——**包括"顺手记一条访问日志到数据库"这种**（它是安全的，但不该在 `GET` 里做写操作，因为爬虫与预取会放大它）。

**`PUT` 是整体替换，`PATCH` 是部分修改**，这个差别在并发下很重要：

```java
// PUT：未出现的字段会被清空（语义是"这就是新状态"）
PUT /users/42   {"name":"张三"}

// PATCH：只改给出的字段
PATCH /users/42 {"name":"张三"}
```

`PATCH` 的标准格式有两种，**不指定的话调用方只能靠猜**：JSON Merge Patch（RFC 7386，直观、无法表达数组操作）与 JSON Patch（RFC 6902，用 `op/path/value` 数组，能力完整但可读性差）。**在 `Content-Type` 里明确**：`application/merge-patch+json` 或 `application/json-patch+json`。

## 三、状态码：4xx 与 5xx 的分界线是"谁的错" {#status}

这条分界线看起来只是分类，实际上决定了好几件事：

| 分界 | 含义 | 谁该行动 | 监控与告警 |
|---|---|---|---|
| **4xx** | **调用方的错**（请求不合法、无权限、资源不存在） | **调用方** | 不该触发告警（除非突增） |
| **5xx** | **服务端的错**（异常、依赖不可用、超时） | **你** | **必须触发告警** |

**所以"一律返回 200 + `code` 字段"这种做法的问题不只是不规范**，它会让三层基础设施同时失效：

```
① 监控与告警：错误率曲线永远是 0 —— 你只能靠日志发现问题
② 网关/服务网格重试：重试策略通常按状态码配置（5xx / 429 才重试），
   200 会被当作成功，该重试的不重试，不该重试的（4xx）反而可能被重试
③ 熔断与负载均衡：把业务失败算成健康，故障实例继续接流量
```

**高频状态码清单**（按"必须记住"排序）：

| 码 | 语义 | 用在什么场景 | 容易搞错的点 |
|---|---|---|---|
| **200** | OK | 查询成功、修改成功 | — |
| **201** | Created | 创建成功，**响应头带 `Location`** 指向新资源 | 不返回 `Location` 就不符合规范 |
| **202** | Accepted | 已受理、异步处理中 | 要用查询接口或 `Location` 告知结果怎么取 |
| **204** | No Content | 成功且**无响应体**（DELETE、PUT） | 返回 204 时不能带 body |
| **400** | Bad Request | 请求**格式**错误（JSON 解析失败、缺必填参数） | 与 422 的边界见下 |
| **401** | Unauthorized | **未认证**（没带凭证/凭证无效） | 名字有误导，实际是"未认证" |
| **403** | Forbidden | **已认证但无权限** | 与 401 的区分：**重新登录能不能解决？能 → 401，不能 → 403** |
| **404** | Not Found | 资源不存在 | **越权时也返回 404**（避免通过 403/404 的差异探测资源是否存在） |
| **405** | Method Not Allowed | 路径对但方法不对 | 响应头应带 `Allow` |
| **409** | Conflict | 与当前资源状态冲突（版本冲突、唯一键重复、状态机不允许） | 乐观锁失败用它，比 400 准确得多 |
| **412** | Precondition Failed | `If-Match` 条件不满足 | 与 409 的分工见[第七节](#idempotency) |
| **415** | Unsupported Media Type | `Content-Type` 不支持 | 前端发了表单、后端只收 JSON 时会遇到 |
| **422** | Unprocessable Entity | 格式正确但**业务校验不通过** | 与 400 的边界：**能不能解析成对象**——能解析但字段值非法 → 422 |
| **429** | Too Many Requests | 限流 | 带 `Retry-After` |
| **500** | Internal Server Error | 未预期异常 | **绝不能把堆栈或 SQL 返回给调用方** |
| **502 / 504** | 上游错误 / 网关超时 | 反向代理层产生 | 排查时要区分"我的服务慢了"与"我的服务挂了" |
| **503** | Service Unavailable | 主动摘除、维护中 | 带 `Retry-After` |

> **400 与 422 怎么选？** 有一条很干脆的判据：**请求体能不能被正确地反序列化成对象。** 不能（JSON 语法错、类型不匹配、缺必填字段导致无法构造）→ **400**；能构造出对象、但**业务规则不通过**（金额为负、状态不允许）→ **422**。
>
> 只在客户端自己校验收到的值、人来看错误信息时，两者差别不大；**但在网关重试与告警策略上，它们都属 4xx，不加区分是对的**。真正需要区分的是 4xx 与 5xx。

**`Retry-After` 是一个被严重低估的响应头**：429 与 503 上带上它，客户端就知道"多久之后再来"，而不是立刻重试把服务打得更死。

## 四、错误契约：让调用方不必读你的源码 {#errors}

**统一错误体是接口设计里收益最高的一处约定**。它的价值在于：调用方可以写**一套**错误处理代码，覆盖全部接口。

```
{
  "code": "ORDER_ALREADY_PAID",          // 机器可判断的业务码（稳定、可枚举）
  "message": "订单已支付，无法取消",       // 给人看的提示（可国际化、可调整）
  "traceId": "a1b2c3d4e5f6",             // 串起日志与链路
  "details": [                            // 字段级错误（校验失败时）
    {"field": "amount", "code": "MIN_VALUE", "message": "金额必须大于 0"}
  ],
  "timestamp": "2026-09-17T10:30:00+08:00",
  "path": "/orders/123/cancel"
}
```

**五条设计纪律**：

| 纪律 | 为什么 |
|---|---|
| **`code` 是给机器读的，稳定且可枚举** | 客户端要用它做分支判断（提示不同文案、走不同补救流程），所以**不能直接复用 `message`** |
| **`message` 是给人读的，允许变化** | 文案改了不该算破坏性变更 |
| **`traceId` 必须返回** | 用户报障时能一句话定位到那次请求。这是[可观测性](/cloud-native/observability/)三支柱真正串起来的接口层开关 |
| **绝不返回堆栈、SQL、类名** | 既是安全问题（泄露结构），也是痕迹问题（调用方会开始依赖它们） |
| **错误码分层**：HTTP 状态码给类别，业务 `code` 给具体原因 | 网关看状态码，业务看 `code`，各取所需 |

**Spring 侧的落地**：`@RestControllerAdvice` + `@ExceptionHandler` 把异常翻译成上面这个结构。两条常被混淆的异常链（参数校验异常与方法级校验异常）、以及如何让框架异常自动变成 `ProblemDetail`，已经在[参数校验与统一异常](/java/spring/spring-framework/crosscutting/validation#two-exception-chains)里写透了——**这一篇只定契约，不重复实现。**

**RFC 9457（`ProblemDetail`）值得单独提一句**：它是 HTTP API 错误响应的**标准格式**（`type` / `title` / `status` / `detail` / `instance`），Spring 6 起内建支持。选它的理由是**零成本获得跨团队共识**——新同事、外部合作方不需要学你的私有格式。**自有格式的代价只有在对接方变多时才显现**，那时改已经晚了。

```java
// Spring 6+ 内建，返回的 Content-Type 是 application/problem+json
ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "订单已支付，无法取消");
pd.setType(URI.create("https://api.example.com/errors/order-already-paid"));
pd.setProperty("traceId", traceId);
return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
```

**一个容易被忽略的约定**：**列表查询返回空集合时用 200 + `[]`，不要用 404。** `404` 的语义是"这个资源不存在"——`/orders?status=PAID` 这个**查询**本身是存在的，只是结果为空。混用的后果是前端要把"空列表"和"接口挂了"分开处理。

## 五、分页：offset 的深翻页代价与游标分页 {#pagination}

分页是接口设计里最"看起来简单、出事最多"的一块。

### 5.1 offset 分页的两个固有缺陷

```
GET /orders?page=5000&size=20      →  LIMIT 100000, 20
```

**缺陷一：性能断崖。** 数据库必须**先扫描并丢弃前 100000 行**才能返回第 5000 页。这不是索引能解决的问题——[深度分页优化](/database/mysql/diagnosis)里讲的"延迟关联/子查询定位起点"都只是缓解，因为**`OFFSET` 本身要求"跳过"这个动作**。

**缺陷二：数据漂移。** 翻页过程中如果有新数据插入到前面，第 2 页会**重复出现第 1 页的末条**；有删除则**漏掉**。这是分页错乱的经典成因，而且它**只在生产的高频写入下出现**，测试环境很难复现。

### 5.2 游标分页

```
GET /orders?cursor=eyJpZCI6MTIzNDV9&limit=20

-- 服务端翻译成：
SELECT * FROM orders WHERE id > 12345 ORDER BY id LIMIT 20
```

| 维度 | offset 分页 | 游标分页 |
|---|---|---|
| 深翻页性能 | 线性退化（`LIMIT 100000, 20`） | **恒定**（走索引定位起点） |
| 数据漂移 | ✅ 会重复/漏项 | **不会**（游标是"从哪继续"，不是"第几页"） |
| 能否跳页 | ✅ 能直接跳第 500 页 | ❌ 只能前后顺序翻 |
| 能否给总数 | ✅ 能 | ⚠️ 需要单独一次 `count`（成本高，常改为"是否有下一页"） |
| 实现复杂度 | 低 | 中（游标要编码、要防篡改） |
| 适合 | 后台管理、数据量小、需要跳页 | **信息流、时间线、导出、大表遍历** |

**选型判据**：**用户会去点"第 500 页"吗？** 不会（信息流只往下滑）→ 游标。会（后台列表要跳页、要排序）→ offset，但**要限制最大页深**（例如最多 100 页），并对超出的请求返回 400 而不是硬扛。

**游标的设计要点**：

```java
// 游标内容 = 排序键的完整元组（保证全序，避免并列导致漏项）
{"createdAt": "2026-09-17T10:30:00Z", "id": 12345}
→ Base64 编码（可选签名，防止调用方伪造越权查询）

// 排序键必须唯一或加上唯一列（如 id）作为最后一位
ORDER BY created_at DESC, id DESC
WHERE (created_at, id) < (?, ?)      -- 元组比较，比 OR 链更清晰
```

**响应结构要把"下一页怎么取"显式给出**：

```json
{
  "items": [ ... ],
  "pageInfo": {
    "nextCursor": "eyJpZCI6MTIzNDV9",   // null 表示没有下一页
    "hasMore": true,
    "total": 12843                        // 可选，成本高时省略
  }
}
```

> **`total` 是最常被滥用的字段**：`SELECT COUNT(*)` 在大表上是全扫描级别的成本，而多数 UI 只是用它显示"共 12843 条"。**权衡：精确总数（贵）、估算总数（`EXPLAIN` 的行数估计，便宜且够用）、或者干脆不返回、只给 `hasMore`。** 关键是**显式决策**，而不是默认返回一个拖慢接口的字段。

## 六、演进与版本：什么改动是兼容的 {#versioning}

**接口一旦发布就被调用方依赖，所以"能不能改"比"怎么设计"更重要。** 先建立一份分类表：

| 改动 | 是否兼容 | 说明 |
|---|---|---|
| **加响应字段** | ✅ 兼容 | **前提：调用方不因未知字段报错**（严格反序列化的客户端会挂——所以要在文档里说明"响应可能新增字段"） |
| **加可选请求参数** | ✅ 兼容 | 缺省时有默认行为 |
| **加新的枚举值** | ⚠️ **伪兼容** | 老客户端遇到未知枚举值可能直接抛异常。**枚举是"兼容性陷阱"最集中的地方** |
| **把必填改为可选 / 把可选改为必填** | ❌ 后者不兼容 | — |
| **字段类型变化**（int → string） | ❌ 不兼容 | 前端 `parseInt("123abc")` 这类问题 |
| **字段语义变化**（元 → 分） | ❌ **最危险** | 类型不变、编译不报错、调用方完全无感——**只有对账时才发现差了 100 倍** |
| **删除字段 / 删除枚举值** | ❌ 不兼容 | — |
| **URL 路径变化** | ❌ 不兼容 | — |
| **错误码语义变化** | ❌ 不兼容 | 客户端在用 `code` 做分支 |

**"加字段"这条要单独强调**：它是**唯一一类绝大多数情况安全的改动**，所以**接口演进的首选策略是"只加不改"**——需要改语义时，加一个新字段（`amountCents`）而不是改老字段（`amount`），两者并行一段时间，等调用方迁完再移除老字段。

### 版本策略

| 策略 | 形态 | 优点 | 代价 |
|---|---|---|---|
| **URL 路径** | `/v1/orders` | 最直观、最好调试、缓存与日志友好 | URL 不"纯"；版本与资源名耦合 |
| **请求头** | `API-Version: 1` | URL 干净 | 不好调试（浏览器地址栏看不出来）、容易被代理剥掉 |
| **媒体类型** | `Accept: application/vnd.example.v1+json` | 语义最"正确"（内容协商） | 调用方几乎都会写错，工具支持差 |
| **查询参数** | `/orders?version=1` | 简单 | 与缓存、日志的配合都别扭 |

**实用结论：URL 路径版本是绝大多数团队的正确选择**——它的收益（可读、可调试、可观测）远大于"URL 不够纯粹"的代价。

**但更重要的是：能不升版本就别升。** 大版本是**成本最高**的演进手段——它意味着维护两套接口、两份文档、两张监控图，且**必须推动所有调用方迁移**。真正的次序应该是：

```
① 加字段 / 加可选参数（零成本）
   ↓ 不够用
② 加新字段并行、老字段标废弃（低成本，可控迁移）
   ↓ 语义确实无法兼容
③ 新增接口路径（/orders/search），老接口保留
   ↓ 整体不兼容、且愿意承担双份维护
④ 起 v2
```

### 废弃流程：让调用方"知道并且有时间"

删除任何东西之前，**调用方必须先知道**。标准动作是三个响应头 + 一份监控：

```http
Deprecation: @1740000000                    # 该资源已废弃（时间戳）
Sunset: Wed, 31 Dec 2026 23:59:59 GMT       # 正式下线时间
Link: <https://api.example.com/v2/orders>; rel="successor-version"
```

配套的**关键一步是"按调用方统计用量"**：在网关或日志里按 `client_id` + 接口路径聚合，于是"还有谁在用老接口"是一个可以查的问题，而不是一个要发邮件问的问题。**没有这一步的废弃计划，最后都会变成"不敢删"。**

## 七、幂等与并发控制 {#idempotency}

### 7.1 幂等键：让重试变安全

`POST` 不幂等，而**网络超时后重试是必然发生的**（客户端重试、网关重试、用户连点两次）：

```
用户点击「提交订单」
   → POST /orders
   → 服务端处理成功，但响应在网络上丢了
   → 客户端超时重试
   → 又创建了一个订单  ← 重复下单
```

**标准解法是幂等键**：调用方生成一个唯一值（UUID），在同一笔业务操作的所有重试里**使用同一个值**。

```http
POST /orders
Idempotency-Key: 7f3c1e2a-...-9b4d

服务端处理：
  ① 以幂等键在「幂等记录表」中尝试插入（唯一索引）
     ├─ 插入成功 → 这是第一次，执行业务，把结果存进记录
     └─ 插入失败 → 这是重试，直接返回已存的结果（不重复执行）
  ② 记录需带过期时间（如 24 小时）与状态（处理中 / 已完成）
```

**四个工程细节**：

| 细节 | 做法 |
|---|---|
| **原子性** | 用**唯一索引**兜底，而不是"先查再插"（并发下两者都会通过检查） |
| **记录什么** | 请求指纹（body 哈希）+ 响应结果。**body 不同但键相同 → 返回 409**（防止误用同一个键发不同请求） |
| **处理中怎么办** | 返回 409 + `Retry-After`，让调用方稍后查询，而不是阻塞等待 |
| **何时过期** | 覆盖"业务上可能的重试窗口"即可（订单类通常 24 小时） |

**幂等不只是接口层的事**：即使接口做了幂等，**数据库的唯一约束仍然是最后一道防线**（`(user_id, idempotency_key)` 或业务唯一键）。**接口层的幂等会被绕过（有人直接调内部服务），数据库约束不会。**

### 7.2 乐观锁：并发修改的两种表达

两个用户同时改同一条数据——**后写的覆盖先写的（lost update）**。两种标准解法：

| 方案 | 表达 | 适用 | 冲突时返回 |
|---|---|---|---|
| **`ETag` / `If-Match`** | 响应带 `ETag: "v7"`，更新时 `If-Match: "v7"` | REST 语义最正统，**同一份数据有多个表现形式时** | **412 Precondition Failed** |
| **版本号字段** | 响应带 `"version": 7`，更新时 body 里带 `version` | 实现最直接，前端友好 | **409 Conflict** |

```http
GET /orders/123
→ 200 OK
  ETag: "7"

PUT /orders/123
If-Match: "7"
{ ... }

→ 200 OK            （版本匹配，更新成功，返回新 ETag）
→ 412 Precondition Failed   （版本已被别人改过，请重新获取）
```

**两者不要混用**（有的接口用 412、有的用 409，调用方就得写两套）。**推荐：对外接口用 `ETag`/`If-Match` + 412；内部服务之间用版本号字段 + 409**——前者的优势是"不需要在 body 里出现技术字段"，后者胜在直观。

**并发控制的另一面是"业务状态机校验"**：`POST /orders/123/cancel` 在订单已发货时返回 **409**（而不是 400）——**409 的含义就是"请求与资源当前状态冲突"**，这与乐观锁失败是同一类的语义。

> **一个反直觉的结论**：并发冲突的返回码选错（用 400 而不是 409/412），不会让功能坏掉——但会让**调用方无法区分"请求写错了"和"需要重新获取数据再试一次"**，于是要么盲目重试（放大冲突），要么直接报错给用户（体验差）。**这类错误的代价不在第一次实现，而在每一次新增调用方。**

## 八、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | RESTful 的核心原则是什么？ | **用资源（名词）表达状态，用 HTTP 方法（动词）表达操作，用状态码表达结果**。URL 里出现 `/getOrder`、`/createOrder` 这类动词，说明方法语义被浪费了。**破例只用于确实不是 CRUD 的动作**（`/orders/123/cancel`） |
| 2 | `PUT` 和 `PATCH` 的区别？ | `PUT` 是**整体替换**（未提到的字段被清空），`PATCH` 是**部分修改**。两者都改资源，但并发语义不同。`PATCH` 必须声明格式（`application/merge-patch+json` 或 `json-patch+json`），否则调用方只能猜 |
| 3 | 为什么不能一律返回 200 + `code` 字段？ | 会让三层基础设施同时失效：**监控告警**（错误率永远为 0）、**网关重试**（按状态码配置，200 被当成功）、**熔断与负载均衡**（业务失败算成健康）。状态码是**给基础设施看**的，业务码是**给业务看**的 |
| 4 | 400 和 422 怎么区分？ | **能不能反序列化成对象**：不能（JSON 语法错、类型不符）→ **400**；能构造出对象但**业务规则不通过**（金额为负、状态不允许）→ **422**。两者同属 4xx，对重试与告警策略而言不需要区分 |
| 5 | 401 和 403 的区别？ | **401 = 未认证**（没带凭证或凭证无效），**403 = 已认证但无权限**。实用判据：**"重新登录能不能解决？"** 能 → 401，不能 → 403。补充：**越权访问时应返回 404**，避免通过 403/404 的差异探测资源是否存在 |
| 6 | 接口错误响应该怎么设计？ | **统一结构 + 稳定业务码 + `traceId`**：`code`（机器判断，稳定可枚举）、`message`（给人看，可变）、`traceId`（串日志与链路）、`details`（字段级校验错误）。**绝不返回堆栈与 SQL**。可考虑 RFC 9457 的 `ProblemDetail` 换取跨团队共识 |
| 7 | 深分页为什么慢？怎么优化？ | 因为 `LIMIT 100000, 20` 要求**先扫描并丢弃前 100000 行**，这是 `OFFSET` 的语义决定的，索引救不了。方案：**游标分页**（`WHERE id > ? ORDER BY id LIMIT 20`，性能恒定）、延迟关联/子查询定位起点（缓解但仍是 offset 语义）、限制最大页深 |
| 8 | offset 分页除了慢还有什么问题？ | **数据漂移**：翻页期间有新增会让第 2 页重复第 1 页的末条，有删除则漏项。**它只在高频写入的生产环境出现**，测试环境难复现。游标分页天然没有这个问题（游标表达"从哪继续"而非"第几页"） |
| 9 | 游标分页的游标里放什么？ | **排序键的完整元组**（如 `created_at + id`），保证全序——只放 `created_at` 会因时间并列而漏项。可 Base64 编码 + 签名，防止调用方伪造出越权查询。**代价是不能跳页，且总数需要单独统计** |
| 10 | 哪些接口改动是破坏性的？ | **类型变化、字段删除、可选改必填、URL 变化、错误码语义变化、字段语义变化（元→分，最危险：类型不变、编译不报错）**。相反**加响应字段是兼容的**（前提是调用方不因未知字段报错）。**加枚举值是"伪兼容"**——老客户端遇到未知枚举可能直接抛异常 |
| 11 | 接口版本怎么管？ | **能不升就别升**，次序：加字段 → 加新字段并行/老字段标废弃 → 加新路径 → 起 v2。真要版本化，**URL 路径版本**（`/v1/orders`）是最实用的选择（可读、可调试、可观测）。**废弃必须先能按调用方统计用量**，否则最后都会"不敢删" |
| 12 | `POST` 不幂等，重试导致重复下单怎么办？ | **幂等键**：调用方为同一笔业务操作生成唯一 `Idempotency-Key`，服务端用**唯一索引**做原子占位（不是"先查再插"），命中即返回已存结果；键相同而 body 不同返回 409。**数据库唯一约束是最后一道防线**——接口层的幂等会被绕过 |
| 13 | 并发修改同一条数据怎么处理？ | **乐观锁**两种表达：`ETag` + `If-Match`（冲突返回 **412**，更正统）、版本号字段（冲突返回 **409**，更直观）。选一种统一用，不要混。**状态机冲突（订单已发货无法取消）也用 409**——它的语义就是"与资源当前状态冲突" |
