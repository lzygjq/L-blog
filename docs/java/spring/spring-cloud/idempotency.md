# 接口幂等

## 一、幂等是什么，和"防重"差在哪 {#what}

**幂等**：同一个操作执行一次和执行多次，**产生的结果和对业务状态的影响完全相同**。

**先做一个容易混的辨析**——幂等和「防重」不是同一件事：

| | 幂等 | 防重 |
|---|---|---|
| 关注点 | **执行多次，结果一致** | **识别并拦截重复请求** |
| 效果 | 重复执行也不会错 | 第二次直接不执行 |
| 例子 | `UPDATE account SET balance = 500 WHERE id = 1` | 订单号唯一索引 |
| 关系 | **防重是实现幂等的一种手段**，但不是唯一手段 | 有些操作天然幂等，**根本不需要防重** |

**为什么这个区分有价值**：面试时被问「怎么保证幂等」，很多人条件反射答「加分布式锁」——但如果是 `SET status = 'PAID'` 这种操作，**它本身就是幂等的，加锁纯属浪费**。先判断「这个操作有没有天然幂等性」，再决定要不要引入额外机制，才是正确顺序。

## 二、什么时候必须做幂等 {#when}

幂等不是"锦上添花的规范"，而是**分布式环境下的必然要求**。原因在于：网络不可靠，而"不可靠"的具体表现形式就是**重复**。

| 场景 | 为什么会重复 |
|---|---|
| **用户重复点击提交** | 手抖、网络慢导致用户以为没提交成功、按钮没置灰 |
| **MQ 消息重复消费** | 绝大多数 MQ 是 **at-least-once**（至少一次）语义——**重复是承诺内的行为，不是 bug** |
| **超时重试** | Feign 重试、网关重试、Nginx 重试、业务代码重试，每一次都可能实际已经成功 |
| **定时任务重复触发** | 调度器重试、执行器集群未协调好、任务超时后又被调度 |
| **支付回调重复通知** | 支付平台的回调机制本身就是**重复通知直到收到成功应答**——这是最经典也最危险的一个 |

**支付回调最需要注意**：它不由你控制、且一定会重发。如果回调处理不幂等，用户付一次钱可能被加两次额度。**这类"外部系统主动重复投递"的场景，没有不做的选项。**

## 三、HTTP 方法的天然幂等性 {#http}

| 方法 | 语义 | 幂等？ | 说明 |
|---|---|---|---|
| `GET` | 查询 | **是** | 只读，天然幂等 |
| `DELETE` | 按唯一标识删除 | **是** | 删一次和删多次，最终结果都是"不存在" |
| `PUT` | **全量替换** | **有条件** | 见下 |
| `POST` | 新增 | **否** | 每次都是一条新记录 |

**`PUT` 的"有条件"是这个话题里最值得说的一个细节**：

```http
PUT /account/1
{ "balance": 500 }          → 【幂等】：无论调多少次，余额都是 500

PUT /account/1/transfer
{ "amount": 100 }           → 【不幂等】：调 2 次就转了 200
```

第二种写法在**语义上其实是错的**——它表达的是"增量修改"，REST 里应当用 `PATCH`，或者把请求设计成携带唯一业务号的"提交一个转账指令"（这样又回到幂等）。

**但要清醒地认识到**：**HTTP 方法的幂等性只是"语义约定"，不是"运行时保证"**。服务端完全可以把 `PUT` 实现成不幂等的。所以：

> 「我们用 PUT 所以是幂等的」——`PUT` 只保证"调多次和调一次**应该**得到同样结果"，**具体实现还得自己保证**。面试时把这两层分开说，比只说 HTTP 语义完整。

## 四、四类方案与各自的适用边界 {#solutions}

### 4.1 数据库唯一索引 {#unique-index}

**最可靠、最简单**，适合**新增**类操作。

```sql
-- 业务唯一键（订单号）建唯一索引
ALTER TABLE `order` ADD UNIQUE KEY `uk_order_no` (`order_no`);
```

```java
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // 关键：不是报错，而是返回【已经存在的那个结果】
    // 否则用户看到"下单失败"，但其实订单已经建好了
    return orderMapper.selectByOrderNo(order.getOrderNo());
}
```

**一个必踩的坑**：不能只靠"先查再插"。

```java
// ❌ 并发下会漏：两个请求同时查到"不存在"，然后都插入
if (orderMapper.selectByOrderNo(no) == null) {
    orderMapper.insert(order);
}

// ✅ 必须靠数据库的唯一约束兜底 —— 唯一索引是【原子】的
```

「先查再插」在单线程下没问题，**是一个很容易在测试环境通过、一上生产就出问题的写法**。这类"检查后执行"的竞态是最典型的并发陷阱。

**局限**：只适用于插入；且唯一键必须是**业务上真正唯一的**（不能拿自增 ID 或时间戳凑）。

### 4.2 Token + Redis {#token}

适合**表单提交、新增 / 修改**，是"前后端配合"的方案：

```text
① 进入页面 / 打开弹窗时，先请求 token 接口
     服务端：生成 UUID → SET token:{uuid} 1 EX 300 NX → 返回 uuid
        │
        ▼
② 前端提交表单时带上这个 token
        │
        ▼
③ 服务端【原子地】校验并删除
     Lua 脚本 / GETDEL：
       · 删除成功（返回 1）→ token 有效 → 执行业务
       · 删除失败（返回 0）→ token 不存在 → 重复请求，直接拒绝
        │
        ▼
④ 执行业务
```

**第 ③ 步"原子"两个字是全部要点**：

```java
// ❌ 分开两步：两个并发请求可能【都】判到存在，然后都执行业务
if (redis.hasKey(key)) {
    redis.delete(key);
    doBusiness();
}

// ✅ 用 Lua 保证"判断 + 删除"是一个原子操作，只有一个请求能拿到 1
String script = "if redis.call('get', KEYS[1]) == ARGV[1] "
              + "then return redis.call('del', KEYS[1]) else return 0 end";
Long result = redis.execute(new DefaultRedisScript<>(script, Long.class), keys, value);
if (result == null || result == 0L) {
    throw new BizException("请勿重复提交");
}
doBusiness();
```

**局限与配套**：

- **只防"同一个 token 被重复使用"**，不防"用户拿到两个 token 提交两次"——所以 token 的发放时机要卡在"即将提交"之前，不能一进页面就发一堆
- token 要**设过期时间**（否则用户拿到不提交，Redis 里堆积）
- 前端要处理"提交失败后 token 已失效"的情况——**如果业务执行失败，token 是否该恢复？** 通常**不恢复**（要求用户重新操作），否则会引入新的一致性问题

### 4.3 分布式锁 {#lock}

适合**并发不高的新增 / 修改**场景：

```java
String lockKey = "order:create:" + orderNo;
RLock lock = redissonClient.getLock(lockKey);
if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
    throw new BizException("操作进行中，请稍后重试");
}
try {
    // 加锁后再查一次状态（双重检查）
    if (orderMapper.existsByOrderNo(orderNo)) {
        return orderMapper.selectByOrderNo(orderNo);
    }
    return doCreate(orderNo);
} finally {
    lock.unlock();
}
```

**为什么"性能较差"**：它把并发**串行化**了——同一时刻只有一个请求能进来。在 QPS 高的接口上，锁竞争本身会成为瓶颈。

**更关键的认知**：加锁只是"让重复请求排队等待"，**它并没有真正解决"如何识别这是重复请求"**——排在前面的执行完，后面的进来仍然要再做一次状态判断。所以锁**必须配合业务状态判断**（上面的双重检查）才成立，单靠锁不构成幂等方案。

**锁的细节坑**（详见[分布式锁与消息队列](/database/redis/lock-and-mq)）：加锁要设过期时间、释放要校验持有者、业务耗时可能超过锁过期时间。

### 4.4 状态机方案：最优雅的一种 {#state-machine}

**如果业务本身有状态流转，用状态判断天然实现幂等**，不需要任何额外组件：

```sql
-- 支付回调：只有从 UNPAID 变成 PAID 才生效
UPDATE `order`
   SET status = 'PAID', pay_time = NOW()
 WHERE id = ? AND status = 'UNPAID';
-- 返回【影响行数】
--   1 → 首次处理成功
--   0 → 说明订单已不是 UNPAID（已处理过 / 状态不对），直接返回成功
```

```java
int affected = orderMapper.markPaid(orderId);
if (affected == 0) {
    log.info("订单 {} 已处理过，忽略重复回调", orderId);
    return Result.success();   // 注意：返回成功，不是失败
}
```

**为什么这是最优方案**：

| 优点 | 说明 |
|---|---|
| **无需额外组件** | 不用 Redis、不用锁、不用去重表 |
| **天然原子** | `WHERE status = ?` 本身就是 CAS（比较并交换）语义，并发下也不会错 |
| **可读性好** | 业务意图清楚："只有未支付的订单才能被标记为已支付" |

**适用条件**：操作必须是**状态流转**。如果是"新增一条记录"，没有"当前状态"可判断，就只能回到唯一索引方案。

**注意返回值的语义**：重复回调应该返回**成功**（让支付平台停止重发），而不是报错——报错会导致支付平台持续重试，把日志刷爆。

## 五、MQ 消费幂等 {#mq}

MQ 是重复的重灾区，因为**至少一次投递是它的语义承诺**：

```text
消息投递 → 消费成功 → 但【提交 ack 时网络失败】
   → Broker 认为没消费成功 → 重投
   → 该消息被消费了两次（业务已执行，ack 没到）
```

**所以"业务成功但 ack 失败"是必然会发生的情况**，不能假设"消费成功就不会重投"。

三种做法：

| 做法 | 说明 |
|---|---|
| **业务唯一键 + 唯一索引** | 消息携带业务唯一 ID，落库时靠唯一约束去重（**推荐，最可靠**） |
| **去重表 / 消息消费记录表** | 单独一张表记录已消费的 `messageId`，消费前先查 / 先插 |
| **Redis `SETNX` 标记** | `SET msg:{messageId} 1 EX 86400 NX`，设置成功才消费（**注意 Redis 数据丢失会导致去重失败**） |

**关于 Redis 做去重的可靠性**：Redis 挂了 / 被清空后，去重记录就没了，重复消息会被再次执行。所以**核心业务（资金、库存）应该用数据库唯一约束，Redis 只用于非核心场景**。

## 六、方案对比 {#compare}

| 方案 | 适用操作 | 性能 | 需要额外组件 | 可靠性 | 推荐度 |
|---|---|---|---|---|---|
| **状态机（条件更新）** | 状态流转 | 最好 | 无 | 高 | ★★★★★ 首选 |
| **数据库唯一索引** | 新增 | 好 | 无（仅索引） | **最高** | ★★★★★ 新增首选 |
| **Token + Redis** | 新增 / 修改 | 好 | Redis | 中高 | ★★★★ 表单场景 |
| **MQ 去重表** | 消息消费 | 中 | 无 / Redis | 高（用 DB 时） | ★★★★ |
| **分布式锁** | 新增 / 修改 | **差** | Redis / ZK | 中 | ★★ 并发低时可用 |

**选择顺序**：**先看能不能用状态机**（最优雅、零成本）→ 新增类用**唯一索引** → 前端交互类用 **Token** → 都不合适才考虑**分布式锁**。

## 七、常见坑 {#pitfalls}

| 坑 | 现象 | 原因 |
|---|---|---|
| **"先查再插"当幂等** | 测试通过，生产出现重复数据 | 并发下两个请求都查到"不存在"，**必须靠唯一索引兜底** |
| **Token 校验和删除分两步** | 并发下两个请求都通过 | 必须用 Lua / `GETDEL` 保证原子 |
| **唯一索引冲突直接抛异常给用户** | 用户看到"下单失败"，但订单其实建好了 | 应捕获后**返回已存在的结果** |
| **重复回调返回失败** | 支付平台持续重发、日志刷爆 | 重复请求应返回**成功**（让它停止重发） |
| **Redis 去重当核心方案** | Redis 重启后重复消费 | 核心业务用数据库唯一约束 |
| **分布式锁没配业务状态判断** | 锁释放后仍可能重复执行 | 锁只做串行化，**必须配双重检查** |
| **给天然幂等的操作加锁** | 白增开销、还引入锁的问题 | `SET status=?`、`SET balance=?` 本身幂等，不需要防重 |
| **只防了前端重复点击** | 所有后端触发路径（重试、MQ、回调）仍会重复 | 幂等必须在**服务端**做，前端置灰只是体验优化 |

## 面试口径

- **定义**：同一操作执行一次与多次，**结果和对业务状态的影响完全相同**。
- **幂等 vs 防重**：防重是"识别并拦截重复请求"（**实现幂等的一种手段**）；幂等是"重复执行不出错"。**有些操作天然幂等，不需要防重**——先判断这一点，再决定要不要上机制。
- **必须做幂等的场景**：用户重复点击、**MQ 重复消费（at-least-once 是语义承诺，不是 bug）**、超时重试（Feign / 网关 / Nginx / 业务重试）、调度重复触发、**支付回调重复通知**。
- **HTTP 方法的幂等性**：`GET` / `DELETE` 幂等；`PUT` **有条件幂等**（全量替换幂等，`amount += 100` 这种增量不幂等，语义上应属 `PATCH`）；`POST` 不幂等。**并且这只是语义约定，不是运行时保证**——实现还得自己做。
- **四类方案与边界**：**状态机条件更新**（状态流转首选，`WHERE status=?` 自带 CAS 语义，零额外组件）、**数据库唯一索引**（新增首选，**必须靠约束而非"先查再插"**）、**Token + Redis**（表单类，**校验与删除必须原子**）、**分布式锁**（并发低时可用，**性能差且必须配状态双重检查**）。
- **"先查再插"是错的**：并发下两个请求都会查到"不存在"，唯一可靠的拦截点是数据库唯一约束（原子）。
- **MQ 幂等的关键认知**：**"业务成功但 ack 失败"必然导致重投**，所以消费端必须幂等；核心业务用数据库唯一约束，Redis 去重只能用于非核心（Redis 可能丢数据）。
- **重复请求应该返回什么**：**成功**（携带已有结果），而不是报错——否则上游（尤其支付平台）会持续重试。
- **幂等过了账仍可能不平**：同一请求不要做两次，解决不了「做完之后两边事实是否一致」。以谁为准、差账分类见[对账与补偿](/methodology/reconciliation)。
