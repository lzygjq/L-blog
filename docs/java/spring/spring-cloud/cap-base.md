# CAP 与 BASE

## 一、先搞清 CAP 在讨论什么 {#intro}

CAP 不是一条工程建议，而是一条**物理约束**。它的前提是一个很朴素的事实：

> **两台机器之间靠网络通信，而网络一定会出问题**——交换机重启、光纤被挖断、机房之间丢包、GC 停顿导致的假超时。

一旦网络断了，系统就被切成两个互相看不见的部分（**分区**）。这时如果两边都还在对外提供服务，**两边的数据就可能各写各的**；如果要保证两边数据一致，就必须让其中一边停下来等。**这就是 CAP 的全部张力。**

## 二、三个指标 {#three}

| 指标 | 含义 | 容易混淆的地方 |
|---|---|---|
| **C — Consistency（一致性）** | 任何时刻，**任意节点**读到的数据都是最新的 | 这里的 C 是**强一致（线性一致）**，不是数据库 ACID 里的 C |
| **A — Availability（可用性）** | 任何**健康的**节点收到请求都必须返回**非错误**响应，不超时、不拒绝 | 注意是"非错误响应"——**返回稍旧的数据也算可用** |
| **P — Partition Tolerance（分区容错性）** | 网络分区时，系统**仍能继续对外服务** | 不是"永不分区"，而是"分区了也能活" |

**A 的定义是最容易答错的**：可用性 ≠ 返回正确数据。**返回一个过期的值，仍然是"可用"**。所以「AP 系统会返回旧数据」不是它的缺陷，而是它为了保证可用而主动付出的代价。

## 三、"三选二"这个说法不严谨 {#misconception}

几乎所有的资料（包括面试话术稿）都写「CAP 三者只能满足两个」。**这句话本身没错，但它会把人引到错误的思维方式上**——好像你可以自由地在三者中挑两个。实际的推理链是这样的：

```text
① 只要是分布式系统（数据在多个节点上）→ 网络分区【必然会】发生
② 所以 P 不是"选不选"的问题，而是"承不承认"的问题
   · 放弃 P = 放弃分布式（回到单机）—— 那就不是分布式系统了
③ 于是真正的取舍只剩：分区发生时，C 和 A 选哪个？
```

**两个更精确的说法**（这样说能让回答上一个档）：

1. **CAP 的取舍只在"分区发生期间"生效**。分区恢复后，系统会回到正常状态，理论上可以既一致又可用——所以准确的说法是「**在分区期间，C 与 A 不可兼得**」，而不是「系统永远只能二选一」。
2. **现实中没有纯粹的 AP 或 CP**，只有「在这个维度上偏向哪边」。绝大多数系统在**分区时才降级**：正常时既保证一致也保证可用，一旦检测到分区，才选择牺牲一边。

**顺着这条线还能答一个加分追问**：「那你为什么要用偏 AP 的注册中心？」——因为注册中心的分区代价是"可能读到稍旧的服务列表"，而服务列表旧一点只是可能多调一次失败；如果为了强一致让它不可用，**服务则连地址都查不到**，代价大得多。**取舍的标准是这个数据的"读错了会怎样"，而不是技术偏好。**

## 四、AP 与 CP 的代表 {#ap-cp}

| 系统 / 组件 | 取向 | 为什么 |
|---|---|---|
| **ZooKeeper、etcd** | **CP** | 用于选主、分布式锁、配置——这类数据"读到旧的会出大问题"，宁可短暂不可用 |
| **Eureka** | **AP** | 各节点平等复制，不做强一致；宁可给出稍旧的服务列表，也不让注册表不可读 |
| **Nacos（临时实例）** | **AP** | 走 Distro 协议，各节点平等、最终一致 |
| **Nacos（非临时实例 / 配置数据）** | **CP** | 走 Raft，选主 + 强一致——配置读错会导致各节点行为不一致 |
| **Redis 主从（默认）** | **AP** | 复制是**异步**的，主挂了可能丢最后一批写；主从切换期间可能读到旧数据 |
| **MySQL 半同步 / 强同步** | 偏 **CP** | 半同步至少要一个从确认；强同步（全确认）可用性更差 |
| **Kafka（`acks=all` + `min.insync.replicas`）** | 偏 **CP** | 宁可写失败也不丢消息 |

**选型口诀**：**这条数据「读到旧的」会怎样？**

- 账户余额、库存扣减、选主结果 → 读到旧的会算错 → **CP**
- 服务列表、商品详情、推荐列表、点赞数 → 读到旧的只是显示旧一点 → **AP**

## 五、BASE 理论 {#base}

BASE 是 **对 CAP 中 AP 这一侧的落地思路**——CAP 只说了"分区时放弃 C"，但没说"放弃 C 之后怎么办"。BASE 回答了这个问题。

| 词 | 含义 | 例子 |
|---|---|---|
| **BA — Basically Available（基本可用）** | 故障时允许**损失部分可用性**，但保证**核心功能**可用 | 大促时推荐位、评价区可以打不开，但**下单、支付必须能用** |
| **S — Soft State（软状态）** | 允许系统存在**中间状态**，即允许数据暂时不一致 | 订单处于"支付中"，此时各系统看到的状态可能不同 |
| **E — Eventually Consistent（最终一致性）** | 不追求实时一致，但**经过一段时间后**数据最终达到一致 | 支付回调后，订单、库存、积分在几十毫秒到几秒内陆续对齐 |

**BASE 和 CAP 的关系一句话说清**：**CAP 是"为什么必须取舍"，BASE 是"取舍之后怎么做"**。C（强一致）在这一侧被 E（最终一致）替代。

### 单机事务到分布式一致性的对应 {#acid-base}

| | 单机（ACID） | 分布式（BASE） |
|---|---|---|
| 原子性 | 数据库保证，要么全成功要么全回滚 | **靠补偿 / 重试 / 对账**，中间态会被看到 |
| 一致性 | 强一致 | **最终一致** |
| 隔离性 | 靠锁 / MVCC | **可能没有隔离**（如 Saga 各本地事务立即提交） |
| 典型问题 | 死锁 | **脏读、重复执行、需要幂等**（见 [接口幂等](/java/spring/spring-cloud/idempotency)） |

**这张表的实际价值**：它解释了为什么分布式场景下**幂等是必备而不是可选**——因为失去了单机事务的原子性和隔离性，重复执行和中间态变成常态。所以「幂等」「对账」「补偿」是一整套配套机制，不是孤立技巧。

## 六、一致性强度谱系与事务方案的对应 {#consistency-map}

「一致」不是一个开关，而是一条从强到弱的谱系：

```text
强 ──────────────────────────────────────────────────────▶ 弱
线性一致      顺序一致     因果一致        最终一致
（任意时刻     （全局有     （有因果关系的   （不保证何时，
  读最新）      统一顺序）    操作有序）       只保证最终对齐）

  ▲                                              ▲
  │                                              │
  XA / 2PC                                    AT / TCC / Saga / MQ
  （CP：宁可不可用，也要一致）                  （AP：先做完，不一致再修）
```

**这个谱系决定了分布式事务方案的两大流派**：

| 流派 | 思想 | 代价 | 代表方案 |
|---|---|---|---|
| **强一致（CP）** | 各分支**先执行但不提交**，等彼此都准备好了再统一提交 / 回滚 | 资源被**长时间锁定**，性能最差，可用性受协调者影响 | **XA**（两阶段提交） |
| **最终一致（AP）** | 各分支**执行完立即提交**，不一致时再通过补偿 / 重试修复 | 中间态对业务可见，**必须配幂等与对账** | **AT、TCC、Saga、MQ** |

**选型的主判据**：**业务能不能容忍"中间态被看到"**。银行转账的账务侧不能容忍，所以奔 CP；电商下单在几秒内数据没对齐，用户完全无感，所以用 AP 换性能。详见 [分布式事务](/java/spring/spring-cloud/transaction)。

## 七、常见坑与误解 {#pitfalls}

| 误解 | 问题所在 |
|---|---|
| **"我们选 CP，所以从来不丢数据"** | CP 只保证分区时的一致性，**不保证不丢数据**——那要另外做同步复制、持久化与确认机制 |
| **"我们选 AP，所以不需要管一致性"** | AP 换来的是一致性"延迟到来"，**必须有对账和补偿机制兜底**，否则就是真的不一致 |
| **"CAP 里 P 是可选的三分之一"** | P 是分布式的前提，**放弃 P 等于放弃分布式** |
| **把数据库 ACID 的 C 和 CAP 的 C 当同一个** | ACID 的 C 是"约束不被破坏"（应用层面），CAP 的 C 是"所有节点读到同一份新数据"（副本层面） |
| **用 CAP 解释一切可用性问题** | CAP 只在**网络分区**时生效。绝大多数线上可用性问题（OOM、慢 SQL、线程池满）跟 CAP 无关，**别硬套** |
| **忽略"分区恢复后"的行为** | 分区期间的脏数据需要在恢复后**收敛**，这部分工作比分区本身更容易被漏掉 |

## 面试口径

- **CAP 是什么**：C（**线性一致**，任意节点读到最新）、A（**健康节点必须非错误响应，返回旧数据也算可用**）、P（分区时仍能服务）。
- **精确表述**：P 是分布式的**前提**而非选项；因此实际取舍是**在分区发生期间**在 C 与 A 之间二选一。**说"三选二"要补一句"取舍只在分区期间生效"**，这样更严谨。
- **AP 代表**：Eureka、Nacos（临时实例，Distro 协议）、Redis 主从（异步复制）；**CP 代表**：ZooKeeper、etcd、Nacos（非临时实例与配置数据，Raft）、Kafka（`acks=all` + `min.insync.replicas`）。
- **选型判据**：看这条数据「**读到旧的会怎样**」——会算错（余额、库存、选主）就 CP；只是显示旧一点（服务列表、商品详情）就 AP。
- **BASE 三个词**：**BA** 基本可用（保核心链路，砍非核心功能）、**S** 软状态（允许中间态）、**E** 最终一致（过一段时间对齐）。**BASE 是 CAP 中 AP 侧的落地思路**——CAP 说"为什么取舍"，BASE 说"取舍后怎么做"。
- **BASE 与 ACID 的对应**：原子性 → **补偿 + 重试 + 对账**；强一致 → **最终一致**；隔离性 → **可能没有**。这解释了为什么分布式下**幂等是必备**。
- **一致性谱系与方案**：强一致侧是 **XA / 2PC**（先执行不提交、统一提交，资源锁定、性能最差）；最终一致侧是 **AT / TCC / Saga / MQ**（执行即提交、失败再补偿）。**主判据是业务能不能容忍中间态被看到。**
- **别硬套 CAP**：绝大多数线上可用性问题（OOM、慢 SQL、线程池满）跟 CAP 无关；CAP 只在**网络分区**场景下解释取舍。
