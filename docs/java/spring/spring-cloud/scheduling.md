# 分布式任务调度

## 一、`crontab` 在集群里会出什么事 {#why}

服务从单机变成多实例，定时任务立刻出三个问题，**第一个是致命的**：

| 问题 | 具体表现 | 严重程度 |
|---|---|---|
| **重复执行** | 3 个实例各有一个 `@Scheduled`，凌晨 2 点的报表任务**跑了 3 遍** | 致命——如果是"给用户发券"，就发了 3 次 |
| **无法统一管理** | 任务散落在各服务的代码里，想看一眼"系统里有哪些定时任务"要翻遍代码 | 高——接手系统时完全不知道有什么在跑 |
| **失败无感知** | 任务报错只在某个实例的日志里，没人知道；没有重试、没有告警 | 高——往往等业务方反馈"数据不对"才发现 |

**为什么"重复执行"是致命的**：它**破坏数据**。而且这类问题在测试环境完全看不出来（测试环境只有一个实例），一上生产就开始出错。

**朴素解法及其不足**：

```java
// 用 Redis 锁保证只跑一次——能用，但很粗糙
if (redis.setnx("job:report:lock", "1", 3600)) {
    doReport();
}
```

这个写法解决了"重复"，但没解决"管理"和"可观测"：任务失败了呢？上次跑了多久？下次要不要重试？**换机器要不要改代码？** 所以需要的是一个**调度平台**，而不是一把锁。

## 二、xxl-job 的架构 {#arch}

xxl-job 把调度能力拆成两个角色——**这是理解它的关键**：

```text
┌──────────────────────────────────────┐
│          调度中心（xxl-job-admin）      │
│  · 任务配置（cron、路由策略、参数）      │
│  · 触发调度（按 cron 计算）             │
│  · 记录调度日志、失败告警               │
│  · 提供 Web 管理台                     │
└──────────────────────────────────────┘
         │                          ▲
         │ ① 下发调度请求（RPC）      │ ③ 执行完回调
         ▼                          │
┌──────────────────────────────────────┐
│   执行器（xxl-job-executor，嵌在应用里）  │
│  · ② 接收调度请求 → 找到对应的 JobHandler │
│  · 执行真正的业务逻辑                    │
│  · 定期向调度中心【心跳注册】             │
└──────────────────────────────────────┘
```

**四个动作串起来**：

```text
① 注册：执行器启动后定期向调度中心心跳，上报自己的地址
   （这就是为什么调度中心知道"这个任务组下有几台机器"）
② 调度：调度中心按 cron 算出该触发了 → 按【路由策略】挑一个执行器 → RPC 下发
③ 执行：执行器根据 JobHandler 名字找到业务代码执行
④ 回调：执行完把结果回调给调度中心 → 写入调度日志（成功/失败/耗时/输出）
```

**这个架构和"在应用里嵌一个定时任务库"的本质区别**：调度信息**集中在一处**，业务应用只负责"执行"。所以改 cron、看执行记录、手动触发、查看失败原因，都在一个 Web 界面上完成，不用登录服务器、不用改代码发版。

### 与其他方案的对比 {#compare-frameworks}

| | Quartz | ElasticJob | **xxl-job** |
|---|---|---|---|
| 形态 | **库**（嵌在应用里） | 库 + ZK 协调 | **平台**（调度中心独立部署） |
| 集群协调 | 靠数据库锁（易成瓶颈） | **无中心**，靠 ZooKeeper 选举 | 靠调度中心的数据库行锁 |
| 管理界面 | **无**（要自己写） | 有（运维界面） | **功能完整**（任务管理、日志、告警） |
| 分片 | 需自己实现 | 支持 | **支持（分片广播）** |
| 动态改 cron | 要重启或自研 | 支持 | **界面上直接改，立即生效** |
| 定位 | 基础调度能力 | 弹性分布式调度 | **开箱即用的调度平台** |

**Quartz 最容易被问到的点**：它的集群模式靠数据库行锁抢占触发权，**任务量大时数据库会成为瓶颈**；而且它没有管理界面，任务配置散在代码和 `QRTZ_*` 表里。

## 三、十种路由策略 {#route}

「路由」在这里的含义是：**任务触发了，该让哪一台执行器来跑**。集群部署时才生效。

按用途分四类：

| 类别 | 策略 | 含义 | 典型场景 |
|---|---|---|---|
| **单节点** | `FIRST` | **固定选第一台**（框架默认） | 要求任务始终在同一台机器执行（如单机批账） |
| | `LAST` | 固定选最后一台 | 灰度节点、临时测试 |
| **负载均衡** | `ROUND` | **轮询** | **最常用**，无状态任务的默认选择 |
| | `RANDOM` | 随机 | 简单打散流量 |
| | `CONSISTENT_HASH` | 按任务标识做一致性哈希，**同一任务固定落到同一台** | 有状态任务、需要缓存本地化的场景 |
| | `LEAST_FREQUENTLY_USED` | 使用次数最少的优先 | 节点性能不均 |
| | `LEAST_RECENTLY_USED` | 最久未被使用的优先 | 冷启动均衡 |
| **故障 / 忙碌转移** | `FAILOVER` | **顺序心跳探测**，第一台**存活**的接管 | **高可用关键任务**（支付、订单处理） |
| | `BUSYOVER` | 顺序**空闲探测**，第一台空闲的执行 | CPU / IO 敏感任务 |
| **并行处理** | `SHARDING_BROADCAST` | **广播到所有执行器**，各带分片参数并行处理 | **大数据量批处理**、全量对账 |

两个值得留意的点：

- **框架默认是 `FIRST`**（固定第一台）。这个默认值在集群下意味着"永远只有一台干活、其余闲置"——所以**生产上基本都要改**，无状态任务用 `ROUND`，关键任务用 `FAILOVER`。
- **`FAILOVER` 与 `BUSYOVER` 的区别容易记反**：看名字会以为 busy 相关的是"找忙的"，实际语义是——**一个是找"活着的不忙的"（FAILOVER 先探活）**，**一个是找"空闲的"（BUSYOVER）**。两者的探测目标不同：FAILOVER 探的是"心跳是否正常"，BUSYOVER 探的是"任务队列是否空闲"。

## 四、调度中心自己不重复触发吗 {#no-dup}

**这是 xxl-job 面试里的一个高价值追问**：调度中心为了高可用通常也是集群部署，那多个调度中心会不会同时触发同一个任务？

答案是**靠数据库抢占**：

```text
① 每个调度中心的调度线程按 cron 扫描「下次触发时间已到」的任务
② 抢任务前，用【数据库行锁 / 乐观锁】更新 xxl_job_lock 表的 schedule_lock
   · 抢到锁的调度中心才继续下面的步骤
   · 没抢到的直接跳过这一轮
③ 抢到的调度中心执行路由 → 下发调度请求
```

此外调度中心内部用**快慢线程池分离**：

| 线程池 | 职责 |
|---|---|
| **快线程池** | 处理调度请求的下发（轻量，要求快） |
| **慢线程池** | 处理执行结果回调、日志写入（较重，允许慢） |

**为什么要分离**：如果回调的日志写入把线程占满，会连带**堵住调度下发**——一个任务的执行结果写日志慢，会导致其他任务都不能按时触发。这种"轻重混在一个池子里互相拖累"是线程池隔离的经典应用场景。

## 五、失败处理：五个配置项各管一段 {#failure}

「任务失败了怎么办」这个问题的完整答案，是**五件事叠加**，缺一个都会留口子：

| 配置 | 管什么 | 说明 |
|---|---|---|
| **失败重试次数** | 失败后自动重跑 | 配置 2 次表示最多重试 2 次；**业务必须幂等**（见[接口幂等](/java/spring/spring-cloud/idempotency)） |
| **路由策略选 `FAILOVER`** | 换一台机器重试 | 原机器可能就是故障源，重试仍打给它没意义 |
| **超时时间** | 卡死时强制中断 | 默认 `0` = **不限超时**（危险，一个卡住的任务会一直占着） |
| **阻塞处理策略** | 上次还没跑完，新的又来了怎么办 | 见下表 |
| **告警** | 让人知道出事了 | 默认支持邮件；生产通常扩展钉钉 / 企微机器人 |

**阻塞处理策略**（任务密集触发时最常出问题的一项）：

| 策略 | 行为 | 什么时候用 |
|---|---|---|
| **单机串行**（默认） | 后来的请求进 FIFO 队列**排队** | 任务必须按顺序执行，且能容忍延迟 |
| **丢弃后续调度** | 上一次还在跑 → **直接丢弃**这次，并标记为失败 | 任务有明确的"时效性"（这次的已经过期了，跑也没意义） | 
| **覆盖之前调度** | **终止**正在跑的任务、清空队列，**立刻执行新的** | 任务只需要跑"最新的那次"（如同一份报表只需最新版本） |

**调度过期策略**（misfire，即"该触发的时间点已经过去了"）：

| 策略 | 行为 |
|---|---|
| **忽略** | 跳过这次，从当前时间重新计算下次触发 |
| **立即执行一次** | 补跑一次，再按正常节奏 |

**这个配置容易被忽略但很关键**：如果任务配置是"每天 2 点"，而 2 点时调度中心正好在重启——「忽略」就意味着**这一天不跑了**，数据缺失。对数据完整性敏感的任务应该选「立即执行一次」。

**另外「日志」也是失败处理的一部分**：xxl-job 提供调度日志（什么时候触发、路由到哪台、调度是否成功）与执行日志（业务代码的 `XxlJobLogger` 输出），并且**支持在界面上手动终止正在跑的任务、手动重跑某次失败**。这些能力是自研调度最容易漏掉的。

## 六、大数据量：分片广播 {#sharding}

### 6.1 从一个具体的困境说起 {#sharding-problem}

假设要处理 500 万条历史数据做重算。单机跑完需要 4 小时，而这个任务必须在夜间窗口内完成——**单机加 CPU 也没用，因为瓶颈可能是单机的 IO 或下游数据库的连接数**。

朴素的解法是"启动多个线程池并行"——但**同一台机器的资源是共享的**，加速比很快撞到天花板。

**分片广播的思路完全不同：让每个执行器实例各自处理一部分数据。**

```text
【普通路由】                     【SHARDING_BROADCAST】
调度中心                          调度中心
   │  挑一台                        │  广播给所有实例
   ▼                                ├──────────┬──────────┐
执行器 A（500 万条，4 小时）          ▼          ▼          ▼
                               执行器 A    执行器 B    执行器 C
                              shardIndex=0 shardIndex=1 shardIndex=2
                              shardTotal=3 shardTotal=3 shardTotal=3
                                  │           │           │
                              166 万条    166 万条    166 万条
按 id % 3 分摊                    ≈1.3h      ≈1.3h      ≈1.3h
```

### 6.2 代码怎么写 {#sharding-code}

xxl-job 广播触发时，会自动把 `shardIndex`（当前实例的序号，从 0 开始）和 `shardTotal`（实例总数）传给每个执行器：

```java
@XxlJob("recalcHistoryJob")
public void recalcHistory() {
    // ① 从上下文取分片参数
    int shardIndex = XxlJobContext.getXxlJobContext().getShardIndex();
    int shardTotal = XxlJobContext.getXxlJobContext().getShardTotal();

    // ② 按 id 取模分摊数据（这是最常用的分摊方式）
    //    业务 SQL 里直接带上分片条件，避免全量捞到内存再筛
    long lastId = 0;
    int batchSize = 1000;
    while (true) {
        List<Record> batch = recordMapper.selectBatchByShard(
                lastId, batchSize, shardIndex, shardTotal);
        if (batch.isEmpty()) break;

        for (Record r : batch) {
            doRecalc(r);
        }
        lastId = batch.get(batch.size() - 1).getId();
    }
    XxlJobLogger.log("分片 {} / {} 处理完成", shardIndex, shardTotal);
}
```

```xml
<!-- 对应的 SQL：分摊逻辑下沉到数据库，不要全捞到内存再过滤 -->
<select id="selectBatchByShard" resultType="Record">
    SELECT * FROM history_record
     WHERE id &gt; #{lastId}
       AND MOD(id, #{shardTotal}) = #{shardIndex}
     ORDER BY id
     LIMIT #{batchSize}
</select>
```

### 6.3 三个必须注意的点 {#sharding-notes}

**① 分片数 = 执行器实例数，会随扩缩容变化。**

`shardTotal` 不是你自己配的数字，而是**当前在线的执行器台数**。这带来一个隐蔽的坑：

```text
假设按 user_id % shardTotal 分配用户数据：
  今天 3 台机器 → user 100 归 A（100 % 3 = 1）
  明天扩到 4 台 → user 100 归 C（100 % 4 = 0）
```

**如果分片逻辑涉及"按分片维护状态"（比如记录每个分片的进度位点），扩缩容会导致分片归属变化、状态错乱。** 解法是**不要让分片承载状态**——每次都从数据本身推导该处理哪些（如上例的 `MOD(id, shardTotal)`），而不是记"我上次跑到哪了"。

**② 分片任务必须幂等。**

因为「某个分片失败后重跑」是常态——重跑时它处理的数据范围不变（`MOD(id, shardTotal)` 是确定的），所以**只要单条记录的处理是幂等的，重跑就安全**。这也是"分摊逻辑要能重复执行"的原因。

**③ 加速比不是线性的。**

- 3 台机器不是"快 3 倍"，因为可能都连同一个数据库、共享带宽和 IO
- **数据分布不均**会让某个分片特别重（比如按 `MOD(id, N)` 分，而最近的 id 集中在某个区间）
- 合理的预期是"显著变快"，具体倍数靠**压测确认**，不要拍胸脯说"N 倍"

## 七、常见坑 {#pitfalls}

| 坑 | 现象 | 原因 |
|---|---|---|
| **沿用默认 `FIRST` 路由** | 集群里永远只有一台在干活 | 默认值是固定第一台，无状态任务应改 `ROUND` |
| **重试 + 不幂等** | 重试产生重复数据 | 失败重试的次数配了，但业务没做幂等 |
| **超时时间留 0** | 任务卡住后一直占用，后续触发全部排队 | 默认不限超时，必须按任务合理耗时设置 |
| **阻塞策略没配** | 任务密集时队列堆积、雪崩 | 默认"单机串行"，密集触发时要有明确策略 |
| **把"Misfire=忽略"当默认没问题** | 某天数据缺失 | 调度中心重启 / 过载导致错过触发点，敏感任务应选「立即执行一次」 |
| **分片任务依赖"上次进度"** | 扩缩容后数据错乱或漏处理 | `shardTotal` 会变，分片归属随之变；**分片任务不要承载状态** |
| **分片逻辑写在应用层全量捞** | 内存溢出、性能更差 | 应该把 `MOD(id, shardTotal) = shardIndex` 下沉到 SQL |
| **任务太分散在多台机器** | 想看有哪些任务要翻代码 | 全部注册到调度中心统一管理，不要残留 `@Scheduled` |
| **告警只配邮件** | 邮件被忽略 | 关键任务接企微 / 钉钉机器人，且**路由到具体负责人** |

## 面试口径

- **为什么需要分布式调度**：单机 `crontab` / `@Scheduled` 在多实例下会**重复执行**（破坏数据）、**无法统一管理**（任务散落、看不见）、**失败无感知**（无重试、无告警）。用一把 Redis 锁只能解决第一个问题，所以需要调度平台。
- **xxl-job 的两个角色**：**调度中心**（独立部署：任务配置、按 cron 触发、路由、记录日志、告警、Web 管理台）+ **执行器**（嵌在业务应用里：心跳注册、接收调度、执行业务逻辑、回调结果）。
- **与 Quartz 的区别**：Quartz 是**库**，嵌在应用里、无管理界面、集群靠数据库行锁（量大易成瓶颈）；xxl-job 是**平台**，调度信息集中、界面化管理、改 cron 立即生效。ElasticJob 是**无中心**方案，靠 ZooKeeper 协调。
- **十种路由策略分四类**：单节点（`FIRST` / `LAST`）、负载均衡（`ROUND` / `RANDOM` / `CONSISTENT_HASH` / `LFU` / `LRU`）、转移（`FAILOVER` 探活 / `BUSYOVER` 探空闲）、并行（`SHARDING_BROADCAST`）。**框架默认 `FIRST`，但生产无状态任务应用 `ROUND`，关键任务用 `FAILOVER`。**
- **调度中心集群怎么不重复触发**：靠**数据库行锁 / 乐观锁抢占**（`schedule_lock`），抢到的才触发；内部把**调度下发与结果回调拆成快慢两个线程池**，避免日志写入拖慢调度。
- **失败处理是五件事**：失败重试次数（**业务要幂等**）+ `FAILOVER` 路由换机器 + 超时时间（默认 `0` 不限，很危险）+ **阻塞处理策略**（单机串行 / 丢弃后续 / 覆盖之前）+ 告警；另外别忘了**调度过期（Misfire）策略**——「忽略」会导致该次任务不跑、数据缺失。
- **分片广播的机制**：调度中心**广播给所有执行器**，每个执行器拿到 `shardIndex` 与 `shardTotal`，用 `MOD(id, shardTotal) = shardIndex` 分摊数据并行处理。
- **分片广播的三个要点**：① **分片数 = 在线执行器台数，会随扩缩容变化** → 分片任务**不要承载状态**（从数据推导而非记录位点）；② **必须幂等**（分片失败重跑是常态）；③ **加速比非线性**（共享数据库 / IO，且数据可能分布不均），倍数靠压测确认。
- **一个工程口径**：分片分摊条件要**下沉到 SQL**（`WHERE MOD(id, ?) = ?`），不要全量捞到应用层再过滤。
