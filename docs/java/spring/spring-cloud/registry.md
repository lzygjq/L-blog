# 注册中心

## 一、不用注册中心会怎样 {#why-registry}

假设订单服务要调库存服务，最直白的写法是把地址写进配置文件：

```yaml
inventory:
  url: http://192.168.1.10:8081
```

这个写法在三种情况下立刻崩掉：

| 情况 | 后果 |
|---|---|
| 库存服务扩容到 3 个实例 | 配置文件写哪个？写一个等于另外两个白部署 |
| 库存服务换机器、IP 变了 | 改配置 + 重启订单服务，且要改所有调用方 |
| 某个实例挂了 | 订单服务照样往它发请求，一直失败到人工发现 |

注册中心把这三件事一次解决：**服务启动时把自己的地址报上去，调用方从注册表里查，而不是从配置里读**。扩容、缩容、换 IP 都变成注册表里的增删，调用方无感。

**一句话定义**：注册中心是一份**带健康检查的服务地址簿**。「地址簿」三个字里，**「健康检查」才是它比配置文件多出来的价值**——没有健康检查，它只是一张会变的配置表。

> **注册表里存什么粒度**，是服务发现设计里最关键的一次取舍：Spring Cloud 存"应用 + 实例"，Dubbo 2 存"接口 + 实例"，后者在大规模下会把注册中心压垮——这段演进见 [Dubbo 的应用级服务发现](/middleware/rpc/dubbo-internals#app-level)。

## 二、Eureka 的工作机制 {#eureka}

### 2.1 三个动作 {#eureka-flow}

```text
① 服务注册    服务提供者启动 ──▶ 上报 {服务名, IP, 端口, 健康检查地址}
                              ──▶ Eureka Server 写入注册表

② 服务拉取    服务消费者 ──▶ 定时从 Server 拉取全量注册表
                          ──▶ 缓存到本地（后续调用直接用本地缓存）

③ 心跳续约    提供者每 30 秒 ──▶ 发一次心跳（证明"我还活着"）
              90 秒没收到心跳 ──▶ 从注册表剔除该实例
```

三个动作对应的默认参数（都能配，但**面试常问的就是默认值**）：

| 动作 | 参数 | 默认值 |
|---|---|---|
| 心跳续约间隔 | `eureka.instance.lease-renewal-interval-in-seconds` | **30 秒** |
| 失效剔除阈值 | `eureka.instance.lease-expiration-duration-in-seconds` | **90 秒** |
| 消费者拉取间隔 | `eureka.client.registry-fetch-interval-seconds` | 30 秒 |

**注意 90 秒这个数字的含义**：一个实例真的挂掉之后，最长要 90 秒才会从注册表消失。这期间调用方拉到的注册表里还有它，会继续把请求发过去、继续失败。所以「注册中心」这一层**不做实时感知**，真正保证调用成功率的是调用端的**负载均衡重试**（见[负载均衡与远程调用](/java/spring/spring-cloud/loadbalancer)）。

### 2.2 服务端的三级缓存 {#eureka-cache}

Eureka Server 内部维护三层结构，这是它「读多写少」场景下的关键设计：

| 层 | 结构 | 作用 |
|---|---|---|
| ① 注册表 | `ConcurrentHashMap` | 真实数据，注册 / 续约 / 剔除都改这里 |
| ② 读写缓存 | `readWriteCacheMap` | 注册表变更后**失效**，下次读到时重建 |
| ③ 只读缓存 | `readOnlyCacheMap` | 消费者**实际读到的就是这个**，默认每 30 秒从②同步一次 |

**为什么这么设计**：消费者的拉取请求量远大于注册变更量（每个消费者都定时拉、但注册表可能几小时才变一次）。让所有读请求都打到注册表会白白锁竞争，加两层缓存后读几乎无锁。

**代价也要知道**：一次注册变更最长要 **30 秒（读写→只读同步）+ 拉取间隔**才能被消费者看到。所以「刚上线的实例，调用方要过一会儿才会调它」是正常现象，不是配错了。

### 2.3 自我保护机制 {#eureka-self-preservation}

这是 Eureka 最容易被误解的机制：

```text
统计周期 15 分钟
若「实际心跳数 / 应收到心跳数」< 85%
   ──▶ 触发自我保护：停止剔除任何实例
```

**为什么要有它**：心跳大量丢失有两种可能——① 真有一批服务挂了；② **Eureka Server 自己网络出问题**，收不到心跳。如果是②，此时把实例全剔掉，会让整个系统"因为注册中心误判而集体下线"。Eureka 的选择是**宁可保留可能已死的实例，也不误杀活着的实例**——这就是它偏 AP 的体现。

**副作用**：服务真挂了但由于自我保护没被剔除，调用方会持续拿到失效地址。所以线上常见两个动作：调小续约阈值，或**在调用端加重试**（这才是根治手段）。

## 三、Nacos 的工作机制 {#nacos}

Nacos 是「注册中心 + 配置中心」二合一，也是目前国内新项目的主流选择。它的核心概念比 Eureka 多一层：**实例分临时和非临时**。

### 3.1 临时实例 vs 非临时实例 {#nacos-ephemeral}

| | 临时实例（`ephemeral=true`，**默认**） | 非临时实例（`ephemeral=false`） |
|---|---|---|
| 健康检查方式 | **客户端上报心跳** → 服务端被动接收 | **服务端主动探测**（连接 / 端口探测） |
| 心跳间隔 | 5 秒 | 由服务端探测周期决定 |
| 不健康判定 | 15 秒未收到 → 标记不健康 | 探测失败 → 标记不健康 |
| 剔除策略 | 30 秒未收到 → **直接从注册表删除** | **只标记不健康，永不剔除** |
| 数据存储 | 内存（随实例消失而消失） | **持久化到磁盘 / 数据库** |
| 一致性协议 | Distro（AP） | Raft（CP） |

**怎么理解这两类**：临时实例适合**无状态的业务服务**（挂了、重启了，注册记录也就没必要留）；非临时实例适合**需要"永远知道它存在"的场景**，比如数据库代理、监控目标、固定机房的中间件——即使它当前不健康，也要在列表里看得见（这跟 DNS 记录要长期存在是一个道理）。

### 3.2 为什么 Nacos 的服务列表更新更及时 {#nacos-push}

| | Eureka | Nacos |
|---|---|---|
| 更新方式 | **只有 pull**：消费者定时拉全量 | **push + pull**：服务端检测到变更主动推 |
| 传输通道 | HTTP 轮询 | Nacos 2.x 用 **gRPC 长连接**；1.x 用 UDP 推送 + 客户端定时校验 |
| 生效延迟 | 最长 30 秒 | 毫秒级（长连接直推） |

**这是 Nacos 相对 Eureka 最实在的改进**：实例上下线后消费者几乎立刻知道，不需要等下一轮轮询。Nacos 1.x 时代用 UDP 推送有丢包问题（所以还要客户端定时拉取兜底），2.x 换成 gRPC 长连接后这个问题基本解决。

### 3.3 AP 还是 CP：同一套组件里的两种模式 {#nacos-cap}

Nacos 不是一个"AP 组件"或"CP 组件"，它**按数据类型分别选协议**：

| 数据类型 | 协议 | 特性 |
|---|---|---|
| 临时实例（注册） | **Distro** | AP——各节点平等，最终一致，优先可用 |
| 非临时实例 | **Raft** | CP——选主，强一致，优先正确 |
| **配置数据** | **Raft** | CP——配置必须一致，不能这台读到 A 那台读到 B |

**所以「Nacos 是 AP 还是 CP」这个问题本身就是错的**，正确答案是「看数据类型」——这个回答比单说 AP 或 CP 高一个档次。原理详见 [CAP 与 BASE](/java/spring/spring-cloud/cap-base)。

### 3.4 五层命名空间 {#nacos-namespace}

Nacos 用五个层级定位一个实例，**排查「调到了别的环境的服务」这类问题时按这个顺序找**：

```text
Namespace（环境隔离：dev / test / prod）
  └── Group（业务分组，默认 DEFAULT_GROUP）
        └── Service（服务名）
              └── Cluster（机房 / 区域，用于就近路由）
                    └── Instance（一个具体实例 IP:Port）
```

**`namespace` 是最常用的隔离手段**：不同环境的服务名往往一样（都叫 `order-service`），靠 namespace 隔开。配错 namespace 会导致测试环境调生产——这是实际事故里出现频率很高的一类。

## 四、对比表 {#compare}

| 维度 | Eureka | Nacos |
|---|---|---|
| 健康检查 | 仅客户端心跳 | 临时实例心跳 + 非临时实例服务端主动探测 |
| 剔除策略 | 心跳超时直接剔除 | 临时实例剔除；非临时实例**只标记不剔除** |
| 列表更新 | 仅客户端定时 pull | **push（长连接）+ pull 兜底**，更及时 |
| CAP | 仅 AP | **按数据类型切换**（Distro / Raft） |
| 额外能力 | 无 | **内置配置中心**、权重、保护阈值、元数据 |
| 控制台 | 简陋 | 完整（服务列表、健康状态、配置管理） |
| 现状 | 1.x 仍维护、**2.x 已停止开发**，官方不推荐新项目使用 | 活跃迭代，Spring Cloud Alibaba 主力 |

**一句话选型**：新项目直接 Nacos（一个组件顶两个）；存量 Eureka 项目没必要为了换而换，但要知道它已不推荐。

## 五、顺带把配置中心讲了 {#config-center}

Nacos 的另一半是配置中心。为什么不另配一个 Config Server——因为**注册和配置本来就是同一件基础设施的两面**：都要求服务启动时先去某个地方"报到"，分开部署等于维护两套高可用集群。

### 5.1 三个坐标 {#config-coords}

```text
dataId    = ${spring.application.name}-${profile}.${file-extension}
            例：order-service-prod.yaml
group     =  DEFAULT_GROUP（可按业务线拆）
namespace =  环境隔离（与注册中心共用同一套 namespace）
```

### 5.2 动态刷新怎么实现的 {#config-refresh}

```text
① 客户端启动时注册监听（长轮询，超时 30 秒）
② 服务端 hold 住请求不立即返回
③ 配置一旦变更 → 服务端立刻返回该请求
④ 客户端重新拉取配置 → 发布 RefreshEvent → 重建受影响的 Bean
```

**关键点**：`@RefreshScope` 能刷新，是因为它标注的 Bean 会被做成**代理**——刷新时销毁旧实例、下次调用时重新创建。所以：

- `@Value` 注入的字段在 `@RefreshScope` 的 Bean 里能刷新；**在普通单例 Bean 里刷不了**（值在创建时就定死了）
- `@ConfigurationProperties` 的 Bean 天然支持刷新（会被重新绑定）
- **数据源、线程池这类 Bean 刷新要非常小心**：重建意味着旧连接池被丢弃，可能出现连接泄漏或瞬时抖动。这类配置改完通常选择重启而不是热刷

## 六、常见坑 {#pitfalls}

| 坑 | 现象 | 原因与解法 |
|---|---|---|
| **自我保护开着** | 服务已停，调用方还在调它 | 15 分钟内心跳丢失率超阈值 → 停止剔除。属预期行为，靠调用端重试兜底 |
| **注册 IP 不对** | 调用方连不上，直接连 IP 反倒能通 | 多网卡 / 容器环境取到了错误的网卡地址 → 显式指定 `spring.cloud.nacos.discovery.ip` |
| **namespace 配错** | 测试环境调到了生产 | 服务名相同、namespace 不同却能互相发现 → 检查 namespace 拼写（用的是 **ID 不是名称**） |
| **`@Value` 刷新不了** | 改了配置没生效 | 所在 Bean 没有 `@RefreshScope`；或改的是数据源类 Bean，本身就不该热刷 |
| **Eureka 刚上线没人调** | 新实例要等一会儿才收到流量 | 三级缓存同步 + 拉取间隔叠加，最多 30 秒以上属于正常 |
| **下线不优雅** | 停服瞬间仍有一批请求失败 | 直接 `kill` 会让调用方拿到失效地址 → 先调注册中心下线接口，等一个拉取周期再停进程 |

## 面试口径

- **注册中心的核心价值**：服务地址簿 + **健康检查**。没有健康检查它就只是配置中心。
- **Eureka 三段流程**：注册 → 拉取（本地缓存）→ 心跳续约；**30 秒心跳、90 秒剔除**。
- **为什么要三级缓存**：读多写少，让消费者读无锁的只读缓存；代价是变更最长 30 秒才可见。
- **自我保护机制**：15 分钟内心跳丢失率 > 85% 就停止剔除——宁可保留死实例，也不误杀活实例，是 AP 取向的直接体现。
- **Nacos 与 Eureka 的五点区别**：① 健康检查分临时 / 非临时；② 非临时实例只标记不剔除；③ 主动 push，更新更及时；④ **Nacos 按数据类型选 AP / CP**，不是单一模式；⑤ Nacos 兼配置中心。
- **Nacos 为什么能 CP**：非临时实例与配置数据走 Raft 选主、强一致；临时实例走 Distro、AP。
- **配置动态刷新的原理**：客户端长轮询（30 秒 hold）拿到变更 → 发 `RefreshEvent` → 销毁并重建 `@RefreshScope` 代理 Bean。**普通单例里的 `@Value` 刷不了**。
- **别忘的边界**：注册中心的感知有延迟，**真正兜住调用成功率的是调用端的重试与熔断**，不是注册中心本身。
