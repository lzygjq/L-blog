# 服务保护

## 一、雪崩不是"一个服务挂了"，是"被放大" {#avalanche}

先说结论：**单个服务挂掉本身不可怕，可怕的是调用它的服务也因此耗尽资源**。雪崩是**放大效应**，不是故障本身。

```text
正常时：
  订单服务 ──40 个线程──▶ 库存服务（RT 50ms）──▶ 优惠券服务（RT 50ms）
  一个请求占用线程 100ms，40 个线程够撑住 400 QPS

优惠券服务变慢（RT 从 50ms 涨到 5s）：
  ① 优惠券服务慢 → 库存服务调它的线程被【长时间占住】
  ② 库存服务的线程池被占满 → 库存服务对新请求【也无法响应】
  ③ 订单服务调库存的线程同样被占住 → 订单服务的线程池也满了
  ④ 订单服务不再接受任何请求 —— 连【不依赖优惠券】的下单接口也挂了
```

注意第 ④ 步：**这才是雪崩最致命的地方**——故障沿着调用链向上传播，最后连跟故障服务毫无关系的功能都不可用。

放大发生的三个前提条件（也是三道防线）：

| 放大的原因 | 对应防线 |
|---|---|
| 调用**同步阻塞**，一个请求占一个线程 | **资源隔离**（限流、隔离舱） |
| 调用**没有超时**，慢请求可以无限期占着线程 | **超时控制** |
| 下游持续失败，上游仍**不断重试 / 不断发送** | **熔断**（快速失败） |

**所以防护是多层叠加的**：超时是第一道，隔离是第二道，熔断是第三道。只做熔断不做超时，等于最后一道防线要等很久才生效。

## 二、三个概念，别混着说 {#three-concepts}

面试里最常被追问的就是这三个词的区别。它们的**作用位置和触发方式都不同**：

| | 服务降级 | 服务熔断 | 服务限流 |
|---|---|---|---|
| **谁触发** | **人为 / 代码预设**（主动） | **框架自动**（被动） | 框架按规则（被动） |
| **做什么** | 返回一个**兜底结果**（缓存值、默认值、"稍后再试"） | **直接拒绝调用**，不再打到下游 | 拒绝超出速率的部分请求 |
| **目的** | 保住核心链路可用 | 给下游**恢复的时间**，避免持续冲击 | 保护自己不被流量打垮 |
| **恢复方式** | 人工开关 / 配置中心开关 | **自动**：半开后试探成功即恢复 | 流量降下来自动恢复 |
| **典型实现** | Feign 的 `fallback` | Sentinel / Resilience4j 断路器 | 网关 / Sentinel 流控 |

**一句话把三者串起来**：

> 限流是**不让太多请求进来**；熔断是**发现下游不行了就先别调了**；降级是**不调了之后给用户一个什么结果**。熔断和限流都会**导致降级**——降级是它们的结果，不是并列的第三种手段。

这个"因果串起来"的说法比"三个概念并列介绍"更能体现理解。

## 三、断路器三状态机 {#circuit-breaker}

熔断的核心是一个**状态机**，三个状态循环迁移：

```text
                失败率超过阈值
   ┌─────────┐ ─────────────────▶ ┌────────┐
   │ Closed  │                    │  Open  │
   │  关闭   │                    │  打开  │
   │ 正常放行 │ ◀───────────────── │ 快速失败│
   └─────────┘   试探成功          └────────┘
        ▲                              │
        │                              │ 等待【熔断时长】
        │                              ▼
        │     试探成功      ┌──────────────┐
        └──────────────────│  Half-Open   │
                           │    半开      │
              试探失败 ────▶│ 放行少量请求  │
              回到 Open     └──────────────┘
```

| 状态 | 行为 | 迁移条件 |
|---|---|---|
| **Closed**（关闭） | 请求正常通过，**同时统计**成功率与耗时 | 统计窗口内失败率超过阈值 → Open |
| **Open**（打开） | **请求直接失败，不打到下游**（这是熔断的意义所在） | 等待熔断时长后 → Half-Open |
| **Half-Open**（半开） | 放行**少量**请求试探下游是否恢复 | 成功 → Closed；失败 → 立刻回 Open |

**三个必须说清的细节**：

1. **Half-Open 只放极少请求**（Hystrix 是 1 个）。目的是"探路"，不是"恢复流量"——如果放多了，下游还没恢复又被压垮。
2. **熔断判定要满足"最小请求数"**。否则一个只有 2 次调用的接口，失败 1 次就 50% 失败率，会被误熔断（见下节参数）。
3. **熔断是"保护下游"还是"保护自己"**——两者都有：对上游而言是快速失败、不浪费自己的线程；对下游而言是停止持续冲击、给它恢复窗口。回答时两个方向都说，更完整。

## 四、Hystrix 的参数与它被移除的原因 {#hystrix}

Hystrix 是断路器的经典实现，**已在 Spring Cloud 2020.0.0 移除**，但它的参数体系仍是最常考的内容。

### 4.1 触发熔断的完整条件 {#hystrix-threshold}

很多资料只说「10 秒内失败率超过 50% 就熔断」，**漏了前面的最小请求数条件**，答出来是错的：

```text
滚动统计窗口：10 秒
① 窗口内请求数 ≥ 20          （requestVolumeThreshold，默认 20）
② 且 失败率 > 50%            （errorThresholdPercentage，默认 50）
   ──▶ 两个条件【同时满足】才熔断

熔断后：Open 持续 5 秒         （sleepWindowInMilliseconds，默认 5000）
   ──▶ 5 秒后进入 Half-Open，放行 1 个请求试探
```

**为什么必须有条件 ①**：没有它，低流量接口会被误熔断——「10 秒内 2 个请求挂了 1 个」= 50% 失败率，但样本量根本不足以说明下游有问题。

### 4.2 隔离策略 {#hystrix-isolation}

| 策略 | 做法 | 代价 |
|---|---|---|
| **线程池隔离**（默认） | 每个下游用**独立线程池**调用，默认 10 个线程 | 有线程切换开销；但一个下游慢不会影响其他下游 |
| **信号量隔离** | 只用一个计数器限并发，**不换线程** | 开销小；但调用仍在调用者线程上，超时控制能力弱 |

**线程池隔离为什么是默认**：它把「一个下游变慢」的影响**限制在那一个线程池里**——这就是"隔离舱（Bulkhead）"思想。代价是每个下游一批线程，几百个下游时线程总数可观。

### 4.3 为什么被移除 {#hystrix-removed}

- **2018 年起进入维护状态**，官方不再加新功能
- 线程池隔离的**模型偏重**（每个下游一套线程池），高并发下线程数膨胀
- 生态转向**两个方向**：Spring 官方的 **Resilience4j**（轻量、函数式、无额外线程）、阿里系的 **Sentinel**（流量治理平台化，带控制台与规则动态推送）

## 五、现役方案：Sentinel 与 Hystrix 不是一个定位 {#sentinel}

### 5.1 定位差异 {#sentinel-position}

| | Hystrix | Sentinel |
|---|---|---|
| 核心定位 | **熔断器**（一个组件解决一个问题） | **流量治理**：流控 + 熔断 + 系统保护 + 热点 + 授权 |
| 隔离方式 | 线程池 / 信号量 | **并发线程数流控**（不建独立线程池） |
| 规则配置 | 代码 / 配置文件，改动要重启 | **动态推送**（控制台改，秒级生效） |
| 统计模型 | 滑动窗口（RxJava 实现） | **LeapArray 滑动窗口**（默认 1 秒切 2 格，每格 500ms） |
| 生态 | 已停更 | 活跃，有控制台、集群流控、网关适配 |

**关键差别在"规则能不能动态改"**：线上流量突增时，改 Hystrix 参数要改配置重启；Sentinel 控制台改完立即生效。这是生产可用性的实质差别。

### 5.2 三组规则 {#sentinel-rules}

```text
① 流控规则（FlowRule）—— 控制【进来】的流量
   指标：QPS / 并发线程数
   流控效果：
     · 快速失败（默认）—— 超出直接拒绝
     · Warm Up（预热）—— 冷启动因子默认 3，逐步放开，防止系统刚启动就被打满
     · 排队等待 —— 匀速放行（本质是漏桶），把突发流量削平而不是丢弃

② 熔断降级规则（DegradeRule）—— 控制【出去】的调用
   三种策略（注意：与 Hystrix 完全不同的参数体系）：
     · 慢调用比例：RT 超过阈值的调用占比过高 → 熔断
     · 异常比例  ：异常占比过高 → 熔断
     · 异常数    ：异常数量超过阈值 → 熔断
   还需要配：最小请求数（防止样本太少误判）、统计时长、熔断时长

③ 系统保护规则（SystemRule）—— 从【整体】兜底
   监控：Load、CPU 使用率、平均 RT、并发线程数、入口 QPS
   触发时限制的是【所有入口流量】——这是最后一道防线
```

**这里特别提醒一个高频错误**：**绝不能把 Hystrix 的参数（10 秒 / 50% / 5 秒）套到 Sentinel 上**。Sentinel 的判定对象是「慢调用比例 / 异常比例 / 异常数」，阈值语义、统计窗口、熔断时长都是独立配置项。两个体系的数字混着说，一听就是背的。

### 5.3 Resilience4j {#resilience4j}

Spring Cloud 官方推荐的替代方案，特点是**模块化、轻量、函数式**：

| 模块 | 作用 | 对应 Hystrix 的 |
|---|---|---|
| `CircuitBreaker` | 断路器 | 断路器 |
| `RateLimiter` | 限流 | ❌ Hystrix 没有 |
| `Bulkhead` | 隔离（信号量 / 固定线程池） | 隔离策略 |
| `Retry` | 重试 | ❌ Hystrix 没有 |
| `TimeLimiter` | 超时 | 超时控制 |

**它是"工具箱"而不是"一体化组件"**：需要哪几个就装哪几个，通过 `application.yml` 配置或代码装饰。默认**用信号量隔离**（不额外建线程池），这也是它比 Hystrix 轻的原因。

## 六、降级逻辑写在哪 {#fallback}

以 OpenFeign 为例，降级代码写在 `fallback` 里：

```java
// 方式一：fallback —— 拿不到异常原因，只能返回兜底值
@FeignClient(name = "coupon-service", fallback = CouponFallback.class)
public interface CouponClient {
    @GetMapping("/coupon/{userId}")
    List<Coupon> listByUser(@PathVariable("userId") Long userId);
}

@Component
public class CouponFallback implements CouponClient {
    @Override
    public List<Coupon> listByUser(Long userId) {
        return Collections.emptyList();   // 空列表兜底：少给优惠券，不影响下单
    }
}
```

```java
// 方式二：fallbackFactory —— 能拿到异常，可区分"超时"和"业务报错"
@FeignClient(name = "coupon-service", fallbackFactory = CouponFallbackFactory.class)
public interface CouponClient { /* ... */ }

@Component
public class CouponFallbackFactory implements FallbackFactory<CouponClient> {
    @Override
    public CouponClient create(Throwable cause) {
        return userId -> {
            log.warn("调用优惠券服务失败，降级返回空列表", cause);
            return Collections.emptyList();
        };
    }
}
```

**推荐用 `fallbackFactory`**：`fallback` 拿不到异常，连日志都记不清原因；`factory` 能拿到 `Throwable`，可以区分超时、连接拒绝、业务异常，也方便打点。

三个配套要点：

1. **降级类必须是 Spring Bean**（`@Component` 或注册成 Bean），否则 Feign 找不到它。
2. **要配合开启断路器**，Feign 侧需要 `spring.cloud.openfeign.circuitbreaker.enabled=true`，否则 `fallback` 不会被触发。
3. **业务异常不应该触发熔断**。要区分「下游真的挂了」和「下游正常返回了一个业务错误」——后者是正常响应，把它计入失败率会导致服务被误熔断。Hystrix 时代用 `HystrixBadRequestException` 排除，Sentinel 时代用 `ignoreExceptions` 配置。

**降级返回什么，才是真正体现设计功力的地方**：

| 场景 | 合理的降级 | 不合理的降级 |
|---|---|---|
| 商品详情页的推荐位 | 返回空 / 缓存的热门推荐 | 整个页面报错 |
| 下单时的优惠券试算 | 按**无优惠**继续下单 | 拒绝下单 |
| 订单列表里的物流信息 | 显示"物流信息加载中" | 列表整个打不开 |
| 支付结果查询 | **绝不可降级**，必须真实结果 | 返回"支付成功"——会造成资金问题 |

**核心原则：降级要保核心链路（能下单、能支付），砍非核心（推荐、排行、物流展示）。** 反过来说，**涉及资金一致性、库存扣减的环节不该降级**，那里需要的是失败和重试，不是兜底值。

## 七、常见坑 {#pitfalls}

| 坑 | 现象 | 原因 |
|---|---|---|
| **只做熔断不做超时** | 熔断要等统计窗口攒够才生效，期间线程已被占满 | 超时是第一道防线，必须同时配 |
| **熔断阈值照搬 Hystrix 数字** | 规则配得莫名其妙 | Sentinel 的参数体系与 Hystrix 完全不同 |
| **最小请求数没配** | 低流量接口频繁误熔断 | 样本太少时比例没有意义 |
| **`fallback` 拿不到原因** | 排查时只有"降级发生了"，不知为何 | 改用 `fallbackFactory` |
| **业务异常触发熔断** | 正常业务错误把服务熔断 | 需配置忽略的异常类型 |
| **降级返回默认值掩盖了故障** | 页面看着正常，其实下游全挂 | 降级必须**打点 + 告警**，否则故障被静默 |
| **熔断时长设得太短** | 下游还没恢复就被反复试探打垮 | 熔断时长要大于下游典型恢复时间 |

## 面试口径

- **雪崩的本质是放大**：一个下游变慢 → 上游线程被占满 → 上游对新请求也不可用 → **故障沿链向上传播，牵连无关功能**。
- **三道防线**：超时（第一）→ 资源隔离（第二）→ 熔断（第三）。只上熔断是不够的。
- **降级 / 熔断 / 限流的分工**：限流是**不让进**、熔断是**不去调**、降级是**不调之后给什么结果**。熔断和限流**都会导致降级**，降级是结果不是并列手段。
- **断路器三状态**：Closed（放行 + 统计）→ Open（快速失败，**不打到下游**）→ Half-Open（放少量请求试探）→ 成功回 Closed / 失败回 Open。
- **Hystrix 触发条件（两个同时满足）**：10 秒窗口内请求数 ≥ **20** 且失败率 > **50%**；Open 持续 **5 秒**后进 Half-Open，放行 **1 个**请求试探。**别漏最小请求数这个条件。**
- **隔离策略**：线程池隔离（默认，一个下游一个池，慢的不影响其他）vs 信号量隔离（轻量，不换线程，超时控制弱）。
- **Hystrix 已被移除**（Spring Cloud 2020.0.0），替代是 **Resilience4j**（轻量函数式、默认信号量隔离）或 **Sentinel**（流量治理平台，规则可动态推送、有控制台）。
- **Sentinel 熔断三策略**：慢调用比例 / 异常比例 / 异常数；流控三效果：快速失败 / Warm Up / 排队等待。**参数体系与 Hystrix 完全不同，不能混着背。**
- **降级写在哪**：Feign 的 `fallbackFactory` 优于 `fallback`（能拿到异常）；降级类必须是 Bean；要开 `circuitbreaker.enabled`；**业务异常要排除在熔断统计之外**。
- **降级原则**：保核心（下单、支付）、砍非核心（推荐、排行）；**资金与库存一致性环节不应降级**。
