# 分布式事务

## 一、本地事务什么时候不够用 {#why}

单机时代，`@Transactional` 就够了——一个数据库连接、一套 undo，要么全成功要么全回滚。**有两种变化会让它失效**：

| 变化 | 例子 | 为什么本地事务失效 |
|---|---|---|
| **一个库拆成了多个库** | 订单库、库存库分开（分库分表的必然结果） | 一个 `Connection` 只能管一个库，跨库就没有统一的提交点 |
| **拆成了多个服务** | 订单服务写订单库，库存服务写库存库 | 两个服务两个连接两个事务，谁也管不了谁 |

一个典型的下单流程涉及三处写入：

```text
订单服务 ──▶ 写订单表（订单库）
库存服务 ──▶ 扣库存（库存库）
积分服务 ──▶ 加积分（积分库）

如果第 ③ 步失败：订单已建、库存已扣、积分没加
   → 用本地事务？管不了三个库
   → 直接忽略？数据不一致，迟早要人工修
```

**先说一个容易被忽略的前提**：不是所有"多步写入"都需要分布式事务。**绝大多数场景其实靠"本地事务 + 消息队列 + 幂等消费"就能解决**，只有确实需要"要么全成、要么全不成"的语义时才上 Seata。**先判断要不要用，比选哪种模式更重要**——引入分布式事务框架会带来额外的部署组件、性能损耗和排障复杂度。

## 二、Seata 的三个角色 {#roles}

Seata 的架构里有三个角色，**面试必问，且常被混着说**：

| 角色 | 全称 | 在哪 | 职责 |
|---|---|---|---|
| **TC** | Transaction Coordinator（事务协调器） | **独立部署的服务端**（Seata Server） | 维护**全局事务**状态，驱动所有分支事务提交或回滚 |
| **TM** | Transaction Manager（事务管理器） | 集成在业务应用里 | 定义**全局事务边界**（标注 `@GlobalTransactional` 的方法），发起全局提交 / 回滚 |
| **RM** | Resource Manager（资源管理器） | 集成在业务应用里 | 管理**分支事务**（本地资源），向 TC 注册、上报状态、执行 TC 下发的指令 |

**一句话区分 TM 和 RM**：**TM 是"发号施令的人"，RM 是"干活的人"**。TM 只负责开启和结束全局事务（它不碰数据），RM 负责真正的业务写入。

```text
① TM 开启全局事务 → 向 TC 注册，拿到全局唯一 XID
② XID 沿调用链透传（放在 RPC 上下文里，所以下游才认得出这是同一个全局事务）
③ 各服务的 RM 执行本地业务，向 TC 注册【分支事务】并上报状态
④ TM 结束全局事务 → 通知 TC 提交或回滚
⑤ TC 汇总所有分支状态 → 决定全局提交或回滚 → 通知各 RM 执行
```

**第 ② 步值得留意**：XID 必须跨服务传递，所以它依赖 RPC 框架的上下文透传能力——**如果调用链中某一跳用了不支持上下文透传的客户端（比如手写的 HTTP 调用），全局事务会退化成多个独立本地事务**，这是很隐蔽的一类故障。

```java
// 全局事务就这么标注：加在最外层的业务方法上
@GlobalTransactional(timeoutMills = 30000, name = "create-order")
public void createOrder(OrderDTO dto) {
    orderService.save(dto);      // 分支事务 ①
    stockService.deduct(dto);    // 分支事务 ②（远程调用）
    pointService.add(dto);       // 分支事务 ③（远程调用）
}
```

## 三、四种模式 {#modes}

**这里是必须纠正的一处**：Seata 官方提供的是**四种**模式（**AT / TCC / Saga / XA**）。不少面试话术稿把「MQ 方案」也算作 Seata 的一种模式，**这是错的**——消息队列是**独立于 Seata 的另一类方案**（见第六节）。这个错很容易被追问出来，因为 Seata 的配置里根本没有"MQ 模式"这个选项。

| 模式 | 一致性 | 侵入性 | 原理 | 性能 | 适用场景 |
|---|---|---|---|---|---|
| **XA** | **强一致（CP）** | 无 | 数据库原生 XA 协议，两阶段提交 | **最差** | 强一致要求高、参与方少、非高并发（银行账务） |
| **AT** | 最终一致 | **无** | 代理数据源，自动生成 `undo_log` 快照，回滚时还原 | 好 | **大多数互联网业务**（默认选择） |
| **TCC** | 最终一致 | **高** | 手写 Try（预留资源）/ Confirm（提交）/ Cancel（释放） | 好（无全局锁） | 有资源预留语义、对性能要求高（资金冻结、库存锁定） |
| **Saga** | 最终一致 | 中高 | 长事务拆成多个本地事务 + 补偿操作 | 好 | **长流程、老系统无法改造**、参与方多 |

### 三种模式的直观差别 {#modes-intuition}

用一个「A 转账给 B」的例子，看三种模式各自怎么做：

```text
【XA】各分支先执行 SQL 但不提交 ──── 全部就绪 ──── 统一提交
      问题：数据库连接和锁一直持有到二阶段结束 → 并发能力最差

【AT】各分支直接执行并提交，但先存一份"改之前的样子"
      出问题 → 用那份快照把数据改回去
      好处：一阶段就提交，不长时间占资源 → 性能好得多

【TCC】不改 SQL，改成三段式业务接口
      Try    ：冻结 A 的 30 元（钱还在 A 账上，但不能用）
      Confirm：真正扣掉这 30 元
      Cancel ：解冻，恢复原状
      好处：不用锁数据库资源 → 性能最好；代价：三个接口都得自己写
```

## 四、AT 模式详解 {#at}

AT 是 Seata 的默认模式，也是用得最多的，**它的细节最值得讲透**。

### 4.1 一阶段：执行并记录"前后镜像" {#at-phase1}

```text
拦截业务 SQL（Seata 通过代理数据源拿到的）
   │
   ├─ ① 解析 SQL 语义，查出【受影响的数据】
   │
   ├─ ② 生成 before image（改动【前】的快照）
   │
   ├─ ③ 执行业务 SQL
   │
   ├─ ④ 生成 after image（改动【后】的快照）
   │
   ├─ ⑤ 把 ② ④ 写进 undo_log 表
   │
   ├─ ⑥ 向 TC 申请【全局锁】
   │
   └─ ⑦ 提交本地事务、释放本地锁（但【保留全局锁】）
```

**第 ⑦ 步是 AT 性能好的根本原因**：一阶段就把本地事务提交了，数据库连接和行锁立刻释放——这正是 XA 做不到的。

### 4.2 二阶段：提交或回滚 {#at-phase2}

```text
【提交】所有分支都成功
   → 各 RM 异步删除 undo_log、释放全局锁
   → 注意：业务数据在一阶段就已经落库了，二阶段【什么都不用做】

【回滚】有分支失败
   → ① 校验脏写：对比【当前数据库中的数据】与 undo_log 里的 after image
         · 一致  → 说明这行没被别人改过，可以安全回滚
         · 不一致 → 说明发生了脏写，【不能自动回滚】，转人工处理
   → ② 用 before image 生成反向 SQL，还原数据
   → ③ 删除 undo_log、释放全局锁
```

**为什么要做脏写校验**（这是最容易被追问的一步）：设想订单服务扣了库存 10→9，在全局回滚之前，另一个非 Seata 管理的事务把库存改成了 5。此时直接用 before image 还原成 10，就会**覆盖掉别人合法的修改**——数据错得更离谱。所以宁可停下来报错，让人来判断。

**全局锁就是用来减少这种情况的**：它保证"同一个全局事务内的资源不被其他全局事务改动"。但注意它**管不了不受 Seata 管理的事务**，所以脏写校验这层兜底依然必要。

### 4.3 隔离性 {#at-isolation}

AT 模式的隔离性要说清两个方向：

| | 机制 | 说明 |
|---|---|---|
| **写隔离** | **全局锁**（TC 维护） | 两个全局事务要改同一行时，后到的必须等前一个结束 |
| **读隔离** | 默认**读未提交** | 全局事务未提交时，其他事务能读到中间结果；需要更强隔离要写 `SELECT ... FOR UPDATE`（会申请全局锁，升级为读已提交） |

**「默认读未提交」是 AT 的一处实际限制**，如果业务不能容忍读到未提交的中间值（比如查余额），就得显式加 `FOR UPDATE`，代价是引入锁等待、性能下降。**这往往就是把 AT 换成 TCC 的理由。**

### 4.4 AT 的适用边界 {#at-limit}

| 适合 | 不适合 |
|---|---|
| 基于**主流关系型数据库**（MySQL / Oracle / PostgreSQL 等） | 涉及 NoSQL、跨异构数据源（AT 靠 SQL 解析，解析不了的文件 / 缓存没法自动回滚） |
| 短事务、参与方少（3~5 个） | **长事务**（全局锁持有时间与之成正比） |
| 想零代码侵入、快速接入 | **热点数据高并发**（全局锁会变成瓶颈，例如秒杀扣库存） |

**关于 `@GlobalTransactional` 的超时**：默认 60 秒。**超时后 TC 会触发全局回滚**——如果业务方法本身没做好幂等，重试时可能产生重复数据。

## 五、TCC 的三个设计要点 {#tcc}

TCC 需要自己写三个接口，**难点不在写，而在这三种异常情况**，它们几乎是 TCC 面试的标准追问：

| 问题 | 什么情况发生 | 怎么解 |
|---|---|---|
| **空回滚** | Try 没执行（请求丢包了），但 TC 触发了 Cancel | Cancel 里先查"是否执行过 Try"，没执行过就**直接返回成功**（不能报错，否则 TC 会一直重试） |
| **防悬挂** | Cancel 比 Try 先到（Try 因网络拥堵超时，TC 先发起回滚，随后那个迟到的 Try 才到） | Cancel **空回滚时记录一条事务记录**；Try 执行前先检查这条记录，已回滚过则**拒绝执行 Try** |
| **幂等** | TC 会重试，同一个 Confirm / Cancel 可能被调用多次 | 用**事务 XID 或业务主键**做判重 |

**这三个问题的共同根因**是「网络不可靠 + TC 会重试」，**它们不是 TCC 的缺陷，而是任何分布式补偿方案都必须面对的**——Saga 模式同样需要空补偿、防悬挂、幂等三件套。

**TCC 与 AT 的关键取舍**：TCC **没有 AT 的全局锁**，所以性能更高、也没有"读未提交"的问题；代价是业务代码侵入大（三个接口 + 三种异常处理），且**要求"Try 成功则 Confirm 必定成功"**——这个约束把风险集中到了 Try 阶段的资源预留设计上。

## 六、消息队列方案：它不是 Seata 的模式 {#mq}

**必须先纠正一个常见的错误说法**：把「MQ 方案」列为 Seata 的一种事务模式。**Seata 官方只有 AT / TCC / Saga / XA 四种模式**；消息队列属于**另一条技术路线**——用"可靠消息 + 幂等消费"实现最终一致，不需要 TC 这样的协调者。

**为什么这两者容易被混在一起**：它们都归在"分布式事务解决方案"这个话题下，且都能达成"最终一致"。但机制完全不同——Seata 的模式**靠协调者（TC）驱动提交或回滚**，MQ 方案**靠消息的可靠性投递 + 消费端幂等**，没有全局协调者。面试时如果把它们并列成"Seata 的第五种模式"，会被直接追问到答不上来。

### 6.1 两条经典路线 {#mq-two}

| 路线 | 做法 | 特点 |
|---|---|---|
| **本地消息表** | 业务操作和"待发送消息"写在**同一个本地事务**里；再由定时任务 / 线程扫描消息表投递到 MQ；消费方幂等消费，成功后回执 | 不依赖 MQ 的高级特性，**任何 MQ 都能用**；需要自己维护消息表和扫描任务 |
| **事务消息**（RocketMQ） | 先发**半消息**（对消费方不可见）→ 执行本地事务 → 提交或回滚半消息 → 若未确认，Broker 回查本地事务状态 | 由 MQ 承担可靠性，代码更简洁；**依赖 MQ 支持事务消息** |

### 6.2 关键是"幂等 + 对账" {#mq-idempotent}

MQ 方案能成立的前提是**"消息一定会被重复投递"**这个假设——所以消费端必须幂等（见[接口幂等](/java/spring/spring-cloud/idempotency)）。此外还需要**对账**：定时比对两边的数据，把少量漏掉 / 不一致的记录修回来。以谁为准、差账怎么分类、窗口怎么开，见[对账与补偿](/methodology/reconciliation)，本篇不展开。

**"最终一致"里的"最终"不是自动发生的**，是靠**重试 + 幂等 + 对账**这三件套保证的。这一点在面试里说出来，比只说"用 MQ 保证最终一致"高一个层次。

**与业务解耦的关系**：MQ 方案的额外好处是——下游消费失败不必阻塞主流程，只是"稍后重试"，主流程的响应时间不受影响。这也是**大多数互联网业务优先选 MQ 而不是 Seata**的原因。

## 七、怎么选 {#selection}

```text
需要"要么全成要么全不成"的强一致吗？
│
├─ 是，且参与方少、并发不高（如账务）
│     └─▶ XA（或直接用数据库 XA，不引 Seata）
│
└─ 否，能接受最终一致
      │
      ├─ 下游不需要同步返回结果（发通知、加积分、更新统计）
      │     └─▶ MQ 方案（本地消息表 / 事务消息）—— 最简单、性能最好
      │
      ├─ 有明确的"资源预留"语义（冻结余额、锁定库存）
      │     └─▶ TCC
      │
      ├─ 流程长、参与方多、下游是老系统改不了
      │     └─▶ Saga
      │
      └─ 大多数常规情况（短事务、参与方少、关系型数据库）
            └─▶ AT（默认选择，零侵入）
```

**一个现实提醒**：**能不用分布式事务就不用**。绝大多数业务可以通过「**重新设计业务流程，让它天然不需要跨服务事务**」来解决——比如把"扣库存"改成"扣库存 + 异步通知"（扣库存是本地的、通知失败可重试），一致性要求就从"强"降到了"最终"，方案复杂度直接下降一个数量级。**面试时说"我们评估后决定不用分布式事务，因为……"，往往比说"我们用了 Seata"更有说服力**——前提是你能讲清为什么。

## 八、常见坑 {#pitfalls}

| 坑 | 现象 | 原因 |
|---|---|---|
| **把 MQ 当成 Seata 的一种模式** | 被追问「Seata 里怎么配 MQ 模式」时答不上来 | Seata 只有四种模式，MQ 是独立方案 |
| **XID 没有跨服务透传** | 全局事务没生效，各写各的 | 调用链中某一跳（如手写 HTTP）不支持上下文透传 |
| **长事务 + AT** | 全局锁长时间不释放，其他事务排队 | 全局锁持有时长正比于事务时长 → 拆短或换 TCC |
| **热点数据用 AT** | 秒杀时全局锁成为瓶颈 | 热点行高并发 → 换 TCC 或改用异步扣减 |
| **`@GlobalTransactional` 超时后重试不幂等** | 产生重复订单 | 默认 60 秒超时触发回滚，业务重试必须幂等 |
| **TCC 没有防悬挂 / 空回滚** | 出现"Try 在 Cancel 之后执行"，数据错乱 | 三个接口必须成对设计（见第五节） |
| **文件 / 缓存 / NoSQL 也想自动回滚** | AT 管不了，数据不一致 | AT 依赖 SQL 解析，非关系型数据源要自己写补偿逻辑 |
| **把分布式事务当第一选择** | 架构复杂度、部署成本、排障难度全部上升 | 先问"能不能通过改业务流程避免跨服务事务" |

## 面试口径

- **先判断要不要用**：绝大多数"多步写入"靠**本地事务 + MQ + 幂等消费**即可；只有确实需要"全成或全不成"时才引入分布式事务框架。
- **三个角色**：**TC**（协调器，独立部署的服务端，维护全局事务、驱动提交回滚）、**TM**（事务管理器，在业务应用里，**定义全局事务边界**并发起全局提交 / 回滚）、**RM**（资源管理器，在业务应用里，管理**分支事务**、注册并上报状态）。**TM 发令、RM 干活、TC 协调。**
- **四种模式（**不是五种**）**：**XA** 强一致、性能最差、无侵入；**AT** 最终一致、无侵入、性能好、**默认选择**；**TCC** 需手写三接口、侵入大、无全局锁性能最好；**Saga** 长事务、补偿式、适合老系统。**MQ 不属于 Seata 的模式**，是独立的最终一致方案。
- **AT 的核心机制**：一阶段拦截 SQL → 记录 **before image / after image** 到 **`undo_log`** → 申请**全局锁** → **提交本地事务**（这是它比 XA 快的根本原因）；二阶段提交时**异步删日志**，回滚时**先校验脏写**（比对当前值与 after image）再用 before image 还原。
- **AT 的隔离性**：写隔离靠**全局锁**；读隔离**默认读未提交**，要读已提交需显式 `SELECT ... FOR UPDATE`（代价是锁等待）。不能容忍这一点的话，就该考虑 TCC。
- **AT 不适合**：长事务、热点数据高并发、非关系型 / 异构数据源。
- **TCC 的三个必答题**：**空回滚**（Try 未执行却收到 Cancel → 直接返回成功并记录）、**防悬挂**（Cancel 先于 Try → Try 执行前检查是否已回滚）、**幂等**（用 XID 判重）。**根因都是"网络不可靠 + TC 会重试"，Saga 同样需要这三件套。**
- **MQ 方案的两条路线**：**本地消息表**（业务与消息在同一本地事务，扫描投递，不依赖 MQ 特性）、**事务消息**（RocketMQ 半消息 + 事务回查）。
- **最终一致不是自动的**：靠 **重试 + 幂等 + 对账** 三件套；「最终」两个字背后是一整套兜底机制。对账闭环见[对账与补偿](/methodology/reconciliation)。
