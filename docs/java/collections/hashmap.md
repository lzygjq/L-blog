# HashMap 实现原理

`HashMap` 是集合里被问得最狠的一个：**数据结构 → 哈希算法 → 扩容 → 并发缺陷**，一条链上的每一环都能单独出一道题。它的底层并不神秘——**数组 + 链表 / 红黑树**，但每一处设计都有明确的取舍理由。

要讲清 `HashMap`，得先把它的两个前置数据结构说透：**红黑树**（解决链表过长）和**散列表**（解决「怎么把 key 变成下标」）。

## 一、从二叉树到红黑树

### 二叉树

> 二叉树：每个节点最多有两个「叉」，即两个子节点，分别是**左子节点**和**右子节点**。

注意两点：

1. **不要求每个节点都有两个子节点**，有的节点只有左子节点，有的只有右子节点；
2. 二叉树每个节点的**左子树和右子树也分别满足二叉树的定义**（递归结构）。

Java 中有两种实现方式：**数组存储**和**链式存储**。基于链式存储的节点可定义如下：

```java
public class TreeNode {
    int val;
    TreeNode left;
    TreeNode right;

    TreeNode() {}

    TreeNode(int val) {
        this.val = val;
    }

    TreeNode(int val, TreeNode left, TreeNode right) {
        this.val = val;
        this.left = left;
        this.right = right;
    }
}
```

### 二叉树分类

常见的二叉树有：**满二叉树、完全二叉树、二叉搜索树、红黑树**。

### 二叉搜索树（BST）

> 二叉搜索树（Binary Search Tree，BST），又名二叉查找树、有序二叉树、排序二叉树。

核心性质：**在树中的任意一个节点，其左子树中每个节点的值都小于这个节点的值，而右子树中每个节点的值都大于这个节点的值**，且没有键值相等的节点。

理想形态下，插入、查找、删除的时间复杂度都是 `O(log n)`。

**但 BST 有个致命弱点**：它的形态取决于插入顺序。如果按 `99, 78, 56, 40, 35, 20, 11` 的顺序插入，树会**退化成链表**，左右子树极度不平衡，此时查找的时间复杂度退化为 `O(n)`。

这个「退化」问题，正是**红黑树**存在的理由。

### 红黑树

> 红黑树（Red Black Tree）：一种**自平衡的二叉搜索树（BST）**。

它靠五条性质来维持平衡：

| 性质 | 内容 |
|---|---|
| 1 | 节点要么是**红色**，要么是**黑色** |
| 2 | **根节点是黑色** |
| 3 | **叶子节点（空节点）都是黑色** |
| 4 | 红色节点的子节点都是黑色（不存在连续两个红节点） |
| 5 | 从任一节点到叶子节点的所有路径都包含**相同数目的黑色节点** |

**在添加或删除节点时，如果不符合这些性质，就会发生旋转**，以达到所有性质——所有红黑规则的目的都是为了保证平衡。

**时间复杂度**：

| 操作 | 过程 | 复杂度 |
|---|---|---|
| 查找 | 走 BST 查找路径 | `O(log n)` |
| 添加 | 先找到插入位置 `O(log n)`，再做 `O(1)` 的旋转调整 | `O(log n)` |
| 删除 | 先找到被删元素位置 `O(log n)`，再做 `O(1)` 的旋转调整 | `O(log n)` |

## 二、散列表

在 `HashMap` 中最重要的数据结构就是**散列表**，散列表中又用到了**红黑树**和**链表**。

### 概念

> 散列表（Hash Table），又名哈希表 / Hash 表，是**根据键（Key）直接访问在内存存储位置的值（Value）**的数据结构，它由**数组演化而来**，利用了数组支持按下标随机访问的特性。

举例：100 人参加马拉松，编号 1–100，用编号直接作为数组下标即可快速找到选手信息。

但如果编号规则变成 `2023ZHBJ001`（2023 年份 + ZH 中国 + BJ 北京 + 001 序号），就**不能直接作为数组下标**了。此时需要一个**散列函数**把 key 转换成数组下标：

```text
hashValue = hash(key)
```

**散列函数的基本要求**：

1. 计算得到的散列值必须是**大于等于 0 的正整数**（要作为数组下标）；
2. 如果 `key1 == key2`，则 `hash(key1) == hash(key2)`；
3. 如果 `key1 != key2`，则 `hash(key1) != hash(key2)`。

### 散列冲突

第 3 条要求在实际中**几乎无法满足**——想找一个散列函数，让不同的 key 算出的散列值都不同，即便 MD5、SHA 这样的哈希算法也做不到。**多个 key 映射到同一个数组下标位置**，就叫**散列冲突**（哈希冲突 / 哈希碰撞）。

### 解决冲突：链表法（拉链）

散列表中数组的每个下标位置称为**桶（bucket）**或**槽（slot）**。链表法的做法是：**每个桶对应一条链表，所有散列值相同的元素都放到同一个槽位对应的链表中。**

**时间复杂度**：

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 插入 | `O(1)` | 算出槽位后直接插入对应链表 |
| 查找 / 删除 | 平均 `O(1)` | 平均情况下查询复杂度是 `O(1)` |
| 查找（极端） | `O(n)` | 散列不均时**散列表退化为链表**，从 `O(1)` 退化为 `O(n)` |
| 查找（链表改红黑树后） | `O(log n)` | 把链表改造为红黑树 |

> **为什么要把链表改造成红黑树？** 除了把极端情况从 `O(n)` 降到 `O(log n)`，还有一个非常重要的原因——**防止 DDoS 攻击**。DDoS（分布式拒绝服务）指多个攻击者同时向目标发动攻击。如果攻击者刻意构造大量哈希值相同的 key，散列表就会退化成链表，查询性能骤降，形成「哈希碰撞攻击」。红黑树能有效抬高这条攻击路径的成本。

## 三、实现原理 {#实现原理}

**`HashMap` 的数据结构：底层使用 hash 表结构，即数组 + 链表或红黑树。**

put 元素时的流程：

1. 当我们往 `HashMap` 中 put 元素时，利用 key 的 `hashCode` 重新 hash 计算出当前对象在数组中的下标；
2. 存储时，如果出现 hash 值相同的 key，此时有两种情况：
   - a. 如果 **key 相同**，则**覆盖原始值**；
   - b. 如果 **key 不同**（出现冲突），则将当前的 key-value **放入链表或红黑树**中；
3. 获取时，直接找到 hash 值对应的下标，再进一步判断 key 是否相同，从而找到对应值。

**链表转红黑树的条件：链表长度大于 8，且数组长度大于 64。**

```text
数据结构的演化：

数组（下标直接访问）
  + 链表（解决散列冲突）
  + 红黑树（解决链表过长，链表长度 > 8 且数组长度 > 64）
```

## 四、JDK 1.7 与 1.8 的差异 {#jdk-17-与-18-的差异}

| 版本 | 数据结构 | 冲突处理 | 扩容时的插入方式 |
|---|---|---|---|
| JDK 1.8 之前 | 数组 + 链表 | 采用**拉链法**：创建一个链表数组，数组中每一格就是一个链表，遇到哈希冲突就把冲突的值加到链表中 | **头插法** |
| JDK 1.8 之后 | 数组 + 链表 + **红黑树** | 当**链表长度大于阈值（默认 8）且数组长度达到 64** 时，将链表转化为红黑树，以减少搜索时间 | **尾插法**（保持与扩容前一样的顺序） |

补充两个 1.8 的细节：

- 扩容 `resize()` 时，红黑树拆分成的树的**结点数小于等于临界值 6**，则**退化回链表**；
- 正因为改成了尾插法，JDK 1.8 **规避了 1.7 的多线程死循环问题**（见下文）。

## 五、put 流程 {#put-流程}

### 源码分析：常见属性

```java
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;   // 默认的初始容量 = 16
static final float DEFAULT_LOAD_FACTOR = 0.75f;       // 默认的加载因子
transient HashMap.Node<K,V>[] table;
transient int size;

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    HashMap.Node<K,V> next;

    Node(int hash, K key, V value, HashMap.Node<K,V> next) {
        this.hash = hash;
        this.key = key;
        this.value = value;
        this.next = next;
    }
}
```

关系式：**扩容阈值 == 数组容量 × 加载因子**（默认 `16 × 0.75 = 12`）。

### 懒惰加载

```java
Map<String, String> map = new HashMap<>();
map.put("name", "itheima");

public HashMap() {
    this.loadFactor = DEFAULT_LOAD_FACTOR;   // all other fields defaulted
}
```

`HashMap` 是**懒惰加载**：**在创建对象时并没有初始化数组**（`table` 仍为 `null`），无参构造函数里只设置了默认加载因子 0.75。数组是在**第一次 put 时**才通过 `resize()` 初始化的。

### put 方法的具体流程

```text
开始
 ├─ 数组 table 是否为空？
 │    是 → resize() 初始化长度为 16 的数组（threshold = 数组长度 × 0.75）
 │    否（非第 1 次）→ 继续
 ├─ 根据 key 计算数组索引值 i
 ├─ table[i] == null ？
 │    是 → 直接插入
 │    否 → 分三种情况
 │         ├─ key 是否存在？
 │         │    是 → 直接覆盖 value
 │         │    否 → 继续
 │         ├─ table[i] 是否是红黑树？
 │         │    是 → 在红黑树中添加
 │         │    否 → 遍历链表到链尾插入结点
 │         │           → 链表长度是否大于 8？是 → 转换为红黑树
 └─ ++size > threshold ？ 是 → resize() 扩容
结束
```

文字版：

1. 判断键值对数组 `table` 是否为空或为 `null`，是则执行 `resize()` 进行扩容（初始化）；
2. 根据键值 `key` 计算 hash 值，得到数组索引；
3. 判断 `table[i] == null`，条件成立则**直接新建节点添加**；
4. 如果 `table[i] == null` 不成立：
   - 4.1 判断 `table[i]` 的**首个元素**是否和 key 一样，相同则**直接覆盖 value**；
   - 4.2 判断 `table[i]` **是否为 treeNode**，即 `table[i]` 是否是红黑树，是则在树中插入键值对；
   - 4.3 **遍历 `table[i]`**，在**链表尾部插入**数据，然后判断链表长度是否大于 8，大于 8 则把链表转换为红黑树，在红黑树中执行插入操作；遍历过程中若发现 key 已经存在，**直接覆盖 value**；
5. 插入成功后，判断实际存在的键值对数量 `size` 是否超过最大容量 `threshold`（数组长度 × 0.75），超过则进行扩容。

## 六、扩容机制 {#扩容机制}

### 扩容流程

```text
开始
 ├─ oldCap > 0 ？
 │    是 → newCap = oldCap * 2
 │    否 → 设置数组容量为 16、扩容阈值 12
 ├─ 新建数组
 └─ 遍历旧数组
      ├─ e.next == null → 直接按 e.hash & (newCap - 1) 放入新数组
      ├─ 是否是红黑树 → 走红黑树的添加（拆分）
      └─ 遍历链表
           ├─ (e.hash & oldCap) == 0 → newTab[j] = oldTab[j]         （留在原位）
           └─ 否则                      → newTab[j + oldCap] = oldTab[j]（原位 + oldCap）
结束
```

### 讲一讲 HashMap 的扩容机制

1. 在**添加元素或初始化**的时候需要调用 `resize` 方法进行扩容：**第一次添加数据时初始化数组长度为 16**，以后**每次扩容都是在达到扩容阈值（数组长度 × 0.75）时触发**；
2. **每次扩容都是之前容量的 2 倍**；
3. 扩容之后会**新创建一个数组**，需要把老数组中的数据挪动到新数组中；
4. 具体迁移规则：
   - **没有 hash 冲突的节点**：直接用 `e.hash & (newCap - 1)` 计算新数组的索引位置；
   - **如果是红黑树**：走红黑树的添加；
   - **如果是链表**：遍历链表，可能需要**拆分链表**，判断 `(e.hash & oldCap)` 是否为 0——该元素的位置**要么停留在原始位置，要么移动到「原始位置 + 增加的数组大小」**这个位置上。

## 七、寻址算法

```java
public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    // ……
    if ((p = tab[i = (n - 1) & hash]) == null) {
        // ……
    }
}
```

两个关键设计：

| 设计 | 作用 |
|---|---|
| `hash(key) = h ^ (h >>> 16)` | **扰动算法**：让 hash 值更加均匀，减少 hash 冲突 |
| `(n - 1) & hash` | 得到数组中的索引，**代替取模，性能更好** |

而 `(n - 1) & hash` 能成立的前提是——**数组长度必须是 2 的 n 次幂**。

## 八、为什么长度必须是 2 的次幂 {#为什么长度必须是-2-的次幂}

两个理由：

1. **计算索引时效率更高**：如果是 2 的 n 次幂，可以用**位与运算代替取模**；
2. **扩容时重新计算索引效率更高**：`hash & oldCap == 0` 的元素**留在原来位置**，否则**新位置 = 旧位置 + oldCap**。

完整链路复述一遍：

```text
1. 计算对象的 hashCode()
2. 调用 hash() 做二次哈希：hashCode 值右移 16 位再异或运算 → 让哈希分布更均匀
3. 最后 (capacity - 1) & hash 得到索引
```

## 九、JDK 1.7 的多线程死循环 {#jdk-17-的多线程死循环}

### 问题根源

JDK 1.7 的数据结构是**数组 + 链表**。在数组进行扩容时，因为链表采用**头插法**，在进行数据迁移的过程中，**有可能导致死循环**。

```java
void transfer(Entry[] newTable, boolean rehash) {
    int newCapacity = newTable.length;
    for (Entry<K, V> e : table) {
        while (null != e) {
            Entry<K, V> next = e.next;
            if (rehash) {
                e.hash = null == e.key ? 0 : hash(e.key);
            }
            int i = indexFor(e.hash, newCapacity);
            e.next = newTable[i];
            newTable[i] = e;
            e = next;
        }
    }
}
```

关键点：

- 变量 `e` 指向需要迁移的对象，变量 `next` 指向下一个需要迁移的对象；
- JDK 1.7 中链表采用**头插法**；
- 迁移过程中**并没有新对象产生，只是改变了对象的引用**。

### 死循环是怎么形成的

假设原链表顺序是 `A → B`：

1. **线程 1** 读取到当前的 `HashMap` 数据（一个链表 `A → B`），在准备扩容时，**线程 2 介入**；
2. **线程 2** 也读取 `HashMap`，直接完成扩容。因为是**头插法**，链表顺序会**颠倒**——原来 `AB`，扩容后变成 `BA`，线程 2 执行结束；
3. **线程 1** 恢复执行，此时线程 1 的临时变量 `e`、`next` 仍引用着原来的两个节点，而线程 2 迁移时已经把 `B` 的 `next` 指向了 `A`。

于是线程 1 继续迁移时：先将 `A` 移入新链表，再把 `B` 插入到链头；由于另一个线程的原因，`B` 的 `next` 已经指向 `A`，最终形成 **`B → A → B` 的环形链表** → 后续任何一次查询走到这个桶都会**死循环**，CPU 被打满。

### 参考回答

> 在 JDK 1.7 的 `HashMap` 中，数组扩容时链表采用**头插法**，数据迁移过程中可能形成死循环。
>
> 比如现在有两个线程：线程一读取到当前的 `HashMap` 数据（其中一个链表），在准备扩容时线程二介入；线程二也读取 `HashMap` 并直接完成扩容，由于是头插法，链表顺序被颠倒（原 `AB` → 变 `BA`），线程二执行结束；线程一继续执行时就会出现死循环——它先将 `A` 移入新链表，再将 `B` 插入链头，而由于另一个线程的原因，`B` 的 `next` 已指向 `A`，于是 `B → A → B` 形成循环。
>
> JDK 1.8 把扩容算法调整为**尾插法**（不再将元素加入链表头，而是保持与扩容前一样的顺序），从而避免了 1.7 的死循环问题。

> **现实结论**：`HashMap` 从来就不是线程安全的。并发场景请用 `ConcurrentHashMap`——它用 CAS + synchronized 保证并发安全，且分段/桶级加锁，性能远优于 `Collections.synchronizedMap`。

| 扩容机制？ | 首次初始化 16，之后每次 2 倍；`hash & oldCap == 0` 留原位，否则移到「原位 + oldCap」 |
| 寻址算法？ | `hash(key) = h ^ (h >>> 16)` 扰动；`(n - 1) & hash` 代替取模取下标 |
| 为什么长度是 2 的次幂？ | 位运算代替取模更快；扩容时只需判断 `hash & oldCap` 即可定位新下标 |
| 1.7 多线程死循环原因？ | 扩容头插法颠倒链表 + 并发迁移，形成 `B → A → B` 环形链表 |
