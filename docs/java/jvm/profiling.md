# 火焰图与性能剖析：把"时间花在哪"变成一张图

> 上一篇：[Arthas 在线诊断](/java/jvm/online-diagnostics)　|　导览：[Java 虚拟机](/java/jvm/)

前面的工具解决"**有没有问题、问题在哪一类**"；火焰图解决的是"**时间具体花在哪一行代码上**"。它是性能优化里唯一能一次看全局、又不侵入代码的手段。

**先把结论放前面**：

1. **火焰图的横轴是「样本占比」，不是时间轴。** 左右顺序没有意义——这是读火焰图的第一条、也是最常错的一条。
2. **"接口慢但 CPU 不高"要看的是 off-CPU（wall-clock）火焰图。** on-CPU 图里那种线程几乎不出现，只看它一定会得出"没有热点"的错误结论。
3. **Java 采样有个特有偏差：安全点偏差。** 这正是 **async-profiler 在 Java 场景优于 `perf`** 的根本原因（[§2](#bias)）。
4. **采样给的是占比、不是精确耗时**，而且是"总占比"——**高频的短方法常常比低频的长方法更值得优化**。

## 一、三种观测手段的代价对比 {#three-ways}

| 手段 | 原理 | 精度 | 代价 | 适用 |
|---|---|---|---|---|
| **手动计时** | 代码里打点（`System.nanoTime()`） | 精确到指定代码段 | 侵入、要发版、容易漏；**观测本身影响结果** | 定位已知的可疑段 |
| **插桩** | 每个方法入口/出口埋点（tracing 类工具） | 精确的调用次数与耗时 | **开销大**，高频调用下放大明显 | 短时、小范围 |
| **采样** | 按固定频率中断并记录**当前调用栈** | **统计推断**（样本足够时很准） | **低（1% 量级）**，可长时间开 | **生产首选** |

**关键认知**：**采样给的是"占比"，不是"精确耗时"。** 一个方法在图上占 30% 宽，含义是"30% 的采样点落在它及其子调用上"——样本量足够时它近似等于时间占比，样本太少时就会失真（这也是"采样时间要够长"的原因）。

**这也和 [Arthas 的 `trace`](/java/jvm/online-diagnostics#trace) 是同一条原理的两面**：`trace` 是插桩式的，所以对高频方法代价大；火焰图是采样式的，所以能放心在生产开。

## 二、Java 采样的两个特有偏差 {#bias}

### 2.1 安全点偏差（safe point bias） {#safepoint}

**JVM 只在安全点（safepoint）才能记录/遍历栈。** 于是：

| 环节 | 会发生什么 |
|---|---|
| 采样信号到达时线程**不在**安全点 | JVM 推迟到下一个安全点才记录 |
| 记录到的是"**到达安全点那一刻**的栈" | 不一定是"采样时刻"的栈 |
| 结果 | 某些方法被**系统性高估**（频繁进出安全点的），某些被**低估**（长时间不经过安全点的紧凑计算循环） |

**async-profiler 的解法**：它用的是 HotSpot 内部的 **`AsyncGetCallTrace`** 接口，**可以在非安全点采集调用栈**，从机制上缓解这类偏差。**这是它相对 `perf` 的核心优势之一。**

### 2.2 perf 为什么看不到 Java 栈 {#perf}

`perf` 是内核采样器，默认拿不到 Java 栈，原因有两个：

| 原因 | 说明 | 解法 |
|---|---|---|
| **JIT 编译后的代码没有符号表** | 内核不知道那段机器码属于哪个方法 | perf-map-agent 生成映射文件 |
| **默认不保留帧指针** | 采样器无法沿帧指针回溯调用链 | `-XX:+PreserveFramePointer`（有轻微性能影响） |

**结论**：**Java 场景直接用 async-profiler，比 `perf + FlameGraph` 少踩两个坑。** `perf` 更适合排查"机器整体在忙什么"（那时看的是 native/内核栈，与 Java 栈互补，见 [Linux 排查实战](/fundamentals/os/linux-tools)）。

## 三、火焰图怎么读 {#read}

### 3.1 六条规则 {#rules}

| # | 规则 | 说明 |
|---|---|---|
| 1 | **横轴 = 样本占比，不是时间轴** | 左右顺序**无意义**，是按名字聚合排序的结果 |
| 2 | **矩形宽度 = 该栈帧出现的比例** | 越宽 = 占用资源越多 |
| 3 | **纵轴 = 调用链深度** | 上方是调用者，下方是被调用者 |
| 4 | **顶层的宽"平顶"就是热点** | 平顶 = 采样在这里结束（叶子），说明时间花在这个函数自身 |
| 5 | **颜色没有含义** | 默认按包名/类型着色，只用于区分 |
| 6 | 优先找**自己代码**里最宽的那块 | JDK / 框架的宽块通常改不动，除非是使用方式或配置问题 |

### 3.2 三种形状的含义 {#shapes}

| 形状 | 含义 | 优化方向 |
|---|---|---|
| **平顶（plateau）** | 大量样本停在此处、向下没有更深调用 | **叶子热点**：就是这里在烧时间 |
| **宽而浅** | 大量并列的窄矩形 | 分散在很多小函数里，多是框架开销或调用方式问题 |
| **窄而深** | 一条细长的链 | 深层嵌套 / 层层封装；看是不是递归或过度分层 |

### 3.3 三种典型误读 {#misread}

1. **把横轴当时间轴**（"左边是先发生的"）——它是**聚合结果的排序**，与先后无关。
2. **以为宽度是"单次耗时"**——它是**总占比**。**每秒 10 万次 × 1μs 的方法，往往比每分钟 1 次 × 100ms 的方法更宽，而改前者的收益更大。**
3. **忽略内联（inlining）**——JIT 把小方法内联进调用者后，**栈里就不会单独出现那一帧**。**"看不到"不等于"没执行"。**

## 四、四类剖析：不同现象看不同的图 {#four-types}

**这一节是整篇最重要的认知：火焰图不止一种。** "时间花在哪"至少有四种问法，**选错类型会得到完全错误的结论**。

| 类型 | 回答的问题 | async-profiler 事件 | 对应现象 |
|---|---|---|---|
| **on-CPU** | CPU 时间花在哪些代码上 | `-e cpu`（默认） | CPU 使用率高 |
| **off-CPU / wall** | 线程在**等**什么（不占 CPU 的时间） | `-e wall` | **接口慢但 CPU 不高** |
| **alloc** | 谁在**分配对象** | `-e alloc` | GC 频繁、分配速率高 |
| **lock** | 谁在**争锁** | `-e lock` | `sy` 高、线程大量 `BLOCKED` |

**最关键的一条**：**"接口慢但 CPU 不高"，必须看 wall-clock（off-CPU）火焰图。**

因为 on-CPU 图只统计线程**在 CPU 上运行**的时间——一个 90% 时间在等数据库的线程，在 on-CPU 图里几乎不出现。**只看 on-CPU 图，你会得出"没有热点"的错误结论，然后往错误的方向优化。**

| 现象 | 看哪类 | 图上会看到 |
|---|---|---|
| CPU 高 | on-CPU | 宽块集中在自己的计算代码里 |
| 接口慢、CPU 低 | **wall / off-CPU** | 宽块在 socket read、锁等待、sleep |
| GC 频繁 | **alloc** | 宽块指向分配点（谁 `new` 得最多） |
| `sy` 高、大量 `BLOCKED` | **lock** | 宽块在锁的获取点 |

> **和 `jstack` 三次采样法的分工**：`jstack` 是"某个瞬间的横截面"，只能看**卡住**的线程；火焰图是"一段时间的聚合"，能看**占比分布**。**卡死类问题用 `jstack`，分布类问题（谁占得多）用火焰图。**

## 五、async-profiler 实操 {#asprof}

```bash
# on-CPU（默认），采 30 秒
./asprof -d 30 -f cpu.html <pid>

# off-CPU / 墙钟：看线程在等什么
./asprof -e wall -d 30 -f wall.html <pid>

# 内存分配：找 GC 压力的源头
./asprof -e alloc -d 30 -f alloc.html <pid>

# 锁竞争
./asprof -e lock -d 30 -f lock.html <pid>

# 包含所有线程（含空闲线程）
./asprof -e wall --all-threads -d 30 -f all.html <pid>
```

**它优于 `perf + FlameGraph` 的四个点**：

| 对比项 | async-profiler | perf + FlameGraph |
|---|---|---|
| 能否看到 Java 栈 | **能（`AsyncGetCallTrace`）** | 需额外符号 / 帧指针配置 |
| 安全点偏差 | **机制上缓解（非安全点采集）** | 存在 |
| 依赖 | **不依赖内核符号与 perf 权限** | 依赖 `perf_event` 权限 |
| 事件类型 | **cpu / alloc / lock / wall 都支持** | 主要 on-CPU |

**产物**：HTML（可折叠交互查看）+ collapsed 文本（可再喂给 FlameGraph 工具生成 SVG）。**排查时优先看 HTML，交付留档时用 collapsed 文本 + 截图。**

> 容器里运行时若受 `perf_event` 权限限制会给出提示，需要时调整宿主机的内核参数；**但要记住"调内核参数"本身是有安全含义的动作**，生产上要走变更流程。

## 六、JFR：低开销的长期采集 {#jfr}

```bash
# 采 60 秒并存文件
jcmd <pid> JFR.start duration=60s filename=/tmp/rec.jfr settings=profile

# 或者长时间挂着，出事再取
jcmd <pid> JFR.start name=slow
jcmd <pid> JFR.dump  name=slow filename=/tmp/rec.jfr
jcmd <pid> JFR.stop  name=slow
```

产物用 **JDK Mission Control（JMC）** 打开。

| 维度 | JFR | async-profiler |
|---|---|---|
| 开销 | **极低（默认配置 1% 量级）** | 低（1% 量级） |
| 是否自带 | **JDK 自带**，无需引入 | 需下载使用 |
| 长时间挂载 | **适合**（可长期开着，事后取证） | 一般按需短时采集 |
| 数据维度 | **最全**：方法采样、分配、GC、锁、IO、异常、线程事件 | 以火焰图为主 |
| 火焰图交互 | 有，但不如 async-profiler 顺手 | **强项** |

**选型建议**：**平时用 JFR 低成本挂着采证据（维度全、随时可取），需要精细的火焰图归因时切 async-profiler。**

## 七、四条采集纪律与压测结合 {#discipline}

| # | 纪律 | 原因 |
|---|---|---|
| 1 | **采样时间足够（≥30 秒）** | 样本太少时统计不稳定，火焰图形状会失真 |
| 2 | **采样期间不部署、不重启** | 启动期的代码会混进样本并占据宽度，干扰判断 |
| 3 | **采完立即取出文件** | 容器随时可能被重建，文件随之消失 |
| 4 | **不在故障高负载时临时加压采集** | 采样器本身有开销，此时叠加可能把服务压垮 |

**与压测结合，才算闭环**：

```text
压测施压 ──→ QPS / RT 曲线（知道"慢"）
                │
                └─ 同期采火焰图 ──→ 耗时落在哪个方法（知道"为什么慢"）
                                        │
                                        └─ 改完 ──→ 同压力复测（验证）
```

**只看压测报告，只能知道"上不去"；只有把"曲线"和"某个方法的宽度"对上，才知道该改哪一行代码。** 这种"压测数据 + 火焰图证据"的组合，也正是[架构师路线图](/projects/architect-roadmap/)里强调的"可验证产出"的一种形态——压测方案见[容量测算与压测方案](/projects/property-saas/capacity-and-perf/)。

## 八、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "火焰图怎么读？" | **横轴是样本占比不是时间轴**，宽度=该栈占比，纵轴=调用深度，颜色无含义；找自己代码里最宽的**平顶** | [六条规则](#rules) |
| 2 | "火焰图上很宽的方法，就是它慢吗？" | 它表示**总占比高**，可能是调用频次高而非单次慢；**改高频小方法往往收益更大** | [三种误读](#misread) |
| 3 | "接口慢但 CPU 不高，火焰图上看不到热点？" | 因为看的是 on-CPU 图，它只统计**在 CPU 上运行**的时间；要改看 **wall-clock（off-CPU）**图 | [四类剖析](#four-types) |
| 4 | "on-CPU 和 off-CPU 火焰图的区别？" | on-CPU 统计 CPU 时间（找计算热点）；off-CPU / wall 统计墙钟时间（找**等待**：IO、锁、sleep） | [四类剖析](#four-types) |
| 5 | "什么是安全点偏差？" | JVM 只在安全点才能记录栈，导致部分方法被系统性高估/低估；async-profiler 用 `AsyncGetCallTrace` 在非安全点采集，机制上缓解 | [安全点偏差](#safepoint) |
| 6 | "perf 为什么看不到 Java 栈？" | JIT 代码没有符号表、且默认不保留帧指针；要 `-XX:+PreserveFramePointer` 或 perf-map-agent——**Java 场景直接用 async-profiler 更省事** | [perf 的盲区](#perf) |
| 7 | "采样和插桩有什么区别？" | 采样按固定频率中断记录栈（低开销、统计推断）；插桩在每个方法埋点（精确但开销大）——**生产首选采样** | [三种手段](#three-ways) |
| 8 | "GC 频繁怎么找到分配源头？" | 做 **alloc 采样**（`-e alloc`），火焰图直接显示哪条调用路径分配了最多对象 | [四类剖析](#four-types) |
| 9 | "锁竞争怎么定位？" | `-e lock` 采样看锁获取点的宽度；或配合 Arthas `thread -b` 找阻塞者（见 [Arthas 在线诊断](/java/jvm/online-diagnostics#cmd-thread)） | [四类剖析](#four-types) |
| 10 | "为什么火焰图上有的方法消失了？" | JIT **内联**把小方法合并进调用者，栈里不再单独出现那一帧——**看不到不等于没执行** | [三种误读](#misread) |
| 11 | "生产上怎么低成本长期采证据？" | 用 **JFR**：JDK 自带、默认开销约 1%、维度最全（方法/分配/GC/锁/IO）；需要精细火焰图时再用 async-profiler | [JFR](#jfr) |
| 12 | "怎么把性能调优做成闭环？" | **压测的同时采火焰图**：曲线告诉你"慢"，火焰图告诉你"慢在哪一行"；改完同压力复测验证 | [采集纪律](#discipline) |
| 13 | "采样时要注意什么？" | 时间够长（≥30s）、中途不重启、采完立刻取文件、**不要在故障高负载时临时加采** | [采集纪律](#discipline) |
