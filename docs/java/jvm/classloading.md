# 类加载机制

## 一、类加载器：四种角色

类加载器的职责：**把 .class 字节码文件加载进 JVM，让程序能跑起来**。

| 加载器 | 实现语言 | 加载范围 |
|---|---|---|
| 启动类加载器（Bootstrap） | C++（JVM 内建，Java 侧拿到的是 null） | `JAVA_HOME/jre/lib` 核心库（rt.jar 等） |
| 扩展类加载器（Ext） | Java | `JAVA_HOME/jre/lib/ext` |
| 应用类加载器（App） | Java | `classpath`，即开发者编写的类与依赖 |
| 自定义类加载器 | Java（继承 `ClassLoader`） | 自定义规则：加密字节码、热部署、插件隔离 |

**版本注意**：JDK 9 起模块化后，Ext 被 **Platform ClassLoader** 取代（加载平台模块），三层结构变为「Bootstrap → Platform → App」。回答时带上版本差异是加分项。

## 二、双亲委派模型

**规则**：一个类加载器收到加载请求时，先把请求委派给父加载器；父加载器还有父就继续向上，直到 Bootstrap。**只有父加载器无法完成时，子加载器才尝试自己加载。**

```
自定义加载器 → App（应用类加载器） → Ext/Platform → Bootstrap
                  ↑ 上图是「委派上升」方向，加载归属判定则自上而下：
                  Bootstrap 能加载就归它，否则逐级下放
```

实现上就在 `ClassLoader#loadClass`：先 `findLoadedClass` 查已加载，再 `parent.loadClass`，父返回 null 才调 `findClass`。

### 为什么要这么设计

两个原因，缺一不可：

1. **避免重复加载**：父加载器加载过的类，子加载器不再重复加载，保证同一个类在 JVM 中唯一（类的唯一性 = 类加载器 + 全限定名）。
2. **安全**：防止核心 API 被替换。若有人自己写了个 `java.lang.String`，按双亲委派会先委托到 Bootstrap，加载的是 JDK 核心库里的 String，伪造类不会被加载。

### 打破双亲委派：三个真实场景

面试追问「什么时候需要打破」才是分水岭——委派不是教条，三类场景必须打破：

| 场景 | 做法 | 原因 |
|---|---|---|
| **SPI**（JDBC、SLF4J 等） | 线程上下文类加载器（`Thread.currentThread().getContextClassLoader()`），父加载器「反向」借用子加载器 | 接口在核心库（Bootstrap 加载），实现类在应用 classpath（App 加载），父看不到子 |
| **Tomcat 等 Web 容器** | 每个 Web 应用一个 WebAppClassLoader，**先自己加载**（加载不到才委派） | 应用间类库隔离；且 Web 应用类优先于容器共享库，实现应用升级不牵连容器 |
| **热部署 / OSGi / 插件化** | 换一个新加载器重新加载类 | 同一个类被两个加载器加载就是两个不同的类，借此实现「卸载重载」 |

## 三、类装载的七个阶段

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
       └────── 连接（Linking）──────┘
```

| 阶段 | 做什么 | 高频考点 |
|---|---|---|
| 加载 | 通过全限定名获取二进制字节流，生成方法区数据结构，堆中创建 `Class` 对象 | 字节流来源可自定义（网络、加密文件）→ 自定义加载器的钩子 |
| 验证 | 文件格式、元数据、字节码、符号引用四层校验 | 保证字节码不会危害 JVM |
| 准备 | 为 **static 变量**分配内存并赋**类型零值**（int=0、引用=null） | `final` 修饰的基本类型/字符串常量在此阶段直接赋真值 |
| 解析 | 常量池中的符号引用 → 直接引用（方法名 → 内存地址） | 可在初始化后再发生（动态绑定/Lambda） |
| 初始化 | 执行 **static 变量赋值 + static 代码块**，按代码顺序；**父类先于子类** | 主动引用才触发初始化（`new`/访问静态字段/反射等）；`Class.forName` vs `ClassLoader.loadClass` 的差异点 |
| 使用 | 从入口方法执行用户代码 | — |
| 卸载 | 类的 `Class` 对象被回收（需加载器可回收等条件） | 热部署场景关心 |

### 两个易混点

**准备阶段赋零值，初始化阶段赋真值**——这是最常被追问的细节：

```java
public static int VALUE = 1234;          // 准备阶段 VALUE=0，初始化阶段才 =1234
public static final int CONST = 1234;    // 准备阶段直接 =1234（常量，无零值过程）
```

**初始化时机**：只有「主动引用」才触发初始化——`new` 实例化、访问静态字段/方法（非常量）、反射、初始化子类先初始化父类、作为启动类。而「被动引用」（访问 `final` 常量、通过子类访问父类静态字段、定义数组）不触发。

## 四、面试口径

> 「类加载器把 .class 加载进 JVM，分为启动、扩展（JDK9 后为平台）、应用三类，还能自定义。双亲委派是指收到加载请求先向上委派，父加载器加载不了才自己加载——好处是避免重复加载保证类的唯一性，同时防止核心 API 被篡改，比如自定义 java.lang.String 不会被加载。装载过程分七个阶段：加载、验证、准备、解析、初始化、使用、卸载，中间三个合称连接；准备阶段给 static 变量赋零值，初始化阶段才执行赋真值和静态代码块。委派机制也不是铁律，SPI 用线程上下文加载器、Tomcat 做应用隔离、热部署换加载器，都是有意打破它的场景。」
