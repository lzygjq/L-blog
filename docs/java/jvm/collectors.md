# 垃圾收集器

## 一、演进主线：一条「停顿时间」的收敛曲线

```
Serial / Serial Old  →  ParNew / Parallel  →  CMS  →  G1  →  ZGC
   单线程            →   多线程吞吐优先    → 低停顿 → 分区可预测 → 亚毫秒
```

**主线逻辑**：堆越来越大、业务对停顿越来越敏感，收集器演进的方向就是**把 STW 时间从「与堆大小成正比」压到「与堆大小无关」**。理解这条线，各个收集器的差异就不用死记。

## 二、各收集器速览与配对关系

| 收集器 | 作用区 | 线程 | 算法 | 特点 |
|---|---|---|---|---|
| Serial | 新生代 | 单线程 | 复制 | 简单高效，适合单核/小内存客户端模式 |
| ParNew | 新生代 | 多线程 | 复制 | Serial 的多线程版，常见的 CMS 搭档 |
| Parallel Scavenge | 新生代 | 多线程 | 复制 | **吞吐量优先**，可精确控制最大停顿与吞吐（自适应调节） |
| Serial Old | 老年代 | 单线程 | 标记-整理 | Serial 的老年代版，也是 CMS 失败时的兜底 |
| Parallel Old | 老年代 | 多线程 | 标记-整理 | 与 Parallel Scavenge 配对，JDK8 默认组合 |
| **CMS** | 老年代 | 并发 | 标记-清除 | **低停顿**先驱，四个阶段（初始标记/并发标记/重新标记/并发清除） |
| **G1** | 整堆 | 并发 | 复制 + 标记 | **JDK9+ 默认**，分区回收、可预测停顿 |
| **Shenandoah** | 整堆 | 并发 | 转发指针 + 读屏障 | 低停顿（毫秒级）且与堆大小解耦；JDK12 引入，**JDK25 起分代模式转正**（JEP 521） |
| **ZGC** | 整堆 | 并发 | 染色指针 + 读屏障 | 亚毫秒级停顿，与堆大小几乎无关；**JDK23 起默认为分代模式，JDK24 起非分代模式被移除** |

**配对规则**：新生代与老年代收集器要成对使用（如 ParNew + CMS、Parallel Scavenge + Parallel Old）；G1 / ZGC / Shenandoah 都是整堆收集器，不需要配对。

### 时间线：面试里最容易答错的「版本现状」

问到收集器时，「某某现在什么状态」比「某某的原理」更容易露馅，因为很多资料停留在 JDK 8 的语境：

| 版本 | 事件 |
|---|---|
| JDK 8 | 默认 Parallel Scavenge + Parallel Old，CMS 仍可用 |
| JDK 9 | **G1 成为默认**；CMS 被标记废弃 |
| JDK 11 | **ZGC 实验性引入**（JEP 333）；Epsilon 无操作收集器加入 |
| JDK 12 | **Shenandoah 引入**（JEP 189，Red Hat 主导） |
| JDK 14 | **CMS 被移除**（JEP 363） |
| JDK 15 | **ZGC 与 Shenandoah 同期转正**（JEP 377 / JEP 379）；**偏向锁默认禁用**（JEP 374） |
| JDK 21 | **分代 ZGC 引入**（JEP 439） |
| JDK 23 | **ZGC 默认切换为分代模式**（JEP 474） |
| JDK 24 | **非分代 ZGC 被移除**（JEP 490，`-XX:ZGenerational` 变为 obsolete 选项） |
| JDK 25 | **Shenandoah 分代模式转正**（JEP 521）；**紧凑对象头转正**（JEP 519，需显式 `-XX:+UseCompactObjectHeaders`） |
| JDK 27 | **紧凑对象头成为默认**（JEP 534，已交付） |

两个必须纠正的过时说法：

- **「CMS 现在还有人用」** → CMS 已在 **JDK 14 移除**，能用到的最新版本是 JDK 13；说「老系统还在跑 CMS」时最好补一句「那些系统都停在 JDK 8/11」。
- **「ZGC 是非分代的」** → **JDK 23 起 ZGC 默认分代，JDK 24 起非分代模式已被移除**，`-XX:+ZGenerational` 这个参数也不需要了（甚至会被警告为废弃选项）。

**紧凑对象头（Compact Object Headers）值得单独记一笔**：它把 64 位 JVM 上对象的对象头从 96 位压到 64 位（约 12 字节 → 8 字节），JDK 24 以实验特性引入（JEP 450）、JDK 25 转正（JEP 519）、JDK 27 成为默认（JEP 534）。官方基准里 SPECjbb2015 的堆占用下降约 22%、GC 次数减少约 15%。**它直接影响 GC 的标记阶段开销**——对象头更小，每次标记要碰的元数据更少。启用前注意两条约束：堆需小于 32GB（依赖压缩类指针），且 JDK 25 时它与 ZGC 不兼容。

## 三、CMS：低停顿先驱与它的三个毛病

四个阶段：

```
初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除
   只标 GC Roots   与用户线程并发   修正并发期间变动   与用户线程并发
```

两个 STW 阶段都极短，并发阶段不阻塞——这就是它「低停顿」的来源。

**三个代价**（面试常问）：

1. **标记-清除算法带来内存碎片**，碎片严重时大对象分配失败 → 触发 Full GC（Serial Old 兜底）→ 停顿反而更长；
2. **并发阶段的浮动垃圾**：并发清理时用户线程仍在产生垃圾，只能留到下次，所以要预留空间（`-XX:CMSInitiatingOccupancyFraction`，默认约 68%）提前触发；
3. **并发模式失败（Concurrent Mode Failure）**：回收速度赶不上分配速度，退化为串行 Full GC，雪崩级停顿。

CMS 在 JDK9 被标记废弃、JDK14 移除——了解它的失败模式，比记住它的参数更值钱。

## 四、G1：分区 + 可预测停顿（JDK9+ 默认） {#g1}

### 核心设计：Region

堆不再物理分代，而是切成**大小相等的一堆 Region**（1~32MB，约 2048 个），每个 Region 动态扮演角色：

```
[E][E][S][O][O][E][H][O][S]...
 E = Eden   S = Survivor   O = Old   H = Humongous（大对象专用，连续 Region）
```

**逻辑分代，物理分区**——这是 G1 与前面所有收集器的根本差别。

### 三个阶段

1. **新生代回收（Young GC）**：Eden 满触发，STW，复制存活对象到 Survivor，够老的晋升 Old；
2. **并发标记（Concurrent Marking）**：老年代占用超过阈值（`-XX:InitiatingHeapOccupancyPercent`，默认 45%）触发，与用户线程并发，**不 STW**；标记后有短暂的重新标记（STW）解决漏标（SATB 快照写屏障）；
3. **混合回收（Mixed GC）**：回收 Eden + Survivor + **部分 Old**，按「回收价值（存活对象少 = 性价比高）」排序挑选 Region——**Garbage First 名字的由来**。

**停顿可预测**：`-XX:MaxGCPauseMillis`（默认 200ms）是软目标，G1 用「停顿预测模型」决定本次回收哪些 Region：预测停得住就多收几个，收不下就少收。

**Full GC 触发**：并发标记失败（回收赶不上分配）时退化为 Full GC。

### G1 vs CMS 对比

| 维度 | CMS | G1 |
|---|---|---|
| 堆划分 | 物理分代 | Region 分区（逻辑分代） |
| 算法 | 标记-清除（有碎片） | 复制 + 标记（Region 间复制，无碎片） |
| 停顿控制 | 不可预测 | 可设目标（MaxGCPauseMillis） |
| 大堆表现 | 堆越大越吃力 | 设计面向大堆（6GB+ 更明显） |
| 状态 | JDK14 已移除 | JDK9+ 默认 |

## 五、ZGC 与 Shenandoah：两条低延迟路线 {#zgc-shenandoah}

G1 已经能做到「可预测停顿」，但它的瓶颈在于：**对象移动（整理）必须 STW**——因为一旦移动了对象，所有指向它的引用都得改，而应用线程此刻正在读这些引用。要突破这一点，就必须让「移动对象」和「应用线程读对象」能**并发**进行。ZGC 和 Shenandoah 分别用两种办法解决了这个问题。

### 5.1 ZGC 的两大机制

**① 染色指针（Colored Pointers）**：把对象的状态信息**编码进引用指针本身**，而不是存在对象头里。

```text
64 位指针（简化示意）
┌────┬────────────┬──────────────────────────┐
│保留位│ 标记/重映射位 │      对象地址             │
└────┴────────────┴──────────────────────────┘
     ↑ 这里存的是「这个对象被标记了吗、地址是不是最新的」
```

这样做的好处：**标记阶段不需要修改对象本身**，只需要处理指针；对象被移动后，指针里的「重映射」位就能告诉后来的读者「你手上这个地址过期了」。代价是 ZGC 只能在 64 位平台上跑（要用掉几个高位）。

**② 读屏障（Load Barrier）**：在**读取对象引用**这个动作上插入一小段检查代码——如果指针处于「需要修正」状态，就顺手把它修正成新地址。

这两者结合的结果是：**对象移动、引用修正、应用线程读对象，可以同时进行**。于是 ZGC 的 STW 阶段只剩极短的初始标记，**停顿时间与堆大小基本无关**——堆从 8GB 涨到 8TB，停顿仍在亚毫秒到几毫秒量级。

### 5.2 分代 ZGC 补上了什么

非分代 ZGC 有个隐藏成本：**没有「大部分对象朝生夕死」这个假设可用**，每次回收都得面对整个堆，吞吐量上明显吃亏。

**分代 ZGC（JDK 21 引入、JDK 23 起为默认）**把对象分成新生代与老年代，绝大多数回收只需要处理年轻代那部分区域。这是从 JDK 21 到 23 吞吐改善的主要来源，也是「ZGC 只适合跑低延迟、吞吐很差」这个旧印象需要更新的原因。

### 5.3 ZGC 与 Shenandoah 的差别

两者都是「并发整理」路线，差别在实现手段：

| | ZGC | Shenandoah |
|---|---|---|
| 关键机制 | 染色指针 + 读屏障 | **转发指针**（Brooks Pointer）+ 读屏障 |
| 停顿量级 | 亚毫秒（常 < 1ms） | 毫秒级（通常 < 10ms） |
| 堆的侵入性 | 不改对象，状态放在指针里 | 每个对象多一个转发指针（少量空间开销） |
| 与堆大小的关系 | 几乎无关 | 基本解耦 |
| 主要维护方 | Oracle | Red Hat |
| 现状 | **JDK 23 起默认分代，JDK 24 起只有分代模式** | JDK 12 引入、JDK 15 转正；**JDK 25 起分代模式转正**（JEP 521，用 `-XX:ShenandoahGCMode=generational` 启用） |

**选哪个**：需要极致停顿（超大堆、TB 级）选 ZGC；中等堆、既想要低延迟又在意吞吐，可以压测对比 Shenandoah 分代模式。**两者都是「用吞吐换停顿」**——并发标记与并发移动要消耗额外的 CPU，这是它们与 Parallel / G1 的本质权衡。

### 5.4 上 ZGC 之前要先回答的三个问题

低延迟收集器不是免费的升级，切换前先过这三个问题：

1. **真的是「停顿」问题吗？** 如果瓶颈是 CPU 打满或内存带宽，换 ZGC 不会变快，甚至更慢（ZGC 更吃 CPU）。
2. **堆有多大？** 中小堆上 G1 通常已经够好；ZGC 的优势在大堆和极致延迟要求下才明显。
3. **能接受吞吐下降几个百分点吗？** 并发开销换来的就是停顿——这是取舍，不是增强。

## 六、选型建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 小内存、单核、客户端 | Serial | 无线程切换开销 |
| 批处理、吞吐优先（大数据任务） | Parallel Scavenge + Parallel Old | 吞吐量最大化 |
| **大多数服务端应用（默认起点）** | **G1** | JDK 9+ 默认，停顿可控、生态成熟、参数资料最多 |
| 中等堆、低延迟且在意吞吐 | Shenandoah 分代模式 | 停顿毫秒级，堆侵入性小 |
| 超大堆（数十 GB 以上）、极致低延迟 | ZGC | 停顿与堆大小基本解耦，且已默认分代 |
| 对象数量极多、想顺带省内存 | 任意收集器 + `-XX:+UseCompactObjectHeaders` | 对象头 12B → 8B，官方基准堆占用降约 22%（堆需 < 32GB） |
| 老系统还在用 CMS | 尽快迁移到 G1 | **CMS 已在 JDK 14 移除**，G1 是官方演进方向 |

**工程提醒**：切换 G1 不等于自动变快——G1 需要合理的 `MaxGCPauseMillis` 和堆大小配合，盲目迁移动辄引发 Full GC；上线前必须在压测环境用 `-Xlog:gc*`（JDK9+）观察 GC 日志确认。

## 七、面试口径

> 「收集器演进主线是把 STW 从跟堆大小成正比压到无关：Serial 单线程 → ParNew / Parallel 吞吐优先（JDK8 默认）→ CMS 是低停顿先驱，四阶段两短 STW，但标记-清除有碎片、有浮动垃圾、可能并发模式失败，**已在 JDK14 移除** → G1 用 Region 逻辑分代、复制算法无碎片，靠停顿预测模型按回收价值挑 Region，所以叫 Garbage First，JDK9 起默认 → ZGC 和 Shenandoah 用**读屏障**让『移动对象』与『应用线程读对象』并发执行，停顿与堆大小解耦，ZGC 亚毫秒、Shenandoah 毫秒级。选型：吞吐优先用 Parallel，绝大多数服务端用 G1，超大堆极致低延迟用 ZGC。版本要记清：CMS 在 JDK14 被移除；ZGC 从 JDK23 起默认分代、**JDK24 起已没有非分代模式**。」

补充几条容易被追问的原理与版本点：

- **ZGC 为什么停顿与堆大小无关**：染色指针把对象状态编码进**引用本身**，读屏障让「引用修正」在**读取时惰性完成**——于是移动对象不再需要 STW。两个机制缺一不可。
- **分代 ZGC 解决了什么**：非分代 ZGC 没有「大部分对象朝生夕死」的假设可用，每轮回收都要面对整个堆，吞吐吃亏。分代 ZGC（JDK21 引入、JDK23 默认）只处理年轻代，吞吐明显改善——这也是「ZGC 吞吐差」这个旧印象需要更新的原因。
- **ZGC 与 Shenandoah 的差别**：ZGC 用**染色指针**（状态在指针里，不改对象），Shenandoah 用**转发指针**（每个对象多一个指针）；都是读屏障 + 并发整理，停顿分别是亚毫秒 / 毫秒级。两者都是**用吞吐换停顿**。
- **版本红线（背下来能避坑）**：CMS → JDK14 移除；ZGC → JDK11 引入、JDK15 转正、JDK21 分代、JDK23 默认分代、JDK24 移除非分代；Shenandoah → JDK12 引入、JDK25 分代转正；紧凑对象头 → JDK24 实验、JDK25 转正、JDK27 默认。
