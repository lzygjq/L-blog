# 分片、路由与深分页：分布式多出来的三类代价

> 上一篇：[查询 DSL 与相关性算分](/search/query-and-scoring)　|　导览：[搜索与检索](/search/)

前 3 篇讲的是 Lucene 那一侧的事（词、段、算分）。从这一篇开始是**分布式的代价**——分片怎么切、数据怎么路由、翻到第 10000 条时会发生什么、集群怎么选主。这三类问题有一个共同点：**它们都是"为了扩展"而付出的额外复杂度，所以每一项都该问一句"这个规模真的需要吗"。**

## 一、分片到底是什么 {#concept}

先破除一个常见的模糊认知：

```text
一个 ES 索引（Index）
  ├── 主分片 P0（一个 Lucene 索引实例）
  ├── 主分片 P1（一个 Lucene 索引实例）
  └── 主分片 P2（一个 Lucene 索引实例）
       每片都各自持有完整的"倒排索引 + doc_values + translog"
       （文档不会同时出现在多个主分片里）
```

**关键理解：一个分片 = 一个完整的 Lucene 索引。** 分片不是"把一份索引切成人头"，而是**把数据按路由切开后，每片独立建索引**。这解释了所有分片相关的现象：

| 现象 | 原因 |
|---|---|
| 分片越多，单次查询越慢 | 查询要**发给所有分片**，协调节点归并，分片数 = 扇出数 |
| 分片越多，写入吞吐可能越高（直到某点） | 写入可并行打到不同分片/节点 |
| 聚合结果是近似的 | 各分片用本地数据算，协调节点合并（见[算分与聚合](/search/query-and-scoring#aggregation)） |
| 分片数不可改 | 路由依赖分片数 |

**分片大小的经验区间**：单个分片 **10GB ~ 50GB**。太小则分片数过多（扇出大、元数据开销大）；太大则单个 Lucene 索引过重（合并慢、恢复慢）。

> **分片不是越多越好**，这是 ES 官方反复强调的一条。分片的开销是**固定成本**：每片都有独立的段、translog、线程资源与集群状态。**一个 3 节点的集群配 1000 个分片，性能会比配 20 个分片差得多。** 常见建议是**每 GB 堆内存对应的分片数控制在 20 个以内**。

## 二、为什么主分片数不可改 {#why-primary-immutable}

这条规则不是"没实现"，而是**路由机制的直接推论**：

```text
写入时：shard = hash(_id) % number_of_primary_shards
查询时：同一个 _id 必须能找到同一个分片（否则读不到）
```

如果允许改主分片数：

```text
原来 3 个主分片：hash("order_123") % 3 = 1  → 数据在 P1
改成 4 个主分片：hash("order_123") % 4 = 3  → 去 P3 找 → 找不到
⟹ 全体文档的落点全部改变 ⟹ 等于全部数据必须重新分布
```

**所以"改主分片数"唯一安全的实现方式就是 reindex**——新建一个分片数正确的索引，把数据搬过去，再切别名。这也意味着 **mapping（字段类型）和分片数有一个共同性质：都是"建索引时就要定对"的一次性决策。**

**估分片数的三个输入**：

| 输入 | 怎么算 |
|---|---|
| 数据总量 | 当前数据量 × 未来 1~2 年的增长预期 |
| 单分片目标大小 | 取 30GB 附近的中间值 |
| 目标分片数 | `总量 ÷ 单分片目标大小`，**向上取整**（宁少勿多） |
| 节点数 | **分片数最好是节点数的整数倍**（避免节点间负载不均） |

> **一个务实的做法：用时间维度切索引。** 日志/流水类数据按天或按月建索引（`log-2026.09`），这样"分片数"这个概念被弱化了——**每个索引都不大，而"扩容"变成了"新索引多给几个分片"**，天然规避了不可改的问题。这也是 ILM（索引生命周期管理）的基础（见[运维与调优](/search/operations-and-log-stack#ilm)）。

## 三、路由：`_id` 与 `_routing` {#routing}

默认路由用 `_id`。但 ES 允许你**自定义路由键**：

```bash
# 写入时指定路由：同一用户的数据强制落同一分片
PUT /order/_doc/1001?routing=user_888
{ "user_id": "user_888", "amount": 99 }

# 查询时必须带同一个路由，否则会打到所有分片
GET /order/_search?routing=user_888
{ "query": { "term": { "user_id": "user_888" } } }
```

**自定义路由的收益与代价，必须成对理解：**

| 收益 | 代价 |
|---|---|
| **查询可以只打一个分片**（带 `routing` 时）—— 从"扇出 N 片"降到"只查 1 片"，性能提升巨大 | **必须记得在查询时也带 `routing`**，否则退回全分片；漏带是"结果正确但慢"的静默问题 |
| 同一路由键的数据物理聚集，利于**按用户维度的批量操作** | **数据倾斜**：大客户（一个 user_id 几百万订单）会把单个分片撑爆，其他分片空闲 |
| 聚合可以按路由预聚合 | 路由键的选择一旦定下，**改路由 = 全量 reindex** |

**判断要不要自定义路由的三步：**

```text
① 查询是否总是带某个"分区键"？（如 user_id / tenant_id / 商户号）
   ├─ 不是 → 不要自定义路由
   └─ 是 ↓
② 该键的分布是否均匀？（有没有"超级大客户"）
   ├─ 严重不均 → 不要用（会倾斜）；考虑改用"复合路由键"打散
   └─ 均匀 ↓
③ 收益是否值得"查询必须记得带 routing"的复杂度？
   └─ 值得 → 用
```

> **多租户 SaaS 场景的典型用法**：用 `tenant_id` 做路由，**让租户数据的物理分布与逻辑边界一致**——这既提升了查询性能，也让"按租户删除数据"这类需求变得简单（可整分片处置）。这一点与[多租户隔离的三种方案](/projects/property-saas/data-warehouse/)是同一个思路在不同层级的体现。

## 四、副本：读扩展与高可用，以及它的写入代价 {#replica}

| | 主分片（Primary） | 副本分片（Replica） |
|---|---|---|
| 数量 | **建索引时固定，不可改** | **随时可改**（`number_of_replicas`） |
| 承担写入 | ✅ | ✅（由主分片同步转发） |
| 承担查询 | ✅ | ✅（这是副本的主要价值） |
| 与主分片的节点关系 | — | **ES 强制副本不与主分片在同一节点**（否则失去意义） |

**三条容易搞混的性质：**

**① 副本数改起来很自由，但改动本身有成本**

```bash
PUT /product/_settings
{ "number_of_replicas": 2 }
```

把副本从 1 加到 2，ES 会启动**分片恢复**：从主分片复制一份完整数据到新节点。**这个过程消耗大量网络与磁盘 IO**，在高负载时执行可能引发连锁反应。**建议在低峰期做**。

**② 副本提升的是"读吞吐"和"可用性"，不是"写吞吐"**

写入要**同步复制到所有副本**，副本越多，单次写入的等待越久（尾延迟尤其明显）。**"加副本能不能提升写入"这个问题，答案是不能。**

**③ `wait_for_active_shards` 控制"写要等几个分片就绪"**

```bash
PUT /product/_doc/1?wait_for_active_shards=all
```

| 值 | 行为 | 场景 |
|---|---|---|
| `1`（默认） | 只要主分片在就写 | 高可用写入（可用性优先） |
| `quorum` / 数字 | 等指定数量的分片副本就绪 | 折中 |
| `all` | 所有副本就绪才写 | **一致性优先**（如金融场景），但可用性下降 |

**这是一条明确的 CAP 取舍**：`all` 更"不丢"但更容易写失败（任一副本节点故障就写不进去）。

## 五、深分页：`from + size` 为什么危险 {#deep-paging}

这是 ES 最经典的一个性能陷阱，也是面试高频。

**先看默认行为：**

```json
{ "from": 9990, "size": 10 }     // 想取第 1000 页
```

看起来只返回 10 条，**但每个分片都要返回"前 10000 条"给协调节点**：

```text
索引 5 个分片，请求 from=9990, size=10
  ① 协调节点把请求发给 5 个分片，每片要求返回 from+size = 10000 条
  ② 每个分片在本地排序，取出自己前 10000 条（含完整文档或至少 ID+排序值）
  ③ 协调节点收到 5 × 10000 = 50000 条，在内存里归并排序，取第 9991~10000 条
  ④ 丢弃其余 49990 条
⟹ 为了 10 条结果，传输并排序了 50000 条
```

**分片数越多、翻得越深，代价越大**——这是**乘法**关系：`分片数 × (from + size)`。

**ES 因此有一个硬保护**：

```bash
# 默认 from + size 不能超过 10000，否则：
Result window is too large, from + size must be less than or equal to: [10000]
# 可通过 index.max_result_window 调大，但调大是"把问题变大"，不是解决
```

### 三种替代方案，各有明确的适用边界

| 方案 | 机制 | 适合 | 不适合 |
|---|---|---|---|
| **`search_after`** | 用**上一页最后一条的排序值**作为"游标"往后取 | **无限下拉、深分页**（推荐首选） | 不能"跳页"（只能顺序往后） |
| **`scroll`** | 生成一个**快照上下文**，分批拉取 | **离线全量导出、大批量处理** | **不适合实时查询**：快照占资源、且看不到新写入的数据 |
| **`point_in_time`（PIT）** | `search_after` 的现代搭档：先开一个时间点快照，再在快照上反复 `search_after` | **深分页 + 结果一致性**（7.10+ 推荐的组合） | 仍需处理 PIT 的创建与释放 |

**① `search_after` 的正确用法**（必须有一个**全局唯一的排序键**）：

```json
// 第一页
{ "size": 10, "sort": [ { "created_at": "desc" }, { "_id": "desc" } ] }

// 下一页：把上一页最后一条的 sort 值原样传进来
{ "size": 10,
  "sort": [ { "created_at": "desc" }, { "_id": "desc" } ],
  "search_after": [ 1758000000000, "doc_888" ] }
```

**两个关键点：**

- **排序键必须唯一**（所以 `_id` 做 tiebreaker），否则"排序值相同的文档"会被跳过或重复。
- **它不能跳页**。所以它适合"下拉加载更多"，**不适合"跳到第 500 页"**。

**② `scroll` 的适用边界必须说清**

```json
POST /product/_search?scroll=5m
{ "size": 1000, "query": { "match_all": {} } }
```

`scroll` 会**创建一个快照并保持一段时间**（`scroll=5m`），期间：
- **数据是冻结的**——索引在 scroll 期间的新写入**不会出现在结果里**；
- **快照占用资源**（段引用不释放、堆内存），并发 scroll 多了会打爆集群；
- 所以它**只适合"导出全量数据"这类一次性任务**，**不适合"用户在翻页"**。

> **一句话选型**：**用户在翻页 → `search_after`（或 PIT + `search_after`）；跑批导出 → `scroll`；要跳页 → 重新设计产品（跳页本身在搜索引擎里就不该支持）。**

**③ 深分页的产品层面解法（往往最有效）**

搜索引擎的"第 1000 页"几乎从无真实用户访问。**所以最终的架构手段是产品层的**：

| 手段 | 做法 |
|---|---|
| **限制可翻页深度** | 只允许翻到前 N 页，之后引导用户"加筛选条件" |
| **筛选替代翻页** | 用分类、时间、价格区间把结果集**收窄到能翻完**的规模 |
| **换引擎** | 一次性导出/大批量扫描交给列式数仓——这也是[Doris 的位置](/bigdata/doris/) |

MySQL 侧的深分页（`limit 100000, 10`）是同一类问题，两边可以对照看（见[分库分表 · 跨节点分页](/database/sharding/)）。

## 六、集群的节点角色与选主 {#nodes}

ES 7.x 之后不再有"节点类型"配置的硬绑定，而是通过**角色（role）**组合：

| 角色 | 职责 | 什么时候需要单独部署 |
|---|---|---|
| **`master`** | 管理集群状态（建索引、改 mapping、分片分配），**不处理文档** | **至少 3 个专用 master**（生产必做）——只有 1 个或 2 个专用 master 都无法形成多数派，反而更脆 |
| **`data`** | 存数据、执行查询与写入 | 数据量大的核心角色，可细分为 `data_hot/warm/cold` 做冷热分层 |
| **`ingest`** | 在写入前做预处理（pipeline：改字段、解析日志） | 写入预处理逻辑重时单独部署，避免抢占 data 节点资源 |
| **`coordinating`**（隐式） | 只做请求分发与结果归并，不存数据、不做主节点 | 高并发查询场景可单独部署，避免归并开销拖累数据节点 |
| **`ml`** | 机器学习任务 | 按需 |

**为什么专用 master 要 3 个（奇数）？** 与[分布式共识](/distributed/consensus#quorum)是同一个道理：选主需要多数派。**3 个专用 master 的前提是它们不承担数据角色**——否则数据压力会让它们响应变慢，触发"master 被踢出集群"的连锁问题。这是 ES 生产事故里非常经典的一类。

## 七、脑裂：成因与防护 {#split-brain}

脑裂（Split Brain）指**集群出现两个各自认为自己是主的子集**，后果是数据写入冲突。ES 7.0 之前这是重灾区，7.0 之后从机制上大幅收紧了。

| 成因 | 说明 |
|---|---|
| **`minimum_master_nodes` 配置不当**（旧版本） | 这是 ES 5/6 时代脑裂的主因：如果 `discovery.zen.minimum_master_nodes` 设成 1（默认），网络分区时两边都能选主 |
| **master 节点混跑数据角色** | 负载导致心跳超时，被误判定为下线 → 反复重选主 |
| **网络分区 / GC 长停顿** | 节点"暂时失联"，但进程还活着 |

**7.0+ 的防护机制（不需要再手工配 `minimum_master_nodes`）：**

```yaml
# 7.x / 8.x：用"投票配置"（voting configuration）自动管理
discovery.seed_hosts: ["host1", "host2", "host3"]   # 首次启动时的节点列表
cluster.initial_master_nodes: ["host1", "host2", "host3"]  # 只在首次集群启动时设置 ★
```

三条例必须遵守的纪律：

| 纪律 | 原因 |
|---|---|
| **`cluster.initial_master_nodes` 只在"全新集群首次启动"时配置** | 它会在**每次重启时都尝试重新选主**。已有数据的集群重启时保留它，可能导致脑裂式的数据丢失（节点会组成新集群、忽略旧数据） |
| **专用 master 至少 3 个（奇数）** | 多数派容错：3 个可容忍 1 个故障 |
| **`discovery.seed_hosts` 用于"加入已有集群"** | 与 `initial_master_nodes` 的用途完全不同，别混用 |

> **一个诊断信号**：`GET /_cluster/health` 返回 `status: yellow/red` 时先分清是**分片未分配**还是**主节点选举有问题**。`_cat/master` 看当前主节点、`_cluster/state` 看元数据版本号，**如果同一个集群出现两个不同的 master 视图，就是脑裂**。

## 八、扩容：reindex 与别名切换 {#scale}

当分片数或 mapping 需要改变时，标准流程是"**新建 + 迁移 + 切别名**"，而且要做到**对业务零停机**：

```text
① 建新索引（分片数/mapping 正确）
      PUT /product_v2

② 迁移数据
      POST /_reindex?wait_for_completion=false      # 后台异步跑
      { "source": { "index": "product_v1" },
        "dest":   { "index": "product_v2" } }

③ 增量同步（迁移期间的新写入不能丢）
      · 业务双写 v1 + v2，或
      · 迁移完成前把增量写入回放一遍（按时间戳/版本号）
      ★ 用外部版本号（version_type=external）让"旧数据自动被拒"，
        这一步就天然幂等且防乱序（见写入链路的并发控制）

④ 切别名（原子操作）
      POST /_aliases
      { "actions": [
          { "remove": { "index": "product_v1", "alias": "product" } },
          { "add":    { "index": "product_v2", "alias": "product" } }
      ]}

⑤ 观察一段时间后再删 v1
```

**四个必须知道的要点：**

| 要点 | 说明 |
|---|---|
| **业务代码永远只访问别名** | **这是整个方案的前提**——代码里出现真实索引名，就无法零停机切换。从第一天起就用别名 |
| **`_reindex` 是异步的** | `wait_for_completion=false` 返回一个 `task_id`，用 `GET /_tasks/{id}` 查进度；同步等待容易超时 |
| **`_reindex` 不复制索引设置** | **分片数、mapping、analysis 都要在新索引上手工建好**（或先用 `_reindex` 的 `dest` 参数指一个已建好的索引） |
| **迁移期间必须处理增量** | 只做一次 reindex 会丢掉迁移窗口内的新写入——这是最常见的翻车点 |

```bash
# 从远端集群迁移也是同一个 API（跨集群 reindex）
POST /_reindex
{ "source": { "remote": { "host": "http://other:9200" }, "index": "product" },
  "dest":   { "index": "product_v2" } }
```

> **切别名是原子的**，所以那一刻不会出现"两个索引都不可用"的窗口。但**索引的写入必须在切换前对齐**——否则切完之后，落在 v1 的那几条数据就成了孤儿。**这一点与数据库灰度切换的"双写 + 校验 + 切换 + 回滚预案"是同一套思路。**

## 九、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "ES 的分片是什么？" | **一个分片就是一个完整的 Lucene 索引**；数据按路由被切开，每片独立建倒排与正排，不是"把一份索引切片" | [分片是什么](#concept) |
| 2 | "分片越多越好吗？" | 不是。分片是**固定成本**（段、translog、线程、集群状态），分片数 = 查询扇出数；建议单分片 10~50GB、**每 GB 堆不超过 20 个分片** | [分片是什么](#concept) |
| 3 | "为什么主分片数不可改？" | 路由是 `hash(_id) % 主分片数`，**分片数一变路由全变**，等于全量重分布；要改只能新建索引 + reindex | [主分片不可改](#why-primary-immutable) |
| 4 | "副本数能改吗？" | 能，随时可改；但改动会触发**分片恢复**（从主分片全量复制），高负载时执行有风险，建议低峰期 | [副本](#replica) |
| 5 | "副本能提升写入性能吗？" | **不能**。写入要同步复制到所有副本，副本越多写入尾延迟越高；副本提升的是**读吞吐与可用性** | [副本](#replica) |
| 6 | "`wait_for_active_shards` 是干什么的？" | 控制"至少几个分片副本就绪才写"：`1` 可用性优先、`all` 一致性优先（任一副本挂着就写不进去）——**典型的 CAP 取舍** | [副本](#replica) |
| 7 | "`_routing` 有什么用？代价是什么？" | 让同组数据落同一分片，**查询可只打一片**；代价是**查询必须记得带 routing**（漏带则静默变慢）+ **热点键会导致数据倾斜** | [路由](#routing) |
| 8 | "深分页为什么慢？" | `from + size` 时**每个分片都要返回 `from+size` 条**给协调节点归并，代价是 `分片数 × (from+size)`——为 10 条结果排序了 N 万条 | [深分页](#deep-paging) |
| 9 | "`max_result_window` 是什么？" | 默认 `from+size ≤ 10000` 的硬保护；**调大它是把问题变大，不是解决** | [深分页](#deep-paging) |
| 10 | "深分页怎么解决？" | 用户在翻页 → **`search_after`（配 PIT）**；跑批导出 → `scroll`；要跳页 → **改产品**（限制深度 / 用筛选收窄） | [深分页](#deep-paging) |
| 11 | "`search_after` 和 `scroll` 的区别？" | `search_after` 是**游标**（无快照、实时、不能跳页）；`scroll` 是**快照**（数据冻结、占资源、只能顺序拉）——**实时查询用前者，离线导出用后者** | [三种方案](#deep-paging) |
| 12 | "`search_after` 的排序要求是什么？" | 排序键必须**全局唯一**（常用业务时间 + `_id` 做 tiebreaker），否则会**跳过或重复**文档 | [三种方案](#deep-paging) |
| 13 | "集群有哪些节点角色？" | `master`（管状态）、`data`（存数据，可冷热分层）、`ingest`（写前预处理）、`coordinating`（只归并）、`ml` | [节点角色](#nodes) |
| 14 | "专用 master 为什么要 3 个？" | 选主需要**多数派**：3 个容忍 1 个故障，1 或 2 个反而更脆；且**必须专用**——混跑数据角色会导致负载超时被误判下线 | [节点角色](#nodes) |
| 15 | "脑裂是怎么产生的？" | 集群出现两个各自认为自己是主的子集（网络分区、心跳超时、master 混跑数据角色、GC 长停顿）；旧版本主因是 `minimum_master_nodes` 配置不当 | [脑裂](#split-brain) |
| 16 | "`cluster.initial_master_nodes` 要注意什么？" | **只在全新集群首次启动时配**；已有数据的集群重启时保留它，可能触发重新选主/组成新集群 → 数据丢失风险 | [脑裂](#split-brain) |
| 17 | "怎么改分片数或 mapping 而不停机？" | **建新索引 → `_reindex`（异步）→ 回放增量 → 原子切别名 → 观察后删旧索引**；前提是**业务只访问别名** | [扩容](#scale) |
| 18 | "`_reindex` 有什么坑？" | ① 是**异步任务**，要用 `_tasks` 查进度；② **不会复制索引设置与 mapping**，新索引要先建好；③ **迁移窗口内的增量会丢**，必须单独回放 | [扩容](#scale) |
