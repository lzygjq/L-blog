# 写入链路与近实时：为什么刚写完还搜不到

> 上一篇：[倒排索引与分词](/search/inverted-index)　|　导览：[搜索与检索](/search/)

这是 ES 最著名的一个"故障现象"：

```text
写入一条订单 → 立刻查询 → 查不到 → 骂 ES 有 bug
   （等 1 秒再查 → 查到了）
```

这不是 bug，是**设计**。而理解它的原因，需要先把"一次写入到底经过了哪些环节"这件事拆开——**拆开之后你会发现，ES 的写入模型里几乎每一个"奇怪"的行为，都是从"Lucene 的段不可变"这一条推出来的。**

## 一、一次写入的完整链路 {#write-path}

假定集群有 3 个节点，索引 3 个主分片、每分片 1 副本，客户端往节点 A 发了一条写请求：

```text
客户端
  │  ① 请求发到任意节点（它成为本次请求的 Coordinating Node 协调节点）
  ▼
┌─────────────────────────────────────┐
│ 协调节点 A                            │
│  ② 用 _id 算路由：shard = hash(_id) % 主分片数
│  ③ 找到该分片的主分片（Primary）在哪台机器
└──────────────┬──────────────────────┘
               │ ④ 转发到主分片所在节点（假设是 B）
               ▼
┌─────────────────────────────────────┐
│ 主分片 B                              │
│  ⑤ 写入前做校验（mapping 类型、dynamic=strict 等）
│  ⑥ 写入 Lucene：进内存缓冲 + 记 translog
└──────────────┬──────────────────────┘
               │ ⑦ 并行转发给所有副本分片（Replica）
               ▼
┌─────────────────────────────────────┐
│ 副本分片 C（与主分片在**不同节点**）    │
│  ⑧ 同样写内存缓冲 + translog           │
└──────────────┬──────────────────────┘
               │ ⑨ 副本确认成功
               ▼
        主分片 B 收到全部副本确认 → ⑩ 返回客户端成功
```

**这张图里有四个值得单独说的点：**

**① 主分片数决定了写请求的"路由"，而 `_id` 决定了"去哪个分片"**

`shard = hash(_id) % 主分片数`——**主分片数一变，所有文档的路由全部改变**。这就是主分片数不可改的根本原因（见[分片、路由与深分页](/search/sharding-and-scale#why-primary-immutable)）。

**② "写主分片再同步副本"是同步的，所以副本数会直接影响写入延迟**

`wait_for_active_shards` 控制"至少几个分片副本就绪才返回"，默认 `1`（只要主分片）。设成 `all` 最安全但最慢。**副本数从 1 加到 2 不会提升写入吞吐，只会提升读吞吐与可用性**——写要同步到所有副本。

**③ `_id` 不指定时，ES 会自动生成**

省略 `_id` 时，ES 生成一个随机 ID 并**跳过"检查 ID 是否存在"这一步**——所以**大量写入时省略 `_id` 比指定 `_id` 更快**（省掉一次读）。但如果你需要幂等覆盖（同一个 `_id` 重复写只留最新），就必须自己指定。**这是一个非常实用的取舍点**。

**④ 校验发生在写入前，所以 mapping 错误是"写入失败"而不是"写入后才发现"**

`dynamic: "strict"` 下写入未定义字段会**直接报错**——这是把问题暴露在最早时机的设计。

## 二、三个动作：refresh / flush / translog {#refresh-flush}

这三个词是 ES 里最容易混的一组，因为它们的名字都像"落盘"，但**落的盘完全不同**。先把一句话结论放出来：

> **`refresh` 管"能不能搜到"（进 Lucene 的 segment，可能还在文件系统缓存里）；`flush` 管"能不能扛断电"（把 Lucene 段真正 fsync 到磁盘，并清空 translog）；`translog` 管"进程崩溃时不丢数据"（每写一条就记，可配置是否 fsync）。**

```text
写入一条文档
      │
      ├──▶ ① 进 In-memory Buffer（内存缓冲）
      │        · 此时搜不到
      │        · 满了/定时器到 → refresh
      │
      └──▶ ② 追加到 translog（事务日志）
               · 每写一条就记，用于崩溃恢复
               · 默认每个请求 fsync 一次（index.translog.durability=request）
               · 累积到阈值（默认 512MB / 30min）→ flush
```

| 动作 | 触发 | 做了什么 | 影响 |
|---|---|---|---|
| **`refresh`** | 默认**每 1 秒**自动；或 `?refresh=true` | 把内存缓冲里的文档**生成一个新的 Lucene segment**，此时该段**可被搜索**（但可能在 OS page cache，未 fsync） | **决定"多久能搜到"**；代价是产生大量小段 |
| **`flush`** | translog 达阈值（512MB/30min）、手动、或正常关闭 | ① 把 Lucene 段 **fsync 到磁盘**；② **清空/滚动 translog**（生成新的 translog 代） | 决定"断电后能恢复到哪一步" |
| **`translog`** | 每条写入 | 追加一条记录 | **进程崩溃时用它重放**（注意：它保护的是"进程崩溃"，`flush` 才保护"机器断电"） |

**一张表看清三种"丢失场景"：**

| 场景 | 会丢吗 | 谁保护 |
|---|---|---|
| 刚写完 1 秒内搜不到 | 数据没丢，只是**搜不到** | `refresh` |
| ES 进程被 kill | 不丢 | `translog`（默认 `request` 级别：每个请求都 fsync translog） |
| 机器断电 / 磁盘损坏 | 取决于 translog 是否 fsync | `flush`（段 fsync）+ translog 的 `durability` 设置 |

> **`index.translog.durability` 是最关键的一个旋钮**：
> - `request`（**默认**）：每个写请求都 `fsync` translog。**不丢，但有 IO 开销**。
> - `async`：按 `sync_interval`（默认 5s）异步 fsync。**性能好，但最多丢 5 秒数据**——日志采集类场景常用。

### 手动 refresh 的代价，远超大多数人的预期

```bash
POST /product/_doc/1?refresh=true      # 单条立即刷新
POST /product/_refresh                 # 手动刷新整个索引
```

`refresh=true` 在**单条测试**里很顺手，但在**批量导入**里是性能杀手：每次 refresh 都会生成一个新的小段，几百条写入就产生几百个段，然后段合并会疯狂运行去收拾。

```text
逐条 refresh 写 10 万条 → 产生大量小段 → merge 风暴 → 写入吞吐崩掉、CPU 打满
批量写 10 万条（不 refresh）→ translog 保证不丢 → 写完后统一 refresh 一次
```

**正确做法**：批量导入时先 `refresh_interval: -1`（关闭自动刷新），灌完数据再手动 `_refresh` 一次并恢复设置。

## 三、"近实时"到底近到什么程度 {#near-realtime}

现在可以正式回答那个问题了：

```text
ES 默认 refresh_interval = 1s
⟹ 一条文档从"写入成功"到"能被搜索到"，最多有 1 秒的延迟
⟹ 这就是"近实时（Near Real-Time, NRT）"这个词的全部含义
```

**为什么不做成实时？** 因为"实时"意味着**每写一条就要生成/更新可搜索的段**，段的数量会爆炸，段合并的开销会把写入吞吐吃光。**1 秒是一个精心选出的平衡点**：用户侧几乎无感知，而写入可以攒够一批再统一建段。

**`refresh_interval` 是一条明确的取舍曲线：**

| 场景 | 设置 | 理由 |
|---|---|---|
| 商品搜索、内容搜索（人要立刻看到） | `1s`（默认） | 交互体验优先 |
| 日志检索（延迟 5 秒可接受） | `5s` ~ `30s` | 写入吞吐优先，日志量通常是搜索的几十倍 |
| 批量导入 / 重建索引 | `-1`（关闭） | 灌完再开 + 手动 refresh |
| 写入极高、查询很少（如埋点） | `30s` 甚至更长 | 进一步换吞吐 |

> **一个必须记住的实践结论**：**业务代码里"写完立刻查"的逻辑，不能依赖 ES 的实时性。** 典型错误是"写入 ES → 立刻查 ES 判断是否成功"。正确做法是**依赖写入的返回值**（`result: created/updated`），或者写入后强制 `?refresh=wait_for`（等待下一次 refresh 完成再返回，是"读己之写"最轻量的手段）。

### 三种 refresh 语义的区别

| 写法 | 行为 | 什么时候用 |
|---|---|---|
| `refresh=true` | **立即**触发一次 refresh（即使没到间隔） | 单条调试、测试用例 |
| `refresh=wait_for` | **等下一次** refresh 自然发生后再返回（不强制、不阻塞他人） | **需要"读己之写"的生产逻辑，推荐** |
| `refresh=false`（默认） | 不管，按间隔来 | 绝大多数写入 |

**`wait_for` 比 `true` 更好的原因**：`true` 是"我说了算，立刻刷"——如果有 100 个并发写都带 `true`，就是 100 次强制刷新；而 `wait_for` 是"排进下一次的队"，**多用户并发时不会互相加剧开销**。

## 四、段合并：不可变索引的必然代价 {#merge}

"段不可变"带来了一连串后果，最重的一个是：**每次 refresh 都会新增一个段，而搜索要查遍所有段。**

```text
写入 1000 条 → refresh → segment_1（1000 条）
再写 1000 条 → refresh → segment_1 + segment_2
…
写了 1 小时 → 可能积累几百个段
⟹ 查询一条数据要查几百个段 → 越来越慢
```

所以 Lucene 有一个**后台合并线程池**，把多个小段合并成一个大段：

| | 合并前 | 合并后 |
|---|---|---|
| 段数 | N 个小段 | 1 个大段 |
| 查询 | 要查 N 个段，再归并排序 | 只查 1 个 |
| 磁盘 | 重复数据多（同一文档的不同版本分散在多段） | 物理清理掉已删标记 |
| 代价 | — | **大量磁盘 IO 与 CPU**，且合并期间占用更多磁盘空间 |

**段合并是 ES 最容易被忽视的资源消耗方。** `_nodes/stats` 里的 `segments.merge_*` 指标、以及 `_cat/segments` 的段数量，都应该纳入监控。

三个可调参数：

| 参数 | 作用 | 调法 |
|---|---|---|
| `index.merge.policy.max_merged_segment` | 单个段的最大体积（默认 5GB） | 一般不动 |
| `index.merge.scheduler.max_thread_count` | 合并线程数 | **用普通机械盘时设为 1**（默认按 CPU 核数的一半算，机械盘并发太多反而更慢） |
| `indices.store.throttle.max_bytes_per_sec` | 合并限速 | 写入高峰期限速，避免合并抢走 IO |

> **一个重要认知**：**force merge 不是"调优手段"，而是"离线收尾动作"。**
> 它对只读索引有效（把几百个段合成 1 个，查询明显变快），但在**仍在写入的索引上执行 force merge 是有害的**——合并出的段很快又会被新写入的段打破，白白消耗巨量 IO。**典型用法：历史月份索引（只读）在归档前 force merge 一次。**

## 五、删除与更新：为什么它们也只是"写" {#delete-update}

这是"不可变"最反直觉的另一面：

| 操作 | 你以为是 | 实际是 |
|---|---|---|
| **删除** `_id=1` | 把它从索引里抠掉 | **只写一个"标记删除"的记录**（`.del` 文件），文档仍然占空间 |
| **更新** `_id=1` 的某字段 | 原地改一个字段 | **把旧版本文档标记删除 + 写入一条完整的新版本文档** |

**所以：**

**① 删掉的数据，磁盘空间不会立刻回收。** 只有当**段合并**发生时，被标记删除的文档才会被物理丢弃。想立刻看到空间回收，只能等合并或 force merge（且 force merge 本身又要占更多空间）。

**② "更新一个字段"的代价 ≈ 重写整条文档。** 对宽文档（几十个字段）频繁改一个字段，是典型的低效写入模式。

**③ 更新让文档"搬家"了，但路由不变。** 因为 `_id` 没变，`_routing` 就没变，所以还是落在同一个分片——**这是 `_id` 路由的稳定性带来的好处**。

**④ 段合并为什么能"顺便"解决删除**：合并时遍历旧段，跳过所有带删除标记的文档，只把活着的文档写进新段。**所以删除的成本被延后到合并时结算**——这也是"写得多、删得多"的索引磁盘占用异常高的原因。

### 版本号与并发控制 {#concurrency}

ES 是分布式的，两条并发更新同一条文档的请求可能同时到达。ES 的处理方式有两种：

**① 内部版本号（`_version`）——自动递增，用于乐观锁**

```bash
# 只有当文档版本还是 3 时才更新；否则返回 409 冲突
PUT /product/_doc/1?if_seq_no=5&if_primary_term=1
{
  "name": "新名字"
}
```

`if_seq_no`（序号）+ `if_primary_term`（主分片代数）替代了旧版的 `version` 参数——**两个值一起用是因为分片可能发生过主副本切换，单看序号无法判断"是不是同一任主分片上的序号"**。

**② 外部版本号（`version_type=external`）——把自己系统的版本带进来**

```bash
PUT /product/_doc/1?version=100&version_type=external
# 只有传入的版本 > 当前版本才写入；≤ 则报 409
```

这个模式在**用 MySQL 的 `update_time` 或 binlog 位点做同步**时特别有用——它让 ES 的写入具备"**幂等 + 防乱序**"的能力：**后到的旧数据会被自动拒绝**，不必依赖消息队列的严格顺序。这是 CDC 同步链路里非常关键的一环（见 [Canal 数据同步](/bigdata/canal/)）。

> **为什么是乐观锁而不是悲观锁？** 因为 ES 的使用场景是"高并发、低冲突概率"（搜索/日志），悲观锁（先锁再改）的代价远高于偶发重试。这与数据库在相同场景下的选择一致——**冲突概率低时，乐观锁的期望成本更低**。

## 六、写入性能：一份可执行的清单 {#write-tuning}

写入慢通常是四类原因，按"性价比"排序：

**① 批量（最有效，且几乎无代价）**

```bash
POST /_bulk
{"index":{"_index":"product","_id":"1"}}
{"name":"A"}
{"index":{"_index":"product","_id":"2"}}
{"name":"B"}
```

| 要点 | 说明 |
|---|---|
| **批次大小** | 单批 5~15MB 是常见甜点区；**不是越大越好**（过大导致协调节点内存压力、超时重试） |
| **避免单条同步写** | 循环单条写入是最常见的性能自杀方式 |
| **压测确定参数** | 用不同批次大小实测吞吐，而不是抄一个数字 |

**② 关掉不必需的刷新与副本（临时导入时）**

```bash
PUT /product/_settings
{ "index": { "refresh_interval": "-1", "number_of_replicas": 0 } }

# 导入完成后恢复（副本会从主分片恢复，此时才产生复制成本）
PUT /product/_settings
{ "index": { "refresh_interval": "1s", "number_of_replicas": 1 } }
```

**导入期把副本设为 0 是标准操作**——否则每批数据都要同步复制一份，写入成本翻倍，且恢复副本时可以按段复制，比逐条复制高效得多。

**③ 少让 ES 做不必要的工作**

| 做法 | 收益 |
|---|---|
| **省略 `_id`** 让 ES 自动生成 | 省掉一次"ID 是否存在"的读 |
| 用 `_routing` 自定义路由（谨慎） | 让同组数据落同一分片，但**可能造成数据倾斜** |
| 不需要的字段设 `"index": false` | 不建倒排，写入更快 |
| 不需要检索的正文存 `"enabled": false` | 只存不索引（当存储用） |
| 不需要位置信息（短语/高亮） | 调低 `index_options`，减小 posting list |

**④ 硬件与集群层**

- **磁盘**：**必须 SSD**。ES 对随机 IO 极敏感，机械盘上一切调优都是徒劳。
- **堆内存**：**不要超过 31GB**（约数，见[运维与调优](/search/operations-and-log-stack#memory)）——超过后失去指针压缩，反而更耗内存。
- **分片数**：主分片过多会让每次写入打到更多节点、加剧合并压力；**单分片 10~50GB 是常见建议区间**。

```text
写入慢的排查顺序：
① 是不是单条同步写？        → 改 bulk
② 是不是 refresh 太频繁？   → 提高 refresh_interval
③ 是不是 merge 在抢 IO？    → 看 _nodes/stats 的 merge 指标，必要时限速
④ 是不是 CPU/磁盘饱和？     → 看节点资源（线程池拒绝数 thread_pool.write.rejected 是关键指标）
```

> **`thread_pool.write.rejected` 是 ES 写入健康度最直接的信号**：队列满了会拒绝请求（`es_rejected_execution_exception`）。**看到它出现，说明写入速度已经超过了集群能吸收的速度**——继续加压只会雪崩，此时应该做的是降速或扩容，而不是重试。

## 七、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "一条文档写入 ES 经历了什么？" | 协调节点按 `hash(_id) % 主分片数` 路由 → 转主分片 → 写内存缓冲 + translog → **同步转发所有副本** → 全部确认后返回 | [写入链路](#write-path) |
| 2 | "为什么刚写完的数据搜不到？" | 写入先进内存缓冲，要经过 **refresh（默认 1s）** 才生成可搜索的 segment——这就是"**近实时**" | [近实时](#near-realtime) |
| 3 | "refresh 和 flush 有什么区别？" | `refresh` **让数据能被搜到**（进段，未 fsync）；`flush` 把段 **fsync 落盘并清空 translog**（抗断电）。一个管可见性，一个管持久性 | [refresh / flush](#refresh-flush) |
| 4 | "translog 是干什么的？" | 每条写入追加记录，**进程崩溃后重放**；默认 `durability=request`（每个请求 fsync，不丢），改 `async` 则最多丢 5 秒 | [refresh / flush](#refresh-flush) |
| 5 | "ES 会丢数据吗？" | 分段看：进程被 kill 不丢（translog）；机器断电则取决于 translog 是否 fsync 与段是否 flush；主分片全挂且有副本未同步时会丢 | [refresh / flush](#refresh-flush) |
| 6 | "写入性能怎么优化？" | ① **用 bulk（5~15MB/批）**；② 导入期 `refresh_interval=-1` + `replicas=0`；③ **省略 `_id`**；④ SSD + 堆不超 31GB；⑤ 关注 `thread_pool.write.rejected` | [写入调优](#write-tuning) |
| 7 | "`refresh=true` 和 `refresh=wait_for` 怎么选？" | 都要"读己之写"时用 **`wait_for`**：它排进下一次刷新，不会像 `true` 那样在并发下触发大量强制刷新 | [三种语义](#near-realtime) |
| 8 | "删除一条文档，磁盘空间会立刻释放吗？" | **不会**。删除只是写"标记删除"，要等**段合并**时才物理丢弃 | [删除与更新](#delete-update) |
| 9 | "更新一个字段的底层动作是什么？" | **标记旧文档删除 + 写入一条完整的新文档**（所以更新 ≈ 重写整条），代价与文档宽度成正比 | [删除与更新](#delete-update) |
| 10 | "段合并是什么？为什么要合并？" | 每次 refresh 产生新段，段越多查询要扫的段越多；后台合并线程把小段合成大段，**顺便物理清理已删文档**。代价是大量 IO/CPU | [段合并](#merge) |
| 11 | "force merge 能提升性能吗？" | 对**只读索引**有效（段数降到 1）；**对仍在写入的索引有害**——合并出的段很快被打破，白耗 IO | [段合并](#merge) |
| 12 | "并发更新同一条文档会怎样？" | 两种控制：**内部版本号**（`if_seq_no` + `if_primary_term`）做乐观锁；**外部版本号**（`version_type=external`）让"旧数据自动被拒"，CDC 同步常用 | [并发控制](#concurrency) |
| 13 | "为什么用乐观锁不用悲观锁？" | 搜索/日志场景**冲突概率低**，乐观锁只在冲突时重试，期望成本更低；悲观锁的加锁开销是白付的 | [并发控制](#concurrency) |
| 14 | "为什么主分片数不能改？" | 路由是 `hash(_id) % 主分片数`，**分片数一变，所有文档的路由都变**，等于全部数据要搬迁。要改只能 reindex | [写入链路](#write-path) |
| 15 | "指定 `_id` 和不指定有什么区别？" | 不指定时 ES 自动生成并**跳过"ID 是否存在"检查**，写入更快；指定 `_id` 才有幂等覆盖语义 | [写入链路](#write-path) |
| 16 | "`refresh_interval` 一般设多少？" | 交互搜索 1s（默认）；**日志检索 5~30s**（写入量远大于查询）；批量导入设 -1，灌完再开 | [近实时](#near-realtime) |
