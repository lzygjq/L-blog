# 倒排索引与分词：为什么"搜不到"几乎总是分词的问题

> 导览：[搜索与检索](/search/)

ES 的复杂度几乎都不是"分布式"带来的，而是 **Lucene 带来的**：它是一套**为"从海量文本里快速找词"而生的索引结构**，而"文本"这件事本身就充满了语言歧义。所以本板块的第 1 篇不讲集群、不讲调优，只讲一件事——**一个词是怎么被存进去、又怎么被找出来的**。这一层没弄清，后面的分片、分页、算分全是背。

## 一、正排与倒排：同一份数据，两种问法 {#fundamental}

先看一个失败案例，它是 ES 新手最常见的一类问题：

```text
商品表里有 name = "Apple iPhone 15 Pro 256G 深空黑"
用户搜 "iphone 256"     → 搜不到
用户搜 "Apple iPhone"   → 能搜到
```

为什么？因为 **"256G" 和 "256" 是两个不同的词**，因为 "iPhone" 大小写在不同字段里写法不一致，也可能因为中文没有空格导致整句被切成了一个巨大的词。**这三类问题的根都在"词"这一层，而不在查询这一层。**

要理解"词"这一层，先要区分两种索引：

| 索引 | 结构 | 回答的问题 | 代价 |
|---|---|---|---|
| **正排**（Forward Index） | `文档 ID → 文档内容 / 字段值` | "第 5 篇文档里有什么" | 查"包含某词的所有文档"要**全量扫** |
| **倒排**（Inverted Index） | `词项 → 包含它的文档 ID 列表` | "哪些文档包含这个词" | **文本必须被切成词**，切错就搜不到 |

**这两种是同一份数据的两种组织方式，不是替代关系。** ES 里两者都存：倒排用于**检索**，正排（`doc_values`）用于**排序、聚合、脚本**——所以"聚合慢"和"搜索慢"是两个完全不同的优化方向（见 [查询 DSL 与相关性算分](/search/query-and-scoring#doc-values)）。

### 为什么数据库的 B+ 树做不了这件事

一个自然的疑问是：MySQL 用 B+ 树也能建索引，为什么还要单独上一套 ES？

因为 B+ 树解决的是**"有序查找"**——它的前提是"顺序有意义"。而**全文检索要的是"包含关系"**，这个词出现在句子的第 3 个字还是第 30 个字，对"能不能被搜到"没有任何影响，顺序在这里没有意义。

| | B+ 树（MySQL） | 倒排索引（Lucene） |
|---|---|---|
| 解决的问题 | 等值、范围、前缀、排序 | **包含、多词组合、相关性排序** |
| 数据单元 | 行（一整条记录） | **词项（term）** |
| "包含"查询 | `LIKE '%abc%'` → **索引失效、全表扫** | 天生就是干这个的 |
| 相关性 | 无 | 有（哪些更匹配，可排序） |

> MySQL 侧"为什么 `%abc%` 会失去索引"见 [索引设计](/database/mysql/index-design)。**一句话分工：需要"排序与事务"找 MySQL，需要"包含与相关性"找 ES。** 两者不是替代关系——ES 几乎从不做唯一数据源（它没有事务、主分片数不可改、跨分片 join 能力弱）。

## 二、倒排索引的内部结构：从 term 到 posting list {#structure}

"倒排"听起来简单，真正的工程难点在于**规模**：一篇文档几十个词，十亿文档就是几百亿个 term 条目。所以它的结构是**分层压缩**的：

```text
倒排索引
├── Term Dictionary（词项字典）        ← 所有出现过的词，按字节序排序
│   ├── term "es"     ──▶ 指向 posting list 的指针
│   ├── term "elastic"──▶ …
│   └── term "search" ──▶ …
│
└── Posting List（倒排表）             ← 每个词后面的文档列表
    term "es" → [ doc_1, doc_7, doc_9, doc_33, … ]
                  ↑ 还带：文档频率 df、每个文档中的词频 tf、词在文档中的位置 offset
```

三层设计各自解决一个问题：

**① Term Dictionary 为什么按字节序排序**

因为要能**二分查找**，也可以理解成一棵"词的前缀树"。更进一步，Lucene 把整个词典压成了 **FST（Finite State Transducer，有限状态转换器）**——它把公共前缀合并成共享路径，因此 `elastic` / `elasticsearch` / `element` 这类词只存一份前缀。**FST 是"内存里能装下上亿个词"的原因**，也是 ES 启动时那段"占内存很慢"的原因——它要被加载进堆外的内存。

**② Posting List 为什么要压缩**

如果不压缩，一个高频词（比如中文里的"的"）的 posting list 可能有几亿个文档 ID。压缩手段有三层：

| 手段 | 做法 | 效果 |
|---|---|---|
| **差值编码**（Delta Encoding） | 存 `[1, 7, 9, 33]` → 存 `[1, +6, +2, +24]` | 大数变小，变长整数就够 |
| **分块 + 变长位宽**（FOR） | 每 128 个 ID 一块，块内按最大差值决定用几个 bit | 差值小的块几乎不占空间 |
| **Roaring Bitmap** | 高基数字段用位图表示"存在与否" | 差集/交集运算极快（`filter` 缓存加速的来源） |

> Roaring Bitmap 不只是 ES 在用：**Doris、ClickHouse、Spark 的聚合都用了它**——这是"同一个数据结构在不同数据密度下需要不同表示"的典型工程案例，见[海量数据算法](/fundamentals/algorithms/high-volume)。

**③ posting list 里除了文档 ID 还存了什么**

这是很多人不知道但非常实用的一点：posting list 里还记录了**词频（tf）和位置（position）**。

- **词频** → BM25 算分的输入（出现 5 次比出现 1 次更相关）
- **位置** → 支持**短语查询**（`match_phrase`）与**高亮**（`highlight`）

所以**关掉位置信息能省空间，代价是失去短语查询能力**——`index_options` 就是控制这个的开关。这是一个典型的"用功能换空间"的旋钮。

## 三、分词器三件套：文本是怎么变成 term 的 {#analyzer}

**分析器（Analyzer）是 ES 里最被低估的组件**——它决定了"文档里的文字"和"查询里的关键词"能不能对上。它不是一个步骤，而是**三个阶段串起来的一条流水线**：

```text
原始文本
   │
   ├─① Character Filter（字符过滤）  在分词之前做替换
   │     例：html_strip 去掉 HTML 标签、mapping 做字符替换（& → and）
   │
   ├─② Tokenizer（分词器）          把字符串切成一个个 token ★核心
   │     例：standard 按 Unicode 词边界切、whitespace 按空格切、ik_smart 中文智能切
   │
   └─③ Token Filter（词项过滤）      对切出来的 token 做加工
         例：lowercase 转小写、stop 去停用词、stemmer 词干还原、
             synonym 同义词扩展、asciifolding 去音标
```

**关键认知：三个阶段是"与"的关系，任意一环缺失/配置错，都会导致搜不到。**

内置分析器的差异可以用一句话概括：

| 分析器 | 切分依据 | `Hello, World! 2024` 切成 | 适用 |
|---|---|---|---|
| `standard` | Unicode 词边界 | `hello` / `world` / `2024` | 英文默认 |
| `simple` | **非字母**即分隔，且转小写 | `hello` / `world` | 只想要纯字母 |
| `whitespace` | 只按空格 | `Hello,` / `World!` / `2024` | **不推荐**：标点会跟着词一起进索引 |
| `keyword` | **完全不切**，整串一个 term | `Hello, World! 2024` | 精确值字段 |
| `language`（如 `english`） | 空格切 + 词干还原 + 停用词 | `hello` / `world` / `2024` | 英文正文（搜 `running` 能命中 `run`） |

> **`whitespace` 的坑值得单独说**：它把 `Hello,` 和 `Hello` 当成两个词，所以搜 `Hello` 搜不到 `Hello,` 开头的句子。**除非有极特殊需求，不要用 `whitespace`。**

### 同一个文本，索引期与查询期会各分析一次

这是理解 ES 检索行为的**核心机制**：

```text
写入时：原文 ──[分析器]──▶ term 列表 ──▶ 存进倒排索引
查询时：关键词 ──[分析器]──▶ term 列表 ──▶ 拿去和倒排索引比对
```

**两次必须用同一个分析器，否则必然搜不到。** 这条机制直接解释了几个经典现象：

| 现象 | 真相 |
|---|---|
| 字段用 `standard` 建索引，查询用 `keyword` 分析 | 查询侧不切词，拿整串去比，**永远匹配不上** |
| 搜 `IPhone` 能命中 `iphone` | `standard` 里有 `lowercase`，两边都被降为小写 |
| 加了大写但搜不到 | 该字段用的是**自义分析器**，其中漏了 `lowercase` |
| 搜 `苹果手机` 搜不到 `Apple 手机` | 两边被切成完全不同的词——**这是同义词（synonym）该解决的，不是分词** |

## 四、中文分词为什么是最大的坑 {#chinese}

英文有天然的空格做分隔，中文没有。这导致中文检索的绝大多数问题都出在分词这一步：

```text
"中华人民共和国" 
  按字切：中 / 华 / 人 / 民 / 共 / 和 / 国      → 搜"华人"会莫名其妙命中（噪声）
  按词切：中华人民共和国                        → 搜"中国"搜不到（漏召回）
  智能切：中华人民共和国 / 中国                → 需要词典与算法共同决定
```

中文分词的四种切法，差异是本质的：

| 切法 | 例子（"我爱北京天安门"） | 特点 |
|---|---|---|
| **单字切分** | 我 / 爱 / 北 / 京 / 天 / 安 / 门 | 召回率高、**精度差**、索引膨胀；但**永远不会漏**——很多搜索兜底方案会同时建单字索引 |
| **最大匹配（正向/逆向）** | 我 / 爱 / 北京 / 天安门 | 依赖词典，**歧义无法解决**（"研究生命起源"→"研究/生命"还是"研究生/命"） |
| **最大概率（HMM / CRF）** | 我 / 爱 / 北京 / 天安门 | 用统计模型解歧义，效果明显更好，**主流方案的基础** |
| **深度学习分词** | 同上，精度更高 | 成本高，ES 生态里少用 |

**ik 是 ES 中文场景的事实标准**，它提供两个分析器，选择本身就是一道判断题：

| 分析器 | 切分策略 | 切 `中华人民共和国国歌` | 特点 |
|---|---|---|---|
| **`ik_smart`** | 粗粒度，**最长匹配优先** | `中华人民共和国` / `国歌` | 索引小、查询快；**召回率低** |
| **`ik_max_word`** | 细粒度，**穷尽所有可能组合** | `中华人民共和国` / `中华人民` / `中华` / `华人` / `人民共和国` / `人民` / `共和国` / `共和` / `国歌` | 索引大、召回率高；**有噪声** |

**工程上的标准答案是"索引期细、查询期粗"**——这不是拍脑袋，而是那个"两次分析"机制的直接推论：

```text
写入（index_analyzer）：ik_max_word   ← 尽可能多切，让任何合理的搜索词都能对上
查询（search_analyzer）：ik_smart     ← 只用一种最可能的切法，避免查询词爆炸
```

### 中文分词的三个残留问题

即使配好了 ik，"搜不到"依然会发生，剩下的是这三类：

| 问题 | 例子 | 手段 |
|---|---|---|
| **词典缺失新词/专有名词** | 品牌名、人名、新造词被切碎 | 自定义词典 + 热更新（ik 的 `ext_dict`） |
| **同义词不统一** | "手机 / 移动电话 / 电话"、简繁混用 | **同义词 filter**（在分析器里做）或查询期扩展 |
| **拼写错误与近似写法** | `iphone` vs `ipnone`、`256G` vs `256` | **模糊查询 / ngram**，或写入时归一化 |

> **一个能立刻用上的判据**：当业务说"搜索不准"，先别去调相关性算分（BM25）——**先问"这个词被切成什么了"**。相关性算分只能解决"排序不好"，解决不了"根本没召回"。

## 五、分析器决定了"能不能搜到"：一条可操作的排查链 {#debug}

ES 提供了一个直接观察分词结果的接口，**它应该是排查任何"搜不到"问题的第一步**：

```bash
# 看一段文本用某个分析器会切成什么
GET /_analyze
{
  "analyzer": "ik_max_word",
  "text": "中华人民共和国国歌"
}

# 看某个字段实际用的是哪个分析器（字段映射上的分析器优先）
GET /product/_analyze
{
  "field": "name",
  "text": "Apple iPhone 15"
}
```

拿到 token 列表后，按这条链往下走：

```text
① 分词结果对不对？
   ├─ token 里没有用户会搜的词   → 分析器选错 / 词典缺词        → 调 analyzer / 加词典
   └─ token 正常                 ↓
② 查询侧的分析器一致吗？
   ├─ 写入与查询分析器不同        → 改 search_analyzer           → 统一
   └─ 一致                        ↓
③ 字段类型对不对？
   ├─ 该用 text 却用了 keyword   → 只有"完全相等"才匹配          → 改 mapping（需 reindex）
   └─ 类型正确                    ↓
④ 那就不是"词"的问题了          → 去查 filter / range / 分片 / 数据是否真的写进去了
```

> **第 ④ 步常被忽略**：有时候根本不是检索问题，而是**数据没同步进来**（如 CDC 管道断了、双写失败）。**先 `GET /index/_count` 确认文档数**，比调 DSL 高效得多。数据同步链路见 [Canal 数据同步](/bigdata/canal/)。

## 六、text 与 keyword：ES 最高频的一题 {#text-keyword}

这是 ES 面试里出现频率最高的一道题，也是最容易在真实项目里踩坑的一个选择：

| | **`text`** | **`keyword`** |
|---|---|---|
| 是否分词 | **是**（走分析器） | **否**（整串作为一个 term） |
| 底层结构 | 倒排索引 | 倒排索引 + **`doc_values`（正排）** |
| 能做全文检索 | ✅ | ❌（只能整体精确匹配） |
| 能做排序 / 聚合 | ❌ **报错**（`Fielddata is disabled`） | ✅ 原生支持 |
| 典型用途 | 标题、正文、描述、日志 message | ID、状态、标签、枚举、用户邮箱、**任何要聚合/排序的字段** |
| 大小写 | 取决于分析器（通常不敏感） | **敏感**（原样存储，`ABC` ≠ `abc`） |

**三条例外规则值得记住：**

**① 用 `text` 做聚合会报错，这是刻意的**

`text` 字段默认**没有 `doc_values`**（因为它被切成了词，按词聚合没意义），而聚合/排序需要正排。ES 会直接拒绝并提示 `Fielddata is disabled on text fields by default`。

有人会打开 `fielddata: true` 绕过它——**这是生产事故的常见来源**：`fielddata` 把词项加载进 **JVM 堆**（而不是 `doc_values` 用的堆外），字段基数一高就是 OOM。**正确做法是加一个 `keyword` 子字段**：

```json
{
  "mappings": {
    "properties": {
      "brand": {
        "type": "text",
        "analyzer": "ik_max_word",
        "fields": {
          "keyword": { "type": "keyword", "ignore_above": 256 }
        }
      }
    }
  }
}
```

```text
全文检索 → brand          （分词，能搜"苹果手机"）
精确聚合 → brand.keyword  （不分词，按原值分组）
```

**这就是"多字段（multi-field）"的标准用法**——**一个字段同时提供两种能力，不牺牲任何一边。**

**② `ignore_above` 是防止长文本进 `keyword` 的保险丝**

`keyword` 要整串存储，一条几百字的日志塞进去会让索引急剧膨胀。`ignore_above: 256` 的意思是**超过 256 字符的值不建索引**（不是截断，是不索引）。

**③ 结构化字段该用 `keyword` 而不是 `text`**

| 字段 | 该用 | 理由 |
|---|---|---|
| 订单号、用户 ID、设备号 | `keyword` | 要精确匹配 + 可能聚合 |
| 状态、类型、城市、标签 | `keyword` | 要聚合分组（`terms` 聚合） |
| 标题、商品名、正文 | `text` + `.keyword` 子字段 | 既要搜又要排序/聚合 |
| 邮箱、URL | `keyword` | 精确查找，且**不希望被切碎** |

> **一个反直觉的例子**：`email` 若建为 `text`，`standard` 分析器会把 `a.b@corp.com` 切成 `a` / `b` / `corp.com`——于是搜 `a` 能搜出一堆无关邮箱。**凡是"整体才有意义"的字段，一律 `keyword`。**

## 七、Mapping 与 dynamic mapping：字段类型一旦定下就改不了 {#mapping}

Mapping 是 ES 的"表结构"，但它和数据库最本质的区别在于：**ES 的索引是不可变的（Immutable）**。这带来一条非常硬的规则：

> **已有数据的字段类型不能修改。** 想把 `text` 改成 `keyword`，只能**新建索引 + reindex + 切别名**。

这条规则是从 Lucene 来的——字段类型决定了它在倒排索引和 `doc_values` 里的存储方式，**改类型等于要求重写已经落盘的段**。所以引出一个非常实用的判断：

**能做 reindex 吗？** 如果索引有几十亿文档、写入还在持续，reindex 的窗口可能根本不存在。**因此 mapping 必须在建索引时就设计对。**（分片数同理不可改，见[分片、路由与深分页](/search/sharding-and-scale#why-primary-immutable)。）

### dynamic mapping：便利与灾难的一线之隔

ES 默认允许"不定义 mapping 直接写文档"，它会**根据第一个文档的值猜类型**：

| 写入的值 | ES 推断的类型 | 危险在哪 |
|---|---|---|
| `"2026-09-16"` | `date` | 后面写入 `"待定"` 会**直接报错** |
| `123` | `long` | 后面写入 `"abc"` 会报错 |
| `12.5` | `float` | 精度丢失 |
| `"订单号A001"` | `text`（**会分词**） | 精确查找失效，且不能聚合 |
| `{"a":1}` | `object` | 数组语义混乱（见下） |

**最危险的一类是"字符串被推成 `text`"**——它静默地把一个应该精确匹配的字段变成了分词字段，而且**这是不可逆的**（不能改类型）。等发现时，通常已经写入了几千万条数据。

**实践纪律：生产索引一律显式定义 mapping，并且关闭或收紧 dynamic。**

```json
{
  "mappings": {
    "dynamic": "strict",          // 未定义字段写入直接报错（推荐：把问题暴露在写入时）
    "properties": {
      "order_no":  { "type": "keyword" },
      "amount":    { "type": "scaled_float", "scaling_factor": 100 },
      "status":    { "type": "keyword" },
      "created_at":{ "type": "date", "format": "strict_date_optional_time||epoch_millis" }
    }
  }
}
```

> `dynamic: "strict"` 的取舍值得说清：它会把"新增字段"变成一次**写入失败**，需要同步改 mapping。听起来麻烦，但**比起几十亿数据写进一个类型错误的字段，这个麻烦小两个数量级**。折中方案是 `"false"`（允许写入但不索引该字段，可事后补 mapping——**新字段不会立刻可搜，需要一个 reindex 或 `_update_by_query` 补索引**）。

### 两个 mapping 上的高频误解

**① ES 没有"数组类型"，也没有真正的"嵌套"**

```json
{ "user": [ {"name":"张三","age":30}, {"name":"李四","age":20} ] }
```

你以为存了两个对象，实际 ES 会把它**拍平**成：

```text
user.name = ["张三", "李四"]
user.age  = [30, 20]
```

于是查 `name=张三 AND age=20`，**会命中这条文档**——因为两个条件在拍平后的数组里都能找到，但**并不存在同一个对象满足它们**（这是经典的"数组关联丢失"问题）。

**解法是 `nested` 类型**：它把每个子对象当成独立的隐藏文档索引，查询时要显式用 `nested` 查询包裹。**代价**：`nested` 文档会让文档数成倍增长，且更新要整组重写。**只有当"子字段之间的关联有意义"时才用 `nested`**，否则就是白付代价。

**② `keyword` 的"大小写敏感"取决于分析器，不是类型本身**

`keyword` 类型默认用 `keyword` 分析器（完全不处理），所以 `ABC` ≠ `abc`。**但你可以给 `keyword` 挂一个 `normalizer`**（`normalizer` 是 `keyword` 版的分析器，只能有 Character Filter 与 Token Filter，不能用 Tokenizer——因为它不切词）：

```json
{
  "settings": {
    "analysis": {
      "normalizer": {
        "lc": { "type": "custom", "filter": ["lowercase", "asciifolding"] }
      }
    }
  },
  "mappings": {
    "properties": { "status": { "type": "keyword", "normalizer": "lc" } }
  }
}
```

**这是"既想精确匹配又不想大小写敏感"的正解**——比改用 `text` 精确得多。

|---|---|---|---|
| 1 | "倒排索引是什么？为什么比 B+ 树适合全文检索？" | 存的是"**词项 → 文档 ID 列表**"；B+ 树解决"有序查找"（`%abc%` 直接失效），倒排天生解决"**包含**"，且能按相关性排序 | [正排与倒排](#fundamental) |
| 2 | "为什么 MySQL 有索引还要上 ES？" | 两者解决的问题不同：MySQL 管**事务与范围**，ES 管**包含与相关性**；ES 不能做唯一数据源（无事务、主分片数不可改） | [正排与倒排](#fundamental) |
| 3 | "ES 凭什么能装下上亿个词？" | 词典压成 **FST**（共享前缀），posting list 用**差值编码 + 分块变长位宽**，高基数列用 **Roaring Bitmap** | [内部结构](#structure) |
| 4 | "posting list 里为什么不只存文档 ID？" | 还存**词频（算分用）与位置（短语查询与高亮用）**；关掉位置能省空间但要放弃短语查询（`index_options`） | [内部结构](#structure) |
| 5 | "分词器包含哪几部分？" | 三件套：**字符过滤 → 分词器 → 词项过滤**，是"与"关系，任一环配错都会搜不到 | [三件套](#analyzer) |
| 6 | "为什么写入和查询要用同一个分析器？" | 写入时把原文切成 term 建立索引，查询时把关键词也切成 term 再去比对；**两边切法不同必然对不上** | [两次分析](#analyzer) |
| 7 | "`ik_smart` 和 `ik_max_word` 怎么选？" | **索引期用 `ik_max_word`（细粒度、召回高），查询期用 `ik_smart`（粗粒度、查询词不爆炸）** ——"索引细、查询粗" | [中文分词](#chinese) |
| 8 | "中文搜索不准，先查什么？" | 先跑 `_analyze` 看**这个词被切成什么了**；相关性算分只能解决"排序不好"，解决不了"没召回" | [排查链](#debug) |
| 9 | "`text` 和 `keyword` 的区别？" | `text` 分词、能全文搜、**不能直接聚合排序**；`keyword` 不分词、精确匹配、有 `doc_values` 可聚合排序 | [text 与 keyword](#text-keyword) |
| 10 | "`text` 字段做聚合报 `Fielddata is disabled` 怎么办？" | **不要开 `fielddata`（占 JVM 堆、易 OOM）**，应加 `.keyword` 子字段用 multi-field 做聚合 | [text 与 keyword](#text-keyword) |
| 11 | "一个字段既要全文搜又要聚合怎么办？" | 用 **multi-field**：主字段 `text` 负责搜，`.keyword` 子字段负责聚合排序 | [text 与 keyword](#text-keyword) |
| 12 | "`ignore_above` 是干什么的？" | 超过指定长度的值**不建索引**（不是截断）；防止长文本塞进 `keyword` 导致索引膨胀 | [text 与 keyword](#text-keyword) |
| 13 | "邮箱字段该用什么类型？" | `keyword`。用 `text` 会被切成 `a` / `b` / `corp.com`，搜 `a` 命中一堆无关邮箱 | [text 与 keyword](#text-keyword) |
| 14 | "ES 能改字段类型吗？" | **不能**。索引不可变，改类型要**新建索引 + reindex + 切别名**；所以 mapping 必须建索引时定对 | [Mapping](#mapping) |
| 15 | "开了 dynamic mapping 有什么风险？" | 会按第一个文档**猜类型**：本该精确匹配的字符串被推成 `text`、后面写不同类型直接报错，**且类型不可改** | [dynamic mapping](#mapping) |
| 16 | "ES 支持数组和嵌套对象吗？" | ES **没有数组类型**，且对象会被**拍平**，导致"子字段关联丢失"（查 `name=张三 AND age=20` 会误命中）；有语义关联时用 `nested`，代价是文档数成倍增长、更新要整组重写 | [数组与嵌套](#mapping) |
| 17 | "`keyword` 能大小写不敏感吗？" | 能，挂 **`normalizer`**（`keyword` 版分析器，只能有字符过滤与词项过滤，不能分词） | [normalizer](#mapping) |
