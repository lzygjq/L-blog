# 查询 DSL 与相关性算分：先说清"要打分还是只要筛选"

> 上一篇：[写入链路与近实时](/search/write-and-read)　|　导览：[搜索与检索](/search/)

ES 的查询 DSL 看起来只是"JSON 版的 SQL"，但它有一个 SQL 里不存在的概念：**算分（scoring）**。而"要不要算分"这一个问题，直接决定了查询能不能用缓存、快不快、结果对不对。**所以这一篇不按语法顺序讲，而是按"这个查询要不要算分"这条主线来分。**

## 一、两种上下文：Query Context 与 Filter Context {#context}

这是 ES 性能优化里**最重要、也最容易忽略**的一条分界：

| | **Query Context（查询上下文）** | **Filter Context（过滤上下文）** |
|---|---|---|
| 写法 | `{"match": {...}}`、裸写在 `query` 下 | `{"bool": {"filter": [...]}}`、`{"term": {...}}` 包在 filter 里 |
| 是否算分 | **算**，参与相关性排序 | **不算**，只回答"是/否" |
| 能否缓存 | ❌ 不缓存（算分依赖全局统计） | ✅ **用 bitset 缓存**（相同 filter 命中同一段时可复用） |
| 性能 | 相对慢 | **快**（无算分开销 + 可缓存） |
| 该用在哪 | 用户输入的搜索词 | **所有"精确筛选"条件**：状态、时间范围、ID、分类、权限 |

**一句话结论：凡是"不参与相关性排序"的条件，一律放进 `filter`。**

```json
// ❌ 常见写法：所有条件都参与算分，浪费且不缓存
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "手机" } },
        { "term":  { "status": "on_sale" } },
        { "range": { "created_at": { "gte": "2026-01-01" } } }
      ]
    }
  }
}

// ✅ 正确写法：搜索词算分，筛选项走 filter
{
  "query": {
    "bool": {
      "must":   [ { "match": { "name": "手机" } } ],
      "filter": [
        { "term":  { "status": "on_sale" } },
        { "range": { "created_at": { "gte": "2026-01-01" } } }
      ]
    }
  }
}
```

**为什么 filter 能缓存而 query 不能？** 因为算分需要"词在**所有文档**里的分布"（IDF），这个统计量随文档增删而变；而 filter 只回答"这个文档在不在集合里"，结果是一个**位图（bitset）**，只要底层段没变就能复用。

> **一个真实收益的量级感**：把 `must` 里的筛选条件全部改到 `filter`，常见收益是**查询耗时下降 30%~70%**，且 QPS 越高收益越明显（因为缓存被反复命中）。**这是一个零风险改动**——结果集完全不变，只是不算分、可缓存。

## 二、四种基础查询：差一个词，语义完全不同 {#basic-queries}

ES 里最容易出错的不是复杂查询，而是这四兄弟——**它们名字相似，行为差得很远**：

| 查询 | 对查询词做分析吗 | 匹配粒度 | 例：字段值 `Apple iPhone 15 Pro` |
|---|---|---|---|
| **`term`** | **不做**（原样查） | 词项（term）精确匹配 | `term: {name: "Apple"}` → ⚠️ 字段是 `text` 时**可能搜不到**（被切成 `apple`） |
| **`match`** | **做**（走字段的分析器） | 分词后**任一词命中即可**（默认 OR） | `match: {name: "iPhone 15"}` → 匹配（iPhone、15 都命中） |
| **`match_phrase`** | 做 | 分词后**必须按顺序相邻出现** | `match_phrase: {name: "iPhone 15"}` → 匹配；`"15 iPhone"` → **不匹配** |
| **`range`** | 不做 | 范围 | `range: {created_at: {gte: "2026-01-01"}}` |

**三个必须知道的细节：**

**① `term` 用在 `text` 字段上是经典陷阱**

```json
// 字段 name 是 text，分析器把 "Apple iPhone" 切成 ["apple","iphone"]
{ "term": { "name": "Apple" } }    // ❌ 搜不到：索引里是 "apple"，而 term 查询不做分析
{ "term": { "name": "apple" } }    // ✅ 能搜到
```

`term` 是**给 `keyword` 字段和已归一化的值用的**。要在 `text` 字段上精确匹配，应该查它的 `.keyword` 子字段。

**② `match` 的默认操作符是 OR，这经常不符合业务预期**

```json
// 用户搜 "红色 连衣裙"，OR 语义：命中"红色"或"连衣裙"的都会返回
{ "match": { "title": "红色 连衣裙" } }

// 要"都要命中"，显式指定 operator
{ "match": { "title": { "query": "红色 连衣裙", "operator": "and" } } }
```

**OR 与 AND 的取舍**：OR 召回高但精度低（可能返回一堆只含"红色"的衬衣）；AND 精度高但可能一条都不返回。**实践中的折中是用 `minimum_should_match`**——比如 `"minimum_should_match": "75%"`，让 4 个词里至少命中 3 个。这是最贴近"用户直觉"的语义。

**③ `match_phrase` 有 `slop` 参数，用来放宽"相邻"要求**

```json
{ "match_phrase": { "title": { "query": "iPhone 15", "slop": 1 } } }
```

`slop` 表示"允许词之间有几个词的距离"：`slop=1` 时，`iPhone 15 Pro` 甚至 `iPhone 快充 15` 都能命中。**代价是位置计算更复杂、变慢。**

> **`term` vs `match` 的判据可以压缩成一句话**：**字段是 `keyword` 或查询值已经归一化 → `term`；字段是 `text` 且输入是"用户原话" → `match`。**（分析器机制见[倒排索引与分词](/search/inverted-index#analyzer)。）

## 三、bool 查询：四个子句各自在干什么 {#bool}

`bool` 是 ES 查询的骨架，四个子句的差异不只是"要不要满足"，**还有"要不要算分"**：

| 子句 | 语义 | 参与算分 | 能否缓存 |
|---|---|---|---|
| **`must`** | **必须**满足（AND） | ✅ 参与，贡献分数 | ❌ |
| **`filter`** | **必须**满足 | ❌ 不参与 | ✅ 可缓存 |
| **`should`** | **应该**满足（影响分数；默认"至少满足一个"） | ✅ 参与 | ❌ |
| **`must_not`** | **必须不**满足（NOT） | ❌ 不参与 | ✅ 可缓存 |

**两个高频混淆点：**

**① `should` 的"至少满足一个"有一条重要例外**

**当 `bool` 里存在 `must` 或 `filter` 时，`should` 的"至少命中一个"约束会失效**——此时 `should` 只用来**加分**，不命中也没关系。

```json
{
  "bool": {
    "must":   [ { "match": { "title": "手机" } } ],   // 有这个，should 就不再是硬要求
    "should": [ { "term": { "brand": "apple" } },     // 命中则加分、排得更前
                { "term": { "is_new": true } } ]
  }
}
```

想强制"至少命中 N 个 should"，必须显式写 `"minimum_should_match": N`。

**② `must_not` 的性能取决于它能不能用 filter 缓存**

`must_not` 是"排除"，它天然不需要算分——**所以 `must_not` 里绝对不要放 `match` 这类需要分析的查询**，应该只放 `term` / `range` / `exists` 这类可过滤条件。

### 一个完整的生产级查询（含最佳实践）

```json
{
  "query": {
    "bool": {
      "must": [
        { "multi_match": {
            "query": "旗舰 手机",
            "fields": ["title^3", "brand^2", "desc"],   // ^ 是权重提权
            "type": "best_fields",
            "minimum_should_match": "75%"
        }}
      ],
      "filter": [
        { "term":  { "status": "on_sale" } },
        { "term":  { "category_id": 101 } },
        { "range": { "price": { "gte": 1000, "lte": 5000 } } },
        { "range": { "created_at": { "gte": "now-30d/d" } } },
        { "exists": { "field": "cover_url" } }
      ],
      "must_not": [
        { "term": { "is_deleted": true } }
      ],
      "should": [
        { "term": { "is_hot": true } },
        { "range": { "stock": { "gte": 100 } } }
      ]
    }
  },
  "sort": [
    { "_score": "desc" },
    { "sales": "desc" }
  ],
  "from": 0,
  "size": 20,
  "_source": ["id", "title", "price", "cover_url"]
}
```

**这个查询里有五处值得单独指出的实践：**

| 做法 | 为什么 |
|---|---|
| `title^3` / `brand^2` 提权 | 标题命中的相关度应该高于描述命中——**这是"搜索结果看起来聪明"最廉价的手段** |
| 筛选条件全在 `filter` | 不算分、可缓存 |
| `must_not` 里只用 `term` | 可过滤，不需要算分 |
| 显式 `_source` 字段列表 | **避免返回整条文档**（宽文档下这是网络与反序列化的主要开销） |
| `sort` 用 `_score` + 业务字段 | 相关性优先，同分时用销量打破平局——**避免"结果顺序不稳定"** |

## 四、相关性算分：从 TF-IDF 到 BM25 {#scoring}

**相关性算分要回答的是：这条文档有多匹配这个查询？** 经典答案是 TF-IDF：

```text
TF  （词频）    ：这个词在这条文档里出现几次？出现越多越相关
IDF （逆文档频率）：这个词在所有文档里有多罕见？越罕见越有区分度
```

**TF-IDF 的两个缺陷，恰好是 BM25 改进的地方：**

| 缺陷 | 说明 | BM25 的改进 |
|---|---|---|
| **TF 无上限** | 一个词出现 100 次比出现 10 次"相关 10 倍"——不合理，**实际是饱和的** | TF 部分加上**饱和曲线**（参数 `k1`）：次数多到一定程度后，贡献趋于平缓 |
| **不惩罚长文档** | 长文档天然包含更多词，更容易命中，于是长文档总是排前面 | 引入**文档长度归一化**（参数 `b`）：**文档越长，命中同样的词得分越低** |

BM25 的两个参数就是这两个改进的旋钮：

| 参数 | 默认 | 作用 | 调法 |
|---|---|---|---|
| `k1` | `1.2` | 控制 **TF 的饱和速度**。越小饱和越快 | 一般不动；调到 0 表示"只看有没有出现，不看次数" |
| `b` | `0.75` | 控制 **长度归一化的强度**。`0` = **不做**长度归一化（长文档不吃亏），`1` = 完全归一化 | **字段长度差异大时要调**：如标题（都短）可调小，正文（长短差很多）保持默认 |

**两条比参数更重要的认识：**

**① `_score` 的绝对值没有意义，只有相对顺序有意义。** 同一个查询在不同数据集上跑出的分数不可比，**不要把它当"匹配度百分比"展示给用户**。

**② 算分可以被完全绕过——而且这往往是正确答案。**

```json
{ "query": { "bool": { "filter": [ ... ] } } }        // 只有 filter：不算分
{ "query": { ... }, "sort": [ { "sales": "desc" } ] }  // 显式 sort 非 _score：算分被跳过
```

**关键机制：一旦你指定了非 `_score` 的排序字段，ES 会跳过算分。** 所以"按销量排序的商品列表"这类需求，**根本不该把搜索词放在 `must` 里**——放在 `filter` 或 `must` 都行，反正不算分；放 `filter` 还能缓存。

> **BM25 的另一种选择**：也可以完全不用 BM25，改用**函数算分（function_score）**——把"销量、上新时间、好评率"这些**业务信号**混进分数。这在实际搜索系统里比调 BM25 参数有效得多。因为**用户心里的"相关"，往往不是文本相关性，而是"我想买的那个"**。

## 五、算分在分布式下的问题：分片会扭曲分数 {#dfs}

这是一个**只在多分片时才暴露**的问题，也是 ES 里最有"分布式味"的一个知识点。

算分需要 IDF，而 IDF 需要"词在所有文档里的分布"这个全局统计。但**每个分片只知道自己那部分文档**：

```text
索引 3 个分片，每个分片 1/3 的数据
查询 "iPhone"，在 3 个分片上各自计算 IDF：
  分片 1：iPhone 出现在 60% 的文档里 → 认为这个词很常见 → 给低分
  分片 2：iPhone 出现在 2%  的文档里 → 认为这个词很罕见 → 给高分
  分片 3：iPhone 出现在 10% 的文档里 → 中等
⟹ 同一条文档，落在不同分片会得到不同分数 ⟹ 全局排序是"局部排序的归并"，可能错序
```

**默认的 `query_then_fetch` 流程是这样的：**

```text
① Query 阶段：协调节点把查询发给所有分片
                每个分片用**本地统计**算分，返回 top N（N = from + size）文档 ID 与分数
② Fetch 阶段：协调节点归并所有分片的 top N，选出真正的 top N，再去取文档内容
```

**问题就在第 ① 步的"本地统计"。** 两种解法：

| 方案 | 做法 | 代价 |
|---|---|---|
| **`search_type=dfs_query_then_fetch`** | 先**额外一轮**请求收集所有分片的词频统计，算出全局 IDF，再下发查询 | **多一轮网络往返**，延迟升高；只在分片少、结果集小、对准确性要求高时用 |
| **主分片数为 1，或副本数 = 分片数** | 让每个分片都持有全量数据 → 统计自然就是全局的 | 牺牲分布式的扩展能力 |
| **不用算分**（推荐） | 显式 `sort` 业务字段，或全部用 `filter` | **没有这个问题**——因为是按明确字段排序 |

> **实践结论：绝大多数生产搜索都不依赖 `_score` 的绝对准确性。** 要么业务排序（销量、时间），要么用 `function_score` 混入业务信号。**记住这条就够应付面试**：**单分片不存在这个问题；多分片默认各算各的；`dfs_query_then_fetch` 能修但要多一轮；工程上通常直接不依赖算分。**

## 六、doc_values 与 fielddata：排序聚合的正排从哪来 {#doc-values}

上一篇提到"倒排管搜索、正排管排序聚合"。这个正排就是 **`doc_values`**：

| | **`doc_values`** | **`fielddata`** |
|---|---|---|
| 存储位置 | **磁盘（堆外，OS page cache）** | **JVM 堆内存** |
| 默认开启 | ✅ `keyword` / 数值 / 日期 / 布尔 默认开 | ❌ **`text` 字段默认禁用** |
| 用途 | 排序、聚合、脚本 | 让 `text` 也能排序聚合 |
| 成本 | 索引体积约增加 10%~20% | **可能直接 OOM** |
| 建议 | 保持默认 | **不要开**，改用 `.keyword` 子字段 |

**这就是"[text 字段聚合报错](/search/inverted-index#text-keyword)"的底层原因**：`text` 没有 `doc_values`（按词聚合没意义），而聚合必须有正排，所以 ES 直接拒绝。

**`doc_values` 的三条实践认知：**

**① 不需要排序聚合的字段可以关掉 `doc_values` 省空间**

```json
{ "properties": { "desc": { "type": "text", "index": true }, 
                  "raw_payload": { "type": "keyword", "doc_values": false } } }
```

**② 关掉之后，该字段就永远无法排序/聚合/脚本访问**——这是一条不可逆的功能性取舍。

**③ `doc_values` 是列式存储**：它按"字段"而不是"文档"组织，所以**同一字段的所有值连续存放**，聚合时可以顺序扫描、CPU 缓存友好。这是 ES 聚合能跑得动的关键。

## 七、聚合（Aggregation）：三种类型与四个高频坑 {#aggregation}

聚合是 ES 除了搜索之外的另一半能力（也是它被称为"准 OLAP"的原因）：

| 类型 | 例子 | 输出 |
|---|---|---|
| **Bucket（分桶）** | `terms`（按字段分组）、`date_histogram`（按时间分桶）、`range` | 一组桶，每个桶里有文档 |
| **Metric（指标）** | `avg` / `sum` / `max` / `cardinality`（基数） | 一个数值 |
| **Pipeline（管道）** | `derivative`（求导）、`cumulative_sum` | 基于其它聚合的**输出**再算 |

**四个必须知道的坑：**

**① `terms` 聚合默认只返回 top 10，而且"不准确"**

```json
{ "aggs": { "by_brand": { "terms": { "field": "brand.keyword", "size": 100 } } } }
```

- **默认 `size: 10`**——**加 `size` 才能拿到更多桶**，但加太大会消耗大量内存（协调节点要合并各分片的桶）。
- **分布式 `terms` 聚合天然是近似的**：每个分片各自返回自己的 top N，协调节点合并。**一个在全局排第 5 的品牌，在某个分片里可能连该分片的前 10 都进不去，于是被漏掉。** 这就是 `doc_count_error_upper_bound` 这个字段存在的原因——**它告诉你"最多可能漏掉多少"**。

**② `cardinality`（去重计数）是近似值**

它用的是 **HyperLogLog++**（与 Redis 的 `PFADD` 同源），内存占用固定、误差约 0.5%~5%。**要精确值只能靠 `terms` 聚合的桶数**，但那又受上面的 size 限制。**这是"用精度换内存"的经典工程取舍**（参见[海量数据算法](/fundamentals/algorithms/high-volume)）。

**③ 聚合是"字段级"的，不能用 `_source` 之外的运行时值**

聚合作用于 `doc_values`，所以字段必须设为可聚合类型。**这又回到 mapping 必须在建索引时定对。**

**④ 聚合的开销和"桶数 × 字段基数"成正比**

对高基数字段（如用户 ID、订单号）做 `terms` 聚合，是压垮集群最常见的方式之一。**这类需求应该交给列式数仓**（见下文边界）。

### 与 Doris 的边界：什么时候不需要 ES

这是一条**很值钱的架构判断**。ES 能做聚合，但它的聚合是"在倒排/正排上现算"；而列式数仓（Doris、ClickHouse）是为聚合而生的：

| 需求 | 选谁 | 理由 |
|---|---|---|
| 全文检索 + 相关性排序 | **ES** | Doris 的倒排索引**做不了复杂相关性排序** |
| 多维过滤 + 少量聚合（搜索页的筛选面板） | **ES** | 一次查询搞定，省一个组件 |
| 大宽表、亿级数据的多维聚合分析 | **Doris** | 列存 + MPP，聚合快一个量级 |
| 日志检索（量大、查询简单、要全文搜） | 看规模：**ES** 或 **Doris 倒排索引** | 日志量极大时，Doris 的倒排索引能省掉一个组件 |
| 既要全文搜又要复杂聚合 | **ES 出 ID，回 Doris/MySQL 取聚合** 或 **双写** | 两套引擎各做擅长的事 |

> **Doris 侧的原话值得引用**：倒排索引"替代的是**日志检索**这类场景，不是复杂的相关性排序；但对'既能过滤又能全文搜'的混合查询，省掉一个组件就是净收益"。完整取舍见 [Doris 数仓 · 四类索引](/bigdata/doris/#indexes)。**判断口径是：能不能接受"没有相关性排序"**。

## 八、按场景选查询：一张速查表 {#cheatsheet}

| 业务需求 | 查询写法 | 关键点 |
|---|---|---|
| 用户搜索框 | `multi_match` + `filter` 筛选 | 字段提权、`minimum_should_match` |
| 精确匹配 ID / 单号 | `term`（字段必须 `keyword`） | 绝不用 `match` |
| 短语 / 带语序的搜索 | `match_phrase`（必要时加 `slop`） | 需要位置信息（`index_options`） |
| 时间范围 + 状态筛选 | `filter` 里的 `range` / `term` | **不算分、可缓存** |
| 商品列表（按销量排） | `filter` + `sort: sales` | **算分被跳过**，搜索词放 `filter` 里更省 |
| 模糊 / 拼写容错 | `fuzzy` 或 `wildcard` / `ngram` | **`wildcard` 前缀通配极慢**，优先用 ngram |
| 聚合报表（找 ES 能做的那部分） | `terms` + `date_histogram` | 注意 `size` 与近似性 |
| 存在性检查 | `exists` | 比 `match_all` + `must_not` 干净 |
| 复杂打分（业务信号） | `function_score` | 比调 BM25 有效 |

> **一个反面清单**（这些查询几乎总是错的）：
> - **`wildcard` 以 `*` 开头**（`*phone`）：等价于全扫，**唯一能救它的是 `ngram`**
> - **`regexp` 查询**：同上，且更慢
> - **`terms` 里塞几万个 ID**：会超 `max_clause_count` 限制，且内存爆炸——**改用 `terms` 的 `lookup` 或分批**
> - **`script` 查询/排序**：每文档执行一次脚本，是 CPU 杀手
> - **`from + size` 深分页**：见[分片、路由与深分页](/search/sharding-and-scale#deep-paging)

## 九、面试问答 {#interview}

| # | 高频问法 | 一句话答案 | 出处 |
|---|---|---|---|
| 1 | "query 和 filter 上下文有什么区别？" | `query` **算分不缓存**；`filter` **不算分、结果用 bitset 缓存**。**不参与排序的条件一律放 `filter`** | [两种上下文](#context) |
| 2 | "`term` 和 `match` 的区别？" | `term` **不做分析**（给 `keyword`/已归一化的值用）；`match` **走分析器分词**（给 `text` 和用户输入用） | [四种基础查询](#basic-queries) |
| 3 | "为什么 `term` 查 `text` 字段搜不到？" | 索引里存的是分析后的 term（如 `apple`），`term` 查询不做分析，拿 `Apple` 去比对必然对不上 | [四种基础查询](#basic-queries) |
| 4 | "`match` 的默认语义是什么？" | **OR**——任一分词命中即可；要 AND 需显式 `operator`，实践中更常用 **`minimum_should_match`** 做折中 | [四种基础查询](#basic-queries) |
| 5 | "`match_phrase` 和 `match` 的区别？" | `match_phrase` 要求词**按顺序相邻**（靠 posting list 里的 position），可用 `slop` 放宽 | [四种基础查询](#basic-queries) |
| 6 | "bool 四个子句的区别？" | `must`/`should` **算分**；`filter`/`must_not` **不算分且可缓存** | [bool 查询](#bool) |
| 7 | "`should` 什么时候不是硬要求？" | 当 `bool` 里存在 `must` 或 `filter` 时，`should` 只用来**加分**；想强制必须显式 `minimum_should_match` | [bool 查询](#bool) |
| 8 | "BM25 比 TF-IDF 好在哪？" | 两点：TF 加了**饱和曲线**（`k1`，词频贡献有上限）、加了**文档长度归一化**（`b`，长文档不占便宜） | [相关性算分](#scoring) |
| 9 | "`_score` 能当匹配度百分比用吗？" | **不能**。分数的绝对值没有意义，只有同一次查询内的**相对顺序**有意义 | [相关性算分](#scoring) |
| 10 | "指定排序字段后还算分吗？" | **不算**。一旦 `sort` 用非 `_score` 的字段，ES 会跳过算分——所以"按销量排的商品列表"不必依赖 `_score` | [相关性算分](#scoring) |
| 11 | "多分片时算分会不准吗？" | 会。各分片用**本地 IDF**，同一文档在不同分片得分不同。默认 `query_then_fetch` 就是"局部 topN 归并" | [分片与算分](#dfs) |
| 12 | "`dfs_query_then_fetch` 是什么？" | 先多一轮收集全局词频统计、算全局 IDF 再查询——**准确但多一次网络往返**；工程上更常见的解法是**干脆不依赖算分** | [分片与算分](#dfs) |
| 13 | "`doc_values` 和 `fielddata` 的区别？" | `doc_values` 在**磁盘/堆外**、默认对非 `text` 开启；`fielddata` 在 **JVM 堆**、`text` 默认禁用、**易 OOM** | [doc_values](#doc-values) |
| 14 | "`text` 字段能排序吗？" | 不能（无 `doc_values`）；**不要开 `fielddata` 绕过**，应加 `.keyword` 子字段 | [doc_values](#doc-values) |
| 15 | "`terms` 聚合结果准确吗？" | **分布式下是近似的**：各分片返回本地 topN，协调节点合并，全局排名靠后的桶可能被漏掉（看 `doc_count_error_upper_bound`） | [聚合的坑](#aggregation) |
| 16 | "`terms` 聚合为什么只返回 10 个？" | 默认 `size: 10`；要更多得显式加 `size`，但过大会显著增加协调节点内存 | [聚合的坑](#aggregation) |
| 17 | "`cardinality` 去重计数准吗？" | **近似值**（HyperLogLog++，误差约 0.5%~5%），用固定内存换精度；要精确只能数 `terms` 桶 | [聚合的坑](#aggregation) |
| 18 | "什么时候不需要 ES？" | 大宽表亿级数据的**多维聚合分析**用 Doris 更合适；Doris 的倒排索引也能覆盖**日志检索**。口径是**能不能接受"没有相关性排序"** | [与 Doris 的边界](#aggregation) |
| 19 | "`wildcard` 前缀通配为什么慢？" | 以 `*` 开头无法用词典定位起点，要遍历所有 term——**等价于全扫**，正解是写入时建 `ngram` | [速查表](#cheatsheet) |

> **本篇是这个板块的第 3 篇。** 到这里，"搜不到"和"搜得慢"的两大来源（**词切错了 / 查询写法错了**）已经讲完。下一篇[分片、路由与深分页](/search/sharding-and-scale)要讲的是**分布式之后多出来的那一类代价**——分片、副本、路由、深分页，以及集群为什么会脑裂。
