# RocketMQ

RocketMQ 在 [消息队列板块导览](/middleware/) 里的定位很明确：**事务消息与延迟消息的强项，电商交易场景的标配**。但只记住这个定位是不够的——面试和实际选型真正会问的是：**它凭什么能做到这两件事？**

答案藏在它的存储模型里。所以本文的顺序是：**先讲 5.x 的架构与 CommitLog 三层存储，再讲事务/顺序/延迟建立在它之上的机制**。跳过存储直接背"半消息 + 回查"，是记不牢的。

## 一、5.x 架构：计算存储分离 {#architecture}

### 与 4.x 的本质区别

| 维度 | 4.x | 5.x |
|---|---|---|
| 协议 | 自定义 Remoting 协议 | **gRPC**（HTTP/2 多路复用、流式），兼容 HTTP |
| 架构 | Broker 既存消息又算逻辑 | **计算与存储分离**：Broker 只管存储与检索，Proxy 承担事务/延迟/轨迹等逻辑 |
| 客户端 | `rocketmq-client` | **`rocketmq-client-java`**（全新 API，与 4.x 是两套东西） |
| Broker 状态 | 有状态，扩容麻烦 | **无状态化**倾向，Proxy 可挂 K8s 秒级扩缩容 |
| 消费模式 | Push / Pull | 增加 **Pop** 消费 |
| 多语言 | 困难（自定义协议） | 容易（gRPC 是通用协议） |

```text
                    ┌──────────────────────────────┐
                    │        NameServer 集群         │
                    │   （无状态，路由注册与发现）     │
                    └───────────────┬──────────────┘
                                    │ 客户端拉取路由
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  ┌───────────┐              ┌───────────┐              ┌───────────┐
  │  Producer  │──gRPC──────▶│   Proxy    │◀────gRPC─────│  Consumer  │
  └───────────┘              │（无状态）   │              └───────────┘
                             └─────┬─────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
              ┌───────────┐                 ┌───────────┐
              │  Broker    │◀───主从同步────▶│  Broker    │
              │ （只负责存储）│                 │            │
              └───────────┘                 └───────────┘
```

**Proxy 这层的意义**：生产者/消费者只与 Proxy 通信，**Broker 的内部实现对客户端透明**——扩容、迁移、换存储引擎都不影响业务侧。这是"无状态化"带来的真实收益。

### 版本时间线（近两年）

| 版本 | 时间 | 关键变化 |
|---|---|---|
| 5.3.3 | 2025-05 | 一段时间的稳定版基线 |
| 5.4.0 | 2025-12-24 | 引入**优先级消息**、RocksDB 支持 |
| **5.5.0** | **2026-04-10** | 引入 **Lite Mode**（面向 AI 场景的轻量订阅机制，RIP-83 Lite Topic） |
| **5.5.1** | **2026-08-20** | 移除 fastjson 1.x（升到 fastjson2 2.0.63）、DLedger 升到 0.3.3.4、**废弃旧的 Broker DLedger 模式**、原生 RocksDB 压缩过滤器 |

> **两条与选型直接相关的信息**：① **5.5.1 起废弃了 Broker 侧的 DLedger 模式**——新部署应该走 **Controller 模式**（见第三节）；② 5.5.0 的 **Lite Mode 是专门为 AI 场景做的**（大量短生命周期订阅、Agent 任务编排），说明 RocketMQ 在往"AI 任务总线"方向走。

## 二、存储模型：CommitLog 三层 {#storage}

**这是理解 RocketMQ 一切特性的地基。** 它用一套"顺序写 + 异步构建索引"的结构，同时满足高吞吐和多种查询需求：

```text
                    ┌──────────────────────────────┐
   消息先追加写入 ──▶│        CommitLog              │  ← 所有 Topic 的消息
   （完全顺序写）     │  （单个文件固定大小，顺序追加） │     混写在一个文件里！
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    │ 异步分发（ReputMessageService）│
                    ▼                             ▼
        ┌───────────────────────┐    ┌───────────────────────┐
        │     ConsumeQueue       │    │      IndexFile         │
        │  按 Topic+Queue 的逻辑  │    │  按 key / 时间区间      │
        │  索引（定长 20 字节）    │    │  的哈希索引            │
        │  → 消费时靠它定位        │    │  → 查询消息时靠它       │
        └───────────────────────┘    └───────────────────────┘
```

### 三个设计点

| 设计 | 好处 |
|---|---|
| **所有 Topic 混写一个 CommitLog** | 写入是**全顺序**的（没有多文件随机写），这是高吞吐的根本 |
| **ConsumeQueue 定长 20 字节** | 消费定位靠它做**一次偏移计算**就够了；定长才能随机访问 |
| **IndexFile 独立** | 满足"按消息 key 查"这类运维需求，且不影响主链路 |

**为什么"混写"反而是优点？** 如果每个 Topic 一个文件，几百个 Topic 就是几百个文件轮流写——**磁盘被迫在多文件间跳来跳去**。混写一个文件，磁盘只做一件事：顺序追加。代价是消费时必须靠 ConsumeQueue 二次定位，但这个代价换来的是吞吐量级上的差异。

> **对比记忆**：Kafka 是**按分区**写日志（每个 Partition 一个 Log 文件，也是顺序写），RocketMQ 是**全 Topic 混写**。两者都在"顺序写"上做文章，只是切分维度不同。

## 三、高可用：两条路的演进 {#high-availability}

| 方案 | 机制 | 现状 |
|---|---|---|
| **主从（异步/同步复制）** | Master 写，Slave 同步；**Master 挂了不能自动切换** | 老方案，4.x 常见 |
| **DLedger** | 基于 Raft，日志格式与原生不同；**IO 负担更重**（要同步 Raft 日志） | ⚠️ **5.5.1 起废弃 Broker 侧 DLedger 模式** |
| **Controller 模式**（推荐） | **Raft 选举 + 原生 CommitLog** 的混合架构：Controller 集群基于 Raft 负责选主与状态管理，Broker 仍用原生 CommitLog 同步 | **5.x 的新方向** |

**Controller 模式的巧妙之处在于职责分离**：把"选主"和"数据同步"拆开——选主用 Raft（保证一致性），数据同步用原生主从（效率更高）。这样既拿到了自动故障转移，又没有 DLedger 那份 Raft 日志的额外 IO 开销。

**切换过程**：Master 故障 → Controller 集群选举新 Master → 客户端通过 NameServer 拿到新路由 → 业务无感。

**另外两个 5.x 的部署特性：**

| 特性 | 价值 |
|---|---|
| **BrokerContainer** | 一个进程里可跑多个 Broker（Master/Slave 混合部署）——**资源利用率**：传统部署里 Slave 几乎闲置，容器化后可以主从交叉部署做到角色对等 |
| **无状态 Broker 部署** | 配合 Proxy 层，扩容不影响业务侧 |

## 四、事务消息：半消息 + 回查 {#transaction}

**这是 RocketMQ 最出名的能力，也是它和 Kafka/RabbitMQ 最大的差异点。** 它解决的问题是：**本地数据库事务和发消息，怎么保证要么都成功、要么都失败？**

### 完整时序

```text
生产者                          Broker                        消费者
   │                              │                             │
   │ ① 发送【半消息】(Half Message) │                             │
   │─────────────────────────────▶│                             │
   │                              │ 存入 CommitLog，             │
   │ ② 返回"接收成功"              │ 但【对消费者不可见】          │
   │◀─────────────────────────────│                             │
   │                              │                             │
   │ ③ 执行【本地事务】             │                             │
   │   （扣库存 / 落订单表）        │                             │
   │                              │                             │
   │ ④a 本地成功 → Commit ────────▶│ 消息转为可见 ────────────────▶│ ⑤ 消费
   │ ④b 本地失败 → Rollback ──────▶│ 消息被丢弃                    │
   │                              │                             │
   │ ⚠️ 如果 ④ 丢了（生产者宕机）：   │                             │
   │                              │                             │
   │ ⑥ Broker 主动【回查】─────────▶│                             │
   │◀─────────────────────────────│                             │
   │ ⑦ 生产者查本地事务表的状态，     │                             │
   │   返回 Commit / Rollback      │                             │
```

### 四个必须搞清的点

| 问题 | 答案 |
|---|---|
| 为什么要有"半消息"？ | 让"消息已到达 Broker"这件事**先于**本地事务完成——这样才有东西可以回查。如果先做本地事务再发消息，发消息失败时本地已提交，无法回滚 |
| 回查什么时候触发？ | Broker 长时间没收到 Commit/Rollback（生产者宕机、网络断了） |
| 回查靠什么判断？ | 靠**生产者查自己的本地事务状态**——所以本地事务必须有可查的记录（事务表/业务状态字段） |
| 回查次数与间隔能配吗？ | 能。**默认回查 15 次**，间隔可配 |

### 三个坑

| # | 坑 | 说明 |
|---|---|---|
| 1 | **回查接口不做幂等** | 回查可能重复触发，返回结果必须幂等，否则可能"提交两次"或状态错乱 |
| 2 | **回查间隔设得太短** | 本地事务如果有长 SQL 会卡住，间隔太短会让回查请求**把数据库连接池打满**。间隔要按本地事务的实际耗时来定 |
| 3 | **以为事务消息能解决一切分布式事务** | 它解决的是"**本地事务 + 发消息**"的原子性（最终一致）。跨多服务的复杂事务仍要考虑 Saga / TCC / 本地消息表等方案；而且**它只保证消息不丢，不保证业务一定成功**——消费端失败还是要靠重试与幂等兜底 |

> **一句话总结它和能力边界**：事务消息 = **"本地事务成功后消息一定可见，本地失败则消息一定不可见"**。它把"发消息"拉进了本地事务的语义范围，这是它的全部价值，也是它的边界。

## 五、顺序消息 {#ordering}

先分清两种，因为面试常在这里挖坑：

| 类型 | 做法 | 并发度 | 实际使用 |
|---|---|---|---|
| **全局有序** | 所有消息进同一个队列 | 极低（等于串行） | ❌ 生产环境基本不用 |
| **分区有序**（严格顺序） | 相同业务键的消息进**同一个队列** | 高（队列数 = 并发度） | ✅ **这才是"顺序消息"** |

```java
// 5.x 新客户端：直接设置 MessageGroup，相同 group 路由到同一队列
Message msg = provider.newMessageBuilder()
        .setTopic("ORDER_TOPIC")
        .setMessageGroup("ORDER_1001")     // ← 同一订单号 → 同一队列
        .setBody("Create Order".getBytes())
        .build();
```

（4.x 需要自己实现 `MessageQueueSelector` 算 Hash 选队列，5.x 直接用 `MessageGroup`。）

**消费端也必须配合**：用 `SimpleConsumer` 或 `PushConsumer`，并开启顺序消费（`ConsumeMode.ORDERLY`）。**RocketMQ 在底层保证同一个 `MessageGroup` 的消息，同一时刻只会被分配给一个消费线程处理**——顺序是"生产端路由 + 消费端串行"两边共同保证的。

**顺序消息的两个代价**：

1. **一条消息卡住，后面全堵**——所以消费逻辑必须能快速失败，不能在里面等外部接口；
2. **重试会破坏顺序**——顺序消息的消费失败重试有特殊处理（会阻塞当前队列），吞吐会明显下降。

> **和 [Kafka 顺序性](/middleware/kafka/ordering) 的对照**：思路完全一样（**把需要有序的消息路由到同一个有序单元**），只是 Kafka 的单元叫 Partition，RocketMQ 叫 MessageQueue；Kafka 靠 partition key，RocketMQ 靠 `MessageGroup`/HashKey。

## 六、延迟消息：从 18 个级别到任意精度 {#delay}

| 版本 | 能力 | 限制 |
|---|---|---|
| 4.x | **18 个固定延迟级别**（1s、5s、10s…2h） | 业务要的延迟不在级别里就只能凑 |
| **5.x** | **时间轮 + `setDeliveryTimestamp`**，支持**任意精度延迟与定时消息** | —— |

```java
// 延迟 5 秒投递
Message delayMsg = provider.newMessageBuilder()
        .setTopic("DELAY_TOPIC")
        .setDeliveryTimestamp(System.currentTimeMillis() + 5000)
        .build();

// 定时消息：指定绝对时间点（例如明天凌晨 2 点跑批）
Calendar c = Calendar.getInstance();
c.add(Calendar.DAY_OF_MONTH, 1);
c.set(Calendar.HOUR_OF_DAY, 2);
c.set(Calendar.MINUTE, 0);
Message scheduleMsg = provider.newMessageBuilder()
        .setTopic("SCHEDULE_TOPIC")
        .setDeliveryTimestamp(c.getTimeInMillis())
        .build();
```

> ⚠️ **规模化的坑：别让大量消息集中在同一秒投递。** 比如把几十万条定时任务全设在 `00:00:00`，时间轮的某个槽位会瞬间承压，出现投递毛刺。**做法：在业务层加随机抖动（jitter）**，把延迟时间打散到前后几分钟。

**对比另外两个 MQ 的延迟能力**：

| MQ | 延迟消息 |
|---|---|
| RabbitMQ | ⚠️ 靠 TTL + 死信队列，或延迟插件；原生支持弱 |
| Kafka | ❌ 不支持，需自建时间轮或外部方案 |
| **RocketMQ** | ✅ **原生**，且 5.x 起任意精度——**这是它相对另两家的显性优势** |

## 七、消费模式与消息轨迹 {#consume-and-trace}

### 三种消费模式

| 模式 | 说明 | 适用 |
|---|---|---|
| **Push（推）** | 客户端被"推"消息（底层其实是长轮询） | 常规业务消费 |
| **Pull（拉）** | 消费者主动拉 | 需要自己控节奏 |
| **Pop（弹）** | 5.x 新增：无状态、消息可"弹"给任意消费者实例 | **云原生 / K8s 场景** |

**Pop 模式的意义**：传统 Push 模式下消费者与队列有绑定关系，实例扩缩容会触发 rebalance（有明显的停顿）。Pop 模式让消费端可以无状态扩缩容——**这是为了适配 K8s 弹性伸缩做的设计**。

**5.5.0 的 Lite Mode** 进一步做了面向 AI 场景的轻量订阅：大量短生命周期订阅、快速注册与注销、事件分发。**方向很明确——RocketMQ 在往"AI 任务总线"上走。**

### 消息轨迹

排查"消息到底丢没丢""为什么重复扣款了"，没有轨迹就只能靠猜。5.x 客户端**原生集成了 Message Trace**：

```java
producer = provider.newProducerBuilder()
        .setClientConfiguration(configuration)
        .setTopics("ORDER_TOPIC")
        .enableTrace(true)          // 开启轨迹
        .build();
```

开启后，**生产 → 存储 → 消费**每个关键节点都会生成 Trace 数据，异步写入内置的 `RMQ_SYS_TRACE_TOPIC`。对接 Dashboard 或 ELK 后能看到：生产耗时、Broker 落盘耗时、消费耗时、消费结果。配合 `MessageKey` / `MessageId` 基本能做到全链路秒级定位。

**这一点值得单独强调**：**可观测性不是运维加分项，而是排查扯皮问题的唯一手段。** 和 [Actuator 与生产可观测](/java/spring/spring-boot/actuator) 里那条结论一样——先能看见，才谈得上优化。

## 八、消费端幂等：三种方案与选择 {#idempotency}

**前提认知**：网络抖动、Broker 主从切换、消费者重启，**消息重复投递是常态**。所以幂等不是"要不要做"，而是"怎么做"。**三个主线的这一条在 RocketMQ 上同样成立**——幂等逻辑与 MQ 无关，见 [板块导览](/middleware/#three-threads)。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **数据库去重表** | 唯一索引 + 消息 ID | 实现最简单 | 高频写库性能扛不住；表会持续膨胀 |
| **Redis 分布式锁** | `SETNX` 消息 ID | 并发友好 | 引入额外依赖；要处理锁过期与 Redis 挂掉 |
| **业务状态机**（推荐） | 利用数据库乐观锁：`UPDATE ... SET status=2 WHERE id=? AND status=1` | **幂等校验与业务逻辑合二为一**，没有额外存储 | 需要业务本身有状态流转 |

```java
@Transactional
public void consumeOrderMessage(Message message) {
    String orderId = message.getKey();
    // 只有当前状态为 1（已创建）时才允许更新为 2（已支付）
    int rows = orderMapper.updateStatus(orderId, 2, List.of(1));
    if (rows == 0) {
        log.info("消息已消费或状态不匹配，直接丢弃：{}", orderId);
        return;                     // 幂等拦截，正常 ack
    }
    // 后续业务逻辑
}
```

> **选型判据**：**业务本身有状态流转 → 无脑选状态机**（大多数交易场景都属于这类）；没有状态流转但有唯一业务键 → 用去重表；高频且已有 Redis → 用 `SETNX`。注意 `rows == 0` 时必须**正常 ack 而不是抛异常**——否则会触发无限重试。

## 九、与 RabbitMQ / Kafka 的三方对照（聚焦差异点） {#comparison}

板块导览里有一张完整的三方对比表，这里只补**容易被忽略的那个维度**：**同样的问题，三家给的答案为什么不同**。

| 问题 | RabbitMQ | Kafka | RocketMQ |
|---|---|---|---|
| **不丢消息** | confirm + 持久化 + 手动 ack | `acks=all` + ISR + 手动提交 offset | 同步刷盘 + 主从复制 + 消费 ack |
| **有序** | 单队列单消费者 | 同 key 进同分区 | `MessageGroup` 进同队列 + `ORDERLY` 消费 |
| **幂等** | 消费端自己实现 | 消费端自己实现 | 消费端自己实现（**三家一样**） |
| **延迟消息** | 弱（TTL + 死信 / 插件） | ❌ | ✅ 原生、5.x 任意精度 |
| **事务消息** | ❌ | ❌（幂等生产者 ≠ 分布式事务） | ✅ 半消息 + 回查 |
| **回溯** | ❌ 消费即删 | ✅ 按 offset | ✅ 按时间 |
| **堆积** | ⚠️ 弱（撑内存） | ✅ 强（就是落盘） | ✅ 强（CommitLog 顺序写） |

**选型结论只有一句**：

```text
要"业务解耦 + 低延迟 + 灵活路由"        → RabbitMQ
要"高吞吐 + 可回溯 + 大数据生态"         → Kafka
要"事务消息 + 延迟消息 + 电商交易场景"    → RocketMQ
```

**最值得追问的一层**：为什么只有 RocketMQ 做了事务消息？因为它起家于**阿里的电商交易场景**——"下单要同时写库和发消息"是那里最高频的痛点。**中间件的特有能力都是被特定业务逼出来的**，这比背特性表有用得多。

## 十、常见坑 {#pitfalls}

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 新部署还用 DLedger 模式 | 5.5.1 起已废弃，走 **Controller 模式**（Raft 选主 + 原生 CommitLog） |
| 2 | 用 4.x 的 API 写 5.x 代码 | 5.x 用 `rocketmq-client-java`，与 `rocketmq-client` 是**两套 API**；`rocketmq-spring-boot-starter` 对新客户端的支持仍在完善，很多团队直接引原生 SDK 手动装配 |
| 3 | **5.x 创建 Producer 时必须声明 Topic** | 与 4.x 不同，`setTopics(...)` 是必需的 |
| 4 | 事务消息回查接口不幂等 | 回查会重复触发，返回结果必须幂等 |
| 5 | 回查间隔按默认值硬套 | 间隔要按本地事务耗时定；设太短会打满数据库连接池 |
| 6 | 以为事务消息能替代所有分布式事务方案 | 它只解决"本地事务 + 发消息"的原子性；跨服务复杂事务仍需 Saga / TCC / 本地消息表 |
| 7 | 追求全局有序 | 并发度极低；用**分区有序**（`MessageGroup`） |
| 8 | 顺序消息的消费逻辑里等外部接口 | 一条卡住后面全堵，消费逻辑必须快速失败 |
| 9 | 大量定时消息集中在同一秒 | 加**随机抖动**打散，避免时间轮槽位尖峰 |
| 10 | 幂等拦截时抛异常 | `rows == 0` 应**正常 ack**（视为已消费），抛异常会触发无限重试 |
| 11 | 只按消息 ID 幂等，不按业务键 | 生产端重发可能产生新 MessageId；**幂等键要用业务唯一键** |
| 12 | K8s 环境仍用传统 Push 消费 | 扩缩容触发 rebalance 有停顿；考虑 **Pop 模式**的无状态消费 |
| 13 | 不开消息轨迹 | "消息丢没丢"变成扯皮；开 `enableTrace`，接 Dashboard/ELK |
| 14 | 假设"RocketMQ 性能最好所以都该用它" | 选型先问"需不需要事务消息/延迟消息/回溯"，**不是比参数** |

## 十一、高频问答 {#interview}

| 问题 | 一句话答案 |
|---|---|
| RocketMQ 5.x 与 4.x 最大的区别？ | **计算存储分离**：新增无状态 Proxy 层（gRPC）承担事务/延迟/轨迹逻辑，Broker 专注存储；客户端换成 `rocketmq-client-java` |
| 存储为什么能做到高吞吐？ | **所有 Topic 混写一个 CommitLog、完全顺序追加**，ConsumeQueue 做定长逻辑索引（20 字节）、IndexFile 做 key 查询；避免多文件随机写 |
| ConsumeQueue 为什么必须是定长？ | 定长才能**一次偏移计算直接定位**——随机访问的前提 |
| 5.x 推荐的高可用方案是什么？ | **Controller 模式**：Controller 集群用 Raft 选主 + Broker 仍用原生 CommitLog 同步；比 DLedger 少了 Raft 日志的额外 IO（DLedger 模式 5.5.1 起已废弃） |
| BrokerContainer 解决什么？ | 一个进程跑多个 Broker（主从混合部署），解决传统部署中 **Slave 资源闲置**的问题 |
| 事务消息的完整流程？ | 发**半消息**（对消费者不可见）→ 执行本地事务 → Commit/Rollback；若 Broker 长时间没收到确认则**主动回查**生产者 |
| 为什么需要"半消息"？ | 让"消息已到达 Broker"先于本地事务完成——**先有可回查的东西**。若先提交本地事务再发消息，发消息失败就无法回滚 |
| 回查靠什么判断？ | 生产者**查自己本地事务的状态**（事务表/业务状态字段）——所以本地事务必须有可查记录 |
| 回查要注意什么？ | 接口必须**幂等**（会重复触发）；回查间隔要按本地事务耗时设，太短会打满连接池（默认回查 15 次） |
| 事务消息能解决所有分布式事务吗？ | 不能。只保证"本地事务 + 发消息"的原子性（最终一致）；且**只保证消息不丢，不保证消费一定成功** |
| 顺序消息怎么实现？ | **分区有序**：生产端用 `MessageGroup`/HashKey 把同一业务键路由到同一队列，消费端用 `ORDERLY` 模式串行处理 |
| 全局有序能用吗？ | 并发度等于串行，生产环境基本不用 |
| 顺序消息的代价？ | 一条卡住后面全堵；重试会破坏吞吐。所以消费逻辑必须快速失败 |
| 延迟消息 5.x 有什么改进？ | 从 4.x 的 **18 个固定级别**变成**时间轮 + 任意精度**（`setDeliveryTimestamp`），并支持定时消息 |
| 大规模延迟消息要注意什么？ | 别让消息集中在同一秒投递（时间轮槽位尖峰），要加**随机抖动** |
| 消息重复消费怎么解决？ | 消费端幂等，三种方案：去重表 / Redis `SETNX` / **业务状态机**（有状态流转时首选，幂等与业务合二为一） |
| 幂等拦截后该 ack 还是抛异常？ | **正常 ack**（视为已消费）——抛异常会触发无限重试 |
| 幂等键该用什么？ | **业务唯一键**，不要只用 MessageId——生产端重发可能生成新 ID |
| 为什么只有 RocketMQ 原生支持事务消息？ | 它起家于阿里电商交易场景，"下单同时写库 + 发消息"是那里最高频的痛点——**特有能力都是被特定业务逼出来的** |
| Pop 消费模式解决什么？ | 无状态消费：避免传统 Push 下扩缩容触发 rebalance 的停顿，适配 K8s 弹性伸缩 |
