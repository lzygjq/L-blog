# 顺序性

## 一、问题场景

"用户下单 → 支付 → 发货"三条消息，如果被乱序消费，就会出现**先发货后支付**的业务事故。

**结论先行**：Kafka **只保证单分区内消息有序**，不保证跨分区顺序——因为分区才是它的"有序单元"。所以保证顺序的通用解法只有一条：**把需要有序的消息路由到同一个分区**。常用的三种做法是按 key 哈希（最常用）、指定分区号、单分区 topic，**它们本质都是用吞吐换顺序**。

## 二、为什么 Kafka 不保证全局有序

```
Topic: order（3 个分区）

生产者依次发送：  msg1(order-1)  msg2(order-2)  msg3(order-1)
                       │              │              │
                       ▼              ▼              ▼
                 ┌──────────┐  ┌──────────┐  ┌──────────┐
                 │Partition0│  │Partition1│  │Partition2│
                 │  msg1    │  │  msg2    │  │  msg3    │
                 └──────────┘  └──────────┘  └──────────┘
                       │              │              │
                       ▼              ▼              ▼
                 Consumer A      Consumer B      Consumer C
                 （三个消费者并行处理，谁先处理完不确定）

  → 全局顺序无法保证：msg3 完全可能比 msg1 先被处理
```

**分区是"并行单元"**——并行和数据有序在原理上就是矛盾的。Kafka 选择了并行（因为要吞吐），所以把"有序"限定在**分区内部**：

| 层级 | 是否有序 |
|---|---|
| **单个分区内** | ✅ **有序**（offset 严格递增，追加写入） |
| 跨分区（同一 topic） | ❌ 无序 |
| 跨 topic | ❌ 无序 |

## 三、三种解法

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 相同 key 路由到同一分区**（最常用） | `new ProducerRecord<>(topic, key, value)`，Kafka 对 key 做 hash（`murmur2(key) % 分区数`）决定分区 | **同一业务实体的消息有序，不同实体仍可并行**——最佳平衡 | 需要业务上有天然的分组键（订单 ID、用户 ID） |
| **② 指定分区号** | `new ProducerRecord<>(topic, partition, key, value)` | 简单直接 | 所有需要有序的消息**挤在一个分区**，并行度低；写死分区号后扩容困难 |
| **③ 单分区 topic** | topic 只设 1 个 partition | **绝对全局有序** | **完全失去并行度**——该 topic 的消费只能串行，吞吐极低 |

### 方案① 的原理

```
按 orderId 做 key：
  order-1 的消息 → hash("order-1") % 3 = 0 → 全进 Partition0  → 有序 ✅
  order-2 的消息 → hash("order-2") % 3 = 1 → 全进 Partition1  → 有序 ✅
  同一订单的"下单/支付/发货"永远落在同一个分区，且分区内 offset 递增 → 必然有序

不同订单分散在不同分区 → 仍然并行 ✅
```

**这就是为什么"用订单 ID 做 key"是最常用的答案**——它实现了"**局部有序 + 整体并行**"，是唯一的双赢方案。

### 三种方案的取舍图

```
并行度 高 ┌──────────────────────────────────────────┐
        │  方案① 相同 key 路由（局部有序、整体并行）    │
        │                                          │
        │  方案② 指定分区号（一批有序、其余并行）      │
        │                                          │
        │  方案③ 单分区 topic（全局有序、零并行）      │
        └──────────────────────────────────────────┘
顺序性 强                    →
```

## 四、消费端的乱序（最容易被漏掉的一环）

**即使消息在分区内有序，消费端多线程处理也会乱序**：

```
Partition0 的消息按序投递：  msg1 → msg2 → msg3
                                  │
消费端线程池并行处理 ─────────────┼──────────────▶
  线程 A 拿走 msg1（处理耗时 100ms）
  线程 B 拿走 msg2（处理耗时 5ms）   → msg2 先处理完 ✗ 乱序
  线程 C 拿走 msg3
```

**解决方案：消费端按 key 做内存队列分流**——保证相同 key 的消息由**同一个线程**处理：

```
poll() 拿到一批消息
      │
      ▼
按 key（如 orderId）hash 到 N 个内存队列
      │
      ├── Queue0 (order-1 的消息) ──▶ 线程 A 串行处理
      ├── Queue1 (order-2 的消息) ──▶ 线程 B 串行处理
      └── Queue2 (order-3 的消息) ──▶ 线程 C 串行处理
      
  → 相同 key 串行（有序）、不同 key 并行（吞吐）✅
  → 参考实现：Kafka Streams 的 repartition 操作、或手动用 ConcurrentHashMap + 队列
```

**同时要注意 `max.poll.records`**：一次 poll 太多，处理时间长会触发 **Rebalance**（超过 `max.poll.interval.ms`），分区被收走后重新分配——**处理到一半的消息会被另一个消费者重放**，造成重复甚至乱序。

| 参数 | 作用 |
|---|---|
| `max.poll.records` | 单次 poll 的最大消息数。**调小**可降低单批处理时长，减少 Rebalance 风险 |
| `max.poll.interval.ms` | 两次 poll 的最大间隔（默认 5 分钟），超过则被踢出消费者组触发 Rebalance |

## 五、顺序性与可靠性的冲突（高分点）

这里有一个**很多人不知道的矛盾**：

```
未开启幂等生产者时：
  max.in.flight.requests.per.connection > 1
  → 生产者可以同时发出多个未确认请求
  → 如果第 1 个请求失败、第 2 个成功，重试第 1 个后
  → Broker 端的顺序变成： msg2, msg1  ✗ 乱序！
```

**解法有三条**（按推荐度）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **开启幂等生产者**（推荐） | `enable.idempotence=true` | 几乎无代价，还会**强制 `acks=all`**，可靠性也一起提升；Kafka 保证 `max.in.flight≤5` 时的顺序 |
| **限制在途请求为 1** | `max.in.flight.requests.per.connection=1` | ✅ 保证顺序，但**吞吐显著下降**（无法流水线发送） |
| 关闭重试 | `retries=0` | ❌ 保证顺序但**牺牲可靠性**（丢消息），不推荐 |

> **所以"要顺序 + 要可靠 + 要高吞吐"的正解是：开启幂等生产者。** 它一举解决重复和乱序，且不牺牲吞吐——**这是 Kafka 0.11 引入幂等生产者最有价值的地方，也是这道题的最佳答法**。

## 六、面试问答

**Q1：Kafka 如何保证消息顺序性？**

首先要明确 **Kafka 只保证单个分区内的消息有序**，不保证跨分区的全局顺序——因为**分区是并行单元，并行与有序天然矛盾**，Kafka 为了吞吐选择了分区并行，所以把"有序"限定在分区内部（分区内 offset 严格递增、追加写入）。所以要保证顺序，思路就是**把需要有序的消息发送到同一个分区**，具体三种做法：① **指定相同 key**（最常用）——发送时用业务 ID（如 `orderId`）作为 key，Kafka 对 key 做 hash 决定分区，**相同 key 一定进同一分区**，这样同一订单的"下单/支付/发货"必然有序，而不同订单分散在不同分区仍然并行；② **直接指定分区号**——`ProducerRecord(topic, partition, value)`，简单但所有顺序消息挤一个分区，并行度低；③ **单分区 topic**——完全有序但彻底失去并行度。**另外还要注意消费端**：如果消费端开了多线程，同一个分区的消息也可能被不同线程并发处理导致乱序，需要在消费端**按 key 做内存队列分流**，保证相同 key 的消息由同一线程串行处理。

**Q2：为什么 `max.in.flight.requests.per.connection > 1` 会影响顺序？**

因为它允许生产者在**前一个请求还没确认时**就发送下一个请求。假设在途数大于 1：msg1 和 msg2 同时发出，如果 **msg1 发送失败而 msg2 成功**，生产者会重试 msg1——重试的 msg1 到达 Broker 时排在 msg2 之后，于是 **Broker 端的存储顺序变成 msg2、msg1，乱序了**。解法有三条：① **开启幂等生产者**（`enable.idempotence=true`）——最佳方案，Broker 按 PID + 序列号丢弃重复消息，乱序窗口被消除，而且几乎不影响吞吐，还会强制 `acks=all` 顺带提升可靠性；② 把 `max.in.flight.requests.per.connection` 设为 **1**——保证顺序，但无法流水线发送，**吞吐明显下降**；③ 关闭重试——牺牲可靠性，不推荐。

**Q3：消费端多线程为什么会导致乱序？怎么解决？**

因为**分区内有序只保证了消息的"投递顺序"，不保证"处理完成顺序"**。消费端如果用一个线程池并行处理同一批消息，msg1 的处理逻辑耗时 100ms、msg2 只耗时 5ms，那么 **msg2 会先处理完**——从业务视角看就是乱序。解决方案是**按 key 做内存队列分流**：`poll()` 拿到消息后，按业务 key（如 `orderId`）哈希到 N 个内存队列，每个队列由**固定一个线程**串行消费。这样相同 key 的消息天然串行（有序），不同 key 走不同队列（并行）。Kafka Streams 里的 `repartition`、或手动用 `ConcurrentHashMap<key, Queue>` + 线程池都是这个思路。

**Q4：为了保证顺序，能不能把 topic 设成单分区？**

技术上可以，但**实践中不推荐**——单分区意味着**彻底失去并行度**：该 topic 的所有消息只能由一个消费者串行处理，吞吐极低，也失去了 Kafka 水平扩展的能力。而且分区数在 Kafka 中**只能增加不能减少**，一旦后续要扩分区，key 到分区的映射关系会改变（`hash(key) % 新分区数`），**原本在同一分区的消息会被打散，顺序性被破坏**。所以正确做法是**用多分区 + 相同 key 路由**：既保证同一业务实体的顺序，又保留不同实体之间的并行度。

**Q5：分区数增加了，原来的顺序还保得住吗？**

**保不住**。Kafka 用 `murmur2(key) % 分区数` 计算目标分区，**分区数变了，同一个 key 算出来的分区号就可能变**。所以扩容分区后，**新增的消息可能落到与之前不同的分区**，同一个订单的旧消息和新消息不再处于同一分区，分区内有序也就无从谈起。这是"按 key 保证顺序"方案的固有局限，实践中要规避的话有两种思路：① **一次性规划足够多的分区**（如 32 个），后续不再变更；② 对顺序要求极高的业务，**接受顺序键在扩容后失效**，用业务侧的状态机或版本号兜底（比如订单状态带版本号，消费端只接受更高版本，天然忽略乱序带来的旧状态）。
