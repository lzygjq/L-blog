# 高性能设计

## 一、问题场景

同样是"把消息写磁盘再让消费者读走"，RabbitMQ 吞吐是**万级**，Kafka 是**十万级**。差距不在"用了什么高深算法"，而在**六个工程层面的设计选择**。

**结论先行**：Kafka 高性能靠**六个设计**——**分区并行、顺序写磁盘、Page Cache、零拷贝、消息压缩、分批发送**。其中**最核心的是"顺序写"和"零拷贝"**：前者把磁盘从"随机写 100KB/s"提升到"顺序写 100MB/s"（快约 1000 倍），后者把消费读取路径的**拷贝次数从 4 次降到 2 次、上下文切换从 4 次降到 2 次**。

## 二、六个设计点

| # | 设计 | 原理 | 收益 |
|---|---|---|---|
| 1 | **消息分区** | topic 分多个 partition，分布在不同 Broker，**并行读写** | 突破单机限制，可水平扩展 |
| 2 | **顺序读写** | 消息**追加写入**磁盘文件末尾 | 顺序写比随机写**快约 100 倍** |
| 3 | **Page Cache** | 利用 OS 的页缓存，写先写页缓存异步刷盘、读命中页缓存直接返回 | 把磁盘访问变成内存访问 |
| 4 | **零拷贝** | 消费者读消息用 `sendfile()`，数据**不经过用户空间** | 省掉 2 次拷贝 + 2 次上下文切换 |
| 5 | **消息压缩** | 生产者批量压缩（snappy / lz4 / gzip / zstd） | 减少磁盘 IO 和网络 IO |
| 6 | **分批发送** | 生产者把消息打包成 batch 批量发送 | 大幅减少网络请求次数 |

### ① 分区并行

```
        Topic: order（6 个分区，分布在 3 个 Broker）
        
Broker1: [P0] [P1]        Broker2: [P2] [P3]        Broker3: [P4] [P5]
            ▲                  ▲                        ▲
            └──────────────────┴────────────────────────┘
                    生产者/消费者可并行操作 6 个分区

→ 吞吐随分区数近似线性增长（受 Broker 资源上限约束）
→ 这也是"分区数决定最大消费并行度"的原因
```

### ② 顺序写磁盘（最关键的一条）

**机械硬盘上一个常被引用的量化对比**：

| 写入方式 | 速度 | 原因 |
|---|---|---|
| **顺序写** | **~100 MB/s** | 磁头无需寻道，连续写入 |
| **随机写** | **~100 KB/s** | 每次都要寻道 + 旋转等待（机械盘寻道是毫秒级） |

**差距约 1000 倍。** Kafka 的做法极简：**消息只追加到文件末尾，永不修改已有数据**。

```
partition 目录下的 segment 文件：
  ┌──────────────────────────────────────────────┐
  │ msg0 │ msg1 │ msg2 │ msg3 │ msg4 │ ... │ (追加) │
  └──────────────────────────────────────────────┘
     ↑                                          ↑
   只读不动                                   write pointer 追加
```

> **为什么 Kafka 能"永不修改"**：因为消息是**不可变（immutable）**的——它只记录"发生过什么"，不记录"当前状态"。这也是它能支持**任意回溯**的根本原因（见[存储与清理](/middleware/kafka/storage)）。

**顺带一个结论**：**即使是 SSD，顺序写也优于随机写**（虽然差距没机械盘那么夸张），因为顺序写能更好地利用预读和写合并。

### ③ Page Cache（页缓存）

**Kafka 几乎不自己管理缓存，而是把这件事交给了操作系统**：

```
生产者写：
   消息 ──▶ 写入 【Page Cache（内核页缓存）】──▶ 返回成功（快）
                    │
                    └─ OS 异步刷盘（由内核决定时机）

消费者读：
   要读的消息在 Page Cache 里？ ── 是 ──▶ 直接从内存返回（快）✅
                                └─ 否 ──▶ 从磁盘读入 Page Cache 再返回
```

| 收益 | 说明 |
|---|---|
| **写快** | 只写内存即返回，不等磁盘 IO |
| **读快** | 热数据（刚写入或刚消费过的）大概率命中页缓存 |
| **省内存** | **Kafka 进程本身不占大量堆内存**——内存都给了 OS 页缓存，且**进程重启后页缓存依然有效** |

> **对比 JVM 堆内缓存的优势**：如果把数据缓存在 JVM 堆里，① 对象头开销大（同样的数据占更多内存）；② GC 压力大；③ **进程重启缓存全丢**。而 Page Cache 对这三个问题天然免疫。**"把缓存交给 OS"是 Kafka 一个很聪明的架构取舍。**

### ④ 零拷贝（面试最爱问）

**先看传统方式的读取路径**（把磁盘文件通过 socket 发给消费者）：

```
传统 read + write（4 次拷贝 + 4 次上下文切换）

  磁盘 ──① DMA拷贝──▶ 内核缓冲区(Page Cache)
                              │
                        ② CPU拷贝
                              ▼
                        用户空间缓冲区（应用程序）
                              │
                        ③ CPU拷贝
                              ▼
                        Socket 缓冲区（内核）
                              │
                        ④ DMA拷贝
                              ▼
                            网卡
```

| 开销 | 次数 |
|---|---|
| 数据拷贝 | **4 次**（2 次 DMA + 2 次 CPU） |
| 上下文切换 | **4 次**（read/write 各两次：用户态↔内核态） |

**Kafka 用 `sendfile()` 系统调用（零拷贝）**：

```
零拷贝 sendfile（2 次拷贝 + 2 次上下文切换）

  磁盘 ──① DMA拷贝──▶ 内核缓冲区(Page Cache)
                              │
                        ② CPU拷贝（仅描述符/偏移量，数据本身不搬）
                              ▼
                        Socket 缓冲区
                              │
                        ③ DMA拷贝
                              ▼
                            网卡
        ★ 数据【从未进入用户空间】
```

| 开销 | 传统方式 | **零拷贝** |
|---|---|---|
| 数据拷贝 | 4 次 | **2 次**（且省掉 2 次 CPU 拷贝） |
| 上下文切换 | 4 次 | **2 次** |
| 数据是否进用户空间 | 是 | **否** |

**"零拷贝"这个名字的含义**：**不是真的零次拷贝**（DMA 拷贝省不掉），而是**"不经过用户空间的拷贝"**——省掉的是那两次 CPU 参与的、最昂贵的内存拷贝。

> **前提条件**：零拷贝要求**数据直接从文件传到网络**，不需要在应用层修改内容。所以 Kafka 的优化是：**发送时不修改消息体**（消息在 broker 端是原样转发的），这样才用得上 `sendfile`。如果 broker 需要解密、格式转换，零拷贝就用不上了——这也是为什么 Kafka 的消息压缩是**生产者压缩、消费者解压**（broker 端不碰数据）。

### ⑤ 消息压缩

| 算法 | 压缩比 | 速度 | 特点 |
|---|---|---|---|
| **`lz4`** | 中 | **最快** | Kafka 默认推荐，兼顾速度与压缩比 |
| `snappy` | 中 | 快 | 常用，Google 出品 |
| `gzip` | **高** | 慢 | 压缩比好但 CPU 开销大，适合带宽紧张 |
| `zstd` | 高 | 中 | Kafka 2.1+ 支持，压缩比接近 gzip 但更快，**新项目首选** |

```java
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");
props.put(ProducerConfig.LINGER_MS_CONFIG, 20);        // 等 20ms 凑批
props.put(ProducerConfig.BATCH_SIZE_CONFIG, 32 * 1024); // 批大小 32KB
```

**关键点：压缩是"按批"进行的**——所以**批越大，压缩效果越好**（相同内容有更多重复模式可压）。这也是"分批发送"能进一步提升压缩比的原因。

**同时降低两种 IO**：压缩后的消息 ① 写磁盘更少 → 减少**磁盘 IO**；② 发给消费者时网络传输更少 → 减少**网络 IO**。

### ⑥ 分批发送

```
逐条发送：  send(msg1) → 网络往返 → send(msg2) → 网络往返 → ...
                       ↑ 每条都有 RTT 和协议开销

分批发送：  send(msg1) ┐
            send(msg2) ├─ 攒成一批 → 一次网络往返 → Broker
            send(msg3) ┘
                       ↑ 请求次数从 N 降到 1
```

| 参数 | 作用 |
|---|---|
| `batch.size` | 单个批次的最大字节数（默认 16KB）。**调大可提升吞吐**（更好的压缩 + 更少请求） |
| `linger.ms` | 发送前等待攒批的时间（默认 0）。**设为 5~100ms 可显著提升批量效果**，代价是延迟增加 |
| `buffer.memory` | 生产者端缓冲区总大小，满了会阻塞发送 |

> **`linger.ms` 的取舍**：默认 0 表示"有消息就立即发"，延迟最低但批量效果差。**设为 20ms 意味着"最多等 20 毫秒凑批"**——延迟增加 20ms，换来的吞吐提升通常远超预期。**这是典型的"延迟换吞吐"，也是 Kafka 延迟高于 RabbitMQ 的原因之一。**

## 三、六个设计的收益归因

```
        吞吐瓶颈在三处：磁盘 IO、网络 IO、CPU

  顺序写磁盘  ──── 解决【磁盘随机 IO】
  Page Cache  ──── 解决【磁盘 IO】（把磁盘访问变内存访问）
  零拷贝      ──── 解决【CPU 拷贝 + 上下文切换】
  消息压缩    ──── 同时减少【磁盘 IO】和【网络 IO】
  分批发送    ──── 减少【网络往返次数】，并让压缩更有效
  分区并行    ──── 突破【单机上限】（横向扩展）

  → 磁盘、网络、CPU 三个瓶颈被同时削弱，这才是十万级吞吐的来源
```

## 四、面试问答

**Q1：Kafka 为什么性能那么高？**

主要有六个原因。① **分区并行**——topic 分成多个 partition 分布在不同 Broker 上，可以并行读写，不受单机限制。② **顺序写磁盘**——消息都是**追加写入**文件末尾，机械盘上顺序写约 100MB/s 而随机写只有约 100KB/s，**快约 1000 倍**。③ **Page Cache（页缓存）**——利用操作系统的页缓存，写操作先写页缓存再异步刷盘，读操作命中页缓存就直接返回，把磁盘访问变成了内存访问；而且 Kafka 自己不用 JVM 堆做缓存，**没有 GC 压力，进程重启后缓存依然有效**。④ **零拷贝**——消费者读消息时用 `sendfile()` 系统调用，数据从页缓存直接送到网卡，**不经过用户空间**，把拷贝从 4 次降到 2 次、上下文切换从 4 次降到 2 次。⑤ **消息压缩**——生产者批量压缩（snappy/lz4/gzip/zstd），同时减少磁盘 IO 和网络 IO。⑥ **分批发送**——生产者把消息打包成 batch 批量发送，大幅减少网络请求次数，而且**批越大压缩效果越好**。**其中顺序写和零拷贝是最核心的两个。**

**Q2：零拷贝省掉了哪几次拷贝？**

传统方式用 `read()` + `write()` 要经历 **4 次数据拷贝和 4 次上下文切换**：磁盘 →（DMA 拷贝）→ 内核缓冲区（Page Cache）→（CPU 拷贝）→ **用户空间缓冲区** →（CPU 拷贝）→ Socket 缓冲区 →（DMA 拷贝）→ 网卡。Kafka 用 **`sendfile()`** 后变成 **2 次拷贝和 2 次上下文切换**：磁盘 →（DMA 拷贝）→ 内核缓冲区 →（只拷贝描述符/偏移量）→ Socket 缓冲区 →（DMA 拷贝）→ 网卡。**关键差别是数据从未进入用户空间**，省掉的是那两次 CPU 参与的内存拷贝。**注意"零拷贝"不是字面无拷贝**——DMA 拷贝无法省略，它真正的含义是"**零次用户空间拷贝**"。

**Q3：零拷贝有什么前提条件？**

**数据必须能直接从文件传输到网络，不能在应用层被修改。** 因为 `sendfile` 是"内核直接把页缓存的数据发到网卡"，应用程序在这个过程中**碰不到数据**，自然也无法解密、转换格式或修改内容。所以 Kafka 的架构配合是：**Broker 端不修改消息体，原样转发**；压缩由**生产者压缩、消费者解压**（Broker 只存压缩后的数据）。如果 Broker 需要解密或格式转换（比如做消息路由改写），就用不上零拷贝了——这也解释了为什么 Kafka 的 Broker 功能"很薄"，它刻意不做影响零拷贝的加工。

**Q4：`linger.ms` 有什么作用？设大了有什么影响？**

`linger.ms` 控制**发送前等待攒批的时间**。默认是 **0**，意思是"有消息就立刻发"，延迟最低但批量效果差、网络请求次数多。把它设为 **5~100 毫秒**，生产者会等这段时间把更多消息凑成一个批次再发，**显著提升吞吐**——因为 ① 网络请求次数大幅减少；② **批越大，压缩比越高**（相同内容有更多重复模式）。代价是**每条消息的延迟增加了这段时间**。所以这是典型的**延迟换吞吐**的取舍：实时性要求高就设小（或 0），追求吞吐就设大。

**Q5：Kafka 为什么不用 JVM 堆内存做缓存？**

因为它把缓存交给了**操作系统的 Page Cache**，这样有三个优势：① **没有 GC 压力**——JVM 堆上大量对象会带来频繁 GC，影响稳定性；② **内存利用率高**——JVM 对象有对象头等额外开销，同样的数据在堆里占的内存更多；而页缓存是紧凑的字节存储；③ **进程重启缓存不丢**——页缓存属于操作系统，Kafka 进程重启后**热数据还在页缓存里**，能立即恢复读取性能；而堆内缓存重启就全没了。另外页缓存还有一个隐性好处：写入时只写页缓存就返回，由 OS 异步刷盘，**把随机的磁盘写合并成顺序写**，进一步减少 IO。

**Q6：为什么压缩要在生产者端做？**

两个原因。① **为了保住零拷贝**——如果 Broker 端要做压缩/解压，就必须把数据读进用户空间处理，**`sendfile` 零拷贝就用不上了**，性能会大幅回退；让生产者压缩、消费者解压，Broker 只是"原样存、原样转"，才能一直走零拷贝路径。② **压缩本来就是"批量"操作，生产者端最有优势**——生产者是攒批发送的，能利用整批数据的重复模式做更好的压缩；而且压缩在客户端做，把 CPU 开销**分散到了各个生产者机器**，避免了 Broker 成为 CPU 瓶颈。**一句话：压缩放在端上，Broker 保持"薄"，才能同时拿到零拷贝和低 Broker 负载。**
