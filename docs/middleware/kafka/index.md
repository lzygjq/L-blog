# Kafka · 导览

Kafka 严格来说**不是一个"消息队列"，而是一个分布式流平台**。这个定位差别决定了它的所有设计取舍：它把消息当作**可重放的事件日志**，而不是"消费完就删的临时数据"。

**结论先行**：Kafka 的核心竞争力是 **高吞吐 + 可回溯 + 水平扩展**，代价是**功能比 RabbitMQ 单薄**（没有原生的延迟队列、死信队列、事务消息）。理解 Kafka 只要抓住三个概念——**分区（并行单元）、副本与 ISR（可靠单元）、offset（消费进度）**。

## 一、核心概念

```
                        ┌──────────── Topic: order ────────────┐
                        │                                      │
   Producer ──▶  ┌──────▼──────┐   ┌─────────────┐   ┌─────────────┐
   按 key hash    │ Partition 0 │   │ Partition 1 │   │ Partition 2 │
   决定分区        │ (Leader)    │   │ (Leader)    │   │ (Leader)    │
                 │  ├ Follower │   │  ├ Follower │   │  ├ Follower │
                 │  └ Follower │   │  └ Follower │   │  └ Follower │
                 │ offset 0,1,2│   │ offset 0,1,2│   │ offset 0,1,2│
                 └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
                        │                 │                 │
                        └────────┬────────┴────────┬────────┘
                                 ▼                 ▼
                        Consumer Group A    Consumer Group B
                        （组内一个分区只给    （不同组各消费一份，
                          一个消费者 →        消息不被"抢走"）
                          组内并行、不重复）
```

| 概念 | 说明 | 关键点 |
|---|---|---|
| **Broker** | 一个 Kafka 服务节点 | 集群由多个 Broker 组成 |
| **Topic** | 逻辑上的消息分类 | 只是逻辑概念，**物理上由多个 Partition 组成** |
| **Partition** | **分区**，物理上一个目录 | **Kafka 的并行单元**：分区数决定最大消费并行度 |
| **Replica** | 每个分区的副本（默认 3） | **可靠单元**：分布在不同的 Broker 上 |
| **Leader / Follower** | 只有 Leader 对外读写，Follower 只同步 | **读写都走 Leader**（这一点常被误解为"从 Follower 读"） |
| **ISR** | In-Sync Replicas，与 Leader 保持同步的副本集合 | **选主只从 ISR 中选**，这是不丢数据的关键 |
| **Offset** | 消息在分区内的唯一递增编号 | **消费进度就是 offset**；可由消费者自己控制、可回溯 |
| **Consumer Group** | 消费者组 | **同一组内一个分区只被一个消费者消费**；不同组各消费一份 |

### 三个必须先建立的认知

**① 并行单元是分区，不是消费者**

```
Topic 有 3 个分区，消费者组有 5 个消费者实例
  → 只有 3 个实例能分到分区，另外 2 个【空闲】
  → 结论：分区数决定了消费并行度上限，加实例超过分区数没有意义
```

**② 顺序性只保证"单分区内有序"**

跨分区没有顺序可言。需要有序的消息必须靠 **相同 key 路由到同一分区**（见[顺序性](/middleware/kafka/ordering)）。

**③ 消息不会因为被消费就删除**

这是与 RabbitMQ 最本质的差别：

| | RabbitMQ | **Kafka** |
|---|---|---|
| 消费后 | **立即删除** | **保留**（按时间/大小清理） |
| 能否重新消费历史消息 | ❌ 不能 | ✅ **可以**（改 offset 即可回溯） |
| 堆积 | ⚠️ 撑内存 | ✅ **堆积就是落盘**，天然支撑海量 |

> **"可回溯"派生出的能力**：新增一个下游消费者时，可以让它**从头消费历史数据**（如新建的数据仓库要导入全量历史）——这在 RabbitMQ 上做不到。这也是 Kafka 能当"流平台"而不只是"MQ"的原因。

## 四、与 RabbitMQ 的取舍

| 维度 | RabbitMQ | Kafka |
|---|---|---|
| 吞吐 | 万级 | **十万级** |
| 延迟 | **微秒级** | 毫秒级（pull + 批量） |
| 消费模型 | push | **pull**（消费者主动拉，可控速） |
| 回溯历史 | ❌ | ✅ |
| 堆积能力 | ⚠️ 弱 | ✅ **强** |
| 延迟/死信 | ✅ 原生丰富 | ❌ 需自建 |
| 事务消息 | ❌ | ❌（只有幂等生产者） |
| 路由灵活度 | ✅ **Exchange 四种类型** | ❌ 只有 topic + key |

**一句话选型**：

```
业务解耦、需要延迟/死信、量不大        → RabbitMQ
日志采集、埋点、流处理、需要回溯、高吞吐 → Kafka
```

完整对比见[消息队列板块导览](/middleware/)。
