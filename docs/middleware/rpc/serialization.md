# 序列化与 IDL：体积、速度与兼容性从哪里来

RPC 的第 3 条失效假设是"参数传的是引用"——跨进程只能传值，于是必须把对象变成字节，再在另一端还原。这一步叫序列化，它看起来只是"编码解码"，实际却同时决定了一件事的三面：**网络带宽、CPU 开销、以及版本升级时会不会炸**。

> **序列化方案没有"最好的"，只有"在这个场景下牺牲了哪几项"。**
>
> 评价它的五个维度是：**体积、速度、跨语言、兼容性（版本演进）、安全**。市面上的方案，没有一个能在五项上同时拿满分——**选型就是在回答"我最不能牺牲哪一项"**。

## 一、序列化到底要同时满足哪五件事 {#what}

| 维度 | 具体含义 | 不满足会怎样 |
|---|---|---|
| **体积** | 编码后的字节数 | 带宽成本、慢网络下的延迟放大 |
| **速度** | 序列化 + 反序列化的耗时 | 高 QPS 下成为 CPU 瓶颈 |
| **跨语言** | 非 JVM 语言能否读写 | 异构系统间无法通信；引入新语言要重写 |
| **兼容性** | **加 / 删 / 改字段后新旧程序能否互通** | 发版即故障——这是最贵的代价，因为它只在升级时暴露 |
| **安全** | 反序列化不可信数据是否可能执行代码 | 远程代码执行（RCE）漏洞 |

**为什么会有"兼容性"这一维？** 因为分布式系统**不存在"同时发版"**——灰度期间新旧版本必然共存，你无法让全世界的消费者和提供者在同一毫秒切换。所以：

> **序列化协议必须能容忍"一端认识这个字段、另一端不认识"。** 这不是"优化"，是**上线的前提条件**。

**为什么会有"安全"这一维？** 因为反序列化本质上是"**用一段外部字节流去构造一个对象**"。如果协议的语义允许字节流里携带"类的全限定名 + 字段值"，那么攻击者就能构造出一个"构造函数有副作用"的对象，让**反序列化这个动作本身**执行代码。JDK 原生序列化、Hessian、部分 JSON 库的历史漏洞都属于这一类（详见[第七节](#security)）。

## 二、五类主流方案的横向对照 {#five-families}

| 维度 | **JDK 原生** | **JSON**（Jackson / Gson） | **Hessian2** | **Protobuf / Thrift** | **Kryo / FST** |
|---|---|---|---|---|---|
| 编码形态 | 二进制 + 类元信息 | 文本 | 二进制、**自描述** | 二进制、**需 schema** | 二进制、**依赖类结构** |
| 是否需 IDL | 否 | 否 | 否 | **是**（`.proto` / `.thrift`） | 否 |
| 体积 | **最大**（含类描述与继承链） | 大（字段名重复 + 文本） | 中 | **最小** | **最小** |
| 速度 | 慢 | 中（解析成本高） | 快 | **快** | **最快** |
| 跨语言 | ❌ 仅 JVM | ✅ 最好 | ⚠️ 实现少，实际以 Java 为主 | ✅ 官方多语言 | ❌ 仅 JVM |
| 可读性 / 调试 | 差 | **最好**（抓包直接看） | 差 | 差（可用 `protoc --decode`） | 差 |
| 兼容性 | 脆弱（`serialVersionUID` 一变就炸） | **好**（跳过未知字段） | 好（自描述、字段带类型） | **最好**（只认编号 + 未知字段保留） | **最差**（类结构变即崩） |
| 安全 | **最差**（历史 RCE 重灾区） | 中（`defaultTyping` 时危险） | 中（有历史漏洞） | **最好**（有 schema，不可能任意类） | 中 |
| 典型用途 | 已淘汰，**生产禁用** | 对外 API、缓存值、日志 | Dubbo 老项目默认 | gRPC、跨语言内部调用、大数据 | 纯 Java 极致性能场景 |

**几处必须记住的细节**：

- **JSON 的"可读"是有代价的**：字段名要跟着每一份报文传输，`{"userName":"zhang"}` 里 `userName` 这 8 个字符是纯开销；而 Protobuf 传的是字段编号，**只在编译期存在名字**。
- **Hessian2 的自描述带来兼容性，也带来体积**：它在字节流里写字段类型与顺序信息，所以**不需要 IDL 就能加字段**（这是它在 Dubbo 里成为默认值的核心原因），代价是体积比 Protobuf 大。
- **Kryo 快是因为"什么都不写"**：它假定两端**类结构完全一致**，只写字段值甚至只写序号。所以它最快最小，也最容易在发版时炸——**用它必须配注册顺序稳定 + 两版本同时上线**。
- **Protobuf 是五个维度里唯一"四项高分"的**：体积、速度、跨语言、安全都好，唯一的门槛是**要写 IDL、要跑代码生成**（这也是它的"不灵活"之处）。

> **一句话选型**：对外用 JSON，跨语言内部用 Protobuf，纯 Java 内部且不想写 IDL 用 Hessian2，追求极致性能且能控制发版用 Kryo——**JDK 原生序列化任何场景都不要用**。

## 三、Protobuf 为什么又小又快 {#protobuf}

先把结论说清楚：**它的优势不是"压缩算法好"，而是"从编码的第一天起就不传输字段名，并且用小整数表示常用信息"**。

一条 Protobuf 消息在字节层是这样排的（这就是所谓 tag-length-value, TLV）：

```text
┌──────────────┬─────────────────────┬──────────────┬─────────────────────┬───
│  tag (1 字节) │ value（变长/定长）    │  tag (1 字节) │ value               │
└──────────────┴─────────────────────┴──────────────┴─────────────────────┴───
     ↑ 高 5 位 = field number，低 3 位 = wire type
```

两个关键设计：

**① tag 而不是字段名。** `tag = (field_number << 3) | wire_type`。字段 `userName = 1` 上线后就是**一个字节 `0x0A`**，而不是 8 个字符。字段名只活在 `.proto` 与生成的代码里。

**② varint 表示整数。** 数值越小占字节越少：`1`～`127` 占 1 字节，`128`～`16383` 占 2 字节。所以：

| 实践 | 原因 |
|---|---|
| **把频繁出现的字段分配 1～15 号** | 1～15 的字段号能塞进 **1 字节** tag；16 之后 tag 要 **2 字节**——**字段号本身就是成本** |
| `sint32` / `sint64` 用于负数 | `int32` 的负数会被编码成**5 字节**（补码全是 1，varint 最坏情况）；`sint` 用 zigzag 把 `-1, 1, -2, 2...` 映射成 `1, 2, 3, 4...` |
| `fixed32` / `fixed64` 用于大数或定长场景 | 绕过 varint，避免大数值的字节膨胀 |
| `repeated` 用 packed 编码 | 数值型数组打包成一条 length-delimited，省掉每个元素的 tag |

**wire type 的四种取值**（决定了 value 怎么读）：

| wire type | 含义 | 对应类型 |
|---|---|---|
| 0 | varint | `int32` / `int64` / `uint32` / `uint64` / `sint*` / `bool` / `enum` |
| 1 | 64 位定长 | `fixed64` / `sfixed64` / `double` |
| 2 | length-delimited | `string` / `bytes` / **嵌套 message** / packed `repeated` |
| 5 | 32 位定长 | `fixed32` / `sfixed32` / `float` |

**这就解释了为什么"改类型"要小心**：如果 wire type 从 0 变成 2（如 `int32` 改成 `string`），另一端的解析会直接错位——因为**它不知道后面该读几个字节**。

> **一个必须知道的 proto3 陷阱（field presence）**：proto3 早期**所有字段都是"隐式存在"**——值为默认值（0 / `""` / `false`）时**不会被序列化**。于是接收方**无法区分"对方显式传了 0"和"对方根本没设置"**。官方后来把 `optional` 关键字加了回来（即显式 presence），需要区分这两种情况时必须显式声明 `optional`（或用 `wrapper` 类型）。**这个坑在"部分更新"语义的接口上会直接导致数据被误清空。**

## 四、IDL 的价值：把契约检查从运行期提到编译期 {#idl}

`.proto` 文件带来的东西不只是代码生成：

| | **无 IDL**（Java 接口 / JSON） | **有 IDL**（Protobuf / Thrift） |
|---|---|---|
| 契约载体 | Java 接口（**双方必须依赖同一个 jar**） | `.proto` 文本（**双方各自生成**） |
| 不一致时何时暴露 | **运行期**——发版后调用才报错 | **编译期**——`protoc` 生成时就对不上 |
| 跨语言 | 不可能（契约是 Java 类型） | **天然**（15+ 语言的生成器） |
| 契约演进 | 靠"共享 jar 同步升级"这种纪律 | 由**协议规则**保证（编号 + 未知字段保留） |
| 版本管理的成本 | 高（共享 jar 是隐性耦合物） | 低（`.proto` 可以独立版本化） |

**"共享 jar"为什么是问题？** 把接口与 DTO 打成一个 `api.jar` 让双方依赖，看起来最省事，但它造成了两个后果：**① 任何一方改一个字段，双方都得重新发版（哪怕对方根本不用这个字段）；② jar 版本不一致时，错误只在运行期以"类找不到 / 字段缺失"的形式暴露**。跨团队时，这个隐性耦合往往比性能问题更早把项目拖垮。

> **IDL 的真正价值是"把接口当成可独立演进的协议"。** 这一点在跨语言、跨团队、跨版本时尤其明显——它是"**契约先行**"在 RPC 层的具体形态。

## 五、演进红线：改字段的五种操作 {#evolution}

这是序列化里**唯一会在生产上造成事故**的部分。以 Protobuf 为例（其他 schema 类协议规则类似）：

| 操作 | 是否安全 | 原因与正确做法 |
|---|---|---|
| **新增字段** | ✅ **安全** | 旧程序会把它当"未知字段"跳过（proto3 也会**保留**未知字段，再次序列化时原样带回） |
| **删除字段** | ✅ 安全，**但必须 `reserved`** | 删字段本身没问题（旧数据里的该字段被忽略）；**危险的是"以后有人复用了这个编号"**——新字段会读到旧数据的字节，静默错乱。所以删字段的规范动作是**同时写 `reserved 2;` / `reserved "old_name";`** |
| **改字段名** | ✅ 安全 | **名字不上线**，wire 格式里只有编号。改名字只影响代码可读性（JSON 映射除外） |
| **改字段编号** | ❌ **破坏性** | 等价于"删掉一个 + 新增一个"，双方数据全错 |
| **改字段类型** | ⚠️ **看情况** | wire type 相同的变长整数之间（如 `int32`→`int64`）通常兼容（但有截断与负数编码问题）；**wire type 变了（如 `int32`→`string`）必然错位** |

**"向前兼容"与"向后兼容"这两个词千万别混**——面试里答反了会显得没想清楚：

| 术语 | 含义（记忆锚点：**站在"新代码"的视角**） |
|---|---|
| **向后兼容**（backward） | **新代码能读旧数据** —— 加字段属于此类（新代码读老报文，缺的字段用默认值） |
| **向前兼容**（forward） | **旧代码能读新数据** —— 依赖"未知字段被跳过"（旧代码读新报文，多的字段被忽略） |

Protobuf 官方给的安全演化规则可以总结成一句：**"编号是永久的，名字是自由的，删除要留痕（`reserved`）"**。

## 六、Dubbo 的序列化：默认值、协商升级与安全检查 {#dubbo-serialization}

Dubbo 侧的三个事实（官方文档口径，按 2026-09）：

**① 默认值取决于协议，不是全局一个：**

| 协议 | 默认序列化 | 说明 |
|---|---|---|
| **`dubbo`**（TCP，20880，**发行版默认**） | **Hessian2** | 官方文档称其"兼容性好、性能高、跨语言"，是 dubbo 协议的默认序列化 |
| **`triple`** + IDL 模式（HTTP/2，50051） | **Protobuf** | 走 `.proto` 的强类型路径 |
| **`triple`** + Java 接口模式 | **Protobuf-wrapper** | 先用 Hessian 序列化再套一层 Protobuf，**性能略降**换来与 Java 接口写法等价 |

**② 升级序列化要靠"协商"，不能硬切（3.2.0 起）。** 直接改服务端序列化会让老客户端解不开，所以引入了 `prefer-serialization`：

```properties
# 服务端：新协议在前，旧协议兜底
dubbo.provider.prefer-serialization=fastjson2,hessian2
dubbo.provider.serialization=hessian2
```

原理是**客户端按服务端注册的配置选序列化方式**，并把选择写进请求头；服务端按请求头决定用哪种反序列化。生效有两个硬前提：**双方都 ≥ 3.2.x，且都引入了对应的序列化实现包**（缺依赖会继续用旧协议，某些场景直接报错）。

**③ 反序列化有类检查，且 3.2 起默认是 STRICT。** 3.1.6 引入类检查机制（类似黑白名单），覆盖 **Hessian2、Fastjson2 与泛化调用**；检查级别 3.1 默认 `WARN`，**3.2 起默认 `STRICT`**（拒绝反序列化非白名单类）。所以"升级 Dubbo 后突然报类检查失败"，通常不是 bug，而是**生产上反序列化了一个不该反序列化的类**——先看那个类该不该进[白名单](#security)，再决定是放行还是改设计。

> **一条实践纪律**：**Provider 与 Consumer 的序列化方式必须一致**（或通过 `prefer-serialization` 明确协商），不要指望框架自动兼容。序列化方式不匹配的报错往往出现在**反序列化阶段**，现象是"字段全空 / 类型转换异常"，很难一眼定位到根因。

## 七、安全边界：反序列化为什么能执行代码 {#security}

反序列化漏洞的成因可以一句话说清：

> **如果字节流里可以携带"类名"，那么"反序列化"就等于"让外部输入决定 JVM 加载并实例化哪个类"。**

而某些类的**构造过程、setter、`readObject`、`finalize` 里带有副作用**（打开连接、加载资源、调用其他方法），把它们组合起来就能形成一条完整的利用链。历史上最有名的几条链都在这个思路上：Java 原生序列化 + Apache Commons Collections、Fastjson 的 `autoType`、Hessian 反序列化、Jackson 的 `enableDefaultTyping`。

**四条防线（按强度排序）**：

| # | 防线 | 说明 |
|---|---|---|
| 1 | **不用能执行代码的序列化** | 用 Protobuf（有 schema，**不可能**构造任意类）；跨进程数据不用 JDK 原生序列化 |
| 2 | **类白名单 / 黑名单** | Dubbo 的类检查就是这个思路；**只允许业务 DTO 包路径**，拒绝一切"看起来像 gadget"的类 |
| 3 | **不反序列化不可信数据** | 外部传入的数据（HTTP 参数、上传文件、第三方回调）**永远不要直接反序列化成对象**，先解析成基础类型再转换 |
| 4 | **过滤器 / 版本升级** | JDK 17 的 `ObjectInputFilter`、依赖库及时打补丁（见 [原生序列化的四个问题](/java/basics/io-nio#serialization-problems)） |

> **最容易被忽略的一条**：RCE 风险不在"序列化"，而在"**反序列化不可信的输入**"。所以判断一个系统是否危险，要问的不是"你用什么序列化协议"，而是"**这条链路上有没有外部可以直接投递字节流的入口**"（MQ、缓存、RPC 入参、上传文件、Cookie 都算）。

## 八、选型判据 {#selection}

| 你的约束 | 选择 | 关键理由 |
|---|---|---|
| 对接浏览器 / 第三方 / 需要人肉调试 | **JSON** | 可读性无法替代；性能瓶颈一般在别处 |
| 跨语言内部调用、要求强契约 | **Protobuf**（gRPC / Dubbo triple） | 五项里唯一四项高分，唯一门槛是写 IDL |
| 纯 Java、不想写 IDL、要稳 | **Hessian2** | Dubbo 老项目默认值；自描述 → 加字段不用改 IDL |
| 纯 Java、极致性能、能控制发版 | **Kryo / FST** | 最快最小；**必须保证两端类结构一致** |
| 反序列化外部不可信数据 | **不要用"可携带类名"的方案**；必须用则加白名单 | 安全是第一优先级 |
| 老系统里的 JDK 原生序列化 | **择机替换** | 体积、性能、跨语言、安全四项全差 |

## 九、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 为什么不用 JDK 原生序列化？ | 四宗罪：**体积最大**（携带类描述与继承链）、**性能最差**、**不能跨语言**、**安全风险最高**（可携带类名 → RCE）；官方自己也在收紧（JDK 17 引入 `ObjectInputFilter`） |
| 2 | 序列化选型看哪几个维度？ | 五项：**体积、速度、跨语言、兼容性（版本演进）、安全**；没有方案全占，选型是"回答我最不能牺牲哪一项" |
| 3 | Protobuf 为什么小？ | 两个设计：**只传字段编号不传字段名**（名字只在编译期存在）；**varint** 让小数占少字节 + 1～15 号字段的 tag 只占 1 字节 |
| 4 | Protobuf 为什么快？ | 定长/变长二进制解析无需词法与语法分析（对比 JSON 要先构建语法树）；字段按编号定位，不需要重新做反射匹配 |
| 5 | `int32` 和 `sint32` 有什么区别？ | 负数占位不同：`int32` 的负数补码会占满 **5 字节**（最坏 varint），`sint32` 用 **zigzag** 把负数映射成小正数，因此**可能有负数的字段必须用 `sint*`** |
| 6 | 删掉一个 Protobuf 字段会怎样？ | 本身安全（旧数据该字段被忽略），**但必须 `reserved` 这个编号与名字**；否则将来有人复用编号时，会把旧数据的字节当新字段读，**静默错位** |
| 7 | 加字段会不会导致旧程序报错？ | 不会，旧程序把它当**未知字段跳过**（proto3 还会保留它，回写时不丢）；这正是 Protobuf 向前兼容的基础 |
| 8 | IDL 到底解决了什么？ | 把**契约检查从运行期提到编译期**，并让契约不再依赖"双方共享同一个 jar"——跨语言、跨团队、可独立演进 |
| 9 | proto3 的 field presence 有什么坑？ | 隐式 presence 下**默认值不会被序列化**，接收方分不清"对方传了 0"与"对方没设置"；需要区分时必须显式 `optional` |
| 10 | Dubbo 的默认序列化是什么？ | 看协议：**`dubbo` 协议（发行版默认）是 Hessian2**，`triple` + IDL 模式是 **Protobuf**；3.2.0 起可用 `prefer-serialization` 做无损升级协商 |
| 11 | 反序列化为什么会 RCE？怎么防？ | 因为部分协议允许字节流携带类名 → 外部输入决定加载哪个类，若该类构造/`readObject` 有副作用即可组合出利用链。**防线：首选不可携带类名的协议（Protobuf），其次类白名单（Dubbo 3.2 起默认 STRICT），再次不反序列化不可信数据，最后是过滤器与依赖升级** |
