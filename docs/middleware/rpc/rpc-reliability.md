# RPC 的可靠性：超时、重试、熔断与优雅上下线

前四篇讲的是"怎么把调用送出去"，这一篇讲的是"**送出去之后不顺利时，怎么不把自己也搭进去**"。RPC 方向的线上事故，绝大多数不是"协议写错了"，而是下面这几件事没设计：

> **超时是唯一的止损开关。**
>
> 没有超时，一个慢下游就能把调用方的线程全部占满，然后调用方的调用方也被占满——**故障沿着调用链一路放大成雪崩**。而重试、熔断、隔离、优雅下线，都是围绕这个开关的配套动作。

## 一、超时：唯一的止损开关 {#timeout}

**为什么必须设超时？** 因为不设超时的调用，其等待时间是**无界的**：

```text
不设超时：下游变慢
   → 调用方线程都被"等待响应"占住（线程池打满）
   → 该服务无法处理任何新请求（包括与故障无关的接口）
   → 它的上游开始等它 → 上游线程也被占满
   → 雪崩
```

**所以超时不是一个"优化项"，而是隔离故障的必要条件**。三个必须记住的点：

| 要点 | 说明 |
|---|---|
| **超时 ≠ 失败** | 超时只意味着**结果未知**（服务端可能已执行）。这决定了"能不能重试"取决于幂等，而不是取决于"失败了当然要重试"（见[四种故障模式](/middleware/rpc/rpc-essentials#failures)） |
| **默认值不能信** | Dubbo 默认超时是 **1000ms**。这个值对"读缓存"太长、对"跑报表"太短——**必须按接口逐个评估**，不能用全局默认 |
| **超时必须小于上游** | 如果 A 等 B 的超时是 3s，而 B 等 C 也是 3s，那么 A 的 3s 永远等不到 B 的"善意超时"；**上游的超时必须比下游小**，才能在链路里形成"逐层先返回" |

> **一条最容易被忽略的纪律**：**超时时间要跟着"业务承诺的响应时间"走，而不是跟着"接口现在的平均耗时"走**。如果 SLA 承诺 500ms 返回，那么超时就必须设在 500ms 之内——否则"没超时但已经超 SLA"的请求，等于把成本转嫁给了上游。

## 二、超时预算：从整条链路的 SLA 倒着分 {#budget}

"每一跳都设 1s"是一个常见的**错误答案**——因为链路上的最坏情况是**累加**的：

```text
A → B → C → D，每跳超时都设 1s
最坏情况：A 等 1s（B 内部又在等 C 1s，C 又在等 D 1s）
→ 但 A 在 1s 时就会超时返回，而此时 B/C/D 上的请求还在继续跑
→ 用户已经拿到超时错误，服务端还在白干活（浪费资源）
```

**正确的做法是"倒着分配"**：

```text
① 先定用户侧的 SLA：例如「接口 1 秒内必须返回」
② 留出本层处理时间：本层需要 200ms（算钱、查库）
③ 剩给下游的总预算：1s − 200ms − 安全余量(如 100ms) = 700ms
④ 若下游还有一层：700ms 再切分给它自己的处理 + 它的下游预算
```

**这解释了"超时传递"（deadline propagation）为什么重要**：上游应当把**剩余时间**（而不是"自己配的那个固定值"）传给下游。gRPC 的 `Deadline` 是**跨进程自动传播**的（放在 HTTP/2 头部里），这是一个被低估的优点；Dubbo 的 `timeout` 是按服务配置的，**需要自己用附件（attachment）传递剩余预算**。

**预算分配的三个原则**：

1. **总量守恒**：所有跳的"等待 + 处理"加起来不能超过第一跳的 SLA；
2. **给下游留出"能返回"的时间**：如果下游超时是 700ms，上游只等 600ms，那么上游永远看不到下游的"业务异常"（只会看到自己的超时），排障难度大幅上升——**上游的超时应比下游的大 50～100ms 的余量**；
3. **批量接口单独算**：一次调 10 个下游的接口，超时应该是"单次的 N 倍"或者并发调用，不能照抄单次超时。

## 三、重试的三条前提：缺一条都不能重试 {#retry}

重试是"用更多的请求换更高的成功率"，它天然有代价。**能不能重试，必须同时满足三条**：

| # | 前提 | 反例（不满足会怎样） |
|---|---|---|
| 1 | **幂等** | 非幂等的"创建订单"重试 → **重复下单** |
| 2 | **有界** | 无限重试 → 下游永远恢复不了（持续加压） |
| 3 | **有退避** | 立即重试 → 同一时刻的重试叠加成尖峰（**重试风暴**） |

**第 3 条的细节**：退避要同时具备**指数增长**和**抖动（jitter）**：

```text
无退避：  100 个客户端同时失败 → 100 个请求立刻重试 → 叠加成 2 倍压力
固定退避：100 个客户端都在 1s 后重试 → 仍然是叠加的尖峰
指数+抖动：每个客户端的重试时间在 [1s, 1s×(2^n + random)] 之间散开
         → 压力被摊平到一段时间上（这才是有效的削峰）
```

**第 2 条的细节**：有界要**同时限制次数与总时长**。只限次数的话，如果单次超时 5s、重试 3 次，最坏耗时 15s+，早已超过上游 SLA。

**关键判据（把三种情况分开）**：

| 失败类型 | 该不该重试 |
|---|---|
| **连接失败 / 未到达**（确定没执行） | ✅ 可以重试（换节点） |
| **超时 / 响应丢失**（结果未知） | ⚠️ **仅在接口幂等时**可以有界重试，否则要靠查证/对账 |
| **业务异常**（服务端明确返回错误） | ❌ **绝不重试**——这是确定的结果，重试只会重复报错 |

## 四、重试风暴：为什么"每个服务只重试 2 次"会变成雪崩 {#retry-storm}

这是 RPC 可靠性里最值得反复强调的一点，因为它的数学非常残酷：

```text
调用链：A → B → C → D，每一层都配了"失败重试 2 次"（= 最多发 3 次）
当 D 变慢时：
   B 对 C 的调用被放大：1 → 3
   C 对 D 的调用被放大：3 × 3 = 9
   实际打到 D 的请求：3 × 3 × 3 = 27 倍
```

**放大系数是乘积，不是加法**——这就是"每个服务都觉得自己的重试很克制"却依然打崩下游的原因。

**四条治理手段**：

| 手段 | 做法 |
|---|---|
| **只在一层重试** | 全链路只允许**最靠近用户的那一层**（或网关）做重试，中间层一律不重试 |
| **重试预算** | 给"重试流量"一个总配额（例如"正常流量的 10%"），超了就不重试——Google SRE 的做法 |
| **熔断兜底** | 下游已经明显不健康时，**熔断优先于重试**：先在客户端断掉流量，再谈重试 |
| **区分失败类型** | 只对"连接失败"这类确定没执行的错误重试；超时重试要额外受幂等约束 |

> **一个关键认知**：**重试是"对偶发故障的补偿"，不是"对系统性故障的对抗"。** 当故障是偶发的（单次网络抖动、单节点重启），重试有效；当故障是系统性的（下游过载、依赖挂掉），**重试只会加速崩溃**——此时唯一正确的动作是熔断 + 限流 + 快速失败。

## 五、幂等：重试的许可证，也是"恰好一次"的唯一出 {#idempotent}

既然重复无法避免（[三种投递语义](/middleware/rpc/rpc-essentials#semantics)），那只能让"重复执行"不产生副作用——这就是幂等。

**幂等的四类实现**（完整展开见[接口幂等](/java/spring/spring-cloud/idempotency)），在 RPC 场景下关注的差异是"**放在哪一层**"：

| 方案 | 放在哪 | 适用 |
|---|---|---|
| **数据库唯一索引** | 存储层 | 创建类操作（防重）——最强、最简单 |
| **状态机 + 条件更新** | 业务层 | 流转类操作（`UPDATE ... WHERE status='待支付'`，看影响行数） |
| **Token + Redis** | 入口层（网关/接口） | 需要"先申请再提交"的场景（如支付） |
| **去重表** | 存储层 | 需要保留"请求 ID → 结果"的映射（可返回首次结果） |

**RPC 侧对应的动作有两个**：

1. **给每个请求带上唯一标识**（业务请求号，而不是框架的 requestId——后者每次重试都会变），这样服务端才能识别"这是同一个业务请求的重试"；
2. **非幂等的写接口显式关闭重试**（Dubbo 的 `retries=0` 或 `Failfast`，[见集群容错](/middleware/rpc/dubbo-internals#cluster)）。

## 六、熔断与降级：把"止损"做在调用方 {#circuit-breaker}

超时解决"单次调用不死等"，熔断解决"**根本不再发起调用**"。断路器三状态机的完整机制在[服务保护](/java/spring/spring-cloud/resilience#circuit-breaker)已成篇，这里只讲 RPC 侧的两个决策：

**① 熔断器该装在客户端还是服务端？**

| 位置 | 保护的是谁 | 说明 |
|---|---|---|
| **客户端**（如 Sentinel 集成 Dubbo、Resilience4j） | **调用方自己** | 下游挂了，我不再等它——保护自己的线程与资源。**这是主战场** |
| **服务端**（服务端限流） | **服务提供方自己** | 防止被上游打垮。但请求已经到达服务端，网络与排队开销已发生 |

**结论**：**客户端熔断是第一道防线**，服务端限流是第二道。

**② 熔断的粒度**：**必须按"被调用的服务 + 方法"细分**，不能全局一个开关。否则一个冷门接口的失败会熔断整个下游服务的所有接口——把"局部故障"扩成了"全局不可用"。同理，[线程池隔离](/java/spring/spring-cloud/resilience#hystrix-isolation)的粒度也应对齐到这块。

**降级**（返回兜底值）与熔断的关系：

```text
熔断触发 → 决定「不再尝试调用」
降级逻辑 → 决定「不再调用之后，返回什么」
```

降级的三档从轻到重：**返回缓存/默认值** → **返回空/部分数据** → **抛业务异常并引导用户稍后重试**。**关键纪律：降级必须被监控和告警**，否则"服务看起来还活着，只是数据一直是兜底值"会成为最难发现的故障（**静默降级**）。

## 七、隔离与限流：让故障停在自己这一格 {#isolation}

| 手段 | 隔离对象 | 机制 | 代价 |
|---|---|---|---|
| **线程池隔离** | 每个下游/接口一个池 | 慢调用只占满自己的池 | 线程数、上下文切换、内存 |
| **信号量隔离** | 并发数上限 | 只做计数（不换线程） | 无法异步、无法超时中断 |
| **限流** | 请求速率 | 令牌桶 / 漏桶 / 滑动窗口（配置见[网关限流](/java/spring/spring-cloud/gateway#ratelimit)） | 被拒的请求要设计好返回 |

**在 RPC 里最该注意的一点**：**服务端的业务线程池也是一个"隔离舱"，但它常常是全局一个**。这会导致"一个慢接口把所有接口拖死"——因为请求都排在同一个队列里。所以：

- 对**重点接口**单独配线程池（Dubbo 支持按服务指定 `threadpool` 与 `threads`）；
- 队列**必须有界**，且拒绝策略要选"快速失败"而不是"无限排队"（无限排队 = 请求最终都会超时，但期间占着内存与连接）；
- 服务端**线程池指标必须暴露**（活跃线程、队列长度、拒绝数），否则线程池打满时你只看得到"超时"，看不到根因。

## 八、优雅上下线：为什么发版时总有几个 503 {#graceful-shutdown}

这是 RPC 里最"工程"、最容易被忽略、也最容易在面试里加分的一题。**根因是四个独立的时间差**：

```text
① 进程被 kill → 服务端不能再处理新请求
② 注册中心 → 消费者：地址变更的推送有延迟（消费者还有本地缓存在用）
③ 消费者本地缓存过期：【关键】消费者不知道这个实例要下线，仍在往它发请求
④ 长连接上的在途请求：已经发出的请求可能正在处理中
```

**如果直接 kill，就会出现**：`①` 已经发生，但 `③` 还在往这个地址发请求 → 报 503 / 连接拒绝。**这不是"抖动"，是设计缺陷。**

**正确的下线顺序（Dubbo 与 K8s 的通用套路）**：

```text
1. 先「反注册」：从注册中心摘掉自己（不再接收新流量）★ 关键第一步
2. 等待「消费者刷新」：睡眠一段时间（覆盖注册中心推送 + 消费者缓存刷新，
   常见配置几秒到十几秒），让流量自然流干
3. 停止接收新请求（关端口 / 拒绝新连接）
4. 等待「在途请求」完成（带超时的优雅等待）
5. 关闭线程池 → 关闭连接 → 退出进程
```

**K8s 下的对应机制**（两处容易踩的坑）：

| 机制 | 作用 | 坑 |
|---|---|---|
| **readiness 探针失败** | 让 Service 从 Endpoint 摘除该 Pod | 摘除是**异步**的，不能指望"探针失败=立刻没流量" |
| **`preStop` 钩子** | 在发 SIGTERM 之前执行——**这是实现"反注册 + 睡眠"的地方** | 不配它就只能靠应用自己响应 SIGTERM |
| **`terminationGracePeriodSeconds`** | SIGTERM 之后等待多久才 SIGKILL | 配得太短 → **在途请求被强杀**；实战常用 30s 以上 |

**上线侧也有对称的问题**：**新实例必须在"完全就绪"之后才注册**（Spring 容器启动完、数据库连接池预热好、本地缓存加载完）。否则新实例一上线就接到流量然后超时——表现为"发版后一段时间错误率升高，随后恢复"。**readiness 探针的意义就在于此**。

> **一条通用判据**：**"服务能处理请求"和"服务愿意接收请求"是两回事**。优雅下线之所以复杂，是因为注册（意愿）与处理能力（能力）之间永远存在时间差，而这两个时间差不能靠"更快"消除，只能靠"顺序"处理。

## 九、链路追踪与上下文透传：RPC 层的隐形义务 {#tracing}

排障时最容易卡住的一步是"**这个报错是哪一个上游请求引起的**"。链路追踪靠的就是 **traceId 沿着调用链传递**——而传递这件事，**在 RPC 层是协议能力**：

| 环节 | 机制 |
|---|---|
| **跨进程传递** | 通过协议头的**附加属性 / attachments**（等同 HTTP Header）带上 `traceId` / `spanId`（[协议头要素](/middleware/rpc/protocol-and-transport#header-fields)） |
| **跨线程传递** | 业务线程池换线程时会丢失 ThreadLocal 上下文 → 需要用可传递的 ThreadLocal（TTL）或在提交任务时手动带过去（[MDC 与日志打通](/java/spring/spring-cloud/tracing#mdc)） |
| **跨异步传递** | 线程池、`CompletableFuture`、消息队列都要显式传递，否则链路断开 |
| **无侵入方案** | SkyWalking / 探针类方案靠字节码增强自动完成透传，代价是版本兼容与性能开销（[无侵入探针](/java/spring/spring-cloud/tracing#skywalking-agent)） |

> **本节只讲"RPC 层要做什么"**——链路的通用模型、跨进程传播的四个断点（网关 / MQ / 线程池 / 响应式）、采样策略与后端选型见[链路追踪与 OpenTelemetry](/cloud-native/observability/tracing-otel)，其中[传播断点](/cloud-native/observability/tracing-otel#propagation)一节与本表互为补充。

**在 RPC 侧必须知道的两点**：

- **attachments 是"隐式契约"**：用它传业务参数（如租户 ID、灰度标记）很方便，但它**不在接口签名里**，容易被新同事忽略而导致功能缺失（例如某个新增的调用路径没带租户 ID → 数据越权）。**建议：能从接口签名传的，就不要藏进 attachments**；
- **attachments 是有成本的**：每个请求都要序列化与传输，滥用它会显著增加协议开销。

## 十、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 为什么说超时是"唯一的止损开关"？ | 不设超时，等待时间无界 → 线程被占满 → 该服务无法处理任何请求 → 故障沿调用链向上放大成雪崩；超时是把"慢"限制在局部的前提 |
| 2 | 超时了到底是成功还是失败？ | **既不是成功也不是失败，是"结果未知"**。服务端可能已执行完、正在执行、或没收到；因此能否重试取决于**幂等**，而不是取决于"失败了就该重试" |
| 3 | 整条链路 1 秒，每跳的超时怎么分？ | **倒着分**：先定用户侧 SLA（1s），减掉本层处理时间与安全余量，剩下的给下游，并逐层递减；同时**上游超时要略大于下游**（留 50～100ms 余量），否则上游永远只能看到自己的超时，看不到下游的业务异常 |
| 4 | 什么时候可以重试？ | 三条同时满足：**幂等 + 有界（次数与总时长）+ 退避（指数 + 抖动）**；且**只对"连接失败/确定未执行"或幂等接口重试**，业务异常绝不重试 |
| 5 | 为什么必须加抖动（jitter）？ | 固定退避会让所有客户端在同一时刻重试，形成尖峰；抖动把重试时间散开，才真正起到削峰作用 |
| 6 | 重试风暴是怎么来的？ | 每层的重试次数是**相乘**而非相加：三层各"重试 2 次"（最多 3 次）→ 最坏打到最底层 **27 倍**流量；治理手段：只在一层重试、重试预算、熔断优先、区分失败类型 |
| 7 | 幂等在 RPC 里怎么落地？ | ① 带**业务唯一请求号**（不能用每次重试都变的框架 requestId）；② 服务端用**唯一索引 / 状态机条件更新 / 去重表**保证重复执行无副作用；③ **非幂等写接口显式关闭自动重试**（Dubbo `retries=0` / failfast） |
| 8 | 熔断应该做在哪一侧？ | **客户端（调用方）是第一道防线**——下游挂了就不再等它，保护自己的线程资源；服务端限流是第二道。熔断粒度必须按"服务 + 方法"，否则一个冷门接口的失败会熔断整个下游 |
| 9 | 降级最危险的形态是什么？ | **静默降级**——服务看起来活着，但一直返回兜底值。**降级必须监控 + 告警**，并明确三档（返回缓存值 / 返回空数据 / 抛业务异常引导重试） |
| 10 | 发版时为什么会出现的 503 / 连接拒绝？ | 四个时间差：① 进程退出**快于**② 注册中心推送、**快于**③ 消费者本地缓存刷新、**快于**④ 在途请求完成。直接 kill 必然出现"消费者还在往已下线的实例发请求" |
| 11 | 优雅下线的正确顺序是什么？ | **反注册（摘流量）→ 睡眠等消费者刷新 → 拒绝新请求 → 等在途请求完成（有超时）→ 关线程池与连接 → 退出**；K8s 下用 `preStop` 实现前两步，`terminationGracePeriodSeconds` 给足等待时间；上线侧对称地要求"完全就绪后才注册" |
