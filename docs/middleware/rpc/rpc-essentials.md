# RPC 的边界：八条被违背的本地调用假设

RPC（Remote Procedure Call，远程过程调用）这个名字里最容易被忽略的是"过程调用"四个字——它的目标不是"传输数据"，而是**让远程调用在写法上和本地调用无法区分**：

```java
// 本地调用
int total = orderService.sumTotal(userId);

// Dubbo 远程调用：写法一模一样，但下面是序列化 + 网络 + 反射
@DubboReference
private OrderService orderService;
int total = orderService.sumTotal(userId);
```

这个伪装是 RPC 全部价值的来源，**也是它全部故障的来源**。本文要做的就是把这个伪装拆开。

## 一、八条本地调用的假设，跨了网络全部失效 {#assumptions}

在单机 JVM 里调用一个方法，下面八件事是**免费成立**的；一旦换成"跨进程调用"，它们会同时变成需要自己去解决的问题：

| # | 本地调用免费得到的 | 跨进程之后的现实 | 谁负责补 |
|---|---|---|---|
| 1 | 延迟可忽略 | 毫秒到秒级，且有长尾抖动 | 超时、批量、异步化（[超时预算](/middleware/rpc/rpc-reliability#budget)） |
| 2 | 一定会返回一个结果 | 可能永久不回，**结果未知** | 超时值（[唯一的止损开关](/middleware/rpc/rpc-reliability#timeout)） |
| 3 | 参数传的是引用 | 只能传值，**必须序列化** | 序列化协议与 IDL（[第 2 篇](/middleware/rpc/serialization)） |
| 4 | 方法恰好执行一次 | 只能"至少一次"或"至多一次" | 幂等设计（[第 5 篇](/middleware/rpc/rpc-reliability#idempotent)） |
| 5 | 中间没有第三方 | 网关 / 代理 / 服务网格都能改行为 | 协议设计（[第 3 篇](/middleware/rpc/protocol-and-transport)） |
| 6 | 地址固定不变 | 对方 IP 随扩缩容、重启而变 | 服务注册与发现（[Dubbo 应用级发现](/middleware/rpc/dubbo-internals#app-level)） |
| 7 | 两侧时间一致 | 时钟不同步，时间戳不能判断先后 | 用逻辑版本 / 序列号，不用时间（[fencing](/distributed/coordination/coordination-lock#fencing)） |
| 8 | 失败可以整体回滚 | 局部失败是常态 | 分布式事务 / 最终一致（[已成篇](/java/spring/spring-cloud/transaction)） |

**记忆的抓手**：第 1、2、6 条是**网络层**的（延迟、不返回、地址变），第 3、5 条是**协议层**的（数据形态、中间人），第 4、7、8 条是**语义层**的（次数、顺序、原子性）。

> **RPC 框架能替你解决的是"怎么把调用送出去、怎么把结果读回来"，它解决不了"网络的不可靠"。** 换句话说：RPC 替换掉的是**你自己手写 Socket、序列化、编解码的工作量**，替换不掉的是**你必须自己做的超时、重试、幂等决策**。这句话是本文后面所有判据的根。

## 二、RPC 的三种投递语义：为什么"恰好一次"做不到 {#semantics}

面试常问"RPC 能保证只执行一次吗"，标准答案不是"能"，而是**要先分清楚在说哪一种语义**：

| 语义 | 含义 | 实现方式 | 代价 |
|---|---|---|---|
| **至多一次**（at-most-once） | 失败就不重试，**可能没执行** | 不重试；或**不自动重试 + 幂等接口** | 业务可能丢操作（如扣款没做） |
| **至少一次**（at-least-once） | 失败就重试，**可能重复执行** | 框架默认行为（Dubbo `retries=2`） | **调用方必须做幂等** |
| **恰好一次**（exactly-once） | 只执行一次，不重不漏 | **在通用 RPC 层做不到**；只能在**业务语义层**模拟 | 需要"去重表 / 状态机 / 唯一键"三件套 |

**为什么"恰好一次"在 RPC 层做不到？** 因为存在这样一个无法消除的窗口：

```text
[调用方] --发出请求--> ... --> [服务端收到并执行] --> ... --> [响应包丢失]
                                            ↑
                      服务端已经执行了，但调用方永远收不到"成功"
```

调用方此时只有两个选择，**且都是错的**：

- 重试 → 可能重复执行（至少一次）；
- 不重试 → 可能丢操作（至多一次）。

**结论**：RPC 层只能提供前两种语义，**第三种必须在业务侧做**——这也是[幂等](/java/spring/spring-cloud/idempotency)为什么是 RPC 可靠性的地基。注意这与消息队列的结论完全一致（见[三条主线](/middleware/#three-threads)）：**"恰好一次"是分布式系统的固有难题，不是某个框架的缺陷**。

> **一个容易被忽略的推论**：既然重复无法避免，那么"**接口的默认设计应当是幂等的**"。一个不幂等的接口（如"余额加 100"）一旦开启重试，就是在制造脏数据；而幂等接口（如"设置余额为 100"、"订单 123 置为已支付"）天然可以安全重试。

## 三、RPC / REST / gRPC 三者的定位差异 {#vs-rest}

第一个层次是**协议**（怎么在网络上说），第二个层次是**框架**（谁来生成代码、管理连接、做治理）。把它们混着比是面试里最常见的答错方式：

| 维度 | **Dubbo（dubbo 协议）** | **gRPC** | **REST（HTTP/1.1 + JSON）** |
|---|---|---|---|
| 传输层 | 自定义二进制协议，**TCP 长连接** | **HTTP/2** | HTTP/1.1（或 2） |
| 序列化 | 默认 Hessian2，可换 Protobuf / Kryo | **Protobuf**（IDL 强绑定） | JSON 文本 |
| 接口定义 | Java 接口（可换 IDL） | **`.proto` 文件，跨语言** | 无强制契约（OpenAPI 是文档） |
| 契约检查时机 | **运行期**（版本不一致时才报错） | **编译期**（`protoc` 生成代码） | 运行期 |
| 流式能力 | 有限 | **四种模式**，双向流 | 无（需 SSE / WebSocket 另配） |
| 浏览器可达 | ❌ | ⚠️ 需 **gRPC-Web** 或网关转码 | ✅ 原生 |
| 可读性 / 调试 | 差（二进制） | 差（二进制，但有 `grpcurl`） | **好**（curl 即可） |
| 网关友好度 | 低（需专门插件解析协议） | 中（HTTP/2 可被 L7 网关识别） | **高** |
| 适用位置 | **同构 Java 微服务内部** | **跨语言内部调用**、流式场景 | **对外 API**、前端调用、第三方集成 |

**三条判据**：

1. **调用方是不是浏览器 / 第三方**？是 → 只能 REST（或 REST 网关后面转 RPC）。
2. **是否要求强契约、跨语言、有流式需求**？是 → gRPC（或 Dubbo 的 triple 协议）。
3. **是否全是 Java 服务、极致追求吞吐**？是 → Dubbo `dubbo` 协议 + Hessian2 / Protobuf。

> **一个常被问到的细节**：为什么内部服务不干脆全用 REST？因为在"每毫秒要处理几千次调用"的场景下，JSON 的文本解析与 HTTP/1.1 的连接管理会成为真实的 CPU 与延迟开销；而 RPC 的收益主要来自**二进制编码 + 长连接复用 + 更少的头部**。但如果你的调用量根本不大，**REST 的可调试性远比那点性能更值钱**——这是典型的"不要为不需要的性能买单"。

## 四、RPC 与消息队列：分界线是"要不要立刻知道结果" {#vs-mq}

两者都是"服务间通信"，但解决的不是同一类问题：

| 维度 | **RPC（同步调用）** | **消息队列（异步事件）** |
|---|---|---|
| 时间耦合 | **强**——调用方必须等（或超时） | **弱**——发完就走，消费方何时处理无关 |
| 空间耦合 | 要知道对方地址（或通过注册中心） | 只需要知道 Broker |
| 返回结果 | 有（这就是它存在的意义） | 一般没有（要靠回调 / 查询） |
| 流量削峰 | **不能**——流量直接打到下游 | **能**——Broker 就是蓄水池 |
| 下游扩容 | 调用方无感，但有连接数压力 | 天然支持（加消费者即扩容） |
| 下游故障 | 调用方跟着报错 / 超时（需熔断保护） | 消息堆积，恢复后继续消费 |
| 顺序性 | 天然按调用顺序（但并发时无保证） | 需显式设计（同 key 同分区） |
| 典型场景 | 查询、校验、下单前必要步骤 | 通知、异步计算、数据同步、削峰 |

**判据只有一句**：

> **"上游必须拿到这个结果才能继续"→ RPC；"上游只要确保这件事会被做"→ 消息队列。**

三个具体的分界信号：

- **要削峰** → 必须 MQ。RPC 没有缓冲区，下游扛不住就整体雪崩；
- **要广播给多个下游** → 必须 MQ（RPC 是一对一，扇出要自己写循环）；
- **下游不可用也要保证不丢** → 必须 MQ（RPC 的下游挂了就是调用失败）。

> **最容易被答错的一个场景**：下单后"扣减库存 + 发短信 + 加积分"。这三个动作里，**扣库存是必要步骤（RPC，失败要回滚）**，而**发短信、加积分是可以事后处理的（MQ）**。把三件事都做成同步 RPC，等于把系统的可用性捆绑在最弱的那个环节上——这是"局部失败被放大成整体失败"的经典形态（见[服务雪崩](/java/spring/spring-cloud/resilience#avalanche)）。

## 五、四种故障模式：最危险的是"结果未知" {#failures}

一次 RPC 从发出到结束，可能落在四种状态上。**注意这里只有一种是"确定的失败"**：

| # | 故障模式 | 现象 | 服务端是否执行过 | 调用方该做什么 |
|---|---|---|---|---|
| 1 | **连接失败** | `ConnectException` / `NoRouteToHost` | **确定没有** | 可安全重试（换个节点） |
| 2 | **超时** | `TimeoutException` | **不知道**（可能已执行完、正在执行、还没收到） | **不能盲目重试**；要么查证、要么靠幂等 |
| 3 | **响应丢失 / 连接断开** | `Connection reset`、读到半个包 | 同上，**不确定** | 同上 |
| 4 | **业务异常** | 服务端返回了明确的错误码 | **确定执行过**（或确定拒绝） | 按业务语义处理，**不要重试** |

**这张表的杀伤力在第 2、3 行**：很多人下意识把"超时"当成"失败"，于是加上自动重试——结果是**在一个本来就已经过载的服务上，把请求量放大了一倍**（见[重试风暴](/middleware/rpc/rpc-reliability#retry-storm)）。

**正确的处置顺序**（这也是线上排障的标准动作）：

```text
超时了
  ├── ① 先看是不是大面积超时
  │     是 → 大概率下游过载或网络问题 → 熔断，别再打
  └── ② 个别超时 → 看接口是否幂等
        幂等   → 可以有界重试（退避 + 换节点）
        非幂等 → 不要重试；靠"查证 + 对账"确认结果
```

> **一句话总结这张表**：**"失败"是确定的，"超时"是不确定的。** 把不确定当成确定，是 RPC 使用中最高频的思维错误。它也是[优雅下线](/middleware/rpc/rpc-reliability#graceful-shutdown)这个问题的根源——发版时那批 503，本质上就是"服务端已经在关了，但调用方还在按旧地址发请求"。

## 六、五条"不该用 RPC"的判据 {#when-not}

RPC 不是所有服务间通信的默认答案。下面五条命中任意一条，都该先停下来想想：

| # | 情况 | 为什么不该用 | 该用什么 |
|---|---|---|---|
| 1 | **需要削峰 / 下游处理能力远小于上游** | RPC 无缓冲，直接透传压力 | 消息队列 |
| 2 | **一个事件有多个（且会增加的）下游** | 扇出要发版改上游代码 | 消息队列（发布订阅） |
| 3 | **调用方是浏览器或第三方** | 二进制协议 + 强契约会变成接入负担 | REST / GraphQL |
| 4 | **跨组织 / 跨团队边界** | 强耦合到对方的接口版本，协作成本高 | 稳定的 HTTP API + 版本策略 |
| 5 | **只是"偶尔传个数据"，量很小** | RPC 的收益（性能）用不上，代价（契约耦合、调试成本）全占了 | 直接 HTTP，或干脆共享数据库视图（视场景） |

**反向的判据同样成立**：如果满足下面三条，RPC 就是最优解——

- **调用方与服务提供方属于同一个组织 / 同一套技术栈**；
- **调用是同步的、必须要结果**；
- **调用量大到"每次调用的固定开销"值得被优化**。

> **一个容易忽略的成本**：RPC 把"远程调用"包装得太漂亮，会诱导出**细粒度的频繁调用**（例如在循环里逐个查用户，即经典的 N+1 问题）。本地方法这么写没关系（纳秒级），跨网络这么写就是灾难。**真正落地时要主动为"远程接口"设计粗粒度的批量方法**——这也是[微服务拆分粒度](/methodology/)问题在接口层的一个投影。

## 七、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | RPC 到底解决了什么问题？ | 把手写 Socket + 序列化 + 编解码的工作量**框架化**：它替换掉的是"怎么送出去、怎么读回来"，**替换不掉网络的不可靠与业务语义的决策** |
| 2 | RPC 调用和本地调用的本质区别？ | 本地调用有八个免费假设（延迟为零、必定返回、传引用、恰好一次、无中间人、地址固定、时钟一致、可回滚），跨进程后这八条全部失效，必须逐个补回来 |
| 3 | RPC 能保证只执行一次吗？ | 不能。存在"服务端已执行但响应丢失"的窗口，调用方重试则可能重复、不重试则可能丢失；**只能做到至少一次或至多一次，恰好一次必须在业务侧用幂等模拟** |
| 4 | 为什么"超时"不能当成"失败"？ | 服务端可能已经执行完成、正在执行、或还没收到；超时只意味着**结果未知**。把超时当失败并自动重试，等于给过载的下游再放大一倍流量 |
| 5 | 什么情况下调用失败可以安全重试？ | 三个条件同时满足：**① 连接失败/未到达（确定没执行）或接口幂等；② 有界（次数 + 总时长上限）；③ 有退避（指数 + 抖动）**，缺一条都可能引发重试风暴 |
| 6 | 内部服务为什么不用 REST 而要上 RPC？ | 收益来自二进制编码、长连接复用、更少头部，在每次调用固定开销显著时才值；**调用量不大时 REST 的可调试性更值钱** |
| 7 | RPC 和消息队列怎么选？ | 分界是"**上游是否必须拿到结果才能继续**"：要结果用 RPC（同步、有时间耦合），只要确保事情会被做用 MQ（异步、可削峰、可广播） |
| 8 | gRPC 相比 Dubbo 的优势在哪？ | 跨语言与强契约（`.proto` 编译期检查）、原生四种流式模式、基于 HTTP/2 因而**网关与服务网格友好**；Dubbo 的优势在 Java 生态内的**接口级治理能力**（路由、容错、泛化调用） |
| 9 | 为什么说 RPC 会诱导出性能问题？ | 它把远程调用写得像本地调用，容易写出"循环里逐个查"的细粒度调用；本地纳秒级无妨，跨网络就是灾难，**必须为远程接口设计粗粒度批量方法** |
