# 协议与传输：一次调用在字节层经历了什么

序列化解决了"一个对象怎么变成字节"，但字节本身还需要被**装进一个有边界的框里**，并在一条长连接上被区分出属于哪次请求。这一层就是协议。

> **自定义 RPC 协议里每一个字段，都在回答两个问题之一：**
>
> **① 怎么从字节流里切出一条完整的消息（分帧）？② 怎么知道这条响应属于哪次请求（复用）？**
>
> 想通这两句，协议头的每个字段都不需要背——它们是这两个问题的必然产物。

## 一、一次调用的六段链路 {#pipeline}

把"消费者调用一个方法"到"拿到返回值"拆开，中间经过六段：

```text
[消费者]
  ① 代理层：动态代理拦截方法调用，把「接口名 + 方法名 + 参数类型 + 参数值」打包成 RpcInvocation
        ↓
  ② 序列化：把 RpcInvocation 编码成字节（Hessian2 / Protobuf / …）
        ↓
  ③ 协议编码：套上协议头（魔数、长度、请求 ID、序列化类型…）→  一个完整"帧"
        ↓
  ④ 网络传输：写入 TCP 长连接（可能经网关 / 代理 / 负载均衡）  ————▶ [服务端]
        ↓                                                           ⑤ 协议解码：按长度切帧，按请求 ID 关联，按序列化类型反序列化
  ⑥ 反射调用：查找到目标实现类的方法，反射执行，把结果按同样流程返回
```

**这张图里每一段都对应一类线上问题**，这就是为什么排障时要知道它：

| 段 | 典型故障 | 排查手段 |
|---|---|---|
| ① 代理 | 泛化调用失败、`No such method` | 看接口签名与版本是否一致 |
| ② 序列化 | 类检查失败、字段丢失、跨版本不兼容 | 看[序列化的协商与类检查](/middleware/rpc/serialization#dubbo-serialization) |
| ③ 协议编码 | 半包 / 粘包、长度字段算错 | 抓包看帧长度（`tcpdump` + Wireshark 按协议解码） |
| ④ 网络 | 连接被中间设备静默断开（NAT 超时） | 看心跳是否生效、连接是否长时无流量 |
| ⑤ 解码 | 请求 ID 错乱（响应串到别的请求上） | 看并发压测下是否出现"结果张冠李戴" |
| ⑥ 反射 | 业务线程池打满、超时 | 看线程池指标（[线程模型](#thread-model)） |

**关键认识**：**RPC 的"调用"在这六段之间不是原子的**——任何一段失败，都可能留下"服务端执行了但调用方不知道"的状态（见[四种故障模式](/middleware/rpc/rpc-essentials#failures)）。

## 二、为什么要自定义协议，而不是直接用 HTTP {#why-custom}

看完六段链路，一个问题自然出现：HTTP 已经把这些都做了，为什么 Dubbo 还要自定义一套二进制协议？

因为 HTTP/1.1 作为"**为人浏览网页设计**"的协议，有三个包袱：

| 包袱 | 具体开销 | RPC 场景下的影响 |
|---|---|---|
| **头部是文本且冗长** | `GET /path HTTP/1.1` + 一堆 `Header: value`，动辄几百字节 | 内部调用参数可能只有几十字节，**头部比正文还大** |
| **无多路复用（1.1）** | 一个连接同一时刻只能跑一个请求 | 想并发就得开多个连接，连接数随 QPS 线性涨 |
| **没有统一的消息边界** | 靠 `Content-Length` / chunked，语义复杂 | 自定义协议用一个长度字段就够，**解析更简单更快** |

**于是自定义协议的目标很明确**：**用最少的字节，把"一次调用（含上下文与附加属性）"表达完整，并支持在一条连接上并发跑**。

> **但要注意这是有代价的**：二进制私有协议**无法被通用网关、抓包工具、服务网格直接理解**——要接入它们就得写插件或做协议转换。这也是 Dubbo 3 官方推荐新项目用 **triple（HTTP/2 语义）** 的原因：**把"能被基础设施理解"当成一项收益**（见[第六节](#grpc)）。

## 三、协议头的必备要素：七个字段各有分工 {#header-fields}

把上一节的两个问题展开，就有了下面这份"最小可用协议头"。**不要背，要顺着问题推**：

| 字段 | 解决什么问题 | 不写会怎样 |
|---|---|---|
| **① 魔数**（Magic） | **快速判断这是不是一个合法请求**，顺便挡掉端口误连 / 扫描流量 | 任何垃圾字节都会被当成请求去解析，服务端容易被无意义流量打满 CPU |
| **② 版本号** | 协议本身的演进（不是业务版本） | 协议升级后新旧节点无法共存 |
| **③ 序列化类型**（或标志位） | 告诉对方**用什么方式反序列化** | 无法支持多序列化并存与[协商升级](/middleware/rpc/serialization#dubbo-serialization) |
| **④ 消息类型** | 请求 / 响应 / 心跳（one-way 也算一类） | 心跳包无法与业务包区分，也分不清收的是请求还是响应 |
| **⑤ 请求 ID**（Request ID） | **把响应关联回请求**——这是并发复用的前提 | 一条连接上并发多个请求后，**响应无法断定属于谁**，结果张冠李戴 |
| **⑥ 消息长度**（Body length） | **分帧**：从字节流里切出一条完整消息 | 遭遇粘包 / 拆包（见下一节），解析必然错乱 |
| **⑦ 附加属性**（Attachments） | 跨进程透传隐式上下文：**traceId、租户 ID、灰度标记、超时时间** | 链路追踪断链、多租户与灰度无法透传（对比 HTTP 的 Header，语义相同） |

**两个容易被忽略的点**：

- **请求 ID 不是"锦上添花"，而是"长连接 + 并发"的必然后果**。一旦一条连接上同时有多个在途请求，就必须有办法把响应配回请求；而"一问一答串行"虽然不需要 ID，却把吞吐锁死了。
- **附加属性是 RPC 版的 HTTP Header**。它的存在说明 RPC 的协议头不只服务"传输"，还承担了**跨进程的隐式上下文传递**——这是[链路追踪](/java/spring/spring-cloud/tracing#mdc)与多租户落地的基础设施。

## 四、粘包与拆包：三种分帧方式 {#framing}

**根因**：TCP 是**面向字节流**的（详见 [TCP 的粘包与拆包](/fundamentals/network/tcp#sticky-packet)），它**不保留"一次 write 对应一次 read"的边界**。你 `write` 了两次，对面可能一次 `read` 全拿到（粘包）；你 `write` 了 1KB，对面可能分三次才收齐（拆包）。

**三种分帧方式**：

| 方式 | 做法 | 优点 | 致命缺点 |
|---|---|---|---|
| **定长** | 每条消息固定 N 字节 | 解析最简单（读到 N 字节即一帧） | **只能用于消息长度固定**的场景；长度不一致时浪费带宽 |
| **分隔符** | 用 `\r\n` / `\0` 等特殊字符标记结尾 | 实现简单、可读 | **消息内容不能包含分隔符**（要转义，转义逻辑容易出 bug）——Redis 协议（RESP）与 HTTP 头部用的就是这类思路 |
| **长度字段**（最主流） | 头部若干字节声明"body 有多长" | **通用、无转义成本、可定长读取** | 需要处理"长度字段本身也可能被拆开"的情况 |

**为什么第三种最可靠，也有个技巧**：长度字段本身也可能处于"只收到一半"的状态，所以解码器要**先按最少字节数尝试读头部**，拿到长度后再等 body 到齐。Netty 的解决方式是把这件事参数化：

```java
// Netty：把"字节流"变成"一帧一帧的消息"
new LengthFieldBasedFrameDecoder(
        maxFrameLength,    // 一帧最大长度（防御超长帧打满内存）
        lengthFieldOffset, // 长度字段从第几字节开始（跳过魔数/版本等）
        lengthFieldLength, // 长度字段占几字节（2/4，取决于能表达多大消息）
        lengthAdjustment,  // 长度值里是否包含头部自身的修正量
        initialBytesToStrip // 解码后是否把协议头剥掉
);
```

**这五个参数就是"长度字段方案"要处理的所有边界**：跳过前置头部、长度字段几个字节、长度值算不算头、解码后要不要留下头。理解它们等于理解协议分帧。

> **一个实践细节**：`maxFrameLength` 必须设置。否则一个恶意（或有 bug 的）客户端声明一个 2GB 长度，服务端会**按这个长度去分配缓冲区**，直接把内存打爆——这类攻击叫"长度字段欺骗"。**分帧解码器同时也是第一道安全边界。**

## 五、长连接与连接池：为什么 RPC 不用短连接 {#connection}

RPC 几乎都用长连接，原因是一个简单的算术：

| | **短连接** | **长连接 + 多路复用** |
|---|---|---|
| 每次调用的额外成本 | TCP 三次握手 +（若有 TLS）握手，**1～3 个 RTT** | **无** |
| 高 QPS 下的连接数 | 与 QPS 成正比，端口耗尽、`TIME_WAIT` 堆积 | 与实例数成正比，**稳定** |
| 服务端文件描述符 | 随并发飙升 | 可控 |
| 代价 | 实现简单 | 需要**心跳保活**、**连接状态管理**、**请求 ID 关联** |

**心跳为什么必须有？** 因为中间设备（防火墙、NAT、云负载均衡）会**静默回收"一段时间没有流量"的连接**——它不会发 FIN，双方都以为连接还在。这在真实故障里表现得很典型：**一个服务隔夜没有流量，第二天第一个请求超时失败，之后恢复正常**。心跳（固定间隔发小包）就是让连接"永不静默"。

**连接数怎么定？** 常见做法是"每消费端到每提供端 N 条连接"（Dubbo 的 `connections` 默认是**共享一条长连接**）：

- 连接太少 → 单连接成为瓶颈（解析串行、单连接的 TCP 窗口限制）；
- 连接太多 → 服务端 fd 与线程资源被耗尽，且**负载均衡反而变差**。

> **判断依据不是"连接数"，而是"单连接是否已成瓶颈"**：看单连接的**在途请求数**与**响应排队时间**。如果单连接平均在途请求只有 1～2 个，加连接通常没用。

## 六、HTTP/2 与 gRPC：用通用性换来的东西 {#grpc}

gRPC 的组成可以一句话说清：**HTTP/2 做传输 + Protobuf 做序列化 + `protoc` 生成 Stub**。其中真正关键的是前一半——**HTTP/2 恰好把 HTTP/1.1 的三个包袱都解决了**：

| HTTP/1.1 的问题 | HTTP/2 的机制 |
|---|---|
| 头部冗长、纯文本 | **HPACK 头部压缩**（静态表 + 动态表 + 哈夫曼编码），重复的头部只在首帧传全 |
| 一个连接一次一个请求 | **多路复用**：一条连接上并发多个"流"，每个流有唯一 ID，**用流 ID 代替了我们自定义协议里的请求 ID** |
| 应用层队头阻塞（1.1 的队头阻塞在应用层） | **二进制分帧**：请求切成帧交错发送，慢响应不再阻塞后面的请求 |
| 无流式语义 | **流（Stream）+ 帧（Frame）** 模型天然支持双向流 |

**注意对照**：HTTP/2 的**流 ID** 与自定义协议的**请求 ID** 解决的是同一个问题；HPACK 与我们"不传字段名"的省字节思路也是同一个目标。**gRPC 没有发明新东西，它只是站在了一个已经被 CDN、网关、服务网格普遍理解的协议上。**

**代价也很明确**：

- **浏览器不能直连**（HTTP/2 分帧无法从 JS 发起），必须走 **gRPC-Web** 或网关转码；
- **每一帧都带 9 字节头部**，极小消息（几十字节）的效率不如裸二进制协议；
- **调试仍不直观**（虽然可以用 `grpcurl` + 反射或 proto 文件解码）。

> **gRPC 的选型判据**：**跨语言 / 需要流式 / 要能被基础设施（网关、网格、负载均衡）理解**——这三条命中任意一条，HTTP/2 带来的通用性就值回票价；否则纯 Java 内部调用，Dubbo 私有协议的性能与治理能力更划算。

## 七、gRPC 的四种调用模式 {#grpc-modes}

`.proto` 里 `stream` 关键字的位置，定义了这个方法属于哪一种：

| 模式 | `.proto` 写法 | 语义 | 典型场景 |
|---|---|---|---|
| **一元**（Unary） | `rpc Get(UserReq) returns (User)` | 一问一答，**等同普通 RPC** | 绝大多数字段查询、写操作 |
| **服务端流** | `rpc List(UserReq) returns (stream User)` | 一问，多答 | 大结果集分批返回、订阅推送 |
| **客户端流** | `rpc Upload(stream Chunk) returns (Ack)` | 多问，一答 | 文件上传、批量写入 |
| **双向流** | `rpc Chat(stream Msg) returns (stream Msg)` | 双向持续收发 | 实时对话、协同编辑、长连接推送 |

**为什么这四种模式在 HTTP/1.1 上很难做？** 因为 HTTP/1.1 的语义是"一个请求对应一个响应"；要模拟双向流只能上 WebSocket 或轮询。**流是 HTTP/2 帧模型的原生能力**，这也是 gRPC 相对 REST 最实质的能力差异——比"性能好"重要得多。

> **一个工程上的提醒**：流式接口**天然是长生命周期的**，因此它把很多"短连接下不成问题"的东西变成了必答题：**超时如何生效（整条流还是每次消息）、断流后如何续传、服务端扩容时流如何迁移**。选流式之前先回答这三个问题。

## 八、线程模型：为什么业务逻辑绝不能写在 IO 线程里 {#thread-model}

这是 RPC 侧最"工程"、也最容易出事故的一节。以 Netty 的 Reactor 模型为例：

```text
Boss 线程组  → 只负责 accept 新连接（数量极少）
      ↓
Worker 线程组（IO 线程） → 只负责 read / write / 编解码   ← 通常 = CPU 核数
      ↓  把"已解码的完整请求"投递给业务线程池
业务线程池         → 执行真正的业务逻辑（查库、算钱、调下游）   ← 数量大，可隔离
```

**铁律**：**IO 线程只做"搬字节"，一个字符的业务逻辑都不能写。**

原因在于 IO 线程是**被连接共享**的：

| 写法 | 后果 |
|---|---|
| 在 IO 线程里查一次数据库（耗时 50ms） | 该线程负责的**所有连接的读写全部停摆 50ms**——阻塞一个线程等于阻塞一批连接 |
| 在 IO 线程里调用另一个 RPC | 调用链套娃，**线程被你自己锁死**，最容易形成全链路死锁 |
| 把业务交给独立线程池 | IO 线程立刻回到"搬数据"状态；业务慢只影响那个线程池（可隔离、可监控、可限流） |

**必须知道的实践点**：

- **线程池要按业务隔离**：不同下游的重要程度不同，用一个共享线程池，慢接口会把整池占满（[舱壁模式](/java/spring/spring-cloud/resilience#hystrix-isolation)）。Dubbo 提供 `fixed` / `cached` / `limited` 等线程池类型，也可以为特定服务单独指定。
- **线程池满时的行为要提前设计**：Dubbo 的默认拒绝策略会**抛异常并让调用方立刻失败**（而不是无限排队）——这其实是好事，**快速失败比队列积压到超时更可控**（对比 [线程池的四种拒绝策略](/java/concurrent/thread-pool#reject-policy)）。
- **线程池大小不是越大越好**：它是有上限的资源，且**每多一个线程就多一次上下文切换**。核心线程数的估算方法与普通业务线程池一致（[怎么定核心线程数](/java/concurrent/thread-pool#pool-size)），关键输入是"**等待时间 / 计算时间的比例**"。
- **虚拟线程正在改变这条边界**（JDK 21+）：业务侧用虚拟线程可以让"阻塞式写法"不再昂贵，但 **IO 线程仍然必须是非阻塞的**——Reactor 的线程模型不因虚拟线程而改变。

## 九、面试口径 {#interview}

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 一次性把 RPC 的完整链路说清楚 | 六段：**动态代理包装调用 → 序列化 → 协议编码（加头）→ 网络传输 → 协议解码 + 反序列化 → 反射执行**；每段都是一类线上问题的来源 |
| 2 | 为什么要自定义协议，不用 HTTP？ | HTTP/1.1 有文本头部冗长、无多路复用、消息边界语义复杂三个包袱；私有协议用最少字节表达一次调用并支持单连接并发；**代价是通用网关/抓包/网格无法直接理解** |
| 3 | 协议头里为什么要魔数？ | 用最少字节**快速判定是不是合法请求**，挡掉端口误连与扫描流量；否则任何垃圾字节都会进入解析流程白耗 CPU |
| 4 | 请求 ID 是干什么的？ | 把响应关联回请求。**只要一条连接上并发跑多个请求，就必须有它**；"一问一答串行"才不需要，但吞吐被锁死 |
| 5 | 粘包拆包怎么解决？ | 三种分帧：**定长 / 分隔符 / 长度字段**。主流是长度字段（通用且无转义成本），Netty 用 `LengthFieldBasedFrameDecoder` 的五个参数把边界情形全部参数化 |
| 6 | `maxFrameLength` 为什么必须设？ | 它同时是性能参数与**安全边界**：不设的话，一个声明超大长度的帧会让服务端按此分配缓冲区，直接打爆内存（长度字段欺骗） |
| 7 | 为什么要心跳？ | 防火墙 / NAT / 云负载均衡会**静默回收空闲连接**（不发 FIN），表现为"隔夜后第一个请求失败，之后正常"；心跳让连接永不静默 |
| 8 | gRPC 为什么用 HTTP/2 而不是自定义协议？ | 为了**被基础设施理解**：网关、服务网格、L7 负载均衡天生懂 HTTP/2；多路复用（流 ID）、HPACK 头部压缩、二进制分帧正好解决 HTTP/1.1 的三个包袱，**gRPC 等于白拿** |
| 9 | gRPC 的四种模式解决什么问题？ | 一元 / 服务端流 / 客户端流 / 双向流；**流是 HTTP/2 帧模型的原生能力**，这是相对 REST 最实质的差异（比性能差异重要）；选流式前要先回答超时、断流续传、扩容迁移三个问题 |
| 10 | 为什么业务逻辑不能写在 IO 线程里？ | IO 线程**被一批连接共享**：在其中做一次 50ms 的查询，等于让该线程上所有连接停摆 50ms；在 IO 线程里再发起 RPC 甚至会把自己锁死。**业务必须投递给独立线程池**，且按业务隔离、明确拒绝策略、按等待/计算比例估算大小 |
