# 集群与高可用

## 一、问题场景

单台 RabbitMQ 宕机 = 整个系统消息链路中断。加机器组成集群能解决"节点挂了还有人服务"，但**加集群不等于消息不丢**：

```
集群 A：3 个节点，队列只存在于 node1
  node1 宕机 ──▶ 队列连同其中的消息一起消失 ❌
                 （其他节点只有元信息，没有消息）

集群 B：3 个节点，队列消息在 3 个节点都有副本
  node1 宕机 ──▶ node2 升级为主，消息完好 ✅
```

**结论先行**：RabbitMQ 的集群模式有三代演进——**普通集群**（只共享元信息，**宕机丢消息，不可用于生产**）→ **镜像集群**（消息多节点同步，但**已被官方标记 deprecated**）→ **仲裁队列 Quorum Queue**（基于 Raft，**3.8+ 官方推荐**）。面试的加分点在于**能说出镜像队列为什么被淘汰**。

## 二、普通集群（Classic Cluster）

**做法**：多个节点组成集群，节点间共享**交换机、队列的元信息**（名称、属性、绑定关系），但**不共享队列中的消息**。

```
        ┌──────────── Cluster ────────────┐
        │                                  │
   ┌────▼────┐      ┌─────────┐      ┌─────────┐
   │ node1   │◀────▶│ node2   │◀────▶│ node3   │
   │         │      │         │      │         │
   │ queue A │      │ (无 queue A  │  │ (无 queue A
   │ + 消息   │      │  的消息) │      │  的消息) │
   └─────────┘      └─────────┘      └─────────┘
        ▲                 │
        │                 │ 客户端连到 node2 访问 queue A
        │                 │ → node2 从 node1 "拉"消息过来再返回
        └─────────────────┘
```

| 特点 | 说明 |
|---|---|
| 共享什么 | 交换机、队列的**元信息**（定义），以及用户、权限、VHost |
| 不共享什么 | **队列中的消息** |
| 跨节点访问 | 连到任意节点都能访问队列，消息由**持有该队列的节点**转发 |
| **致命缺点** | **队列所在节点宕机 → 队列和消息一起丢失**（只是元信息还在） |

**用途**：提升**吞吐**（多个节点分担连接与队列），但**不提供数据高可用**。所以**不能单独用于生产**。

> 元信息存在哪：传统模式靠磁盘上的 `.erlang.cookie` 与 mnesia 数据库在各节点间同步；这也是为什么**集群节点必须使用同一个 Erlang Cookie**。

## 三、镜像集群（Mirror Queue）

**做法**：在普通集群的基础上，把**队列的消息在多个节点间同步备份**。

```
        ┌────── 镜像队列 queue A ──────┐
   ┌────▼────┐      ┌─────────┐   ┌─────────┐
   │ node1   │─────▶│ node2   │   │ node3   │
   │ Master  │ 同步  │ Mirror  │   │ (未镜像) │
   │ queue A │      │ queue A │   │         │
   └─────────┘      └─────────┘   └─────────┘
        │ 宕机
        ▼
   node2 的 Mirror 自动提升为 Master ✅ 消息不丢
```

**配置**：通过 `ha-mode` 策略参数控制镜像范围：

| `ha-mode` | 含义 |
|---|---|
| **`all`** | 镜像到**所有**节点（最稳，但**同步开销最大**——节点越多写放大越严重） |
| **`exactly`** | 镜像到**指定数量**的节点（配合 `ha-params` 使用，如 `exactly` + `2`） |
| **`nodes`** | 镜像到**指定名称**的节点（配合 `ha-params` 列出节点名） |

```bash
# 示例：所有队列镜像到所有节点
rabbitmqctl set_policy ha-all "^" '{"ha-mode":"all"}'
```

### ⚠️ 镜像队列已被官方废弃（面试加分点）

**RabbitMQ 3.8 起，官方已把镜像队列标记为 deprecated，推荐用仲裁队列替代。** 原因：

| 问题 | 说明 |
|---|---|
| **脑裂风险** | 基于"同步复制 + 选主"的实现不严谨，网络分区时可能出现**双主**，导致数据分叉 |
| **同步阻塞** | 镜像同步是**同步操作**，任何一个镜像节点慢（网络抖动、磁盘慢）都会**拖慢整个队列的写入** |
| **性能开销大** | 每个消息要同步到所有镜像节点，**写放大严重**，`ha-mode=all` 时节点越多越慢 |
| **不支持新特性** | 与流（Stream）、单活消费者（Single Active Consumer）等新特性不兼容 |
| **选主不严格** | 主节点故障时，可能选出一个**数据未同步完**的镜像作为新主 → **消息丢失** |

**一句话**：镜像队列用"同步复制"实现了冗余，但**没有共识协议保证一致性**，所以在网络分区和选主场景下不可靠。

## 四、仲裁队列（Quorum Queue）—— 3.8+ 推荐

**做法**：基于 **Raft 共识协议**的复制队列，用**多数派（Quorum）**保证数据一致。

```java
// 声明仲裁队列：只需一个参数
@Bean
public Queue orderQueue() {
    return QueueBuilder.durable("order.queue")
            .withArgument("x-queue-type", "quorum")     // 关键
            .withArgument("x-quorum-initial-group-size", 3)  // 副本数，建议 3 或 5
            .build();
}
```

### Raft 带来的四个保证

| 保证 | 说明 |
|---|---|
| **强一致** | 消息写入需要**多数派**（如 3 副本中的 2 个）确认才算成功——不会出现"主说有、从说没有" |
| **自动选主** | Leader 故障后由 Raft 选举新 Leader，**只从数据最新的副本中选**，不会选出落后副本 |
| **无脑裂** | Raft 的"多数派"机制从原理上**杜绝双主**（少数派无法凑够多数票） |
| **配置简单** | 声明队列时加一个 `x-queue-type=quorum`，不需要额外的 policy |

### 为什么多数派能防脑裂

```
3 副本：node1(Leader) / node2 / node3
网络分区：node1 单独一边，node2+node3 一边

node1 想继续服务 → 需要至少 2 票 → 只有自己 1 票 → 【无法写入】❌
node2+node3 → 2 票 → 【选出新 Leader 继续服务】✅

结论：同一时刻只可能有一方能凑够多数派 → 不可能双主
```

### 仲裁队列的限制（要一起说）

| 限制 | 说明 |
|---|---|
| **只支持持久化队列** | 不能声明为非持久化 |
| **不支持 `ha-mode` 那套 policy** | 副本数靠 `x-quorum-initial-group-size` 或集群默认值 |
| **不支持部分死信/优先级特性** | 早期版本不支持优先级队列；死信支持但与经典队列行为有差异 |
| **副本数建议奇数** | 3 或 5——偶数（如 4）在容错能力上等同于少一个（4 副本容错 1，与 3 副本相同），只是浪费资源 |

## 五、三种模式对比与选型

| 维度 | 普通集群 | 镜像集群 | **仲裁队列** |
|---|---|---|---|
| 消息是否多节点备份 | ❌ 不备份 | ✅ 同步复制 | ✅ **Raft 复制** |
| 节点宕机是否丢消息 | ✅ **丢** | ⚠️ 一般情况不丢，**选主时可能丢** | ✅ **不丢**（多数派确认 + 只选最新副本） |
| 一致性 | — | 弱（无共识协议） | **强一致** |
| 脑裂风险 | — | ✅ **有** | ❌ **无**（多数派机制） |
| 自动选主 | — | ✅（但不严谨） | ✅（Raft，只选最新） |
| 写入性能 | 最高 | 低（同步阻塞、写放大） | 中（多数派确认，可接受） |
| 官方态度 | 仅提升吞吐 | **已 deprecated** | ✅ **3.8+ 推荐** |
| 配置方式 | 默认 | `ha-mode` policy | `x-queue-type=quorum` |
| 适用 | 不单独用于生产 | 存量系统 | **新项目一律用它** |

**选型结论**：

```
新项目                    → 仲裁队列（x-queue-type=quorum），副本数 3 或 5
存量系统还在用镜像队列     → 规划迁移到仲裁队列
只需要分担连接和吞吐       → 普通集群 + 仲裁队列（元信息共享，消息 Raft 复制）
```

## 六、集群之外的完整高可用

集群只解决了"Broker 节点"这一层，真正的高可用还需要：

| 层次 | 手段 | 解决的问题 |
|---|---|---|
| **节点层** | 仲裁队列（Raft 3/5 副本） | Broker 宕机不丢消息、自动选主 |
| **接入层** | **HAProxy / Nginx 负载均衡** | 客户端只连 VIP，屏蔽后端节点变化 |
| **入口层** | **Keepalived** 虚拟 IP | 负载均衡器自身的高可用 |
| **客户端** | 开启**自动重连**（`automaticRecoveryEnabled`） | 连接断开后自动恢复拓扑与订阅 |
| **存储层** | 持久化 + 磁盘冗余 | Broker 整机损坏 |

**一句话**：**RabbitMQ 的高可用 = Raft 复制（数据不丢）+ 负载均衡（访问不断）+ 客户端自动重连（连接自愈）**，三者缺一不可。

## 七、面试问答

**Q1：RabbitMQ 的高可用机制有哪些？**

主要有三种集群模式。① **普通集群**——各节点共享**交换机、队列的元信息**（不包含队列中的消息）。访问某个节点时如果队列不在该节点，会从数据所在节点把消息传过来。**致命缺点是队列所在节点宕机，队列中的消息就丢了**，所以基本不能单独用于生产。② **镜像集群**——队列的消息在多个节点间**同步备份**，主节点宕机后镜像自动提升为主，消息不丢；通过 `ha-mode` 配置范围：`all`（所有节点）、`exactly`（指定数量）、`nodes`（指定节点）。**但镜像队列官方已经不推荐了**。③ **仲裁队列（Quorum Queue）**——**RabbitMQ 3.8+ 推荐**，基于 **Raft 共识协议**，数据强一致、自动选主、配置简单（声明队列时设 `x-queue-type=quorum`）。**新项目应该直接用仲裁队列。**

**Q2：镜像队列为什么被官方废弃？**

四个原因：① **有脑裂风险**——它没有共识协议，网络分区时可能同时出现两个主节点，导致数据分叉；② **选主不严谨**——主节点故障时可能选出一个**数据还没同步完**的镜像作为新主，从而**丢消息**；③ **同步阻塞 + 写放大**——镜像同步是同步操作，任何一个镜像节点慢都会拖慢整个队列的写入，`ha-mode=all` 时节点越多越慢；④ **不支持新特性**——与流队列、单活消费者等不兼容。而仲裁队列基于 Raft，用**多数派确认**保证强一致、用**只选最新副本**保证不丢数据、从原理上杜绝脑裂，所以成为替代方案。

**Q3：仲裁队列为什么能用多数派防脑裂？**

因为它基于 **Raft**，写入必须获得**多数派**（3 副本中的 2 个）的确认。假设 3 个副本中 node1 是 Leader，发生网络分区后 node1 独自一边、node2 和 node3 在另一边：node1 想继续服务需要至少 2 票，但它只有自己 1 票，**无法写入**；而 node2+node3 有 2 票，能选出新 Leader 继续服务。**同一时刻只可能有一方凑够多数派**，所以从原理上不可能出现两个主节点同时接受写入——这就是多数派机制的价值。而镜像队列没有这层约束，两边都认为自己可以服务，就产生了双主。

**Q4：副本数设几个合适？**

**建议 3 或 5（奇数）**。因为 Raft 的容错能力是"**允许少数派故障**"：3 副本允许 1 个节点故障（剩 2 个仍是多数派），5 副本允许 2 个故障。而**偶数副本在容错能力上等同于少一个**——4 副本同样只能容错 1 个（剩 3 个，多数派需 3 票，刚好够；再坏一个剩 2 个就不够多数派了），所以 4 副本和 3 副本容错能力相同，却多消耗一个节点的资源。**奇数副本在"容错能力 / 资源成本"的性价比上最优。**

**Q5：集群就够了吗？还需要什么？**

不够。集群只解决了"Broker 节点"这一层，完整的高可用还需要三层：① **接入层**——用 HAProxy 或 Nginx 做负载均衡，客户端只连 VIP，屏蔽后端节点的变化；② **入口层**——用 Keepalived 做虚拟 IP，保证负载均衡器自身的高可用（否则 LB 成了新的单点）；③ **客户端层**——开启自动重连（`automaticRecoveryEnabled`），连接断开后自动恢复拓扑和订阅关系。再往下还有**持久化 + 磁盘冗余**应对整机损坏。一句话：**RabbitMQ 的高可用 = Raft 复制（数据不丢）+ 负载均衡（访问不断）+ 客户端自动重连（连接自愈）**。
