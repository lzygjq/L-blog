# 消息堆积与惰性队列

## 一、问题场景

凌晨告警：某队列积压 **1200 万条**消息，Broker 内存被打满，触发流控（flow control），**生产者开始被阻塞**——故障从"消费慢"升级成了"整个系统写不进去"。

**结论先行**：消息堆积的本质是 **生产速度 > 消费速度**。三种解法按"见效速度"排序：**① 加消费者（提高并行度，最直接）→ ② 消费者内开线程池（提升单机处理能力）→ ③ 惰性队列（把消息落磁盘，避免撑爆内存）**。但要强调：**惰性队列是兜底方案，不是常规方案**——它用"时效性下降"和"受限于磁盘 IO"换"能扛百万级堆积"。**真正的解法永远是提升消费速度，而不是让消息待得更久。**

## 二、堆积的成因与危害

### 为什么会堆积

| 成因 | 典型场景 |
|---|---|
| **生产突增** | 大促、批量导入、上游定时任务集中在某个点 |
| **消费变慢** | 消费逻辑里有慢 SQL、远程调用超时、依赖的下游服务变慢 |
| **消费者挂了** | 消费者进程异常退出但没人发现，消息只进不出 |
| **消息体积变大** | 单条消息从 1KB 涨到 100KB，同样的 QPS 下吞吐骤降 |
| **消费逻辑有阻塞** | 消费线程池满、`basicNack(requeue=true)` 死循环重投 |

### 堆积的危害（按严重程度）

| 危害 | 说明 |
|---|---|
| **内存打满 → 流控** | 消息默认存内存，堆积到阈值触发 **flow control**，**生产者被阻塞**——故障扩散到上游 |
| **触发页换出（paging）** | 内存不足时消息被换到磁盘，性能急剧下降，且**换出期间可能阻塞队列** |
| **消息 TTL 过期被丢** | 若队列设了 `x-message-ttl`，堆积中排在后面的消息可能**还没被消费就过期** |
| **队列被挤满产生死信** | 设了 `x-max-length` 时，**最早的消息被挤出**成为死信 |
| **下游压力反扑** | 一次性消费完堆积消息，会把积压的流量瞬间打到下游数据库——"消费雪崩" |

> **最后一条常被忽略但很致命**：堆积了 8 小时的消息，如果用加消费者"一口气"全速消费，下游数据库可能直接被压垮。**正确的做法是"限速消费"**——宁可多花时间，也别把下游打挂。

## 三、三种解法

| 方案 | 做法 | 特点 | 适用 |
|---|---|---|---|
| **① 增加消费者** | 部署更多消费者实例，提高消费并行度 | **最直接**，但受限于队列所在节点的处理能力，且成本高 | 消费能力不足、队列有多个消费者可并行 |
| **② 消费者内开线程池** | 单个消费者内部用线程池并行处理 | 提升**单机**消费速度，无需加机器 | 消费逻辑本身可并行、且不能靠加实例解决 |
| **③ 惰性队列** | 设 `x-queue-mode=lazy`，消息**直接存磁盘不进内存** | 支持**百万级堆积**，但受限于磁盘 IO、**时效性降低** | 堆积量特别大时的**兜底方案** |

> **其实还有第四种：从源头止损**——在上游限流、暂停生产、或把非核心消息临时丢弃/降级。生产事故处理时这往往是最快见效的一步。

### 加消费者为什么有时不管用

**队列的消费并行度上限受"队列所在节点"限制**——RabbitMQ 中一个队列是**单节点**结构（镜像/仲裁只是多副本，消费仍由 Master/Leader 处理）。所以：

```
队列 queue A 在 node1 上
  → 加再多消费者实例，消费能力上限还是 node1 的处理能力
  → 正确做法：把消息拆到多个队列（如按业务/租户分队列），分摊到不同节点
```

**面试加分点**：**"加消费者之前，要先确认队列是不是挤在同一个节点上"**——否则加实例只是徒增连接数。

## 四、惰性队列（Lazy Queue）

### 原理

**默认队列是"内存优先"的**：消息先进内存，只有在内存压力大时才换出到磁盘。所以堆积极易打满内存。

**惰性队列反过来——磁盘优先**：

```
普通队列                              惰性队列（x-queue-mode=lazy）
                                    
received ──▶ 内存（RAM）               received ──▶ 磁盘（直接落盘）
              │                                     │
              │ 内存不足时才换出                      │ 消费者要消费时
              ▼                                     ▼
            磁盘                                   加载到内存 → 投递给消费者
```

| 特性 | 说明 |
|---|---|
| **接收即落盘** | 消息**直接写磁盘，不驻留内存** |
| **消费时才加载** | 消费者拉取时才从磁盘读入内存，投递后即可释放 |
| **支持数百万条堆积** | 因为不占内存，堆积能力只受**磁盘容量**限制 |
| **时效性降低** | 磁盘读写的延迟远高于内存，**吞吐和延迟都变差** |
| **性能稳定** | 因为不会因内存不足触发换出，**避免了"换出抖动"导致的性能断崖** |

```java
// 声明惰性队列
@Bean
public Queue lazyQueue() {
    return QueueBuilder.durable("order.lazy.queue")
            .withArgument("x-queue-mode", "lazy")     // 关键参数
            .build();
}
```

```bash
# 也可以用 policy 批量设置（推荐——不用改代码，可动态开启）
rabbitmqctl set_policy lazy "^lazy\." '{"queue-mode":"lazy"}' --apply-to queues
```

> **`x-queue-mode` 可以动态切换**（policy 方式），但**切换过程中队列会被阻塞**（要重建内部结构），所以**不要在业务高峰期切换**。

### 惰性队列的两个代价（面试要一起说）

| 代价 | 说明 |
|---|---|
| **吞吐下降** | 每条消息都要写磁盘，正常负载下吞吐明显低于普通队列（因为普通队列大部分时候只碰内存） |
| **延迟上升** | 消费时要读磁盘，P99 延迟变高 |

**所以正确用法是"按队列区分"**：**核心的、低延迟的队列用普通模式；可能大量堆积的、对时效不敏感的队列（如报表生成、离线任务、日志归档）用惰性模式**。而不是全局开惰性。

## 五、堆积的应急处置流程

生产上遇到堆积告警，按这个顺序处理：

```
① 先止血 —— 确认消费端是不是挂了
     ├─ 消费者进程异常退出？→ 重启并修复
     └─ 消费逻辑报错死循环？→ 先停掉问题消费者，避免无效重投

② 看是不是生产突增
     ├─ 是上游异常流量？→ 上游限流 / 临时降级非核心消息
     └─ 是正常业务高峰？→ 走下面的扩容

③ 扩消费能力（按性价比）
     ├─ 队列是否挤在单节点？→ 拆队列到多节点（这才是瓶颈所在）
     ├─ 加消费者实例
     └─ 消费者内开线程池并行处理

④ 堆积量极大（百万级以上）
     └─ 开惰性队列兜底（x-queue-mode=lazy 或 policy 动态设置）
        ⚠️ 注意：切换会短暂阻塞队列，避开高峰

⑤ 消费阶段必须限速
     └─ 别一次把积压的流量全打到下游数据库——用令牌桶/批量拉取控制速率

⑥ 事后
     ├─ 死信队列 + 延迟队列做兜底重试
     └─ 加监控：队列长度、消费速率、Broker 内存、流控状态
```

**监控指标清单**（配置告警时用）：

| 指标 | 告警阈值建议 |
|---|---|
| 队列消息数（`messages_ready`） | 持续增长即告警（不设绝对值，看趋势） |
| 消费者数量（`consumers`） | 为 0 立即告警——**这是最该配的一条** |
| Broker 内存使用率 | > 70% |
| 流控状态（`blocked`） | 一旦出现即告警 |
| 死信队列长度 | > 0 即关注 |

> **"消费者数量为 0" 是最有价值的告警项**——绝大多数堆积事故的根因就是消费者挂了没人知道，而队列长度告警往往滞后很久才触发。

## 六、面试问答

**Q1：消息堆积怎么解决？**

消息堆积的本质是**生产速度大于消费速度**。三种思路：① **增加消费者**——部署更多消费者实例提高消费并行度，最直接，但要先确认队列是不是挤在同一个节点上（RabbitMQ 一个队列是单节点结构，消费上限受该节点处理能力限制，此时应该先拆队列）；② **消费者内开线程池**——单个消费者内部用线程池并行处理，提升单机消费速度；③ **惰性队列**——设置 `x-queue-mode=lazy`，消息**直接存磁盘而不占内存**，支持百万级堆积，但受限于磁盘 IO、时效性降低，**适合做兜底方案而非常规方案**。此外还要注意：**消费堆积消息时一定要限速**，否则积压的流量一次性打到下游数据库会造成二次故障。

**Q2：惰性队列的原理是什么？**

普通队列是"**内存优先**"——消息先进内存，只有内存压力大时才换出到磁盘，所以堆积极易打满内存并触发流控。惰性队列反过来是"**磁盘优先**"：① 接收到消息**直接写入磁盘，不驻留内存**；② 消费者拉取时才**从磁盘读取加载到内存**，投递后即可释放；③ 因此**堆积能力只受磁盘容量限制**，可以支持数百万条。代价是**吞吐下降、延迟上升**（磁盘 IO 远慢于内存），但换来的是**性能稳定**——不会因为内存不足触发页换出导致性能断崖。所以正确用法是**按队列区分**：核心低延迟队列用普通模式，可能大量堆积、对时效不敏感的队列（报表、离线任务、归档）用惰性模式。

**Q3：`requeue=true` 会导致堆积吗？**

会，而且会形成**恶性循环**。当消费失败时调用 `basicNack(requeue=true)`，消息会被**重新放回队头**（RabbitMQ 默认放回原位置附近）并**立即再次投递**给消费者。如果这条消息是"必然失败"的（比如数据格式错误、依赖的服务永久不可用），就会形成**消费-失败-重投-再失败**的死循环：① 消息数不减，看起来像堆积；② 消费线程被无限占用，**正常的消息也消费不了**；③ CPU 和日志被大量无效处理打满。**正确做法是 `requeue=false`**，让消息进死信队列（见[死信与延迟队列](/middleware/rabbitmq/dead-letter)），配合 Spring Retry 做**有限次**本地重试。

**Q4：为什么"加消费者"不一定管用？**

因为 **RabbitMQ 中一个队列在结构上属于单个节点**——镜像队列或仲裁队列只是把消息**复制**到多个节点做冗余，但**消费仍然由 Master（或 Leader）节点统一处理**。所以这个队列的消费并行度上限，受限于**该节点的 CPU、网络和磁盘能力**，加再多消费者实例也突破不了。真正有效的做法是**先把消息拆到多个队列**（按业务、租户或哈希分片），让它们分布在不同的节点上，再对每个队列加消费者——**瓶颈从"节点处理能力"变成了"队列数量"，才能真正水平扩展**。

**Q5：堆积时直接全速消费有什么风险？**

会造成**下游雪崩**。假设系统积压了 8 小时的消息，如果加消费者后全速消费，这些消息携带的请求会**在几分钟内同时打到下游数据库或服务上**——下游平时只承受 1 倍流量，突然要承受几十倍的峰值，很可能直接被压垮，故障从"消息堆积"升级为"数据库雪崩"。**正确做法是限速消费**：用令牌桶控制消费速率、或按批次消费并在批间加入间隔，让积压慢慢消化；同时**优先消费新消息**（避免老的堆积消息拖累实时业务），把历史堆积放到低峰期慢慢处理。
