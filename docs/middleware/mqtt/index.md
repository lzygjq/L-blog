# 物联网 MQTT

把 MQTT 放进"消息队列"板块，本身就需要一句解释——**它不是消息队列**。

MQTT（Message Queuing Telemetry Transport）是**设备接入协议**：一端是海量、弱网、可能随时掉线的设备，另一端是云上的服务。把 [RabbitMQ](/middleware/rabbitmq/) 的模型套到设备场景上会立刻失效——不是性能不够，而是**约束条件完全不同**。

## 一、为什么设备接入不能直接套消息队列 {#why-not-mq}

先看约束差异，这是理解 MQTT 一切设计的起点：

| 约束 | 服务端到服务端（RabbitMQ/Kafka） | 设备接入（MQTT） |
|---|---|---|
| **连接数** | 几十到几百个长连接 | **几十万到上亿**，每台设备一条 |
| **网络** | 内网，稳定 | 4G/WiFi/弱网，**频繁掉线重连** |
| **端点能力** | 服务器 | 单片机 / 嵌入式，**内存与电量极其有限** |
| **通信方向** | 多为单向（生产 → 消费） | **双向**：云端要能主动下发指令 |
| **协议开销** | 不敏感 | **头部多一个字节都要算**（NB-IoT 按流量计费） |
| **消息语义** | 至少要"不丢" | 要能**按业务选择**丢不丢（温度采样丢几条无所谓，开锁指令绝不能丢） |
| **寻址** | 队列 / 分区 | **主题（Topic）**，设备只关心自己订阅的那几条 |

**一句话**：消息队列的模型是"**把消息可靠地从 A 搬到 B**"，MQTT 的模型是"**让一百万个受限设备和一个云端保持联系**"。后者要解决的问题多得多。

## 二、协议核心：六个必须搞清的机制 {#protocol}

### ① 发布订阅 + 主题层级

```text
设备（Publisher）                  Broker（EMQX）                 服务（Subscriber）
   │                                    │                              │
   │  PUBLISH  robot/1001/telemetry     │                              │
   │───────────────────────────────────▶│                              │
   │                                    │  匹配订阅关系                 │
   │                                    │─────────────────────────────▶│
   │                                    │   SUBSCRIBE robot/+/telemetry
```

主题用 `/` 分层，天然适合表达设备-功能的关系：

```text
robot/{deviceId}/telemetry      设备上报遥测数据
robot/{deviceId}/command        云端下发指令
robot/{deviceId}/command/ack    设备确认指令
```

**两个通配符，用途完全不同**：

| 通配符 | 含义 | 例子 |
|---|---|---|
| `+` | 匹配**一层** | `robot/+/telemetry` → 所有设备的遥测 |
| `#` | 匹配**剩余所有层**（只能在末尾） | `robot/#` → 该前缀下的一切 |

> ⚠️ **通配符的隐藏代价**：`#` 订阅会让 Broker 把海量消息全部投给一个订阅者，**是典型的性能与安全陷阱**。生产环境要**限制通配符订阅权限**（EMQX 的 ACL 可以做到），否则一个内部服务就能把整个集群的流量拉走。

### ② QoS：三级语义，是**选择**不是"越高越好"

| QoS | 语义 | 代价 | 该用在哪 |
|---|---|---|---|
| **0** | 最多一次（发了不管） | 最低开销 | 高频遥测、可丢的采样数据 |
| **1** | **至少一次**（可能重复） | 中等 | 大多数业务数据——**注意必须自己做幂等** |
| **2** | **恰好一次**（四次握手） | 开销最大，吞吐明显下降 | 极少数场景（计费、不可重复的操作） |

**三个反直觉的结论：**

1. **QoS 2 很少值得用**。"恰好一次"要四次握手，开销大、吞吐低；而**大部分"重复"问题在业务层做幂等更划算**（这和 [消费端幂等](/middleware/#three-threads) 是同一个道理——中间件层面的"恰好一次"代价高，应用层的幂等便宜）。
2. **QoS 是逐条消息协商的**，不是连接级的——你可以让遥测用 QoS 0、指令用 QoS 1。
3. **QoS 1 保证"至少一次"，重复是特性不是 bug**。把它当成"一定送达但可能重复"，业务上必须配幂等键。

### ③ 会话：离线期间的消息怎么办

MQTT 5.0 把一个含糊的概念拆成了两个明确的参数：

| 参数 | 作用 |
|---|---|
| **Clean Start** | 连接时是否丢弃已有会话状态 |
| **Session Expiry Interval** | 会话在断开后保留多久（0 = 断开即清） |

```text
Clean Start = false + Session Expiry = 3600
   └─▶ 设备断线 1 小时内重连，能收到离线期间积累的 QoS 1/2 消息
```

**这就是"设备离线期间能不能收到指令"的答案**——靠会话保留 + Broker 缓存离线消息（QoS 0 的消息不缓存）。

> **设计要点**：**Session Expiry 要与业务期望对齐**。设太长 → Broker 要为海量离线设备长期保存消息（内存/磁盘压力）；设太短 → 设备回来时错过指令。

### ④ 保留消息（Retained）：新订阅者立刻拿到最新状态

普通消息是"发出去就走了"；**保留消息会把最后一条挂在主题上**，任何新订阅者一订阅就立刻收到。

**典型用途**：设备状态（在线/离线、当前配置）。新上线的服务不需要等下一次上报，订阅立即就能知道当前状态。**清理方式**：往该主题发一条空 payload 的保留消息。

### ⑤ 遗嘱消息（Will）：设备"死了"怎么通知

设备在连接时**预先登记**一条遗嘱。当 Broker 检测到该连接**异常断开**（不是正常 DISCONNECT），就替设备发布这条遗嘱。

```text
设备 CONNECT 时登记：topic = robot/1001/status, payload = "offline", retain = true
        │
        ├─ 正常断开 → Broker 丢弃遗嘱
        └─ 异常断开（断电/断网/崩溃）→ Broker 发布遗嘱 → 监控立刻知道设备失联
```

**这是设备在线状态监控的标准做法**——不需要应用层做心跳超时判断，Broker 帮你做了。

### ⑥ Keep Alive 与主题别名

| 机制 | 作用 |
|---|---|
| **Keep Alive** | 约定心跳间隔；Broker 在该间隔的 1.5 倍内没收到任何包就判定连接断开（触发遗嘱） |
| **主题别名（Topic Alias）** | 用一个小整数代替长主题名，**避免反复传长字符串**——省流量 |

> **Keep Alive 与流量是一对矛盾**：心跳太密耗电耗流量（NB-IoT 场景很痛），太疏则故障发现慢。**设备场景通常按"最坏网络条件下的容忍时延"来定**，而不是按"想多快知道"。

### MQTT 5.0 相比 3.1.1 的增强

| 增强 | 价值 |
|---|---|
| **原因码（Reason Code）** | 3.1.1 报错信息含糊；5.0 每次操作都有明确原因码，排障容易得多 |
| **共享订阅** | 同组订阅者**分摊**消息（见第五节）——后端水平扩展的关键 |
| **用户属性** | 可以随消息带自定义键值（类似 HTTP Header），**不改 payload 就能传元数据** |
| **请求/响应（Response Topic）** | 支持标准的"请求-应答"语义，不用自己约定主题 |
| **流控与消息过期** | 服务端可以给客户端发配额；消息可以带过期时间 |
| **增强认证** | 支持多轮质询-应答，可以对接更复杂的认证流程 |

## 三、Broker 选型与 EMQX 架构 {#broker}

| Broker | 定位 | 说明 |
|---|---|---|
| **EMQX** | 云上大规模集群 | Erlang/OTP 写的；官方宣称单节点 400 万连接、集群上亿连接 |
| **Mosquitto** | 轻量、单机 | 单节点约十几万连接级，**无原生集群**；适合边缘/小规模 |
| **NanoMQ** | 边缘网关 | 资源受限的边缘端 |

### EMQX 5.x 的 Core + Replicant 架构

**这是它和 4.x 最本质的差别**，也是能撑起百万级连接的原因：

```text
        4.x：全互联集群（Full Mesh）
        ┌───────────────────────────────┐
        │  每个节点都保存全量数据副本     │
        │  节点数 N → 复制开销 O(N²)     │
        │  → 规模一上去就撑不住          │
        └───────────────────────────────┘
                       ↓ 5.x 改为
        ┌───────────────────────────────────────────┐
        │        Mria + RLOG 架构                    │
        │  ┌─────────────────┐   ┌────────────────┐ │
        │  │  Core 节点       │   │ Replicant 节点  │ │
        │  │ 处理写、持有全量  │──▶│ 只读、异步复制   │ │
        │  │ 集群状态（权威）  │RLOG│ 承载大量连接     │ │
        │  └─────────────────┘   └────────────────┘ │
        │  扩连接 = 加 Replicant，不参与写共识        │
        │  → 打破 O(N²) 的扩展瓶颈                   │
        └───────────────────────────────────────────┘
```

**关键点：Replicant 节点不参与写共识**，只承载连接与转发。所以**扩连接容量 = 加 Replicant**，成本接近线性。这是它能宣称亿级连接的结构性原因。

其他生产特性：**无主集群**（节点对等，无单点）、**自动发现**（手动/static/DNS/etcd/**Kubernetes**）、**滚动升级不中断**。

### ⚠️ 版本与许可：选型时必须核对

| 版本线 | 状态 | 说明 |
|---|---|---|
| **5.8.x** | **LTS** | 支持到 **2027-08-27**，求稳选这个 |
| 5.9 / 5.10 | 功能版本 | 18 个月支持周期 |
| **6.0 / 6.1 / 6.2** | **6.x 已 GA** | 6.0（2025-09-30）、6.1（2025-12-30）、**6.2（2026-03-31）为最新功能版本** |

> ⚠️ **许可变化必须提前确认**：**自 EMQX 5.9.0 起，EMQX 采用 BSL 1.1（商业源代码许可）发布**。社区用户仍可使用，源码会在指定变更日期后转为完全开源许可（如 Apache 2.0）；**商业客户可购买许可获得高级功能与支持**。**如果你的项目对许可敏感，要在选型阶段就把这条确认清楚，别等到上线前才发现。**

**协议与能力覆盖**：MQTT 3.1/3.1.1/5.0、**MQTT over QUIC**（EMQX 是这条路线的推动者，多路复用 + 连接迁移，适合弱网）、WebSocket、以及 MQTT-SN / CoAP / LwM2M / STOMP 等网关。

## 四、认证与安全 {#security}

设备安全的难点在于：**设备会被物理接触、固件可被提取、没有浏览器那套信任基础设施**。

| 层次 | 做法 | 说明 |
|---|---|---|
| **传输加密** | TLS / **mTLS（双向证书）** | mTLS 是设备侧最可靠的方案：**一机一证**，证书即身份 |
| **认证** | 用户名密码 / **JWT** / MQTT 5.0 **增强认证** | 后端可对接 file / Redis / MySQL / PostgreSQL / MongoDB |
| **授权（ACL）** | 按主题与操作授权 | **必须限制设备只能订阅/发布自己的主题**，禁止通配符订阅 |
| **异常防护** | flapping 检测 + 黑名单 | 防止设备疯狂重连打爆 Broker；可按 IP / clientId / username 拉黑 |

**ACL 设计是设备安全的核心**。一个典型的授权规则：

```text
设备 1001 只允许：
  PUBLISH   robot/1001/telemetry
  PUBLISH   robot/1001/command/ack
  SUBSCRIBE robot/1001/command
  （拒绝一切通配符订阅、拒绝其他设备的主题）
```

> **没有 ACL 的 MQTT 集群等于公开的广播电台**：任何设备都能订阅 `#` 拿到全部数据、并向别人的主题发指令。**ACL 不是可选项。**

## 五、主题设计与共享订阅 {#topic-design}

### 命名规范的三条原则

| 原则 | 说明 |
|---|---|
| **从左到右由粗到细** | `robot/{deviceId}/telemetry`，便于用 `+` 做层级匹配与 ACL 授权 |
| **不在主题里放业务状态** | 主题是**寻址**，不是数据。状态放 payload，否则主题数量会爆炸 |
| **避免用设备自报的 ID 直接做主题层级** | 设备自报 ID 可伪造 → 必须与 ACL 的授权身份做绑定校验 |

### 共享订阅：后端水平扩展的关键

**问题**：如果 3 个服务实例都订阅 `robot/+/telemetry`，默认语义是**每个实例都收到全部消息**（广播）。但通常你要的是**分摊**。

**共享订阅**（MQTT 5.0 特性，EMQX 等 broker 也支持）解决这个：

```text
                     ┌────────────────────────┐
   robot/+/telemetry │  $share/group1/robot/+/telemetry
        │            └───────────┬────────────┘
        ▼                        ▼
   ┌─────────┐            ┌──────────────────────────┐
   │  Broker  │───────────▶│  $share/group1/... 的消息 │
   └─────────┘            │  只会被【组内一个实例】收到 │
                          └──────────────────────────┘
                                 ├──▶ 服务实例 A
                                 ├──▶ 服务实例 B   ← 负载分摊
                                 └──▶ 服务实例 C
```

**这一条的意义和 [Kafka 的消费者组](/middleware/kafka/) 完全一样**：让消费端可以水平扩展而不是各自拿到全量数据。

### 一个典型的主题结构

```text
robot/{deviceId}/telemetry             设备 → 云：遥测上报（QoS 0/1）
robot/{deviceId}/event                 设备 → 云：事件（告警、状态变更）
robot/{deviceId}/command               云 → 设备：指令下发（QoS 1，retain=false）
robot/{deviceId}/command/ack           设备 → 云：指令执行确认
robot/{deviceId}/status                设备 → 云：在线状态（**retain=true**，遗嘱也发这里）
robot/{deviceId}/config                云 → 设备：配置下发（**retain=true**）
```

**注意 `status` 与 `config` 用 retain**：新订阅者立刻拿到最新状态与配置，不用等下一次变化——这是保留消息的典型用法。

## 六、与消息队列的桥接：边缘到云端 {#bridge}

MQTT 解决的是**接入**，不是**后端处理**。真实系统通常是"MQTT 接入 + 传统 MQ 处理"：

```text
海量设备
   │  MQTT（QoS 1）
   ▼
┌──────────────┐   规则引擎 / 数据桥接   ┌──────────────┐
│ MQTT Broker  │────（SQL 过滤、转换）──▶│ Kafka        │
│  (EMQX)      │                        │ RabbitMQ     │
│              │                        │ MySQL/TDengine│
└──────────────┘                        │ HTTP Webhook  │
                                        └──────────────┘
```

EMQX 内置**基于 SQL 的规则引擎**：用一条 SQL 匹配主题与 payload，把结果转发到 Kafka、PostgreSQL、MySQL、MongoDB、Redis、时序库、HTTP 等**四十多种目标**。

> **这个架构定位很清楚**：**MQTT Broker 只做"接入 + 就近处理"**，重业务逻辑交给后端服务。把复杂业务塞进规则引擎，会让边缘配置变成不可测试、不可版本控制的"藏起来的代码"——**规则引擎适合做过滤、转换、路由，不适合承载业务规则。**

## 七、机器人 / 设备场景的落地要点 {#device-scenario}

结合"设备接入 + 云端指令"这类场景，几个必须提前设计的点：

| 要点 | 设计 |
|---|---|
| **弱网重连** | 客户端要**指数退避重连**（固定间隔重连会在网络恢复瞬间形成惊群，把 Broker 打爆）；服务端配 flapping 检测 |
| **指令幂等** | 云端下发指令必须带**指令 ID**，设备侧去重——**网络抖动会让 QoS 1 的指令重复到达**（和 [消费端幂等](/middleware/#three-threads) 同源） |
| **指令超时** | 下发后等 ack 要有超时，超时后**重发还是放弃要业务定**；不能无限等 |
| **离线指令** | 靠会话保留（Session Expiry）+ QoS ≥ 1；**要评估 Broker 存储压力** |
| **设备影子（Shadow）** | 云端保存设备期望状态与最新上报状态，设备上线后**只同步差异**，而不是重放全部历史指令 |
| **OTA 升级** | 大文件**不要走 MQTT**——MQTT 推一个带 URL 的指令，设备自己去 HTTPS 下载。走 MQTT 传固件会拖垮 Broker |
| **时钟不可靠** | 设备时钟可能不准，**不要用设备上报的时间做业务判断**，以服务端接收时间为准 |
| **单向不可信** | 设备上报的数据要校验范围与合法性；**设备身份由证书/ACL 保证，不靠 payload 里自报的 ID** |
| **状态一致性** | 用 retain + 遗嘱维护"设备在线状态"，但要注意"**遗嘱有延迟**"（要靠 Keep Alive 判定），别把它当成实时心跳用 |

## 八、常见坑 {#pitfalls}

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 把 MQTT 当消息队列用（指望消费组、回溯、堆积） | MQTT 是**设备接入协议**；后端处理仍要 Kafka/RabbitMQ 承接 |
| 2 | 无脑用 QoS 2 | 四次握手开销大、吞吐低；**大部分场景 QoS 1 + 业务幂等更划算** |
| 3 | 以为 QoS 1 不会重复 | QoS 1 = "**至少一次**"，重复是特性，设备/消费端必须幂等 |
| 4 | 没有 ACL，或允许通配符订阅 | `#` 订阅等于把全集群数据广播给自己；**ACL 是必选项** |
| 5 | 设备 ID 直接用 payload 里自报的值 | 身份必须由**证书/ACL 绑定**，自报 ID 可伪造 → 越权 |
| 6 | 忽略 EMQX 5.9 起的 BSL 许可 | 选型阶段就确认许可与商业授权范围 |
| 7 | 固定间隔重连 | 网络恢复瞬间会形成**惊群**打爆 Broker；用**指数退避 + 抖动** |
| 8 | Session Expiry 设得过长或过短 | 太长 → Broker 长期为海量离线设备存消息；太短 → 设备回来错过指令 |
| 9 | 用 MQTT 传固件/大文件 | 只推 URL，设备自己走 HTTPS 下载 |
| 10 | 把遗嘱当实时在线状态 | 遗嘱靠 Keep Alive 判定，**有延迟**；实时性要求高要自己做心跳 |
| 11 | 大量主题（每设备多主题）不做规划 | 主题数量爆炸会拖慢路由匹配；**保持层级规范、避免把状态写进主题** |
| 12 | 把业务规则塞进规则引擎 | 规则引擎适合过滤/转换/路由；业务逻辑放后端代码（可测试、可版本控制） |
| 13 | 单节点部署就上生产 | 无集群则单点故障会导致**全部设备失联**；用 Core-Replicant 或至少多节点 |
| 14 | 靠设备时钟做业务判断 | 设备时钟不可靠，以**服务端接收时间**为准 |

## 九、高频问答 {#interview}

| 问题 | 一句话答案 |
|---|---|
| MQTT 是消息队列吗？ | **不是**。它是设备接入协议：解决海量受限设备、弱网双向通信；后端处理仍需要 Kafka/RabbitMQ |
| MQTT 的 QoS 三级分别是什么？ | 0 = 最多一次（可丢）；1 = **至少一次**（可能重复）；2 = 恰好一次（四次握手，开销大） |
| 为什么 QoS 2 很少用？ | 握手开销大、吞吐明显下降；**大多数"重复"问题在业务层做幂等更划算** |
| QoS 1 会不会重复？ | 会。它保证的是"至少一次"，**重复是特性**——消费端/设备端必须幂等 |
| `+` 和 `#` 的区别？ | `+` 匹配一层，`#` 匹配剩余所有层（只能在末尾）。`#` 订阅是性能与安全陷阱，生产必须限制 |
| 设备离线期间的指令怎么办？ | 靠**会话保留**（`Clean Start=false` + `Session Expiry Interval`）+ QoS ≥ 1 的离线消息缓存；QoS 0 不缓存 |
| 保留消息和普通消息的区别？ | 保留消息会把**最后一条挂在主题上**，新订阅者一订阅立刻收到；适合设备状态与配置下发 |
| 遗嘱消息用在哪？ | **设备异常断开的通知**：连接时登记，Broker 检测到异常断开后替设备发布——在线状态监控的标准做法 |
| 共享订阅解决什么？ | 让多个后端实例**分摊**消息，而不是各自收到全量——等价于 Kafka 的消费者组 |
| EMQX 5.x 为什么能撑百万连接？ | **Core + Replicant（Mria + RLOG）**：Replicant 只承载连接、不参与写共识，扩连接不引起 O(N²) 复制开销 |
| EMQX 的许可有什么变化？ | **5.9.0 起改用 BSL 1.1**；社区可用，商业功能与支持需授权——选型时必须确认 |
| MQTT 安全的核心是什么？ | **mTLS 一机一证 + ACL 按主题授权**。没有 ACL 的集群等于公开广播电台 |
| 设备重连该怎么设计？ | **指数退避 + 抖动**；固定间隔会在网络恢复瞬间形成惊群打爆 Broker |
| 为什么设备身份不能看 payload 里的 ID？ | 可伪造 → 能冒充别的设备下发指令；身份必须由证书/ACL 绑定 |
| OTA 升级消息怎么发？ | MQTT **只推 URL**，固件走 HTTPS 下载；用 MQTT 传大文件会拖垮 Broker |
| 设备影子是什么？ | 云端保存"期望状态 + 最新上报状态"，设备上线只同步差异——避免重放全部历史指令 |
| MQTT 和 Kafka/RabbitMQ 怎么协作？ | MQTT 负责**边缘接入**，通过规则引擎/数据桥接把消息转发到 Kafka/RabbitMQ 做后端处理 |
